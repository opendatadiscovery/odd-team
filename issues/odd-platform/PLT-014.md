## What

Three operator-visible defects on the AlertManager webhook ingestion path, all on the same handler chain. The auth posture is **already documented** at `docs.opendatadiscovery.org/features/active-platform-features/alerting` (per WebFetch 2026-05-27) - *"The AlertManager webhook endpoint is not authenticated. ODD Platform whitelists the entire `/ingestion/**` namespace in Spring Security ... it does not cover `/ingestion/alert/alertmanager`."* The defects below are the **operator-visible consequences** of that posture, none of which are surfaced today.

**Defect 1 - Forge-and-display compound. HOLDS - driven on the running stack.** `AlertServiceImpl.handleExternalAlerts` (`:178`) maps the webhook payload's `labels.entity_oddrn` directly to `AlertPojo.dataEntityOddrn` with NO validation beyond the DB FK and NO check that the caller has permission to alert that entity. Combined with the cross-owner read on the platform-wide "All" alerts tab (PLT-121), any caller with network reach (anonymous under `auth.type=DISABLED` - the default - and under OAUTH2/LDAP via the `/ingestion/**` whitelist; BLOCKED only under LOGIN_FORM; see PLT-003) can POST a forged `entity_oddrn` and inject an OPEN Distribution Anomaly alert against any **existing** entity. The forged alert surfaces on the All tab readable by every authenticated user - indistinguishable from real. DRIVEN 2026-06-07..06-10 (`integration-tests/protocols/IT-115-alertmanager-webhook-ungated.md`): anonymous POST -> 200, one OPEN DA row on an unowned entity; a non-existent oddrn -> 400 USR003 (the `alert.data_entity_oddrn` FK requires a real entity, so the forge needs a guessable real ODDRN).

**Defect 2 - Generator URL "stored XSS in the alerts UI" - FALSIFIED. Re-scoped to the Slack path only.** It is true that `generatorURL` is parsed via `UriComponentsBuilder.fromUri(...)` which does NOT block `javascript:` (verified 2026-06-10 by rendering `UriComponentsBuilder.fromUri(URI.create("javascript:alert(1)"))...toString()` -> `javascript:?g0.moment_input=...`), and that the raw string is stored into the chunk description via `String.format("Distribution Anomaly. URL: %s", queryUrl)` (`AlertServiceImpl.java:168,185`). **But it does not render as XSS or a link in the web UI:** the alerts UI renders `alertChunk.description` as plain, React-escaped text inside a `<Typography>` - `AlertItem.tsx:184-186` and `DataEntityAlertItem.tsx:137-139` (verified by FE trace 2026-06-10) - no Markdown, no `dangerouslySetInnerHTML`, no `<a href>`, no `grep` hit for `Markdown` in the alerts components. So a `javascript:` or attacker URL appears as inert literal text; there is no script execution and no clickable open-redirect on the web surface. The only renderer that interprets this untrusted text is the **Slack notification** mrkdwn path, which is exactly **PLT-015** (and even there it is mrkdwn injection, not JS execution). The web-UI XSS claim is dropped; the residue is "untrusted URL stored verbatim and forwarded to Slack unescaped" -> tracked by PLT-015.

**Defect 3 - "No idempotency -> Prometheus retries duplicate alerts" - FALSIFIED.** `ReactiveAlertRepositoryImpl.createAlerts` (`:324-343`) does issue `INSERT ... RETURNING` with no `ON CONFLICT` clause - true. But the `alert` table carries a **partial unique index** `alert_unique_messenger_oddrn_is_missing ON alert (data_entity_oddrn, type) WHERE messenger_entity_oddrn IS NULL AND status = 1` (`V0_0_61__introduce_stacked_alerts.sql:78`). External DA alerts have `messenger_entity_oddrn = NULL` (handleExternalAlerts never sets it), `type = 4` (DISTRIBUTION_ANOMALY), `status = 1` (OPEN) - so the index **applies**. A retry that re-POSTs the same entity while its prior alert is still OPEN therefore hits the index -> `DataAccessException` C23 -> `UniqueConstraintException` -> **HTTP 400 USR003** (verified: `JooqReactiveOperations.java:41,48` `onErrorMap(... ExceptionUtils::translateDatabaseException)`; `ExceptionUtils.java:30-32` + `:73` -> "Term/.../Database constraint violation"). No duplicate row is created. The IT-115 protocol's "clear prior alerts (idempotency)" preamble exists precisely because a second POST otherwise collides. So operators do NOT see N-times-duplicated alerts; the real residue is the OPPOSITE: the missing `ON CONFLICT` makes the insert ERROR instead of degrading gracefully, and because `createAlerts` builds one multi-row INSERT in a transaction (`:330-341`), a single webhook batch that contains any already-OPEN `(entity, DA)` pair fails the WHOLE batch (the other alerts in it are lost). Severity of this residue is operational, not duplication.

## User-facing impact

- WHO: an unauthenticated network caller (Defect 1); operators reading the Alerts UI are the victims.
- WHAT they do: POST a forged AlertManager payload (real `entity_oddrn`, no credential) to `/ingestion/alert/alertmanager`.
- WHAT they observably get (Defect 1, verified by FE/BE trace + driven IT-115 2026-06-10): a 200 and one OPEN DISTRIBUTION_ANOMALY alert attributed to an unowned entity, visible to every authenticated user on the platform-wide All tab (`AlertServiceImpl.listAll` -> `AlertItem.tsx:136,184-186`), indistinguishable from a real alert.
- What they do NOT get (verified, FALSIFIED claims): (Defect 2) no XSS or clickable link from `generatorURL` - the alerts UI prints the chunk description as React-escaped plain text (`AlertItem.tsx:184-186`, `DataEntityAlertItem.tsx:137-139`); a `javascript:` URL shows as inert text. (Defect 3) no duplicate alert rows on retry - the partial unique index makes the retry 400 instead (`V0_0_61:78`; `ExceptionUtils.java:73`).
- Real residue beyond Defect 1: the same untrusted `generatorURL`/description IS rendered as interpreted mrkdwn in the Slack notification (PLT-015 - static trace; not driven here), and a retry/duplicate webhook batch fails wholesale with 400 instead of degrading (operational, not a duplication or security issue).

## Why it matters

The AlertManager webhook is the operator's interface for *"forward Prometheus alerts into ODD Platform so they show up next to data quality alerts."* The intent is reasonable; **Defect 1 alone** makes it a hostile-input surface that ships with no operator-visible hardening guidance.

Severity stays HIGH - but on **Defect 1 alone**:
- Defect 1 enables **cross-tenant alert injection without authentication** in the default (DISABLED) deployment and under OAUTH2/LDAP (PLT-003) - DRIVEN, not theoretical (IT-115). The default Kubernetes/Compose deployments expose this through the same ingress as the rest of the platform.
- Defect 2's web-UI XSS rationale is withdrawn (escaped plain-text render); the only injection surface is the Slack path = PLT-015.
- Defect 3's duplication rationale is withdrawn (DB unique index blocks it); the residue is graceful-degradation, not noise amplification.

This is the case-law class of LSN-001 / LSN-002 (operators following our guide off a cliff) for Defect 1; LSN-031 (a UI claim shipped without reading the frontend) for the two falsified defects.

## Suggested fix

Three coordinated fixes, one PR per fix is fine but they share a test-fixture surface so one combined PR is reasonable:

### Defect 1 fix

Two options:

**Option A (recommended for unauthenticated remote ingestion)** - add a shared-secret check via `X-API-Key` or `Authorization`:

```java
@PostMapping(path = "ingestion/alert/alertmanager")
public Mono<Void> handleAlertManager(
    @RequestHeader("X-AlertManager-Token") String token,
    @RequestBody AlertManagerWebhookRequest req
) {
    return alertManagerAuthService.validate(token)
        .then(alertService.handleExternalAlerts(req.getAlerts()));
}
```

The token is operator-configured at deployment (`alertmanager.webhook.token` config key); AlertManager's `http_config.bearer_token` field carries it.

**Option B (alternative - network-edge guard)** - leave the handler unauthenticated but document explicitly that operators MUST front the path with an ingress / proxy ACL. Less robust; relies on deployment discipline.

Recommend Option A - shared-secret is a 20-line change and removes the network-discipline dependency.

### Defect 1 fix - entity_oddrn validation (mandatory regardless of auth fix)

```java
// AlertServiceImpl.handleExternalAlerts - validate before INSERT
return dataEntityRepository.existsByOddrn(entityOddrn)
    .flatMap(exists -> exists
        ? alertRepository.createAlerts(alertPojos)
        : Mono.error(new InvalidEntityOddrnException(entityOddrn))
    );
```

### Defect 2 fix (re-scoped)

The alerts UI already renders the description as escaped plain text, so there is NO web-UI XSS to fix. The remaining hardening is defensive only:
- Optional: scheme allow-list at ingestion so a `javascript:`/`data:` `generatorURL` is rejected before storage (`UriComponentsBuilder.fromUri` does not block it):

```java
final URI gen = externalAlert.getGeneratorURL();
if (gen != null && !Set.of("http", "https").contains(gen.getScheme())) {
    throw new BadUserRequestException("Unsupported generatorURL scheme");
}
```
- The mrkdwn-escaping of the description before Slack delivery is **PLT-015** (the real injection surface). Coordinate the fix there, not here.

### Defect 3 fix (re-scoped)

There is no duplication to fix - the partial unique index `alert_unique_messenger_oddrn_is_missing` already prevents a duplicate OPEN DA alert. The defensible change is graceful degradation so a retry/duplicate webhook does not 400 (and a multi-alert batch is not lost wholesale): make `createAlerts` tolerate the existing index with `ON CONFLICT DO NOTHING` keyed on the index that already exists, rather than inventing a new constraint:

```java
// ReactiveAlertRepositoryImpl.createAlerts - target the EXISTING partial index
context.insertInto(ALERT, ...)
    .onConflict(ALERT.DATA_ENTITY_ODDRN, ALERT.TYPE)   // matches alert_unique_messenger_oddrn_is_missing
    .where(ALERT.MESSENGER_ENTITY_ODDRN.isNull().and(ALERT.STATUS.eq(OPEN)))
    .doNothing()
    .returning(...)
```

NB: the draft's earlier proposal added a NEW `UNIQUE (data_entity_oddrn, type, status, external_id)` constraint sourced from `labels.fingerprint`. **There is no `external_id` column on `alert` (migrations verified) and `ExternalAlert` does not parse `fingerprint` (only `labels`, `generatorURL`, `startsAt`)** - that fix as written would not compile. Use the existing index above.

## How discovered

Surfaced during the Mode B run of `docs/coverage/undocumented-features` on 2026-05-27 (substrate `F-007` - AlertManager Integration). Primary-source re-verified this run at `AlertManagerController.java:1-25` per scanner-feed log `code_verification_targets`.

**Corrected 2026-06-10 (user-facing verification sweep):**
- Defect 1 HOLDS and is driven (IT-115). Auth-mode nuance refined per PLT-003 (anonymous under DISABLED/OAUTH2/LDAP; blocked under LOGIN_FORM) - was "any authenticated user otherwise".
- Defect 2 was "stored XSS in the alerts UI"; actually the alerts UI renders the chunk description as React-escaped plain text (`AlertItem.tsx:184-186`, `DataEntityAlertItem.tsx:137-139`) - no XSS, no link. Real residue is the Slack mrkdwn path (PLT-015). The `UriComponentsBuilder` not-blocking-`javascript:` fact is real but inert on the web surface.
- Defect 3 was "Prometheus retries -> duplicate alert rows in the UI"; actually the partial unique index `alert_unique_messenger_oddrn_is_missing` (`V0_0_61:78`) blocks a duplicate OPEN DA alert -> the retry 400s (USR003) instead. Real residue is graceful-degradation + wholesale-batch-failure, not duplication. The previously-proposed `external_id`/`fingerprint` natural key does not exist in the schema or DTO.
