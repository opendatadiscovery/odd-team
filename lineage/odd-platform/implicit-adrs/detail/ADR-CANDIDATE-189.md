**Decision statement**: The platform-api HTTP contract is governed by a TWO-FILE OpenAPI 3.0.3 source-of-truth pair: `odd-platform-specification/openapi.yaml` (4212 lines — 194 operations across 35 tags under `/api/**`) + `components.yaml` (2937 lines — ~250 schemas, referenced 487 times). The spec is the authoritative declaration of HTTP method / path / request-body / response-body shape; controllers `@Override` methods inherited from generated `*Api` interfaces and never carry their own `@RequestMapping`. The architectural commitments are FOUR:

1. **OpenAPI is the path/method/shape source of truth.** Every `/api/**` endpoint is declared in `openapi.yaml`; controllers `implement *Api` and inherit routing from the generated interface. Adding or changing a route is therefore an `openapi.yaml` + regenerate flow, not a controller-edit flow. The pattern is observed at 19+ enriched controller sidecars (the strongest single architectural pattern in the catalog per ADR-CANDIDATE-001's enumeration); THIS ADR anchors the SPEC SIDE of the same pattern.

2. **One spec file per audience.** Platform-api (the UI/API consumer contract) lives in this repo's `odd-platform-specification/openapi.yaml`. Ingestion-api (the producer wire contract) lives in the separate `opendatadiscovery-specification` repo. The dual-spec architecture is the deliberate separation between "operators integrating consumers" and "operators integrating producers" — each consumer-facing surface gets its own SDK generator, its own Swagger UI tab, its own version cadence. Per the live api-reference page WebFetched 2026-05-20: "The two definitions in Swagger UI are: ingestion-api: describes all ingestion endpoints and platform-api: describes all endpoints for the ODD platform."

3. **Schemas live in a sibling file, not inline.** The 487 `$ref: './components.yaml/#/components/schemas/...'` invocations from `openapi.yaml` against `components.yaml` is the deliberate authoring convention. Inline schemas were rejected — the two-file split enables schema reuse across operations, reduces the path-section scrolling cost, and concentrates the data-model change surface in one file.

4. **Tag-based grouping is the domain-partitioning convention.** The 35 tags partition 194 operations along feature boundaries (`dataEntity` is the largest with 45+ ops; single-operation tags like `genai`, `links`, `identity`, `feature`, `title`, `metadata` reflect very-narrow features). The tag is the routing primitive for both Swagger UI's left-nav AND for OpenAPI Generator's per-tag controller interface generation. Adding a new feature surface is "add a tag + author operations under it" — the generator does the rest.

The architectural pair (ADR-CANDIDATE-001 controller-side + ADR-CANDIDATE-189 spec-side) is the canonical "contract-first" stance the platform implements. The CONSEQUENCE: any non-spec-driven change to a `/api/**` endpoint (a hand-rolled `@PostMapping` on a controller, a path-string typo in SECURITY_RULES that doesn't match the spec, a status-code drift between spec and impl, a missing field on a request DTO) is structurally caught by the spec as the central reference — and the absence of contract-conformance tests is exactly why DRIFT does accumulate (per the openapi.yaml sidecar's `bugs_limitations_corner_cases[2]` — status-code drift at 9+ endpoint-level instances; per REFACTOR-217 — SecurityConstants path-string drift; per DOC-GAP-099 — inverse-semantic / missing-field / operationId-misnamed).

**Wisdom test**: PASS on all three questions.
1. **Intentional?** YES — four independent commitments:
   - The 19+ controller sidecars uniformly applying `@Override` on generated interfaces (the strongest single pattern in the catalog).
   - The dual-repo split (platform-spec here vs ingestion-spec separate) — deliberate audience separation.
   - The two-file schema split + 487-fold reuse — deliberate authoring discipline.
   - The 35-tag partitioning — deliberate feature-boundary architecture.
2. **Structural impact?** YES — every future `/api/**` endpoint must be declared here first; every controller change must propagate from spec; every drift between spec and impl IS a finding (per REFACTOR-217 silent-authz-bypass, per the 9+ status-code instances). The CONTRACT-FIRST stance binds the entire platform-api surface.
3. **Refactoring or structural?** STRUCTURAL — moving away from contract-first would require rewriting every controller to declare its own routing, abandoning the generated interfaces, and rebuilding the SDK / UI client. Not a refactor.

**Existing ADR**: none in `adrs/`. Composes deeply with ADR-CANDIDATE-001 (OpenAPI-generated controller interfaces — the controller-side mirror), ADR-CANDIDATE-027 (ingestion-endpoint auth trust gradient — references separately the ingestion-spec sibling), ADR-CANDIDATE-061 (ingestion controller-side semantic validation — the schema-vs-code-validation split).
