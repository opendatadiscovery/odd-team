## What

Two operator-visible defects on the Lookup Tables surface. Both are independent fixes (one UI, one backend) but ship in this single PLT to bound the upstream conversation around the page.

**Defect 1 - Lookup Tables listing silently truncates at 30 rows (one-line DOM-id mismatch).** `LookupTablesList.tsx:51` declares `<ScrollableContainer container id='lookup-tables-list' $offsetY={165}>`. Line 53 declares `<InfiniteScroll scrollableTarget='directory-entities-list'>` - the `scrollableTarget` references the Directory feature's DOM id (`Directory/Entities/EntitiesList/EntitiesList.tsx:45,47` - the copy-paste source), NOT the local container id. Verified against the vendored `react-infinite-scroll-component` source: a string target resolves via `document.getElementById` (`dist/index.js:214-215`), and a null result silently falls back to `window` (`dist/index.js:326-329`, `this.el = ... this._scrollableNode || window`). The actual scrolling happens INSIDE `ScrollableContainer` (fixed height `calc(100vh - toolbar - 165px)` + `overflow: auto`, `shared/styled-components/scrollable-container.ts:8-9`), so the page body is laid out to fit the viewport and the scroll events that drive the list never reach the window listener. `next` (= `fetchNextPage`, `:55`) is never invoked; the 31st row is never requested. The list APPEARS complete: the loader renders only when a fetch is in flight or the list is empty (`dist/index.js:441-445`), so with 30 rows and no scroll events there is no skeleton, no "Load more" affordance, no pagination indicator. The H1 counter at `LookupTables.tsx:60-62` (`<NumberFormatted value={facets?.total} />`) comes from a DIFFERENT endpoint - the reference-data search facets, whose `total` is the real match count (`LookupDataSearchServiceImpl.java:63-67`, `tableRepository.countByState`) - so it shows e.g. "250 lookup tables overall" above a 30-row list; that discrepancy IS the only operator-visible signal, and most won't notice. Per `system-mission.md:125-141` pillar P-03 Master Data Management is intentionally narrow (Lookup Tables is the SOLE child surface today); the listing bug means 100% of P-03's user-facing UX is degraded for any tenant exceeding 30 tables. Highest operator-volume impact in batch-5.

**Defect 2 - Lookup Table rename emits no ActivityEvent.** `ReferenceDataServiceImpl.updateLookupTable` (lines 107-124) has no `@ActivityLog` annotation (re-verified 2026-06-10: no activity import anywhere in the file - none of the lookup-table mutations emit); and the `lookup_tables` table carries no author/version columns at all - only `created_at`/`updated_at` timestamps (`V0_0_86__create_schema_and_tables_for_custom_tables.sql:1-14`), so "who renamed it" is recorded nowhere. The `ActivityEventTypeDto` enum (27 values, re-verified) has no `LOOKUP_TABLE_RENAMED` slot - would become a 28th value if added. The physical rename chain is real: when the computed `tableName` changes, `ReferenceDataRepositoryImpl.updateLookupTable` (`:180-202`) issues `ALTER TABLE ... RENAME TO` plus sequence + constraint renames (`:191-200`). Combined with the documented LSN-001-class ALTER-TABLE rename hazard (DOC-182 Caveat 3 - UI rename issues `ALTER TABLE ... RENAME TO` against the documented public `lookup_tables_schema` PostgreSQL surface, silently breaking downstream BI/ETL pipelines), the audit silence amplifies the blast radius: post-mortem investigations on a downstream pipeline break cannot answer "who renamed which table when" from platform logs. Cross-pillar audit-asymmetry pattern: same shape as F-057 (DQ severity audit silence) and F-025a.4 (Query Examples audit silence on DOC-183 Caveat 4) - third operator-mutating surface with no audit emission.

## User-facing impact

- **Defect 1 (static trace consistent - FE + vendored library source 2026-06-10; NOT driven):** the mechanism is code-settled - `scrollableTarget='directory-entities-list'` does not exist on this page, so `getElementById` returns null and the scroll listener falls back to `window` (`dist/index.js:214-215, 326-329`) while the rows scroll inside the fixed-height `overflow: auto` container (`scrollable-container.ts:8-9`), and the loader renders only mid-fetch (`dist/index.js:441-445`). The resulting observable - an operator with >30 lookup tables sees the first 30 rows, a header counting the true total (e.g. "250 lookup tables overall", `LookupTables.tsx:60-62`), and no loading affordance - is data-dependent (needs >30 tables) and layout-runtime, so it stays unflagged. Remaining check: load Master Data -> Lookup Tables on a stack with >30 tables and confirm the list stops at 30 while the header reads the full count.
- **Defect 2 (verified by BE trace 2026-06-10):** after a rename breaks a downstream consumer of the public `lookup_tables_schema` PostgreSQL surface, the operator's question "who renamed which table when" has NO answer anywhere in the platform: the Activity feed never received an event (no `@ActivityLog` on any lookup-table mutation), and the `lookup_tables` row stores no author - only an `updated_at` timestamp (`V0_0_86`). The only recourse is PostgreSQL-side audit tooling, if the operator happened to have it enabled before the rename.

## Why it matters

Combined operator impact:

- **Defect 1** affects every tenant with >30 lookup tables - moderate-sized organisations exceed 30 quickly (country codes, tier mappings, customer enumerations, one table per business-domain). Pillar P-03 is intentionally narrow per `system-mission.md`; degrading the SOLE UI surface for the SOLE feature means the pillar is operationally broken for medium+ deployments.
- **Defect 2** combines with the DOC-182 Caveat 3 + the operator-action LSN-001-class default-footgun (UI metadata edit triggers downstream ALTER TABLE on the documented public schema): the operator's natural diagnostic question after a downstream pipeline break ("who renamed which table when") is unanswerable from platform logs. Forces operators to PostgreSQL `pg_audit` / external audit log + manual cross-reference.

Severity is CRITICAL because Defect 1 silently degrades pillar P-03's entire surface for any non-trivial deployment; Defect 2 is the audit-asymmetry pattern's third instance and compounds with an existing operator-action-layer default-footgun.

## Suggested fix

### Defect 1 - one-line `scrollableTarget` rename

```tsx
// LookupTablesList.tsx:53
- <InfiniteScroll scrollableTarget='directory-entities-list'
+ <InfiniteScroll scrollableTarget='lookup-tables-list'
  ... >
```

Regression-resistance: factor the container id + the scrollable target through a single shared constant (e.g., `const SCROLL_CONTAINER_ID = 'lookup-tables-list'`) so a future copy-paste cannot drift them again. Paired test in **TST-001** asserts scroll fires `fetchNextPage`.
