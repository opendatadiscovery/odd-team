## Description

`docs/data-discovery/search.md`'s new **Query syntax** section closes its operators paragraph with:

> **Operators narrow a query — they never switch prefix matching off.** `cust -test` still finds `Customers`,
> so you can start with a loose query, see too many rows, and add an exclusion without your results collapsing.
> **Only the parts you make explicit become exact: a quoted phrase and an excluded word match the word you
> actually typed.**

The first two sentences are true and are the paragraph's real subject — I verified them. The **last** sentence
is not: Postgres's `english` text-search configuration **stems** every lexeme on both sides of the match, so a
quoted phrase and an excluded word match the word's *stem*, not the word typed. Measured, not reasoned:

| I typed | Compiles to | Matches / excludes | The page implies |
|---|---|---|---|
| `"customer orders"` | `'custom' <-> 'order'` | matches **`Customer Order singular`** — a row containing neither word as typed | only the words as typed, adjacent |
| `customer -test` | `!'test' & 'custom':*` | **excludes `Customer tests suite` AND `Customer testing framework`** — neither contains `test` | only `test` is excluded |

```
to_tsvector('Customer tests suite')        -> 'custom':1 'suit':3 'test':2
to_tsvector('Customer testing framework')  -> 'custom':1 'framework':3 'test':2
to_tsvector('Customer Order singular')     -> 'custom':1 'order':2 'singular':3
```

(`default_text_search_config = pg_catalog.english`, confirmed on a throwaway `postgres:13.2-alpine`.)

**This is not a defect the operators introduced.** Stemming has always applied to the plain prefix path —
`cust` finds `Customers` partly because `Customers` stems to `custom`. What is new is that this sentence is the
**first place on the page (or anywhere in the manual) that characterises how precisely a query matches**, and
it characterises it wrongly. A reader who never had a reason to think about the question is now given an answer,
and the answer is more absolute than the engine.

**No page in the manual mentions stemming.** `grep -rli "stemming|stemmed|word stem" docs/` returns nothing.
For an operator meeting Postgres FTS for the first time, plural-and-participle collapsing is the single most
surprising thing it does, and the section already has the right home for it — the "A few details worth knowing"
list, which is where the hyphen, `or`, quoting and no-positive-term rules already live.

## Why this was NOT held against CTRIB-060 at review

Recorded so the judgment is auditable rather than implicit. The sentence's **operative** claim — that operators
narrow a query without revoking prefix matching, and that the operator-scoped parts are not prefix-expanded — is
true, is what the paragraph is about, and is the whole reason the compositional mechanism was chosen over
`websearch_to_tsquery`. The imprecision is on a different axis (stemming vs prefix), describes behaviour the
long-released plain path already had, and leads no reader into a wrong action: the error direction is *more*
results matched and *more* rows excluded, not a query that returns nothing. That is materially unlike the
round-2 blocker, which was a table row that returned **No matches found** as printed.

It was filed against the then-open PR #111 rather than folded into a fourth CTRIB round precisely because
nothing is published yet — the fix is free until the 1.0.0 gate, and it does not need a rework cycle to land.

## Acceptance criteria

- [ ] The closing sentence no longer claims the matched text is "the word you actually typed". Something like:
      *"Only the parts you make explicit stop expanding: a quoted phrase and an excluded word are not
      prefix-matched — they match that word and its grammatical variants, not everything starting with it."*
- [ ] The section's "A few details worth knowing" list gains one bullet naming the mechanism in the operator's
      voice, with a worked example on both sides — e.g. *"**Words match by root, not letter-for-letter.**
      `order` also finds `Orders`, and `-test` also excludes `testing` and `tests`. This applies to the whole
      search box, operators or not."*
- [ ] The table's `"customer orders"` cell ("the words **next to each other, exactly**") is re-read against the
      new bullet — *exactly* there means *adjacently, not as prefixes*, and should not be left to carry
      "letter-for-letter" as well.
- [ ] Verified on `postgres:13.2-alpine` after editing: the two rows in the table above behave as the corrected
      prose says.
- [ ] A branch off the **current** `origin/release/1.0.0` head and its own PR onto the train (PR #111 is merged; do not reopen it).
- [ ] Owed at the 1.0.0 release gate (with CTRIB-060's own list): the corrected sentence and the new bullet
      render on `https://docs.opendatadiscovery.org/features/data-discovery/search`.
