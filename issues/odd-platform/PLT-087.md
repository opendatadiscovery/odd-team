## What

Three small-surface code defects on the DataSource lifecycle that share a shape: per-method cleanup gaps that the originating author left implicit. Each is operator-visible in a specific way; all three ship together.

**Defect 1 - `delete` orphans the associated TOKEN row + does not clear the FTS `search_entrypoint` vector.** `DataSourceServiceImpl.java:85-96` (delete; it IS `@ReactiveTransactional`, `:86`) blocks with `CascadeDeleteException` when a live non-deleted `data_entity` child references the source (`existsNonDeletedByDataSourceId`, `:88`); otherwise soft-deletes via `dataSourceRepository.delete(id)`. Verified 2026-06-10: the body is exactly the existence-check + `dataSourceRepository.delete(id).map(DataSourcePojo::getId)` (`:88-95`) - it **never touches `tokenRepository` and never calls `updateSearchVectors`**. **The associated TOKEN row is orphaned** (the data-source token has no soft-delete and is not removed here; F-020 sibling - see PLT-085 for the Collector parallel). **The FTS `search_entrypoint` vector is NOT cleared** - an asymmetry with `update`, which DOES call `updateSearchVectors` (`:77,:80`, defined `:127-136`); soft-deleted data-source names persist in catalog search until other events refresh the affected entries.

**Defect 2 - `regenerateDataSourceToken` is NOT `@ReactiveTransactional`.** `DataSourceServiceImpl.java:98-106` is **the only mutating method on this class without `@ReactiveTransactional`** (compare lines 52, 69, 86 which all carry it). If `tokenRepository.updateToken` fails after the `dataSourceRepository.getDto` read, partial state is undefined.

**Defect 3 - `regenerateDataSourceToken` returns the plaintext token in the response body with no `Cache-Control: no-store` header.** Verified 2026-06-10: the controller `DataSourceController.regenerateDataSourceToken` returns `ResponseEntity.ok(...)` with no cache header (`DataSourceController.java:53-59`; grep for `CACHE_CONTROL`/`no-store` in that controller returns nothing), and `TokenMapper.mapValue` emits the **full** plaintext value when `dto.showToken()` is true (`TokenMapper.java`), which is the case on a fresh regenerate. So the rotation response body carries the cleartext token and is cacheable. Intermediate proxies / browser history / corporate inspection appliances may cache. Combined with PLT-085 (plaintext-at-rest), the token has multiple persistence surfaces an operator did not authorise.

## User-facing impact

Code-settled on the structural facts; the operator-observable consequences are static-trace + a runtime check. "User" here is the operator (the DataSource lifecycle is a Management/admin surface). All three code structures are verified 2026-06-10:
- Defect 1: `delete` (`:85-96`) does not touch `tokenRepository` and does not call `updateSearchVectors`, while `update` does (`:77,80`). So the token row is left behind and the FTS vector is not cleared on delete - structurally certain.
- Defect 2: `regenerateDataSourceToken` (`:99-106`) lacks `@ReactiveTransactional` while create/update/delete carry it - structurally certain.
- Defect 3: the rotation response returns the plaintext token (`TokenMapper.mapValue` on `showToken`) with no `Cache-Control` (`DataSourceController.java:53-59`) - structurally certain.

Not driven (runtime-only): the orphan-TOKEN accretion rate and the "deleted source still appears in search" window for Defect 1 (depends on when other events refresh the FTS vector), the partial-failure incidence for Defect 2, and whether any real proxy/browser actually caches the Defect 3 response. Remaining check to make these concrete: drive a DataSource delete + a token regenerate on a running instance and inspect the `token`/`search_entrypoint` tables and the rotation response headers; no workspace probe-run exists for this lifecycle yet.

## Why it matters

**Defect 1**: Operators auditing `TOKEN` rows for orphans see growth without obvious source (the parent data-source is soft-deleted). Operators searching for a "deleted" data source find it surfacing in faceted catalog search until other events trigger a refresh.

**Defect 2**: Partial-state risk; manifests as inconsistent operator state on transient DB errors. Small probability per event, real cumulative risk.

**Defect 3**: Plaintext token caching by intermediate proxies extends the credential's exposure window beyond the operator's control. Operators rotating a leaked token expect tight blast radius - a cached response in a corporate proxy / browser tab history undermines that.

Severity MEDIUM because:
- None of the three is a security-defect-class on its own; all three are operator-trust / state-consistency caveats
- The three together are a small-surface hardening pass; an upstream maintainer can land them in a single small PR

## Suggested fix

### Defect 1 - delete should clean up TOKEN + FTS

(`delete` is already `@ReactiveTransactional` at `:86` - the change is the TOKEN + FTS cleanup, not the annotation. The `@ReactiveTransactional` line below is retained, not added.)

```java
// DataSourceServiceImpl.java:85-96
@ReactiveTransactional
public Mono<Long> delete(final long id) {
    return dataSourceRepository.getDto(id)
        .flatMap(dto ->
            dataSourceRepository.delete(id)
                .then(Mono.justOrEmpty(dto.tokenId()))
                .flatMap(tokenRepository::delete)            // <- clear the TOKEN row
                .then(searchEntrypointService.updateSearchVectors(
                        ChangeContext.dataSourceDeleted(id))) // <- refresh FTS
                .thenReturn(id)
        );
}
```

(Exact wiring depends on whether TOKEN should be soft-deleted (adds `deleted_at`) or hard-deleted; recommend hard-delete since TOKEN has no historic value once the parent is gone. If hard-delete causes FK conflict, add `ON DELETE CASCADE` to the TOKEN->DATA_SOURCE FK in a follow-up migration.)

### Defect 2 - annotate regenerate

```java
// DataSourceServiceImpl.java:98-106
+ @ReactiveTransactional
  public Mono<DataSource> regenerateDataSourceToken(final long id) {
      return dataSourceRepository.getDto(id)
          .flatMap(dto -> tokenRepository.updateToken(...))
          .map(updated -> dataSourceMapper.mapDto(updated));
  }
```

One-line annotation; matches the 3 sibling methods.

### Defect 3 - Cache-Control on the rotation response

Controller-side:

```java
@PutMapping("/api/datasources/{id}/regenerateToken")
public Mono<ResponseEntity<DataSource>> regenerateDataSourceToken(@PathVariable long id) {
    return dataSourceService.regenerateDataSourceToken(id)
        .map(ds -> ResponseEntity.ok()
            .header(HttpHeaders.CACHE_CONTROL, "no-store, no-cache, must-revalidate")
            .header(HttpHeaders.PRAGMA, "no-cache")
            .body(ds));
}
```

(Apply the same pattern to the Collector token rotation response under PLT-085's scope OR file a separate one-liner.)
