## Description

`docs/data-lineage/microservices.md` closes with:

> * [API Reference -> Lineage](../developer-guides/api-reference/lineage.md) — the same lineage HTTP surface
>   used for both data-object and microservice lineage. **Calling it directly? Always pass an explicit
>   `lineage_depth` — omitting it returns HTTP 500, not a default-depth graph.**

That is the pre-0.29.0 behaviour. `odd-platform#1758` (CTRIB-030) added `default: 1` to `lineage_depth` in
`odd-platform-specification/openapi.yaml`, so an omitted parameter now binds to `1` and returns the depth-1
graph. **DOC-481** (status `done`, milestone 0.29.0) corrected exactly this claim — but its `affected_files`
list named only **two** of the three pages that carried it:

- `docs/developer-guides/api-reference/lineage.md` — CORRECTED (":24 ... **Omitting `lineage_depth` applies a
  server-side default of `1`** ... sending an explicit value is no longer required — #1758").
- `docs/data-lineage/data-objects.md` — CORRECTED (":45 ... an omitted `lineage_depth` returns the same
  single-hop graph the UI requests by default. (Before `0.29.0` ... that is fixed — #1758.)").
- `docs/data-lineage/microservices.md` — **NOT corrected**. Still live with the superseded claim.

So the doc product now says two opposite things about the same endpoint, and the page that is wrong is the
one that *links to* the two that are right.

## Failure shape

**Parallel surfaces with drift** — the corrected and the superseded version of one claim are both live —
compounded by **incomplete-sweep residue**: a `done` item whose scope enumerated 2 of 3 surfaces. This is the
same convergence failure the workspace has case-law for (memory
`feedback_converge_claim_complete_not_instance_loop`): fix the *claim* across the whole tree, not the
instances the filing session happened to grep.

## User-facing impact

An operator or SDK author reading the microservices page is told to always send `lineage_depth`. Two concrete
consequences on a 0.29.0+ deployment:

1. **Defensive code that is now dead weight.** A client author adds a mandatory-parameter guard and a retry
   path for a 500 that cannot happen, then has to unpick it when their 4xx/5xx alerting never fires.
2. **Worse — misattributed debugging.** When something else on the lineage path *does* 500, the operator's
   first hypothesis is the documented one ("I must have dropped `lineage_depth`") and they spend the first
   pass of the investigation in the wrong place.

Neither is data-destroying, hence `high` rather than `critical` — but it is *incorrect documentation*, which
the priority order ranks above missing documentation.
