**New structural anchors surfaced (per the 5 ZI route-module sidecars)**:

- **The MULTI-PERMISSION AND-of-permissions semantic surprise** (per queryExamples-route sidecar `stress_findings.auth_gates.[DETAILS route]`): *"the PermissionProvider uses `allowedPermissions.every(...)` AND logic — so within the details-route context, `isAllowedTo` evaluates true only if the user has BOTH UPDATE AND DELETE; a user with only one gets `isAllowedTo: false`."* The MULTI-PERMISSION `WithPermissionsProvider allowedPermissions={[A, B]}` is NOT semantically equivalent to "the user has at least one of A or B" — it requires ALL. A reviewer auditing the platform's RBAC and seeing `allowedPermissions={[QUERY_EXAMPLE_UPDATE, QUERY_EXAMPLE_DELETE]}` reasonably reads it as "either UPDATE or DELETE is sufficient" — but the implementation requires BOTH. THIS is a NEW DIMENSION of the META: the parameter's name `allowedPermissions` (plural) suggests OR semantics; the implementation enforces AND semantics. The actual per-action gates (the separate `<WithPermissions>` calls at `QueryExampleDetailsContainerActions.tsx:40` and `:53`) correctly use OR-equivalent single-permission checks; the wrapper's AND semantic only affects what the `isAllowedTo` context publishes for descendants to consult. Net: the AND vs OR confusion is bounded but real. The doc-product fix (the META section per DOC-GAP-302 part 1) should explicitly call this out: "`WithPermissionsProvider allowedPermissions={[A, B]}` requires BOTH A and B to be held by the current user; for OR semantics, use multiple `<WithPermissions>` instances or nested providers."
