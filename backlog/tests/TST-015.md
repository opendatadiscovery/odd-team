## Description

OFFSET/LIMIT pagination over an ORDER BY whose sort key is NOT unique is unstable: rows that tie on the sort value have a DB-defined (effectively arbitrary) relative order, so a concurrent insert/update that lands between two page fetches can shift the offset window and make a row appear on two consecutive pages (duplicate) or on neither (skip). The fix is a deterministic tiebreaker — append the unique `id` as a secondary ORDER BY key.

**Correction to the harvest finding (verified 2026-06-08).** The report grouped THREE endpoints (alerts / runs / owner-assoc). On reading the code, the alert list query is NOT vulnerable — it already paginates on a composite, stable key: `List.of(new OrderByField(ALERT.LAST_CREATED_AT, SortOrder.DESC), new OrderByField(ALERT.ID, SortOrder.DESC))` (`ReactiveAlertRepositoryImpl.java:475-476`, and the outer select re-applies both, `:505`). Alerts are the model to copy, not a defect. The two genuinely-vulnerable endpoints are:

- **Data-entity task runs** — `getDataEntityRuns` paginates on a single key, `END_TIME DESC`, with no tiebreaker (`ReactiveDataEntityTaskRunRepositoryImpl.java:176-182`):
  ```java
  jooqQueryHelper.paginate(baseQuery, DATA_ENTITY_TASK_RUN.END_TIME, SortOrder.DESC, (page - 1) * size, size);
  ```
  `END_TIME` ties whenever runs share an end timestamp; it is also nullable (a still-running task has no end time), and ties/NULLs are exactly where ordering is unspecified.

- **Owner-association requests** — `getDtoList` paginates on a single key, `STATUS_UPDATED_AT DESC`, with no tiebreaker, both in the inner `paginate(...)` (`ReactiveOwnerAssociationRequestRepositoryImpl.java:103-105`) and the outer `.orderBy(...STATUS_UPDATED_AT).desc())` (`:131`). A realistic tie source is a same-instant cascade-decline (many requests resolved in one transaction share `STATUS_UPDATED_AT`).

The `JooqQueryHelper.paginate` overload that takes a single `Field` builds the window with only that field (`JooqQueryHelper.java:55-61, 63-90`); the no-arg overload deliberately defaults to `baseSelect.field("id")` (`:42-45`), which is the project's own evidence that a unique tiebreaker is the intended baseline. The two endpoints above bypass that by passing a single non-unique field.

**Typed gate: validates-feature (probe-gated).** This guards the intended contract — stable, gap-free, duplicate-free pagination across both endpoints — and the probe (PENDING-F-040-2 for task-runs, PENDING-F-174-2 for owner-assoc) establishes whether the skip/dup is actually observable under a concurrent insert/resolve mid-scroll on a live stack before the id-tiebreaker fix is applied upstream. It is not a known-bug pin: the desired end state is stable pagination, so we assert that, not the current instability.

## Implementation Notes
Medium. Use the local docker PG test stand (the order of tied/NULL rows is engine-defined; prove it on the real engine). Seeding: insert (2 × pageSize) task runs with an identical `END_TIME` (and a couple with NULL `END_TIME` to exercise the NULLS-ordering corner), and a same-instant batch of owner-association requests sharing `STATUS_UPDATED_AT`. Fetch page 1 and page 2 and assert the multiset union = the seeded set with no repeats and no omissions; repeat the fetch and assert identical order. For the concurrent skip/dup (a row mutated between fetches sliding the offset window), defer to the PENDING probes — a single-threaded slice cannot interleave a write between two page reads. The fix is mechanical: switch each call to `paginate(baseQuery, List.of(<existingKey> DESC, new OrderByField(<TABLE>.ID, SortOrder.DESC)), offset, limit)` and re-apply the same composite in any outer `.orderBy(...)`. Read both repository methods end-to-end first to confirm the outer-query orderBy (owner-assoc rebuilds the order in the CTE wrapper) gets the tiebreaker too, or the inner fix is undone by the wrapper.
