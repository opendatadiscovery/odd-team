## Description

DOC-183 covers four operator caveats on the Query Examples page (RBAC grid split, 10-of-13 unscoped reads, XSS via MDEditor.Markdown render, no @ActivityLog audit silence). This item adds four NET-NEW caveats — three on the authoring surface (`QueryExampleForm`) and one composite caveat covering the Query Example Details page's tab navigation (the page has THREE tabs but the live doc names ZERO of them).

**Caveat 5 — Authoring-time XSS intervention point uncaptured (F-131a — extends DOC-183 Caveat 3).** `QueryExampleForm.tsx:83 + :94 + :105-111` validates only `required: true, validate: value => !!value.trim()` on the `definition` Input and the `query` Markdown editor. Authoring is the FIRST intervention point in the XSS chain; the form passes raw user input (including `<script>` payloads) straight to the API. DOC-183 Caveat 3 captures the RENDER-time XSS via `MDEditor.Markdown`; this caveat captures the AUTHORING-time defence-in-depth gap — same family, different intervention layer.

**Caveat 6 — Dialog close loses Markdown drafts silently (F-131b).** `QueryExampleForm.tsx:128-141` (the DialogWrapper) has no `handleNavigationWarning`, no dirty-form detection, no autosave, no localStorage draft persistence. An operator in the middle of authoring a query example who clicks outside the dialog OR hits Escape loses their work with no warning. For a custom SQL snippet of moderate size this is a real loss — minutes-to-hours of work disappear.

**Caveat 7 — `definition` is plain Input at authoring but Markdown at render — mode-mismatch UX (F-131c).** `QueryExampleForm.tsx:85-87` renders the definition field as a plain `<Input>` — NOT a Markdown editor. The render site `QueryExampleDetailsOverview.tsx:19` renders the same field through `<Markdown value={definition} />`. An author typing `**bold**` into the definition field sees plain text in the form; on the details page they see rendered bold. The asymmetry creates a footgun for XSS payloads typed naively into a "plain" field (Caveat 5 amplifier).

**Caveat 8 — Query Example Details page tab navigation completely undocumented (F-132a).** The Details page mounts THREE tabs (Overview Markdown render + Linked Entities + Linked Terms) selected by `?tab=` URL param with hint badges. The live page mentions "linked data entities and terms" without naming the tabs as distinct sub-views. Four operator-relevant facets accumulate: (a) `?tab=foo` URL param has no runtime validation — landing with a typo'd value renders a page with NO active tab + BLANK body (silent UX degradation); (b) `linkedEntitiesHint` reads `pageInfo.total` (across all pages) while `linkedTermsHint` reads `items.length` (only loaded items) — inconsistent counting; the badge understates for paginated linked-terms collections; (c) no breadcrumb back-to-list — operators rely on browser Back or sidebar tab click; (d) tabs are read-only — unlinking an entity requires navigating to that entity's page; multi-link management is a workflow paper-cut.
