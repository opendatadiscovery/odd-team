## What

The User filter on the global Activity Feed AND on every per-entity Activity tab is **mislabelled**: UI label and live docs both describe it as "events PERFORMED by the selected users (actor-axis, multi-select, useful for auditing a specific person's platform activity)." The SQL binds `userIds` query param to `OWNER_ID` via `USER_OWNER_MAPPING`. The filter narrows to "events on entities OWNED BY the selected user's owner mapping" — NOT "events PERFORMED by the user."

A compliance reviewer auditing "what did Bob do last week" gets "events on Bob's owned entities, performed by anyone" — a fundamentally different question with potentially overlapping but generally distinct result sets.

The doc-side framing (DOC-206) is the first mitigation — the page now explicitly states the entity-ownership-axis semantic and warns operators off the actor-axis misreading. This PLT ships the structural fix.

## Why it matters

**Compliance / audit workflows are broken.** "What did Bob do" returns "what happened to Bob's owned things" — overlapping but distinct sets. A team lead asking "what did my team do this week" gets "events on entities my team owns" — different question.

**The doc has now been corrected (DOC-206 reframes the User filter as entity-ownership axis).** But the UI label is still "User" and operators who don't read the doc will continue to use it as actor filter. The structural fix is required to close the LSN-020 loop.

**LSN-020 class anchor.** This is the FIRST live-doc-tier confirmation of the LSN-020 family. The DQ Title filter (DOC-GAP-264) is structurally the same class. Fixing this surface is the canonical case of doc + code alignment on filter-axis semantic.

Severity is HIGH because:
- Compliance / audit use cases produce confidently-wrong answers.
- The same misleading framing surfaces at TWO entry points (global + per-entity) so the gap compounds.
- Doc mitigation is only as good as the operator's read-the-doc discipline; the structural fix closes the gap for everyone.

## Suggested fix

**Three options; recommend Option C as the safest.**

**Option A — rename the filter to match the semantic.** Change the UI label from "User" to "Owner of entity"; update the OpenAPI query param doc + the live doc text (DOC-206 already does the doc part). Smallest change, but the underlying semantic "owner-of-entity-axis filter" is awkward for the actor-axis question many operators actually want.

**Option B — rebind the SQL to the actor axis.** Add a new filter (`actorUserIds` or similar) that binds at SQL to `activity.created_by`. Existing `userIds` filter stays. Operator chooses the question (actor vs entity-ownership). UI exposes both labels.

**Option C (recommended) — rebind `userIds` to the actor axis + rename the existing entity-ownership filter to a new param.** Most operators want actor-axis ("what did Alice do") when they pick a User filter; the entity-ownership-axis is the less-common question. Rename SQL:

```java
// ReactiveActivityRepositoryImpl.java
// userIds (actor axis):
.and(activity.created_by IN (:userIds))

// new entity-ownership-axis filter: ownerUserIds → USER_OWNER_MAPPING → OWNER_ID
// (keeps existing query shape under the renamed param)
```

UI:

```tsx
// Filters.tsx
<MultipleFilter filterName='userIds' name={t('Performed by user')} options={...} />
<MultipleFilter filterName='ownerUserIds' name={t('Entity owner is user')} options={...} />
```

Operator distinguishes the two axes; the typical use case ("what did Alice do") is the default behaviour for the more obvious filter name. Spec change requires a sibling commit on `opendatadiscovery-specification` (rename + new param). Backwards-compat: a temporary compat shim mapping the old `userIds` to the new `ownerUserIds` for one release would let existing API clients survive — but the rename is the right ship.
