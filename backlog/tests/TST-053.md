## What

`IT-124` (`rbac-policy-lifecycle.spec.ts`, F-006, regresses PLT-110) FAILS its two grant-lifecycle cases. The
seeded grant (alice -> owner -> role -> policy(`OWNER_DELETE`)) does NOT resolve: the granted DELETE returns
**403** where the test expects **204** ("the grant chain did not resolve — check `user_owner_mapping.provider`
IS NULL for LDAP, and the `owner_to_role`/`role_to_policy` edges").

## Evidence (this is NOT the CTRIB-022 s2s change)

- IT-124 was **green** on the last 5 `multi-stack` runs (2026-06-11 .. 2026-06-16, `ODD_SUT=working`).
- It FAILS today on **both** my working-tree SUT (origin/main + the one-line s2s null-guard) **and** the cached
  published **0.28.0** image — i.e. it fails on code that does NOT contain the s2s fix and predates the recent
  main commits. So the s2s change is causally exonerated (IT-124 uses LDAP cookie auth, no `X-API-Key`; the
  s2s filter's pass-through is identical pre/post-fix), and this is not a clean "regressed after 0.28.0" story
  either (0.28.0 fails too).
- The environment today showed memory pressure (a `ref:main` SUT build aborted on JVM GC thrashing; a ghcr pull
  timed out). IT-124 does LDAP login + a 6-table raw-SQL grant seed + an immediate authz check — timing-fragile
  under load.

## Leading hypothesis + triage

**Most likely: environmental/timing fragility** of the LDAP grant seed (green on a clean box 06-16, red on a
strained box today; fails regardless of code version). **Cannot fully rule out** a platform RBAC
grant-resolution regression — that would be release-relevant for 0.29.0. Triage:
1. Re-run `run-suite.sh IT-124` on an unloaded machine (no concurrent builds/stacks) — does it go green? -> flakiness.
2. If still red: add a readiness wait/poll after the grant seed (the grant must propagate before the authz check)
   and verify `user_owner_mapping.provider IS NULL` + the `owner_to_role`/`role_to_policy` edges are seeded for
   the current schema (a migration may have changed a seeded table).
3. If the grant genuinely never resolves on a clean box across versions -> escalate as a platform RBAC bug (PLT).

## Why it matters

IT-124 is a green-target pin in `multi-stack`; a flaky/failing green-target erodes the suite gate (a real
regression could hide behind "oh, IT-124 is just red again"). Either harden the seed (flakiness) or escalate
(regression). Surfaced to the maintainer in the CTRIB-022 handback because it touches the 0.29.0 release window.

## Resolution (2026-06-19) — root-caused + fixed, NOT flaky

A **deterministic regression in the test seed**, not flakiness, not the s2s change, not a platform bug.
`V0_0_92__backfill_user_owner_mapping_provider.sql` (GHSA-8wf2-7c5g-h59v / PLT-120 / CTRIB-018, ~06-16) changed
`AuthIdentityProviderImpl` to persist the auth-mode literal (`'LDAP'`) as `user_owner_mapping.provider` for
non-OAUTH2 logins instead of `NULL`, and `getUserRolesByOwner` matches `PROVIDER.eq('LDAP')`. IT-124 still
seeded `provider = NULL` (the pre-V0_0_92 assumption, stated verbatim in its own comments) -> alice's
owner/role/grant no longer resolved -> 403. It failed identically on cached `0.28.0` and current main (both
carry V0_0_92); the lone 06-16 "green" was the pre-V0_0_92 working tree.

Fix: `rbac-policy-lifecycle.spec.ts` seed `provider = 'LDAP'` (+ corrected 3 stale "provider IS NULL for LDAP"
comments). Verified: `run-suite.sh IT-124` -> **2 passed (e2e:PASS)** on the working SUT.

Lesson (the real value): a real, deterministic regression was **misattributed to flakiness and left red through
implement AND /review** when V0_0_92 landed. The class fix is the quality process, not this test (2026-06-19
process-redesign discussion). The platform is fine; the test seed, the review, and the suite gate were the miss.
