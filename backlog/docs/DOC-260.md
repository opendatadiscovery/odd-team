## Description

The live `/data-discovery/search` page (WebFetched 2026-05-27, 200 OK) describes the seven facet sidebar, "Per-result transparency" icons, and the FTS pipeline. It is **silent on every load-bearing operator-trust facet of the search runtime**: the URL is a server-side session reference (sharable + mutable + housekeeping-evicted), the facet aggregators return cross-owner counts to any authenticated caller, the query string is persisted unescaped through `to_tsquery` (any operator character poisons the session row and 500s every subsequent facet read), the filter sidebar silently truncates datasource/namespace options at 100, clicking a result row inflates the entity's `view_count` by +2 (LSN-017 doubling), and the catalog page exposes a 9-tab class strip the doc does not enumerate. Six operator-visible behaviours need a Known Limitations and one new sub-section.

**Caveat 1 — `/search/{searchId}` is a server-side session reference, not a URL-encoded query (F-017a).** `searchRoutes.ts:7-12` builds `/search/{searchId}` where `searchId` is the UUID of a row in the `search_facets` table (`V0_0_1__init.sql:204-211` declares the schema with NO `owner_id` / `created_by` column). The session row carries the typed query, facet selections, page state, and a 30-day TTL (per F-010's `SearchFacetsHousekeepingJob`). Three operator-trust implications: (a) sharing a `/search/{uuid}` URL with a teammate hands them an interactive cursor into your typed query, not a snapshot — they can mutate it; (b) clicking the Catalog top-nav drops the session UUID from the URL (per `SearchRoutes.tsx` mount behaviour) and creates a new server-side row on next type — operators do not realise they accumulate session rows in the database; (c) the session row has no owner binding, so any authenticated user with the UUID reaches it (typical operator mental model is "URL = my query state, opaque to others" — incorrect here).

**Caveat 2 — Cross-owner facet enumeration is the default; any authenticated caller drills the full Owner directory + per-owner counts (F-017b).** `SearchController.java:30-47` carries NO `@PreAuthorize` (verified by grep this run); `SecurityConstants.java` has NO `/api/search` rule (zero matches). The six facet aggregators in `ReactiveSearchFacetRepositoryImpl` apply only `getDataEntityDefaultConditions` (HOLLOW / STATUS / EXCLUDE_FROM_SEARCH) — no `OWNERSHIP` join. An authenticated caller drilling `GET /api/search/{id}/facet/OWNERS` receives the platform's complete Owner enumeration (display name + per-owner count); the same shape holds for `TAGS`, `NAMESPACES`, `DATASOURCES`, `GROUPS`, `TYPES`. Under `auth.type=DISABLED` the endpoints are anonymously reachable (sister case to DOC-GAP-008 / DOC-GAP-252 Directory closure).

**Caveat 3 — tsquery operator characters in the search box poison the session row PERMANENTLY; every subsequent facet/list read 500s (F-017c — CRITICAL security).** `JooqFTSHelper.tsQuery` (per F-017 sidecar lines 164-168) does NOT escape tsquery syntactic operators (`(`, `)`, `&`, `|`, `!`, `*`, `:`). The persisted `query_string` reaches `to_tsquery(?)` directly on every read of the session row. A POST with a query like `foo )(` writes the malformed string to the row; every subsequent facet read inflates a Postgres `syntax error in tsquery` → 500. Because the housekeeping job (F-010) only evicts rows by `last_accessed_at` cadence and reads count as touches, the row can sit broken for hours/days until the operator manually mutates the query string to a non-broken value or starts a new session by navigating to /search. Operators sharing a URL where the original poster typed an operator character serve their teammates a persistent 500. No client-side validation, no API-side validation; the wire contract accepts the malformed input.

**Caveat 4 — `Filters.tsx` hard-codes `size: 100` for datasource + namespace facet lookups; deployments with >100 of either silently lose options (F-017e).** `Filters.tsx:32-33` (verified this run): `dispatch(fetchDataSourcesList({ page: 1, size: 100 })); dispatch(fetchNamespaceList({ page: 1, size: 100 }));`. The dropdowns in the Filter sidebar render only the first 100 datasource and namespace rows returned by the list endpoints, in whatever order the repository returned (no operator-controllable sort). An operator with 100+ datasources or namespaces (typical in enterprise multi-team deployments) cannot filter by sources past index 100; the missing options are invisible — no "+N more", no pagination affordance, no search-within-dropdown.

**Caveat 5 — Clicking a result row inflates the clicked entity's `view_count` by +2 per click; routine browsing skews the Popular ranking from the search side (F-147a).** `ResultItem.tsx:42` resolves `detailsLink = dataEntityDetailsPath(searchResult.id)` and the entire row at `ResultItem.tsx:72-76` is `onClick={() => navigate(detailsLink)}`. The destination (`/dataentities/{id}/overview`) fires the F-001 LSN-017 useEffect-doubling pattern, empirically pinned at +2 view_count and +2 xhr per click (per the F-001 chain probe P-004). Routine browsing through search results inflates the Catalog Overview's "Recommended"/"Popular" ranking — the operator who reads a search row twice writes that entity's popularity by +4. There is no debounce / dedup; every navigation from search amplifies. Cross-links to the F-001 inflation-loop family (PLT-091 carries the search-side fix; the canonical home-page-side trigger is the same LSN-017 surface).

**Caveat 6 — The catalog page exposes a 9-tab class strip the docs do not enumerate (F-148a).** `SearchResultsTabs.tsx:24-64` (verified this run) hardcodes 9 tabs along the Catalog result list: **All / My Objects / Datasets / Transformers / Data Consumers / Data Inputs / Quality Tests / Groups / Relationships**. The live `/data-discovery/search` page mentions in passing that the **Type** facet "appears after an entity-class tab is selected at the top of the Catalog" — implying the tabs exist — but does NOT enumerate them, does NOT explain that the strip is a separate filter axis from the seven sidebar facets, and does NOT name "My Objects" as a personal-namespace tab. Operators read the page and miss the My-Objects affordance entirely.
