- **ADR-CANDIDATE-033** (NEW 2026-05-12C): CSRF is unconditionally disabled across all four reactive auth modes by deliberate convention — Lines `DisabledAuthSecurityConfiguration.java:15`, `LoginFormSecurityConfiguration.java:54`, `OAuthSecurityConfiguration.java:96`, `LDAPSecurityConfiguration.java:143` all call `.csrf(ServerHttpSecurity.CsrfSpec::disable)`. The consistency across four independent `@Configuration` classes encodes intent rather than oversight; the consumer-facing API is treated as a stateless REST surface
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar explicit `implicit_adr` (`LoginFormSecurityConfiguration`) — cross-confirmed by the parallel `.csrf(... disable)` calls in the other three `*SecurityConfiguration` classes. The 4-file consistency is unmistakable
  - **Surfaced by**:
    - `odd-platform__java__LoginFormSecurityConfiguration__config-key-consumer__auth_type@L31.md:implicit_adrs.[3]` ("CSRF is disabled across all reactive auth modes by deliberate convention. Lines 54 of LoginFormSecurityConfiguration mirrors `OAuthSecurityConfiguration.java:96`, `LDAPSecurityConfiguration.java:143`, and `DisabledAuthSecurityConfiguration.java:15` — all four call `.csrf(ServerHttpSecurity.CsrfSpec::disable)`.")
  - **Decision statement**: ODD's four reactive auth modes unconditionally disable CSRF protection by calling `.csrf(ServerHttpSecurity.CsrfSpec::disable)` at the SecurityWebFilterChain layer. The 4-file consistency (Disabled / LoginForm / OAuth / LDAP) is the intent anchor — the maintainer copied the same pattern across each new auth mode rather than treating CSRF on a per-mode basis. The decision treats the consumer-facing API as a stateless REST surface where CSRF is not a defense layer; bearer-token / session-cookie authentication is expected, and CSRF protection is delegated to the assumption that clients set `Authorization` headers (which CSRF does not generate) rather than relying on session cookies for state-changing requests. The trade-off: LOGIN_FORM mode is the canonical exception to the stateless-REST framing — session-cookie-based authentication is exactly the case where CSRF is the canonical defense vector, and the disable on LOGIN_FORM mode is the structural smell (REFACTOR-105 captures the gap). The decision is borderline ADR-vs-gap; per the wisdom test, the cross-mode consistency IS the deliberate stance even though the LOGIN_FORM consequence is documentably risky.
  - **Wisdom test**: BORDERLINE PASS. The cross-mode consistency (4 files, identical pattern) is the intent anchor; the maintainer chose to disable CSRF on every mode rather than configure it per-mode. The pattern IS deliberate, but the absence of a defending comment (every file calls `.csrf(... disable)` with no rationale-stating comment) means the rationale is inferred from cross-file consistency. Surface as ADR with explicit borderline flag — if the maintainer's stance is "REST clients with bearer-token / OAuth2 session cookies don't need CSRF", document it; if the maintainer's stance was "session-cookie-based-mode (LOGIN_FORM) NEEDS CSRF but we forgot", treat as gap.
  - **Borderline flag**: TRUE — promotes to ADR with explicit borderline annotation. The maintainer's triage decision is required to resolve the LOGIN_FORM exception.
  - **Evidence**:
    - LoginFormSecurityConfiguration.md says: "LoginFormSecurityConfiguration.java:54 + OAuthSecurityConfiguration.java:96 + LDAPSecurityConfiguration.java:143 + DisabledAuthSecurityConfiguration.java:15"
  - **Existing ADR**: none.
  - **Co-surfaced gaps** (link from `refactoring-scopes.md`): REFACTOR-105 (CSRF disabled on session-cookie-based auth mode (LOGIN_FORM) — the LOGIN_FORM exception; MEDIUM), REFACTOR-095 (CSRF disabled cross-mode but undocumented on the live security pages — LOW).
  - **Proposed action**: Promote to `adrs/drafts/csrf-disabled-cross-mode.md` (new ADR) with `borderline_flag: true`. Document the stateless-REST framing rationale. The maintainer's triage decision is: (a) confirm the stance is deliberate ("our auth modes don't rely on session cookies for state-changing requests as a project convention") and document; (b) flip CSRF back ON for LOGIN_FORM (the session-cookie mode) and document the per-mode posture; (c) deprecate LOGIN_FORM in favour of OAUTH2/LDAP for production, which removes the session-cookie+CSRF tension.
  - **Severity rationale**: LOW — cross-mode convention; the LOGIN_FORM consequence is captured at REFACTOR-105 (MEDIUM) where the gap-shaped half of the decision lives.
