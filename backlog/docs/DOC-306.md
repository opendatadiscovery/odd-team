## Description

DOC-288 correctly established that `attachment.max-file-size` is a **UI client-side** pre-upload filter with **no server-side per-file re-validation**. The accompanying framing of the server-side ceiling, however, is imprecise and **understates** the hazard:

- `odd-platform.md:1028`: "…the effective server-side ceiling is `spring.codec.max-in-memory-size`… A direct (non-UI) API caller can therefore exceed `attachment.max-file-size`, **up to that codec limit**."
- `odd-platform.md:1037`: "…the **codec buffer is the only server-side size limit on the upload path**."

The attachment upload path is **chunked and streamed to disk** (`FileServiceImpl.uploadFileChunk` → `FilePart.transferTo(...)`, verified @ ede5d277). `spring.codec.max-in-memory-size` bounds the **per-request / per-chunk in-memory buffer**, not the total assembled file. The server appends chunks without summing their sizes, so the realized **total** file can exceed the 20 MB codec value. The practical truth is therefore stronger than the doc states: there is effectively **no server-side total-file size ceiling** on the upload path — not "a ceiling at the codec limit." For a security/robustness caveat, framing the codec value as the effective cap *understates* what an uncapped direct caller can upload.

Separately: chunk staging is hardcoded to `/tmp/odd/chunks` (`FileUtils.java:24`), an ephemeral `/tmp` path **independent of** the configurable `attachment.local.path` — so even a LOCAL deployment reconfigured to a durable path still stages chunks under `/tmp`. Worth a one-line note in the same data-loss/robustness class as the DOC-288 ephemeral-default caveat.

**Failure shape**: incomplete / imprecise caveat — a security-relevant size statement that is directionally correct but understates the exposure.
