## ADR-CANDIDATE-117 — Owner-anchored lineage variants use a two-phase anchor + derived-set architecture (`/my/upstream`, `/my/downstream`): phase 1 resolves the user's owned-entity oddrn set; phase 2 expands one lineage hop and EXPLICITLY EXCLUDES the anchor set from the response

**Classification**: promote
**Severity**: HIGH
**Pillars affected**: [P-01-data-discovery, P-05-data-lineage, P-09-security-access-control]
**Support**: 2 sidecars (batch M `getMyObjectsWithUpstream` + batch M `getMyObjectsWithDownstream`) — primary-source confirmation at the controller-method layer for both members of the lineage-variant pair; composes with ADR-CANDIDATE-015 (owner-scoped routes — three-endpoint triplet) and ADR-CANDIDATE-075 (repositories take no Principal — service layer owns owner-id resolution)
**Batch**: M (2026-05-19)

**Surfaced by**:
- `odd-platform__java__DataEntityController__controller-method__getMyObjectsWithUpstream.md:implicit_adrs.[0]` (HIGH) — "Anchor-set + derived-set architecture for owner-aware lineage reads. The two-phase pattern at `DataEntityRelationsServiceImpl.java:25-39` is the deliberate architectural choice: phase 1 resolves the user's owned-entity oddrn set (anchor); phase 2 expands one lineage hop and explicitly excludes the anchor set from the result. The exclusion (`Predicate.not(oddrns::contains)` at line 37) is INTENTIONAL — the maintainer chose to return the lineage *neighbourhood* rather than the owned set itself, because the base `getMyObjects` endpoint already returns the owned set. The three endpoints (`/my`, `/my/upstream`, `/my/downstream`) compose a coherent owner-anchored discovery surface, with each endpoint answering a different question: 'what do I own?', 'what flows into what I own?', 'what flows out of what I own?'."
- `odd-platform__java__DataEntityController__controller-method__getMyObjectsWithDownstream.md:implicit_adrs.[1]` (HIGH) — "Owner-scoped lineage variants use a DIFFERENT code path than `getMyObjects` — the lineage-expanded set is NON-owner-scoped at the response layer; owner-scoping is an ANCHOR-SET DEFENCE-IN-DEPTH pattern. ... The pattern is: (a) fetch the user's owned entities (the ANCHOR), (b) traverse the lineage graph one hop, (c) return reached oddrns EXCLUDING the originally-owned set, (d) project to DataEntityRefs via `listByOddrns` which also has NO owner filter. This is intentional — the maintainer's design is 'show me my data ecosystem context, with my owned entities excluded as the implicit centre'."

**Decision statement**: ODD's `/my/upstream` and `/my/downstream` endpoints are NOT owner-filtered reads of "entities I own plus their lineage" — they are deliberately the **complementary lineage-neighbourhood** of the owned set, with the owned entities themselves explicitly excluded. The two-phase architecture at `DataEntityRelationsServiceImpl.getDependentDataEntityOddrns` (lines 25-39) composes:

1. **Phase 1 — anchor set resolution**: `authIdentityProvider.fetchAssociatedOwner().flatMapMany(o -> dataEntityRepository.listByOwner(o.getId())).map(de -> de.getDataEntity().getOddrn()).collect(Collectors.toSet())` — produces the `Set<String> oddrns` of entities the caller owns. The single owner-scoping site for this endpoint family (REFACTOR-225 single-point-of-failure surface).
2. **Phase 2 — single-hop lineage expansion**: `lineageRepository.getLineageRelations(oddrns, LineageDepth.empty(), streamKind)` — fetches LINEAGE rows touching the anchor set in the chosen direction; `LineageDepth.empty()` (depth=-1, single-hop only — see ADR-CANDIDATE-118) bounds the response.
3. **Phase 3 — flatten + DEDUPLICATE**: `.flatMap(lp -> Flux.just(lp.getParentOddrn(), lp.getChildOddrn())).distinct()` — unions the parent and child oddrns across all touching edges and removes duplicates.
4. **Phase 4 — EXPLICITLY EXCLUDE the anchor**: `.filter(Predicate.not(oddrns::contains))` (line 37) — **drops every oddrn that is in the owned set**. THIS IS THE LOAD-BEARING DECISION: the response is the lineage *neighbourhood* of what the user owns, with the owned set itself removed.
5. **Phase 5 — final projection**: `listByOddrns(oddrns, false, false, page, size)` — fetches the DataEntity rows; NO owner filter at this layer (the architectural trust-boundary risk codified as REFACTOR-225 / REFACTOR-237).

The decision composes a **three-endpoint owner-anchored discovery surface** (`/my`, `/my/upstream`, `/my/downstream`) where each endpoint answers a different question for the UI's `Recommended` panel (`odd-platform-ui/src/components/Overview/OwnerEntitiesList/OwnerEntitiesList.tsx:77-91` rendering "My Objects / Upstream dependents / Downstream dependents / Popular" panels):
- `/my`: **what do I own?** — base path, owner-scoped via JOIN OWNERSHIP at SQL.
- `/my/upstream`: **what flows INTO what I own?** — the anchor + single-hop upstream neighbours, NOT owned.
- `/my/downstream`: **what flows OUT FROM what I own?** — the anchor + single-hop downstream neighbours, NOT owned.

The architectural composition is coherent: the user's "data ecosystem context" is the union of (`/my` ∪ `/my/upstream` ∪ `/my/downstream`); each endpoint returns a disjoint slice. The UI label `Upstream dependents` (`OwnerEntitiesList.tsx:87`) is semantically accurate — it labels the panel as non-owned upstream entities. The OpenAPI summary `data entities owned by current user with upstream dependencies` (`openapi.yaml:843-844`) is the contract surface that disagrees with this design — see DOC-GAP-099 / REFACTOR-225 / REFACTOR-203 for the cross-channel drift.

**Wisdom test**: PASS on all three questions.
1. **Intentional?** YES — the `Predicate.not(oddrns::contains)` filter at line 37 is an explicit positive choice; the three-endpoint composition is a deliberate UI-product decision (the three React panels at OwnerEntitiesList.tsx:77-91 render exactly the three endpoint responses).
2. **Structural impact?** YES — affects the OpenAPI contract for two endpoints (/my/upstream, /my/downstream); affects the UI's home-page composition; affects every third-party API consumer reading the spec.
3. **Adding/removing the exclusion would be STRUCTURAL?** YES — removing line 37 would silently change the response semantic for two endpoints from "lineage neighbourhood" to "owned set + neighbourhood"; the UI's panel rendering would double-count entities; the OpenAPI contract layer would need a different summary; the entire owner-anchored discovery composition would collapse to two near-duplicate endpoints.
