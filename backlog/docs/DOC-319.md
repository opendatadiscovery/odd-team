## Description

Operators running attachments in a **multi-replica** deployment (the standard HA Kubernetes posture: N API replicas behind a load balancer) have a deployment-shaped limitation that the live docs do not currently name: **chunked-upload staging is node-local**, and it applies to BOTH `attachment.storage=LOCAL` and `attachment.storage=REMOTE`.

The chunk base path is hard-coded (`/tmp/odd/chunks`, `FileUtils.java:24 @ ede5d277`), the per-upload directory is created at *initiate* time on whichever replica handled that request, and each chunk is written to the local filesystem of whichever replica receives it — upstream of the LOCAL/REMOTE storage dispatch. With a non-sticky load balancer and no shared volume, `initiate` and the chunk POSTs can land on different replicas, so a chunk write hits a missing directory (intermittent opaque 500), or chunks scatter and `complete` finds an incomplete set. Even REMOTE (S3/MinIO) uploads are affected, because the chunk window stages locally before the assembled file is streamed to the bucket.

This is an **operational deployment caveat** — a "here is what your topology must provide" note for operators — not a security advertisement. It is the operator-facing companion to the platform-side fix tracked as **PLT-118**.

### Scope vs. existing attachment docs (grep-the-backlog-first — read before implementing)

`DOC-253` (status: **done**) already documents two adjacent things on the SAME pages, and DOC-319 must extend, not duplicate, them:

- DOC-253 Caveat 1 documents the chunk-staging `/tmp` limitation for the **container-restart** case (an upload lost when a single container restarts mid-upload). DOC-319 adds the **multi-replica request-routing** dimension (an upload that fails with zero restarts because two requests of the same upload hit two different replicas, requiring a shared RWX volume and/or sticky routing). Frame it as a new sub-paragraph under DOC-253's existing chunk-staging admonition, not a new top-level caveat.
- DOC-253 Caveat 3 + the pre-existing LSN-002 region warning already document the **us-east-1 region pin** (`MinioConfig` never calls `.region(...)`; retrospective `retrospectives/LSN-002-minio-region-unset.md`). DOC-319 does NOT re-document the region pin — it **cross-links** the existing warning so an operator planning a REMOTE multi-replica rollout sees the region constraint and the chunk-staging/topology constraint together as one coherent "REMOTE deployment checklist".

The net-new content of DOC-319 is: (1) the multi-replica / shared-volume / sticky-routing requirement, and (2) a single consolidated cross-reference tying it to the already-documented region pin so the REMOTE deployment story reads as a whole.
