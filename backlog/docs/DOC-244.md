## Description

The live `features/data-lineage` page (WebFetched 2026-05-27) describes the lineage pillar across data-object + microservices lineage. The page is **silent on the my-objects triplet** (`/api/dataentities/my` + `/my/upstream` + `/my/downstream`) — three endpoints with very specific semantic that together answer "what do I own? / what flows IN? / what flows OUT?", an architecture with a single-point-of-failure at the owner-scoping site, AND a spec-vs-implementation inversion in the two `/upstream` + `/downstream` operations' OpenAPI summaries.

**Facet 1 — Anchor-set single-point-of-failure (F-015a, HIGH→CRITICAL).** Owner-scoping for the my-objects lineage triplet is enforced at EXACTLY ONE site — `DataEntityRelationsServiceImpl.java:26` (`authIdentityProvider.fetchAssociatedOwner()`). Downstream the lineage CTE (`ReactiveLineageRepositoryImpl.java:122-176`) has NO OWNERSHIP join NO owner predicate; the final projection `listByOddrns` (`ReactiveDataEntityRepositoryImpl.java:228-253`) is a pure `WHERE DATA_ENTITY.ODDRN.in(...)` scan with no owner JOIN. CONTRAST with the base `/my` endpoint's repository method `listByOwner` (`:515-534`) which DOES JOIN OWNERSHIP. A regression at the anchor (fallback owner-id under DISABLED, a misordered WebFilter dropping SecurityContext, USER_OWNER_MAPPING corruption returning wrong owner, flatMap-vs-map typo) silently leaks the lineage neighbourhood of an unintended owner. Today's code is correct; the architecture provides ZERO defence against a future regression. Combined with F-011d's provider-null cross-mode bleed at USER_OWNER_MAPPING (DOC-245), a multi-mode deployment with username collision is one regression away from cross-owner lineage neighbourhood leak.

**Facet 2 — OpenAPI summary INVERSION (F-015b, HIGH→CRITICAL).** `openapi.yaml:843-844` declares `getMyObjectsWithUpstream` summary as "Get my objects with upstream dependencies" and description "Returns list of data entities owned by current user with upstream dependencies". Symmetric copy at `:861-862` for `getMyObjectsWithDownstream`. The actual response is the INVERSE — the NON-owned upstream/downstream-adjacent set (`Predicate.not(oddrns::contains)` at `DataEntityRelationsServiceImpl.java:37` explicitly EXCLUDES the owned set). The UI label `Upstream dependents` at `OwnerEntitiesList.tsx:87` is semantically accurate; the spec contradicts both code and UI. Third-party API consumers compiling clients from openapi.yaml receive the wrong shape — consume as "my entities" (wrong) or never realise the discrepancy because the DataEntityRef shape is the same as the `/my` endpoint. (DOC-GAP-099 — 4-angle triangulated per substrate; promoted to PRIMARY-SOURCE-confirmed this scan.)

**Facet 3 — Unbounded anchor-set IN-clause fan-out (F-015c, MEDIUM→HIGH).** `dataEntityRepository.listByOwner(o.getId())` (DataEntityRelationsServiceImpl.java:27) fetches ALL owned entities with NO pagination. `getLineageRelations(oddrns, LineageDepth.empty(), UPSTREAM)` constructs a CTE with `WHERE CHILD_ODDRN IN (?, ?, ...)` cardinality = full anchor-set size. Memory and DB-CPU cost scale with anchor set, NOT with the requested page size. Postgres planner cost is non-linear above ~1000 IN elements; jOOQ does not paginate the IN clause. An admin owner or CI-bot owner owning thousands of entities triggers O(anchor) memory + DB-CPU on every `/my/upstream` call even for `size=5`. The Recommended panel on the Catalog Overview home page fires this endpoint on every SPA mount.

**Facet 4 — Silent-empty indistinguishable (F-015d, LOW→MEDIUM).** Four distinct conditions produce the SAME `HTTP 200 + []`: (a) caller has no `USER_OWNER_MAPPING`; (b) caller's owner owns zero entities; (c) owned entities exist but no upstream/downstream LINEAGE edges; (d) no SecurityContext (DISABLED mode). No 401, no 403, no signal distinguishing.
