## Description

The housekeeping subsystem **permanently deletes data** on a 15-minute schedule (resolved alerts, search-facet history, soft-deleted data entities with ~25 cascading child tables including S3 attachments, and empty `activity`/`message` partitions), yet it exposes **no operational telemetry whatsoever**:

- **No metric.** There is no Micrometer counter, gauge, or timer anywhere in the housekeeping package — no `housekeeping_deleted_total`, no per-job duration, no backlog gauge (how many rows are eligible for deletion / how far behind the reaper is).
- **No audit event.** Deletions are not emitted as structured audit records; there is no compliance-grade "what was deleted, when, how many" trail.
- **Logs are DEBUG-only.** Every per-job deletion count is logged at `log.debug` ("deleted N resolved alerts", "Deleted data entities with ids ...", "Dropped N partitions"). The shipped default log level for the package is `info` (odd-platform.md:1131), so on a default deployment these lines are **not emitted at all**. Only connection-acquisition failure and per-job exceptions log at `error`.

How this misleads an operator: the existing docs note (at the TTL-misconfiguration caveat, odd-platform.md:830) says a silent mass-wipe emits "no Prometheus counter" — but that is framed narrowly around the `housekeeping.ttl.*=0` accident. The broader, always-true gap is undocumented: even in **normal** operation an operator has no way to (a) observe that deletions are happening and at what volume, (b) detect a **stuck or wedged cycle** (e.g. the cycle blocked behind a held ShedLock or a long-running delete), or (c) satisfy a compliance requirement that "deletions are logged/audited." An operator who assumes the platform records its own deletions will find nothing actionable when asked to prove what was purged.

This is a documentation caveat plus a named follow-up for the instrumentation. The code enhancements (`housekeeping_deleted_total` counter + a structured audit event) are upstream operability work, not part of this doc item — log them as a follow-up PLT, do not implement here.
