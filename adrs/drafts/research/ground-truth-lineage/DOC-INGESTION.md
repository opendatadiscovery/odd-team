# DOC-INGESTION — ingesting the live GitBook manual into the ontology as first-class graph nodes

Single research thread feeding the ground-truth-lineage ADR. Decision-grade. Adopt as written unless the ADR states a reason not to. Five decisions, each a firm recommendation with a confidence level; a rejection ledger at the end. Every recommendation is grounded in **both** 2025-2026 production RAG/GraphRAG prior-art **and** the conventions already shipped in this repo (`nodes.jsonl` / sidecars / `concepts.yaml` / `doc-gaps.md` / the graph-query-layer ADR), so doc ingestion is an *extension* of the existing substrate, not a parallel system.

## The verdict in one paragraph

**Split at the heading/anchor boundary (H1+H2, H3 only when it carries a stable explicit anchor), make the durable node ID a content-addressed function of `repo-relative-path + heading-path` (never the live GitBook URL slug), commit the doc mirror as a `doc-nodes.jsonl` + per-page sidecar pair that exactly parallels `nodes.jsonl` + the existing enrichment sidecars, share ONE physical vector index with code/concept prose but tag every vector with a `node_type` facet for filtered retrieval, and detect drift with a two-layer content-hash scheme — a `source_sha256` over the normalised source markdown (catches upstream drift, runs every rebuild, free) plus a periodic `live_verified_at` + `live_status` field refreshed by a lychee/WebFetch live-fetch pass (catches GitBook render/slug drift, the documented `attachments.md → data-entity-attachments` class of hazard).** Files stay canonical; the graph + embeddings stay derived, ephemeral, git-ignored, rebuilt-from-files — identical to the contract the graph-query-layer ADR already ratified. The single non-obvious call is decision 2: the live URL slug is **GitBook-runtime-generated from the page title, not stored in the repo, and demonstrably unstable** — so it can be a *resolved, re-verified attribute* of a doc node but must never be its identity.

## Recommendations (opinionated)

### 1. Chunking granularity → **heading/anchor level (H1+H2 primary; H3 only with an explicit stable anchor), with a recursive sub-split fallback for oversized sections.** Confidence: **HIGH.**

Split the corpus at markdown heading boundaries — one graph node per H1/H2 section — and apply a token-budget recursive sub-split *only* to the minority of sections that exceed the embedder window. **Do not** go to page level (too coarse for a 512-token embedder; the largest pages — `configuration-and-deployment/odd-platform.md` at ~93 KB, `integrations/collectors/odd-collector.md` at ~71 KB — are 20-40× the window and would produce blurred, useless page-level vectors). **Do not** go to pure embedding-driven semantic-chunk level (it discards the author's own structural signal, costs an embedding per sentence, and the 2025 evidence says it does not pay for itself).

Why heading-level is right here, specifically:
- **The corpus is already structured for it.** 993 ATX headings across 104 pages ≈ **~9.5 headings/page**; 569 H2s. Heading-level splitting yields on the order of **~600-800 doc-section nodes** (H1+H2, with H3 folded into its parent unless separately anchored). That sits cleanly alongside the code side's ~2,500 vectors that the [graph-query-layer ADR](../graph-query-layer/SCHEMA.md) already sized — total index stays in the low thousands, well inside the "exact brute-force NumPy kNN, no ANN, fully deterministic" regime that ADR chose. **Section granularity is the precedent already set in this repo** ("Embed at section granularity (parent-document pattern)", graph-query-layer SUMMARY §4) — doc ingestion must match it, not invent a new granularity.
- **Header-aware splitting is the production default for technical manuals.** LangChain's [`MarkdownHeaderTextSplitter`](https://docs.langchain.com/oss/python/integrations/splitters/markdown_header_metadata_splitter) splits on heading levels and attaches the header path as chunk metadata, preserving document hierarchy — the recommended shape for manuals. LlamaIndex's `MarkdownNodeParser` is the same idea. The header path is *free, deterministic structure the author already authored* — exactly the signal semantic chunking spends compute to re-derive.
- **The 2025-2026 evidence rejects semantic chunking as the default.** A NAACL 2025 Findings result reported fixed ~200-word chunks matching or beating semantic chunking across retrieval + generation; a 2026 benchmark put recursive 512-token splitting first (~69%) and semantic chunking well behind (~54%) — see the survey roundup at [Firecrawl's 2026 chunking guide](https://www.firecrawl.dev/blog/best-chunking-strategies-rag) and [Weaviate's chunking write-up](https://weaviate.io/blog/chunking-strategies-for-rag). The consensus recommendation is *start structural/recursive, add semantic only if a measured gap demands it.*
- **The oversized-section fallback is a settled pattern.** Pipe `MarkdownHeaderTextSplitter` → a recursive/token splitter so that **overlap is applied only inside a section that exceeds the window, and never across section boundaries** ([LangChain split-markdown docs](https://docs.langchain.com/oss/python/integrations/splitters/markdown_header_metadata_splitter)). Concretely: target ~512 tokens/chunk to match the bge-small window; when a single H2 body exceeds it, sub-split with ~64-token overlap and suffix the child IDs (`#heading-path/part-2`). Most ODD sections are well under one window; only the config/collector mega-pages trigger the fallback.
- **Keep the section as the retrieval-and-citation unit (parent-document pattern).** Embed the section (or its sub-chunks), but the node the retriever surfaces and the maintainer cites is the **whole H2 section** with its `source_file:source_line` range. This is the [small-to-big / parent-document retriever](https://medium.com/data-science/advanced-rag-01-small-to-big-retrieval-172181b396d4) pattern — index small, return the coherent parent — and it matches the "headline-vector, traverse-to-full-node" shape the graph-query-layer ADR already uses for code.

**Net:** one node per H1/H2 section; H3 promoted to its own node only when it carries an explicit stable anchor (decision 2); token-recursive sub-split with bounded overlap for the few oversized sections; the section is the citation unit.

### 2. Anchor/ID stability → **durable internal ID = `sha256(repo-relative-path + "\0" + heading-path)`; the live GitBook URL slug + anchor are a *resolved, re-verified attribute*, NEVER the identity.** Confidence: **HIGH.**

This is the load-bearing decision and the one most likely to be gotten wrong. The reasoning chain:

- **GitBook derives the published page slug from the page *title*, slugified — not from the markdown filename — and the slug is not stored in your git repo.** This is confirmed three ways: (a) GitBook's own [slug help](https://gitbook.com/docs/help-center/published-documentation/custom-domains/how-can-i-change-the-slug-in-the-url) describes the slug as a renameable, SEO-oriented title-derived string; (b) the [GitbookIO discussion #275](https://github.com/orgs/GitbookIO/discussions/275) reports a manually-set slug *reverting* to an auto-generated hyphenated form and a maintainer confirming "the slug isn't stored in your GitHub repository sync"; (c) **this project's own evidence**: `data-discovery/attachments.md` (SUMMARY title "Data Entity Attachments") publishes at `.../data-discovery/data-entity-attachments`, and `doc-gaps.md`'s batch history records hard 404s on `/active-platform-features/data-collaboration`, `/active-platform-features/notifications`, `/active-platform-features/search` while the canonical `/features/active-platform-features/*` paths serve 200. The slug is **externally controlled, title-coupled, and historically unstable.** Binding a node's identity to it would make the entire graph re-key whenever a maintainer edits a heading or GitBook re-slugs.
- **GitBook heading anchors are auto-generated from heading text and break when the heading text changes** unless a custom anchor is pinned via the [Edit anchor feature](https://gitbook.com/docs/creating-content/blocks/heading) ("this will remain the anchor even if you change the header itself"). So the *anchor* is as volatile as the slug, for the same reason — both are title/heading-text functions.
- **The only identifier under your version control and stable across renders is the repo-relative file path + the heading path.** The path moves only on an explicit `git mv` (a reviewable diff), and the heading path moves only on an explicit heading edit (also a diff). Both are *your* deterministic inputs, not GitBook's runtime output. Hash them for a compact, collision-safe primary key, and **keep the human-readable `path#heading-path` as the descriptor** — exactly mirroring how `nodes.jsonl` already builds IDs: `"odd-platform yaml application.yml config-prefix:spring"` with a parallel human `path` field `application.yml#spring`. Doc nodes get `id: "documentation md <relpath> doc-section:<heading-path>"` and `path: "<relpath>#<heading-slug>"`.
- **Resolve internal ID → live URL + anchor as a derived, re-verifiable mapping, computed at rebuild and re-checked on the live pass.** Compute the *candidate* live slug deterministically (lowercase, spaces→hyphens, punctuation stripped — the [github-slugger](https://github.com/Flet/github-slugger) algorithm GitBook approximates, with the documented duplicate `-1`/`-2` suffixing), then **verify it against the live site** rather than trusting it. Store the verified result on the node (`live_url`, `live_anchor`, `live_status`, `live_verified_at`). The repo's `doc-gaps.md` batch history shows the team *already does* live 200/404 verification by hand per batch — this decision just formalises that into a node attribute. Where the computed slug ≠ the live slug (the `attachments → data-entity-attachments` class), the live pass records the real slug and flags a `slug-rewrite` finding (feeds `doc-gaps` as a `broken-url`/`meta` candidate — the exact category that file already tracks).
- **Two stability tiers, declared per node.** `anchor_stability: pinned` when the source uses an explicit GitBook custom anchor or an HTML `<a id=…>`; `anchor_stability: derived` (default) when it's title-generated and therefore fragile. Verification cadence and the willingness to externally cite the anchor key off this field.

**Net:** identity = content-hash of `path + heading-path` (yours, stable, diffable); the live URL/anchor = a derived, re-verified attribute with a stability tier; slug-rewrite divergence is a tracked finding, not a silent break.

### 3. Canonical file representation → **`doc-nodes.jsonl` (one line per doc-section node) + per-page enrichment sidecars under `lineage/{repo}/doc-understanding/`, both carrying `source_sha256` and `extracted_at_commit`; doc edges fold into the existing `edges.jsonl`.** Confidence: **HIGH.**

Make the doc mirror a **structural twin of the code substrate** so every existing tool (the reducers, the retriever, the manifest, the Quality Bar's provenance discipline) treats doc nodes and code nodes uniformly:

- **`lineage/{repo|"documentation"}/doc-nodes.jsonl`** — the deterministic substrate, one JSON object per doc-section node, generated by an extractor pass over `documentation/docs/**/*.md` (NOT hand-edited — same rule as `nodes.jsonl`). Each line:
  ```json
  {"id":"documentation md data-discovery/attachments.md doc-section:uploading-attachments",
   "kind":"doc-section","axis":"documentation","lang":"markdown",
   "descriptor":"Uploading attachments","heading_level":2,
   "heading_path":["Data Entity Attachments","Uploading attachments"],
   "path":"data-discovery/attachments.md#uploading-attachments",
   "source_line":[42,71],
   "source_sha256":"<sha256 of normalised section body>",
   "page_sha256":"<sha256 of normalised whole page>",
   "frontmatter_description":"…",
   "computed_slug":"data-entity-attachments",
   "anchor_stability":"derived",
   "live_url":null,"live_anchor":null,"live_status":null,"live_verified_at":null,
   "repo":"documentation","extracted_at_commit":"<sha>"}
  ```
  This reuses `nodes.jsonl`'s exact field vocabulary (`id / kind / axis / lang / descriptor / path / repo / metadata`) plus doc-specific fields. The `axis: "documentation"` makes doc nodes a first-class axis alongside `config_prefixes`, `controllers`, etc.
- **Per-page sidecars at `lineage/{repo}/doc-understanding/<relpath>.md`** — the *agentic enrichment layer*, exactly parallel to `lineage/odd-platform/understanding/*.md`. One sidecar per page (not per section — page is the natural authoring unit and keeps the file count ~104, not ~800), carrying the same frontmatter envelope already in use (`node_id`/`schema_version`/`enriched_at_commit`/`prompt_version`/`confidence_overall`/`session_id`) plus the cross-links this whole exercise exists to produce: `describes_concepts:` (→ `concepts.yaml` IDs), `describes_features:` (→ `feature-flows.yaml` F-NNN), `describes_code:` (→ `nodes.jsonl` IDs / `source_file:line`), and `doc_gap_refs:` (→ existing DOC-GAP-NNN). The sidecar is where a human/agent *curates* the bidirectional links; the `.jsonl` stays mechanical.
- **Edges fold into the existing `edges.jsonl`** — no separate doc-edge file. New edge `type`s: `documents` (doc-section → code node / concept / feature) and its inverse is derivable, mirroring how `edges.jsonl` already carries `"type":"configures"` from a config class to a config prefix. A doc-section that describes `auth.type` emits `{"src":"documentation md …doc-section:disabled-authentication","dst":"odd-platform java …config-key-consumer:auth.type@L18","type":"documents","metadata":{…}}`. This is the bidirectional chunk↔entity linkage that production GraphRAG treats as mandatory for citation grounding ("every text chunk stores the entity IDs it mentions; every graph node stores the source chunk IDs… without this you cannot cite", [Amazon Bedrock GraphRAG](https://aws.amazon.com/blogs/machine-learning/build-graphrag-applications-using-amazon-bedrock-knowledge-bases/)).
- **`source_sha256` over *normalised* section text is the regeneration + drift primitive (decision 5).** Normalise before hashing — strip trailing whitespace, collapse blank-line runs, normalise line endings — so a cosmetic reflow does not look like content drift (the same lesson the [Drift linter](https://fiberplane.com/blog/drift-documentation-linter/) learned hashing a *normalised* AST so reformatting doesn't false-positive). Git already proves the model: content-addressed `blob <size>\0<content>` hashing means identical content ⇒ identical hash, one byte change ⇒ new hash ([Git object hashing](https://blogs.kenokivabe.com/article/git-object-hashing-and-content-addressability)). We apply it at section granularity.
- **The mirror is committed (diff-friendly, reviewable) but mechanically regenerable.** This satisfies the maintainer's hard constraint — *SoT is files in the repo, like `nodes.jsonl`* — and the maintainer's fear (redundancy→drift) is answered structurally: the `.jsonl` is regenerated from `documentation/docs/`, the regeneration is idempotent, and a CI check (`regenerate && git diff --exit-code`) catches any hand-edit or upstream drift the same way the code substrate is kept honest.

**Net:** `doc-nodes.jsonl` (mechanical substrate) + `doc-understanding/<page>.md` sidecars (curated links) + doc edges in the shared `edges.jsonl`, all carrying `source_sha256` + commit provenance, all regenerable, all diff-friendly — a structural twin of the code substrate, not a parallel universe.

### 4. Embedding strategy for the mixed corpus → **ONE physical vector index, but every vector carries a `node_type` facet (`code-sidecar | concept-gloss | doc-section`) for filtered + boosted retrieval. Same model, same 512-token chunks, version-tagged.** Confidence: **HIGH.**

- **Share the index — separate sub-indexes are unjustified at this scale and break cross-modal recall.** With ~2,500 code vectors + ~600-800 doc vectors + concept glosses, the whole thing is a few thousand 384-d vectors → exact brute-force NumPy kNN, sub-millisecond, fully deterministic (the regime the graph-query-layer ADR already chose). Physically partitioning it buys nothing operationally and *costs* the headline cross-modal query — "where is X documented **and** implemented" — which is the entire point of ingesting docs into the *same* ontology. The correct lever is a **metadata facet, not a separate store**: tag each vector `node_type` and let the retriever filter or boost. "Embedding with a single model version and tracking that version in metadata prevents mixing incompatible vector spaces" and "partitioning/chunking decisions determine retrieval quality more than model choice" — [Unstructured on mixed-type indexes](https://unstructured.io/insights/vector-embeddings-the-key-to-better-search-relevance).
- **The real mixing pitfall is *topic-blurred chunks*, not *type-mixed indexes*.** "A chunk that mixes topics produces a blurred vector that retrieves poorly" (same source). Decision 1 already eliminates that failure mode: heading-bounded sections are single-topic by authorial construction. So the documented risk of mixing is neutralised at the chunking layer, not the index layer.
- **Embed *distilled prose*, never raw markup.** Strip markdown syntax (link targets, code-fence backticks, table pipes, HTML) before embedding the section body; embed the human-readable prose + the heading path as a prefix for topical anchoring. This matches the graph-query-layer decision to embed *distilled NL sidecar prose, not raw code* — bge-small is an English-prose embedder; feeding it raw YAML/markup wastes the window and pollutes the vector. Keep a structured/keyword filter in the hybrid so exact identifiers (`auth.type`, `data-entity-attachments`) are still matchable — the same exact-token mitigation the graph-query-layer PITFALLS thread flagged.
- **Chunk size: target ~512 tokens to fill (not overflow) the bge-small window**; this is the size the 2026 benchmark put first for recursive splitting, and it matches the embedder of record. Sub-split only oversized sections (decision 1).
- **Cache + invalidate embeddings keyed `(section_source_sha256, model_id)`** — identical to the graph-query-layer "embedding cache keyed (section-text-hash, model-id)" invariant, and it ties straight into decision 5: when `source_sha256` changes, the embedding is recomputed; when it doesn't, the cached vector is reused. Free drift-coupling.

**Net:** one index, faceted by `node_type`, single version-pinned model (bge-small-en-v1.5, 384-d, 512-tok), distilled-prose input, structured filter retained for exact tokens, embedding cache keyed on the section content hash.

### 5. Freshness / drift detection → **two-layer content-hash + live-verification, with a freshness SLA. (a) `source_sha256` per section, checked every rebuild (catches upstream-markdown drift, free, deterministic). (b) `live_status` + `live_verified_at` refreshed by a periodic lychee/WebFetch pass (catches GitBook render/slug drift, the 404/slug-rewrite class). Plus existing code↔doc drift via `doc-gaps`.** Confidence: **MEDIUM.**

Three distinct drift surfaces, three distinct detectors — conflating them is the trap:

- **(a) Source drift — derived mirror vs upstream `documentation/docs/**/*.md`.** Detector: re-run the extractor, recompute `source_sha256`/`page_sha256` over normalised text, `git diff` the regenerated `doc-nodes.jsonl`. Any non-empty diff = the mirror is stale relative to source. Cheap, deterministic, runs every rebuild, gate-able in CI (`regenerate && git diff --exit-code` — the same honesty check the code substrate uses). This is *also* the embedding-invalidation trigger (decision 4) and the signal that a page's sidecar links may need a re-review. Content-addressing is the right primitive (Git's own model; normalise first so reflow ≠ drift, per [Drift](https://fiberplane.com/blog/drift-documentation-linter/)). **HIGH confidence on this layer.**
- **(b) Render/publish drift — mirror vs the live `docs.opendatadiscovery.org` site.** This is the layer the maintainer's stated hazard lives in: GitBook can 404 a path, rewrite a slug, or truncate a meta description (the 200-char cap already in the team's memory) **without any change to the source markdown** — so layer (a) cannot see it. Detector: a periodic live pass that, per doc node, fetches `live_url` (+`#live_anchor`), records `live_status` (200/404/3xx), the *actual resolved* slug, and `live_verified_at`. Tooling: [**lychee**](https://github.com/lycheeverse/lychee) is the right engine — fast async Rust link-checker, **`--include-fragments` to validate `#anchor` existence** (directly covers anchor-stability tier `derived`), `--cache` + `--max-cache-age` (default 1 day) to avoid re-hammering the site, `--format json` for machine ingestion, and `--remap` to encode the known filename→slug rewrites. Where lychee can't introspect rendered content (it checks reachability, not body text), fall back to WebFetch for the handful of nodes needing render-text confirmation — which is exactly what `doc-gaps.md`'s batch history already does by hand. **Note:** lychee/HTTP caching here is request-dedup, *not* a true freshness signal — GitBook does not expose reliable per-page `ETag`/`Last-Modified` for content versioning, so **do not rely on conditional-GET for drift**; the authoritative live signal is the periodic re-fetch + the recorded `live_status`/resolved-slug delta. **MEDIUM confidence — operational cadence (how often, how many nodes/pass) is tunable, and live-introspection depth depends on what GitBook's rendered HTML exposes.**
- **(c) Code↔doc semantic drift — does the doc still tell the truth about the code?** This already exists and must not be rebuilt: the `doc-gap-finder` reducer + `doc-gaps.md` is the system of record (77 of its 95 current findings are `drift`). Doc ingestion *strengthens* it: once doc-sections are nodes with `documents` edges to code nodes, a code-node change whose linked doc-section's `source_sha256` is unchanged is a **machine-detectable code-moved-doc-didn't** signal — promote it to a `DOC-GAP` candidate via the existing `playbooks/follow-up-on-disk.md` route. **MEDIUM confidence** — the edge layer makes this detectable, but adjudicating *real* drift vs benign change stays an agentic judgement, as it is today.
- **Freshness SLA, declared and enforced.** Borrow the docs-as-code `last-verified` convention ([doc-drift CI](https://understandingdata.com/posts/doc-drift-detection-ci/), [Docsie on documentation drift](https://www.docsie.io/blog/glossary/documentation-drift/)): a node whose `live_verified_at` exceeds the SLA (recommend **30 days**, tighter for `anchor_stability: derived` nodes) is *stale-unverified* and surfaces in `doc-gaps` as a `stale-page` candidate — a category that file already defines but currently reports as 0. Pin the SLA in the ADR so "verify the live site" stops being per-reviewer discretion and becomes a dated node attribute.

**Net:** hash-diff for source drift (free, every build, HIGH), periodic lychee/WebFetch live pass for render/slug drift (MEDIUM, cadence-tunable, no reliable ETag so re-fetch is authoritative), the existing `doc-gaps` reducer for semantic code↔doc drift (now machine-flaggable via edges), all governed by a 30-day `live_verified_at` SLA that feeds the `stale-page` category.

## What we deliberately reject and why

- **Page-level nodes.** Rejected (decision 1). A 512-token embedder cannot represent a 93 KB config page in one vector; the result is a blurred centroid that retrieves nothing precisely. Page is the right *sidecar* unit (decision 3) but the wrong *embedding/node* unit.
- **Pure semantic (embedding-driven) chunking as the splitter.** Rejected (decision 1). 2025-2026 evidence shows it doesn't beat structural/recursive splitting on retrieval+generation while costing an embedding per sentence ([Firecrawl](https://www.firecrawl.dev/blog/best-chunking-strategies-rag), NAACL 2025 Findings, [Weaviate](https://weaviate.io/blog/chunking-strategies-for-rag)). The manual is *already* semantically segmented by its author via headings — re-deriving that with compute is waste. Hold it in reserve only if a measured retrieval gap on a specific page demands it.
- **The live GitBook URL slug (or anchor) as the node identity.** Rejected hard (decision 2). It is GitBook-runtime-generated from the title, not stored in the repo, demonstrably reverts/rewrites ([discussion #275](https://github.com/orgs/GitbookIO/discussions/275)), and this project has already been bitten by it (`attachments.md → data-entity-attachments`; the `/active-platform-features/*` 404 cluster in `doc-gaps.md`). Identity must be a function of repo-controlled inputs (path + heading path). The slug is a *verified attribute*, never the key.
- **A separate doc-only vector index / a separate doc-edge file.** Rejected (decisions 3, 4). At a few thousand vectors a partition buys nothing and breaks the cross-modal "documented AND implemented" query that justifies the whole effort; a `node_type` facet on a shared index is strictly better. Doc edges belong in the existing `edges.jsonl` with new `type:"documents"` — a parallel file would fragment the graph the retriever traverses.
- **A vector DB (or any server engine) as the doc SoT.** Rejected — restates the project's hard contract and the graph-query-layer ruling: SoT = diff-friendly files in the repo; the index is disposable, git-ignored, rebuilt-from-files. A hosted/served store also fails the local-only / no-API-bills / single-maintainer constraints. (Kùzu/served graph engines already rejected upstream in the graph-query-layer ADR; same logic applies — nothing here reopens it.)
- **A second embedding model tuned for docs.** Rejected (decision 4). One version-pinned model (bge-small-en-v1.5) across code-prose + concept-gloss + doc-prose keeps the vector space coherent; mixing model versions silently corrupts cross-type similarity. If doc retrieval quality underperforms in the shadow-mode gate, the lever is chunking/distillation, not a second model.
- **Conditional-GET (ETag/Last-Modified) as the live freshness signal.** Rejected as *authoritative* (decision 5). GitBook does not expose reliable per-page content validators, and lychee's `--cache` is request-dedup, not version-tracking. The authoritative live signal is the dated re-fetch result (`live_status` + resolved-slug delta + `live_verified_at`), not a 304.
- **Embedding raw markdown/markup.** Rejected (decision 4). Backticks, link targets, table pipes, HTML waste the 512-token window and pollute an English-prose embedder. Embed distilled prose + heading-path prefix; keep a keyword/structured filter for exact identifiers.
- **Conversation-only "we should verify the live site" notes.** Rejected on principle (workspace rule). Freshness becomes a *dated node field* (`live_verified_at`) under an SLA and a `stale-page` `doc-gaps` category — never a per-reviewer memory.

## How this lands in the existing substrate (one-screen integration map)

| New thing | Mirrors / extends | File |
|---|---|---|
| `doc-nodes.jsonl` (mechanical, regenerable) | `nodes.jsonl` field vocabulary; `axis:"documentation"` as a new axis | `lineage/{repo}/doc-nodes.jsonl` |
| per-page doc sidecars (curated links) | `understanding/*.md` enrichment sidecars + their frontmatter envelope | `lineage/{repo}/doc-understanding/<relpath>.md` |
| `documents` edges (doc-section → code/concept/feature) | `edges.jsonl` `type:"configures"` pattern; bidirectional chunk↔entity grounding | existing `edges.jsonl` |
| doc vectors in the shared index, `node_type:"doc-section"` facet | graph-query-layer §3-4 (rustworkx + brute-force NumPy kNN, section granularity, embedding cache keyed on content hash) | git-ignored, ephemeral, rebuilt-from-files |
| `source_sha256` / `page_sha256` + CI `regenerate && git diff --exit-code` | code-substrate regeneration honesty check; Git content-addressing | in `doc-nodes.jsonl` |
| `live_url`/`live_status`/`live_verified_at` + 30-day SLA + lychee/WebFetch pass | `doc-gaps.md`'s existing hand-done live 200/404 verification; `broken-url`/`stale-page`/`meta` categories | node fields + `doc-gaps` reducer input |
| `anchor_stability: pinned|derived` | the GitBook custom-anchor vs auto-anchor distinction | in `doc-nodes.jsonl` |

The doc corpus enters the ontology as **one more axis** of the same substrate, with the same provenance discipline, the same derived-ephemeral index contract, and the same drift-as-tracked-finding posture the workspace already runs. Nothing about the code substrate changes; the maintainer's "SoT = files, fear = drift" constraint is honoured by making the doc mirror a regenerable, hash-checked, diffable twin of `nodes.jsonl`.
