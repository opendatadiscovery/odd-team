## Description

Feature F-001's hypothesis H-012 promises: "Two operators opening the same popular entity's detail page concurrently each have their read counted correctly (no lost updates), and a client paging through the full Popular list sees each entity exactly once." Two sub-claims hang off this, and **neither is settled by a test** — both are currently asserted by **SQL semantics, not by a run** (the sidecar's words; P-301 is the obligation to MEASURE them):

1. **No lost update on `view_count`** — the increment is `UPDATE data_entity SET view_count = view_count + 1`, which Postgres makes atomic per-statement, so N concurrent detail-reads of the same entity should produce exactly +N. The doubling caveat (LSN-017, +2 per browser page-open) means the probe drives the API directly (one +1 per call) to isolate the lost-update question.
2. **Pagination stability** — `getPopular` is non-transactional + offset-based, so a client paging while concurrent reads mutate `view_count` may see an entity twice or skip one beyond the documented 1-row offset-shift tolerance.

The probe skeleton **already exists** fully authored at `lineage/odd-platform/probes/P-301.yaml` (`status: pending-reflection-verification`, `feature_id: F-001`, `test_class: integration`, emitted for H-012). This item is **not** to author a probe — it is to **RUN** the existing one against the local ephemeral docker stack and commit the observation trace, converting H-012's two halves from `probe-needed` to `confirmed`/`partial`/`contradicted` with measured values.

**Typed gate: validates-feature (the H-012 concurrency-correctness promise).** Running P-301 either confirms the no-lost-update + duplicate/skip-free promises (PASS → H-012 verdict flips to confirmed) or surfaces a measured lost-update count / duplicate/skip rate (a bug-candidate → file the upstream PLT). This is a real behavioural verification, not a static pin.
