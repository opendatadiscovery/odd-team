## What

The Slack Events webhook (`POST /api/slack/events`, enabled with Data Collaboration) accepts a request body of **unbounded size** with **no per-caller rate limit** and **no authentication** at the controller level. Every accepted event that survives parsing is persisted as a row in the `message_provider_event` table with the full payload stored in a `JSONB` column. A forged or replayed flood of large bodies - the endpoint is internet-facing by design - therefore (a) buffers arbitrarily large strings into memory during deserialization and (b) writes unbounded rows into the collaboration event table, which is then drained by a single-leader background processor. There is no upstream guard that caps body size or throttles request rate before this work happens.

## Where

`datacollaboration/controller/EventApiController.java:22-24` - the mapping binds the entire request body as a single in-memory `String` with no size constraint and no auth annotation:

```java
@PostMapping(path = "/api/slack/events")
public Mono<ResponseEntity<SlackEventResponse>> handleSlackEvent(
    @RequestBody final Mono<String> rawRequestBody
) {
```

Accepted payloads land in the `JSONB` event column - `db/migration/V0_0_59__data_collaboration.sql:32`:

```sql
    event                     JSONB,
```

(the surrounding `message_provider_event` table, `V0_0_59__data_collaboration.sql:25-39`; the parent `message` table is `PARTITION BY RANGE (created_at)`, `:21`). The single-leader drain processes these rows downstream, so unbounded inserts both bloat the table and queue work for one consumer. The endpoint has no HMAC signature check and no `@ConditionalOn`/auth guard on the path beyond `@ConditionalOnDataCollaboration` (which only gates whether the feature is wired at all).

## Why it matters

This is a **resource-exhaustion / denial-of-service** surface on an anonymously-reachable endpoint. Concrete impact: an attacker (or a misbehaving proxy) can POST many large bodies and (1) drive heap pressure during deserialization of multi-megabyte strings, (2) inflate the `message_provider_event` JSONB table with junk rows, consuming disk and slowing the table, and (3) starve the single-leader event processor, delaying or stalling legitimate Slack thread-reply delivery for every tenant on the deployment. Affected: any ODD deployment with Data Collaboration + a publicly-routable Slack webhook. It is medium rather than high because it requires the feature to be enabled and exposed and does not by itself leak or corrupt data - but the absence of any cap or throttle means a single source can degrade collaboration delivery and grow the DB without bound, intermittently and silently (no rejection, no alert).

## Suggested fix

Bound the work before it reaches parsing and persistence:

1. **Body-size cap** - reject bodies above a sane Slack-event ceiling (Slack event payloads are small; a few hundred KB is generous) at the WebFlux codec / route level (`spring.codec.max-in-memory-size` is global; a route-scoped limit or an explicit length check in the handler is preferable so other endpoints are unaffected). Return 413 (or 400) without buffering the whole body.
2. **Rate limit** - add a per-source request throttle on `/api/slack/events` (e.g. a lightweight in-process limiter / bucket keyed by source IP or by Slack team id once signature verification exists) so a flood is shed with 429 before it hits the DB.
3. Pair this with request-signature verification (Slack `X-Slack-Signature` HMAC) so only genuine Slack deliveries are processed - tracked separately (see PLT-054, Slack-events no-HMAC, F-098 H-001); a size+rate cap is the load-shedding half and is worth doing independently. Open to alternatives on the limiter implementation.

The DoS framing is the load-bearing concern; load probe `PENDING-F-098-2` is queued to characterise table growth and processor starvation under a flood against a running stack.
