## Description

Activity Feed is a central operator surface; the live page (WebFetched 2026-05-27, 200 OK) has **regressed in coverage** since the substrate's 2026-05-20 evidence and is **actively misleading** on one filter axis. This item ships five rewrites consolidating the user-facing reality.

**F-064a — STATE-UPDATE regression: 'My Objects' view-mode no longer mentioned (HIGH; strengthens DOC-GAP-142 + DOC-GAP-149 META).** Substrate evidence (2026-05-20): page "mentions 'My objects' view-mode but does NOT name the user-owner-association prerequisite." Live (2026-05-27): page contains NO discussion of a 'My objects' view-mode or user-owner mapping prerequisites at all. The feature still exists in the UI (Activity tabs include MY_OBJECTS); the doc is now SILENT on the feature entirely. Together with DOC-GAP-142 (federated-user no auto-create), the operator-trap surface is WIDER than before.

**F-064b — Live page actively MIS-STATES the User filter as actor-axis (HIGH; LSN-020 doc-tier confirmation).** Live page reads verbatim "show events performed by one or more selected users (multi-select)... Useful for auditing a specific person's platform activity." Code: the User filter dropdown lists OWNERS; the `userIds` query param binds at SQL to OWNER_ID via USER_OWNER_MAPPING; the filter narrows to "events on entities OWNED by the selected user's owner" — NOT "events PERFORMED by the user." A compliance reviewer auditing "what did Bob do last week" gets "events on Bob's owned entities, performed by anyone." **The doc-side framing creates the LSN-020 misleading-input semantic at the operator's primary entry point.** The doc framing is MORE DANGEROUS than silence.

**F-064c — Silent-empty cross-feature pattern; admin onboarding gap (MEDIUM).** Every "My" view (Activity / Alerts / future Owned-Entities) routes through `AuthIdentityProviderImpl.fetchAssociatedOwner():50-53`. Returns Mono.empty() when no mapping row exists. Downstream code silently emits empty list / zero counts. Platform admin authoring Roles/Policies/Owners during setup typically configures these FOR OTHERS — their own account often has no `user_owner_mapping`. The admin experiences every "My" view as silent-empty during onboarding, may conclude the platform is broken before finishing setup.

**F-196a — Per-entity Activity tab has no type-tabs axis vs global feed (MEDIUM).** Per-entity Activity tab exposes only date + eventType + userIds filters; global Activity page exposes a TYPE-TABS axis (ALL / MY_OBJECTS / UPSTREAM / DOWNSTREAM) the per-entity surface has NO equivalent for. Per-entity is implicitly ALL-equivalent; operators expecting "filter my-owned changes on this entity" cannot. Live doc names the per-entity tab; does not name the absence of type-tabs.

**F-196c — Per-entity Activity tab cross-channel reach into soft-deleted entities (MEDIUM doc-side).** `DataEntityDetailsRoutes.tsx:105` mounts the per-entity Activity tab BARE — no RestrictedRoute, no WithPermissionsProvider. The Activity tab is the ONLY entity-detail tab without a `hidden:` clause — it survives soft-deleted entities. Combined with the backend's cross-owner posture (F-021 family), any authenticated user reads the audit trail for any data entity (including soft-deleted) via the per-entity Activity tab. The live doc says the tab "scopes the feed to events on that entity only" — does NOT mention access posture or soft-delete behaviour.
