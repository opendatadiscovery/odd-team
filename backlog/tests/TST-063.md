## Description

`#1842` asks for an "own performance gate" and CTRIB-062 delivered real measurements — but they do not cover
the claim the code makes, and the gap was found by auditing the *sentence* rather than the code.

**What IS established:**

- **The rendered SQL shape is guaranteed by construction, not by hope.** `unnestIn` uses
  `DSL.condition("{0} in (select unnest({1}))", column, DSL.val(ids, BIGINT[]))`. `DSL.condition(String,
  QueryPart...)` is jOOQ's **plain-SQL template** API: it substitutes binds and emits the template verbatim,
  performing no query rewriting. No jOOQ transformation can turn this into `= ANY(array)` or a literal IN list.
- **That shape's plan was measured at scale (M3).** On a 200 000-row fixture with a 10 000-id scope:
  `= ANY(array)` on the joined `data_entity` → Hash Right Join, array re-scanned per row, **54 443 ms**;
  `asset_search_entrypoint.asset_id IN (SELECT unnest(?))` → Bitmap Heap Scan (FTS-driven) + hashed semi-join,
  **249 ms**. A 218x difference, caught *before* the code was written.
- **Both shipped indexes were measured** (M1 lineage `child_oddrn` 880 ms → 22 ms; M4 `ownership(owner_id)`
  107 ms → 4.9 ms) and one "obvious" optimisation was **rejected for measuring slower** (M5).

**What is NOT established, and why it matters.** Every one of those numbers came from **hand-written probe SQL
on a throwaway Postgres**. None went through the running application, and — more importantly — none exercised
the **complete** query this method builds: three left joins (`data_entity` / `term` / `query_example`), the
kind-guarded eligibility predicate, entity-class array overlap, facet semi-joins, the sort, and keyset
pagination. Any of those can change which node the planner chooses as driver.

So the claim *"keeping the predicate off the join is what preserves the FTS-bitmap-driven plan"* is true of the
**measured** query and **unverified** of the **shipped** one. The comment has been narrowed to say exactly that
and to cite this item; this is the work that would let it be widened again.

## Acceptance criteria

- [ ] A repeatable perf probe seeds a dense fixture (>= 100 000 indexed assets; an owner whose lineage scope
      reaches the 10 000-node cap) and runs `EXPLAIN (ANALYZE, BUFFERS)` on the **actually executed** query —
      captured from the running platform, not re-typed from intent.
- [ ] The plan is asserted, not eyeballed: the FTS/GIN path drives, the scope is a hashed semi-join (not a
      per-row re-scan), and no `Seq Scan` on `asset_search_entrypoint`.
- [ ] The interactive latency bound from the plan is measured end-to-end: `POST /api/search/assets` at
      `downstream_depth=3` over a cap-reaching scope returns in **< 1 s** (plan-time projection was ~0.53 s).
- [ ] If the plan differs from M3's, the comment is corrected and the shape re-designed — the M3 outcome shows
      that measuring this class of thing changes the design rather than merely confirming it.

## Notes

**Why this is filed rather than fixed in-slice.** Closing it properly means a permanent perf test with a dense
fixture — a substantial new artefact that would land unreviewed at the end of a long session. Narrowing the
claim to the evidence costs nothing and is honest; inventing the artefact under time pressure is how an
unverified gate gets a green checkmark. The maintainer decides at GATE 2 whether the residual blocks merge.

**How it was found — the transferable part.** The `ctrib061` stream audited its own OpenAPI description and
noticed it asserted a planner behaviour ("probes the key and lets the planner choose a semi-/anti-join") with
no measurement behind it. Applying the same lens here surfaced this. **Two independent streams each wrote a
performance sentence into a public artefact and verified a proxy for it** — the pattern is a correct local
action with an unconsidered global claim, and it is worth a retrospective alongside the shared-spec/per-stream-SUT
finding (`TST-060`/`TST-061`).

## Resolution — 2026-09-01, CLOSED

**The question this item asked is answered, and the answer is the good one.** It asked whether the FTS bitmap
still *drives* the ranked query once `ReactiveAssetSearchRepositoryImpl`'s three left joins, kind guards,
facet semi-joins, sort and keyset pagination are all present at catalog scale — because every number behind
the scope predicate's design had been taken on hand-written probe SQL, not on the query the platform issues.

It was re-measured in CTRIB-062 Phase F on a running LOGIN_FORM platform: **120 000 indexed assets**, 30 000
lineage edges, `auto_explain` capturing the plan PostgreSQL actually executed, and the scope genuinely
resolved (`scopeTruncated: true`, `NODE_CAP`, `total: 10000`):

```
->  Bitmap Heap Scan on asset_search_entrypoint   (actual time=99.1..216.0 rows=10000)
      ->  Bitmap Index Scan on asset_search_entrypoint_search_vector_gin_idx
                                                  (actual time=74.9 rows=120000)
            Index Cond: (search_vector @@ to_tsquery(...))
```

The GIN index drives, 120 000 candidates come back, and the scope is applied as a **filter on the bitmap heap
scan** narrowing them to exactly 10 000 — not a separate join, not a per-row rescan. Ranked page 507.77 ms;
the lineage hops never crossed the 200 ms `auto_explain` threshold, so `V0_0_101`'s indexes are doing their
job.

**Closed at review** (`/review CTRIB-062` re-review, 2026-09-01). The finding that closes it also produced a
defect of its own worth recording: the measurement was taken, but the code comment that *cited this item*
was left saying the question was still open, so the PR simultaneously claimed both. That was raised as C1 and
fixed in the same pass — `ReactiveAssetSearchRepositoryImpl` now carries the executed plan inline.

**What did NOT close with it**, so it is not lost here: the dominant remaining cost at catalog scale is the
pre-existing `count(*)` (median 274 ms on the same stand), which every search pays with or without a scope.
That is tracked separately as `issues/odd-platform/PLT-260`.
