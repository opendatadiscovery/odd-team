## What

The file name an uploader supplies for an attachment is used verbatim in two unsafe places, with no sanitisation anywhere in between:

1. **Path traversal** - when `attachment.storage=LOCAL` (the default), the raw file name is fed straight into `Path.resolve(fileName)` to compute where the file is written. A name like `../../etc/cron.d/x` or an absolute path escapes the intended per-entity directory and lets an attacker write to an arbitrary location the API process can reach.
2. **Content-Disposition header injection** - on download, the same raw file name is string-concatenated into the unquoted `Content-Disposition` response header. A name containing CR/LF (or a `"`) injects additional response headers / breaks the header, enabling response-splitting and content-spoofing against the downloading client.

There is no `..`/separator/NUL/length check and no RFC 6266 header quoting at any layer.

## Where

The uploaded name originates from the form data and is set on the pojo unmodified, then used to build the on-disk path:

`odd-platform-api/.../mapper/FileMapper.java:30-31`
```java
filePojo.setName(fileMetadata.getFileName());
filePojo.setPath(pathConstructor.getFilePath(fileMetadata.getFileName(), dataEntityId));
```

The LOCAL path constructor resolves that name directly against the entity directory - the classic traversal sink:

`odd-platform-api/.../service/attachment/local/LocalFilePathConstructor.java:31-32`
```java
public String getFilePath(final String fileName, final long dataEntityId) {
    return getFileDirectory(dataEntityId).resolve(fileName).toString();   // <- raw fileName; ".." escapes the dir
}
```

On download, the same name is concatenated into the header **unquoted and unescaped**:

`odd-platform-api/.../controller/DataEntityAttachmentController.java:76-79`
```java
return attachmentService.downloadFile(fileId).map(dto -> ResponseEntity.ok()
    .header(HttpHeaders.CONTENT_DISPOSITION, "attachment;filename=" + dto.fileName())   // <- CRLF/quote injection
    .contentType(MediaType.APPLICATION_OCTET_STREAM)
    .body(dto.resource()));
```

## Why it matters

Two distinct security defects share one untrusted input:

- The **path traversal** is the more severe arm: an authenticated uploader can cause the API process to write attacker-named files outside the storage root (overwrite/poison files, drop content into writable system directories, or fill arbitrary volumes). Under `attachment.storage=LOCAL` - the default, `matchIfMissing = true` - every default deployment is exposed.
- The **header injection** lets a malicious file name corrupt the download response for any user who fetches that file (response-splitting, spoofed filename/headers), a client-side integrity/spoofing risk.

Both are silent: nothing logs or rejects the hostile name, and the damage manifests only when the file is written (traversal) or downloaded (header). Severity **high**: arbitrary-path write on the default storage mode reachable by an authenticated uploader, plus a response-injection sink on the public download path.

## Suggested fix

Sanitise the file name once, at the trust boundary (upload), and additionally encode it at the header sink:

- Strip the name to its base component and reject traversal/control characters before it is ever used:
  ```java
  final String safe = Paths.get(fileMetadata.getFileName()).getFileName().toString();
  if (safe.isBlank() || safe.contains("..") || safe.chars().anyMatch(c -> c < 0x20)) {
      throw new BadUserRequestException("Invalid file name");
  }
  ```
  Use `safe` for both `setName(...)` and `getFilePath(...)`. In `LocalFilePathConstructor.getFilePath`, additionally assert the resolved path stays under the entity directory (`resolved.normalize().startsWith(dir.normalize())`) as defence in depth.
- In `downloadFile`, emit the header via Spring's `ContentDisposition` builder so the filename is RFC 6266 quoted/encoded rather than concatenated:
  ```java
  .header(HttpHeaders.CONTENT_DISPOSITION,
          ContentDisposition.attachment().filename(dto.fileName(), StandardCharsets.UTF_8).build().toString())
  ```

Open to alternatives on the exact character policy; the load-bearing requirements are (a) no `..`/separator can reach `resolve(...)`, and (b) the file name is escaped, not concatenated, in the response header.
