## Description

There is no application-level length cap on an entity description: the OpenAPI schema declares the field as an unconstrained string and the column is an unbounded `text`. DOC-187 already states the bare "no length cap" fact (`entity-description.md:25`). What is **not** documented is the operational consequence of authoring a genuinely large description — three effects that together make "unbounded" misleading:

1. **Implicit ~256KB request-size ceiling (framework default).** The platform never overrides Spring WebFlux's default in-memory codec buffer (`maxInMemorySize`, 256KB) — a repo-wide search finds no `maxInMemorySize` / `defaultCodecs` / codec override in the platform sources or config. A `PUT /api/dataentities/{id}/description` body larger than the framework default is rejected by the codec before the handler runs, surfacing as a generic `DataBufferLimitException` → 4xx/5xx rather than a friendly "description too long" message. So the *effective* cap is the framework default, not "unlimited."
2. **Full-text-search vector rebuilt on every save.** `DataEntityInternalStateServiceImpl.updateDescription` (`DataEntityInternalStateServiceImpl.java:56-60`) calls `reactiveSearchEntrypointRepository.updateDataEntityVectors(dataEntityId)` on every description write — a large body means a correspondingly large `tsvector` recomputed and rewritten each save.
3. **Description stored twice in the activity payload.** The same method carries `@ActivityLog(event = DESCRIPTION_UPDATED)` (line 56); the activity record captures both the previous and the new full description (the page already notes the old-state/new-state diff at `entity-description.md:51`). Each large edit therefore writes roughly **two** extra copies of the body into the activity store, which accumulates over the edit history.

None of these is a bug — they are the realistic cost of "unbounded text." Operators bulk-importing long descriptions, or treating the field as a document store, deserve to read this caveat next to the "no length cap" claim instead of discovering it through an opaque codec exception or activity-table growth.
