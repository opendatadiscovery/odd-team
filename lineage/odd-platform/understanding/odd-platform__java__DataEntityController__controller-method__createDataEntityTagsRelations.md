# DataEntityController#createDataEntityTagsRelations — semantic understanding

## understanding

`createDataEntityTagsRelations` is the reactive `PUT /api/dataentities/{data_entity_id}/tags` handler — five lines that read the request body as `Mono<TagsFormData>`, call `dataEntityService.upsertTags(dataEntityId, form)`, and lift the resulting `Flux<Tag>` into `200 OK`. Despite the `create*` operationId, the underlying semantic is **replace-all** for INTERNAL tags on a data entity: the form supplies a complete `tag_name_list`, the service computes the diff against the current internal-tag relations and (a) auto-creates any tag whose name does not yet exist in the `tag` directory, (b) inserts relation rows for the new set, (c) deletes relation rows that are absent from the new list, and (d) leaves EXTERNAL (ingested) tag relations untouched. Authorization is enforced centrally by a `SecurityRule` for `PUT /api/dataentities/{data_entity_id}/tags` that demands the `DATA_ENTITY_TAGS_UPDATE` permission, evaluated per-data-entity through the `DataEntityPermissionExtractor` Policy-resolution pipeline. The hypothesis-of-the-batch is **confirmed**: a caller with `DATA_ENTITY_TAGS_UPDATE` for a single data entity can mint new rows in the global Tag directory without holding `TAG_CREATE` — and this side-effect is in fact **explicitly documented** in the OpenAPI spec, which is unusual relative to the Owner/Title pattern.

## bugs_limitations_corner_cases

- "Permission side-door: `DATA_ENTITY_TAGS_UPDATE` mints global Tag directory rows without `TAG_CREATE` — a caller with `DATA_ENTITY_TAGS_UPDATE` on any single data entity can submit `tag_name_list: ['arbitrary-new-name']` and a new row appears in the global `tag` directory (visible to every other user via `GET /api/tags/popular`). The documented permission story ('TAG_CREATE controls the Tag directory') is incomplete: `DATA_ENTITY_TAGS_UPDATE` also grows it, by spec-acknowledged design. **The asymmetry is exacerbated by scope**: `TAG_CREATE` is `MANAGEMENT`-scoped (always unconditional), while `DATA_ENTITY_TAGS_UPDATE` is `DATA_ENTITY`-scoped and therefore conditionally grantable via `\"is\": \"dataEntity:owner\"`. A per-data-entity-owner can therefore mint global tag rows that pollute the popular-tags surface for users with no permission on their data entity. This is **the same pattern shape as batch-F's `DATA_ENTITY_OWNERSHIP_CREATE`→Owner/Title** side-door, but with one critical difference: the Tag side-door is explicitly documented in `openapi.yaml:1174` ('Also creates corresponding tags in the system if they don't exist'), so it qualifies as `implicit_adrs[1]` for intent **AND** as a `bugs_limitations_corner_cases` entry for the unintended consequence (cross-tenant tag pollution; permission boundary erosion). - "Operation name vs. behaviour drift: PUT replace-all semantics under create-language naming — the OpenAPI spec, the operationId, the controller method name, and the spec summary all say 'create' / 'creates' for an operation that diffs and deletes.
