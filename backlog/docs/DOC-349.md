## Description

The fail-start warning on `active-platform-features.md` correctly tells operators that `notifications.enabled` and `datacollaboration.enabled` are read with no built-in fallback and abort startup if missing from a custom / externalized configuration. But the hint closes with: *"The other subsystem flags (`genai.enabled`, `metrics.storage`) do not share this hazard."* That closing sentence reads as "only these two keys have the no-default hazard."

That is incorrect for at least one more key: `notifications.message.downstream-entities-depth` carries the **identical** no-default hazard. Its consumer (`NotificationConfiguration.alertNotificationMessageTranslator`, NotificationConfiguration.java:121-132) injects it via `@Value("${notifications.message.downstream-entities-depth}")` (NotificationConfiguration.java:123) with **no default segment** in the SpEL — exactly like the two flags the warning already names (whose SpEL is `${datacollaboration.enabled}` / `${notifications.enabled}`, FeatureResolverImpl.java:16-17 → FeatureResolver.java:7,10, also default-less). A custom configuration that enables notifications but omits `notifications.message.downstream-entities-depth` cannot resolve the placeholder and aborts startup the same way.

The miss misleads an operator who, trusting the closing sentence, externalizes notification config and carries forward only `notifications.enabled` — and then hits a startup failure on the un-mentioned depth key. The fix is small: either add `notifications.message.downstream-entities-depth` to the enumerated no-default keys, or soften the closing sentence so it no longer asserts that *only* the two flags share the hazard.
