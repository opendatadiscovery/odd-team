- **DOC-GAP-122**: Lost-update race on `PUT /api/policies/{id}` — `PolicyServiceImpl.update` (lines 71-81) issues TWO separate R2DBC calls outside any `@ReactiveTransactional`: `policyRepository.get(id)` (line 74) reads current row → mapper applies form-data → `policyRepository::update` (line 79) writes new row. Two concurrent updates against the same policy can lost-update silently with no error returned to either caller. The sibling `RoleServiceImpl.update` (RoleServiceImpl.java:64) IS `@ReactiveTransactional`; the asymmetry between Policy and Role is undocumented and structurally surprising (MEDIUM — admin-rare-frequency, but a multi-admin audit landing on inconsistent policy state has no signal to recover from)
  - **Category**: drift (live `/configuration-and-deployment/enable-security/authorization/policies` documents the JSON shape; the per-CRUD-method transaction discipline is invisible; the asymmetry vs sibling RBAC service `roles.md` is invisible)

  - **Evidence**:
    - `PolicyServiceImpl.java:71-81` — verbatim: `public Mono<Policy> update(final long id, final PolicyFormData formData) { policyJSONValidator.validate(formData.getPolicy()); return policyRepository.get(id) .switchIfEmpty(Mono.error(new NotFoundException("Policy", id))) .map(p -> policyMapper.applyForm(p, formData)) .flatMap(policyRepository::update) .map(policyMapper::mapDetails); }`. **No `@ReactiveTransactional` annotation.**
    - `RoleServiceImpl.java:64` — verbatim: `@ReactiveTransactional public Mono<Role> update(final long id, final RoleFormData formData) { ... }`. The sibling RBAC service IS annotated.
    - `ReactiveAbstractCRUDRepository.java:107-110, 162-173` — the base `update` method is single-statement (`UPDATE ... WHERE id = ?`); self-atomic at the DB layer. The race is NOT at the DB layer — it's at the service-tier read-then-write composition.
    - **The race window**: client A reads v1 (line 74) ✓ → client B reads v1 concurrently (within the same wall-clock millisecond on a healthy R2DBC pool) ✓ → client A's mapper applies form-data-A to its v1 pojo and writes (line 79 → v2 success) ✓ → client B's mapper applies form-data-B to its OWN copy of v1 and writes (line 79 → v3 success — but v3 was derived from v1, NOT v2). **Client A's change is silently overwritten.** Postgres has no optimistic-concurrency token on the row (no `version` field on PolicyPojo, verified by reading PolicyServiceImpl.java:7-21) and no row-level lock.
    - **What lost-update means in this domain**: policies are JSON-shaped authorization rules. Client A and Client B may both legitimately add a new permission to the same policy ("add LOOKUP_TABLE_READ", "add LOOKUP_TABLE_WRITE"). The lost-update produces a policy that has B's change but not A's — A's edit is silently dropped. There's no error to either caller; both see HTTP 200; the platform shows the policy with only B's change. A multi-admin audit ("we both saw the policy update succeed; why are A's permissions missing?") has no signal to recover from.
    - **The sibling asymmetry**: `RoleServiceImpl.create` (line 51-61), `.update` (line 63-77), `.delete` (line 79-92) — all three carry `@ReactiveTransactional`. `PolicyServiceImpl.create` (line 62-69), `.update` (line 71-81), `.delete` (line 83-95) — NONE of the three carry `@ReactiveTransactional`. The maintainer-design intent is opaque; there is no comment defending the absence on Policy or the presence on Role. The cascade-delete check in `PolicyServiceImpl.delete` (lines 89-92) ALSO races (see DOC-GAP-112 cascade-delete race-window) — the entire Policy service is non-transactional while the Role service is fully transactional. This is the canonical instance of the per-service transaction-boundary asymmetry that DOC-GAP-116 META centers on.
    - Live-page state (inherited from batch-E WebFetch 2026-05-12 status 200; current-session WebFetch denied): `/configuration-and-deployment/enable-security/authorization/policies` documents the JSON shape; silent on the lost-update behaviour. `/configuration-and-deployment/enable-security/authorization/roles` documents Roles; silent on the transactional-vs-non-transactional asymmetry. The doc-product has no story for "which RBAC mutations are race-safe and which are not".
  - **Proposed doc action**: **Three-part action**.
    1. **Doc-side primary**: extend `configuration-and-deployment/enable-security/authorization/policies.md` with a "Concurrency behaviour" admonition: "**Concurrent updates to the same policy can result in lost updates** — the platform has no optimistic-concurrency token on policy rows, no row-level lock, and no transactional wrapping of the read-then-write flow on `PUT /api/policies/{id}`. Two administrators editing the same policy simultaneously can both receive HTTP 200; the second writer's changes overwrite the first's silently. For multi-admin deployments, coordinate policy edits out-of-band or wait for the platform-side fix (cross-link to the code-side ticket). **The sibling Roles API does NOT have this gap** — `PUT /api/roles/{id}` is transactional; concurrent role edits serialise correctly."
    2. **Code-side primary** (file `/log-issue odd-platform`): three ordered options. (a) **Minimum**: add `@ReactiveTransactional` to `PolicyServiceImpl.update` matching the RoleServiceImpl pattern; the wrapping transaction scopes the read+write to a single R2DBC connection. NOTE: per the sidecar's bugs_limitations_corner_cases[0] commentary, even the wrapping transaction does NOT by itself prevent lost-update without `SELECT ... FOR UPDATE` or row-version tracking; it only provides connection-scoping. (b) **Medium**: extend to `SELECT ... FOR UPDATE` on `policyRepository.get(id)` — closes the lost-update race definitively. (c) **Full**: add an `updated_at` / `version` optimistic-concurrency field to the PolicyPojo + a corresponding `If-Match` header on the PUT endpoint; returns 412 Precondition Failed if the version doesn't match.
    3. **Pillar-side meta-recommendation**: the per-service transaction-boundary asymmetry is the canonical instance for DOC-GAP-116 META; the meta-recommendation's reviewer checklist should specifically include "for any RBAC primary-surface page, verify the page documents the concurrency model of each mutating operation".
