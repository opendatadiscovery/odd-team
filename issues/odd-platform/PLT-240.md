> **Future direction follow-up to [#1781](https://github.com/opendatadiscovery/odd-platform/issues/1781) / CTRIB-032.** Tracked on disk per the GATE-1 decision (deprecation signal = docs note + tracked follow-up). Not scheduled; file when the team is ready to pick it up.

## Summary

As of the #1781 fix (0.29.0), a lookup table's Description is propagated to the associated Data Entity's
**external (source) description** and rendered on the entity overview, while the entity's **internal
(catalog-curated) description** — edited via the overview's *About → Add info / Edit info*, with `[[term]]`
live links — remains independent. So a lookup-table entity carries **two** descriptions:

- **external** = the lookup-table form's description (source-provided; read-only on the overview);
- **internal** = the catalog curator's description (editable; term-linkable).

This is a deliberate, backward-compatible transitional shape. The intended future direction (maintainer,
2026-06-23) is to **consolidate to a single description** — keeping only the internal (catalog) description —
so operators are not presented with two description surfaces for the same object.

## Proposed direction (to be designed when scheduled)

- Decide the single canonical description for a lookup-table entity (the internal/catalog description is the
  likely target — it is editable and term-linkable).
- Retire the external/internal split for lookup-table entities: either stop populating `external_description`
  from the lookup-table form and migrate existing external descriptions into `internal_description`, or remove
  the lookup-table form's Description field in favour of the entity-About editor.
- Add a user-facing deprecation signal on the transitional external description ahead of removal.
- Update `documentation/docs/master-data-management/lookup-tables.md` (the 0.29.0 note already flags a future
  consolidation — see DOC-480) and the ontology.

## Why this is deferred, not done now

The #1781 fix deliberately chose the backward-compatible external-description routing (no contract change, no
data migration, no removal) to resolve the immediate bug with minimal blast radius. Consolidation is a larger,
separately-scoped change (a migration and/or a contract/UI change) that warrants its own design + GATE-1 — it
is not folded into the #1781 PR (G-C5 scope discipline).
