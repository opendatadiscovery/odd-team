- **REFACTOR-391** (NEW 2026-05-19O): GitHub `login` rename produces an orphan `USER_OWNER_MAPPING` row — silent loss of owner-link on any GitHub username change. The handler uses `login` as the username (default `user-name-attribute: login`); GitHub allows free login renames (90-day escrow then released); a renamed user presents `(alice2, github)` to AuthIdentityProviderImpl while the prior `(alice, github)` USER_OWNER_MAPPING row is orphaned. NO `id`-based fallback exists
  - **Category**: owner-mapping-drift
  - **Surfaced by**:
    - `GithubUserHandler.md:bugs_limitations_corner_cases.[0]` (HIGH)
    - `GithubUserHandler.md:security.known_security_gaps.[0]` (HIGH)
    - `GithubUserHandler.md:docs_link_semantic.doc_drift_findings.[2]` (MEDIUM doc-vs-code)
  - **Statement**: GitHub allows users to RENAME their `login` string at any time (free; the old name is held in escrow for 90 days then released for re-registration). ODD's `GithubUserHandler` uses `login` as the username (`USER_LOGIN = "login"` at line 36; default `adminAttribute = USER_LOGIN` at line 56). A user `alice` who logs in once (USER_OWNER_MAPPING row created with `oidc_username='alice', provider='github'`), then renames their GitHub login to `alice2`, on next login presents `(alice2, github)` to AuthIdentityProviderImpl.fetchAssociatedOwner. The prior `(alice, github)` row is ORPHANED; the user lands in the platform with NO Owner association. Their `My Objects` view silently renders empty. NO `id`-based fallback exists (GitHub's stable numeric `user.id` IS available in the OAuth2User attributes but ODD does not consume it). The live docs do not warn GitHub operators about this. Cross-link: F-011 facet `compound_key_silent_in_docs` (general); this is the GitHub-specific facet.
  - **Evidence**: `GithubUserHandler.java:36, 56` (USERNAME = login + adminAttribute = login default) + `AuthIdentityProviderImpl.java:29-30` (the (username, github) tuple construction) + `ReactiveUserOwnerMappingRepositoryImpl.java:116-127` (the lookup that requires exact match) + GitHub API docs (rename behaviour — public knowledge)
  - **Existing-ADR-or-implied-prescription**: ADR-CANDIDATE-135 NEW (GitHub OAuth2-non-OIDC) — the handler is structurally committed to OAuth2User attributes; switching to id-based stable identifier would require schema migration (USER_OWNER_MAPPING.oidc_username becomes oidc_id) + every existing row backfilled (impossible without re-querying GitHub for every prior user). The gap is NOT a structural decision; the maintainer simply did not add an id-fallback when writing the handler. Adding the fallback is refactoring.
  - **Proposed remedy**: Add an `id`-based secondary lookup: if `(username, github)` lookup returns empty, try `(github_user_id, github)` using the OAuth2User's `id` attribute (GitHub guarantees `id` is stable across renames). Add a `github_user_id VARCHAR` column to USER_OWNER_MAPPING (nullable for non-GitHub rows). On first GitHub login, write BOTH the username AND the id; on subsequent logins, prefer the id-based lookup. Add a doc warning to live docs about username-vs-id semantics for GitHub. Alternatively (lower-leverage): document the limitation and instruct operators to manually re-link users after a rename via the OwnerAssociationRequest flow.
  - **Severity rationale**: HIGH — silent loss of owner-link on any GitHub rename. Latent until rename happens; not detectable from server logs. Cross-link to compromise: a renamed user re-acquiring the prior name (after the 90-day escrow) inherits NO catalog rights — fail-safe in this direction. BUT: the orphaned data continues to be visible to other Owner-scoped queries (via the prior owner-id), and the original user's data trail is permanently disconnected from their new identity. A migration UX hazard.
  - **Suggested backlog grouping**: `OAuth2 hardening sprint` (paired with REFACTOR-390 GHES + DOC-NNN on the live OAuth2/OIDC page for GitHub username-rename semantic)
