## Description

IT-104 ("Management section top-level chrome") runs on the `odd-minimal` stack with `AUTH_TYPE=DISABLED`, and on that stack the dummy principal resolves the POLICY permissions as GRANTED. IT-104 itself records this: "DISABLED — the dummy principal resolves `OWNER_ASSOCIATION_MANAGE` as granted (DOM-probed), so ALL nine sidebar tabs render" (`IT-104-management-chrome.md:30-32`), and its only Policies assertion is the CORNER PIN that the Policies/Roles/Associations tabs are *advertised* (visible) — not what a principal WITHOUT the perm sees.

The Policies sub-area is gated by a `WithPermissionsProvider` requiring all three POLICY perms (`ManagementRoutes.tsx:130-137`):

```tsx
<Route path='policies' element={
  <WithPermissionsProvider
    allowedPermissions={[Permission.POLICY_CREATE, Permission.POLICY_UPDATE, Permission.POLICY_DELETE]}
    resourcePermissions={[]}
    Component={PolicyList}
  />
} />
```

The gate is satisfied purely from the principal's global permissions — `PermissionProvider` computes `isAllowedTo = allowedPermissions.every(perm => [...globalPermissions, ...resourcePermissions].includes(perm))` (`PermissionProvider.tsx:19-25`), and `globalPermissions` comes from the identity fetched at boot (`App.tsx:48` — `dispatch(fetchIdentity())`). On DISABLED that identity carries the POLICY perms, so `isAllowedTo` is always true and the no-perm branch (what a viewer WITHOUT the perms sees on the Policy list) is never rendered in any current IT. That branch — the access-denied / empty / hidden behaviour for an unauthorized or anonymous viewer of the Policy list — is therefore unpinned: a regression that silently exposed (or broke) the no-perm experience would not turn any test RED.

**Typed gate: characterization-pin (LSN-029).** This pins the CURRENT permission-gated behaviour of the Policy-list route for a principal that does NOT hold the POLICY perms. It asserts what the no-perm/anon viewer actually sees today (per `WithPermissionsProvider` + `PermissionProvider` — the `PolicyList` component is not rendered for an unauthorized principal). It goes RED the instant the gate's behaviour changes (perms no longer required, the gated component leaks, or the no-perm fallback changes), which is exactly the regression IT-104 cannot catch because IT-104's principal is over-permissioned.

- [ ] The test asserts the CURRENT no-perm behaviour: with the POLICY perms absent, `PermissionProvider.isAllowedTo` is false, so the `PolicyList` component is not rendered for that route (assert the gated content / Policy-list table is absent or the access-denied fallback is shown — capture whatever the route renders today). This is the characterization baseline.
- [ ] The protocol states explicitly that it covers the gap IT-104 leaves open (IT-104's dummy principal HAS the perms), citing `IT-104-management-chrome.md:30-32` and `ManagementRoutes.tsx:130-137`.
- [ ] The test goes RED if the gate stops requiring the POLICY perms, if `PolicyList` renders for an unauthorized principal, or if the no-perm fallback changes (LSN-029 flip protocol noted in the protocol: on RED, intentional change ⇒ re-baseline + convert to `validates`; unplanned ⇒ investigate the leak). It is not skipped/disabled.
