    - **The operator-impact narrative — auth.type=DISABLED**: an operator runs ODD with `auth.type=DISABLED` for an internal-team demo (a permit-all deployment). `/actuator/env` is anonymously reachable from any network plane. A network attacker scanning the platform port can: (a) hit `/api/appInfo` (DOC-GAP-199) to confirm it's ODD + the precise version + auth mode; (b) hit `/actuator/env` to extract the entire resolved property source — including all 8 credential surfaces above, the JDBC URL, the S3 endpoint, the Slack/Webhook URLs.
    - **The operator-impact narrative — auth.type=LOGIN_FORM**: under LOGIN_FORM + ADMIN-for-all (DOC-GAP-218), any form-authenticated user has ADMIN authority. Per LoginFormSecurityConfiguration's permittedPaths (which does NOT permit-all `/actuator/**`), `/actuator/env` requires authentication. But any of `admin:admin`, `root:root`, or any other configured LOGIN_FORM user can authenticate and read everyone else's credentials via `/actuator/env`. The shared-secret model leaks every operator's credentials to every other operator.
    - **The operator-impact narrative — auth.type=OAUTH2/LDAP**: OAUTH2 and LDAP modes whitelist `/actuator/**` per `SecurityConstants.WHITELIST_PATHS:95-96`. So `/actuator/env` is ANONYMOUSLY READABLE under OAUTH2 + LDAP too. The same blast radius applies as DISABLED.
    - **The unmasked-Slack/Webhook-URL specific blast**: a Slack incoming webhook URL is a bearer credential for the Slack channel (anyone with the URL can post to the channel). Spring Boot's default masking does NOT include `url` in the substring list; `notifications.receivers.slack.url` is unmasked. A network attacker who reaches `/actuator/env` can hijack the Slack channel by reading the URL verbatim and posting their own messages. Operator-impact: alerts can be silenced (DROP from the webhook receiver) AND impersonated (POST attacker-controlled "this alert is resolved" messages).
    - **The unmasked-auth.login-form-credentials specific blast**: the LOGIN_FORM credentials string is the ENTIRE user store under LOGIN_FORM mode. Under any auth mode that permits-all `/actuator/**` (DISABLED, OAUTH2 whitelist, LDAP whitelist), the entire user-credential set is anonymously readable.
    - **The compound with DOC-GAP-218 (LOGIN_FORM no AuthorizationCustomizer)**: under LOGIN_FORM, the leaked credentials grant ADMIN access bypassing RBAC. Any attacker reading `/actuator/env` gains MULTIPLE ADMIN sessions.
    - **The structural insight (4-sidecar config-class triangulation)**: batch X surfaces THIS finding via FOUR distinct config-class sidecars all converging on the same actuator-env exposure surface. The pattern is: every config-class that consumes a `@Value`-injected credential carries the leak; the leak is centralised at `application.yml:226-240`. Fixing the leak at the central config closes ALL credential families simultaneously; per-family fixes (e.g., annotating individual `@Value` fields with `@Sensitive`) would require N changes for N credentials.
