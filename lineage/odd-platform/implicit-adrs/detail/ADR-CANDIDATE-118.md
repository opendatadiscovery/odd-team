## ADR-CANDIDATE-118 — Single-hop lineage scope for owner-anchored views is encoded via `LineageDepth.empty()` (depth=-1 sentinel), not via an explicit `depth=1` factory or a recursive-CTE `depth=1` parameter

**Classification**: promote (borderline_flag — see wisdom test)
**Severity**: MEDIUM
**Pillars affected**: [P-05-data-lineage, P-01-data-discovery, P-09-security-access-control]
**Support**: 2 sidecars (batch M `getMyObjectsWithUpstream` + batch M `getMyObjectsWithDownstream`) — both members of the lineage-variant pair use `LineageDepth.empty()` at `DataEntityRelationsServiceImpl.java:34`; the encoding (depth=-1, empty=true) propagates through `ReactiveLineageRepositoryImpl.java:174` where the recursive CTE termination predicate `tDepth.lessThan(lineageDepth.getDepth())` becomes `tDepth < -1` (never true), terminating recursion after the seed step.
**Batch**: M (2026-05-19)

**Surfaced by**:
- `odd-platform__java__DataEntityController__controller-method__getMyObjectsWithUpstream.md:implicit_adrs.[1]` (HIGH) — "Single-hop lineage expansion via `LineageDepth.empty()` — explicit choice to bound the response. The depth passed to `getLineageRelations` is `LineageDepth.empty()` (`LineageDepth.java:16-18`: depth=-1, empty=true), which makes the recursive CTE's WHERE clause `tDepth.lessThan(-1)` always false (`ReactiveLineageRepositoryImpl.java:174`) — the recursion never fires. The maintainer chose single-hop scope deliberately: the UI use case is the home-page `Recommended -> Upstream dependents` panel showing 5 entities (`OwnerEntitiesList.tsx:59` hardcodes `size: 5`), and a deep traversal would produce O(graph-size) results irrelevant to the panel's purpose. A future requirement to show 'all upstream lineage of my objects' would need a different endpoint (or a `depth` query parameter) — the current design does not accommodate that."
- `odd-platform__java__DataEntityController__controller-method__getMyObjectsWithDownstream.md:implicit_adrs.[2]` (MEDIUM) — "One-hop traversal encoded via `LineageDepth.empty()`, not `LineageDepth.of(1)`. The relations service hard-codes `LineageDepth.empty()` at DataEntityRelationsServiceImpl.java:34. ... the recursion terminates after the seed step. The maintainer chose the `empty()` semantic to mean 'seed-only edges' rather than `of(1)` to mean 'one hop' — subtle but consequential: a future refactor changing the CTE termination to `lessThanOrEqual` would silently expand this endpoint to two hops because the `empty()` flag is not consumed as a special case, only the `-1` integer value is."

**Decision statement**: ODD's owner-anchored lineage variants (`/my/upstream` and `/my/downstream`) bound their lineage expansion to **single-hop only** by passing the magic value `LineageDepth.empty()` (which produces `new LineageDepth(-1, true)` per `LineageDepth.java:16-18`) into `getLineageRelations`. The recursive-CTE termination at `ReactiveLineageRepositoryImpl.java:174` (`tDepth.lessThan(lineageDepth.getDepth())`) becomes `tDepth < -1`, which is never true at depth=0 (the seed) or beyond, so the recursive UNION ALL never fires and only the seed step's one-hop edges materialise.

The decision composes:
- **(a) Single-hop is the right scope for the UI use case**: The home-page `Recommended` panel renders 5 upstream + 5 downstream entities (`OwnerEntitiesList.tsx:59` hardcodes `{ page: 1, size: 5 }`). A deep traversal would materialise O(graph-size) edges before SQL pagination clips to size=5 — the maintainer chose to bound work at the CTE level, not at the SQL-pagination level.
- **(b) The encoding is via `LineageDepth.empty()`, not via `LineageDepth.of(1)`**: The class exposes TWO factory methods (`LineageDepth.of(int)` accepting any integer, `LineageDepth.empty()` returning the (-1, true) sentinel). The maintainer chose the named factory `empty()` over the parameterised `of(1)` — semantically signalling "this is the no-recursion case", but using the magic depth value to disable the recursion.
- **(c) The class signature suggests an explicit empty=true branch but the CTE does NOT consult it**: `LineageDepth` is a record `(int depth, boolean empty)` per `LineageDepth.java:8-19`; only the `int depth` field is read by the CTE termination predicate (REFACTOR-242 NEW; same-batch finding from REFACTOR-242 at batch H). The class signature documents an intent that the code does not enforce — the `boolean empty` field appears vestigial.

**Wisdom test**: PASS with borderline_flag. The decision IS architectural (the choice of single-hop scope is structural for the UI's owner-anchored discovery surface); the IMPLEMENTATION is borderline (sentinel-encoded rather than explicit-branch). Both lenses are valid:
1. **As an ADR (the SCOPE decision)**: PASS — intentional (the `LineageDepth.empty()` factory exists and is named to signal intent), structural (affects every `/my/upstream` and `/my/downstream` response — capping breadth at single-hop is what makes the endpoints serve the home-page panel rather than a graph-traversal API), and structural-change (lifting to multi-hop would require a depth query parameter, a different SQL plan, a different response-size budget).
2. **As a refactoring gap (the IMPLEMENTATION encoding)**: REFACTOR-242 NEW (batch H) already covers — the `boolean empty` field appears vestigial; the recursion termination is by magic value; a future change to the CTE predicate (`lessThanOrEqual` instead of `lessThan`) silently doubles the scope without any test signal.

The borderline_flag carries because BOTH a positive design choice (single-hop scope) AND an implementation gap (sentinel encoding) live in the same surface. The ADR captures the design intent; REFACTOR-242 captures the implementation gap. Surface BOTH separately — the ADR is the prescription, the refactor is the gap the prescription does not defend.

**Evidence**:
- getMyObjectsWithUpstream.md says: "`DataEntityRelationsServiceImpl.java:34` (`LineageDepth.empty()` passed verbatim) + `LineageDepth.java:8-19` (the empty=true / depth=-1 encoding) + `ReactiveLineageRepositoryImpl.java:174` (the `tDepth.lessThan(lineageDepth.getDepth())` gate) — intent_anchor: '`LineageDepth.empty()` is a static factory method explicitly named `empty()`, semantically signaling no recursion; the `boolean empty` field is distinct from `int depth = -1` (depth=-1 alone could be misread as unlimited); the dual-encoding makes the maintainer's intent unambiguous'"
- getMyObjectsWithDownstream.md says: "DataEntityRelationsServiceImpl.java:34 (`LineageDepth.empty()` call) + LineageDepth.java:16-18 (the `-1, true` sentinel) + ReactiveLineageRepositoryImpl.java:174 ... intent_anchor: '`LineageDepth.empty()` is the only call site that uses the `empty=true` flag; the recursive-CTE termination predicate ignores the flag and reads only the int depth value — the maintainer's choice of the empty() factory over of(1) is structural (factory method exists with a distinct name) but the CTE doesn't honour the distinction'"

**Existing ADR**: none. **Composes with ADR-CANDIDATE-117** (owner-anchored lineage neighbourhood — this ADR is the SCOPE bound for that ADR's phase-2 expansion). **Composes with ADR-CANDIDATE-072** (recursive-CTE lineage depth + progressive expansion — the per-entity lineage endpoints use `LineageDepth.of(depth)` for client-driven depth; the owner-anchored endpoints use `LineageDepth.empty()` for server-fixed single-hop; the two factories serve two distinct UX semantics).

**Cross-link gaps** (refactoring-scopes anchored on consequences this ADR DOES NOT defend):
- **REFACTOR-242 STRENGTHENED** (batch M): `LineageDepth.empty()` semantics are call-site folklore — the `empty` flag is never read; only the `-1` value matters. This ADR's design DEPENDS on the `tDepth.lessThan(-1)` predicate behaving as today; a future refactor changing the predicate silently violates the single-hop contract. The gap is the implicit-vs-explicit encoding.

**Proposed action**: Promote to `adrs/drafts/owner-anchored-lineage-single-hop-scope.md` (new ADR). Document: (a) the single-hop scope choice for the `/my/upstream` and `/my/downstream` endpoints, anchored on the UI's home-page panel use case; (b) the dual factory pattern (`LineageDepth.empty()` for single-hop vs `LineageDepth.of(N)` for client-driven depth) as the structural difference between owner-anchored views and per-entity lineage views; (c) the trade-off: the scope is server-fixed (operators cannot widen via query parameter); a future "deep lineage of my objects" use case requires a new endpoint or a depth parameter on these endpoints. Doc-side: the live `/features/data-lineage` page should disclose the single-hop scope and the contrast with per-entity `?lineage_depth=N`. Cross-link the implementation gap REFACTOR-242 as the maintainability cost — collapse the dual-encoding to an explicit `seedOnly()` factory + remove the dead `boolean empty` field, while preserving the architectural decision codified here.

**Severity rationale**: MEDIUM — pattern-shaping decision visible at the dual-factory layer; affects two endpoints' contracts; the implementation encoding gap (REFACTOR-242) is a known maintainability cost but does not invalidate the architectural decision.
