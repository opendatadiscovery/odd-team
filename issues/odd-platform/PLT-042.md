## What

The lineage depth control on `/api/dataentities/{id}/lineage/{up,down}stream` is layered across 5 surfaces - UI dropdown, URL parser, controller, service, repository - but only ONE layer validates the input. The other four hand the value through unchanged. This is the LSN-001 (attachment-storage default) failure shape applied to a recursive-CTE walk parameter; without defence-in-depth, an operator manually editing `?d=10000` triggers a 10000-depth recursive-CTE walk against Postgres with no defence at any layer.

**Layer 1 - UI dropdown.** `odd-platform-ui/src/components/DataEntityDetails/Lineage/HierarchyLineage/lineageLib/constants.ts:97-99` declares `export const lineageDepth = [1, 2, 3, 4, ..., 20]` - the dropdown options. **APPEARS to be the safety boundary.**

**Layer 2 - URL parser.** `odd-platform-ui/src/lib/hooks/useQueryParams.ts:36` calls `parse(queryStr, { ...queryStringOptions, parseNumbers: true, parseBooleans: true })`. The `parseNumbers: true` setting accepts ANY positive integer unclamped from `?d=`. **The URL is the actual contract.**

**Layer 3 - Click-through propagation.** `odd-platform-ui/src/components/DataEntityDetails/Lineage/HierarchyLineage/.../Node.tsx:46-52` propagates `d: node.depth || 1` to the new URL on graph-node click. If the user previously set `?d=50` via URL edit, click-through preserves 50 - bypassing the dropdown cap entirely. **The dropdown is never consulted on propagation.**

**Layer 4 - Controller.** Verified 2026-06-10: the cap lives in the OpenAPI spec, which declares `lineage_depth` with `minimum: 1` and **no `maximum`** for both `getDataEntityUpstreamLineage` (`odd-platform-specification/openapi.yaml:1260-1266`) and `getDataEntityDownstreamLineage` (`:1294-1300`). The codegen surfaces that as `@Min(1)` with no `@Max` on the generated `DataEntityApi` interface; the impl `DataEntityController.getDataEntityUpstreamLineage`/`getDataEntityDownstreamLineage` (`DataEntityController.java:256-271`) takes a plain `Integer lineageDepth` and forwards it. (This replaces the original "verify exact line in your tree" hedge - the cap's true home is the spec.)

**Layer 5 - Service.** `odd-platform-api/src/main/java/.../service/LineageServiceImpl.java:87-91` - `getLineage(final long dataEntityId, final int lineageDepth, ...)` takes a primitive `int` and wraps it as `LineageDepth.of(lineageDepth)` (`:96`). Verified 2026-06-10 that `LineageDepth.of` is a pure constructor wrapper with **no clamp** (`dto/lineage/LineageDepth.java:12-14`); no `Math.min(...)` anywhere in the read body.

**Layer 6 - Repository.** `ReactiveLineageRepositoryImpl.getLineageRelations(rootOddrns, LineageDepth, streamKind):122-126` builds a `DSL.withRecursive(...)` CTE whose recursion bound is the depth directly: `.where(tDepth.lessThan(lineageDepth.getDepth()))` (`:174`). A depth of 10000 recurses up to 10000 levels - no guard.

**Net effect.** Operators reading `docs.opendatadiscovery.org/developer-guides/api-reference/lineage` (`minimum 1`) + seeing the 20-entry dropdown reasonably assume the platform enforces 20 as a hard cap. The actual hard cap is the JVM/Postgres timeout. Cycle-diamond amplification (DOC-GAP-105 family) further compounds the cost - depth x cycle-graph-shape x no-cycle-guard.

## User-facing impact

WHO: any caller of `/api/dataentities/{id}/lineage/{up,down}stream` - an authenticated user editing the URL, an API/curl consumer, or anyone on the network under `auth.type=DISABLED`.

- **"No depth cap at any layer" - verified by full-chain trace 2026-06-10; structurally settled.** UI dropdown tops out at 20 (`constants.ts:97-99`), but the URL parser accepts any positive int (`useQueryParams.ts:36` `parseNumbers: true`), the spec/controller enforce only `@Min(1)` (`openapi.yaml:1260-1266,1294-1300`), the service does not clamp (`LineageServiceImpl:88-96` + `LineageDepth.of` no-op), and the repository feeds the value straight into a recursive CTE bound (`ReactiveLineageRepositoryImpl:174`). So `?lineage_depth=10000` (API) or `?d=10000` (UI URL, propagated by `Node.tsx:51` with no `Math.min`) reaches Postgres unclamped. This is a pure code-structure fact - no layer rejects it.
- **The performance consequence - static trace consistent; NOT driven.** Whether a deep walk actually exceeds the transaction timeout or pegs a Postgres connection depends on the graph's size, fan-out, and cycle shape - it needs a live drive against a non-trivial lineage graph to quantify. The exact remaining check: `curl '.../lineage/downstream?lineage_depth=10000'` against a seeded multi-hop/cyclic graph and observe latency / connection state / whether it 500s on timeout. `user_facing_verified` stays false for that reason. The observable for a SMALL graph is benign (recursion terminates when relations run out); the risk is large/cyclic graphs.

## Why

Same shape as LSN-001 (attachment-storage default - what the operator sees vs what the system accepts). The UI dropdown is a presentation-only safety boundary. Operators following the dropdown reasonably believe 20 is the hard cap; the actual exposure surface includes any caller who can edit the URL.

**Operational pressure**: a single curl-with-`?d=10000` against `/api/dataentities/{id}/lineage/downstream` can produce a recursive-CTE walk that exceeds the transaction timeout (or pegs the Postgres connection); chronic accidental setting (URL pasted from a colleague, copy-paste from CI logs) silently degrades platform performance.

## How

Two-line defence-in-depth fix:

1. **Controller - add `@Max(20)`** (or extract a constant `LINEAGE_DEPTH_HARD_CAP` if the cap may need tuning):
   ```java
   public Mono<ResponseEntity<DataEntityLineage>> getDataEntityUpstreamLineage(
       Long dataEntityId,
       @Min(1) @Max(20) Integer lineageDepth,  // <- ADD @Max
       ...
   ) { ... }
   ```
   Same edit on `getDataEntityDownstreamLineage` + any other lineage handler taking `lineageDepth`.

2. **UI click-through - clamp to dropdown cap on `Node.tsx`:**
   ```tsx
   // Before:
   navigate(dataEntityLineagePath(entityId, { ...defaultLineageQuery, d: node.depth || 1 }));
   // After:
   navigate(dataEntityLineagePath(entityId, { ...defaultLineageQuery, d: Math.min(node.depth || 1, 20) }));
   ```
   Same shape on any sibling click-through callsite under `HierarchyLineage/` that propagates `d` to a new URL.

Optional polish: lift `20` into a shared constant (`HARD_LINEAGE_DEPTH_CAP`) exposed on both UI and API tiers so the value is single-sourced.
