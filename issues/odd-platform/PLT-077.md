## What

`AppInfoController.java:18` reads `@Value("${auth.type}") final String authType` - no `@NotBlank`, no enum constraint, no default. If an operator unsets the key (empty env var) OR typos (`OUATH2`, `LOGINFORM`), every `@ConditionalOnProperty(value="auth.type", havingValue=...)`-gated `SecurityWebFilterChain` config fails to match: `DisabledAuthSecurityConfiguration` (`DISABLED`, `:10`) / `LoginFormSecurityConfiguration` (`LOGIN_FORM`, `:31`) / `OAuthSecurityConfiguration` (`OAUTH2`, `:71`) / `LDAPSecurityConfiguration` (`LDAP`, `:51`). None wire, so the application defines no user `SecurityWebFilterChain` bean - and crucially none of these also activates `@EnableWebFluxSecurity` (it sits only on the LOGIN_FORM / OAUTH2 / LDAP configs).

**The resulting posture is the OPPOSITE of "unguarded" (see ## How discovered).** `spring-boot-starter-security` is on the classpath (`gradle/libs.versions.toml:52,126` - the `spring` bundle). With reactive Spring Security present and NO user chain + NO active `@EnableWebFluxSecurity`, Spring Boot's `ReactiveSecurityAutoConfiguration` / `WebFluxSecurityConfiguration` contributes a **default chain that authenticates every exchange** (HTTP Basic / form login, with a generated default password). So a typo'd `auth.type` boots a platform that is **locked closed** - every endpoint requires credentials the operator never configured - not an anonymously-reachable one. No `spring.autoconfigure.exclude` of that autoconfig exists (checked `application.yml`).

The real, surviving defect is therefore: `auth.type` is unvalidated, so a typo **silently fails closed** (default-secured lockout) at boot with no descriptive error - a deployment-time footgun, but a fail-CLOSED one (availability/diagnosability), not the fail-OPEN security hole originally asserted.

FE note: `Overview.tsx:25-27` - `Boolean(appInfo?.authType && appInfo.authType !== 'DISABLED')` is genuinely a loose comparison (empty string -> `false` hides OwnerAssociation; any typo'd non-DISABLED value -> `true` shows it). But its practical effect under a typo is moot: `/api/appInfo` is itself behind the default-secured chain, so the SPA cannot reach the point of rendering Overview at all in a locked-out deployment.

## User-facing impact

- Verified by BE trace 2026-06-10: a typo'd / empty `auth.type` activates none of the four `@ConditionalOnProperty(value="auth.type")` security configs (`DisabledAuthSecurityConfiguration:10`, `LoginFormSecurityConfiguration:31`, `OAuthSecurityConfiguration:71`, `LDAPSecurityConfiguration:51`; no unconditional `SecurityWebFilterChain` bean exists in the source tree). With `spring-boot-starter-security` on the classpath (`libs.versions.toml:52,126`) and no `@EnableWebFluxSecurity` active, Spring Boot's reactive security autoconfig supplies a default authenticated chain -> the deployment is **locked out**, not open. Static trace consistent; not driven (cannot reconfigure/restart the shared stack from here) - remaining check: a one-shot boot with `AUTH_TYPE=typo` to capture the actual 401/redirect on `/api/appInfo`.
- Operator-facing consequence: a typo'd `auth.type` yields a platform nobody can log into (no usable credentials), with no clear "auth.type=X is invalid" message - a startup-debugging trap. NOT the "same anonymously-reachable surface as DISABLED" the issue originally claimed.
- Auth mode: this is the auth-mode-selection bug itself; the failure is the absence of any of the four intended modes (the autoconfigured fallback is not one ODD configures).

## Why it matters

Low - downgraded from medium 2026-06-10, and the `security_sensitive` exposure framing is withdrawn: a typo'd `auth.type` fails CLOSED into Spring's default-secured chain (a lockout / availability + diagnosability problem), not an anonymous-exposure hole. It is still a real deployment-time footgun worth a fail-fast - an operator should get "auth.type=OUATH2 is not one of DISABLED/LOGIN_FORM/OAUTH2/LDAP" at startup rather than a mysteriously un-loginable platform - but it is not the LSN-001-class silent-exposure defect originally asserted.

## Suggested fix

**Option A - @Pattern annotation on @Value (recommended, simplest).**

```java
// AppInfoController.java (and other readers if they exist)
@Value("${auth.type}")
@Pattern(regexp = "DISABLED|LOGIN_FORM|OAUTH2|LDAP", message = "auth.type must be one of DISABLED, LOGIN_FORM, OAUTH2, LDAP")
private String authType;
```

Spring's `@Pattern` validator runs at boot if `@Validated` is on the class.

**Option B - Enum-typed @ConfigurationProperties (more idiomatic Spring 3).**

```java
@ConfigurationProperties(prefix = "auth")
public record AuthProperties(AuthType type) {
    public enum AuthType { DISABLED, LOGIN_FORM, OAUTH2, LDAP }
}
```

Spring boot would fail-fast at startup if `auth.type` is unset or unparsable.

**Option C - @PostConstruct startup self-check (defensive).**

```java
@PostConstruct
void validateAuthType() {
    Set<String> validValues = Set.of("DISABLED", "LOGIN_FORM", "OAUTH2", "LDAP");
    if (!validValues.contains(authType)) {
        throw new IllegalStateException("auth.type=" + authType + " is not a valid value. Use one of: " + validValues);
    }
}
```

Recommended Option B - Spring 3 idiomatic; one place owns the contract; type-safe at compile time for downstream readers.

UI defence-in-depth: tighten `Overview.tsx:25-27` to whitelist auth-types:

```tsx
const validAuthType = ['LOGIN_FORM', 'OAUTH2', 'LDAP'].includes(appInfo?.authType);
```
