## What

`PUT /api/dataentities/{data_entity_id}/description` against a data-entity id that **does not exist** (e.g. a typo'd or stale id) returns **HTTP 200 OK** with the submitted description echoed back in the body - as if the write succeeded - when in fact nothing was written. The UPDATE matches zero rows, the reactive chain short-circuits on an empty result, and the controller still completes the exchange as a success. Two things go silent at once: (1) the client gets a `200` and a plausible-looking body for a write that never landed, and (2) no `DESCRIPTION_UPDATED` activity event is emitted (the activity handler is downstream of the short-circuit), so the no-op is invisible in the audit/activity feed as well. The **sibling** endpoint for dataset-field descriptions, written in the same style, correctly returns `404` for a missing field.

## Where

The miss is a missing `switchIfEmpty` on the entity-description update. Chain, top to bottom:

```java
// controller/DataEntityController.java:203 - completes as 200 even when the service emits empty
public Mono<ResponseEntity<InternalDescription>> upsertDataEntityInternalDescription(...) {
    return internalDescriptionFormData
        .flatMap(form -> dataEntityService.upsertDescription(dataEntityId, form))
        .map(ResponseEntity::ok);   // never invoked on empty -> WebFlux sends default empty 200
}
```

```java
// service/DataEntityInternalStateServiceImpl.java:55 - @ActivityLog is here; it never fires on a no-op
@ReactiveTransactional
@ActivityLog(event = ActivityEventTypeDto.DESCRIPTION_UPDATED)
public Mono<DataEntityPojo> updateDescription(... final long dataEntityId, ...) {
    return dataEntityRepository.setInternalDescription(dataEntityId, formData.getInternalDescription())
        .flatMap(pojo -> ...)   // no switchIfEmpty -> empty Mono propagates, downstream never runs
        ...
}
```

```java
// repository/reactive/ReactiveDataEntityRepositoryImpl.java:432 - UPDATE ... WHERE id = ? RETURNING
@Override
public Mono<DataEntityPojo> setInternalDescription(final long dataEntityId, final String description) {
    final String newDescription = StringUtils.isEmpty(description) ? null : description;
    final var query = DSL.update(DATA_ENTITY)
        .set(DATA_ENTITY.INTERNAL_DESCRIPTION, newDescription)
        .where(DATA_ENTITY.ID.eq(dataEntityId))   // <-- 0 rows on a missing id
        .returning();
    return jooqReactiveOperations.mono(query)     // <-- emits EMPTY, not an error, on 0 rows
        .map(r -> r.into(DataEntityPojo.class));
}
```

Contrast - the dataset-field sibling, identical shape but with the guard present, so it **does** 404:

```java
// service/DatasetFieldInternalInformationServiceImpl.java:32
return reactiveDatasetFieldRepository.updateDescription(datasetFieldId, formData.getDescription())
    .switchIfEmpty(Mono.error(new NotFoundException("DatasetField", datasetFieldId)))   // <-- the guard PLT-169 is missing
    .flatMap(pojo -> ...);
```

## Why it matters

This is a **silent** correctness defect on a write endpoint. A client (or a generated SDK) that PUTs a description to the wrong id receives an unqualified success and a body that looks saved - the operator believes the documentation/description was applied when it was discarded. Because the `DESCRIPTION_UPDATED` activity event is skipped, the no-op also leaves no trace in the activity log, so it cannot be reconstructed after the fact. It is not data loss (no existing data is overwritten) and not a security hole, but it is a write that lies about its outcome, and the platform already proves it knows the right pattern one endpoint over. The inconsistency between the two sibling endpoints is itself a defect - a client cannot rely on uniform not-found semantics across the description APIs. Severity medium.

## Suggested fix

Add the same guard the dataset-field path already has, so a missing entity becomes a real not-found:

```java
// DataEntityInternalStateServiceImpl.updateDescription (or in DataEntityRepositoryImpl.setInternalDescription)
return dataEntityRepository.setInternalDescription(dataEntityId, formData.getInternalDescription())
    .switchIfEmpty(Mono.error(new NotFoundException("DataEntity", dataEntityId)))
    .flatMap(pojo -> ...);
```

This both restores the 404 and lets the `@ActivityLog`/downstream chain behave correctly (it simply never runs on the error path, which is correct). Note the `404`-vs-caveat decision is a maintainer call - if upsert-on-missing is ever intended to be a legitimate create, that should be explicit and documented rather than a silent 200 no-op; the dataset-field sibling's 404 is the strong precedent for choosing 404. Open to alternatives.
