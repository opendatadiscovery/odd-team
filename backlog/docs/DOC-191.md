## Description

This is the **single most operator-load-bearing item from batch-10** — the live `docs.opendatadiscovery.org/features/data-discovery/statuses` page promises behaviour that the code does not deliver. The doc says:

> *"the platform's housekeeping job permanently deletes a `DELETED` entity ... only after the entity's status-update timestamp is older than `housekeeping.ttl.data_entity_delete_days`. The default window is **30 days**."*
>
> *"after the 30-day TTL expires, the next housekeeping run performs a hard delete, removing the entity and every cascading row attached to it."*

The code does NOT do this.

**Caveat 1 — SHB-004 mapper bug breaks the 30-day retention promise (F-044a).** `DataEntityMapperImpl.java:241-253` `applyStatus` method:
- Line 247: `pojo.setStatus(statusDto.getId());` — sets new status FIRST.
- Line 249: `if (statusDto.getId() != pojo.getStatus())` — guard runs AFTER the assignment. `pojo.getStatus()` now equals `statusDto.getId()`. The guard is **always false**.
- Line 250: `pojo.setStatusUpdatedAt(...)` — **never reached**.

Every status transition (manual PUT + scheduled auto-flip + ingestion replay) leaves `status_updated_at` NULL. The Housekeeping TTL key (`DataEntityHousekeepingJob.java:73-82` — `STATUS_UPDATED_AT.lessOrEqual(now - data_entity_delete_days)`) NEVER matches a NULL value in SQL three-valued logic. **The DELETED row, plus all its cascading metadata + lineage + tags + terms + ownership + statistics, persists forever.**

Operator-visible consequences:
- The doc PROMISES "permanent deletion after 30 days." The code DELIVERS "soft-delete forever."
- An operator counting `WHERE status = 'DELETED'` sees the count monotonically grow.
- Storage planning based on the documented retention is silently wrong; the table grows unbounded.
- FK references to deleted entities stay live; statistics rollups remain skewed.
- The `isStale` flag continues to render for "deleted" entities.
- Compliance-driven retention policy ("we delete data 30 days after retire") is silently false — legal exposure if operators trust the doc.

**Caveat 2 — Scheduled auto-flip has no per-tick batch cap (F-044b).** `ReactiveDataEntityRepositoryImpl.getPojosForStatusSwitch:256-262` issues an unbounded SELECT — no LIMIT clause. `DataEntityStatusSwitchJob.java:21-31` runs at fixed-rate 10 minutes under a 9-minute ShedLock. A backfill that DRAFT-marks 5K entities + sets `status_switch_time` an hour out triggers a single-transaction bulk flip processing 5K pojos × cascade fan-out — potentially exceeding the 9-minute lock window; the job completes but the next tick skips, creating phantom-double-tick latency. The doc is silent on the cadence (10 min), the lock window (9 min), and the burst behaviour.
