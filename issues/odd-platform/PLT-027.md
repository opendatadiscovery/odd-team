## What

**The docs promise. The code does not deliver.**

The live page at `docs.opendatadiscovery.org/features/data-discovery/statuses` states (WebFetched 2026-05-27):

> *"the platform's housekeeping job permanently deletes a `DELETED` entity ... only after the entity's status-update timestamp is older than `housekeeping.ttl.data_entity_delete_days`. The default window is 30 days."*
>
> *"after the 30-day TTL expires, the next housekeeping run performs a hard delete, removing the entity and every cascading row attached to it."*

The code does NOT do this.

**The mapper bug.** `DataEntityMapperImpl.java:241-253` `applyStatus` method:

```java
// Line 247: mutate FIRST
pojo.setStatus(statusDto.getId());

// Line 249: guard runs AFTER the mutation - always false
if (statusDto.getId() != pojo.getStatus()) {
    // Line 250 - NEVER REACHED
    pojo.setStatusUpdatedAt(OffsetDateTime.now());
}
```

`pojo.getStatus()` on line 249 returns the value just written on line 247. The condition is always false. Line 250 (`setStatusUpdatedAt`) is **never reached**. Every status transition - manual PUT, scheduled auto-flip, ingestion replay - leaves `status_updated_at` NULL.

**The TTL never fires.** `DataEntityHousekeepingJob.java:73-82` issues:

```sql
WHERE STATUS_UPDATED_AT.lessOrEqual(now() - INTERVAL 'data_entity_delete_days days')
  AND STATUS = 'DELETED'
```

In SQL three-valued logic, `NULL.lessOrEqual(...)` is NULL, not TRUE - the predicate never matches the NULL value. Every entity transitioned through the mapper is **permanently excluded** from hard-delete.

**Cascading consequences.** The DELETED row + all its cascading metadata (lineage / tags / terms / ownership / statistics / lookup-table-attachments / per-column annotations / custom-metadata values) **persist forever**. FK references stay live. The `isStale` flag continues to render. The `WHERE status = 'DELETED'` count grows monotonically. Storage planning based on the documented retention is silently wrong.

**The batch-cap defect (Defect 2 - F-044b).** Separately, `ReactiveDataEntityRepositoryImpl.getPojosForStatusSwitch:256-262` issues an unbounded SELECT - no LIMIT. `DataEntityStatusSwitchJob.java:21-31` runs at fixed-rate 10 minutes under a 9-minute ShedLock. A backfill that DRAFT-marks 5K entities with `status_switch_time` an hour out triggers a single-transaction bulk flip processing 5K pojos x cascade fan-out - potentially exceeding the 9-minute lock window; the job completes but the next tick skips, creating phantom-double-tick latency.

## How to reproduce

1. Take any data entity (manual or ingested).
2. PUT `/api/dataentities/{id}/statuses` body `{ "status": "DELETED" }`.
3. Inspect the DB: `SELECT id, status, status_updated_at FROM data_entity WHERE id = ?`. `status_updated_at` is NULL.
4. Wait 30 days (or set `housekeeping.ttl.data_entity_delete_days: 0` in `application.yml` and restart for fast-iteration).
5. Run the housekeeping job. The entity is NOT hard-deleted; the `WHERE status_updated_at <= now() - interval '30 days'` predicate doesn't match NULL.
6. The DELETED row persists indefinitely.

## Suggested fix

**Thread A - Mapper code fix (Defect 1; the headline).** Reorder `applyStatus`:

```java
final var oldStatus = pojo.getStatus();
final var newStatus = statusDto.getId();
if (oldStatus != newStatus) {
    pojo.setStatus(newStatus);
    pojo.setStatusUpdatedAt(OffsetDateTime.now());
}
```

Three lines. The fix captures the previous status BEFORE the assignment, runs the comparison, then conditionally writes both fields. The behavioural fix lands in `applyStatus`; the entire status-transition chain (manual PUT + scheduled auto-flip + ingestion replay) inherits.

**Thread B - Data-fix migration (the legacy data is also stuck).** A Flyway migration backfilling `status_updated_at` for existing DELETED rows whose value is NULL. Two policy options:

- **Option B1 - conservative now() backfill.** `UPDATE data_entity SET status_updated_at = NOW() WHERE status = 'DELETED' AND status_updated_at IS NULL`. The TTL clock starts ticking from the migration moment. Effect: existing DELETED rows are hard-deletable 30 days after the migration ships. Operators expecting "everything that's been DELETED for >30 days is gone immediately" need a CHANGELOG warning.

- **Option B2 - `data_entity.updated_at`-based heuristic.** `UPDATE data_entity SET status_updated_at = updated_at WHERE status = 'DELETED' AND status_updated_at IS NULL`. The TTL clock approximates "when this row was last touched" - closer to the operator's mental model but `updated_at` may be later than the actual DELETED-transition time.

Recommend Option B1 - the conservative ship; the CHANGELOG warning is small overhead vs the cleaner semantics.

**Thread C - Per-tick batch cap on status-switch (Defect 2 - F-044b).** Add a LIMIT clause to `ReactiveDataEntityRepositoryImpl.getPojosForStatusSwitch` - recommend 200 per tick (1/25th of the 5K-burst worst case). The scheduler runs every 10 minutes; a 5K backfill drains in ~250 minutes worst-case, well within operator-tolerable latency. Add a metric (`status_switch_job.pending_count`) so operators can alert on accumulation.

## Operator impact (the headline cost)

This is the most-operator-load-bearing defect in batch-10. The doc-vs-code contradiction is verbatim. Operators who:

- **Plan storage based on the documented 30-day retention** see the `data_entity` table grow unbounded. The cascading rows (lineage / tags / terms / per-column annotations) all persist. Database storage costs grow against zero return-on-investment.
- **Operate under compliance-driven retention policy** (legal requirement to delete records 30 days after retire) discover the platform silently violated the policy. Legal exposure if operators trust the doc.
- **Reason about statistics rollups** see DELETED entities still counted. Catalog Overview tile counts include zombie rows.
- **Try to re-create an entity at a deleted oddrn** hit FK-conflict-on-re-create paths that should have cleared. Re-ingestion silently double-counts.
