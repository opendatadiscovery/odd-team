## What

The Slack Events webhook (`POST /api/slack/events`, enabled with Data Collaboration) does not validate the request body before deserializing it. When Slack — or any caller — POSTs a body that is not well-formed JSON, or whose `event` field is present but is a JSON scalar/array rather than an object, the request fails with **HTTP 500 Internal Server Error** instead of a client error (4xx). Slack's Events API treats any non-2xx, **non-3xx 5xx response as "delivery failed, retry"** and re-delivers the same event with backoff (and, on repeated 5xx, eventually disables the subscription). A genuinely malformed or unsupported payload therefore turns into a retry loop: the same un-parseable event is redelivered again and again, each attempt costing a deserialize + a 500. A 4xx tells Slack "this request is bad, do not retry" and breaks the loop.

## Where

`datacollaboration/controller/parser/SlackEventParser.java:22-23` — the raw body is handed straight to `deserializeJson` with no surrounding `try`/validation:

```java
public ParseResult parse(final String rawJson) {
    final Map<String, Object> requestMap = JSONSerDeUtils.deserializeJson(rawJson, new TypeReference<>() {
    });
```

`JSONSerDeUtils.deserializeJson(String, TypeReference)` rethrows a Jackson parse failure as a bare `RuntimeException` (`utils/JSONSerDeUtils.java:48-52` — `catch (JsonProcessingException e) { throw new RuntimeException(e); }`), so a malformed body propagates out of `parse` as an unchecked exception.

`datacollaboration/controller/parser/SlackEventParser.java:45` — once parsed, the `event` member is cast without a type check:

```java
final Map<String, Object> rawEvent = (Map<String, Object>) requestMap.get("event");
```

If `event` deserialized to a `String`, `Number`, or `List` (e.g. `{"type":"event_callback","event":"oops"}`), this throws `ClassCastException` — again an unchecked exception out of `parse`.

Both exceptions are caught only by the catch-all advice, which maps them to 500 — `controller/exception/ControllerAdvice.java:61-66`:

```java
@ExceptionHandler(Exception.class)
@ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
public ErrorResponse handleServerException(final Exception e) {
    log.error("Internal server error", e);
    return buildResponse(new ExceptionWithErrorCode(ErrorCode.SERVER_EXCEPTION, "Internal Server Error"));
}
```

There is no handler that maps a malformed-body condition to 400 here; `BadUserRequestException` → 400 exists (`ControllerAdvice.java:24-28`) but the parser never raises it. The controller's own `ParseResult.ERROR` branch (broken-payload-with-null-`event`) already returns `ResponseEntity.badRequest()` (`EventApiController.java:34-37`, `SlackEventResponse.error()` at `:53-55`), so the 400 path is the established intent for bad payloads — but it is only reached for the `event == null` case, not for un-parseable JSON or a non-object `event`.

## Why it matters

This is a **loud-but-self-amplifying** failure on an unauthenticated, internet-facing endpoint (the Slack webhook is reachable by design). A single malformed or unsupported delivery does not just fail once: Slack reads the 500 as retryable and redelivers, so one bad event becomes a sustained stream of identical 500s, each running a full deserialize attempt. Affected: any ODD deployment with Data Collaboration + a Slack subscription, where Slack (or an upstream proxy that mangles a body) sends something the parser cannot handle. It also pollutes server logs with `Internal server error` stack traces for what are really client/contract problems, masking real 500s. Severity is medium: no data loss or auth bypass, but it converts a benign bad request into avoidable, compounding load and on-call noise, and risks Slack auto-disabling the subscription after enough 5xx.

## Suggested fix

Make a malformed or structurally-wrong body a deterministic 4xx, not a 5xx, so Slack stops retrying:

1. Guard the deserialization in `SlackEventParser.parse`: catch the parse failure (or pre-validate that the body is JSON) and return a `ParseResult` of type `ERROR` instead of letting a `RuntimeException` escape — the controller already turns `ERROR` into `ResponseEntity.badRequest()`.
2. Replace the unchecked cast at `:45` with a type check (`requestMap.get("event") instanceof Map<?, ?> m ? m : <ERROR result>`), so a non-object `event` yields the same 400 rather than a `ClassCastException`.
3. Alternatively/additionally, throw `BadUserRequestException` on a malformed body so the existing `ControllerAdvice` 400 mapping applies uniformly — pick whichever keeps the parser's `ParseResult` contract clean. Open to alternatives on the exact placement.

The 4xx-vs-5xx distinction is the load-bearing behaviour; probe `PENDING-F-098-1` is queued to confirm the current 500 and the post-fix 4xx against a running stack.
