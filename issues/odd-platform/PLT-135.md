## What

On the next `POST /ingestion/datasources` that names an existing datasource ODDRN, `DataSourceIngestionServiceImpl.prepareForUpdate` **overwrites** `name` and `description` from the collector payload - silently. There is no merge-conflict check, no `lastModifiedBy` discrimination, no `log.warn`, no Activity event, and no diff in the response. An operator's deliberate UI rename ("Snowflake - Prod Finance") reverts to whatever the collector config carries ("snowflake-default") the next time the collector starts. The disjoint UI write path (`DataSourceMapper.applyToPojo`) also writes name/description, so operator-side and collector-side both write the same fields with last-writer-wins and no coordination.

This is **net_new** - tracked today only as REFACTOR-423 (no doc/issue home). It pairs with H-005 (REFACTOR-424) and the ADR-CANDIDATE-142/143 promotion but has no code-side PLT.

## Impact

An operator curates a datasource name in the UI; the next time the collector starts, the name reverts to the collector config with no warning and no audit trail to explain why. Diagnosing it requires reading the collector config AND knowing the S2S re-registration path overwrites name/description - neither visible from the UI. This is the datasource-side mirror of the platform-wide audit-silence pattern.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: at `DataSourceIngestionServiceImpl.prepareForUpdate` (lines 86-88), emit an Activity event / `log.warn` on a name/description overwrite, **or** add `lastModifiedBy` discrimination so operator UI edits are not silently reverted. Tracked today only as REFACTOR-423; pairs with H-005 (REFACTOR-424) and the ADR-CANDIDATE-142/143 promotion.
