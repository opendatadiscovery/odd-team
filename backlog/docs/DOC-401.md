## Description

`PostgreSQLLeaderElectionManagerImpl.acquire(long advisoryLockId, boolean replicationConnection)` takes a second `boolean` argument whose name is only visible in the signature — there is no javadoc. The four call-sites pass the literal `false` or `true`, and a maintainer skimming `acquire(id, false)` vs `acquire(id, true)` can easily misread the flag as a wedge-safety / blocking-vs-non-blocking toggle (e.g. "true = block, false = try-once"). That reading is wrong: the boolean selects whether `PGConnectionFactory.getConnection(replicationConnection)` returns a logical-replication connection or an ordinary one; it has **no bearing on lock semantics**. The lock acquisition is **always blocking** — the method unconditionally executes `SELECT pg_advisory_lock(<id>)` (the blocking variant) regardless of the boolean. The misread is maintainer-facing only (no operator impact), but it is exactly the kind of ambiguity that leads someone to "fix a wedge" by flipping the flag and changing nothing about the wedge.

This is a one-method javadoc clarification. It folds naturally into **PLT-089** (the advisory-lock fail-fast wrapper), which already targets this same file and already documents that the acquisition uses the blocking `pg_advisory_lock` variant.
