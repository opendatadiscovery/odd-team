## Description

The CTRIB-024 fix (odd-platform #1757, milestone 0.29.0) adds `RUNNING` as a first-class run status
(wire enum `DataEntityRunStatus` + FE `palette.runStatus`/`reportStatus`). The paired docs update
([[DOC-471]]) revised `docs/data-quality/test-run-history.md` so its status filter now lists **seven**
statuses (adds **Running**). The **sibling** page `docs/data-quality/dashboard.md` was **not** updated and
now drifts in two ways once 0.29.0 publishes:

1. **Self-contradiction (parallel surfaces with drift).** `dashboard.md:22` states the Test Results
   Breakdown ring renders "the full set is **Success, Failed, Skipped, Broken, Aborted, and Unknown** (the
   **same six statuses** as the per-test [Test Run History] status filter)". After 0.29.0 the linked Test
   Run History filter has **seven** statuses, so "the same six statuses as the per-test Test Run History
   status filter" is factually wrong and the manual contradicts itself across two linked pages.

2. **Stale behaviour (the Running slice can now render).** The dashboard counts tests by their **latest
   run's status** (`data_entity_task_last_run`). A test whose latest run is in-flight carries `RUNNING`.
   Pre-0.29.0 the FE `palette.runStatus` had no `RUNNING` key, so a RUNNING latest-status would have blanked
   the dashboard render (the PLT-052 unknown-status-blank class, but for RUNNING). The #1757 change added a
   `RUNNING` palette entry, so the dashboard can now render a **Running** slice in the Test Results Breakdown
   without crashing. The page should reflect that Running is a renderable breakdown status in 0.29.0.

This is the LSN-006 / LSN-007 "locally well-executed, globally drift-producing" class: the run-status-set
change was correct on its own page but left a linked sibling page enumerating the old set. Routed on the
documentation `release/0.29.0` train (same train as [[DOC-471]] / CTRIB-024), so it publishes with the fix —
fold into docs PR #102 or a sibling commit on `release/0.29.0`.
