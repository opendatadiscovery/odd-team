## What

The catalog **Overview** page - the first surface a user lands on after login - is structured so that layout shift (CLS) occurs after first paint. Its loading skeleton (`isLoading`) is gated on only **two** of the page's data sources (identity fetch + popular tags). The moment those two resolve, the skeleton is replaced by the real layout, but three of the page's self-fetching regions (`Domains`, `DataEntitiesUsageInfo`, `Directory`) - plus the conditional `OwnerAssociation` - fetch their own data **independently** and render literally `null` (zero height) until their requests return. They then pop in and push the content below them down.

Verified 2026-06-10 by reading each region: `Domains` returns `null` until `useGetDomains` resolves (`Domains.tsx:12`); `DataEntitiesUsageInfo` returns `null` on `isError || !usageInfo` (`DataEntitiesUsageInfo.tsx:56`); `Directory` returns `null` until `useGetDataSourceTypes` resolves (`Directory.tsx:12`). Because `isLoading` does not include any of these three fetch states (`Overview.tsx:29-32`), the skeleton is torn down while these regions are still empty, so the shift happens in the gap between "primary two resolved" and "secondary three resolved."

**Correction (2026-06-10):** an earlier revision claimed "the skeleton reserves no space for the hero." That is false - `OverviewSkeleton.tsx:34-36` explicitly reserves the hero (a `height='74px'` skeleton inside the same `pt/pb` centered grid as `MainSearch`). The skeleton also already reserves an info-bar row (4 x `height='94px'`, matching `DataEntitiesUsageInfo`) and four data-list columns (matching `Domains`/`Directory`/etc). So the issue is **not** an unreserved hero; it is (a) the geometry of the skeleton not exactly matching the loaded regions' final heights, and (b) the `isLoading` gate dropping before the secondary regions have data, so they render at zero height after the skeleton is gone. The shift is real but bounded by those regions' final heights, not "unbounded."

## Where

`odd-platform-ui/src/components/Overview/Overview.tsx` - the loading gate watches only identity + tags:

```tsx
// Overview.tsx:29 - isLoading depends on ONLY two of the page's data sources
const isLoading = React.useMemo(
  () => isIdentityFetching || isTagsFetching,
  [isIdentityFetching, isTagsFetching]
);

if (isLoading) {
  return (
    <S.Container>
      <SkeletonWrapper
        renderContent={({ randWidth }) => <OverviewSkeleton width={randWidth()} />}
      />
    </S.Container>
  );
}
```

The rendered tree (`Overview.tsx:44-61`) is the hero plus five regions; three regions self-fetch and are not represented in `isLoading` (the hero and tags ARE reserved in the skeleton):

```tsx
// Overview.tsx:44 - real layout
return (
  <S.Container>
    <Grid container justifyContent='center' sx={{ pt: 4, pb: 5 }}>
      <MainSearch mainSearch />                  {/* hero - reserved in skeleton (OverviewSkeleton.tsx:34-36) */}
    </Grid>
    <S.TagsContainer container>{tags && <TopTagsList tags={tags} />}</S.TagsContainer>  {/* gated by isLoading */}
    <Domains />                                  {/* self-fetching, returns null until loaded -> pops in */}
    <DataEntitiesUsageInfo />                     {/* self-fetching, returns null until loaded -> pops in */}
    <Directory />                                 {/* self-fetching, returns null until loaded -> pops in */}
    {isShowOwnerAssociation && (                  {/* conditional (non-DISABLED auth) + self-fetching */}
      <WithPermissionsProvider ... Component={OwnerAssociation} />  {/* allowedPermissions=[DIRECT_OWNER_SYNC] */}
    )}
  </S.Container>
);
```

`TopTagsList` is bound to `isLoading` (via `isTagsFetching`) and the hero/tags footprints are reserved by `OverviewSkeleton`. The shift comes from `Domains`, `DataEntitiesUsageInfo`, and `Directory` (and `OwnerAssociation` when shown): each manages its own fetch and renders `null` (zero height) after the skeleton is gone, until its data returns.

## User-facing impact

Static-verified, magnitude not driven. The code structure that produces a post-skeleton layout shift is confirmed: `isLoading` (`Overview.tsx:29-32`) excludes the three self-fetching regions, and each of those regions renders `null` until its own fetch resolves (`Domains.tsx:12`, `DataEntitiesUsageInfo.tsx:56`, `Directory.tsx:12`). So after the skeleton is torn down, `Domains` / `DataEntitiesUsageInfo` / `Directory` (and `OwnerAssociation` on non-DISABLED auth) appear at zero height and then push content down as their data arrives - a real, visible reflow on the landing page.

What is NOT verified here (runtime-only): the actual CLS score / shift magnitude, and how much of the shift the existing skeleton geometry already absorbs. The skeleton DOES reserve the hero, the tag row, an info-bar row, and four data-list columns (`OverviewSkeleton.tsx:34-45`), so the visible jump is the delta between those reserved footprints and the regions' real final heights, plus the always-present gap where the secondary fetches lag the primary two. Remaining check to quantify: load the running Overview page on a throttled network and measure CLS (Lighthouse) / watch the reflow; no workspace probe-run exists for this surface yet.

## Why it matters

Layout shift on the landing page is an every-user, every-load UX defect on the first surface after login: the page can jump under the cursor while the user is reaching for search or a domain card (a mis-click hazard) and it costs Core Web Vitals on the app's entry point. It is worst on a slow network or a cold catalog, where the secondary fetches lag the primary two the most, which makes it under-reported but consistently present. No data risk; a UX regression on the platform's front door. Severity **medium** (corrected from high): the shift is real and code-confirmed, but it is bounded by the secondary regions' final heights (not "unbounded"), the hero/tags are already reserved, and the magnitude is unmeasured - so it does not clear the bar for high without a driven CLS number.

## Suggested fix

The skeleton already reserves the hero, tag row, an info-bar row, and four data-list columns (`OverviewSkeleton.tsx:34-45`); the gap is that the three self-fetching regions render `null` after the skeleton is gone. Close the gap so nothing changes height after first paint:

1. Have each self-fetching region render its own fixed-height local skeleton while its data is in flight (preferred - keeps the hero/tags painting fast), so a slow `Domains` / `DataEntitiesUsageInfo` / `Directory` / `OwnerAssociation` fetch never changes the surrounding geometry. `Domains` and `Directory` currently `return ... : null` and `DataEntitiesUsageInfo` returns `null` on `!usageInfo`; replace those `null` branches with a sized placeholder.
2. **Or** fold those regions' fetch states into the page-level `isLoading` gate (`Overview.tsx:29-32`) so the shared `OverviewSkeleton` stays up until everything has data - simpler, but delays the hero/tags paint until the slowest secondary fetch returns.
3. Either way, audit that the reserved skeleton heights in `OverviewSkeleton` match each region's real final height (the residual jump is that delta).

The principle: nothing on this page should change height after first paint. Open to alternatives on whether the reservation lives in the shared `OverviewSkeleton` or in per-region local skeletons; either removes the shift.
