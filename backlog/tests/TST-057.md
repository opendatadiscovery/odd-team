## Description

`search-url-facets.spec.ts:112` — *"a class tab writes the facet to the URL + refilters; the All tab removes
it (round-1 write + round-2 removal)"* (F-017 / ST-1b, part of IT-151) — is a **load-sensitive timing flake**.

- **Observed RED (once):** in the `review-ctrib050` full **feature-complete** run (337 tests, single worker,
  SUT `odd-team-sut-revctrib050` = odd-platform `2c0bfaf3`, digest `sha256:10141b3e…`), this test **failed at
  16.6s** — a timeout on one of its assertions, at position **292/337** (i.e. after ~291 prior tests had
  loaded the single-worker box + the shared stack).
- **GREEN in isolation on the same SUT:** re-running IT-151 (`ODD_STREAM=revctrib050b
  ODD_PLATFORM_IMAGE=odd-platform:odd-team-sut-revctrib050 run-suite.sh IT-151`) → **4/4 passed**, with
  `:112` GREEN in **4.7s** (well under the 15s bound). The implementer's own isolated IT-151 run was likewise
  4/4.
- **Not attributable to the CTRIB-050 / ST-1d change:** that change is a proven **no-op** for a
  class-tab-only selection (no sidebar/enum facet selected ⇒ `resolveFacetNames` returns an empty map ⇒
  `fillResolvedFacetNames` is a no-op; `entityClasses` are skipped in the resolver). The other three
  `search-url-facets` tests (`:143`, `:186`, `:226` incl. the ST-1d assertion) and all `search-url-state`
  (ST-1a) tests passed under the same full-suite load.

### Third instance (ctrib059, 2026-08-30) — same class, DIFFERENT BUCKET (odd-platform CI unit test)

The class is **not confined to the odd-team Playwright harness**. In the `ctrib059` full
`:odd-platform-api:build` (the CI replica, 4 Gradle test workers + ~10 concurrent Testcontainers Postgres
instances), **`OpenApiDocsContractTest.platformApiGroupDocumentLoads()`** failed with
`IllegalStateException: Timeout on blocking read for 60000000000 NANOSECONDS` — **747 tests completed, 1
failed**, build RED in 23m46s.

- **GREEN in isolation on the SAME tree, idle box:** `run-platform-tests.sh --tests "*OpenApiDocsContractTest*"`
  → **3/3 PASS**, with `platformApiGroupDocumentLoads` at **17.79s** — against a **60s** bound

- **The margin measured directly (the decisive number).** Re-running the SAME full build on an otherwise idle
  box went **BUILD SUCCESSFUL in 19m7s, 747 tests / 0 failures** — and in that green run
  `platformApiGroupDocumentLoads` still took **47.808s**. So under full-suite load the operation costs ~48s
  against a 60s bound: a **~12s margin, ~2.7x slower than idle**. The test is not "occasionally slow"; it runs
  routinely within ~20% of its timeout whenever the suite is loaded, which is why it tips over intermittently.
  This is the measurement the remedy should be sized against.
- **Confirmed independently, and the margin is WORSE than measured above (`/review CTRIB-059`, 2026-08-30).**
  The reviewer's own full CI-replica build at the same commit `c49fc784` went **BUILD SUCCESSFUL in 23m27s,
  747 tests / 0 failures** — and in that green run `platformApiGroupDocumentLoads` took **58.5s against the
  60s bound**: a **1.5s margin (97.5% of the timeout consumed)**. Two independent full-suite runs on this box
  now bracket the loaded cost at ~48-59s, i.e. the test passes or fails essentially on scheduler luck. Treat
  the unit-bucket remedy as the higher-priority half of this item — a false RED here blocks a public PR.
- **The document generator is healthy:** 17.79s matches the **17.3s** healthy baseline recorded by the session
  that authored this test on the fixed springdoc 2.8.17 (`contributor/CTRIB-008.md:443`).
- **NOT the PLT-141 bug re-appearing:** that bug hangs **both** group documents (`CTRIB-008.md:274` /
  `state/PROGRESS.md`: "60s `Timeout on blocking read` **x2 groups** captured verbatim"). Here the sibling
  `ingestionApiGroupDocumentLoads` and `swaggerConfigListsBothGroups` both PASSED in the same class — only the
  large `platform-api` document (191 operations) exceeded the bound.
- **Not attributable to CTRIB-059** (snapshotted `popularity_score`, #1839 ST-5c): the change adds no
  controller, no `@ControllerAdvice`, and no request mapping, so it cannot alter the OpenAPI document; and the
  test passes with the change present.

### Fourth instance (/review CTRIB-059, 2026-08-30) — the INVERSE shape: deterministically RED **cold**, and change-independent

`swagger-openapi-discovery.spec.ts:63` (IT-042, `F-097` — the `@regresses #1759`/PLT-141 guard) failed in the
reviewer's own `feature-complete` run at `test-results` line 77: the bare un-grouped `/api/v3/swagger-ui.html`
document did not return within the helper's **8s** bound (`fetchOpenApiDocument`, `swagger-openapi-discovery.spec.ts:35`
— a `catch` turns the timeout into `ok:false`, so the failure reads as "the document must load", not "it was slow").

**Measured, not argued — and it is NOT a load flake:**

| run | SUT | result |
|---|---|---|
| `feature-complete` (321/16, 32.1m, warm suite) | reviewed `c49fc784` | RED at `:77` — the two GROUP docs passed, the bare un-grouped one timed out |
| `run-suite.sh IT-042` **cold, idle box** | reviewed `c49fc784` | RED **earlier**, at `:71` — even the FIRST group doc exceeded 8s |
| `run-suite.sh IT-042` **cold, idle box** | `origin/main` `00b03129` (no ST-5c) | RED identically at `:71` |

So the bound is below springdoc's **cold first-build** cost: the unit bucket measures that same document build at
**17.8s idle / 47.8-58.5s under load** against its own 60s bound. IT-042 therefore passes only when an earlier spec
in the suite has already warmed springdoc — an **order-dependent** test, not a flaky one. It went GREEN in the
implementer's `feature-complete` run and RED in the reviewer's purely because of what ran before it.

**Change-independent (A/B on two images).** Identical failure on a SUT built from `origin/main`, which carries no
`V0_0_100` and no `AssetPopularitySnapshotJob` (verified by listing the migration + class inside both images).
Nothing to file upstream; the platform serves both grouped documents correctly — the unit-bucket
`OpenApiDocsContractTest` was 3/3 GREEN at the same commit.

**Why this instance raises the priority of a suite-level remedy:** the two earlier instances false-RED a *local*
regression run (costing reviewer time). This one false-REDs **odd-platform CI**, where a RED build blocks a PR
and is visible to upstream maintainers — the cost lands on the public project, not just on us. The remedy shape
also differs by bucket: the unit instance is a **fixed 60s client bound on a genuinely slow (~18s) operation**
under worker contention, not a chain of UI settles.

**Why it flakes:** `:112` is the most fragile of the four facet tests — it drives a full **round-1 write +
round-2 removal** cycle with **6 separate `{ timeout: 15_000 }` assertions**, each a UI-settle wait. Under
full-suite load (single Playwright worker, shared odd-minimal stack), one settle can exceed 15s. With
`playwright.config` `retries: 0` ("a regression pin must never be masked by a retry"), a single slow settle
becomes a hard RED — so this will **intermittently false-RED `feature-complete`** for every future
contributor/reviewer run, wasting exactly the maintainer/reviewer time the regression harness exists to save.

### Seventh instance (ctrib062 rework / #1842 ST-8, 2026-08-31) — a SECOND unit-bucket test, and it passes by three seconds

`LoadIngestionTest.testInjectingManyDataEntities` joins this class. It is **not** recorded above, so a stream
hitting it had nothing to check against.

**How it surfaced.** The rework's full `:odd-platform-api:build` came back **774 tests, 2 failed** — the
already-tracked `OpenApiDocsContractTest.platformApiGroupDocumentLoads` *and* `LoadIngestionTest`, both
`IllegalStateException: Timeout on blocking read for 60000000000 NANOSECONDS`. checkstyleMain, checkstyleTest,
assemble and bootJar all passed; only `test` failed.

**The A/B, decision rule pre-registered before the run** (this item's own §Fifth/§Sixth lesson: a conclusion
reached after seeing the number is not a conclusion). Same targeted pair, same box, same command:

| test | A: rework `991e0499` | B: base `82e7e70e` | A/B |
|---|---|---|---|
| `LoadIngestionTest.testInjectingManyDataEntities` | **57.02s** | 33.66s | 1.69x |
| `OpenApiDocsContractTest.platformApiGroupDocumentLoads` | 32.92s | 19.22s | 1.71x |
| `OpenApiDocsContractTest.ingestionApiGroupDocumentLoads` | 3.34s | 2.18s | 1.53x |
| `OpenApiDocsContractTest.swaggerConfigListsBothGroups` (**control**) | 7.17s | 4.39s | **1.63x** |

**Verdict: GREEN on both arms ⇒ the two build failures are load-driven, not caused by the change.** That is
the pre-registered reading and it is the whole answer to the question that was asked.

**The A-vs-B ratios are NOT evidence of a regression, and must not be quoted as one.** Every measurement moved
by ~1.6-1.7x *including the control* — a test the change cannot touch. The arms therefore ran at different
load, which is precisely the confound this item already warns about ("only uncensored absolutes at comparable
controls mean anything"); 7.17s vs 4.39s controls are not comparable. Normalised against the control the
subjects move **1.037x**, **1.049x** and **0.938x** — noise, with one *below* one.

**The mechanism a reviewer would reasonably suspect, checked rather than waved off.** ST-8 adds three indexes
(`V0_0_101`: `lineage(child_oddrn)`, `ownership(owner_id)`, `term_ownership(owner_id)`), indexes cost writes,
and `testInjectingManyDataEntities` is write-heavy over exactly those tables. If that were the cause the
subject would have moved **more** than the control. It moved 3.7% more, and the other ingestion-path test
moved 6% *less*. The data does not support it.

**What IS new, solid and actionable — the reason this entry exists.** On a box this item's own calibration
calls quiet (control ~7-8s; arm A's control was 7.17s), `LoadIngestionTest` needs **57.02s against a 60s
bound — a 2.98s margin.** Even at arm B's quieter 33.66s the bound is only 1.8x the measured cost, for a test
whose cost scales with the volume it injects. It is not a test that "flakes under load"; it is a bound that
was never sized against its own measured cost, and any CI runner slower than this box fails it
deterministically. That is this item's thesis, in a second unit-bucket test.

**Practical guidance, extended:** a RED here is read the same way as the springdoc instance — one uncensored
quiet-box run, compare absolutes at a comparable control. Do not attribute it to your change, and do not
compare across two runs whose controls differ.

### Fifth instance (ctrib062 / #1842 ST-8, 2026-08-31) — CORRECTED IN PLACE; three claims retracted

> **This section originally recorded a phantom regression and told the next reader to investigate it.**
> Rewritten by its author once better data existed. What it got right: the bound's margin collapses under
> load, and the PLT-141 shape discriminator. What it got wrong is retracted inline below; the definitive
> numbers are in the sixth instance.

**What was measured** (isolated `--tests "*OpenApiDocsContractTest*"`, 60s bound, on a box whose neighbouring
gradle build was live but *invisible to the check being used*):

| SUT | `swaggerConfig` | `ingestionApi` | `platformApi` | result |
|---|---|---|---|---|
| `origin/main` **`82e7e70e`** (no contributor change present) | 15.086s | 7.230s | **59.693s** / 60s | PASS by **307 ms** |
| `contrib/CTRIB-062-my-data-filter` | 29.887s | 13.487s | >=60.337s (censored) | RED |

**RETRACTED — (1) "59.693s idle".** It was not idle. A neighbouring stream's build was running and was not
detected, because the check used (`GradleDaemon|GradleWrapperMain`) cannot match gradle's test workers, which
are `java -Dorg.gradle.internal.worker.tmpdir=<worktree>/...`. Quiet, this operation costs **~21-24s**.

**RETRACTED — (2) the control-normalisation.** This section proposed `platformApi / (ingestionApi +
swaggerConfig)` as "the robust discriminator". It is not a discriminator at all: `platformApi` and
`ingestionApi` **share springdoc's lazily-built model**, so whichever document is requested first pays the
reflection walk and the "control" is *downstream of the subject*. Measured across five runs,
`swaggerConfigListsBothGroups` alone spans **1.656 / 4.543 / 4.657 / 9.251 / 15.086s** — a 9x spread. That
spread is the argument. Do not revive it. (It is still valid *within* one class across runs, where JUnit 5's

**RETRACTED — (3) the phantom regression.** This section asserted "a genuine 3.4x regression in
document-build cost that nobody has explained" and that "the ~17.8s -> ~59.7s degradation on `main` deserves
its own investigation". **There is no regression.** 17.8s and 59.7s are the same operation at different
machine load. It also projected a loaded cost of "~116s by control-normalised projection"; the actual
uncensored loaded figure is **43.75s**. Left standing, this would have sent the next reader hunting a ghost

instance where `platformApi` alone exceeds its bound while `ingestionApi` and `swaggerConfig` pass is
contention. An instance where **both** group documents hang is the real thing and should be escalated
immediately. This remains the fastest triage available on a RED.

**STANDS — contention is cross-stream and was invisible.** Detection required `ps aux --sort=-%mem`. Use
`pgrep -f 'gradle.*worker|GradleWrapperMain|GradleDaemon'`. Filed as `TST-061`, together with the unscoped

### Sixth instance (ctrib061 / #1841 ST-7 + ctrib062, 2026-08-31) — THE MEASUREMENT, and a retraction

Three uncensored runs (`@AutoConfigureWebTestClient` bound raised 60s -> 300s, diagnostic only, restored under
a `trap ... EXIT INT TERM` with the restore evidenced in each log), each on a quiet box, each under the
heavy-e2e flock, controls = `ingestionApiGroupDocumentLoads` + `swaggerConfigListsBothGroups`:

| subject | controls | `platformApiGroupDocumentLoads` | vs clean main |
|---|---|---|---|
| clean `origin/main` @ 82e7e70e | 7.283s | **24.156s** | baseline |
| `contrib/CTRIB-061-favorites-filter` (+1 scalar property) | 7.196s | **20.671s** | **−3.485s** |
| `contrib/CTRIB-062-...` (+5 scalar properties) | 7.677s | **23.122s** | **−1.034s** |
| the same ctrib062 branch under ~2x load | 14.492s | 43.750s | (the number that started this) |

**The operation costs ~21-24s on an idle box.** Two independent spec-changing branches and clean `main` are
indistinguishable. The 60s bound therefore has **~36s of headroom quiet and effectively none under load** —
which is this item's thesis, now with numbers instead of inference.

**RETRACTED from the fifth-instance section above (written from censored + control-normalised data, both since
withdrawn):**

1. *"the loaded cost is now ~116s by control-normalised projection"* — the projection assumed box state held
   across runs; it does not hold on this machine for ten minutes. The actual uncensored loaded figure was
   **43.75s**, not ~116s.
2. *"a genuine 3.4x regression in document-build cost that nobody has explained"* and *"the ~17.8s -> ~59.7s
   degradation on `main` deserves its own investigation"* — **there is no regression.** 17.8s and 59.7s are the
   same operation at different load. Clean `main` measures 24.156s quiet. **Nobody should spend time hunting
   this.**

**Why the control-normalised discriminator must not be revived.** `platformApiGroupDocumentLoads` and
`ingestionApiGroupDocumentLoads` share springdoc's lazily-built model: whichever document is requested FIRST
pays the reflection walk over every controller and `@ControllerAdvice`, and the second reuses it. The
"control" is therefore *downstream of the subject*, ordered by a JUnit method order nobody controls or
observes — `swaggerConfigListsBothGroups` was measured at 1.656s, 4.543s, 4.657s, 9.251s and 15.086s across
runs. It is valid **within** one class across runs (deterministic default ordering keeps the confound
constant), and invalid **across** streams. Only uncensored absolutes at comparable controls mean anything.

**Structural finding worth keeping.** springdoc's cost driver is the reflection walk over operations,
controllers and advice. A scalar property on an existing schema adds none of those, and the only mechanism by
which a property can hang a document build is a schema **cycle**, which a scalar cannot form. Two slices now
measure as evidence for this, in opposite directions from the same prediction — so a spec change adding only
scalar properties can be expected not to move this number, and a future RED here should be read as load until
an uncensored quiet-box run says otherwise.

**Practical guidance for the next stream that hits a RED here:** do not attribute it to your change and do not
reach for a ticket that describes the same symptom. Take one uncensored measurement on a quiet box (controls
~7-8s; a few hundred ms over 7s is still quiet) and compare the absolute against the 24.156s `main` baseline
above.
