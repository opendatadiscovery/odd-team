## What

The toolbar shows a **Logout** menu item in every authentication mode, and clicking it always navigates the browser to `GET /logout`. Under `auth.type=DISABLED` there is no Spring Security logout chain wired (`.logout(...)` is configured only on the LOGIN_FORM / OAUTH2 / LDAP chains, never on DISABLED). What the request then does is **not** a 404 - the platform's catch-all SPA filter rewrites it - so the operator-visible symptom is subtler than a hard error: the browser is handed back the SPA shell at an in-app route that does not exist, the page goes blank under a still-present toolbar, and the user is not logged out (there is no session to terminate under DISABLED anyway). The control is presented as a working primary action but is inert in the bundled default deployment mode.

## Where

The handler hard-codes a full-page navigation to `/logout` in all modes - `odd-platform-ui/src/components/shared/elements/AppToolbar/AppToolbar.tsx:35-37`:

```tsx
const handleLogout = () => {
  window.location.href = '/logout';
};
```

It is wired to the menu item rendered unconditionally in the toolbar (same file, line 117: `<AppMenuItem onClick={handleLogout}>{t('Logout')}</AppMenuItem>`).

The DISABLED security chain wires **only** `permitAll` - no `.logout(...)` - so nothing on the security side maps `/logout` - `odd-platform-api/.../config/DisabledAuthSecurityConfiguration.java:12-18`:

```java
@Bean
public SecurityWebFilterChain securityWebFilterChainDisabled(final ServerHttpSecurity http) {
    return http
        .csrf(ServerHttpSecurity.CsrfSpec::disable)
        .authorizeExchange(authorizeExchangeSpec -> authorizeExchangeSpec.anyExchange().permitAll())
        .build();
}
```

(For contrast, `.logout(...)` *is* wired on the other chains: `LoginFormSecurityConfiguration.java:59`, `OAuthSecurityConfiguration.java:100`, `LDAPSecurityConfiguration.java:146`.)

## User-facing impact

**Auth mode: `auth.type=DISABLED` (the bundled default - `permitAll` + a synthetic all-permissions `admin` identity).** Verified end-to-end by tracing both ends:

- The request `GET /logout` does **not** hit a 404. `ResourceProviderWebFilter.filter` (`odd-platform-api/.../config/ResourceProviderWebFilter.java:14-42`) rewrites every path that is not `/api`, `/ingestion`, `/actuator`, or a static asset (`/assets`, `/img`, `/manifest.json`, `/favicon.ico`) to `/index.html` and serves it. `/logout` matches none of those prefixes, so the operator gets **HTTP 200 + the SPA shell**, not an error page.
- The React Router tree in `odd-platform-ui/src/components/App.tsx:59-89` declares explicit routes (`/`, search, management, alerts, ...) but **no catch-all `path="*"` route**, and there is no `/logout` client route anywhere under `src/routes/`. So once the shell loads at URL `/logout`, no `<Route>` matches and React Router renders an **empty content area beneath the persistent toolbar** - no redirect home, no "not found" placeholder.

Net: the operator clicks the obvious "Logout" control, the app blanks out (toolbar still showing), and they remain on the synthetic `admin` identity. The affordance is dead, but the failure reads as "the app broke" rather than "404", which is the corrected symptom.

## Why it matters

Pointless-but-confusing failure on the platform's most common first-run configuration: DISABLED is the bundled default an operator gets when they stand the platform up to try it. A labelled primary action ("Logout") that blanks the page is a broken-affordance trust hit - the operator clicks the obvious control and the app appears broken. (There is also nothing to log out *of* under DISABLED, so even a working route would be meaningless - the right behaviour is to not present the affordance.) Medium because it is cosmetic/UX rather than data-loss or security, but it is on a high-traffic surface in the default mode.

## Suggested fix

Make the logout affordance mode-aware: hide the Logout menu item entirely under DISABLED (where there is no session to terminate), or adapt it to a sensible no-op/explanation. The client already knows it is in DISABLED mode from the synthetic all-permissions `admin` identity; a dedicated auth-mode signal on the identity payload would let the toolbar suppress the item deterministically. Open to alternatives.
