# DataSourceIngestionServiceImpl — semantic understanding

## understanding

The reactive service bean orchestrating the `POST /ingestion/datasources` S2S boot-of-collector flow — a 118-line implementation (`DataSourceIngestionServiceImpl.java:34-118`) of the single-method `DataSourceIngestionService` interface (`DataSourceIngestionService.java:7-9`). Invoked exclusively from `IngestionController.createDataSource` (batch P sidecar) after the controller has extracted the matched `collectorId` from the WebSession's `COLLECTOR_ID_SESSION_KEY` attribute (set by `IngestionDataSourceFilter` upstream — UNCONDITIONAL `@Component`, no `auth.ingestion.filter.enabled` gating). The method orchestrates a five-step pipeline INSIDE a single `@ReactiveTransactional` boundary (line 40): (1) resolve the Collector by id via `reactiveCollectorRepository.getDto(collectorId)` (line 42) — fail with `NotFoundException` if absent (line 43); (2) map every payload `DataSource` item to a `DataSourcePojo` via `mapDataSources(dataSourceList, c)` (lines 99-111) — stamping the namespace_id from the COLLECTOR's pre-configured namespace via `MappingUtils.extractFieldFromNullableObject(c.namespace(), NamespacePojo::getId)` (line 106), NOT from any namespace info in the payload; (3) resolve existing rows by ODDRN via `reactiveDataSourceRepository.getDtosByOddrns` (line 47); (4) partition the payload into `toUpdate` (existing ODDRNs — via `prepareForUpdate` lines 74-92) and `toCreate` (NEW ODDRNs — via `prepareForCreate` lines 94-97); (5) execute bulkUpdate + bulkCreate concatenated as a Flux. **The architectural load-bearing line is 86-88**: `prepareForUpdate` returns `new DataSourcePojo(a).setName(i.getName()).setDescription(i.getDescription())` — a COPY-CONSTRUCT from the existing pojo, then EXPLICIT-SETTER for ONLY name + description. This is the SERVICE-TIER ENACTMENT of ADR-CANDIDATE-142 (partial-merge UPSERT) — the narrowing to 2 payload-driven fields lives HERE; the repository would faithfully write any column the service supplied (batch R sidecar primary source). This sidecar is the THIRD VERTEX of the ADR-CANDIDATE-142 triangulation: batch P controller observes the service call; batch R repository confirms the SQL-tier would NOT have constrained the field set; THIS batch S service is the file:line where the 2-field stamp is structurally encoded. Combined with the namespace-from-Collector inheritance (line 106 — the ENACTMENT of ADR-CANDIDATE-143) and the silent `Flux<DataSource>` shape (line 41 — the controller discards the result via `.then`), this service is the SOLE owner of the operator-collector boundary contract: collectors register identity + 2 mutable fields; everything else is operator-owned.

## security

- **auth_mode_relevance**: `INTERNAL_ONLY — this is a service-tier bean invoked by the controller AFTER authentication. ## performance

- **hot_paths**:
  - "Per-request: 4 DB round-trips inside @ReactiveTransactional — (1) `reactiveCollectorRepository.getDto(collectorId)` line 42 (a 2-LEFT-JOIN against NAMESPACE + TOKEN per ReactiveCollectorRepositoryImpl.java:46-57); (2) `reactiveDataSourceRepository.getDtosByOddrns` line 47 (a 2-LEFT-JOIN against NAMESPACE + TOKEN per batch R sidecar's `getDtosByOddrns` lines 104-110); (3) `bulkUpdate(toUpdate)` line 57 (multi-row UPDATE per partition); (4) `bulkCreate(toCreate)` line 66 (multi-row INSERT per partition). All sequential; no parallel execution within the transaction. The filter's UPSTREAM token-lookup (per batch P sidecar — `IngestionDataSourceFilter.collectorRepository.getByToken(token)`) adds a 5th round-trip outside the transaction." — evidence: DataSourceIngestionServiceImpl.java:42-66
  - "Mapper invocation per payload item — `mapDataSources` (lines 99-111) iterates the payload list and invokes `dataSourceIngestionMapper.mapIngestionModel` per item (DataSourceIngestionMapperImpl.java:9-19). The mapper is stateless and O(1) per call; total cost is O(N) where N = payload size. Negligible vs the DB I/O." — evidence: DataSourceIngestionServiceImpl.java:99-111 + DataSourceIngestionMapperImpl.java:9-19
  - "`extractOddrns` (lines 113-117) is O(N) over the mapped DataSourcePojos — used at line 47 to build the IN-clause for `getDtosByOddrns`. For typical 30-datasource payloads, IN-clause cardinality is small; for pathological 1000-datasource payloads the IN-clause grows linearly (PostgreSQL handles large IN-clauses gracefully via hash-aggregation in the planner)."
- **throughput_characteristics**:
  - "Single batch per HTTP call — one DataSourceList per @ReactiveTransactional invocation. Collectors typically register all their datasources in ONE call at startup (per the documented 'once at startup' pattern from the custom-collectors live doc, WebFetched 2026-05-20 status 200)."
  - "Synchronous within @ReactiveTransactional — no parallel execution of the 4 DB calls. The chain is `collector lookup → existing-by-ODDRN read → bulkUpdate + bulkCreate concatenated via Flux.concat (line 68)`. The bulkUpdate + bulkCreate are concatenated but NOT parallel — `Flux.concat` waits for the first publisher to complete before subscribing to the second. So bulkUpdate FULLY executes before bulkCreate begins."
  - "Reactive Mono/Flux signature — non-blocking from the WebFlux perspective. Inside `@ReactiveTransactional` the operations fire sequentially against a single R2DBC connection. The transaction binds ONE connection from the pool for the duration of the call."
- **resource_allocation**:
  - "Heap: full payload list materialised in memory (the Mono<DataSourceList> deserialised to a concrete List<DataSource>). For 30-datasource payloads (~5KB JSON each → 150KB total), heap impact is negligible. For 1000-datasource payloads (~5MB), still well within `spring.codec.max-in-memory-size: 20MB` (per batch P sidecar). The mapped DataSourcePojo list adds another O(N) heap allocation; the actualDict + toUpdate + toCreate lists add three more O(N) allocations. Total heap: O(N) where N = payload size, bounded by 20MB upstream cap." — evidence: DataSourceIngestionServiceImpl.java:45-67 + application.yml:14-15 (per batch P sidecar)
  - "DB connection: ONE R2DBC connection bound for the duration of @ReactiveTransactional. For typical 30-datasource payloads at ~30-50ms total transaction time, this is fine. For 1000-datasource payloads (1-10 seconds), the connection is held for the full duration — which scales connection-pool sizing requirements." — evidence: DataSourceIngestionServiceImpl.java:40
  - "Mapper / helper allocations: each invocation of `MappingUtils.extractFieldFromNullableObject` (line 106) is a static method call returning a `Long` (or null) — negligible. The `DataSourceIngestionMapperImpl.mapIngestionModel` allocates a new DataSourcePojo per call; for 1000-item payloads, this is 1000 DataSourcePojo allocations — bounded but observable."
- **scaling_characteristics**:
  - "Service is stateless — instances scale horizontally. Three final injected dependencies; no in-memory state; no per-request cache." — evidence: DataSourceIngestionServiceImpl.java:33-37 (constructor + finals)
  - "@ReactiveTransactional holds ONE R2DBC connection per concurrent request — scales linearly with concurrent collector ingestion requests. Connection pool sizing must accommodate (max concurrent collectors) × 1."
  - "Race on concurrent re-registration of the same ODDRN by two collectors (per `bugs_limitations_corner_cases[6]`) — bounded by Postgres READ COMMITTED isolation; one transaction wins, the other rolls back with SQLSTATE 23505. No SELECT FOR UPDATE at this service layer (the entity-ingestion path uses `getIdByOddrnForUpdate` per batch R sidecar; this datasource-registration path does NOT)."
  - "No advisory locks. The platform has advisory locks (per the concept catalog `202-queue-postgres-advisory-lock-single-sender-pattern`) for OTHER subsystems (notifications, housekeeping) but NOT for datasource registration. Concurrent collector ingestion of the same ODDRN relies on the partial unique index for safety."
- **known_performance_gaps**:
  - "**No bulk-batch sizing limit at the service layer.** A 1000-item payload (or 10,000-item) is processed in one transaction; `bulkUpdate` and `bulkCreate` partition internally (per batch R sidecar's notes on `executeInPartitionReturning`), but the transaction duration scales with payload size.   - "**Sequential bulkUpdate + bulkCreate via Flux.concat (line 68)** — even though the two operations are independent (different partitions of the payload), they execute SEQUENTIALLY inside the transaction. Parallelising via `Flux.merge` would shorten the wall-clock duration but risks deadlocks under the @ReactiveTransactional binding (R2DBC's single-connection model). The current sequential pattern is correct but not optimal for very large payloads." — evidence: DataSourceIngestionServiceImpl.java:56-68 — severity: LOW
  - "**4 sequential DB round-trips per call** — collector lookup + existing-by-ODDRN read + bulkUpdate + bulkCreate. The filter's UPSTREAM token-lookup (5th round-trip per batch P sidecar's hot_paths) duplicates information: the filter found the Collector by token; this service then re-fetches the same Collector by id.
