## What

The shipped `Feature` enum has exactly **two** values - `DATA_COLLABORATION` and `ALERT_NOTIFICATIONS` (`generated-sources/models/Feature.ts:20-23`; backend `FeatureResolverImpl.java:22-28`). Tracing both ends settles the only real wart: `ALERT_NOTIFICATIONS` is **exposed** by `GET /api/features/active` (when `notifications.enabled=true`) but is **never consumed anywhere in the frontend** - it is a backend feature flag with no `WithFeature` gate and no other reader (grep for `ALERT_NOTIFICATIONS` over `odd-platform-ui/src` returns only the enum declaration). `DATA_COLLABORATION`, by contrast, is wired correctly: it gates exactly the in-page Slack affordances it is meant to (`DataEntityDetailsHeader.tsx:132` Share button, `Message.tsx:59` "Open in Slack", `MainThreadMessage.tsx:36`), all via `WithFeature`.

The two defects this issue was originally filed for are **both falsified** (see ## How discovered):

- **"Defect 1 - chrome-invariant" is FALSE as framed.** The 9 top-level toolbar tabs were never a feature-flag surface, and no Feature value was ever intended to gate one. The original claim that `datacollaboration.enabled=false` should hide the "Data Modelling" tab is a category error: the Data Modelling tab routes to Query Examples (`queryExamplesPath`), which is unrelated to the Slack Data Collaboration feature; the Discussions UI that DATA_COLLABORATION actually gates is a per-entity sub-route (`/dataentities/{id}/discussions`), not a tab. There is no "tab visible despite a disabled flag" bug.
- **"Defect 2 - boot-immutable" is not a defect.** `FeatureResolverImpl` captures the two `@Value` booleans into a `final Set<Feature>` in its constructor (`FeatureResolverImpl.java:14,20-30`) - the ordinary Spring pattern. There is no `@RefreshScope`, no `/actuator/refresh`, and nothing (doc or endpoint contract) promising runtime-toggleable features: "active features" means "enabled at this deployment", resolved at boot. Expecting a live actuator refresh of a non-`@RefreshScope` bean is reading a promise into the name that the code never made.

## User-facing impact

- Verified by FE trace 2026-06-10: `ALERT_NOTIFICATIONS` has **no** UI consumer - `grep -rn ALERT_NOTIFICATIONS odd-platform-ui/src` returns only `Feature.ts:22`. An operator who sets `notifications.enabled=true` sees the flag reflected in `GET /api/features/active` but no UI element keys off it. Impact: none beyond an inert flag in the exposure response; LOW.
- Verified by FE trace 2026-06-10: the 9 toolbar tabs render unconditionally regardless of feature flags (`ToolbarTabs.tsx:34-82`, no flag read) - and that is correct, not a defect: no Feature value maps to a tab. DOM-confirmed by the workspace integration test IT-101 (`integration-tests/protocols/IT-101-application-toolbar.md`, 3/3 green 2026-06-07) which pins all 9 tabs as unconditional chrome.
- Verified by FE trace 2026-06-10: `DATA_COLLABORATION` correctly hides/shows the per-entity Slack affordances via `WithFeature` (`DataEntityDetailsHeader.tsx:132`, `Message.tsx:59`, `MainThreadMessage.tsx:36`). The exposure surface itself (the `GET /api/features/active` contract + anonymous reach under DISABLED) is already characterized by IT-117 (`integration-tests/protocols/IT-117-feature-flag-exposure.md`).
- Auth mode: the anonymous-reach observation on the exposure endpoint is a property of `auth.type=DISABLED` (`DisabledAuthSecurityConfiguration` `permitAll()`), tracked under IT-117, not here.

## Why it matters

Low - downgraded from medium 2026-06-10: both originally-asserted defects are falsified (chrome-invariance is a category error; boot-immutability is expected non-`@RefreshScope` Spring behaviour). The only surviving, code-settled wart is the orphan `ALERT_NOTIFICATIONS` flag - exposed by the backend, gating nothing in the UI - which is the opposite shape of the original "chrome ignores a flag" claim and carries no user-visible consequence (an inert flag). Worth a small cleanup (either wire ALERT_NOTIFICATIONS to the alert-notification UI it was presumably intended for, or drop it from the exposed enum), not a medium-severity gating bug.

## Suggested fix

Resolve the one real inconsistency - `ALERT_NOTIFICATIONS` exposed but unconsumed - by deciding the flag's intent:

- If alert-notification UI is meant to be feature-gated, wrap the relevant alert-notification affordance(s) in `<WithFeature featureName={Feature.ALERT_NOTIFICATIONS}>` so the exposed flag has an effect; **or**
- If the notification toggle is purely a backend concern, remove `ALERT_NOTIFICATIONS` from the `Feature` enum / the `/api/features/active` exposure so the contract does not advertise a flag the UI ignores.

No change is warranted for the toolbar tabs (they are correctly unconditional) or for `FeatureResolverImpl`'s constructor capture (correct Spring semantics; only adopt `@RefreshScope` if runtime feature toggling becomes an explicit, documented requirement).

## How discovered

Mode-B feature-flow scanner run `SR-20260527T2030Z` against feature F-034 (Platform Feature-Flag Exposure). Substrate facets `feature_flag_set_dispatched_but_not_consumed_by_navigation_chrome` + `boot_immutable_runtime_change_silently_ignored`.

**Corrected 2026-06-10 (user-facing verification sweep):** was a two-defect medium ("chrome is invariant to flags" + "boot-immutable refresh ignored"); both falsified by reading both ends. Chrome-invariance: was "disabling `datacollaboration.enabled` should hide the Data Modelling tab"; actually the Feature enum has only DATA_COLLABORATION + ALERT_NOTIFICATIONS (`Feature.ts:20-23`), no Feature maps to any top-level tab, and DATA_COLLABORATION already correctly gates its per-entity Slack affordances via `WithFeature` (`DataEntityDetailsHeader.tsx:132`, `Message.tsx:59`, `MainThreadMessage.tsx:36`) - the workspace's own IT-101 pins all 9 tabs as deliberate unconditional chrome. Boot-immutable: was "runtime refresh silently ignored"; actually a `@Value`-in-constructor `final Set` with no `@RefreshScope` / `/actuator/refresh` anywhere and no documented runtime-toggle promise - the expected Spring contract, not a defect (the workspace's IT-117 already treats "active" as deployment-wide/boot-bound). Re-scoped to the one surviving code-settled fact: `ALERT_NOTIFICATIONS` is exposed but has zero FE consumers (`grep` returns only `Feature.ts:22`). Same failure mode as PLT-167/PLT-176: UI claims asserted from a backend/substrate facet without reading the frontend.

Doc-side companion: **DOC-248** (originally to publish chrome-invariance + boot-immutability caveats) should be revised in step - those caveats describe non-defects; the only publishable note, if any, is the orphan ALERT_NOTIFICATIONS flag.
