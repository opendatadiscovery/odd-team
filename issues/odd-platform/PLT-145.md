## What

Editing a Lookup Table's **name** in the UI (a pure-metadata action, the operator's mental model) triggers a
physical `ALTER TABLE … RENAME TO …` on the public `lookup_tables_schema` Postgres relation that backs the
table. There is no warning dialog, no deprecation alias, and no activity/audit event. Every downstream
consumer still joining the old relation (`lookup_tables_schema.n_{ns}__{old_name}`) — dbt models, BI queries,
notebooks, views — breaks immediately with `relation "…" does not exist`. This is the same operator-harm
class as LSN-001 (attachment ephemeral default) and LSN-002 (MinIO region unset): a documented, reasonable
operator action quietly destroys a thing they depend on.

## Reproduced live (docker `:latest`, auth.type=DISABLED, 2026-06-07 — IT-048 UC-001)

1. Create lookup table `it048…` → physical relation `lookup_tables_schema.n_1__it048…` exists.
2. `PUT /api/referencedata/table/{id}` with a changed `name` → 200.
3. DB read-back: **old physical relation gone (`false`), new physical relation present (`true`)** — the
   rename cascaded to the physical table. A pre-existing join to the old name now errors.

A description-only edit (name unchanged) does **not** rename the physical table (IT-048 UC-002, the
harmless-edit guard, confirmed) — so the trigger is specifically the name change.

## Root cause

`ReferenceDataServiceImpl.updateLookupTable` (odd-platform-api/.../service/ReferenceDataServiceImpl.java:107–122)
gates the physical update on a name-changed check and, when the name differs, calls
`referenceDataRepository.updateLookupTable(...)` which issues the jOOQ DDL rename against
`lookup_tables_schema`. Business-name and physical-name are coupled 1:1 with no indirection.

## Operator impact

Silent, irreversible-at-the-data-layer breakage of every external query bound to the lookup table. The
operator gets a 200 and no signal that they just renamed a live physical relation other pipelines read.

## Fix options (per F-059 reflection)

- Decouple the business display-name from an immutable physical relation name (rename = metadata-only); **or**
- keep a deprecation **alias VIEW** at the old name on rename; **and**
- raise a UI confirm-dialog at rename-time + emit an `ActivityEvent` so the change is auditable.

## Regression guard

Pinned GREEN today by **IT-048 / F-059-UC-001** (LSN-029 characterization pin asserting the current
physical-rename behaviour). The pin flips RED the moment the platform stops renaming the physical relation —
that red is the measurable fix-landed signal. The harmless-edit guard IT-048/UC-002 stays green.
