## What

`PUT /api/datasetfields/{id}/tags` builds each `TagToDatasetFieldPojo` with only `tagId` + `datasetFieldId` and **never calls `.setOrigin(...)`**; `createDatasetFieldRelations` then maps the pojo via `jooqReactiveOperations.newRecord(TAG_TO_DATASET_FIELD, p)` and INSERTs. The `origin` column is `varchar NOT NULL DEFAULT 'INTERNAL'`. Whether the endpoint **works at all** for a non-empty tag payload is statically undetermined: if jOOQ's `newRecord`-from-pojo omits the unset column the DB default applies and the insert succeeds; if jOOQ emits an explicit `NULL` the INSERT violates `NOT NULL` and **every non-empty PUT fails with a 500**. The data-entity sibling sidesteps this by explicitly calling `.setExternal(false)`; the dataset-field path relies on the default. This is the single critical untested path on the tagging feature.

This is **net_new** — no existing item tracks it. (PLT-026 is the tagging-behaviour cluster — ranking, side-channel mints, audit asymmetry — and does not include this insert-shape defect.)

## Impact

If jOOQ emits the explicit NULL: every attempt to tag a dataset field returns a 500 — the feature is dead for any real payload (empty-payload clears still work, masking it in some flows). If `origin` persists as something other than `INTERNAL`: the next call's `deleteDatasetFieldInternalRelations` (`WHERE origin='INTERNAL'`) misses those rows and the field accumulates orphan internal relations. Either way the operator hits a hard failure or silent relation drift.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: explicitly `.setOrigin(TagOrigin.INTERNAL.toString())` on the `TagToDatasetFieldPojo` (`DatasetFieldServiceImpl.java:264-271`), mirroring the data-entity path's `.setExternal(false)`. Confirm the failure mode via P-030 before/after.
