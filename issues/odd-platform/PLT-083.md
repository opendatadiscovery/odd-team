## What

Two defects in the housekeeping subsystem that ship together - one is data-loss-class (LSN-001 shape), one is consistency-with-platform-pattern. Both are small-surface code changes. A third surface (the `AlertHousekeepingJob` jOOQ operator-precedence bug) is **already covered by PLT-005** (filed 2026-04-25 during DOC-021 review); coordinate the fixes.

**Defect 1 - Java-side TTL fields default to 0; partial config override silently collapses the grace window to zero and immediately purges RESOLVED alert history, search-facet history, and ALL soft-deleted entities + their cascading S3 attachments within 15 minutes of restart (HIGHEST - LSN-001 shape).** `HousekeepingTTLProperties.java:9-11` declares the three TTL fields as primitive `int` with **no initialiser**. Spring binds primitive `int` default `0` if an operator overrides `application.yml` and forgets to re-supply the `housekeeping.ttl.*` block (Helm chart values overlay, `--spring.config.location=` to a different profile, Spring Cloud Config slice, Kubernetes ConfigMap mount).

**Corrected 2026-06-10 - blast radius is the grace window, not the whole catalog.** Each job's delete is GATED on a status predicate, so TTL=0 does NOT "delete everything"; it sets `cutoff = now() - 0 days = now()` and deletes every row already in the delete-eligible state:
- `DataEntityHousekeepingJob.doHousekeeping` (`:73-78`) deletes only entities with `STATUS = DELETED` AND `STATUS_UPDATED_AT <= cutoff` - i.e. every currently soft-deleted entity (active/non-deleted entities are untouched). For those, `deleteDataEntities` (`:84-129`) cascades through ~30 child tables (`:99-122`) and `fileUploadService.deleteFiles(...).block()` (`:142`) deletes the corresponding object-store attachments.
- `AlertHousekeepingJob.doHousekeeping` deletes only alerts with `STATUS in (RESOLVED, RESOLVED_AUTOMATICALLY)` AND `STATUS_UPDATED_AT <= cutoff` - i.e. every resolved alert (open/unresolved alerts are untouched).
- `SearchFacetsHousekeepingJob` similarly prunes search-facet history past the (now zero) window.

So the data lost is the **recoverable / historical** data that the 30-day window exists to protect: a user soft-deletes an entity expecting 30 days to undo, and instead it is hard-purged with its attachments on the next cycle. Recovery requires Postgres PITR + object-store versioning replay. No boot warning, no log line above DEBUG, no Prometheus counter. The schedule is confirmed 15-minute (`HousekeepingJobManager.java:25`, `@Scheduled(fixedRate = 15, MINUTES)`).

**Defect 2 - `PostgreSQLSessionHousekeepingJobHandler` has no `@SchedulerLock` (multi-replica Nx DB load).** `PostgreSQLSessionHousekeepingJobHandler.java:13` is `@Scheduled(fixedRate = 1, timeUnit = TimeUnit.HOURS)` (method `deleteExpiredSessions()`, `:14`) with NO `@SchedulerLock` annotation. INCONSISTENT with the orchestrated housekeeping jobs - `HousekeepingJobManager.runHousekeepingJobs()` carries `@SchedulerLock(name = "housekeepingJob", lockAtLeastFor = "14m", lockAtMostFor = "14m")` at `HousekeepingJobManager.java:26`; the WAL/partition/data-collaboration subsystems coordinate via advisory locks (see PLT-089). The session-housekeeping bean exists ONLY when `session.provider = INTERNAL_POSTGRESQL` (`SessionConfiguration.java:37-43`); the shipped default is IN_MEMORY, so this is dormant by default. On a multi-replica `INTERNAL_POSTGRESQL` deployment, every replica selects-then-deletes expired `SPRING_SESSION` rows hourly (`PostgreSQLSessionHousekeepingJob.java:27-46`): Nx redundant DB load. Deletes are idempotent so correctness is preserved; the issue is wasted DB load + inconsistency-with-pattern + incident-response surprise.

## User-facing impact

Both defects are operator-facing (data integrity / DB load); there is no UI rendering claim. Every observable below is misconfiguration- and runtime-dependent, so `user_facing_verified` stays `false`.

- **Defect 1, end user + operator:** preconditions - `housekeeping.enabled=true` (default, `application.yml:166`) AND an operator override that drops the `housekeeping.ttl.*` block (so the primitive `int` fields bind to 0). Then, within one 15-minute cycle, every entity a user previously SOFT-DELETED (expecting a 30-day undo window) is hard-purged together with ~30 child-table rows and its object-store attachments, and every RESOLVED alert + search-facet history past the now-zero window is deleted. The observable: soft-deleted entities stop being recoverable and their attachments 404 in object storage. *Static trace consistent; not driven* - reproducing requires the partial-override misconfig on a running stack with soft-deleted data present (status predicate + `minusDays(0)` mechanism verified by BE trace 2026-06-10 at `DataEntityHousekeepingJob.java:73-78,142` and `AlertHousekeepingJob`). NOTE (corrected): active/non-deleted entities and open alerts are NOT affected - the original "deletes EVERYTHING" was an overstatement.
- **Defect 2, operator:** on multi-replica `INTERNAL_POSTGRESQL`, the session cleanup runs once per replica per hour instead of once cluster-wide - Nx redundant but idempotent DB load; no correctness impact, no UI symptom. *Static trace consistent; not driven* - requires a >=2-replica INTERNAL_POSTGRESQL stack to measure the extra load. Dormant under the default IN_MEMORY provider.

## Why it matters

**Defect 1** is the failure mode of LSN-001 repeated on a different config family. The 2026-04 attachment-storage-default case wiped production data; this is the same shape on housekeeping (and the cascading attachment delete on `DataEntityHousekeepingJob` line 142 makes it worse - the data-entity-delete path also wipes the corresponding object-store attachments). Operators deploying via Helm with a values overlay that drops the housekeeping block - a common pattern when standardising per-env overlays - get, within 15 minutes of their first restart, a silent immediate purge of every soft-deleted entity (+ its ~30 child-table rows + attachments) and every resolved alert, with the 30-day recovery window collapsed to zero. (Scope corrected 2026-06-10: this is the recoverable/historical tier, not the live catalog - active entities and open alerts survive.)

**Defect 2** is operator-cost not correctness - but the inconsistency-with-pattern is a debugger trap (operators reading `application.yml` see 4 `*.advisory-lock-id` keys; an additional Nx DB load on `SPRING_SESSION` doesn't trace back). Default `spring.session.timeout: -1` (never-expire) renders the job a no-op today; the moment an operator sets a finite timeout, the Nx load surfaces.

## Suggested fix

### Defect 1 - two options, both reasonable

**Option A (recommended) - field initialisers:**

```java
// HousekeepingTTLProperties.java:8-12
@Setter @Getter @ConfigurationProperties("housekeeping.ttl")
public class HousekeepingTTLProperties {
-    private int resolvedAlertsDays;
-    private int searchFacetsDays;
-    private int dataEntityDeleteDays;
+    private int resolvedAlertsDays = 30;
+    private int searchFacetsDays = 30;
+    private int dataEntityDeleteDays = 30;
}
```

Minimal-risk. Matches the safety floor in `application.yml`. Partial overrides no longer wipe everything.

**Option B - validators + fail-fast:**

```java
@Setter @Getter @Validated @ConfigurationProperties("housekeeping.ttl")
public class HousekeepingTTLProperties {
    @Min(1) private int resolvedAlertsDays = 30;
    @Min(1) private int searchFacetsDays = 30;
    @Min(1) private int dataEntityDeleteDays = 30;

    @PostConstruct
    void validate() {
        // hard-fail boot if 0 explicitly set
    }
}
```

More opinionated; rejects the (rare but possible) operator who actually wants `0` for one of the keys.

### Defect 2 - one option

```java
// PostgreSQLSessionHousekeepingJobHandler.java:13
+ import net.javacrumbs.shedlock.spring.annotation.SchedulerLock;
  ...
  @Scheduled(fixedRate = 1, timeUnit = TimeUnit.HOURS)
+ @SchedulerLock(name = "sessionHousekeepingJob", lockAtMostFor = "PT55M")
  public void cleanup() { ... }
```

Aligns with the 5 HousekeepingJobManager-orchestrated jobs. Pick a lockName distinct from `housekeepingJob` so the two don't share.

## How discovered

**Corrected 2026-06-10 (user-facing verification sweep):** Defect 1's "the next cycle ... deletes EVERYTHING" was an overstatement - every housekeeping job's delete is gated on a status predicate (`STATUS=DELETED` for entities, `STATUS in (RESOLVED, RESOLVED_AUTOMATICALLY)` for alerts), so TTL=0 collapses the grace window to zero and purges the already-soft-deleted/resolved tier immediately, but does not touch active entities or open alerts (verified at `DataEntityHousekeepingJob.java:73-78` + `AlertHousekeepingJob`). The data-loss severity stands (HIGH): zero-grace hard-purge of soft-deleted entities + cascading attachments, silent.
