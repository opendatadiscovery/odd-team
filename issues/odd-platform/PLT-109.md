## What (non-disclosing)

The search-result **highlight** endpoint builds a SQL string by interpolating the **user-supplied search
query** directly into a `ts_headline(...)` call, then runs it as a jOOQ **plain-SQL field** (verbatim SQL, no
bind parameters, no escaping). Because the user query reaches that plain-SQL field without parameterisation, a
crafted query executes arbitrary read-side SQL on the catalog database connection.

**Scope (refined by the maintainer PoC):** only the **query** path is injectable. The co-interpolated catalog
`text` is **not** - `DataEntityHighlightConverter.searchableString()` doubles single quotes before that value
reaches the sink.

**Confirmed exploitable** - maintainer live dynamic test 2026-05-30 (the technique and a working payload are
recorded in the private advisory; withheld here). The vulnerable method is byte-identical on the current
`origin/main`, re-verified 2026-06-16 (CTRIB-017 reproduction at the SQL sink).

## Where

| File | Lines | Role |
|------|-------|------|
| `odd-platform-api/src/main/java/.../repository/reactive/ReactiveDataEntityRepositoryImpl.java` | `getHighlightedResult` (~798-806) | `ts_headline` SQL assembled by raw interpolation of the user query, run as a jOOQ plain-SQL field; **the injectable sink** |
| `odd-platform-api/src/main/java/.../repository/util/JooqFTSHelper.java` | `tsQuery()` | tokenises the user query without escaping; **contrast:** `ftsCondition`/`ftsRankField` in the same helper bind via `to_tsquery(?)` - the **safe** pattern the fix mirrors |
| `odd-platform-api/src/main/java/.../service/search/DataEntityHighlightConverter.java` | `searchableString()` | doubles `'`, so the `text` co-vector is **not** injectable (and is why the fix must also drop that doubling once `text` is bound) |
| `odd-platform-api/src/main/java/.../controller/SearchController.java` | `highlightDataEntity` | reaches the sink; route `GET /api/search/{search_id}/data_entities/{data_entity_id}/highlights` |

## Why it matters

Confirmed unauthenticated (under the shipped default `auth.type=DISABLED`) arbitrary read-side SQL via catalog
search, demonstrated reading data out of the catalog DB in the API response. Network-reachable, no privilege
required, high confidentiality impact - and because ingestion tokens are stored in plaintext in the DB
(`lineage/odd-platform/refactoring-scopes.md:346`), a read-side SQLi escalates toward platform-wide ingestion
compromise. The "guidance is the cliff" class at its worst - catalog search is assumed safe.

## Fix

Tracked as **`contributor/CTRIB-017.md`** (milestone 0.28.0): stop interpolating - pass `text` and the tsquery
as **bind parameters** to the `ts_headline`/`to_tsquery` plain-SQL field (mirror the safe siblings
`ftsCondition`/`ftsRankField`), and drop the now-redundant manual quote-doubling in `searchableString()`. Add
unit (Testcontainers, driving `getHighlightedResult` with a metacharacter payload, RED->GREEN) + integration
(full HTTP chain) regression tests. Repo-wide audit confirmed this is the lone user-input raw-SQL sink.
Disclosure path: **private GHSA fork + verified-patch handover** (no public PR until the advisory publishes).
