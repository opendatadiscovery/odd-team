## What

The token-reveal widget shared by **Collectors** and **Data Sources** (two near-identical components) has UX/maintainability weaknesses that are best fixed as one cluster because they share the same code and the same data shape. **Two of the four originally-claimed halves were over-stated on a backend-only / no-FE-read basis and are corrected below after tracing the components, the redux slices, and `TokenMapper`** (see How discovered):

1. **The regenerate dialog does not mention that an enabled ingestion filter will reject the old token.** The regenerate confirmation dialog asks only "Are you sure you want to regenerate token for this datasource/collector?" - it does not tell the operator that the previous token value is overwritten in place. **Scope correction (verified):** the "running collector starts failing auth" consequence holds ONLY when the operator has set `auth.ingestion.filter.enabled=true`, which is **`false` by default** - out of the box the token is never validated on `POST /ingestion/*` at all, so regeneration breaks nothing for a default deployment. This is the same conditionality already established and code-verified in **PLT-108** (the backend in-place-UPDATE finding); the dialog-copy gap is real but its consequence is conditional on a non-default flag, not unconditional.
2. **The one-shot plaintext token can be clobbered by a list refetch - but the operator is already warned to save it.** A freshly generated/regenerated token is the *only* time the real plaintext value is available from the server; after that every list/get path returns a masked value (`TokenMapper.mapValue`, `showToken=false`). The clobber mechanism is real and code-confirmed: `regenerateDataSourceToken.fulfilled` does `upsertOne(payload)` with the plaintext entity, but `fetchDataSourcesList.fulfilled` does `setAll(...)` with the masked entities, and the child `useEffect` re-derives `isHidden` from the value - so if the list re-fetches *while the reveal is open*, the plaintext is replaced by `******...`. **Correction:** there is no automatic/background poll on these redux thunks, so this is not "an ordinary list refresh" firing on its own - it requires a user-initiated navigation or page reload. And the parent already renders a prominent warning the instant the plaintext shows ("Save token in a secure location. You will not be able to retrieve it again." - `DataSourceItem.tsx:113-122`), so the operator is explicitly told to copy it now. The residual UX nit is real (a refetch *can* drop the value before they copy), but the "operator is blindsided / only recovery is a destructive re-rotation" framing over-states it.
3. **Masked-vs-plaintext detection is a duplicated magic-string bet (the cleanest, fully-verified defect).** Both components independently decide the token is masked with `token.value.substring(0, 6) === '******'`. There is no shared constant and no server-provided "is masked" flag - the prefix `"******"` is a convention emitted by `TokenMapper.mapValue` and reverse-engineered by the UI in two places that can drift apart if the backend prefix ever changes.
4. **The masking is server-side, not a client reveal affordance - this is the intended GitHub-PAT one-shot pattern, not a defect.** **Correction (verified against PLT-085):** the value the UI renders in the masked state IS the server's masked string (`"******" + last-6`); the component does **not** hold a full plaintext that it merely hides with CSS - `$isHidden` only toggles background colour/margin (`DataSourceItemTokenStyles.ts`), it does not blur or mask characters. The full plaintext is in the store *only* during the one-shot reveal window (just after create/regenerate), which is exactly when the operator wants it visible to copy. So "plaintext sits in redux / rendered as visible text with no masking affordance" describes only that intended one-shot window. PLT-085's FE/BE trace already established this masked-everywhere-except-one-shot reveal as the shipped, correct, GitHub-PAT-style behaviour. The only legitimate residual point is to avoid keeping the plaintext in the store longer than the copy interaction needs; adding a separate `type="password"`/reveal-toggle would actually work *against* the deliberate "show once, never retrievable again" design.

## User-facing impact

**Verified by FE + BE trace 2026-06-10** (both token components, both `*Styles.ts`, both parent `*Item.tsx`, both redux slices, `TokenMapper.java`; cross-checked against the already-verified PLT-085 and PLT-108):

- **Regenerate dialog copy (half 1):** the dialog genuinely omits any "this overwrites the token in place" note. But the operator-visible *consequence* (a running collector starts 401-ing) occurs ONLY when `auth.ingestion.filter.enabled=true` (NON-default); on a default deployment the ingestion token is never validated, so regeneration is harmless. The user-facing defect is "missing precaution in copy," conditional on a non-default flag - not an unconditional outage trigger. (Same scope PLT-108 already code-verified.)
- **One-shot clobber (half 2):** code-settled mechanism - `upsertOne` plaintext (`slice :41`) is overwritten by `setAll` masked entities (`slice :29`) and the child `useEffect` re-derives `isHidden`. But there is no background poll on these thunks, so it fires only on a user-initiated list re-fetch / page reload, and the parent already shows "Save token in a secure location. You will not be able to retrieve it again." (`DataSourceItem.tsx:113-122`) at the moment of reveal. Real but narrow UX nit, not a blindsiding foot-gun.
- **Magic-string detection (half 3) - the clean, load-bearing defect:** `token.value.substring(0,6) === '******'` (both components, `:25-27`) is duplicated with no shared constant and no server `masked` flag; a backend prefix change silently breaks the reveal logic in two unlinked places. Holds without qualification.
- **Masking affordance (half 4) - FALSIFIED as a defect:** the masked state shows the server's `******`+last-6, not a CSS-hidden plaintext (`*Styles.ts` only toggles background/margin). The GitHub-PAT-style "reveal once at creation, masked forever after" pattern is the verified, intentional, correct behaviour (PLT-085). A `type="password"` reveal-toggle would contradict that design. The only legitimate residual: do not hold plaintext in the store longer than the copy interaction needs.

No data loss, no anonymous-attacker surface. The surviving actionable work is the shared-constant refactor (half 3) plus the dialog-copy precaution (half 1).

## Why it matters

On a credentials surface (ingestion auth tokens) the cumulative UX is the kind operators remember, which is why the cluster is worth one coordinated pass - but the load-bearing severity is lower than the prior revision implied. Half 3 is a genuine maintainability/correctness hazard (a server-side masking-prefix change silently breaks the reveal logic in two un-linked, drift-prone copies). Half 1 is a worthwhile copy improvement (state that regenerate overwrites the token in place), with the caveat that the breakage it warns about is conditional on a non-default flag. Halves 2 and 4 are narrow-to-falsified once the existing "save it now" warning and the intentional one-shot pattern are accounted for. Kept at medium - leaning to the lower end - because half 3 spans two drift-prone copies on a security-sensitive widget and half 1 touches operator credential hygiene.

## Suggested fix

Consolidate the two components onto one shared token-reveal element and fix the parts that survive verification:

1. Add a precaution to the regenerate dialog text: regeneration overwrites the token value in place; if ingestion-auth filtering is enabled, any running collector/datasource using the old value will fail authentication until reconfigured. (Frame the "will fail auth" part as conditional, matching PLT-108's verified scope - do not assert an unconditional outage.)
2. (Optional, narrow) Persist the one-shot plaintext in local component state keyed to "just generated" so a user-initiated list re-fetch does not drop it before the operator copies it; the existing "save it now" warning already covers the common case, so this is polish, not load-bearing.
3. **(Load-bearing)** Replace the `substring(0, 6) === '******'` bet with a single shared constant and, ideally, a server-provided `masked: boolean` on the token DTO so the UI stops inferring server state from a string prefix in two places.
4. Do **not** add a separate reveal/hide affordance - the masked-everywhere-except-one-shot pattern is intentional (PLT-085). The only change here is to avoid holding plaintext in the store longer than the copy interaction needs.

Open to alternatives on the DTO change (a server `masked` flag is cleaner but is a contract change); the front-end work (half 1 copy, half 3 shared constant) lands without backend coordination.
