## What

On the next `POST /ingestion/datasources` that names an existing datasource ODDRN, `DataSourceIngestionServiceImpl.prepareForUpdate` **overwrites** `name` and `description` from the collector payload - silently. There is no merge-conflict check, no `lastModifiedBy` discrimination, no `log.warn`, no Activity event, and no diff in the response. An operator's deliberate UI rename ("Snowflake - Prod Finance") reverts to whatever the collector config carries ("snowflake-default") the next time the collector starts. The disjoint UI write path (`DataSourceMapper.applyToPojo` + `updateDataSource`) writes the same name/description fields, so operator-side and collector-side both write them with last-writer-wins and no coordination.

This is **net_new** - tracked today only as REFACTOR-423 (no doc/issue home). It pairs with H-005 (REFACTOR-424) and the ADR-CANDIDATE-142/143 promotion but has no code-side PLT.

## Where

The overwrite (line numbers verified against current HEAD `3049b9af`; the original `@ ede5d277` pin is stale, code unchanged):

```java
// service/DataSourceIngestionServiceImpl.java:86-89 - prepareForUpdate rebuilds the pojo, taking name+description from the ingested payload
return new DataSourcePojo(a)
    .setName(i.getName())            // :87 - overwrites the operator's UI rename
    .setDescription(i.getDescription());  // :88 - overwrites the operator's UI description
```

- `DataSourceIngestionServiceImpl.java:51` -> `reactiveDataSourceRepository.bulkUpdate(toUpdate)` persists the rebuilt pojos (full-pojo update via `ReactiveAbstractCRUDRepository.bulkUpdate:130`).
- `DataSourceIngestionServiceImpl.java:53, 62` - only `log.debug` on the to-update / to-create oddrn lists; no INFO/WARN and no Activity event recording the overwrite. `createDataSources` is `@ReactiveTransactional` (`:40`) but that is orthogonal - the transaction does not detect or warn on the operator-vs-collector field collision.
- UI write path that sets the same fields: `DataSourceForm.tsx` exposes editable `name` (`:96`) and `description` (`:131`); `updateDataSource` thunk (`datasources.thunks.ts:49-55`) PUTs `DataSourceUpdateFormData`, whose `name`/`description`/`namespace_name` are mapped by `DataSourceMapper.applyToPojo` (`:49`). Spec: `DataSourceUpdateFormData` carries `name`, `description`, `namespace_name` (`odd-platform-specification/components.yaml:1317`).

## User-facing impact

Confirmed user-facing (verified 2026-06-10 by tracing both write paths). An operator renames or re-describes a datasource in the Management UI (the form fields are editable and the `PUT` lands), sees their value, and then the next collector start silently reverts `name` and `description` to the collector config - with **no warning, no Activity-feed entry, and no diff**. The operator has no in-product signal that a re-registration overwrote their curation; diagnosing it requires knowing that the S2S `POST /ingestion/datasources` path rewrites these fields from the collector payload, which is invisible from the UI. Not data loss of catalog records and not a security issue, but a silent revert of deliberate operator metadata on every collector tick. Severity medium (held).

(Precision note: the collector payload's `name`/`description` come from the ingestion `DataSource` model via `DataSourceIngestionMapper.mapIngestionModel`; whichever values the collector sends - including blanks if the collector omits them - replace the operator's, so the revert is unconditional on the to-update path.)

## Suggested fix

Per the reflection's `proposed_fix_anchor`: at `DataSourceIngestionServiceImpl.prepareForUpdate` (lines 86-88), emit an Activity event / `log.warn` on a name/description overwrite, **or** add `lastModifiedBy` discrimination so operator UI edits are not silently reverted. Tracked today only as REFACTOR-423; pairs with H-005 (REFACTOR-424) and the ADR-CANDIDATE-142/143 promotion.
