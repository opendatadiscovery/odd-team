  - **Evidence**:
    - **The empty-cascade chain** (per sidecar primary source — `IntegrationController.java:19-22` + `IntegrationServiceImpl.java:20-23` + `ResourceFilesIntegrationRegistry.java:15-17`):
      - Controller: `getIntegration(String integrationId, ServerWebExchange exchange)` returns `Mono<ResponseEntity<Integration>>`; body is `return integrationService.get(integrationId).map(ResponseEntity::ok);`
      - Service: `integrationService.get(integrationId)` returns `Mono<Integration>` — `Mono.justOrEmpty(registry.get(id)).map(integration -> integrationMapper.map(integration, staticArgumentMappingContext));`
      - Registry: `registry.get(id)` is a TreeMap lookup — returns `Integration` instance or `null`.
      - `Mono.justOrEmpty(null)` is `Mono.empty()`; the `.map` is short-circuited; the controller's `.map(ResponseEntity::ok)` is also short-circuited; the final `Mono` emits empty.
    - **Spring WebFlux's empty-Mono semantic**: a reactive controller returning `Mono.empty()` (or `Mono<ResponseEntity<?>>.empty()` — both surface identically through the `ResponseBodyResultHandler`) produces HTTP 204 No Content. This is framework-default behaviour; the controller does not customize it. Verified statically (per sidecar evidence) AND symmetric with WebFlux documentation.
    - **The OpenAPI contract claim** (per sidecar primary source — `openapi.yaml:75-81`): the spec declares `GET /api/integrations/{integration_id}` with ONLY a `'200'` response key, body `Integration`. No `'404'`, no `'204'`. A spec-compliant client expects 200 with body on success and either an unhandled status or a thrown ResponseError on missing. The 204 is in neither the contract nor the documented error path.
    - **The platform-wide GET-by-id convention** (per sidecar — comparison evidence): most platform GET-by-id endpoints throw `NotFoundException` on missing-entity, which `ControllerAdvice` translates to HTTP 404 with body `{message: ..., code: 'USR002'}`. Examples:

    - **The operator-visible ambiguity**: an operator probing `GET /api/integrations/snowflake-xyz` and receiving HTTP 204 cannot tell whether: (a) the integration exists but has no body (currently impossible — the runtime always populates a non-empty body for existing integrations); (b) the integration does not exist (the actual reason for 204 currently). For a future feature that legitimately returns 204 (e.g., an integration that exists but has no wizard content), the same status code becomes ambiguous; for the current state, the 204 is misleading because the platform-wide convention is 404.
    - **The third-party SDK consequence**: an integrator generating a TypeScript / Java client from `openapi.yaml` encounters a 204 the spec does not declare. Generator-specific behaviour:
      - Most generators throw on undocumented 2xx response codes → silent runtime error.
      - Some generators map any 2xx to success with null body → the client treats 204 as "integration exists with null content", silently miscategorising the missing-id state.
      - Strict generators return a discriminated union of declared response codes only → 204 is "unhandled response" → the client must explicitly handle the absent-spec case.
      The integrator's reaction depends entirely on the SDK generator's choices; none of the options surface "the integration does not exist".
