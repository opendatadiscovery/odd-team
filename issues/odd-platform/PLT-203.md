## What

On the **Management → Owner Associations** admin page, the "Create association" dialog (which manually binds a platform user to an Owner via `POST` user-owner-mapping) gives the operator **no explicit success feedback** after a successful submit. There is no success toast, no inline confirmation, and no redirect to the resulting association — the **only** signal that the bind succeeded is that the modal closes. An admin who looks away during the brief request, or who is on a slow connection, has no durable cue that the operation completed and is liable to click Save again.

## Where

`odd-platform-ui/src/components/Management/OwnerAssociations/OwnerAssociationsHeader/OwnerAssociationForm/OwnerAssociationForm.tsx:108`

```tsx
const {
  mutateAsync: createUserOwnerMapping,
  isPending: isAssociationCreating,
  isSuccess,
} = useCreateUserOwnerMapping();
...
const onSubmit = async (data: UserOwnerMappingFormData) => {
  await createUserOwnerMapping({
    userOwnerMappingFormData: data,
  });
};
...
return (
  <DialogWrapper
    ...
    handleCloseSubmittedForm={isSuccess}   // <-- line 108: success is consumed ONLY to close the dialog
    isLoading={isAssociationCreating}
    clearState={clearState}
    confirmOnClose
  />
);
```

`isSuccess` is wired solely into `handleCloseSubmittedForm` — the mutation's success branch fires no toast and performs no navigation. There is no `onSuccess` callback raising a notification, and the page does not re-render to show the new association in a way the admin is taken to.

## Why it matters

Silent (no error — the operation genuinely succeeds; the defect is the absence of confirmation). Affects platform **administrators** managing user↔owner bindings. The concrete risk is a **duplicate audit row**: an admin who does not register the modal-close as "done" re-submits, creating a second mapping/association record and polluting the association History with a duplicate entry that then has to be reconciled. It is not data-loss and not a security issue, hence medium — but it is a repeatable correctness/UX trap on an admin surface where the audit trail is expected to be clean.

## Suggested fix

Add explicit success feedback to the mutation's success path: a success toast (the platform's existing notification mechanism) and/or an inline confirmation, ideally with a redirect/scroll to the newly-created association so the admin sees the result. Closing the dialog should remain, but it should not be the *only* signal. Open to alternatives on the exact affordance (toast vs. inline banner vs. redirect), but the success state must be made explicit rather than inferred from the modal disappearing.
