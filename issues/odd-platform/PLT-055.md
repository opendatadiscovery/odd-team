## What

DQ test severity mutation emits NO ActivityEvent row, stamps NO `last_modified_by`, increments NO version, dispatches NO notification. The PUT `/api/datasets/{data_entity_id}/dataqatests/{dataqa_test_id}/severity` is gated by `DATASET_TEST_RUN_SET_SEVERITY` permission but the audit trail of who-changed-what-and-when is unobservable.

Live `sla-statuses.md` (2026-05-27) explicitly states severity changes can flip a dataset's SLA colour from Yellow to Red **without any test pass/fail status changing**. SLA colour is consumed BY BI TOOLS via `GET /api/datasets/{data_entity_id}/sla` (Confluence, Notion, Excel, Looker). **Cross-origin flip happens with no platform-side signal of who triggered it.**

## User-facing impact

All load-bearing claims here are code-structure absence facts; every one re-verified by FE/BE trace 2026-06-10.

- **WHO acts:** a user holding `DATASET_TEST_RUN_SET_SEVERITY` opens a dataset's Test Reports panel and picks a new severity from the right-side select (`TestReportDetailsOverview.tsx:42-52`, severity select wrapped in `WithPermissions permissionTo={Permission.DATASET_TEST_RUN_SET_SEVERITY}` at :79-80, dispatching the `setDataQATestSeverity` thunk -> PUT `/api/datasets/{data_entity_id}/dataqatests/{dataqa_test_id}/severity`). The write succeeds: 200 + updated `DataEntity`.
- **WHAT is recorded:** nothing attributable. No activity event exists for this mutation -- `ActivityEventTypeDto.java` has no DQ-severity member (verified by reading the full 30-member enum), `DataQualityServiceImpl.setDataQualityTestSeverity` (:62-81) carries `@ReactiveTransactional` but no `@ActivityLog` (the only activity-emission mechanism, `ActivityAspect.java`), and the upsert touches only the 3-column `data_quality_test_severity` table -- `V0_0_44__dataqatest_severity.sql` declares `data_quality_test_id, dataset_id, severity` and nothing else: no `last_modified_by`, no `updated_at`, no version column to increment (verified by FE/BE trace 2026-06-10).
- **WHAT compliance sees:** the Activity feed cannot show the change (no event type = nothing to render -- absence settled statically); the DB row cannot answer "who/when" (no columns). "Who set this test to Critical" is unanswerable from any platform surface (verified by FE/BE trace 2026-06-10).
- **No notification fires:** notification delivery is WAL-driven off `alert`-table inserts; the severity path writes no alert row, and `grep severity` across the notification package returns zero hits (verified 2026-06-10).
- **Cross-origin observer:** `GET /api/datasets/{data_entity_id}/sla` serves a colour PNG (`CachingByteArraySLAResourceResolver.java:44-49`, `sla_red/yellow/green.png`) documented for embedding in BI tools (`sla-statuses.md:25-29`). The Yellow->Red flip on a pure severity reclassification is deterministic calculator arithmetic: a FAILED test moved Major->Critical moves the dataset from `hasFailedMajors -> YELLOW` (`SLACalculator.java:93-95`) to `anyCriticalFailed -> RED` (:84-86) with no run-status change -- exactly what the live doc states (`sla-statuses.md:39`). The BI consumer sees the colour change with no platform-side cause trail (static trace; the flip itself is arithmetic, not timing-dependent).

## Why it matters

Three workflows broken: (1) Compliance reviewers cannot answer "who changed SLA to Red on May 14" without DB inspection; (2) Operators triaging a flip cannot distinguish test-result change from severity reclassification; (3) BI tools see cross-origin flip with NO platform-side cause.

Blast radius wider than F-019 owner-lifecycle audit-silence - change consumed OUTSIDE platform UI. A team lead viewing Confluence sees Red Monday morning with no idea why. Sibling to LSN-001/LSN-002 silent-operator-trap class.

Severity HIGH: deliberate write + observable consequence + zero audit trail.

## Suggested fix

Read-old-then-emit-then-upsert (prior severity read at upsert-time anyway via existing-row check).

```java
@ReactiveTransactional
@ActivityLog(event = ActivityEventType.DATA_QUALITY_TEST_SEVERITY_CHANGED)
public Mono<Void> setDataQualityTestSeverity(long datasetId, long taskId, Severity severity) {
  return repository.fetchSeverity(datasetId, taskId)
      .defaultIfEmpty(Severity.MAJOR)
      .flatMap(oldSeverity -> {
        if (oldSeverity == severity) return Mono.empty();
        return repository.upsertSeverity(datasetId, taskId, severity)
            .then(activityEventPublisher.publish(
                ActivityEvent.builder()
                    .eventType(DATA_QUALITY_TEST_SEVERITY_CHANGED)
                    .dataEntityId(datasetId)
                    .oldState(Map.of("severity", oldSeverity, "taskId", taskId))
                    .newState(Map.of("severity", severity, "taskId", taskId))
                    .principal(authIdentityProvider.getPrincipal())
                    .build()));
      });
}
```

Schema: `ActivityEventType` gains `DATA_QUALITY_TEST_SEVERITY_CHANGED`; `activity-event-payload` schema gains variant with `taskId` / `oldSeverity` / `newSeverity`. `activity.data_entity_id NOT NULL` (DOC-GAP-192) NOT a blocker - DQ severity is per-dataset which DOES have a data_entity_id.

Backfill: forward-only. Audit trail begins at deploy.
