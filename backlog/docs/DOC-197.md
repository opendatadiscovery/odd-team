## Description

The live `configuration-and-deployment/odd-platform.md#enable-data-collaboration` section publishes the Slack app manifest verbatim and names `datacollaboration.slack-oauth-token` + `datacollaboration.enabled` + the `{ODD_PLATFORM_BASE_URL}/api/slack/events` webhook URL. The substrate batch-6 primary-source re-verification confirms two operator-visible gaps the page does not name.

**Facet 1 — Slack at-least-once delivery has no platform-side dedup (F-098a, HIGH).** Verified at primary source this run:
- `message_provider_event` table (`V0_0_59__data_collaboration.sql:25-39`) has NO UNIQUE constraint on `(provider, event_id)`; the only PK is `id BIGSERIAL`.
- `ReactiveMessageRepositoryImpl.createMessageEvent` (line 136-155) issues `DSL.insertInto(MESSAGE_PROVIDER_EVENT).set(record)` with NO `.onConflict(...)` clause.
- Slack's Events API delivers events at-least-once (Slack's own published semantic — retries on missed 2xx ACK within ~3s).
- Result: duplicate Slack retries (which happen routinely) insert duplicate rows; the downstream processor materialises N child `message` rows for one logical event. Operator-observable: the same message appears twice (or more) on the data-entity Discussions tab.

The same endpoint also has no inbound-webhook signature verification (verified via grep — `X-Slack-Signature|signing.secret|HmacSha256|...` returns ZERO MATCHES across `odd-platform/**/*.java|kt|yml|yaml`). That facet is DEDUP DOC-GAP-290 (corroboration write-back EXECUTED this run) — not re-emitted; tracked separately.

**Facet 2 — Slack `incoming-webhook` bot scope is requested in the published manifest but is UNUSED (F-098b, MEDIUM).** The Slack app manifest published in the live docs requests `incoming-webhook` as a bot scope alongside the scopes actually used (`channels:history`, `channels:read`, `chat:write`, `users:read`). The platform does NOT post messages via Slack incoming webhooks — outbound messaging uses the bot OAuth token (`chat:write` scope) instead. A least-privilege-conscious workspace admin reviewing the requested scopes asks "what does ODD do with incoming-webhook?" The answer is "nothing". The `incoming-webhook` scope is a historical copy-paste from a Slack example manifest.
