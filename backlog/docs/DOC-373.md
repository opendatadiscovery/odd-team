## Description

When `session.provider` is `REDIS`, ODD Platform stores every HTTP session in Redis, so a Redis outage means every authenticated request fails. But the platform's `/actuator/health` endpoint does **not** report Redis health:

- `application.yml:244-245` ships `management.health.redis.enabled: false` — the Spring Boot Redis health indicator is explicitly disabled in the bundled defaults.
- `SessionConfiguration.java:61-65` — the `RedisSessionConfiguration` static class is annotated `@ConditionalOnProperty(... havingValue = "REDIS") @EnableRedisWebSession` and has an **empty body**. It wires no `HealthIndicator`, no readiness contributor, nothing that surfaces Redis liveness.

Net operator-facing failure: with `REDIS` selected and Redis down (or unreachable, or evicting under `maxmemory`), the platform returns a 5xx storm to users while `/actuator/health` keeps returning `UP`. A load balancer or Kubernetes readiness probe pointed at `/actuator/health` will keep routing traffic to a platform that cannot serve a single authenticated request. The `odd-platform.md` REDIS subsection currently documents connection keys, TLS, pool sizing, and eviction-delegated-to-Redis, but says nothing about the health endpoint being blind to Redis — so an operator wiring a readiness probe is misled into thinking the probe covers the session store.

This item adds the caveat. The code fix (enable `management.health.redis.enabled` and/or add a Redis readiness contributor when `provider=REDIS`) is an upstream operability enhancement, not part of this doc.
