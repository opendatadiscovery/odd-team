## The Cornerstone-5 decision

Three options:

1. **Status quo — accept the gap.** The doc tree carries per-collector pages with per-adapter detail; the cross-adapter matrix lives on the odd-collectors README. The doc product cross-links to the README for the matrix surface (current state). No new content; no new canonical home; the canonical-homes.md "no canonical home today" annotation persists. Risk: a renamed repo or a moved README section silently breaks the link (the LSN-003 dbt-link case-law).
2. **Add a matrix page in the integrations hub.** `docs/integrations/README.md` (or a new `docs/integrations/per-adapter-features.md`) carries the full capability matrix — adapter columns × feature rows (filters, ERD, partitioning, etc.). Per-collector pages back-link to the matrix; the matrix page links per-adapter to the collector page for detail. Cost: authoring + maintenance of a matrix table that has to track 40+ adapters' feature surfaces. The matrix becomes a single SoT for cross-adapter feature claims.
3. **Add a config-examples canonical home.** A new subtree under `docs/integrations/config-examples/` carries per-adapter `collector_config.yaml` snippets (one per adapter, copy-pasteable). The figure caption on `ingestion-filters.md` retargets to the relevant per-adapter snippet. Cost: another large authoring + maintenance surface — and arguably duplicates content that already lives in the odd-collectors monorepo's `config_examples/` directory.

Option 2 is the cleanest doc-product alignment but a non-trivial authoring surface. Option 3 has a clearer path to redundancy with the upstream config_examples directory. Option 1 (status quo) is honest about the gap — log the deferral, accept the risk, fix when the per-collector authoring batch (DOC-070-style) gives the matrix a natural home.

**Recommended decision (for user approval): Option 1 today; fold into a future per-collector authoring batch.** The matrix has limited reader value pre-deployment (an operator picking a stack already knows their data sources); post-deployment, the per-adapter page is the right depth. Carrying the matrix as a separate page risks drift relative to the per-collector pages (parallel surfaces). Option 1 lets the doc product evolve naturally; the GitHub link survives as a "see the upstream contributor README for the matrix" pointer with a known limitation.
