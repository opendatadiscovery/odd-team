## What

Three defects on the Notification Settings dialog + adjacent Resolve/Reopen button. Doc-side mitigation (DOC-201) names them as known limitations; structural fixes are this PLT. All three re-verified 2026-06-10 against the components (line numbers corrected; the housekeeping hard-delete premise behind Defect 2 confirmed against the BE job).

**Defect 1 - Notification Settings dialog has no optimistic concurrency check.** `NotificationSettings.tsx:49-53` (`handleSubmitForm`) submits the halt-config (`dataEntityAlertConfig`) with no version field; the form (`useForm`, `:40-43`) carries no version either. Two operators submitting simultaneously: the later write silently overwrites the earlier one. No version, no If-Match, no concurrent-edit detection. HOLDS.

**Defect 2 - Alert Resolve/Reopen button has no confirmation dialog, and resolution is destructive after a TTL.** `DataEntityAlertItem.tsx:111-120`: the Resolve/Reopen Button (`:113-118`) fires `onClick={alertStatusHandler}`, which dispatches `updateAlertStatus` immediately (`:38-44`) with no confirmation. Resolution is destructive in combination with housekeeping: `AlertHousekeepingJob.java:28-43` **hard-deletes** alerts (and their `ALERT_CHUNK` history) once `STATUS in (RESOLVED, RESOLVED_AUTOMATICALLY)` and older than `housekeepingTTLProperties.getResolvedAlertsDays()`. So an accidental Resolve click puts the alert + its history on a hard-delete timer with no undo prompt. HOLDS (hard-delete premise verified against the BE job).

**Defect 3 - Notification Settings dialog hardcoded English copy.** `NotificationSettings.tsx:57` ("Notification settings" title), `:76-79` (the "Select the type of notifications..." body), `:102-104` (the "When the time is up..." caption), and `:111` (`text='Apply'`) are hardcoded - no `t()`. The PARENT button that opens the dialog DOES use `t('Notification settings')` (`DataEntityAlerts.tsx:57`) - mid-feature i18n inconsistency. HOLDS.

## Why it matters

Defect 1 silently corrupts halt-config in multi-operator workflows (last write wins). Defect 2 is the most load-bearing: the BE hard-deletes resolved alerts and their chunk history after the TTL (`AlertHousekeepingJob.java:40-43`), so a single accidental Resolve click - with no confirmation - starts an irreversible countdown on audit data the platform's own workaround narrative recommends exporting before resolving. Defect 3 is small but represents the same i18n discipline gap flagged in the DOC-180 family.

## User-facing impact

Verified 2026-06-10 by tracing the components + the housekeeping job:

- **Defect 1 (latent, multi-operator):** the Notification Settings "Apply" submits no version, so two operators editing the same entity's halt-config concurrently get last-write-wins with no "changed by another user" signal. Visible only in the (uncommon but real) concurrent-edit case; the single-operator path is unaffected. Code-confirmed (no version in `useForm` state or the submit payload); the "silent overwrite" is the runtime consequence of the missing version, standard last-write-wins.
- **Defect 2 (active, destructive):** code-confirmed end-to-end - the Resolve/Reopen button mutates immediately with no confirmation (`DataEntityAlertItem.tsx:113-118` -> `:38-44`), and a resolved alert + its chunk history is hard-deleted once past the resolved-alerts TTL (`AlertHousekeepingJob.java:30-43`). A misclick on Resolve therefore irreversibly destroys alert history after the TTL window, with no UI warning. This is the genuinely user-facing, genuinely destructive part of the cluster.
- **Defect 3 (active, cosmetic/i18n):** code-confirmed - a non-English operator sees the dialog title, body, caption, and Apply button in English while the button that opened the dialog is localized. Pure i18n inconsistency, no data impact.

Severity MEDIUM stands, driven by Defect 2's destructive-misclick path; Defects 1 and 3 are latent/cosmetic respectively.

## Suggested fix

**Defect 1 - optimistic concurrency (Option A recommended):** add `version` column on `data_entity_alert_halt_config`; UI submits `If-Match: <version>`; server 412 on stale write; UI surfaces "Configuration was changed by another user - reload."

**Defect 2 - confirmation dialog:**
```tsx
<Button onClick={() => setConfirmOpen(true)}>{t('Resolve')}</Button>
<ConfirmationDialog
  open={confirmOpen}
  body={t('This alert will be retained for {{days}} days then permanently deleted. Use the API workaround to export before resolving. Proceed?', { days: housekeepingDays })}
  onConfirm={dispatchUpdateAlertStatus}
/>
```

**Defect 3 - i18n the strings:**
```tsx
// NotificationSettings.tsx:57 (and the :76-79 body, :102-104 caption, :111 Apply)
- <Typography variant='h4' component='span'>Notification settings</Typography>
+ <Typography variant='h4' component='span'>{t('Notification settings')}</Typography>
// + add entries to en/es/fr/ua/hy/ch.json
```
