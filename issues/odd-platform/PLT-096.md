## What

Three defects on the entity detail page's Overview sidebar list truncation (Tags / Terms / Groups columns) - one real semantic bug where slice-then-sort silently defeats the importance-aware comparator, one undefined-behaviour cleanup where a bare `.sort()` on a struct array is a no-op, and one truncation-affordance gap where `View All (N)` only reveals the full count after click. All re-verified 2026-06-10 against the components (line numbers + comparator text corrected; sibling instances upgraded from "likely" to confirmed).

**Defect 1 - slice-then-sort defeats importance ordering on Tags (F-179a - MEDIUM semantic bug).** `OverviewTags.tsx:54-65`: `tags.slice(0, visibleLimit).sort(tagsCompare).map(...)` with `visibleLimit = 20` (`:23`). **`.slice(0, 20)` runs FIRST; `.sort(tagsCompare)` only orders the already-truncated window.** The `tagsCompare` comparator (`:26-32`) promises "important first, then alphabetical" but only WITHIN whatever 20 elements the source array happened to put first. For an entity with >20 tags whose important ones sit past index 19, the visible 20 are array-order and may contain NO important tag. Worse, the "View All" expansion (`:70-72`) ALSO does `slice(visibleLimit).sort(tagsCompare)` on the remainder independently - so even expanded, the list is two separately-sorted halves split at an arbitrary index, never a single globally-importance-ordered list. HOLDS (the bug is real; the mechanism is slightly worse than "important hidden behind cap" - importance order is never computed across the whole set).

**Defect 2 - Bare `.sort()` no-op on OverviewGroups (F-179b - LOW cleanup).** `OverviewGroups.tsx:49-54`: `dataEntityGroups.slice(0, visibleLimit).sort().map(...)` with `visibleLimit = 10` (`:24`). Bare `.sort()` on `DataEntityRef[]` -> JS default comparator stringifies via `toString()` -> all elements become `"[object Object]"` and compare equal -> silent no-op. The View-All branch (`:59-61`) repeats the same no-op `.sort()`. Misleading to readers who infer "sort happens here." HOLDS.

**Defect 3 - `View All (N)` count only visible after click (F-179c - LOW UX).** `OverviewTags.tsx:85`: `text={viewAll ? t('Hide') : \`${t('View All')} (${tags?.length})\`}`. The `(N)` suffix is the ONLY signal there are MORE than 20 tags before the user clicks. An operator skimming the page may not notice the parenthetical and conclude the entity has only 20 tags. Sibling shape at `OverviewGroups.tsx:71-73`. HOLDS.

## User-facing impact

Verified 2026-06-10 by reading the components and tracing the exact order of operations:

- **Defect 1 (active, semantic):** code-confirmed slice-then-sort - `OverviewTags.tsx:54-56` slices to the first 20 source-order tags, THEN sorts only those 20. For any data entity with >20 tags whose `important` tags are not already in the first 20 source positions, those important tags do NOT appear in the visible list (they fall into the separately-sorted, collapsed View-All remainder). A user looking at a heavily-tagged entity sees a top-20 that misrepresents importance - the platform's "important tags rise to the top" affordance is broken for exactly the entities where it matters most. The same bug exists on the term-detail Tags list (`Terms/.../OverviewTags.tsx:47-49`). Reproducibility depends on data shape (>20 tags with important ones past index 19), but the defect is purely client-side and code-settled.
- **Defect 2 (active, but invisible/cleanup):** code-confirmed no-op - `.sort()` on a `DataEntityRef[]`/`LinkedTerm[]` with no comparator does nothing (default stringify makes all elements equal). User impact is effectively nil today (the list renders in source order either way); the defect is misleading code that invites a future incorrect refactor. Same no-op on `OverviewTerms.tsx:49`.
- **Defect 3 (active, polish):** code-confirmed - the only "there are more" signal before clicking is the `(N)` suffix on the View All button (`OverviewTags.tsx:85`, `OverviewGroups.tsx:71-73`). A skim-reading operator can miss it and under-count. Minor, real, low-severity.

Severity MEDIUM stands, driven by Defect 1 (genuine, user-visible mis-ordering on heavily-tagged entities); Defects 2 and 3 are cleanup and polish.

## Why it matters

- **Defect 1 is the real semantic bug** - the importance-aware comparator is product-level user intent ("important tags rise to the top"); slice-then-sort silently disregards that intent for any entity with >20 tags. Operators tagging 30+ entities in a domain see "important" tags get hidden behind the 20-row cap; the affordance the platform promises is broken.
- **Defect 2 is misleading code** - the `.sort()` call signals to a reader that ordering happens; in fact nothing happens. A future maintainer touching `OverviewGroups.tsx` may assume the sort is meaningful and refactor incorrectly.
- **Defect 3 is a polish defect** - the `(25)` count after the View All label is too subtle. Operators reading the page rapidly skip it. The fix is one inline `Showing 20 of 25` row above the list.

Severity MEDIUM driven by Defect 1; Defects 2 + 3 are cleanup / polish.

## Suggested fix

### (a) Defect 1 - Sort BEFORE slice

```tsx
// OverviewTags.tsx:54-65
[...tags].sort(tagsCompare).slice(0, visibleLimit).map(tag => (
  <TagItem key={tag.id} tag={tag} />
))
```

The spread is necessary because `.sort` mutates; we need to leave the source array untouched. Apply the SAME (a) fix to `Terms/TermDetails/Overview/OverviewTags/OverviewTags.tsx:47-49` - it is a confirmed second instance of this exact slice-then-sort-with-`tagsCompare` bug. (`OverviewTerms.tsx` is a Defect-2 case, not Defect-1: it uses a bare `.sort()` with no comparator - handle it via the (b) path below.)

### (b) Defect 2 - Remove the no-op OR supply a comparator

Two paths:

**(b1) Remove the bare `.sort()`** if the underlying repository already returns groups in a meaningful order (verify the wire payload):

```tsx
// OverviewGroups.tsx:49-54
dataEntityGroups.slice(0, visibleLimit).map(group => (
  <GroupItem key={group.id} group={group} />
))
```

**(b2) Supply a comparator** (e.g., by group name) if there is no upstream ordering guarantee:

```tsx
const groupsCompare = (a: DataEntityRef, b: DataEntityRef) =>
  (a.internalName ?? a.externalName).localeCompare(b.internalName ?? b.externalName);

[...dataEntityGroups].sort(groupsCompare).slice(0, visibleLimit).map(...)
```

(Prefer (b2) for consistency with the OverviewTags fix shape.)

### (c) Defect 3 - Inline "Showing 20 of 25" affordance

```tsx
// OverviewTags.tsx - above the list:
{!viewAll && tags && tags.length > visibleLimit && (
  <S.TruncationHint variant="caption" color="text.secondary">
    {t('Showing {{visible}} of {{total}}', { visible: visibleLimit, total: tags.length })}
  </S.TruncationHint>
)}
```

The `View All (N)` button can keep the count suffix for redundancy; the inline hint is the visible signal.
