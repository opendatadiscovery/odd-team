## What

The Management -> Associations -> New (Pending) tab's per-row Accept / Reject ConfirmationDialog text does two things wrong at once:

1. **Broken i18n key -> ungrammatical text in EVERY locale (corrected/enriched 2026-06-10).** The Accept dialog builds its text from `t('will be map to owner')` (`NewAssociationRequest.tsx:74-76`). That key is **ungrammatical** ("will be **map**", should be "mapped") AND - the part the original draft missed - **it does not exist in any of the six translation catalogs**. The catalogs already ship the *correct* key `"will be mapped to owner"` (present, and translated, in `en/es/ch/fr/ua/hy.json`, e.g. `en.json:418`, `fr.json:413`), but the component never references it. Because i18next is configured with no `saveMissing`/custom missing-key handler (`locales/i18n.ts`), a missing key falls back to **returning the key string verbatim** - so every locale (not just English) renders the broken English "...will be map to owner..." and the already-translated string is dead. So this is two bugs in one line: a grammar typo *and* a silent translation miss that defeats localization for 5 non-English locales. The Reject dialog by contrast uses only keys that exist and are grammatical (`'Association request to map user'` `en.json:51`, `'to owner'` `:408`, `'will be rejected'` `:419`).
2. **Missing operational guidance** - neither dialog names the operation's reversibility or the next-step path. Accept creates a `user_owner_mapping` row that is reversible only via the Active-tab Remove (a separate sub-tab with its own ConfirmationDialog). Reject is a status-only update that stays in History indefinitely with no re-trigger affordance. Operators get no signal whether they're about to do something they can undo.

Sister UX surfaces with identical defect shape:
- `ActiveAssociationRequest.tsx:80-84` (per-row Remove ConfirmationDialog - "User X will stop being associated with owner Y") - terse, no consequence disclosure (see DOC-223 for the doc-side coverage of the consequences)
- `DataSourceItemToken.tsx:37-49` + `CollectorItemToken.tsx:37-49` (token-rotation ConfirmationDialog - "Are you sure?" + "Regenerate token for X?") - no no-grace-period warning (cross-link DOC-218 doc-side; possibly fold here or split per maintainer preference)

## Where

`odd-platform-ui/src/components/Management/OwnerAssociations/OwnerAssociationsList/OwnerAssociationsNew/NewAssociationRequest/NewAssociationRequest.tsx:70-104`

The actual code builds the dialog text through i18next `t()` interpolation (not a raw literal - re-read verbatim 2026-06-10):

```tsx
// Accept dialog (NewAssociationRequest.tsx:73-77)
actionText={
  <>{`${t('User')} "${username}" ${t('will be map to owner')} "${ownerName}"`}</>
}   // 'will be map to owner' is BOTH ungrammatical AND absent from all 6 catalogs ->
    // i18next echoes the key verbatim -> "...will be map to owner..." in every locale.
    // The correct, already-translated key 'will be mapped to owner' (en.json:418 et al.) is unused.

// Reject dialog (NewAssociationRequest.tsx:91-93) - all keys exist + are grammatical; no undo/permanence hint
actionText={`${t('Association request to map user')} "${username}" ${t('to owner')} "${ownerName}" ${t('will be rejected')}`}
```

The mirror pattern at `EditableOwnerItem.tsx:59-72` is a positive example - the cascade-block ConfirmationDialog enumerates the referent rows that would block the delete, giving the operator a direct path forward.

## User-facing impact

Verified by reading the component (`NewAssociationRequest.tsx:73-93`), the six locale catalogs, and `locales/i18n.ts`. Two operator-visible effects, both code-settled:

1. **Every** operator (all 6 locales) clicking Accept on a pending association request sees the ungrammatical confirmation text "User \"X\" will be map to owner \"Y\"" - because the requested i18n key is missing and i18next falls back to echoing it. Non-English operators additionally lose localization on this string: the correct translated form ships in their catalog but is never looked up. This is a concrete, reproducible rendering bug (hence severity low, not a pure no-sev adjustment), distinct from the (separate) UX-enrichment ask.
2. Neither Accept nor Reject dialog discloses reversibility, so operators cannot tell from the dialog whether the action is undoable (Accept -> reversible via Active-tab Remove; Reject -> moves to History, user must re-submit). This half is the genuine UX-quality adjustment.

## Why it matters

Two operator-visible failures stacked:
- Operators reading the ungrammatical "be map" form a (subliminal) "this codebase is sloppy" impression that erodes confidence in the platform's reliability for security-adjacent workflows.
- Operators without doc context (which they currently lack - see DOC-219 for the doc-side coverage) cannot infer the operation's reversibility from the dialog. They either over-cautiously avoid clicking, or click through and discover the Active-tab Remove path by trial-and-error.

The grammar fix is trivial and standalone. The richer-dialog-text request is a UX-quality enhancement matching the `EditableOwnerItem.tsx:59-72` cascade-block precedent.

## Suggested fix

1. **Grammar + i18n fix (trivial, ship immediately)**: at `NewAssociationRequest.tsx:74-76`, change the key reference `t('will be map to owner')` -> `t('will be mapped to owner')`. The target key already exists and is translated in all six catalogs (`en.json:418`, `es/ch/fr/ua/hy`), so this single edit fixes both the grammar **and** the silent translation miss with no catalog change. (Optionally remove the now-orphaned broken key if it appears anywhere, and delete the stale grammatical typo from any catalog that carries it - none currently do.)
2. **Dialog enrichment** (UX quality, mirror EditableOwnerItem.tsx:59-72 disclosure pattern):
   - Accept dialog: "User X will be mapped to owner Y. To undo: visit Management -> Associations -> Active and click Remove on this row."
   - Reject dialog: "Association request to map user X to owner Y will be rejected. The request will move to History; the user can submit a fresh request from their home page."
3. Apply the same enrichment treatment to `ActiveAssociationRequest.tsx:80-84` (Remove dialog) - add consequence disclosure naming the user's downstream views going silent-empty (cross-link DOC-223). Optionally fold the token-rotation dialog enrichment (DOC-218 doc-side; richer dialog text mirroring the cascade-block precedent) into this same PR, or split.
