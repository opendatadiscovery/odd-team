## Description

Routing the ST-6 doc change surfaced that the 1.0.0 documentation train **does not exist in this environment**,
and neither does the content three `pending-release` items say is already authored on it.

**Verified 2026-08-30 in `../documentation` (by content, not only by SHA):**

| Check | Result |
|---|---|
| `git branch -a` | only `origin/main` and `origin/release/0.28.0` — **no `release/1.0.0`** |
| `git cat-file -t` on the five commits cited by DOC-494/495/497 (`aa7b651`, `61cd0a8`, `7259606`, `891ed14`, `5b2bb04`) | **all five MISSING** |
| `git log --all -- docs/data-discovery/recently-viewed.md` | **no ref carries the page** |
| `origin/main:docs/data-discovery/search.md` contains `search?q=` | **0 occurrences** — the ST-1a/ST-1b rewrites are not on main either |
| the worktrees the items name (`../documentation-ctrib048docs`, `../documentation-ctrib049docs`) | **gone** |

DOC-495 and DOC-497 both record that the push to the shared train was **maintainer-gated and still pending**; the
worktrees were subsequently removed, so the commits became unreachable and were pruned. DOC-494 states its content
was committed *on* `release/1.0.0` — a branch that does not exist here.

**Why this is critical rather than tidy-up:** these items carry `status: pending-release`, which tells the release
gate their content is authored and only awaiting publication. At the 1.0.0 gate the train would be merged, the
items flipped, and the pages would simply not be there — and the same premise would be applied to DOC-499's
coverage matrix.

## Acceptance criteria

- [ ] Establish whether the content survives anywhere the maintainer holds it (another clone, a stash, an unpushed
      local branch) — recovery is preferred over re-authoring.
- [ ] If it does not survive, re-author DOC-494 / DOC-495 / DOC-497 content and set their status honestly back to
      `pending` until it is on a reachable branch.
- [ ] Create `release/1.0.0` off `documentation` `origin/main` and push it, so subsequent slices (including
      #1840 / ST-6) have a real train to land on rather than a per-slice orphan branch.
- [ ] Add a release-gate precondition to `playbooks/release-train-merge.md`: every `pending-release` doc item's
      cited commit must resolve (`git cat-file -e`) on a **reachable** branch before the gate proceeds.

## Notes

The recurring shape is the same one LSN-034/LSN-038 describe from the other direction: work that is "done" in a
record but never made it onto a shared, reachable ref. The proposed gate precondition is the forcing function —
a record that cites a SHA nobody can resolve is not evidence.
