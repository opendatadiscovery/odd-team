## What

`data_entity.view_count` is the sole ranking signal for the home-page "Popular" / "Recommended" strip (`GET /api/dataentities/popular` orders by `VIEW_COUNT DESC` with only an id-DESC tiebreaker), and the counter that feeds it is trivially inflatable:

1. **+2 per detail-open (double fetch).** Opening an entity detail page fires `fetchDataEntityDetails` twice because the `useEffect` dependency array contains `details.status?.status`, which is itself populated by the fetch's fulfilled action - first render `status=undefined` -> real, second render re-fires. Each call is a bare `view_count + 1` UPDATE, so a single page-open registers as **+2** (empirically pinned by probe P-004). This is the LSN-017 surface.
2. **No rate-limit, no idempotency key, no auth gate, no anti-abuse signal, no index on `view_count`.** A scripted detail-read loop - anonymous under `auth.type=DISABLED` - pumps any chosen entity to the top of the Popular column.

The published catalog-overview / entity-detail pages present view count as neutral display metadata and describe Popular as "most-viewed", with no caveat that the signal is self-reinforcing and forgeable.

Sources: HARVEST-024, HARVEST-026, HARVEST-027 (doc-understanding harvest, 2026-05-29). Doc caveat tracked at `backlog/docs/DOC-297.md`.

## User-facing impact

**Verified - workspace runtime evidence (probe P-004, the LSN-017 surface).** The +2-per-open is not a backend extrapolation; it is pinned by a runtime probe against a real local stack:

- Probe run `lineage/odd-platform/probe-runs/2026-05-19-P-004.yaml` (`ran_against_substrate_commit: ede5d277`, `stack_profile: odd-minimal`, `AUTH_TYPE=DISABLED`) drove a single detail-page open and asserted, all PASS: `xhr_count == 2`, `final_view_count - initial_view_count == 2`, and `final_view_count - initial_view_count == xhr_count` (`observe_outcomes.final_view_count: 2`). So one UI page-open writes `view_count += 2`.
- The FE double-fetch is code-settled: `DataEntityDetails.tsx:56-64` lists `details.status?.status` (line 63) in the `useEffect` dependency array; that field is populated by the fetch's own fulfilled action, so the first render fires the fetch (`status=undefined`), the fulfilled status mutates the dep, and the effect re-fires - two `GET /api/dataentities/{id}` calls, each a `+1` UPDATE (`incrementViewCount`, repo:176). This is **not** the React 18 StrictMode double-invoke (that is dev-only and unmounts/remounts; this fires in production and is driven by the status dependency). There is no de-dup, debounce, idempotency key, or mount-once sentinel on the path.
- The contract pin `IT-001` (`integration-tests/protocols/IT-001-view-count-backend-delta.md`) confirms the backend itself is a clean `+1` per `GET` (delta == 5 over five calls); the doubling is therefore purely the FE firing twice, exactly as scoped here.
- Ranking exposure: `getPopular` (controller:307) -> `listPopular` orders solely by `VIEW_COUNT DESC` with an `ID DESC` tiebreaker (verified above), so the inflated counter is the sole DESC signal for the home-page "Popular" strip. `getDataEntityDetails` (controller:140-145) carries no `@PreAuthorize`, so under the shipped `auth.type=DISABLED` default the increment is reachable anonymously - a scripted detail-read loop inflates any entity to the top.

The remaining unverified-by-runtime element is the **ranking-manipulation outcome** (a scripted loop visibly reordering the live Popular strip) - the double-count and the sole-DESC-signal are both pinned; the "trivially inflatable to #1" claim is the deductive composition of those two verified facts (un-throttled ungated `+1` write x sole DESC ranking), not separately driven.

## Why it matters

The "Popular" strip is a primary discovery surface - it is how operators and data consumers decide what data matters. Because its sole input is an unauthenticated, un-throttled, double-counting counter, the ranking reflects how often pages were *opened* (and how easily a script can open them), not what the organisation actually values. Any user - anonymous under the shipped `DISABLED` default - can promote an arbitrary entity to the top with a trivial read loop, and routine browsing already over-counts 2x. This is the LSN-001/002 class: the platform presents a trustworthy-looking signal that is silently gameable, and the docs reinforce the false trust.

## Suggested fix

- Fix the LSN-017 double-fetch: remove `details.status?.status` from the `useEffect` dependency array (or guard the fetch behind a mount-once sentinel) so a page-open writes at most +1.
- Debounce/dedup the write server-side: a per-entity-per-session sentinel (or an idempotency key) so a single session cannot pump the counter; consider authenticating the increment so anonymous loops under `DISABLED` cannot inflate.
- Harden the ranking: add a secondary signal (recency, distinct-viewer count) so a single counter is not the sole input, and add an index on `view_count` for the ordering.
