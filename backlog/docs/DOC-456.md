## Description

The user-facing page and the operator reference make **opposite** claims about whether the attachment
upload API enforces `attachment.max-file-size`:

- `data-discovery/attachments.md:33` — "The single restriction is **file size**, which is capped at
  `attachment.max-file-size` megabytes (default `20`). **Files larger than the cap are rejected by the
  upload API.**"
- `configuration-and-deployment/odd-platform.md:1044` — "the per-file upload limit the **UI enforces
  before upload**... the server does **not** re-validate per-file size on the upload path... There is
  therefore **no effective server-side total-file size limit**: a direct (non-UI) API caller can exceed
  `attachment.max-file-size` by any amount."

The operator reference is the verified-against-code statement (the cap is a UI/client-side pre-upload
hint, consumed only by `AttachmentServiceImpl.getUploadOptions()`; neither `LocalFileUploadServiceImpl`
nor `RemoteFileUploadServiceImpl` re-validates against it — see the `application_yml__config-prefix__attachment`
sidecar's `security_review`). So `attachments.md:33` is **wrong** and, worse, understates a real
enforcement gap — the same failure class as LSN-001 / LSN-002 (a doc claim that does not match the
consumer code). **Incorrect documentation outranks missing documentation** (CLAUDE.md Priority Order #1).

## Acceptance Criteria

- [ ] `data-discovery/attachments.md:33` reworded so the size cap is described as a **UI / client-side
      pre-upload check**, NOT an upload-API rejection (align with `odd-platform.md:1044`).
- [ ] The corrected sentence does not claim server-side enforcement; ideally cross-links to the
      "Attachment Storage Configuration" operator section for the authoritative detail.
- [ ] Live page (post-merge) no longer states files are "rejected by the upload API".
