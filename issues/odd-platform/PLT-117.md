## What

The platform's backend PRESERVES per-dataset Data Quality (DQ) **report / SLA** data for **soft-deleted** datasets: the DQ report and SLA read paths resolve existence with `existsIncludingSoftDeleted` (not `exists`), so a direct API caller can still answer "what was this dataset's DQ state just before it was deprecated/deleted?". But the **UI removes every DQ surface for a soft-deleted dataset**: the `test-reports/*` route is wrapped in a `RestrictedRoute` gated on `isAllowedTo={!isStatusDeleted}` with `redirectTo='../overview'`, AND the matching "Test reports" tab is hidden from the tab bar (`hidden: ... || isStatusDeleted`). So an operator cannot reach the DQ report/SLA data the backend still serves; if they deep-link or bookmark the `test-reports` URL they are silently redirected to Overview with no explanation.

The result is a **cross-channel inconsistency on the DQ report/SLA read paths**: a direct API caller gets the DQ report/SLA the backend preserves for a soft-deleted dataset, while the UI offers no path to it. The audit/forensic value the `existsIncludingSoftDeleted` choice creates is unreachable from the surface most operators use.

This is purely a UI-routing/visibility defect; the backend is correct on the report/SLA paths and is the positive half of the contradiction. Two scoping corrections from the original draft are folded in below (it is a blanket `isStatusDeleted` policy, not test-reports-specific; and the tab is *hidden*, not a click-then-redirect).

## Where

All cites re-verified against the working tree on 2026-06-10 (HEAD `3049b9af`; reflection anchor `ede5d277`).

The UI removes the DQ surface in TWO places. First, the tab is hidden from the tab bar for a soft-deleted entity (`odd-platform-ui/src/components/DataEntityDetails/DataEntityDetailsTabs/DataEntityDetailsTabs.tsx:64-68`):

```tsx
{
  name: t('Test reports'),
  link: dataEntityTestReportsPath(dataEntityId),
  hidden: !isDataset || !datasetQualityTestReportTotal || isStatusDeleted,
},
```

Second, the route itself is guarded so a deep-link / bookmark is redirected (`odd-platform-ui/src/components/DataEntityDetails/DataEntityDetailsRoutes/DataEntityDetailsRoutes.tsx:56-69`):

```tsx
<Route path='test-reports/*' element={
  <RestrictedRoute isAllowedTo={!isStatusDeleted}
                   redirectTo='../overview'
                   component={TestReport} />
}>
```

This is a **blanket policy**, not test-reports-specific: the same `isStatusDeleted` gate hides+guards Lineage, Test reports, History, Alerts, Linked entities, and Discussions (`DataEntityDetailsTabs.tsx:62,67,72,79,84,98`; `DataEntityDetailsRoutes.tsx:49-53,59-63,73,88-92,98-102,109-113`).

The backend preserves DQ data for soft-deleted datasets on the **report and SLA read paths only** (`odd-platform-api/.../service/DataQualityServiceImpl.java`):

```java
getDatasetTestReport(datasetId): existsIncludingSoftDeleted(datasetId)   // line 55
getDatasetSLA(datasetId):        existsIncludingSoftDeleted(datasetId)   // line 96 (feeds getSLA/getSLAReport)
setDataQualityTestSeverity(...): existsIncludingSoftDeleted(...)         // lines 67-68 (a write, not a read surface)
```

Scope correction: `getDatasetTests` - the endpoint the TestReport tab's *test list* actually calls (`TestReport.tsx:44` -> `fetchDataSetQualityTestList`) - does NOT use `existsIncludingSoftDeleted`; it goes straight to the repository (`DataQualityServiceImpl.java:38-51`). So the "API serves the full DQ history" contrast is accurate for the **report counts and SLA** (`getDatasetTestReport`/`getSLA`/`getSLAReport`), not for the test list. The original draft's "every DQ read path" claim is narrowed accordingly.

## User-facing impact

Verified end-to-end on 2026-06-10 by reading both ends. Auth-independent (the gate keys on entity status, not auth mode). Two distinct user experiences, both confirmed in code:

- **Normal navigation:** the "Test reports" tab is simply ABSENT from the tab bar of a soft-deleted dataset (`DataEntityDetailsTabs.tsx:67`, `hidden: ... || isStatusDeleted`). There is no visible tab to click, so the "click -> silent redirect with no explanation" story in the original draft does NOT occur via the chrome. The operator just sees no DQ section and concludes the deleted dataset has none.
- **Deep-link / bookmark:** if the operator navigates straight to `.../test-reports` (a saved link, a shared URL, browser history), the route guard redirects them to `../overview` with no message (`DataEntityDetailsRoutes.tsx:59-63`). This is the only path where the unexplained redirect is observed.

Either way the DQ report-counts + SLA the backend still serves for that dataset (`DataQualityServiceImpl.java:55,96`) are unreachable from the UI, while a direct API caller (`GET /data_entities/{id}/data_quality_test_report`, `/sla`) gets them - a real cross-channel split, but scoped to the report/SLA paths, not the full test list.

## Why it matters

A forensic workflow - "the dataset was deprecated and soft-deleted; what was its DQ report/SLA just before deletion?" - is reachable via the API but has no UI path. The platform pays for preservation in the backend (`existsIncludingSoftDeleted` on the report/SLA reads) and then offers no surface for it once the dataset is soft-deleted.

The cross-channel split is the substantive hazard: a UI user concludes "this deleted dataset has no DQ data" while the report/SLA is one `curl` away. An operator cannot treat the UI as a complete view of what the platform retains.

Severity **medium** holds: no data is lost or exposed (the backend still serves it), and the API workaround exists - but a deliberately-preserved capability has no human surface. Note this is a *blanket* soft-deleted-entity UI policy (six tabs), so "fix test-reports in isolation" would be inconsistent with the rest of the deleted-entity UX; see Suggested fix.

## Suggested fix

The load-bearing requirement: a human operator can reach the DQ report/SLA the backend preserves for a soft-deleted dataset, or is told clearly why they cannot. Because the hiding is a **blanket** `isStatusDeleted` policy across six tabs (`DataEntityDetailsTabs.tsx:62-98`), pick a treatment that is coherent for soft-deleted entities as a whole, not a one-off for test-reports:

1. **Align the report/SLA surfaces with the backend (preferred)** - for soft-deleted datasets, un-hide the "Test reports" tab (`DataEntityDetailsTabs.tsx:67`) and drop the route guard (`DataEntityDetailsRoutes.tsx:59-63`), rendering it read-only/"archived" so it honours the `existsIncludingSoftDeleted` data the backend already returns. (Scope it to the DQ report/SLA the backend actually preserves - the test *list* path is not preserved, so the read-only view should be driven by `getDatasetTestReport`/SLA.)
2. **Make the asymmetry explicit** - if hiding deleted-entity tabs is a deliberate product choice, replace the silent `redirectTo='../overview'` on deep-links with an explicit "This dataset is deleted; its DQ report/SLA is available via the API" message, and document the deleted-entity UI policy.

Either way, decide it as a deleted-entity policy (the other five gated tabs share the same `isStatusDeleted` mechanism), not a test-reports patch.

Defect survives, re-scoped to the report/SLA cross-channel split; severity unchanged (medium); `user_facing_verified` flipped true (both ends now code-settled). Same failure mode as PLT-176: a UI claim shipped from a UI walk without re-reading the live component.

Distinct from **PLT-055** (the other F-022 platform-side item), which covers a different finding on this feature - the audit-silence on the DQ severity *mutation* (H-005). PLT-117 is the soft-deleted *read*-surface redirect (H-006).
