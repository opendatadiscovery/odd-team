## Description

The `/api/activity/counts` endpoint returns four numbers — `total_count`, `my_objects_count`, `upstream_count`, `downstream_count` — that an API consumer or UI author would naturally read as a partition of the total (i.e. `total = my + upstream + downstream`). They are **not** a partition, and the docs/OpenAPI say nothing about it.

Two facts make the four numbers non-additive and potentially mutually inconsistent:

1. **Overlapping sets.** The four counts answer four *independent* questions over sets that overlap: every event is in `total`; an event on an entity the user owns *and* that is upstream of something is counted in both `my_objects_count` and `upstream_count`; an entity can be both upstream and downstream in different lineage relationships. So the three sub-counts can sum to **more or less** than `total_count`, and there is no documented invariant relating them.

2. **No transactional snapshot.** The four counts are computed by four separate reactive queries that are then combined with `Mono.zip(...)` — there is no enclosing transaction or shared snapshot. Under concurrent writes (the platform is actively ingesting activity events), the four queries can observe the database at four slightly different points in time, so even the within-set arithmetic is not guaranteed self-consistent across the four numbers in a single response.

How this misleads a consumer: a UI or client that renders "Other = total − (my + upstream + downstream)", or that asserts the parts sum to the whole, will display negative or nonsensical values intermittently and have no way to know from the contract that this is expected. The OpenAPI description is currently just "Returns activity counts for dedicated period," which gives the consumer no reason to suspect non-additivity.

This is documentation/contract-description work only; no code change.
