## Description

Three classes of openapi.yaml drift surfaced this batch — all single-file edits, all visible to every SDK consumer and every Swagger UI viewer. They follow the same pattern as SPC-001 (multi-facet single-file spec hygiene) and ship naturally as one commit on a single branch.

**Facet 1 — `getMyObjectsWithUpstream` / `getMyObjectsWithDownstream` summary INVERSION (F-015b, HIGH→CRITICAL).** `openapi.yaml:843-844` declares `getMyObjectsWithUpstream` summary as `Get my objects with upstream dependencies` and description as `Returns list of data entities owned by current user with upstream dependencies`. Symmetric copy at `:861-862` for `getMyObjectsWithDownstream`. The actual response is the INVERSE — the NON-owned upstream/downstream-adjacent set (`Predicate.not(oddrns::contains)` at `DataEntityRelationsServiceImpl.java:37` explicitly EXCLUDES the owned set). The UI label `Upstream dependents` at `OwnerEntitiesList.tsx:87` is semantically accurate; the spec contradicts both code and UI. (DOC-GAP-099 promoted to PRIMARY-SOURCE-confirmed; corroborates substrate F-015 facet `spec_says_X_impl_does_Y`.)

**Facet 2 — `PermissionResourceType` enum exposes `MANAGEMENT` but the runtime endpoint REJECTS it (F-090a, HIGH→CRITICAL).** `components.yaml:3381-3387` declares the `PermissionResourceType` enum with FOUR values, including `MANAGEMENT`. `PermissionServiceImpl.java:24-27` rejects `MANAGEMENT` calls on `GET /api/resource/{type}/{id}/permissions` with HTTP 400 USR001 because management-scope permissions live on the COMPLEMENTARY endpoint (`GET /api/identity/whoami` → `Identity.permissions`). Two ways the spec can be tightened: (a) REMOVE `MANAGEMENT` from `PermissionResourceType` + introduce a separate `getNonContextualPermissions` operationId pointing at whoami; or (b) split `PermissionResourceType` into `ContextualResourceType` (3 values) + a separate `ManagementOperation` enum exposing management permissions via whoami. Recommended: (a) — minimal-change path; lift to (b) later if a richer Management API surface is contemplated.

**Facet 3 — `getAppInfo` operation has NO `security:` element (F-119c, LOW→MEDIUM).** `openapi.yaml:2704-2717` defines `getAppInfo` with NO `security:` element. The generated `AppInfoApi` interface has no `@PreAuthorize`. The spec layer does NOT encode the intentional "open under DISABLED" posture; readers see an endpoint with no security marker and may assume it is server-authenticated. Cross-link with batch-2 F-029a (OpenAPI spec carries zero `securitySchemes` block — addressed by SPC-001).

## Acceptance Criteria

Three separable acceptance criteria; ship as one commit OR three on a single branch.

### Facet 1 (summary inversion — small change)

- [ ] `openapi.yaml:843-844` — rewrite `getMyObjectsWithUpstream` summary + description:
  - Summary: "Get upstream neighbours of my objects (entities I do NOT own that flow INTO entities I own)"
  - Description: "Returns the upstream-adjacent set of data entities — the entities that flow INTO entities owned by the current user, **excluding the owned anchor set itself**. Matches the UI label 'Upstream dependents'. To list the entities the current user OWNS, use `GET /api/dataentities/my`."
- [ ] `openapi.yaml:861-862` — symmetric rewrite for `getMyObjectsWithDownstream`:
  - Summary: "Get downstream neighbours of my objects (entities I do NOT own that consume from entities I own)"
  - Description: "Returns the downstream-adjacent set of data entities — the entities that consume FROM entities owned by the current user, **excluding the owned anchor set itself**. Matches the UI label 'Downstream dependents'. To list the entities the current user OWNS, use `GET /api/dataentities/my`."

### Facet 2 (PermissionResourceType tightening — medium change)

- [ ] Decision: REMOVE `MANAGEMENT` from the `PermissionResourceType` enum at `components.yaml:3381-3387`. Three remaining values: `DATA_ENTITY`, `TERM`, `QUERY_EXAMPLE` (verified against the runtime — three contextual extractors: `DataEntityPermissionExtractor`, `TermPermissionExtractor`, `QueryExamplePermissionExtractor`; the enum must **never** gain `NAMESPACE`, which has no extractor and would throw on dispatch). Corrected per DOC-337.
- [ ] Add a new operationId surfacing management-scope permissions explicitly via the existing whoami endpoint:
  - Option A: leave the spec untouched on the management side — whoami already exposes `Identity.permissions` carrying the management permissions. Document the two-endpoint orchestration in the operationId description on `getResourcePermissions` (e.g., "For management-scope permissions, use `getIdentity` → `Identity.permissions`").
  - Option B (richer): add a new `getManagementPermissions` operationId at `GET /api/management/permissions` (server-side: read whoami chain) for SDK-discoverability. Stretch goal — skip if maintainer time-constrained.
- [ ] Coordinate with platform-side: the platform's `PermissionServiceImpl.java:24-27` BadUserRequestException branch becomes unreachable code if the spec drops MANAGEMENT (clients can no longer mint such requests at the SDK layer). The runtime guard can be retained as defence-in-depth; flag for upstream cleanup.

### Facet 3 (getAppInfo security element — small change)

- [ ] `openapi.yaml:2704-2717` — add `security: []` (explicit-empty) to the `getAppInfo` operation to denote "open by design" + a short inline description sentence: "Returns deployment introspection (platform version, auth-mode, login-form-redirect target). Anonymously reachable under DISABLED auth-mode; reachable to all authenticated callers under other modes."

### Cross-cutting

- [ ] Once the spec lands in `opendatadiscovery-specification`, the platform repo's vendored copy needs sync — coordinate via the spec's release / vendor channel.
- [ ] Live-side verification: spawn the platform locally (or stage) and load `/api/v3/api-docs` — confirm the new summaries + security elements render in Swagger UI.
