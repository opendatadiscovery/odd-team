## Description

The Owner and Namespace delete confirmation dialogs tell the operator the entity "**will be deleted permanently**", but neither claim is true:

1. **It is a soft-delete, not permanent.** `ReactiveOwnerRepositoryImpl` and `ReactiveNamespaceRepositoryImpl` both extend `ReactiveAbstractSoftDeleteCRUDRepository`, whose `delete(id)` issues an `UPDATE ... SET deleted_at = now()` (via `getDeleteChangedFields()`), not a row removal. (For namespaces, `management.md` even documents that a soft-deleted namespace name can be re-created later because a partial-unique index frees the slot.)
2. **It is blockable, not unconditional.** `OwnerServiceImpl.delete` rejects with `CascadeDeleteException("Owner cannot be deleted: there are still resources attached")` when any term-ownership, data-entity-ownership, or user-owner-mapping row references the owner; `NamespaceServiceImpl.delete` rejects the same way when any data source, collector, term, or non-deleted data entity references the namespace. So "permanently" is doubly misleading — the delete may not happen at all, and when it does it is recoverable until housekeeping purges it.

The third delete dialog in the same Management area — `DataSourceItem` — already gets this right: its copy is `Delete "<name>" datasource?` with **no** "permanently" claim. So this is a two-string inconsistency, not a systemic one.

**This is a UI-copy fix, not a doc fix.** The doc side is already closed: `management.md:66-68` (shipped via DOC-211) documents the cascade-block contract for the Owner / Namespace / DataSource trio AND explicitly calls out that "the UI's ConfirmationDialog says only 'Are you sure? X will be deleted permanently.' — it does not name the conditional outcome." DOC-211 and DOC-255 are the doc-side items (both `done`). The residual carried here is the in-product dialog wording in the two `.tsx` files. PLT-038 is a **different** dialog (the Owner-Association New-request Accept/Reject dialog, `NewAssociationRequest.tsx:70-104`); it actually cites `EditableOwnerItem` as a positive precedent for cascade-block disclosure but does not touch the "deleted permanently" copy — so this string fix is genuinely untracked.
