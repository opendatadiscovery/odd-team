## Description

No ODD authentication mode auto-creates a `user_owner_mapping` row for the signing-in user, and there is no setup-wizard / first-login prompt that nudges an admin to self-associate. `AuthIdentityProviderImpl.fetchAssociatedOwner()` is a pure read — it resolves the current user and calls `userOwnerMappingRepository.getAssociatedOwner(username, provider)`; it never creates a mapping. The consequence is an admin onboarding dead-end: a freshly-deployed platform's first administrator sets up Roles, Policies, and Owners for everyone else, then finds their own personalised surfaces (`My Objects` on Activity, on Alerts, on the recommended-entities surface) silently empty because no row binds their account to an Owner. Nothing in the running product points the admin at the fix.

**The documentation side is already closed.** `activity-feed.md:23` carries a "Pre-flight checklist for platform admins" that names exactly this failure mode ("you likely have no `user_owner_mapping` for your own account... Management → Associations → Create association — fixes the silent-empty failure mode"), and `user-owner-association.md` fully documents the admin direct-bind workflow. The residual carried by this item is therefore **not** a doc change — it is the missing **in-product self-association affordance** (a first-login prompt, an empty-state CTA on the `My Objects` tabs, or a setup-wizard step) so that an admin does not have to read the manual to escape the dead-end. This is a product/UX decision; the item is flagged SME-consult and the affected `documentation/` pages are listed `read`-only to keep the doc baseline from being duplicated.
