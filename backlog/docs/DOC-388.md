## Description

The Lineage API-reference page describes the `expanded_entity_ids` query parameter as **"IDs of `Data Entity Group` entities that should be expanded inline in the response"** (`api-reference/lineage.md:25`). That class restriction is wrong: the platform applies **no class or type filter** to the ids passed in this parameter.

Tracing the parameter end-to-end:

- `DataEntityController.java:258,268` accepts `expandedEntityIds` on the upstream/downstream endpoints.
- `LineageServiceImpl.java:99` hands it straight through: `getLineageRelationsForDepthOne(expandedEntityIds, lineageStreamKind)`.
- `ReactiveLineageRepositoryImpl.java:142-145` runs `... .join(DATA_ENTITY).on(joinCondition).where(DATA_ENTITY.ID.in(rootIds).and(LINEAGE.IS_DELETED.isFalse()))` — the only predicate on the ids is `DATA_ENTITY.ID.in(rootIds)`. There is no `entity_class`/`type`/group filter anywhere in the query.

So any data-entity id (a dataset, a transformer, a quality test, a group — anything) passed in `expanded_entity_ids` gets its depth-one neighbours merged into the response. A direct-API operator who reads "Data Entity Group ids only" and therefore *avoids* passing a non-group id is being told the endpoint is narrower than it is; conversely the wording implies the platform rejects/ignores non-group ids, which it does not. The parameter expands the depth-one lineage around **any** entity id.

This is a wording-accuracy fix. Per the harvest note, DOC-087 only relocated the prose for this parameter; DOC-225 and DOC-320 touched the lineage page but did not correct this specific class claim.
