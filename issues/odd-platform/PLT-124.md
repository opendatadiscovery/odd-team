## What

`PUT /api/datasetfields/{id}/tags` builds each `TagToDatasetFieldPojo` with only `tagId` + `datasetFieldId` and **never calls `.setOrigin(...)`** (`DatasetFieldServiceImpl.getUpdatedRelations`, `:264-271`); `createDatasetFieldRelations` (`ReactiveTagRepositoryImpl.java:350-370`) then maps the pojo via `jooqReactiveOperations.newRecord(TAG_TO_DATASET_FIELD, p)` and INSERTs. The `origin` column is `varchar NOT NULL DEFAULT 'INTERNAL'::varchar` (`V0_0_82__add_tag_to_dataset_field.sql`). The user-facing outcome turns on ONE jOOQ rendering question that is best confirmed at runtime: does `newRecord`-from-pojo emit `origin` as an explicit `NULL`, or omit the column?

- **If explicit NULL (strongly indicated, see Evidence):** the INSERT supplies `origin = NULL`; a column DEFAULT does NOT apply to an explicitly-supplied NULL, so the `NOT NULL` constraint is violated and **every non-empty PUT fails with a 500** - the UI "add tag to a column" action is dead for any real payload (empty-payload clears still succeed because `createDatasetFieldRelations` short-circuits on an empty collection, `:351-353`, masking it in clear-only flows).
- **If column omitted:** the DB default `'INTERNAL'` applies and the insert succeeds; the latent risk is then only if `origin` ever persists as non-`INTERNAL` (the next call's `deleteDatasetFieldInternalRelations` filters `WHERE origin='INTERNAL'`, `:289-294`, and would miss such rows).

The data-entity sibling does NOT rely on the default - `TagServiceImpl.java:106-109` explicitly calls `.setExternal(false)` on its `external BOOLEAN NOT NULL DEFAULT FALSE` column (`V0_0_47:2`); the dataset-field path is the lone tag-relation writer that leaves its NOT-NULL-DEFAULT column unset. This is the single critical untested path on the tagging feature.

This is **net_new** - no existing item tracks it. (PLT-026 is the tagging-behaviour cluster - ranking, side-channel mints, audit asymmetry - and does not include this insert-shape defect.)

**jOOQ-default analysis (added 2026-06-10):** the mapping context is `DSL.using(SQLDialect.POSTGRES)` with **default Settings** (`JooqReactiveOperations.java:26`, jOOQ 3.18.4) - no custom insert/changed-flag setting. `DSLContext.newRecord(Table, pojo)` calls `record.from(pojo)`, whose documented behaviour marks the changed flag `true` for every *mapped* field (the pojo maps `origin`, so `origin=null` is loaded and flagged changed); `insertInto(...).set(record)` then renders all changed fields. Under that default, `origin` is emitted as an **explicit `NULL`**, the DB DEFAULT does not apply, and the `NOT NULL` constraint fails -> the "dead endpoint / 500" branch. This points strongly to the failing outcome, but jOOQ's exact NULL-vs-omit rendering for a NOT-NULL-DEFAULT column - combined with the batch `newRecord()` chaining and `onDuplicateKeyIgnore()` - is precisely the kind of thing this codebase has been burned assuming; it must be **confirmed by running it**, not asserted from the manual.

Verdict is **RUNTIME-ONLY** pending P-030 (`lineage/odd-platform/probes/P-030.yaml`, currently a never-run skeleton), which reproduces the before/after to settle whether jOOQ emits the NULL. The statics above are all code-settled; only the jOOQ rendering (and thus which of the two impacts is live) is undriven.

## User-facing impact

**Static-not-driven (the load-bearing user-facing claim is runtime-gated).** The user surface is the column/dataset-field tag editor: a user adds a tag to a dataset field in the Structure tab and the FE issues `PUT /api/datasetfields/{id}/tags` with a non-empty `tags` payload. What the user experiences depends entirely on the unresolved jOOQ rendering:

- If the INSERT supplies explicit `NULL` (strongly indicated by the default-Settings analysis above): the request 500s, the tag is not saved, and the operator sees a generic failure with no tag added - the feature is effectively dead for any real (non-clearing) tag edit.
- If jOOQ omits the column: the tag saves with `origin='INTERNAL'` and the feature works; no user-visible defect remains on the happy path.

**Remaining check to flip `user_facing_verified` -> true:** run P-030 (or drive the UI tag-add against a local `odd-minimal` stack and read back the HTTP status + the `tag_to_dataset_field` row). This is a genuine BE-only-to-user-facing gap of exactly the class this sweep guards: the two outcomes ("dead endpoint" vs "works fine") are wildly different user experiences and the draft must not assert either as settled until driven. `user_facing_verified` therefore stays **false**. No FE component was found that would mask a 500 here (the tag editor surfaces request failures), so if the NULL branch is real the user impact is direct.

## Impact

If jOOQ emits the explicit NULL: every attempt to tag a dataset field returns a 500 - the feature is dead for any real payload (empty-payload clears still work, masking it in some flows). If `origin` persists as something other than `INTERNAL`: the next call's `deleteDatasetFieldInternalRelations` (`WHERE origin='INTERNAL'`) misses those rows and the field accumulates orphan internal relations. Either way the operator hits a hard failure or silent relation drift.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: explicitly `.setOrigin(TagOrigin.INTERNAL.toString())` on the `TagToDatasetFieldPojo` (`DatasetFieldServiceImpl.java:264-271`), mirroring the data-entity path's `.setExternal(false)`. Confirm the failure mode via P-030 before/after.
