- **DOC-GAP-110**: Alert reopen-conflict guard is application-level read-then-write without `SELECT FOR UPDATE` or DB-side `UNIQUE(data_entity_oddrn, type) WHERE status = OPEN` partial-index — two concurrent reopen requests for the same data-entity-and-type can both pass the EXISTS check and both proceed to UPDATE, briefly violating the "one OPEN of the same type per data entity" invariant (MEDIUM)
  - **Category**: drift (live alerting page does not describe the reopen-conflict semantic at all; operators evaluating ODD's alerting model for compliance or data-integrity guarantees cannot find documentation of how concurrent reopens behave)

  - **Evidence**:
    - `ReactiveAlertRepositoryImpl.java:397-420` — `openAlertWithTheSameTypeExistsForDataEntity` issues a read-only `SELECT EXISTS` over a self-join CTE; no `FOR UPDATE` clause; no advisory lock. The query checks whether an OPEN alert of the same type already exists for the data entity, but does not lock the rows it inspects.
    - `ReactiveAlertRepositoryImpl.java:297-306` — `updateAlertStatus` is a plain UPDATE; no `FOR UPDATE` on the read side, no optimistic-concurrency token / version field on the alert row, no DB-side partial unique index gating the open-state transition.
    - `AlertServiceImpl.java:124-131` — the unsequenced read-then-write composition: `openAlertWithTheSameTypeExistsForDataEntity(...)` is called, then conditionally `updateAlertStatus(...)`. Two concurrent reopen requests for two different alerts of the same type on the same data entity can BOTH execute the EXISTS check before either UPDATE commits — both see no existing OPEN → both proceed to UPDATE → the "one OPEN per (data_entity, type)" invariant is violated.
    - **Schema absence**: `V0_0_55+` migration history declares NO `UNIQUE INDEX (data_entity_oddrn, type) WHERE status = OPEN` partial index. The application-level invariant has no SQL-level backstop.
    - Live-page state (inherited from batch-A WebFetch 2026-05-10 status 200; current-session WebFetch denied): `/features/active-platform-features/alerting` describes the alert lifecycle ("OPEN" → "RESOLVED" → "OPEN" via reopen) but does NOT describe (i) the concurrent-reopen race window, (ii) the "one OPEN per (entity, type)" invariant as a documented contract, (iii) the application-level vs SQL-level enforcement boundary. The doc-product silence makes the gap invisible to operators reading the page.
  - **Proposed doc action**: **Two-part action**.
    1. **Code-side primary** (file `/log-issue odd-platform`): two ordered options. (a) **Minimum**: change `openAlertWithTheSameTypeExistsForDataEntity` to a `SELECT FOR UPDATE` (single keyword addition), AND wrap the surrounding `AlertServiceImpl.updateStatus` invocation in a `@ReactiveTransactional` so the lock is held until the UPDATE commits. The lock would serialise concurrent reopens of the same alert pair. (b) **Medium**: add a Postgres partial unique index `CREATE UNIQUE INDEX alert_unique_open_per_entity_type ON alert(data_entity_oddrn, type) WHERE status = OPEN;` as defence-in-depth; the lock prevents two-concurrent-OPENs from being created, the index backstops if the lock is ever bypassed.

Operators triaging concurrent state-change events from external alert producers may see contradictory state until the next status update settles."). After the code-side fix lands, refine to "the platform enforces this invariant via a row-level lock on the existence check; concurrent reopens of the same alert pair are serialised."

The race window is narrow (the time between EXISTS check and UPDATE commit) but exists on every concurrent reopen for the same (data_entity, type) pair. Under high ingestion concurrency (multiple data quality test runs reporting the same FDQT alert type on the same entity simultaneously) the window IS reachable. The compound risk with DOC-GAP-002 (cross-owner read on All tab) is that operators triaging from the cross-owner-readable tab may see contradictory state.
