# ReactiveAlertRepositoryImpl — semantic understanding

## understanding

`ReactiveAlertRepositoryImpl` is the jOOQ-on-R2DBC reactive repository that owns every read and write against the `ALERT` and `ALERT_CHUNK` tables — the single primary-source landing site for the alert SQL surface of the platform. It implements the 19-method `ReactiveAlertRepository` interface: a paginated/cross-owner platform-wide listing (`listAllWithStatusOpen`, the canonical query behind `AlertController.getAllAlerts`), an owner-scoped variant (`listByOwner`), a lineage-CTE-driven dependent-objects listing (`listDependentObjectsAlerts`), per-data-entity listings, a batched bulk-insert path (`createAlerts` → `executeInPartitionReturning` 1000-row batches), the mutation path (`updateAlertStatus`, `resolveAutomatically`), the reopen-guard probe (`openAlertWithTheSameTypeExistsForDataEntity`), chunk + last-created-at side-write helpers, and the data-entity lookup for the authorization extractor (`getDataEntityIdByAlertId`). The class carries NO `@ReactiveTransactional` — transactions are declared on the calling `AlertServiceImpl` methods (`handleExternalAlerts`, `applyAlertActions`). The repository does not emit activity events directly; activity emission is the service layer's responsibility (`AlertServiceImpl` registers `OPEN_ALERT_RECEIVED` / `RESOLVED_ALERT_RECEIVED` / `ALERT_STATUS_UPDATED` via `ActivityService.createActivityEvents`).

- invariants:
  - "**No owner predicate on `listAllWithStatusOpen`** — the SQL is `SELECT * FROM alert WHERE status = OPEN` with no ownership filter (`ReactiveAlertRepositoryImpl.java:143-145`). Every authenticated caller of `GET /api/alerts` sees every open alert across the platform. This is the canonical primary-source confirmation of REFACTOR-024."
  - "**No `@ReactiveTransactional` on the repository class** (`ReactiveAlertRepositoryImpl.java:63-65`). Transaction boundaries are declared at the service layer; the class-level annotation does NOT exist here. `handleExternalAlerts` and `applyAlertActions` on `AlertServiceImpl` carry `@ReactiveTransactional` (`AlertServiceImpl.java:152, 201`); `updateStatus` does NOT carry the annotation (`AlertServiceImpl.java:111-113`)."
  - "**`getOpenAlertsForEntities` is the ONLY method that uses `forUpdate()`** (`ReactiveAlertRepositoryImpl.java:133`). An inline comment frames the intent: `// While BIS and FDT type of alerts usually are engaged in one ingestion request / FDQT type more likely can be reported from various data sources. / In such cases 'for update' clause prevents potential concurrent issues`. The mutation path (`updateAlertStatus`, `resolveAutomatically`) does NOT use `FOR UPDATE` — a deliberate asymmetry the repository's comment explains for the ingestion case but does not address for status mutations."
  - "**Pagination via `pageifyResult`** — `JooqQueryHelper.paginate` wraps the base query in a window-function-based COUNT(*) OVER () + ROW_NUMBER() OVER (ORDER BY ...) (`JooqQueryHelper.java:73-90`) and emits both the page slice and total count in a single query. The OFFSET is `(page - 1) * size` computed at the caller (e.g. `ReactiveAlertRepositoryImpl.java:147`); a caller passing `page=0` produces a negative OFFSET — implementation-defined behaviour in Postgres (rejects negative OFFSET)."
  - "**`createAlerts` uses 1000-row batched INSERT** — `executeInPartitionReturning` partitions the input at `JooqReactiveOperations.java:24` BATCH_SIZE=1000 and emits a multi-`set()` insert per partition (`ReactiveAlertRepositoryImpl.java:332-342`)."
  - "**Status mutations record `STATUS_UPDATED_AT = DateTimeUtil.generateNow()` and `STATUS_UPDATED_BY = userName`** (`ReactiveAlertRepositoryImpl.java:301-302`). For `resolveAutomatically`, `STATUS_UPDATED_BY = NULL` via `DSL.inline(null, String.class)` (`ReactiveAlertRepositoryImpl.java:317`) — sentinel for system-driven resolution."
  - "**`USER_OWNER_MAPPING` join uses `DELETED_AT IS NULL`** (`ReactiveAlertRepositoryImpl.java:84-85`, 106-107, 500-501) — a soft-delete-aware lookup so that an alert's `status_updated_by` resolves to an `OWNER` row only when the user-owner binding is still active. A deleted user-owner mapping breaks the join silently; the alert is still returned but `OwnerPojo` resolves to NULL on the LEFT JOIN."

  - "**No direct config-key consumption.** The class reads no `@Value` keys, no `@ConfigurationProperties` beans. Behaviour is parameter-driven (page / size / owner id / alert ids).   - "(Indirect) `housekeeping.ttl.resolved_alerts_days` — the `AlertHousekeepingJob` hard-DELETEs rows from `ALERT` + `ALERT_CHUNK` per this TTL (`AlertHousekeepingJob.java:28-43`). The repository does not consume the key, but its read methods will silently return shrinking result sets as the housekeeping job purges rows aged past TTL."
- requires-runtime:
  - "Spring Data R2DBC + jOOQ — `JooqReactiveOperations.flux` / `JooqReactiveOperations.mono` translate jOOQ queries to R2DBC `DatabaseClient.inConnection` calls (`JooqReactiveOperations.java:30-49`). Without an R2DBC `DatabaseClient` bean the repository cannot construct any query."
  - "PostgreSQL — the lineage CTE uses `WITH RECURSIVE` (`ReactiveAlertRepositoryImpl.java:451`) and array concatenation `parent_oddrn || parent_oddrn` (`ReactiveAlertRepositoryImpl.java:435`); both are PG-specific. - couples-to:
  - "`JooqQueryHelper.paginate` — the cross-method pagination helper that emits the COUNT(*) OVER () + ROW_NUMBER() OVER (ORDER BY ...) wrapper. The repository's `createAlertJoinQuery` (`ReactiveAlertRepositoryImpl.java:474-483`) is one of N call sites; a future change to the pagination helper (e.g. switching to keyset pagination) ripples across this repository's five paginated methods."

Reads returning an alert that gets housekept mid-render would either: (a) succeed if the read completes before the delete commits, or (b) silently return zero chunks if the chunk delete completes first and the alert read materialises stale state. There is no `FOR SHARE` guard on the read paths to prevent this."

- **throughput_characteristics**:
  - "Reactive R2DBC throughout — non-blocking I/O, no thread held during DB await. Per-request thread cost is O(1) at the WebFlux layer; throughput is bounded by the R2DBC connection pool size (config via Spring `spring.r2dbc.pool.max-size`)."
  - "**Batched writes via `executeInPartitionReturning` at 1000 rows/partition** (`createAlerts` line 332-342). Partition count = ⌈N/1000⌉; each partition is a single multi-row INSERT … RETURNING. For N ≤ 1000 (typical ingestion), one round-trip; for N=10000 (an unusual cross-data-entity event), ten round-trips."
  - "**Read paths are single round-trip per call** — every read method issues ONE jOOQ query (the window-function pagination consolidates page + count into one query). No N+1 patterns; the `get(long)` method's chunk aggregation uses `jsonArrayAgg` (`ReactiveAlertRepositoryImpl.java:80`) to inline chunks into the parent query."
- **resource_allocation**:
  - "**No streaming on read** — `listAllWithStatusOpen` calls `.collectList()` (line 152) before `pageifyResult`; all rows for the page are accumulated in a Reactor `List` before mapping to `Page<AlertDto>`. For `size=1_000_000` (unbounded by controller — per AlertController.getAllAlerts neighbour sidecar's REFACTOR-024 finding), this is a million-row list in heap. The Reactor backpressure is consumed by the `collectList()`; downstream consumers see the materialised list."
  - "**`jsonArrayAgg` materialises ALERT_CHUNK rows as a single JSON array per ALERT row** — for an alert with 10K chunks (a chronically-failing DQ test ingested over a year), the JSON aggregate is held in PG memory before being returned. R2DBC then deserialises the JSON to `List<AlertChunkPojo>` via `jooqRecordHelper.extractAggRelation`."
  - "**`getOpenAlertsForEntities` returns the entire OPEN alert set for the supplied data-entity oddrn list** — no LIMIT, no batching at the repository layer. The caller (`AlertActionResolver`) supplies the oddrn list (bounded by the ingestion request's data entity count, typically ≤100 per request)."
- **scaling_characteristics**:
  - "**Stateless — instances scale horizontally.** The repository carries no instance state; the three injected fields (`jooqReactiveOperations`, `jooqQueryHelper`, `jooqRecordHelper`) are Spring beans."
  - "**No DB-level lock or advisory lock at the repository layer except `FOR UPDATE` on `getOpenAlertsForEntities`.** All other methods (including the mutation path) operate without explicit locking; row-level locks are PG's default for UPDATE statements but no broader transactional fence exists."
  - "**Recursive CTE for lineage (`getChildOddrnsLinageByOwnOddrnsCte`) is O(depth × fanout) in jOOQ-emitted SQL evaluation** — for a heavily-fanout lineage graph (one parent with 10K children, each with 10K children of their own), the recursive CTE evaluates to O(10K × 10K) = O(100M) row evaluations. The `parent_oddrn || parent_oddrn` array-membership check prevents pure cycles but does NOT bound the work for legitimate deep graphs."
  - "**Pagination uses OFFSET, not keyset** — cost grows linearly with page number. For `page=1000, size=10`, Postgres scans and discards 10000 rows before returning the 10 requested. Deep pagination is O(N) per page; keyset pagination would be O(1) but is not implemented."
- **known_performance_gaps**:
  - "**`listByOwner` empty-result total uses platform-wide count, not owner-scoped count** — cross-reference `bugs_limitations_corner_cases[5]`. This is also a perf gap because the empty-result path triggers an unnecessary platform-wide COUNT query when the caller's owner has zero alerts; the more useful query (`countAlertsWithStatusOpenByOwner`) is cheaper (uses the OWNERSHIP join's index) but is not invoked." — evidence: `ReactiveAlertRepositoryImpl.java:177` — severity: LOW
  - "**No upper bound on `size` propagated from caller** — `listAllWithStatusOpen` issues `LIMIT {size}` directly; a caller supplying `size=1_000_000` materialises a million-row response. The cost is mostly memory + serialisation, not DB (PG handles large LIMIT efficiently); but the response body size can exceed Reactor codec limits." — evidence: `ReactiveAlertRepositoryImpl.java:147` (`(page - 1) * size, size` passed through) — severity: MEDIUM (cross-references the AlertController.getAllAlerts neighbour sidecar's pagination-bound gap)
  - "**OFFSET-based deep pagination — keyset not implemented** — see `scaling_characteristics`. For high-volume pagination from the UI, the cost is O(page × size) per page; for a chronic platform with 100K open alerts and operators paging through the entire history, the last few pages cost ~100K row scans each." — evidence: `JooqQueryHelper.java:81-83` (LIMIT/OFFSET pattern) — severity: LOW
  - "**`jsonArrayAgg` for ALERT_CHUNK materialisation may produce very large JSON payloads per alert** — for an alert with thousands of chunks, the JSON aggregate inflates the row size. Postgres has no specific limit on aggregate size, but the cost of serialising and deserialising a 10MB JSON per row is non-trivial." — evidence: `ReactiveAlertRepositoryImpl.java:80` (the `jsonArrayAgg` call) — severity: LOW
  - "**No method-level observability — no `@Timed`, no Micrometer counters, no structured log entries.** Latency regressions surface only in R2DBC / WebFlux metrics, not at the repository boundary. An operator investigating 'why is the alerts page slow today' has no per-method visibility." — evidence: `ReactiveAlertRepositoryImpl.java:1-526` (no `@Timed`, no `Counter`, no `log.` calls) — severity: LOW
