## What

Three RBAC side-doors on the Business Glossary / Term HTTP surface - each lets a caller do something the permission model is documented to gate:

1. **Term-to-term link/unlink has no `SecurityRule`.** The direct term-to-term linking endpoints fall through to `.authenticated()`; the docs say "Add term" is gated by `TERM_UPDATE`. Any authenticated user can link/unlink terms regardless of `TERM_UPDATE`.
2. **`POST`/`PUT /api/terms` create a platform-wide namespace without `NAMESPACE_CREATE`.** Both `createTerm` and `updateTerm` invoke `namespaceService.getOrCreate(namespaceName)`, so a caller holding only `TERM_CREATE` / `TERM_UPDATE` mints a brand-new platform-wide namespace without the dedicated `NAMESPACE_CREATE` permission. (The same `getOrCreate` pattern lets `PUT /api/terms/{id}/tags` mint tags without `TAG_CREATE`.)
3. **`addDataEntityTerm` gate never fires (singular/plural path mismatch).** The `DATA_ENTITY_ADD_TERM` permission is registered at the singular `/api/dataentities/{id}/term`, but the spec/controller expose the plural `/api/dataentities/{id}/terms`. The `AuthorizationCustomizer` path-matcher never matches, so the gate never fires and the endpoint falls through to `.authenticated()`.

Sources: HARVEST-029, HARVEST-041, HARVEST-042 (doc-understanding harvest, 2026-05-29). Doc caveat tracked at `backlog/docs/DOC-299.md`.

## Why it matters

An operator who designs a separation-of-duties policy from the permissions documentation - "only namespace admins hold `NAMESPACE_CREATE`", "only glossary editors hold `TERM_UPDATE`" - gets a more-permissive deployment than they authored. A `TERM_CREATE`-only user silently pollutes the platform-wide namespace and tag directories; a merely-authenticated user re-wires the term graph; and the entity-level term-link gate is dead code that gates nothing. None of these surface an error - the policy looks enforced and isn't. This is the LSN-002 class (the `/term` vs `/terms` family is a recurring path-mismatch defect in this codebase - see Related).

## Suggested fix

- Add a `SecurityRule` for the term-to-term link/unlink endpoints (gate on `TERM_UPDATE` to match the documented contract).
- Split the namespace/tag creation side-doors: either require `NAMESPACE_CREATE` / `TAG_CREATE` when `getOrCreate` would create (reject otherwise), or make term/tag writes reference only pre-existing namespaces/tags. The UI should signal that typing a novel namespace will create one.
- Fix the `addDataEntityTerm` registration to the plural `/api/dataentities/{id}/terms` so the `DATA_ENTITY_ADD_TERM` gate matches the real route. A build-time validator asserting every `SecurityConstants` path resolves to a live controller route would catch this whole class.
