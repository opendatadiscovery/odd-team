# SHB-004 — applyStatus bug silently breaks `status_updated_at` and the 30-day retention window

**Category**: merged
**Severity**: HIGH

## Hypothesis

Operators see a "soft-delete retention is broken end-to-end — DELETED entities are never hard-deleted, contradicting the documented 30-day TTL" defect because `DataEntityMapperImpl.applyStatus` sets `pojo.setStatus(statusDto.getId())` **before** the `if (statusDto.getId() != pojo.getStatus())` check, so the guard always evaluates false and `status_updated_at` is NEVER updated on any status transition. Downstream, `DataEntityHousekeepingJob`'s TTL query (`STATUS_UPDATED_AT.lessOrEqual(now - N days)`) compares against a NULL column for all entities transitioned through this code path — NULL `<=` X evaluates to NULL (≈ false in SQL three-valued logic), so the housekeeping query NEVER matches. The 30-day retention promise documented at `/features/data-discovery/statuses` is silently false. This is the F-010 / Status-feature intersection that no F-NNN anchors.

## Evidence

- `odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/mapper/DataEntityMapperImpl.java:242-253` — the inverted-order check. `pojo.setStatus(statusDto.getId())` on line 247 runs BEFORE `if (statusDto.getId() != pojo.getStatus())` on line 249; at the check point `pojo.getStatus()` already equals `statusDto.getId()`, so the condition is always false and `setStatusUpdatedAt(...)` is never reached.
- `odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/scheduling/DataEntityHousekeepingJob.java:73-82` — the TTL query that depends on the column: `STATUS_UPDATED_AT.lessOrEqual(now - data_entity_delete_days)`. NULL comparison returns NULL → row not included in the delete set.
- `odd-platform-api/src/main/resources/application.yml:170` — `housekeeping.ttl.data_entity_delete_days: 30` — the documented 30-day default.
- Live doc: `https://docs.opendatadiscovery.org/features/data-discovery/statuses` (verified 2026-05-12 status 200, fetched_excerpt: "`DELETED entities remain recoverable for 30 days by default, governed by the housekeeping.ttl.data_entity_delete_days configuration setting.`")
- Cross-ref: `lineage/odd-platform/understanding/odd-platform__java__DataEntityController__controller-method__updateStatus.md:bugs_limitations_corner_cases[0]` (HIGH-severity entry for this exact bug).
- F-010 anchors the Housekeeping TTL Enforcement family; this bug is the **upstream defect that silently disables one of the five housekeeping jobs** for the data-entity domain.

## Notes

- This is a **two-character fix** (move the `setStatus` assignment one block down, or capture the prior status into a local before mutating). The code-review eye-roll is real; the operational consequence is HIGH because both the manual PUT path AND the scheduled auto-flip job (SHB-003) route through this same mapper.
- **Verification by anyone with a local stack**: PUT a status, then SELECT `status_updated_at` from `data_entity` — the column will be NULL for every transition. The 30-day clock literally never starts.
- **Combined with the `status_switch_time`-based auto-flip (SHB-003)**: an entity reaches DEPRECATED → auto-flips to DELETED at `status_switch_time` → housekeeping is supposed to hard-delete 30 days later → never does → the entity stays soft-deleted forever (consuming row space, FK references, statistics rollups, and the `isStale` flag continues to render).
- **Operator-facing failure mode**: an operator who relies on the documented 30-day window to clean up their catalog discovers (years in) that the `data_entity` table has grown unbounded because nothing the platform ships actually expires DELETED rows. The bug is invisible until they run `SELECT count(*) WHERE status = 'DELETED'` and find the count never drops.
- This is a **canonical case for the SHB-001 / LSN-001 family**: silent defaults / silent failure paths that contradict published docs. Same severity profile as LSN-001 (attachment-storage default wiping data) and LSN-002 (region unset). Recommend a parallel LSN.
- The mapper is generated by MapStruct (`DataEntityMapperImpl` is the impl); a manual `@AfterMapping` or pre-mutation snapshot is the idiomatic fix. The bug suggests the manual `applyStatus` was retrofitted onto generated code without sufficient review.

## Next

1. **REFACTOR-NNN — HIGH** — fix `DataEntityMapperImpl.applyStatus` to capture prior status into a local before `setStatus`. One PR, one-line diff.
2. **TEST-GAP** — `DataEntityStatusChangeTest` does NOT assert that `status_updated_at` is set after a PUT. A new assertion `assertNotNull(getPojoFromDB(entityId).getStatusUpdatedAt())` would catch this.
3. **DATA-FIX migration** — historical `data_entity` rows that have transitioned through this code path have NULL `status_updated_at`; for DELETED rows this is the bug surface. A one-shot migration `UPDATE data_entity SET status_updated_at = COALESCE(status_updated_at, status_switch_time, updated_at, now()) WHERE status = 'DELETED' AND status_updated_at IS NULL` would un-stick the housekeeping query.
4. **DOC-NNN** — the live `/features/data-discovery/statuses` page should NOT be changed (the documented behaviour is correct intent); the CODE should be changed to match.
5. **LSN-NNN candidate** — retrospective for the family: "silent-correctness-bug-anchored-on-published-promise — applyStatus ordering inversion broke 30-day TTL invisibly."
6. **Cluster** with SHB-003 — same surface, sibling feature.
