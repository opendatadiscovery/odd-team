## What

Two DEG-read endpoints on the same platform return **opposite contracts** for the same semantic condition (DEG exists but has zero members):

- `GET /api/dataentitygroups/{id}/lineage` - raises **404 NotFoundException** (verified at `LineageServiceImpl.java:62`: `switchIfEmpty(Flux.error(new NotFoundException("Data entity group", dataEntityGroupId)))`).
- `GET /ingestion/entities/{degOddrn}/children` - returns **200 OK** with empty `CompactDataEntityList` (verified at `IngestionController.java:75-79` - `getDataEntitiesByDEGOddrn`).

A collector author probing both with the same DEG ODDRN writes two different error-handling code paths. Reconciliation scripts face asymmetric error-handling on the two endpoints. The asymmetry IS the contract - but the contract is operator-debug-surprising and breaks the "same condition, same response" expectation that REST consumers carry.

## Why

REST consumers (collector authors, third-party integrators, internal scripting) reasonably expect "same condition, same shape". When one endpoint returns 404 for empty and the sibling returns 200, callers must implement endpoint-specific dispatch logic - and they must DISCOVER the asymmetry, because no doc captures it.

The operator-debug-expectation is **empty -> 404** (matches the lineage endpoint's current behaviour). The lineage endpoint's 404 is doc-anchored - the live API reference doc treats empty-DEG as a not-found condition. The sibling membership endpoint's 200-empty is the outlier.

## How

Two options, each load-bearing:

**Option A (preferred) - align the membership endpoint to 404 on empty.** Update `IngestionController.getDataEntitiesByDEGOddrn` to switch to `Mono.error(NotFoundException)` when the membership list is empty (or when the DEG is not found - separately). Update `ingestionService.getDataEntitiesByDEGOddrn` accordingly:

```java
public Mono<CompactDataEntityList> getDataEntitiesByDEGOddrn(final String degOddrn) {
    return reactiveDataEntityRepository.getDEGMembership(degOddrn)
        .switchIfEmpty(Mono.error(new NotFoundException("Data entity group", degOddrn)))
        .collectList()
        .map(this::toCompactDataEntityList);
}
```

This breaks backward compatibility for any collector that depends on 200-empty (verify with a substrate scan: are there collector tests asserting 200 with empty items?). If yes, deprecation cycle: announce on the doc + ship a future-deprecation header + change the contract in the next major.

**Option B (less surgical) - align the lineage endpoint to 200-empty on empty.** Replace the `switchIfEmpty(Flux.error(NotFoundException))` with a `defaultIfEmpty(EmptyDataEntityGroupLineage)` that returns an empty graph. Operationally easier (no breaking change for membership consumers; the lineage endpoint's existing 404 callers will simply receive 200 with empty graph instead). Trade-off: the lineage endpoint's existing doc framing ("DEG not found -> 404") needs updating to disambiguate the three condition classes (DEG missing -> 404; DEG empty -> 200-empty; wrong entity type -> 400-validation).

Recommendation: **Option A** if collector backward-compat is acceptable (the user-debug-expectation is empty -> 404); **Option B** if backward-compat is strict.

## Paired doc-side fix

**DOC-199** ships the operator-facing caveat: name the asymmetry on the API reference's lineage page + the (currently non-existent) S2S read-API page. DOC-199 is load-bearing on its own (operators reading the doc can route around the gap); PLT-036 aligns the contracts in code.
