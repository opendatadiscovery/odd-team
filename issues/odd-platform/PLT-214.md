## What

`GET /api/owner_association_request/activity` returns HTTP 500 when the `status` query parameter is omitted. `status` is declared OPTIONAL in the OpenAPI, so a spec-compliant caller that does not pass it - the most natural first call ("show me all activity") - gets an opaque server error. Supplying any `status` value (e.g. `?status=PENDING`) returns 200. This is NOT the authorization gap (PLT-191) and NOT the framework missing-required-param case (PLT-143); it is an OPTIONAL parameter whose absence crashes the query path.

## Where

The conditions builder null-guards `status` correctly, so the crash is downstream - in the main query / `fetchCount` / mapping path that runs when no `status` filter is applied:

`.../repository/reactive/ReactiveOwnerAssociationRequestActivityRepositoryImpl.java:121-140` (`getConditions` - the null-guard that is NOT the problem):
```java
private List<Condition> getConditions(final String query, final OwnerAssociationRequestStatusParam status) {
    final List<Condition> conditions = new ArrayList<>();
    ...
    if (status != null) {            // null status correctly adds NO status condition
        switch (status) { ... }
    }
    return conditions;               // null status -> empty/where-less query -> 500 downstream
}
```

The chain:
- `controller/OwnerAssociationRequestController.java:47-53` - `status` is an optional `OwnerAssociationRequestStatusParam`.
- `service/OwnerAssociationRequestActivityServiceImpl.java:20-28` - delegates to `activityRepository.getDtoList(page, size, query, status).map(mapper::mapPage)`.
- `repository/.../ReactiveOwnerAssociationRequestActivityRepositoryImpl.getDtoList` (the main select + `fetchCount`, lines ~66-117) is where the no-`status` path 500s.

OpenAPI: `openapi.yaml` `/api/owner_association_request/activity` declares `status` as an OPTIONAL query parameter.

## User-facing impact

User: an API consumer / SDK (or the UI) calling the owner-association activity endpoint. Driven live (localhost:8080, `AUTH_TYPE=DISABLED`):

- `GET /api/owner_association_request/activity?page=1&size=5` (no `status`) -> **HTTP 500** `{"code":"SYS001","message":"Internal Server Error",...}`.
- `GET /api/owner_association_request/activity?status=PENDING&page=1&size=5` -> **HTTP 200** `{"items":[],"page_info":{"total":0,"hasNext":false}}`.

So the endpoint's most natural call (no status filter, i.e. "all activity") is exactly the one that 500s; the consumer has to guess that an OpenAPI-optional parameter is actually mandatory. (Verified 2026-06-09, local stack.)

## Why it matters

The default, all-statuses view is the call a UI or a first-time API consumer makes - and it is the one that fails. The 500 is opaque (SYS001), gives the caller nothing actionable, and contradicts the published contract (the parameter is documented optional). A correct unfiltered call should return all activity (HTTP 200), not crash. Medium: a broken default read path plus a contract violation; no data loss or security exposure on its own (the authorization gap on this endpoint is the separate PLT-191).

## Suggested fix

Make the no-`status` path return all activity instead of 500ing: null-guard the downstream main query / `fetchCount` / mapping in `getDtoList` so an absent `status` simply omits the status filter and returns every row (HTTP 200) - matching what `getConditions` already does. Alternatively, if "all statuses" is not a supported view, declare `status` REQUIRED in the OpenAPI and return a clean 400 on absence (never a 500). Open to alternatives; the load-bearing change is that omitting an OpenAPI-optional parameter never produces a 500.

**How to verify:** `GET /api/owner_association_request/activity` without `status` returns HTTP 200 with all activity (or a clean 400 if `status` is made required) - not 500; `?status=PENDING` still returns 200.

## How discovered

Surfaced while driving PLT-191 (the owner-association activity authorization gap) through `playbooks/user-facing-verification.md` against a running stack on 2026-06-09: the endpoint 500'd without `status` and returned 200 with `?status=PENDING`, revealing a required-in-practice optional parameter. Distinct from PLT-191 (authorization), PLT-143 (framework missing-REQUIRED-param -> 500 translation; this is an OPTIONAL param crashing downstream), and PLT-148 (owner-association writes inoperable under DISABLED).
