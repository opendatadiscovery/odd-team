## What

Slack's Events API delivers events at-least-once (Slack's own published semantic - retries on a missed 2xx ACK within ~3s; retries continue for up to ~3 attempts over ~hours). The platform's Slack-events processing pipeline has **no platform-side dedup**, so a retried event is processed again as a fresh event and materialises a duplicate Discussion message.

Verified inbound flow (BE trace 2026-06-10): `/api/slack/events` (`EventApiController.java:22-42`) -> `enqueueMessageEvent` -> `SlackMessageProviderEventHandler.enqueueEvent` (`:24-43`) inserts a `message_provider_event` row (state PENDING) for events that are replies to tracked messages; a background processor (`DataCollaborationMessageEventProcessor`, fetching PENDING rows `forUpdate` at `DataCollaborationRepositoryImpl.java:146-149`) turns each PENDING row into a child `message` and then `deleteEvent`s it (`:180-182`). Nothing dedups the insert, so a Slack retry inserts a SECOND PENDING row -> the processor creates a SECOND child `message` -> the same reply renders twice (or more) on the data-entity Discussions tab.

**Corrected 2026-06-10 (user-facing verification sweep):** the original draft proposed `UNIQUE(provider, event_id)` + `ON CONFLICT` and quoted a `message_provider_event` table with `event_id VARCHAR(255)` / `event_type VARCHAR(255)` columns and a `createMessageEvent(MessageProviderEventPojo eventPojo)` signature. **None of those exist.** The real table (`V0_0_59__data_collaboration.sql:25-39`) has columns `id BIGSERIAL PK, parent_message_uuid, parent_message_created_at, provider VARCHAR(64), action SMALLINT, event JSONB, created_at, state SMALLINT, error_message` - there is **no `event_id` and no `event_type` column**, so there is no natural Slack-event key persisted at all. The Slack message identity (`ts` / `client_msg_id`) lives only inside the `event` JSONB blob. The real `createMessageEvent` signature is `createMessageEvent(String event, MessageEventActionDto action, MessageProviderDto messageProvider, UUID parentMessageUUID)` (`ReactiveMessageRepositoryImpl.java:136-155`). What **does** hold from the original: the INSERT (`DSL.insertInto(MESSAGE_PROVIDER_EVENT).set(record)`, `:150-151`) has NO `.onConflict(...)`, and the table has NO UNIQUE constraint - so there is genuinely zero dedup. The fix is therefore larger than a one-line constraint: a dedup key must first be **persisted** before any UNIQUE can reference it (see "How" below).

This is orthogonal to (and tracked separately from) the no-inbound-signature-verification defect on the same endpoint (the inbound `/api/slack/events` has no HMAC verification - tracked at DOC-GAP-290 / PLT-054; confirmed still absent 2026-06-10: `EventApiController` reads the raw body and parses it with no signature check).

## Why

Duplicate Discussion messages are operator-visible. Workspace admins seeing the same Slack message rendered 2-4x on the same data-entity Discussions tab lose confidence in the integration. The root cause (Slack's published at-least-once semantic + zero platform-side dedup) is benign-to-fix but corrosive-to-trust if unfixed.

The signature-absence defect (DOC-GAP-290 / PLT-054) lets ANY anonymous caller emit synthetic Slack events (`/api/slack/events` is in `SecurityConstants.WHITELIST_PATHS:95-96` and has no HMAC check - confirmed 2026-06-10); combined with the no-dedup defect, an attacker can replay a captured Slack event N times to amplify the corruption. The two defects compound; fixing each one independently shrinks the attack surface and the trust-loss surface respectively.

## User-facing impact

The "user" is a workspace admin / team using Slack Data Collaboration (an opt-in feature: `datacollaboration.enabled=true` + a Slack bot token; off by default per `application.yml`).

- **WHO/WHAT:** when Data Collaboration is enabled, anyone whose Slack reply triggers an Events-API retry (a missed/slow ACK) has their reply rendered 2+ times on the data-entity Discussions tab. The duplication is attributed to real Slack content, so it looks like the platform double-posted.
- **Mechanism is BE-trace-confirmed, the visible duplication is runtime-observable (not driven 2026-06-10):** the chain insert(no-dedup) -> processor -> child `message` -> Discussions render is code-traced (`EventApiController:22-42` -> `SlackMessageProviderEventHandler:24-43` -> `ReactiveMessageRepositoryImpl:136-155` insert with no `.onConflict` -> `DataCollaborationRepositoryImpl:146-149` PENDING-fetch -> child message). What is NOT driven is the end-to-end "same reply shows twice in the UI" - that requires a running stack with a Slack bot and an induced retry. The duplicate-row half is settled by the absence of any UNIQUE/ON CONFLICT; the UI-render half is the strongly-implied consequence.
- **NOT a default-deployment issue:** Data Collaboration ships disabled, so this only affects operators who turned it on.

## How

**Re-scoped 2026-06-10:** because there is no `event_id`/`event_type` column, the original "add `UNIQUE(provider, event_id)`" is not directly applicable - a dedup key has to be **persisted first**. Two-piece change:

**1. Persist a dedup key.** Extract the Slack event identity (the message `ts`, or `client_msg_id` when present) from the inbound payload and store it in a new column - e.g. `provider_event_id VARCHAR(255)` on `message_provider_event` - populated in `SlackMessageProviderEventHandler.enqueueEvent` / `createMessageEvent`. (Both Slack `ts` and `client_msg_id` are stable across retries of the same logical event; `ts` is always present, `client_msg_id` only on user-authored messages, so `ts` is the safer key.)

**2. Flyway migration** (new `V0_0_NN__message_provider_event_dedup.sql`) - add the column, then a partial UNIQUE over it:

```sql
ALTER TABLE message_provider_event
    ADD COLUMN IF NOT EXISTS provider_event_id VARCHAR(255);

-- Natural dedup key for at-least-once delivery. Partial so legacy NULL rows don't collide.
CREATE UNIQUE INDEX IF NOT EXISTS message_provider_event_provider_event_id_unique
    ON message_provider_event (provider, provider_event_id)
    WHERE provider_event_id IS NOT NULL;
```

(Legacy rows pre-date the column and are NULL - the partial predicate keeps them out of the constraint. No historical-duplicate cleanup is needed because the processor `deleteEvent`s rows after processing, so the table holds only in-flight PENDING events.)

**3. Repository INSERT - add ON CONFLICT DO NOTHING** against the real signature:

```java
public Mono<Void> createMessageEvent(final String event,
                                     final MessageEventActionDto action,
                                     final MessageProviderDto messageProvider,
                                     final UUID parentMessageUUID) {
    // ... set provider_event_id on the record from the extracted Slack ts ...
    final var query = DSL.insertInto(MESSAGE_PROVIDER_EVENT)
        .set(record)
        .onConflictOnConstraint(DSL.name("message_provider_event_provider_event_id_unique"))
        .doNothing();
    return jooqReactiveOperations.mono(query).then();
}
```

Alternative (no schema change): compute a deterministic hash from the event JSONB + provider + `parent_message_uuid` and store/UNIQUE that as the idempotency key. The explicit `ts` column is preferable - it is human-debuggable and matches Slack's own identity.

## Tests

- Integration test: POST the same Slack reply event 3x (same `ts`) to `/api/slack/events`; after the processor drains, query `message` - expect exactly 1 child message for the parent thread (today's behaviour: 3 child messages, since each retry inserts a fresh PENDING `message_provider_event` row).
- Unit/repo test: `createMessageEvent` called twice with the same extracted `provider_event_id` inserts one row (ON CONFLICT DO NOTHING swallows the second).
- Regression check: distinct Slack events (different `ts`) flow through unchanged; legitimate message-edited (`MessageChangedEvent`) events continue to work.
