## Description

Two operator-misleading framings on the live Quality Dashboard page. Both are doc-side fixes; the structural alternatives (rename / add a second aggregation surface) are deferred to PLT-052.

**F-032b — LSN-019 semantic misalignment (HIGH).** Live doc reads verbatim "the count of test runs broken down by status (passed / failed / skipped)" — promises per-RUN semantics. The SQL delivers per-TEST-by-latest-run via `DATA_ENTITY_TASK_LAST_RUN.task_oddrn` PRIMARY KEY (one row per test, latest run only). UI label, per-category total composition (`TestCategoryResults.tsx:14-17, :33`), URL operation name (`getDataQualityTestsRuns`), OpenAPI summary, AND the live docs all promise "test runs"; SQL delivers "tests by latest-run-status."

**Operator-visible consequence**: An operator reading "Test Results Breakdown: 12 passed / 3 failed" believes 15 RUNS happened; reality is "15 tests EXIST, of which 12 most recently passed." If the same test fails 100 times in a row, the dashboard shows "1 failed" not "100 failed." Compliance/audit reading "how many test failures this week" gets a fundamentally wrong number.

**F-032e — Category card ordering is alphabetical, not severity (LOW).** `DataQualityContent.tsx:75-77` sorts via `category.localeCompare`. Operator opening /data-quality to find "which category is failing worst" must scan all panels; the panel order conveys nothing about quality. Live doc lists the six categories alphabetically but does NOT state the order IS alphabetical (vs severity / failure-count).
