## What

Every read path of the Activity feed builds its base query by **inner-joining** activity rows to the `data_entity` they reference. An inner join only returns activity rows whose referenced data entity still exists. If a data entity is hard-deleted (its `data_entity` row removed), every activity record that pointed at it is silently filtered out of all activity reads — the history is not deleted from the `activity` table, it simply becomes unreachable through the feed. The events survive in storage but are invisible to operators, and the same inner join also drops them from the activity count, so the totals shrink to match.

## Where

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/repository/reactive/ReactiveActivityRepositoryImpl.java:219`

```java
final var query = DSL.select(selectFields)
    .from(ACTIVITY)
    .join(DATA_ENTITY).on(DATA_ENTITY.ID.eq(ACTIVITY.DATA_ENTITY_ID))   // INNER JOIN — drops rows when the entity is gone
    .leftJoin(USER_OWNER_MAPPING)
    .on(...);
```

The same inner join gates the dependent-activities count query:

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/repository/reactive/ReactiveActivityRepositoryImpl.java:197`

```java
final var countQuery = DSL.selectCount()
    .from(ACTIVITY)
    .join(DATA_ENTITY).on(DATA_ENTITY.ID.eq(ACTIVITY.DATA_ENTITY_ID))
    .leftJoin(USER_OWNER_MAPPING)
    .on(...);
```

Note the contrast with the owner join immediately below it, which is a `leftJoin` — the entity join being an inner join is what makes a missing entity erase the row rather than merely null out a column.

## Why it matters

The Activity feed is the platform's audit history. Coupling its visibility to the **current existence** of the referenced data entity means the audit trail is not durable against deletion:

- **Hard-deleting an entity makes its entire activity history disappear (silent).** All record of who created, edited, tagged, or re-owned that entity vanishes from the feed and from counts the instant the entity row is removed. For audit purposes this is the worst time to lose the history — deletion is exactly the action an operator may later need to investigate.
- **Counts silently understate true activity.** Because the count query carries the same inner join, totals drop in lockstep, so there is no numeric tell that history was lost.
- **Who is affected:** any deployment that hard-deletes data entities (manual cleanup, decommissioned sources, ingestion that prunes entities). Soft-deleted entities whose rows remain are unaffected; the loss is specific to rows actually removed from `data_entity`.

Severity **high**: it is silent, irreversible from the reader's perspective, and lands on an audit/compliance surface where history durability is the whole point.

## Suggested fix

Decouple activity-history visibility from current entity existence (open to alternatives):

1. **Change the entity join to a `leftJoin`** and make the entity-derived fields nullable in the projection/mapper, so an activity row whose entity is gone still renders (with whatever entity context is recoverable, or a "deleted entity" placeholder). This mirrors the existing `leftJoin` treatment of the owner mapping on the same query.
2. **Mandate soft-delete for data entities** so the `data_entity` row is retained (flagged deleted) and the inner join keeps matching, with deleted entities filtered/annotated at the presentation layer rather than dropped at the join.

Option 1 is the smaller, more direct fix and matches the surrounding join style; option 2 is appropriate if soft-delete is already the intended lifecycle and the hard-delete path is the anomaly.
