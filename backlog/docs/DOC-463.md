## Description

The History tab on `user-owner-association.md` documents (correctly) that two distinct administrative actions both write a **Declined** row to the audit stream:
- **Reject a pending request** → Declined
- **Remove an approved binding** → Declined

These are operationally very different events: one is "we never let this user in", the other is "this user had owner access (possibly for months) and we revoked it". The History tab's **Status** column shows the same literal "Declined" for both, with no field that distinguishes them. During an incident or access review, an auditor reading a "Declined" row against a user who demonstrably had access for a long period is actively misled — the status implies the request was refused, when in fact the binding was removed after a long active period.

The page enumerates the mapping in the write-path table (`:116-123`) but does not warn the reader that the Status column is therefore lossy. An operator using the History tab as the audit surface (which the page positions it as — "a complete record of every association decision") needs to know that "Declined" is two-valued and that disambiguating a removal from a refusal requires correlating `Resolved at` against the user's earlier `Approved` row (or the underlying activity stream), not reading the Status column alone.

## Acceptance Criteria

- [ ] The History tab section of `user-owner-association.md` gains an admonition (`{% hint style="warning" %}` or `info`) stating that a **Declined** row means **either** a refused pending request **or** a removed (previously-approved) binding, and that the Status column alone does not distinguish the two.
- [ ] The admonition gives the operator the disambiguation path: a removal is preceded by an `Approved` row for the same user-owner pair (correlate `Resolved at` timestamps), whereas a refusal has no prior `Approved` row; for authoritative attribution use the underlying `activity.created_by` / activity stream rather than the Status column.
- [ ] The note is placed adjacent to the existing write-path → recorded-as table (`:116-123`) so the reader sees the ambiguity at the point the mapping is presented; it does not duplicate the table.
- [ ] Operator language only — no workspace IDs on the published page (Gate 11).
- [ ] Live-site verified post-merge: WebFetch `https://docs.opendatadiscovery.org/configuration-and-deployment/enable-security/authorization/user-owner-association` and confirm the admonition renders under the History tab section.

## Context

Surfaced by the 2026-06-16 editorial audit of `enable-security/` during the CTRIB-018 review.

**Failure shape:** reader-flow defect — a documented status value is two-valued and the page presents the mapping without warning that the resulting audit column is ambiguous for forensic / compliance use.

**Verbatim passage** — `user-owner-association.md:116-123` (the write-path → recorded-as table):
> | Write-path | Recorded as |
> | Approve a pending request | Approved |
> | Reject a pending request | Declined |
> | **Create association** (admin direct-bind) | Approved |
> | **Remove** a binding | Declined |
>
> A binding created with **Create association** therefore appears in History as an Approved row, and a removal appears as a Declined row — both attributed to the administrator who performed them. The History tab is a complete record of every association decision on the deployment.

Both "Reject a pending request" and "Remove a binding" land on **Declined**; the prose calls the History tab "a complete record" without noting the Status column cannot separate a never-admitted user from a revoked-after-active one.

**Recommended fix:** a short admonition immediately after the table, e.g. *"A `Declined` row is two-valued — it records either a request that was refused or a previously-approved binding that was later removed. The Status column does not distinguish them: a removal is always preceded by an `Approved` row for the same user-owner pair, while a refusal is not. For incident review, correlate the `Resolved at` timestamps (or read the underlying activity stream) rather than relying on `Declined` alone."*
