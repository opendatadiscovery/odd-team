## Description

The audit-silence pattern (write paths with no `@ActivityLog` / no audit row → forensic reconstruction impossible) is cross-cutting. The Owner / Term / Namespace / DEG / Activity-Feed audit-silence axis is already tracked (DOC-246 audit-trail-scope page; DOC-181/251/188; PLT-062 the code-side emission epic). The feature-reflection pass surfaced **four additional audit-silent surfaces not covered by those items**, plus one over-count:

1. **Attachment mutations (F-027/H-013)** — uploads/deletes/link-edits have no `@ActivityLog` anywhere; attachment changes are untraceable. Compounds the cross-entity-escalation findings (PLT-086).
2. **Token rotation / collector+datasource delete (F-125/H-006)** — emit no Activity event and no audit-log row; only single-state `token.updated_by` (NULL under DISABLED, overwritten each rotation) is the trace, so "who rotated it before last" is unrecoverable. `@ActivityLog` is structurally blocked (the Activity Feed is data-entity-scoped, F-021a) — this surface needs the distinct audit mechanism the PLT-062 / audit-trail-scope ADR family proposes.
3. **Owner-association binding REMOVAL (F-173/H-006)** — the owner-association activity log has CREATED/APPROVED/DECLINED types but **none for removal**; an auditor sees the grant but never the revocation.
4. **Term-to-term link/unlink (F-152/H-011)** — not recorded in the Activity Feed (no `@ActivityLog`), unlike every sibling term-linkage op; the write endpoints are also un-RBAC'd (RBAC half → PLT-101).

Plus: **description-edit double-event (F-192/H-011)** — one description edit containing a term marker emits TWO Activity events (description-updated + term-assignment-updated) with the same actor/timestamp; an auditor infers two actions where one occurred.
