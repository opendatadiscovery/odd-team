## What

The data-entity housekeeping job deletes orphaned attachment files from object storage (S3/MinIO) with a **blocking** reactive call that runs **inside the jOOQ database transaction**, on the transaction's shared JDBC `Connection`, with **no timeout**. If the storage backend hangs (a slow or unresponsive S3/MinIO endpoint, a network partition, a throttled bucket), the blocked call holds the database transaction and the housekeeping connection open for as long as the storage call blocks. Because the whole delete cascade runs in one transaction, a single hung object-store request wedges the entire housekeeping cycle - no data entities are purged and the connection stays checked out - until the underlying HTTP client's own (potentially unbounded) timeout fires, if ever.

## Where

`odd-platform-api/src/main/java/.../housekeeping/job/DataEntityHousekeepingJob.java:142`

The blocking storage call:

```java
private void deleteFiles(final DSLContext dslContext, final List<Long> dataEntityIds) {
    final List<FilePojo> deletedFiles = dslContext.deleteFrom(FILE)...fetch(...);
    final List<FilePojo> filePojos = deletedFiles.stream()
        .filter(file -> file.getDeletedAt() == null)
        .toList();
    fileUploadService.deleteFiles(filePojos).block();   // line 142 - blocking, no timeout
}
```

This is reached from inside the surrounding transaction (same file):

```java
public void doHousekeeping(final Connection connection) {
    DSL.using(connection).transaction(ctx -> {          // line 71 - opens the txn on the shared Connection
        ...
        deleteDataEntities(dslContext, dataEntitiesToDelete);   // line 80
    });
}
```

`deleteDataEntities(...)` invokes `deleteFiles(dslContext, dataEntityIds)` at line 117, so `fileUploadService.deleteFiles(...).block()` executes while the jOOQ transaction is open on the same connection.

## Why it matters

Housekeeping is a background subsystem that **permanently deletes data**; operators expect it to make steady progress and not interfere with the database. Coupling an external object-store call to the lifetime of a DB transaction is a reliability hazard: a hung S3/MinIO call leaves a database transaction and a pooled connection open indefinitely, and stalls the whole purge cycle (no entities deleted) rather than degrading gracefully. The failure is intermittent (it only manifests when storage is slow/unreachable) and largely invisible - the job logs only at debug level - so an operator may not notice the cycle has wedged. Severity is medium: it is not data loss or a security issue, but it is a latent availability/operability defect on a destructive background path, and an unbounded blocking call inside a transaction is a clear anti-pattern.

## Suggested fix

Perform the object-store delete **outside** the database transaction and bound it with a timeout. Two concrete options:

1. Collect the to-delete `FilePojo` list inside the transaction, return it, and run `fileUploadService.deleteFiles(filePojos)` after the transaction commits, with an explicit `.timeout(Duration.ofSeconds(...))` (operator-tunable). The DB rows are removed transactionally; the storage cleanup runs separately and, on timeout/failure, logs the orphaned object keys for a later sweep rather than wedging the cycle.
2. At minimum, add `.timeout(...)` to the `deleteFiles(...)` reactive chain so a hung storage call fails fast instead of blocking the transaction indefinitely.

A dynamic-verification probe (P-310) is the right way to confirm the wedge behaviour and validate the fix against a deliberately-slowed MinIO endpoint. Open to alternatives on exactly where the post-commit cleanup is orchestrated.
