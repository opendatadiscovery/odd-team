# DOC-508 — the Integration Wizard is empty out of the box, and only the developer page says so

## Failure shape

**Cross-audience absence.** A load-bearing fact about an operator-facing surface is documented exactly once,
on the page written for a different audience.

`developer-guides/api-reference/integrations.md` states it plainly:

> **On a stock platform build `GET /api/integrations` returns `{ "items": [] }`.** The manifests that populate
> the registry are loaded from `META-INF/wizard/*.yaml` on the classpath, and the platform ships none — they
> arrive only through external classpath overlays. An empty list means no manifests were supplied, not that
> the endpoint failed.

**Verified against the source, not inferred** (odd-platform @ `contrib/CTRIB-062-my-data-filter`, 2026-09-01):
`IntegrationRegistryFactory.java:26` scans `classpath*:META-INF/wizard/*.yaml`, and
`find . -path '*META-INF/wizard*'` over the whole repository returns **nothing**. The claim holds.

## Why it matters

The three pages an operator actually reads all describe a populated wizard:

* `integrations/integration-wizard.md` — *"**Pick** an integration card (PostgreSQL, Snowflake, …)"* is step 2
  of a six-step "How operators use it" walkthrough. Step 2 cannot happen on a stock deployment.
* `management.md` (the Integrations row of the nine-tab table) — *"The Integration Wizard surface — pick an
  integration template, fill in its parameters, and copy the generated `collector_config.yaml` snippet."*
* `integrations/README.md` — *"To shorten the path from 'I picked an integration' to 'I have a working
  `collector_config.yaml` snippet', the platform **ships an Integration Wizard** under **Management →
  Integrations**."*

The wizard page does say the registry is manifest-driven and that adding one means *"dropping a new manifest
into a JAR on the platform's classpath"* — but a reader takes that as *how to add a **new** integration*, not
as *there are none*. So the operator opens **Management → Integrations**, sees an empty pane, and has no way to
tell an empty registry from a broken feature: there is no empty-state copy in the UI and no sentence in the
docs to land on. That is the same "cannot distinguish nothing-configured from broken" defect class already
tracked for another surface in `DOC-393`, and the same reason
`memory/feedback_verify_absence_by_reading_config` exists — an empty surface is the most expensive kind of
undocumented default, because the reader's first hypothesis is "it's broken" and their second is "I did
something wrong".

## Recommended fix

1. **`integration-wizard.md` is the canonical home** (Gate 10 / Cornerstone 5 — this is feature behaviour, not
   API reference). Add a short admonition high on the page, *before* "How operators use it": the registry is
   overlay-driven, the shipped platform carries no manifests, so a stock deployment shows an empty
   Integrations pane, and that is expected rather than a fault. Say where manifests come from
   (`META-INF/wizard/*.yaml` on the classpath, supplied by a distribution or an operator-built overlay JAR)
   and that a restart is required — the page already documents the restart, so this sits beside it.
2. **`management.md` and `integrations/README.md` get one clause each**, pointing at that admonition rather
   than repeating it — both currently promise a working card-pick flow with no qualifier.
3. Leave the API-reference hint as-is; it is correctly homed for the client-author audience, and after (1) it
   becomes the second surface rather than the only one.
