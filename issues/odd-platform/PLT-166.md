## What

The `/management/integrations` route is the only route under Management with no per-route permission wrapper. Every other Management route is mounted inside its own `WithPermissionsProvider` (or a `RestrictedRoute` gated by an explicit `hasAccessTo(...)`) with a route-specific `allowedPermissions`, so its child components see a permission context scoped to that route's own permissions. The integrations route is mounted bare, so its children fall through to the **parent** permission context that wraps the whole of `ManagementRoutes` - the `Management` component's `WithPermissionsProvider` with `allowedPermissions={[OWNER_ASSOCIATION_MANAGE]}` (`Management.tsx:9-12`). There is no dedicated integration permission gating the route, which means the moment a real `hasAccessTo(<integration perm>)` check is added inside the Integrations UI it will deny-by-default (the integration permission is not in the inherited `OWNER_ASSOCIATION_MANAGE`-only allow-list), silently shipping a dead/inert control.

**This is a latent trap, not a present defect.** Verified 2026-06-10 by reading the Integrations subtree: `Integrations.tsx`, `IntegrationPreviewList`, `Integration`, and all their children call **no** `hasAccessTo` / `usePermissions` / `WithPermissions` - so today there is no gated control on the screen, dead or otherwise. The route is read-mostly and the missing guard has no current user-visible effect. The defect is the inconsistent route wiring and the trap it sets for the next engineer.

An earlier revision claimed the context was inherited from "the adjacent associations route." That is wrong - corrected 2026-06-10. Sibling `<Route>` elements in the same `<Routes>` do not nest, so one route never inherits another's provider. The inherited context is the **parent** `Management`-level provider (`Management.tsx:9-12`), which happens to carry `OWNER_ASSOCIATION_MANAGE`; the sibling wrapped routes each override it with their own `WithPermissionsProvider`, and only the bare integrations route falls through to it. The end state the original described (children see an `OWNER_ASSOCIATION_MANAGE`-only allow-list) is correct; the source was misattributed.

## Where

`odd-platform-ui/src/components/Management/ManagementRoutes/ManagementRoutes.tsx:150` - the bare route (contrast every sibling, which wraps in `WithPermissionsProvider` with an explicit `allowedPermissions={[...]}`):

```tsx
// ...every other route is wrapped, e.g.:
//   <Route path='datasources' element={<WithPermissionsProvider allowedPermissions={[DATA_SOURCE_CREATE, ...]} .../>} />
//   <Route path='associations/*' element={<RestrictedRoute isAllowedTo={hasAccessTo(OWNER_ASSOCIATION_MANAGE)} .../>} />
<Route path='integrations/*' element={<Integrations />} />   // :150 - no WithPermissionsProvider, no RestrictedRoute
```

`odd-platform-ui/src/components/Management/Management.tsx:9-12` - the **parent** provider that wraps all of `ManagementRoutes` (including the bare integrations route); its `allowedPermissions` is the only context the integrations subtree sees, because the bare route adds none of its own:

```tsx
<WithPermissionsProvider
  allowedPermissions={[Permission.OWNER_ASSOCIATION_MANAGE]}   // :10 - the inherited allow-list
  resourcePermissions={[]}
>
  ... <ManagementRoutes /> ...   // :18
</WithPermissionsProvider>
```

`odd-platform-ui/src/components/shared/contexts/Permission/PermissionProvider.tsx:27-32` - the deny-by-default access helper that the bare route's children will fall foul of (a permission must be in BOTH the global/resource grant AND the active context's `allowedPermissions`; for the bare route that allow-list is `[OWNER_ASSOCIATION_MANAGE]`, so any future integration-permission check resolves false):

```tsx
const getHasAccessTo = React.useCallback(
  (to: Permission) =>
    [...globalPermissions, ...resourcePermissions].includes(to) &&
    allowedPermissions.includes(to),                 // :29-31 - must also be in this route's allow-list
  [allowedPermissions, resourcePermissions, globalPermissions]
);
```

## User-facing impact

None today - verified 2026-06-10 by reading the rendered tree. The integrations screen is read-mostly (`IntegrationPreviewList` + an `Integration` detail view) and its subtree contains no `hasAccessTo` / `usePermissions` / `WithPermissions` consumer, so no control is currently gated, disabled, or hidden by the inherited context. The route renders and works for any user who can reach Management. There is no data exposure and no over-grant: the inherited context is `OWNER_ASSOCIATION_MANAGE`-only, and `WithPermissions` (the consumer that hard-returns `null` on `!hasAccessTo`, `WithPermissions.tsx:24,28`) is not used here.

The impact is entirely **prospective**: the first engineer to add an action behind `hasAccessTo(<integration perm>)` (or wrap it in `WithPermissions`) inside the Integrations subtree will ship a control that is invisible/disabled for everyone, because the inherited allow-list is `[OWNER_ASSOCIATION_MANAGE]` and will not contain the integration permission. Remaining check to make this concrete: none required for the current claim (it is code-settled that no such gate exists today); the trap is verified structurally.

## Why it matters

The defect is a structural inconsistency and a trap, not a present exposure. The route does not declare which permission it requires; it silently falls through to the parent `Management`-level context (`OWNER_ASSOCIATION_MANAGE`). The next engineer who adds an action behind `hasAccessTo(...)` inside the Integrations subtree will ship a control that is permanently disabled for everyone, with no obvious cause - a dead control that looks like a bug report waiting to happen. Severity is **low** (corrected from high): there is no current user-visible effect (no gated control exists in the subtree today) and no data-exposure; the value is preventing a future silent regression and bringing the one un-wrapped route in line with its siblings. It rises only if/when the Integrations screen gains a permission-gated action.

## Suggested fix

Mount the route through the same permission machinery as its siblings: wrap it in a `WithPermissionsProvider` (or `RestrictedRoute`) with the correct integration permission in `allowedPermissions`, so its children get a route-scoped permission context. If integrations is intentionally meant to have no permission gate (a deliberate everyone-can-view screen), make that explicit - give it its own `WithPermissionsProvider` with an explicit (possibly empty, documented) permission set rather than letting it silently inherit the chrome's `OWNER_ASSOCIATION_MANAGE` context. Open to alternatives on which permission, but the route should declare its own contract rather than borrow one.
