## Description

The **create** path of this same defect class is fixed under #1769 / CTRIB-033 (a uniqueness pre-check in
`createLookupTable` returning an actionable 400 USR003). The **rename** path has the identical un-guarded
collision and is deliberately left out of that PR to keep it scoped to the two reported defects + the
destructive DELETE twin (see the #1769 scope comment).

`ReferenceDataServiceImpl.updateLookupTable` (`odd-platform-api/.../service/ReferenceDataServiceImpl.java:112-130`)
recomputes the physical table name via the same lossy `buildTableName` (`:197-200`,
`name.toLowerCase().replace(" ","_")`, prefixed `n_<namespaceId>__`) and issues a physical relation rename when
the computed name differs from the current one (`:125-128`) — with **no uniqueness pre-check**. Renaming table A
to a display name that normalises to a DIFFERENT existing table B's physical name in the same namespace collides
at the DDL `ALTER TABLE ... RENAME TO` layer and surfaces a generic **500 SYS001**, exactly like the create-path
collision in #1769 (a).

## Why it is its own item (not folded into #1769)

- It is a different method/flow (`updateLookupTable`, not `createLookupTable`), and the fix needs **self-exclusion
  logic** (a rename to the table's OWN current name must not be reported as a collision — the existing `:125`
  no-op check handles the unchanged-name case, but a uniqueness pre-check must exclude the row being renamed).
- The maintainer scopes rename concerns deliberately (#1769 notes the rename -> physical-relation-rename
  **data-loss** concern is filed separately as **PLT-145**, high). This collision-500 is a sibling rename facet;
  it should be triaged alongside PLT-145 to decide whether the rename path's hardening lands as one change.

## Suggested fix

Apply the same normalised-name uniqueness pre-check used in the #1769 createLookupTable fix to
`updateLookupTable`, excluding the table being renamed (`table_name <> :newName AND id <> :thisTableId`), and
return the same actionable 400 USR003 ("Lookup table with this name already exists in this namespace") instead
of letting the physical rename 500.

## Reproduction sketch (not yet driven live)

Create table A and table B in one namespace; `PUT /referencedata/table/{A}` with a `name` that normalises to B's
physical name -> expect (today) a 500 SYS001; after the fix -> 400 USR003.
