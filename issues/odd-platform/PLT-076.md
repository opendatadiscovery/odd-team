## What

`PermissionServiceImpl.java:47-48` throws `IllegalArgumentException("No extractor for resource type %s".formatted(resourceType))` from `getExtractor(...)` when a `PolicyTypeDto` value has no matching `*PermissionExtractor` bean (e.g. a new `PolicyTypeDto` with `hasContext=true` added without its `ContextualPermissionExtractor`). `ControllerAdvice.java:24-66` declares `@ExceptionHandler`s for `BadUserRequestException`/`NotFoundException`/`UniqueConstraintException`/`CascadeDeleteException`/`WebExchangeBindException`/`GenAIException` and a catch-all `@ExceptionHandler(Exception.class)` (line 61-66) - there is NO handler for `IllegalArgumentException`, so it falls to the catch-all and surfaces as **HTTP 500** with code `SYS001` and body message `"Internal Server Error"` (verified: `Exception.class` handler at `ControllerAdvice.java:61-66` rebuilds the response from `ErrorCode.SERVER_EXCEPTION`).

Scope note (precision): the two *public* `PermissionServiceImpl` methods already throw `BadUserRequestException` (-> 400) for the has-context / no-context **input** mismatch (`PermissionServiceImpl.java:26,36`). The unhandled `IllegalArgumentException` is reachable only via the private `getExtractor` fallthrough - i.e. a **deploy/wiring gap** (a `PolicyTypeDto` value live with no extractor bean), not arbitrary user input. So the 500 is an operator/maintainer-facing diagnostic-quality defect, not a user-input validation hole.

Same shape as batch-2 F-007b / Policy JSON validator finding (IllegalArgumentException -> 500 instead of 400). This is a CLASS issue - `IllegalArgumentException` is a common-enough JVM idiom that not handling it is a regression vector for every new feature that uses it as a guard.

## User-facing impact

- Verified by BE trace 2026-06-10: `ControllerAdvice` (`ControllerAdvice.java:24-66`) has no `IllegalArgumentException` handler; the catch-all `@ExceptionHandler(Exception.class)` (`:61-66`) maps any unhandled throwable to HTTP 500 / `SYS001` / `"Internal Server Error"` (`ErrorCode.java:13` `SERVER_EXCEPTION("SYS001")`). So the missing-extractor `IllegalArgumentException` (`PermissionServiceImpl.java:47-48`) does surface as 500, not the descriptive 400 - confirmed static trace, not driven (the trigger needs a misconfigured extractor list, not reproducible from the UI).
- Audience is the operator/on-call, not the end user: the failing call is the permission-read surface, and the 500 reads as a platform crash rather than the "resource type X has no extractor" config gap it actually is. No data exposure, no auth bypass - a diagnostic-quality defect.
- Auth mode: independent of `auth.type` (the extractor lookup runs after authz); reproducible under any mode once a `PolicyTypeDto` lacks its extractor bean.

## Why it matters

Maintainer adding a new resource type AND forgetting the extractor sees HTTP 500 not the descriptive HTTP 400 - confusing diagnostic; misleads on-call who reads "Internal Server Error" as a platform crash instead of a config gap. Class-wide fix benefits F-006 + F-090 + future cases (anywhere in the codebase that uses IllegalArgumentException as a validation guard).

## Suggested fix

Add a class-wide @ExceptionHandler:

```java
// ControllerAdvice.java
@ExceptionHandler(IllegalArgumentException.class)
public Mono<ResponseEntity<ProblemDetails>> handleIllegalArgument(IllegalArgumentException ex) {
    log.warn("IllegalArgumentException at request boundary: {}", ex.getMessage());
    ProblemDetails problem = new ProblemDetails()
        .code("USR400")
        .message(ex.getMessage());
    return Mono.just(ResponseEntity.status(HttpStatus.BAD_REQUEST).body(problem));
}
```

Verify the contract with existing IllegalArgumentException-throwing paths - particularly the Policy JSON validator (batch-2 F-007b) - that the mapping to HTTP 400 is the operator-correct semantic.

Alternative: be more selective - wrap each known IllegalArgumentException-throwing branch with a `BadUserRequestException` so the existing handler in ControllerAdvice fires. Less Spring-idiomatic but more explicit.

Recommended: the class-wide handler - minimum-code-change + future-proofs against new IllegalArgumentException paths.
