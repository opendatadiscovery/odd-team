## What

The `ActivityEmptyPartitionsHousekeepingJob` empty-check (`SELECT count(*) = 0`) and the `DROP TABLE` (no `IF EXISTS`) are **two separate statements on the shared connection**, not wrapped in a transaction and holding no pre-emptive lock - unlike `AlertHousekeepingJob` / `DataEntityHousekeepingJob`, which `transaction(...)`-wrap their deletes. An `INSERT INTO activity` that lands **after** the count-zero check but **before** the DROP commits on the writer's autocommit connection, and then `DROP TABLE` destroys the just-inserted row with no re-check and no error to the original caller. The class name promises it only drops *empty* partitions; the race makes that promise unsafe against in-flight writes.

This is **net_new** at the code-fix level: it is carried only as a feature-flow drift facet plus probe P-022; no `issues/` or `backlog/` item tracks the defect. (F-021 / VAL-LSN-019-B surfaced the same race from the Activity-Feed side but filed no PLT.) Filing is gated on P-022 confirming reachability - the probe pins whether the window is hittable under realistic write timing.

## Evidence

From the F-010 reflection (`lineage/odd-platform/feature-reflections/detail/F-010.yaml`), hypothesis H-007:

```
PartitionServiceImpl.java:133-142 (isPartitionEmpty) + :120-127 (dropPartition)
  // isPartitionEmpty: SELECT count(*) = 0 FROM <partition>
  // dropPartition:    DROP TABLE <partition>   (no IF EXISTS, no recheck under lock)

EmptyPartitionsHousekeepingJob.java:16-33   (orchestration - the un-transactioned check-then-drop)
  // List<String> empty = partitionService.getEmptyPastPartitions(connection, target, exclusions())  // check pass
  // for (partition : empty) partitionService.dropPartition(connection, partition)                    // drop pass
  // NOT wrapped in transaction(...); no pre-emptive lock on the partition
  // (ActivityEmptyPartitionsHousekeepingJob just sets getTargetTable()=ACTIVITY)

AlertHousekeepingJob.java:25   (contrast - this one DOES wrap)
  // DSL.using(connection).transaction(ctx -> { ...select ids... ...delete... })
```

Probe P-022 (`lineage/odd-platform/probes/P-022.yaml`) is the existing activity check-then-drop race probe; P-012 is a sibling. Static analysis says the race window is real (Q-E.3 / Q-B.2); reachability requires running the system - no probe RUN exists on disk yet.

## User-facing impact

BE-only; no UI surface. The "user" is the operator / auditor relying on the activity (audit) trail, and the consumer-visible effect (IF the race is hit) is a silently missing audit row.

- **Static structure verified by BE trace 2026-06-10.** The empty-check (`isPartitionEmpty`, `SELECT count(*)=0`, `PartitionServiceImpl.java:133-142`) and the `DROP TABLE` (`dropPartition`, no `IF EXISTS`, `:120-127`) run as two separate statements with no enclosing transaction and no pre-emptive lock (`EmptyPartitionsHousekeepingJob.java:16-33`); the sibling `AlertHousekeepingJob` wraps its delete in `DSL.using(connection).transaction(...)` (`AlertHousekeepingJob.java:25`), confirming the inconsistency.
- **Race reachability is runtime-only; not driven.** For the DROP to destroy a row, an `INSERT INTO activity` must land in a *past* partition between the check and the drop. Activity `created_at` defaults to `NOW()` and the table is `PARTITION BY RANGE (created_at)` (`V0_0_48__add_activity.sql:9,13`), so under normal operation new rows go to the *current* partition, not a past one - the window is the date-rollover boundary (a write timestamped just before midnight, or any backdated / bulk activity write, landing in yesterday's partition exactly as housekeeping deems it past+empty). Probe `P-022` is defined to pin this; no probe RUN exists on disk, so reachability is unconfirmed.
- **If reachable:** silent loss of an audit-trail row the writing code saw as committed-success - the worst kind of audit defect (the record the operator believes was saved is gone, no error, no compensating undo).

`user_facing_verified` stays false: the observable is a concurrency race that cannot be confirmed without driving the system (the remaining check is the P-022 run). Severity HIGH is conditional on that confirmation.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: wrap the `getEmptyPastPartitions` empty-check and `dropPartition` in a single transaction taking an `ACCESS EXCLUSIVE` lock **before** the count check, **or** re-check emptiness under the lock immediately before DROP (`PartitionServiceImpl.java:108-127`). Gate the fix on P-022's reachability outcome.
