## What

The Management -> Associations -> "+ Create association" form (Branch C of the user-owner-association write-path family - see DOC-220) accepts any non-empty string in the `oidcUsername` field. There is:
- No format validation (it could be an email, a UUID, a free-text "alice", a typo)
- No existence check against the IdP
- No validation that the username corresponds to an actual identity record on file

The backend then inserts the binding without resolving the username. Confirmed 2026-06-10: `UserOwnerMappingServiceImpl.createRelation` (`UserOwnerMappingServiceImpl.java:15-18`) takes the raw `username, provider, ownerId` and does `deleteRelation(username, provider).then(createRelation(username, provider, ownerId))` - **no format check, no IdP existence check, no identity-record lookup** anywhere in the service. So both ends accept the string verbatim.

Outcome: an admin can bind an Owner to a username string that does not yet exist (or never will exist) in the IdP. The resulting `user_owner_mapping` row is an **orphan binding from day one** - now confirmed code-end-to-end (FE has only `required: true`; BE inserts the raw string).

## Where

`odd-platform-ui/src/components/Management/OwnerAssociations/OwnerAssociationsHeader/OwnerAssociationForm/OwnerAssociationForm.tsx:62-76`

Verified verbatim during this session:

```tsx
// oidcUsername Controller
defaultValue: '',
rules: { required: true }   // <- required-only; no pattern, no format check, no async existence query
```

Backend insertion site - verified 2026-06-10:

```java
// UserOwnerMappingServiceImpl.java:15-18 - no validation of any kind
public Mono<UserOwnerMappingPojo> createRelation(final String username, final String provider, final Long ownerId) {
    return userOwnerMappingRepository.deleteRelation(username, provider)   // delete-then-insert (idempotent on username+provider)
        .then(userOwnerMappingRepository.createRelation(username, provider, ownerId));
}
```

- The service performs a `deleteRelation(username, provider)` before `createRelation`, so re-binding the **same** username+provider replaces the existing row (no duplicate, no UNIQUE violation for that exact pair); the orphan risk is the username never matching a real identity, not row duplication.
- `SecurityConstants.java:155-158` (cited from the original scan) gates the endpoint by `OWNER_RELATION_MANAGE` - not re-verified this session; the validation-absence claim does not depend on it.

## User-facing impact

Code-settled on the verification claim (no validation either end); the downstream consequence is partly static, partly runtime. Verified: the "+ Create association" dialog's `oidcUsername` field has only `required: true` (`OwnerAssociationForm.tsx:62-76`) and the backend service inserts the string verbatim (`UserOwnerMappingServiceImpl.java:15-18`) - so an admin who types a malformed or not-yet-existent username gets no feedback at submit time and a `user_owner_mapping` row is written for that string. That is the load-bearing, fully code-settled claim.

Not driven (runtime-only): the exact downstream behaviour when the bound username later does/doesn't arrive as a real principal - i.e. whether `F-011` resolution silently misses the user and they end up requesting a second binding. Remaining check to make that concrete: with a non-DISABLED auth mode, create an association to a bogus username, then log in as the intended user and observe whether the OwnerAssociation widget treats them as unbound; no workspace probe-run exists for this path.

## Why it matters

The downstream consumer of `user_owner_mapping` is `F-011` (Principal-to-Owner Resolution) - every authentication flow that maps an authenticated principal to their Owner row. With an orphan binding present (admin made a typo, or pre-bound a not-yet-onboarded user with a misspelled username), the intended user is silently never matched to the Owner the admin thought they bound. The user logs in, sees the home-page OwnerAssociation widget asking them to request a binding (because resolution missed them), and submits a request the admin then approves. Note (corrected 2026-06-10): the service deletes any existing row for the same `username + provider` before inserting (`UserOwnerMappingServiceImpl.java:16`), so the failure is the **wrong** username never matching - not a duplicate row or a UNIQUE-constraint clash for the same pair. The "two rows / UNIQUE error" framing in the earlier revision is therefore down-weighted; the real harm is a binding that points at a string no principal will ever present.

Severity MEDIUM because:
- The defect is admin-side; end users are not directly affected
- BUT - orphan bindings accumulate quietly in the Owner-Association directory
- AND - the operator audit "who is bound to which Owner" returns rows that don't correspond to real users
- AND - composition with F-075b's self-mint side-door means a malicious admin (or one with a typo prone to a privileged username) can bind a real future username to a chosen Owner before that username arrives, pre-staging an attack on an OIDC-group-mapped principal

## Suggested fix

1. **Client-side validation pass**: add format validation appropriate to the deployment's identity-naming convention (email-shaped / non-whitespace string / charset filter). Provide an info hint in the form clarifying the expected format and naming the active IdP.
2. **Async existence check** (preferred when feasible): wire a backend endpoint (e.g. `GET /api/idp/users/{username}/exists` or a search-by-username surface) and call it on field blur. Show an existence warning when the username is not yet known to the IdP - but allow proceed (an admin may pre-bind a not-yet-onboarded user as a feature). The signal is a warning, not a hard error.
3. **Backend defensive validation**: at `POST /api/owners/mapping`, validate the format unconditionally; emit a 400 with a clear error code for typo'd usernames; emit a separate warning header / extended response body when the username is well-formed but unknown to the IdP at submit time.

Open to alternatives - the admin pre-staging use case is real (operators want to set up associations before a user logs in for the first time), so a hard-reject on missing IdP records is the wrong call.
