## What

Issue #1764 bundled one bug and two architectural gaps around `data_entity.view_count`.
The bug (the front-end double-fetch that registered +2 per page-open) is fixed by the
#1764 PR. The two design gaps remain, deliberately deferred (see the scope comment on
#1764), and this issue gives them their own tracking:

1. **The increment is unguarded.** `GET /api/dataentities/{id}` bumps `view_count` by +1
   on every call with no rate-limit, no idempotency key, no per-user/session
   de-duplication, and no auth requirement (`getDataEntityDetails` carries no
   `@PreAuthorize`; under the shipped `auth.type=DISABLED` default the call is anonymous).
   A scripted read loop inflates any entity's count without restriction - runtime-pinned:
   10 unauthenticated GETs produced exactly +10 (workspace probe P-002).
2. **The inflatable counter is the sole ranking signal for the home-page Popular column.**
   `listPopular` orders by `VIEW_COUNT DESC` alone (ID-desc tiebreak only) - no recency,
   no distinct-viewer weighting, no decay. There is also no index on `view_count`, so the
   ordering scans.

Net effect: any caller on the network can drive an arbitrary entity to the top of a
primary discovery surface, and the platform presents that ranking as "most popular".
The published docs carry an explicit "trivially inflatable - do not treat as trustworthy
usage evidence" warning on the catalog-overview and entity-detail pages until this lands.

## User-facing impact

- The Popular column (rendered when auth is enabled and the user has an owner
  association; the API is reachable under every auth mode) orders by a counter any
  network caller can pump. Operators reading "Popular" as organisational signal are
  reading an unauthenticated, unthrottled tally.
- Routine legitimate browsing also skews the ranking toward frequently-opened (not
  necessarily valued) entities - by design, but with no balancing signal.
- With many entities, the unindexed `view_count DESC` ordering is a sequential scan on
  a hot home-page query.

## Why it matters

The Popular strip is a primary discovery surface; its trustworthiness is a product
promise. A signal that is (a) anonymous-writable, (b) unthrottled, and (c) the only
ranking input cannot honestly back that promise. This is a design decision, not a
patch: any naive server-side sentinel (cookie- or IP-based de-dup) is attacker-
controlled and would only add complexity while the docs still need the "inflatable"
warning.

## Suggested fix (design options - pick at the proposal stage, not piecemeal)

- **Authenticate or gate the increment**: only count views for authenticated principals
  (no-op under `DISABLED`), or expose an explicit opt-in counting endpoint instead of
  counting on every GET.
- **Count distinct viewers, not fetches**: a `(data_entity_id, principal, day)`-grained
  de-dup table or HyperLogLog-style approximation; rank Popular by distinct viewers
  with a recency decay.
- **Rate-limit / debounce at the write source** as a stopgap (per-entity token bucket) -
  acknowledging it does not stop a patient attacker, only accidental hammering.
- **Add a secondary ranking signal** (recency of views, ownership links) so a single
  counter is never the sole input.
- **Index `view_count`** (or the replacement ranking key) for the Popular ordering.

Each option changes either the security posture of a public endpoint or the meaning of
a user-facing ranking - i.e. this needs a short design proposal (ADR-class) before code.
