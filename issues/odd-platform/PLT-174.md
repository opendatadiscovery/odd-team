## What

The Activity Feed endpoint (`GET /api/activity`) accepts an `owner_ids` filter and a `type` selector. `type` selects one of four views - `ALL`, `MY_OBJECTS`, `DOWNSTREAM`, `UPSTREAM`. The `owner_ids` filter is **only actually applied** when `type` is `ALL` (or omitted). For `MY_OBJECTS`, `UPSTREAM`, and `DOWNSTREAM` the `owner_ids` argument is **silently dropped** on the way into the repository, so the owner filter has **no effect** for three of the four views. The API contract exposes `owner_ids` as an unconditional, optional query parameter on the operation - nothing signals that it is honored for only one value of `type` - so a client that filters activity by owner under `MY_OBJECTS`/`UPSTREAM`/`DOWNSTREAM` gets back unfiltered results and is given no indication that the filter was ignored.

## Where

`odd-platform-api/src/main/java/.../service/activity/ActivityServiceImpl.java:108-113` - only the `ALL`/`null` branches forward `ownerIds`; the other three switch arms call methods that have no `ownerIds` parameter at all:

```java
if (type == null) {
    return fetchAllActivities(..., ownerIds, ...);          // ownerIds forwarded
}
return switch (type) {
    case MY_OBJECTS -> fetchMyActivities(..., /* no ownerIds */ ...);          // line 108
    case DOWNSTREAM -> fetchDependentActivities(..., /* no ownerIds */ ...);   // line 110
    case UPSTREAM   -> fetchDependentActivities(..., /* no ownerIds */ ...);   // line 112
    case ALL        -> fetchAllActivities(..., ownerIds, ...);                 // line 114 - ownerIds forwarded
};
```

`fetchMyActivities` (`ActivityServiceImpl.java:184`) and `fetchDependentActivities` (`:201`) have no `ownerIds` parameter in their signatures, so the caller's `ownerIds` is discarded for those three modes.

The controller passes `ownerIds` through unconditionally - `ActivityController.java:38` forwards it straight into `getActivityList(...)` - and the contract exposes it unconditionally. In `odd-platform-specification/openapi.yaml` the `getActivity` operation (line 3210) declares `owner_ids` (lines 3241-3247) and `type` (lines 3255-3258) as independent optional query parameters, with no note that `owner_ids` applies only when `type=ALL`:

```yaml
operationId: getActivity
parameters:
  ...
  - name: owner_ids        # lines 3241-3247
    in: query
    schema:
      type: array
      items:
        type: integer
        format: int64
  ...
  - name: type             # lines 3255-3258
    in: query
    schema:
      $ref: './components.yaml/#/components/schemas/ActivityType'   # ALL | MY_OBJECTS | DOWNSTREAM | UPSTREAM
```

## Why it matters

This is a silent contract violation: the API advertises an `owner_ids` filter that does nothing for three of four activity views, with no error and no warning. A consumer building an owner-scoped activity view (for example, "show me my-objects activity for owners X and Y") receives a full, unfiltered result set and has no way to know the filter was ignored - the results simply look wrong, or look like the filter "doesn't work". It erodes trust in the API and can mislead anyone using the activity feed for owner-scoped review. Severity is medium: it is not a security or data-loss issue, but it is a real correctness/contract defect on a documented filter, and the failure mode is silent.

## Suggested fix

Either (a) thread `ownerIds` through all four view modes - add the `ownerIds` parameter to `fetchMyActivities`/`fetchDependentActivities` and their downstream repository queries so the owner filter is honored consistently - or (b) if the owner filter is intentionally unsupported for `MY_OBJECTS`/`UPSTREAM`/`DOWNSTREAM`, drop `owner_ids` from those code paths' contract surface or document in the OpenAPI operation that `owner_ids` is honored only for `type=ALL`. Option (a) (consistent filtering) is the better default for an advertised filter; option (b) is acceptable if there is a deliberate reason the other views cannot be owner-scoped. Open to alternatives.
