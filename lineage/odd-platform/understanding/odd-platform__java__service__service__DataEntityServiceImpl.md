# DataEntityServiceImpl — semantic understanding

## understanding

`DataEntityServiceImpl` is the **orchestration hub between `DataEntityController` and the data-entity persistence layer** — 685 lines, 22 public methods (implementing the 22-method `DataEntityService` interface at `DataEntityService.java:34-95`) plus 12 private helpers. It is the only place where `@ReactiveTransactional` boundaries are placed for the data-entity domain (8 occurrences: lines 197, 246, 288, 308, 324, 337, 357, 388, 411) — every write that needs atomicity is delimited here, not in the repository (per the repo-sidecar invariant `ReactiveDataEntityRepositoryImpl.md:concepts.invariants.[3]` — the repository has NO transactional annotation). The service is a **thin facade for some methods** (`listPopular` line 228-231 is a 1-line pass-through; `getDataEntityClassesAndTypes` line 137 is a constant; `listByTerm` line 234-243 is a 3-line pass-through with one map step) AND **a fat orchestrator for others** (`getDetails` line 196-209 chains 5 reactive steps: repository read → entity-class enrichment → parent-group enrichment → details enrichment → view-count UPDATE → response map; `createMetadata` line 247-285 chains 7+ steps for the metadata-create flow; `addDataEntityToDEG` line 388-408 zips two entity reads + a relation create + a filled-flag mark). Three feature-flow hops route through this file: **F-001 getDetails** (line 196-209, the `@ReactiveTransactional` boundary wrapping read-then-incrementViewCount), **F-003 listPopular** (line 227-231, the 1-line pass-through that re-confirms the view-count→popular loop), **F-004 upsertDescription** (line 323-333, the `@ReactiveTransactional` boundary delegating to `DataEntityInternalStateServiceImpl.updateDescription`). The service applies **NO owner-scoping at any read path that lists data entities except `listAssociated`** (line 212-225, which explicitly fetches the caller's associated owner first via `authIdentityProvider.fetchAssociatedOwner()`); `getDetails`, `getDimensions`, `getDataEntitiesByDatasourceAndType`, `getDataEntityGroupsChildren`, `getDomainsInfo`, `getDataEntityUsageInfo`, `listByTerm`, `listPopular` all return cross-owner data to any authenticated caller — confirming the read-collaborative posture is consistent at the service tier (cross-ref `getDataEntityDetails.md:implicit_adrs.[0]`). The file is **pure reactive** (zero `.block()` / `.blockOptional()` calls — verified by grep) so the batch-D anti-pattern (`.block()` inside an `@ReactiveTransactional`) is NOT present here.
