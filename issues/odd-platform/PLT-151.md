## What

The predefined-name protection on roles and policies is incomplete and internally inconsistent across the three CRUD verbs. `create()` performs **no** reserved-name check at all on either `Policy` or `Role`, while `update()` and `delete()` each guard against the privileged "Administrator" name — but they do not agree on how to compare it. The result is two operator-visible holes:

1. **Re-minting a trusted name.** If the seeded `Administrator` role/policy is ever removed (e.g. an out-of-band soft-delete, a botched migration, or the partial-unique-index allowing the seeded name to be re-used), any caller permitted to create can POST a brand-new role/policy literally named `Administrator` with attacker-chosen permission bindings. `create()` will accept it because it never inspects the name.
2. **A case-variant that is creatable, editable, and permanently undeletable.** A role named lowercase `administrator` slips past `update()` and `delete()` differently: `update()` compares with case-**sensitive** `.equals(...)` (so the lowercase variant is editable), but `delete()` compares with case-**insensitive** `.equalsIgnoreCase(...)` (so the lowercase variant is rejected as "predefined and cannot be deleted"). The same name is thus simultaneously editable and undeletable — a wedge that can only be cleared by direct DB surgery.

## Where

Four loci, one name-guard cluster:

**`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/service/RoleServiceImpl.java:51-61` — `create()` has no name guard:**
```java
public Mono<Role> create(final RoleFormData formData) {
    final List<Long> policies = getPolicyIdsList(formData);
    return Mono.just(formData)
        .map(roleMapper::mapToPojo)
        .flatMap(roleRepository::create)          // no reserved-name check anywhere
        .flatMap(role -> roleToPolicyRepository
            .createRelations(role.getId(), policies)
            .thenReturn(role))
        ...
```

**`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/service/PolicyServiceImpl.java:62-69` — `create()` validates only the JSON schema, never the name:**
```java
public Mono<PolicyDetails> create(final PolicyFormData formData) {
    policyJSONValidator.validate(formData.getPolicy());   // schema only
    return Mono.just(formData)
        .map(policyMapper::mapToPojo)
        .flatMap(policyRepository::create)                // no ADMINISTRATOR_POLICY guard
        .map(policyMapper::mapToDetails);
}
```

**`odd-platform-api/.../service/RoleServiceImpl.java:68` — `update()` is case-SENSITIVE:**
```java
.filter(role -> !role.getName().equals(UserProviderRole.ADMIN.getValue()))
```

**`odd-platform-api/.../service/RoleServiceImpl.java:81-82` — `delete()` is case-INSENSITIVE:**
```java
.filter(role -> Stream.of(UserProviderRole.values())
    .noneMatch(r -> r.getValue().equalsIgnoreCase(role.getName())))
```

(`PolicyServiceImpl` shows the mirror gap on the Policy side: `update()` at `:76` and `delete()` at `:87` both compare with case-sensitive `.equals(ADMINISTRATOR_POLICY)`, so a lowercase `administrator` policy is fully unguarded by either verb, and `create()` at `:63` is unguarded entirely.)

## Why it matters

This is a privilege-escalation / integrity hole on the RBAC surface, which is exactly the surface that is supposed to be the hardest to tamper with. The failure is **silent** — no error, no log, no audit trail (the audit-silence on these methods is tracked separately as PLT-062). An operator who believes "Administrator is a protected, immutable, seeded identity" is wrong in two ways: it can be re-created under attacker control after deletion, and a near-identical case variant behaves inconsistently enough to leave an unremovable row. Anyone able to reach Role/Policy create (which, under `auth.type=DISABLED`, is *anyone unauthenticated* — see PLT-152) can mint a trusted-looking `Administrator` and bind it to a `MANAGEMENT`/`ALL` policy. High severity: it defeats the intended immutability of the most privileged built-in identity, and the case asymmetry is a latent footgun even for legitimate admins.

## Suggested fix

Treat all three verbs as one name-guard cluster and make them uniform:

1. Add a reserved-name guard to **both** `PolicyServiceImpl.create` and `RoleServiceImpl.create` that rejects any attempt to create a role/policy whose name collides with a predefined name (`Administrator` / the `UserProviderRole` values), raising `BadUserRequestException`.
2. Make the comparison **case-insensitive in all three verbs** (`create`/`update`/`delete`) — `equalsIgnoreCase` (or normalise to a canonical case before comparison) — so a lowercase `administrator` cannot diverge into the editable-but-undeletable state. Pick one comparison helper and use it everywhere.
3. Apply the same fix symmetrically on the Policy side (the `ADMINISTRATOR_POLICY` constant comparison at `PolicyServiceImpl.java:76,87`).

Open to alternatives on exactly where the reserved-name set is centralised, but the invariant must hold identically across create/update/delete.
