## What

Three related defects on the Identity Probe / DISABLED-mode synthetic admin surface:

**Defect 1 - Synthetic admin with DYNAMIC blast radius (F-085a).** `IdentityController.whoami` (`IdentityController.java:23-28`) calls `identityService.whoami()` and `.switchIfEmpty(dummyOwner())`; `dummyOwner()` (`:30-33`) returns `new Identity().username("admin").permissions(Arrays.asList(Permission.values()))`. (Mechanism precision, verified 2026-06-10: the fallback fires whenever the security context has no authenticated principal - it is not literally branched on `auth.type=DISABLED` inside the controller. Under DISABLED there is no principal, so `whoami` returns the all-permissions synthetic admin; the operator-visible outcome the draft describes is correct.) `Permission.values()` dynamically expands - adding a new Permission to the OpenAPI spec AUTOMATICALLY enters this grant. ZERO authentication + ZERO audit + DYNAMIC blast radius. Operators who flip DISABLED on for a quick demo and forget have an anonymous all-permissions API surface.

**Defect 2 - Auth-mode fingerprint in ONE call (F-085b).** `whoami` is NOT in `WHITELIST_PATHS`. Under LOGIN_FORM the SecurityWebFilterChain returns 302; under OAUTH2/LDAP it returns 401; under DISABLED 200+admin. Four response shapes ARE the fingerprint.

**Defect 3 - admin/ADMIN literal collision (F-085c).** `IdentityController.java:32` literal `"admin"` (lowercase); `S2sAuthenticationFilter.java:31-34` literal `"ADMIN"` (uppercase). Two distinct identity surfaces; both undocumented; both case-collidable with operator-named users.

## User-facing impact

Mixed: the synthetic-admin and literal-collision facts are code-settled; the auth-mode fingerprint is runtime-observable and was NOT driven on a running stack this pass.

- **Defect 1 (HOLDS, code-settled).** Under `auth.type=DISABLED` (no authenticated principal), `GET /api/identity/whoami` returns `username:"admin"` with `permissions = Permission.values()` (every permission) - `IdentityController.java:23-33`. Any new permission added to the spec auto-joins this grant. A deployment that inherits DISABLED from a template grants the full write surface to anonymous callers. Auth mode: DISABLED only (under real auth modes the service returns the real principal and the fallback never fires).
- **Defect 2 (RUNTIME-ONLY for the exact codes; whitelist-absence is code-settled).** `whoami` is not in `WHITELIST_PATHS` (`SecurityConstants.java:96`), so under non-DISABLED modes it hits the `/**` -> `.authenticated()` catch-all (`AuthorizationCustomizer.java:29-30`) and is rejected by the mode's default entry point. The claim that the four modes yield four distinguishable response shapes (302 vs 401 vs 200+admin) depends on Spring Security's per-mode default entry point - there is NO custom `authenticationEntryPoint`/`exceptionHandling` in the auth package (grep, 2026-06-10), so the precise codes are framework defaults that should be confirmed with a live probe across the four modes before relying on the exact matrix. The reconnaissance concern is plausible; the exact codes are not pinned by a readable line.
- **Defect 3 (HOLDS, code-settled).** `IdentityController.java:32` uses lowercase `"admin"`; `S2sAuthenticationFilter.java:31-33` uses uppercase `"ADMIN"`. Both are reserved synthetic identities; an Owner named `admin`/`ADMIN` collides. Auth mode: DISABLED (lowercase dummy) and S2S/ingestion (uppercase principal).
- Remaining-check: the auth-mode response-code matrix (Defect 2) needs a 4-mode live probe to confirm the exact codes.

## Why it matters

DISABLED mode is dev/demo-only per docs, but the synthetic-admin shape means a deployment that accidentally inherits DISABLED from a template has ZERO defence - and the dynamic blast radius means future Permission additions silently enter the grant. The auth-mode fingerprint reduces attacker recon to one GET. The admin/ADMIN literal collision is a footgun for any deployment naming an Owner `admin` or `ADMIN`.

## Suggested fix

**Thread A - Explicit DISABLED acknowledgment (Defect 1).**

Require an explicit environment variable to enable DISABLED mode beyond `auth.type=DISABLED` alone:

```java
@Value("${odd.disabled-auth-ack:}")
private String disabledAuthAck;

@PostConstruct
void validateDisabledAuthAck() {
    if ("DISABLED".equalsIgnoreCase(authType)
        && !"I_ACCEPT_NO_AUTH_NO_AUDIT".equals(disabledAuthAck)) {
        throw new IllegalStateException(
            "auth.type=DISABLED requires explicit acknowledgment via env var ODD_DISABLED_AUTH_ACK=I_ACCEPT_NO_AUTH_NO_AUDIT. " +
            "DISABLED grants synthetic ADMIN with ALL permissions to anonymous callers; see " +
            "https://docs.opendatadiscovery.org/configuration-and-deployment/enable-security/authentication/disabled-authentication");
    }
}
```

Operators inheriting DISABLED from a template fail-fast on boot with a clear message pointing to the doc that enumerates the reachable surfaces.

**Thread B - Uniform 401 for whoami across non-DISABLED modes (Defect 2).**

Under LOGIN_FORM, configure `whoami` to return 401 instead of redirect to login - anonymous reconnaissance no longer distinguishes LOGIN_FORM from OAUTH2/LDAP via response code. The SPA bootstrap path already handles 401 (treats as "not logged in"), so the user-visible behavior is unchanged.

**Thread C - Shared SystemUsers constants (Defect 3).**

```java
// New file: odd-platform-api/src/main/java/.../auth/SystemUsers.java
public final class SystemUsers {
    public static final String DISABLED_DUMMY = "admin";
    public static final String S2S_PRINCIPAL = "ADMIN";
    
    private SystemUsers() {}
}
```

Update `IdentityController.java:32` and `S2sAuthenticationFilter.java:31-34` to use these constants. Add a doc admonition that these literals are reserved + that Owner provisioning should avoid them.
