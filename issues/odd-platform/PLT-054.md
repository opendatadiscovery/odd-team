## What

Four defects on the Slack data-collaboration integration. Doc-side mitigation ships as DOC-204; structural fixes are this PLT.

**Defect 1 - `/api/slack/events` accepts forged POSTs from any internet caller (HIGH).** `EventApiController.java:23-25` deserializes raw body from `@RequestBody Mono<String>` and never reads any header; `SlackEventParser.parse` (`SlackEventParser.java:22-23`) goes straight to JSON deserialise. Grep for `X-Slack-Signature`, `signing.secret`, `verifySignature`, `HmacSha256` returns ZERO matches across `odd-platform-api/src` (verified 2026-06-10). Slack's protocol mandates HMAC-SHA256 over `v0:{timestamp}:{body}` - ODD does NONE of this. The endpoint is additionally in `WHITELIST_PATHS` (`SecurityConstants.java:96`) -> `.permitAll()` (`AuthorizationCustomizer.java:22-23`), so it is unauthenticated by design (Slack cannot carry an ODD session) and HMAC is the only possible defence. Any internet caller can forge `event_callback` payloads; the parser only accepts thread-reply `message` events (`SlackEventParser.java:56-105`), so the forgeable effect is injecting/modifying thread-reply messages attributed to Slack into a data entity's Discussions.

  CORRECTION (verified 2026-06-10): the original draft added "plant `javascript:` URLs" implying stored XSS on render. That is **FALSE**. Discussion message `text` is rendered as React-escaped `{text}` inside a MUI `<Typography>` (`MessagesList/Message/Message.tsx:77`, `CurrentMessage/Thread/ThreadContent/ThreadMessage/ThreadMessage.tsx:35`); there is **no** `dangerouslySetInnerHTML` anywhere in the DataCollaboration tree. The "Open in Slack" link uses `to={url}` where `url` is ODD's own `resolveMessageUrl` (the Slack permalink resolved server-side), not a field carried in the forged event payload. The defect is forged-message *injection*, not script execution.

**Defect 2 - At-least-once delivery has no idempotency guard, but the cited dedup-key mechanism does not exist (MEDIUM, premise corrected).** `ReactiveMessageRepositoryImpl.createMessageEvent` (`ReactiveMessageRepositoryImpl.java:136-155`) does a plain `insertInto(MESSAGE_PROVIDER_EVENT).set(record)` with no `ON CONFLICT`, and `getUUIDByProviderInfo` (`:188-195`) has no `LIMIT 1` (order-undefined return on multi-result). Those two facts HOLD. **However**, the original draft's fix - "add a UNIQUE on `(provider, event_id)`" - is not applicable as written: the `message_provider_event` table (`V0_0_59__data_collaboration.sql:25-39`) has **no `event_id` column** (its columns are `id BIGSERIAL`, `parent_message_uuid`, `parent_message_created_at`, `provider`, `action`, `event JSONB`, `created_at`, `state`, `error_message`; grep for `event_id` across all migrations = zero). There is no stored Slack event id to deduplicate on. A real dedup would require extracting Slack's `event_id` from the inbound JSON, persisting it in a new column, and uniquing on `(provider, <new event_id column>)` - a larger change than the one-line ON CONFLICT the draft implied. Re-scoped in Suggested fix below.

**Defect 3 - Slack channels autocomplete uses startsWith filter (LOW).** `SlackMessageProviderClient.java:52` - `slackChannel.name().startsWith(nameLike)`. Typing the middle of a channel name returns nothing.

**Defect 4 - 1-minute Caffeine cache on Slack channels (LOW).** `SlackMessageProviderClient.java:36-44` - `expireAfterWrite(1, MINUTES)`. Freshly-invited bot-channel membership invisible for up to 60s.

## User-facing impact

VERIFIED (BE wiring + FE render trace + grep), 2026-06-10:

- **Defect 1 (HOLDS, HIGH):** `POST /api/slack/events` is anonymously reachable in every auth mode when Data Collaboration is enabled (whitelisted -> permitAll), with no HMAC. A forged `event_callback` injects/edits thread-reply messages attributed to Slack into a data entity's Discussions surface. Auth mode: webhook is whitelisted, so this is auth-mode-independent. NOT a stored-XSS vector (text is React-escaped; see Defect 1 correction).
- **Defect 2 (HOLDS as a data-integrity gap; fix re-scoped):** no idempotency on event ingest, so a duplicated Slack delivery (Slack retries on non-2xx within ~3s) inserts duplicate `message_provider_event` rows and the processor can materialise duplicate child messages an operator sees in a thread. The specific `(provider, event_id)` unique index the draft proposed cannot be created - no such column exists.
- **Defect 3 (LOW):** typing the middle of a channel name in the Slack-channel autocomplete returns nothing (`startsWith`), a daily UX papercut for operators with prefixed channel names.
- **Defect 4 (LOW):** a freshly bot-invited channel is invisible in the autocomplete for up to 60s (1-minute cache).
- Remaining-check (not driven on a running stack this pass): the live duplicate-child-message materialisation under a replayed delivery was not exercised end-to-end; the missing-ON-CONFLICT and missing-LIMIT-1 are code-settled, the user-visible duplicate-row outcome is inferred from them.

## Why it matters

Defect 1 is most operator-load-bearing: any internet caller forges events into the platform's message stream (anonymous remote write into Discussions). It is NOT an XSS/open-redirect vector - message text is React-escaped on render and the "Open in Slack" URL is resolved server-side, not carried in the event (see Defect 1 correction). Security-conscious deployments need reverse-proxy HMAC verification today (per DOC-204 caveat) until the in-app HMAC check lands. Defect 2 is a data-integrity hazard (duplicate child messages on replayed delivery). Defects 3+4 are UX surprises operators work around.

Severity HIGH: Defect 1 is anonymous remote write into the message stream. (Severity unchanged - the write-injection finding stands on its own; the falsified XSS sub-claim was not the basis for HIGH.)

## Suggested fix

**Defect 1 - HMAC-SHA256 signature verification:**
```java
public boolean verify(String body, String timestamp, String signature) {
  if (!isFreshTimestamp(timestamp)) return false;   // reject replay > 5 min
  final var basestring = "v0:" + timestamp + ":" + body;
  final var computed = "v0=" + HmacUtils.hmacSha256Hex(signingSecret, basestring);
  return MessageDigest.isEqual(computed.getBytes(UTF_8), signature.getBytes(UTF_8));
}

@PostMapping("/api/slack/events")
public Mono<ResponseEntity<Void>> postSlackEvent(
    @RequestBody Mono<String> body,
    @RequestHeader("X-Slack-Request-Timestamp") String timestamp,
    @RequestHeader("X-Slack-Signature") String signature) {
  return body.flatMap(raw -> verifier.verify(raw, timestamp, signature)
      ? slackEventService.handle(raw).thenReturn(ResponseEntity.ok().build())
      : Mono.just(ResponseEntity.status(401).build()));
}
```
Config: `datacollaboration.slack-signing-secret`; Spring Sanitizer masks `secret`-suffixed names.

**Defect 2 - persist Slack's event id, then unique + ON CONFLICT (re-scoped - the original column does not exist):**
Slack's `event_id` is not currently stored. Add a migration that introduces an `event_id VARCHAR` column on `message_provider_event`, have `SlackEventParser`/`createMessageEvent` extract and persist Slack's top-level `event_id`, then:
```sql
ALTER TABLE message_provider_event ADD COLUMN event_id VARCHAR(128);
CREATE UNIQUE INDEX uq_message_provider_event_provider_event_id ON message_provider_event(provider, event_id);
```
```java
dslContext.insertInto(MESSAGE_PROVIDER_EVENT).set(record)
  .onConflict(MESSAGE_PROVIDER_EVENT.PROVIDER, MESSAGE_PROVIDER_EVENT.EVENT_ID).doNothing();
```
Plus `LIMIT 1` on `getUUIDByProviderInfo` (`ReactiveMessageRepositoryImpl.java:188-195`). (Alternatively, dedup on a deterministic hash of the event JSON if adding a column is undesirable - but a dedicated `event_id` column is the Slack-idiomatic key.)

**Defect 3 - contains filter:**
```java
- .filter(slackChannel -> slackChannel.name().startsWith(nameLike))
+ .filter(slackChannel -> StringUtils.containsIgnoreCase(slackChannel.name(), nameLike))
```

**Defect 4 - configurable TTL (actual code uses `expireAfterWrite(1, TimeUnit.MINUTES)` at `SlackMessageProviderClient.java:38-40`):**
```java
- .expireAfterWrite(1, TimeUnit.MINUTES)
+ .expireAfterWrite(channelCacheTtlMinutes, TimeUnit.MINUTES)   // datacollaboration.channels-cache-ttl-minutes
```

## How discovered

Surfaced during Mode B batch-3 scan of `docs/coverage/undocumented-features` on 2026-05-27 (substrate `F-038`). Doc-side caveats ship via DOC-204.

**2026-06-10 verification sweep (G15):** all four defects re-traced against the working tree. Defect 1 (HMAC absence) HOLDS - with the added wiring fact that the webhook is whitelisted/permit-all (not session-gated). Defects 3 (startsWith) and 4 (1-min cache) HOLD; line refs tightened. Two corrections: (a) Defect 1's "plant `javascript:` URLs / XSS on render" sub-claim is FALSIFIED - Discussion message text is React-escaped `{text}` (`Message.tsx:77`, `ThreadMessage.tsx:35`) and there is no `dangerouslySetInnerHTML` in the DataCollaboration tree; the finding is forged-message injection, not script execution. (b) Defect 2's premise that a `(provider, event_id)` unique index closes the dedup gap is wrong - `message_provider_event` has no `event_id` column (verified across all migrations); the missing ON CONFLICT and missing LIMIT 1 are real, but a real dedup needs a new column. Severity unchanged (HIGH rests on Defect 1's anonymous write, which stands).
