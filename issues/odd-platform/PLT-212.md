## What

The dedicated `WebClient` the platform uses to call the external GenAI service is built with no codec configuration, so it inherits Spring WebFlux's **default 256 KB in-memory buffer limit** for decoding the response body. Any GenAI answer larger than 256 KB therefore fails with `DataBufferLimitException` ("Exceeded limit on max bytes to buffer"), which the service wraps and surfaces to the user as a generic HTTP 500. The GenAI feature documentation frames the answer-size ceiling as "governed only by the global WebFlux limit (default 20 MB)" - but that 20 MB app-wide limit is configured elsewhere and is **not** applied to this client, so the real ceiling on the outbound response path is 256 KB, roughly an 80x gap between documented and actual behaviour.

## Where

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/config/WebClientConfiguration.java:26-29`

```java
return WebClient.builder()
    .clientConnector(connector)
    .baseUrl(genAIProperties.getUrl())
    .build();
```

No `.codecs(c -> c.defaultCodecs().maxInMemorySize(...))` call - so the WebFlux default (`262144` bytes = 256 KB) governs response decoding for `genAiWebClient`. (The 20 MB ceiling the docs reference is the app-wide `spring.codec.max-in-memory-size`-style setting, which a builder-constructed `WebClient` does not pick up unless explicitly applied.)

## Why it matters

Loud but misleading. A long-form AI answer (a multi-page summary, a large generated table) over 256 KB fails with an opaque HTTP 500 rather than the full answer the docs promise. The operator's own documentation tells them 20 MB is fine, so they have no reason to suspect a 256 KB limit; troubleshooting leads nowhere because the error is generic. Severity is low - it requires an unusually large answer to trigger and causes a failed request, not data loss or a security issue - but it is a real code-vs-docs contradiction that wastes operator time and breaks the feature's stated capability for large outputs.

## Suggested fix

Add an explicit codec override to the `genAiWebClient` builder, sizing the in-memory buffer to match the answer ceiling the platform intends to support (e.g. the 20 MB the docs reference, or a deliberately chosen value):

```java
return WebClient.builder()
    .clientConnector(connector)
    .baseUrl(genAIProperties.getUrl())
    .codecs(c -> c.defaultCodecs().maxInMemorySize(/* intended ceiling, e.g. 20 MB */))
    .build();
```

Pair the code change with a documentation correction so the GenAI page states the true ceiling. Open to alternatives on the exact byte limit - the point is that the configured limit and the documented limit must agree.
