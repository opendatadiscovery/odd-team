## What

`ReactiveDataEntityRelationshipRepositoryImpl.getRelationships` paginates the
relationship-class data_entity rows FIRST (a CTE page of `size` rows ordered by id,
filtered only by entity class + optional name + the 0.28.0 visibility trio) and applies
the `?type=ERD|GRAPH` filter AFTERWARDS, inside the INNER JOIN to `relationships`
(`RelationshipsType.ALL == type ? noCondition() : relationship_type = ...`). The count
query reuses only the CTE's condition list - it never sees the type filter.

Consequences for the ERD / GRAPH tabs (type != ALL):

1. **Pages under-fill.** A page window of 30 relationship entities is selected by id,
   THEN non-matching types are dropped - a page can return fewer than 30 rows (or zero)
   while more matching rows exist beyond the window. A zero-row window with
   `has_next: true` risks an infinite-scroll stall (react-infinite-scroll-component
   fires `next` on scroll; an empty page renders nothing to scroll).
2. **The H1 total over-counts.** `page_info.total` counts ALL visible relationship
   entities regardless of the selected tab - the ERD tab's "N relationships overall"
   badge includes every GRAPH relationship too.

## Where

```
odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/repository/reactive/ReactiveDataEntityRelationshipRepositoryImpl.java
  // homogeneousQuery (class+name+visibility, NO type) -> jooqQueryHelper.paginate(...)
  // -> join(relationships).on(... and type filter)   <- type drops rows AFTER the page window
  // -> count: selectCount.where(conditionList)        <- no type condition at all
```

## User-facing impact

NOT yet driven on a running system (static trace; probe P-248 pins the planned
observation). Expected: on a catalog where ERD and GRAPH relationships interleave in id
order, the ERD tab shows short/empty pages and a total that includes GRAPH rows. With
today's only relationship emitters being ERD-producing adapters (postgresql/snowflake),
most real catalogs are single-type and the defect is invisible - it surfaces the moment
graph relationships ship alongside ERD ones.

## Suggested fix

Move the type predicate into the paginated CTE (join `relationships` inside
`homogeneousQuery`, or EXISTS-semi-join on `relationships.data_entity_id +
relationship_type`) so the page window and the count both see the type filter. Same
class as the PLT-176 fan-out lesson: filters must constrain the paginated set, not the
post-page join.

## How discovered

The CTRIB-006 (#1752) ontology refresh re-derived the relationships route sidecar at the
fix branch tip; the file-analyser flagged that the new visibility trio narrows the CTE +
count consistently while the PRE-EXISTING type filter still sits join-side, outside both.
Deliberately excluded from the #1752 PR (G-C5 bounded diff; needs its own
pagination-correctness test design). Probe: lineage/odd-platform/probes/P-248.yaml.

## Live reproduction (2026-06-12, IT-128 ingestion-grade stand)

Measured on the first ingestion-grade e2e stand (real neo4j + postgres sources -> the
real odd-collector -> platform built from contrib/CTRIB-006-relationships-hardening
@ abe51417; integration-tests/protocols/IT-128-relationships-ingestion-pipeline.md) with
7 ingested relationship entities (5 GRAPH + 2 ERD):

```
GET /api/relationships?page=1&size=30&type=GRAPH -> items: 5, page_info.total: 7
GET /api/relationships?page=1&size=30&type=ERD   -> items: 2, page_info.total: 7
```

Both type-filtered reads report the ALL-types total. The trap also bit in practice: the
stand's first ingestion-wait predicate polled `total == 5` and timed out 180s while the
data had landed (run-log/2026-06-12-IT-128.md run 2); IT-128 now counts items and its
protocol documents the trap. UI consequence unchanged from the analysis above: the
ERD/GRAPH tab headline over-counts ("7 relationships overall" on a 5-row tab).
