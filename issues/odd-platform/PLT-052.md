## What

Four issues on the catalog-wide Data Quality Dashboard. The load-bearing user-facing defect is Defect 2 (a flagship-page semantic mislabel that misleads compliance reads); the others are a latent code-quality fragility and two filter-usability rough edges. Doc-side LSN-019 disclosure ships via DOC-203; code-side fixes are this PLT.

**Defect 1 - Non-optional palette lookup (latent; NOT a present page crash).** `DataQualityContent.tsx:47-48` - `palette.runStatus[status].color ?? palette.dataQualityDashboard.unknown`. `palette.runStatus` (`theme/palette.ts:122-129`) is keyed by exactly the SIX `DataEntityRunStatus` values; the `.color` (rather than `?.color`) would throw a TypeError BEFORE the `??` if `status` were ever outside those six. **But an out-of-enum status cannot reach this component in the shipped system** - verified 2026-06-10 by tracing the backend: the dashboard mapper coerces every unrecognised DB status string to `UNKNOWN` before serialisation (`DataQualityCategoryMapperImpl.java:35-37`, `EnumUtils.getEnum(DataEntityRunStatus.class, row.status(), DataEntityRunStatus.UNKNOWN)`), and `addMissingStatuses` (`:45-60`) guarantees exactly the six closed-enum statuses are returned; the OpenAPI contract enum (`DataEntityRunStatus.java`) and the generated FE type (`generated-sources/models/DataEntityRunStatus.ts:20-27`) are both closed to the same six. The only way to reach the throw is a FUTURE enum value added to the Java/OpenAPI enum AND the palette inconsistently - i.e. a coordinated schema change, at which point the palette is updated in the same change. This is a one-character defensive hardening (`?.color`), not a present-tense defect, and not the page-blanking crash an earlier revision claimed.

**Defect 2 - LSN-019 'test_results' counts TESTS by latest-run-status, NOT RUNS (the real user-facing defect).** Three layers agree on the wrong meaning: UI label, per-category total, OpenAPI op name, live docs verbatim "count of test runs broken down by status." SQL delivers per-TEST-by-latest-run: the dashboard query groups by `(category, DATA_ENTITY_TASK_LAST_RUN.STATUS)` and counts over `DATA_ENTITY_TASK_LAST_RUN` (`ReactiveDataQualityRunsRepositoryImpl.java:95-100`), whose `task_oddrn` PRIMARY KEY (`V0_0_45__last_runs_table.sql:9`) is one row per test. A test failing 100 times shows "1 failed" not "100 failed."

**Defect 3 - Autocomplete stuck EMPTY-STATE (not a spinner) on backend error.** `MultipleFilterItemAutocomplete.tsx:91-104` - stale-closure useEffect sets `optionsLoading=true` on open, sets it false only inside the `isSuccess` branch; dep array is `[searchText, autocompleteOpen]`, omitting `hookResult`. On a backend error `optionsLoading` strands `true`. Note (verified 2026-06-10): `optionsLoading` drives ONLY `noOptionsText={optionsLoading ? '' : 'No options'}` (`:162`); there is NO spinner element in the component. So the user-visible symptom is a dropdown that shows a BLANK no-options area forever instead of "No options" - a degraded empty-state, not a stuck spinner as an earlier revision claimed.

**Defect 4 - freesolo autocomplete accepts unresolvable typed value (LOW).** `MultipleFilterItemAutocomplete.tsx:166` sets `freeSolo`; `handleAutocompleteSelect` (`:48-55`) casts the typed string to `FilterOption` and calls `onSelectOption`, which pushes `{ name: searchText }` (no `.id`) into the selected set (`hooks/index.ts:29-36`). A chip APPEARS (keyed on the undefined `option.id`, `TagFilter.tsx:39`) but the filter request carries ids, so the typed value is ignored by the backend - verified 2026-06-10.

## User-facing impact

- **WHO:** a platform user (commonly a compliance / data-quality reviewer) on the catalog-wide Data Quality Dashboard (`/dataquality`), plus anyone using its filter sidebar.
- **WHAT they do / observe - Defect 2 (the load-bearing one):** they read the "Test Results Breakdown" donut + per-category totals as "how many test RUNS ended in each status," because the label, the OpenAPI op name, and the live docs all say "runs." What they actually see is "how many TESTS have their LATEST run in each status" - a test that failed 100 times contributes 1, not 100. Verified by BE trace 2026-06-10: `ReactiveDataQualityRunsRepositoryImpl.java:95-100` (groupBy over `DATA_ENTITY_TASK_LAST_RUN`) + `V0_0_45__last_runs_table.sql:9` (PK task_oddrn = one row per test). This is a confidently-wrong number on a flagship page; severity is carried by this defect.
- **Defect 1 - NOT user-observable today.** The dashboard does NOT blank on an unexpected status: the value cannot occur. Verified by BE/FE trace 2026-06-10: `DataQualityCategoryMapperImpl.java:35-37` coerces any unknown DB status to `UNKNOWN`; the contract + generated FE enum are closed to 6 values; `palette.runStatus` has all 6 keys (`theme/palette.ts:122-129`). No render path reaches the non-optional `.color` with an undefined key. (There is also no ErrorBoundary anywhere in the FE - verified by grep 2026-06-10 - so IF it ever threw it would indeed blank the route; but it cannot throw from data in the shipped system.)
- **Defect 3:** on a filter-options backend error the dropdown shows a BLANK no-options region (not "No options"), indefinitely - a confusing empty state, not a spinner. Verified by FE trace 2026-06-10 (`MultipleFilterItemAutocomplete.tsx:162` - `optionsLoading` has no other consumer).
- **Defect 4:** a typed-but-unmatched filter value shows a chip that does nothing to the results. Verified by FE trace 2026-06-10 (`hooks/index.ts:29-36`; chip keyed on undefined `option.id`).

## Why it matters

Defect 2 is **silent semantic misinformation** at the platform's flagship DQ landing - a compliance reviewer reading the wrong question gets a confidently-wrong answer, and it is true in the shipped system today. Defects 3+4 erode filter usability. Defect 1 is a latent code-quality hardening (non-optional property access guarded today by the BE `UNKNOWN` coercion and the closed enum) - worth fixing pre-emptively but not a present-tense failure.

Severity MEDIUM (was HIGH): the page-blanking crash that justified HIGH is not reachable in the shipped system (Defect 1 reclassified to latent); the remaining real user-facing defect is the Defect 2 semantic mislabel, which misleads but does not break the page.

## Suggested fix

**Defect 1 - pre-emptive defensive lookup (latent; low urgency):**
```tsx
- color: palette.runStatus[status].color ?? palette.dataQualityDashboard.unknown,
+ color: palette.runStatus[status]?.color ?? palette.dataQualityDashboard.unknown,
```
One-character optional-chain so a future enum addition that lands in the contract but not the palette degrades gracefully instead of throwing. (An app-level ErrorBoundary is a separate, broader hardening - the FE currently has none anywhere; out of scope for this DQ-specific item.) Not urgent: the BE `UNKNOWN` coercion + closed enum mean this cannot throw from data today.

**Defect 2 - LSN-019 alignment (Option B recommended):**
- Option A - rename label/operation/spec/doc to "Test Results - Latest Run by Status." Honest, no schema change.
- **Option B** - add a SECOND aggregation surface delivering true per-run counts (requires schema-tier event log).
- Option C - explicit doc disclosure (already shipping as DOC-203). Stop-gap.

**Defects 3+4 - autocomplete cleanup:**
```tsx
useEffect(() => {
  setOptionsLoading(hookResult.isFetching);
  if (hookResult.isSuccess) setOptions(...);
  if (hookResult.isError) setOptions([]);
}, [searchText, autocompleteOpen, hookResult.isSuccess, hookResult.isFetching, hookResult.isError]);
// + disable freeSolo for id-bound filter dimensions
```
