## Description

The live Business Glossary page (WebFetched 2026-05-27) covers the Overview + Linked Entities + Linked Columns + Linked Terms + Query Examples surfaces narratively but does not document the five-tab composition, the per-tab data-fetch contract, the discoverability of tabs for zero-count entities, OR the silent truncation behaviour on the Linked Columns tab. Four NET-NEW caveats clarify the per-tab UX gap.

**Caveat 7 — Term Detail Overview double-fetches the 12-JOIN hot path; every Term URL open hits the platform's most expensive query TWICE (F-151a).** `TermDetails.tsx:37-45` dispatches `fetchTermDetails({termId})` on mount via Redux thunk. The Overview sub-route (the default landing per `TermDetailsRoutes.tsx:46`) fires its own `useGetTermByID({termId})` via tanstack-query (`Overview.tsx:19-21`). Both endpoints route through `ReactiveTermRepositoryImpl.getTermDetailsDto` — the 12-JOIN + 7 jsonArrayAgg + 4 countDistinct HOT PATH (per F-002 batch-N). Every page open on a Term URL hits this query TWICE. Heavily-linked Terms with thousands of relations amplify the latency by 2× with no shared cache key in between. Operators tuning PostgreSQL for the platform see twice the load they would expect for the surface.

**Caveat 8 — Tabs auto-hide on zero count; new operators cannot tell whether linking is supported (F-151b).** `TermDetailsTabs.tsx:24, 30, 36` set `hidden: !termDetails?.entitiesUsingCount` (and equivalent for columns / terms). A Term with zero linked entities silently has NO "Linked entities" tab in the strip; the same for columns and terms. Operators new to ODD landing on a Term page with zero links cannot discover that linking IS supported — there is no signal until at least one link exists. The Query Examples tab is ALWAYS shown (no hidden gate), which is the correct discoverability shape; the three reverse-lookup tabs disagree.

**Caveat 9 — Overview TERMS mini-panel duplicates the Linked-Terms TAB with inconsistent affordances (F-151c).** The Term Overview tab carries a "TERMS" mini-panel showing linked terms inline with Add/Delete affordances (`Overview.tsx:65-72`). The Linked-Terms TAB (`TermLinkedTermsList.tsx:15-100`) shows the SAME linked terms in a paginated table — but with a search input, no Add affordance, and no Delete affordance. Same data, two surfaces, asymmetric affordances. Operators learn one affordance set on Overview and then can't perform Add/Delete in the tab where they'd reasonably look for bulk operations.

**Caveat 10 — TermLinkedColumnsList InfiniteScroll `next={() => {}}` — pagination silently broken; UI PROMISES more pages via `hasMore` but never advances (F-153a — LSN-024-class silent-empty applied to reverse-lookup pagination).** `LinkedColumnsList.tsx:77` wires `<InfiniteScroll next={() => {}}>`. The hook `useGetTermLinkedColumns` does not expose a `fetchNextPage` function — `LinkedColumnsList.tsx:22-27` calls it with single-page args `{termId, page: 1, size: 50, query}`. The fixed `size: 50` (line 16) caps the visible set. Worse: `hasMore={pageInfo.hasNext}` (line 78) is forwarded honestly — the UI tells the user "more available" via the spinner shape but the scroll trigger does NOTHING. A Term with 51+ linked Dataset Fields silently truncates at column 50; operators see the spinner appear briefly but the data never advances. Compare LinkedTermsList.tsx:24-31 (working pattern using `useInfiniteQuery` + `fetchNextPage`). For glossary-governance scenarios (compliance team auditing "what columns reference the term 'PII'?") the truncation IS the failure.
