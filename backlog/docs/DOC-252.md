## Description

The live `/features/management` Collectors section (WebFetched 2026-05-27, 200 OK) names the workflow phrases — "Issue a token before deploying a Collector; rotate a leaked token; remove a Collector that's been retired." It is **silent on token storage (plaintext-at-rest), no-grace rotation semantics, one-shot visibility UX, anonymous list-enumeration under DISABLED, and the default `auth.ingestion.filter.enabled: false` posture that nullifies rotation's security effect on the bulk-ingestion path**. Three load-bearing caveats need to land in one revision.

**Caveat 1 — UI-vs-API asymmetry under `auth.type=DISABLED` (F-020a).** Under DISABLED, `/api/identity` returns `permissions: []`; the UI's `WithPermissions` HOC universally HIDES Create/Edit/Delete/Regenerate-Token buttons (`CollectorsList/` components). An operator inspecting the UI infers "locked down." The backend `DisabledAuthSecurityConfiguration.java:11-19` uses `.anyExchange().permitAll()` — bypassing every `SECURITY_RULES` entry — and **accepts every request unauthenticated**. An attacker with network reach can mint new collectors, copy masked tokens via list-enumeration (last-6-chars leak — F-020 substrate UI-tier evidence), AND regenerate tokens forcing in-flight collectors to 401. This is the 19th surface of the REFACTOR-185 UI-vs-API asymmetry pattern.

**Caveat 2 — Collector token plaintext-at-rest; SQL match is plaintext equality; non-constant-time application equality (F-020b — security HIGH).** Tokens are stored verbatim plaintext in `TOKEN.VALUE` (`V0_0_28__add_token.sql:4` declares `value varchar(40) NOT NULL` with no hashing column, no UNIQUE). `TokenGeneratorImpl.java:34-42` writes `RandomStringUtils.randomAlphanumeric(40)` verbatim INSERT. Every DB-side reader (pg_dump, replica, backup, jOOQ log leak, application-log leak) recovers every live credential. Soft-deleted Collectors leave their TOKEN row orphaned (TOKEN has no `deleted_at` column; F-031 cross-link — DOC-255 Caveat 2 covers the DataSource sibling). Two TOKEN rows MAY share the same value (no UNIQUE on `VALUE`). `IngestionDataEntitiesFilter.java:55-58` does `tokenPojo.getValue().equals(token)` — non-constant-time, a timing oracle exists in principle. `ReactiveCollectorRepositoryImpl.java:94` does `TOKEN.VALUE.eq(token)` plaintext SQL equality. Operators with PgBackup pipelines / pgaudit ingestion / Datadog DB observability discover production collector credentials in their logs.

**Caveat 3 — Token rotation has no grace period AND no security effect on default deployments (F-020c).** `CollectorServiceImpl.regenerateToken` (lines 83-90) issues a single `UPDATE token SET value = ?, updated_at = ?` — overwrites the prior value in-place. In-flight collectors using the prior token start 401-ing IMMEDIATELY on the next ingestion call. Separately, `application.yml:48` carries `auth.ingestion.filter.enabled: false` as the default — `IngestionDataEntitiesFilter` is INACTIVE on `POST /ingestion/entities`. Rotating the token has **NO security effect** on the bulk-ingestion path under default config; it only affects `POST /ingestion/datasources` which the always-on `IngestionDataSourceFilter` still gates. Operators rotating a leaked token under default deployment fix only HALF the attack surface.
