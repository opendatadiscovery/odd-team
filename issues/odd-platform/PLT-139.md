## What

On a fresh boot, `NotificationSubscriber` creates the logical-replication **slot before the publication** (ADR-0044 lazy create-order: `registerReplicationSlot` then `registerPublication`). PostgreSQL's `pgoutput` logical decoding requires the publication to exist **as of the LSN being decoded**. If any WAL change lands at an LSN between slot-creation and publication-creation, the replication stream fails in the change callback with:

```
ERROR: publication "odd_platform_publication_alert" does not exist
  Where: slot "odd_platform_replication_slot", output plugin "pgoutput", in the change callback, associated LSN 0/19xxxxx
  at org.opendatadiscovery.oddplatform.notification.NotificationSubscriber.run(NotificationSubscriber.java:68)
```

The slot cannot advance past that LSN, so the subscriber **retries the same failing change forever** (`active=false` on the slot; no notifications delivered). Because there is **no DROP/recreate path** anywhere in `notification/` (ADR-0044 "lazy-create, no-drop"), a **container restart does NOT recover it** - the slot persists at the bad `restart_lsn` and re-wedges. Notifications are silently dead until an operator manually drops the slot.

This is **flaky / timing-dependent**: it triggers only when a WAL write occurs in the (sub-millisecond) window between slot- and publication-creation. On boots with no such write the chain works (an alert delivers to a webhook in ~4s). Observed both outcomes across fresh boots this session.

The create-order (slot call at :50 before publication call at :51) is the root cause; the no-DROP design (ADR-0044; zero DROP statements anywhere in `notification/`, grep-verified 2026-06-10) is why it is unrecoverable.

## User-facing impact

User: an operator who enabled notifications (`notifications.enabled=true` + wal_level=logical) and relies on alert delivery (Slack/webhook/email).

What they observably get: on an affected fresh boot/redeploy, **alerts silently stop being delivered cluster-wide** - the UI keeps working normally, alerts still appear in the UI, but no notification ever reaches a receiver; the only traces are a platform-log `ERROR: publication "odd_platform_publication_alert" does not exist` and `pg_replication_slots.active = false`. A container restart does not recover delivery. **Driven, not static** - runtime evidence on disk:

- `integration-tests/run-log/2026-06-02-feature-complete.md:36-43` - happy-path delivery works (~4s insert->webhook) on clean boots; the wedge reproduced on other fresh boots of the same stack; plain restart did NOT recover.
- `integration-tests/run-log/2026-06-02-feature-complete.md:45-52` - 2-replica stack: BOTH replicas wedged, `pg_locks` advisory granted count stayed 0 (lock flap), i.e. no stable leader and all alerting dead cluster-wide; standby never wedges (it blocks on the advisory lock before streaming); verified un-wedge recovery = stop leader -> `pg_drop_replication_slot` -> start (publication then pre-exists).
- `integration-tests/protocols/IT-011-notifications-wal-lifecycle.md:53-54,67` - the wedge signature documented as the manual check's known failure mode; IT-011 pins the deterministic slot/publication lifecycle instead of flaky delivery.

## Why it matters

Silent, permanent notification death on a fraction of fresh boots / redeploys - exactly the LSN-class failure ODD's quality bar exists to catch (operator follows the docs, enables notifications, and after some deploy they silently stop, with no error surfaced to the UI). The verified manual recovery is: stop the platform (or leader replica) -> `SELECT pg_drop_replication_slot('odd_platform_replication_slot')` -> start it again, so the publication pre-exists when the slot is recreated (run-log :51; a drop alone or a restart alone is not enough). Severity HIGH: it is reachable in any notifications-enabled deployment, intermittently, and self-perpetuating across restarts.

**Blast radius - it also destabilises leader election (multi-replica), confirmed 2026-06-02.** The subscriber loop is `while (...) { try (Connection c = leaderElectionManager.acquire(100, true)) { ... stream ... } }`. When the stream errors on the wedge, the try-with-resources **closes the connection - releasing the advisory lock** - then the loop re-acquires and re-errors. So a wedged leader does not hold the advisory lock stably; it *flaps* it. Observed on a 2-replica stack: both replicas wedged, `pg_replication_slots.active=false`, and `SELECT count(*) FROM pg_locks WHERE locktype='advisory' AND granted` stayed **0** - i.e. **no stable leader at all** -> no WAL consumer -> all alerting dead cluster-wide (not just one slot). This also blocks HA failover testing (IT-012) without first un-wedging a clean leader (drop slot + restart so the publication pre-exists). Fix option 1 (publication-before-slot) resolves both the single-node wedge and the leader-flap.

## Suggested fix

Any of (in order of preference):

1. **Create the publication BEFORE the replication slot.** If the publication exists when the slot is created, the slot's snapshot includes it and no change can be decoded against a catalog where it is absent. (Reorder `registerPublication` before `registerReplicationSlot` in `run()`.)
2. **Controlled recovery on the wedge:** catch the `publication does not exist` (SQLState 42704) on the stream and drop + recreate the slot once (a bounded, logged recovery - relaxing the strict no-drop for this provably-recoverable case). Pairs with the silent-thread-death detection (TEST-GAP-796).
3. Create both atomically / ensure no published-table writes between the two creations.

## How discovered

Building the I3 notifications-WAL integration test (`integration-tests/`, IT-011) on 2026-06-02. The happy-path (insert an alert -> WAL subscriber -> webhook stub) delivered reliably in some fresh boots (~4s) but on others the subscriber wedged with the error above; a platform restart did not recover it (`pg_replication_slots.active` stayed false). The deterministic ADR-0040/0044 lifecycle pin shipped instead (IT-011); this wedge is filed as the finding. Run-log: `integration-tests/run-log/2026-06-02-feature-complete.md`.

Re-verified 2026-06-10 (user-facing verification sweep): every code citation re-read against current `main` (8c142e15) - the create-order at `NotificationSubscriber.java:50-51`, the slot/publication registration bodies at `:104-126`/`:128-158`, the read-loop frame at `:68`, the config keys at `application.yml:177-179`, and the no-DROP absence (grep over `notification/`); the lock-flap mechanism matches the code structure (stream error -> generic catch at `:90-92` -> try-with-resources closes the raw `DriverManager` connection from `PGConnectionFactory.java`, ending the PG session and releasing the session-scoped advisory lock -> 10s sleep at `:94-100` -> re-acquire). All user-facing claims trace to the 2026-06-02 runtime artefacts cited under "User-facing impact"; nothing falsified.
