## Description

Two related attachment-storage inaccuracies, both on the data-loss / data-integrity hazard class that LSN-001 exists to catch:

1. **Architecture.md wrong default path.** The page states the LOCAL attachment-storage default is `./attachments/`. The shipped default is `/tmp/odd/attachments` — an **ephemeral** path that most container runtimes wipe on restart (LSN-001's exact failure mode: an attachment-storage default that silently loses data on container restart). The `./attachments/` string understates the hazard: a reader who sees a relative project-dir path does not infer "this is under `/tmp` and will be wiped."

2. **odd-platform.md `attachment.max-file-size` overclaim.** The config page presents `attachment.max-file-size` as a "max per uploaded file" server guard. The code reads it **only** into the UI's client-side file-picker filter — there is **no server-side re-validation**. A non-UI caller (or anyone bypassing the browser) can upload a file larger than `max-file-size`, up to the codec's hard ceiling. An operator who relies on this key as a server-enforced limit has no such limit.

Both are Critical: #1 is a data-loss caveat in a default deployment (top of the Priority Order); #2 is a security/robustness control an operator believes exists but does not.

**Failure shape**: code-doc drift on two surfaces, both in the LSN-001/002 "default with consequence" class.
