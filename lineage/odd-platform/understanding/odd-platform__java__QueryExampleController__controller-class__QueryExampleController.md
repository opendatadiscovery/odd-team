# QueryExampleController — semantic understanding

## understanding

`QueryExampleController` is the **HTTP controller-class for the entire Query Examples surface** (pillar P-02 Data Modelling per `system-mission.md:108-123`) — 125 lines, 13 endpoints implementing the OpenAPI-generated `QueryExampleApi` interface, each method a one-or-two-line reactive delegation to one of two injected services (`QueryExampleService` — 9 endpoints; `QueryExampleSearchService` — 4 endpoints). The class composes three resource axes of the query-example feature into a single API root at `/api/queryexample/**`: (a) **Query-example CRUD** (4 endpoints — list, create, get-details, update, delete); (b) **Read-by-relationship** (2 endpoints — by-dataset-id, by-term-id, providing the reverse-lookup from a data entity or term to its attached query examples); (c) **Faceted search session** (5 endpoints — create session, get/update facets, results, suggestions). **Authorisation surface is silently incomplete**: per `SecurityConstants.java` lines 112-113 + 312-317, only **3 of the 13 endpoints have SecurityRule entries** — `createQueryExamples` (`QUERY_EXAMPLE_CREATE` at line 112), `updateQueryExample` (`QUERY_EXAMPLE_UPDATE` at line 312-314), `deleteQueryExample` (`QUERY_EXAMPLE_DELETE` at line 315-317); the remaining 10 endpoints (all reads + all search-session endpoints) fall through to `AuthorizationCustomizer`'s catch-all `pathMatchers("/**").authenticated()` — read-collaborative posture by design per `system-mission.md:267`. **The 7-permission grid claimed by the docs** (verified via WebFetch 2026-05-20 of `https://docs.opendatadiscovery.org/features/data-modelling/query-examples` — `QUERY_EXAMPLE_CREATE / _UPDATE / _DELETE / _DATASET_CREATE / _DATASET_DELETE / _TERM_CREATE / _TERM_DELETE`) is split across THIS controller (the first three) and two sibling controllers — `DataEntityController` carries the dataset linkage permissions (`SecurityConstants.java:318-324`), `TermController` carries the term linkage permissions (`SecurityConstants.java:187-193`). **The query body is stored verbatim (`text NOT NULL` per `V0_0_84__create_query_example.sql:5`) AND rendered through `@uiw/react-md-editor`'s `MDEditor.Markdown` in TWO UI sites** (`QueryExampleDetailsOverview.tsx:25` for both definition and query; `QueryExamplesListItem.tsx:45-52` for the catalog table) — placing this controller as the **4th XSS surface in the F-004 family** (peer to `DataEntityController.upsertDataEntityInternalDescription`, `TermController.createTerm/updateTerm`, `DataEntityController.upsertDataEntityCustomMetadata`). **Delete is hard-delete-with-relation-cleanup**: `QueryExampleServiceImpl.deleteQueryExample` (lines 84-92) hard-deletes the data-entity link rows + term link rows BEFORE calling `queryExampleRepository.delete` which the soft-delete CRUD base translates to `UPDATE query_example SET deleted_at = NOW(), is_deleted = TRUE` per the `ReactiveAbstractSoftDeleteCRUDRepository` superclass (line 53 of `ReactiveQueryExampleRepositoryImpl.java`) — so the JOIN-table rows vanish permanently but the example itself tombstones with `deleted_at` populated. **No tests cover the controller class itself**; `QueryExampleServiceTest` covers `createQueryExample`, `createQueryExampleToDatasetRelationship` (a method NOT exposed by this controller — that endpoint lives on `DataEntityController.createQueryExampleToDatasetRelationshipNew`), `getQueryExampleDetails`, `deleteQueryExample`, and a `BadUserRequestException` duplicate-relation path — but the HTTP wiring is untested.

## downstream_side_effects

What this controller's endpoints cause to happen elsewhere — DB writes, FTS-vector updates, alert flow, activity-log emission, search-index changes.

- **PostgreSQL writes** (per endpoint that mutates):
  - `createQueryExamples` → `INSERT INTO query_example` (line 43 of service) + `INSERT INTO query_example_search_entrypoint` (the `updateQueryExampleVectors` call, service line 166-167)
  - `updateQueryExample` → `UPDATE query_example SET definition=..., query=..., updated_at=NOW()` (line 149 of service, via `update(pojo)`) + `INSERT/UPDATE INTO query_example_search_entrypoint` (search vectors re-derived from new definition + query, service line 166-167)
  - `deleteQueryExample` → 3-step transaction (lines 86-91 of service):
    - `DELETE FROM data_entity_to_query_example WHERE query_example_id = ?` (hard delete of link rows)
    - `DELETE FROM query_example_to_term WHERE query_example_id = ?` (hard delete of term link rows)
    - `UPDATE query_example SET deleted_at = NOW(), is_deleted = TRUE WHERE id = ?` (soft delete of the example itself, via the abstract soft-delete CRUD base)
    - **No DELETE of `query_example_search_entrypoint`** — FTS entrypoint row leaks (`bugs_limitations_corner_cases.[3]`)
  - The reads (`getQueryExampleByDatasetId / ByTermId / Details / List`) and the search endpoints (`queryExamplesSearch / getQueryExampleSearchFacetList / getQueryExampleSearchResults / getQueryExampleSearchSuggestions`) are all PostgreSQL reads. `queryExamplesSearch` additionally INSERTs into `search_facets` (the shared facet-session table — same one `SearchController.search` uses).
- **FTS-vector materialisation**: `updateQueryExampleVectors` is the side-effect of every create AND every update. The vector includes BOTH `definition` AND `query` (`V0_0_84__create_query_example.sql:30-33` — `query_example_vector` and `data_entity_vector` columns; the `data_entity_vector` is updated separately whenever the example's linked entities change).
- **Activity Feed emission**: **NONE** — this controller's operations do NOT emit Activity Feed entries (verified by reading the full `QueryExampleServiceImpl.java` — no `@ActivityLog` annotations). Compare with `TermServiceImpl` which DOES emit `TERM_ASSIGNMENT_UPDATED` activities on term linkage operations. The asymmetry is canonical to the audit-log-presence-asymmetry concept.
- **Search-facet-session lifecycle**: `queryExamplesSearch` creates a new `search_facets` row in PostgreSQL with the issued UUID; this row lives until the housekeeping job runs (`housekeeping.ttl.search_facets_days = 30` default per the F-010 housekeeping pillar feature). Subsequent calls to `getQueryExampleSearchFacetList / Results / updateQueryExampleSearchFacetList` mutate that row.
- **No outbound events**: nothing here triggers an alert (no `BACKWARDS_INCOMPATIBLE_SCHEMA` or `FAILED_DQ_TEST` flows are reachable from this controller), no Slack message, no notification, no webhook, no OpenTelemetry trace emission beyond Spring's default request span. The controller is pure CRUD.
- **No cascade to data entities or terms**: deleting a query example does NOT delete the data entities it was attached to (`removeRelationWithDataEntityByQueryId` deletes ONLY rows in `data_entity_to_query_example`, not `data_entity` itself). Conversely, deleting a data entity via `dataEntityService.delete` does NOT cascade to its query examples — the `data_entity_to_query_example` table has FK constraints to both `data_entity` and `query_example` but no `ON DELETE CASCADE` (verified by `V0_0_84__create_query_example.sql:18-22`). Orphan link rows (FK still pointing at a soft-deleted DataEntity) are a real possibility — see `bugs_limitations_corner_cases.[5]`.

## performance

- **hot_paths**:
  - "`getQueryExampleDetails` (line 66) — three sequential DB round-trips: (1) fetch QueryExamplePojo, (2) fetch the dataset-relations DTO with 4 jsonArrayAgg JOINs (`ReactiveDataEntityQueryExampleRelationRepositoryImpl.java:75-87`), (3) fetch DataEntityDimensions for each linked entity via `DataEntityService.getDimensionsByIds`. The 3rd step's depth is unbounded by query-example's API — bounded by the number of dataset linkages. Operators who attach a query example to dozens of datasets see proportional latency."
  - "`getQueryExampleByDatasetId` and `getQueryExampleByTermId` (lines 52, 59) — single-query 5-jsonArrayAgg JOIN (`ReactiveDataEntityQueryExampleRelationRepositoryImpl.java:75-87`). Returns ALL query examples linked to the entity in one fetch; for a popular entity with many query examples this is O(N) over the example count."
  - "`getQueryExampleSearchSuggestions` (line 119) — FTS-ranked query against `query_example_search_entrypoint.search_vector` via the GIN index `query_example_search_entrypoint_search_vector_idx` (`V0_0_84__create_query_example.sql:38-39`); FTS is fast but the index size grows with the search-vector text + entrypoint row leak (see `bugs_limitations_corner_cases.[3]`)."
- **throughput_characteristics**:
  - "All 13 endpoints are reactive `Mono<ResponseEntity<...>>` — non-blocking but each makes ≥1 DB round-trip"
  - "Create + update each make 2 round-trips: 1 for the primary INSERT/UPDATE + 1 for the search-vector update (`QueryExampleServiceImpl.java:166-167`)"
  - "Delete makes 3 round-trips: 2 hard-deletes for link rows + 1 soft-delete for the example itself"
  - "No batch endpoints — every mutation is per-example"
- **resource_allocation**:
  - "No outbound HTTP — controller is pure DB-driven"
  - "PostgreSQL connection per request via R2DBC reactive pool"
  - "Search session creates a row in `search_facets` (consumed by other catalog search sessions too) — shared resource with other faceted-search surfaces"
- **scaling_characteristics**:
  - "Stateless controller — instances scale horizontally"
  - "**No pagination on the by-dataset and by-term endpoints** — `getQueryExampleByDatasetId` and `getQueryExampleByTermId` return ALL query examples for an entity in a single response (`QueryExampleMapper.mapListToQueryExampleList` line 72-74 hard-codes `hasNext=false`, `total=items.size()`). If a single dataset accumulates thousands of query examples, response time degrades O(N)."
  - "**No FTS-index size cap** — the GIN index `query_example_search_entrypoint_search_vector_idx` grows unboundedly with create + update operations and is NEVER cleaned up on delete (see `bugs_limitations_corner_cases.[3]`)."
- **known_performance_gaps**:
  - "by-dataset / by-term endpoints are unbounded — no pagination. Real-world risk: a heavily-curated dataset accumulates dozens of query examples; the per-entity tab response time degrades. — evidence: QueryExampleController.java:52-56, 59-63 + QueryExampleMapper.java:72-74 — severity: MEDIUM"
  - "Search-entrypoint table grows unboundedly — no housekeeping job, no DELETE on query-example delete. — evidence: QueryExampleServiceImpl.java:84-92 + the absence of `QueryExampleSearchEntrypointHousekeepingJob` — severity: MEDIUM (slow storage leak)"
  - "FTS index over `definition + query` text combination — for a 1MB query body, the search vector is sizeable; GIN-index insert latency scales with text length. No documented upper bound. — evidence: V0_0_84__create_query_example.sql:30-39 — severity: LOW"
  - "`getQueryExampleDetails` fan-out to `DataEntityService.getDimensionsByIds` is unbounded — for a query example attached to 50 datasets, the response returns 50 full DataEntityDimensionsDto payloads (each with its own JSON projection). — evidence: QueryExampleServiceImpl.java:107-111 + DataEntityServiceImpl `getDimensionsByIds` — severity: LOW (rare in practice)"
