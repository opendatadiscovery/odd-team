## Description

`data-discovery/groups-domains.md` inverts the platform's class-vs-type taxonomy in two places:

1. **"What a DEG is"** says: *"A DEG is itself a Data Entity (of type `DATA_ENTITY_GROUP`)…"* — wrong. `DATA_ENTITY_GROUP` is a **class** (id 8 in `DataEntityClassDto`, DataEntityClassDto.java:50), not a type.
2. **"ML experiments"** says: *"an **ML experiment** is a Data Entity Group of class `ML_EXPERIMENT`…"* — wrong. `ML_EXPERIMENT` is a **type** (id 6 in `DataEntityTypeDto`, DataEntityTypeDto.java:20), and it is one of the member types *of* the `DATA_ENTITY_GROUP` class (DataEntityClassDto.java:50 lists `ML_EXPERIMENT` in the `DATA_ENTITY_GROUP` type set).

The correct framing: **a DEG is a Data Entity of CLASS `DATA_ENTITY_GROUP`; an ML experiment is a DEG whose TYPE is `ML_EXPERIMENT`** (i.e. class `DATA_ENTITY_GROUP`, type `ML_EXPERIMENT`).

This is not a cosmetic naming slip — it actively undercuts the platform's documented mental model. `entity-detail-page.md:85` states the load-bearing rule: *"Class is the load-bearing taxonomy; type is descriptive. The class array drives every per-class composition decision on the page… The type is a finer-grained descriptive label…"* The groups-domains page tells the operator the opposite about the very same two identifiers, so an operator reading both pages gets contradictory definitions of what "class" and "type" mean, and may try to filter / reason about DEGs by the wrong axis.
