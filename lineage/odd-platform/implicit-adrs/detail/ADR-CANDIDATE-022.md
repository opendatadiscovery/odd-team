- **ADR-CANDIDATE-022** (NEW 2026-05-10A): View-modes for activity streams are encoded as a single `type` enum parameter (ALL / MY_OBJECTS / DOWNSTREAM / UPSTREAM) dispatching at the service layer — NOT as separate endpoints (`/api/activity/mine`, `/api/activity/upstream`)
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar (`getActivity`) but cross-validated by the contrasting pattern at `DataEntityController` (ADR-CANDIDATE-015) which uses **separate** endpoints (`/my`, `/my/upstream`, `/my/downstream`) for the same conceptual problem space. The two patterns are deliberately divergent for the same maintainer.
  - **Surfaced by**:
    - `odd-platform__java__ActivityController__controller-method__getActivity.md:implicit_adrs.[2]` ("The four `ActivityType` enum values (ALL / MY_OBJECTS / DOWNSTREAM / UPSTREAM) encode UI-driven view modes as a server-side dispatch parameter rather than as separate endpoints (e.g. `/api/activity/mine`, `/api/activity/upstream`). The controller method signature, the service `getActivityList` switch (ActivityServiceImpl.java:107-117), and the components.yaml enum (components.yaml:3159-3166) all model this as a single parameterised endpoint." — intent_anchor: "The `switch (type)` block exhausts the four enum members on a single method — the type is the dispatch parameter; separating into endpoints would have required four interface methods.")
  - **Decision statement**: Activity-feed view-modes are encoded as a single `type` enum parameter on `GET /api/activity` rather than as separate endpoints. The four enum values (ALL / MY_OBJECTS / DOWNSTREAM / UPSTREAM) dispatch at the service layer (`ActivityServiceImpl.getActivityList` switch at lines 107-117) to four method bodies (`fetchAllActivities`, `fetchMyActivities`, `fetchDependentActivities` × 2). Trade-off: single endpoint reduces interface surface but couples the view-mode dimension to a dispatch parameter that callers must know about; the parameter is undocumented on the live activity-feed feature page. Note the deliberate divergence with ADR-CANDIDATE-015 (DataEntityController owner-scoped reads) — that pattern uses **separate** endpoints (`/my`, `/my/upstream`, `/my/downstream`) for the structurally-similar problem. The maintainer chose differently for activity vs. data-entity-listing — unclear whether this is a posture difference or one of the two patterns is the canonical-and-the-other-is-legacy.
  - **Wisdom test**: PASS. Deliberate (the explicit enum + switch construction is a positive choice); structural (every future view-mode addition must extend the enum or break the contract). The contrast with ADR-CANDIDATE-015 sharpens the wisdom-test answer: this is a deliberate divergence within a maintainer's own work, not an oversight.
  - **Evidence**:
    - getActivity.md says: "ActivityController.java:32 (`final ActivityType type`) + ActivityServiceImpl.java:107-117 (the four-arm `switch (type)`) + components.yaml:3159-3166 (the closed enum)"
  - **Existing ADR**: none.
  - **Co-surfaced gaps** (link from `refactoring-scopes.md`): REFACTOR-059 (Activity `type=null` and `type=ALL` both route to `fetchAllActivities` via separate branches — defence-in-depth gap that a future refactor adding owner-scoping to one branch would silently bypass via the other).
  - **Proposed action**: Promote to `adrs/drafts/view-modes-as-single-parameter.md` (new ADR), explicitly cross-referencing ADR-CANDIDATE-015 as the contrasting "view-modes-as-separate-endpoints" pattern for owner-scoped listings. The maintainer's triage decision is: (a) commit to the enum-dispatch as the platform's preferred shape and refactor `/my*` to `?owner=me`-style; (b) commit to the separate-endpoints as the platform's preferred shape and refactor `getActivity` to `/api/activity/mine` etc; (c) accept that activity-streams use parameter-dispatch and entity-listings use separate-endpoints, and codify the rule. Doc-side: the live activity-feed page should document the four view-modes (currently omitted).
  - **Severity rationale**: MEDIUM — API-shape decision; sets the convention for every future view-mode feature on the platform.
