## What

Two defects on the attachment subsystem ship together - one is a multi-tenant authorization escalation (high security), one is a deployment-defaults gap that forces operators on EKS/IRSA into a credential-hygiene anti-pattern.

**Defect 1 - three `DataEntityAttachmentController` mutation endpoints discard the URL's `data_entity_id`; a user with `DATA_ENTITY_ATTACHMENT_MANAGE` on entity A mutates entity B's file/link by id (HIGH security).** The auth gate is scoped per-entity: each mutation rule uses the `DATA_ENTITY` resolver against the path's `{data_entity_id}` (`SecurityConstants.java:247-275`), so the gate evaluates the caller's `DATA_ENTITY_ATTACHMENT_MANAGE` *on entity A* (the URL entity). But the controller methods then operate on `fileId` / `linkId` only and discard `dataEntityId`. The three affected endpoints (verified against the generated contract + service):

- `DELETE /api/dataentities/{data_entity_id}/files/{file_id}` -> `attachmentService.deleteFile(fileId)` (`DataEntityAttachmentController.java:82-88` -> `AttachmentServiceImpl.java:86-88`)
- `PUT    /api/dataentities/{data_entity_id}/links/{link_id}` -> `attachmentService.updateLink(linkId, fd)` (`:100-107` -> `:50-52`)
- `DELETE /api/dataentities/{data_entity_id}/links/{link_id}` -> `attachmentService.deleteLink(linkId)` (`:110-115` -> `:55-57`)

A holder of `DATA_ENTITY_ATTACHMENT_MANAGE` on entity A issues `DELETE /api/dataentities/{A_id}/files/{B_file_id}` - the gate sees A (allowed), the delete acts on B's file. No service-tier check asserts the file/link belongs to the URL entity. Combined with the READ endpoints carrying NO `SecurityRule` (the GET rules are absent - `getAttachments` and `downloadFile` fall through to `.authenticated()`; `downloadFile` is itself a cross-entity read by `fileId`), the cross-entity scope is operator-invisible. **Multi-tenant deployments lose attachment isolation by default.**

(Correction from the draft's first revision: the URL has no `/attachments/` segment - the real paths are `/files/{file_id}` and `/links/{link_id}`; and it is NOT "7 mutation endpoints" - only these THREE discard the id. The upload endpoints `initiateFileUpload`/`saveLinks` correctly pass `dataEntityId` to the service, and the chunk/complete endpoints operate on a `uploadId` scope. See How discovered.)

**Defect 2 - `MinioConfig` builder leaves three parameters unset (this is the LSN-002 minio-region class).** Per Gate-5 unset-parameter audit on `MinioAsyncClient.builder()` (`MinioConfig.java:19-25`, verified verbatim). Note the bean is `@ConditionalOnProperty("attachment.storage" == "REMOTE")` (`:10`) and the shipped default is `attachment.storage: LOCAL` (`application.yml:216`), so these only bite a REMOTE deployment:
- `.endpoint(url)` configured (ok)
- `.credentials(accessKey, secretKey)` configured (ok)
- `.region(...)` UNSET - SDK defaults to `us-east-1`; there is no in-code fail-fast at `@PostConstruct`; no `attachment.remote.region` config key in the codebase (grep returns zero matches - the `attachment.remote` block has only `url`/`access-key`/`secret-key`/`bucket`, `application.yml:219-224`). This is exactly the LSN-002 case (`retrospectives/LSN-002-minio-region-unset.md`).
- `.httpClient(...)` UNSET - SDK uses its default HTTP client with default timeouts; a slow S3 endpoint stalls the upload without an operator-tunable hook. (The draft's "~10s" figure is not verified - the MinIO client's defaults are not 10s; stated here only as "SDK default timeouts" to avoid an unverified number.)
- `.credentialsProvider(...)` UNSET - **no IAM-role support**; operators on EKS with IRSA, or any AWS-native deployment expecting a `DefaultCredentialsProvider` chain, MUST provide static access-key/secret-key in `application.yml` / Helm secrets, which is itself a credential-hygiene gap.

## User-facing impact

**Defect 1 (cross-entity attachment mutation):** verified-trace, code-settled wiring. The escalation chain is real and tight: the SecurityRule binds the gate to the URL's `{data_entity_id}` via the `DATA_ENTITY` resolver (`SecurityConstants.java:247-275`), and the controller+service then act on `fileId`/`linkId` with zero entity-scope check (`DataEntityAttachmentController.java:82-115` -> `AttachmentServiceImpl.java:50-57,86-88`). **Auth-mode dependency:** the *observable* escalation requires a non-DISABLED auth mode where `DATA_ENTITY_ATTACHMENT_MANAGE` is actually evaluated per-entity (LDAP gives per-user roles locally). Under the shipped default `auth.type=DISABLED` (`application.yml:34`) every request is permitAll so there is no "A vs B" distinction - the cross-entity write is just one facet of full anonymous write. The *wiring defect* (gate on A, mutate B) is fully code-settled regardless of mode. Not driven on a running multi-tenant stack; the remaining check is an authz integration test under LDAP proving the B-file delete succeeds with only A-scoped grant.

**Defect 2 (MinioConfig unset params):** code-settled, REMOTE-only. The three unset builder calls are verbatim in `MinioConfig.java:21-24`; there is no `region` config key (grep zero). No user-facing UI surface - this is a deployment-correctness defect that manifests as (a) wrong-region S3 failures (LSN-002), (b) no IRSA/IAM-role auth, (c) untunable timeouts. Only active when `attachment.storage=REMOTE` (default is `LOCAL`).

## Why it matters

**Defect 1**: Multi-tenant deployments (different teams ingesting into different namespaces, each owning their data entities) discover the cross-entity bypass only when an attacker proves it. The auth model says "per-entity ownership" - the implementation says "any authenticated user with the permission on any entity, anywhere." This is the operator-trust-failure class - operators following ODD's RBAC documentation believe they have per-entity isolation; they do not.

**Defect 2**: AWS-native deployments (EKS + IRSA is the modern AWS Kubernetes pattern) cannot use IAM-role auth; operators must provision static IAM keys in Helm secrets, rotate them manually, and accept the credential-hygiene burden. The platform's documented S3 support is "works with static credentials only" - not what operators expect from a 2024+ AWS deployment.

Severity HIGH because:
- Defect 1 is a security defect class (silent multi-tenant cross-contamination)
- Defect 2 forces operator-side credential-hygiene anti-patterns on the most common modern AWS pattern (IRSA)

## Suggested fix

### Defect 1 - assert dataEntityId matches at the mutation entry point

```java
// DataEntityAttachmentController.java (each of 7 mutation methods)
public Mono<...> deleteFile(
    @PathVariable("data_entity_id") long dataEntityId,
    @PathVariable("file_id") long fileId,
    ...) {
  return attachmentService.assertFileBelongsToEntity(fileId, dataEntityId)   // <- NEW guard
      .then(attachmentService.delete(fileId));
}
```

Service-tier helper:

```java
public Mono<Void> assertFileBelongsToEntity(long fileId, long entityId) {
  return fileRepository.getById(fileId)
      .filter(file -> file.getDataEntityId().equals(entityId))
      .switchIfEmpty(Mono.error(new ForbiddenException("file does not belong to entity " + entityId)))
      .then();
}
```

Apply to the three by-id mutation endpoints (`deleteFile`, `updateLink`, `deleteLink`); for links use an `assertLinkBelongsToEntity` analogue. Read endpoints (`getAttachments`, `downloadFile`) get their own treatment under the broader DOC-GAP-082 META read-posture decision (separate PLT if ever filed).

### Defect 2 - add the three missing builder calls

```java
// MinioConfig.java
public MinioAsyncClient client() {
    final MinioAsyncClient.Builder builder = MinioAsyncClient.builder()
        .endpoint(properties.getRemote().getUrl())
        .region(Optional.ofNullable(properties.getRemote().getRegion())
                        .orElse("us-east-1"));    // <- explicit default; doc-side warns

    // credentials: static keys OR DefaultCredentialsProvider for IAM-role flow
    if (properties.getRemote().getAccessKey() != null) {
        builder.credentials(
            properties.getRemote().getAccessKey(),
            properties.getRemote().getSecretKey());
    } else {
        // empty keys -> assume EKS/IRSA / EC2 instance profile / ECS task role
        builder.credentialsProvider(DefaultCredentialsProvider.create());
    }

    // operator-tunable HTTP timeouts
    if (properties.getRemote().getTimeout() != null) {
        builder.httpClient(buildHttpClientWithTimeouts(properties.getRemote().getTimeout()));
    }

    final MinioAsyncClient client = builder.build();

    // fail-fast: if endpoint is AWS S3 AND region not explicitly set, log loud warning
    if (isAwsEndpoint(properties.getRemote().getUrl())
            && properties.getRemote().getRegion() == null) {
        log.warn("MinioConfig: AWS S3 endpoint with no explicit region - using us-east-1");
    }

    return client;
}
```

Add `attachment.remote.region`, `attachment.remote.timeout-ms` to `AttachmentRemoteProperties`. Defaults preserve back-compat (region defaults to us-east-1, timeout defaults to SDK defaults, credentials default to static keys if supplied).

## How discovered

Mode B run of `docs/coverage/undocumented-features` on 2026-05-27 (substrate `F-027` - Attachment Lifecycle).

Corrected 2026-06-10 (user-facing verification sweep):
- Defect 1 was "7 mutation endpoints, URL `/api/dataentities/{id}/attachments/files/{file_id}`"; actually only THREE endpoints discard the entity id (`deleteFile`, `updateLink`, `deleteLink`) and the URL has no `/attachments/` segment - real paths `/files/{file_id}` and `/links/{link_id}` (verified against the generated `DataEntityAttachmentApi` + `AttachmentServiceImpl`). The upload endpoints (`initiateFileUpload`, `saveLinks`) DO pass `dataEntityId` to the service; chunk/complete operate on `uploadId`. The escalation survives, re-scoped to the three by-id mutations (plus `downloadFile` as a cross-entity GET). The auth gate uses the `DATA_ENTITY` resolver scoped to the URL entity (`SecurityConstants:247-275`), which is exactly what makes "gate on A, mutate B" possible - confirmed.
- Defect 2's "Where" code block invented a `properties.getRemote().getUrl()` accessor; the real `MinioConfig` uses `@Value`-injected `url`/`accessKey`/`secretKey` fields (`:12-17`) and builds with `.endpoint(url).credentials(accessKey, secretKey)` (`:21-23`). The three-unset-params finding is unchanged and is the LSN-002 class. The "~10s" default-timeout figure was unverified and has been softened.
- `user_facing_verified` false -> true: all wiring claims are code-settled (controller/service/SecurityRule traced). The only runtime-only aspect is *observing* the escalation, which needs a non-DISABLED auth mode (logged in User-facing impact).
