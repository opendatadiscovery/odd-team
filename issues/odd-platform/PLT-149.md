## What

`GET /api/integrations/{integration_id}` for an **unknown** id returns **HTTP 200 with a zero-length body** — not 404, and not the 204 the ontology / earlier static analysis had recorded. Verified live (2026-06-07, `:latest` image):

```
$ curl -s -D - -o /dev/null http://localhost:18080/api/integrations/this-does-not-exist
HTTP/1.1 200 OK
content-length: 0
```

(A known id at the same endpoint returns 200 + a ~3.3 KB JSON `Integration` body.)

Root cause: the registry lookup returns an empty reactive stream on a miss, and the controller maps it with `.map(ResponseEntity::ok)` — which is **never invoked** on an empty `Mono`, so Spring WebFlux completes the exchange with a default empty 200 (no `switchIfEmpty(...)` to translate the miss into a `NotFoundException`/404). Compare `MetadataFieldServiceImpl.get`, which DOES `switchIfEmpty(Mono.error(new NotFoundException(...)))` on a missing id.

Two consequences:

1. **No 404 for a missing resource.** A client cannot distinguish "integration does not exist" from "integration exists but has an empty body" by status code; the existence oracle is a 200-with-empty-body, which most generated SDK clients will try to deserialize as an `Integration` and fail (or yield a null object) rather than handle as a not-found.
2. **Contract drift.** `openapi.yaml` for `getIntegration` declares only a `200` response (schema `Integration`). It documents **neither** the empty-body 200 that actually ships **nor** the `404`/`204` a reader would expect. (Note: prior static analysis recorded this as a `204`; the live behaviour is a 200-empty — the spec and the analysis are both wrong about the wire.)

## Where

```
controller/IntegrationController.java:19-22
  getIntegration(): integrationService.get(integrationId).map(ResponseEntity::ok)
  — no switchIfEmpty; empty Mono -> default empty 200

integration/service/IntegrationServiceImpl.java (get)
  -> integrationRegistry.get(id) ... (Mono.empty on miss; no error mapping)

integration/.../ResourceFilesIntegrationRegistry.java:15-17
  get(): Mono.justOrEmpty(registry.get(id))   — source of the empty Mono

contract: openapi.yaml (getIntegration) — declares only 200; no 404, no 204, no empty-body note

contrast (correct pattern): service/MetadataFieldServiceImpl.get — switchIfEmpty(Mono.error(new NotFoundException(...)))
```

## Why it matters

`/api/integrations/{id}` is a public, anonymously-reachable surface (under `auth.type=DISABLED` it is reachable with no credential at all). A 200-with-empty-body on a missing id is a contract trap for every API consumer and SDK generator: status-code-driven error handling sees "success", body-driven deserialization sees garbage/null. It also makes the wizard's free-form `String integrationId` path parameter a silent enumeration oracle (200-empty vs 200-body) with no logging. The fix is small and local (add `switchIfEmpty(Mono.error(new NotFoundException("Integration", id)))` in the service or registry-get, and declare the `404` in `openapi.yaml`).

## Proposed fix

1. Add `switchIfEmpty(Mono.error(new NotFoundException("Integration", integrationId)))` to `IntegrationServiceImpl.get` (or `ResourceFilesIntegrationRegistry.get`), mirroring `MetadataFieldServiceImpl.get`.
2. Declare the `404` response on `getIntegration` in `openapi.yaml` (and remove any stale 204 expectation).
3. Regression guard already exists: **IT-098 UC-04** (`integration-tests/e2e/specs/integration-wizard-manifests.spec.ts`) is an LSN-029 characterization pin asserting the CURRENT 200-empty behaviour; it **flips RED the moment the 404 ships** — at which point update the pin to assert the corrected 404 and move it to the green lane.
