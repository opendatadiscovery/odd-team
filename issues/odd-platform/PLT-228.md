## What

`S2sAuthenticationFilter` is a `@Component implements WebFilter` with no `@ConditionalOnProperty`, so Spring
WebFlux auto-registers it into the global filter chain and it runs on every request under every auth mode -
including `auth.type=DISABLED` where s2s is off. The optional hardening (raised in issue #1765 as "a deeper,
optional hardening") is to gate the filter's registration on `auth.s2s.enabled` so it does not run at all when
s2s is disabled - removing the per-request work and the surface entirely when the feature is off.

This is the deliberately-excluded second half of PLT-001 / CTRIB-022. The PLT-001 crash itself
(`S2sTokenProvider.isValidToken` NPE -> unauthenticated 500/DoS on the default) is FIXED by CTRIB-022's
null-guard; after that fix the filter is a harmless pass-through, so this item is a low-priority cleanup, NOT a
crash fix.

## Why it is NOT a trivial change (needs an ADR first)

`S2sTokenProvider.isValidToken` and `S2sAuthenticationFilter` today never check `s2sEnabled` - activation is
purely "is a token configured". The `auth.s2s.enabled` flag's ONLY current effect is the `@PostConstruct`
startup validation (fail fast if enabled=true but no token). So:

- A deployment with `auth.s2s.token=<set>` but `auth.s2s.enabled=false` (or unset) currently HAS working s2s
  auth (the token is accepted).
- Gating the filter on `@ConditionalOnProperty("auth.s2s.enabled", havingValue="true")` would SILENTLY DISABLE
  s2s auth for that deployment - a behaviour/contract change, not a pure addition.

Because it changes the meaning of `auth.s2s.enabled` (and touches a security component's registration), this is
a security-posture change: it warrants a short ADR deciding the intended `enabled` semantics (does a configured
token alone activate s2s, or must `enabled=true` be set?) before any code (contributor pillar G-C7).

## Suggested approach

1. ADR: define `auth.s2s` activation semantics (recommended: `enabled=true` is required to activate; a token
   without `enabled` is a misconfiguration warned at startup). Document the migration note for any deployment
   relying on token-without-enabled.
2. Gate the filter (`@ConditionalOnProperty`) and/or short-circuit `isValidToken`/the filter on `!s2sEnabled`
   per the ADR.
3. Tests: a `@WebFluxTest`/slice asserting the filter is inert when `enabled=false`; the existing IT-112
   (DISABLED, unconfigured) stays green; add coverage for `enabled=true` + token.

## How discovered

Scope exclusion recorded during CTRIB-022 (the PLT-001 null-guard, issue #1765). The null-guard fully closes the
reported DoS; this hardening is the issue's explicitly-"optional" deeper change, deferred here so the
enabled-flag semantics get a proper decision rather than a silent contract change bundled into a hotfix.
