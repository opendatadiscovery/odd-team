## What

When ODD resolves the currently-authenticated principal to its associated Owner, it keys the lookup on `(username, provider)` - but it only ever supplies a real `provider` value for **OAuth2** logins. For **every other authentication mode** (LOGIN_FORM, LDAP, and the DISABLED/S2S synthetic principals), the resolver emits `provider = null`. As a result, two genuinely different people who happen to share the same username across different non-OAuth2 modes - for example a LOGIN_FORM user `alice` and an LDAP user `alice` - both resolve to the **same** `(alice, null)` Owner row. The Owner association (and everything scoped by it: owner-scoped reads, "my objects", attribution) silently collapses across auth modes. This is a silent cross-mode identity takeover: one person inherits the other's Owner binding with no warning, no error, and no audit signal.

This is the identical defect tracked by **PLT-120** (resolver root-cause, same fix-site `AuthIdentityProviderImpl.java:29-33`/`:32`, same F-011 H-001 origin). See the REJECT-CANDIDATE note above.

## Where

`odd-platform-api/src/main/java/.../auth/AuthIdentityProviderImpl.java:29-33` - only OAuth2 carries a provider discriminator; all other modes get `null`:

```java
if (authentication instanceof OAuth2AuthenticationToken oauthToken) {
    return new UserDto(username, oauthToken.getAuthorizedClientRegistrationId());
} else {
    return new UserDto(username, null);     // LOGIN_FORM, LDAP, DISABLED, S2S -> provider == null
}
```

Same file, the resolver that keys on that `(username, provider)` pair:

```java
public Mono<OwnerPojo> fetchAssociatedOwner() {
    return getCurrentUser()
        .flatMap(user -> userOwnerMappingRepository.getAssociatedOwner(user.username(), user.provider()));
}
```

Because `provider` is `null` for all non-OAuth2 modes, `getAssociatedOwner(username, null)` cannot distinguish a LOGIN_FORM `alice` from an LDAP `alice` - they map to the same Owner. The SQL mechanism is in `ReactiveUserOwnerMappingRepositoryImpl.getConditions` (`:116-127`, verified 2026-06-10): when the provider is empty it adds `USER_OWNER_MAPPING.PROVIDER.isNull()` (an if/else, not an `OR`), so every non-OAuth2 lookup resolves on `OIDC_USERNAME=? AND PROVIDER IS NULL`. (PLT-120 carries this same `getConditions` evidence plus the Postgres NULL-distinct unique-index nuance and the `IdentityServiceImpl` whoami angle, which this draft omits.)

## Why it matters

Owner association is an authorization-relevant boundary: it scopes "my objects" views, owner-filtered reads, and attribution of who did what. Collapsing two distinct human identities onto one Owner because they share a username in two different auth backends is a silent security/identity defect - it is materially a cross-mode takeover under a username overlap, with no log line and no fail-fast. It is most likely to bite a deployment that runs (or migrates between) more than one auth mode, or one that imports LDAP users alongside existing LOGIN_FORM users. The collapse is invisible until someone notices they can see, or are credited with, another user's owner-scoped data. Severity is medium: it requires a username collision across modes to trigger, but when it triggers it is an unannounced identity boundary breach at the resolution root.

## Suggested fix

Carry a real, non-null provider discriminator for LOGIN_FORM and LDAP (and define an explicit sentinel for the S2S/DISABLED synthetic principals) so that `(username, provider)` is unique per real identity source. Concretely: in `AuthIdentityProviderImpl.getCurrentUser`, derive the provider from the authentication type (e.g. `LOGIN_FORM`, `LDAP`, the OAuth2 registration id for OAuth2, and a reserved literal for S2S) instead of falling through to `null`; mirror the column on `USER_OWNER_MAPPING` and in `getAssociatedOwner` so the lookup discriminates by mode. A migration/runbook will be needed to backfill the provider column for existing `provider = null` mappings. Open to alternatives on the exact provider vocabulary.
