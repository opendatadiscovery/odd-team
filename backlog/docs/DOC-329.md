## Description

Multiple service-tier update paths are non-transactional read-then-write or full-replace PUTs with no optimistic-lock detection, so concurrent edits silently lose updates. Where a sibling service IS `@ReactiveTransactional`, the asymmetry is the oversight. Confirmed across features by the feature-reflection pass:

- **RBAC (F-006/H-007, F-006/H-011)** — `PolicyServiceImpl.update` is a non-transactional read-then-write (lost-update race); sibling `RoleServiceImpl` IS `@ReactiveTransactional`. The cascade-delete check + soft-delete are two non-transactional R2DBC calls — a concurrent role-bind may race into the orphan-binding state the defence advertises it prevents.
- **DataSource (F-031/H-013)** — two concurrent PUT edits are last-write-wins with no optimistic-lock detection; combined with REPLACE semantics a later edit silently clobbers an earlier operator's field changes.
- **Collector (F-020/H-009)** — update is full-replace (MapStruct `@MappingTarget`); a partial-form PUT silently nulls description + namespace (undocumented PUT-is-replace contract).
- **Entity description (F-004/H-008)** — concurrent description edits are last-writer-wins with silent loss; no optimistic locking, and both activity events capture the same `oldState` baseline, hiding the lost update.

This documents the operator-facing contract (last-writer-wins; PUT replaces, it does not patch). Per-instance optimistic-concurrency code fixes belong to the per-service hardening epics (PLT-053 Notification Settings, PLT-066/DOC-247 owner empty-roles, PLT-037 namespace TOCTOU); the RBAC `PolicyServiceImpl` transactional-asymmetry instance has no filed home — log it as a follow-up upstream PLT when this ships (see Implementation Notes).
