## What

The notification sender posts one HTTP request per alert synchronously, with no batching and no rate-limit handling. When the receiver (e.g. Slack) responds with `429 Too Many Requests` - which Slack's incoming-webhook rate limit (~1 msg/s with short bursts) will produce under any burst of alerts - the sender treats that status identically to any other non-200: it throws a `NotificationSenderException` whose message does not even include the status code ("didn't complete with 200 status code"). The `Retry-After` header that the receiver returns to tell the client how long to wait is **never read** (`response.headers()` is never inspected), and there is no back-off or retry: the processor catches the exception per-sender, logs a generic error, and the WAL stream advances past the alert (`AlertNotificationMessageProcessor.java:29-34`; LSN applied/flushed at `NotificationSubscriber.java:83-84`), so the message is **never re-attempted**. The practical effect during an alert storm (exactly when notifications matter most) is that the receiver rate-limits the platform and the over-limit portion of the burst is **dropped permanently** rather than delayed-and-delivered - with nothing in the log distinguishing "rate-limited, retryable" from a real receiver outage.

## Where

**`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/notification/sender/AbstractNotificationSender.java:16-30`:**
```java
protected void sendAndValidate(final HttpRequest httpRequest)
        throws NotificationSenderException, InterruptedException {
    final HttpResponse<String> response;
    try {
        response = httpClient.send(httpRequest, HttpResponse.BodyHandlers.ofString());
    } catch (final IOException e) {
        throw new NotificationSenderException("Couldn't send HTTP request", receiverId(), e);
    }

    if (response.statusCode() != HttpStatus.OK.value()) {                 // line 26
        throw new NotificationSenderException(
            "Notification sender response didn't complete with 200 status code", receiverId());
    }
}
```

Line 26 collapses every non-200 - `429`, `4xx`, `5xx` alike - into a single thrown exception. `429` is not distinguished, `response.headers()` (and thus `Retry-After`) is never inspected, and the call is a blocking 1:1 `httpClient.send(...)` per message with no coalescing (one POST per alert per sender: `SlackNotificationSender.java:40-49`).

The drop site - **`AlertNotificationMessageProcessor.java:26-35`**: the per-sender `try/catch` logs `"Error occurred while sending notification via Slack"` at `error` and continues; `process` returns normally, so the subscriber flushes the LSN (`NotificationSubscriber.java:83-84`) and the alert is gone for that receiver.

## User-facing impact

Users: everyone subscribed to the Slack channel (or webhook receiver) for ODD alerts, during any high-volume alert event; secondarily the operator reading platform logs.

What they observably get: when alert INSERTs outpace the receiver's rate limit, each over-limit alert produces exactly one POST, one `429`, one generic `log.error`, and **no delivery, ever** - subscribers see a burst arrive partially with no marker that anything is missing, and the platform log cannot tell them rate-limiting was the cause (the exception message omits the status code - verified by BE trace 2026-06-10: `AbstractNotificationSender.java:26-29`, `AlertNotificationMessageProcessor.java:29-34`). The 1:1-POST / no-retry / no-Retry-After / drop-and-advance facts are settled statically; **the burst behaviour itself is static trace consistent; not driven** - reproducing the actual 429 path needs a real rate-limiting receiver (Slack relay), which the local stack does not provide. Remaining check: drive a burst (>1 msg/s) against a Slack webhook (or a 429+Retry-After stub) and count deliveries vs drops.

## Why it matters

This degrades alerting precisely under load. The failure is **silent at the delivery boundary**: subscribers see a chunk of an alert burst simply never arrive, and while the platform does emit a per-drop `log.error`, that log line carries neither the status code nor `Retry-After` - so even a log-reading operator cannot tell rate-limiting (retryable) from a real outage. The affected parties are everyone subscribed to notifications during any high-volume event - which is the scenario alerting exists for. Because `429` is the receiver explicitly saying "slow down, retry after N seconds" and the code does the opposite (drop and continue), correctly-deliverable alerts are lost. High severity: lost alerts during a storm is a worst-case behaviour for a notification system, and the fix is a standard, well-specified protocol behaviour the sender currently ignores.

## Suggested fix

1. **Differentiate `429`** from other non-200 statuses in `sendAndValidate`.
2. **Read the `Retry-After` header** from the response (`response.headers().firstValue("Retry-After")`) and back off for the indicated duration (supporting both the delta-seconds and HTTP-date forms), then retry the send up to a bounded number of attempts.
3. Consider **coalescing/batching** bursts and applying a client-side rate limit so the platform does not hammer the receiver into `429` in the first place.

Open to alternatives on the back-off/retry policy details (max attempts, jitter, per-receiver queueing), but `Retry-After` must be honoured rather than discarded.
