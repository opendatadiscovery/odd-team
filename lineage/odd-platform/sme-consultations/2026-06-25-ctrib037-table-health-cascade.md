# Table Health ring: where BROKEN / RUNNING / UNKNOWN belong, and whether #1794's Broken→Warning is right

## TL;DR

**Map BROKEN to Error, not Warning** — and note that this is what ODD's *own live manual already says* happens today ("any latest run is failed **or broken**" = Error), so #1794's `Broken→Warning` would regress a documented, shipped behaviour to diverge from BOTH the published manual and the platform's alerting model (which treats `BROKEN == FAILED`). The semantic reason is decisive: in ODD's actual producer ecosystem, a *data-assertion failure* is recorded as **FAILED** (the `odd-great-expectations` adapter maps GE `success: false → FAILED`, never BROKEN); **BROKEN is the "the run machinery failed / the test could not produce a clean verdict" state** — an operational problem an at-a-glance health ring must surface in red, not soften to amber. **`Running → Healthy` is correct** (an in-flight retry must not degrade a table's health — consistent with the CTRIB-024/#1757 "RUNNING is first-class, not a problem" direction). **A distinct fourth `Unknown` bucket is the right shape** *provided* it is rendered as a neutral/muted "we don't know" state distinct from green — observability tools converge on surfacing indeterminate ("No Data"/"Stale") separately rather than silently scoring it healthy. The single highest-value GATE-1 recommendation: keep BROKEN in Error; the only real open call is whether UNKNOWN earns its own slice or folds into Warning.

## Question scope

Four coupled product decisions for the **Table Health** ring (the catalog-wide at-a-glance data-health donut — distinct from per-test alerting and from the SLA ratio):

1. What do FAILED vs BROKEN mean semantically in ODD and in the dominant DQ tools (dbt / GE / Soda) — is BROKEN "data failed the assertion" or "the test itself errored / no verdict"?
2. For a health ring specifically, BROKEN → **Error** (alerting-consistent) or **Warning** (#1794)?
3. Is `Running → Healthy` correct, or should RUNNING be neutral/excluded?
4. Is a distinct fourth `Unknown` table-health bucket right, vs folding UNKNOWN into Warning/Healthy?

**Archetype:** mixed — vocabulary (Q1) + implicit-requirements/plausibility (Q2, Q4) + workflow-consistency (Q3).

**Out of scope** (named so the caller knows where this ends): the jOOQ/SQL that computes the rollup; the exact donut colour tokens; the separate `RUNNING`-missing-from-wire-enum / HTTP-500 defect (covered in the 2026-06-19 sibling consultation, PLT-144) — I assume the dashboard's accounting can *see* RUNNING runs and answer only how RUNNING should *score*. I did not re-derive the code facts the caller supplied (`TASK_RUN_FAIL_STATUSES`, `SLACalculator`) beyond a spot-confirm.

## Domain plausibility

**Operator workflow this serves (Rule 4 — "Audit data quality across a domain"):** a steward opens the catalog-wide Quality Dashboard to answer one question — *"how much of my monitored estate is actually trustworthy right now?"* The Table Health ring is the single-glance answer. The load-bearing requirement of an at-a-glance health signal is **it must not under-report a real problem**: a table whose test machinery is broken (no clean verdict produced) is *not* trustworthy, and colouring it amber ("minor, look later") rather than red ("this is broken") is exactly the under-report that erodes the dashboard's credibility. This is the same logic ODD already applies in alerting, and — verified below — the same logic ODD's own published manual already documents for the ring.

**Verdict:** HIGH-PLAUSIBILITY that BROKEN belongs in **Error**. It maps to the audit workflow, matches ODD's shipped+documented behaviour, and matches the platform's alerting model. #1794's `Broken→Warning` is LOW-PLAUSIBILITY as stated — it rests on reading BROKEN as "unconfirmed failure", which is the *opposite* of how ODD's producers populate the field (see Q1).

## Industry vocabulary alignment (Q1 — what FAILED vs BROKEN mean)

The pivotal distinction every mature DQ tool draws is **"the data violated the assertion" (a verdict) vs "the check could not be evaluated" (no verdict)**:

- **Great Expectations** (canonical, verified): a validation result carries `success: true|false` — *"A `true` or `false` indicator of whether the Expectation passed."* — and a **separate** `exception_info` dict with `raised_exception` / `exception_message` for *"an expectation [that] cannot be evaluated due to an error."* So GE cleanly separates *data-failed* (`success:false`) from *check-errored* (`exception_info` populated).
- **ODD's mapping of GE is the decisive ground truth** (`odd-great-expectations/mapper.py:63-77`, read 2026-06-25): the adapter sets `SUCCESS` when `validation_result.success` is true and **`FAILED` when it is false** — and emits *nothing else*. A confirmed data-assertion failure in ODD is **FAILED**. By elimination, **BROKEN is not the data-failed state** — it is reserved for the run-could-not-produce-a-verdict / pipeline-broke case (the GE-`exception_info` / dbt-`ERROR` analogue), which is why it sits alongside FAILED in the failure set everywhere ODD evaluates it.
- **dbt** (verified): dbt's `severity: error|warn` and `error_if`/`warn_if` are *thresholds on the **count of failing rows*** — i.e. they grade the *severity of a data result*, not test-execution failure. *"if the number of failures is nonzero, the test returns an error"*; the docs frame everything as row-count thresholds *"from successful test query execution, not SQL execution failures."* dbt's separate `ERROR` line in its summary (`PASS / WARN / ERROR / SKIP`) is where an actual run failure lands. Takeaway: even dbt's `warn` is a *data* outcome, not an *indeterminate* one — there is no DQ tool in which "the engine broke" is treated as merely a warning.
- **ODD's contract itself documents none of this** (`odd-models-package/odd_models/models/models.py:169-176` and `odd-platform-specification/components.yaml:1421-1430`, read 2026-06-25): the 7-value `QualityRunStatus` / `DataEntityRunStatus` enums carry **no inline comment distinguishing BROKEN from FAILED**. *This absence is itself the root cause of the platform's inconsistency* and is worth a DOC-NNN follow-up (define BROKEN vs FAILED in the wire contract + the DQ docs).

**Recommended alignment:** preserve ODD's enum; **document** BROKEN as *"the test run did not produce a clean pass/fail verdict (the run itself failed or errored)"* and FAILED as *"the run completed and the data did not satisfy the assertion."* Under that (correct) reading, BROKEN is a *more* alarming signal than a warning, not a softer one.

## Implicit requirements (Q2 — BROKEN → Error vs Warning)

- **Functional — BROKEN belongs in Error, and ODD already ships+documents it there.** The live dashboard page states verbatim: a table is **Error** *"when any latest run is failed or broken"*, **Healthy** *"when none of its latest test runs is anything but a success,"* and Warning is *"everything in between."* It even pre-empts the #1794 framing: *"Searching the dashboard for a 'broken tables' count will not find that label — the broken/failed runs roll up into the **Error** slice."* So `Broken→Warning` is not a *new* design choice — it is a **regression of documented behaviour** that would also make the ring diverge from alerting. *(citation: docs.opendatadiscovery.org/features/data-quality/dashboard, 200, 2026-06-25.)* Confidence: HIGH.
- **Functional — alerting consistency confirms the direction.** `IngestionTaskRunAlertState.TASK_RUN_FAIL_STATUSES = {BROKEN, FAILED}` (`IngestionTaskRunAlertState.java:20-23`, read 2026-06-25) fires `FAILED_DQ_TEST` on both, with the literal message *"Test %s failed with status %s"* — the platform tells the operator a BROKEN run is a *failure*. A health ring that classified the same run as a mere Warning would contradict the alert the operator just received for it. *(citation: IngestionTaskRunAlertState.java:20-23,43,63-64.)* Confidence: HIGH.
- **Note the deliberate non-alignment with SLA, and keep it.** The caller is right that `SLACalculator` counts only SUCCESS+FAILED and ignores BROKEN. That is *correct for an SLA ratio* (a pass/fail success-rate metric should not let "the engine broke" count as a data failure that tanks the percentage — it would be unfair to the producer). But a **health signal is not a ratio**: its job is "is anything wrong?", and a broken run *is* something wrong. So Table Health legitimately diverges from SLA here — they answer different questions. The two surfaces are *both* right with *different* BROKEN handling; do not "harmonise" them. *(citation: caller-supplied `SLACalculator`; domain knowledge on ratio-vs-signal semantics.)* Confidence: HIGH.
- **Security / Performance / Reliability:** unchanged by this decision. The rollup reads the same latest-run rows the dashboard already reads; classification is a pure function of statuses already in hand. Confidence: HIGH.

**Verdict on Q2:** **BROKEN → Error.** Reject `Broken→Warning`. If #1794's author wants a finer Error breakdown, the right shape is an Error slice that is *splittable* into "failed" vs "broken" on drill-down — never a demotion of broken out of Error.

## Operator workflows + Q3 (Running → Healthy)

- **`Running → Healthy` is correct.** A health ring answers "is the table trustworthy *based on what we know*?" An in-flight run is not yet evidence of anything; degrading a table to Warning/Error merely because a test is *currently executing* would make the ring flicker red every time a scheduled test starts — punishing the operator for the system doing its job. RUNNING (like SKIPPED/ABORTED) should be **neutral**: it neither confirms health nor confirms a problem, so it falls through to Healthy only when no FAILED/BROKEN/UNKNOWN is present (which is exactly #1794's cascade). 
- **This is consistent with the CTRIB-024/#1757 direction** established in the 2026-06-19 sibling consultation: ODD treats RUNNING as a *first-class, surfaced* status (top of the run list, badged) — *visible*, not *penalising*. "Surface the in-flight run prominently" and "don't let an in-flight run degrade aggregate health" are the same philosophy: RUNNING is informational, not a failure. The one cross-check: ensure "Running doesn't hurt health" doesn't mean "Running hides a prior problem" — the cascade already handles this correctly, because it keys on the *latest* run per test and a FAILED/BROKEN *latest* run still wins over a sibling test's RUNNING. Confidence: HIGH (workflow-consistency + sibling consultation).

## Q4 — a distinct fourth `Unknown` bucket

- **A distinct `Unknown` slice is the right product shape, on one condition: render it as a neutral/muted "we don't know" — visually distinct from green Healthy.** The failure mode to avoid is folding UNKNOWN into **Healthy**: that would let "we have no idea about this table" masquerade as "this table is fine," which is the credibility-killer for a trust dashboard. Folding into **Warning** is defensible-but-lossy (it conflates "indeterminate" with "in-between-bad," and UNKNOWN is not a severity, it's an absence of information).
- **Observability tools converge on surfacing indeterminate state separately, not scoring it as pass.** Datadog's monitor status enum carries **`No Data`** as a distinct value alongside `Alert`/`Warn`/`OK` (verified in the 2026-06-20 sibling consultation: *"`Triggered` (`Alert`, `Warn`, `No Data`) or `OK`"*). GitHub Actions carries **`stale`** and `neutral` as conclusions distinct from `success`/`failure` (verified in the 2026-06-19 sibling consultation enum). The pattern: *"we couldn't determine a result" is a first-class, separately-shown state, never silently coloured as success.* A dedicated ODD `Unknown` slice matches this convention.
- **Caveat (HIGH-value):** the slice only earns its place if UNKNOWN actually occurs in practice. ODD's GE adapter never emits UNKNOWN (it emits only SUCCESS/FAILED), so the population of UNKNOWN-latest tables depends on which producers emit it (custom `/stats` pushes, the dbt adapter, profiler). **Recommend the GATE-1 matrix flag this**: if UNKNOWN is effectively never the worst status in real deployments, a fourth slice is dead UI — fold into Warning with a documented note. If it occurs, give it its own muted slice. This is a one-query check the maintainer can run against demo/prod data before committing the 4th bucket. Confidence: MEDIUM (the *shape* recommendation is HIGH; whether UNKNOWN is non-empty in practice is unverified — see Caveats).

## Recommended framing for the caller

> **Keep BROKEN in Error** — it is what ODD's live manual already documents ("failed **or broken**" = Error) and what alerting already does (`TASK_RUN_FAIL_STATUSES = {BROKEN, FAILED}`), and it is semantically correct because ODD records a *data-assertion* failure as **FAILED** (the GE adapter proves this), leaving BROKEN to mean "the run produced no clean verdict" — an operational problem a health ring must show in red. **Reject #1794's `Broken→Warning`** as a regression that would split the ring from both the published docs and the alert the operator just got. **`Running → Healthy` is correct** (RUNNING is neutral/informational, consistent with the #1757 "surface-don't-penalise" direction). **A distinct muted `Unknown` slice is the right shape** (matches Datadog `No Data` / GitHub `stale`), but **gate it on whether UNKNOWN is ever actually the worst latest status in real data** — if not, fold into Warning with a note. Bundle a DOC-NNN to *define BROKEN vs FAILED in the wire contract + DQ docs*, since the enum currently documents neither — that undocumented gap is the root cause of the three surfaces diverging.

GATE-1 matrix shorthand the maintainer can lift: **Error** = any latest FAILED **or BROKEN** (recommended, = today's documented behaviour); **Warning** = the genuine in-between only; **Unknown** = worst latest is UNKNOWN with no FAILED/BROKEN (separate muted slice *if non-empty in practice*, else fold to Warning); **Healthy** = only SUCCESS/SKIPPED/ABORTED/RUNNING. The real bug being fixed is the *current* Warning over-reach (SKIPPED/ABORTED/RUNNING/UNKNOWN wrongly reading Warning); #1794 is right to fix that — it is only wrong on the single BROKEN demotion.

## Caveats and uncertainty

- **Whether UNKNOWN is ever the worst latest status in real deployments is unverified.** ODD's GE adapter emits only SUCCESS/FAILED; I did not enumerate every producer's status-emission to confirm UNKNOWN-latest tables occur in practice. The *shape* recommendation (muted separate slice, never folded into Healthy) is HIGH-confidence; the *necessity* of the 4th slice is MEDIUM — a one-query check against demo/prod (`count of tables whose worst latest run-status = UNKNOWN`) would resolve it before committing UI. This is the one thing I'd verify before the 4th bucket ships.
- **Soda not verified.** Every Soda docs URL I tried (`soda-cl/optional-config`, `soda-cl-overview`, `soda-cl/checks`, `soda/glossary`) returned 404 (2026-06-25); their docs site reorganised and I did not substitute a guessed URL or pretrained recollection. The fail-vs-error distinction therefore rests on **GE (verified, and the one ODD actually adapts)** + **dbt (verified)** — two independent, convergent sources, which is sufficient for HIGH confidence on Q1. A Soda data point would be additive, not load-bearing; if wanted, it's a focused follow-up fetch against the current Soda docs URL.
- **ODD does not define BROKEN vs FAILED anywhere user-facing.** Confirmed by reading both the wire contract (`models.py:169-176`) and the spec (`components.yaml:1421-1430`) — no inline descriptions — and the live DQ docs (test-run-history page lists the seven statuses but explicitly *"does not define what each status means"*). The semantic reading of BROKEN here is inferred from the *producer mapping* (GE→FAILED for data-failure) + alerting placement, not from a definition ODD publishes. That inference is HIGH-confidence (the GE mapper is unambiguous), but the absence of a published definition is real and should become a DOC-NNN.
