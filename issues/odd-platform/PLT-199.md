## What

The platform defines a **second, dedicated R2DBC connection pool** (`customConnectionPool`) for the Lookup Tables feature's custom database schema. Unlike the conditional housekeeping component next to it, this pool **bean** is **unconditional** - the bean is created on every startup (no `@ConditionalOnProperty`), regardless of whether any Lookup Table is ever defined or queried, and it is a hard dependency of the Lookup Tables wiring (`customDataClient` / `customTransactionManager`).

**The pool is cold, not warm, on startup** - so this is a code-hygiene wart, not a runtime resource leak. r2dbc-pool 1.0.0 warms its `initialSize` connections **lazily** via `ConnectionPool.warmup()` on first acquire; the manual `new ConnectionPool(builder.build())` here never calls `warmup()` (grep-verified: no `warmup()` call exists in the codebase), and the shipped pool config inherits Spring Boot's framework default `minIdle=0` (bytecode-verified). So on a deployment that never queries a Lookup Table, the custom pool holds **zero** open connections - it is an idle pool *object*, not idle *connections*. It can grow toward `maxSize` (framework default 10) only once a custom-schema query actually runs. The genuine operator-facing concern - the undocumented total per-replica connection ceiling (both pools warm = ~20) and the absence of pool metrics - is already tracked by F-120 / IT-096 and its DOC/PERF follow-ups; THIS item is narrowly the bean-conditionality hygiene fix.

## Where

`config/R2DBCConfiguration.java:54` - the bean has no `@ConditionalOnProperty`:

```java
@Bean(name = "customConnectionPool", destroyMethod = "dispose")
public ConnectionPool databaseClientForCustomSchema(
    @Value("${spring.custom-datasource.url:}") final String url,
    @Value("${spring.custom-datasource.username:}") final String username,
    @Value("${spring.custom-datasource.password:}") final String password,
    final DataSourceProperties dataSourceProperties,
    final R2dbcProperties properties) {
    ...
    return new ConnectionPool(builder.build());   // R2DBCConfiguration.java:86
}
```

The pool's `customDataClient` / `customTransactionManager` beans (lines 94-110) hang off the same `@Qualifier("customConnectionPool")`, so the pool is a hard dependency of the Lookup Tables wiring and gets instantiated with the context.

**Contrast - the conditional sibling** `housekeeping/HousekeepingJobManager.java:17-18`, which gates its scheduled DB work on a property exactly the way this pool should:

```java
@Component
@ConditionalOnProperty(value = "housekeeping.enabled", havingValue = "true")
```

## User-facing impact

**No startup connection cost on Lookup-Tables-free deployments** - verified by BE trace + workspace runtime evidence 2026-06-10. The custom pool bean is unconditionally constructed (`R2DBCConfiguration.java:54-87`, no `@ConditionalOnProperty`), but it holds zero open connections until first acquire: r2dbc-pool 1.0.0 `ConnectionPool.warmup()` is the only path that opens `initialSize` connections, nothing in the codebase calls it (grep over `odd-platform-api/src/main/java`), and `minIdle=0` (Spring Boot framework default, bytecode-verified). IT-096 (`integration-tests/protocols/IT-096-r2dbc-pool-sizing.md`, status `ready`) pins exactly this: UC-4 asserts a Lookup-Tables-free stack's live r2dbc-postgresql connection count sits at the primary pool alone (~10) and is "strictly below 2xmaxSize=20" because "the manual `new ConnectionPool(...)` never warms it". So an operator does NOT see a doubled connection footprint from this bean. The only observable cost is once Lookup Tables IS used, the custom pool can grow to `maxSize` (framework default 10) on top of the primary - which is the undocumented total-ceiling concern already homed in F-120/IT-096, not this item.

## Why it matters

Code-hygiene, not a runtime resource leak (severity corrected medium -> low; see *How discovered*). The defect is that a feature-specific pool bean is instantiated on deployments that never use the feature - it is dead wiring carried by every context, and it does not follow the conditional pattern its housekeeping sibling already establishes. The practical cost is bounded to (1) one idle (cold) pool object per replica even when Lookup Tables is unused, and (2) once the feature is exercised, the pool adding to the per-replica connection ceiling. Neither is data loss, neither is a startup connection doubling, and the connection-ceiling/observability concern that *is* operator-facing is tracked elsewhere (F-120/IT-096). The value here is consistency with `HousekeepingJobManager` and not paying for wiring a deployment never uses - a small, justified clean-up.

## Suggested fix

Gate the `customConnectionPool` bean (and, by extension, its dependent `customDataClient` / `customTransactionManager` beans) with `@ConditionalOnProperty` keyed on the Lookup Tables / custom-datasource toggle, mirroring `HousekeepingJobManager`:

```java
@Bean(name = "customConnectionPool", destroyMethod = "dispose")
@ConditionalOnProperty(value = "spring.custom-datasource.url")   // or a dedicated lookup-tables.enabled flag
public ConnectionPool databaseClientForCustomSchema(...) { ... }
```

If a dedicated feature flag is preferred over keying on `spring.custom-datasource.url` presence, introduce a `lookup-tables.enabled` property and gate all three beans on it. Open to alternatives on the exact property name - the load-bearing change is that the pool is conditional, so it is not opened on deployments that never exercise the feature.

Corrected 2026-06-10 (user-facing verification sweep): was severity medium on the rationale that the unconditional pool "opens its initialSize connections at startup... doubling the platform's baseline connection footprint" / "a real resource leak for the common case where Lookup Tables is unused"; actually the pool is COLD at startup - r2dbc-pool 1.0.0 warms `initialSize` only via `ConnectionPool.warmup()`, which is never called here (no `warmup()` in `odd-platform-api/src/main/java`), and `minIdle=0` (bytecode-verified framework default), so an unused custom pool holds zero connections. IT-096 (`integration-tests/protocols/IT-096-r2dbc-pool-sizing.md`, status `ready`) independently pins this (UC-4: Lookup-Tables-free footprint is the primary pool alone, < 2xmaxSize). The startup-doubling claim is the corpus failure mode (a runtime cost extrapolated from the bean's unconditionality without tracing the library's lazy-warmup behaviour). Re-scoped to the surviving, code-settled defect: an unconditionally-instantiated feature-specific bean (a hygiene fix mirroring `HousekeepingJobManager`), medium -> low. The total-ceiling/observability concern that justified urgency lives in F-120/IT-096, not here.
