## Summary

`DataEntityMapperImpl` dereferences class-specific details DTOs **without a null guard** for three of
its five class branches. When a `DATA_TRANSFORMER` or `DATA_QUALITY_TEST` entity reaches the mapper with a
null details DTO, the mapper throws a `NullPointerException` -> the whole response 500s with a generic
`SYS001 "Internal Server Error"`. This fires on the **catalog search results list** and on the **entity
detail** endpoint - two primary user-facing surfaces.

## The defect (primary-source)

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/mapper/DataEntityMapperImpl.java`

(Line numbers verified 2026-06-10 against `../odd-platform`.)

- `mapPojo` (used by the search-results list via `mapPojos`, `:174-175`) and `mapDtoDetails`
  (entity detail, `:256`) both branch per entity class.
- The `DATA_SET` branch is null-safe: `entity.setStats(mapStats(dto.getDataSetDetailsDto()))` (`:95`) -
  `mapStats` returns an empty `DataSetStats()` on a null argument (`:551-554`).
- The `DATA_TRANSFORMER` branch (`mapPojo:99`, `mapDtoDetails:298`) is **not**:
  `entity.setSourceList(dto.getDataTransformerDetailsDto().sourceList()...)` - direct deref of a possibly-null
  `getDataTransformerDetailsDto()` (also `:105` targetList).
- The `DATA_QUALITY_TEST` branch (`mapPojo:114`, `mapDtoDetails:314-331`) is **not**:
  `dto.getDataQualityTestDetailsDto().linkedUrlList()...` - same shape.
- The `DATA_CONSUMER` (`:125`) / `DATA_INPUT` (`:133`) branches also deref directly, but their DTOs are
  populated non-null on the dimensions path (verified: consumer-class entities render 200), so they do not
  currently fault.
- The `DATA_ENTITY_GROUP` branch DOES guard: `... && dto.getGroupsDto() != null` (`:140`) - proving the
  authors apply the guard pattern, just **inconsistently**.

The exception observed live (probe-odd-platform, 2026-06-07):

```
java.lang.NullPointerException: Cannot invoke
"...DataEntityDimensionsDto$DataTransformerDetailsDto.sourceList()" because the return value of
"...DataEntityDimensionsDto.getDataTransformerDetailsDto()" is null
        at ...mapper.DataEntityMapperImpl.mapPojo(DataEntityMapperImpl.java:99)
        at ...mapper.DataEntityMapperImpl.mapPojos(DataEntityMapperImpl.java:175)
        *__checkpoint --> Handler ...SearchController#getSearchResults(...)
```

## Reproduction (live, deterministic)

1. Seed a searchable `DATA_TRANSFORMER` entity (`entity_class_ids = '{2}'`) with a `search_entrypoint`
   vector, and no transformer details sub-data.
2. `POST /api/search {query, filters:{}}` -> 200, session `total: 1`.
3. `GET /api/search/{id}/results` -> **500 `SYS001`**.

Same with `DATA_QUALITY_TEST` (`entity_class_ids = '{4}'`). `DATA_SET`, `DATA_CONSUMER`, and
`DATA_ENTITY_GROUP` classes return 200 under the identical seed shape.

## User-facing impact

**Verified-trace** (BE source + driven), 2026-06-10. The throw site is code-settled (`DataEntityMapperImpl.java:99`
deref of `getDataTransformerDetailsDto().sourceList()` with no guard; the global `@RestControllerAdvice` maps the
resulting `NullPointerException` via its `Exception.class` catch-all to HTTP 500 `SYS001`,
`ControllerAdvice.java:61-66`), and IT-068 drives it live on the running stack (in the passing feature-complete
suite). On the catalog Search page the results list renders **zero rows** and an error panel, even though the
class-tab strip simultaneously shows e.g. `Transformers | 1` (the facet count aggregator is null-tolerant - the
self-contradicting "Transformers | 1" over an errored empty list is asserted by IT-068's pin). The operator
sees "1 transformer matched" but an empty, errored list - a stark, self-contradicting surface. Any search whose
result page contains one such entity fails entirely (the 500 is for the whole page, not the single row). The
entity detail endpoint fails the same way for an affected entity.

Whether a fully-ingested transformer always populates the details DTO is a separate question; regardless, a
**list/detail mapper must not 500 the entire response on one entity's null sub-projection**. The fix is a
defensive null-guard, consistent with the existing `DATA_ENTITY_GROUP` branch.

## Fix shape

Null-guard the `DATA_TRANSFORMER`, `DATA_QUALITY_TEST` (and defensively `DATA_CONSUMER` / `DATA_INPUT`)
branches in both `mapPojo` and `mapDtoDetails` - skip the source/target/linked-list mapping (leaving the lists
empty) when the respective details DTO is null, mirroring the `getGroupsDto() != null` guard already present.

## Regression guard

Pinned GREEN today as an LSN-029 characterization pin: **IT-068 / F-148** ("a transformer-class entity in the
search result set currently 500s the results list"). It flips RED when the mapper is hardened (the row then
renders and the GET returns 200) - that RED is the measurable closure signal.

Convergent re-confirmation (2026-06-07, IT-073 / F-206 build): independently re-observed live - a searchable
`entity_class_ids={2}` entity with no transformer details 500s `GET /api/search/{id}/results`
(`...DataTransformerDetailsDto.sourceList() ... is null` at `DataEntityMapperImpl.mapPojo`), confirming the
defect is reproducible across seed paths. IT-073 (search-row class-badge) consequently runs its
encoding-distinctness corner on a DATA_SET row (the only NPE-safe class for the raw-seed path) rather than a
second class. No new PLT - this issue already owns it.
