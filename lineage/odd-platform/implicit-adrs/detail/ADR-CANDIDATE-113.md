## ADR-CANDIDATE-113 — DEG membership writes do NOT auto-create the target DEG; `isManuallyCreatedDEG` defensive predicate explicitly gates against the auto-create-on-miss family (Owner/Title/Tag) — DEGs are first-class entities with their own `DATA_ENTITY_GROUP_CREATE` permission

**Classification**: promote (intent-anchored — distinguishes DEG family from Owner / Title / Tag auto-create family)
**Severity**: HIGH
**Pillars affected**: [P-01-data-discovery, P-09-security-access-control, P-08-management-administration]
**Support**: 2 sidecars (`addDataEntityDataEntityGroup` + `deleteDataEntityFromDataEntityGroup`); the predicate is reused symmetrically on both write paths and the rejection error message is a verbatim intent anchor
**Batch**: L (2026-05-19)

**Surfaced by**:
- `odd-platform__java__DataEntityController__controller-method__addDataEntityDataEntityGroup.md:implicit_adrs.[0]` (HIGH) — "DEG membership writes do NOT auto-create the target DEG — `DataEntityServiceImpl.java:393-397` explicitly requires the target DEG to exist AND be `manuallyCreated=true` AND have the DATA_ENTITY_GROUP class id; the matching `BadUserRequestException` carries the intent text. This DIVERGES from the REFACTOR-199/206/223 auto-create-on-miss family (Owner, Title, Tag — all of which silently mint directory rows from per-resource permissions)"
- `odd-platform__java__DataEntityController__controller-method__deleteDataEntityFromDataEntityGroup.md:implicit_adrs.[2]` (HIGH) — "DEG-type pre-check rejects ingested (non-manually-created) DEGs — `isManuallyCreatedDEG(pojo)` requires BOTH `pojo.getManuallyCreated() == true` AND `contains(pojo.getEntityClassIds(), DATA_ENTITY_GROUP.getId())` ... An ingested DEG (where `manually_created = false`, e.g. a DBT model group ingested from collectors) cannot have entities removed via this endpoint. The intent is to keep ingested DEG membership immutable from the UI — the ingestion pipeline is the canonical source of truth for ingested DEGs and operator edits would create drift"

**Decision statement**: ODD treats Data Entity Groups (DEGs / Domains / ML Experiments / DAGs / KAFKA_SERVICE / API_SERVICE / DATABASE_SERVICE — all `DATA_ENTITY_GROUP`-class subtypes per `DataEntityClassDto.java:50`) as a HEAVIER architectural primitive than Owner / Title / Tag rows. DEGs carry their own metadata (owners, tags, terms, descriptions, statuses), participate in Group lineage, appear on the Catalog Overview's Domain tiles, and are first-class data entities with their own `DATA_ENTITY_GROUP_CREATE` permission gate (`SecurityConstants.java:35` imports the permission; `DataEntityController.java:84-89` is the dedicated `POST /api/dataentitygroups` endpoint). DEG-membership writes — `addDataEntityToDEG` (`DataEntityServiceImpl.java:387-408`) and `deleteDataEntityFromDEG` (`:411-438`) — therefore enforce a defensive pre-check that the target DEG must EXIST and be MANUALLY-CREATED. The predicate is captured as a 4-line private method `isManuallyCreatedDEG(pojo) = pojo.getManuallyCreated() && contains(pojo.getEntityClassIds(), DATA_ENTITY_GROUP.getId())` at `DataEntityServiceImpl.java:483-486`; both write paths consume it via `.filter(this::isManuallyCreatedDEG).switchIfEmpty(BadUserRequestException("Entity with id %s is not manually created DEG"))`. Three structural consequences follow: (a) **No side-effect DEG creation** — unlike OwnershipServiceImpl.java:52 (`ownerService.getOrCreate(owner_name)` auto-mints Owner rows) or TagServiceImpl.java:80-86 (auto-creates Tag rows), the DEG path REJECTS calls referencing non-existent DEGs with HTTP 400. Side-doors past `DATA_ENTITY_GROUP_CREATE` are structurally foreclosed. (b) **Ingested DEGs are immutable from this surface** — an `odd-collector` emits a `DataEntity` with `entityClass=DATA_ENTITY_GROUP` and `manually_created=false`; operators cannot add/remove members through these endpoints. The ingestion pipeline owns ingested-DEG membership; UI edits cannot diverge. (c) **Predicate is DRY across add+delete** — both write paths share `isManuallyCreatedDEG`; future maintainers needing to relax the constraint (e.g., allow ingested DEGs to receive manual membership) change one line. The OpenAPI surface restates the constraint at `openapi.yaml:1073` ("Adds data entity to manually created data entity group"), so the manually-created constraint surfaces in three layers (predicate, error message, spec). The live Permissions doc (verified 2026-05-19 status 200) confirms the framing: "DATA_ENTITY_ADD_TO_GROUP: Allows adding a data entity to a manually created group." Trade-off accepted: operators clicking 'Add to group' on an ingested DEG's UI surface receive a 400 with no doc-side context; the absence of a "manually-created vs ingested DEG" disambiguation at the operator-facing groups-domains.md page is a separately-tracked doc-drift candidate.

**Wisdom test**: PASS on all three questions. (1) **Intent stated**: the BadUserRequestException carries the verbatim message "Entity with id %s is not manually created DEG" (`DataEntityServiceImpl.java:397, 420`) — the maintainer explicitly named the constraint in the rejection path; the OpenAPI description restates it; the Permissions live doc echoes it. (2) **Structural impact**: the divergence from the Owner / Title / Tag auto-create family is architectural — DEGs are first-class data entities with their own creation permission, while Owners / Titles / Tags are directory-rows that are subordinate to per-resource permissions. The two patterns are deliberately different. (3) **Adding/removing the predicate is structural**: relaxing the predicate (auto-create-DEG-on-miss inside the membership-write path) would be a fundamentally different security model — a `DATA_ENTITY_ADD_TO_GROUP` holder could mint arbitrary DEGs by side-effect, bypassing the `DATA_ENTITY_GROUP_CREATE` gate. Refactoring within structure (e.g., tighten the predicate to include a soft-delete check) would not change the ADR.

**Existing ADR**: none. **Contrasts directly with ADR-CANDIDATE-049** (Owner identity-decoupled directory CRUD — separate two-stage flow), **ADR-CANDIDATE-065** (Tag auto-create-on-miss is INTENTIONAL and spec-acknowledged), **REFACTOR-199** (Owner auto-create via createOwnership bypasses OWNER_CREATE), **REFACTOR-206** (Title auto-create has no allowlist). Composes with **ADR-CANDIDATE-058** (data-entity status / soft-delete-as-state — DEGs as first-class data entities inherit the status machine). Composes with **ADR-CANDIDATE-002** (centralised SECURITY_RULES — DATA_ENTITY_ADD_TO_GROUP + DATA_ENTITY_DELETE_FROM_GROUP + DATA_ENTITY_GROUP_CREATE are three separate Policy permissions, each registered at SecurityConstants.java:228-236 / 35).

**Cross-link gaps** (refactoring-scopes anchored on consequences this ADR DOES NOT defend):
- **REFACTOR-331 (NEW batch L)** — Write-collaborative DEG: even with the manually-created constraint, the SecurityRule scopes on the CHILD entity, not the parent DEG; `DATA_ENTITY_ADD_TO_GROUP`-holders can place arbitrary entities into any manually-created DEG. The ADR defends against side-effect DEG creation; it does NOT defend cross-owner DEG-pollution.
- **REFACTOR-332 (NEW batch L)** — DEG membership flips unaudited (cross-batch with batch-I @ActivityLog AOP traps). The ADR's manually-created discipline does not extend to audit-trail.
- **REFACTOR-338 (NEW batch L)** — Soft-deleted membership + re-add produces misleading "already in this DEG" error. The predicate gates the DEG-side but not the soft-delete-state of the relation row.
- **Doc-gap candidate**: the operator-facing groups-domains.md page does NOT explain the manually-created vs ingested distinction — operators clicking 'Add to group' on an ingested DEG receive a cryptic 400.

**Proposed action**: Promote to `adrs/drafts/deg-no-auto-create-on-miss.md` (new ADR). Document: (1) the architectural distinction between DEGs (first-class data entities with their own `DATA_ENTITY_GROUP_CREATE` permission) and Owner/Title/Tag (directory rows subordinate to per-resource permissions); (2) the symmetric predicate (`isManuallyCreatedDEG`) usage at both add+delete sites; (3) the three-layer manifestation (predicate + error message + OpenAPI description). Cross-link with ADR-CANDIDATE-049 (the contrasting Owner directory model), ADR-CANDIDATE-065 (Tag auto-create — the deliberate exception), REFACTOR-199/206 (the auto-create gaps the DEG family deliberately avoids), REFACTOR-331 (the cross-owner DEG pollution gap this ADR does NOT defend). Doc-side: the live groups-domains.md page must articulate the manually-created vs ingested distinction at the operator surface.

**Severity rationale**: HIGH — load-bearing security/governance decision; explicitly distinguishes the DEG family from the auto-create-side-channel family that REFACTOR-199 / REFACTOR-206 surface as bugs. A future maintainer relaxing the predicate (e.g., to auto-create-DEG-on-miss for ergonomic Add-to-new-group UX) would silently introduce the side-channel that this ADR explicitly forecloses; the load-bearing nature merits ADR documentation.
