## Description

The platform's audit posture is BIFURCATED across exactly two architectural shapes, and the SHAPE of the bifurcation is schema-rooted (not "we forgot to add @ActivityLog annotations"). The POSITIVE half — Owner-Association-Request workflow — has a dedicated typed-event audit table. The NEGATIVE half — RBAC + Owner / Term / Namespace lifecycle — has NO recoverable audit trace anywhere on the platform, and the schema makes adding one structurally non-trivial.

Compliance auditors and security reviewers reading the existing Activity Feed page (which says "records changes to data entities") do NOT know that the prose's "changes" is silently scoped to a 27-value enum and a schema-FK-NOT-NULL constraint that excludes RBAC mutations + Owner lifecycle + Term lifecycle + Namespace lifecycle entirely. A new dedicated page on the security pillar names the architectural reality so operators can make informed compliance decisions.

**The schema-rooted facts (F-006a, HIGH→CRITICAL):**

- `V0_0_48__add_activity.sql:4,12` declares `activity.data_entity_id NOT NULL FK` — the audit table STRUCTURALLY CANNOT store events that are not scoped to a single data entity. Adding `@ActivityLog(POLICY_CREATED)` to `PolicyServiceImpl.create` would not compile (the annotation processor demands a data-entity context that the call site does not have).
- `ActivityEventTypeDto.java:3-31` declares 27 enum constants. None correspond to RBAC mutations (Policy/Role CRUD), Owner lifecycle, Term lifecycle, Namespace lifecycle, Datasource lifecycle, Collector lifecycle. Extending the enum without the schema change is non-load-bearing — the FK constraint still rejects the row.
- **9-sidecar audit-silence verification this run**: controllers (`RoleController`, `PolicyController`), repositories (`ReactivePolicyRepositoryImpl`, `ReactiveRoleRepositoryImpl`, `ReactiveActivityRepositoryImpl`), services (`OwnerServiceImpl:87-100`, `PolicyServiceImpl:62-95`, `RoleServiceImpl:49-87`, `TermServiceImpl`), UI (`PolicyList.tsx`, `RolesList.tsx`) — NONE carry `@ActivityLog`, `@Slf4j`, or any audit call.
- **Positive half exists in parallel**: `owner_association_request_activity` table (`V0_0_82__add_owner_association_activity.sql` and successors) — dedicated table with a 5-value typed enum for that workflow. Demonstrates the architectural intent: workflows get dedicated tables; entity-level changes get the shared `activity` table; nothing else gets an audit trail.

**Operator consequence (the compliance picture):**
- An attacker with brief admin access can delete the seeded Administrator role, recreate it with attacker-chosen policy bindings (the partial-unique-index allows re-use of seeded names; see F-006 substrate's `role_create_administrator_name_asymmetry_mirror` facet), and leave NO trace except an orphaned `owner_to_role` row.
- Compliance auditors expecting "who renamed Owner-X from Alice to Bob at T" have NO recoverable trace anywhere on the platform.
- Combined with the case-sensitivity mismatch facet (`role_service_predefined_name_case_sensitivity_mismatch`), an attacker can recreate `administrator` (lowercase) while the seeded `Administrator` (titlecase) exists — silently, by-design, no trail.

  - **## What IS audited (positive half)** — table:

    | Subject | Where it's stored | Event types | Coverage |
    |---|---|---|---|
    | Data Entity changes (descriptions, tags, terms, ownership, metadata, alerts, custom-metadata, etc.) | `activity` table | 27-value `ActivityEventTypeDto` enum | Per-entity audit; visible in Activity Feed UI |

  - **## What is NOT audited (negative half — schema-rooted)** — clearly call out each silent surface:
    - **RBAC mutations** — Policy CRUD, Role CRUD, Permission assignments. Creating, updating, or deleting Roles and Policies leaves NO trace. Renaming a Role leaves no trace. Re-binding a Policy to a different Role leaves no trace.
    - **Owner lifecycle** — Owner CRUD (create / rename / soft-delete). Owner-Role binding changes (`OwnerServiceImpl.java:87-100`).
    - **Term lifecycle** — Term CRUD on the business glossary.
    - **Namespace lifecycle** — Namespace CRUD.
    - **Datasource / Collector lifecycle** — Datasource creation / deletion. Collector token rotation.
    - Each bullet cites the audit-silent service file:line (e.g., `PolicyServiceImpl.java:62-95` — no @ActivityLog, no @Slf4j).
  - **## Why this gap exists (architectural framing)** — schema-rooted explanation:
    - `activity.data_entity_id` is `NOT NULL FK` in the schema (`V0_0_48__add_activity.sql:4`) — the table CANNOT store events without a data-entity context.
    - `ActivityEventTypeDto` has 27 values, all data-entity-scoped — no values exist for RBAC / Owner / Term / Namespace lifecycle.
    - The positive-half pattern (dedicated `_activity` tables per workflow) is the architectural escape hatch; nothing analogous exists for RBAC / Owner / etc.
    - Closing the gap requires coordinated migration (see PLT-062): schema migration making `data_entity_id` NULLable + adding `subject_kind` + `subject_id` discriminator OR a separate `platform_event` table; extending `ActivityEventTypeDto` with ~21 missing enum values; ActivityHandler implementations; `@ActivityLog` annotations across ~25 service methods.
  - **## Compliance implications** — for operators with SOX, HIPAA, GDPR, SOC2 audit requirements:
    - Document that RBAC + Owner / Term / Namespace mutations have no recoverable trace. Recommend compensating controls:
      - **Database-level audit**: enable Postgres `pg_audit` or equivalent to capture mutations to `policy`, `role`, `owner`, `term`, `namespace`, `datasource` tables.
      - **Kubernetes-level audit**: capture authenticated API calls at the ingress / service-mesh layer (mTLS audit logging).
      - **Application logs (DEFENCE-IN-DEPTH NOT ENOUGH)**: even with structured logging, the platform does NOT emit on RBAC mutations (`PolicyServiceImpl` has no `@Slf4j` of any kind). Application logs do not substitute for an audit trail today.
    - Reserve admin-tier access tightly; combined with the `partial-unique-index` allowing seeded-name re-use, an attacker with brief admin access can delete + recreate the seeded `Administrator` role with attacker-chosen policy bindings, leaving NO trace except an orphaned `owner_to_role` row.
