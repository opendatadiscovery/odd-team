## Description

The live Lookup Tables page (WebFetched 2026-05-27) covers the feature workflow + the 9 PostgreSQL field types + the SQL-joinable schema-direct-access promise. It is silent on four operator-visible behaviours, each load-bearing:

**Caveat 1 — LOOKUP_TABLE_* permissions are GLOBAL, not per-table (F-026a).** All 9 `LOOKUP_TABLE_*` SecurityRule entries at `SecurityConstants.java:114, 326-354` use the `NO_CONTEXT` resolver — the resolver does NOT pass the table-id to a per-table permission-scope extractor. Contrast with TERM (`SecurityConstants.java:174-193` TERM resolver) and DATA_ENTITY (`SecurityConstants.java:195-227` DATA_ENTITY resolver). **A Policy granting `LOOKUP_TABLE_UPDATE` permits modifying ANY lookup table** — multi-tenant deployments expecting per-table RBAC granularity get global-table RBAC. A user with LOOKUP_TABLE_UPDATE granted for "their team's tables" can update every team's tables.

**Caveat 2 — Cascade orphan when parent DataEntity is deleted (F-026b).** `LookupDataServiceImpl.java:114-118` does not enforce the inverse-direction FK on parent DataEntity deletion. Deleting the parent DataEntity via `/api/dataentities/{id}` OR via ingestion soft-delete TTL leaves orphan rows in `lookup_tables_schema.n_*` AND an orphan `lookup_tables` row. The catalog and the data store drift; the operator sees a "missing table" from the catalog UI but the underlying PostgreSQL table is still queryable from BI/ETL.

**Caveat 3 — Rename ALTER TABLE silently breaks downstream BI/ETL pipelines (F-026c).** The page's "Original Name of Lookup Table functions as a table identifier within PostgreSQL" sentence implies the name is stable. `ReferenceDataRepositoryImpl.java:181-202` rebuilds `tableName = name.toLowerCase().replace(" ", "_")` and issues `ALTER TABLE ... RENAME TO`. Downstream pipelines that hardcoded the table name (the SQL-joinable schema-direct-access contract this page promises) break silently on rename — no Postgres VIEW alias, no rename-blocker, no warning at the rename UI.

**Caveat 4 — XSS surface extends to row values + column names + table name (F-026d — 5th surface of F-004 stored-XSS family).** `LookupCharValidator.java:14-17` returns the input value verbatim with no sanitization. The platform stores and renders unsanitized text in row values, column names, and the table name itself. Stored XSS surface across the Lookup Tables UI.

- [ ] **Caveat 1 framing** explicitly names the global-table RBAC posture — *"Any operator granted `LOOKUP_TABLE_UPDATE` (or `_DELETE`) can modify or delete every lookup table in the platform, regardless of how Policies are scoped. Cross-link to PLT-019.
- [ ] **Caveat 2 framing** names the cascade-orphan behaviour on parent DataEntity delete — operator mitigation: avoid deleting parent DataEntities that have Lookup Tables; use the platform's Lookup Table delete first. Cross-link to PLT-019.

RENAME TO` against the underlying PostgreSQL table. Downstream BI/ETL pipelines that reference the old name break immediately and silently."* Operator mitigation: do not rename a Lookup Table after external usage exists; rebuild any downstream pipeline references in the same change window. Cross-link to PLT-019.
- [ ] **Caveat 4 framing** names the XSS surface in operator-frame: *"Lookup Table values, column names, and table names are stored and rendered without escaping. Treat the Lookup Tables UI as a trusted-input surface — do not paste content from untrusted sources."* Cross-link to PLT-019.
