## Description

The live `features/data-lineage/microservices.md` page (WebFetched 2026-05-27, 200 OK) describes the OpenTelemetry ingestion path + the UI rendering — it has improved since substrate authoring and now explicitly says "same UI surface as Data Objects Lineage" + "Microservices appear in the catalog as `MICROSERVICE`-class transformer entities" (the substrate's `microservices_lineage_indistinguishable_from_data_object_lineage_no_class_aware_ui` facet is reclassified to **ontology-confirmed-positive** this run). What the page is still silent on are the two operator-visible facets that operators of a multi-team microservices deployment care about most:

**Facet 1 — Cross-owner enumeration amplified on microservices class (F-054a, CRITICAL).** `LineageServiceImpl.getLineage` (line 87-91) has no `EntityClass` parameter and no owner-scoping at the service tier; the repository tier has no owner JOIN. Any authenticated user can read any microservice's upstream/downstream call graph including services owned by other teams. The cross-owner-enumeration class (REFACTOR-203 family) is AMPLIFIED on this class because microservice lineage exposes operational topology that schema-lineage does not — competitor service-call patterns become visible. An SRE at a multi-team org expecting per-team microservice-lineage visibility discovers via empirical click-through that EVERY microservice is readable.

**Facet 2 — Microservice-specific OpenTelemetry trace fields silently dropped at the response DTO mapper (F-054b, HIGH).** `DataEntityLineageNode` response DTO is class-agnostic. A third-party `odd-tracing-gateway` collector emitting microservice-specific metadata (operation_name, span_kind, error_rate, p95_latency, callsPerMinute, service-call-cardinality) would have those fields silently dropped at the response-DTO mapper, invisible at both UI and API layers. The doc mentions OpenTelemetry ingestion but is silent on which trace fields survive in the response DTO returned by `/api/dataentities/{id}/lineage/downstream`.
