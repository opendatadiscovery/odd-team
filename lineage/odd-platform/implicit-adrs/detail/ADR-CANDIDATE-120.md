## ADR-CANDIDATE-120 — DEG-lineage uses a non-recursive edge-fetch with BIDIRECTIONAL bound-set filter (`PARENT_ODDRN.in(oddrns).and(CHILD_ODDRN.in(oddrns))`) — recursion lives at the MEMBERSHIP layer, NOT at the EDGE layer; the response is per-connected-component, INTERNAL-only

**Classification**: promote
**Severity**: MEDIUM
**Pillars affected**: [P-05-data-lineage, P-01-data-discovery]
**Support**: 1 sidecar (batch M `getDataEntityGroupsLineage`) — multiple co-surfacing implicit_adrs entries; composes with ADR-CANDIDATE-119 (inner-DEG suppression) and ADR-CANDIDATE-072 (recursive-CTE lineage architecture).
**Batch**: M (2026-05-19)

**Decision statement**: ODD's DEG-lineage endpoint composes a **three-decision architecture** that together define the response shape:

1. **Recursive at the MEMBERSHIP layer, non-recursive at the EDGE layer**: Member enumeration uses a Postgres `WITH RECURSIVE` CTE (`ReactiveGroupEntityRelationRepositoryImpl.getDEGEntitiesOddrns`, lines 177-204) to walk transitively through nested DEGs and produce a bounded `List<String>` of member oddrns. Edge fetching then uses the simpler `getLineageRelations(List<String>)` (`ReactiveLineageRepositoryImpl.java:112-119`) — a single non-recursive SELECT-DISTINCT on LINEAGE rows where BOTH `PARENT_ODDRN` AND `CHILD_ODDRN` are in the member set. Recursion happens ONCE, at member-resolution time; edge expansion is a single bounded query. Contrast with per-entity lineage (`LineageServiceImpl.getLineage`) which uses the recursive lineage CTE (`ReactiveLineageRepositoryImpl.java:122-148`) for edge traversal bounded by `LineageDepth.of(N)`.

2. **Bidirectional bound-set filter (INTERNAL-only)**: `where(LINEAGE.PARENT_ODDRN.in(oddrns).and(LINEAGE.CHILD_ODDRN.in(oddrns)).and(LINEAGE.IS_DELETED.isFalse()))` (lines 115-117). Edges crossing the DEG boundary — exiting to a non-member parent or entering from a non-member child — are DROPPED. The DEG-lineage view is the **internal** lineage of the group; external context (upstream sources OUTSIDE the DEG; downstream consumers OUTSIDE the DEG) is not surfaced. An operator wanting "show me everything connected to this DEG" uses the per-entity lineage endpoints on individual members instead.

3. **Per-connected-component response shape (NOT per-member)**: The response is `List<DataEntityLineageStream>` (one stream per connected component) rather than `List<DataEntityLineageStream>` (one per DEG member). `establishDEGRelations` (lines 200-216) partitions the DEG's edge graph into disjoint connected components and emits ONE stream per component, anchored on the first DEG-member oddrn discovered. The `participatedOddrns` accumulator (line 209) ensures each component is emitted exactly once. The 3-arg `getLineageStream` overload at line 197 always passes `List.of()` for groups and `Map.of()` for groupsRelations — the DEG-lineage response NEVER surfaces sub-group memberships in the response payload, only the underlying flat edge graph.

The three-decision composition makes the DEG-lineage view structurally distinct from per-entity lineage:
- per-entity lineage: ONE starting oddrn, depth-bound recursive traversal, includes cross-boundary edges to any reachable entity, groups + groupsRelations populated.
- DEG-lineage: SET of starting oddrns (transitively resolved members), single-step bound-set filter, INTERNAL-only edges, per-connected-component partition, groups + groupsRelations always empty.

**Wisdom test**: PASS on all three questions.
1. **Intentional?** YES — three positive code-anchored decisions: (a) the DIFFERENT method (`getLineageRelations(List<String>)` vs `getLineageRelations(Set<String>, LineageDepth, LineageStreamKind)`) at LineageServiceImpl.java:66; (b) the explicit bidirectional `.and()` predicate at ReactiveLineageRepositoryImpl.java:115-117; (c) the `List.of(), Map.of()` hardcoded args at LineageServiceImpl.java:197.
2. **Structural impact?** YES — affects the response-shape contract for `/api/dataentitygroups/{id}/lineage`; affects the UI's DEGLineage component's rendering model; affects every third-party API consumer reading the OpenAPI spec.
3. **Adding/removing the bidirectional bound-set filter would be STRUCTURAL?** YES — relaxing `.and()` to `.or()` would silently leak external-context edges into the DEG-lineage response; changing to per-member emission instead of per-component would multiply the response payload; populating groups + groupsRelations would change the response schema. All three decisions are independently load-bearing.

**Existing ADR**: none. **Composes with ADR-CANDIDATE-072** (per-entity recursive-CTE lineage + progressive expansion — the per-entity lineage architecture; THIS ADR is the deliberate divergence for the DEG-anchored variant). **Composes with ADR-CANDIDATE-119** (DEG-lineage inner-DEG suppression — the two ADRs together describe the full DEG-lineage architecture: the bound-set filter at the edge layer + the DEG-stripping filter at the response-assembly layer).

**Cross-link gaps** (refactoring-scopes anchored on consequences this ADR DOES NOT defend):
- **REFACTOR-241 STRENGTHENED** (batch M): the OR-predicate in `getLineageRelations(List<String>)` is misleading — both conjuncts are equivalent; a future maintainer "simplifying" might widen the filter to OR-of-either-endpoint and silently leak external-context edges (cross-boundary leak that this ADR's bidirectional `.and()` filter prevents).
- **REFACTOR-350 NEW** — DEG-lineage cross-boundary edges silently filtered with NO doc disclosure. Operators viewing DEG-lineage cannot tell external context exists; the API contract should disclose the INTERNAL-only semantic.
- **REFACTOR-343 NEW** — DEG-lineage cross-owner CO-MEMBERSHIP enumeration. The bidirectional bound-set filter does NOT defend against this — once a user has the DEG ID, they read every connected-component subgraph of every owner's entities in the DEG. The decision codified here shapes the response; the consequence is the separately-tracked enumeration gap.

**Proposed action**: Promote to `adrs/drafts/deg-lineage-internal-edge-fetch.md` (new ADR). Document: (a) the three-decision composition (membership recursive / edge non-recursive / bidirectional bound-set / per-connected-component); (b) the contrast with per-entity lineage at the architectural level (different repository method, different filter shape, different response partition); (c) the INTERNAL-only semantic + the recommendation for "external context" use cases (per-entity endpoints on individual DEG members); (d) the response-shape commitment (per-connected-component, groups + groupsRelations always empty). Doc-side: the live `/developer-guides/api-reference/lineage` page should disclose the INTERNAL-only behaviour and the recommended workaround for external-context views. Cross-link REFACTOR-241 (the misleading OR-predicate as the maintainability risk this ADR's `.and()` filter is vulnerable to).

**Severity rationale**: MEDIUM — codebase-architectural decision shaping a distinct endpoint family with a distinct query plan; affects the API contract for every DEG-lineage consumer. Not HIGH because the consequence is bounded to the DEG-lineage endpoint; not LOW because the three-decision composition is load-bearing for maintainers reasoning about DEG-lineage refactors.
