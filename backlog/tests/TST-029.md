## Description

`IngestionDataEntitiesFilter` is the bean that enforces the per-collector token on `POST /ingestion/entities` (it throws `AccessDeniedException("Token is not correct")` when the resolved token mismatches — `IngestionDataEntitiesFilter.java:55-58`). The bean is `@ConditionalOnProperty(value = "auth.ingestion.filter.enabled", havingValue = "true")` (`IngestionDataEntitiesFilter.java:20`), and the shipped default for that property is `false` (`application.yml:48`, under `auth.ingestion.filter.enabled`). Net effect: in a default deployment — even with UI auth enabled — the ingestion API accepts anonymous writes because the filter bean is never instantiated.

This is the DOC-004 security-critical default (status `done`: the operator-facing caveat is now documented in `documentation` `configuration-and-deployment/enable-security`). But LSN-030 demands that a security finding documented as a caveat also carry a **regression pin** so the default cannot silently change without a test going red. No such pin exists today.

**Typed gate — characterization-pin (LSN-029).** This PINS the CURRENT shipped posture: `auth.ingestion.filter.enabled` defaults to `false`, i.e. the ingestion filter is OFF by default. It is GREEN today and goes RED the instant the default flips to `true` (the eventual security hardening) or the conditional/property name changes. It is NOT `@Disabled` — a disabled test is a blind pin (LSN-029). On RED: if the default was intentionally hardened to `true`, invert the assertion to pin the new secure default and re-tag `@regresses` (the anonymous-write hole the harden closes); if the property name/condition merely drifted, investigate.
