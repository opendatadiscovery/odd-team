## Description

The findings file's CCO-4 cross-cutting observation called for **ONE new doc page** covering the per-entity detail page surface — the load-bearing observation across F-176 (Overview tab composition), F-177 (Class/Type badges), F-178 (Header authoring affordances), F-206 (Badge widget encoding), and F-179 (Overview sidebar list truncation) is that the `DataEntityClassNameEnum` enum drives 7+ rendering decisions across the per-entity detail page, but no doc page exists tying enum members to their UI consequences. F-178's authoring caveats are covered by DOC-262 on the statuses page; F-208's per-entity stale-icon surface composition is covered by DOC-264; this item ships the canonical per-entity detail page documentation covering Overview composition + badges + sidebar truncation defects.

The existing `data-discovery/` sub-pages each describe ONE aspect of the detail page (`statuses.md` → status badge; `tagging.md` → Tags panel; `business-names.md` → business name; `groups-domains.md` → Groups panel; `attachments.md` → Attachments panel). There is no canonical home for the **composition** — the 12-panel Overview tab, the class-conditional rendering, the per-panel permission model, the class/type badge widget asymmetry, the Top-N + View-All sidebar truncation. CCO-4's recommendation is to add ONE umbrella page that ties these together; the per-aspect sub-pages already cited above continue to host their own aspect-specific deep dives, and the new page cross-links them.

**Section 1 — Per-entity Overview tab composition (F-176a + F-176d).** `Overview.tsx:67-147` (verified this run) composes the 12-panel Overview tab surface from seven `WithPermissionsProvider` wraps + two class-conditional gates. The 12 sub-panels: Description, Attachments, Metadata, General, Groups, Tags, Terms (the seven permissioned ones), plus OverviewStats (class-conditional render at `:91`), OverviewDataQualityReport (class+truthiness-conditional at `:105`), the Lineage thumbnail, the Recent Activity strip, and the per-class metadata block. No single composer-level `<WithPermissionsProvider>` declares the full panel-permission map — a reviewer cannot derive "which roles see which panels" from one grep.

**Section 2 — Per-class panel matrix (F-176a — class-conditional rendering).** `OverviewStats.tsx:23-83` switches over `entityClass.name` with `default: return null`. The panels visible on the Overview tab depend on the entity's class set: SET (Dataset) unlocks the Structure tab + DQ panel; TRANSFORMER shows the lineage anchor in its consumer/producer chains; CONSUMER unlocks the consumer-specific metadata; QUALITY_TEST unlocks the test-execution history; INPUT, RELATIONSHIP, ENTITY_GROUP each gate different panels. **Entities with an unknown class (`entityClasses === undefined`, `[]`, or an enum value the UI does not recognise) render no stats panel silently** (F-176c). A new ingestion that fails to set the class hits the silent-absence path on every detail page.

**Section 3 — DQ-zero vs DQ-loading indistinguishability (F-176b).** `Overview.tsx:105` (verified this run): `{isDataset && datasetQualityTestReport?.total ? <SectionContainer>...</SectionContainer> : null}`. A dataset with zero test reports renders no DQ section. A dataset whose `datasetQualityTestReport` thunk is still loading also renders no DQ section. Both cases produce the same DOM absence. Operators watching the Overview load cannot tell "this dataset has no tests" from "the platform is still fetching test results." Add either a loading skeleton OR an explicit "no quality tests configured" empty-state.

**Section 4 — Class badges and Type badges: rendering and gotchas (F-177a + F-177b + F-177c + F-206a + F-206b).** `DataEntityDetailsHeader.tsx:79-85` renders the entity's class badges via `entityClasses?.map(...)` using `<EntityClassItem entityClassName={...}/>`. Per-class colour coding is applied via `theme.palette.entityClass[$entityClassName]`. **Five gotchas**: (a) the badge has no tooltip explaining what each class unlocks (F-177a — operators discover by trial); (b) `EntityClassItem.tsx:13-29` renders empty when `entityClassName` is undefined → silent visual whitespace (F-206a); (c) `DataEntityDetailsHeader.tsx:74-75` wraps the badge row with `<Grid flexWrap='nowrap'>` → an entity with 4+ classes overflows without wrap (F-177c); (d) `EntityTypeItem.tsx:9` declares the union `DataEntityTypeNameEnum | 'DCT'` — the `'DCT'` string is hardcoded outside the OpenAPI-generated enum, with no comment explaining the special case (F-177b); (e) `EntityTypeItem.tsx:13-19` uses a uniform background colour with no per-type colour coding — asymmetric with the class badge which IS colour-coded (F-206b).

**Section 5 — Top-N + View All sidebar list truncation (F-179a + F-179b + F-179c).** The Tags, Terms, and Groups columns on the Overview tab cap at 20 visible items + a `View All (N)` toggle. Three defects: (a) `OverviewTags.tsx:54-65` runs `.slice(0, 20).sort(tagsCompare)` — the slice runs FIRST, so the importance-aware comparator only orders the truncated window (F-179a). An entity with 25 tags whose "important" tags sit at indices 22-24 renders top-20 in array order with no important tag visible. (b) `OverviewGroups.tsx:49-54` runs `.slice(0, 20).sort()` (bare, no comparator) — JavaScript's default `.sort()` stringifies via `toString` so `DataEntityRef[]` items all compare equal → the sort is a silent no-op (F-179b). (c) The `View All (N)` suffix is the ONLY visual signal that more than 20 items exist (F-179c) — if the operator does not notice the parenthetical count, they conclude the entity has 20 tags.

**Section 6 — Per-panel permission model (F-176d).** Seven `WithPermissionsProvider` wraps each carrying a different `allowedPermissions` array — Description / Attachments / Metadata / General / Groups / Tags / Terms. No central composer-level provider; the per-panel permission map is split across 7 sites in `Overview.tsx`. Operators auditing "what does role X see on the Overview tab" need to read every site.
