# TermDetails (Term detail page UI shell) — semantic understanding

## understanding

`TermDetails.tsx` (88 lines) is the root React component for the Term detail page (`/terms/:termId/{overview|linked-entities|linked-columns|linked-terms|query-examples}`) — a thin shell that (a) on mount fires ONE `fetchTermDetails({termId})` thunk + ONE `fetchResourcePermissions({resourceId: termId, permissionResourceType: TERM})` thunk (lines 37-45), (b) gates `TermDetailsHeader` (which carries the Edit + Delete affordances) behind `WithPermissionsProvider` with `allowedPermissions=[TERM_UPDATE, TERM_DELETE]` (lines 59-70), (c) renders `TermDetailsTabs` + `TermDetailsRoutes` unconditionally once the term is loaded (lines 71-72), and (d) routes back to `/termsearch/:termSearchId` after a successful `deleteTerm` dispatch (line 50). **Structurally the closest analog to `DataEntityDetails.tsx` (the canonical LSN-017 source)** — but the useEffect dep-array shape is materially DIFFERENT: TermDetails deps are `[termId]` ONLY (line 45), whereas DataEntityDetails deps include `details.status?.status` (DataEntityDetails.tsx:63 — a value DERIVED from the fetch response itself, causing the canonical doubling). TermDetails does NOT exhibit the LSN-017 shape — verified by reading lines 37-45 end-to-end + tracing every dep. The term's `definition` field flows through `Overview.tsx` → `TermDefinition.tsx` (lines 39-47 of Overview.tsx) → `<Markdown value={transformDescriptionToMarkdown(definition)} />` → `@uiw/react-md-editor`'s `MDEditor.Markdown` which uses `rehype-raw` (verified via `pnpm-lock.yaml:3900,5922,8843`) WITHOUT `rehype-sanitize` (Grep'd entire `odd-platform-ui/` returns ZERO matches for `rehype-sanitize` or `allowDangerousHtml`-disabling import) — **this extends the F-004 stored-XSS surface to TermDefinition.** The Delete CTA in `TermDetailsHeader` (lines 66-92 of header) wires to `handleTermDelete` which dispatches `deleteTerm` (thunks/terms.thunks.ts:39-55) → soft-delete via `ReactiveTermRepositoryImpl` inherited base (`UPDATE term SET deleted_at = NOW()` per ReactiveTermRepositoryImpl sidecar). The shell itself has no rendering branch for soft-deleted Terms: the page is reachable only by id resolution against `getTermDetails` which auto-filters `TERM.DELETED_AT IS NULL` (per ReactiveTermRepositoryImpl sidecar invariants), so a soft-deleted Term renders the AppErrorPage path (lines 80-83) via `isTermDetailsNotFetched`. **Linked-terms display** (the prompt's V0_0_91 schema-drift batch-N intersection): linked terms are loaded via `getTermDetailsDto` (the 12-JOIN repository hot path) which DOES NOT filter `term_to_term.deleted_at IS NULL` (per ReactiveTermRepositoryImpl sidecar known invariant — the V0_0_91-vs-V0_0_76 schema-drift facet); soft-deleted Terms that participate in `term_to_term` rows surface here IFF the TARGET Term itself is non-deleted — the asymmetric guard cited at ReactiveTermRepositoryImpl.java:427-433 (`TERM.DELETED_AT.isNull()` on target). This UI shell inherits the asymmetry transparently.

## bugs_limitations_corner_cases

- "**Double-fetch: shell + Overview both load the same TermDetails.** Lines 37-45 dispatch `fetchTermDetails({termId})`; Overview.tsx:19-21 uses `useGetTermByID({termId})` which is an INDEPENDENT fetcher (verified by reading Overview.tsx end-to-end + Grep'ing `useGetTermByID` returns it as a separate hook). When the user lands on `/terms/:termId/overview` (the default route per TermDetailsRoutes.tsx:46), TWO `GET /api/terms/{termId}` requests fire. **Critically: each backend GET runs the 12-JOIN `getTermDetailsDto` hot path** (per ReactiveTermRepositoryImpl sidecar known invariant — the 12 LEFT JOIN + 4 countDistinct + 7 jsonArrayAgg amplification). For typical Term catalogues with <100 linked entities this is sub-200ms per fetch; for a heavily-linked Term (say 500 linked DataEntities + 200 linked DatasetFields) the doubled fetch doubles the database load on every page-open. **THIS IS NOT THE LSN-017 SHAPE** (the trigger isn't a useEffect dep array; it's two independent components both reading the same data) — but it is a SIBLING class: **cross-component fetch duplication on a hot backend path.** Severity is MEDIUM because the backend cost is real but bounded; the fix is to consolidate to one fetcher (drop the Overview's `useGetTermByID` and read from Redux instead, OR drop the shell's `fetchTermDetails` and rely on Overview to fetch lazily). The reverse case (Overview alone — no shell fetch) would mean the Header lacks `name + updatedAt` until Overview lands; current architecture pre-fetches for header rendering." — evidence: TermDetails.tsx:37-45 + Overview.tsx:19-21 (the second fetch via `useGetTermByID`) + ReactiveTermRepositoryImpl.java:194-238 (the 12-JOIN hot path) — severity: MEDIUM

- "**`useTermsRouteParams` NaN propagation on malformed URL.** `parseInt(termId, 10)` at termsRoutes.ts:60 returns `NaN` if the URL segment is non-numeric (e.g. `/terms/abc/overview`). NaN flows into `useAppSelector(getTermDetails(NaN))` (line 32) which returns the empty fallback; `getResourcePermissions(TERM, NaN)` (line 34) similarly returns empty. The `fetchTermDetails({termId: NaN})` dispatch (line 38) hits `GET /api/terms/NaN` — backend returns 400 (NumberFormatException on path-variable bind) or 404 depending on the controller's path-variable parse. The `isTermDetailsNotFetched` becomes true → AppErrorPage shows — no crash, but the error path is unprincipled (it relies on the backend producing a 4xx). A defensive `if (isNaN(termId)) return <NotFoundPage />` would make the UX explicit." — evidence: termsRoutes.ts:60 + TermDetails.tsx:25, 32, 34, 38, 41 — severity: LOW

- "**`deleteTerm.fulfilled` slice reducer does NOT remove the term from `byId`.** terms.slice.ts:74-78 — only `allIds` is filtered. The deleted term's data lingers in `state.terms.byId[deletedId]` indefinitely (until full page reload). Since the user navigates AWAY immediately after delete (TermDetails.tsx:50), there's no observable consequence — the byId ghost is unreachable.
