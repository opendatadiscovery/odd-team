- **ADR-CANDIDATE-054** (NEW 2026-05-12F): The centerpiece data-entity detail read is a **read-as-write** operation — `getDataEntityDetails` runs inside `@ReactiveTransactional` and unconditionally increments `view_count` per call via `incrementViewCount` chained into the orchestration pipeline. The decision makes view-count tracking a first-class invariant of the detail read (powering `getPopular` ranking + recommendation panels), accepting that every read also touches the database write path
  - **Category**: promote
  - **Support**: surfaced by 2 sidecars (`getDataEntityDetails` batch F + `DataEntityServiceImpl` batch I primary source) — single occurrence but architecturally meaningful: the deliberate transactional coupling of a read endpoint with a write side-effect is unusual enough to surface as an explicit ADR

  - **Decision statement**: `DataEntityController.getDataEntityDetails` is the platform's only documented read endpoint that runs inside `@ReactiveTransactional` and performs a write side-effect as part of the read pipeline. `DataEntityServiceImpl.getDetails` (line 197) carries `@ReactiveTransactional`; the orchestration chain at lines 199-208 reads `getDetails` → enrich-class details (5-zip) → enrich-parents → enrich-details (4-zip) → `incrementViewCount` → `mapDtoDetails`. The increment fires `UPDATE data_entity SET view_count = view_count + 1 WHERE id = ?` via `ReactiveDataEntityRepositoryImpl.java:173-180` and the new value is reflected in the response's `DataEntityDetails.viewCount` field. The decision codifies: (a) view-count is platform state worth tracking (powers `getPopular` ranking + recommendation panel via `getMostPopular`); (b) read-call counting at the controller boundary is preferable to async aggregation or sampling — every detail render is precisely counted; (c) the transactional boundary ensures that a failed enrichment rolls back the increment, so the count reflects successful renders only; (d) **NEW 2026-05-19I**: incrementViewCount itself is FAIL-SOFT on missing-entity races via `.switchIfEmpty(Mono.just(dto))` (DataEntityServiceImpl.java:488-495) — the maintainer chose graceful degradation over throwing an error during a millisecond race; this is a deliberate sub-decision that completes the read-as-write design. Trade-off accepted: (i) hot-key write contention on popular entities (REFACTOR-201's perf consequence); (ii) trivial inflatability — a malicious client can script `GET /api/dataentities/{id}` to push an entity to the top of Popular (REFACTOR-201's correctness consequence); (iii) no HTTP-cache headers can be applied to this endpoint without breaking the count semantic (REFACTOR-200's cache-headers absence is partly defended by this ADR).
  - **Wisdom test**: PASS. The explicit `@ReactiveTransactional` placement + the chained `incrementViewCount` + the `viewCount` field's first-class presence on the published `DataEntityDetails` contract + the `getPopular` consumer endpoint are all positive design choices. The alternative (async view-count aggregation, e.g., a sampling counter or a queue-fed write path) would have decoupled the count from the read; the maintainer chose the synchronous in-transaction increment. Structural for the detail endpoint's identity as "read-write hybrid". The batch-I service-tier sidecar confirms the design choice at primary source — `getDetails` is THE single read method with @ReactiveTransactional out of 22 public methods on the service.
