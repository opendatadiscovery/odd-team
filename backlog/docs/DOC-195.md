## Description

`POST /ingestion/entities` is the load-bearing collector ingestion endpoint. Both the integrations pillar landing and the API reference are SILENT on every observable error condition. A custom-collector author writing retry-with-backoff logic against the public contract has no way to distinguish "I sent malformed data" from "platform crashed" — every distinction is needed for production-grade retry behaviour. Three substrate-grade gaps land in one revision.

**Facet 1 — 3 client-error conditions surface as HTTP 5xx (F-096a, CRITICAL).** Verified at primary source this run:
- **Duplicate ODDRN in batch** → `Collectors.toMap(DataEntityIngestionDto::getOddrn, identity())` at `IngestionServiceImpl.java:86` uses the DEFAULT throwing merger → `IllegalStateException: Duplicate key` → uncaught → HTTP 5xx.
- **Unknown `data_source_oddrn`** → `dataSourceRepository.getIdByOddrnForUpdate(...).switchIfEmpty(Mono.error(() -> new NotFoundException(...)))` at `IngestionServiceImpl.java:68-69` raises `NotFoundException` → uncaught at the ingestion controller (no `@ExceptionHandler` advice on this controller) → HTTP 5xx.
- **Oversized payload** → `DataBufferLimitException` from Spring's body codec → HTTP 5xx.

A collector author following the integrations doc writes retry-with-backoff on 5xx; the retry storm against a duplicate-ODDRN payload pegs the platform for the entire retry budget. Same shape for unknown-datasource. Spec returns 200 (`postDataEntityList` line 38-45) but the spec document declares 201 — separately covered by DOC-GAP-074-META and SPC-001.

**Facet 2 — `data_source_oddrn` row-lock held for FULL pipeline duration (F-096b, HIGH).** `dataSourceRepository.getIdByOddrnForUpdate(...)` issues a Postgres `SELECT ... FOR UPDATE` against the `data_source` row at the head of the `@ReactiveTransactional ingest(...)` pipeline (`IngestionServiceImpl.java:66-68`). The lock is held for the FULL pipeline duration — datasource resolution + 14-processor chain + OTLP export. Two concurrent collectors emitting to the SAME datasource serialise on the lock; the loser may exceed the transaction timeout → 5xx with **no `Retry-After` header**, no 429 signal.

**Facet 3 — `@Slf4j` annotation present, zero `log.*` calls in `IngestionServiceImpl.ingest` body (F-096c, MEDIUM).** `@Slf4j` at line 53 materialises a `log` SLF4J reference. The `ingest(...)` method body (lines 65-94) has ZERO `log.*` invocations — even at DEBUG. Operators looking at platform logs see only the exception trace, not the discriminator (collector-id, datasource-oddrn, entity count). The SRE response window is doubled: needs platform-side access to the application log to find the actual exception.
