## What

`LoginFormSecurityConfiguration.java` has three security-posture defects that compound under LOGIN_FORM auth-mode. The shipped docs (DOC-234 caveat companion) acknowledge LOGIN_FORM as dev/demo, but the divergence from OAUTH2 / LDAP siblings is significant enough that LOGIN_FORM should either honour the same posture or be code-side fail-fast under any production-looking configuration.

**Defect 1 — `SECURITY_RULES` is INERT under LOGIN_FORM.** Line 55-57 does `.authorizeExchange(spec -> spec.pathMatchers(permittedPaths).permitAll().pathMatchers("/**").authenticated())` and STOPS — no chained `.authorizationCustomizer(...)` call. Contrast `OAuthSecurityConfiguration.java:98` + `LDAPSecurityConfiguration.java:145` which both wire `new AuthorizationCustomizer(permissionService, extractors)`. Operators authoring Policies via Management UI in LOGIN_FORM mode get a fully-built RBAC configuration that the live auth chain SILENTLY IGNORES (because every LOGIN_FORM user is already ADMIN-authority — line 81: `.authorities(grantedAuthorityExtractor.getAuthorities(true))`).

**Defect 2 — CSRF unconditionally disabled.** Line 54: `.csrf(ServerHttpSecurity.CsrfSpec::disable)`. A logged-in browser session is the canonical CSRF target. Compounds with the platform's lack of `SameSite=Strict` directive (F-087b) + non-Secure cookies on non-HTTPS deployments — triple compounding.

**Defect 3 — `auth.login-form-redirect` open-redirect.** Line 41 reads `@Value("${auth.login-form-redirect:}")` with empty default; line 43 invokes `parseURI(redirectUri)`; line 88-90 calls `URI.create(redirectUri)` with NO scheme or host allowlist. Helm-chart deployments where this value is templated from upstream env-var pipelines have no platform-side boundary against attacker-controlled values.

## Why it matters

LOGIN_FORM mode is shipped as dev/demo, but it is in production use in real deployments (Helm charts ship with `auth.type: LOGIN_FORM` overridable). The triple compounding means a logged-in operator visiting an attacker-controlled page triggers state-changing requests via CSRF; the open-redirect amplifies into a phishing surface; SECURITY_RULES inertness invalidates any Policy-table-based defense.

Beyond LOGIN_FORM specifically: the silent-divergence pattern (LOGIN_FORM behaves DIFFERENTLY from OAUTH2/LDAP without the doc warning operators) is the LSN-001 / LSN-002 family — silent defaults that operators following published guidance fall off.

## Suggested fix

**Thread A — Wire AuthorizationCustomizer OR fail-fast (Defect 1).**

Option A1 — wire AuthorizationCustomizer in LOGIN_FORM the same way OAUTH2/LDAP do:

```java
// Add after .authorizeExchange(...) at line 57
.authorizationManager(new AuthorizationCustomizer(permissionService, extractors))
```

Side-effect: Policy/Role tables become live in LOGIN_FORM. Operators with non-empty Policy tables get the intended gating. Operator-side: Policies that worked-through-bypass before now produce 403s.

Option A2 — fail-fast on boot if Policies exist:

```java
@PostConstruct
void warnIfPoliciesExist() {
    long policyCount = policyRepository.count().block();
    if (policyCount > 0) {
        log.warn("LOGIN_FORM auth-mode is dev/demo only. Policies exist ({}), but AuthorizationCustomizer is NOT wired in LOGIN_FORM. Switch to OAUTH2 or LDAP.", policyCount);
    }
}
```

Recommended: Option A2 first (low-risk warn-only); Option A1 as a follow-up when the warn-period reveals zero impact OR after operator migration plan.

**Thread B — Conditional CSRF enable (Defect 2).**

Replace the unconditional `.csrf(...::disable)` with a conditional CSRF that's enabled by default and disable-able via `@ConditionalOnProperty(name = "auth.login-form.csrf.enabled", havingValue = "false")`. Requires SPA-side handling — either double-submit cookie OR `X-Requested-With: XMLHttpRequest` header on all state-changing requests.

Realistic phasing: ship the CSRF token endpoint + SPA-side handling first; THEN enable conditional CSRF in a later release.

**Thread C — Allowlist `auth.login-form-redirect` (Defect 3).**

```java
@Value("${auth.login-form-redirect:}")
private String redirectUri;
@Value("${auth.login-form-redirect.allowlist:}")
private List<String> redirectAllowlist;  // host:port entries, comma-separated

private URI parseRedirectUri() {
    if (redirectUri.isEmpty()) return null;
    URI uri = URI.create(redirectUri);
    if (!redirectAllowlist.isEmpty() && !redirectAllowlist.contains(uri.getHost() + ":" + uri.getPort())) {
        throw new IllegalStateException("Redirect host " + uri.getHost() + " not in auth.login-form-redirect.allowlist");
    }
    return uri;
}
```

Boot-time validation rather than per-request — the redirect target is configuration-time, not request-time.
