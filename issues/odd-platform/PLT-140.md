## What

`TermServiceImpl.listByTerm` (the Term Detail **Linked Terms** reverse-lookup read) returns a **fabricated `pageInfo`**: it hardcodes `hasNext=false` and sets `total` to the *returned page's row count* (`item.size()`), not the true link count. This is an API-contract wart visible to direct consumers of `GET /api/terms/{term_id}/linked_terms`. **It does not cause the user-facing harm the earlier revision of this issue claimed** - both of those claims were falsified on a full end-to-end trace (see below).

This issue originally asserted two HIGH user-facing defects. Both are FALSE:

1. ~~`GET /api/terms/{term_id}/term` returns 500/405 and the tab hangs (overloaded path stem).~~ **FALSIFIED.** The reverse-lookup read is `GET /api/terms/{term_id}/linked_terms` (`openapi.yaml:2888`, `operationId: getTermLinkedTerms`), a distinct path that returns `200`/`LinkedTermList`. The `/api/terms/{term_id}/term` stem carries ONLY the link write (`POST`, `:2945`) and `/term/{linked_term_id}` the unlink write (`DELETE`, `:2968`) - there is no GET on `/term`, no path collision with the read, and the FE never calls `/term` for the read. The read does not error or hang.
2. ~~`listByTerm` hardcodes `hasNext=false` so terms #51+ are unreachable via the UI's infinite scroll (LSN-024 silent-truncation).~~ **FALSIFIED.** The FE does **not** consume the backend `hasNext`. `useGetTermLinkedTerms` wraps each page through a client-side `addNextPage` helper that recomputes pagination as `hasNext = (size === response.pageInfo.total)` (`lib/hooks/api/terms.ts:63`). Because the backend *also* fakes `total = page-size`, a full first page (50 rows) yields `total=50`, so the FE computes `hasNext = (50 === 50) = true`, sets `nextPage=2`, and the infinite scroll **does** fetch page 2 (the repository applies a real `LIMIT/OFFSET`, `ReactiveTermRepositoryImpl.java:494-495`, so page 2 returns rows 51+). The list terminates correctly when a short final page makes `size !== total`. Terms #51+ ARE reachable in the UI.

So the genuine residue is narrow: the backend `pageInfo` is wrong for direct API consumers, and the FE only works because a second bug (client-side `size === total` heuristic) happens to cancel the first. That coupling is fragile but currently correct end-to-end.

## User-facing impact

**None in the shipped UI** - verified-trace 2026-06-10 end-to-end. The Linked Terms tab pages past 50 correctly because `LinkedTermsList.tsx` drives `InfiniteScroll next={fetchNextPage} hasMore={hasNextPage}` (`:66-69`) off `useInfiniteQuery`, whose `getNextPageParam` reads the **client-recomputed** `nextPage` (`terms.ts:91`, derived in `addNextPage` from `size === total`, `:63`), not the backend `hasNext`. Impact is confined to direct consumers of `GET /api/terms/{term_id}/linked_terms`, who receive `total = <returned page row count>` (never the true total) and `hasNext = false` always - a contract that mis-describes the collection. There is no hang, no 500, no truncated tab.

Remaining latent risk (no current user symptom): the FE's correctness depends on the backend continuing to fake `total = page-size`. If `listByTerm` is "fixed" to return the *true* total without also updating the FE heuristic, `addNextPage`'s `size === total` test would become `50 === <trueTotal>` = false on the first page, and the UI would then truncate at 50. The two changes must land together (see fix).

## Why it matters

Low severity. The backend `pageInfo` is an incorrect API contract for non-UI consumers, and the system is only end-to-end-correct via an accidental cancellation of two bugs - a latent footgun for the next maintainer who touches either side. No operator-visible defect today.

## Suggested fix

Fix both sides together, or the UI regresses (see Remaining latent risk):

1. **Real pagination in `listByTerm`** - compute `total` from a COUNT over the term-to-term relation and `hasNext` from `(page * size) < total`, returning a truthful `pageInfo` (mirrors how the sibling `getTermLinkedColumns` / linked-entities reads should also behave).
2. **Update the FE to consume the real `hasNext`** - replace the `addNextPage` `size === total` heuristic (`terms.ts:63`) with `getNextPageParam` reading the backend `pageInfo.hasNext` directly, so the client no longer depends on `total` being the page size. (The same `addNextPage` helper is shared - audit other callers.)
3. Add an integration test (contract / WebTestClient) asserting `total` equals the true link count and `hasNext` is true when >50 links exist (regression anchor for the contract, and for the FE heuristic).

## How discovered

Surfaced by the LSN-030 feature-reflection rollout (feature-reflector v0.3.0), feature F-152 (Term Detail - Linked Terms reverse-lookup), hypotheses H-002 (reverse read 500/405) + H-006 (hardcoded hasNext=false). Consolidated 2026-06-04 (`findings/feature-reflection-triage/2026-06-04-consolidated.md`, cluster N4).

**Corrected 2026-06-10 after the user-facing verification sweep** traced both claims end-to-end against `../odd-platform`:
- The "overloaded `/term` path 500/405" claim (H-002) was a backend-only inference; the OpenAPI spec shows the read lives on the separate `/linked_terms` path and the FE calls it there (`getTermLinkedTerms`). No collision, no error.
- The "silent truncation past 50" claim (H-006) was falsified by reading the FE: `addNextPage` recomputes `hasNext = size === total` client-side and never reads the backend flag, so the UI pages correctly. The surviving defect is a backend contract wart only; severity HIGH -> LOW; `user_facing_verified` flipped to true (every load-bearing claim is now code-settled). Same failure mode as PLT-176/PLT-167: a UI claim shipped without reading the frontend.
