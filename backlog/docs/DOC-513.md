# DOC-513 — the API reference is one reference, presented two ways

## Failure shape

**Parallel surfaces with drift**, inside a single reference section. A reader moving between sibling pages of
the same reference meets two different table contracts, and on two pages loses a column the other eight give
them.

## The split

| Shape | Pages |
|---|---|
| `\| Method \| Path \| Operation ID \| Purpose \|` (4 columns) | `alerts`, `data-collaboration`, `directory`, `genai`, `glossary`, `integrations`, `lineage`, `reference-data` — **8** |
| `\| Method + Path \| Operation \| …` (2-3 columns, **no Operation ID column**) | `query-examples` (16 endpoints), `relationships` (3 endpoints) — **2** |

`query-examples.md` partially compensates by inlining a few operation ids in prose — *"(operation
`queryExamplesSearch`)"* — which is the tell that the field is wanted and the column is missing;
`relationships.md` puts the operation id in the second column but calls it `Operation`, so the same value
appears under three different headings across the section.

## Why the Operation ID column is the substantive half

It is not decoration. The operation id is the join key between a documented row and everything generated from
the spec — the Java controller interface method (ADR-0001, generated controller interfaces), the TypeScript
client method, and the `openapi.yaml` block a reader greps to check a field. A developer working from
`query-examples.md` has to guess or grep for it; the same developer on `glossary.md` reads it off the row.

## Also, one placeholder abbreviation

`lineage.md:42/48` writes `GET /api/dataentitygroups/{id}/lineage`. The spec's path template is
`/api/dataentitygroups/{data_entity_group_id}/lineage` (`odd-platform-specification/openapi.yaml:2809`), and
every other api-reference page uses the spec's exact placeholder names (`{data_entity_id}`, `{term_id}`,
`{lookup_table_id}`, `{relationship_id}`). The endpoint is real and correctly described — only the template
string is abbreviated, which breaks a `grep` from the page into the spec.

## Recommended fix

Normalise the two pages onto the 4-column shape used by the other eight, filling the Operation ID column from
the spec, and expand `{id}` to `{data_entity_group_id}` on `lineage.md`. No content changes — the endpoint
descriptions on both pages are accurate.

## What this sweep also established — the section is otherwise clean

Every documented endpoint path across all ten api-reference pages was mechanically extracted and checked
against `odd-platform-specification/openapi.yaml` (166 paths). **Every documented path resolves.** The four
that did not match a spec path on the first pass were each run down and are all correct:

* `/ingestion/alert/alertmanager` (`alerts.md`) — the page states outright that it is **not** covered by the
  OpenAPI spec because the payload is a Prometheus-defined contract.
* `/api/slack/events` (`data-collaboration.md`) — same, a Slack Events API contract.
* `/ingestion/entities/{degOddrn}/children` (`lineage.md`) — an ingestion-surface sibling cited inside a
  comparison table, correctly labelled as such.
* `/api/dataentities` (`relationships.md`) — appears only in prose as a visibility-rules comparison, not as a
  documented endpoint.

Worth recording alongside the finding: a reference section whose every path checks out against the contract is
the normal state here, and this item is a presentation inconsistency, not an accuracy defect.
