- **REFACTOR-417** (NEW 2026-05-19O): IngestionDataEntitiesFilter path matcher is HARD-CODED to the exact literal `/ingestion/entities` (no wildcard, no property injection, no regex). A new endpoint `POST /ingestion/entities/batch` / `/ingestion/entities/v2` / `/ingestion/entities/stream` would silently BYPASS authentication. No compile-time signal, no test asserting the path scope, no `@docs` annotation pinning the literal
  - **Category**: hard-coded-path
  - **Surfaced by**:
    - `IngestionDataEntitiesFilter.md:bugs_limitations_corner_cases.[1]` (MEDIUM future-regression risk)
  - **Statement**: `IngestionDataEntitiesFilter.java:28` constructs the path matcher as `new PathPatternParserServerWebExchangeMatcher("/ingestion/entities", HttpMethod.POST)` — the path is a hard-coded literal string. There is no `@Value("${ingestion.filter.path:...}")` injection, no central path-registry, no wildcard, no regex. A future API addition like `POST /ingestion/entities/batch` (a hypothetical batch-mode endpoint) OR `POST /ingestion/entities/v2` (a hypothetical v2 of the contract) would NOT be matched by this filter, and would BYPASS the auth check. There is no compile-time signal, no test asserting the path scope, no `@docs` annotation pinning the literal. The naming convention (`IngestionDataEntitiesFilter` ↔ `/ingestion/entities`) is the only documentation; ADR-CANDIDATE-027 captures the convention but doesn't defend against the regression.
  - **Evidence**: `IngestionDataEntitiesFilter.java:28` (literal string `"/ingestion/entities"`)
  - **Existing-ADR-or-implied-prescription**: ADR-CANDIDATE-027 (ingestion-token opt-in + hard-coded path matcher per-subclass) — the hard-coded pattern IS the design; the gap is the absence of a test or compile-time guard against the regression.
  - **Proposed remedy**: Either (a) add an integration test that asserts the filter intercepts `POST /ingestion/entities` and DOES NOT intercept sibling paths (`/ingestion/entities/batch`, `/ingestion/entities/v2`); fail the test if a future endpoint is added without an explicit filter siblings. (b) Change the matcher to a wildcard `new PathPatternParserServerWebExchangeMatcher("/ingestion/entities/**", HttpMethod.POST)` — catches all future variants but loses the per-endpoint-class precision. (c) Add a startup boot-time check that enumerates `/ingestion/*` paths exposed by controllers and asserts each is covered by a filter (or the AlertManager whitelist). The maintainer should pick based on the test-vs-runtime-vs-wildcard trade-off.
  - **Severity rationale**: MEDIUM — future-regression risk. Not a bug today; latent vulnerability surface.
  - **Suggested backlog grouping**: `Ingestion hardening sprint` (paired with REFACTOR-080 hardcoded path matcher from batch B — consolidate into one path-coverage hardening review)
