- **ADR-CANDIDATE-030** (NEW 2026-05-12C): Each auth mode is wired by an EXPLICIT `SecurityWebFilterChain` bean as statement-of-intent — not by relying on Spring Boot's autoconfiguration fallthrough. The four `*SecurityConfiguration` classes form an enum-by-construction with mutually-exclusive `@ConditionalOnProperty(value="auth.type", havingValue=...)` gates and NO `matchIfMissing=true` on any of them; mode selection is by enumeration, not chain composition
  - **Category**: promote
  - **Support**: surfaced by 4 sidecars across the auth-mode family (DisabledAuthSecurityConfiguration.java:10 + LoginFormSecurityConfiguration.java:31 + OAuthSecurityConfiguration.java:71 + LDAPSecurityConfiguration.java:51) — the parallel structure across four sibling files IS the intent anchor
  - **Surfaced by**:
    - `odd-platform__java__DisabledAuthSecurityConfiguration__config-key-consumer__auth_type@L10.md:implicit_adrs.[1]` ("The DISABLED mode is intentionally a stripped-down permit-all chain... rather than 'no SecurityWebFilterChain bean at all'... The bean exists and explicitly calls .csrf(...disable) followed by .anyExchange().permitAll(). A 'no bean' approach would have produced the same runtime behaviour (Spring Boot autoconfigures a permit-all reactive chain when none is user-defined), so the maintainer chose to author an explicit chain to make the DISABLED posture STATEMENT-of-intent rather than emergent behaviour.")
    - `odd-platform__java__DisabledAuthSecurityConfiguration__config-key-consumer__auth_type@L10.md:implicit_adrs.[2]` ("All four `*SecurityConfiguration` classes are mutually exclusive by `@ConditionalOnProperty(value=\"auth.type\", havingValue=\"...\")` without `matchIfMissing`. The design is 'pick exactly one of four modes, otherwise nothing wires' — a mode selection by enumeration, not by chain composition.")
  - **Decision statement**: ODD's auth-mode design is **enum-by-construction** rather than composition-by-chain. The four `*SecurityConfiguration` classes (Disabled / LoginForm / OAuth / LDAP) each author an explicit `SecurityWebFilterChain` bean gated by `@ConditionalOnProperty(value="auth.type", havingValue="<MODE>")` with NO `matchIfMissing` — only one of the four registers at any given boot. The DISABLED mode in particular constructs an EXPLICIT permit-all chain rather than relying on Spring Boot's autoconfiguration fallthrough — the maintainer's signal that the permit-all posture is a deliberate statement-of-intent, not emergent default behaviour. The decision has three structural consequences: (a) adding a new auth mode is an add-a-class change (no central dispatcher to modify); (b) typoed / empty `auth.type` produces no security chain (fall-through to Spring Boot's reactive-security defaults — REFACTOR-098 captures this); (c) the four parallel files duplicate boilerplate (CSRF disable, permit-all WHITELIST_PATHS, `.authenticated()` fall-through) — the maintainer accepted some duplication for the discoverability of per-mode shapes.
  - **Wisdom test**: PASS. The cross-file parallel structure (4 files, identical pattern) is the intent anchor; the DISABLED mode's choice to author an explicit chain rather than rely on Spring Boot defaults is a positive design statement; the absence of `matchIfMissing` on every gate is consistent with the enum-by-construction model. Structural for every future auth-architecture change.
  - **Evidence**:
    - DisabledAuthSecurityConfiguration.md says: "DisabledAuthSecurityConfiguration.java:13-18 (the explicit-chain construction itself as intent anchor — chose to author rather than rely on autoconfiguration fallthrough)"
    - DisabledAuthSecurityConfiguration.md says: "DisabledAuthSecurityConfiguration.java:10 + LoginFormSecurityConfiguration.java:31 + OAuthSecurityConfiguration.java:71 + LDAPSecurityConfiguration.java:51 (four parallel `@ConditionalOnProperty(value=\"auth.type\", havingValue=\"...\")` annotations consistently authored across the four sibling files)"
  - **Existing ADR**: none. Composes with ADR-CANDIDATE-025 (AnyNestedCondition idiom — the disjunction-when-needed companion to enum-by-construction) and ADR-CANDIDATE-024 (AppInfo reporter-not-reactor — the single `@Value` consumer that reads the raw enum string). Folding into a unified "auth.type runtime switch architecture" ADR family is a strong triage option.
  - **Co-surfaced gaps** (link from `refactoring-scopes.md`): REFACTOR-098 (missing-key fall-through on `auth.type` — no `matchIfMissing` means typo'd or empty value produces no bean from any mode), REFACTOR-073 (no boot-time security-posture validator — strengthens to 4-sidecar triangulation).
  - **Proposed action**: Promote to `adrs/drafts/auth-mode-enum-by-construction.md` (new ADR). Document the explicit-chain-as-statement-of-intent rationale (DISABLED's permit-all is authored rather than defaulted — operators reading the code see a clear "we chose to permit-all" signal). Cross-link with ADR-CANDIDATE-025 (AnyNestedCondition for disjunctive matching) and ADR-CANDIDATE-029 (DISABLED-as-default). The ADR's existence does NOT defend the missing-`matchIfMissing` consequence (REFACTOR-098); the maintainer must explicitly decide whether to add `matchIfMissing=true` on the DISABLED class (keeping the existing default) or to add a `FailFastSecurityConfiguration` that triggers when `auth.type` is empty/invalid.
  - **Severity rationale**: MEDIUM — pattern-shaping decision. Future auth mode additions (e.g. SAML, JWT) should reuse this idiom; future maintainers reading the four files should understand the enum-by-construction stance to avoid "let's add a fifth mode via chain composition" PRs.
