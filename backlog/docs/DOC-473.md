## Description

Two commits that describe **unreleased 0.29.0** behaviour are on the **published** documentation `main`
(`git@github.com:opendatadiscovery/documentation.git`), and the change is **LIVE** on
`docs.opendatadiscovery.org`. Per the release-train model (`adrs/drafts/release-train-doc-gating.md`,
G-C11), unreleased-behaviour docs must live ONLY on `release/{version}` and publish at the release gate —
never on `main`. The live manual must describe the **latest published release** (0.28.0), not unshipped
behaviour. This is the LSN-034 class, made live.

**Confirmed live (2026-06-19):** `curl -sL https://docs.opendatadiscovery.org/data-quality/test-run-history`
→ 200, body carries the `316dd14` copy ("**Before 0.29.0** …", "RUNNING is a **first-class** status") and
**no longer** carries the danger caveat "The page returns HTTP 500 while a test is currently running". A
0.28.0 operator — the current release — whose DQ test is in flight still hits that 500, but the published
page now tells them it is "fixed in 0.29.0" and has removed the workaround. Actively-misleading documentation
on the live manual (Priority Order #1, Critical).

**The two commits on `origin/main`:**
- `316dd14` docs(data-quality): Test Run History — RUNNING first-class in 0.29.0 (no HTTP 500). Removed the
  HTTP-500-while-running danger caveat. (#1757 / CTRIB-024 — the code fix is in **DRAFT PR #1793, unmerged**;
  0.29.0 not shipped.)
- `fb03ce3` docs(lookup-tables): retire the list-truncation + rename-audit-silence caveats (fixed in 0.29.0).
  Removed two caveats still true for 0.28.0. (#1753 / CTRIB-023 — the code fix merged to odd-platform main
  `525200f9` but is `pending-release`; 0.29.0 not shipped.)

**Train topology is inconsistent (evidence the push-to-main was unintended):** `origin/release/0.29.0` is at
`fb03ce3` — i.e. the train branch has the lookup-tables commit but is **missing** `316dd14`; meanwhile
`origin/main` has **both**. So the test-run-history 0.29.0 doc is on `main` but not even on the train it was
supposed to ride; the lookup-tables 0.29.0 doc is on both. The intended state (per the CTRIB-023/024 ledgers'
`docs_routing`) is: both commits ONLY on `release/0.29.0`, neither on `main` until the 0.29.0 release gate.

## Decision (2026-06-19): RE-GATE — prepared locally, awaiting the maintainer's push

The maintainer chose **re-gate** (forward-only). Prepared in the local `documentation` repo (all **UNPUSHED**;
push is the maintainer's per the agreed split):

- **`main` → `24c7040`** — two forward-only reverts: `git revert 316dd14` (test-run-history) + `git revert
  fb03ce3` (lookup-tables). Verified: `docs/data-quality/test-run-history.md` + `docs/master-data-management/
  lookup-tables.md` are now **byte-identical to `cf44b04`** (the 0.28.0-truth baseline) — `git diff cf44b04 HEAD
  -- <both pages>` is empty; the HTTP-500-while-running caveat and the lookup-tables truncation/rename-audit
  caveats are back. No force-push, no history rewrite.
- **`release/0.29.0` → `23d7a3c`** — fast-forwarded from `fb03ce3` so the train now carries all three 0.29.0
  doc commits (`fb03ce3` lookup-tables + `316dd14` test-run-history + `23d7a3c` dashboard). The train is
  internally consistent (test-run-history = seven statuses; dashboard explains the six-vs-seven).

**Push (maintainer):**
```
git -C ../documentation push origin main              # 316dd14 -> 24c7040 (+2 reverts); restores the live 0.28.0 manual
git -C ../documentation push origin release/0.29.0    # fb03ce3 -> 23d7a3c (+316dd14, +23d7a3c)
```
Then re-verify live: `curl -sL https://docs.opendatadiscovery.org/data-quality/test-run-history` should once
again carry the "returns HTTP 500 while a test is currently running" danger caveat.

## ⚠️ Release-gate consequence (do NOT plain-merge the train into main at 0.29.0)

Because `main` now holds *reverts* of `fb03ce3`+`316dd14`, a plain `merge release/0.29.0 -> main` at the 0.29.0
release gate will **NOT** re-publish the 0.29.0 content (the merge-base is `316dd14`; only `main` re-touched
those two files, via the reverts, so the reverts win and the pages stay at 0.28.0). The release-train-merge
step for 0.29.0 MUST instead **take the train's doc state** for these pages — recommended:
```
# on main, at the 0.29.0 release gate:
git checkout release/0.29.0 -- docs/data-quality/test-run-history.md \
                               docs/data-quality/dashboard.md \
                               docs/master-data-management/lookup-tables.md
git commit -m "docs: publish 0.29.0 Test Run History + Dashboard + Lookup Tables (release gate)"
```
(equivalently `git revert 2e033d7 24c7040` to revert-the-reverts, then bring `23d7a3c`). `playbooks/release-train-merge.md`
should encode this for any page that was reverted-on-main pending its release.

## Recommended remediation — paths considered (path 1 chosen)

This is a history operation on the **public** `main` of a published manual; it is **not** something an agent
should execute unilaterally (destructive/irreversible-on-public-branch; needs the maintainer's strategy call
AND push authority). Two viable paths:

1. **Re-gate (recommended):** `git revert fb03ce3 316dd14` on `main` (forward-only, no force-push), restoring
   the 0.28.0-correct caveats on the live manual; ensure BOTH commits live on `release/0.29.0` (cherry-pick
   `316dd14` — and this item's `23d7a3c` dashboard fix — onto the train, which currently lacks them). The
   0.29.0 release gate then merges the train to `main` when 0.29.0 actually ships.
2. **Accept + fast-track (only if 0.29.0 is shipping imminently):** leave the docs on `main` and ship 0.29.0
   now so the live manual matches a published release. Only valid once odd-platform 0.29.0 is tagged/released
   and PR #1793/#1792 are merged+released — today they are not.

Until one is taken, the live manual misleads every 0.28.0 operator who hits the in-flight-run 500 or the
lookup-tables truncation.
