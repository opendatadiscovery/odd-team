## What

`ODDOAuth2Properties.java:32` declares the `provider` field on `OAuth2Provider` as type `String` instead of the `Provider` enum. A typo like `provder: google` (missing `i`) silently routes through generic OIDC discovery - every `*UserHandler.shouldHandle` check fails on the typo'd value, so the handler chain falls through to `CustomOIDCUserHandler`. No admin path; no fail-fast.

The only validation today is `ODDOAuth2Properties.validate()` (`@PostConstruct`, `:16-28`), which throws only when `clientId` or `provider` is **empty** (`StringUtils.hasText`) - it does NOT check enum membership. So an empty `provider` fails fast, but a non-empty typo passes validation and falls through. The fallthrough is concrete: `CustomOIDCUserHandler.shouldHandle` (`:28-34`) returns `!providers.contains(provider.toLowerCase())` where `providers` is the lower-cased set of `Provider` enum names - i.e. it claims any value NOT in the enum, including every typo. `OAuthSecurityConfiguration.getProviderByProviderId` (`:199-201`) feeds the raw `provider` string into that `shouldHandle` selection.

Operator-visible: typo in `provider: Googel` silently produces a Custom OIDC deployment that "appears to be Google" - operator's admin-detection config (admin-groups / admin-principals) doesn't fire; operator's mental model "I'm running Google OAuth" is wrong.

## User-facing impact

- Verified by BE trace 2026-06-10: `OAuth2Provider.provider` is `String` (`ODDOAuth2Properties.java:32`); the only guard is the `@PostConstruct validate()` non-empty check (`:25-27`), which a typo passes. `CustomOIDCUserHandler.shouldHandle` (`:28-34`) explicitly claims every value not in the `Provider` enum, so a typo'd provider is enriched by Custom OIDC, never by the intended provider handler. Static trace consistent; not driven (needs an OAUTH2 stack with a real IdP) - remaining check: a boot with `provider: <typo>` to observe the Custom OIDC path taken and admin-detection not firing.
- Consequence (operator, not end-user): authentication still works (Custom OIDC discovery succeeds against any compliant IdP), but provider-specific behaviour - admin-group / admin-principal promotion (`AbstractOIDCUserHandler.java:33-55`), provider logout-revocation - silently does not apply. A user the operator expected to be promoted to admin via provider groups stays a plain USER. The failure is "looks like it works, admin detection doesn't."
- Auth mode: OAUTH2 only (`auth.type=OAUTH2`); the per-client `provider` value selects the user handler.

## Why it matters

Medium (unchanged) - a silent boot-time fallback that mis-routes the provider handler: the operator gets a working login but loses provider-specific admin promotion / logout-revocation with no error, and their mental model of which provider is running is wrong. The most operator-frustrating shape of failure (appears healthy; a security-relevant capability - admin detection - silently absent).

## Suggested fix

Change the field type from `String` to `Provider`:

```java
// ODDOAuth2Properties.java - before
public class OAuth2Provider {
    private String provider;
    // ...
}

// (after)
public class OAuth2Provider {
    private Provider provider;
    // ...
}
```

Spring Boot's `@ConfigurationProperties` binding fails-fast at startup if the configured `provider` value is not a valid `Provider` enum constant. Operator sees a clear error message: `Cannot bind value 'provder' to enum Provider - valid values are: COGNITO, GITHUB, GOOGLE, ODD_IAM, AZURE, CUSTOM_OIDC`.

Note: this requires adding a `CUSTOM_OIDC` enum value if Custom OIDC is intentionally supported as a configurable provider type (currently it's the implicit fallback). Two paths:

- **Option A**: add `CUSTOM_OIDC` to the Provider enum; operators must EXPLICITLY set `provider: CUSTOM_OIDC` for Custom OIDC routing.
- **Option B**: keep `CustomOIDCUserHandler` as the implicit fallback for `provider: null`; require non-null provider to be a valid Provider value.

Recommended Option A - explicit > implicit. Operators choosing Custom OIDC are doing so deliberately; making it explicit forces the choice + eliminates the typo fallback.

Coordinated with PLT-071 (Okta + Keycloak handlers). After PLT-071 adds `OKTA` + `KEYCLOAK` to the Provider enum, PLT-082's enum coverage grows to 7 values matching the doc-claimed 7 providers.
