- **ADR-CANDIDATE-053** (NEW 2026-05-12E): Policy document JSON Schema validation is enforced **at WRITE time, not at READ time** — `PolicyJSONValidator` loads `schema/policy_schema.json` once at construction (V2019-09 `JsonSchemaFactory`) and validates the inbound `policy` text per `create` / `update` invocation, raising `IllegalArgumentException` on schema violations BEFORE any DB write. The persisted `policy` text column is schema-valid by construction; read paths can trust the shape without re-validation
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar (`createPolicy`) but the structural shape applies to every persistence path through `PolicyServiceImpl` (the validator runs unconditionally on both `create` at line 64 and `update` at line 73)
  - **Surfaced by**:
    - `odd-platform__java__PolicyController__controller-method__createPolicy.md:implicit_adrs.[1]` ("Policy bodies are validated against a bundled JSON Schema at write-time, not just at read-time, ensuring the persisted `policy` text column is always schema-valid against the V201909 schema bundled with the running build" — evidence: PolicyJSONValidator.java:18-22 (loads `schema/policy_schema.json` once at construction) + PolicyJSONValidator.java:24-33 (validates per request, raises IllegalArgumentException on non-empty errors) + PolicyServiceImpl.java:64 (validator invoked before any persistence) — intent_anchor: the validator is named `PolicyJSONValidator` (not `PolicyValidator` or `PolicyShapeChecker`), is annotated `@Component` so it lives in the DI container, and is invoked unconditionally on the create AND update paths)
  - **Decision statement**: ODD treats the policy JSON document as a structured DTO subject to JSON Schema validation at every persistence boundary. The validator is a Spring `@Component` (`PolicyJSONValidator`) that loads `schema/policy_schema.json` once at construction using `JsonSchemaFactory.getInstance(SpecVersion.VersionFlag.V201909)`. Both `PolicyServiceImpl.create` (line 64) and `PolicyServiceImpl.update` (line 73) call `policyJSONValidator.validate(...)` BEFORE invoking the repository. On non-empty validation errors, the validator throws `IllegalArgumentException("Policy is not valid: " + errors)` — the request is rejected before any DB write. The decision codifies: (a) the `policy` text column is schema-valid by construction across all rows ever persisted; (b) read paths (`getPolicy`, `getPolicyList`, the `getCurrentUserPolicies` join in `PolicyServiceImpl.java:103-107`) can trust the shape WITHOUT re-validation; (c) operators authoring policies via the UI's `Management → Access Management → Policies` editor receive immediate schema-validation feedback. Trade-off accepted: any future schema change (e.g. adding a new `permission` constant to the schema's `MANAGEMENT` enum) requires either backwards-compatibility in the schema OR a migration step to re-validate existing rows. Composing with ADR-CANDIDATE-002 (centralised SECURITY_RULES — the validator's error path) and ADR-CANDIDATE-048 (narrow-validator scope at the @ConfigurationProperties layer — the same maintainer's discipline of "validate the shape that determines the behaviour"). The validator's choice of `IllegalArgumentException` over the project's `BadUserRequestException` (used in `PolicyServiceImpl` on lines 13, 77, 88) is the gap captured at REFACTOR-208 — the framing is "the request was syntactically invalid" but the response code may surface as 500 rather than 400.
  - **Wisdom test**: PASS. The validator is a positive design choice (named explicitly, `@Component`-managed, invoked at both write paths, with a schema bundled in the build). The choice of write-time over read-time is structural (the validator's responsibility is the "policies persisted are always schema-valid" invariant). The schema bundled at `schema/policy_schema.json` (V2019-09) is the contract.
  - **Evidence**:
    - createPolicy.md says: "PolicyJSONValidator.java:18-22 (loads `schema/policy_schema.json` once at construction) + PolicyJSONValidator.java:24-33 (validates per request, raises IllegalArgumentException on non-empty errors) + PolicyServiceImpl.java:64 (validator invoked before any persistence)"
    - createPolicy.md says: "PolicyServiceImpl.java:64, 73 (validator invoked on create AND update — unconditional pre-persistence check)"
  - **Existing ADR**: none. Composes with ADR-CANDIDATE-001 (controllers-as-delegates — the validator runs at the SERVICE layer, not at the controller, consistent with the controller-as-thin-delegate posture).
  - **Co-surfaced gaps** (link from `refactoring-scopes.md`): REFACTOR-208 (validator throws `IllegalArgumentException` instead of `BadUserRequestException` — depending on the `ExceptionsHandler` mapping, schema violations may surface as 500 not 400; MEDIUM), REFACTOR-209 (schema versioning + migration story not documented — a future schema change requires either back-compat or a re-validation migration; LOW), REFACTOR-210 (`GET /api/policies/schema` returns the live schema to any authenticated user without a SECURITY_RULES entry — not a vulnerability but undocumented; LOW), REFACTOR-189 (Administrator-name reservation create-vs-update asymmetry — the validator validates schema shape but not name-reservation; cross-cutting with RoleService; HIGH).
  - **Proposed action**: Promote to `adrs/drafts/policy-schema-validation-at-write.md` (new ADR). Document the write-time-validation invariant + the schema versioning (V2019-09) + the consequences for future schema evolution (migrations required for breaking changes). Cross-link with REFACTOR-208 (IllegalArgumentException-vs-BadUserRequestException error-class mismatch) as the canonical case for the validator's API-surface gap. Doc-side: the live `/configuration-and-deployment/enable-security/authorization/policies` page should explicitly document (a) the schema-validation step, (b) the `GET /api/policies/schema` endpoint as the canonical schema-discovery mechanism for custom integrations, (c) the `Administrator` policy-name reservation on update/delete (currently undocumented per DOC-GAP-A from the sidecar).
  - **Severity rationale**: MEDIUM — data-integrity decision; affects every policy persistence path and underwrites the read-path trust contract.
