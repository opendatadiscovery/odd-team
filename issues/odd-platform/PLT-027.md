## What

**Defect 1 - the dead guard (real, but narrower than first reported).** `DataEntityMapperImpl.java:242-253` `applyStatus`:

```java
// DataEntityMapperImpl.java:247 - mutate FIRST
pojo.setStatus(statusDto.getId());
pojo.setStatusSwitchTime(DateTimeUtil.mapUTCDateTime(status.getStatusSwitchTime()));
// :249 - guard compares the value just written to itself - always false
if (statusDto.getId() != pojo.getStatus()) {
    pojo.setStatusUpdatedAt(DateTimeUtil.generateNow());   // :250 - never reached
}
```

`pojo.getStatus()` on line 249 returns the value written on line 247; line 250 is unreachable. Consequence: transitions that flow through `applyStatus` never refresh `status_updated_at`.

**What `applyStatus` actually gates (the original report got this wrong).** `applyStatus` is called from exactly one site: the NON-DELETED branch of `DataEntityInternalStateServiceImpl.changeStatusForDataEntities` (`DataEntityInternalStateServiceImpl.java:90`). The DELETED branch (`:78-80`) routes to `softDeleteDataEntities` -> `dataEntityRepository.delete(ids)` (`:109`), and that path writes the timestamp via `getDeleteChangedFields` (`ReactiveDataEntityRepositoryImpl.java:110-116`): `STATUS = DELETED`, `STATUS_UPDATED_AT = now()`, `STATUS_SWITCH_TIME = null`.

**So the 30-day retention TTL DOES fire.** `DataEntityHousekeepingJob.java:73-78` selects `STATUS = DELETED AND STATUS_UPDATED_AT <= now() - data_entity_delete_days` and hard-deletes the entity plus every cascading row (`:84-126`), including object-storage attachment files (`deleteFiles`, `:117` + `:131-143`). Defaults: `housekeeping.enabled: true`, `data_entity_delete_days: 30` (`application.yml:165-170`). An earlier revision of this issue claimed the guard makes `status_updated_at` permanently NULL so "DELETED entities persist forever" - that was a single-call-site extrapolation, falsified by the dispatch branch above. Code-verified 2026-06-08 (DOC-338 proof chain) and re-verified 2026-06-10.

All three transition entry points were re-traced 2026-06-10:
- Manual PUT `/api/dataentities/{id}/statuses` -> `DataEntityController.updateStatus:194-198` -> `DataEntityServiceImpl:479` -> `changeStatusForDataEntities` (DELETED -> soft-delete path; others -> `applyStatus`).
- Scheduled auto-flip: `DataEntityStatusSwitchJob.java:25-29` flips ONLY to DELETED -> always the soft-delete path; never hits the dead guard.
- Ingestion (re)ingest: never calls `applyStatus`; `IngestionMapperImpl.java:188, 201-204` sets `statusUpdatedAt` explicitly (new entity / DELETED-resurrection -> `now`; otherwise carries the previous value forward).

**Residual effect of Defect 1:** every non-DELETE transition (DRAFT/STABLE/DEPRECATED/UNASSIGNED, including restore-from-DELETED) leaves `status_updated_at` at its previous value (or NULL for legacy rows). The sole reader of `data_entity.status_updated_at` is the housekeeping predicate above, which only consults rows with `STATUS = DELETED` - rows written by the soft-delete path, where the timestamp is correct. Net: wrong column data and a dead code path, but no reachable consumer today (grep 2026-06-10: no other BE read; the field is not on the `DataEntityStatus` API model; the UI's `statusUpdatedAt` hits are the Alert and OwnerAssociationRequest models, different tables).

**Defect 2 - unbounded status-switch batch (F-044b; unchanged).** `ReactiveDataEntityRepositoryImpl.getPojosForStatusSwitch:256-262` issues a SELECT with no LIMIT (`WHERE status_switch_time IS NOT NULL AND status_switch_time <= now()`). `DataEntityStatusSwitchJob.java:21-22` runs it every 10 minutes under `@SchedulerLock(lockAtLeastFor = "9m", lockAtMostFor = "9m")` and `.block()`s the whole flip. A backfill that schedules thousands of entities for the same `status_switch_time` produces one single-transaction bulk soft-delete (cascade fan-out per entity, `DataEntityInternalStateServiceImpl:106-128`). If a run exceeds `lockAtMostFor = 9m`, ShedLock releases the lock mid-run - a second replica may start a concurrent run over the same still-unflipped rows (the rows only stop matching once the first transaction commits `STATUS_SWITCH_TIME = null`), double-applying e.g. the statistics decrement (`:117`).

## User-facing impact

**None observable today from Defect 1 - verified by FE/BE trace 2026-06-10.** The DELETED lifecycle the docs promise (30-day retention, then irreversible hard purge incl. attachments) is what the code delivers; the dead guard sits only on the non-DELETE branch, and `data_entity.status_updated_at` has no consumer besides the purge predicate (no API-model field, no UI render site - the UI's `statusUpdatedAt` usages bind to Alert/OwnerAssociationRequest models). A user changing DRAFT -> STABLE -> DEPRECATED sees correct statuses everywhere; the only artefact is a silently stale DB column - a trap for any future consumer ("status changed N days ago" UI, audit query, support SQL), which would inherit wrong values with no error.

**Defect 2:** static trace consistent; not driven. The visible failure would be operational: a multi-thousand-entity backfill flips in one long blocking transaction; if it exceeds the 9-minute lock on a multi-replica deployment, a concurrent second run can double-decrement entity-class statistics (Catalog Overview tile counts drift low). Remaining check: run two replicas against a >9-minute backlog of `status_switch_time` rows and watch `data_entity_statistics`.

## How to reproduce (Defect 1, the residual)

1. PUT `/api/dataentities/{id}/statuses` body `{ "status": "STABLE" }` (or any non-DELETED status) on an entity with a known `status_updated_at`.
2. `SELECT status, status_updated_at FROM data_entity WHERE id = ?` - the status changed; `status_updated_at` did not.
3. (Counter-check that falsified the original claim) PUT `{ "status": "DELETED" }` - `status_updated_at` IS set to now() by the soft-delete path, and the entity is hard-purged once it ages past `data_entity_delete_days`.

## Suggested fix

**Thread A - fix the dead guard (3 lines).** Capture-before-mutate in `applyStatus`:

```java
final Short oldStatus = pojo.getStatus();   // jOOQ pojo getter returns boxed Short
pojo.setStatus(statusDto.getId());
pojo.setStatusSwitchTime(DateTimeUtil.mapUTCDateTime(status.getStatusSwitchTime()));
if (!Objects.equals(statusDto.getId(), oldStatus)) {
    pojo.setStatusUpdatedAt(DateTimeUtil.generateNow());
}
```

No data-fix migration is needed for retention (the purge path writes its own timestamp); a backfill is only worth it if a consumer of non-DELETED `status_updated_at` ships.

**Thread B - cap the status-switch batch.** Add a LIMIT (e.g. 200/tick) to `getPojosForStatusSwitch` so a backfill drains across ticks instead of one mega-transaction racing the 9-minute lock; optionally emit a pending-count metric.

## Operator impact

Re-scoped 2026-06-08/2026-06-10: the original "storage grows unbounded / compliance-retention silently violated / zombie rows forever" impact story is retracted - retention works as documented. Surfaced during Mode B batch-10 triage (2026-05-27) as a claimed verbatim doc-vs-code contradiction ("TTL never fires; DELETED entities persist forever"). **Corrected 2026-06-08 (editorial-audit code verification, DOC-338) and re-verified 2026-06-10 (user-facing verification sweep): was "status_updated_at NEVER set -> 30-day purge never fires -> DELETED persists forever"; actually the DELETED transition never goes through `applyStatus` - `DataEntityInternalStateServiceImpl.changeStatusForDataEntities:78-80` branches DELETED to `softDeleteDataEntities`, whose `getDeleteChangedFields` writes `STATUS_UPDATED_AT = now()` (`ReactiveDataEntityRepositoryImpl.java:110-116`), so the purge (`DataEntityHousekeepingJob.java:73-78`) fires as documented.** The dead guard is real but gates only non-DELETE transitions, whose timestamp no shipped consumer reads. The original revision asserted the inverted conclusion from a single call-site read - the class of miss the consumer-read gate exists for.
