## Description

During the 0.29.0 release-review full regression (`ODD_SUT=published:0.29.0`, feature-complete suite),
`activity-user-filter.spec.ts:130` ("the global page exposes Owner + Made by (owner) + Made by (user)
filters") FAILED with a 60s `waitForResponse` timeout — **1 of 318**, while **317 passed**. It is a
**test-harness flake, not a product defect or a 0.29.0 regression**:

- Root cause (the spec): the test does `await page.goto('/activity?...')` (line 131) and only THEN
  `await page.waitForResponse(r => /\/api\/activity(\?|$)/.test(r.url()) && r.ok())` (line 132). When the
  `/api/activity` response arrives between `goto` resolving and the listener attaching, the listener misses
  it and waits the full 60s → timeout. Classic Playwright `waitForResponse`-after-`goto` race.
- Measured proof it is NOT a product break: the 4 sibling tests in the SAME spec (lines 141/160/187/211)
  that navigate to the same `/activity` page and exercise the same `owner` / `made_by_owner` / `made_by_user`
  filters ALL PASSED in the same run (1.6s / 2.7s / 1.8s / 1.0s) — so the endpoint returns 2xx and the
  filters render. And the feature (#1657 / F-021/F-196 activity actor filters) has **no code change in the
  0.29.0 delta** (`0.28.0..0.29.0`).

This is distinct from [[TST-023]] (per-entity Activity tab filter-change reducer race, a characterization
pin to author) — this item is purely the global-feed spec's own goto/waitForResponse ordering.

## Acceptance Criteria
- [ ] Restructure the wait so the response listener is attached BEFORE navigation, e.g.
  `const [resp] = await Promise.all([page.waitForResponse(r => /\/api\/activity(\?|$)/.test(r.url()) && r.ok()), page.goto('/activity?...')]);` (mirror the pattern the passing sibling tests use).
- [ ] The spec runs GREEN on `run-suite.sh feature-complete` across ≥3 consecutive runs (no intermittent
  60s timeout).
- [ ] No assertion weakened; the three filter-visibility assertions (lines 134-136) are unchanged.
