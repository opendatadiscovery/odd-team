## ADR-CANDIDATE-067 — `@ReactiveTransactional` boundary asymmetry — list-shaped reads stay OUTSIDE TX; per-resource writes ARE INSIDE TX (multi-step)

**Severity**: MEDIUM
**Classification**: promote
**Support count**: 9 sidecars (4 controller-method + 5 repository — batch G + batch H)
**Axes present**: controllers, services, repositories
**Surfaced by**:
- `getPopular.md:implicit_adrs[3]` ("No transactional boundary on the read path — `listPopular` is a single SELECT, no side-effect, no view-count touch.")
- `addDataEntityTerm.md:implicit_adrs[0]` (service-level `@ReactiveTransactional` on writes, controller-level absence)
- `upsertDataEntityInternalDescription.md:implicit_adrs[6]` (nested `@ReactiveTransactional` on outer + inner service)
- `createDataEntityTagsRelations.md:implicit_adrs[2]` (duplicate `@ReactiveTransactional` annotation on outer + inner service — defensive intent)
- **STRENGTHENED 2026-05-19H (repository-layer confirmation — ALL 5 repositories in batch H)**:
  - `ReactiveDataEntityRepositoryImpl.md:implicit_adrs[5]` ("The repository is deliberately untransactional. Transaction boundaries live one layer up at the service. This allows individual repository methods to compose freely under either a shared transaction (when a caller wraps several calls in @ReactiveTransactional) or no transaction (when a caller fires-and-forgets). The trade-off is that callers can forget to wrap and silently lose atomicity." — confirms no @ReactiveTransactional at `ReactiveDataEntityRepositoryImpl.java:88-91`)
  - `ReactiveLineageRepositoryImpl.md:invariants[6]` (no @ReactiveTransactional at class or method level; the paired `batchDeleteByEstablisherOddrn` + `batchInsertLineages` rely on caller's `@ReactiveTransactional` at `LineageServiceImpl.java:124-133`)
  - `ReactiveOwnershipRepositoryImpl.md:implicit_adrs[1]` (the DB-constraint + ExceptionUtils translation pattern is repository-layer; the `@ReactiveTransactional` at `OwnershipServiceImpl.java:49,78,101` is service-layer)
  - `ReactivePolicyRepositoryImpl.md:concepts.invariants[4]` (single-statement INSERT/UPDATE on `create`/`update` — NO @ReactiveTransactional on these inherited methods; only bulkCreate/bulkUpdate are transactional)
  - `ReactiveAlertRepositoryImpl.md:implicit_adrs[0]` ("Repository layer is transaction-free; transactions are declared at the SERVICE layer. The class has no `@ReactiveTransactional` annotation; the AlertServiceImpl ingestion-write paths (`handleExternalAlerts` line 152, `applyAlertActions` line 201) carry the annotation and the mutation path (`updateStatus` line 111-113) deliberately does NOT.")

**Decision statement**: The platform applies `@ReactiveTransactional` selectively: per-resource write paths (description, internal_name, terms, tags, ownership, status, attachment, metadata, alert ingestion, lineage rewrite-by-establisher, policy CRUD bulk paths) carry `@ReactiveTransactional` at the SERVICE LAYER — never at the controller, **never at the repository**. Multi-step writes (write + FTS-vector refresh + filled-flag toggle + activity-log emission + cross-service side effects) span ONE transaction. Conversely, list-shaped reads (`listPopular`, `listAssociated`, `listByOwner`, `listAllWithStatusOpen`, `getLineageRelations`) carry NO `@ReactiveTransactional` — they are single SELECTs with no side effects. `getDataEntityDetails` (batch F) is the deliberate exception on the read side: it carries `@ReactiveTransactional` BECAUSE of the read-as-write view_count UPDATE (a deliberate read-write coupling). The asymmetry is STRUCTURAL: the TX boundary is a function of whether the operation mutates state, not a uniform pattern.

**Batch H deepening**: The repository-layer is **uniformly transaction-free** across ALL 5 repositories examined. Not a single `@ReactiveTransactional` annotation at the repository class level. Single-statement INSERT/UPDATE/DELETE methods are atomic per-statement; multi-statement consistency depends on the caller's transaction boundary holding the DB connection for the duration. The deliberate-non-transactionality at the repository is its own architectural commitment: it allows repository methods to compose freely either under a shared transaction (typical case) or as fire-and-forget (test code, scheduled jobs). The trade-off is that any caller bypassing the service layer (a future direct controller-to-repository call, a one-off script) silently loses atomicity. This is documented in `ReactiveDataEntityRepositoryImpl.md:implicit_adrs[5]` as "the trade-off is that callers can forget to wrap and silently lose atomicity" — the maintainer accepts this risk.

**Evidence**:
- `getPopular.md` says: "No transactional boundary on the read path... Contrast with `getDataEntityDetails` (batch F implicit_adrs[2]) which carries `@ReactiveTransactional` to wrap the read + the view-count UPDATE in one transaction. `listPopular` reads `view_count` but never writes — the producer/consumer asymmetry is the implicit decision: the consumer half does not amplify the loop."
- `upsertDataEntityInternalDescription.md` says: "nested transactional annotations on both layers reflect the intent that a partial-failure state (e.g. description written but term-relations not updated) is forbidden."
- `createDataEntityTagsRelations.md` says: "Reactive transactional boundary is duplicated — both `DataEntityServiceImpl.upsertTags` and `TagServiceImpl.updateRelationsWithDataEntity` carry `@ReactiveTransactional`. The outer-tx encloses the inner one (Spring's default `PROPAGATION_REQUIRED`)."
- (NEW 2026-05-19H) `ReactiveLineageRepositoryImpl.md` says: "Ingestion atomicity via paired `batchDeleteByEstablisherOddrn` + `batchInsertLineages` under caller's `@ReactiveTransactional` — the repository deliberately exposes the delete-by-establisher and insert primitives as separate methods rather than a single `replaceLineagesByEstablisher(...)` so the caller (LineageServiceImpl.replaceLineagePaths at LineageServiceImpl.java:124-133) can compose them inside ONE transactional boundary. The `@ReactiveTransactional` lives on the SERVICE method, not on either repository method."
- (NEW 2026-05-19H) `ReactiveAlertRepositoryImpl.md` says: "Repository layer is transaction-free; transactions are declared at the SERVICE layer. The class has no `@ReactiveTransactional` annotation; the AlertServiceImpl ingestion-write paths (`handleExternalAlerts` line 152, `applyAlertActions` line 201) carry the annotation and the mutation path (`updateStatus` line 111-113) deliberately does NOT. The decision is visible in the annotation placement — every write method on this repository is composable into a service-declared transaction, but the repository never opens its own."

**Rationale (wisdom test 3-question)**:
1. *Intentional?* YES — uniform pattern: writes carry the annotation at the service, reads do not, except where the read mutates (getDataEntityDetails). The pattern is consistent across 7+ writes and 3+ reads at the service layer, AND across 5 repositories at the repository layer (NONE carry the annotation). Defensive duplicate-annotation on nested services (Tags, Description) is intentional.
2. *Structural impact?* YES — affects connection-pool usage, partial-failure semantics, isolation level inheritance, the rule "controllers are TX-naive", and the rule "repositories are TX-naive" (so they compose under any caller). The selective service-layer placement IS the architecture.
3. *Refactoring or structural?* STRUCTURAL — switching to "all paths transactional" or "all paths non-transactional" would be a redesign. Switching to "transactions live at the repository" would also be a redesign (it would break the composability that the service-layer boundary enables).
→ ADR-CANDIDATE.

**Existing ADR**: partial overlap with ADR-CANDIDATE-059 (which says "Multi-step per-data-entity write paths use service-layer @ReactiveTransactional"). This candidate EXTENDS-EXISTING by adding the read-side asymmetry, the nested-annotation defensive pattern, AND (new in batch H) the repository-layer uniform-non-transactionality confirmation across 5 repositories.

Alternatively, create `adrs/drafts/reactive-transactional-boundary-asymmetry.md` as a fresh ADR if ADR-CANDIDATE-059 hasn't been promoted yet.

**Severity rationale**: MEDIUM — pattern-shaping decision on transaction-boundary placement, confirmed across 9 sidecars (4 in batch G + 5 in batch H) and consistent across the entire repository layer. The pattern is load-bearing for every multi-step write on the platform.
