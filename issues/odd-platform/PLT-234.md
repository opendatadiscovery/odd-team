## Description

The sharpest instance of the redux-thunk `ConfirmationDialog` silent-close class (PLT-233), called out
separately because it does more than mis-close — it **navigates away as if the deletion succeeded**.

`Terms/TermDetails/TermDetails.tsx:47-53`:

```tsx
const handleTermDelete = useCallback(
  (id: number) => () =>
    dispatch(deleteTerm({ termId: id })).then(() => navigate(termsSearchPath(termSearchId))),
  [termSearchId]
);
```

A redux-toolkit dispatch promise **resolves even on failure** (`handleResponseThunk.ts:41` →
`rejectWithValue`), so `.then(navigate)` runs unconditionally. When `DELETE /api/terms/{id}` is refused
(RBAC 403, 500, a future referential guard), the user is navigated to the term-search page **as if the term
were deleted** — directly contradicting the error toast (#1771) and leaving the still-existing term findable
only by going back. This is worse than the generic silent-close (PLT-233): it actively asserts a false
success and moves the user off the page.

Static trace only (not yet driven on the running stack — `user_facing_verified: false`); confirm live when
worked.

## Suggested fix

Gate the navigation on actual success — `.unwrap()` the dispatch so the `.then(navigate)` only runs when the
delete resolved (and the rejection flows to `ConfirmationDialog`'s inline error, post-#1766):

```tsx
const handleTermDelete = (id: number) => async () => {
  await dispatch(deleteTerm({ termId: id })).unwrap();
  navigate(termsSearchPath(termSearchId));
};
```

(The same `.unwrap()` consumer fix PLT-233 prescribes for the generic arm; this consumer additionally needs
the navigation moved inside the success branch.)

## Acceptance

- A failed term delete does NOT navigate away; the dialog shows the inline error and the term remains on its
  page.
- A successful term delete still navigates to term-search (behaviour preserved).
