## Description

Editorial-audit finding from `/review batch:feature/docs-editorial-followups-2026-05-07` (DOC-155..159) on 2026-05-07.

`docs/active-platform-features/genai.md` L112 ("Where to next" section, bullet 3) cross-links the `POST /api/genai/ask` endpoint description directly to the OpenAPI spec source on GitHub:

> *"`POST /api/genai/ask` (operationId `genAiQuestion`, tag `genai`) — the request/response shape and verb live in [`opendatadiscovery/odd-platform-specification → openapi.yaml`](https://github.com/opendatadiscovery/odd-platform/blob/main/odd-platform-specification/openapi.yaml)."*

Per `pillars/documentation/canonical-homes.md` "API reference" row, the canonical home for HTTP endpoint descriptions is the `developer-guides/api-reference` subtree (hub `api-reference.md` + 9 per-feature sub-pages: alerts, data-collaboration, directory, glossary, integrations, lineage, query-examples, reference-data, relationships).

The GenAI endpoint is **NOT covered** in the api-reference subtree today — `grep -i "genai\|/api/genai\|genAiQuestion" docs/developer-guides/api-reference*` returns 0 hits. So the canonical home is sparse for this content, and the genai.md feature page reaches outside the doc product to the spec source on GitHub for its API contract.

This is **the same Cornerstone-5 application as DOC-156** — a feature page sending readers outside the doc product when a canonical home is the right destination — but with a different fix shape: DOC-156 was a pure link retarget (the canonical home was already populated); DOC-161 is a Cornerstone-5 outcome 2 ("home exists but is sparse — extend the home, then link"), so the work is "add GenAI coverage to api-reference subtree" + "retarget the link", not just a link retarget.

## The three options

1. **Add GenAI as a 10th api-reference sub-page** — create `docs/developer-guides/api-reference/genai.md` covering the single endpoint (`POST /api/genai/ask`, operationId `genAiQuestion`, request/response schemas, status codes, RBAC if any, related Sources line). Update `api-reference.md` hub's per-feature index. Update SUMMARY.md. Retarget `genai.md` L112 to `../developer-guides/api-reference/genai.md`. Mirrors the existing 9 per-feature sub-page pattern.
2. **Extend api-reference.md hub directly** — add a single-endpoint section for GenAI on the hub page itself (no new sub-page; smaller surface; no SUMMARY change). Retarget `genai.md` L112 to `../developer-guides/api-reference.md#genai` (anchor).
3. **Defer with annotation** — mirror DOC-159 Option 1: log on `pillars/documentation/canonical-homes.md` "API reference" row that GenAI coverage is missing, leave the GitHub link with a deferred-to-DOC-NNN note. Less appropriate here than for DOC-159's matrix because GenAI's API surface is small and stable (single endpoint), so the cost of adding coverage is low.

**Recommended decision: Option 1.** The api-reference subtree's per-feature sub-page pattern is the established home shape (post-DOC-088 hub-and-spokes refactor); adding genai.md as a 10th sub-page is a small extension that keeps the hub structure consistent and self-similar. The endpoint is already well-defined (single `POST /api/genai/ask`, single request/response schema in the spec), so the authoring surface is bounded.

## Context

- **Why low priority.** The link works today; the operator hitting it lands on the OpenAPI YAML which does carry the request/response shape. The defect is *cross-link consistency* and *audience targeting* (the GitHub YAML is a contributor-facing surface; the api-reference doc-home is the developer-facing one). Same severity as DOC-156's pre-existing pattern.
- **Why log it now.** The DOC-156 cleanup batch and editorial audit drew the line at use-case-page narrative. The same shape exists on a feature page (`active-platform-features/genai.md`); making the audit consistent across feature pages too is the right scope for an editorial follow-up. Logging here so the next authoring batch picks it up; not folding into DOC-156 because the fix shape is different (extend the canonical home, not just retarget).
- **Why this slipped through PR #68 (Features.md carve-out) review.** The carve-out was scoped to Data Discovery + Integrations buckets (the 8 features that needed dedicated detail pages). `active-platform-features/genai.md` was already a dedicated detail page pre-carve-out (it landed on PR #63 via DOC-140), so it was not in the carve-out's scope; the editorial audit on PR #68's scope did not re-walk the active-platform-features subtree.
- **Pre-existing defect, not introduced by this batch.** The genai.md file's L112 reference predates DOC-155..159; the cross-link pattern was authored in DOC-140 / earlier. This item documents long-standing cross-link inconsistency on the api-reference surface.
- **Bidirectional code↔doc gap.** Per `pillars/documentation/gates.md` Gate 6, the `POST /api/genai/ask` endpoint exists in code (Spring controller) and in the spec (OpenAPI YAML), but is NOT in the api-reference subtree (the doc-product canonical home for endpoint descriptions). This is the LSN-001-class missing-coverage finding: an implemented surface without doc-side coverage at the canonical home. The 9 existing api-reference sub-pages cover their respective features completely; GenAI is the 10th feature whose endpoint surface should follow the same pattern.
