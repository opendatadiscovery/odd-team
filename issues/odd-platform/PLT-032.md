## What

Two defects on the per-entity Discussions tab - **Defect 1 is a duplicate of the canonical PLT-010** (verified 2026-06-10); Defect 2 (Thread.tsx silent navigation) is a distinct surviving finding, corrected below to match the actual code.

**Defect 1 - Discussions tab visible when feature disabled (F-197a) - REJECT-CANDIDATE: DUPLICATE of PLT-010.** This restates the exact tab-visibility defect already tracked, earlier and as a single claim, in **PLT-010** (found 2026-05-03). The behaviour itself is verified-real: `DataEntityDetailsTabs.tsx:96-99` gates the Discussions tab only on `isStatusDeleted`, not on the data-collaboration feature flag, so the tab renders on a default (`datacollaboration.enabled=false`) deployment. **PLT-010 is canonical** and carries the corrected mechanism analysis (the `Feature.DATA_COLLABORATION` / `getActiveFeatures` / `WithFeature` plumbing already exists and is used by the Share button on the same page; the tab simply was not wrapped). This item should be closed against PLT-010 to avoid double-filing the same fix; the only reason it is not a pure reject is the distinct Defect 2 below. The live-doc "currently rendered regardless of the flag" acknowledgement is operator-honest but is patching a code defect with doc copy.

**Defect 2 - Thread.tsx navigates away on relatedMessagesError with no error context (F-197b) - DISTINCT, corrected.** `Thread.tsx:31-42` - when `relatedMessagesError` is set, the thread effect navigates to the parent discussions list URL (`dataEntityDetailsPath(dataEntityId, 'discussions')`) with NO error toast and NO inline banner. The operator's "open a thread" click rewrites the URL with no explanation - they cannot tell whether they clicked something wrong, the thread was deleted, or the platform is partially down. **Correction (the original draft mis-cited this):** the redirect is NOT a standalone `useEffect` keyed on `relatedMessagesError`. It is the first statement inside the thread's main `useEffect`, whose dependency array is `[dataEntityId, messageId, size]` - `relatedMessagesError` is not in the deps. So the navigation does not fire reactively the instant the error appears; it fires on the next run of that effect (a `dataEntityId` / `messageId` / `size` change) while the error flag happens to be set. The silent-degradation UX concern stands; the exact trigger timing differs from the original write-up.

## User-facing impact

**Defect 1 (duplicate):** same as PLT-010 - on a default deployment the Discussions tab renders and clicking it produces a no-content surface (the `@Conditional` controller returns 404); low-severity first-launch UX. Tracked canonically on PLT-010.

**Defect 2 (distinct):** verified 2026-06-10 at `Thread.tsx:31-42`. When a thread's related-message fetch errors, the user is bounced from the thread URL back to the discussions list with no toast and no banner - the only signal is the URL silently changing. This is a real (if narrow) silent-degradation paper-cut: the error path fires on transient backend errors or on a deleted/stale thread. It is rare (requires a thread fetch to error while the effect re-runs) and non-destructive, so low severity - but the operator is left unable to distinguish "I mis-clicked" from "the platform is failing."

## Why it matters

Defect 1 is a duplicate of PLT-010 (UI feature-flag misalignment) - see that item for the full analysis; do not double-implement.

Defect 2 is small but representative of a broader UX pattern in the data-collaboration surface: errors silently degrade rather than surfacing diagnostic context. Operators don't know whether they did something wrong or the platform is failing.

Severity is LOW for the pair because:
- Defect 1 is honest-in-doc; operators on a disabled deployment learn to ignore the tab quickly.
- Defect 2 is a thread-load failure mode that's rare (the thread message-fetch error path only fires on backend transient errors or a deleted thread the user has stale state for).

## Suggested fix

**Defect 1 - see PLT-010 (canonical).** The fix is to gate the Discussions tab + route on the already-exposed `Feature.DATA_COLLABORATION` flag (`getActiveFeatures` / `WithFeature`), exactly as the Share button on the same page already does. Do not implement separately here. Once shipped, the doc-side acknowledgement in `data-collaboration.md` updates to remove the "currently" framing.

**Defect 2 - Thread.tsx error context.** Surface the error instead of a silent redirect. Because the navigation currently lives inside the main effect (deps `[dataEntityId, messageId, size]`), the cleanest fix also moves the error handling into its own error-keyed effect so it reacts the instant the error appears:

```tsx
// add a dedicated effect keyed on the error flag:
React.useEffect(() => {
  if (relatedMessagesError) {
    showErrorToast(t('Failed to load thread - returning to discussions list'));
    navigate(dataEntityDetailsPath(dataEntityId, 'discussions'));
  }
}, [relatedMessagesError, dataEntityId, navigate, t]);
```

Or - show an inline error banner in place of the silent navigation; let the operator choose to go back or retry.
