## What

The home page's "Popular" data-entity tile is computed **catalog-wide**, not per user. It lists the platform's globally most-viewed data entities, ordered by a shared `view_count`, identical for everyone who sees it, with no per-principal scoping and no personalisation signal in the query at all. It renders under a section heading the FE labels **"Recommended"** (`OwnerEntitiesList.tsx:76`), so the global leaderboard sits beside genuinely owner-scoped tiles ("My Objects", "Upstream dependents", "Downstream dependents") under a heading that reads as personalised. The "Popular" tile itself is labeled "Popular" with a star icon (`:101`), but the enclosing "Recommended" framing still implies the whole section is for-you. Through the same query, each entity's **name** and **alert state** (`has_alerts`) are surfaced - so a viewer sees the names + alerting status of the catalog's top-viewed entities even where they have no relationship to them.

**Scope correction (was overstated):** this is NOT seen by "every signed-in user," and it is NOT on the default deployment. The whole strip only renders for an authenticated user who already has an Owner association (`OwnerAssociation.tsx:84-85`: `if (identity && ownership) return <OwnerEntitiesList/>`), inside an Overview block gated by `authType !== 'DISABLED'` AND `Permission.DIRECT_OWNER_SYNC` (`Overview.tsx:25-27,53-59`). On the shipped default `auth.type=DISABLED` the strip does not render at all. So the audience is "authenticated, owner-associated users," not "everyone."

## Where

The endpoint takes only paging parameters - no principal, no owner:

`odd-platform-api/.../controller/DataEntityController.java:307-313`

```java
@Override
public Mono<ResponseEntity<Flux<DataEntityRef>>> getPopular(final Integer page,
                                                            final Integer size,
                                                            final ServerWebExchange exchange) {
    return Mono.just(dataEntityService.listPopular(page, size))
        .map(ResponseEntity::ok);
}
```

The repository query orders the **whole** `DATA_ENTITY` table by `VIEW_COUNT` descending with no owner/principal condition:

`odd-platform-api/.../repository/reactive/ReactiveDataEntityRepositoryImpl.java:629-649`

```java
@Override
public Flux<DataEntityDto> listPopular(final int page, final int size) {
    final DataEntityCTEQueryConfig cteConfig = DataEntityCTEQueryConfig.builder()
        .limitOffset(new DataEntityCTEQueryConfig.LimitOffset(size, (page - 1) * size))
        .orderBy(DATA_ENTITY.VIEW_COUNT.sort(SortOrder.DESC))   // global view_count, no owner filter
        .build();
    ...
    final var select = DSL.with(deCteName)
        .as(dataEntitySelect)
        .select(deCte.fields())
        .select(hasAlerts(deCte))          // alert-state of arbitrary entities surfaces too
        .from(deCteName)
        .orderBy(getOrderFields(cteConfig, deCte));
    return jooqReactiveOperations.flux(select)
        .map(dataEntityDtoMapper::mapDtoRecordFromCTE);
}
```

The spec itself documents the endpoint as catalog-wide: `odd-platform-specification/openapi.yaml:877-891` (`getPopular`, "Returns list of the most popular data entities throughout the catalog"), paging params only.

**The FE consumer and its framing** (added 2026-06-10 - the original draft cited only the BE):

- `odd-platform-ui/.../Overview/OwnerAssociation/OwnerEntitiesList/OwnerEntitiesList.tsx:76` - section heading `<Typography variant='h1'>{t('Recommended')}</Typography>`; `:100-104` renders the "Popular" tile (`entityListName={t('Popular')}`, `StarIcon`) fed by `popularEntities`.
- `:58-64` - `useEffect` dispatches `fetchPopularDataEntitiesList({page:1,size:5})`; the thunk (`redux/thunks/dataentities.thunks.ts:177-182`) calls `dataEntityApi.getPopular({page,size})` - confirming this tile is the `getPopular` consumer.
- `OwnerEntitiesList/DataEntityList/DataEntityList.tsx:38-49` - each item renders `item.internalName || item.externalName` (the **name**) and, when `item.hasAlerts`, an `AlertIcon` + `$hasAlerts` styling (the **alert state**). `DataEntityRef.has_alerts` is in the contract (`components.yaml:912-913`).
- **Gating:** `OwnerAssociation.tsx:84-85` renders `OwnerEntitiesList` only when `identity && ownership`; `Overview.tsx:25-27,53-59` gates the whole `OwnerAssociation` on `authType !== 'DISABLED'` + `Permission.DIRECT_OWNER_SYNC`.

## User-facing impact

**Real but bounded; not "every user" and not on the default deployment** - verified by FE+BE trace 2026-06-10.

1. **Misleading framing (holds, re-scoped).** The global "Popular" tile sits under a "Recommended" heading (`OwnerEntitiesList.tsx:76`) next to genuinely owner-scoped tiles, so the section reads as personalised when the Popular column is a single global leaderboard. The tile's own label is "Popular" (`:101`), which softens but does not remove the "Recommended"-section implication.
2. **Cross-owner name + alert-state visibility (holds).** The tile renders the **names** and **alert icons** of the catalog's top-viewed entities (`DataEntityList.tsx:38-49`; BE `hasAlerts(deCte)` -> `has_alerts` ref field) to a viewer with no necessary relationship to them. In a multi-team deployment this exposes entity existence/naming/alerting of assets the viewer may not own.
3. **Audience corrected (FALSIFIED as written).** Was "every signed-in user... on the first screen they see." Actually: only authenticated users who already hold an Owner association (`OwnerAssociation.tsx:84-85`), and never on the shipped default `auth.type=DISABLED` (the block is gated off, `Overview.tsx:25-27`). So the exposure surface is "auth-enabled, owner-associated users," not everyone.

Not driven live this sweep (static FE+BE trace only); remaining check = drive the Overview page as an owner-associated user on an auth-enabled stack and confirm the "Popular" tile shows other owners' entity names + alert icons.

## Why it matters

**Silent**, and affects authenticated owner-associated users on auth-enabled deployments (corrected from "every user"; see *User-facing impact*). The framing mismatch (global data under a "Recommended" section) is a UX/consistency defect, and the cross-owner name + alert-state visibility deserves a deliberate decision rather than an accident of a global `ORDER BY`.

Severity **medium retained**, on a narrowed basis: the "every user / first screen" reach is gone, but the cross-owner alert-state visibility under a personalised-reading heading is a genuine information-exposure smell that warrants either a relabel or a deliberate "yes, this is intentionally catalog-wide" decision. It is not destructive and (depending on auth posture) the entities may already be broadly listable, which keeps it below high.

## Suggested fix

The primary fix is **documentation** - state plainly that Popular is a global, catalog-wide leaderboard, not a per-user recommendation (tracked doc-side; see *How discovered*). This issue exists for the **code-side** option if the project prefers a behavioural change instead of (or in addition to) the doc caveat:

- **Lowest-cost:** relabel the surface from any "Recommended/for you" framing to plainly "Most viewed across the catalog", so presentation matches the global query. (open to alternatives)
- **Higher-cost (true personalisation):** scope `listPopular` to the calling principal - accept the authenticated owner and add an ownership/association condition (mirroring the owner-aware queries already in `ReactiveDataEntityRepositoryImpl`, e.g. `findByState(..., OwnerPojo owner)` directly below `listPopular`), so the strip reflects entities the user owns or is associated with.

Pick per product intent; the relabel is the minimal honest fix if personalisation is out of scope.
