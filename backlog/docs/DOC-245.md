## Description

`AuthIdentityProviderImpl.java:32` emits `UserDto(name, null)` for any auth mode that isn't OAUTH2 (LOGIN_FORM, LDAP, DISABLED, S2S). Four LEFT JOIN sites in `ReactiveActivityRepositoryImpl.java` (lines 157-158, 178-179, 199-200, 221-222) join `USER_OWNER_MAPPING ON OIDC_USERNAME = ACTIVITY.CREATED_BY AND DELETED_AT IS NULL` — **provider-AGNOSTIC**. Multi-mode deployments (e.g., LOGIN_FORM 'alice' + LDAP later imports 'alice') see row duplication in the activity feed + non-deterministic OwnerPojo display.

Forensic incident response over an audit feed is misled — a LOGIN_FORM user and an LDAP user with the same name resolve to the same OwnerPojo even when they are different people. The operator-visible symptom: activity feed entries authored by `alice` show inconsistent OwnerPojo display name (the most recent USER_OWNER_MAPPING wins each LEFT JOIN evaluation; non-deterministic across replicas).

**This is an LDAP + LOGIN_FORM specific caveat** — OAUTH2 mode includes the provider discriminant in `UserDto(name, provider)`, so the JOIN would discriminate if the JOIN condition included `PROVIDER`. But the JOIN condition is provider-agnostic at all four sites. So the bleed surface materialises when the deployment is in LOGIN_FORM or LDAP mode AND multiple modes have produced same-named principals in the past.

## Acceptance Criteria

- [ ] LDAP page (`ldap.md`) gains a "## Cross-mode user-name collision (activity feed read paths)" sub-section covering:
  - The platform's activity-feed read paths join `USER_OWNER_MAPPING` on `OIDC_USERNAME` only — the JOIN does NOT discriminate by provider. If your deployment has historically used multiple auth modes (e.g., started on LOGIN_FORM with seed users, then enabled LDAP), a user `alice` in LOGIN_FORM and a user `alice` in LDAP can resolve to the same OwnerPojo in activity feed rendering. The most recent USER_OWNER_MAPPING row wins; results are non-deterministic across replicas.
  - **Operator mitigation today**: never reuse usernames across auth modes when migrating; if you migrate from LOGIN_FORM to LDAP, decommission LOGIN_FORM users by deleting their USER_OWNER_MAPPING rows BEFORE introducing LDAP users with the same login.
  - **Forensic note**: do NOT rely on activity-feed Owner attribution for incident response in multi-mode deployments without verifying the auth mode of the actor via the underlying `activity.created_by` value.
  - Track PLT-065 for the platform-side JOIN-discriminant fix.
