## What

When a user assigns ownership and types a title (role) that does not yet exist, the platform silently mints a permanent, platform-wide row in the Title directory — with **no permission check, no allow-list, and no audit record**. The Title directory is shared authorization-relevant vocabulary (it is the same `title` directory that filters reads elsewhere), yet anyone who can create an ownership can extend it. Every other comparable vocabulary-minting surface in the product (Owner, Term, Namespace, Tag) is gated by a dedicated `*_CREATE` permission; Title alone is not — there is no `TITLE_CREATE` permission anywhere in the API contract or the code.

## Where

`odd-platform-api/.../service/TitleServiceImpl.java:18-22` — `getOrCreate` inserts on miss with no authorization at all:

```java
@Override
public Mono<TitlePojo> getOrCreate(final String name) {
    return titleRepository.getByName(name)
        .switchIfEmpty(titleRepository.create(new TitlePojo().setName(name)));  // mint on miss, no perm check
}
```

Reached from the ownership-create flow, which calls it with the free-form `titleName` straight off the form:

```java
// odd-platform-api/.../service/OwnershipServiceImpl.java:52-53
return Mono.zip(ownerService.getOrCreate(formData.getOwnerName()),
        titleService.getOrCreate(formData.getTitleName()))   // :53 — caller, free-form title from form
```

`OwnershipServiceImpl.update` (`:106`) calls the same `getOrCreate` on the update path. The `Permission` enum that gates every other directory mint defines `OWNER_CREATE`, `TERM_CREATE`, `NAMESPACE_CREATE`, `TAG_CREATE` (`odd-platform-specification/components.yaml:203-224`) but contains **no `TITLE_CREATE`** — a project-wide grep for `TITLE_CREATE` returns nothing.

## Why it matters

This is a silent privilege/governance hole. Anyone who can attach an owner to an entity (a common, low-privilege action) can permanently grow the platform-wide Title vocabulary one free-form string at a time, with no audit trail recording who added what or when. There is no length/charset bound and no de-duplication beyond exact-name match, so the directory is a pollution surface (`Steward`, `steward`, `' steward '` become distinct permanent rows) and — under `auth.type=DISABLED` — an unauthenticated caller can do it. Because Title is authorization-relevant shared vocabulary, an uncontrolled, unaudited mint of it is a security-adjacent defect, not merely cosmetic. Severity high: it is a missing access control on a shared, persistent, governance-relevant directory, and it is the one minting surface that escaped the `*_CREATE` permission convention applied to every sibling.

## Suggested fix

Bring Title in line with the other directory-minting surfaces: add a `TITLE_CREATE` permission to the `Permission` enum and enforce it on the title-mint path (or gate the mint behind an allow-list of already-existing titles for users without it, falling back to "title not found" rather than silently creating). Emit an Activity/audit event on title creation so the mint is attributable, mirroring the audit applied to owner/term/namespace creation. Add a server-side name bound (length + trim) while touching this path. Open to alternatives on whether minting is permission-gated vs. allow-listed, but it must not remain unauthorized and unaudited.
