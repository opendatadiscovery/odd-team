## Description

The `GET /api/datasets/{data_entity_id}/sla` PNG-badge endpoint sets **no caching headers** and **re-runs the dataset SLA SQL aggregation on every request**. There is no `ETag`, no `Cache-Control`, no `Last-Modified`, and therefore no conditional-request (HTTP 304) path. `sla-statuses.md` recommends this endpoint for BI image-embed tiles (Confluence macros, Notion embeds, Excel `IMAGE()`, Looker/Tableau image tiles) without warning operators about the per-render cost.

How it misleads an operator: a BI dashboard with N auto-refreshing tiles each embedding a `/sla` badge re-executes N independent SLA aggregations against Postgres on every dashboard refresh — there is no caching layer in front of the computation and the HTTP response cannot be revalidated cheaply by an intermediary cache or the browser. A dozen tiles refreshing on a 30-second cadence is a sustained, entirely avoidable query load. The response body is **deterministic** — it is one of exactly three static PNGs (`sla_red.png` / `sla_yellow.png` / `sla_green.png`, `CachingByteArraySLAResourceResolver.java:44-49`) selected by the computed `SLA` enum — so a strong `ETag` (derived from the enum value, or even a constant per-colour tag) is trivially computable and would let every revalidation collapse to a 304 with no body and no recompute. The platform sets none of this today (`DataQualityController.java:42-48` maps the resolved `Resource` straight to `ResponseEntity::ok`).

This adds the operator-facing BI-embed performance caveat. The code-side fix (emit `ETag` + `Cache-Control` and short-circuit on `If-None-Match`) is an upstream performance enhancement — a separate follow-up, not part of this doc.

## Context

Source feature: **F-022** (Data Quality SLA). Surfaced in the 2026-06-08 contradiction-harvest / editorial read.

Canonical code truth (verified by reading the source):

- `DataQualityController.getSLA` (`DataQualityController.java:42-48`) calls `dataQualityService.getSLA(dataEntityId)`, maps it through `slaResourceResolver::resolve`, then `ResponseEntity::ok` — **no caching headers are attached** at any step.
- `DataQualityServiceImpl.getSLA` (`DataQualityServiceImpl.java:84-86`) → `getDatasetSLA` (`:95-101`) executes `reactiveDataEntityRepository.existsIncludingSoftDeleted(datasetId)` **and** `dataQualityRepository.getSLA(datasetId)` (the test-status rows) on every call, then `SLACalculator.calculateSLA` aggregates them. This is the per-render SQL re-run; nothing memoises it.
- The resolved body is a cached in-memory `ByteArrayResource` chosen from exactly three static class-path PNGs by the `SLA` enum (`CachingByteArraySLAResourceResolver.java:14-25`, `:44-49`) — so the response is fully deterministic from a 3-value enum and an `ETag` is trivially derivable.

No `known_refs`. Sibling DQ performance/disclosure caveats already live on `sla-statuses.md` (the unset-severity-as-Major aggregate caveat and the any-authenticated-reader caveat); this one is a distinct, non-overlapping performance angle on the PNG endpoint specifically.
