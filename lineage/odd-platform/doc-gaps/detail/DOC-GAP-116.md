- **DOC-GAP-116**: **META-FINDING** — Service-tier `@ReactiveTransactional` boundary pattern is a platform-wide ADR-grade decision (every reactive service places txn boundaries at the service, every Reactive*Repository class is un-annotated) but is undocumented at any layer; developers reading the live docs cannot understand which writes are atomic with which side-effects, and the asymmetry across SIBLING services (RoleServiceImpl IS transactional on all 3 mutating methods; PolicyServiceImpl is NOT transactional on any) is itself undocumented — operators reasonably assuming "platform follows a uniform transaction discipline" are wrong (HIGH-meta — affects every developer-guide page that describes platform writes; affects every operator considering ODD's data-integrity guarantees)
  - **Category**: drift (meta — pattern-vs-doc divergence on a structural decision)
  - **Surfaced by**:
    - `odd-platform__java__service__service__AlertServiceImpl.md:implicit_adrs.[0]` — "Transaction boundaries declared at the service layer, with deliberate asymmetry per method" (HIGH confidence) **(NEW batch I)**

    - `odd-platform__java__service__service__LineageServiceImpl.md:implicit_adrs.[1]` — "Establisher-keyed atomic-rewrite contract for ingestion" (only `replaceLineagePaths` is annotated; the read paths are not) **(NEW batch I)**
    - `odd-platform__java__service__service__PolicyServiceImpl.md:implicit_adrs.[5]` — "Service composition methods (create, update, delete) are NON-TRANSACTIONAL at this layer, in deliberate inconsistency with the sibling RoleServiceImpl which IS transactional" **(NEW batch I)**

  - **Evidence**:
    - **Pattern verbatim — platform-wide**: every Spring `@Service` class in `<odd-platform-repo>/odd-platform-api/src/main/java/.../service/*ServiceImpl.java` places `@ReactiveTransactional` annotations on mutating methods directly; every `Reactive*RepositoryImpl` class in `<odd-platform-repo>/odd-platform-api/src/main/java/.../repository/reactive/*.java` carries NO transactional annotation. Verified by grep across the 5 batch-I sidecars + the 5 batch-H repository sidecars.
    - **The decision (positive — service tier)**:
      - `AlertServiceImpl.java:152, 201` — `@ReactiveTransactional` on `handleExternalAlerts` + `applyAlertActions` (bulk-mutation paths)
      - `AlertServiceImpl.java:111-113` — DELIBERATELY un-annotated `updateStatus`; relies on `ActivityAspect.java:42`'s synthetic `@ReactiveTransactional` to provide the wrapping transaction
      - `IngestionServiceImpl.java:66` — `@ReactiveTransactional` on `ingest(...)` — the single top-level annotation that scopes the entire 14-processor chain in one transaction (one of the most consequential txn-boundary choices in the platform)
      - `DataEntityServiceImpl.java:197, 246, 288, 308, 324, 337, 357, 388, 411` — 9 `@ReactiveTransactional` annotations on the service (1 read — `getDetails` — which pairs the read with `incrementViewCount`; 8 writes)
      - `LineageServiceImpl.java:125` — `@ReactiveTransactional` on `replaceLineagePaths` (the ingestion-write); `getLineage` and `getDataEntityGroupLineage` are intentionally UN-annotated (pure reads with no atomic-write coupling)
    - **The decision (negative — repository tier)**: per batch-H sidecars, every `Reactive*RepositoryImpl` class (Alert / Lineage / Policy / Ownership / DataEntity) carries NO `@Transactional` / `@ReactiveTransactional` annotation. The repository tier is intentionally policy-agnostic, reusable across different transaction shapes.
    - **The asymmetry (within the service tier)**: NOT every service follows the same atomicity rule:
      - `RoleServiceImpl.java:50, 64, 77` — `@ReactiveTransactional` on all 3 CRUD methods (create / update / delete)
      - `PolicyServiceImpl.java:62, 71, 83` — `@ReactiveTransactional` on NONE of the 3 CRUD methods (the lost-update race that motivates DOC-GAP-122)
      - `OwnershipServiceImpl.java` — `@ActivityLog` + ownership-edge mutations carry transactions (per batch-H Ownership sidecar)
      - `DataEntityServiceImpl.updateStatus` (lines 458-481) — DELEGATES the txn to `DataEntityInternalStateServiceImpl.changeStatusForDataEntities` (DataEntityInternalStateServiceImpl.java:74-75); the wrapper method does NOT have its own annotation
    - **Operator-visible consequence**: the doc-product has no story for "which writes are atomic with which side-effects". Examples that operators reasonably ask:
      - "Does ingesting a 1000-entity payload atomically commit all 1000?" — YES (IngestionServiceImpl.java:66 — single top-level `@ReactiveTransactional`); not documented anywhere operator-facing
      - "Does updating a policy concurrently with another admin produce a deterministic result?" — NO for Policy (DOC-GAP-122); YES for Role (sibling carries `@ReactiveTransactional`); not documented
      - "Does updating an alert status emit an activity-feed row atomically with the status change?" — YES under non-integration-test profile (AlertServiceImpl.java:112 + ActivityAspect.java:42); NO under integration-test profile (`@Profile("!integration-test")` skips the AOP — DOC-GAP-A class hidden test-coverage trap)
      - "Does an FTS recompute failure roll back the description write?" — YES (the FTS-vector rebuild lives inside `upsertDescription`'s `@ReactiveTransactional` boundary at DataEntityServiceImpl.java:324); operators reading the docs cannot know this
    - Live-page state (inherited): no `/developer-guides/...` page describes the platform's transaction model; no `/configuration-and-deployment/...` page describes atomicity guarantees; no `/features/...` page covers it. The pattern is the platform's most consequential architectural decision and is entirely undocumented operator-facing.
  - **Proposed doc action**: **Three-part action**.
    1. **Doc-side primary** (new page): create `/developer-guides/architecture/transaction-model.md` (or equivalent canonical-home) covering: (i) the platform-wide pattern (txn at the service tier, repository tier is policy-agnostic); (ii) the per-service inventory of annotated methods with one-line semantic descriptions; (iii) the within-service asymmetries (e.g. Policy vs Role; updateStatus vs the rest of DataEntityServiceImpl); (iv) the AOP-coupled paths (`@ActivityLog` provides a synthetic transaction via `ActivityAspect.java:42`); (v) the `@Profile("!integration-test")` carve-out and its testing-implications; (vi) the per-feature atomicity guarantees operators can rely on. Cross-link from every `/active-platform-features/*` page that describes a write surface (Alerts, Policies, Roles, Owners, Ownership-edges, Ingestion).
    2. **Code-side companion** (file `/log-issue odd-platform`): three ordered options. (a) **Minimum**: add a class-level Javadoc to every `Reactive*RepositoryImpl` saying "Per platform convention, transaction boundaries are declared at the service tier. This repository is intentionally un-annotated; do not add `@Transactional` here." — codifies the convention against future regression. (b) **Medium**: add a class-level Javadoc to every service that participates in cross-service transactions (e.g. DataEntityServiceImpl.updateStatus → DataEntityInternalStateServiceImpl.changeStatusForDataEntities) naming the delegation; codifies the cross-service boundary. (c) **Full**: ship a Spring ApplicationContext-aware sanity-check at boot time (via Spring `@PostConstruct`) that verifies every mutating service method on every `@Service` class is either `@ReactiveTransactional`-annotated, or has a documented carve-out (in a maintained allowlist), or delegates to a `@ReactiveTransactional`-annotated downstream method.
    3. **Pillar-side meta-recommendation**: add to `pillars/documentation/gates.md` a reviewer checklist item: "For any doc page describing a platform write operation, verify the page describes (a) which methods are transactional and which are not, (b) what the failure mode looks like if the transaction is aborted, (c) what side-effects are atomic with the write (activity-feed emissions, FTS-vector rebuilds, OTLP exports, downstream-service calls). The default doc-product assumption is 'reads are pure, writes are atomic with declared side-effects' — when a write is NOT atomic with a side-effect (e.g. PolicyServiceImpl's read-then-write, or ingestion's OTLP-after-commit), the page must say so."
