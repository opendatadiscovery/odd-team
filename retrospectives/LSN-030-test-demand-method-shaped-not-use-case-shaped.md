# LSN-030: Features are modelled as drift catalogues, never as promises — the user-facing promise has no schema slot, no gap category, and no test

## What happened
The term description-mention feature (`[[ns:term]]` wiki-links — feature **F-056**) is a stateful, cross-tier, cross-time reconciliation engine: typing `[[namespace:name]]` into a data-entity or dataset-field description creates a managed `is_description_link=TRUE` edge (`TermServiceImpl.java:201,362`), renders it as a live deeplink to the term detail page with the definition as tooltip (`useTermWiki.ts:186`), stages unmatched mentions and back-resolves them when the term is later created (`TermServiceImpl.java:421`, called from `createTerm` `:116`), retracts the edge when the mention is removed from the text (`:368-375`), and **blocks deletion of any term still mentioned anywhere** (`:155-160`). After hundreds of tests were written across the platform, this feature had **exactly one** test touching it (`TermServiceImplTest.delete_termMentionedInDescription_errorsBadRequest`, the delete-guard) and **zero** tests of its reason to exist — the happy-path link, the no-match staging, the cross-time resolution, the edit-retraction, the render/deeplink. The ontology's only catalogued gap was TEST-GAP-478, a *permission-bypass* note on the write method. The feature's `feature-flows.yaml` `test_matrix` read `control_summary 0/4`, and no `feature-reflections/detail/F-056.yaml` was ever produced.

## Why it slipped
A corpus-wide sweep (2026-06-03) proved the root cause is structural and universal, not a one-off: **the methodology models a feature as a drift catalogue, never as a promise.** Three facts. (1) *Schema:* all **113/113** feature-flow files carry an `observed_vs_expected` drift catalogue; **0/113** have any `use_case` / `acceptance` / `scenario` / `promise` field — the schema has nowhere to record what a feature *does for a user*, only where it diverges from expectation. (2) *Taxonomy:* all **1038** TEST-GAP nodes fall in seven categories — `missing-edge-case` (335), `missing-security` (310), `missing-integration` (253), `missing-unit` (99), `missing-performance` (39), `missing-binding` (10), `sidecar-stale` (3) — every one a *defect-type* or a *test-layer*; **there is no `functional` / `happy-path` / `acceptance` category**, so "the feature's promise is unverified" is a sentence the gap taxonomy literally cannot express. (3) *Seeding lens:* **38 of 70** seeded features (54%) were born from `SHB-*` security shadow-bugs and inherited the drift lens at birth — F-047 (SHB-010) and F-056 (SHB-030) have test demands that are 100% regression-guards on known risks ("Description-link survives DELETE", "permission-bypass regression", "cross-namespace pollution regression"), not one of which asserts the user-facing promise. Because test demand is derived from the drift model, every test the methodology asks for *hardens a presumed-working feature*; the happy path has no schema slot, no gap category, and — for findings-seeded features like F-056 (`related_test_gaps: []`) — no representation at all. F-056's happy path is untested not because the methodology couldn't see the feature, but because **the methodology has no place to write down what a feature promises — only what is wrong with it.**

The mechanism beneath it, traced: test demand has exactly one generative source that feeds the work backlog — the per-node sidecar's `tests_coverage_semantic.uncovered_behaviours`, which `test-coverage-mapper` joins against real test files to emit `TEST-GAP-NNN`, ranked by *structural* criticality (`security_aggregate × performance_aggregate × fan-in`). But the sidecar's unit of analysis is **one file**, so its "behaviours" are **method responsibilities** — `handleDataEntityDescriptionTerms parses and writes`, `regex edge cases`, `delete guard`. A feature like F-056 is **not in any single file**: it is emergent across the regex, the write-reconciler, the create-time resolver, the delete-guard, the repository queries, the React hook, and the render component. The bottom-up source is therefore *constitutionally* blind to it — it can only ever say "method X lacks a test," never "the use-case *resolve-a-mention-after-the-term-is-created* is unverified." Worse, the word `behaviours` in the field name read like *use-cases* to every reviewer, so a sidecar showing `uncovered_behaviours: [9 items]` looked tracked when not one of the nine was a use-case — the vocabulary manufactured false comfort.

The methodology *does* have layers that see whole features — `feature-flow-builder` (Layer 4) and the `feature-reflector` (Layer 4b). They are the cure. But (a) the feature-flow `test_matrix` collapses a feature's test need into **four coarse type-cells** (unit/integration/perf/security, each GAP/PARTIAL/COVERED) — a coverage-*type* checklist, never the use-case matrix; "0/4" says *you have no integration test*, never *you have no test that a dangling mention resolves cross-time*, so it is a low-information demand indistinguishable from hundreds of identical "needs an integration test" rows. (b) The `feature-reflector`, which *does* produce use-case-level understanding, **emits findings only on CONTRADICTED hypotheses** (bugs/caveats); a *confirmed* hypothesis — "yes, the feature really does resolve mentions cross-time, traced by hand" — produces nothing, when it is in fact the single strongest possible signal that a test must exist: we manually proved a subtle behaviour real and then discarded the proof instead of crystallising it into a guard. And (c) reflection **was never run on F-056 at all** — it has been applied to ~24 cherry-picked features (stopping near F-031), so the one layer that could have produced the matrix was not even pointed at this feature.

The deeper pattern — and the reason this is severity-high, not a one-off: this is the **fourth** time the methodology has discovered that a lower layer cannot see higher-order behaviour (LSN-017 per-node-scan can't see cross-layer user effects → added feature-flows + 4-class matrix; LSN-020 no top-down reflection → added Layer-4b; LSN-023 feature ontology built without the UI; LSN-025 substrate enumerated only entry-points). Each revision added a new **seeing** layer. **Not one of them was ever wired into the test-demand generator.** Test obligations are still minted exclusively by the oldest, lowest, method-shaped layer and ranked by a structural criticality formula with no behavioural-complexity axis; the test build-out then consumed that method-shaped backlog against a line-coverage ratchet (50% + 98%). So hundreds of tests advanced the method/line frontier — which Goodhart's law then made *the* definition of progress — while the feature-use-case frontier sat at zero, and no dashboard measured the second frontier, so green looked like done. The methodology kept buying better eyes and never connected any of them to its hands.

## Rule that emerged
Give the methodology a place to record a feature's **promise**, then derive tests from the promise — not only from the drift. Concretely (status open — proposed methodology revision, not yet built): (1) add a **`use_cases` / acceptance-scenario block to the feature-flow schema** (the slot absent from all 113 features today) and a **`missing-functional` category to the TEST-GAP taxonomy** (the word absent from all 1038 gaps), so "the feature's promise is unverified" becomes expressible, countable, and rankable; the feature layer then emits a per-feature **use-case test matrix** — happy / empty-or-no-match / resolve-later / teardown / edit-reconcile / render / each security+edge facet — each row a typed test obligation, and this matrix becomes the feature's coverage *denominator*, replacing the 4-cell type checklist as the unit of "covered." (2) The `feature-reflector` emits test demands on **confirmed** hypotheses, not only contradicted ones, and is run **systematically** across all features, not a hand-picked subset. (3) `/align` reports a **second coverage frontier** — verified use-cases / total use-cases — as a first-class number distinct from line/method coverage, so the line-coverage ratchet can never again stand in for behavioural coverage. (4) Criticality ranking gains a **behavioural-complexity axis** (stateful / cross-time / cross-tier / reconciling / user-facing) so a bizarre engine outranks a boring high-fan-in CRUD endpoint. (5) Rename the sidecar field `uncovered_behaviours → uncovered_method_responsibilities` and reserve *use-case* / *behaviour* for the feature-layer matrix, killing the vocabulary that masked the gap. This is wiring + representation, not a new layer — the perception already exists; only the pipe from perception to obligation is missing.

## Forcing question
Before calling a feature tested, ask: *"Have I written the use-cases this feature promises a user — happy path, empty, resolve-later, teardown, edit, render — as an enumerated matrix, and does each row have a test? Or have I only confirmed that its methods are executed?"* Method coverage executes lines; use-case coverage keeps promises — and only the second is what an operator feels.
