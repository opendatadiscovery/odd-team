## What

`NamespaceServiceImpl.delete` (and the analogous `OwnerServiceImpl.delete` + `DataSourceServiceImpl.delete`) implements a deterministic cascade-block contract — `Mono.zip` of existence-predicates on referent tables; emit `CascadeDeleteException` if any predicate returns true; otherwise issue soft-delete UPDATE. The contract itself is sound. The implementation is **not atomic** with itself: cascade-check + soft-delete UPDATE share no transaction, no row-lock, no advisory lock. Under READ COMMITTED isolation, a concurrent INSERT into a referent table BETWEEN the EXISTS predicates and the parent UPDATE leaves orphan rows pointing at a soft-deleted parent.

`NamespaceServiceImpl.delete` is additionally **not marked `@ReactiveTransactional`** — single-thread partial failures (network blip between EXISTS and UPDATE) leave the namespace in an inconsistent state.

## Why it matters

Under sustained admin-delete + ingestion-insert load, orphan referent rows accrete (FK passes at insert because the parent row exists at predicate-check time, but the parent is soft-deleted by the time the next reader looks). The orphan is hidden from list reads (soft-delete filter) but visible via direct by-id read — see the F-019 visibility-asymmetry facet for the read-side surface.

Operators trusting the cascade-block contract to keep referent tables consistent get silent data drift. The contract is RIGHT in spec; the implementation has a race window that breaks the spec under concurrency.

Severity MEDIUM because:
- The race window is narrow (millisecond-scale between EXISTS and UPDATE)
- The orphan rows do not cause user-visible failures except in the direct-by-id read path (which is a separate concern)
- BUT — at production-scale ingestion load (where many deployments live), the window is reliably hit

## Suggested fix

1. Add `@ReactiveTransactional` to `NamespaceServiceImpl.delete` (and the sibling Owner / DataSource services for symmetry).
2. Inside the transaction, either: (a) issue a SELECT FOR UPDATE on the parent row before the EXISTS predicates, OR (b) issue the EXISTS predicates against the same snapshot via repeatable-read isolation, OR (c) hold a PostgreSQL advisory lock keyed on the parent table-id while the cascade-check + soft-delete fire.
3. Verify symmetric treatment across the 3+ cascade-block sites (cross-link REFACTOR-430 if it remains open).
4. Add an integration test that exercises the race window — two concurrent transactions, one running cascade-check + soft-delete, the other inserting a referent row in between — assert the orphan does NOT materialize.

Open to alternatives — the right primitive depends on whether jOOQ-Reactive supports the chosen isolation mode out of the box for the target Postgres version.
