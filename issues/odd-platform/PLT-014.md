## What

Three operator-visible defects on the AlertManager webhook ingestion path, all on the same handler chain. The auth posture is **already documented** at `docs.opendatadiscovery.org/features/active-platform-features/alerting` (per WebFetch 2026-05-27) — *"The AlertManager webhook endpoint is not authenticated. ODD Platform whitelists the entire `/ingestion/**` namespace in Spring Security ... it does not cover `/ingestion/alert/alertmanager`."* The defects below are the **operator-visible consequences** of that posture, none of which are surfaced today.

**Defect 1 — Forge-and-display compound.** `AlertServiceImpl.handleExternalAlerts` maps the webhook payload's `labels.entity_oddrn` directly to `AlertPojo.dataEntityOddrn` with NO validation that the oddrn refers to a real DataEntity and NO check that the caller has permission to alert that entity. Combined with the cross-owner read on the platform-wide "All" alerts tab (REFACTOR-024 family), any caller with network reach (anonymous under `auth.type=DISABLED`; any authenticated user otherwise) can POST a forged `entity_oddrn` and inject a Distribution Anomaly alert against any target. The forged alert surfaces on the All tab readable by every authenticated user — a reviewer cannot distinguish forged from real.

**Defect 2 — Generator URL stored-XSS / open-redirect surface.** The webhook payload's `generatorURL` is parsed via `UriComponentsBuilder.fromUri(...)` which does **not block `javascript:` scheme**. The URL is then embedded into the alert description via `String.format("Distribution Anomaly. URL: %s", queryUrl)`. Combined with Defect 1 (unauthenticated webhook), any caller can plant `javascript:alert(1)` payloads OR attacker-controlled URLs that render in the UI's alert description. Stored XSS in the alerts UI.

**Defect 3 — No idempotency — Prometheus retries duplicate alerts.** `ReactiveAlertRepositoryImpl.createAlerts` issues `INSERT ... RETURNING` with no `ON CONFLICT (...) DO NOTHING` clause. Prometheus's standard retry policy duplicates rows on retry. The application-level `AlertActionResolver` de-duplication used by the in-platform path is intentionally skipped on the AlertManager path. Operators see N-times-duplicated alerts in the UI for every transient network blip between AlertManager and the platform.

## Why it matters

The AlertManager webhook is the operator's interface for *"forward Prometheus alerts into ODD Platform so they show up next to data quality alerts."* The intent is reasonable; the defects make it a hostile-input surface that ships with no operator-visible hardening guidance.

Severity is HIGH because:
- Defect 1 enables **cross-tenant alert injection without authentication** when the platform's network edge does not restrict who can POST to `/ingestion/alert/alertmanager`. The default Kubernetes/Compose deployments expose this through the same ingress as the rest of the platform.
- Defect 2 turns the same unauthenticated surface into a **stored XSS vector** — the forged alert's URL field renders in the alerts UI.
- Defect 3 is operational reliability — duplicate alerts make the alert review workflow noisy; combined with Defects 1+2, an attacker can amplify their forged alerts via retry-induction.

This is the case-law class of LSN-001 / LSN-002 (operators following our guide off a cliff).

## Suggested fix

Three coordinated fixes, one PR per fix is fine but they share a test-fixture surface so one combined PR is reasonable:

### Defect 1 fix

Two options:

**Option A (recommended for unauthenticated remote ingestion)** — add a shared-secret check via `X-API-Key` or `Authorization`:

```java
@PostMapping(path = "ingestion/alert/alertmanager")
public Mono<Void> handleAlertManager(
    @RequestHeader("X-AlertManager-Token") String token,
    @RequestBody AlertManagerWebhookRequest req
) {
    return alertManagerAuthService.validate(token)
        .then(alertService.handleExternalAlerts(req.getAlerts()));
}
```

The token is operator-configured at deployment (`alertmanager.webhook.token` config key); AlertManager's `http_config.bearer_token` field carries it.

**Option B (alternative — network-edge guard)** — leave the handler unauthenticated but document explicitly that operators MUST front the path with an ingress / proxy ACL. Less robust; relies on deployment discipline.

Recommend Option A — shared-secret is a 20-line change and removes the network-discipline dependency.

### Defect 1 fix — entity_oddrn validation (mandatory regardless of auth fix)

```java
// AlertServiceImpl.handleExternalAlerts — validate before INSERT
return dataEntityRepository.existsByOddrn(entityOddrn)
    .flatMap(exists -> exists
        ? alertRepository.createAlerts(alertPojos)
        : Mono.error(new InvalidEntityOddrnException(entityOddrn))
    );
```

### Defect 2 fix

Scheme allow-list at URL ingestion + UI-side sanitization defence-in-depth:

```java
// in the alert chunk construction site
URI uri = UriComponentsBuilder.fromUri(URI.create(queryUrl)).build().toUri();
if (!Set.of("http", "https").contains(uri.getScheme())) {
    throw new InvalidGeneratorUrlException(queryUrl);
}
```

And ensure the alerts UI renders the URL via a sanitized renderer (no `dangerouslySetInnerHTML` on the description field).

### Defect 3 fix

Add `ON CONFLICT DO NOTHING` on a natural-key constraint:

```sql
-- Postgres-side
ALTER TABLE alert
  ADD CONSTRAINT alert_natural_key
  UNIQUE (data_entity_oddrn, type, status, external_id);
```

```java
// ReactiveAlertRepositoryImpl.createAlerts
context.insertInto(ALERT, ...)
    .onConflictOnConstraint("alert_natural_key")
    .doNothing()
    .returning(...)
```

`external_id` field comes from `labels.fingerprint` in the AlertManager payload — Prometheus's identifier for the alert grouping.
