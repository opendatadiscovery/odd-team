## What

`AzureLogoutSuccessHandler` calls `URI.create(provider.getLogoutUri())` with **no null-guard**, and the OAuth2 props validator checks `clientId` + `provider` but **not** `logoutUri`. So an Azure-SSO operator who omits the optional-looking `logout-uri` boots successfully and then hits an NPE -> HTTP 500 on the **first logout attempt** - the failure appears only at runtime, not at boot. The sibling `CognitoLogoutSuccessHandler` carries the `StringUtils.isEmpty` early-return guard; Azure does not. Separately, the handler invalidates only the local Spring `WebSession` - no token is revoked at Azure, so the IdP session stays valid until its natural TTL.

This is **distinct from PLT-075** (logout-handler open-redirect: no base-url allowlist across all 5 handlers) - a different defect. The Azure NPE-on-null-logoutUri + no-revoke is not tracked by PLT-075.

## User-facing impact

Static-trace-verified end-to-end against source HEAD (the NPE throw site, the missing validator check, the Cognito guard it's compared against, and the local-only session invalidation were all read directly); not driven on a live Azure-SSO stack. Auth mode: applies only under **OAuth2 with the Azure provider** (`@Conditional(AzureCondition.class)`); inert under every other auth mode.

- **NPE -> HTTP 500 on first logout when `logout-uri` is unset - confirmed by reading the code.** `AzureLogoutSuccessHandler.handle` calls `URI.create(provider.getLogoutUri())` at L39 with no null-guard; if the operator omitted the optional-looking `logout-uri`, `getLogoutUri()` is null, `URI.create(null)` throws NPE, and ODD's single global `@RestControllerAdvice` maps a non-NotFound/non-BadUserRequest throwable to HTTP 500. The operator boots cleanly (the OAuth2 props validator, L17-28, checks only `clientId` + `provider`, not `logoutUri`) and the failure surfaces only on the first Logout click - every user is then unable to log out. The sibling `CognitoLogoutSuccessHandler` (L33-35) has exactly the `StringUtils.isEmpty(...)` early-return guard Azure lacks.
- **Local-only logout even when `logout-uri` is set - confirmed.** `handle` ends with `getSession().flatMap(WebSession::invalidate)` (L47): only the local Spring `WebSession` is cleared; no token is revoked at Azure, so the IdP session stays valid until its natural TTL. A user on a shared workstation who clicks Logout still has a live Azure session, with no UI signal.

Remaining check before a definitive runtime claim: drive an Azure-OAuth2 stack with `logout-uri` unset, click Logout, and confirm the 500 (and, with it set, confirm the Azure session survives a local logout).

## Impact

(a) An Azure operator following the docs but omitting the optional-looking `logout-uri` ships a deployment where every Logout click returns a 500 - users cannot log out at all, and the failure surfaces only at runtime. (b) Even when `logout-uri` is set, the local-only logout means a user on a shared workstation who clicks Logout still has a live Azure session - a real security-posture gap the UI gives no signal about.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: add the `StringUtils.isEmpty` early-return guard at `AzureLogoutSuccessHandler.java:39` matching Cognito (`CognitoLogoutSuccessHandler.java:33-35`), and add `logoutUri` to `ODDOAuth2Properties.validate` when `provider=azure`; document the no-token-revoke caveat. Distinct from PLT-075 (logout open-redirect).
