## What

The data-entity file-attachment feature advertises a maximum file size via the upload-options endpoint, and the web UI uses that value to reject oversized files before uploading. But the limit is **never enforced on the server**. The chunked upload path accepts each `uploadFileChunk` request and writes the chunk straight to disk with no byte accounting and no comparison against the configured maximum. A client that calls the upload API directly — bypassing the browser UI — can therefore upload a file of any size, in as many chunks as it likes, with the server happily streaming every byte to storage. The configured `attachment.max-file-size` is a presentation hint returned to the client, not a server-side guard.

## Where

The cap is read from config and **only echoed to the client** as upload options:

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/service/attachment/AttachmentServiceImpl.java:27-28,60-61`

```java
@Value("${attachment.max-file-size}")
private Integer maxFileSize;
...
@Override
public Mono<DataEntityUploadOptions> getUploadOptions() {
    return Mono.just(new DataEntityUploadOptions().maxSize(maxFileSize * 1_000_000));
}
```

The chunk-upload entry point performs **no size check** — it parses the index and delegates straight to the service:

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/controller/DataEntityAttachmentController.java:54-62`

```java
@Override
public Mono<ResponseEntity<Void>> uploadFileChunk(final Long dataEntityId,
                                                  final UUID uploadId,
                                                  final Mono<Part> fileMono,
                                                  final String index,
                                                  final ServerWebExchange exchange) {
    return fileMono
        .flatMap(file -> attachmentService.uploadFileChunk(uploadId, file, Integer.parseInt(index)))
        .map(ResponseEntity::ok);
}
```

And the service writes the chunk to disk with no byte limit (`maxFileSize` is not referenced anywhere on this path):

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/service/attachment/FileServiceImpl.java:58-67`

```java
@Override
public Mono<Void> uploadFileChunk(final UUID uploadId, final Part file, final int index) {
    if (file instanceof FilePart filePart) {
        final Path chunkDirectory = FileUtils.getChunkDirectory(uploadId);
        final Mono<Void> uploadedMono = Mono.defer(() -> Mono.just(chunkDirectory)
            .flatMap(path -> filePart.transferTo(path.resolve(String.valueOf(index)))));
        return checkProcessingUploadById(uploadId).then(uploadedMono);
    } else {
        return Mono.error(new BadUserRequestException("Uploaded multipart is not a file"));
    }
}
```

The only validations on this path are "is it a file part?" and "is there a processing upload with this id?". Neither per-chunk size nor cumulative size is ever checked against `maxFileSize`.

## Why it matters

Because the limit lives only in the client, it is trivially bypassed by any non-browser caller (curl, a generated SDK client, a script):

- **Storage-fill denial of service.** A caller can upload arbitrarily large files, repeatedly, to fill the attachment storage volume. There is no server-side ceiling to stop it.
- **Heap / resource pressure.** Unbounded chunk uploads streamed through the application put pressure on the node and degrade the platform for all users, independent of the storage backend.
- **Defense-in-depth gap.** A size limit that exists only as a UI affordance provides no actual protection; the security property the operator believes they have (capped uploads) does not hold against the API.
- **Who is affected:** every deployment exposing the attachment upload API, especially with authentication disabled or weakly scoped, where any reachable client can drive the upload endpoints directly.

Severity **high**: an externally reachable, unbounded write-to-storage path is a denial-of-service vector, and the configured protection is silently ineffective.

## Suggested fix

Enforce the configured maximum server-side on the chunk-upload path, not just in `getUploadOptions` (open to alternatives):

1. Validate cumulative upload size against `maxFileSize * 1_000_000` as chunks arrive (track bytes written per `uploadId`, e.g. at `FileServiceImpl.uploadFileChunk`), and reject with a `BadUserRequestException` (HTTP 4xx) once the limit is exceeded — mirroring the existing `checkProcessingUploadById` validation style on the same path.
2. As defense-in-depth, also bound the per-request multipart size at the WebFlux codec / framework layer so a single oversized chunk cannot be buffered before the application-level check runs.

The configured value is already available (`AttachmentServiceImpl.maxFileSize`); the fix is to consult it where bytes are actually written, not only where options are reported to the client.

Surfaced during the 2026-06-08 contradiction-harvest (feature-reflection contradiction triage) — see the harvest report `integration-tests/run-log/2026-06-08-feature-complete.md` and the F-027 (file attachments) feature reflection (`lineage/odd-platform/feature-reflections/detail/F-027.yaml`), whose "max-file-size is enforced" hypothesis was traced through the upload path and contradicted: the cap appears only in `getUploadOptions` and is absent from the chunk-write path.
