## Description

The Test Report detail overview renders the Quality Test's `expectation` object **verbatim** as pretty-printed JSON: `const stringifyParams = JSON.stringify(qualityTest?.expectation, null, 2);` (`TestReportDetailsOverview.tsx:54`), displayed in the "Parameters" panel (`TestReportDetailsOverview.tsx:135-137`) and expandable through a "See more" modal (`:138-145`). The `expectation` object carries the upstream DQ framework's expectation configuration — for Great Expectations and dbt this can include sample failing values, threshold rows, column/table identifiers, and other test-result detail. No redaction, no schema enforcement, no per-owner gate is applied: the panel shows whatever the framework pushed, to **any authenticated viewer** of that test (and, under `auth.type=DISABLED`, anonymously), regardless of dataset ownership.

How it misleads an operator: an operator reading `sla-statuses.md` learns severities are operator-set and that DQ read endpoints are reachable to any authenticated user, but **nothing tells them the expectation/parameters payload itself is a confidentiality surface**. In a multi-tenant deployment, a viewer from one team opens any other team's Quality Test detail and reads the raw expectation JSON — which routinely embeds failed-row samples (PII column values, customer ids, transaction amounts) for Great Expectations and compiled SQL / column names for dbt. This is the **same leak class as DOC-185's `status_reason`** field, but a **different channel**: DOC-185 documents the per-run diagnostic-text leak on the Test Run History page; this is the static expectation-config leak on the Test Report Parameters panel. Both flow from the platform-wide catalog-read-collaborative posture (no per-owner read gate on DQ surfaces).
