## What

The `!external` guard that protects Collector-pushed tags from UI overwrite (`updateTag` and `deleteTag` both `.filter(!tagDto.external())`) reads **only** the data-entity aggregate: `external` = `boolOr(tag_to_data_entity.external)`, and `getDto` joins **only** `TAG_TO_DATA_ENTITY`. The `tag_to_dataset_field` table uses a separate `TagOrigin` enum (`INTERNAL` / `EXTERNAL` / `EXTERNAL_STATISTICS`) which `getDto` never joins. So a tag whose **only** Collector-set origin is an `EXTERNAL` `tag_to_dataset_field` row (with no external data-entity relation) **passes** the `!external` guard and can be renamed via `PUT /api/tags/{id}` or deleted via `DELETE /api/tags/{id}` by any UI user holding `TAG_UPDATE` / `TAG_DELETE` — silently mutating or destroying the Collector-owned dataset-field tag.

This is **net_new** — no existing item tracks the incompleteness of the external-guard's aggregate.

## Impact

A tag pushed by a Collector exclusively at the dataset-field level (`EXTERNAL` / `EXTERNAL_STATISTICS` origin) is unprotected: a UI user can rename it (breaking the Collector's next reconcile, which keys on the name) or delete it (so the next ingestion re-creates it, churning). The protection the operator believes is uniform — "Collector tags are read-only in the UI" — holds only for the data-entity side. The positive invariant is real but incomplete.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: extend `getDto`'s `external` aggregate to also OR over `tag_to_dataset_field.origin IN ('EXTERNAL','EXTERNAL_STATISTICS')` (`ReactiveTagRepositoryImpl.java:54-66`).
