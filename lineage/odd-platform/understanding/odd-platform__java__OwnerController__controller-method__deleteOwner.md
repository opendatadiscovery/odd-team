# OwnerController#deleteOwner — semantic understanding

## understanding

`deleteOwner` is the reactive `DELETE /api/owners/{owner_id}` handler — a four-line WebFlux delegation that calls `ownerService.delete(ownerId)` and lifts to `204 No Content`. The endpoint is the **directory-level destruction verb** for the Owner entity (sibling of `createOwner` and `updateOwner` on the same controller); it is gated by `OWNER_DELETE` permission via the centralised `SecurityConstants.SECURITY_RULES[146-147]` rule pipeline. The underlying `OwnerServiceImpl.delete` (`OwnerServiceImpl.java:88-100`) runs a transactional three-leg cascade-block check (`termOwnership.existsByOwner` + `ownership.existsByOwner` + `userOwnerMapping.isOwnerAssociated`) and either **soft-deletes** the owner row (UPDATE `owner` SET `deleted_at = NOW()` via `ReactiveAbstractSoftDeleteCRUDRepository.delete`) **plus hard-deletes ALL of the owner's role bindings** (`ownerToRoleRepository.deleteOwnerRelationsExcept(id, List.of())` issues `DELETE FROM owner_to_role WHERE owner_id = ?`) — or fails with `CascadeDeleteException` (HTTP 400 USR004, "Owner cannot be deleted: there are still resources attached"). This is a **mixed soft+hard-delete shape**: the owner row persists with `deleted_at` set (the name is freed for re-use via the partial-unique-index `owner_name_unique ON owner(name) WHERE deleted_at IS NULL` per `V0_0_64__remove_is_deleted_field.sql:70`), while the role bindings are physically removed; the cascade-block protects against destroying owner-bearing entities but is silent on (a) the soft-deleted-owner-association-request orphan path and (b) the search-vector refresh that `update` performs but `delete` skips.

- invariants:
  - "**Soft-delete on the owner row + hard-delete on role bindings — asymmetric persistence.** `OwnerServiceImpl.delete:97` calls `ownerToRoleRepository.deleteOwnerRelationsExcept(id, List.of())` which issues `DELETE FROM owner_to_role WHERE owner_id = ? AND role_id NOT IN ()` (`ReactiveOwnerToRoleRepositoryImpl.java:52-56`) — hard-DELETE. `OwnerServiceImpl.delete:98` calls `ownerRepository.delete(id)` which inherits `ReactiveAbstractSoftDeleteCRUDRepository.delete(long)` — UPDATE `owner` SET `deleted_at = generateNow()` (`ReactiveAbstractSoftDeleteCRUDRepository.java:50-59`). The role-binding history is permanently lost; the owner directory row persists indefinitely."
  - "**Cascade-block is the SOLE persistence-layer safety against orphaning OWNERSHIP / TERM_OWNERSHIP / USER_OWNER_MAPPING.** Both `OWNERSHIP` and `TERM_OWNERSHIP` are HARD-DELETE tables (`ReactiveOwnershipRepositoryImpl.java:85-91` + `ReactiveTermOwnershipRepositoryImpl.java:55-61` use `deleteFrom`). `USER_OWNER_MAPPING` is soft-deleted. The FK from each of these to OWNER has NO `ON DELETE CASCADE` (verified: `user_owner_mapping_fk_owner` at `V0_0_4__add_user_owner_mapping.sql:6` and `owner_association_request_owner_fk` at `V0_0_51__add_owner_association_request.sql:11` carry no ON DELETE). If the service-layer cascade-block were bypassed by a direct DB UPDATE setting `owner.deleted_at` (or by a future refactor weakening the existence checks), no DB-side mechanism would prevent the orphan-row state. **Mirror of the F-006 family pattern.**"
  - "**The cascade-block is NOT atomic with the deletes that follow.** `OwnerServiceImpl.delete:90-100` is `@ReactiveTransactional` (line 88), so the three `existsBy*` reads, the `deleteOwnerRelationsExcept`, and the `ownerRepository.delete` run inside one transaction. BUT the existence checks `termOwnership.existsByOwner` (`ReactiveTermOwnershipRepositoryImpl.java:74-80`) and `ownership.existsByOwner` (`ReactiveOwnershipRepositoryImpl.java:120-127`) do NOT carry `SELECT FOR UPDATE` locks on the owner row. A concurrent `POST /api/dataentities/{id}/ownership` writing a fresh OWNERSHIP row referencing this owner between the existence-check and the soft-delete is theoretically race-windowed (no advisory lock on owner_id, no row-level lock acquired by the existence-check). The race window is bounded by the transaction's isolation level (default `READ COMMITTED` per Spring/R2DBC defaults — `READ COMMITTED` does not serialize the read against concurrent writes on the same key)."
  - "**`isOwnerAssociated` filters on `DELETED_AT IS NULL` but `existsByOwner` (Ownership + TermOwnership) does NOT.** `ReactiveUserOwnerMappingRepositoryImpl.java:88-96` adds `AND DELETED_AT IS NULL` to the EXISTS subquery — a soft-deleted user_owner_mapping does NOT block owner deletion. `ReactiveOwnershipRepositoryImpl.java:120-127` and `ReactiveTermOwnershipRepositoryImpl.java:74-80` query raw tables without any deleted-at filter — but OWNERSHIP and TERM_OWNERSHIP are HARD-DELETE tables, so this is correct (no stale soft-deleted rows could exist). The asymmetry is consistent with the underlying schema; it is NOT a bug, but it is an unstated invariant the maintainer must hold when reading the code."

## security

- **auth_mode_relevance**: `LOGIN_FORM | OAUTH2 | LDAP` (the three modes that protect the UI/API surface this controller is mounted on, per batch-C class-level sidecars for each `*SecurityConfiguration`). Under `DISABLED` the endpoint is anonymously reachable — the SecurityRule remains in the list but the filter chain doesn't run (`DisabledAuthSecurityConfiguration.java:10` per batch-C sidecar). `S2S` is not relevant — S2S protects `/ingestion/entities` POST only, not `/api/owners*`. - **ingestion_filter_relevance**: `NO — UI/API surface, not /ingestion/entities`. The `IngestionDataEntitiesFilter` matches `/ingestion/entities` POST only (per batch-A class-level sidecar); `DELETE /api/owners/{owner_id}` does not match.
- **authorization_assertions**:
  - "`SecurityRule(NO_CONTEXT, '/api/owners/{owner_id}' DELETE, OWNER_DELETE)` — the rule is registered in `SecurityConstants.SECURITY_RULES[146-147]` and consumed by `AuthorizationCustomizer` to add a permission check to the WebFlux security chain. `NO_CONTEXT` AuthorizationManagerType signals this is a global (non-per-resource) gate, evaluated against the caller's Policy/Permission set. Note: the `{owner_id}` path-template is matched by the path matcher; the rule does NOT consult `owner_id` to do per-resource authorization (e.g. 'only this owner's manager can delete') — any caller with the `OWNER_DELETE` permission can delete ANY owner. Consistent with `OWNER_CREATE` / `OWNER_UPDATE` siblings." — evidence: `SecurityConstants.java:146-147`

The cascade-block CHECKS ownership rows (`OwnerServiceImpl.java:91`) but does not narrow the operation by the caller's principal identity. - **data_exposure**:
  - "No data is exposed in the success path — `204 No Content`. - **hot_paths**: [] — N/A. Owner deletion is an admin-time operation (per the live owners doc, "managed in the Management → Owners tab"), not a per-render or per-event call.   - "Stateless controller method — horizontal scaling unconstrained at this layer" — evidence: `OwnerController.java:41-45` (no instance state)
