## What

The Swagger UI shell loads, but the OpenAPI document never loads - the page sits on **"Failed to load API definition."** The underlying spec request (the api-docs JSON) **hangs forever** (no response; CPU ~1%, so it's a dead thread, not a loop).

Root cause: **`springdoc-openapi` 2.2.0 is binary-incompatible with Spring Framework 6.2.x.** springdoc 2.2.0 calls `new ControllerAdviceBean(Object)` - a constructor Spring **removed** in 6.2. When springdoc walks the platform's `@ControllerAdvice` (to build response schemas), it throws:

```
java.lang.NoSuchMethodError:
  'void org.springframework.web.method.ControllerAdviceBean.<init>(java.lang.Object)'
    at org.springdoc.core.service.GenericResponseService...  [springdoc-openapi-2.2.0.jar]
                                                             [spring-webflux-6.2.11.jar]
```

The `NoSuchMethodError` kills the reactive worker thread, so the request's `Mono` never completes and the HTTP call hangs. Both spec groups (platform-api, ingestion-api) time out.

## Where

- `gradle/libs.versions.toml:25` -> `springdoc-openapi = '2.2.0'` (pinned), consumed by `odd-platform-api/build.gradle:49`.
- Spring Boot is **3.4.10** (verified in the build banner) -> Spring Framework **6.2.x**.

## When / why it broke

Commit **`2033822e`** - *"fix(security): spring boot upgrade and dependency alignment (#1736)"* (2026-04-01) - bumped spring-webflux **6.1.14 -> 6.2.11** (Spring Boot -> 3.4.10) for CVE fixes, but **left `springdoc-openapi` pinned at 2.2.0**. Before that commit, Spring 6.1.14 was compatible with springdoc 2.2.0 and Swagger worked. The security-driven Spring upgrade left springdoc behind. The current `:latest` image carries the broken combination.

## Impact

- The interactive API surface (`{base}/api/v3/api-docs` Swagger UI) and the OpenAPI JSON are **dead on every current deployment** - operators and SDK consumers can't read or test the live spec. The demo (`demo.oddp.io`) is affected on current builds.
- This is a **silent feature regression** that shipped undetected because **there was no test pinning the OpenAPI-spec endpoint.** An integration test now pins it (odd-team `IT-042`, currently RED - it flips green when this is fixed).
- The published docs page describing Swagger was also (separately) orphaned from `SUMMARY` and 404'd; recovered + caveated in `documentation` PR `docs/recover-swagger-api-reference`.

## Reproduce

```
curl -m 8 -i {base}/api/v3/swagger-ui.html     # the OpenAPI JSON spec -> HANGS (no response within 8s)
curl -i {base}/api/v3/api-docs                  # the UI -> 302 -> shell 200, but the in-page spec fetch hangs
```

## Fix

Bump springdoc to the Spring Boot 3.4 / Spring 6.2-compatible line in `gradle/libs.versions.toml`:

```
springdoc-openapi = '2.7.0'   # was 2.2.0
```

No code change needed - it's a stale-jar binary-compatibility problem. After the bump, verify the OpenAPI JSON returns and the Swagger UI loads the definition. Keep a CI/integration check (odd-team `IT-042` already pins the spec endpoint) so a future Spring/springdoc drift is caught immediately rather than shipping silently.

## Footnote (usability, optional)

The springdoc paths are deliberately **swapped** in `application.yml`: Swagger **UI** -> `/api/v3/api-docs`, OpenAPI **JSON** -> `/api/v3/swagger-ui.html`. Even after the version fix, the intuitive `.../api-docs` serves the UI, not the spec - consider un-swapping for clarity (separate, optional change).
