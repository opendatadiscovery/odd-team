## Description

The "Auto-create side-door" table on `namespaces.md` (lines 62-67) lists the four sister services that mint Namespace rows through `NamespaceServiceImpl.getOrCreate(name)` when their request body carries a non-empty `namespace_name`. The table is **asymmetric**: the Data Source row correctly lists both the create and update endpoints (`POST /api/datasources`, `PUT /api/datasources/{id}`) with both gating permissions (`DATA_SOURCE_CREATE`, `DATA_SOURCE_UPDATE`), but the Term, Collector, and Data Entity Group rows list **CREATE only**.

This is wrong: the UPDATE paths for all three of those services *also* call `namespaceService.getOrCreate(...)` and therefore also bypass `NAMESPACE_CREATE`:

- `TermServiceImpl.updateTerm(...)` calls `namespaceService.getOrCreate(formData.getNamespaceName())` (TermServiceImpl.java:138).
- `CollectorServiceImpl.update(...)` calls `namespaceService.getOrCreate(form.getNamespaceName())` (CollectorServiceImpl.java:57).
- `DataEntityGroupServiceImpl.updateDataEntityGroup(...)` calls `namespaceService.getOrCreate(formData.getNamespaceName())` (DataEntityGroupServiceImpl.java:84).

An operator who reads the table concludes that a holder of `TERM_UPDATE`, `COLLECTOR_UPDATE`, or `DATA_ENTITY_GROUP_UPDATE` cannot mint a namespace — but they can: renaming a term / collector / DEG to a namespace string that does not yet exist silently inserts a new `namespace` row. The mitigation paragraph at line 74 lists the permissions to treat as implicitly granting namespace-creation rights (`DATA_SOURCE_CREATE`, `DATA_SOURCE_UPDATE`, `TERM_CREATE`, `COLLECTOR_CREATE`, `DATA_ENTITY_GROUP_CREATE`) — it omits the three `*_UPDATE` permissions, so an operator hardening the deployment would leave the UPDATE side-door open.
