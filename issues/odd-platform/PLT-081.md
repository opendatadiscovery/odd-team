## What

The `admin-groups` configuration knob uses **case-insensitive SUBSTRING containment** instead of exact equality in TWO provider handlers:

**LDAP (F-124a — substrate-confirmed).** `LDAPSecurityConfiguration.java:96` invokes `containsIgnoreCase(properties.getGroups().getAdminGroups(), authority)` — substring match. Operator config `admin-groups: ['ops']` against LDAP groups `devops`, `noops`, `appops`, `dataops` silently promotes EVERY member of EVERY one of those groups to ADMIN.

**GitHub (F-124b — NEW NOT IN SUBSTRATE, surfaced this run).** `GithubUserHandler.java:119` invokes `containsIgnoreCase(provider.getAdminGroups(), userTeam)` — same SUBSTRING pattern. Operator config `admin-groups: ['admins']` against GitHub teams `team-admins`, `admins-readonly`, `data-admins` promotes every member of every match.

Operator mental model "admin-groups is an exact-match list" diverges from runtime behaviour. The doc explicitly mentions both LDAP admin-groups and GitHub admin-groups; neither warns about substring-match.

## Why it matters

A security audit assuming exact-match semantics misses entire user populations granted ADMIN via short admin-group tokens. **HIGH severity in this batch** — silent privilege escalation across two providers.

The mitigation today is operator-side (use long full-group-name tokens like `ODD_PLATFORM_ADMINS`). Operators following the doc as written hit this footgun.

The cross-provider pattern is the load-bearing observation: this is NOT an LDAP-specific quirk; it's a `containsIgnoreCase` idiom used across at least 2 handlers. A class-level audit should sweep the codebase for `containsIgnoreCase` against any admin-detection / authorization input.

## Suggested fix

**Thread A — Joint LDAP + GitHub fix:**

```java
// LDAPSecurityConfiguration.java:96 — before
.filter(a -> containsIgnoreCase(properties.getGroups().getAdminGroups(), a.getAuthority()))

// (after)
.filter(a -> properties.getGroups().getAdminGroups().stream()
    .anyMatch(g -> g.equalsIgnoreCase(a.getAuthority())))
```

```java
// GithubUserHandler.java:119 — before
.filter(userTeam -> containsIgnoreCase(provider.getAdminGroups(), userTeam))

// (after)
.filter(userTeam -> provider.getAdminGroups().stream()
    .anyMatch(g -> g.equalsIgnoreCase(userTeam)))
```

Both calls use `equalsIgnoreCase` rather than substring — exact-match against admin-group entries.

**Thread B — Operator-side migration note (release notes / CHANGELOG):**

Operators relying on substring-match behaviour (intentionally or by accident) will see their previously-ADMIN users drop to USER on the release. Document the change as a SECURITY hardening:

> **BREAKING: admin-groups now requires exact group-name match (was: substring).**
> Previously `admin-groups: [ops]` matched LDAP groups `devops`, `noops`, `appops`, `dataops`. After this release the match is exact: `admin-groups: [ops]` matches only the literal group `ops`.
> To preserve previous behaviour, list each group explicitly: `admin-groups: [devops, noops, appops, dataops]`.
> See https://docs.opendatadiscovery.org/configuration-and-deployment/enable-security/authentication/ldap (DOC-238 reference).

**Thread C — Class-level grep audit (recommended follow-up):**

Sweep the codebase for other `containsIgnoreCase` calls against admin-detection / authorization input. Verify each: substring is intentional or accidental? Each occurrence either becomes `equalsIgnoreCase` or is documented with the substring rationale.

## Withdrawn (2026-06-08, per DOC-336)

This issue is a **NO-OP** and is withdrawn. It proposed changing `containsIgnoreCase` → `equalsIgnoreCase` to "fix" an admin-groups SUBSTRING overpromotion — but `OperationUtils.containsIgnoreCase(collection, element)` is **already** `collection.stream().anyMatch(element::equalsIgnoreCase)` (`OperationUtils.java:7-9`): full case-insensitive **equality**, not substring. The GitHub (`GithubUserHandler.java:119`) and LDAP admin-group matches already use full equality. There is no substring bug to fix; acting on this issue would risk introducing one. The doc surfaces that carried the false substring claim were corrected by DOC-336.
