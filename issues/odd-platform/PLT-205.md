## What

On a data entity's **Discussions** tab, when there are no messages the empty-state placeholder reads "No messages" - and that string is **hardcoded English**, not passed through the i18n translation function. Every other user-facing string in the surrounding Data Collaboration UI is translated; this one is not, so under a non-English locale the empty Discussions panel shows untranslated English while the rest of the page is localised.

## Where

`odd-platform-ui/src/components/DataEntityDetails/DataCollaboration/MessagesList/MessagesList.tsx:70`

```tsx
{isMessagesLoaded && !messagesLength && (
  <EmptyContentPlaceholder text='No messages' />   // <-- literal string, no t() wrap
)}
```

`MessagesList.tsx` does not import `useTranslation` at all, so the literal is the only option as written. Contrast the sibling component in the same `DataEntityDetails` tree, `LinkedItemsList/LinkedItemsList.tsx`, which DOES wrap its empty-state:

```tsx
// LinkedItemsList.tsx:4   import { useTranslation } from 'react-i18next';
// LinkedItemsList.tsx:19  const { t } = useTranslation();
// LinkedItemsList.tsx:86  <EmptyContentPlaceholder text={t('No linked entities')} />
```

The two empty-states are structurally identical (`EmptyContentPlaceholder text=...`); one is translated, one is not - a localisation drift between siblings.

Note on the placeholder itself: `EmptyContentPlaceholder` *does* call `useTranslation` internally, but only for its **default** fallback - it renders `text ?? t('No information to display')` (`components/shared/elements/EmptyContentPlaceholder/EmptyContentPlaceholder.tsx`). When a `text` prop is supplied it is rendered verbatim, so the caller must pass an already-`t()`-wrapped string. `MessagesList.tsx:70` passes the raw literal `'No messages'`, so it renders untranslated regardless of the placeholder's own i18n.

## User-facing impact

Static code trace, not driven under a non-English locale in this sweep. Verified by reading the source (2026-06-10): on a data entity's Discussions tab, when `isMessagesLoaded && !messagesLength` (`MessagesList.tsx:69`), the empty-state renders `<EmptyContentPlaceholder text='No messages' />` (`:70`) - a hardcoded English literal, and `MessagesList.tsx` imports no `useTranslation` (imports at `:1-10`). So under a non-English UI locale the Discussions empty panel shows English "No messages" while the surrounding collaboration UI is localised. Cosmetic/i18n only - no functional, data, or security impact; visible solely to non-default-locale operators in the empty state. Remaining check: confirm on a running stack under a non-English locale (the `multilingual-i18n.spec.ts` rail covers the i18n surface but does not assert this specific empty-state).

## Why it matters

Silent (no error; visible only to non-English users, and only in the empty state). Affects operators running the platform under a non-default locale: the Discussions panel leaks an untranslated English string, breaking the localisation contract that the rest of the collaboration UI honours. Real consistency/i18n defect but purely cosmetic - no functional, data, or security impact, and only in the empty state under a non-default locale. **Severity low** (regraded from medium 2026-06-10): per the workspace Priority Order a cosmetic/i18n string sits at Low; the draft's own assessment is "low functional impact," so medium overstated it. The fix is trivial.

## Suggested fix

Import `useTranslation` in `MessagesList.tsx`, pull `const { t } = useTranslation();`, and wrap the literal: `<EmptyContentPlaceholder text={t('No messages')} />` - mirroring `LinkedItemsList.tsx:86`. Add the corresponding key to the translation catalogues.

Surfaced in the 2026-06-08 feature-reflection contradiction harvest - `lineage/odd-platform/harvest/2026-06-08-contradiction-harvest.md`, sourced from the F-197 feature reflection (`lineage/odd-platform/feature-reflections/detail/F-197.yaml`). ## Addendum 2026-06-15 (WHOLE-CLASS rescope) -- this is the dominant i18n problem, not a single string

`user_facing_verified: true` now. During CTRIB-014 (#1751 per-locale translation) the maintainer drove the
REAL page `/data-modelling/relationships` under `ua` and found it almost entirely English -- the "No messages"
empty-state above is one instance of a LARGE class.

**The catalog-key class is closed; THIS (unwrapped) class is what keeps i18n "still English".** There are two
kinds of i18n string in the SPA:
1. **catalog-key** -- a `t('<literal>')` call exists; the key just has to be present in every locale catalog.
   `#1748` (3 tabs) + `#1751`/CTRIB-014 (the 84 remaining keys) + the vitest key-parity guard CLOSED this class
   (all 436 `t()` keys present in all 7 catalogs, gated).
2. **unwrapped** -- a hardcoded English literal with NO `t()` (or a dynamic `t(variable)`), so it never reaches
   i18next and renders English under EVERY locale. No catalog/translation work can fix it -- there is no key.
   THIS is class 2, and it is why each catalog pass felt like a sliver: the catalog metric is blind to it.

**Flagship instance -- the entire Relationships page is class 2 (code-verified 2026-06-15):**
- `DataModelling/Relationships/RelationshipsTitle.tsx:19` -> `<Typography variant='h1'>Relationships</Typography>` (heading, hardcoded)
- `RelationshipsTitle.tsx:21` -> `<NumberFormatted .../> relationships overall` (count caption, hardcoded)
- `RelationshipsSearchInput.tsx:17` -> `placeholder='Search relationships'` (hardcoded)
- `RelationshipsTabs.tsx:11,15,19` -> tab `name: 'All' | 'ERD' | 'Graph'` (hardcoded)
None of these files import `useTranslation`. (The Data Modelling *sidebar tab* "Relationships" DOES use `t()`
and is translated by CTRIB-014 -- so under `ua` the tab reads "Зв'язки" but the page body is English.)

**App-wide magnitude (heuristic lower bound, 2026-06-15):** ~65 distinct hardcoded user-facing string
*props* (`placeholder=`/`label=`/`title=`/`text=`/...) not via `t()`; plus JSX text nodes (the "Relationships"
heading class) on top. Worst-offender dirs: `shared`, `DataEntityDetails`, `Terms`, `DataModelling`,
`MasterData`, `Management`. Order of magnitude: dozens-to-~100+ strings, concentrated in newer features built
without i18n discipline.

## Suggested fix (whole-class -- converge once, then guard)

1. **Sweep + wrap:** enumerate every user-facing string literal in JSX text + UI props that is not `t()`-wrapped;
   wrap each in `t('...')`, add the key to `en.json` (the natural-keys convention), and translate across the 6
   non-en catalogs (the same motion as #1751). For dynamic strings (`Search ${x}`, `${n} overall`) use
   i18next interpolation keys (`t('Search {{kind}}', { kind })`, `t('{{count}} relationships overall', {count})`).
2. **CI guard (the lead deliverable -- the convergence):** add a lint rule that FAILS the build on an unwrapped
   user-facing JSX string literal -- `eslint-plugin-i18next`'s `no-literal-string` (allow-list code-only props
   like `variant`/`color`/`data-*`), or a custom AST rule. This is to class 2 what the key-parity test is to
   class 1: without it, every new feature re-introduces unwrapped strings and i18n never converges. Free +
   self-hosted; wire it into the FE lint job. (Note: that FE job is itself not yet in CI -- see PLT-215
   addendum #3; the guard lands with the FE-checks wiring.)
3. Bundle the per-page wraps into a few bounded PRs (e.g. Relationships page; shared components; DataEntityDetails)
   rather than 65 single-string tickets -- "fix the whole claim", do not loop the instance.

Acceptance = drive each touched page under `ua` and read zero English (the rendered-page test, not the catalog
%). PLT-205's "No messages" empty-state is folded in as instance #1.
