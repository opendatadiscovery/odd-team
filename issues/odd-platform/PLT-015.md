## What

`SlackMessageGenerator` renders `AlertChunkPojo.description` (ingestion-supplied text) verbatim into the Slack mrkdwn payload it POSTs to the operator's Slack webhook. Slack's mrkdwn syntax interprets the following tokens as control sequences:

- `<!channel>` and `@channel` -> broadcast notification to every member of the receiving Slack channel
- `<https://attacker.example|click here>` -> renders as "click here" hyperlink, target URL hidden from casual readers
- `<!here>` -> broadcast notification to online members
- `<!subteam^SUBTEAM_ID>` -> broadcast notification to a Slack subteam

The verbatim render is real (verified 2026-06-10): `generateAlertMessage` embeds `buildDescriptionsFromChunks(message.getAlertChunks())` through `markdownText(...)` with no escaping (`SlackMessageGenerator.java:76-77`; `buildDescriptionsFromChunks` at `:95-101` is `.map(AlertChunkPojo::getDescription).collect(joining)` - no sanitisation).

**The headline compound in the original draft is FALSIFIED.** It claimed a remote caller injects `<!channel>` / fake-link markup *via the unauthenticated AlertManager webhook* (PLT-014 Defect 1). That path does not carry mrkdwn tokens: an external alert's chunk description is the fixed literal `String.format("Distribution Anomaly. URL: %s", queryUrl)` (`AlertServiceImpl.java:185`), and `queryUrl` derives from `ExternalAlert.generatorURL`, which is typed `java.net.URI` (`ExternalAlert.java:13`) - Jackson/`URI.create` REJECTS `<`, `>`, `|` with `IllegalArgumentException` (verified 2026-06-10), so `<!channel>` / `<url|text>` cannot pass through the webhook. The webhook therefore cannot deliver the mrkdwn payload this issue is about.

**The real injection vector** is ingestion-sourced chunk descriptions: a failed-job/failed-DQ alert's description is `"Job %s failed with status %s".formatted(taskRun.getTaskRunName(), taskRun.getStatus())` (`IngestionTaskRunAlertState.java:139`), where `taskRunName` is free text supplied by the collector via `POST /ingestion/entities`. A `taskRunName` containing `<!channel>` flows verbatim to Slack. Under `auth.type=DISABLED` (default) the `/ingestion/entities` path is itself anonymous, so the anonymous-injection property survives - but through the ingestion-entities endpoint, not the alertmanager webhook, and only for alerts whose entity has a configured Slack notification.

## User-facing impact

- WHO: a Slack-workspace member receiving ODD alert notifications; the injector is whoever can write a task run with a crafted `taskRunName` (anonymous under DISABLED via `/ingestion/entities`; collector-token-holder otherwise).
- WHAT happens: a `taskRunName` like `<!channel> URGENT` becomes a chunk description and is POSTed to the configured Slack webhook as mrkdwn; Slack interprets `<!channel>` (workspace-wide ping) or `<url|text>` (masked link).
- PRECONDITIONS (verified by config/BE trace 2026-06-10): notifications are OFF by default (`application.yml:172-173` `notifications.enabled: false`); this requires the operator to have enabled notifications AND configured a Slack receiver AND the alerted entity to be subscribed. Not a default-on surface.
- OBSERVABILITY: this is an **external-receiver runtime observable** - the `@channel` broadcast/fake link is only visible in a real Slack workspace. Static trace consistent (description -> markdownText -> Slack POST, no escape); **not driven** - `user_facing_verified: false`. Remaining check: enable notifications + a Slack (or capture) webhook, ingest a task run with `taskRunName='<!channel>'`, trigger the alert, observe the rendered Slack message.
- The web Alerts UI is NOT affected: it renders the same description as React-escaped plain text (`AlertItem.tsx:184-186`), so the token shows as inert text there (this is the same FE fact that falsifies PLT-014 Defect 2).

## Why it matters

The verbatim-mrkdwn render is a real footgun for any operator who wires Slack notifications: a collector that names a job/test with mrkdwn tokens (maliciously, or accidentally with a `<...>`-shaped name) will ping or mislead the whole workspace. The fix is a one-line sanitisation helper - cheap and low-regression.

Severity downgraded HIGH -> MEDIUM: the original HIGH rested on "fully remote, fully unauthenticated via the AlertManager webhook," which is falsified (URI-constrained). The surviving vector requires notifications enabled + Slack configured (operator opt-in) and injection through the ingestion path. Still worth fixing - mrkdwn escaping of untrusted text before Slack delivery is unambiguously correct.

## Suggested fix

`MrkdwnUtils` ALREADY EXISTS (`odd-platform-api/.../notification/processor/message/MrkdwnUtils.java` - currently `bold(...)` + `buildLink(...)`). **Add** an `escape(...)` method to it (do NOT create a new file, as the earlier revision proposed):

```java
// add to the existing MrkdwnUtils
public static String escape(final String text) {
    if (text == null) {
        return null;
    }
    return text.replace("&", "&amp;").replace("<", "&lt;").replace(">", "&gt;");
}
```

Then escape the untrusted description at the embedding site:

```java
// SlackMessageGenerator.buildDescriptionsFromChunks (:95-101)
- .map(AlertChunkPojo::getDescription)
+ .map(c -> MrkdwnUtils.escape(c.getDescription()))
```

Apply the same to any other field that originates from untrusted ingest if it is ever embedded via `markdownText` (today only the joined chunk description is). Note `buildLink`/`bold` wrap platform-controlled values (entity name/type, URL), not ingest text.

Add a unit test:

```java
@Test
void escapeNeutralizesBroadcastTokens() {
    assertThat(MrkdwnUtils.escape("<!channel> urgent")).isEqualTo("&lt;!channel&gt; urgent");
    assertThat(MrkdwnUtils.escape("<https://x|y>")).isEqualTo("&lt;https://x|y&gt;");
}
```
