## What

Changing an alert's status from the UI (Resolve an open alert, or Reopen a
resolved one) has two defects in the same flow:

1. On the **Data Entity -> Alerts** tab the status change is NOT reflected in
   the list after the action. A success toast appears, but the alert's status
   badge keeps showing the previous status (e.g. "Open") and the button keeps
   offering "Resolve". Only a full page refresh (or leaving and re-entering the
   tab, which re-fetches) shows the new status. The change IS persisted on the
   back end -- the bug is that the client view goes stale.
2. There is **no confirmation step** before the status flips. A single click on
   "Resolve" / "Reopen" immediately changes the alert's triage state, with no
   "Are you sure?" prompt, on both the global Alerts page and the per-entity
   Alerts tab.

## Where

All references are `odd-platform-ui` (front end), verified against `main`.

**Defect 1 -- stale status: a payload-key mismatch between the thunk and the reducer.**

- Thunk `updateAlertStatus` returns the entity id under the key `dataEntityId`:
  `src/redux/thunks/alerts.thunks.ts` (in `updateAlertStatus`, around L70-86):
  ```ts
  const alert = await alertApi.changeAlertStatus(params);
  return { alert: castDatesToTimestamp(alert), dataEntityId: params.entityId };
  ```
- The reducer reads the entity id under the key `entityId` (so it is always
  `undefined`): `src/redux/slices/alerts.slice.ts` (in `updateAlertStatus.fulfilled`,
  around L69-85):
  ```ts
  const { alert, entityId: dataEntityId } = payload; // reads payload.entityId -> undefined
  if (dataEntityId) {
    // per-entity branch -- NEVER taken, because dataEntityId is always undefined
    state.dataEntityAlerts[dataEntityId].items = ...
    return state;
  }
  // fall-through: updates the GLOBAL list instead
  state.alerts.items = state.alerts.items.map(el => el.id === alert.id ? alert : el);
  return state;
  ```
- The per-entity tab renders from `state.dataEntityAlerts[id].items`, which the
  reducer never updates: `src/redux/selectors/alert.selectors.ts` (around L58-62):
  ```ts
  export const getDataEntityAlerts = (dataEntityId: number) =>
    createSelector(getAlertsState,
      alertsState => alertsState.dataEntityAlerts[dataEntityId]?.items || emptyArr);
  ```
- The dispatch site that DOES pass an entity id:
  `src/components/DataEntityDetails/DataEntityAlerts/DataEntityAlertItem/DataEntityAlertItem.tsx`
  (`alertStatusHandler`, around L38-44):
  ```ts
  const params = { alertId, alertStatusFormData: { status }, entityId: dataEntityId };
  dispatch(updateAlertStatus(params));
  ```
- A success toast fires regardless of which slice was updated:
  `src/redux/thunks/alerts.thunks.ts` `setSuccessOptions`:
  `Alert successfully ${alertStatusFormData.status?.toLowerCase()}.`

  Net effect: on the per-entity tab the new alert is written to the GLOBAL
  `state.alerts.items` (which the tab does not render) instead of
  `state.dataEntityAlerts[id].items` (which it does) -- so the row stays stale
  until a re-fetch. The global Alerts page is unaffected because it dispatches
  WITHOUT an entity id, so the reducer's fall-through correctly updates the very
  list it renders.

**Defect 2 -- no confirmation dialog before the flip (both surfaces).**

- Global Alerts page:
  `src/components/Alerts/AlertsList/AlertItem/AlertItem.tsx` -- `handleResolve` ->
  `dispatchUpdateAlertStatus` (around L42-72) dispatch directly from the button
  `onClick` (around L160-167). No dialog.
- Per-entity tab:
  `src/components/DataEntityDetails/DataEntityAlerts/DataEntityAlertItem/DataEntityAlertItem.tsx`
  -- `alertStatusHandler` (around L38-44) wired to the button `onClick`
  (around L113-118). No dialog.

## User-facing impact

An operator triaging alerts on a data entity's **Alerts** tab clicks "Resolve"
(or "Reopen"). They see a green toast -- "Alert successfully resolved." -- but
the row's status badge still reads "Open" and the button still says "Resolve".
The operator cannot tell whether the action worked: the toast says yes, the row
says no. Common reactions are to click again (re-issuing the change) or to assume
the feature is broken. The true state only appears after a manual page refresh.

The global Alerts page does reflect the change immediately, which makes the
behaviour inconsistent between two places that look like they do the same thing.

Separately, on both surfaces a single accidental click flips an alert's triage
state with no confirmation -- there is no guard against mis-clicking "Resolve" on
an alert that is still active, or "Reopen" on one that was deliberately closed.

Note on verification: this is traced statically against `main` (the thunk,
reducer, selector, and dispatch-site files were read and the key mismatch
confirmed); it has not yet been reproduced on a running stack, so
`user_facing_verified` is `false`. The root cause is a deterministic logic error
(the `if (dataEntityId)` branch is unreachable), not a timing/heuristic guess.

## Why it matters

Alert triage is a core operator workflow on the platform. A status control whose
result is invisible until a page refresh -- while a success toast claims it
worked -- directly undermines trust in the alerting surface: the UI contradicts
itself on screen. The missing confirmation compounds it, since an accidental
status flip is silent and has no undo prompt. Severity is medium rather than
high because the back-end state is correct and the stale view self-heals on
refresh (no data loss, no security exposure) -- but the on-screen contradiction
is exactly the kind of "the docs/product lie" experience that erodes confidence.

## Suggested fix

1. **Stale status (defect 1):** align the payload key so the per-entity branch
   can run. Either have the thunk return `entityId: params.entityId` (to match
   the reducer's `const { alert, entityId } = payload`), or have the reducer read
   `const { alert, dataEntityId } = payload` (to match the thunk's emitted key).
   A one-line change either way; it restores the currently-dead
   `state.dataEntityAlerts[id].items` in-place update so the tab re-renders
   without a refresh. Add a reducer unit test asserting that, after
   `updateAlertStatus.fulfilled` with an entity id, the matching alert in
   `state.dataEntityAlerts[id].items` carries the new status.
2. **Confirmation (defect 2):** wrap the "Resolve" / "Reopen" trigger in the
   existing `ConfirmationDialog`
   (`src/components/shared/elements/ConfirmationDialog/ConfirmationDialog.tsx`),
   used by other state-changing actions in the app -- reuse it rather than adding
   a new dialog. Its `onConfirm: () => Promise<unknown>` returns the dispatch
   promise so the dialog shows loading/error inline.

Open to alternatives -- e.g. an optimistic update plus a tab re-fetch on success
would also fix defect 1, though the key-alignment fix is smaller and matches the
existing reducer design.
