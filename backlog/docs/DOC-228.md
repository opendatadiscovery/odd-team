## Description

The substrate batch-6 scan re-verified the entire ingestion-auth chain at primary source (5 ingestion controller handlers + IngestionDataEntitiesFilter + SecurityConstants WHITELIST + application.yml). It surfaces **two NEW dimensions** on top of DOC-168's foundation: a YAML-side caveat absence and the absence of an operator-facing 80-cell deployment matrix.

**Facet 1 — Property-name misdirection persists at the YAML surface (F-094a, HIGH).** The live docs HAVE been updated since substrate authoring — `/configuration-and-deployment/enable-security` now explicitly states "The `/ingestion/**` namespace is whitelisted in Spring Security (`SecurityConstants.WHITELIST_PATHS`), so it never traverses the UI authentication chain regardless of `auth.type`" and `/configuration-and-deployment/odd-platform` warns "`auth.ingestion.filter.enabled` only guards `/ingestion/entities` (POST) — it does not cover `/ingestion/alert/alertmanager`". This is the FIRST documented ontology-doc-mitigation in the mode-B catalogue. BUT — `application.yml:46-48` still declares the key with NO in-line comment naming the narrow scope. Operators auditing YAML files in isolation (a common pattern for security audits — offline, in a config-merge tool, in a CI-time review of Helm overrides) cannot reconstruct the narrow scope.

**Facet 2 — The 80-cell deployment matrix is not enumerated anywhere (F-094b, HIGH).** The live `/configuration-and-deployment/enable-security` page provides a 3-row endpoint table and describes 3 of the 4 `auth.type` values. The actual matrix is structurally determined by 5 controller handlers × 4 SecurityWebFilterChain variants × 2 `IngestionDataEntitiesFilter` ConditionalOnProperty values × 2 `S2SAuthFilter` ConditionalOnProperty values = **80 cells**. Operators auditing a deployment cannot answer "if I set `auth.type=OAUTH2` + `auth.s2s.enabled=true` + `auth.ingestion.filter.enabled=true`, which 5 endpoints are auth-required and which are open?" without reading source.
