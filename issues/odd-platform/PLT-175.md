## What

`GET /api/activity` (the platform-wide activity feed) applies the caller-supplied `size` parameter directly as the SQL `LIMIT` with no upper clamp at any layer. A caller can request `size=2147483647` and the platform issues a single query bounded only by Postgres/network buffers and the size of the `activity` table - an unbounded, expensive read available to any authenticated caller. The same parameter is also passed boxed (`Integer size`) into the jOOQ query builder; when it arrives `null`, jOOQ emits **no `LIMIT` clause at all** and the query returns the entire result set. There is no `@Min`/`@Max` on the controller parameter and no `minimum:`/`maximum:` in the OpenAPI `SizeParam`, so neither the framework nor the spec defends against an oversized or absent value.

## Where

OpenAPI declares `size` for this operation via the shared `SizeParam`, which carries no bounds:

`odd-platform-specification/openapi.yaml:3273` (operation `getActivity`)
```yaml
        - $ref: './components.yaml/#/components/parameters/SizeParam'
```

`odd-platform-specification/components.yaml:4222-4229`
```yaml
    SizeParam:
      name: size
      in: query
      description: Size
      required: true
      schema:
        type: integer
        format: int32
```
(`required: true` on the wire, but no `minimum:`/`maximum:`.)

Controller - `size` is a bare boxed `Integer`, no validation annotation:

`odd-platform-api/.../controller/ActivityController.java:24-40`
```java
    public Mono<ResponseEntity<Flux<Activity>>> getActivity(final OffsetDateTime beginDate,
                                                            final OffsetDateTime endDate,
                                                            final Integer size,
                                                            ...
        return Mono.just(
                activityService.getActivityList(beginDate, endDate, size, datasourceId, namespaceId, tagIds, ownerIds,
                    userIds, type, eventType, lasEventId, lastEventDateTime))
            .map(ResponseEntity::ok);
```

Repository - `size` is handed straight to `.limit(...)` with no clamp; a `null` size emits no `LIMIT` clause:

`odd-platform-api/.../repository/reactive/ReactiveActivityRepositoryImpl.java:85-88` (`findAllActivities`)
```java
        final var baseQuery = buildBaseQuery(datasourceId, namespaceId);
        final List<Condition> conditions = getCommonConditions(beginDate, endDate, datasourceId, namespaceId, tagIds,
            ownerIds, userIds, eventType);
        return findActivities(baseQuery, conditions, lastEventId, lastEventDateTime, size);
```
The caller-supplied `size` is threaded, unmodified, into the private `findActivities(..., size)` (`:281-285`), which applies it as the SQL `LIMIT`:

`odd-platform-api/.../repository/reactive/ReactiveActivityRepositoryImpl.java:292-294`
```java
        final var finalQuery = baseQuery.where(conditions)
            .orderBy(ACTIVITY.CREATED_AT.desc(), ACTIVITY.ID.desc())
            .limit(size);
```
`org.jooq.SelectLimitStep#limit(Integer)` with a `null` argument produces a query with **no** `LIMIT` - i.e. the whole table.

## User-facing impact

**Direct-API / DISABLED-mode class - NOT a UI surface (verified 2026-06-10, group G22).** The shipped Activity UI never triggers this: the fetch thunk hard-codes the page window to `activityListSize = 30` (`odd-platform-ui/src/redux/thunks/activity.thunks.ts:20,45`), so an ordinary browser session always sends a small, bounded `size`. The exposure is therefore to anyone who can call `GET /api/activity` directly - any authenticated caller, or any caller at all under the default `auth.type=DISABLED` posture (`application.yml`) where the endpoint is reachable without credentials. Two trigger paths, both code-settled:
- `size=2147483647` (or any large value) -> a single `LIMIT 2147483647` over the monotonically-growing `activity` table, fully materialised and serialised.
- the `size` query parameter omitted on a hand-built request -> `Integer size == null` -> `.limit(null)` emits **no** `LIMIT` clause (jOOQ semantics) -> whole-table read. (Note the contract marks `size` `required: true`, so a spec-conformant generated client cannot hit the null path; only a raw/malformed request can.)

Not driven against a live stack in this sweep; the asymmetry (unvalidated `Integer size` -> `.limit(size)` with no clamp at controller, service, or repo) is static-trace settled. `user_facing_verified` stays `false`: the load-bearing *cost* claim (a single cheap request -> expensive full-table work) is an unmeasured runtime assertion, not yet observed under load.

## Why it matters

`/api/activity` is reachable by any authenticated caller (and anonymously under `auth.type=DISABLED`). The activity table grows monotonically with every catalog mutation, so on a mature install it is one of the largest tables. A single `size=2147483647` request - or a malformed client that drops the `size` query parameter and reaches the `null` path - turns one HTTP call into a full-table scan plus an in-memory map-and-serialize of every row into an `Activity` array. The cost is loud (latency, memory, DB load) but trivially triggered, with no audit of who triggered it: a denial-of-service amplification primitive available to any logged-in user. Severity is medium: not data-loss, not a credential bypass, but a cheap-request -> expensive-work asymmetry on a public, always-present endpoint with no rate or size ceiling.

## Suggested fix

Clamp `size` to a sane maximum at the service layer (e.g. `Math.min(size == null ? DEFAULT_SIZE : size, MAX_SIZE)` with a documented default and ceiling), so the value reaching `.limit(...)` is always a bounded positive integer. Belt-and-braces: add `minimum: 1` / `maximum: <ceiling>` to the `SizeParam` schema (or a dedicated activity size param) in `components.yaml` so the contract advertises the bound and the generated controller can enforce it. Open to alternatives on where the clamp lives, but the service tier is the one layer common to both `getActivityList` and `getMyActivity`, so it is the safest single point.

## How discovered

Surfaced in the 2026-06-08 contradiction-harvest (`integration-tests/run-log/` / feature-reflection triage) while reflecting on feature **F-021** (activity feed). This is the **same class** as the already-drafted pagination-bound issues **PLT-134** (per-entity alert read - `GET /api/dataentities/{id}/alerts`, unbounded `size`, negative `OFFSET`) and **PLT-042** (lineage depth - controller `@Max` + UI clamp), but it is a **distinct endpoint and parameter**: neither of those touches `GET /api/activity`, and the activity path additionally has the `null`-size -> no-`LIMIT` whole-table behaviour because the parameter is boxed and unvalidated. It is filed separately so the fix lands on the activity service rather than being folded into an unrelated endpoint's PR.

**Verified 2026-06-10 (user-facing verification sweep, group G22) - HOLDS as a direct-API/DISABLED-mode class.** Re-read all citations: controller `size` is a bare boxed `Integer` with no validation annotation (`ActivityController.java:26`); the service forwards it unmodified (`ActivityServiceImpl.java:88,104,114`); the repo applies it as `.limit(size)` with no clamp (`ReactiveActivityRepositoryImpl.java:294`, threaded via `findActivities` `:281-285`); and neither the operation `SizeParam` ref (`openapi.yaml:3273`) nor the shared `SizeParam` definition (`components.yaml:4222-4229`, `required: true`, no `minimum:`/`maximum:`) carries a bound.
