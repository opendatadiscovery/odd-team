## Description

The live published [Lookup Tables](https://docs.opendatadiscovery.org/master-data-management/lookup-tables) page's **Supported field types** table tells operators the `TIME` field type maps to PostgreSQL `time` with the use note **"Time of day (no date component)"** (`lookup-tables.md:75`). The code does the opposite: `TIME` maps to a PostgreSQL **`timestamp`** column and accepts only full date+time instants.

This corrects a wrong claim on a live page. An operator who reads the table, picks `TIME` expecting a time-of-day column, and enters a bare `13:45:00` gets a `400 BadUserRequestException` on insert (and the generated column is a `timestamp`, not a `time`) — actively misleading documentation, which is our top priority class.

Canonical code truth:
- `LookupTableColumnTypes.java:44` — `TYPE_TIME(TIMESTAMP, "TIME", DataSetFieldType.TypeEnum.TIME, new LookupTimestampValidator())`. The jOOQ `DataType` is `SQLDataType.TIMESTAMP` (imported at `:25`), so the DDL column is `timestamp`, not `time`. (The `DataSetFieldType.TypeEnum.TIME` is the catalog-display field-type only — it does not change the underlying PostgreSQL column type.)
- `LookupTimestampValidator.java:9` imports `SQLDataType.TIMESTAMP`; `:14` builds the column as `TIMESTAMP.defaultValue(...)`; `:22-31` validates every value via `Timestamp.valueOf(value)`, which requires the JDBC `yyyy-[m]m-[d]d hh:mm:ss[.f...]` form and throws `BadUserRequestException` on any other input (e.g. a bare `hh:mm:ss`).
