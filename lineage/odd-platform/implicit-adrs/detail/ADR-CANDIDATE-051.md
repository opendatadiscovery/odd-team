- **ADR-CANDIDATE-051** (NEW 2026-05-12E): Resource-type↔context coupling is encoded at the `PolicyTypeDto.hasContext` enum field, NOT at controller-hierarchy or service-class layer — `PermissionServiceImpl` enforces `hasContext == true` for `/api/resource/{type}/{id}/permissions` and `hasContext == false` for the sibling `/api/permission/{type}` non-contextual endpoint, with both invariants guarded by a single `BadUserRequestException`. The enum-field-driven dispatch is the project's chosen idiom for "resource-type has a context object vs. global permission"
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar (`getResourcePermissions`) but the structural shape applies to every existing AND future resource type the platform may add (extensible by enum extension, not by class hierarchy)
  - **Surfaced by**:
    - `odd-platform__java__PermissionController__controller-method__getResourcePermissions.md:implicit_adrs.[2]` ("Resource-type ↔ context coupling encoded at the enum, not at the controller — `PolicyTypeDto` carries a `hasContext` boolean (`PolicyTypeDto.java:8-14`) and `PermissionServiceImpl` enforces the invariant `hasContext == true` for this endpoint (`PermissionServiceImpl.java:25-27`); the symmetric endpoint for non-contextual permissions enforces `hasContext == false` (`PermissionServiceImpl.java:35-37`). The decision is to surface the resource-type's contextual nature through an enum field rather than a class hierarchy or controller-level dispatch — both endpoints share one service and one enum, with the invariant guarded by `BadUserRequestException`." — intent_anchor: `if (!policyTypeDto.isHasContext()) { throw new BadUserRequestException('Resource type ' + resourceType + ' does not have context'); }` at PermissionServiceImpl.java:25-27)
  - **Decision statement**: ODD models the "this resource type has a context object" property as a `boolean hasContext` field on the `PolicyTypeDto` enum (`DATA_ENTITY(hasContext=true)`, `TERM(hasContext=true)`, `QUERY_EXAMPLE(hasContext=true)`, `MANAGEMENT(hasContext=false)`). Two endpoints share one `PermissionService`: `GET /api/resource/{type}/{id}/permissions` enforces `hasContext == true` (with `BadUserRequestException` on mismatch); `GET /api/permission/{type}` enforces `hasContext == false` (with the symmetric exception). The decision codifies "context vs. global is a property of the type, not a property of the path" — adding a new contextual resource type means (a) adding an enum member with `hasContext = true` and (b) authoring a new `ContextualPermissionExtractor` registered with the type. The contract endpoint shape stays the same; no controller change is required.
  - **Wisdom test**: PASS. The choice of enum-field-with-invariant over class-hierarchy (e.g. `ContextualPolicyType` vs `NonContextualPolicyType` subtypes) or controller-level dispatch (separate `/api/contextual-permissions` and `/api/non-contextual-permissions` routes) is a positive structural choice. The single shared service + the symmetric exception messages confirm it. Structural — every resource type lives in this enum; every permission discovery routes through this dispatch.
