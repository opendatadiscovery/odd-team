## Description

The OAuth2/OIDC logout handlers build the IdP end-session redirect with **no `state` and no `nonce` parameter**, contrary to the OpenID Connect RP-Initiated Logout 1.0 §5 recommendation that an RP SHOULD send a `state` value so it can verify the post-logout callback is the response to its own request. Both handlers construct the redirect URL with only `client_id` plus the post-logout return URI:

- `AzureLogoutSuccessHandler.java:38-44` — `UriComponentsBuilder.fromUri(logoutUri).queryParam("post_logout_redirect_uri", ...).queryParam("client_id", ...)`. No `state`, no `nonce`.
- `CognitoLogoutSuccessHandler.java:40-46` — `...queryParam("client_id", ...).queryParam("logout_uri", ...)`. No `state`, no `nonce`.

Without an unguessable `state` echoed back on the post-logout callback, a third-party page can force a victim's browser to hit the platform's logout endpoint (logout-CSRF) and the platform cannot detect that the logout was not user-initiated. On its own this is a nuisance (forced logout). It **compounds with PLT-075** — the same handlers derive `post_logout_redirect_uri` from the inbound `Host` / `X-Forwarded-Host` header with no allowlist — so a forced logout can be chained to land the victim on an attacker-controlled domain that the IdP's wildcard logout-URI allowlist still accepts.

The `oauth2-oidc.md` page documents the `logout-uri` property (AWS Cognito and Azure AD sections) but says nothing about the missing `state`/`nonce` or the logout-CSRF exposure. An operator reading the page has no way to know the end-session flow is unauthenticated against CSRF. This item adds the operator-facing caveat; the per-handler code fix (emit and verify a `state` value) is an upstream security enhancement that should fold into PLT-075's remediation rather than ship as a doc.
