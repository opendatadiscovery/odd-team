(b) an authenticated insider with read access to URL bars in shared screen-sharing contexts can hijack any user's session.   - **Proposed doc action**: **Two-part action**.
    1. **Doc-side primary**: extend `features/data-discovery/search.md` with a "Session handling" admonition: "**Search session UUIDs are bearer tokens**. When you save or share a search URL, you grant anyone with the URL full read AND update access to that session's filter state and query. The platform does NOT bind sessions to the creating user — UUIDs are the only identifier. Sessions persist indefinitely; the platform does not currently expire stale sessions. Operators concerned about session-state disclosure (e.g. when sharing URLs in bug reports or chat messages) should either treat search URLs as confidential or use the URL-less query-only form via direct API calls."
    2. **Code-side primary** (file `/log-issue odd-platform`): three ordered options. (a) **Minimum**: add a feature flag `search.sessions.bind-to-owner: true|false` (default `false`) that, when enabled, captures the principal's owner_id at session creation and rejects reads/updates from other principals. (b) **Medium**: add a TTL eviction job to Housekeeping (e.g. `search_facets.ttl-days = 30`) that prunes rows with `last_accessed_at < NOW() - INTERVAL '30 days'`. (c) **Full**: add the `owner_id` column to `search_facets`; enforce owner-scoped reads + writes at the repository layer; add a forward migration with a per-instance default owner mapping for existing rows.
