## Description

DOC-167 (pending) covers F-005's UI-side caveats (`d=1` hardcoded mask + click-through depth compounding). DOC-227 extends DOC-167 with the two architectural facets that emerge when you trace the 5-layer pipeline end-to-end — and that match the LSN-001 (attachment-storage default) failure shape exactly.

**Facet 1 — 4-layer absent-validation pattern (F-055a, CRITICAL — LSN-001-shape).** The lineage depth control has 5 layers; only ONE validates:
1. UI dropdown shows `[1..20]` (`HierarchyLineage/lineageLib/constants.ts:97-99`) — appears to be the safety boundary.
2. URL `?d=` parser via `query-string` library with `parseNumbers: true` (`lib/hooks/useQueryParams.ts:36`) — accepts ANY positive integer unclamped.
3. Controller carries `@Min(1)` (no `@Max`).
4. Service (`LineageServiceImpl.getLineage` line 87-91) hands the primitive `int` through.
5. Repository consumes the value directly in the recursive-CTE termination predicate.

The dropdown's apparent safety boundary is decorative — only the URL is the contract. An operator manually editing `?d=10000` (or pasting a URL from a colleague) triggers a 10000-depth recursive-CTE walk that Postgres may struggle to serve, with no defence at any layer. Same shape as LSN-001's attachment-storage default — the operator-visible knob is one thing; what the system actually accepts is another.

**Facet 2 — Click-through-from-manually-edited-URL bypasses the dropdown cap entirely (F-055b, HIGH).** Clicking a graph node propagates `d: node.depth || 1` to the new URL (`HierarchyLineage/.../Node.tsx:46-52` per F-005b's substrate primary-source). If the user previously set `?d=50` via URL edit (the parser allowed it), the new view opens with `?d=50` — bypassing the dropdown cap entirely. The dropdown's 20-entry array is never consulted on click-through propagation. Distinct from F-005b's "depth INCREASING per click" framing — F-055b is about depth PRESERVING beyond the dropdown's cap once the URL has been manually edited.
