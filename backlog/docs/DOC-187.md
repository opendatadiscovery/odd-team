## Description

Entity Description Editing is the canonical "operator types Markdown → platform persists verbatim → UI renders with rehype-raw and no rehype-sanitize" surface — the **anchor of a 6-surface stored-XSS family** that already has 5 sibling backlog/issue artefacts (PLT-018 Query Examples, PLT-019 Lookup Tables, the AlertManager generatorURL family on PLT-014, the Notifications Slack-mrkdwn family on PLT-016). The feature is **undocumented end-to-end** today: the Data Discovery section index does NOT list entity description as a covered topic (confirmed by WebFetch 2026-05-27); the Permissions page lists `DATA_ENTITY_DESCRIPTION_UPDATE` but never describes what authoring looks like, what format the description is in, or what gets rendered back to readers.

**Two load-bearing facets need a new canonical home (Cornerstone 5):**

**Facet 1 — End-to-end undocumented authoring surface (F-004a).** Operators discover the MDEditor by trial. The PUT body goes to `ReactiveDataEntityRepositoryImpl.setInternalDescription:430-438` — pure `DSL.update(...).set(INTERNAL_DESCRIPTION, newDescription).where(ID.eq(...)).returning()` with the sole pre-write transformation `newDescription = StringUtils.isEmpty(description) ? null : description` (line 431). No `Jsoup.clean`, no `Encode.html`, no length cap, no allowlist. The DB column is `data_entity.internal_description text` (no length cap). Read-back via `getDetails` returns the verbatim string; UI Preview renders via `Markdown.tsx:84-127` (rehype-raw, no rehype-sanitize). There is NO operator-facing description of "how do I write a description", "what Markdown is supported", "what is the `[[Namespace:Term]]` auto-link side-channel" (F-002b on DOC-177), or "what does the editing/audit trail look like".

**Facet 2 — Six-surface XSS class undocumented (F-004b).** The same Markdown-storage-verbatim + render-without-sanitize pattern spans six surfaces:
  1. **Entity description** (the canonical surface) — `ReactiveDataEntityRepositoryImpl.setInternalDescription:430-438` + render via `InternalDescriptionPreview` → `Markdown.tsx`.
  2. **Dataset-field description** (per-column) — `ReactiveDatasetFieldRepositoryImpl.updateDescription:73-80` + render via `DatasetFieldDescriptionPreview` → `Markdown.tsx`.
  3. **Term definition** — `TermServiceImpl.create/updateTerm:101-117, 119-145` + render via `TermDefinition.tsx:39-47` → `Markdown.tsx`.
  4. **Query Example definition + query** — `QueryExampleDetailsOverview.tsx:25` → `@uiw/react-md-editor` directly (NOT shared `Markdown.tsx`) — covered by PLT-018 + DOC-183.
  5. **Lookup Table row values + column names + table name + description** — `LookupCharValidator.getValue:14-17` — covered by PLT-019 + DOC-182.
  6. **Slack mrkdwn injection** — `SlackMessageGenerator.markdownText:77` renders `AlertChunkPojo.description` strings as Slack mrkdwn — covered by PLT-016 + DOC-180.

Surfaces 1-3 share `Markdown.tsx:113-124` as the **single SPA-tier fix anchor** — one config-line change (add `rehypePlugins: [rehypeSanitize]`) closes all three. The defensive partial-mitigation envelope (common script-tag execution closed by Chromium policy, attribute-vector execution closed by React filtering; SVG-onload / CSS-expression / `javascript:`-URL vectors remain unmeasured) is operator-load-bearing — security-conscious operators currently have no doc page to read about the platform's XSS-class posture.
