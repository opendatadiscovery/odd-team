## Description

The platform's `Feature` set (`Feature` enum + `/api/features/active` endpoint) is **boot-immutable AND chrome-invariant** — two related properties that diverge from operator expectations of feature-flag systems.

**Facet 1 — Chrome-invariant (F-034a, MEDIUM→HIGH).** `App.tsx:49` dispatches `fetchActiveFeatures()` on SPA mount; the resulting `Feature` set is stored in Redux. `ToolbarTabs.tsx:34-82` builds the 9-tab navigation row in a `useMemo` with NO `useAppSelector(getActiveFeatures)` read, NO `WithFeature` wrapping. Sub-page affordances DO use `WithFeature` (`Message.tsx:59`, `MainThreadMessage.tsx:36`, `DataEntityDetailsHeader.tsx:132`), but the tab itself remains visible. Disabling `datacollaboration.enabled=false` (the shipped default) does NOT hide the Data Modelling tab; users click it and land on Query Examples surface where the feature-gated affordances are wrapped in WithFeature and produce a non-functional sub-page. Operator's user-observable mental model: "the platform-feature gating is consistent across the UI". Reality: the chrome layer is invariant to the flag set.

**Facet 2 — Boot-immutable (F-034b, MEDIUM→HIGH).** `FeatureResolverImpl.java:14, 16-31` captures the `@Value`-injected booleans into a `private final Set<Feature>` ONCE in the constructor; subsequent runtime mutation (e.g., via `/actuator/refresh` if exposed) is NOT reflected. Endpoint name `getActiveFeatures` and the prose "active features" promise runtime-current view; reality is boot-snapshot. An operator toggling a feature in `application.yml` + actuator-refresh sees the platform's `/api/features/active` return the OLD boot-time set until process restart.

## Acceptance Criteria

- [ ] `Features.md` gains a short "## Platform-feature flags — chrome-invariance and boot-immutability" sub-section (positioned near the existing data-collaboration / data-modelling teaser, or in a generic "Active platform features" container) covering:
  - **Chrome-invariance**: top-level navigation tabs (Data Modelling, etc.) are visible regardless of the corresponding feature-flag setting. Feature-gated functionality WITHIN those tabs (Message UI affordances on entity details; sub-page actions) DOES check the flag set, but the tab IS visible. Operators disabling a platform-feature should expect the tab to still appear, but its content to be empty / non-actionable.
  - **Boot-immutability**: the active feature set is captured at JVM boot. Runtime config changes (e.g., via `actuator/refresh`) are NOT reflected; the platform must be restarted for feature-flag changes to take effect.
  - **Operator recommendation**: when toggling platform features for an environment, restart the JVM process; do not rely on actuator-refresh.
  - Cross-link to the `datacollaboration.enabled` config key on odd-platform.md (and any other feature-flag config keys: `genai.enabled`, `multilingual-ui.enabled`, etc.).
- [ ] `configuration-and-deployment/odd-platform.md` gains a one-line caveat under each platform-feature config key (`datacollaboration.*` block, `genai.*` block, etc.) — "Feature toggling: this value is captured at JVM boot. A restart is required for changes to take effect. Top-level UI navigation tabs remain visible regardless of the setting; sub-page affordances honour the flag."
