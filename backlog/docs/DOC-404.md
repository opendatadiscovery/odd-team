## Description

`DELETE /api/owners/{id}` does not distinguish "deleted an owner" from "the owner id was never there". The service method is idempotent at the data layer and never asserts existence, so deleting an already-gone or never-existed owner id returns the same success the client gets for a real delete.

`OwnerServiceImpl.delete(long id)` (`OwnerServiceImpl.java:89-100`) builds the reactive chain:

1. `Mono.zip(...)` of three attachment checks (term-ownership, ownership, user-owner-mapping) — `OwnerServiceImpl.java:90-91`.
2. `.filter(exists -> !exists).switchIfEmpty(Mono.error(new CascadeDeleteException("Owner cannot be deleted: there are still resources attached")))` — `OwnerServiceImpl.java:94-96`. This only errors when the owner DOES exist and has attached resources.
3. `.then(ownerToRoleRepository.deleteOwnerRelationsExcept(id, List.of()))` then `.then(ownerRepository.delete(id))` — `OwnerServiceImpl.java:97-98`. `ownerRepository.delete(id)` is a soft-delete UPDATE that affects zero rows when the id does not exist, and the chain still completes with `.then()` (Void) — i.e. success.

There is **no** `switchIfEmpty(Mono.error(new NotFoundException("Owner", id)))` on the delete path. Contrast the read path in the same class — `getOwnerDtoById` at `OwnerServiceImpl.java:102-107` DOES carry `.switchIfEmpty(Mono.error(new NotFoundException("Owner", ownerId)))`. The delete verb deliberately (or by omission) does not.

**How it misleads an operator.** A client calling `DELETE /api/owners/{id}` and treating the success response as proof the owner existed and was removed will be wrong for any stale or typo'd id — the API confirms a deletion that never happened. Scripts that reconcile owner inventory ("delete owner 42, confirm gone") get a green response whether or not 42 was ever an owner. This is a contract-clarity gap, not a data bug — the data layer is correctly idempotent.

This is distinct from PLT-087 (the upstream issue family on owner-side mutation behaviour); this item documents the existing live behaviour for operators rather than proposing a code change.
