## Description

The `relationships` table schema admits more than one row per `data_entity_id`, but the detail read collapses to a single value with jOOQ `.mono()` — an unobserved branch.

`V0_0_87__create_relation_tables.sql:1-10` creates `relationships` with `id bigserial PRIMARY KEY`, a nullable `data_entity_id bigint`, and only a foreign-key constraint (`relationship_fk_data_entity` → `data_entity(id)`). There is **no UNIQUE constraint on `data_entity_id`** (and no unique index). So one `data_entity` can legitimately back multiple `relationships` rows.

`ReactiveRelationshipsRepositoryImpl.java:197` reads `return jooqReactiveOperations.mono(query)...` where the query is filtered `.where(relationshipsDataEntity.field(DATA_ENTITY.ID).eq(relationshipId))` (line 194) and `.groupBy(groupByFields)` (line 195). With `.mono()`, a multi-row result either raises an "exactly one / too many results" style error or silently returns the first row — the behaviour is currently unverified. Whichever it is, it is a contract the detail page depends on.

**Typed gate: characterization-pin (LSN-029).** This is a probe-gated pin: run the probe to observe the ACTUAL behaviour (error vs. silent row-1), then write a test asserting that current behaviour so any future change (adding a UNIQUE constraint, switching `.mono()` to `.flux()`/aggregation, or a deliberate "pick latest" rule) trips it RED. Do NOT assert a guessed behaviour — observe first.
