## What

When the Dictionary tab's term-search session create or restore fails - including an expired auth session - the page renders an **empty term list with no inline error and no retry affordance**, and the failure is not recorded in the slice. The original issue called this a "silent frozen empty page". That overstates it: **a global error toast DOES fire** on every rejection. Corrected on user-facing verification 2026-06-10.

What is actually true (verified):

- **A toast fires.** Both `createTermSearch` and `getTermsSearch` are built with `handleResponseAsyncThunk` (`termSearch.thunks.ts:21-24, 35-42`) and neither passes `switchOffErrorMessage`. So on any rejection the wrapper's catch calls `showServerErrorToast(err)` (`handleResponseThunk.ts:34-39`), which renders a visible error toast whenever the response has a status (`errorHandling.tsx:48-68`). An auth-expiry (401) produces a status, so the user gets a "401 / An error occurred" toast - they are **not** left with zero signal.

- **But the page itself shows nothing and offers no retry.** `TermSearch.tsx` has no inline error state: the create dispatch (`:37-42`) chains `.unwrap().then(navigate)` with **no `.catch`** (so the `navigate` simply never happens), and the restore dispatch (`:46-47`) is fire-and-forget with no `.then`/`.catch`. The slice has **no `.rejected` reducer** for any term-search thunk - `extraReducers` (`termSearch.slice.ts:193-228`) registers only `.fulfilled` cases. So after the transient toast auto-dismisses, the user is left on an empty Dictionary with no persistent error, no explanation, and no in-page retry; reloading repeats the same toast-then-empty cycle.

So the real defect is a **degraded error UX** (transient toast only; no inline error, no retry, no `.rejected` state), not a silent failure. That is a smaller defect than the original framing.

## Where

- `TermSearch.tsx:37-42` - create-session dispatch: `.unwrap().then(navigate)`, no `.catch` (on failure the navigate is skipped; nothing else happens).
- `TermSearch.tsx:46-47` - restore-session dispatch: `dispatch(getTermsSearch(...))` fire-and-forget, no `.then`/`.catch`.
- `termSearch.slice.ts:193-228` - `extraReducers`: only `.fulfilled` cases for `createTermSearch` / `updateTermSearch` / `getTermsSearch` / `fetchTermsSearchResults` / `getTermsSearchFacetOptions` / `fetchTermSearchSuggestions`; **no `.rejected`** for any.
- `handleResponseThunk.ts:34-39` - the global catch that fires `showServerErrorToast` unless `switchOffErrorMessage` is set (it is not, here).
- `errorHandling.tsx:48-68` - `showServerErrorToast` -> visible error toast when `response.status` is set.

(All line numbers verified against current HEAD `3049b9af`; the original `@ ede5d277` pin is stale but the code is unchanged.)

## User-facing impact

A user whose session create/restore fails on the Dictionary tab (transient backend error or expired auth) sees a **transient error toast** and then an **empty Dictionary with no inline error and no retry**. They are not left with zero signal (the original "no error at all" claim is false), but the in-page state is unhelpful: once the toast dismisses there is no persistent indication of what went wrong or how to recover, and there is no special handling that routes an expired session to re-authentication. Severity **medium -> low**: the global toast already prevents the true silent-failure harm; what remains is missing inline error/retry polish on one tab.

## Suggested fix

Add a `.rejected` reducer for the term-search thunks in `termSearch.slice.ts` that records an error/empty state, and render an inline error + retry in `TermSearch.tsx` (and/or a `.catch` on the create dispatch so a failed bootstrap is handled in-component rather than only via the global toast). Optionally route an auth-expiry (401) to the login flow. This is a UX-hardening item, not a silent-data defect; it can fold into the same "Terms subsystem error-handling hardening" epic as PLT-059 Defect 4 (`TermsForm.tsx` - same missing in-component handling class, different component).

## How discovered

Surfaced by the Layer-4b feature-reflection over feature flow F-024 (Term Search & Browse) on 2026-06-01 - hypothesis H-012. **Corrected 2026-06-10 during the user-facing verification sweep**: the reflection asserted a "silent frozen empty page" from the missing `.catch`/`.rejected` alone, without tracing the thunk wrapper. `handleResponseAsyncThunk` toasts every un-suppressed rejection globally, so the failure is visible - the actual gap is the missing inline error/retry and `.rejected` state, which is a lesser severity. Same corpus failure mode as the PLT-176 lesson (a "silent failure" claim that did not check the FE error path: redux thunks toast errors globally).
