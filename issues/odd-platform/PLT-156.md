## What

The Activity feed resolves the actor ("who did this") of each activity row by joining the activity's `created_by` username to the `user_owner_mapping` table and then to the `owner` it points at. That join carries an extra predicate, `user_owner_mapping.deleted_at IS NULL`. As a consequence, the moment a user→owner association is **soft-deleted** (its `deleted_at` is set), every historical activity row that user ever produced loses its resolved owner: the left join finds no surviving mapping, the owner comes back null, and the actor disappears from the displayed history. Worse, if that username is later **reassigned** to a different owner (a new, non-deleted mapping), all of the original actor's past activity is now attributed to whoever currently holds the mapping — the audit trail is silently rewritten to name the wrong person.

## Where

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/repository/reactive/ReactiveActivityRepositoryImpl.java:220-222`

```java
.leftJoin(USER_OWNER_MAPPING)
.on(USER_OWNER_MAPPING.OIDC_USERNAME.eq(ACTIVITY.CREATED_BY)
    .and(USER_OWNER_MAPPING.DELETED_AT.isNull()))
.leftJoin(OWNER).on(OWNER.ID.eq(USER_OWNER_MAPPING.OWNER_ID));
```

The activity is keyed only by `created_by` (the username string) at write time; the human-readable actor is reconstructed at read time exclusively through this mapping join. Because the join is gated on `DELETED_AT IS NULL`, the link from a historical activity to the person who performed it is only as durable as the current mapping row. The same gated join also appears on the dependent-activities count path:

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/repository/reactive/ReactiveActivityRepositoryImpl.java:198-200`

```java
.leftJoin(USER_OWNER_MAPPING)
.on(USER_OWNER_MAPPING.OIDC_USERNAME.eq(ACTIVITY.CREATED_BY)
    .and(USER_OWNER_MAPPING.DELETED_AT.isNull()));
```

## Why it matters

The Activity feed is the platform's audit/attribution surface — it is where an operator goes to answer "who changed this dataset's description / tags / ownership, and when". The defect makes that attribution **non-durable and retroactively mutable**:

- **Soft-deleting a mapping orphans past activity (silent).** Removing a user's owner association — a routine admin action — strips the actor from all of that user's prior activity rows. The events still exist but read as authorless. No error, no warning.
- **Reassigning a username rewrites history (silent + misleading).** If the same `oidc_username` is later mapped to a different owner, every past action by the original person is now displayed as performed by the new owner. This is the dangerous case: the audit trail does not go blank, it lies — it confidently names the wrong actor.
- **Who is affected:** any deployment where owner mappings are ever edited, revoked, or re-pointed (staff turnover, role changes, owner cleanup). The longer the platform runs, the more historical attribution is exposed to silent corruption.

Severity **high**: this is integrity loss on an audit surface, and the reassignment case actively misattributes actions rather than merely dropping them.

## Suggested fix

Make actor attribution durable against soft-delete and reassignment. Options (open to alternatives):

1. **Drop the `DELETED_AT IS NULL` predicate from the actor-resolution join** so historical activity continues to resolve the owner that the mapping recorded, then handle the "this owner is deleted" presentation concern at the display layer (e.g. render the historical name, optionally annotated as inactive). This preserves history without surfacing soft-deleted owners as if they were active.
2. **Snapshot the actor at write time** — denormalise the resolved owner/display identity onto the activity row when the event is created, so reads never depend on the mutable mapping. This is the most robust fix for an audit surface but is a larger change.

A point fix that merely removes the predicate must be paired with care so soft-deleted owners are not re-exposed elsewhere as active; the write-time snapshot avoids that coupling entirely.

This is **distinct from `PLT-065`** (cross-auth-mode owner-identity bleed, a different root cause in how identities are matched across auth modes) and **distinct from `PLT-031`**: this issue is specifically about the `DELETED_AT IS NULL` predicate on the activity actor-resolution join causing historical attribution to vanish or be rewritten when a mapping is soft-deleted or reassigned.
