# GAPS — Concrete data-flow gaps between the scanner pipeline and the ontology pipeline today

A **gap**, for this artefact, is a place where one pipeline holds information the other needs to do its job correctly — but no channel exists today that passes the information across. Each row of the inventory below was observed by reading the actual files of both pipelines on `main` at 2026-05-27.

## 2. Two-failure-mode mapping

**Failure mode 1 — Scanner alone is too coarse** (extracts from entry points; misses cross-cutting). The gaps that contribute:

- **G-05** — Scanner uses 1 axis (UI routes); ontology has 6. The scanner literally cannot see ui_shell / config_prefixes without the manifest.
- **G-08** — Scanner can't ask "is this feature already classified as `ui-incomplete`?"; surfaces every shell as a "feature."
- **G-09** — Cross-cutting findings (Lombok-toString leak, default-open posture, partial-home POJOs) live in sidecar META layers the scanner can't read.
- **G-10 / G-11** — Cross-cutting investigation context (shoebox, SME notes) is invisible; scanner misses the "we know this is a thing, just unverified" half-state.
- **G-13** — Scanner can't ask "is the code for this UI already sidecar-covered?"; runs a full doc-side audit even when the code-side is solved.

**Failure mode 2 — Ontology alone is too bottom-up** (isolated implementation descriptions; can't reliably name features). The gaps that contribute:

- **G-01** — Ontology builds feature-flows for entry points without knowing which are already named in the scanner's enumeration manifest (which carries human-curated feature names).
- **G-04** — Ontology re-surfaces findings against code-paths the maintainer has already addressed via backlog items.
- **G-07** — Sidecars can't tell when a doc URL has just been rewritten and the `docs_link_semantic` block needs re-evaluation against the *new* text vs the old.
- **G-14** — feature-reflector produces "user-facing hypothesis" verdicts identical in shape to scanner findings, but with no merge — the bottom-up view never meets the requirements-registry view.
- **G-19** — Ontology has commit-delta tooling; scanner has the "what does the user-facing doc say should exist" axis. Each is half of "did this code change drift the docs?"

## 3. What's NOT a gap (looks like one, is by design)

- **Scanner doesn't do AST analysis.** The scanner intentionally stays at the entry-point / config-key / URL level and delegates code-walk to the ontology (per `adrs/drafts/code-lineage-substrate.md` "MVP acceptance"). This is the layered architecture, not a gap.
- **Sidecars don't track backlog items by ID.** Sidecars are about code; backlog is about work commitments. Coupling them at the sidecar level would tightly bind two independently-evolving stores. The right join is at the *retrieval* layer (a query that joins sidecar.node_id × backlog.affected_files), not at the storage layer.
- **`/triage` doesn't auto-create backlog items from reducer outputs.** The maintainer-in-the-loop on triage is the intentional gate — auto-promotion of 312 TEST-GAP rows would flood the backlog. The gap (G-18) is that today *zero* are promoted, not that auto-promotion should be the answer.
- **`/concepts` doesn't read `documentation/docs/main-concepts.md` autonomously beyond anchoring.** Concept-merger anchors to it as canonical vocabulary but doesn't try to rewrite it. This is correct — the doc page is the source of truth, not an output.
- **Shoebox isn't fed to the scanner.** Shoebox is explicitly defined (`lineage/odd-platform/shoebox/README.md`) as evidence-the-maintainer-is-still-triangulating; routing unfinished hypotheses into a deterministic scanner enumeration would force premature finalisation (the LSN-023 failure mode). G-10 above is about *awareness*, not *consumption*.

## 4. Reverse-direction gaps — places where the ontology could feed the scanner (clue-source mode)

These are the same data flows as the inventory above, viewed from the ontology side as the *upstream* producer instead of the *downstream* consumer:

| Flow | Ontology produces | Scanner needs | What it would replace |
|---|---|---|---|
| R-01 (mirrors G-01 + G-13) | `feature-flows/detail/F-NNN.yaml` — "this feature exists, this is the code chain, this is the entry point" | The scanner's "axis enumeration" step | Re-greping `routes/` for every doc-coverage scan. Scanner asks ontology: "give me every entry point and tell me which already have feature-flows; I'll audit doc-side only for those." |
| R-02 (mirrors G-02 + G-09 + G-15) | `doc-gaps.md` — "code at file:line claims X; doc at URL claims Y; verify" | The scanner's drift-detection step | The scanner's independent `docs-accuracy-*` scans. Scanner dedupes against DOC-GAP-NNN; only adds *new* drift, never re-files. |
| R-03 (mirrors G-12) | `concepts.yaml` — canonical vocabulary + aliases + synonym drift | Gate 2 (synonyms/aliases) authority | Manual term checks. Scanner reads canonical and flags doc pages using non-canonical forms. |
| R-04 (mirrors G-10) | `shoebox/detail/SHB-NNN.md` — feature hypotheses the maintainer hasn't graduated | Probe targets / "is this in the docs?" check | Silent miss. Scanner asks ontology: "give me every open SHB; I'll check whether any doc page mentions the concept" — keeps the maintainer's WIP visible to the audit. |
| R-05 (cross-cutting) | The graph layer (`graph/` directory + `nodes.jsonl` + `edges.jsonl` + `/retrieve` skill — 929 nodes / 479 edges; semantic search via the labeled-property-graph projection) | A pre-flight "is there ANY ontology coverage of {topic}?" lookup | Breadth-first enumeration. Before the scanner enumerates UI routes for a doc-coverage scan, it `/retrieve`s "anything tagged ui-shell with no doc URL" and gets a focused list. |
| R-06 (mirrors G-17 + G-18) | `refactoring-scopes.md` + `test-map.yaml` | Candidate feeds for `/log-issue` and (future) tests-pillar `/triage` | 211 + 312 candidates rotting in YAML. Scanner-side `/triage` learns to consume reducer outputs as a first-class finding source, not just `findings/`. |
| R-07 (mirrors G-14) | `feature-reflections/detail/F-NNN.yaml` — top-down intent-vs-implementation verdicts | The scanner's `docs-accuracy-feature-behavior` finding shape | Independent feature-behaviour scans. Scanner reads contradicted/partial hypotheses and files only the *new* drift it can see. |
| R-08 (mirrors G-19) | `manifest.yaml`'s `last_scan_commit` + reducer `processed_node_ids` tracking | "Which scanners should re-run after the platform repo moved?" | Manual git-log inspection. Scanner asks ontology for the delta; only re-runs scanners whose axis nodes changed. |

The reverse direction is structurally the more important one: the scanner is a closed-form question generator (does the docs claim what the code does?) and the ontology has spent ~50 sidecars × 6 reducers building the most precise answer key the project has ever had to that question. Today the answer key sits next to the question paper and they never touch.

## 5. Bottom line

Twenty gaps, fifteen one-directional (scanner → blind) and five reverse (ontology → unconsumed). The two pipelines were built on different timelines (scanner: 2026-04; ontology: 2026-05) and neither was designed to ingest the other. The fusion ADR needs to pick a small number of high-leverage joins — at minimum **G-03 / G-17 / G-18** (the three "ontology produces N candidates, scanner-side triage sees zero" flows), **G-01 / R-01** (the enumeration-axis join), and **G-04** (backlog awareness in reducers) — and accept that the rest are addressed by the same shared retrieval layer or remain by-design unfused.
