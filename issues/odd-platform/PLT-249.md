## What

ODD Platform gives a user no way to pin the assets they care about. The only personalised surface on the
main page is the "Recommended" block, and it renders only for users who have completed internal **Owner**
association -- and not at all when `auth.type=DISABLED`. There is a global "Popular" list (`view_count DESC`,
shared by everyone) but nothing personal.

Add **Favorites**: a user clicks a star on any viewable asset; the star turns gold; the starred set is shown
as a 5-item panel on the main page (with a "View all" link) and as a new filterable top-level **Favorites**
tab. Favorites are **per user** -- keyed on the logged-in identity `(oidc_username, provider)`, NOT the
internal Owner -- so every user gets them, including users with no Owner association. When `auth.type=DISABLED`
(no authenticated principal at all), Favorites fall back to a single shared instance-wide bucket.

This is the first of two related navigation features for release 1.0.0 (the second is **Recently Viewed**).
**This issue ships the shared foundation both features reuse** (identity resolution, the polymorphic asset
model, the faceted list endpoint, the main-page panel slot, the top-level tab + facet sidebar, and the new
"Asset type" facet). Recently Viewed depends on this issue.

## User-facing impact

- A user opens any asset (or sees it in a list / search result) and clicks the star; it fills gold and the
  asset is now in Favorites. Clicking again removes it (star returns to outline).
- On the main page the user sees a "Favorites" panel with their 5 most-recently-starred assets and a "View all"
  link to the Favorites tab.
- On the Favorites tab the user filters by Namespace, Datasource, Tag, Owner and **Asset type** (multi-select,
  default All), ordered newest-favorited first, paginated.
- A user with no Owner association (today shown no personal surface) now gets Favorites. Under DISABLED auth the
  panel/tab are labelled non-possessively ("Favorites") and back a single shared bucket.

`user_facing_verified: false` -- this is a not-yet-built feature; the behaviour above is the intended design,
to be driven against the running system during implementation/review.

## Why it matters

Pinning frequently-used assets is table-stakes navigation in a data catalog, and ODD has no equivalent. The
gap is sharpest for the large audience of users who never complete Owner association: today they get zero
personalisation on the landing page. Favorites is also the first **purely personal, ownership-free,
navigation-only** surface in ODD -- it does not overlap Ownership (no Owner needed, implies no stewardship),
Alerts/subscriptions (no notifications -- pull, not push), Tags (private, not a shared governed taxonomy),
Data Entity Groups (creates no catalog object or lineage), or Popular (personal, not a global view-count list).

## Suggested fix

Open to refinement; this is a researched design (PRD-0001), reviewed for security and performance.

### Shared foundation (this issue owns it; Recently Viewed reuses it)

1. **Identity resolver.** One reusable helper resolving the current user to `(oidc_username, provider)` from the
   security context, with `switchIfEmpty` to a reserved sentinel `('__shared__','DISABLED')` for DISABLED auth.
   Always the full tuple (username alone collides across providers -- the V0_0_92 lesson). Identity comes from
   the security context only, never a request parameter, so no user can read/write another user's bucket.
2. **Polymorphic asset reference.** An asset is `(asset_kind, asset_id)` with
   `asset_kind in {DATA_ENTITY, TERM, QUERY_EXAMPLE, LOOKUP_TABLE}`. The four kinds use independent bigserial
   sequences, so ids collide across kinds -- the pair is mandatory, never `asset_id` alone. (Design-time check:
   confirm whether a Lookup Table is favourited by its reference-data id or its `data_entity` projection id --
   read `ReferenceDataController` + `V0_0_86`; if it is only ever a `DATA_ENTITY` projection, fold the kind in.)
3. **Faceted list endpoint** mirroring `getAlertsList`:
   `GET /api/favorites/list?asset_types=&namespace_ids=&datasource_ids=&tag_ids=&owner_ids=&page=&size=`
   (all optional, multi-select; `size` capped server-side ~100). Ordered `favorited_at DESC`. The main-page
   panel calls the same endpoint with `size=5`. Facets that a kind does not carry (e.g. query examples have no
   datasource/namespace) exclude that kind when set; the Asset-type facet is the primary cross-kind filter.
4. **Visibility by reuse, no denormalisation.** Do NOT store the asset title/metadata on the favorite row.
   Resolve titles live by semi-joining `(asset_kind, asset_id)` back onto each kind's existing list/detail query,
   so the canonical lifecycle-visibility predicate is inherited and a later-deleted asset simply drops out.
5. **Main-page panel + top-nav tab.** A reusable panel (title, star icon, up to 5 rows, "View all", slim
   empty-state) inserted into `Overview.tsx` above the Owner block and outside its gating. A new `AppMenuItem`
   + route + tab page reusing the Search/Alerts filter+list layout, with the existing
   `components/Search/Filters/*` (Datasource/Namespace/Owner/Tag) plus a new multi-select **Asset type** facet.
6. **"Asset type" facet + vocabulary.** ODD has no published "Asset" term and already ships a data-entity-only
   "Type" facet, so "Asset" is a deliberate new umbrella noun for the union; present the facet grouped (Data
   Entities [refine by entity class], Glossary Terms, Query Examples, Lookup Tables), default All, and document
   "Asset" in the user docs.

### Favorites-specific

- **Star = idempotent set-state, not a flip** (a read-then-flip races on double-click):
  `PUT /api/favorites/{asset_kind}/{asset_id}` (ensure-present) / `DELETE /api/favorites/{asset_kind}/{asset_id}`
  (ensure-absent). Plus a batch `POST /api/favorites/status` (body: asset refs) returning the favourited subset,
  so any list/search view can render stars without per-DTO changes.
- **Data model** (migration `V0_0_94`, UTC timestamps, no FK to asset tables):

  ```
  favorite(id bigserial pk, oidc_username varchar(512), provider varchar(255),
           asset_kind varchar(64), asset_id bigint,
           created_at timestamp NOT NULL default (now() at time zone 'UTC'),
           deleted_at timestamp default null)
  unique index on (oidc_username, provider, asset_kind, asset_id)            -- set-state UPSERT target
  index on (oidc_username, provider, created_at DESC) where deleted_at is null  -- list/panel ordering
  ```

  Un-star = `UPDATE ... SET deleted_at = now()`; re-star = `... ON CONFLICT DO UPDATE SET deleted_at = NULL,
  created_at = now()`. Read filters `deleted_at IS NULL`. No `CREATE INDEX CONCURRENTLY` (Flyway runs in a
  transaction; the table is new/empty). No FK to the four asset tables (overlapping id-spaces, heterogeneous
  delete) -- orphans handled by filter-on-read plus a periodic orphan sweep in the existing housekeeping job
  (`housekeeping/HousekeepingJobManager.java`). Favorites have no TTL (curated).

- **Read-path performance.** Order/paginate on the indexed `favorited_at`, then semi-join the page of
  `(asset_kind, asset_id)` onto each kind's existing list query (`WHERE id IN (...)`) -- keeps `LIMIT`
  index-driven and avoids a 4-way polymorphic UNION that cannot use an index for `ORDER BY ts DESC LIMIT n`.

- **Security.** Authenticated-only; identity from context only. NO new RBAC policy type (consistent with the
  existing model -- favourites are personal, not a governed resource). The DISABLED shared bucket exposes no
  data the already-anonymous catalog does not; label it non-possessively.

### Cross-cutting (do not silently defer)

OpenAPI (`openapi.yaml` + `components.yaml`: `AssetKind` enum, polymorphic asset ref, list/status schemas;
cap `SizeParam`) -> regenerate BOTH Java and TS clients; backend controller/service/repository(+Impl)/mappers +
JOOQ regen after the migration; frontend Redux slices/thunks/selectors, a shared `<FavoriteStar>` (reuse
`StarIcon`; filled-vs-outline + `aria-pressed`, NOT colour-alone), the panel, the tab, the facet sidebar, the
route, the nav entry; i18n strings in all six locales (en/es/fr/ua/hy/ch); user docs (Features + the "Asset"
term). No activity-log entry (favouriting is personal, not an audited entity change).
