# SHB-114 — Read-collaborative posture: every authenticated user enumerates the catalog

**Category**: open
**Severity**: MEDIUM

## Hypothesis

The platform's authorization model is **READ-COLLABORATIVE by deliberate design** — there is NO per-entity read gate on data-entities, policies, roles, owners, terms, query-examples, lookup-tables, alerts, or any other catalog object. Every authenticated user can enumerate every row, see every detail, and read every metadata field. The Policies/Permissions/Roles framework covers MUTATIONS (POST/PUT/PATCH/DELETE) only; GETs fall through to `pathMatchers("/**").authenticated()` at `AuthorizationCustomizer.java:29-30`. The decision is deliberate, consistent across controllers, codified in `SecurityConstants.SECURITY_RULES` (~100+ rules, overwhelmingly POST/PUT/PATCH/DELETE-shaped), AND nowhere documented as the platform's explicit doctrine. The feature is **"Read-collaborative doctrine — every authenticated user can enumerate the catalog; no per-row read scoping"** — an undocumented design choice with material confidentiality implications for operators running ODD across mixed-trust user populations.

## Evidence

- `odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/auth/AuthorizationCustomizer.java:29-30` — the catch-all `spec.pathMatchers("/**").authenticated()` — applies to every endpoint not matched by an earlier SECURITY_RULE. Read endpoints (GETs) typically have no rule entry; they fall through.
- `odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/auth/util/SecurityConstants.java:98-355` — the SECURITY_RULES table. Inspection of the pattern: rules are overwhelmingly `HttpMethod.POST` / `PUT` / `PATCH` / `DELETE`-shaped. GET endpoints rarely have entries. The Policies / Roles / Owners / Permissions read surfaces, the entire data-entity catalog, lookup-tables, terms, query-examples — all GETs uncovered.
- `odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/controller/PolicyController.java:27-32` (`getPolicyDetails`) + `:34-41` (`getPolicyList`) + `:59-63` (`getPolicySchema`) — three read endpoints, NO `@PreAuthorize`, NO `SECURITY_RULES` entry. Authenticated callers see every policy by id including the full JSON statement document (DATA_ENTITY_INTERNAL_NAME_UPDATE permission grants, etc.).
- `odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/controller/PermissionController.java:19-25` — per the PermissionController sidecar's `implicit_adrs[1]`: "Read-side endpoint is intentionally NOT in SECURITY_RULES — the read-collaborative posture. Any authenticated user can query their own permissions on any resource because the response reveals only what the policy graph would already grant them." Anchored at the controller-class implicit ADR.
- `odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/controller/RoleController.java:27-34` (`getRolesList`) — no SECURITY_RULES entry. Any authenticated user sees every role + every policy binding. The service-tier principal-aware fork (`RoleServiceImpl.java:40-47`) decides whether they see the FULL catalog (admin) or only their attached roles (non-admin) — a CONTENT FORK, not a permission gate; the endpoint is reachable to all authenticated callers.
- Live `/configuration-and-deployment/enable-security/authorization` page WebFetched 2026-05-25 — describes Policies/Permissions/Roles/Owners but does NOT name the read-collaborative posture, does NOT say "every authenticated user sees every entity", does NOT enumerate which endpoints are gated by which Permission. Operators reading the docs see the Policies/Permissions/Roles framework and reasonably assume it applies universally.
- F-006 (RBAC policy lifecycle), F-008 (Batch Ingestion — read-side leakage facet), F-017 (Search Filter Facets — cross-owner facet enumeration) — three existing feature flows touch on the read-collaborative posture from different angles. None NAMES it as the platform's explicit doctrine.

## Notes

- **This is the architectural ADR-candidate underlying ~12 separate F-NNN flows.** The decision "we are read-collaborative; mutation-gated only" is the load-bearing principle that explains why F-014 (Per-Entity Alert View) leaks cross-owner alerts; F-017 leaks cross-owner facets; F-018 has cross-tenant Tag visibility; F-021 (Activity Feed) has cross-owner audit-trail read; F-025 has 10/13 query-example endpoints without security rules. Every one of those features is a downstream consequence of the implicit ADR. Naming the ADR explicitly would let operators reason about ODD's threat model.
- **Operator threat model**: an operator deploys ODD across a mid-size organization (200 users, 5 departments, 100k data entities). Users from different departments share the catalog. The platform's authentication chain (LOGIN_FORM or OAUTH2 or LDAP) confirms identity; the authorization framework regulates mutations (you can edit YOUR datasets); but reads are universal. User A in Marketing sees user B in Finance's data entity, including custom metadata fields, lineage edges, owner chips, alert resolution history, tag annotations, term linkages, query-example bodies — the lot. There is NO per-row owner-scoped read gate. The doctrine is "the catalog is a shared knowledge surface; collaboration trumps confidentiality".
- The doctrine is operationally correct for ODD's documented use case (a shared discovery catalog). It becomes incorrect IF an operator deploys ODD into a multi-tenant SaaS context, a regulatory-bounded environment (HIPAA-shaped data discovery across hospitals), or a vendor-shared-tenant environment. Operators in those contexts cannot deploy ODD safely without external scoping (separate platform instances per tenant) — but the docs do not warn them.
- Cross-link with F-014 (per-entity alert view), F-015 (my-objects anchor-set), F-017 (search filter facets), F-021 (activity feed) — these flows enumerate the read-collaborative consequences but do not name the doctrine.
- The mutation-gating-only doctrine has an asymmetry: per-owner "my-objects" scoping IS implemented (F-015) — operators see additional rows when they ARE owners (positive scoping), but never fewer rows when they are NOT (no negative scoping). The asymmetry compounds the operator confusion: "if my-objects works, surely catalog reads scope too" → NO.
- Caveat — actuator endpoints (`/actuator/health`, `/actuator/env`, `/actuator/prometheus`, `/actuator/info`) are also publicly readable under DISABLED + WHITELIST_PATHS includes `/actuator/**`. The combination of read-collaborative + actuator-exposed is the central case of REFACTOR-185.
- This is an ADR candidate FIRST and a feature candidate SECOND. The ADR shape: "ODD Platform is read-collaborative — every authenticated user reads every catalog row. Mutations are gated by Policies/Permissions/Roles/Owners. This is INTENTIONAL: the operator's deployment is assumed to be a trusted shared collaboration space, not a multi-tenant confidentiality surface." The doctrine should live as an ADR; the feature flow F-NNN would enumerate the operator-observable read surfaces that lack scoping.
