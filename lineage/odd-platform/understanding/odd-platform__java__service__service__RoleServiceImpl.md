# RoleServiceImpl — semantic understanding

## understanding

The Role half of the RBAC mutation surface AND the source of every authorized
request's "what roles does the current user have" answer. The class
(`RoleServiceImpl.java:31-143`) wraps `ReactiveRoleRepository` and three
relation/lookup repositories (`ReactiveRoleToPolicyRepository`,
`ReactiveOwnerToRoleRepository`, `ReactiveUserOwnerMappingRepository`) plus
the `AuthIdentityProvider` to expose five methods: `list` / `create` / `update`
/ `delete` (operator CRUD via `POST/GET/PUT/DELETE /api/roles[/{id}]`) plus
`getCurrentUserRoles` — the read-side AUTHORIZATION HOT PATH invoked
transitively from `PolicyServiceImpl.list` (line 54) and
`PolicyServiceImpl.getCurrentUserPolicies` (line 104) on EVERY authorized
HTTP request that traverses the permission framework. The service owns four
invariants the repository does not: (1) the predefined `Administrator` /
`User` names are reserved against UPDATE (case-SENSITIVE) and DELETE
(case-INSENSITIVE) but NOT against CREATE — the create-side gap surfaced in
batch E is PRIMARY-SOURCE in this file at lines 49-61 (no name check);
(2) ALL THREE mutating methods are `@ReactiveTransactional` (lines 50, 64, 77)
— the deliberate inconsistency-vs-PolicyServiceImpl (none of policy's three
mutations carry the annotation per batch I); (3) the role-to-policy edge set
is REWRITTEN ENTIRELY on update (delete-except-then-create at lines 112-121)
but INSERT-ONLY on create (line 56-57); (4) the cascade-delete defence at
lines 85-88 raises `CascadeDeleteException("Role is attached to a owner")`
[sic — singular grammar] if any `owner_to_role` row references the role —
the SOLE service-layer protection against a soft-deleted role with surviving
owner bindings. The `list` path branches by user role IN MEMORY: ADMIN
callers hit `roleRepository.listDto`, non-ADMIN callers receive only their
own attached roles via `filterUserRoles` (lines 41-44, 136-142) which IGNORES
the page/size request parameters and returns `hasNext=false` — identical
pagination-asymmetry pattern to PolicyServiceImpl.list per batch I.

- invariants:
  - "All THREE mutating methods are `@ReactiveTransactional` (RoleServiceImpl.java:50, 64, 77). The annotation wraps the multi-call read-then-write composition on update (lines 66-72: get + name-check + updateRoleName + updateRolePolicyRelations + getDto) and delete (lines 79-91: get + name-check + isRoleAttachedToOwner + deleteRoleRelationsExcept + delete) into a single connection-scoped R2DBC transaction. This is the DELIBERATE asymmetry vs PolicyServiceImpl (batch I) which has NONE of its three mutations annotated — the platform's pattern is inconsistent across the two RBAC services. The wrap does NOT by itself prevent lost-update without `SELECT ... FOR UPDATE` (no row-version field on RolePojo) but it at least scopes read+write to a single R2DBC connection — strictly stronger than PolicyServiceImpl's complete absence."
  - "Predefined-role name reservation is ASYMMETRIC across create / update / delete AND case-asymmetric within itself. CREATE (lines 49-61) has NO name pre-check — protected only by the partial unique index `role_name_unique WHERE deleted_at IS NULL` (V0_0_55__add_policies_and_roles.sql:42, recreated by V0_0_64__remove_is_deleted_field.sql:88-90 per batch N). UPDATE (line 68) rejects on case-SENSITIVE `!role.getName().equals(UserProviderRole.ADMIN.getValue())` — only the literal string 'Administrator' is protected from rename; the User role is independently protected by the inner updateRoleName check at lines 104-106. DELETE (lines 81-82) rejects on case-INSENSITIVE `Stream.of(UserProviderRole.values()).noneMatch(r -> r.getValue().equalsIgnoreCase(role.getName()))` — BOTH 'Administrator' and 'User' protected, AND 'administrator' / 'user' / 'ADMINISTRATOR' / etc. ALL match. The drift is observable: a role created with name 'administrator' (lowercase) bypasses the unique index (Postgres VARCHAR comparison is byte-for-byte case-sensitive), is rename-able via update (case-sensitive equals does not match), but is NOT deletable via delete (case-insensitive matches the enum)."
  - "Role mutations of the OWNER-ROLE edge set differ asymmetrically across create / update / delete. CREATE (lines 56-57) issues `roleToPolicyRepository.createRelations(roleId, policies)` — INSERT-ONLY into role_to_policy. UPDATE (lines 112-121) issues `deleteRoleRelationsExcept(roleId, newPolicies)` THEN `createRelations(roleId, newPolicies)` — DELETE-then-INSERT wholesale rewrite of the role's policy bindings. DELETE (line 89) issues `deleteRoleRelationsExcept(roleId, List.of())` — DELETE ALL role_to_policy rows for the role before the soft-delete of the role itself. The `deleteRelationsExcept` shape (ReactiveRoleToPolicyRepositoryImpl.java:51-56) is a `DELETE FROM role_to_policy WHERE role_id = ? AND policy_id NOT IN (...)` — a HARD delete, not soft-delete. So role_to_policy edges are physically removed on every update and delete; only the role row itself is soft-deleted."
  - "The cascade-delete defence on owner-binding is HARD-BLOCKING. RoleServiceImpl.java:85-88 — `ownerToRoleRepository.isRoleAttachedToOwner(id)` then `filter(Boolean::booleanValue)` then `flatMap(isAttached -> Mono.error(new CascadeDeleteException(\"Role is attached to a owner\")))`. If any `owner_to_role` row references the role, the delete fails with HTTP 400 (CascadeDeleteException → ControllerAdvice.handleCascadeDelete → BAD_REQUEST). The defence is BOTH (a) the inverse of OwnerServiceImpl.delete (batch P, which HARD-deletes owner_to_role edges before soft-deleting the owner) — the platform deliberately chooses one side to fail-and-prompt-cleanup (Role) and the other side to auto-cleanup (Owner) — AND (b) the parallel of PolicyServiceImpl.delete (batch I, which raises CascadeDeleteException if role_to_policy rows reference the policy). Both Role and Policy delete paths FAIL on bound parent resources; both Owner and Role-update paths AUTO-CLEAN the child edges before the parent mutation. The asymmetry between Role-delete (fail on owner bindings) and Owner-delete (clean role bindings) means an operator must detach roles from owners on the OWNER side via PUT /api/owners/{id} (or DELETE /api/owners/{id} which auto-cleans), NOT on the ROLE side."
  - "List path branches by user role IN MEMORY (RoleServiceImpl.java:40-47). For non-ADMIN users (`roles.stream().noneMatch(r -> r.pojo().getName().equals('Administrator'))` returns TRUE) the `.map(roles -> filterUserRoles(roles, query))` is taken — building an in-memory `Page<RoleDto>` from the user's already-attached RoleDto collection (lines 136-142), IGNORING the `page` and `size` request parameters and setting `hasNext=false`. For ADMIN users, the `.filter` fails, the Mono empties, and `.switchIfEmpty(Mono.defer(() -> roleRepository.listDto(page, size, query)))` (line 45) hits the repository's CTE-paginated list. Asymmetric pagination contract by role — identical pattern to PolicyServiceImpl.list at lines 52-60 per batch I."
  - "User-role rename protection. RoleServiceImpl.java:103-107 — `if (role.getName().equals(UserProviderRole.USER.getValue()) && !StringUtils.equals(role.getName(), formData.getName())) return Mono.error(new BadUserRequestException('User role name cannot be changed'))`. The User role can be updated IN PLACE (e.g. its policy bindings can be rewritten) but its name cannot. The Administrator role is blocked from update ENTIRELY at line 68 (outer filter). Combined, the predefined-role surface is: Administrator → no update at all; User → policy bindings mutable, name immutable; both → no delete; neither → no name protection on create."
  - "`getCurrentUserRoles` is the AUTHORIZATION HOT PATH — invoked from `PolicyServiceImpl.list` (PolicyServiceImpl.java:54) and `PolicyServiceImpl.getCurrentUserPolicies` (line 104) on every authorized HTTP request that traverses the permission framework. The two-tier fallback chain at RoleServiceImpl.java:96-101 — userOwnerMappingRepository.getUserRolesByOwner (4-way JOIN per ReactiveUserOwnerMappingRepositoryImpl.java:99-114 + REFACTOR-389) → if empty, getUserProviderRole + roleRepository.getByName → if STILL empty, List.of() — means per-request DB cost is 1-2 JOIN round-trips PLUS the parallel PolicyService chain's 1 JOIN. No request-scoped cache, no user-scoped cache."
