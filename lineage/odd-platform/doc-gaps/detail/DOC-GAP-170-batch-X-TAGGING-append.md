### Scope expansion — THREE asymmetries, not one

DOC-GAP-170's original framing named ONE asymmetry (soft-delete on `tag` vs hard-delete on `tag_to_*` relations). The `deleteTag` controller-method sidecar surfaces TWO MORE the original finding did not capture:

1. **Cascade-table asymmetry** (original) — `tag_to_term` + `tag_to_data_entity` HARD-deleted; `tag` SOFT-deleted; **`tag_to_dataset_field` NOT TOUCHED AT ALL** (the original DOC-GAP-170 said relations are hard-deleted; the precise truth is that 2 of 3 relation tables are hard-deleted and the 3rd is orphaned — the `deleteDatasetFieldRelations(long)` method exists at `ReactiveTagRepositoryImpl.java:299-306` but is never called from the delete chain).
2. **FTS-refresh count asymmetry** (NEW) — `delete` refreshes 1 search vector; `update` refreshes 3. After a delete, the data-entity-side `search_entrypoint.tag_vector` still carries the deleted tag's token.
3. **FTS-refresh ordering defect** (NEW) — the one refresh `delete` does perform runs AFTER the `tag_to_term` rows are hard-deleted, so its discovery CTE (`SELECT term_id FROM tag_to_term WHERE tag_id = ?`) is empty — the refresh is a no-op for cleaning the deleted tag's name out of `term_search_entrypoint.tag_vector`.

The proposed doc-action's "Deleting and recreating tags" subsection (item 1) should be expanded: the operator-facing caveat must now state (a) `tag_to_dataset_field` rows are ORPHANED (not deleted), (b) a global full-text search for a deleted tag's name can still surface previously-tagged entities until an unrelated write refreshes those search vectors. The code-side `/log-issue` action gains a third point: `TagServiceImpl.delete` should call `deleteDatasetFieldRelations(tagId)` inside the `Flux.zip` (the `deleteTag` sidecar's `request_inputs` block names this as the exact fix anchor) AND refresh all three search vectors (mirroring `update`'s `updateSearchVectors`), with the term-side refresh re-ordered BEFORE the `tag_to_term` delete.
