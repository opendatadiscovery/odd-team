## Description

`metadata-stale.md` is written around the premise that the freshness signal is a single binary widget that "renders nothing" when an entity is fresh (line 64: "renders the orange icon only when `is_stale=true`; in every other case it renders nothing — no DOM, no whitespace"; line 58: "the UI shows the same absence of icon"). That is accurate for the **catalog lists** — Search result rows, the Directory level-4 list, Overview tiles — which all render the shared `MetadataStale` widget that returns `null` when `isStale` is false.

But the **entity detail-page header does not** follow that grammar. In the header, the fresh (non-stale) state renders a **neutral clock glyph (`TimeGapIcon`) plus a relative "last-ingested" timestamp label** ("ingested 3 hours ago"). The header switches between two glyphs: stale → the `MetadataStale` orange `StaleIcon` (with tooltip), fresh → the neutral `TimeGapIcon` + an always-visible relative label. Only the *entirely-uningested* case (`lastIngestedAt` null) renders nothing in the header.

So an operator reading metadata-stale.md and then opening an entity detail page sees a clock icon + "ingested X ago" on a perfectly fresh entity and has no doc that explains it — the page led them to expect "no icon = fresh, orange icon = stale," and the header presents a *third* visual state (neutral clock + relative label) the page never mentions. Two visual grammars for the same underlying fresh state; the doc documents only one.

This is a render-grammar caveat, distinct from the multi-replica clock-skew edge case already in metadata-stale.md (§"Multi-replica deployments…", the F-024/H-008 hypothesis) — it is about the *fresh-state glyph differing between list and detail*, not about the stale cutoff flickering.
