## Description

Gate 9 (factual claim provenance) finding from `/review batch:feature/state-doc141-ia-refactor-2026-05-07` 2026-05-07.

`docs/data-discovery/tagging.md` L28 introduces a permissions table with the framing:

> *"The platform exposes four `TAG_*` RBAC permissions:"*

The table that follows (L30-35) lists four rows:

| Permission | Action |
|---|---|
| `TAG_CREATE` | Create a new tag in the catalog vocabulary. |
| `TAG_UPDATE` | Edit a tag's name or its Important flag. |
| `TAG_DELETE` | Remove a tag from the catalog vocabulary. |
| `TAG_ASSIGNMENT_UPDATED` | Activity-feed event marker emitted whenever tag assignments on an entity change. |

**The factual mismatch:** `TAG_ASSIGNMENT_UPDATED` is **not** an RBAC permission. It is an entry on the `ActivityEventType` enum at `odd-platform/odd-platform-specification/components.yaml:3173`, alongside other activity markers (`OWNERSHIP_CREATED`, `DATA_ENTITY_CREATED`, `TERM_ASSIGNMENT_UPDATED`, …). The actual RBAC permissions are at `components.yaml:158-260` under the `Permission` enum; only **three** rows match `TAG_*`:

```
- TAG_CREATE       (line 221)
- TAG_UPDATE       (line 222)
- TAG_DELETE       (line 223)
```

The implementing commit (`0466040`) acknowledged the right separation in its body:

> *"TAG_* permissions verified at the same components.yaml: TAG_CREATE / TAG_UPDATE / TAG_DELETE = three (under Management permissions per permissions.md), plus TAG_ASSIGNMENT_UPDATED activity marker."*

…but the authored page text framed all four as "RBAC permissions". This is the precise drift the Gate 9 banned-phrase / verified-source rule exists to catch — the maintainer knew the right answer, but the page text didn't reflect it.

**Mirror defect on Features.md L93** — the carved-out Features.md teaser says:

> *"…the four `TAG_*` RBAC permissions…"*

— same wrong framing, propagated from tagging.md to the index teaser. Fix both.

**Reference for the right shape:** `docs/data-glossary/business-glossary.md` L49-61 handles the analogous TERM_* case correctly:

```
The platform exposes seven `TERM_*` RBAC permissions:
[7-row table]
Plus the cross-cutting `TERM_ASSIGNMENT_UPDATED` activity-event marker emitted whenever a term is linked to or unlinked from a data entity.
```

Two clearly distinct constructs, separately framed. tagging.md should adopt the same shape.

## Context

- **Why medium (not high).** Operator confusion potential is real (an operator reading tagging.md may try to grant `TAG_ASSIGNMENT_UPDATED` as a permission and fail), but the surface is small and the fix is local. Critical-priority is reserved for actively-misleading claims that would cause data loss or security exposure on a default deployment; this is the standard "factually wrong claim, fix when noticed" tier.
- **Why this slipped through Gate 9.** The implementing commit body documented the right separation; the authored text didn't reflect it. The Gate 9 verification step on `/implement` should have caught this — likely the verification was claim-by-claim against components.yaml but didn't re-check the count framing. The fix here is local; the systemic question is whether Gate 9's procedure catches "verified count differs from authored framing" — if a similar shape appears, log an LSN.
