    - **The threat model**: a webhook URL is functionally equivalent to a bearer credential — anyone with the URL can POST to the receiver. Multiple plausible URL-leak vectors: (a) `/actuator/env` exposure (Spring's default mask list does NOT include the substring "url" — per sibling sidecar's evidence at NotificationConfiguration.java:91); (b) container images shipped with `application.yml` embedded (a common operator anti-pattern); (c) Helm chart values pushed to a public Git repo; (d) screen-share / docs-screenshot leakage. Once the URL leaks, an attacker can forge arbitrary alerts at the operator's receiver — e.g., spoof a "PRODUCTION DATABASE FAILURE" alert to trigger an on-call wake-up, or spoof an "ALL CLEAR" to mask a real incident. The receiver has NO mechanism to verify the payload's origin.
    - **The compound with DOC-GAP-235 (cross-tenant exposure)**: a multi-tenant deployment leaks every tenant's alerts to ONE operator URL; an attacker forging alerts can target the receiver with payloads claiming to be from any tenant — receiver-side multi-tenant routing logic (parsing `dataEntity.namespaceName`) becomes untrustworthy without origin verification.
    - **The compound with DOC-GAP-006 (`/actuator/env` exposes secrets by default)**: the webhook URL IS a credential; the actuator-env exposure of the URL is the leak vector that closes the loop on this finding. The two findings together = "anyone who can read /actuator/env can forge alerts at the receiver".
    - **Industry comparison** (per sidecar evidence): Slack incoming webhooks use HTTPS-with-secret-in-URL (the URL IS the auth — but Slack-side rotation is supported); GitHub webhooks ship `X-Hub-Signature-256: sha256=<HMAC>` with a shared secret per webhook; Prometheus AlertManager's `webhook_config` supports `http_config.authorization` + `http_config.basic_auth`. ODD is the outlier among comparable platforms.
    - **The fix-shape spectrum**: (a) doc-side fix: explicitly state that ODD does NOT sign payloads + recommend operator-side mitigations (private network / VPN deployment / HTTP gateway with mTLS / IP allowlist on the receiver); (b) code-side fix MINIMUM: add a `notifications.receivers.webhook.secret` config key + compute HMAC-SHA256 over the serialised body + emit as `X-ODD-Signature-256: sha256=<hex>` header per webhook industry convention; (c) code-side fix COMPANION: add a generic `notifications.receivers.webhook.headers.X` config-knob shape for operator-supplied auth headers (Bearer token, API key, tenant identifier).
