## Description

User feedback during `/review batch:feature/state-doc141-ia-refactor-2026-05-07` (2026-05-07) flagged that the bucket-attribution rule in Cornerstone 2 (codified in `pillars/documentation/cornerstones.md` L24-33 by commit `62a5011`) endorses a pattern that violates the doc product's IA principle.

**The cornerstone today (L26-27) says:**

> *"The bucket's aspect landing **indexes the feature** in its Subsections list (or in an "Other {bucket} features" sub-list when the feature lives inline on `Features.md` rather than on a dedicated page). The link from the bucket landing to the feature is the canonical reading path; the same feature must be reachable from its bucket without grepping `Features.md`."*

**The user's IA principle (verbatim from the review feedback):**

> *"Features/Overview is an index of all the features with brief description to grasp the entire functionality of the platform and it should have links to the detailed explanations of the features in the dedicated sections — not vice versa where we have references for index from some dedicated pages — this is crazy and stupid."*

These conflict. The cornerstone today **mandates** the reverse-link pattern (bucket landing's "Other {bucket} features" sub-list → Features.md anchor); the user's principle **forbids** it.

This item updates the cornerstone to match the user's principle. DOC-149 then carries out the doc-side cleanup per the new rule.

## What needs to change in Cornerstone 2

The current L24-33 block has three parts: (1) the "every feature attributes to exactly one bucket" rule, (2) the bidirectional attribution mechanism (Features.md → bucket landing AND bucket landing → feature), (3) the "Other {bucket} features" sub-list pattern for inline-on-Features.md features. Parts (1) and (2) stand. Part (3) is the defect — replace with the no-reverse-link rule.

Specifically:

- **Keep**: "Every feature attributes to exactly one bucket — no orphans" (L24, with the eight-bucket enumeration).
- **Keep**: Features.md → bucket landing closing-sentence pattern ("Part of the [Bucket] section…") on Features.md sections.
- **Replace**: The "or in an 'Other {bucket} features' sub-list when the feature lives inline on Features.md" clause (L26).
- **Add**: The new rule — features inline on Features.md that belong to a bucket must be **homed on that bucket's landing** (as inline sections OR via dedicated detail pages), not punted back to Features.md from the bucket landing. The bucket landing's `## Subsections` list is the canonical home; do not introduce a parallel "Other {bucket} features" pointer-list.
- **Add**: The general no-reverse-link rule — `Features.md` is the index; cross-link direction is one-way (Features.md → detail). Bucket landings, detail pages, and other surfaces below the index MUST NOT cross-link back to a Features.md anchor for canonical reference.
- **Add**: The migration corollary — when a feature currently lives inline on Features.md AND is referenced by a detail page or bucket landing, the right move is to migrate the feature's content to its bucket landing (or to a new dedicated detail page) rather than to add a reverse-link to Features.md.

## Context

- **Why high priority.** This cornerstone is loaded by every authoring session in the documentation pillar. Until it changes, future `/implement` runs may legitimately re-introduce the reverse-link pattern thinking they are following the rule. The cost of re-doing this cleanup grows with every batch.
- **Why this blocks DOC-149.** Without the cornerstone update first, the implementer doing the doc-side cleanup has no codified authority for the new rule — they would be acting against the stated cornerstone. The cornerstone update lands first; the cleanup follows.
- **Why this is a state-repo change (not a doc-repo change).** Cornerstones live in the framework workspace (odd-team), not in the published docs. The documentation pillar's rules are how authoring sessions are governed; updating them is bookkeeping work for the framework, not user-facing content.
- **Maintainer note.** The original cornerstone (commit 62a5011) was authored 2026-05-07 — the same day the user flagged its consequence on DOC-141 review. This is not a long-standing miss; it is a same-day course correction. The pattern was reasonable on paper (bucket landing should index its features → if some live inline on Features.md, link to those anchors → "Other {bucket} features" sub-list captures that link), but in practice it inverted the index/detail relationship and produced the failure the user flagged. The lesson: even a well-reasoned codification can entrench the wrong shape; user feedback on the resulting doc IS the validation step.
