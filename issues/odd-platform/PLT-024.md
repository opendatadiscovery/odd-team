## What

Data Entity Group (DEG) Membership Management has 10 substantive behavioural drifts vs operator expectations and the published doc framing. Six are addressable in code:

**Defect 1 - Write-collaborative posture by design (F-012b).** `SecurityConstants.java:228-236` registers the membership routes (`/api/dataentities/{data_entity_id}/data_entity_group` POST and `.../{data_entity_group_id}` DELETE) with `AuthorizationManagerType.DATA_ENTITY` and permissions `DATA_ENTITY_ADD_TO_GROUP` / `DATA_ENTITY_DELETE_FROM_GROUP` - the resource scope is bound to the CHILD `data_entity_id`, NOT the parent `data_entity_group_id`. `PolicyPermissionDto.java:22-23` confirms both are `DATA_ENTITY(DATA_ENTITY)`-scoped. (Nuance, verified 2026-06-10: DEG-side permission enums DO exist - `DATA_ENTITY_GROUP_CREATE(MANAGEMENT)` and `DATA_ENTITY_GROUP_UPDATE(DATA_ENTITY)` at `PolicyPermissionDto.java:36-37`, and a `DEG` `AuthorizationManagerType` is wired for `/api/dataentitygroups/{data_entity_group_id}` PUT at `SecurityConstants.java:308-311` - but NONE of these gate *membership*. There is no DEG-scoped permission on add-to-group / delete-from-group.) A caller with `DATA_ENTITY_ADD_TO_GROUP` on entity X can place X into ANY manually-created DEG in the catalog, including DEGs owned by unrelated organisational silos. Multi-team deployments cannot enforce per-DEG boundary RBAC. The Catalog Overview's Domain tiles are pollutable via drive-by writes.

**Defect 2 - Forensic silence on membership mutations (F-012a sub-facet).** `DataEntityServiceImpl.java:387-408` (addDataEntityToDEG) carries `@ReactiveTransactional` (line 388) but **no `@ActivityLog`**. Same for `deleteDataEntityFromDEG` (lines 411-438). The `ActivityEventTypeDto.DATA_ENTITY_RELATION_UPDATED` value exists in the enum but is **dead** - no code path emits it. Auditors querying activity for a DEG's membership history find nothing.

**Defect 3 - Idempotence asymmetry (F-012c).** ADD raises 400 on duplicate (line 402: `.switchIfEmpty(Mono.error(new BadUserRequestException("Data entity is already in this DEG")))`). DELETE silently returns 204 on no-op (line 424: `.collectList()` flows to `ignoreElements().thenReturn(noContent())` - no `.switchIfEmpty`). Reconciliation scripts face asymmetric error-handling.

**Defect 4 - Empty DEG persists with no auto-cleanup.** Removing the last child entity leaves the DEG row + its lookup-tables-schema + its tags / terms / lineage attached but childless. Catalog Overview Domain tiles continue to surface the empty group until manual DELETE.

**Defect 5 - DISABLED auth bypass.** The membership endpoints are reachable anonymously under `auth.type=DISABLED` (the SecurityConstants entries are permission-based - under DISABLED, the permission check is short-circuited per the broader `auth.type=DISABLED` posture). Operators running DISABLED-mode demos discover anyone-can-rewrite-the-tile-grid mid-demo.

**Defect 6 - PARTIALLY FALSIFIED (verified 2026-06-10): the two main failure modes already carry distinct messages.** The original draft claimed already-in-DEG, not-a-manual-DEG, and bad-body all collapse to `"Data entity is already in this DEG"`. Reading `DataEntityServiceImpl.addDataEntityToDEG` (`:389-407`) and `deleteDataEntityFromDEG` (`:412-437`): the not-a-manual-DEG case throws a DISTINCT message - `"Entity with id %s is not manually created DEG"` (add `:396`, delete `:419`) - and already-in-DEG throws `"Data entity is already in this DEG"` (add `:402`; DELETE has no equivalent, see Defect 3). So these two are NOT conflated. The only residual is that a malformed/empty request body is not given a dedicated, friendly message (it fails generic bean/deserialisation validation). Down-scoped to LOW: add a body-validation message for the empty-`data_entity_group_id` case; the failure-class disambiguation the draft asked for largely already exists.

## User-facing impact

Static analysis (BE code-settled), 2026-06-10 - the DEG membership UI was not driven on a running stack this pass; the RBAC/audit/idempotence facts below are all code-confirmed:

- **Defect 1 (HOLDS) - cross-team DEG pollution. Auth mode: any mode with policy-based RBAC (LOGIN_FORM/OAUTH2/LDAP with Policies; and trivially DISABLED).** A user holding `DATA_ENTITY_ADD_TO_GROUP` on a child entity can add it to *any* manually-created DEG; the permission is evaluated against the child, never the DEG. A multi-team deployment that expects per-DEG boundaries cannot enforce them, and Catalog Overview Domain tiles can be polluted by an unrelated team.
- **Defect 2 (HOLDS) - no audit trail.** Neither `addDataEntityToDEG` nor `deleteDataEntityFromDEG` carries `@ActivityLog`; `DATA_ENTITY_RELATION_UPDATED` is a dead enum value. The Activity Feed shows nothing for membership changes - a compliance auditor finds no record.
- **Defect 3 (HOLDS) - asymmetric idempotence.** ADD -> 400 on duplicate; DELETE -> silent 204 on no-op. Reconciliation scripts must special-case the two.
- **Defect 6 (PARTIALLY FALSIFIED -> LOW)** - the not-manual-DEG vs already-in-DEG cases already return distinct messages (`:396`/`:419` vs `:402`); only the empty-body case lacks a friendly message.
- **Defects 4 (empty-DEG persistence) & 5 (DISABLED bypass)** are design/posture observations, not code defects - Defect 5 is the documented DISABLED-mode posture (a deliberate dev/demo grant; see PLT-072), and Defect 4 is a product decision (auto-cleanup vs explicit flag). Remaining-check: the empty-DEG tile persistence and the DISABLED reachability were reasoned from code, not driven in the UI.

## Suggested fix (six independent threads)

**Thread A - Permission scope (Defect 1; the biggest decision).** Two options:
- **Option A1 - Introduce per-DEG permission scope.** New permission `DATA_ENTITY_GROUP_MEMBERSHIP_MANAGE` evaluated against the target DEG's `data_entity_group_id`. Add a `DATA_ENTITY_GROUP` scope to `PolicyPermissionDto`. Rewire the two SecurityRule entries. Default existing Policies grant the new permission to anyone who previously held `DATA_ENTITY_ADD_TO_GROUP` (preserve compatibility).
- **Option A2 - Document the write-collaborative posture explicitly + ship a deployment-time toggle.** Add `odd.deg.membership.strict_permission_scope: false` config (default false to preserve compatibility); when true, the permission is evaluated against the DEG-id instead.

Option A1 is the right long-term posture for a maintained enterprise data catalog. Option A2 is a faster ship that preserves backwards compatibility - the operator still controls.

**Thread B - Activity emission (Defect 2).** Add `@ActivityLog(event = DATA_ENTITY_RELATION_UPDATED, ...)` to both methods. Emit before/after payloads in the DatasetField pattern (see PLT-026 for the cross-pillar harmonisation). Revives the dead enum value.

**Thread C - Symmetric idempotence (Defect 3).** Either:
- ADD switches to silent 204 on duplicate (matches DELETE) - simpler but loses error-on-misuse signal.
- DELETE switches to 400 on missing-pair (matches ADD) - better signal; breaking change for reconciliation scripts that rely on silent 204.

Recommend ADD-becomes-silent: most reconciliation workflows treat ADD-then-DELETE as idempotent, and 204 is the standard idempotent-write response.

**Thread D - Empty DEG cleanup (Defect 4).** Either:
- Auto-delete the DEG row on last-member-removal (cascade through the DEG-side rollups).
- Surface "empty DEG" status on the DEG entity (a flag) and let operators decide.

Recommend the flag - auto-delete is irreversible and may surprise operators who intend to refill the DEG.

**Thread E - DISABLED bypass (Defect 5).** Review the DISABLED-mode SecurityConstants posture for membership endpoints. If DISABLED is meant only for dev/demo (per `LSN-002-minio-region-unset` framing), this is intentional and a doc caveat suffices (DOC-188 covers). If a multi-team DISABLED demo is a real use case, gate behind a DISABLED-strict toggle.

**Thread F - 400 disambiguation (Defect 6 - mostly already done).** Two of the three messages already exist and are distinct (`"Data entity is already in this DEG"` at `:402`; `"Entity with id %s is not manually created DEG"` at `:396`/`:419`). The only gap is the malformed/empty-body case. Minimal remaining work:
- `BadUserRequestException("Request body missing data_entity_group_id")` - body validation (replaces the current generic null/deserialisation error). The other two need no change.
