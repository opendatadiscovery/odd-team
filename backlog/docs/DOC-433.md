## Description

The odd-tracing-gateway page tells an operator two different host ports for the same `GET /entities` outbound endpoint:

- **Narrative / API-surface table** say the endpoint is on port `8080`:
  - Line 29: "**Exposes the inferred entities** through `GET /entities` on port `8080` ..."
  - Line 198 (Outbound API table): `| HTTP | 8080 | GET /entities[?changedSince=<ISO-8601>] | ... |`
- **The Docker Compose example** (line 116) maps `"8081:8080"`:
  ```yaml
  ports:
    - "8081:8080"   # GET /entities
    - "9090:9090"   # OTLP gRPC
  ```

An operator who copies the Compose block verbatim and then follows the narrative to `http://localhost:8080/entities` hits nothing — the gateway is reachable on host port **8081** (container `8080`) under that mapping. The narrative port is the *container* port; the example publishes it on host `8081`. Nothing on the page reconciles the two, so the copy-paste path silently dead-ends.

`8080` is correct as the gateway's *internal/container* listen port (it is the gRPC-server Spring Boot app's HTTP port). The defect is that the Compose example remaps it to host `8081` without the page ever saying so. Low severity (local-evaluation snippet, not a production posture), but it is a self-inconsistency on a live published page that wastes a first-run operator's time.


## Second instance (found 2026-09-02) — the resolver chain is described two incompatible ways

The **Configuration reference** describes the service-name resolver ordering rule once, and then contradicts it
one table later. Both sentences are on the live page.

| Line | Says |
|---|---|
| `:143` (`app.defaultNamePriority`, default `0`) | "**Lower-priority resolvers run last; the first resolver returning a name wins.**" |
| `:154` (`app.docker.namePriority`, default `10`) | "With the default value, **the Docker resolver runs after the default resolver but its result wins** (the resolver chain stops at the first match in priority order)." |

The two cannot both be true. Under `:143`'s rule, the Docker resolver (priority `10`) runs **before** the
Default resolver (priority `0`) — "lower-priority runs last" — and first-match-wins is then what makes the
Docker name win. `:154`'s parenthetical agrees with that mechanism ("stops at the first match in priority
order") but its main clause states the opposite ordering: if Docker really ran *after* Default, and the chain
stopped at the first match, then Default — which is **always active** and always returns the `service.name`
attribute — would win every time and the Docker resolver could never take effect at all.

So the page simultaneously tells an operator that enabling `app.docker.enabled=true` with the default
priorities (a) makes the container image the canonical service name (`:20`, `:154`) and (b) runs the resolver
that produces it only after the one that already answered. An operator debugging "why is my service still
named from `service.name` when I enabled the Docker resolver?" gets no usable answer from this page — and an
operator who trusts `:154` will raise `APP_DOCKER_NAME_PRIORITY` when the fix (if any) is the opposite.

**Not resolvable from this workspace.** `odd-tracing-gateway` is a separate repository and is not cloned here,
so which clause is wrong was not determined — only that they are mutually exclusive. The fix must read
`src/main/java/org/opendatadiscovery/tracing/gateway/resolver/` (the sort applied to the `ServiceNameResolver`
beans) and restate **one** rule, then re-express `:143`, `:154` and `:163` against it.

Note `:163` (`app.k8s.namePriority`, also default `10`) states no ordering claim at all, so whichever rule is
correct, that row needs the same one sentence for parity — the K8s and Docker resolvers share a priority and an
operator running both needs to know what happens then.

## Implementation Notes

Smallest correct fix is option (b): keep `8081:8080` (a deliberate "don't collide with the Platform's own `:8080`" choice in a local stack) and add one sentence under the Compose block, e.g. "With the mapping above the gateway's `GET /entities` is reached at `http://localhost:8081/entities` — `8081` is the published host port, `8080` is the container port the narrative and the API-surface table refer to." This preserves the no-collision intent of the example while removing the contradiction. Do not change the OTLP gRPC line (`9090:9090` is consistent). No code change — this is the gateway's own repo, not odd-platform; the port facts are sourced from the page's own cross-cited gateway source tree.
