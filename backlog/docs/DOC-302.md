## Description

The shipped security posture is "off", and the docs never say so plainly. Three code-confirmed facets:

1. **`auth.type=DISABLED` is the shipped default.** The authentication README enumerates four auth mechanisms as a flat menu but omits that **`DISABLED` is the `application.yml`-shipped default**. An operator reading the page does not learn that the **out-of-box posture is permit-all, no authentication** — every endpoint is open and the synthesised principal is an admin. This is the LSN-001/002 "default-with-consequence" class.

2. **EKS quick-launch puts the DISABLED default on a public LoadBalancer.** The EKS quick-launch page never mentions `auth.type`. Following it deploys a **fully unauthenticated** UI/API on a **public LoadBalancer** (mitigated only by `source-ranges` if the operator sets them). The page's only security caveat is HTTP-vs-HTTPS — it omits that the platform itself is wide open by default.

3. **`ldap://` sends credentials in cleartext.** The LDAP page is silent on `ldap://` vs `ldaps://`; the code accepts any scheme verbatim. The page's **own example** `ldap://localhost:389` sends the **bind password and every user's login credential in cleartext** with **no boot warning** (LSN-002 — the unset-secure-default class).

High — the product ships insecure by default and the docs present that posture as normal without the security caveats an operator needs.

**Failure shape**: missing security caveats (Gate 3/6) on the out-of-box auth posture across three deploy/auth surfaces.
