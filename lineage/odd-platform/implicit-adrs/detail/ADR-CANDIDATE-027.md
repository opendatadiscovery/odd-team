- **ADR-CANDIDATE-027** (NEW 2026-05-10B): Ingestion-token verification on `POST /ingestion/entities` is **opt-in** via `auth.ingestion.filter.enabled` (no `matchIfMissing=true` on the `@ConditionalOnProperty`, explicit `false` default in `application.yml:48`); path matching is hard-coded per-subclass in the filter constructor; sibling ingestion endpoints (`/ingestion/datasources`, `/ingestion/alert/alertmanager`) have different protection postures (unconditional filter, no filter respectively)
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar (`IngestionDataEntitiesFilter.auth.ingestion.filter.enabled@L20`) — the four sub-decisions compose into a coherent ingestion-auth architectural family; cross-validated by the contrast with the always-on `IngestionDataSourceFilter` (also surfaced in the same sidecar) and the never-protected `AlertManagerController` (cited from batch A's ADR-CANDIDATE-006)

  - **Decision statement**: The platform's ingestion-auth model is a per-endpoint composition of three different postures: (a) `POST /ingestion/datasources` (datasource registration) is ALWAYS protected by `IngestionDataSourceFilter` — unconditionally registered, no toggle, requires the collector's bearer token; the structural reason is bootstrap-order (a collector must be known before its datasources exist, so the verification cannot be optional); (b) `POST /ingestion/entities` (data-entity ingestion) is OPT-IN-protected by `IngestionDataEntitiesFilter`, gated by `@ConditionalOnProperty(value="auth.ingestion.filter.enabled", havingValue="true")` (no `matchIfMissing=true`); `application.yml:46-48` ships `auth.ingestion.filter.enabled: false` explicitly (not commented out, not relying on the no-matchIfMissing default) — the deliberate "operator must see the toggle" stance; (c) `POST /ingestion/alert/alertmanager` is UNPROTECTED by any application-layer filter — this is the ADR-CANDIDATE-006 network-delegated-auth decision. The pattern's auth-trust gradient is: collector-registration (mandatory) → data-ingestion (opt-in) → external-alert-ingestion (operator-network-delegated). Path matching is hard-coded per-subclass (one filter class per ingestion path) rather than registry-driven.
  - **Wisdom test**: PASS. The four sub-decisions compose with intent: (a) the explicit `false` in YAML is the load-bearing visibility decision; (b) the conditional-vs-unconditional sibling registration encodes bootstrap-order constraint; (c) the hard-coded path-matcher-in-constructor is consistent across the package; (d) the trust-gradient (registration mandatory → ingestion opt-in → alertmanager network-delegated) is a deliberate architectural model. Structural (every future `/ingestion/*` endpoint must choose where on this gradient it lives, and a future change to the gradient must contend with the existing pattern).
