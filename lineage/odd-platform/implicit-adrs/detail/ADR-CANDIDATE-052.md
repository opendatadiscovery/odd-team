- **ADR-CANDIDATE-052** (NEW 2026-05-12E): Search is a **server-side stateful session** — `POST /api/search` creates a `search_facets` row keyed by a server-generated UUID, returns the UUID + aggregated facet counts (not result rows), and requires the caller to call subsequent endpoints (`GET /api/search/{search_id}/results`, `PUT /api/search/{search_id}`, `GET /api/search/{search_id}/facet/{facet_type}`, `GET /api/search/{search_id}/data_entities/{data_entity_id}/highlights`) to retrieve / mutate the session. The pattern is reused across four feature surfaces (catalog search, terms search, query-example search, reference-data search), each with its own session-UUID handle
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar (`search`) but the convention is reused across four parallel controllers (`SearchController`, `TermController.searchTerms`, `QueryExampleController`, `ReferenceDataController`) — the four-surface consistency makes the pattern structural rather than per-feature
  - **Surfaced by**:
    - `odd-platform__java__SearchController__controller-method__search.md:implicit_adrs.[0]` ("Search-session-as-server-state pattern — `POST /api/search` does NOT return results directly; it creates a server-side `search_facets` row keyed by a server-generated UUID, returns aggregated facet counts + the UUID, and requires the caller to call `GET /api/search/{search_id}/results` for paginated rows. The same UUID is used by `getSearchFacetList`, `updateSearchFacets`, `getFiltersForFacet`, and `highlightDataEntity` — every search interaction is bound to a persistent session row. Sibling features (`/api/terms/search`, `/api/queryexample/search`, `/api/referencedata/search`) replicate the same session-UUID pattern." — intent_anchor: "the entire `SearchApi` interface plus the parallel `TermController` / `QueryExampleController` / `ReferenceDataController` controllers all use the same `searchId` UUID handle — a session-on-server pattern is applied consistently across four feature surfaces, signalling intentional design rather than accident.")
  - **Decision statement**: ODD's search surface is implemented as a server-side stateful session. The `POST` endpoint persists a `FacetStateDto` (filter selections + raw query string + my-objects boolean) into the `search_facets` table keyed by a server-generated UUID, and returns the UUID + aggregated facet counts WITHOUT result rows. Result-row pagination, facet refinement, filter updates, and per-entity highlight queries all route through subsequent endpoints keyed by the UUID. The session-row carries the query state across multi-step UI interactions (a user drilling into a result, scrolling for more pages, and updating facets reuses the same session). Trade-off accepted: server retains query state at the cost of (a) an unbounded `search_facets` table requiring housekeeping (handled by `SearchFacetsHousekeepingJob` with `housekeeping.ttl.search_facets_days` TTL per REFACTOR-141); (b) raw query text persisting in the DB for the TTL period (PII surface — REFACTOR-204); (c) no per-user owner column on the session row, so any user knowing a session UUID can fetch its results (mitigated by UUID-v4 unguessability + read-collaborative posture per ADR-CANDIDATE-003 — REFACTOR-205). The pattern is reused across four feature surfaces (catalog, terms, query examples, reference data) — the four-surface consistency makes the pattern intentional.
  - **Wisdom test**: PASS. The structural commitment is anchored at FOUR independent controllers each implementing the same `searchId` UUID pattern with the same lifecycle (create session → fetch results → mutate facets → drop after TTL). The decision is positive (the alternative — returning result rows directly + stateless aggregation — would be simpler but precludes the cross-call session continuity the UI exploits). Structural for every future search-shaped feature.

Composes with ADR-CANDIDATE-003 (read-collaborative borderline — the absence of per-user session-row owner is consistent with the borderline posture).
