## Description

`oauth2-oidc.md`'s **Admin-detection per-provider matrix** uses two different phrasings in the same table for
what the code does with one shared helper:

| Provider row | "Match semantic" as published | Correct? |
|---|---|---|
| **AWS Cognito** | `exact match on both` | **NO** |
| **GitHub** | `exact (principals); case-insensitive full match (groups)` | **half** — the groups half is right, the principals half is not |
| **Google** | `exact match` | **NO** |
| **Azure AD** | `exact match` | **NO** |
| **Okta** | `case-insensitive full match` | yes |
| **Keycloak** | `case-insensitive full match` | yes |
| **Custom OIDC** | `case-insensitive full match` | yes |

The table's own use of *"case-insensitive full match"* in four rows makes *"exact match"* in the other rows
read as **case-sensitive** — the GitHub row draws that contrast explicitly inside a single cell
(`exact (principals); case-insensitive full match (groups)`).

## What is actually true (verified in source, not inferred)

Every OAuth2/OIDC provider — and LDAP — resolves `admin-principals` and `admin-groups` through **one** helper:

- `odd-platform-api/.../utils/OperationUtils.java:7-10`
  ```java
  public static boolean containsIgnoreCase(final Collection<String> collection, final String element) {
      return collection.stream().anyMatch(element::equalsIgnoreCase);
  }
  ```
  i.e. **case-insensitive, full-value equality** — no substring, no prefix.
- `auth/handler/impl/AbstractOIDCUserHandler.java:38` (`admin-principals`) and `:50` (`admin-groups`) — the
  base class **Cognito and Azure AD both extend**, and which `CustomOIDCUserHandler` (Okta / Keycloak / any
  non-enumerated provider) inherits.
- `auth/handler/impl/GoogleUserHandler.java:60` — `containsIgnoreCase(provider.getAdminPrincipals(), adminPrincipal)`.
- `auth/handler/impl/GithubUserHandler.java:59` — `containsIgnoreCase(provider.getAdminPrincipals(), name)`;
  `:119` for the team names.
- `config/LDAPSecurityConfiguration.java:48` — the same static import, so LDAP matches identically.

There is no per-provider divergence in the match semantic at all. `admin-promotion.md:51` already states this
correctly: *"Across every mode and provider, `admin-groups` / `admin-principals` matching is **case-insensitive,
full-value equality**"* — and `oauth2-oidc.md`'s own GitHub `admin-groups` admonition (:140, shipped by
**DOC-336**) says *"This is consistent with every other provider — across all modes, `admin-groups` /
`admin-principals` matching is full-value, case-insensitive equality (no substring, no prefix)"*.

So the page contradicts **itself** three rows apart, and contradicts the cross-mode reference it links to.

## User-facing impact

The error is in the **under-estimating** direction, which is the dangerous one for an ADMIN grant:

1. **A stale, differently-cased entry is believed inert but is live.** An operator who removes an admin by
   changing `admin-principals: [Alice@corp.com]` to a different case — or who leaves a legacy capitalised entry
   in place expecting it to no longer match the IdP's lowercased `email` claim — has **not** revoked anything.
   The page tells them "exact match"; the code promotes `alice@corp.com` to ADMIN on the next login.
2. **Defensive duplication.** The safe reading of "exact match" is to list every casing variant, which bloats
   the config and makes the real grant list harder to audit — the opposite of what an admin-grant list needs.

Not `critical` (it does not by itself widen a grant beyond what the operator wrote down), but it is
*incorrect documentation on a security control*, so `high`.
