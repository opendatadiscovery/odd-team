## What

The Dictionary / Term-search box (the `TermSearch.tsx` clone of the Catalog Search) routes typed text through the same `JooqFTSHelper.tsQuery` path that inlines the query into a raw `to_tsquery(?)` with no escaping of tsquery operators (`! ( ) : <-> & | ' \`). A query containing a parenthesis or colon (common in technical term names) is persisted into the search session row and then makes **every** subsequent faceted read for that session fail at `to_tsquery` parse time with Postgres `42601` - a persistent HTTP 500 on every later open of that session URL until the row mutates or the TTL evicts it.

This is the **PLT-090-class drift on the Term-search surface** and is **distinct from PLT-090**, which scopes the `/api/search` (Catalog) `SearchController` surface. The reflection recommends filing this as a Term-search extension of PLT-090 (one consolidated `JooqFTSHelper` fix closes both surfaces), gated on P-360 confirmation.

## Evidence

From the F-024 reflection (`lineage/odd-platform/feature-reflections/detail/F-024.yaml`), hypothesis H-009 (and the canonical F-017 anchor it inherits):

```
JooqFTSHelper.java:164-168   (@ ede5d277)
  // tsQuery splits on space, appends ':*', joins with '&', inlines into to_tsquery(?)
  // with NO escaping of tsquery operators

JooqFTSHelper.java:100-105   (@ ede5d277)
  // raw to_tsquery(?) over the persisted query_string -> 42601 on a metacharacter
```

Verdict is **probe-needed** pending P-360 (`lineage/odd-platform/probes/P-360.yaml`), which reproduces the typed-text -> poisoned-Term-session -> facet-read-500 end-to-end. (The Catalog-surface twin is pinned by P-188 under F-017.)

## Impact

A user searching the Dictionary for a term whose name contains a colon, parenthesis, or other tsquery metacharacter gets a 500 and a session that is permanently broken - every subsequent action on that session URL also 500s - with no on-screen explanation; refreshing repeats the failure because the poisoned query is in the persisted row. Because the session is bearer-token-shaped (the search_facets row has no per-user binding), a poisoned session URL can be shared as a denial-of-service vector.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: escape tsquery operators in `JooqFTSHelper.tsQuery` (`JooqFTSHelper.java:164-168`), or switch to `websearch_to_tsquery`. The consolidated `JooqFTSHelper` fix closes both the F-017 `SearchController` surface (PLT-090) and this F-024 Term-search surface - file as a Term-search extension of PLT-090, not a fresh root cause. Confirm via P-360 first. (Note: the highest-severity twin, the `ts_headline` `String.formatted` SQL-injection, is separately filed as PLT-109 / GHSA-rjp9-9vgm-q94c - different sink, different severity class.)
