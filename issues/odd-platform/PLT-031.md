## What

The per-entity Activity tab (every data-entity detail page) is mounted BARE in `DataEntityDetailsRoutes.tsx:105` — no `RestrictedRoute`, no `WithPermissionsProvider`. Contrast `/alerts` at lines 70-84 which uses BOTH, and `/history` / `/linked-entities` which use `RestrictedRoute` on `!isStatusDeleted`. **The Activity tab is the ONLY entity-detail tab without a `hidden:` clause** (`DataEntityDetailsTabs.tsx:91-94`) — it survives soft-deleted entities.

Combined with the backend's cross-owner posture (`getDataEntityActivity` cross-owner reach — F-021 + F-014 family), **any authenticated user reads the audit trail for any data entity (including soft-deleted) via the per-entity Activity tab**.

The cross-channel reach is symmetric to F-014's `soft_delete_inclusive_existence_check` facet — audit trail visible while entity is hidden from catalog list endpoints.

## Why it matters

The per-entity Activity tab leaks audit history for entities the user has no business reading:

- **Soft-deleted entities** — visible in this tab; hidden from the catalog list endpoints. The intent of soft-delete is "out of sight"; the audit trail stays accessible.
- **Cross-owner entities** — same as the F-021 family: an authenticated user with no ownership of dataset X can navigate to `/dataentities/{xId}/activity` and read every operator action on the dataset.
- **The contrast with sibling tabs** is the giveaway: alerts uses `RestrictedRoute + WithPermissionsProvider`; history/linked-entities use `RestrictedRoute`; Activity uses neither. The pattern looks like an oversight, not an intentional design.

Operator-visible consequence is symmetric to F-014's soft-delete-inclusive existence check: when an entity is "deleted" in the UI, its audit history remains readable via this tab. A compliance audit ("can a user with no ownership read the history of a hidden dataset?") returns yes.

Severity is MEDIUM because:
- The cross-owner reach is the backend's existing posture (REFACTOR-024 family); fixing only the UI tab here doesn't close the underlying gap — but the UI tab's bare mount is a recognisable cosmetic-vs-structural divergence that operators will see.
- The soft-delete dimension is an intentional read-after-hide that may or may not be by design — needs an architectural-intent confirmation from the team.
- Doc-side mitigation (DOC-206) names the posture explicitly so operators are aware until the team decides the right shape.

## Suggested fix

**Two architectural options; the team needs to choose intent before code.**

**Option A — gate the tab with `RestrictedRoute` on `!isStatusDeleted` AND add a `hidden:` clause on `DataEntityDetailsTabs.tsx:91-94`.** Aligns the tab with the sibling tabs' pattern; soft-deleted entities no longer surface their audit history via the UI. The backend stays cross-owner — that's a REFACTOR-024 family decision, not this PLT's scope.

```tsx
// DataEntityDetailsRoutes.tsx:105
<Route path='/activity' element={
  <RestrictedRoute condition={!isStatusDeleted}>
    <DataEntityActivity />
  </RestrictedRoute>
} />

// DataEntityDetailsTabs.tsx:91-94
{ label: t('Activity'), path: 'activity', hidden: isStatusDeleted }
```

**Option B — explicit "audit history matters most on deleted entities — visible by design" framing, both in code and doc.** No code change; instead, formalise the intent as the platform's audit-retention contract. Operators rely on it for compliance reviews where they need post-deletion forensic access. Doc-side mitigation (DOC-206) already names the cross-channel posture; this option closes the loop with explicit architectural intent.

**Option C — RBAC posture decision (REFACTOR-024 family).** The cross-owner reach is the underlying gap; gate the BACKEND `getDataEntityActivity` with an `ENTITY_ACTIVITY_READ` permission + per-entity ownership check. Larger scope; coordinates with the platform-wide RBAC posture work.

Recommendation: **Option A** as the immediate ship; raise Option B vs Option C as the team architectural intent question at the next platform-wide RBAC review.
