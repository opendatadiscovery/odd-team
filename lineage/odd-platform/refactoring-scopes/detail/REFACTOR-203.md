The repository-layer evidence is more conclusive than the controller-method evidence: **the lineage table itself has NO owner column** (verified across all 4 lineage-related migrations — `V0_0_2__add_lineage.sql:1-7` + `V0_0_17__add_establisher_into_lineage.sql:1-2` + `V0_0_26__remove_length_constraints.sql` + `V0_0_79__data_deprecation.sql:11-12`). JOIN-side owner filtering at the lineage CTE is therefore structurally impossible without joining to data_entity → ownership. The CTE itself (`ReactiveLineageRepositoryImpl.java:163-175`) filters ONLY on `is_deleted = false`; there is no owner predicate in the seed or recursive step. When invoked from `LineageServiceImpl.getLineage` (the lineage-canvas read path), NO owner-scoping is applied at any layer. When invoked from `DataEntityRelationsServiceImpl.getDependentOddrns` (the `/my` lineage variants), owner-scoping is single-point-of-failure at the anchor set — see REFACTOR-237 (NEW companion) for the defence-in-depth gap. The triangulation is now: (a) controller layer (REFACTOR-203 origin — no owner argument), (b) service layer (no owner filter), (c) repository layer (no owner JOIN), (d) schema layer (no owner column on lineage). All four layers confirm the cross-owner enumeration vector at primary source.
  - **Statement**: The controller method calls `LineageService.getLineage(dataEntityId, depth, expandedEntityIds, DOWNSTREAM)` with no `Authentication`/`Principal` argument (`DataEntityController.java:256-262`); the service implementation does not consume the reactor `Context` for the current user (`LineageServiceImpl.java:87-122`) and the repository walk filters only by `LINEAGE.IS_DELETED.isFalse()` (`ReactiveLineageRepositoryImpl.java:167, 174`). The returned graph therefore contains every data entity reachable via the lineage edges, including entities the caller has no owner relationship to. Combined with REFACTOR-024 (getAllAlerts cross-owner exposure), REFACTOR-053 (getActivity), REFACTOR-187 (SearchController), and REFACTOR-200 (centerpiece detail read), lineage is the **graph-shaped cross-owner enumeration vector**: an authenticated caller can pivot from any one accessible entity to its full reachable subgraph across owner boundaries. The graph shape is materially wider than search because lineage edges encode causal connections — leaking the existence of a downstream transformer or consumer can reveal another team's internal pipeline structure even if the team's individual entities are not separately enumerable. VALIDATES REFACTOR-044 from earlier batch (which speculated on a lineage cap as the structural mitigation).
  - **Evidence**: `DataEntityController.java:255-263` (no owner argument) + `LineageServiceImpl.java:87-122` (no owner filter) + `ReactiveLineageRepositoryImpl.java:122-176` (no owner column in lineage table; filter is `IS_DELETED.isFalse()` only) + (NEW 2026-05-19H) `V0_0_2__add_lineage.sql:1-7` + `V0_0_17__add_establisher_into_lineage.sql:1-2` + `V0_0_79__data_deprecation.sql:11-12` (the schema migrations that confirm the absence of an owner column)

Option (a) aligns with ADR-CANDIDATE-003's resolution.
