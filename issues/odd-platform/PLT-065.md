## What

`AuthIdentityProviderImpl.java:31-33` emits `new UserDto(username, null)` for any auth mode that isn't an `OAuth2AuthenticationToken` (i.e. LOGIN_FORM, LDAP, DISABLED, S2S all carry a `null` provider; only OAUTH2 carries the registration id at `:30`). Four LEFT JOIN sites in `ReactiveActivityRepositoryImpl.java` (the `.leftJoin(USER_OWNER_MAPPING).on(...)` at lines 156-158, 177-179, 198-200, 219-221) join `USER_OWNER_MAPPING ON OIDC_USERNAME = ACTIVITY.CREATED_BY AND DELETED_AT IS NULL` - **provider-AGNOSTIC**.

The asymmetry is the load-bearing fact and it is internal to the codebase: the platform's own canonical owner-lookup, `ReactiveUserOwnerMappingRepositoryImpl.getConditions` (`:116-127`), DOES discriminate by provider (`PROVIDER.eq(provider)` when set, else `PROVIDER.isNull()`), and `AuthIdentityProviderImpl.fetchAssociatedOwner` (`:50-53`) feeds it the provider. The activity-feed read joins are the only owner-resolution sites that drop that discriminant. So in a deployment that has ever run more than one provider with a colliding username (e.g. LOGIN_FORM 'alice' and a later LDAP-imported 'alice'), the activity feed can attach the wrong OwnerPojo, and if both `alice` rows are un-deleted the LEFT JOIN can duplicate the activity row.

## User-facing impact

RUNTIME-ONLY for the bleed observable; the JOIN asymmetry is CODE-SETTLED.

- **JOIN asymmetry (verified-trace, static):** the four activity-feed joins omit the provider predicate that the canonical owner lookup uses - confirmed by reading `ReactiveActivityRepositoryImpl.java:156-221` against `ReactiveUserOwnerMappingRepositoryImpl.java:116-127`. This is a code-settled inconsistency that needs no running stack.
- **Bleed / row-duplication observable (static-not-driven; manifests under multi-provider deployments):** "the activity feed shows the wrong owner / duplicates a row for same-named users" requires a deployment that has populated `USER_OWNER_MAPPING` rows for the same `oidc_username` under two different `provider` values (e.g. switched LOGIN_FORM -> LDAP, or runs OAUTH2 + S2S, keeping both mapping rows un-deleted). Under a single-provider deployment - and under the default `auth.type=DISABLED` (`application.yml:34`), where there is one synthetic identity - the collision cannot arise, so nothing manifests. Not driven in this workspace; remaining check = seed two un-deleted `USER_OWNER_MAPPING` rows for one username under different providers, open the activity feed, observe wrong/duplicated OwnerPojo.

## Why it matters

For incident-response operators auditing "who did X at time T" in a multi-provider deployment, the activity feed can mis-attribute or duplicate. The bleed is silent - no error, just an inconsistent OwnerPojo display name - and is non-deterministic if the matching un-deleted mapping row differs. The fix aligns the read joins with the provider-aware lookup the rest of the platform already uses.

## Suggested fix

Add `AND PROVIDER = ?` to every LEFT JOIN to USER_OWNER_MAPPING. Schema migration optional (the bleed is purely a JOIN-condition issue). Pseudo-SQL pattern:

```sql
LEFT JOIN user_owner_mapping uom
  ON uom.oidc_username = activity.created_by
  AND uom.provider = ?    -- NEW: provider discriminant
  AND uom.deleted_at IS NULL
```

The `?` is bound at query time from the AuthIdentityProvider - for LOGIN_FORM and LDAP this is the literal mode name; for OAUTH2 it's the provider-id. For DISABLED the provider is NULL (no need to JOIN at all - synthetic admin).

For S2S filter - the entry is `null`-provider per AuthIdentityProviderImpl.java:32; a separate JOIN with `provider IS NULL` is needed to maintain backward compatibility with existing S2S-created activity rows.

Verification path: write integration test that creates 2 USER_OWNER_MAPPING rows for `alice` in different providers, then asserts that activity-feed rendering returns distinct OwnerPojo display names.
