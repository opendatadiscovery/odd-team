- **DOC-GAP-125**: AlertManager webhook's `ExternalAlert.startsAt` field is declared `LocalDateTime` (timezone-naive — `ExternalAlert.java:14`) while AlertManager's standard payload carries RFC3339 timezone-aware timestamps; Jackson's default `LocalDateTime` deserialisation silently strips the offset; `AlertServiceImpl.java:162-172` reads `externalAlert.getStartsAt().format(ALERT_MANAGER_TIME_FORMATTER)` (pattern `yyyy-MM-dd HH:mm:ss`, line 67-68) and uses the result in the `g0.moment_input` / `g0.end_input` query parameters of the embedded generator URL — the URL embedded in the chunk description points to a Prometheus query window keyed by the SERVER's local time, not the alert's actual timestamp; operators clicking the link may see no data because the query window is off (MEDIUM)

  - **Surfaced by**:
    - `odd-platform__java__service__service__AlertServiceImpl.md:bugs_limitations_corner_cases.[7]` (MEDIUM — ExternalAlert.startsAt is LocalDateTime timezone-naive) **(NEW batch I)**

  - **Evidence**:
    - `ExternalAlert.java:14` — verbatim field declaration: `private LocalDateTime startsAt;`. The type is `LocalDateTime` — JDK's timezone-naive timestamp type. Jackson's default deserialisation of an RFC3339 string into `LocalDateTime` strips the offset silently (no warning, no exception).
    - `AlertServiceImpl.java:67-68` — verbatim formatter declaration: `private static final DateTimeFormatter ALERT_MANAGER_TIME_FORMATTER = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");`. The format has NO timezone component; the formatted string is interpreted by AlertManager / Prometheus as local-to-the-SERVER time.
    - `AlertServiceImpl.java:162-172` — verbatim usage chain: `final String startsAt = externalAlert.getStartsAt().format(ALERT_MANAGER_TIME_FORMATTER); final URI uri = UriComponentsBuilder.fromUri(externalAlert.getGeneratorURL()).queryParam("g0.moment_input", startsAt).queryParam("g0.end_input", startsAt).build().toUri(); ... chunkPojo.setDescription(String.format("Distribution Anomaly. URL: %s", uri));`.
    - **The operator-visible consequence**:
      - AlertManager fires an alert at 2026-05-19T14:30:00+00:00 (UTC).
      - ODD platform server runs in UTC; collector deserialises `startsAt` to `LocalDateTime.of(2026, 05, 19, 14, 30, 0)`.
      - Formatter produces `"2026-05-19 14:30:00"`.
      - URL embedded in description: `https://prometheus.example.com/graph?...&g0.moment_input=2026-05-19 14:30:00&...`.
      - Operator viewing ODD UI in a different timezone (e.g. PT, UTC-7) sees the chunk description's URL; clicks it; Prometheus interprets `2026-05-19 14:30:00` as LOCAL-TO-PROMETHEUS time which may be UTC-7 → the query window is 7 hours off from the alert's actual time. Operator sees an empty Prometheus graph; investigation fails.
      - The same failure mode hits the reverse case: ODD server in non-UTC, Prometheus in UTC — the LocalDateTime represents the ODD-server's interpretation of the original RFC3339 string, which may differ from both Prometheus and the operator's locale.
    - **The fix is one type change**: change `ExternalAlert.startsAt` to `OffsetDateTime` (timezone-aware); update `ALERT_MANAGER_TIME_FORMATTER` to include an offset component (e.g. `yyyy-MM-dd'T'HH:mm:ssXXX`); the embedded URL then carries the correct timezone-anchored timestamp. Backwards-compatibility: the change accepts strict RFC3339 input from AlertManager (its default output format) and produces a more-strict embedded-URL format. Existing alerts with pre-existing LocalDateTime-formatted URLs would not be affected (they're already stored).
