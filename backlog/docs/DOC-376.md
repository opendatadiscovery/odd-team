## Description

The ingestion ingress (`POST /ingestion/entities`, the `postDataEntityList` operation) is **fully synchronous** — there is no `202 Accepted`, no queue, and no status/poll endpoint. The controller returns `ResponseEntity.ok()` (HTTP 200) only **after** the entire ingestion pipeline has run to completion inside the request transaction, and the service method is `@ReactiveTransactional`, so the persist + processor-chain + metric-export work all execute inline on the request before the 200 is emitted.

The operator consequence is undocumented: **the caller (collector or push-adapter) must size its HTTP client read-timeout to the platform's worst-case per-batch processing time**, not to a generic "fast API" budget. A large batch, or a batch that lands on a contended data source (which already serialises on a `SELECT … FOR UPDATE` row-lock for the whole pipeline duration — see `integrations/README.md:151`), can hold the request open for the full processing window. A read-timeout sized for a typical REST call will abort mid-ingest; because there is no idempotency-status endpoint to poll, the caller cannot distinguish "timed out but the platform committed" from "timed out and nothing landed" without re-sending (the upsert is ODDRN-keyed and idempotent per ADR-0073, so a re-send is safe, but the caller has to know that).

`integrations/README.md:151` already documents the per-data-source contention/serialisation half (no `Retry-After`, no `429`, recommend client backoff with jitter) but does **not** state the sync-no-202 model or give read-timeout-sizing guidance. SPC-003 names the timeout only for the spec-side error schema, and DOC-195 does not cover this. This item documents the sync model + the read-timeout-sizing rule as one operator-facing caveat, homed next to the existing contention note so the whole "what to expect on the wire from the ingestion endpoint" story lives in one place.
