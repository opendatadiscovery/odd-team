## Description

The notification channel endpoints (Slack incoming-webhook URL, generic webhook URL) and the email recipient list are bound **once at JVM boot** via constructor `@Value` injection on the sender beans, and there is **no runtime reload path**. The docs already state that the *feature toggle* (`notifications.enabled`) is "captured at JVM boot and frozen for the lifetime of the process" (odd-platform.md:440), but they say nothing about the **endpoints and recipients** carrying the same boot-immutable property.

How this misleads an operator: if a Slack/webhook URL leaks (these incoming-webhook URLs are bearer secrets — anyone holding the URL can post into the channel) or a recipient must be removed, the operator may reasonably assume they can update `notifications.receivers.slack.url` / `notifications.receivers.webhook.url` / `notifications.receivers.email.notification.emails` and have it take effect — for example via a Spring Boot Actuator `/refresh`, which is the idiomatic mechanism for re-binding `@Value`-backed config. It will not take effect. The platform does **not** wire `@RefreshScope` on the sender beans and does **not** expose an Actuator refresh endpoint, so a `/refresh` (even if one were added) would not re-bind these constructor-injected values. The only way to rotate a leaked URL or change recipients is a **full JVM restart**. During the window between leak and restart the old URL stays live.

This is operability-doc work only (caveat text); no code change. PLT-068 is unrelated.

## Context

Source feature: **F-009** (notifications). Surfaced by the 2026-06-08 contradiction-harvest.

Canonical code truth (read and confirmed):
- `NotificationConfiguration.java:104` — the email sender bean takes `@Value("${notifications.receivers.email.notification.emails}") final String notificationEmails` as a **constructor parameter**, and the recipient list is materialised once at construction: `List.of(notificationEmails.trim().split(","))` (line 118). Constructor-injected `@Value` is bound at bean-creation time and never re-read.
- The same file binds the channel URLs the same way: `slackNotificationSender` takes `@Value("${notifications.receivers.slack.url}") final URI slackWebhookUrl` (line 77) and `webhookNotificationSender` takes `@Value("${notifications.receivers.webhook.url}") final URI webhookUrl` (line 91) — both constructor params, both frozen at boot.
- No runtime-reload path exists: a repo-wide search for `@RefreshScope`, an Actuator `refresh` endpoint, or `spring-cloud-context` runtime wiring under `odd-platform-api/src/main/` returns nothing. (The `spring-cloud-dependencies` BOM is imported in `odd-platform-api/build.gradle:74`, but `@RefreshScope` is not used anywhere, so no bean re-binds on config change.)

Related (cross-link, do not duplicate): the existing `notifications.enabled` boot-immutability note (odd-platform.md:440) and the silent-partial-delivery recipient caveat (notifications.md:59) are about *different* properties of the same subsystem; this item adds the missing endpoint/recipient mutability dimension and should cross-reference both rather than restate them.
