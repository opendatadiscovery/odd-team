## ⚠️ VERIFICATION 2026-06-08 — CLARIFY before implementing

> **Adversarial fact-check (sev MEDIUM).** LOGIN_FORM<->LDAP does NOT orphan (both provider=null) — orphaning is OAUTH2-target-specific. Title/Description over-state; the item self-corrects in Notes line 60. Scope the runbook to provider-tuple-changing transitions; state LOGIN_FORM<->LDAP needs no backfill.
>
> Full report: `lineage/odd-platform/harvest/2026-06-08-doc-verification.md`.

## Description

When a deployment switches `auth.type` from `LOGIN_FORM` to `OAUTH2` (or `LDAP`), **every existing user-owner mapping is silently orphaned** — not because of a name collision between two different users, but because the *same* user's identity tuple changes underneath their existing mapping.

The platform keys owner associations on a compound `(OIDC_USERNAME, PROVIDER)` tuple. Under `LOGIN_FORM` (and `LDAP`), a login produces `UserDto(username, provider=null)`, so `alice`'s mapping row is stored as `(alice, null)`. After switching to `OAUTH2`, the same person signs in via, say, GitHub and the platform produces `UserDto(alice, "github")`. The owner lookup builds its WHERE clause as `OIDC_USERNAME = 'alice' AND PROVIDER = 'github'` — which does **not** match the stored `(alice, null)` row (the null-provider branch and the named-provider branch are mutually exclusive). The result: `alice`'s **My Objects** goes empty, her ownership is stranded, alerts/personalised tabs render nothing — and the platform emits no warning, because from its perspective `(alice, github)` is simply a brand-new identity with no mapping yet. The same happens for **every** pre-migration user at once.

How this misleads an operator: nothing in the docs warns that a migration *between* modes invalidates the existing `USER_OWNER_MAPPING` rows wholesale, and there is **no runbook** for the only safe path — backfilling the `PROVIDER` column on the existing rows to the value the new mode will present (the OAuth2 client registration id for OAUTH2; the agreed sentinel/provider value for LDAP) before or during the cutover. An operator who has spent weeks letting users self-associate under `LOGIN_FORM` will lose all of it on the switch with no recovery guidance.

This is **distinct** from the three existing caveats and must not restate them:
- **DOC-312** (done) — GitHub *login rename* orphans one user's `(alice, github)` mapping. Single-user, intra-OAUTH2, rename-driven. Not a mode switch.
- **DOC-245 / DOC-272** — cross-mode *collision*: two **different** same-named users (`alice`@LOGIN_FORM and `alice`@LDAP) both stored with empty provider resolve to the same `OwnerPojo` in activity-feed reads (a read-path bleed). That caveat's mitigation is "don't reuse usernames / delete LOGIN_FORM rows to avoid collisions." DOC-362 is the inverse concern: the *same* user's mapping must **survive** the switch, which needs a positive backfill procedure, not a deletion.

## Context

Source features: **F-011** (compound-key `(username, provider)` silent in docs) and **F-124** (auth-mode migration). Surfaced by the 2026-06-08 contradiction-harvest.

**DEDUP — F-124 / H-010 (LDAP migration) is the same class, probe-routed:** the LDAP-migration hypothesis is the same orphaning mechanism with `LDAP` as the target mode; this one item carries the whole class (LOGIN_FORM→OAUTH2 **and** LOGIN_FORM→LDAP, and the symmetric LDAP↔OAUTH2 case) so the fix + review close it in one pass. Do not file a separate LDAP-migration doc item.

Canonical code truth (read and confirmed):
- `AuthIdentityProviderImpl.java:29-33` — `getCurrentUser()` returns `new UserDto(username, oauthToken.getAuthorizedClientRegistrationId())` for an `OAuth2AuthenticationToken`, else `new UserDto(username, null)`. So `LOGIN_FORM`/`LDAP` logins carry `provider = null`; OAUTH2 carries the client registration id.
- `ReactiveUserOwnerMappingRepositoryImpl.java:116-127` — `getConditions(oidcUsername, provider)` always adds `OIDC_USERNAME.eq(...)`, then adds `PROVIDER.eq(provider)` when provider is non-empty **else** `PROVIDER.isNull()`. The two branches are mutually exclusive, so a stored `(alice, null)` row is never returned by an `(alice, "github")` lookup — confirming the wholesale orphaning at a mode switch. `getAssociatedOwner` (lines 76-85) drives the user's owner resolution through exactly this `getConditions`.

Related (cross-link, do not duplicate): user-owner-association.md already documents that "Provider is not always a reliable discriminator" because LOGIN_FORM/LDAP share an empty provider — link the new runbook from there. The existing collision caveats (login-form.md, ldap.md) and DOC-312 (GitHub rename) cover adjacent-but-distinct failure modes as detailed in the Description.

**Paired upstream fix:** **PLT-173** (`issues/odd-platform/PLT-173.md`) — "carry a real provider for LOGIN_FORM/LDAP" so `(username, provider)` is unique per real identity source; its own body notes "a migration/runbook will be needed to backfill the provider column for existing `provider = null` mappings." This DOC item is that runbook, shipping now on the doc side; PLT-173 is the code-side fix handed off upstream (same work-vs-handoff split as DOC-312 ↔ PLT-111).
