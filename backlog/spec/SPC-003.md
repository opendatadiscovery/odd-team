## Description

Only **3 of 194 operations** declare any `4xx`/`5xx` response, and there is no shared `ErrorResponse` component schema (F-029/H-002). SDK consumers generated from the spec therefore have no typed error model — they cannot distinguish a retryable failure (5xx, 429) from a non-retryable one (400/403/404), and every error surfaces as an untyped body. This is the structural reason the ingestion error-contract surfaces (F-096/H-008 synchronous-no-202 posture; F-095/H-010/H-011 unknown-field / empty-body asymmetry) have no typed shape to map onto.

This is a natural sibling to SPC-001 (which adds `securitySchemes` + reconciles 201-vs-200 across 7+ controllers + renames the legacy title) on the same `openapi.yaml` hygiene branch, but is a DISTINCT facet — SPC-001 does not add an error schema or operation-level error coverage.

## Acceptance Criteria
- [ ] A shared `ErrorResponse` schema is added to `components.yaml` modelling the platform's actual error body (verify the runtime `@ControllerAdvice` / error DTO shape: code like `USR001`/`USR003`, message, status — read the platform `ControllerAdvice` before authoring).
- [ ] Operation-level `responses` for the common error statuses (`400`, `401`, `403`, `404`, `500`; `429` where rate-limited) are added — at minimum on the high-traffic ingestion + CRUD operations — each `$ref`-ing the shared `ErrorResponse`.
- [ ] The `ErrorResponse` schema documents the `code` field's meaning (e.g., `USR003` = duplicate name) so SDK consumers can branch on it (ties to DOC-333's USR003/400-on-collision contract).
- [ ] Cross-cutting: once the spec lands, the platform's vendored copy needs sync via the spec release/vendor channel.
- [ ] Live-side verification: load `/api/v3/api-docs` locally and confirm the error responses + schema render in Swagger UI.
