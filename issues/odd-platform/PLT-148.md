## What

Under `auth.type=DISABLED` - the posture the docs recommend for evaluation / single-user / local deployments - **every owner-association write endpoint returns HTTP 500 `SYS001` and performs no write.** The four affected endpoints are the entire write surface of the Management -> Associations UI plus the home-page self-request form:

| Endpoint | UI surface | Live result under DISABLED |
|---|---|---|
| `POST /api/owner_association_request` | home self-request form (F-142) | **500** (no `owner_association_request` row) |
| `PUT /api/owner_association_request/{id}` | Pending tab Accept/Reject (F-171) | **500** (request status unchanged, no `user_owner_mapping`) |
| `POST /api/owners/mapping` | header "Create association" (F-172) | **500** (no `user_owner_mapping` row) |
| `DELETE /api/owners/mapping/{owner_id}` | Active tab Remove (F-173) | **500** (mapping not soft-deleted) |

The READ surface is unaffected - `GET /api/owner_association_request` (Pending/Active lists) and `GET /api/owner_association_request/activity` (History tab) return 200. So the operator sees the three tabs populate normally, sees the Accept / Reject / Remove / Create buttons rendered and enabled (the synthetic admin has every permission), clicks one, and gets a silent 500. The UI surfaces no actionable error.

## Root cause

`OwnerAssociationRequestServiceImpl` resolves the acting user via `AuthIdentityProviderImpl.getCurrentUser()`, which reads the reactive security context and has no fallback:

```java
// AuthIdentityProviderImpl.java:24-35
public Mono<UserDto> getCurrentUser() {
    return ReactiveSecurityContextHolder.getContext()
        .map(SecurityContext::getAuthentication)
        .map(authentication -> { ... });   // empty Mono when there is no SecurityContext
}
```

Under DISABLED auth, `DisabledAuthSecurityConfiguration` builds a filter chain that only does `anyExchange().permitAll()` - it installs **no anonymous `Authentication`**:

```java
// DisabledAuthSecurityConfiguration.java:13-18
return http
    .csrf(ServerHttpSecurity.CsrfSpec::disable)
    .authorizeExchange(spec -> spec.anyExchange().permitAll())
    .build();
```

So `ReactiveSecurityContextHolder.getContext()` is empty, `getCurrentUser()` emits empty, and every service method that does `getCurrentUser().switchIfEmpty(Mono.error(() -> new RuntimeException("There is no current authorization")))` throws. The throw sites observed live (2026-06-07):

- `OwnerAssociationRequestServiceImpl.java:55-56` (create)
- `OwnerAssociationRequestServiceImpl.java:92-93` (triage update)
- `OwnerAssociationRequestServiceImpl.java:134-135` (createManualAssociationRequest, reached by direct-bind)
- `OwnerAssociationRequestServiceImpl.java:158-159` (cancelAssociationByOwnerId, reached by direct-bind + remove)

The reason the platform *looks* like it has an `admin` user is a **separate, controller-local fallback** that masks this everywhere except these write paths:

```java
// IdentityController.java:24-31
public Mono<ResponseEntity<AssociatedOwner>> whoami(final ServerWebExchange exchange) {
    return identityService.whoami()
        .map(ResponseEntity::ok)
        .switchIfEmpty(Mono.just(new ResponseEntity<>(dummyOwner(), HttpStatus.OK)));  // synthetic admin w/ all perms
}
```

`whoami` returns a synthetic `admin` with all permissions, so the SPA renders every affordance as enabled - but no equivalent fallback exists in `AuthIdentityProvider`, so the moment a write needs the current user, it 500s. The inconsistency between the two layers is the trap: the UI is told "you are admin, you can do everything", the write layer is told "there is no current authorization".

## User-facing impact

**Verified-trace end-to-end** (auth mode: `auth.type=DISABLED`), 2026-06-10. The write affordances DO render enabled for the synthetic admin, and the writes DO 500 - both halves confirmed against the running stack and the FE source:

- **BE 500 is runtime-driven.** All four throw sites are code-settled (`OwnerAssociationRequestServiceImpl.java:55-56,92-93,134-135,158-159`, `getCurrentUser().switchIfEmpty(error(...))`); `getCurrentUser()` (`AuthIdentityProviderImpl.java:24-35`) reads `ReactiveSecurityContextHolder` with no fallback; `DisabledAuthSecurityConfiguration.java:13-18` installs no anonymous `Authentication`; the resulting `RuntimeException` falls to `ControllerAdvice.java:61-66` (`Exception.class` -> 500 SYS001). IT-105 drove `POST /api/owner_association_request` -> 500 + no row written, live (:18080, 3/3 pass, in the passing feature-complete suite); IT-106/107/108 pin the other three writes the same way.
- **The buttons render enabled because the synthetic admin holds every permission.** `IdentityController.whoami` (`:24-31`) returns `dummyOwner()` with `Permission.values()` (ALL permissions) when the security context is empty - i.e. exactly under DISABLED. The FE stores these as `globalPermissions` (`PermissionProvider.tsx:17`, fed from whoami). The gate `getHasAccessTo(to) = [...globalPermissions, ...resourcePermissions].includes(to) && allowedPermissions.includes(to)` (`PermissionProvider.tsx:27-31`) therefore passes for the owner-management permissions, so: the header **"Create association"** button (`OwnerAssociationsHeader.tsx:29-39`, gated `Permission.OWNER_RELATION_MANAGE` via `WithPermissions`) renders; the Pending **Accept/Reject** buttons (`NewAssociationRequest/NewAssociationRequest.tsx:84,...`, `hasAccessTo(Permission.OWNER_ASSOCIATION_MANAGE)`) render enabled; the Active **Remove** button (`ActiveAssociationRequest/ActiveAssociationRequest.tsx:91`, `hasAccessTo(Permission.OWNER_ASSOCIATION_MANAGE)`) renders enabled; the home self-request form (`Overview/OwnerAssociation/OwnerAssociationForm`, `useCreateOwnerAssociationRequest`) submits. Each click then hits the BE 500 above with no actionable error.

Net operator experience under DISABLED: every owner-association write surface looks fully available and silently fails. (NOTE: PLT-040, referenced below, separately observes the Remove button gates on `OWNER_ASSOCIATION_MANAGE` in the UI but `OWNER_RELATION_MANAGE` in the backend - a distinct permission-name mismatch, independent of this 500 and not material under DISABLED where the synthetic admin holds both.)

## Why it matters

This is the LSN-001/LSN-002 failure class: a feature that works in the maintainer's OAUTH2/LDAP test deployment but is silently broken in the posture an operator reaches first. An evaluator running DISABLED auth who tries to bind a user to an owner - via the prominent "Create association" button, or the home-page self-request form - hits a 500 with a generic "Internal Server Error" and no path forward. The owner-association feature is effectively undocumented-as-DISABLED-incompatible, and nothing guards it (the feature-flows showed F-172/F-173/F-142 all at 0 verified promises). The two LSN-001/002 cases shipped under "medium / undocumented feature"; this is the same shape - the operator follows the UI off a cliff with our name on it.

There is also an **audit-consistency** angle: the only operator-visible audit trail (History tab) can never record a direct-bind/unbind/triage event under DISABLED, because those events can never successfully occur.

## Suggested fix

Two viable directions; the first is preferred:

1. **Install an anonymous principal under DISABLED auth** so `ReactiveSecurityContextHolder` resolves a stable system identity (e.g. `admin` / no provider) - mirror what `whoami`'s `dummyOwner()` already pretends exists. This makes the whole write surface consistent with the read surface and with the UI's "you are admin" claim, and is the smallest behavioural change that makes DISABLED a fully-functional single-user posture. Add an `AnonymousAuthenticationWebFilter` (or equivalent) to `DisabledAuthSecurityConfiguration`.

2. **Give `AuthIdentityProvider.getCurrentUser()` a DISABLED-mode fallback** that returns the same synthetic identity `IdentityController.dummyOwner()` uses, centralising the fallback so the two layers agree.

Whichever is chosen, the `dummyOwner()` fallback in `IdentityController` should be reconciled with it so there is exactly one definition of "who the user is under DISABLED auth".

If the *intended* design is that owner-association is OAUTH2/LDAP-only, then the endpoints must fail closed with a clear `400/409` + an operator-readable message ("owner association requires an authentication provider; not available under auth.type=DISABLED"), the UI must hide/disable the affordances under DISABLED, and the docs must state it - not a generic 500.

## How discovered

Surfaced while authoring the IT-105..IT-110 e2e suite for the Owner-Association management cluster against the live odd-minimal stack. Every write probe returned 500; the container log pinpointed `getCurrentUser().switchIfEmpty(...)` as the throw site, and reading `DisabledAuthSecurityConfiguration` + `IdentityController.whoami` revealed the read/write fallback asymmetry. The e2e specs IT-105/106/107/108 characterization-pin the current 500 (GREEN now, RED the instant the write path starts succeeding) so the fix is caught the moment it lands.
