## What

The activity-feed query joins the tag and owner association tables to support the `tag_ids` and `owner_ids` filters, but it never de-duplicates the result. When a caller supplies **both** filters (or any filter against a one-to-many relation where an entity carries several matching rows), the `LEFT JOIN` multiplicity produces the same activity event N×M times — identical id, timestamp, payload and actor — once per matching (tag, owner) pair. The feed renders each duplicate as a separate row, and because the query is also `LIMIT`-bounded by `size`, the duplicates consume slots that should hold distinct events, so a page can silently show fewer real events than its size suggests.

## Where

The joins are added per-filter — both `tagIds` and `ownerIds` add a separate `leftJoin` against a one-to-many association table:

`odd-platform-api/.../repository/reactive/ReactiveActivityRepositoryImpl.java:237-242`
```java
        if (CollectionUtils.isNotEmpty(tagIds)) {
            query.leftJoin(TAG_TO_DATA_ENTITY).on(TAG_TO_DATA_ENTITY.DATA_ENTITY_ID.eq(DATA_ENTITY.ID));
        }
        if (CollectionUtils.isNotEmpty(ownerIds)) {
            query.leftJoin(OWNERSHIP).on(OWNERSHIP.DATA_ENTITY_ID.eq(DATA_ENTITY.ID));
        }
        return query;
```

The final query orders and limits but applies **no `DISTINCT`** and no pre-aggregation of the join rows back to one row per activity:

`odd-platform-api/.../repository/reactive/ReactiveActivityRepositoryImpl.java:290-294`
```java
        final var finalQuery = baseQuery.where(conditions)
            .orderBy(ACTIVITY.CREATED_AT.desc(), ACTIVITY.ID.desc())
            .limit(size);
        return jooqReactiveOperations.flux(finalQuery)
            .map(this::mapDto);
```
Each row is mapped 1:1 to an `ActivityDto` (`mapDto`, line 304), so every duplicated join row becomes a duplicated feed entry. An entity tagged with 3 of the requested tags and owned by 2 of the requested owners surfaces its activity event 3×2 = 6 times.

## Why it matters

The defect is silent and intermittent — it only manifests when a caller combines filters or when an entity has multiple matching associations, which is exactly the "narrow it down" path a power user takes. The result is a feed that double-counts (or N-counts) recent activity: the same "dataset updated" or "owner assigned" event appears several times in a row, eroding trust in the feed as an audit surface, and — combined with the `LIMIT` — pushing genuinely older-but-distinct events off the page. No data is corrupted, but the displayed history is wrong. Medium severity: a correctness/UX defect on a read-only surface, reachable by any authenticated caller using the documented multi-filter UI.

## Suggested fix

Make the query return one row per activity event regardless of join multiplicity. The minimal change is to add `DISTINCT` to the select; the more robust change (preferred if the projection includes columns from the joined tables) is to pre-aggregate — restructure the tag/owner predicates as `EXISTS` subqueries (or `IN (SELECT ...)`) so the association tables filter without fanning out the row count. Open to alternatives, but the fix must hold for the both-filters-set case, which is the only case current tests do not cover.

**How to verify:** with both `tag_ids` and `owner_ids` set against an entity that matches several of each, each activity event appears exactly once in the response — a repository test seeding multi-tag/multi-owner data and asserting no duplicate event ids.

## How discovered

Surfaced during a product-owner review of the activity feed. The existing tests exercise single-filter activity queries only, so the fan-out — which requires two filters simultaneously — was never observed by a test. Scope note: this is result *correctness* under multi-filter, distinct from the unrelated unbounded-`size` clamp on the same endpoint (they touch adjacent lines but address different defects).
