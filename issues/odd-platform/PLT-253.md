## What

PR #1864 made manual term-to-term links symmetric so a link is visible and removable from either term's
page. It does this with a derived table, `symmetricTermRelations()`, defined as

```
SELECT assigned_term_id, target_term_id, is_description_link FROM term_to_term
UNION ALL
SELECT target_term_id, assigned_term_id, is_description_link FROM term_to_term
WHERE is_description_link = false
```

i.e. every row, plus a mirrored copy of each manual row. That is correct when a pair is stored ONCE.
It double-counts when the same pair is stored in BOTH orientations, which the schema allows and the
pre-#1864 UX actively encouraged.

`term_to_term` has `PRIMARY KEY (target_term_id, assigned_term_id)`, so `(X, Y)` and `(Y, X)` are two
distinct, legal rows. `linkTermWithTerm` inserts without checking for the reverse row. And before #1864
a link created on X's page did not appear in Y's Overview TERMS panel at all -- so an operator who
wanted it there would simply add it again from Y, creating the second row. Existing deployments are
therefore likely to already carry such pairs, and #1864 makes them visible as duplicates on upgrade.

With both rows present, the derived table yields the counterpart twice for the Overview join
(`target_term_id = X`), and `jsonArrayAgg` is not `DISTINCT`, so the term is emitted twice. The badge
uses `countDistinct` and still reports 1.

## User-facing impact

On a term whose link to another term happens to be stored in both orientations, the Overview TERMS panel
lists that term twice, while the "Linked terms" tab badge counts it once. The operator sees a duplicated
chip and a count that disagrees with what is on screen -- the same "backend duplicates vs de-duplicated
count" confusion class as PLT-176. Removing the link clears both rows (the #1864 delete matches either
orientation), so the state is recoverable, but the duplicate is visible until then.

The "Linked terms" TAB is NOT affected: its query groups by the term's own columns, so the duplicate rows
collapse. Only the Overview panel and its disagreement with the badge are visible.

## How to reproduce

1. Create two terms, X and Y.
2. On X's page: Overview -> TERMS -> Add term -> pick Y.
3. On Y's page: Overview -> TERMS -> Add term -> pick X.
   (Post-#1864 the link is already shown there, so this is the deliberate-double-add path. Pre-#1864 it was
   NOT shown, which is how existing data acquired both rows.)
4. Open X's page: the TERMS panel lists Y twice; the "Linked terms" tab badge reads 1.

The mechanism was proven by executing the merged query shape (the `UNION ALL` derived table, the
`target_term_id` join, the non-distinct array aggregate, and the `countDistinct` badge) over a two-term
fixture: one stored orientation yields panel `["Y"]` / badge `1`; both orientations yield panel
`["Y","Y"]` / badge `1`; a description link stays directional and is not mirrored.

## Suggested fix

Three parts -- the first alone removes the visible defect:

1. **De-duplicate the derived table.** Use `UNION` instead of `UNION ALL` in `symmetricTermRelations()`
   (or `SELECT DISTINCT` over the union). The mirrored copy of `(X, Y)` is then absorbed by the stored
   `(Y, X)` row rather than added to it.
2. **Guard the write.** `linkTermWithTerm` should treat an existing link in EITHER orientation as
   already-linked (no-op, or `400` in the style of "Term already assigned to data entity" at
   `TermServiceImpl.java:174`), so no new both-orientation pairs are created.
3. **Clean existing data.** A migration that collapses each duplicated manual pair, keeping one row.
   Sketch (must exclude description links, which are legitimately directional):

```sql
DELETE FROM term_to_term a
USING term_to_term b
WHERE a.is_description_link = false
  AND b.is_description_link = false
  AND a.target_term_id   = b.assigned_term_id
  AND a.assigned_term_id = b.target_term_id
  AND a.target_term_id   > a.assigned_term_id;
```

Add a regression test for the both-orientations case: #1864's `TermRepositoryTest` covers
count/soft-delete, symmetry, remove-from-either-side and description-link directionality, but not a pair
stored twice.

## Notes (adjacent, not part of this bug)

- `symmetricTermRelations()` replaces a direct table reference in the term-detail query (which already
  carries a large join fan-out), in the term LIST query `findByState`, and in `listByTerm`. `term_to_term`
  has no index on `assigned_term_id` alone (the PK leads with `target_term_id`), so that join was already
  unindexed; the union doubles a scan that was already sequential. At glossary scale this is a constant
  factor, not a new problem -- noted here so it is weighed if the term pages ever get slow.
- `term_to_term.deleted_at` exists in the schema but has no readers or writers: term relations are hard
  deleted. Vestigial column, unrelated to this bug.
