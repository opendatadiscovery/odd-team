## Description

Assigning an Owner role ("title") on a data entity resolves the title name through a **read-then-insert** helper: `getByName(name)` and, if nothing comes back, `create(new TitlePojo().setName(name))`. There is no `INSERT ... ON CONFLICT` — the check and the insert are two separate statements. When two operators (or two concurrent requests) create an ownership grant naming the **same brand-new title** at the same time, both reads miss, both attempt the insert, and the second insert violates the `title_name_unique` partial unique index on `title(name)`.

Because the title creation runs inside the ownership-create transaction (`OwnershipServiceImpl.create` is `@ReactiveTransactional`), the constraint violation does **not** just fail the title insert — it **rolls back the entire ownership grant**. The operator's "add owner" action returns an opaque **HTTP 400 with error code USR003** (`UNIQUE_CONSTRAINT`) and the ownership is not recorded, even though the title name they chose is perfectly valid and now exists. A retry succeeds (the title now resolves via `getByName`), so the failure is transient and self-correcting, but the error surface gives no hint that a concurrent first-use of a new title was the cause. This is undocumented; an operator hitting it during a bulk-ownership or scripted-assignment run sees a baffling 400 on a valid request.

  - The opaque code — `ErrorCode.java:11`: `UNIQUE_CONSTRAINT("USR003", false, true)` is the error returned on the constraint violation.
