## What

The collector token contract has three operator-critical properties the documentation does not surface (it frames regeneration as a benign recovery action and tells operators to copy/use the token without caveat):

1. **Regeneration is an in-place UPDATE with NO grace window.** `regenerateToken` mutates the SAME `token` row - `ReactiveTokenRepositoryImpl.updateToken` runs `UPDATE token SET value=<new> WHERE id=<same id>` (`:30-39`), and `TokenGeneratorImpl.regenerate` (`:44-52`) overwrites `.setValue(...)` on the existing pojo - so there is no old/new token pair and no rotation-grace period. **Scope correction (verified 2026-06-10):** the resulting "running collector 401s immediately" consequence holds ONLY when the operator has set `auth.ingestion.filter.enabled=true` - that flag is `false` by DEFAULT (`application.yml:48`), so out of the box the collector token is never validated on `POST /ingestion/entities` at all (the `IngestionDataEntitiesFilter` bean is `@ConditionalOnProperty(havingValue="true")` and is not even instantiated). When the filter IS enabled, the filter compares the stored token (`IngestionDataEntitiesFilter.java:56-57`, `throw new AccessDeniedException` on mismatch), so the in-place UPDATE makes an already-running collector start failing on the next ingest the instant the UPDATE commits - ingestion stops until the collector is reconfigured and redeployed. The earlier "a running collector 401s immediately" framing was unconditional and is a backend-only overstatement for the default deployment.
2. **Token stored plaintext at rest; full plaintext returned on the create/regenerate response.** The `token.value` column is `varchar(40) NOT NULL` with no hashing (`V0_0_28__add_token.sql:4`). On create and on regenerate the response carries the FULL plaintext value (`TokenMapper.mapValue` returns the raw value when `dto.showToken()` is true, which `create`/`updateToken` both set, `ReactiveTokenRepositoryImpl.java:26,38`). Refinement: the collector-LIST endpoint masks it (`"******" + last-6`, `TokenMapper.java:15-18`), and the UI shows the masked form with a Regenerate button rather than the value (`CollectorItemToken.tsx:26,34-53`), so the plaintext exposure in transit is the create/regenerate response specifically; the durable concern is plaintext-at-rest.
3. **Rotation is NOT audit-logged.** No `@ActivityLog` (or any Activity-Feed write) on `regenerateCollectorToken` (controller `:48-50`), `CollectorServiceImpl.regenerateToken` (`:83-89`), or `TokenGeneratorImpl.regenerate` - verified absent 2026-06-10.

Sources: HARVEST-011, HARVEST-051, HARVEST-057 (doc-understanding harvest, 2026-05-29). Doc caveat tracked at `backlog/docs/DOC-292.md`.

## User-facing impact

**Verified trace; the user surface is the Management -> Collectors token panel and the (operator-driven) ingestion runtime.** This is an operator/credential finding, not a rendered-data bug:

- **In-place rotation - CONFIRMED.** The new value lands on the same `token.id` row (`ReactiveTokenRepositoryImpl.updateToken:35` `WHERE TOKEN.ID.eq(tokenPojo.getId())`); no second row, so no overlap window - a zero-downtime rotation is structurally impossible.
- **401-immediately - CONFIRMED BUT CONDITIONAL.** Only when `auth.ingestion.filter.enabled=true` (NOT the default). With the flag off - the shipped default - the old token was never being checked, so regeneration does not break a running collector; ingestion accepts any/no token. This conditionality is the key correction; the prior revision asserted the breakage unconditionally.
- **Plaintext - CONFIRMED, scoped.** At rest: `varchar(40)`, no hash (`V0_0_28:4`). In transit: full value only on the create/regenerate response (`TokenMapper.mapValue` + `showToken=true`); the list endpoint and the UI panel show `******`+last-6 (`TokenMapper.java:15-18`, `CollectorItemToken.tsx:26,34`). The regenerate action itself is RBAC-gated in the UI behind `Permission.COLLECTOR_TOKEN_REGENERATE` (`CollectorItemToken.tsx:36`).
- **Unaudited - CONFIRMED.** No `@ActivityLog` on the controller/service/generator path (verified absent).

Remaining check (not driven): an end-to-end run of "enable the filter, start a collector on token A, regenerate via UI, observe the next `POST /ingestion/entities` return 401/403" - the code path is settled (filter equality check + in-place UPDATE), but no probe/IT log for this exact sequence exists in the workspace.

## Why it matters

An operator who follows the docs' "you must regenerate it" recovery advice on a live deployment takes ingestion down without warning: every running collector 401s the instant the UPDATE commits, and ingestion stays broken until each collector is reconfigured and redeployed. There is no overlap window in which both tokens are valid, so a zero-downtime rotation is impossible with the current shape. Compounding it, the token is plaintext at rest and in transit-response and the rotation is unaudited - so a leaked backup exposes live credentials and there is no record of who rotated what. This is the LSN-002 class: the documented operation is a benign-looking action that breaks production.

## Suggested fix

- Introduce a rotation grace window: support a short-lived old/new token pair (accept both for a configurable overlap) so a running collector keeps ingesting while it is reconfigured - making zero-downtime rotation possible. At minimum, document that regeneration breaks active ingestion until redeploy.
- Hash the token at rest (store a hash, compare on the read side) and avoid returning it in plaintext beyond the single creation response; mask it in any actuator/log surface.
- Add an audit-log entry on token regeneration (who/when/which collector).
