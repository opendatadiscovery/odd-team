# ReactiveTermRepositoryImpl — semantic understanding

## understanding

`ReactiveTermRepositoryImpl` is the **persistence-tier hub** for ODD Platform's Business Glossary (pillar P-06 per `system-mission.md` lines 182-198) — 656 lines, 15 public methods implementing `ReactiveTermRepository` plus the inherited soft-delete CRUD from `ReactiveAbstractSoftDeleteCRUDRepository`. It owns every read of the `term` table (single-row lookups, paginated lists, FTS-ranked suggestions, faceted search), the cross-table aggregations that assemble `TermDetailsDto` (term + namespace + owners + titles + tags + assigned-terms graph + 4 distinct count aggregates), and the three link-table READ shapes that drive the Term-to-DataEntity / Term-to-DatasetField / Term-to-Term linkage feature (P-06:F-001). Writes flow through the inherited base (`create` / `update` / `delete` — `delete` is a soft-delete UPDATE setting `term.deleted_at = NOW()`); this file adds no write methods of its own — writes to the LINK tables live in a sibling `TermRelationsRepositoryImpl`. Every read predicate filters `TERM.DELETED_AT IS NULL` (lines 143, 156, 188, 234, 257, 279, 367, 387, 403, 432, 451, 461, 505), making term soft-deletion immediately invisible to all read paths. The class composes a 1-level CTE pattern (`termCTE = paginate(homogeneousQuery, ...).asTable("term_cte")`) in `listTermRefDtos` / `findByState` / `listByTerm` to push aggregation joins outside the paginated subquery — a JOIN-fan-out-after-LIMIT pattern that prevents row multiplication from the `LEFT JOIN ownership / tags / data_entity_to_term / dataset_field_to_term / term_to_term` chain. **`hasDescriptionRelations(termId)` is load-bearing** (lines 409-438): it's the only method other code uses to determine whether a Term can be safely renamed or hard-deleted, by EXISTS-checking the three link tables filtered to `is_description_link = TRUE` AND the parent `data_entity.status != DELETED` (lines 415, 425). Three observable drift facets trace to this file: (1) **`getTermDetailsDto` 4-aggregation JOIN explosion** (lines 194-238) — 8 LEFT JOINs on a single root row, the 4 `countDistinct` aggregates work because the GROUP BY captures every `TERM.*` and `NAMESPACE.*` field but unnamed combinatorial fan-out makes Postgres materialise N × M × P × Q rows before the DISTINCT reduces them; (2) **the `hasDescriptionRelations` guard is bypassed when the only mentioning parent is soft-deleted** (lines 415, 425) — confirmed at primary source; the existence check excludes `status = DELETED`, so a Term mentioned only in a soft-deleted entity's description can still be hard-deleted via `TermServiceImpl.delete`, after which restoring the entity leaves the `[[ns:term]]` text dangling; (3) **`listByTerm` pagination shape inconsistency** (lines 480-499) — `LIMIT/OFFSET` is applied AFTER the CTE+JOIN+GROUP BY rather than inside the CTE, and `pageifyResult` is NOT called (unlike `listTermRefDtos` and `findByState`) so the caller's `Flux<LinkedTermDto>` materialisation does not surface a `total` or `hasNext` — `TermServiceImpl.listByTerm` wraps with `Page.builder()...total(items.size())...hasNext(false)` (a hard-coded broken paginator that the service sidecar already records as a MEDIUM-severity gap).

- invariants:
  - "**Every read filters `TERM.DELETED_AT IS NULL`.** Verified at lines 143, 156, 188, 234, 257, 279 (via the `conditions.add(TERM.DELETED_AT.isNull())` at line 279 inside `findByState`), 367, 387, 403, 432, 451, 461, 505. A soft-deleted Term is invisible to every reader; coupled with the partial unique index `term_name_namespace_unique ON term(name, namespace_id) WHERE deleted_at IS NULL` (`V0_0_35__add_terms.sql:16`), this means a Term with name X in namespace Y can be soft-deleted and a new Term with the same `(X, Y)` can be created (same soft-delete-aware recreation pattern documented for `ReactivePolicyRepositoryImpl`)."
  - "**Soft-delete is for `term` ONLY.** The three link tables (`data_entity_to_term`, `dataset_field_to_term`, `tag_to_term`, `term_ownership`) had their `deleted_at` columns DROPPED in `V0_0_76__term_relations_hard_delete.sql:1-22` (verified at primary source). Term-to-DataEntity unlinks, Term-tag changes, Term-ownership removals are HARD DELETE — no audit trail beyond the activity-event JSON stored elsewhere. The `term_to_term` table is the ASYMMETRIC exception (`V0_0_91__add_term_to_term.sql:6` keeps `deleted_at`) but the repository never filters it — see bugs."
  - "**Name+namespace lookup is case-INSENSITIVE everywhere.** Verified at lines 156-157 (single lookup), 167 (batch OR-chain lookup). The partial unique index uses raw `(name, namespace_id)` (not lower-case-folded) per `V0_0_35__add_terms.sql:16` — case-folding consistency depends on application-layer enforcement. A Term created as `finance/Customer` and a candidate `finance/CUSTOMER` are detected as collisions by `equalIgnoreCase` at the application layer, but two concurrent INSERTs with case-different names that both pass the `equalIgnoreCase` check could theoretically both succeed at the DB (the unique index is byte-comparison). The duplicate-prevention is application-layer, not DB-layer."
  - "**`hasDescriptionRelations` excludes parents with `status = DELETED`.** Verified at lines 415 (`DATA_ENTITY.STATUS.ne(DataEntityStatusDto.DELETED.getId())`) and 425 (same predicate for the dataset-field → data-entity chain). The term-to-term branch (lines 427-433) instead filters `TERM.DELETED_AT.isNull()` on the TARGET term — different semantics. The asymmetry is intentional (data-entity uses `STATUS = DELETED` for soft-delete per `ReactiveDataEntityRepositoryImpl.java:109-123`, term uses `deleted_at IS NULL`) but introduces a corner case: a Term mentioned only in a soft-deleted data-entity's description PASSES the guard (returns FALSE), allowing the Term to be hard-deleted or renamed; when the data-entity is later restored (`/api/dataentities/{id}/status → ACTIVE`), the description's `[[ns:term]]` text now references a non-existent Term that will silently downgrade to 'unhandled' on the next description edit."
  - "**Pagination shape is inconsistent across the 4 list methods.** `listTermRefDtos` (line 117) uses `paginate(homogeneousQuery, ...)` + `pageifyResult` (line 130); `findByState` (line 316) same pattern; `listByTerm` (lines 494-495) applies `limit(size).offset((page-1)*size)` to the OUTER query WITHOUT `pageifyResult` — the caller (`TermServiceImpl.listByTerm`) is forced to manufacture a `Page.builder().total(items.size()).hasNext(false)` (per the TermServiceImpl sidecar). The structural mismatch means `listByTerm` cannot honour `total > size` correctly."
  - "**CTE-based `findByState` GROUP BY includes the CTE's columns AND `NAMESPACE.fields()`.** Line 320-322. `getTermDetailsDto` (line 200-202) GROUP BY includes `TERM.fields() + NAMESPACE.fields()`. The CTE-vs-source-table choice is a subtle pattern: CTE-based methods (`listTermRefDtos`, `findByState`, `listByTerm`) reference the CTE's fields (which jOOQ remaps via `jooqRecordHelper.remapCte` at line 543), while direct-table methods (`getTermDetailsDto`, `getDataEntityTerms`, `getDatasetFieldTerms`) reference `TERM.fields()` directly. Two distinct `mapRecordToRefDto` overloads (lines 534-546) honor the distinction."
  - "**`extractOwnershipRelation` throws `IllegalArgumentException` on missing dict lookups (lines 595-602).** If the JSON-aggregated owner/title dictionaries don't contain a referenced ownership's owner_id or title_id, the method throws `IllegalArgumentException` mid-stream. The exception path is silently mapped by reactor's error channel — a corrupted ownership row would surface to the caller as a 5xx with a generic message. This is defensive but harsh."
  - "**`SUGGESTION_LIMIT = 5` is hard-coded.** Line 82. The query-suggestions API returns at most 5 results regardless of caller preference. Compare `findByState` which paginates."
  - "**Reactive-transactional perimeter is OUTSIDE this class.** No method here is annotated `@ReactiveTransactional`. The transaction boundary lives in `TermServiceImpl` (every mutator there carries the annotation per the TermServiceImpl sidecar invariants). Reads are read-committed by default."

Postgres can short-circuit on OR-EXISTS once the first subquery matches." — evidence: `ReactiveTermRepositoryImpl.java:409-438` + `TermServiceImpl.java:128, 156`
  - "`getByNameAndNamespace(List)` on every description-edit auto-link path — single OR-chained batch query. - **throughput_characteristics**:
  - "Single-row reads (`getTermRefDto`, `getByNameAndNamespace`, `existsByNamespace`) — point lookups, milliseconds, throughput bounded by R2DBC pool size."
  - "List reads (`listTermRefDtos`, `findByState`, `listByTerm`) — paginated; per-page cost dominated by the inner paginated query plus the outer aggregation join. The CTE-first pattern keeps the LIMIT semantics correct."
  - "Aggregation reads (`getTermDetailsDto`) — heaviest; single-shot but executes a wide JOIN expansion. No batch endpoint exists for fetching N term details — each call is a separate query."
  - "Inherited bulk writes (`bulkCreate`, `bulkUpdate`) are `@ReactiveTransactional` (per `ReactiveAbstractCRUDRepository.java:113, 129`) but NOT exercised by `TermServiceImpl` (which uses single `create` / `update` per Term)."
- **resource_allocation**:
  - "Per call: one R2DBC connection acquired via `JooqReactiveOperations.mono` / `.flux` — non-blocking on the reactive thread, returned to pool on terminal signal."
  - "Per `getTermDetailsDto` call: the intermediate result set (Postgres-side fan-out × jsonArrayAgg materialisation) is collected into one Record passed through `mapRecordToDetailsDto`.
