## Description

The lineage pages share three undocumented (or softened) behaviours, all confirmed in code:

1. **No RBAC on any lineage endpoint.** The downstream / upstream / DEG (group) lineage endpoints carry **no SecurityRule** and fall through to `authenticated()` — there is **no owner check**. Any authenticated user can read the full **cross-owner** lineage subgraph; the DEG/group path is strictly wider (cross-owner co-membership). Under `auth.type=DISABLED` these are reachable by **any unauthenticated** caller.

2. **DISABLED-mode reachability is not flagged on microservices.** The microservices page frames exposure as "authenticated catalog user", but under DISABLED the cross-owner microservice-topology read is reachable by any unauthenticated probe — and service-call topology is more sensitive than ordinary dataset lineage.

3. **Unset `lineage_depth` is a hard crash, not an "undefined default".** The pages soften (or inherit a softening of) the missing-depth behaviour. The code parameter is a **primitive `int`**; a missing value autoboxes from `null` → **NPE → HTTP 500**. The OpenAPI declares `required: false`, so a spec-compliant caller who omits `depth` gets a 500. `api-reference/lineage`'s "unset returns a default depth" is **unimplementable** as written.

High — security exposure (cross-owner / unauthenticated) plus an API contract that crashes on a documented-as-optional parameter.

**Failure shape**: missing security caveats (Gate 3/6) + softened-crash drift on the lineage surfaces.
