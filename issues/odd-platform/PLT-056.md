## What

Six operator-visible defects on the Data Modelling Relationships listing surface (`/data-modelling/relationships`). The listing is the entry point for ERD / Graph relationship discovery — operators land on it from sidebar navigation and expect to discover catalog topology. The published doc page (live 2026-05-27) describes a two-column source/target contract, a type-aware tab strip, a 30-row infinite-scroll list, and a search input. Primary-source verification surfaces six independent code-side defects against that contract.

**Defect 1 — Target column displays SOURCE data (one-line code bug).** `odd-platform-ui/src/components/DataModelling/Relationships/RelationshipsListItem.tsx:73-81` (Target cell) renders the SAME source-data fields as the Source cell at lines 64-72. `item.targetDataEntity` is never referenced anywhere in the 85-line file (sibling components `RelationshipTypes/EntityRelationship.tsx:33-35` and `RelationshipTypes/GraphRelationship.tsx:32-34` consume it correctly). Every relationship row in the catalog shows the same dataset in both columns.

**Defect 2 — No authorization gate at any layer; the list is a catalog-wide enumeration oracle (the highest-severity defect in the cluster).** Three relationship endpoints (list + erd-detail + graph-detail) have NO `@PreAuthorize`, NO `SecurityConstants` rule entry (verified by 357-line read of `auth/util/SecurityConstants.java` — no `/api/relationships/**` entry), NO service-level check, NO namespace / owner / `EXCLUDE_FROM_SEARCH` filter at `ReactiveDataEntityRelationshipRepositoryImpl`. Every authenticated caller sees every relationship in the catalog including hidden and cross-tenant. Asymmetric to `/api/dataentities` (which DOES apply `EXCLUDE_FROM_SEARCH`).

**Defect 3 — Row-click routes to the same data-entity URL regardless of relationship type.** `RelationshipsListItem.tsx:52` calls `dataEntityDetailsPath(item.id)` UNCONDITIONALLY. The doc page promises type-specific routing; the implementation gives uniform routing. Doc-side fix (the cheap option) is captured in DOC-229 Caveat 3.

**Defect 4 — `?type=foo` URL param accepts arbitrary strings with no runtime validation.** `Relationships.tsx:19` is a TYPE ASSERTION (`as RelationshipsType`) with no runtime check. Arbitrary strings propagate to the backend → opaque 400; the UI tab strip silently shows no active tab (`RelationshipsTabs.tsx:27-32 findInitTabIdx` returns -1).

**Defect 5 — `relationship_id` parameter is silently `data_entity.id`, NOT `relationships.id`.** `ReactiveRelationshipsRepositoryImpl.java:194` filters by `data_entity.id` (entity_class=9 row representing the relationship). `RelationshipMapper.java:53` returns `id = data_entity.id`. Third-party SDK consumers reading the OpenAPI spec literally get 404 OR an unrelated relationship's payload.

**Defect 6 — Search filters by relationship name, NOT by source/target dataset name.** `ReactiveDataEntityRelationshipRepositoryImpl.java:69` binds `?q=` to `DATA_ENTITY.EXTERNAL_NAME.containsIgnoreCase` on the relationship-class row only. (Doc-side caveat in DOC-229 Caveat 4; code-side fix optional — the operator may prefer source/target-name search.)

## Why it matters

A single page in the catalog provides a complete cross-tenant relationships enumeration to any authenticated user. Combined with the Target-column bug (every row visibly broken) and the URL-param fragility (deep-links yield blank UI), the platform's Data Modelling pillar's flagship discovery surface is hostile by default:

- **Multi-tenant exposure** (Defect 2): one IDP, multiple operator teams → every team's relationships visible to every authenticated user.
- **Discovery workflow broken** (Defect 1): operators cannot answer "what relationships point at ORDERS?" from the list page.
- **API consumer breakage** (Defect 5): third-party SDKs built against the OpenAPI spec literally get wrong data.

Severity is CRITICAL because Defects 1 + 2 are immediate operator-visible breakages on the feature's primary discovery surface; Defect 5 is a published-API integrity issue.

## Suggested fix

Three distinct fixes; recommend grouping into 2 PRs:

### PR-1 — Display + UX (Defects 1 + 4)

**Defect 1 — one-line rename:**

```tsx
// RelationshipsListItem.tsx:75-79
- dataEntityId={item.sourceDataEntity.id}
- name={item.sourceDataEntity.internalName || item.sourceDataEntity.externalName || ''}
- oddrn={item.sourceDataEntity.oddrn || ''}
+ dataEntityId={item.targetDataEntity.id}
+ name={item.targetDataEntity.internalName || item.targetDataEntity.externalName || ''}
+ oddrn={item.targetDataEntity.oddrn || ''}
```

**Defect 4 — runtime validate the `?type=` param:**

```tsx
// Relationships.tsx:19
- const type = (searchParams.get('type') ?? RelationshipsType.ALL) as RelationshipsType;
+ const rawType = searchParams.get('type') ?? RelationshipsType.ALL;
+ const type = Object.values(RelationshipsType).includes(rawType as RelationshipsType)
+   ? (rawType as RelationshipsType)
+   : RelationshipsType.ALL;
```

### PR-2 — Authorization + scoping (Defects 2 + 5)

**Defect 2 — introduce `/api/relationships/**` RBAC scope:**

Add to `SecurityConstants.java` (mirror the dataentity entries):

```java
.pathMatchers("/api/relationships/**").access(authorizationManager(RELATIONSHIP_VIEW))
```

Define `RELATIONSHIP_VIEW` permission + ownership / namespace JOIN at `ReactiveDataEntityRelationshipRepositoryImpl`. At minimum, apply the `EXCLUDE_FROM_SEARCH` predicate as `/api/dataentities` does.

**Defect 5 — rename or document the `relationship_id` semantic alias:**

Two options:
- **Option A (recommended)** — document the alias in the OpenAPI spec (parameter description + a `x-semantic-note: "relationship_id is the data_entity.id of the relationship-class entity (entity_class=9)"` extension). Doc-side fix is DOC-229 Caveat 6.
- **Option B** — rename the OpenAPI parameter to `data_entity_id` (breaking change for existing SDKs).

### Defect 3 (cheap doc-side fix) is captured in DOC-229 Caveat 3 — no code change required unless the team wants true type-specific URLs (would require new UI routes).

### Defect 6 (search scope) — operator-judgement call. Either extend the SQL to also match source/target entity names (cheap; DOC-229 Caveat 4 documents the current scope), or leave as-is and accept the caveat.
