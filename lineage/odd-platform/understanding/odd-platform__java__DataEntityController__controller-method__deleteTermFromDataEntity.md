# DataEntityController#deleteTermFromDataEntity — semantic understanding

## understanding

`deleteTermFromDataEntity` is the reactive `DELETE /api/dataentities/{data_entity_id}/terms/{term_id}` handler — three lines that call `termService.removeTermFromDataEntity(termId, dataEntityId)` and lift the result into `204 No Content` (`DataEntityController.java:158-163`). The service issues a HARD `DELETE FROM data_entity_to_term WHERE data_entity_id = ? AND term_id = ? AND is_description_link = FALSE` (`TermRelationsRepositoryImpl.java:80-88`), captures a `TERM_ASSIGNMENT_UPDATED` activity event with BEFORE/AFTER terms-list state, and — if the data-entity has no remaining terms — clears the `data_entity_filled.TERMS` flag via `markEntityUnfilled` (`TermServiceImpl.java:181-196`).

**Headline finding (HIGH severity, primary-source confirmed):** the `DATA_ENTITY_DELETE_TERM` permission gate is silently dead due to a SecurityRule path-mismatch. `SecurityConstants.java:240-242` registers `new PathPatternParserServerWebExchangeMatcher("/api/dataentities/{data_entity_id}/term/{term_id}", DELETE)` (SINGULAR `term`); the OpenAPI spec at `openapi.yaml:1042` declares the operation path as `/api/dataentities/{data_entity_id}/terms/{term_id}` (PLURAL); the controller `@Override` inherits the plural path from the generated `DataEntityApi`. `AuthorizationCustomizer.customize` (`AuthorizationCustomizer.java:24-30`) only fires the permission check when `rule.matcher()` matches the request — the singular matcher never matches — and the no-match fallback is `.pathMatchers("/**").authenticated()` (line 29-30). Net effect: ANY authenticated user under LOGIN_FORM/OAUTH2/LDAP can DELETE any term-to-data-entity relation regardless of their Policy set. This is the SYMMETRIC counterpart of the addDataEntityTerm bug (batch G PRIMARY-SOURCE) — link AND unlink are both unauthorized server-side, even though the UI gates the delete button via `WithPermissions permissionTo={Permission.DATA_ENTITY_DELETE_TERM}` (`TermItem.tsx:48`).
