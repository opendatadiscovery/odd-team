## What

The toolbar shows a **Logout** menu item in every authentication mode, and clicking it always navigates the browser to `GET /logout`. Under `auth.type=DISABLED` there is no Spring Security logout chain wired, so that request hits an endpoint with no handler and the user lands on a 404 (or the SPA's not-found fallback) instead of any sensible logout outcome. The control is presented as a working primary action but is dead in the bundled default deployment mode.

## Where

The handler hard-codes a full-page navigation to `/logout` in all modes - `odd-platform-ui/src/components/shared/elements/AppToolbar/AppToolbar.tsx:36`:

```tsx
const handleLogout = () => {
  window.location.href = '/logout';
};
```

It is wired to the menu item rendered unconditionally in the toolbar (same file, line 117: `<AppMenuItem onClick={handleLogout}>{t('Logout')}</AppMenuItem>`).

The DISABLED security chain wires **only** `permitAll` - no `.logout(...)` - so nothing maps `/logout` - `odd-platform-api/.../config/DisabledAuthSecurityConfiguration.java:13-17`:

```java
return http
    .csrf(ServerHttpSecurity.CsrfSpec::disable)
    .authorizeExchange(authorizeExchangeSpec -> authorizeExchangeSpec.anyExchange().permitAll())
    .build();
```

## Why it matters

Loud-but-pointless failure on the platform's most common first-run configuration: DISABLED is the bundled default an operator gets when they stand the platform up to try it. A labelled primary action ("Logout") that dead-ends on a 404 is a broken-affordance trust hit - the operator clicks the obvious control and the app appears broken. (There is also nothing to log out *of* under DISABLED, so even a working route would be meaningless - the right behaviour is to not present the affordance.) Medium because it is cosmetic/UX rather than data-loss or security, but it is on a high-traffic surface in the default mode.

## Suggested fix

Make the logout affordance mode-aware: hide the Logout menu item entirely under DISABLED (where there is no session to terminate), or adapt it to a sensible no-op/explanation. The client already knows it is in DISABLED mode from the synthetic all-permissions `admin` identity; a dedicated auth-mode signal on the identity payload would let the toolbar suppress the item deterministically. Open to alternatives.
