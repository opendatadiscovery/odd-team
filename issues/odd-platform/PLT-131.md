> **User-facing surface FALSIFIED 2026-06-10 (G20 sweep).** The original draft's load-bearing claim - a direct `GET /api/owners/{id}` returns a soft-deleted Owner instead of 404 - is **wrong: there is no by-id GET endpoint.** `OwnerApi` (generated contract) exposes exactly `POST /api/owners`, `GET /api/owners` (list), `PUT /api/owners/{owner_id}`, `DELETE /api/owners/{owner_id}` - and `OwnerController` implements only `createOwner` / `getOwnerList` / `updateOwner` / `deleteOwner`. No `getOwner(id)`. So the GDPR-by-id-read, the reconnaissance-by-recorded-id, and the "still there if I hit the id directly" scenarios are all unreachable. The underlying code omission (`getDto` lacks the deleted_at filter) is **real but latent / defense-in-depth**, not a directly user-reachable defect. Title, severity (medium -> low), security flag (true -> false), and Impact rewritten to the verified truth.

## What

The Owner **list** path correctly hides soft-deleted Owners (`deleted_at IS NULL`, applied by the soft-delete base class via `listCondition` -> `addSoftDeleteFilter`), but the **by-id DTO** path does not: `ReactiveOwnerRepositoryImpl.getDto` (L65-83) issues `WHERE OWNER.ID = id` (L79) with **no** `deleted_at IS NULL` filter. The `switchIfEmpty(NotFoundException)` that would 404 a missing owner is at the **service** layer (`OwnerServiceImpl.getOwnerDtoById:102-107`, line 105) and fires only when the id never existed - so for a *soft-deleted* owner, `getDto` returns the row (name + previously-attached roles) and the service maps it instead of 404ing.

**But this method has no by-id read endpoint behind it.** `getDto` is reachable only via:
- `OwnerServiceImpl.getOwnerDtoById` -> consumed only by `OwnerAssociationRequestServiceImpl.createUserOwnerMapping` (L113) and `deleteActiveUserOwnerMapping` (L121) - i.e. it returns the owner DTO as the *result of a write* (create/delete a user-owner mapping for a supplied owner id), not as a readable lookup;
- the create/update owner flows, which call `getDto(owner.getId())` to echo back the just-mutated (therefore live) owner.

So the omission is a **latent correctness gap**: it would bite the day a by-id GET is added, and it lets `createUserOwnerMapping` echo a soft-deleted owner if one is referenced by raw API - but it does not expose soft-deleted owners through any read surface today.

This is **net_new** - not in any existing PLT. (PLT-110 is the *Policy*-grant-path `deleted_at` omission; this is the *Owner* `getDto` omission. SHB-095 seeded the GDPR-erasure scenario but filed no PLT.)

## User-facing impact

**FALSIFIED at the read surface; the code omission is latent.** Verified by reading the generated `OwnerApi` contract and `OwnerController` end-to-end against source HEAD:

- There is **no `GET /api/owners/{owner_id}`** endpoint. `OwnerApi` has only `POST /api/owners`, `GET /api/owners` (list, deleted_at-filtered), `PUT /api/owners/{owner_id}`, `DELETE /api/owners/{owner_id}`; `OwnerController` implements `createOwner` / `getOwnerList` / `updateOwner` / `deleteOwner` and nothing else. So all three originally-claimed impacts are **unreachable**: (1) GDPR by-id read - no by-id read; (2) reconnaissance via recorded ids - nothing to read them through; (3) "still there if I hit the id directly" - no id endpoint to hit.
- The two reachable callers of `getDto` are **write results, not reads**: `createUserOwnerMapping` (`OwnerAssociationRequestServiceImpl:113`) and `deleteActiveUserOwnerMapping` (`:121`) return the owner DTO after mutating a mapping, and the owner create/update flows echo the just-mutated (live) owner. The only residual real consequence: `createUserOwnerMapping` would echo a **soft-deleted** owner's name/roles in its response if a raw API call supplies a soft-deleted owner id (admin-gated; the UI owner-picker is list-filtered).
- Auth posture: even the originally-claimed "ungated read" is moot since no read endpoint exists; the mapping-mutation callers require owner-association management. Under `DISABLED` the mutation paths are anonymous, but they are writes, not a soft-deleted-owner read channel.

Net: a genuine latent correctness gap (the `getDto`/`list` asymmetry) worth fixing for defense-in-depth and to forestall a future by-id endpoint, but **not** a directly user-facing data-exposure defect. Remaining surface check: if a by-id GET is ever added on `getDto`, it must inherit the deleted_at filter.

## Suggested fix

Add `.where(OWNER.DELETED_AT.isNull())` to `ReactiveOwnerRepositoryImpl.getDto` (the SHB-095 fix) so the by-id DTO path matches the list path, and audit every `getDto`-style method in soft-delete repositories for the same omission. This is defense-in-depth today (no by-id read endpoint exists) but prevents `createUserOwnerMapping` from echoing a soft-deleted owner and makes any future by-id GET safe by construction. Distinct from PLT-110 (Policy grant-path).
