## What

Three defects on the Directory subsystem - one infrastructure-information leak (the level-2 response reflects every `@PathField`-annotated property of the data source's ODDRN to every authenticated caller, including `host`, `database`, `port`, `account`, `warehouse`, `cluster`, `topic`), one display-correctness defect (the level-4 page and count repository methods apply different filter predicates so X-of-Y silently mismatches under `EXCLUDE_FROM_SEARCH`), and one URL-fragility defect (the route hook coerces a non-numeric type-id to `NaN` without an isNaN guard, propagating NaN to 6 downstream consumers).

**Defect 1 - Level-2 ODDRN reflection leaks infrastructure properties (F-023d - HIGH).** `DirectoryServiceImpl.getOddrnPathProperties` (`DirectoryServiceImpl.java:153-171`) walks every `@PathField`-annotated field on the data source's parsed ODDRN path via reflection and emits the resolved string-value map in the level-2 response (assembled in `getDirectoryDatasourceList`, `:66-82`; emit at `:76-78`). The ODDRN path components are the connection coordinates - e.g. PostgreSQL `host` + `database`, Snowflake `account` + `warehouse`, Kafka `cluster` (the exact per-type field set is whatever the external oddrn-generator-java path class annotates `@PathField`; the reflect-all-`@PathField` mechanism is what is verified here). The call hops `DirectoryController.getDirectoryDatasourceList -> DirectoryServiceImpl.getDirectoryDatasourceList -> ReactiveDataSourceRepository.findByPrefix` - none apply an `OWNERSHIP` join or any per-tenant filter. Any authenticated caller (anonymous under `auth.type=DISABLED`) calling `GET /api/directory/datasources?prefix={type-prefix}` enumerates the infrastructure inventory of every registered data source of that type.

**Defect 2 - Level-4 page and count apply different predicates; X-of-Y silently wrong (F-023c - MEDIUM).** `ReactiveDataEntityRepositoryImpl.listByDatasourceAndType` (the **page** call, `:595-613`, via `cteDataEntitySelect` `:909-939`) applies soft-delete (`STATUS != DELETED`, `:121`) + `HOLLOW.isFalse()` (`:918`) only. `countByDatasourceAndType` (the **count** call, `:616-627`) uses `getDataEntityDefaultConditions` (`:970-975`) which ADDS **`EXCLUDE_FROM_SEARCH`**. In deployments using `EXCLUDE_FROM_SEARCH` to hide intermediate / transient entities from search but still allow direct browsing (a common collector hygiene pattern), the level-4 UI renders e.g. `30 entities` in the list but the count badge reads `25` - operators auditing per-source completeness see an unexplained mismatch (the list is the larger number, since it does not exclude the hidden entities).

**Defect 3 - `useDirectoryRouteParams` no isNaN guard (F-023a / corroborates DOC-GAP-252 NaN-route-hook dimension - LOW).** `directoryRoutes.ts:29-41`: `parseInt(dataSourceId, 10)` at line 37 with no isNaN guard; `parseInt(typeId, 10)` at line 34 (where `typeId === 'all'` maps to `undefined`, not `'all'`). A deep-link to `/directory/postgresql/abc/all` produces `dataSourceId: NaN`, consumed by 6 components. The symptom is **not** a silent broken view (corrected 2026-06-10): `Entities.tsx:27` fires `useGetDataSourceEntityTypes({ dataSourceId: NaN })` with no `enabled` guard, the request hits `/api/directory/datasources/NaN/types`, the BE returns HTTP 400 (`NaN` cannot bind to a `Long` path variable), and `Entities.tsx:60-64` renders an `AppErrorPage`. The user gets a generic API error page - not a 404 and not a silent broken render.

## User-facing impact

**Defect 1 - infrastructure properties on the wire (verified by BE trace 2026-06-10; the leak-vs-posture judgement is deployment-dependent).** WHO: any authenticated caller / API consumer (anonymous under `auth.type=DISABLED`). WHAT: `GET /api/directory/datasources?prefix={prefix}` (`getDirectoryDatasourceList`; openapi `/api/directory/datasources`, `prefix` is a query param, `openapi.yaml:3760-3779`). WHAT THEY GET: for each data source, a `properties` map built by reflecting every `@PathField` field of the parsed ODDRN path (`DirectoryServiceImpl.getOddrnPathProperties` `:153-171`; emit `:66-82`). For an ODDRN those components are the connection coordinates (e.g. PostgreSQL host + database, Snowflake account). No `OWNERSHIP`/caller scope is applied (`getDataSourcesByPrefix` -> `findByPrefix`). The reflect-all-`@PathField` mechanism and the API emitting the map are verified by BE trace; the exact field set per type is from the external oddrn-generator-java path classes (not re-read here), and whether returning these to every authenticated caller is a vulnerability or the documented read-collaborative posture is the deployment's call.

**Defect 2 - list count exceeds the badge (verified by BE trace 2026-06-10).** WHO: an operator on the level-4 directory page (`GET /api/directory/datasources/{data_source_id}?type_id=...`, `getDatasourceEntities`). WHAT THEY GET: list and badge are computed by two methods with different predicates - the list (`listByDatasourceAndType` `:595-613` -> `cteDataEntitySelect` `:909-939`) filters only soft-delete (`STATUS != DELETED`, `:121`) + `HOLLOW.isFalse()` (`:918`); the count (`countByDatasourceAndType` `:616-627` -> `getDataEntityDefaultConditions` `:970-975`) ADDS `EXCLUDE_FROM_SEARCH.isNull().or(isFalse())`. So with `EXCLUDE_FROM_SEARCH=true` entities under the source, the rendered list (`Entities.tsx:55,81-87`) includes them but the badge (`pageInfo.total`, `Entities.tsx:50-53,74-78`) excludes them - list larger than badge. The divergence direction is verified by BE trace; the exact on-screen numbers are data-dependent (not driven).

**Defect 3 - NaN deep-link shows an API error page, not a silent broken view (corrected; verified by FE/BE trace 2026-06-10).** WHO: an operator opening a malformed directory deep-link (e.g. `/directory/postgresql/abc/all`). WHAT THEY GET: `useDirectoryRouteParams` (`directoryRoutes.ts:37`) returns `dataSourceId = parseInt('abc',10) = NaN` (no isNaN guard); `Entities.tsx:27` fires `useGetDataSourceEntityTypes({ dataSourceId: NaN })` with no `enabled` guard (`directory.ts:32-39`), the request hits `/api/directory/datasources/NaN/types`, the BE returns HTTP 400 (`NaN` cannot bind to a `Long` path variable), `isTypesError` is set, and `Entities.tsx:60-64` renders an `AppErrorPage`. The user sees a generic API error page - not the "silent broken view" the prior revision claimed, and not a 404. Verified by FE/BE trace.

## Why it matters

- **Defect 1 is the operator-trust load-bearing fix.** Operators frequently expose `host` strings that double as internal DNS targets (`db-replica-3.prod.acme.internal`); `account` reveals the Snowflake organization name; `cluster` exposes Kafka bootstrap servers. Read-collaborative posture is the explicit architectural choice across the catalog (DOC-GAP-082 META), but the infrastructure-property reflection is the most-egregious leak surface - a multi-tenant deployment without reverse-proxy gating exposes every team's source topology to every team. Under `auth.type=DISABLED` the leak is anonymous.
- **Defect 2 is a display-correctness defect** that breaks operator confidence - "the platform's page count contradicts itself" is a credibility hit even when the underlying data is correct. Operators auditing collector coverage cannot rely on the count badge.
- **Defect 3 is a minor UI fragility** - operators copy-pasting URLs / saving bookmarks produce malformed deep-links easily; the result is a generic API error page (the NaN `data_source_id` 400s the level-4 types request) rather than a clear "source not found" message or redirect. It does NOT compound with Defect 1: the NaN is in the level-4 path and 400s before any data-source row is returned; Defect 1's leak is on the separate level-2 prefix-list endpoint.

Severity HIGH because Defect 1 meets the multi-tenant data-disclosure threshold and DOC-260 / DOC-261 ship the caveats as load-bearing operator warnings.

## Suggested fix

Three coordinated fixes; Defect 1 should ship under explicit operator opt-in to preserve the current read-collaborative behaviour for deployments that rely on it.

### (a) Defect 1 - Owner-scoped reflection + redaction option

Two paths; pick one based on deployment posture:

**(a1) RBAC: gate `/api/directory/**` with an `OWNERSHIP`-joined repository call.** Add `@PreAuthorize` to `DirectoryController` (or a `SecurityConstants` rule); pass caller's owner_id through `getOddrnPathProperties` and only emit reflected properties for data sources the caller has visibility into. Closes the leak; preserves the existing UI shape for owners of the sources they can see.

**(a2) Redaction: feature-flag `directory.reflect-infrastructure-properties` (default false in 2026-06+).** Operators wanting the existing behaviour set it true; default behaviour redacts the reflected properties to `***` or omits them from the wire response. Cheaper to ship; less disruptive to existing deployments; closes the default-secure path.

Recommendation: (a2) immediately + (a1) as a follow-up. Operators who explicitly want the existing posture flip the flag; new deployments land on the default-secure shape.

### (b) Defect 2 - Align the predicate sets

```java
// ReactiveDataEntityRepositoryImpl.java
// The count already uses getDataEntityDefaultConditions() (HOLLOW + STATUS != DELETED + EXCLUDE_FROM_SEARCH).
// The page (listByDatasourceAndType) only gets soft-delete (STATUS != DELETED) + HOLLOW from cteDataEntitySelect.
// (b1) Add the missing predicate to the page's cteConditions so both agree:
cteConditions.add(DATA_ENTITY.EXCLUDE_FROM_SEARCH.isNull().or(DATA_ENTITY.EXCLUDE_FROM_SEARCH.isFalse()));
// OR (b2) drop EXCLUDE_FROM_SEARCH from getDataEntityDefaultConditions() for the count path.
```

Note that `EXCLUDE_FROM_SEARCH` was originally a search-only gate; the Directory's level-4 browse is a different UX. Two options: (b1) apply `EXCLUDE_FROM_SEARCH` to both (entities hidden from search are also hidden from Directory level 4 - consistent with operator intent); (b2) apply it to neither (level-4 is direct browse, not search - show everything). Recommend (b1) because operators using `EXCLUDE_FROM_SEARCH` already expect the entity hidden from discovery surfaces; Directory level 4 is a discovery surface.

### (c) Defect 3 - isNaN guard + 404 fallback

```ts
// directoryRoutes.ts
export const useDirectoryRouteParams = () => {
  const { typeId, dataSourceId } = useParams();
  const parsedTypeId = typeId === 'all' ? 'all' : Number(typeId);
  const parsedDataSourceId = Number(dataSourceId);
  return {
    typeId: Number.isNaN(parsedTypeId) ? undefined : parsedTypeId,
    dataSourceId: Number.isNaN(parsedDataSourceId) ? undefined : parsedDataSourceId,
    isInvalid: Number.isNaN(parsedDataSourceId) || (typeId !== 'all' && Number.isNaN(parsedTypeId)),
  };
};
```

In the consuming components, route `isInvalid` -> 404 page or "Source not found" inline message.

## How discovered

Mode B run of `docs/coverage/undocumented-features` on 2026-05-27 (substrate `F-023` - Directory Browsing). The level-2 reflection mechanism was inherited from the F-023 chain hop 2a sidecar evidence; the level-4 predicate divergence was inherited from chain hops 3a/3b. Cross-batch context: DOC-GAP-008 (controller-tier ungating) + DOC-GAP-252 (UI-tier closure) are the two prior surfaces of the read-collaborative-posture-on-Directory finding family; this PLT closes the data-tier dimension.

**Corrected 2026-06-10 (user-facing verification sweep).** All three defects survive, re-scoped to verified code. (1) Defect 1 method/endpoint - was `getDataSources` / `ReactiveDataSourceRepository.list` / `GET /api/directory/{type-prefix}` / reflection cited `138-171`; actually `getDirectoryDatasourceList` -> `findByPrefix` / `GET /api/directory/datasources?prefix=...` (prefix is a query param) / reflection in `getOddrnPathProperties` `DirectoryServiceImpl.java:153-171` (the fabricated `enrichWithPathProperties`/`oddrnGeneratorRegistry` snippet does not exist). (2) Defect 2 predicates - confirmed (page lacks `EXCLUDE_FROM_SEARCH`, count has it) but the soft-delete is `STATUS != DELETED` via `addSoftDeleteFilter` (`:121`), not a `DELETED_AT.isNull()` column filter as the snippet showed. Same failure mode as PLT-176/PLT-167: a UI symptom and code citations asserted without reading the FE/BE end-to-end.
