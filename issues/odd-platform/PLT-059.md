## What

Five defects on the Term create / edit dialog (`TermsForm.tsx`). Three are security-class (XSS surface + RBAC bypass on namespace-create + silent failure-mode); two are correctness defects (duplicate-check fragility at scale + cache invalidation against undefined id).

**Defect 1 - Term definition Markdown editor accepts arbitrary HTML/JS - 3rd Term-specific surface of the F-004 stored-XSS family (F-154d).** `TermsForm.tsx:168-186` renders the definition field as `<Markdown {...field} editor height={200} />`. The editor accepts arbitrary Markdown including raw HTML and inline JavaScript. On submit, the raw string round-trips through `TermServiceImpl.createTerm` / `updateTerm` (no sanitisation per F-002 batch U + F-004 batch U). The render side (`TermDefinition.tsx:39-47` -> `Markdown.tsx`) does no `rehype-sanitize`. Any operator with `TERM_UPDATE` permission can plant `<script>` payloads via this dialog; the F-004 family stored-XSS triggers for every authenticated viewer.

**Defect 2 - NamespaceAutocomplete silently creates novel namespaces; TERM_CREATE bypasses NAMESPACE_CREATE (F-154e).** `TermsForm.tsx:161-167` renders `<NamespaceAutocomplete>` with no creation gate. A user typing a namespace name not in the dropdown submits the form; on the backend, the string flows to `namespaceService.getOrCreate(namespaceName)` - bypassing `NAMESPACE_CREATE`. UI gives no signal that typing a novel namespace will create one.

**Defect 3 - Duplicate-name check is fragile at scale and CREATE-mode-only (F-154a).** `TermsForm.tsx:71-75` dispatches `fetchTermsSearchResults({searchId, page: 1, size: 1000})` on mount. Line 84 gates the duplicate detector on `if (!term?.id)` - CREATE-mode only. Three stacking issues: (a) `size: 1000` hardcoded - catalogs with 1001+ terms silently skip the check for the 1001th term; (b) EDIT mode never runs the check - renaming to collide is unwarned; (c) the backend uniqueness constraint is authoritative but has no graceful-error path documented.

**Defect 4 - Dialog dispatch chain has no `.catch` handler; silent failure on backend reject (F-154b).** `TermsForm.tsx:100-111` - `dispatch(createTerm|updateTerm).unwrap().then(...)` with NO `.catch(...)`. If backend rejects (uniqueness violation, validation, RBAC mismatch), the chain rejects silently; the dialog stays open with form filled in and no error message. LSN-024-shaped silent-empty class. The Alert component scaffolding already exists at `TermsForm.tsx:50, 122-147`.

**Defect 5 - `queryClient.invalidateQueries({queryKey: ['term', termId]})` uses route termId in CREATE mode where termId is `undefined` (F-154c).** `TermsForm.tsx:105-108` invalidates by route termId in both modes. In CREATE mode, the route termId is `undefined` / `NaN` (per F-024 batch ZH parseInt propagation). The invalidate fires for `['term', undefined]` - invalidates nothing OR wrong cache slot. Future cached lookups for `['term', undefined]` accumulate dead entries.

## Why it matters

The TermsForm is the operator's primary authoring surface for the Glossary feature. Combined with DOC-177 / DOC-199 caveats on the same page, every defect here lands in front of operators on every create/edit interaction:

- **Defect 1**: stored-XSS on a public surface; trigger fires for every reader of any Term anywhere - multi-tenant blast radius.
- **Defect 2**: separation-of-duties policies expecting `NAMESPACE_CREATE` to gate namespace creation leak via TermsForm; multi-team deployments have a hidden side-door.
- **Defect 4**: silent UX failure on every backend reject - operators cannot tell whether they succeeded; cache may go stale; trust in the dialog erodes.

Severity is CRITICAL (Defect 1 XSS family + Defect 2 RBAC bypass - both on documented public surfaces).

## Suggested fix

Recommend three PRs:

### PR-1 - Security (Defects 1 + 2)

**Defect 1 - wire `rehype-sanitize` at the render layer (paired with PLT-023 family):**

```tsx
// Markdown.tsx - single SPA-tier fix
const sanitisedRender = useMemo(() => ({rehypePlugins: [rehypeSanitize]}), []);
return <MDEditor.Markdown source={value} {...sanitisedRender} />
```

This closes Defect 1 for term definitions AND closes 5 sibling surfaces (per DOC-187 family META). Coordinate with **PLT-023** to avoid duplicate work - the consolidated F-004 fix is one config change at `Markdown.tsx:113-124`.

Defence in depth at authoring: add Jsoup.clean + length cap at `TermServiceImpl.createTerm` / `updateTerm` so the backend stores sanitised text even before the renderer hardens.

**Defect 2 - split TERM_CREATE from NAMESPACE_CREATE:**

```tsx
// TermsForm.tsx:161-167
<NamespaceAutocomplete
  restrictToExisting={!hasPermission(NAMESPACE_CREATE)}
  onNovelInput={(name) => setShowCreateNamespacePrompt(true)}
/>
{showCreateNamespacePrompt && (
  <CreateNamespaceDialog
    permission={NAMESPACE_CREATE}
    onCreated={(ns) => setNamespace(ns)}
  />
)}
```

Backend hardening: `namespaceService.getOrCreate(name)` consults `NAMESPACE_CREATE` before creating; throws `ForbiddenException` if the caller lacks permission. (See F-002 batch K family for the architectural META - same pattern applies to tag-create via TagsEditForm, see PLT-060.)

### PR-2 - UX correctness (Defects 3 + 4 + 5)

**Defect 3 - replace client check with server-side `check-name-availability` endpoint:**

```
GET /api/terms/check-name-availability?name=X&namespaceName=Y -> 200 { available: true|false }
```

Fired on blur of the name field; no client-side memory of 1000 terms required. Authoritative gate. Update TermsForm to call it.

**Defect 4 - add `.catch` handler + render Alert:**

```tsx
// TermsForm.tsx:100-111
dispatch(createTerm|updateTerm)
  .unwrap()
  .then(...)
+ .catch((e) => {
+   setError(serializeBackendError(e));
+   // existing Alert at lines 122-147 already renders setError state
+ });
```

**Defect 5 - use `response.id` from the unwrap for invalidation:**

```tsx
// TermsForm.tsx:105-108
- queryClient.invalidateQueries({queryKey: ['term', termId]})
+ queryClient.invalidateQueries({queryKey: ['term', response.id]})
```

### PR-3 - Defence-in-depth audit

Once PR-1 + PR-2 land, do a TermsForm penetration-test: try `<script>` payloads in definition + name + namespace, confirm `rehype-sanitize` filters; try novel namespace name without `NAMESPACE_CREATE`, confirm rejected; try EDIT-mode rename-to-collide, confirm client check fires.
