## What

**REJECT-CANDIDATE - the load-bearing user-facing claim is falsified by the code and the docs are already correct (verified 2026-06-10).** The original draft claimed Okta + Keycloak "fall through `CustomOIDCUserHandler` with NO admin-detection," that "every Okta + Keycloak user is granted USER role at login," and that "operators configuring `admin-groups` see ZERO admin path - the handler ignores it." Reading the handler chain disproves all three.

What is true: `Provider.java:3-5` declares a five-value enum (COGNITO / GITHUB / GOOGLE / ODD_IAM / AZURE) and Okta/Keycloak are not enum values - they route through `CustomOIDCUserHandler` (any provider not in the enum; `CustomProviderCondition`). But "not an enum value" does NOT mean "no admin path":

- **`admin-principals` works for the Custom OIDC path with no extra config.** `AbstractOIDCUserHandler.enrichUserWithProviderInformation` (`:32-43`) evaluates `admin-principals` against the user's `admin-attribute`/`username-attribute` claim for EVERY handler, including the custom one. A matching login is promoted to ADMIN.
- **`admin-groups` also works on the Custom path - but only if the operator also sets `groups-claim`.** Same method, `:44-55`: `groupsClaim = provider.getGroupsClaim()` if set, else `getDefaultGroupsClaim()`. `CustomOIDCUserHandler.getDefaultGroupsClaim()` returns `null` (`:42-44`), so unlike Cognito (`"cognito:groups"`) / Azure (`roles`) there is no DEFAULT groups claim. With `groups-claim` configured, the group-based admin match runs normally.

So the only real, narrow gap vs first-class providers is: **`admin-groups` alone (without `groups-claim`) silently no-ops on the Custom OIDC path, because there is no default groups claim.** That is a documentation/UX caveat - and it is already documented (see below) - not "ZERO admin path." Okta/Keycloak are fully usable today.

The "docs claim 7 but code has 5" drift is also a non-issue: listing 7 provider NAMES while routing two of them through a generic handler is the documented, intended design, and the live docs describe the exact runtime behaviour (including the `groups-claim` caveat) accurately.

## User-facing impact

Verified 2026-06-10 by reading the handler chain and confirming the live docs (and the published site).

- **Code:** an Okta or Keycloak operator who sets `admin-principals` gets ADMIN promotion on login with no further config (`AbstractOIDCUserHandler:33-43`, case-insensitive full match). An operator who wants group-based promotion sets `groups-claim` + `admin-groups` and it works (`:44-55`). Only `admin-groups` WITHOUT `groups-claim` silently does nothing - because `CustomOIDCUserHandler.getDefaultGroupsClaim()` is `null`. The draft's "every Okta/Keycloak user is USER / ZERO admin path / handler ignores admin-groups" is false.
- **Docs:** the live `oauth2-oidc` page carries an "Admin-detection per-provider matrix" whose Okta/Keycloak/Custom rows state exactly this, plus an explicit hint: *"Okta, Keycloak, and any other 'Custom OIDC' provider DO promote to ADMIN via admin-principals."* `admin-promotion.md` repeats it. Confirmed on the published site (`docs.opendatadiscovery.org/.../oauth2-oidc`): 7 providers listed; the Okta/Keycloak admin-promotion sentence present. So there is no doc-vs-code contradiction to resolve - DOC-339 already aligned the docs to the code.

Net: no operator following the current docs is misled, and no admin user is stranded. This item does not describe a live defect.

## Why it matters

The original premise (a doc-vs-code first-class-vs-fall-through divergence where "admin users never resolve to ADMIN") is **falsified**: Okta/Keycloak operators DO have an admin path (`admin-principals` unconditionally; `admin-groups` once `groups-claim` is set), and the live docs already document this precisely. There is no operator-facing breakage to fix. The residual is a small ergonomics gap - no default groups claim on the custom path, so `admin-groups` alone silently no-ops - which is already a documented caveat, and the matter of whether to invest in dedicated Okta/Keycloak handlers (with sensible default group claims) is an optional convenience feature, not a defect.

## Suggested fix

**Caveat first: there is no operator-load-bearing fix needed** - the premise is falsified and the docs are accurate. The options below are an OPTIONAL convenience feature (improve out-of-the-box ergonomics so `admin-groups` works without forcing the operator to also know the per-provider claim name). If the maintainer does not want to grow the handler surface, the correct disposition is to CLOSE this item against the existing docs (the `groups-claim` caveat is already published). Should the convenience feature be pursued:

**Option A - Add OktaUserHandler + KeycloakUserHandler with provider-specific default group claims (convenience only).**

Each handler reads the appropriate provider-specific group claim:

- **Okta**: groups claim is typically `groups` (configurable in the Okta admin console). A dedicated handler could default `getDefaultGroupsClaim()` to `"groups"` so `admin-groups` works without the operator also setting `groups-claim`.
- **Keycloak**: roles live under NESTED claims - `realm_access.roles` (realm-level) or `resource_access.{client_id}.roles` (client-level). NOTE: the current generic code reads the claim via `oidcUser.getAttribute(groupsClaim)` and expects a flat `List<String>` (`AbstractOIDCUserHandler:47`), so a nested path like `realm_access.roles` does NOT resolve through a plain `groups-claim` today. A dedicated Keycloak handler that flattens the nested roles claim is the real ergonomic value-add here (this, not "no admin path", is the genuine Keycloak gap).

A convenience implementation would add the enum values and wire the handlers in the user-resolution chain; it does not change the fact that `admin-principals` already works.

**Option B - Provide a generic OIDC-group-claim handler usable across Okta + Keycloak + Custom OIDC (longer-term).**

A `GenericOIDCUserHandler` parameterised on `groups-claim-name` (default `groups`, override per provider), ideally with nested-claim support. One handler, many providers.

Recommendation: this is optional convenience, not a fix. If pursued, Option A (a small dedicated Keycloak handler that flattens nested roles) captures most of the real value; Option B is a refactor for later. Otherwise CLOSE against the existing, accurate docs.
