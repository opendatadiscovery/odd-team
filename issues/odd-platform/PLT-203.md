## Rejection

Rejected as a false positive (2026-06-10 sweep). The central claim ('no success toast; the only signal is the modal closing') is false: the mutation hook fires an explicit `showSuccessToast('Owner association created successfully')` and invalidates the list queries (`ownerAssociationRequest.ts:67-84`). The original draft read only the form component, not the hook. There is no defect.

> **REJECT-CANDIDATE (2026-06-10, user-facing verification sweep).** The load-bearing claim - "no success toast... the only signal that the bind succeeded is that the modal closes" - is FALSIFIED. The mutation hook `useCreateUserOwnerMapping` fires an explicit success toast and invalidates the association list queries on success. There is no defect here. Retained (status untouched per sweep rules) for the audit trail; do not file.

## What

~~On the **Management -> Owner Associations** admin page, the "Create association" dialog gives the operator no explicit success feedback after a successful submit: no success toast, no inline confirmation, no redirect; the only signal is that the modal closes.~~ **FALSIFIED.** This claim was drawn from `OwnerAssociationForm.tsx` alone (which only consumes `isSuccess` to close the dialog) without reading the mutation hook that wires the success path. The hook `useCreateUserOwnerMapping` (`odd-platform-ui/src/lib/hooks/api/ownerAssociationRequest.ts:67-84`) has an explicit `onSuccess` that BOTH raises a success toast - `showSuccessToast({ message: 'Owner association created successfully' })` (`:75`) - AND invalidates `ownerAssociationRequestList` + `ownerAssociationActivityList` (`:76-81`) so the History re-renders with the new row. So the admin gets a durable, explicit confirmation **and** the list refreshes; the modal close is not the only signal. The duplicate-audit-row trap the issue posited does not arise from missing feedback.

## Where

`odd-platform-ui/src/components/Management/OwnerAssociations/OwnerAssociationsHeader/OwnerAssociationForm/OwnerAssociationForm.tsx:108`

```tsx
const {
  mutateAsync: createUserOwnerMapping,

...

...
return (
  <DialogWrapper
    ...
    handleCloseSubmittedForm={isSuccess}   // <-- line 108: success is consumed ONLY to close the dialog

    clearState={clearState}
    confirmOnClose
  />

```

Within `OwnerAssociationForm.tsx`, `isSuccess` is indeed wired only into `handleCloseSubmittedForm` (`:108`) - **but the success feedback does not live in this component.** It lives in the mutation hook the component calls, `useCreateUserOwnerMapping`:

```ts
// odd-platform-ui/src/lib/hooks/api/ownerAssociationRequest.ts:67-84
export function useCreateUserOwnerMapping() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationKey: ['createUserOwnerMapping'],
    mutationFn: params => ownerAssociationRequestApi.createUserOwnerMapping(params),
    onSuccess: async () => {
      showSuccessToast({ message: 'Owner association created successfully' });   // :75
      await queryClient.invalidateQueries({ queryKey: ['ownerAssociationRequestList'] });   // :76-78
      await queryClient.invalidateQueries({ queryKey: ['ownerAssociationActivityList'] });   // :79-81
    },
  });
}
```

`showSuccessToast` is the platform's real toast mechanism (`odd-platform-ui/src/lib/errorHandling.tsx:40`, renders an `AppToast` via `toast.custom`). So the success branch DOES fire a toast and DOES refresh the lists. The original "no `onSuccess` callback raising a notification" assertion missed the hook.

## User-facing impact

**An admin DOES get explicit success feedback** - verified by FE trace 2026-06-10. On a successful Create-association submit, `useCreateUserOwnerMapping.onSuccess` (`ownerAssociationRequest.ts:74-82`) raises the toast "Owner association created successfully" (`:75`, via `showSuccessToast` -> `errorHandling.tsx:40`) and invalidates the `ownerAssociationRequestList` / `ownerAssociationActivityList` queries (`:76-81`), so the association History list re-fetches and shows the new entry. The modal close (`OwnerAssociationForm.tsx:108`) is one of three concurrent signals, not the only one. The posited duplicate-audit-row trap (admin re-submits because they did not register the close) does not hold: the toast is the durable cue and the list updates. No defect.

## Why it matters

It does not - this is a REJECT-CANDIDATE (rationale corrected at the top of the file and in *How discovered*). The original medium severity rested entirely on "the only signal is the modal close," which the FE trace falsifies. There remains no missing-feedback defect on this surface.

## Suggested fix

None - no defect. (For the record, the success affordance the issue asked for already exists: a success toast + list invalidation in `useCreateUserOwnerMapping.onSuccess`.) A genuine *enhancement* (e.g. scroll/redirect to the newly-created row) would be a separate UX-polish item, not the correctness/UX trap this issue claimed; not filing one absent product signal.
