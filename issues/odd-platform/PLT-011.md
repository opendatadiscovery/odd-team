## REOPENED 2026-06-14 — the leak IS live; the rejection's premise was false

**This was wrongly rejected.** The 2026-06-10 rejection (retained below) declared the cross-locale leak
impossible because *"a key would have to be missing from `en.json` ... not the coverage pattern here"*
(see the Rejection's own line: *"The only way to surface a non-English fallback string would be a key
missing from `en.json` but present in `es`/`ch`"*) — assuming `en.json` is the most-complete catalogue.
**That premise is FALSE: PLT-215, filed the SAME DAY (2026-06-10), documents ~70 `t()` keys missing from
`en.json`.** The two items were two halves of one proof and were never joined — a rejection accepted on a
premise an open sibling finding already falsified.

The leak is now LIVE on `main` (verified 2026-06-14 during the CTRIB-011 review; maintainer spot-check):

- **Trigger commit `8b0155f7`** ("feat brazilian portuguese translation", #1564) added `br.json` AND
  inserted `br` into the chain: `fallbackLng: ['en','es','br','ch','fr','ua','hy']` (`i18n.ts`).
- Resolution order is `[activeLang, en, es, br, ch, fr, ua, hy]`. For a key absent from `en` (and `es`)
  but present in `br`, the chain resolves at **`br` → a Portuguese string for EVERY non-Brazilian user.**
- **Regression vs released:** at 0.27.13 (`ede5d277`, no `br` in the chain) these keys rendered the raw
  English key; now they render Portuguese.
- **Blast radius (SCRIPTED — keys in `br`−`en` ∩ `t('literal')` call sites = 4 rendered strings):**
  `Search by name` → "Buscar por nome" (DQ-dashboard filters / catalog Search / Terms search),
  `Query` → "Consulta", `Query examples` → "Exemplos de consulta", `Relationships` → "Relacionamentos"
  (DataModelling). (8 keys diverge `br`−`en`; 4 are actually `t()`-rendered. No Spanish leak — `es` carries
  no en-missing rendered key.)
- **Exposure:** `8b0155f7` is in NO release tag → unreleased; **ships in 0.28.0 (due 2026-06-22)** unfixed.

**Fix (unchanged from the Suggested-fix below — now load-bearing, not cosmetic):** `fallbackLng: 'en'`. A
fallback chain routed through *other* locales IS the leak; with `'en'`, an en-missing key renders the
English key, never a foreign language. Pair with **PLT-215** (complete `en.json` + a CI key-parity guard
that fails the build when a `t('literal')` key is absent from `en.json` — kills the precondition). Belongs
in one contributor change (GATE 1) before 0.28.0.

> The 2026-06-10 rejection below is retained as the historical record AND as case-law: a rejection whose
> load-bearing premise ("en is complete") is contradicted by an open sibling finding (PLT-215) must not be
> accepted. The i18n-leak retrospective (LSN, pending) cites this pair.

## Rejection (2026-06-10 — SUPERSEDED by the reopen above; retained as historical record + case-law)

Rejected as a false positive (2026-06-10 sweep). i18next prepends the active language and then walks `fallbackLng` with `en` FIRST (`getFallbackCodes` / `toResolveHierarchy`), so a missing key resolves to English - never to Spanish/Chinese/another locale; `en.json` is the most-complete catalogue so the chain always resolves. Only a cosmetic, non-idiomatic-array tidy remained, which is not a user-facing defect.

## What

The platform UI bootstraps i18next at `odd-platform-ui/src/locales/i18n.ts:30` with:

```ts
fallbackLng: ['en', 'es', 'ch', 'fr', 'ua', 'hy'],
```

The array literal is non-idiomatic - the conventional value for "fall back to English" is the string `'en'`. But the asserted user-visible consequence (French/Ukrainian/Armenian users seeing Spanish or Chinese strings) **does not occur**. An earlier revision claimed i18next walks this array "in order" so a French user hits `es.json` (Spanish) FIRST. That is false on two counts, both verified against the installed i18next source (`i18next@^23.2.0`):

1. **The active language is tried FIRST, before the fallback array.** `Translator.translate` resolves the lookup order via `LanguageUtils.toResolveHierarchy(code, fallbackCode)`, which builds `codes` starting with the active `code` and only THEN appends the fallback array (`node_modules/i18next/dist/cjs/i18next.js:873-895`, esp. the active-`code` push at `:888-890` followed by the `fallbackCodes.forEach` at `:891-893`). So a French user's order is `['fr', ...fallbacks]`.
2. **`en` is the FIRST entry in the fallback array.** `getFallbackCodes` returns an array fallback as-is (`i18next.js:860-873`, the `[object Array] -> return fallbacks` branch at `:864`). So the effective resolution chain for any active locale L is `[L, en, es, ch, fr, ua, hy]` (duplicates dropped). A key missing from L resolves to **`en` (English)**, never Spanish/Chinese.

For the asserted Spanish/Chinese leakage to happen, a key would have to be missing from BOTH the active locale AND `en` while present in `es`/`ch`. The coverage pattern is the opposite: `en.json` is the most-complete reference (highest key count of the six; quick count 2026-06-10: en=1684 vs es/ua/hy=1668 quote-tokens), so the chain effectively always resolves at `en` before reaching any later entry. The user-visible symptom is "missing key falls back to English" - the intended behaviour.

## Where

- `odd-platform-ui/src/locales/i18n.ts:30` - the `fallbackLng` array literal that ships to production (still accurate; verified 2026-06-10).
- `odd-platform-ui/src/locales/translations/{en,es,ch,fr,ua,hy}.json` - the six locale files; `en.json` is the most-complete (reference) locale.
- `node_modules/i18next/dist/cjs/i18next.js:860-895` - the `getFallbackCodes` + `toResolveHierarchy` resolution algorithm that falsifies the leakage claim.

## User-facing impact

- WHO: any user on a non-English locale (fr / ua / hy / es / ch) hitting a key missing from their active locale file.
- WHAT they do: navigate the UI normally; partial-coverage keys exist today (per F-043a / DOC-171).
- WHAT they observe: the missing string renders in **English**, not Spanish or Chinese. Verified by FE/source trace 2026-06-10: active language is resolved first (`i18next.js:888-893`) and `en` is the first fallback (`i18next.js:864` returns the array literal whose first element is `'en'`), so the chain resolves at `en` for any key present in `en.json`; `en.json` is the most-complete locale. There is NO cross-locale string leakage in the shipped UI. (The only way to surface a non-English fallback string would be a key missing from `en.json` but present in `es`/`ch` - not the coverage pattern here.) Pure code-structure fact; settled by reading the installed i18next resolution code.

## Why it matters

Low / cosmetic. The intent ("fall back to English when the active locale is missing a key") is already what happens, because the active language is prepended and `en` leads the fallback array. The array literal is simply non-idiomatic: the i18next-documented value for this intent is the string `'en'`, and the array form additionally lists `supportedLngs`-shaped content (the set of which-locales-exist) in the `fallbackLng` slot, which has no effect on resolution given `en` is first. Worth a one-line tidy for clarity / to prevent a future reorder accidentally putting a non-`en` locale first, but it is NOT a user-facing bug today.

Severity downgraded medium -> low: the load-bearing user-facing rationale (Spanish/Chinese mid-page) is falsified; what remains is a cosmetic code-quality cleanup with no observable symptom.

## Suggested fix

Cosmetic tidy (not a behaviour fix - the resolved behaviour is already English-first):

```ts
// odd-platform-ui/src/locales/i18n.ts:30
- fallbackLng: ['en', 'es', 'ch', 'fr', 'ua', 'hy'],
+ fallbackLng: 'en',
```

`fallbackLng: 'en'` matches the documented i18next pattern for *"fall back to English when a key is missing"* and removes the misleading list. The list-of-locales semantics belong on `supportedLngs`, a separate i18next option for input-validation of the user-selected locale that has no effect on missing-key fallback resolution. (Net runtime behaviour is unchanged - `en` is already the first fallback - so this is a readability / future-proofing change only.)

Surfaced during the Mode B run of the `docs/coverage/undocumented-features` scanner on 2026-05-27 (substrate `F-043` - Multilingual UI). The scanner's primary-source verification of `i18n.ts` flagged the array shape; the cross-locale-surprise consequence was an inferred facet on F-043.

Corrected 2026-06-10 (user-facing verification sweep): was "i18next walks this array in order, so a French user sees Spanish (es) FIRST, then Chinese (ch), ... before English"; actually i18next prepends the ACTIVE language and `en` is the FIRST fallback, so a missing key resolves to English - verified against the installed source (`node_modules/i18next/dist/cjs/i18next.js:860-895`; active-code push `:888-890`, fallback append `:891-893`, array-fallback returned as-is `:864`) and the locale coverage (`en.json` is the most-complete file). The asserted Spanish/Chinese leakage cannot occur for any key present in `en.json`. Title + What rewritten; severity medium -> low; reclassified from a user-facing i18n bug to a cosmetic code-quality tidy. This is the corpus failure mode (a UI symptom asserted without tracing the actual resolution code) caught in the sweep.
