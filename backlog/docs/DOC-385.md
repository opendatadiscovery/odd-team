## Description

The inline entity-description Markdown editor has **no dirty-form protection**: clicking **Cancel** discards every unsaved edit silently, with no confirm-discard prompt, no autosave, and no draft persistence. An operator part-way through rewriting a long description who clicks Cancel (or toggles edit mode off) loses the in-progress text with no warning. The entity-description page documents the authoring workflow but does not state this.

Verified by read:
- `useTermWiki.ts:46-49` — `toggleEditMode` runs `setEditMode(!editMode); setInternalDescription(description);` — toggling edit mode **unconditionally** re-seeds the editor state from `description` (the last-saved prop), throwing away whatever the operator had typed. There is no comparison of current-vs-saved, no guard, no prompt.
- `InternalDescriptionEdit.tsx:35` — the **Cancel** button is wired straight to `toggleEditMode` (`<Button text='Cancel' onClick={toggleEditMode} .../>`), so Cancel = "discard and re-sync to last-saved" with no intermediate confirmation. (Save is a separate handler, `handleUpdateDescription`, at line 31.)

This is the entity-description sibling of a hazard already documented elsewhere for **other** surfaces — DOC-193 covers the per-column composer's unsaved-changes hazard (`DatasetFieldOverview.tsx`), and DOC-232 covers the Query Example dialog's draft-loss on close (`QueryExampleForm.tsx`). Neither covers the entity-description editor, which is its own component (`InternalDescriptionEdit` + `useTermWiki`). This item closes that gap for the entity-description surface.
