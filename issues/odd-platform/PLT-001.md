## What

`S2sTokenProvider.isValidToken(String token)` dereferences the internal `s2sToken` field without a null check. When server-to-server auth is unconfigured (`auth.s2s.enabled=false` / unset), the `@Value("${auth.s2s.token:#{null}}")` binding leaves `s2sToken` null, and `s2sToken.equals(token)` throws `NullPointerException` for any non-blank `token`.

The sole caller, `S2sAuthenticationFilter`, is a global Spring WebFlux `WebFilter` annotated `@Component` with **no** `@ConditionalOnProperty`. In WebFlux, any `WebFilter` bean is auto-registered into the global filter chain regardless of which `SecurityWebFilterChain` is active - so the filter runs on **every** request even under `auth.type=DISABLED` (the shipped default), where the security config never gates it. A request carrying any `X-API-Key` header therefore returns **HTTP 500** on every endpoint.

Verified live against the shipped default (`AUTH_TYPE=DISABLED`, `auth.s2s` unset): a request with any `X-API-Key` header returns 500 on endpoints that are 200 without the header. Any unauthenticated caller can turn any endpoint into a 500 by adding one header - a trivial unauthenticated denial-of-service on the default configuration.

## Where

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/auth/S2sTokenProvider.java:15-21`

```java
public boolean isValidToken(final String token) {
    if (StringUtils.isBlank(token)) {
        return false;
    }
    return s2sToken.equals(token);   // NPE when s2sToken is null
}
```

The `@Value` bindings are declared on lines 10-13 (`s2sToken` defaults to `null`; `s2sEnabled` defaults to `false`). The caller `S2sAuthenticationFilter` (`auth/S2sAuthenticationFilter.java:17-19`) is a `@Component implements WebFilter` with no `@ConditionalOnProperty`, so it runs for every auth mode.

## User-facing impact

User: any unauthenticated API consumer. Driven live against the shipped default (`AUTH_TYPE=DISABLED`, `auth.s2s` unset): `GET /api/dataentities/classes` returns 200 normally, but the same request carrying any `X-API-Key` header returns HTTP 500. So any caller can turn any endpoint into a 500 by adding one arbitrary header - an unauthenticated denial-of-service, no credential and no token knowledge required. (Verified 2026-06-09, local stack.)

## Why it matters

- **Reachable on the shipped default.** Under `auth.type=DISABLED` with `auth.s2s` unset, any request carrying an `X-API-Key` header returns HTTP 500 - verified live. This is an unauthenticated denial-of-service: the caller needs no credential and no knowledge of any token; one arbitrary header value crashes the request, on every endpoint.
- Defensive null handling on a public method of a security-sensitive component is a baseline expectation.
- The fix is a one-line change with zero behavioural risk: for `auth.s2s.enabled=true` behaviour is unchanged; for the unconfigured case the filter correctly becomes a pass-through instead of crashing.

## Suggested fix

Guard the null explicitly, or use a null-safe comparison:

```java
public boolean isValidToken(final String token) {
    if (StringUtils.isBlank(token) || StringUtils.isBlank(s2sToken)) {
        return false;
    }
    return s2sToken.equals(token);
}
```

A deeper, optional hardening is to gate `S2sAuthenticationFilter`'s registration on `auth.s2s.enabled` so the filter does not run at all when S2S is off - removing the per-request overhead and the surface entirely under `DISABLED`.

**How to verify:** a request carrying any `X-API-Key` header under `AUTH_TYPE=DISABLED` returns its normal response, not HTTP 500. Add a unit test asserting `isValidToken("anything")` returns `false` when the configured token is null/blank.

## How discovered

Surfaced during a consumer-read audit of the server-to-server authentication filter chain (`S2sAuthenticationFilter` -> `S2sTokenProvider`) while reviewing the documented S2S auth posture, and reproduced live against the shipped `AUTH_TYPE=DISABLED` default.
