## What

`WithPermissions` is named like a render-gate but behaves as a permission-context provider. The three render branches at `WithPermissions.tsx:12-49` unconditionally render the child - the wrapper exposes the permission state via context; descendants must consult the context defensively. If a descendant doesn't consult the context, OR if the context isn't hydrated on first render, the gated control briefly appears to unprivileged users.

The pattern is **cross-cutting**: surfaces in Alerts (`DataEntityAlerts.tsx:53` wraps the halt-config Button), Activity (F-021 batch-ZL note #6), Discussions, every place a control sits behind `WithPermissions`. **The wrapper's NAME implies a render-gate; the wrapper's BEHAVIOR is a context-provider.**

## Why it matters

The wrapper's **name vs behavior mismatch** is a structural defect that propagates across the UI surface:

1. **Pattern of breakage** - every place WithPermissions wraps a control, two failure modes exist: (a) the descendant doesn't consult the context (no gate enforced); (b) the context is briefly empty on first render (control flashes visible to unprivileged users). Both are silent - no compilation error, no runtime exception, no security log.

2. **Maintainer cognitive load** - a contributor reading `<WithPermissions>...</WithPermissions>` reasonably assumes a gate. The codebase has wrappers that name-promise gating but only provide context; the contributor's intuition fights the actual semantics on every change.

3. **F-014d is the canonical instance** - Notification Settings halt-config Button briefly visible to unprivileged users on first render. F-021 batch-ZL note #6 captures the cross-cutting pattern; this PLT is the structural fix.

Severity is MEDIUM because:
- Each instance is small (brief flash on first render; missed gate is a UX bug not a backend-permission-bypass);
- The cross-cutting nature compounds - fixing every instance individually misses the class; fixing the wrapper closes all of them.

## Suggested fix

**Three options; recommend Option B as the structural fix.**

**Option A - rename WithPermissions to make the context-vs-gate distinction explicit.** Cosmetic-only; the underlying semantic gap stays.

```
WithPermissions  ->  PermissionContext   (for the context shape)
WithPermissions  ->  RequirePermission   (for a true render-block; new component)
```

Existing consumers migrate to one of the two; the name tells the maintainer what to expect.

**Option B (recommended) - refactor WithPermissions to short-circuit render when permission absent.** Three render branches collapse to two:

```tsx
function WithPermissions({ permissionTo, children, fallback = null }) {
  const status = useFetchResourcePermissions(...);
  if (status === 'loading') return fallback;   // safer: render fallback during load
  if (status === 'success' && !permissions[permissionTo]) return fallback;
  if (status === 'error') return fallback;     // fail closed
  return (
    <PermissionContext.Provider value={{ permissions }}>
      {children}
    </PermissionContext.Provider>
  );
}
```

`fallback` defaults to `null` (button hidden) but consumers can pass an empty-state component. **Fails closed on error** - the structurally correct posture. Loading state hides the control to prevent the brief flash.

Migration: existing call sites work unchanged for the common "hide on absent" case; consumers that wanted the legacy context-only behaviour pass `fallback={children}` to opt back in (rare).

**Option C - JSDoc on the wrapper documenting the context-not-gate semantics.** Doc-only; doesn't fix the propagating defect.
