## What

Custom Metadata is a paired feature surface - F-013 (per-entity VALUE write) + F-046 (FIELD catalogue read). Five operator-visible defects span both halves. The OpenAPI contract, the UI toast, the schema-default convention, and the audit-feed enum surface all silently lie about the implementation's actual behaviour.

**Defect 1 - Silent UPDATE-not-UPSERT (F-013b).** `ReactiveMetadataFieldValueRepositoryImpl.java:94-104` is pure UPDATE:
```java
DSL.update(METADATA_FIELD_VALUE)
   .set(VALUE, pojo.getValue())
   .set(ACTIVE, pojo.getActive())
   .where(METADATA_FIELD_ID.eq(?).and(DATA_ENTITY_ID.eq(?)))
   .returning()
```
Missing `(entity_id, field_id)` pair -> zero-row UPDATE -> Mono empty -> silent 200 OK with empty body. UI displays "Metadata successfully updated." (`metadata.thunks.ts:51-54`). OpenAPI declares operationId "upsert" - implies replace-or-create semantics. **Reconciliation pipelines silently lose writes.**

**Defect 2 - ACTIVE column dropped to NULL on every UPDATE (F-013c) - latent data-cleanliness, NOT an invisibility bug.** `ReactiveMetadataFieldValueRepositoryImpl.java:98`: `.set(METADATA_FIELD_VALUE.ACTIVE, pojo.getActive())`. The caller (`DataEntityServiceImpl.java:292-295`) builds the pojo with only `dataEntityId`, `metadataFieldId`, `value` - it never calls `.setActive(true)`, so `pojo.getActive()` is boxed `Boolean` null and the UPDATE writes explicit NULL. DB DEFAULT TRUE applies on INSERT only (`V0_0_1__init.sql:180`). **The claimed "invisibility" consequence does NOT occur - verified 2026-06-10:** grep across the repository layer finds NO reader that filters `METADATA_FIELD_VALUE.ACTIVE` (the only reference to the column anywhere is the `.set(...)` write on `:98`); the read path (`ReactiveMetadataFieldValueRepositoryImpl` get/list, joined on `METADATA_FIELD_ID` only) does not constrain on ACTIVE. So an edited row is still read back and rendered. The defect is real (a column that should be TRUE silently becomes NULL on every edit, dirtying the data and breaking any FUTURE reader that assumes `active = TRUE`) but it is latent: no current user-facing surface hides the row. An earlier revision called this a "latent invisibility bug" with "every edit hides the row if any reader filters strictly TRUE" - the conditional was never confirmed and is false today.

**Defect 3 - pageInfo theatre + no LIMIT on catalogue read (F-046a).** `MetadataFieldMapperImpl.java:28-33` constructs `new PageInfo().total((long) pojos.size()).hasNext(false)` - total is items.length, hasNext is hardcoded false. SQL at `ReactiveMetadataFieldRepositoryImpl.java:44-56` is unbounded (no LIMIT/OFFSET/ORDER BY). Production deployments with 10K+ INTERNAL fields see a 1-2 MB response on every autocomplete keystroke. SDK clients written from the OpenAPI spec build "load more" workflows that never fire.

**Defect 4 - No CUSTOM_METADATA_FIELD_READ permission (F-046b).** `GET /api/metadata/fields` has NO entry in `SecurityConstants.SECURITY_RULES` - falls through to `.authenticated()`. Under `auth.type=DISABLED`, anonymous callers enumerate every INTERNAL field name in the deployment. Multi-team deployments expose operator-named field schemas (`finance_cost_centre`, `marketing_attribution`, `pii_redaction_rule`) across team boundaries. Compounds with the auto-create-on-miss side-channel: any user with `DATA_ENTITY_CUSTOM_METADATA_UPDATE` on ONE entity can MINT new catalogue entries visible to every authenticated user.

**Defect 5 - Dead CUSTOM_METADATA_* ActivityEventTypeDto enum values.** `ActivityEventTypeDto.java` carries `CUSTOM_METADATA_CREATED`, `CUSTOM_METADATA_UPDATED`, `CUSTOM_METADATA_DELETED` - all three are **dead** (no code path emits them). Auditors querying activity for custom-metadata mutations find nothing despite the surface API suggesting otherwise.

## User-facing impact

- **Defect 1 (silent UPDATE-not-UPSERT) - the load-bearing one, scoped to API consumers.** A direct caller of `PUT /api/dataentities/{id}/metadata/{field_id}` (operationId `upsert`, so SDK users reasonably expect create-or-update) for a (data_entity_id, metadata_field_id) pair that has no existing row gets HTTP 200 with an empty body and NO row written - the UPDATE matches zero rows -> empty Mono (`ReactiveMetadataFieldValueRepositoryImpl.java:95-104` + service chain `DataEntityServiceImpl.java:287-305`). Reconciliation pipelines silently lose writes. **The platform UI does NOT hit this path** - verified 2026-06-10: the FE has SEPARATE thunks, `createDataEntityCustomMetadata` (POST, for new values) and `updateDataEntityCustomMetadata` (the upsert endpoint, only for editing an existing value) (`metadata.thunks.ts:13-56`); so a UI user always has a row first. The "Metadata successfully updated." toast (`:53`) fires on the 200, but the UI's update only ever targets an existing pair, so the toast is truthful FOR THE UI. The silent-success-on-missing-pair is an API-contract defect, not a UI-user defect.
- **Defect 2 (ACTIVE -> NULL):** no user-facing symptom today (see corrected text above) - latent data-cleanliness only.
- **Defect 3 (pageInfo theatre + unbounded read):** a user typing in a custom-metadata field-name autocomplete triggers `GET /api/metadata/fields`, which returns EVERY internal field (no LIMIT) with `pageInfo.total = items.length, hasNext = false` (`MetadataFieldMapperImpl.java:28-33`). On a large deployment this is a heavy response per keystroke; SDK clients that build "load more" off `hasNext` never page. Verified by BE trace 2026-06-10.
- **Defect 4 (no READ permission):** `GET /api/metadata/fields` is gated only by the default `.authenticated()` (`AuthorizationCustomizer.java:30`; no per-endpoint rule in SecurityConstants). Under `auth.type=DISABLED` any caller enumerates all internal field names. Note (verified 2026-06-10): this is the SAME posture as every other read endpoint lacking a SecurityRule under DISABLED - it is not uniquely exposed, but the catalogue can carry operator-named vocabulary, which is why a dedicated read permission is still worth it.
- **Defect 5 (dead audit events):** an auditor filtering the Activity Feed for custom-metadata changes finds nothing - the three `CUSTOM_METADATA_*` enum values have no emitter (`ActivityEventTypeDto.java:17-19`; no annotation/emit site found 2026-06-10). Corroborating signal: the Activity Feed FE explicitly EXCLUDES these three from the event-type filter dropdown (`Activity/Filters/Filters.tsx:39-41`), consistent with them being dead.

## Suggested fix (five independent threads)

**Thread A - True UPSERT semantics (Defect 1).** Either:
- Switch to `INSERT ... ON CONFLICT (data_entity_id, metadata_field_id) DO UPDATE` (the right shape for the operationId).
- Rename operationId to "updateMetadataFieldValue" + add `.switchIfEmpty(Mono.error(new NotFoundException(...)))` -> 404 on missing pair. Less invasive but is a breaking change for SDK consumers.

Option A1 (true UPSERT) preserves the OpenAPI contract.

**Thread B - Preserve ACTIVE (Defect 2).** Two options:
- `pojo.setActive(true)` in the service before the UPDATE (preserves DEFAULT TRUE semantics).
- Surgical UPDATE excluding the ACTIVE column when not explicitly set.

Option B1 is simpler. After the fix, audit downstream consumers of `active` to confirm no `IS NULL` filters were being relied upon as a deactivation signal.

**Thread C - Real pagination (Defect 3).** Implement LIMIT/OFFSET at SQL + accurate total via `COUNT(*)` over the filtered set + truthful hasNext. OR drop PageInfo from the OpenAPI schema if pagination is genuinely not desired (and document the unbounded contract). Recommend real pagination - the autocomplete keystroke load is operator-load-bearing.

**Thread D - Read permission (Defect 4).** Introduce `CUSTOM_METADATA_FIELD_READ` permission OR document the catalog-wide enumeration posture explicitly. Recommend the permission - the catalogue carries operator-named vocabulary that can encode PII (per the F-046b finding's enumeration example). Backwards-compat: default existing Policies grant the new permission to anyone who previously held `DATA_ENTITY_CUSTOM_METADATA_UPDATE` (the operator likely already had implicit read).

**Thread E - Revive CUSTOM_METADATA_* events (Defect 5).** Add `@ActivityLog(event = CUSTOM_METADATA_CREATED, ...)` etc. to the service methods. Emit before/after payloads in the DatasetField pattern (cross-link PLT-024 + PLT-026 for cross-pillar harmonisation). The enum values exist; the work is annotating the call sites.

## Operator impact

- Reconciliation pipelines (direct API consumers) silently lose writes on a missing pair - Defect 1. (UI users unaffected - separate create/update thunks.)
- Custom-metadata edits dirty the `active` column to NULL on every UPDATE - Defect 2. No user-visible symptom today (no reader filters on `active`); latent risk for any future `active = TRUE` reader.
- Autocomplete keystroke load on multi-team deployments - Defect 3.
- Catalogue field-name enumeration to any authenticated caller (anonymous under DISABLED) + drive-by catalogue minting - Defect 4.
- Compliance auditors find no record of custom-metadata mutations - Defect 5.

## How discovered

Surfaced during the 2026-05-27 Mode B batch-10 triage (F-013a/b/c + F-046a/b). Corrected 2026-06-10 (user-facing verification sweep):
- Defect 2: was "latent invisibility bug - every edit hides the row if any reader filters strictly TRUE"; actually no reader filters `METADATA_FIELD_VALUE.ACTIVE` at all (the only reference is the `:98` write), so nothing is hidden today. Re-scoped to latent data-cleanliness.
- Defect 1: confirmed, and scoped precisely to direct API consumers - the UI uses separate create/update thunks (`metadata.thunks.ts:13-56`) and never hits the missing-pair path, so the success toast is truthful for the UI.
- Defect 4: confirmed, with context that the ungated-read posture is shared by other endpoints under DISABLED (not unique to this one).
- Defects 3 + 5: confirmed by code trace; Defect 5 corroborated by the FE excluding the dead events from the Activity filter (`Activity/Filters/Filters.tsx:39-41`).
- Severity unchanged (HIGH): Defect 1 (silent write loss for reconciliation) + Defect 3 (unbounded per-keystroke read) carry it. Only the Defect 2 consequence was over-stated; corrected. Same failure mode as PLT-176: an "invisibility" consequence asserted without verifying that any reader actually filters on the column.
