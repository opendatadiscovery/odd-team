# IngestionController.postDataEntityList — semantic understanding

## understanding

`postDataEntityList` is the canonical S2S ingestion entry point: collectors `POST /ingestion/entities` with a `DataEntityList` payload (one `data_source_oddrn` + a list of `DataEntity` items) and the controller hands the deserialised payload to `IngestionServiceImpl.ingest(...)` inside a reactive pipeline that returns `200 OK` (`ResponseEntity.ok().build()`) on success. The controller itself carries **no** authorization annotation (no `@PreAuthorize`, no programmatic `permissionService.hasPermission(...)`), no payload size validation beyond the global `spring.codec.max-in-memory-size: 20MB` cap, no rate limit, and no idempotency key — authentication is delegated entirely to the path-scoped `IngestionDataEntitiesFilter` WebFilter (gated by `auth.ingestion.filter.enabled`, which defaults to `false`). The only payload-level guard is `CollectionUtils.isNotEmpty(del.getItems())`, which surfaces empty lists as a 400 via `BadUserRequestException("Ingestion payload is empty")`.

- entities: [`DataEntityList` (request body — `data_source_oddrn` + `items: List<DataEntity>`), `IngestionService` (the downstream worker — `ReactiveTransactional`), `dataSourceId` (resolved from the payload's `data_source_oddrn`), `Mono<ResponseEntity<Void>>` (reactive response shape), `BadUserRequestException` (HTTP 400 wrapper)]
- operations: [accept-data-entity-list, reject-empty-payload-400, delegate-to-ingestion-service, return-200-OK]
- invariants:
  - "Controller has no authorization at the method level — neither `@PreAuthorize` on `postDataEntityList` nor on the `IngestionApi` interface it implements (the interface is OpenAPI-generated and contains no security annotations). Authorization for this endpoint lives EXCLUSIVELY in `IngestionDataEntitiesFilter` and is gated by `auth.ingestion.filter.enabled` (defaults `false` per application.yml:48)."
  - "Empty `items` list short-circuits to 400 `BadUserRequestException(\"Ingestion payload is empty\")` BEFORE the service is invoked — but a null `items` field or a payload with `items: []` plus an invalid `data_source_oddrn` does NOT 400 at the controller; it propagates to `IngestionServiceImpl.ingest(...)` which surfaces `NotFoundException(\"dataSource\", oddrn)` (HTTP 5xx via default reactive error handler — there is no `@ExceptionHandler(NotFoundException)` returning 404 on the ingestion path)."
  - "Controller returns `200 OK` (`ResponseEntity.ok().build()`, line 44). The OpenAPI specification at `opendatadiscovery-specification/specification/odd_api.yaml:23-25` declares the success response as `201 Created`. Code disagrees with spec — `200 OK` is what tests assert (`BaseIngestionTest.java:79` — `expectStatus().isOk()`). The spec drift has shipped."
  - "Datasource scoping is **payload-driven, NOT token-driven**: `IngestionServiceImpl.ingest(...)` (line 68) resolves the datasource via `dataSourceRepository.getIdByOddrnForUpdate(dataEntityList.getDataSourceOddrn())` — i.e. the **caller chooses** which datasource's ODDRN to ingest into, by writing it in the request body. When the `IngestionDataEntitiesFilter` is active, the filter validates the bearer token against the datasource named in the payload — so a valid collector A's token authenticates only datasources A is registered against. When the filter is OFF (the default), there is no cross-tenant check at all."
  - "Body parsing is REACTIVE — the method signature takes `Mono<DataEntityList> dataEntityList` (line 38), so the WebFlux runtime defers deserialisation until the inner subscriber pulls; in practice `flatMap(ingestionService::ingest)` triggers the parse on the first signal. The full body is buffered to JSON via `spring.codec.max-in-memory-size: 20MB` (application.yml:15) — exceeding that cap throws `DataBufferLimitException` → 500 to the caller (not 413)."
- audiences: [odd-collector / odd-collector-sdk HTTP clients pushing data-entity definitions, odd-platform operators standing up an ingestion pipeline, security reviewers auditing the S2S surface]

## security

- **auth_mode_relevance**: `S2S — via path-scoped IngestionDataEntitiesFilter, gated by auth.ingestion.filter.enabled (default false)`. The four UI auth modes (`DISABLED | LOGIN_FORM | OAUTH2 | LDAP`) do **NOT** protect this path — `/ingestion/**` is in `SecurityConstants.WHITELIST_PATHS` (SecurityConstants.java:95-96), enforced for OAUTH2/LDAP via `AuthorizationCustomizer.java:22` and for LOGIN_FORM via the `permittedPaths` in `LoginFormSecurityConfiguration.java`. Authentication on this endpoint is **EXCLUSIVELY** the responsibility of `IngestionDataEntitiesFilter`. Per the live S2S doc (WebFetched 2026-05-12), the operator-facing recommendation conflates `auth.s2s.enabled` (global X-API-Key filter, single shared token) with `auth.ingestion.filter.enabled` (path-scoped Authorization: Bearer filter, per-datasource tokens) — the codebase composes them, but the docs do not explain the difference.
- **ingestion_filter_relevance**: `YES — this IS the endpoint the filter is built to protect`. `IngestionDataEntitiesFilter.java:28` hard-codes the path matcher to `POST /ingestion/entities`, which is exactly this controller-method's surface. The controller itself does no auth; the filter is the only gate. When `auth.ingestion.filter.enabled=false` (default), the filter bean is not registered and the endpoint is reachable without credentials.
- **authorization_assertions**: `[]` — none at the controller-method layer. There is no `@PreAuthorize`, no programmatic `permissionService.hasPermission(...)`, no inline auth check (verified: line 37-45). The `IngestionApi` interface this method overrides is OpenAPI-generated and carries no security annotations either. The only enforcement layer is the `IngestionDataEntitiesFilter` WebFilter (sibling sidecar) — and only when its gating property is `true`.
- **owner_scoping**: `N/A — ingestion path is not owner-scoped`. The platform's Owner / User-owner-association model applies to UI/API CRUD operations; ingestion is a collector-to-platform machine-to-machine flow keyed by datasource ODDRN, not by Owner. Ingested entities are not stamped with `created_by_owner = <calling collector's owner>`; the calling collector's TOKEN is identity-of-collector, not identity-of-user. Ownership is established later in the platform's UI/API flows.

## performance

- **hot_paths**:
  - "every `POST /ingestion/entities` request incurs: 1 reactive body-collect (up to 20 MB), 1 Jackson deserialise to `DataEntityList`, 1 empty-check, 1 service-level call into `IngestionServiceImpl.ingest` which executes a synchronous `@ReactiveTransactional` pipeline (datasource lookup → entity upsert → processor chain → OTLP metric export) — the controller-side cost is dominated by deserialisation and the synchronous-wait on the service pipeline, not by the controller's own logic." — evidence: IngestionController.java:37-45 + IngestionServiceImpl.java:65-74
  - "when `auth.ingestion.filter.enabled=true`, the request body is parsed TWICE — once by the filter (for `dataSourceOddrn` extraction; sibling sidecar performance.throughput_characteristics[1]) and once by the controller's `Mono<DataEntityList>` binding. The controller side cannot avoid this; it is structural to the filter-then-controller pipeline." — evidence: IngestionDataEntitiesFilter.java:40 + IngestionController.java:38
- **throughput_characteristics**:
  - "Per-request single-payload semantics — one `DataEntityList` per HTTP call. Collectors typically batch their per-tick scan results into one POST (odd-collector / odd-collector-sdk pattern), so a typical request carries hundreds-to-thousands of `DataEntity` items in one payload, not one entity per call."
  - "Synchronous response — the controller does NOT return 202 Accepted + background processing. The HTTP connection is held open for the duration of: body parse → datasource resolve → entity dedup-and-upsert (with `bulkUpdate` and `bulkCreate` operations inside the transaction) → processor chain → OTLP export. A slow Postgres or saturated R2DBC pool surfaces as HTTP timeouts on the collector side, prompting retries — which compound load."
  - "Reactive `Mono` signature — non-blocking from the WebFlux perspective, but the `@ReactiveTransactional` boundary serialises the DB writes inside one transaction. Inside the transaction, multiple `bulkUpdate` / `bulkCreate` calls fire sequentially."
- **resource_allocation**:
  - "Full request body buffered in memory up to `spring.codec.max-in-memory-size: 20MB` (application.yml:14-15) during deserialisation. When the filter is active, the body is buffered TWICE (filter-side + controller-side per the WebFlux pipeline). Per-request heap allocation: ~ 20 MB cap + Jackson POJO graph for the parsed `DataEntityList`." — evidence: application.yml:14-15 + IngestionController.java:38 + IngestionDataEntitiesFilter.java:37-60
  - "Transaction lifetime is the entire ingestion duration. Long-running ingestions hold Postgres locks (on the matched datasource row, via `getIdByOddrnForUpdate` — `SELECT ... FOR UPDATE`) for the call duration, blocking concurrent ingestions for the same datasource." — evidence: IngestionServiceImpl.java:68 (`getIdByOddrnForUpdate` — note the `ForUpdate` suffix) + IngestionServiceImpl.java:65-74 (transaction scope spans the entire pipeline)
  - "OTLP metric export runs INSIDE the per-request flow (`.flatMap(otlpMetricService::exportMetrics)`, IngestionServiceImpl.java:72). Each request triggers an outbound metric push; metric backend latency directly affects ingestion latency."
- **scaling_characteristics**:
  - "Stateless controller — instances scale horizontally without coordination. No instance fields beyond the four injected services (line 32-35)."
  - "Per-datasource row-level lock (via `getIdByOddrnForUpdate`) serialises concurrent ingestions targeting the SAME datasource. Cross-datasource ingestions are not serialised — different collectors / datasources scale linearly." — evidence: IngestionServiceImpl.java:68
  - "No pagination on input — a single payload can contain thousands of `DataEntity` items (bounded only by the 20 MB body cap). The downstream `bulkUpdate`/`bulkCreate` operations partition by ODDRN existence (line 96-145), so the per-item cost is amortised, but the per-request memory footprint scales linearly with payload size."
- **known_performance_gaps**:
  - "Synchronous-blocking-on-pipeline: there is no async-accept mode. A collector tick that ingests 50 MB of data (capped to 20 MB per request, so split across multiple requests) holds HTTP connections open for the full pipeline duration. A 202+queue mode (write payload to a durable queue, process asynchronously, expose a status-check endpoint) would decouple intake from processing. Cost: persistence-layer complexity + back-channel for ingestion-failure reporting." — evidence: IngestionController.java:38-44 (synchronous `.thenReturn`) + IngestionServiceImpl.java:65-74 (full pipeline before `.then()`) — severity: LOW (operational characteristic; severity depends on workload)
  - "Duplicate body parse when filter is active — see sibling sidecar (IngestionDataEntitiesFilter performance.known_performance_gaps[0]). Controller-side cannot fix; structural to the filter-then-controller WebFlux pipeline." — evidence: IngestionDataEntitiesFilter.java:40 + IngestionController.java:38 — severity: MEDIUM (cross-references the filter sidecar; not unique to this node)
  - "OTLP metric export coupled to per-request hot path. `IngestionServiceImpl.ingest` (line 72) calls `otlpMetricService::exportMetrics` inside the request flow. A slow / unhealthy OTLP backend slows every ingestion request. No timeout / circuit-breaker on the OTLP call is visible in the service flow. A backgrounded metric export would decouple metric-backend health from ingestion latency." — evidence: IngestionServiceImpl.java:72 — severity: MEDIUM
