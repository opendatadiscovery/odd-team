## What

The lineage read endpoints on `DataEntityController` carry two operator-critical defects:

1. **Unset `lineage_depth` -> NPE -> HTTP 500** (the two per-entity endpoints `getDataEntityDownstreamLineage` + `getDataEntityUpstreamLineage`). The controller passes a boxed `Integer lineageDepth` into `LineageServiceImpl.getLineage`, which takes a primitive `int`; a missing `lineage_depth` autounboxes `null` and throws `NullPointerException` synchronously in the controller method *before* the service's reactive chain is entered. The global `@RestControllerAdvice` catch-all (`ControllerAdvice.java:61-66`, `@ExceptionHandler(Exception.class)` -> `INTERNAL_SERVER_ERROR`) maps that NPE to **HTTP 500**. The generated contract declares `lineage_depth` `required=false` with NO `defaultValue` (so omitting it yields `null`, not a default depth) and `@Min(1)` but NO `@Max` - so an arbitrarily large value is forwarded unclamped into the recursive CTE, which has no cycle guard and `.collectList()`-materialises the full graph in JVM heap - a memory/CPU amplification vector on branchy/diamond topologies. (The third endpoint, `getDataEntityGroupsLineage`, takes NO `lineage_depth` param, so the NPE does not apply to it; its DEG traversal is recursive Java with a `handledOddrns` visited-set - `LineageServiceImpl:218-233` - so it is NOT exposed to the no-cycle-guard amplification either. The unbounded/no-cycle-guard concern is specific to the per-entity CTE path.)
2. **No authorization on any lineage endpoint** (all three: downstream, upstream, DEG `/lineage`). None has a `SECURITY_RULES` entry (grep of `SecurityConstants` for `lineage` is zero), so all fall through to the catch-all `.pathMatchers("/**").authenticated()`, and the service performs no owner/anchor check (`LineageServiceImpl` has no `AuthIdentityProvider` field). Any authenticated user who knows an entity-id or DEG-id reads the full reachable cross-owner lineage subgraph (other teams' pipeline structure). Under the shipped `auth.type=DISABLED` default this is anonymously reachable. The DEG `/lineage` path is strictly wider blast radius - it enumerates the cross-owner co-membership graph of the whole catalogue.

Sources: HARVEST-030, HARVEST-031, HARVEST-032, HARVEST-043, HARVEST-044 (doc-understanding harvest, 2026-05-29). Doc caveat tracked at `backlog/docs/DOC-293.md`.

## User-facing impact

Verified-trace 2026-06-10 (controller, service, generated contract, ControllerAdvice, repository CTE, SecurityConstants all read).

- **NPE -> 500 (Defect 1):** code-settled and complete. A spec-compliant `GET /api/dataentities/{id}/lineage/downstream` (or `/upstream`) WITHOUT `lineage_depth` autounboxes `null` into the primitive `int` at the controller call site (`:261`/`:271`), throwing `NullPointerException` synchronously; `ControllerAdvice`'s `Exception` catch-all returns HTTP 500 (`:61-66`). The most common first call against the endpoint fails with an opaque 500 - confirmed by tracing, no run needed. This matches the prompt's "autoboxing NPE -> catch-all -> 500" pattern exactly.
- **No `@Max` / unbounded recursion (Defect 1 cont.):** code-settled. `@Min(1)` is present, `@Max` is absent; `LineageDepth.of(int)` performs no clamp; the recursive CTE terminates only on `tDepth < depth` with no visited-set. Real DOS-amplification requires a sufficiently branchy/cyclic graph (runtime-only to *demonstrate*), but the absence of every guard is settled in source.
- **Zero RBAC (Defect 2):** code-settled wiring; *anonymously reachable under the shipped `auth.type=DISABLED` default*. No SecurityRule on any lineage route + no `AuthIdentityProvider` in the service = any authenticated user (or anyone, under DISABLED) reads cross-owner lineage. Under non-DISABLED auth it remains readable by any authenticated user (no per-owner scope exists to enforce). The cross-tenant *exposure* is the settled fact; what a specific deployment's operator considers "hidden" is the runtime framing.

No FE surface is load-bearing here - these are API-contract / authz defects a third-party consumer hits directly. Remaining optional runtime check: a probe issuing the no-depth call to capture the literal 500 body, and a deep-graph call to measure heap growth.

## Why it matters

A third-party API consumer following the published reference (which advertises `lineage_depth` as optional and softens the unset case to "undefined today") makes a spec-compliant call and gets an opaque HTTP 500 in production - the most common first call against the endpoint fails. Separately, the zero-RBAC posture means lineage - which reveals the shape of other teams' data pipelines - is readable by any authenticated user, and anonymously under the shipped `DISABLED` default. The DEG endpoint widens this to whole-catalogue co-membership enumeration. The unbounded depth + no-cycle-guard recursion is a denial-of-service amplifier on real DAGs. This is the LSN-001/002 class on both the crash and the silent over-exposure.

## Suggested fix

- Make the controller parameter a boxed `Integer` end-to-end and either (a) supply a server-side default depth when null, or (b) reject null with a 400 and a clear message - never let it reach the primitive and NPE. Document whichever behaviour ships.
- Add `@Max(...)` on the controller parameter and a defensive clamp at the service tier; add a cycle guard / visited-set to the recursive CTE so diamond topologies terminate without row amplification.
- Add `SECURITY_RULES` entries (or a programmatic owner-scope check via `AuthIdentityProvider`) on all three lineage endpoints; the DEG endpoint in particular should be owner/anchor-scoped given its wider blast radius.
