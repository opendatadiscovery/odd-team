## What

`SecurityConstants` registers two path-matcher SecurityRule entries for the Term-to-Entity link operation using the **singular** path `/api/dataentities/{data_entity_id}/term`. The actual endpoint exposed via the OpenAPI spec and serviced by `DataEntityController` uses the **plural** path `/api/dataentities/{data_entity_id}/terms`. The `PathPatternParserServerWebExchangeMatcher` never matches the live request path -> both `DATA_ENTITY_ADD_TERM` (POST) and `DATA_ENTITY_DELETE_TERM` (DELETE) gates silently fall through to the global `.authenticated()` rule.

**Result: any authenticated user under LOGIN_FORM / OAUTH2 / LDAP can link OR unlink any term to any data entity, regardless of how Policies are configured for these two permissions.**

## Where

```
odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/auth/util/SecurityConstants.java:238
  new PathPatternParserServerWebExchangeMatcher(
      "/api/dataentities/{data_entity_id}/term", POST)        // <-- SINGULAR `term`

odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/auth/util/SecurityConstants.java:241
  new PathPatternParserServerWebExchangeMatcher(
      "/api/dataentities/{data_entity_id}/term/{term_id}", DELETE)   // <-- SINGULAR `term` again
```

vs. the actual endpoints:

```
odd-platform-specification/openapi.yaml:973
  /api/dataentities/{data_entity_id}/terms:                   # <-- PLURAL `terms`
    post: ...

odd-platform-specification/openapi.yaml:1042
  /api/dataentities/{data_entity_id}/terms/{term_id}:         # <-- PLURAL `terms` again
    delete: ...
```

The Java controller (`DataEntityController.addDataEntityTerm`, `:150`, and `DataEntityController.deleteTermFromDataEntity`, `:159`) services the plural path per the spec; the SecurityRule matcher binds to the singular path; the match never happens. Unmatched paths fall to the terminal `.pathMatchers("/**").authenticated()` rule (`AuthorizationCustomizer.java:29-30`). All four citations re-verified 2026-06-10. Note the correct sibling pattern directly below in the same file: the dataset-field term rules use plural `/api/datasetfields/{dataset_field_id}/terms` (`SecurityConstants.java:298-301`) and DO match their endpoints.

## User-facing impact

- **The permission gates are inert - verified by BE trace 2026-06-10 (pure code-structure fact):** `PathPatternParserServerWebExchangeMatcher("/api/dataentities/{data_entity_id}/term", POST)` can never match the live `POST /api/dataentities/{id}/terms` (literal segment `term` != `terms`), so `DATA_ENTITY_ADD_TERM` / `DATA_ENTITY_DELETE_TERM` are never evaluated for these endpoints; the requests pass with `.authenticated()` only.
- **WHO can exploit it / WHAT they observably get (static trace consistent; not driven):** any user with a valid session under LOGIN_FORM / OAUTH2 / LDAP can call both endpoints directly (curl/SDK) and link or unlink any term on any data entity, regardless of Policy configuration. Under `auth.type=DISABLED` the whole API is `permitAll` anyway (`DisabledAuthSecurityConfiguration.java:16`), so this finding adds nothing there. The live 200-without-permission has not been driven against a policy-configured stack - that is the one remaining runtime check.
- **The UI does NOT expose the bypass - verified by FE trace 2026-06-10:** the Add-term / delete-term affordances are policy-gated client-side (`OverviewTerms.tsx:31, 94`, `TermItem.tsx:48` wrap in `WithPermissions`; the permission list comes from the policy-evaluated permission service, `PermissionServiceImpl.java:22-39`, NOT from SecurityConstants). An unauthorized user sees no button - so the operator's UI looks correctly locked down while the API is open, which is exactly why the defect stays invisible.
- **Authorized users are unaffected:** a non-matching matcher can only fail open, never falsely deny.

## Why it matters

Operators who allocated `DATA_ENTITY_ADD_TERM` and `DATA_ENTITY_DELETE_TERM` to a restricted role believe the link / unlink operations are gated by those permissions. They are not. Every authenticated user can perform both operations regardless of the Policy grid.

The bug class is "auth layer hides endpoint" - the SecurityConstants rule exists, looks correct to a reader auditing the file, but is operationally inert because the path string is wrong. The same defect class produces silent authorization bypass; it is **invisible to operators auditing Policies in the UI** because the UI shows the permission map the operator configured, not whether the SecurityRule path-matcher actually matches the live URL.

Severity is HIGH because (a) the defect is a complete bypass of two named permissions, (b) any authenticated user is sufficient - no privilege escalation needed beyond a valid session, (c) operators have no way to discover this without reading SecurityConstants line-for-line, (d) the symmetric DELETE half (line 241) compounds the impact - the operator's "term-link governance" trust is doubly broken.

This is the case-law class of LSN-001 / LSN-002 (operators following our guide off a cliff). The doc-side disclosure that *"the permission is currently inert"* is shipping as part of `DOC-177` while this code-side fix is in flight.

## Suggested fix

Two options. The recommended fix closes the immediate bug; the broader fix closes the entire class.

### Option A - minimal-risk fix (recommended for first PR)

Rename the singular `/term` paths to plural `/terms` in SecurityConstants:

```java
// odd-platform-api/src/main/java/.../auth/util/SecurityConstants.java:238
- new PathPatternParserServerWebExchangeMatcher(
-     "/api/dataentities/{data_entity_id}/term", POST)
+ new PathPatternParserServerWebExchangeMatcher(
+     "/api/dataentities/{data_entity_id}/terms", POST)

// odd-platform-api/src/main/java/.../auth/util/SecurityConstants.java:241
- new PathPatternParserServerWebExchangeMatcher(
-     "/api/dataentities/{data_entity_id}/term/{term_id}", DELETE)
+ new PathPatternParserServerWebExchangeMatcher(
+     "/api/dataentities/{data_entity_id}/terms/{term_id}", DELETE)
```

Two-line change. Aligns with the spec. Closes both POST and DELETE halves.

### Option B - close the class (broader change, follow-up PR)

Add a build-time validator that compares every SECURITY_RULES path against the OpenAPI paths. The validator fails the build when a SecurityRule path string does not match any spec path. This catches both halves of REFACTOR-217 today and prevents the next path-mismatch silent bypass tomorrow.

Sketch (pseudo-code):
```java
@Test
void securityRulesMatchOpenApiPaths() {
    Set<String> openApiPaths = loadOpenApiPaths();         // parse openapi.yaml
    Set<String> securityRulePaths = SecurityConstants.SECURITY_RULES.stream()
        .map(this::extractPathPattern)                     // PathPatternParserServerWebExchangeMatcher
        .collect(toSet());
    Set<String> rulesNotMatchingAnyPath = securityRulePaths.stream()
        .filter(rulePath -> openApiPaths.stream().noneMatch(spec -> pathMatches(rulePath, spec)))
        .collect(toSet());
    assertThat(rulesNotMatchingAnyPath).isEmpty();
}
```

A failing test would have caught this defect at build time. Recommended as a follow-up.
