## Description

Three ingestion-surface corrections — one severity escalation, two factual fixes:

1. **Default-unauthenticated `/ingestion/**` — state the severity.** `auth.ingestion.filter.enabled` defaults to **`false`**, so the ingestion endpoints are **whitelisted** (no auth) on the HTTP port. `integrations/README` cross-links the ingestion posture but does **not** state the LSN-001/002-grade severity: on the default posture, **any caller can register or ingest into any datasource** simply by writing that datasource's ODDRN — there is no per-collector authorization. The README must call this out as a security caveat, not a footnote.

2. **The custom-collector skeleton does NOT "start cleanly".** `custom-collectors.md` says the skeleton "sends an empty `DataEntityList` every 10 minutes and starts cleanly." The platform **rejects** an empty payload: `isNotEmpty` → `BadUserRequestException("Ingestion payload is empty")` → **HTTP 400**. A reader following the skeleton sees a **400 every cycle**, not a clean start. The page must either correct the claim or change the skeleton to emit a non-empty payload.

3. **`/ingestion/entities/datasets/stats` is ungated and does no parent-child validation.** The profiler page omits that `POST /ingestion/entities/datasets/stats` has **no auth gate** and performs **no parent-child validation** — any caller knowing a field ODDRN can overwrite that field's `dataset_field.stats` JSONB. (Distinct from the endpoint+payload correctness fix in DOC-287; this is the security caveat.)

High — security exposure on the ingestion surface plus a skeleton that contradicts observed behaviour.

**Failure shape**: missing security caveat (Gate 3/6) + code-doc drift ("starts cleanly" vs 400).
