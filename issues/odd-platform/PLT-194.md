## What

When ODD is configured with the Cognito OAuth provider but **no** `logout-uri` is set for it, clicking "Log out" does not actually log the user out. The Cognito logout handler returns early with `Mono.empty()` the moment it sees an empty `logout-uri`, and that early return happens *before* the line that invalidates the user's `WebSession`. So the session is never invalidated: the user is told they logged out, no error is shown, but their session cookie remains valid and the next request is still authenticated. Session invalidation only runs on the *other* path - when a `logout-uri` is present - so the local sign-out is silently coupled to an optional redirect setting.

## Where

The empty-`logout-uri` early return short-circuits the handler before any session work:

`auth/logout/CognitoLogoutSuccessHandler.java:33-35`
```java
if (StringUtils.isEmpty(provider.getLogoutUri())) {
    return Mono.empty();
}
```

The session invalidation that this early return skips lives at the very end of `handle(...)`, reachable only when a `logout-uri` is configured:

`auth/logout/CognitoLogoutSuccessHandler.java:36-49`
```java
final ServerHttpResponse response = exchange.getExchange().getResponse();
response.setStatusCode(HttpStatus.FOUND);
final var requestUri = exchange.getExchange().getRequest().getURI();

final var uri = UriComponentsBuilder
    .fromUri(URI.create(provider.getLogoutUri()))
    ...
    .build()
    .toUri();

response.getHeaders().setLocation(uri);
return exchange.getExchange().getSession().flatMap(WebSession::invalidate);
```

## User-facing impact

**Auth mode: OAUTH2 with the Cognito provider, configured with no `logout-uri`.** Verified by reading the handler in full (`CognitoLogoutSuccessHandler.java:29-50`): the *only* statement that invalidates the local session is `WebSession::invalidate` on the **last line** (`:49`), and it is reachable solely on the path where a `logout-uri` is present. The empty-`logout-uri` guard at `:33-35` returns `Mono.empty()` first, so when no `logout-uri` is configured the session is never touched.

Operator-visible symptom: a Cognito user clicks "Log out," the request returns cleanly with no error, but the `WebSession` (and its cookie) stays valid - the next request is still authenticated. On a shared or kiosk machine the previous user's session remains live for the next person, which is precisely what logout exists to prevent. Because it is gated on the *absence* of an optional setting, a deployment can ship this without realizing the button is decorative; nothing in the logs points at the cause. It does not affect `auth.type=DISABLED` or non-Cognito providers, but Cognito-without-IdP-redirect is a valid and common configuration, so within it this is a hard, reproducible session-persistence bug.

## Why it matters

This is a **silent authentication defect.** The operator-visible symptom is "I clicked log out, the page returned cleanly, but I'm still logged in" - and because it is gated on the *absence* of an optional `logout-uri`, it is easy to ship a Cognito deployment that exhibits it without realizing the logout button is decorative. On a shared or kiosk machine this means the previous user's session stays live for the next person, which is exactly the failure logout exists to prevent. There is no error and nothing in the logs to point at the cause. Severity is medium: it requires a specific (but entirely valid and common) configuration - Cognito provider with no IdP-side logout redirect - but within that configuration it is a hard, reproducible session-persistence bug.

## Suggested fix

Invalidate the session **before** the empty-`logout-uri` early return, so local sign-out always happens regardless of whether an IdP redirect is configured. For example, restructure so the `WebSession::invalidate` runs unconditionally and only the redirect-URI construction is guarded by the `logout-uri` presence check:

```java
return exchange.getExchange().getSession()
    .flatMap(WebSession::invalidate)
    .then(Mono.defer(() -> {
        if (StringUtils.isEmpty(provider.getLogoutUri())) {
            return Mono.empty();
        }
        // ... set FOUND + Location redirect, as today ...
    }));
```

Open to alternatives on the exact composition; the invariant is that the local `WebSession` is invalidated on every logout, and the `logout-uri` only governs the optional redirect.

## How discovered

Surfaced by the 2026-06-08 feature-reflection contradiction harvest (harvest report under `integration-tests/run-log/`, 2026-06-08) across feature reflections F-086 (Cognito logout flow) and F-089 (OAuth logout / session-termination surfaces): a product-owner hypothesis that "logout always terminates the local session" was contradicted by reading `CognitoLogoutSuccessHandler.java`, where the empty-`logout-uri` branch returns before `WebSession::invalidate`.

**Verified 2026-06-10 during the user-facing verification sweep:** re-read the whole handler - the empty-`logout-uri` early `Mono.empty()` at `:33-35` and the lone `WebSession::invalidate` at `:49` reachable only on the `logout-uri`-present path. The ordering bug is exactly as described; `user_facing_verified` raised false -> true.

Distinct from two related logout defects already tracked: **PLT-073** (Cognito logout does not *revoke* the upstream token at the IdP - a different concern; this issue is about not terminating the *local* session at all on the no-uri path) and **PLT-130** (the Azure logout handler NPE - a different provider and a different crash mechanism). This is the Cognito-specific ordering bug between the empty-uri early return and session invalidation.
