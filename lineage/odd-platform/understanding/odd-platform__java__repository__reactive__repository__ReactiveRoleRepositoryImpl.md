# ReactiveRoleRepositoryImpl — semantic understanding

## understanding

The persistence-layer bean owning every read and write to the `role` table — the table holding the named bundles of Policy references that the platform's authorization framework binds to Owners (and through `user_owner_mapping`, to authenticated users). The implementation file is a 94-line shell (`ReactiveRoleRepositoryImpl.java:1-94`) adding exactly three methods that return the role-with-joined-policies view — `getDto(id)`, `listDto(page, size, nameQuery)`, `getByName(name)` — each issuing a `SELECT role.* + jsonArrayAgg(POLICY.*)` aggregated through `ROLE_TO_POLICY`. Standard CRUD — `create / update / get / list / delete / bulkCreate / bulkUpdate` — is entirely inherited from `ReactiveAbstractSoftDeleteCRUDRepository` (`ReactiveRoleRepositoryImpl.java:28-29`); soft-delete means `delete(id)` is an UPDATE setting `deleted_at = NOW()`, never a `DELETE FROM`, and every `get` / `list` is auto-scoped to `WHERE deleted_at IS NULL` (`ReactiveAbstractSoftDeleteCRUDRepository.java:77-89`). The three custom methods DO carry the soft-delete filter on the ROLE table — `addSoftDeleteFilter(ROLE.ID.eq(id))` at lines 47, `listCondition(nameQuery)` at line 56 (which the soft-delete base overrides at `ReactiveAbstractSoftDeleteCRUDRepository.java:87-89`), and `addSoftDeleteFilter(ROLE.NAME.eq(name))` at line 89 — but NONE of them filter `POLICY.deleted_at IS NULL` on the joined policy table, so soft-deleted policies still bound via `role_to_policy` show up aggregated into the policies array. The DB-side counterpart is a partial UNIQUE INDEX `role_name_unique ON role(name) WHERE deleted_at IS NULL` (`V0_0_55__add_policies_and_roles.sql:42`, recreated by `V0_0_58__rename_constraints.sql:3-9` then by `V0_0_64__remove_is_deleted_field.sql:88-90`) — the SQL-layer recreation-after-soft-delete invariant that the controller-layer `Administrator`-name asymmetry (batch E) depends on.

## concepts

- entities: [RolePojo (jOOQ-generated row record — id, name, created_at, updated_at, is_deleted, deleted_at), RoleRecord (the typed jOOQ record), ROLE (jOOQ Tables constant referring to the `role` table), ROLE_TO_POLICY (jOOQ Tables join-table constant), POLICY (jOOQ Tables constant joined for the dto views), PolicyPojo (the joined value), RoleDto (RolePojo + Set<PolicyPojo> — produced by RoleRecordMapper.mapRecordToDto), role_name_unique (partial unique index — DB-layer enforcement), Page<RoleDto> (paginated wrapper for listDto)]
- operations:
  - "getDto(id): SELECT role.* + jsonArrayAgg(policy.*) FROM role LEFT JOIN role_to_policy ON role.id = role_to_policy.role_id LEFT JOIN policy ON role_to_policy.policy_id = policy.id WHERE role.id = ? AND role.deleted_at IS NULL GROUP BY role.* — returns Mono<RoleDto> with attached PolicyPojo set"
  - "listDto(page, size, nameQuery): paginated CTE — first selects `role_cte` filtered by `addSoftDeleteFilter(super.listCondition(nameQuery))` (containsIgnoreCase on role.name + deleted_at IS NULL) and paginated by OrderByField(ROLE.ID, ASC) with offset/limit, then LEFT JOINs role_to_policy + policy and aggregates policies per role — Mono<Page<RoleDto>>"
  - "getByName(name): SELECT role.* + jsonArrayAgg(policy.*) FROM role LEFT JOIN role_to_policy + policy WHERE role.name = ? AND role.deleted_at IS NULL GROUP BY role.* — Mono<RoleDto>"
  - "inherited create (INSERT INTO role(name, created_at, updated_at, is_deleted, deleted_at) VALUES (?, NOW(), NOW(), FALSE, NULL) RETURNING ALL — ReactiveAbstractCRUDRepository.java:103-107)"
  - "inherited update (UPDATE role SET name = ?, updated_at = ? WHERE id = ? AND deleted_at IS NULL RETURNING ALL — ReactiveAbstractCRUDRepository.java:107-110 + ReactiveAbstractSoftDeleteCRUDRepository.java:77-79)"
  - "inherited get (SELECT * FROM role WHERE id = ? AND deleted_at IS NULL — ReactiveAbstractCRUDRepository.java:69-74 + ReactiveAbstractSoftDeleteCRUDRepository.java:77-79)"
  - "inherited delete (UPDATE role SET deleted_at = NOW() WHERE id = ? AND deleted_at IS NULL RETURNING ALL — soft-delete via ReactiveAbstractSoftDeleteCRUDRepository.java:50-58)"
  - "inherited list / bulkCreate / bulkUpdate (@ReactiveTransactional only on bulk variants — ReactiveAbstractCRUDRepository.java:113, 129)"
- invariants:
  - "Every CRUD read and the inherited delete are auto-scoped to `deleted_at IS NULL` by ReactiveAbstractSoftDeleteCRUDRepository.addSoftDeleteFilter (ReactiveAbstractSoftDeleteCRUDRepository.java:96-104). Custom getDto/listDto/getByName ALSO apply the soft-delete filter on ROLE (ReactiveRoleRepositoryImpl.java:47, 56 via base override at ReactiveAbstractSoftDeleteCRUDRepository.java:87-89, and 89). Soft-deleted roles are invisible to every defined read path; double-deletion is a no-op (the UPDATE matches zero rows)."
  - "The three custom JOIN methods (getDto / listDto / getByName) FILTER soft-deleted ROLES at the ROLE table but DO NOT filter soft-deleted POLICIES (ReactiveRoleRepositoryImpl.java:45-48, 67-70, 87-90). The LEFT JOIN against POLICY has NO `policy.deleted_at IS NULL` predicate, so a soft-deleted policy still bound via `role_to_policy` (a row whose policy_id references a policy with non-NULL `deleted_at`) is materialised into the aggregated `policy_relations` array. This is the symmetric mirror of the batch-H finding on getRolesPolicies — the asymmetry is consistent across the two RBAC repositories."
  - "Role-name uniqueness is enforced at the DATABASE layer via the partial unique index `role_name_unique ON role(name) WHERE deleted_at IS NULL` (V0_0_55__add_policies_and_roles.sql:42; recreated by V0_0_58__rename_constraints.sql:3-9 then by V0_0_64__remove_is_deleted_field.sql:88-90). The repository has no service-layer pre-check; a duplicate INSERT fails as a Postgres SQLSTATE 23505 which `JooqReactiveOperations.mono` maps to `UniqueConstraintException` via `ExceptionUtils.translateDatabaseException` (ExceptionUtils.java:30-32) with the message `'Role with this name already exists'` (ExceptionUtils.java:57-59)."
  - "Soft-delete plus the partial unique index together implement: a role with name X can be soft-deleted, then a new role with the same name X can be created (the partial index excludes the soft-deleted row from uniqueness). The seeded `Administrator` and `User` rows (V0_0_56__add_predefined_roles_and_policies.sql:33-36) occupy the protected names — but ONLY for as long as the seeded rows exist. The soft-delete column `deleted_at` (LocalDateTime) is the SQL-layer flag; the V0_0_64 migration is the moment the platform converged on `deleted_at IS NULL` as the canonical filter (earlier V0_0_55 and V0_0_58 used `is_deleted IS FALSE` against the now-removed `is_deleted` column)."
  - "Single-statement INSERT / UPDATE on `create` / `update` (ReactiveAbstractCRUDRepository.java:103-110) — NO @ReactiveTransactional on these inherited methods. Only bulkCreate / bulkUpdate are transactional (lines 113, 129). The Role create / update / delete paths therefore commit per-statement; the service layer (RoleServiceImpl.java:50, 64, 77) wraps the create / update / delete flows in `@ReactiveTransactional` to make the role INSERT + role↔policy INSERTs atomic — the persistence layer assumes the service supplies the transaction boundary, and a service-bypassing caller would lose atomicity (no orphan-prevention)."
  - "The CTE-based listDto query (ReactiveRoleRepositoryImpl.java:55-79) is structurally different from getDto / getByName: it FIRST paginates the ROLE rows (ASC by id) and ONLY THEN joins policies — preventing the policy multiplicity from inflating page boundaries. Without the CTE, a role with N policies would consume N row slots before page-truncation. Paging is `(page-1)*size, size` (line 58-59), so page numbers are 1-indexed."
- audiences: [RoleServiceImpl (sole caller of every method on this repository — see upstream_callers), PolicyServiceImpl (transitive consumer via roleService.getCurrentUserRoles → roleRepository.getByName, on every authorized HTTP request that traverses the permission framework), database operators investigating the `role` table directly, RoleController (HTTP-surface caller for the entire CRUD)]

- coupling:
  - "Strong coupling to the soft-delete base class — changing the soft-delete column name (`deleted_at`) or replacing the soft-delete pattern with hard delete would silently break the partial unique index assumption that operators rely on for the `recreate-after-delete` behaviour batch-E surfaced."
  - "Tight coupling to the schema's foreign-key choice on ROLE_TO_POLICY: the FK is on `policy_id` referencing `policy(id)` with NO `ON DELETE CASCADE` and NO trigger removing role_to_policy rows when `policy.deleted_at` is set (V0_0_55__add_policies_and_roles.sql:52). The implicit contract: a soft-deleted policy bound to a role STILL surfaces in the aggregated `policy_relations` JSON returned by getDto/listDto/getByName — because the LEFT JOIN does not filter `policy.deleted_at IS NULL`. This is the structural mirror of the batch-H finding on `ReactivePolicyRepositoryImpl.getRolesPolicies`: a soft-deleted policy with surviving bindings continues to confer permissions transitively. Today the cascade-delete defence at PolicyServiceImpl.java:89-92 prevents this in normal flows by refusing to soft-delete a bound policy, but the same defence does NOT live in the RoleService — RoleServiceImpl.delete (line 89) directly removes role_to_policy edges before soft-deleting the role (acceptable, but means a HARD-DELETED policy with surviving bindings is structurally impossible only because the policy-side defence prevents it; the role-side has no defence)."
  - "Implicit coupling to RoleServiceImpl as sole caller: the repository is referenced ONLY by RoleServiceImpl.java:33 and by its own interface (verified by Grep at session 2026-05-19). Every CRUD invariant the platform depends on — `Administrator`/`User`-name protection on update/delete, the create/update/delete asymmetry, the cascade-delete check against owner_to_role, the @ReactiveTransactional gating — lives in the service, NOT the repository. The repository is intentionally role-agnostic at the persistence layer (same pattern as ReactivePolicyRepositoryImpl per batch H)."
  - "Implicit coupling to the AUTHORIZATION HOT PATH via `getByName`: PolicyServiceImpl.getCurrentUserPolicies (PolicyServiceImpl.java:103-104) calls `roleService.getCurrentUserRoles()` which in turn calls `roleRepository.getByName(role.getValue())` for the user-provider-role resolution path (RoleServiceImpl.java:99, 123-126). This is the read-side hot path: EVERY authorized request that traverses ManagementPermissionExtractor or AbstractContextualPermissionExtractor flows through `getByName` on a fall-back path when the user has no explicit owner-attached roles."

## performance

- **hot_paths**:
  - "`getByName` is on the AUTHORIZATION HOT PATH. PolicyServiceImpl.getCurrentUserPolicies (PolicyServiceImpl.java:103-104) calls `roleService.getCurrentUserRoles()` which on the fall-back path (no explicit owner-attached role) calls `roleRepository.getByName(role.getValue())` (RoleServiceImpl.java:99, 123-126). The query is a single JOIN (role ⋈ role_to_policy ⋈ policy) with `WHERE role.name = ? AND role.deleted_at IS NULL` — sub-millisecond on typical row counts (a handful of seeded roles). The result Mono<RoleDto> is consumed in-memory by the extractor chain. NO caching layer is present at the repository, service, or extractor level — every authorized request hits Postgres for this path AND for the parallel PolicyRepository.getRolesPolicies path (so two queries per request)." — evidence: ReactiveRoleRepositoryImpl.java:82-93 + RoleServiceImpl.java:95-101, 123-126 + PolicyServiceImpl.java:103-104 + ManagementPermissionExtractor.java:33 + AbstractContextualPermissionExtractor.java:27
  - "`getDto` and `listDto` are admin-listing paths — invoked from RoleController.getRolesList (`GET /api/roles`) per request from operators viewing the Management → Access Control → Roles tab. Per-call cost dominated by the LEFT JOIN's jsonArrayAgg aggregation plus the CTE wrap for listDto." — evidence: ReactiveRoleRepositoryImpl.java:42-80 + RoleController.java:27-34 + RoleServiceImpl.java:40-47
  - "create / update / delete are admin-rare paths. Per-call cost dominated by the @ReactiveTransactional wrap (multi-statement transaction) at RoleServiceImpl.java:50, 64, 77 plus the inherited base-class single-statement INSERT/UPDATE." — evidence: RoleServiceImpl.java:50-92 + ReactiveAbstractCRUDRepository.java:103-110, 158-173
- **throughput_characteristics**:
  - "Single-role create / update / delete — no bulk endpoint exposed via the service for roles (RoleServiceImpl exposes only single-item operations). The base class supports bulkCreate / bulkUpdate (ReactiveAbstractCRUDRepository.java:113-142) and those ARE @ReactiveTransactional, AND OwnerRepositoryImplTest.testListOwner DOES invoke `roleRepository.bulkCreate(...)` directly (line 197) — but no service exposes this path."
  - "getDto / listDto / getByName: single JOIN per call with jsonArrayAgg aggregation, no streaming — Mono materialises the full result. Acceptable for typical role-cardinality (single-digit roles, single-digit policies-per-role). For listDto specifically, the CTE-then-aggregate pattern correctly bounds result-set-row-count to page size BEFORE the jsonArrayAgg expansion."
- **resource_allocation**:
  - "Per call: one R2DBC connection acquired via DatabaseClient.inConnection (JooqReactiveOperations) — non-blocking on the reactive thread, returned to pool on terminal signal."
  - "Per call (getDto / getByName / listDto): the result Mono<RoleDto> or Mono<Page<RoleDto>> is held in memory. For a typical Role bound to ~1-10 policies, ~500 bytes per PolicyPojo, the per-RoleDto allocation is single-KB. A listDto page of 50 roles × 10 policies × 500 bytes = ~250KB per request — trivial for the JVM heap. A pathological role bound to thousands of policies would scale proportionally."
  - "The jsonArrayAgg aggregation happens INSIDE Postgres (server-side memory), then the JSON is parsed into Set<PolicyPojo> on the application side. This places the aggregation memory cost on Postgres rather than the JVM — appropriate for a small-N aggregation."
- **scaling_characteristics**:
  - "Stateless. No locks, no advisory locks, no session state. Concurrent INSERTs of the same role name serialise at the DB via the partial unique index. Concurrent UPDATEs of the same role id can race within a @ReactiveTransactional service wrap (which only protects the multi-statement chain; it does not provide optimistic-concurrency tokens — verified at ReactiveAbstractCRUDRepository.java:103-110 by absence of `version` field handling)."
  - "Horizontal scaling: instances behind a load balancer share the Postgres backend; concurrency is bounded by the R2DBC connection pool size (`spring.r2dbc.pool.max-size`). The getByName authorization-hot-path is THE highest-frequency caller of this repository; under high load it becomes a Postgres connection-pool consumer."
- **known_performance_gaps**:
  - "No caching of getByName. The result for stable seeded role names ('Administrator', 'User') is essentially never-invalidated for the lifetime of the seeded rows. On a busy platform with N authorized req/s, this is N DB calls (resolving the user-provider-role). A short-TTL request-scoped or process-wide cache (or a Caffeine LoadingCache scoped to seeded-role-name lookups) would significantly reduce DB load on this exact pattern. Today's behaviour is correct (always fresh) but not optimised — particularly because PolicyRepository.getRolesPolicies is ALSO called per-request, making 2 DB round-trips per authorized request the authorization-hot-path cost." — evidence: ReactiveRoleRepositoryImpl.java:82-93 (no @Cacheable, no caching layer) + RoleServiceImpl.java:95-101 (also no caching) + PolicyServiceImpl.java:103-104 (parallel call to PolicyRepository.getRolesPolicies — also uncached) — severity: LOW
  - "getDto / listDto / getByName return the FULL POLICY text on every call. The `policy` column is `text` (V0_0_55__add_policies_and_roles.sql:23) — typical policies are ~1KB, but a pathological policy could be megabytes. The query has no projection to omit `policy` text when only the role's id/name are needed — but every consumer DOES need the full RoleDto (the permission extractors need the policy statements), so this is not a real gap, just an observation that the data shape forces a full-row read." — evidence: ReactiveRoleRepositoryImpl.java:43, 67, 85 (`jsonArrayAgg(POLICY.asterisk().toString())`) — severity: LOW
