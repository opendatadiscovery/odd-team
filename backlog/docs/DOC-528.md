# DOC-528 — the ingestion error contract is documented as unstructured 5xx; the platform answers structured 4xx

## The claim, verbatim

`documentation/docs/integrations/README.md`, section **Ingestion error contract**:

> Three client-side error conditions currently surface as **HTTP 5xx** (rather than 4xx) because the
> platform's controller has no `@ExceptionHandler` advice for the underlying exception classes. Collector
> authors writing retry-with-backoff logic against the public contract should treat the conditions below as
> **client errors that look like server errors** […]

| Client-side condition | Underlying exception | Current HTTP shape | Recommended client behaviour |
|---|---|---|---|
| Duplicate ODDRN inside one batch | `IllegalStateException: Duplicate key` | 5xx | Deduplicate […] |
| **Unknown `data_source_oddrn` in the batch** | **`NotFoundException`** | **5xx** | Verify the data-source has been registered […] |
| Payload exceeds the configured codec limit | `DataBufferLimitException` | 5xx | Reduce batch size […] |

and the closing sentence:

> The platform-side hardening to convert these conditions to structured 4xx responses (`400`, `404`, `413`)
> is **on the roadmap**; **until it ships**, the doc-side contract above is the canonical client guidance.

## What the platform actually does — DRIVEN, not read

Run against a live platform built from odd-platform `cdaa7d45` (the `/review CTRIB-066` SUT, container
`revctrib066-odd-platform`, API on `:18100`), 2026-09-06:

```
$ curl -i -X POST /ingestion/entities -H 'Content-Type: application/json' \
       -d '{"data_source_oddrn":"//nosuchsource/probe2","items":[{"oddrn":"//x/dup","name":"a","type":"TABLE"},
                                                                 {"oddrn":"//x/dup","name":"b","type":"TABLE"}]}'
HTTP 404
{"code":"USR002","message":"DataSource with oddrn //nosuchsource/probe2 is not found",
 "retryable":false,"resolvable":false,"details":null}
```

and, incidentally, the empty-payload path is also already structured:

```
$ curl -i -X POST /ingestion/entities -d '{"data_source_oddrn":"//nosuchsource/probe","items":[]}'
HTTP 400
{"code":"USR001","message":"Ingestion payload is empty","retryable":false,"resolvable":true,"details":null}
```

So the row the page singles out as the one an operator hits most — an unregistered data source — is **404 with
a machine-readable body**, not a 5xx.

## Why the premise is wrong

The page's stated reason is *"the platform's controller has no `@ExceptionHandler` advice for the underlying
exception classes."* That is not the case and has not been for years:

- `controller/exception/ControllerAdvice.java` is annotated `@RestControllerAdvice` with **no**
  `basePackages` / `assignableTypes` restriction, so it is global — it covers `IngestionController` exactly
  as it covers every other `@RestController`.
- `:33-36` maps `@ExceptionHandler(NotFoundException.class)` → `@ResponseStatus(HttpStatus.NOT_FOUND)`.
- `service/ingestion/IngestionServiceImpl.java:69` is the throw site:
  `.switchIfEmpty(Mono.error(() -> new NotFoundException("dataSource", dataEntityList.getDataSourceOddrn())))`.
- The structured body is the spec's own `ErrorResponse` (`odd-platform-specification/components.yaml:3941`
  carries `retryable`), and `exception/ErrorCode.java:9-10` defines `BAD_REQUEST("USR001", false, true)` /
  `NOT_FOUND("USR002", false, false)`. `git log -S retryable` dates that contract to **`5d5fcfb9`,
  2022-11-11, "Error handling (#1097)"** — i.e. the "hardening … on the roadmap" the page promises had
  already shipped three and a half years before the page was written.

## Reader harm

The audience is collector and push-adapter **authors** — the readers least able to check, because they are
writing against the published contract from outside the platform. The page tells them to build a per-condition
heuristic ("treat these 5xx as client errors, pre-flight with a GET, do not blanket-backoff on 5xx") when the
platform already hands them `retryable: false` in the response body. Two concrete costs:

1. **Wrong retry logic.** An author who codes "retry all 5xx, do not retry 4xx" per the page will retry
   nothing on the unknown-datasource path (correct by luck) but will also never read `retryable`, so the
   `DataBufferLimitException` case — which may genuinely still be a 5xx — is handled by the same blunt rule
   the page warns against.
2. **A missing contract.** `code` / `retryable` / `resolvable` are the fields a client SHOULD branch on, and
   the manual never mentions that they exist anywhere on this page.

## Recommended fix direction

1. **Re-drive all three rows** against a running platform before rewriting — this audit drove only the
   unknown-`data_source_oddrn` row (404) and the empty-payload path (400). The duplicate-ODDRN row needs a
   *registered* data source to reach the `Collectors.toMap` merger, and the codec-limit row needs an
   oversized body; both are still **unverified here** and may well remain 5xx.
2. Replace the "no `@ExceptionHandler` advice" premise with the actual mechanism: a global
   `@RestControllerAdvice` that maps `NotFoundException` → 404 and `BadUserRequestException` /
   `WebExchangeBindException` → 400, and returns the spec's `ErrorResponse`.
3. **Document the error body as the contract**: `code` (`USR001` / `USR002` / …), `message`, `retryable`,
   `resolvable`. Tell clients to branch on `retryable`, not on the status class. That is the guidance the
   section exists to give, and it is one field away.
4. Delete the "on the roadmap / until it ships" sentence for whatever is measured as already shipped; keep it
   only for the rows that re-driving proves are still unstructured 5xx.
5. Cross-check `developer-guides/api-reference/*` for the same premise — the ingestion endpoint response
   contract was authored in the same commit (`2614e64`, 2026-05-28, DOC-171/195/196/240/248) and may repeat it.

## Provenance

The passage entered on `2614e64` (2026-05-28) as part of the DOC-171/195/196/240/248 batch. No test pins the
ingestion error status anywhere in `odd-platform-api/src/test` or in the odd-team e2e suites, which is why the
claim survived: it was authored from a read of the controller, never driven. A regression guard belongs with
the fix — a `BaseIngestionTest`-style web test asserting `404` + `USR002` on an unknown data source would pin
the contract the page will then describe.
