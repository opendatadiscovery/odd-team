## Description

The Management section's layout has two operator-facing characteristics the live doc does not capture:

1. **Desktop-only chrome.** The Management shell is a fixed two-column split with `wrap='nowrap'` and hard column widths — `Management.tsx:13-19` (`<S.Container container wrap='nowrap'>`, `<S.SidebarContainer item xs={3}>`, `<S.ContentContainer item xs={9}>`), with **no `sm`/`md`/`lg` breakpoint overrides**. The sidebar styled-component reinforces this: it is `position: fixed` with a hard pixel `maxWidth: ${maxSidebarWidth}px`, and the content container is offset by a fixed `paddingLeft: ${maxSidebarWidth + 16}px` — `ManagementStyles.ts:5-16`. On a narrow viewport (phone/tablet) the `nowrap` row cannot reflow and the fixed-px sidebar does not collapse, so the content pane is cramped against a non-responsive sidebar. The doc currently describes the sidebar/content layout (`docs/management.md:9`) without noting it is desktop-optimised.

2. **Frozen tab set.** The nine Management tabs are a hand-written literal array — `ManagementTabs.tsx:19-50` — rendered in a fixed UI order. The only per-user variation is that **Associations** is conditionally hidden when the user lacks `OWNER_ASSOCIATION_MANAGE` (`ManagementTabs.tsx:14-17, 39-43`); there is **no** affordance to pin, reorder, or per-user hide any other tab. The doc lists the nine tabs (`docs/management.md:13-25`) and already documents the Associations permission-hide (`docs/management.md:23, 27, 42`), but does not state that the set is otherwise fixed and non-customizable.

Neither point is a bug — both are intentional product shape — but an operator on a tablet, or one expecting to tailor their Management navigation, currently has no documented expectation. This is a layout/expectations caveat on the existing Management page.
