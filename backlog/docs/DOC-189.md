## Description

Custom Metadata is a paired feature surface: F-013 (per-entity VALUE write) + F-046 (FIELD catalogue read). Both halves are **completely undocumented** — no page, no glossary entry, no operator workflow description. WebFetch on 2026-05-27 confirms: `/active-platform-features/metadata` returns 404; `/active-platform-features/custom-metadata` returns 404; the Data Discovery section index does NOT list custom metadata as a covered topic. The Permissions page lists `DATA_ENTITY_CUSTOM_METADATA_{CREATE,UPDATE,DELETE}` but never describes authoring, never describes the read side (no `CUSTOM_METADATA_FIELD_READ` permission exists), and never names the autocomplete catalogue.

**Five load-bearing facets need a new canonical home (Cornerstone 5):**

**Facet 1 — End-to-end undocumented authoring + read surface (F-013a + F-046a paired).** Operators visit `/dataentities/{id}/overview`, edit the Metadata panel via `OverviewMetadata` composer, dispatch one of three thunks (create / update / delete). The PUT endpoint `/api/dataentities/{id}/metadata/{field_id}` is documented in OpenAPI as "upsert"; the read companion `GET /api/metadata/fields` is the catalogue feed. Eight `MetadataFieldType` options (BOOLEAN/INTEGER/FLOAT/STRING/DATETIME/ARRAY/JSON/UNKNOWN). Two origins (INTERNAL operator-authored / EXTERNAL collector-ingested). Field names are case-sensitive (`cost_centre` ≠ `Cost_centre`) — a common operator surprise.

**Facet 2 — Silent UPDATE-not-UPSERT (F-013b).** `ReactiveMetadataFieldValueRepositoryImpl.java:94-104` is pure `DSL.update(METADATA_FIELD_VALUE).set(VALUE, ...).set(ACTIVE, pojo.getActive()).where(METADATA_FIELD_ID.eq(?).and(DATA_ENTITY_ID.eq(?))).returning()` — no `INSERT ... ON CONFLICT`. Missing `(entity_id, field_id)` pair → zero-row UPDATE → Mono empty → silent 200 OK. The UI displays "Metadata successfully updated." (`metadata.thunks.ts:51-54`). OpenAPI declares operationId "upsert" — implies replace-or-create semantics. Reconciliation pipelines silently lose writes.

**Facet 3 — `active` column silently dropped to NULL on every UPDATE (F-013c).** Line 98 writes `.set(ACTIVE, pojo.getActive())`. The caller (`DataEntityServiceImpl.java:292-295`) never calls `.setActive(true)` on the pojo. `pojo.getActive()` returns boxed `Boolean` null. UPDATE writes explicit NULL. DB DEFAULT TRUE only applies on INSERT (`V0_0_1__init.sql:180`). Any platform code filtering `WHERE active = TRUE` (rather than `IS DISTINCT FROM FALSE`) silently drops edited rows.

**Facet 4 — pageInfo theatre + no LIMIT on catalogue read (F-046a).** `MetadataFieldMapperImpl.java:28-33` constructs `new PageInfo().total((long) pojos.size()).hasNext(false)` — `total` is items.length on every call; `hasNext` is hardcoded false. SQL at `ReactiveMetadataFieldRepositoryImpl.java:44-56` is unbounded (no LIMIT/OFFSET/ORDER BY). Production deployments with 10K+ INTERNAL fields see a 1-2 MB response on every autocomplete keystroke. SDK clients written from the OpenAPI spec build "load more" infinite-scroll workflows that never fire.

**Facet 5 — No `CUSTOM_METADATA_FIELD_READ` permission; catalogue enumerates entire deployment vocabulary (F-046b).** `GET /api/metadata/fields` has NO entry in `SecurityConstants.SECURITY_RULES` — falls through to `.authenticated()`. Under `auth.type=DISABLED`, anonymous callers enumerate every INTERNAL field name in the deployment. Multi-team deployments with operator-named field schemas (`finance_cost_centre`, `marketing_attribution`, `pii_redaction_rule`) leak vocabulary across team boundaries. The auto-create-on-miss side-channel compounds: any user with `DATA_ENTITY_CUSTOM_METADATA_UPDATE` on a single entity can MINT new catalogue entries visible to every authenticated user.

**Forensic silence cross-tie**: the `ActivityEventTypeDto` enum carries `CUSTOM_METADATA_CREATED`, `CUSTOM_METADATA_UPDATED`, `CUSTOM_METADATA_DELETED` values — all three are **dead** (no code path emits them; same pattern as `DATA_ENTITY_RELATION_UPDATED` on DOC-188 / DOC-181).
