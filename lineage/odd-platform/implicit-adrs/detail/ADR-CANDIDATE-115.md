## ADR-CANDIDATE-115 — CRUD-asymmetry pattern: ADD and DELETE are independent Policy capabilities (two distinct permissions per pair) AND ADD-on-duplicate raises HTTP 400 while DELETE-on-missing is silently 204 — the two-axis asymmetry is consistent across DEG-membership, OWNERSHIP, term-linkage, and (latent) tag-assignment

**Classification**: promote (cross-cutting CRUD-asymmetry pattern; broader than DEG)
**Severity**: MEDIUM
**Pillars affected**: [P-09-security-access-control, P-01-data-discovery, P-06-data-glossary]
**Support**: 2 sidecars from batch L (`addDataEntityDataEntityGroup` + `deleteDataEntityFromDataEntityGroup`); confirmed by cross-batch pattern citation of OWNERSHIP_CREATE / OWNERSHIP_UPDATE / OWNERSHIP_DELETE (batch K, three separate permissions) + DATA_ENTITY_ADD_TERM / DATA_ENTITY_DELETE_TERM (batch I) + DATA_ENTITY_CUSTOM_METADATA_CREATE / UPDATE / DELETE (batch L); the pattern is codebase-wide
**Batch**: L (2026-05-19)

**Surfaced by**:
- `odd-platform__java__DataEntityController__controller-method__deleteDataEntityFromDataEntityGroup.md:implicit_adrs.[1]` (HIGH) — "ADD and DELETE are DISTINCT policy capabilities — `SecurityConstants.java:228-236` registers `DATA_ENTITY_ADD_TO_GROUP` for POST and `DATA_ENTITY_DELETE_FROM_GROUP` for DELETE as TWO separate `SecurityRule` entries with TWO different permissions. `PolicyPermissionDto.java:22-23` declares both as `DATA_ENTITY`-scoped enum values. The implicit ADR: 'adding an entity to a group and removing it are independent capabilities that may be granted separately by Policy.' This is consistent with the OWNERSHIP_CREATE / OWNERSHIP_UPDATE / OWNERSHIP_DELETE pattern (three distinct permissions per `SecurityConstants.java:213-227`)"
- `odd-platform__java__DataEntityController__controller-method__deleteDataEntityFromDataEntityGroup.md:invariants.[3]` (HIGH) — "Asymmetric HTTP idempotence with ADD — the DELETE path issues `deleteRelationsReturning(groupOddrn, entityOddrn)` which returns the deleted rows; on a no-op (the membership didn't exist), the Flux completes empty, `collectList()` produces an empty list, and the pipeline continues to 204 SUCCESSFULLY. There is NO `switchIfEmpty` check. The ADD counterpart does the opposite: `createRelationsReturning(...).switchIfEmpty(Mono.error(BadUserRequestException(\"Data entity is already in this DEG\")))` raises 400 on a duplicate. DELETE is idempotent in HTTP surface; ADD is non-idempotent."
- `odd-platform__java__DataEntityController__controller-method__addDataEntityDataEntityGroup.md:bugs_limitations_corner_cases.[6]` ("Idempotency mismatch with retries — the service's `BadUserRequestException(\"Data entity is already in this DEG\")` on duplicate is HTTP 400 (resolvable, not retryable). ... The matching DELETE path is idempotent (returns no error for already-deleted rows — the `deleteRelationsReturning` query simply produces an empty Flux which is collected to an empty list and returned). The ADD/DELETE asymmetry could surprise operators writing automation against this endpoint")

**Decision statement**: ODD's per-data-entity write surface treats every relation-row as having INDEPENDENTLY-GRANTABLE add+delete permissions AND ASYMMETRIC HTTP semantics for duplicate-state. Two axes compose: (Axis A — Policy granularity) for every CRUD relation, the platform declares TWO or THREE separate `PolicyPermissionDto` enum values rather than a single MANAGE capability. Concrete instances: `DATA_ENTITY_ADD_TO_GROUP` / `DATA_ENTITY_DELETE_FROM_GROUP` (PolicyPermissionDto.java:22-23); `OWNERSHIP_CREATE` / `OWNERSHIP_UPDATE` / `OWNERSHIP_DELETE` (`SecurityConstants.java:213-227`); `DATA_ENTITY_ADD_TERM` / `DATA_ENTITY_DELETE_TERM` (`SecurityConstants.java:237-242`); `DATA_ENTITY_CUSTOM_METADATA_CREATE` / `UPDATE` / `DELETE` (`SecurityConstants.java:201-211`); and the same shape at the tag and namespace surfaces. The intent: granular Policy authoring — an admin Policy can grant "data steward can ADD members but not REMOVE them" or "deprecation-operator can DELETE but not ADD." (Axis B — HTTP idempotence) for the same CRUD relation, ADD on duplicate raises HTTP 400 ('"Data entity is already in this DEG"', '"Owner is already attached"', etc.) while DELETE on missing returns HTTP 204 silently (`deleteRelationsReturning` produces empty Flux, no `switchIfEmpty`, pipeline completes to no-content). The intent: DELETE follows the REST idempotence convention (the request's effect — "this relation is absent" — is achieved whether or not a row was actually removed); ADD does not (the request's effect — "this relation is present" — was already true, so the request fails as a duplicate). Both axes are deliberately encoded structurally (Axis A at PolicyPermissionDto enum + SecurityConstants.SECURITY_RULES; Axis B at the service-layer `.switchIfEmpty` placement asymmetry). Trade-off accepted: (a) operator authoring Policies must understand the compound-capability rule (grant 'manage DEG memberships' requires BOTH ADD_TO_GROUP and DELETE_FROM_GROUP) — REFACTOR-NNN cross-link below; (b) operators writing idempotent automation against the API face different contracts for ADD vs DELETE on the same relation — the ADD path needs retry-on-409-like handling, the DELETE path doesn't.

**Wisdom test**: PASS on all three questions. (1) **Intent stated**: Axis A is anchored at PolicyPermissionDto's three-or-more separately-declared enum values per relation; the maintainer explicitly chose granularity over compound permissions in five different relation tables. Axis B is anchored at the SERVICE-LAYER `.switchIfEmpty` placement (present on ADD, absent on DELETE) — a deliberate code-shape choice. (2) **Structural impact**: the granular permission model determines every operator-facing Policy authoring decision; the HTTP-idempotence asymmetry determines every API client's retry strategy. Both decisions cascade into the operator UX and the doc-product surface. (3) **Collapsing the two axes would be structural**: a single MANAGE permission would change the Policy model; aligning HTTP semantics (both ADD and DELETE idempotent, or both non-idempotent) would change the API contract.

**Existing ADR**: none. **Composes with ADR-CANDIDATE-002** (centralised SECURITY_RULES — the multi-permission registration is the structural anchor for Axis A). **Composes with ADR-CANDIDATE-113** (DEG no-auto-create-on-miss — the manually-created constraint is enforced symmetrically on ADD+DELETE, but the PERMISSIONS gating those operations are independently grantable).

**Cross-link gaps** (refactoring-scopes anchored on consequences this ADR DOES NOT defend):
- The operator-trap: granting "manage DEG memberships" requires BOTH ADD_TO_GROUP and DELETE_FROM_GROUP — no doc warns operators. Surface as a DOC-NNN follow-up at the live Policies page.
- ADD-path retry surprise: an HTTP 400 on duplicate breaks idempotent automation that expects 200/201 for "create-or-noop." Cross-link with REFACTOR-NNN (the misleading "already in this DEG" message under soft-delete state — REFACTOR-338 batch L).
- The asymmetry pattern itself is undocumented in the API-reference live pages.

**Proposed action**: Promote to `adrs/drafts/crud-asymmetry-policy-granularity-and-http-idempotence.md` (new ADR). Document: (1) the four-or-five separate-permissions instances across DEG-membership, OWNERSHIP, term-linkage, custom-metadata, and tag-assignment; (2) the ADD-non-idempotent vs DELETE-idempotent HTTP contract; (3) the operator-facing compound-capability consequence ("manage X" requires BOTH ADD-X and DELETE-X grants); (4) the API-client consequence (idempotent automation needs to swallow 400-duplicate or pre-check existence before ADD). Cross-link with ADR-CANDIDATE-002 (the SECURITY_RULES centralisation), ADR-CANDIDATE-113 (the DEG family's manually-created constraint applied symmetrically), REFACTOR-338 (the misleading-error on soft-deleted-membership re-add). Doc-side: the live Policies page should call out compound capabilities; the API-reference per-feature pages should describe the ADD/DELETE asymmetric idempotence.

**Severity rationale**: MEDIUM — pattern-shaping decision that 5+ relation tables follow; affects every operator authoring Policies and every API client building idempotent automation. Not security-architecture-defining (HIGH would require evidence that the asymmetry creates security gaps the maintainer wouldn't accept) but load-bearing for operator UX and API-client patterns.
