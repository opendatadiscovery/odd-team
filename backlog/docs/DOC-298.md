## Description

Two authorization-doc inaccuracies that lead an operator to build an access model that does not behave as documented:

1. **policies.md recommends an invalid condition operator.** A mitigation note on the policies page tells the operator to use the condition operator **`in`**. The policy condition schema allows only `all | any | eq | ...` and is `additionalProperties: false`, so `in` is **rejected** — and the validation failure surfaces as **HTTP 500** (not a clean 4xx). The page's own operator list elsewhere does not even include `in`, so the page contradicts itself. An operator who follows the mitigation authors a policy the platform rejects with a 500.

2. **roles.md overstates the Owner-role override and omits the DISABLED bypass.** The roles page claims the Owner-role override is **unconditional** ("binds to Owner → loses ADMIN"). The code makes it **conditional on a non-empty owner role set**: a user bound to a **zero-role Owner** still **retains auth-chain ADMIN** via the fallback. So an operator who relies on "bind to Owner to drop admin" can leave a zero-role Owner with full ADMIN. Separately, under `auth.type=DISABLED` the whole permission-resolution chain is **bypassed** — the synthesised anonymous principal maps to `Administrator` and every callsite runs full ADMIN regardless of any Owner-role binding. The page documents neither the conditionality nor the DISABLED bypass.

Critical — #1 hands the operator a recommendation that fails with a 500; #2 is a false security guarantee about how to drop admin rights.

**Failure shape**: code-doc drift (an invalid recommendation that 500s) + missing/false security caveats on the roles model.
