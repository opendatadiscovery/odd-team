- **ADR-CANDIDATE-054** (NEW 2026-05-12F): The centerpiece data-entity detail read is a **read-as-write** operation — `getDataEntityDetails` runs inside `@ReactiveTransactional` and unconditionally increments `view_count` per call via `incrementViewCount` chained into the orchestration pipeline. The decision makes view-count tracking a first-class invariant of the detail read (powering `getPopular` ranking + recommendation panels), accepting that every read also touches the database write path
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar (`getDataEntityDetails`) — single occurrence but architecturally meaningful: the deliberate transactional coupling of a read endpoint with a write side-effect is unusual enough to surface as an explicit ADR
  - **Surfaced by**:
    - `odd-platform__java__DataEntityController__controller-method__getDataEntityDetails.md:implicit_adrs.[2]` ("**Read counts as a write — `getDetails` runs inside `@ReactiveTransactional` and side-effects `view_count`.** `DataEntityServiceImpl.java:197` carries `@ReactiveTransactional`; line 199-208 chains `incrementViewCount` into the pipeline; `ReactiveDataEntityRepositoryImpl.java:173-180` issues an `UPDATE data_entity SET view_count = view_count + 1 WHERE id = ?` with `.returningResult(...)` so the new value is returned and reflected in the response. The decision: track view-count for the `getPopular` ranking (`DataEntityController.java:308-313`) and the recommendation panel, accepting that every read is also a write at the DB layer." — intent_anchor: "the explicit `incrementViewCount` step in the orchestration chain, paired with the `viewCount` field surfaced in the DataEntityDetails contract (`DataEntityDetails.java:84`) and the `getPopular` endpoint that consumes it")
  - **Decision statement**: `DataEntityController.getDataEntityDetails` is the platform's only documented read endpoint that runs inside `@ReactiveTransactional` and performs a write side-effect as part of the read pipeline. `DataEntityServiceImpl.getDetails` (line 197) carries `@ReactiveTransactional`; the orchestration chain at lines 199-208 reads `getDetails` → enrich-class details (5-zip) → enrich-parents → enrich-details (4-zip) → `incrementViewCount` → `mapDtoDetails`. The increment fires `UPDATE data_entity SET view_count = view_count + 1 WHERE id = ?` via `ReactiveDataEntityRepositoryImpl.java:173-180` and the new value is reflected in the response's `DataEntityDetails.viewCount` field. The decision codifies: (a) view-count is platform state worth tracking (powers `getPopular` ranking + recommendation panel via `getMostPopular`); (b) read-call counting at the controller boundary is preferable to async aggregation or sampling — every detail render is precisely counted; (c) the transactional boundary ensures that a failed enrichment rolls back the increment, so the count reflects successful renders only. Trade-off accepted: (i) hot-key write contention on popular entities (REFACTOR-201's perf consequence); (ii) trivial inflatability — a malicious client can script `GET /api/dataentities/{id}` to push an entity to the top of Popular (REFACTOR-201's correctness consequence); (iii) no HTTP-cache headers can be applied to this endpoint without breaking the count semantic (REFACTOR-200's cache-headers absence is partly defended by this ADR).
  - **Wisdom test**: PASS. The explicit `@ReactiveTransactional` placement + the chained `incrementViewCount` + the `viewCount` field's first-class presence on the published `DataEntityDetails` contract + the `getPopular` consumer endpoint are all positive design choices. The alternative (async view-count aggregation, e.g., a sampling counter or a queue-fed write path) would have decoupled the count from the read; the maintainer chose the synchronous in-transaction increment. Structural for the detail endpoint's identity as "read-write hybrid".
  - **Evidence**:
    - getDataEntityDetails.md says: "DataEntityServiceImpl.java:197-208 (`@ReactiveTransactional` + `.flatMap(this::incrementViewCount)`) + ReactiveDataEntityRepositoryImpl.java:173-180 (the UPDATE statement)"
    - getDataEntityDetails.md says: "DataEntityController.java:308-313 (`getPopular` consumes `view_count` for ranking) + DataEntityDetails.java:84 (`viewCount` first-class published field)"
  - **Existing ADR**: none. Composes with ADR-CANDIDATE-007 (uniform Mono pipeline — the controller still emits `.map(ResponseEntity::ok)`; the transaction is at the service, not the controller) and ADR-CANDIDATE-056 (zip-merge multi-stage enrichment — the increment is the chain's final step before serialisation).
  - **Co-surfaced gaps** (link from `refactoring-scopes.md`): REFACTOR-201 (view-count UPDATE inside `@ReactiveTransactional` — retries inflate, rollbacks silently roll back the increment, no idempotency key, trivial inflation by scripted reads to push to Popular; MEDIUM), REFACTOR-211 (`view_count` hot-key write-contention scales as O(reads) — Postgres row-locks on popular entities; MEDIUM perf). The ADR's design DOES NOT defend these gaps; the maintainer's triage decision is whether view-count should be moved to an eventually-consistent counter (async aggregation, dedicated counters table, or in-memory micrometer counter flushed periodically) to preserve the ranking signal while removing the hot-key write contention.
  - **Proposed action**: Promote to `adrs/drafts/data-entity-detail-read-as-write.md` (new ADR). Document the trade-off explicitly: synchronous in-transaction view-count is precise but creates hot-key write contention + correctness gaps (REFACTOR-201, REFACTOR-211). Cross-link with ADR-CANDIDATE-056 (zip-merge enrichment) and ADR-CANDIDATE-007 (uniform Mono pipeline). Doc-side: the live `/features/data-discovery` page should mention that view-count powers Popular ranking (so operators understand why detail reads are not idempotent).
  - **Severity rationale**: MEDIUM — feature-architecture decision; affects every detail read in the platform. The transactional coupling of read+write is unusual enough to warrant explicit codification.
