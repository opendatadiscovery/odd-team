## What

In the Integration code-snippet wizard, a numeric parameter (any argument whose `type` is not `STRING` — i.e. the `number` branch) is rendered with `type='number'` but is **never validated for being a sensible number**. The form's `validate` rule only checks the **string** case (a non-empty trimmed string); for the numeric field the rule returns `undefined`, which react-hook-form treats as "valid". As a result a user can paste or type a negative value, a decimal, or a non-numeric string (which an `<input type="number">` surfaces as an empty/`NaN` value) and the **Configure** button stays enabled. The unchecked value is substituted into the Handlebars template and ends up verbatim in the `collector_config.yaml` snippet the operator copies out — so a wizard field intended to capture, say, a positive integer port/limit can emit `-3`, `1.5`, or a blank into a config the operator then trusts.

## Where

`components/Management/Integrations/Integration/IntegrationContent/IntegrationCodeSnippetWithForm/IntegrationCodeSnippetWithForm.tsx:86-90` — the `validate` rule short-circuits to `undefined` for anything that isn't a string:

```tsx
rules={{
  required: true,
  validate: value => {
    if (typeof value === 'string') return !!value.trim();
    // no `return` for the numeric branch -> undefined -> treated as valid
  },
}}
```

`IntegrationCodeSnippetWithForm.tsx:101` — the same field is rendered as a numeric input, so the value reaching `validate` is a number (or `NaN`/empty on a non-numeric paste), which the rule above never inspects:

```tsx
type={arg.type === 'STRING' ? 'string' : 'number'}
```

The `Configure` button is gated only on `formState.isValid` (line 117), so a value that the `validate` rule waves through enables submit, and `handleParamsFormSubmit` (line 28-31) feeds it straight into the compiled template at line 26 / 130.

## Why it matters

Silent. There is no error state, no disabled button, and no log — the operator gets a green Configure and a config snippet that looks authoritative. The wizard's whole purpose is to hand operators a correct copy-paste config; a wizard that emits a negative or decimal where a positive integer is required produces a config that fails (or, worse, misbehaves) only later at collector runtime, far from the field that caused it. Bounded blast radius (one operator's generated snippet, caught at collect time), hence medium — but it defeats the wizard's core promise of producing a valid config.

## Suggested fix

Validate the numeric branch in the same `validate` rule, parallel to the string branch:

```tsx
validate: value => {
  if (typeof value === 'string') return !!value.trim();
  return Number.isFinite(value) && value >= 0;   // refine min / integer-only per arg semantics
}
```

If the argument schema carries min/max/integer-vs-decimal hints, enforce those (and surface a field-level error message rather than only disabling Configure). Open to alternatives on exactly which numeric constraints apply — the load-bearing change is that the non-string branch is no longer waved through unconditionally.

**How to verify:** a negative, decimal, or empty/`NaN` numeric value disables the Configure button (or shows a field-level error) instead of producing a snippet — a react-hook-form unit/component test on the numeric branch.

## How discovered

Surfaced during a product-owner review of the Integration code-snippet wizard, then confirmed by reading `IntegrationCodeSnippetWithForm.tsx` (the `validate` rule has no numeric branch, while the field renders as `type='number'`).
