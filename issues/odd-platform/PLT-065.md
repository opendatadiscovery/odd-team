## What

`AuthIdentityProviderImpl.java:32` emits `UserDto(name, null)` for any auth mode that isn't OAUTH2 (LOGIN_FORM, LDAP, DISABLED, S2S). Four LEFT JOIN sites in `ReactiveActivityRepositoryImpl.java` (lines 157-158, 178-179, 199-200, 221-222) join `USER_OWNER_MAPPING ON OIDC_USERNAME = ACTIVITY.CREATED_BY AND DELETED_AT IS NULL` — **provider-AGNOSTIC**.

Multi-mode deployments (e.g., LOGIN_FORM 'alice' + LDAP later imports 'alice') see row duplication in the activity feed + non-deterministic OwnerPojo display. Forensic incident response over the audit feed is misled — a LOGIN_FORM user and an LDAP user with the same name resolve to the same OwnerPojo even when they are different people.

## Why it matters

For incident-response operators auditing "who did X at time T" in a multi-mode deployment, the platform's audit feed is unreliable. The bleed is silent — no error, just inconsistent OwnerPojo display name. Non-deterministic across replicas if the most-recent USER_OWNER_MAPPING row varies by replica.

## Suggested fix

Add `AND PROVIDER = ?` to every LEFT JOIN to USER_OWNER_MAPPING. Schema migration optional (the bleed is purely a JOIN-condition issue). Pseudo-SQL pattern:

```sql
LEFT JOIN user_owner_mapping uom
  ON uom.oidc_username = activity.created_by
  AND uom.provider = ?    -- NEW: provider discriminant
  AND uom.deleted_at IS NULL
```

The `?` is bound at query time from the AuthIdentityProvider — for LOGIN_FORM and LDAP this is the literal mode name; for OAUTH2 it's the provider-id. For DISABLED the provider is NULL (no need to JOIN at all — synthetic admin).

For S2S filter — the entry is `null`-provider per AuthIdentityProviderImpl.java:32; a separate JOIN with `provider IS NULL` is needed to maintain backward compatibility with existing S2S-created activity rows.

Verification path: write integration test that creates 2 USER_OWNER_MAPPING rows for `alice` in different providers, then asserts that activity-feed rendering returns distinct OwnerPojo display names.
