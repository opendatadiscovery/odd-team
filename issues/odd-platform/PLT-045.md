## What

`POST /ingestion/entities` is the load-bearing collector ingestion endpoint. Defects on the error-contract + observability surface mean custom-collector authors writing retry-with-backoff get the wrong signals on SOME client errors, the row-lock contract has no signal for contended writes, and the rollback-path logs are empty.

**Defect 1 - SOME client-error conditions surface as HTTP 5xx (F-096a).** Re-verified at primary source 2026-06-10 against `ControllerAdvice` (a GLOBAL `@RestControllerAdvice`, `ControllerAdvice.java:20`):
- **Duplicate ODDRN in batch** -> `Collectors.toMap(DataEntityIngestionDto::getOddrn, identity())` at `IngestionServiceImpl.java:86` (in `persistDataEntities`, run inside the `ingest` flatMap) uses the DEFAULT throwing merger -> `IllegalStateException: Duplicate key` -> falls through to the catch-all `@ExceptionHandler(Exception.class)` (`ControllerAdvice.java:61-62`) -> **HTTP 500** (should be 400). HOLDS.
- **Oversized payload** -> Spring's body codec raises `DataBufferLimitException` (extends `IllegalStateException`); no specific handler exists, so the catch-all maps it to **HTTP 500** (should be 413). HOLDS structurally (the exact status is not driven - WebFlux may surface a codec error differently; see ## User-facing impact).
- **Unknown `data_source_oddrn`** -> `dataSourceRepository.getIdByOddrnForUpdate(...).switchIfEmpty(Mono.error(() -> new NotFoundException("dataSource", ...)))` at `IngestionServiceImpl.java:68-69` raises `NotFoundException`, which the GLOBAL advice maps to **HTTP 404** (`ControllerAdvice.java:30-32`). **This is already a clean client error - the original "5xx" claim is FALSIFIED** (corrected 2026-06-10). A well-behaved collector will not retry-storm a 404.

So the retry-storm hazard is real for duplicate-ODDRN and oversized-payload (both 500), NOT for unknown-datasource (404). A collector author writing retry-with-backoff on 5xx still piles on for the first two.

**Defect 2 - `data_source_oddrn` row-lock held for FULL pipeline duration (F-096b).** `dataSourceRepository.getIdByOddrnForUpdate(...)` at `IngestionServiceImpl.java:66-68` issues a Postgres `SELECT ... FOR UPDATE` against the `data_source` row at the head of the `@ReactiveTransactional ingest(...)` pipeline; the lock is held for the FULL pipeline duration (datasource resolution + 14-processor chain + OTLP export). Two concurrent collectors emitting to the SAME datasource serialise on the lock; the loser may exceed the transaction timeout -> 5xx with **no `Retry-After` header**, no 429 signal.

**Defect 3 - Zero `log.*` calls in the ingest body (F-096c).** `@Slf4j` annotation at `IngestionServiceImpl.java:53` materialises a `log` reference. The `ingest(...)` method body at lines 65-94 has ZERO `log.*` invocations - even at DEBUG. Operators looking at platform logs see only the exception trace, not the discriminator (collector-id, datasource-oddrn, entity count). The SRE response window is doubled: needs platform-side application-log access to find the actual exception.

## User-facing impact

This is a BE/contract-only issue; the "user" is a collector / API consumer of `POST /ingestion/entities`. No UI surface.

- **Duplicate ODDRN in batch -> HTTP 500 - verified by BE trace 2026-06-10 (code-settled).** `toMap` throwing merger (`IngestionServiceImpl.java:86`) -> `IllegalStateException` -> global catch-all (`ControllerAdvice.java:61-62`). A client bug is reported as a server error; a collector retrying on 5xx storms the platform with an un-fixable-by-retry payload. Should be 400.
- **Unknown datasource -> HTTP 404 - verified by BE trace 2026-06-10 (code-settled). The draft's "5xx" was wrong.** `NotFoundException` (`:68-69`) -> global advice (`ControllerAdvice.java:30-32`). Already a clean, correct client error; no fix needed; no retry storm.
- **Oversized payload -> HTTP 5xx (likely 500) - static trace consistent; NOT driven.** `DataBufferLimitException` has no dedicated handler, so the catch-all should map it to 500, but WebFlux can surface a body-decode failure as a wrapped input error; the exact status needs a drive (POST a body over `spring.codec.max-in-memory-size` and read the status). Should be 413.
- **Concurrent collectors to the same datasource serialise on a row lock - static trace consistent; NOT driven.** `getIdByOddrnForUpdate` is a real `SELECT ... FOR UPDATE` (`ReactiveDataSourceRepositoryImpl.java:94-98`) held for the full `@ReactiveTransactional ingest` pipeline (`:66-73`). Two collectors emitting to the same datasource serialise; whether the loser times out (and with what status, and the absence of a 429/`Retry-After`) needs a concurrency drive.
- **Zero observability on the ingest path - verified by BE trace 2026-06-10 (code-settled).** `@Slf4j` is present (`:53`) but `grep 'log\.'` over `IngestionServiceImpl.java` returns nothing - no `log.*` anywhere. On any failure the collector sees only the HTTP status; the discriminator (datasource-oddrn, entity count) is in no log line.

## Why

Custom-collector authors write retry-with-backoff against the public ingestion contract. The platform currently returns the same status (5xx) for "your batch had a duplicate ODDRN" (client bug) and "the platform crashed" (platform bug). Retry storms against the former pile on the platform for the entire retry budget; retry storms against the latter never recover.

The row-lock contention dimension compounds this: under any concurrent-collector deployment (the platform's expected pattern), two collectors emitting to the same datasource serialise. Without a 429 + `Retry-After`, the loser's retry storm worsens the contention.

The logging absence makes SRE response 2-3x slower - the only signal in collector logs is "HTTP 500"; the actual exception (and the discriminator that scopes the failure to a specific batch / datasource / entity count) only lives in the platform application log, which collector-side responders typically can't reach.

## How

Per-defect fix:

**Defect 1 - structured error responses:**

```java
// In IngestionServiceImpl.ingest, change the duplicate-key merger:
.map(dtos -> dtos.stream()
    .collect(Collectors.toMap(
        DataEntityIngestionDto::getOddrn,
        identity(),
        (a, b) -> {
            throw new BadUserRequestException(
                "Duplicate ODDRN in batch: " + a.getOddrn());
        }
    )))

// NOTE: unknown-datasource already maps to 404 via the global ControllerAdvice (NotFoundException handler) -
// no new handler needed for it. Only the duplicate-key (-> 400) and oversized-payload (-> 413) need fixing.

// Add a DataBufferLimitException handler to the global ControllerAdvice (currently it falls to the catch-all -> 500):
@ExceptionHandler(DataBufferLimitException.class)
public ResponseEntity<ErrorEnvelope> handlePayloadTooLarge(DataBufferLimitException e) {
    return ResponseEntity.status(HttpStatus.PAYLOAD_TOO_LARGE)  // 413
        .body(new ErrorEnvelope("PAYLOAD_TOO_LARGE", "Increase spring.codec.max-in-memory-size or reduce batch size"));
}
```

**Defect 2 - narrow the lock scope OR ship a 429 signal:**

Option A (preferred): narrow the lock scope. Resolve the datasource id BEFORE entering the `@ReactiveTransactional` boundary (un-`FOR UPDATE` lookup), then start the transaction with just the id - no row-lock for the pipeline body.

Option B (fallback): catch the transaction-timeout exception and surface as HTTP 429 with `Retry-After`:
```java
.onErrorMap(TransactionTimeoutException.class, e -> 
    new ResponseStatusException(HttpStatus.TOO_MANY_REQUESTS, "Datasource ingestion serialised; retry with backoff", 
        Map.of("Retry-After", "30")))
```

**Defect 3 - structured logging on every rollback path:**

```java
// In IngestionServiceImpl.ingest, after the row-lock entry:
.doOnNext(id -> log.info("ingest start collector={} datasource_oddrn={} entity_count={}",
    collectorId, dataEntityList.getDataSourceOddrn(), dataEntityList.getItems().size()))
.doOnError(e -> log.warn("ingest rollback collector={} datasource_oddrn={} entity_count={} cause={}",
    collectorId, dataEntityList.getDataSourceOddrn(), dataEntityList.getItems().size(), e.getMessage(), e))
```

(`collectorId` requires plumbing - substrate-batch finding F-097c also hits this; consider a request-scoped `IngestionContext` bean.)

## Tests

- Integration test on duplicate-ODDRN in batch: POST with `{ items: [{oddrn: X, ...}, {oddrn: X, ...}] }` returns 400 with `error_code: DUPLICATE_ODDRN`.
- Integration test on unknown-datasource: POST with `{ data_source_oddrn: "unknown" }` returns 404 with `error_code: DATASOURCE_NOT_FOUND`.
- Integration test on oversized payload: POST > `spring.codec.max-in-memory-size` returns 413.
- Concurrent-collector test (Option A): 10 concurrent POSTs to the same datasource succeed without serialisation; OR (Option B): contended POSTs return 429 with `Retry-After`.
- Log-assertion test: ingestion success emits an `INFO ingest start` log line; ingestion failure emits a `WARN ingest rollback` log line; both lines include collector-id + datasource-oddrn + entity-count.

## How discovered

Mode B batch-6 triage (2026-05-27). **Corrected 2026-06-10 (user-facing verification sweep): one of the three "client error -> 5xx" sub-claims FALSIFIED.** `ControllerAdvice` is a GLOBAL `@RestControllerAdvice` (`:20`) that maps `NotFoundException` -> 404 (`:30-32`), so unknown-datasource was ALREADY a clean 404, not 5xx; only duplicate-ODDRN (500 via catch-all) and oversized-payload (likely 500) misreport client errors as server errors. Defect 2 (FOR-UPDATE row-lock for the full pipeline) and Defect 3 (zero `log.*` in the ingest body) HOLD as code-settled. Severity high -> medium: the headline 5xx count dropped from 3 to 2 and the surviving items are error-contract / observability / concurrency hardening, with no data-loss or security dimension. `user_facing_verified` stays false: the oversized-payload status and the concurrency serialisation/timeout are not driven.
