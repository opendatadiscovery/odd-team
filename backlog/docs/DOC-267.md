## Description

`authorization/owners.md` is 9 lines after batch-12 (DOC-207..224) shipped a 118-line `user-owner-association.md`. The owners page reads:

> ODD Platform allows to create platform-managed users — owners. Owners are Data Owners — people who manage and maintain a particular data entity or term.
>
> You can manage owners in the [Management → Owners](../../../management.md) tab.
>
> ...
>
> Every ODD Platform user should associate themselves with one of the existing owners. This process is described in the [User-owner association](user-owner-association.md) section.

This is structurally inconsistent with what the platform actually does and what the batch-12-expanded user-owner-association.md now describes:

1. **"Platform-managed users" is misleading.** Owners are NOT users — they are catalog identities that users bind to. A user has an OIDC/LDAP/S2S auth identity; an Owner is a separate, catalog-side row with its own name, roles, and lifecycle. The 1-to-1 binding between user and Owner is the bridge. The "platform-managed users" framing makes operators assume Owners are an auth-side construct.

2. **The Owner directory is freeSolo accreted, not curated.** The new user-owner-association.md describes the freeSolo Owner-name input (`OwnerAssociationForm.tsx:167-172`) + the `OwnerServiceImpl.getOrCreate` side-door (`OwnerServiceImpl.java:38-42`): typing a brand-new owner name on the home-page form mints a new Owner row. With `DIRECT_OWNER_SYNC` on the same caller, the new Owner is created AND bound in one POST. Owners.md is silent on this accretion model and on the cleanup recommendation.

3. **Owners.md doesn't enumerate the three write-paths to a binding.** The new user-owner-association.md describes self-request + DIRECT_OWNER_SYNC auto-approve + admin direct-bind as the three paths. Owners.md mentions only the self-request path implicitly via "every user should associate themselves".

4. **Owner roles are not mentioned.** Roles.md describes Owner roles as the bound user's effective role (superseding user roles), but Owners.md doesn't mention that an Owner CAN carry roles, or how to attach them.

5. **Permission gates on the Owner CRUD surface** (`OWNER_CREATE`, `OWNER_UPDATE`, `OWNER_DELETE`) are not named on owners.md. They are on permissions.md but a reader of owners.md has no hint they exist.

## Acceptance Criteria

- [ ] Rewrite `owners.md` to ~50-80 lines covering:
  - [ ] **What an Owner is** — a catalog identity distinct from the user identity; named row in the `owner` table; can be bound to zero or one user; carries optional Owner roles; serves as the unit of ownership on data entities.
  - [ ] **How Owners are created** — three paths: (a) Management → Owners → Create owner button (`OWNER_CREATE` gate), (b) freeSolo accretion when a user types a new name on the home-page Owner-association widget (the [Choosing an owner name](user-owner-association.md#choosing-an-owner-name) flow), (c) freeSolo accretion when a user with `DIRECT_OWNER_SYNC` submits the same form (auto-approve). Cross-link the three paths to user-owner-association.md sections.
  - [ ] **Owner names accumulate over time** — the freeSolo input does not deduplicate against case / whitespace variants; recommend a deployment-wide owner-name convention; cleanup is via Management → Owners.
  - [ ] **Owner roles** — name the role-attach affordance; describe owner-role-supersedes-user-role precedence (cross-link roles.md); name `ROLE_CREATE` / `ROLE_UPDATE` / `ROLE_DELETE` gates.
  - [ ] **Owners on data entities** — ownership relation (entity → owner) is curated on each entity's detail page; cross-link the entity-detail-page.md Permissions surface section.
  - [ ] **Where to next** — cross-link user-owner-association.md, roles.md, permissions.md, management.md (the Owners tab), and the entity-detail-page.md.
- [ ] Verify the rewritten page is internally consistent with user-owner-association.md (the new 3-branch write-path framing) and with permissions.md (the Owner CRUD + relation gates).
- [ ] Live-site verification post-merge: WebFetch the rewritten URL and confirm all sections render.

## Context

Found during the `/review` editorial audit after batch-12 shipped. The cross-page coherence check: when one page is comprehensively rewritten, every page that the rewritten page references back to should be checked for parallel-surface drift. owners.md is the natural "starting point" for an operator learning the Owner model — the 9-line stub is the front door to a 118-line interior, with no transition.

This is a **Gate 6 (bidirectional code↔doc coverage) + Gate 10 (content-type homing)** finding: owners.md is the canonical home for the Owner-model content type. Currently it embeds zero of the Owner model — that content lives on user-owner-association.md and on permissions.md. The fix is to give owners.md its proper content load.
