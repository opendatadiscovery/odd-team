## Description

The live Relationships page (`docs.opendatadiscovery.org/features/data-modelling/relationships`, WebFetched 2026-05-27) documents the two-column contract (Source / Target entity), the type tab strip, infinite-scroll pagination at page-size 30, and the search input — but is silent on permissions and on the actual code-side behaviour of each documented surface. Primary-source verification against `../odd-platform/` surfaces six independent caveats that contradict or expand the live page.

**Caveat 1 — Target column displays the SOURCE data entity (F-037a — code bug visible on every list view).** `RelationshipsListItem.tsx:73-81` (Target cell) renders `dataEntityId={item.sourceDataEntity.id}` + `name={item.sourceDataEntity.internalName || item.sourceDataEntity.externalName || ''}` + `oddrn={item.sourceDataEntity.oddrn || ''}` — **identical to the Source cell at lines 64-72**. `item.targetDataEntity` is never referenced anywhere in the 85-line file (it IS consumed correctly by sibling components `RelationshipTypes/EntityRelationship.tsx:33-35` and `RelationshipTypes/GraphRelationship.tsx:32-34`). Operators see the same dataset in BOTH columns for every row. The discovery workflow "find all relationships where ORDERS is the target" is silently broken.

**Caveat 2 — No authorization gate at any layer; the list is a catalog-wide enumeration oracle (F-037b + F-037g).** None of the three relationship endpoints (list + erd-detail + graph-detail) has a `@PreAuthorize`, a `SecurityConstants` rule entry (verified by 357-line read per substrate batch-ZH), a service-level check, or a namespace / owner / `EXCLUDE_FROM_SEARCH` filter at `ReactiveDataEntityRelationshipRepositoryImpl`. The route mounts BARE — `DataModellingRoutes.tsx:40` contrasts with the wrapped query-examples route at lines 19-25 + 31-37. Every authenticated caller sees every relationship in the catalog including hidden and cross-tenant entries. Asymmetric to `/api/dataentities` (which DOES apply `EXCLUDE_FROM_SEARCH`). Multi-tenant deployments expecting team-scoped visibility expose every team's relationships to every authenticated user via this single page.

**Caveat 3 — Row-click navigates to the same data-entity URL regardless of type (F-037c).** The page says "the platform routes to the `/api/relationships/erd/{id}` or `/api/relationships/graph/{id}` payload depending on the relationship type." `RelationshipsListItem.tsx:52` calls `dataEntityDetailsPath(item.id)` UNCONDITIONALLY — the URL the operator lands on is identical for ERD and GRAPH. The type-specific endpoints are reached from inside the data-entity overview page's relationship-card rendering, not from the row click on the list. An operator scripting deep-links to "detail pages" cannot rely on the doc's URL prediction.

**Caveat 4 — Search filters by relationship name, NOT by source/target dataset name (F-037d).** `ReactiveDataEntityRelationshipRepositoryImpl.java:69` binds `?q=` to `DATA_ENTITY.EXTERNAL_NAME.containsIgnoreCase` on the relationship-class data_entity row. An operator typing "orders" expecting to find every relationship involving the ORDERS table is silently disappointed — the search matches the relationship's own name field.

**Caveat 5 — `?type=foo` URL param accepts arbitrary strings with no runtime validation (F-037e).** `Relationships.tsx:19` uses a TYPE ASSERTION (`as RelationshipsType`) with no runtime check. Any string propagates to the backend → opaque 400 from Spring enum binding; the UI tab strip silently shows no active tab (`RelationshipsTabs.tsx:27-32 findInitTabIdx` returns -1 for unknown). A deep-link with a typo'd `?type=` value yields blank UI with no error message.

**Caveat 6 — `relationship_id` parameter is silently `data_entity.id`, NOT `relationships.id` (F-037f).** `ReactiveRelationshipsRepositoryImpl.java:194` filters by `data_entity.id` (the entity_class=9 row representing the relationship). `RelationshipMapper.java:53` returns `id = data_entity.id`. The UI round-trip works because both sides use the same id. A third-party API consumer reading the OpenAPI spec literally and supplying `relationships.id` from a direct PostgreSQL query gets 404 OR a payload for an unrelated relationship.
