## What

Three related operator-trust defects on the Search subsystem. (1) The `search_facets` table has no `owner_id` / `created_by` column - session rows are server-side state shared by URL across any authenticated caller who learns the UUID. (2) The 7-endpoint Search controller has NO `@PreAuthorize` and the 6 facet aggregators apply no `OWNERSHIP` join - any authenticated caller drilling `/api/search/{id}/facet/OWNERS` enumerates the entire Owner directory plus per-owner counts; the same shape holds for `TAGS`, `NAMESPACES`, `DATASOURCES`, `GROUPS`, `TYPES`. (3) `JooqFTSHelper.tsQuery` does not escape tsquery operator characters (`(`, `)`, `&`, `|`, `!`, `*`, `:`) - a single POST with a malformed query like `foo )(` writes the broken string to the session row; every subsequent facet/list read calls `to_tsquery(?)` on it and returns HTTP 500. The poisoned state persists until the operator manually mutates the query string or the housekeeping job evicts the row (default 30 days).

**Defect 1 - Session row has no owner binding (F-017a - HIGH).** `V0_0_1__init.sql:204-211` declares the `search_facets` table with `id (uuid), query_string (varchar 255), filters (jsonb)`; `last_accessed_at` is added later by `V0_0_52__introduce_housekeeping.sql`. There is NO `owner_id`, NO `created_by`, and NO `deleted_at` (housekeeping hard-deletes the row). `searchRoutes.ts:7-12` builds the URL `/search/{searchId}` from the row UUID; `useSearchRouteParams()` (`searchRoutes.ts:18-19`) is consumed by `Search.tsx` (`Search.tsx:27`). Any authenticated user reaching the URL reaches the session row - the operator mental model of "URL = my opaque query state" is incorrect.

**Defect 2 - Cross-owner facet enumeration is the default (F-017b - HIGH).** `SearchController` (`SearchController.java:23-92`) carries zero `@PreAuthorize` annotations on the class or any of its 7 methods (verified this run); `SecurityConstants.java` has no `/api/search` rule and `/api/search` is not in `WHITELIST_PATHS` (verified zero matches), so search falls through to the global `.authenticated()` rule. `ReactiveSearchFacetRepositoryImpl`'s 6 data-entity facet aggregators apply only the default conditions (HOLLOW / STATUS != DELETED / EXCLUDE_FROM_SEARCH) - none scope the result to the caller's owner. Authenticated callers drilling `GET /api/search/{search_id}/facet/OWNERS` enumerate the platform's complete Owner directory + per-owner counts. Under `auth.type=DISABLED` the endpoints are anonymously reachable.

**Defect 3 - `JooqFTSHelper.tsQuery` does not escape tsquery operators (F-017c).** `JooqFTSHelper.tsQuery` (`JooqFTSHelper.java:164-168`) only splits the query on a single space and appends `:*` to each token; `ftsCondition` (`JooqFTSHelper.java:100-105`) then interpolates the result straight into `to_tsquery(?)`. tsquery treats `(`, `)`, `&`, `|`, `!`, `*`, `:` as syntactic operators; any unbalanced/malformed combination (or even a stray double space, which yields an empty `:*` token) raises `ERROR: syntax error in tsquery` at the database tier and the controller returns HTTP 500. Because `SearchServiceImpl.search` commits the row (`create`, `SearchServiceImpl.java:80`) *before* computing facets (`getFacetsData`, `SearchServiceImpl.java:81`) on separate non-transactional reactive operations, the malformed `query_string` is **persisted** even though the POST itself 500s; every subsequent read of that search id re-runs `to_tsquery` and fails the same way. The persistent, weaponisable vector is `PUT /api/search/{search_id}` (`updateSearchFacets`) against a *known* search id - the initial POST returns 500 without surfacing the new id (`useCreateSearch.ts:16` navigates only on success), but any caller who learns a search id can overwrite its query and DoS it for everyone who loads it, until the row is overwritten with a valid query or evicted by housekeeping (default 30 days of inactivity).

## User-facing impact

Two distinct user populations, both reachable by any authenticated caller (anonymous when `auth.type=DISABLED`):

**API consumer / search user - tsquery 500 (Defect 3, verified by BE trace 2026-06-10).** Any query containing a tsquery operator character (`( ) & | ! * :`) or a stray double space reaches `to_tsquery` unescaped (`JooqFTSHelper.tsQuery` `:164-168` tokenises on a single space and appends `:*`; `ftsCondition` `:100-105` interpolates the result into `to_tsquery(?)`), so PostgreSQL raises `syntax error in tsquery` and the request returns HTTP 500. `SearchServiceImpl.search` persists the row (`create`, `SearchServiceImpl.java:80`) before computing facets (`getFacetsData`, `:81`) on separate non-transactional reactive operations, so the `query_string` is committed even though the POST 500s; every later read of that id re-runs `to_tsquery` and 500s again - `getSearchFacetList` -> `getFacets` (`:65-72`), `getSearchResults` (`:98-112`), `getFiltersForFacet`. Verified by BE trace. In the UI the symptom is a broken search page: `Search.tsx` loads the facet list (`getDataEntitiesSearch`) and results for the routed id, surfacing the 500 via `handleResponseAsyncThunk` - static trace consistent; not driven.
  - Persistent / cross-owner reach: `PUT /api/search/{search_id}` (`updateSearchFacets`) overwrites any known row's query with no owner check (`search_facets` has no `owner_id`; no `SecurityConstants` rule on `/api/search`), so any caller who learns a colleague's shared/bookmarked search id can 500 it persistently. The exact persistence window (each read refreshes `last_accessed_at`, so an actively-retried poisoned row never ages out; an abandoned one is evicted after `housekeeping.ttl.search_facets_days`, default 30 - `application.yml:169`) and the cross-owner reachability are static-trace consistent; not driven.

**API consumer - cross-owner facet enumeration (Defect 2, verified by BE trace 2026-06-10).** `GET /api/search/{search_id}/facet/OWNERS` (path confirmed `/api/search/{search_id}/facet/{facet_type}`, `openapi.yaml:702`) returns every Owner name + per-owner entity count: `getOwnerFacetForDataEntity` (`ReactiveSearchFacetRepositoryImpl.java:340-372`) applies only `getDataEntityDefaultConditions` with no join scoping the result to the caller's owner; the TAGS/TYPES/GROUPS/STATUSES facets are the same shape. Whether this is a leak or the documented read-collaborative posture is deployment-dependent; the absence of caller-scoping is the verified code fact.

**Session row has no owner (Defect 1, verified by schema trace 2026-06-10).** `search_facets` is `id / query_string varchar(255) / filters jsonb` (`V0_0_1__init.sql:204-211`) plus `last_accessed_at` (added `V0_0_52`); no `owner_id`, no `created_by`, no `deleted_at`. `SearchController` has no `@PreAuthorize` and no `SecurityConstants` rule matches `/api/search`, so read and update of any search id fall through to the global `.authenticated()` rule only. Verified by BE/schema trace.

## Why it matters

- **Defect 3 is exploitable in one click.** Any authenticated caller can POST `query='foo )('` and the session row 500s on every subsequent read for the next 30 days. Under `auth.type=DISABLED` this is reachable anonymously. The blast radius is one session row per shot - but session rows are sharable URLs; a malicious / careless actor on a team can permanently break a teammate's bookmarked search.
- **Defect 2 leaks the multi-tenant boundary** in deployments where Owner / Namespace / Tag taxonomies map to organisational units. The `facet/OWNERS` enumeration is the load-bearing case (display names + counts of every Owner in the platform); but the same shape holds for `TAGS` (security labels), `NAMESPACES` (per-team scope), `GROUPS` (project groupings) - any taxonomy the operator built into their classification system leaks across owner boundaries.
- **Defect 1 is the load-bearing wire** for both (2) and (3) - the session row has no owner; a sharable URL is a sharable mutable cursor; an attacker who learns a colleague's URL can mutate the session state and poison it. Even after Defects 2 + 3 are fixed, the no-owner-binding is the persistent attack surface.

Severity HIGH because the compound is reachable in production deployments today; the fixes are bounded; operator workarounds are nonexistent (Defect 2 requires platform-side aggregator changes; Defect 3 requires escape logic in `JooqFTSHelper`; Defect 1 requires a schema migration + read-path filter).

## Suggested fix

Three coordinated fixes; defect 3 ships standalone if defects 1 + 2 require more design.

### (a) Defect 3 - Escape tsquery operator characters at `JooqFTSHelper`

```java
// odd-platform-api/src/main/.../repository/util/JooqFTSHelper.java
// Sanitize INSIDE the existing single-arg tsQuery(String) - the only place that builds the
// tsquery token string consumed by ftsCondition() / ftsRankField().
private static final Pattern TSQUERY_OPERATORS = Pattern.compile("[()&|!*:]");

public String tsQuery(final String plainQuery) {
    if (plainQuery == null || plainQuery.isBlank()) {
        return "";
    }
    // Strip operator characters; keep the existing tokenise + prefix-match (:*) + AND (&) behaviour.
    final String stripped = TSQUERY_OPERATORS.matcher(plainQuery).replaceAll(" ");
    return Arrays.stream(stripped.trim().split("\\s+"))
            .filter(s -> !s.isEmpty())
            .map(token -> token + ":*")          // prefix-match per existing UX
            .collect(Collectors.joining("&"));   // AND tokens (matches current joiner)
}
```

Operators typing `(` get the character stripped (meaningless as a search term anyway); operators typing `foo OR bar` get the words searched independently. Existing prefix-match (`:*`) and AND-join (`&`) behaviour preserved; the empty-token case (double space) is dropped instead of producing a bare `:*`.

### (b) Defect 2 - Add a security rule + per-tenant facet filter

```java
// odd-platform-api/src/main/.../config/SecurityConstants.java
.pathMatchers(HttpMethod.GET,  "/api/search/**").authenticated()  // explicit, not fall-through

// odd-platform-api/src/main/.../repository/ReactiveSearchFacetRepositoryImpl.java
//   In each of the 6 facet aggregators (Owners, Tags, Namespaces, Datasources, Groups, Types),
//   add a CTE that scopes the joined OWNERSHIP rows to the caller's owner_id (or omits the join
//   under an operator-configurable "read-collaborative" feature flag for deployments that opt
//   into the existing posture explicitly).
```

The aggregator should accept a caller-Owner-id parameter (from `ReactiveSecurityContextHolder`) and join through `OWNERSHIP` so a caller only counts entities they have ownership / view rights on.

## How discovered

Mode B run of `docs/coverage/undocumented-features` on 2026-05-27 (substrate `F-017` - Search Filter Facets; sidecar facets `search_session_uuid_no_owner_binding`, `cross_owner_facet_enumeration_via_facet_aggregators`, `tsquery_operator_injection_dos_via_persisted_query`). Three of the six F-017 facets graduate into this PLT as upstream code-side fixes; the doc-side caveats ship as **DOC-260**.

**Corrected 2026-06-10 (user-facing verification sweep):** the `## Where` citations were re-read against source and several were wrong; all three defects survive, re-scoped to the verified code. (1) `search_facets` columns - was `id/query_string/last_accessed_at/deleted_at`; actually `id/query_string(varchar 255)/filters` (`V0_0_1__init.sql:204-211`) with `last_accessed_at` added by `V0_0_52` and NO `deleted_at` (the no-owner-binding finding stands). (2) `SearchController` methods - was `createSearchFacets/searchDataEntities/getFilters/getSearchFacets`; actually `getFiltersForFacet/getSearchFacetList/getSearchResults/search/updateSearchFacets/getSearchSuggestions/highlightDataEntity` (`SearchController.java:23-92`; the no-`@PreAuthorize` finding stands). (3) `tsQuery` - was a 2-arg `tsQuery(Field<String>, String)` returning a `Condition`; actually `tsQuery(String)` returning a token string (`JooqFTSHelper.java:164-168`), with the `to_tsquery(?)` interpolation in `ftsCondition` (`:100-105`). (4) "a single POST DoSes the session" - actually the initial POST orphans the row without returning its id (`useCreateSearch.ts:16`), so the persistent vector is `PUT /api/search/{id}` against a known id (enabled by Defect 1's missing owner binding). Same failure mode as the PLT-176/PLT-167 lessons: code citations and a user-facing mechanism asserted without re-reading source end-to-end.
