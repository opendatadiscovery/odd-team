## What

Six operator-visible defects on the Data Modelling Relationships listing surface (`/data-modelling/relationships`). The listing is the entry point for ERD / Graph relationship discovery - operators land on it from sidebar navigation and expect to discover catalog topology. The published doc page (live 2026-05-27) describes a two-column source/target contract, a type-aware tab strip, a 30-row infinite-scroll list, and a search input. Primary-source verification surfaces six independent code-side defects against that contract.

**Defect 1 - Target column displays SOURCE data (one-line code bug).** `odd-platform-ui/src/components/DataModelling/Relationships/RelationshipsListItem.tsx:73-81` (Target cell) renders the SAME source-data fields as the Source cell at lines 64-72. `item.targetDataEntity` is never referenced anywhere in the 85-line file (sibling components `RelationshipTypes/EntityRelationship.tsx:33-35` and `RelationshipTypes/GraphRelationship.tsx:32-34` consume it correctly). Every relationship row in the catalog shows the same dataset in both columns.

**Defect 2 - No permission rule + no default visibility filters; the list keeps showing entities every sibling read surface hides.** Three relationship endpoints (list + erd-detail + graph-detail) have NO `SecurityConstants` rule entry (re-verified 2026-06-10: grep for `relationship` over the 356-line `auth/util/SecurityConstants.java` returns zero matches), no service-level check, and no visibility predicate at `ReactiveDataEntityRelationshipRepositoryImpl.getRelationships` - the only WHERE conditions are the entity-class match and the optional name filter (`:66-75`). The endpoints fall through to the global `.authenticated()` rule (`AuthorizationCustomizer.java:29-30`); under `auth.type=DISABLED` the whole API is `permitAll` anyway (`DisabledAuthSecurityConfiguration.java:16`). Honest scope (corrected 2026-06-10): ODD catalog READS carry no entity-level RBAC anywhere, so "any authenticated user can list all relationships" is the platform's documented read-open posture, not a relationships-specific bypass. The real, relationships-specific asymmetry is the missing default visibility predicates: the data-entity list/search tier applies `HOLLOW = false` + `STATUS != DELETED` + `EXCLUDE_FROM_SEARCH is null or false` as its defaults (`ReactiveDataEntityRepositoryImpl.getDataEntityDefaultConditions`, `:970-976`), while the relationships list applies NONE of the three - soft-DELETED and exclude-from-search-flagged relationship entities remain listed here after every other surface hides them.

**Defect 3 - Row-click routes to the same data-entity URL regardless of relationship type.** `RelationshipsListItem.tsx:52` calls `dataEntityDetailsPath(item.id)` UNCONDITIONALLY. The doc page promises type-specific routing; the implementation gives uniform routing. Doc-side fix (the cheap option) is captured in DOC-229 Caveat 3.

**Defect 4 - `?type=foo` URL param accepts arbitrary strings with no runtime validation.** `DataModelling/Relationships.tsx:19` (the file sits directly under `DataModelling/`, not `DataModelling/Relationships/`) is a TYPE ASSERTION (`as RelationshipsType`) with no runtime check. The raw string is sent verbatim to `GET /api/relationships`, whose generated controller binds `type` to the required `RelationshipsType` enum (`components.yaml:4393-4398`); an enum bind failure yields a 400 (static trace consistent; not driven). On the failed query the page renders the EMPTY state, not an error: `relationships` collapses to `[]`, `isEmpty` flips true, the H1 reads "0 relationships overall", and `EmptyContentPlaceholder` shows (`Relationships.tsx:26-36, 76`); the tab strip shows no active tab (`RelationshipsTabs.tsx:27-30` `findInitTabIdx` returns -1, which `AppTabs.tsx:45` maps to `false` - handled, no crash).

**Defect 5 - `relationship_id` is silently `data_entity.id`; the payload's own `*_relationship_id` fields do NOT round-trip into it.** `ReactiveRelationshipsRepositoryImpl.java:194` filters by the relationship-class row's `data_entity.id`; `RelationshipMapper.java:53` returns that same `data_entity.id` as the list item's `id`. Corrected 2026-06-10: the surface is SELF-consistent for the canonical flow - list `id` -> `/api/relationships/{erd|graph}/{relationship_id}` returns the right relationship, and the UI itself feeds the data-entity id into the param (`OverviewEntityRelationship.tsx:18`); the original "SDK consumers literally get 404 OR an unrelated relationship's payload" overstated the default experience. The real trap: the details payload exposes `erd_relationship_id` (= `erd_relationship_details.id`, `ErdRelationshipMapper.java:21`) and `graph_relationship_id` (= `graph_relationship.id`, `GraphRelationshipMapper.java:22`) - ids from two OTHER tables, neither valid as `{relationship_id}`. A consumer feeding either back into the path gets an empty/404 result, or - when the number collides with another relationship's `data_entity.id` - an unrelated relationship's payload.

**Defect 6 - Search filters by relationship name, NOT by source/target dataset name.** `ReactiveDataEntityRelationshipRepositoryImpl.java:69` binds `?q=` to `DATA_ENTITY.EXTERNAL_NAME.containsIgnoreCase` on the relationship-class row only. (Doc-side caveat in DOC-229 Caveat 4; code-side fix optional - the operator may prefer source/target-name search.)

## User-facing impact

- **Defect 1 (verified by FE trace 2026-06-10):** every row on `/data-modelling/relationships` renders the SOURCE dataset in BOTH the Source and Target columns - `RelationshipsListItem.tsx:74-79` passes `item.sourceDataEntity.{id,internalName,externalName,oddrn}` to the Target cell; `item.targetDataEntity` appears nowhere in the 85-line file. An operator asking "what does this relationship point AT?" cannot get the answer from the list; the correct target IS shown after click-through (the entity Overview uses `targetDataEntity` correctly - `EntityRelationship.tsx:33-35`, `GraphRelationship.tsx:32-34`).
- **Defect 2 (static trace; read posture):** any authenticated user (any visitor under `auth.type=DISABLED`) can page through all relationships, INCLUDING relationship entities that are soft-DELETED or flagged `exclude_from_search` - the repository applies none of the default visibility predicates the data-entity surfaces apply (verified by BE trace 2026-06-10, `ReactiveDataEntityRelationshipRepositoryImpl.java:66-75` vs `ReactiveDataEntityRepositoryImpl.java:970-976`). Listing per se is the platform-wide read-open posture, not a bypass.
- **Defect 3 (verified by FE trace 2026-06-10):** clicking any row lands on the generic data-entity URL (`RelationshipsListItem.tsx:52`); the destination page is functional and renders type-specific relationship detail, so the impact is URL semantics, not a broken landing.
- **Defect 4 (FE half verified by trace 2026-06-10; BE 400 static trace consistent, not driven):** a mistyped/stale `?type=` deep-link renders an empty list + "0 relationships overall" + no active tab + NO error message - indistinguishable from an empty catalog.
- **Defect 5 (verified by FE+BE trace 2026-06-10):** UI users are unaffected (the UI feeds the right id everywhere). Only API/SDK consumers that feed the payload's `erd_relationship_id`/`graph_relationship_id` back into `{relationship_id}` get 404/wrong-entity responses.
- **Defect 6 (verified by BE trace 2026-06-10):** the search box matches only the relationship entity's own `external_name` (`:69`); searching by source/target dataset name silently returns nothing.

## Why it matters

The Data Modelling pillar's flagship discovery surface is visibly wrong on every row and silently inconsistent with the rest of the catalog:

- **Discovery workflow broken** (Defect 1): operators cannot answer "what relationships point at ORDERS?" from the list page - the Target column repeats the Source dataset on 100% of rows.
- **Visibility-filter asymmetry** (Defect 2): soft-DELETED and exclude-from-search-flagged relationship entities stay listed here after every other catalog surface hides them; and there is no RBAC hook to scope the surface if a deployment ever needs one.
- **API contract trap** (Defect 5): the `*_relationship_id` fields the details payload exposes are not valid inputs for the `{relationship_id}` path param they appear to name.

Severity stays CRITICAL on the strength of Defect 1 alone: the feature's primary listing renders factually wrong data in one of its two contract columns for every relationship in the catalog (verified 2026-06-10); the remaining defects are high-grade hardening around the same surface.

## Suggested fix

Three distinct fixes; recommend grouping into 2 PRs:

### PR-1 - Display + UX (Defects 1 + 4)

**Defect 1 - one-line rename:**

```tsx
// RelationshipsListItem.tsx:75-79
- dataEntityId={item.sourceDataEntity.id}
- name={item.sourceDataEntity.internalName || item.sourceDataEntity.externalName || ''}
- oddrn={item.sourceDataEntity.oddrn || ''}
+ dataEntityId={item.targetDataEntity.id}
+ name={item.targetDataEntity.internalName || item.targetDataEntity.externalName || ''}
+ oddrn={item.targetDataEntity.oddrn || ''}
```

**Defect 4 - runtime validate the `?type=` param:**

```tsx
// Relationships.tsx:19
- const type = (searchParams.get('type') ?? RelationshipsType.ALL) as RelationshipsType;
+ const rawType = searchParams.get('type') ?? RelationshipsType.ALL;
+ const type = Object.values(RelationshipsType).includes(rawType as RelationshipsType)
+   ? (rawType as RelationshipsType)
+   : RelationshipsType.ALL;
```

### PR-2 - Authorization + scoping (Defects 2 + 5)

**Defect 2 - apply the catalog's default visibility predicates (and optionally an RBAC hook):**

Minimum, no-design-cost fix: add the same three default conditions the data-entity tier uses (`ReactiveDataEntityRepositoryImpl.getDataEntityDefaultConditions`, `:970-976`) to `ReactiveDataEntityRelationshipRepositoryImpl.getRelationships`:

```java
conditionList.add(DATA_ENTITY.HOLLOW.isFalse());
conditionList.add(DATA_ENTITY.STATUS.ne(DataEntityStatusDto.DELETED.getId()));
conditionList.add(DATA_ENTITY.EXCLUDE_FROM_SEARCH.isNull().or(DATA_ENTITY.EXCLUDE_FROM_SEARCH.isFalse()));
```

A `/api/relationships/**` SecurityConstants entry + permission is a separate, larger decision (catalog reads are RBAC-free platform-wide today; introducing read RBAC here alone would be the inconsistency).

**Defect 5 - rename or document the `relationship_id` semantic alias:**

Two options:
- **Option A (recommended)** - document the alias in the OpenAPI spec (parameter description + a `x-semantic-note: "relationship_id is the data_entity.id of the relationship-class entity (entity_class=9)"` extension), and state explicitly that `erd_relationship_id` / `graph_relationship_id` in the details payload are NOT valid `{relationship_id}` inputs. Doc-side fix is DOC-229 Caveat 6.
- **Option B** - rename the OpenAPI parameter to `data_entity_id` (breaking change for existing SDKs).

### Defect 3 (cheap doc-side fix) is captured in DOC-229 Caveat 3 - no code change required unless the team wants true type-specific URLs (would require new UI routes).

### Defect 6 (search scope) - operator-judgement call. Either extend the SQL to also match source/target entity names (cheap; DOC-229 Caveat 4 documents the current scope), or leave as-is and accept the caveat.
