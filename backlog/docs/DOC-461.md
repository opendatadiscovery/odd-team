## Description

The `NAMESPACE_CREATE` operator-caveat on `permissions.md:93` is internally inconsistent: it says "**four** sister-service side-doors" and "**four** other parent permissions" but then **lists five** permission keys. An operator counting the listed keys against the "four" label cannot tell whether the count is wrong, a key is spurious, or one is missing — and this is the security-relevant blast-radius statement (which permissions are an indirect grant of namespace-creation), so an imprecise count erodes trust in the exact surface an operator audits.

The canonical home for this caveat — the [Namespaces page](../../../management/namespaces.md) `## Auto-create side-door` section — gets it right by framing the cluster as **four sister *services*** and listing four service rows; the Data Source service row carries **two** verbs/permissions (`DATA_SOURCE_CREATE`, `DATA_SOURCE_UPDATE`), so the cluster is **four services / five permissions**. `permissions.md:93` collapses the two axes ("four" services vs five permissions) into a single mislabelled "four", producing the verbatim "four ... (lists five)" contradiction.

## Acceptance Criteria

- [ ] `permissions.md:93` (`NAMESPACE_CREATE` row) reconciles the count: state the cluster as **four sister services** carrying **five permissions** (because the Data Source service contributes both `DATA_SOURCE_CREATE` and `DATA_SOURCE_UPDATE`), OR drop the "four" service-count framing from this page and simply say "the following five parent permissions silently mint namespace rows" — either way the stated number matches the enumerated keys.
- [ ] The number is reconciled against code (`NamespaceServiceImpl.getOrCreate` callers) before publishing — confirm the four service entry-points and the five permission gates listed on the Namespaces page (`management/namespaces.md:60-74`) are the true and complete set; correct both pages if code disagrees.
- [ ] The `permissions.md` framing and the Namespaces page framing agree on the same number(s) and the same key list (Cornerstone-2 single-source: the Namespaces page is canonical; `permissions.md` cross-links to it, already does at `:93`).
- [ ] Operator language only — no workspace IDs on the published page (Gate 11).

## Context

Surfaced by the 2026-06-16 editorial audit of `enable-security/` during the CTRIB-018 review.

**Failure shape:** stale-claim / count-drift (parallel surfaces). The caveat exists and is substantively correct on both pages; only the *count label* on `permissions.md` is wrong, and it disagrees with its own enumeration.

**Verbatim passage** — `permissions.md:93`:
> `NAMESPACE_CREATE`. Allows creating a new namespace via `POST /api/namespaces`. **Operator caveat — four sister-service side-doors**: four other parent permissions (`DATA_SOURCE_CREATE`, `DATA_SOURCE_UPDATE`, `TERM_CREATE`, `COLLECTOR_CREATE`, `DATA_ENTITY_GROUP_CREATE`) silently mint namespace rows through their `namespace_name` form field. ... See [Namespaces → Auto-create side-door](../../../management/namespaces.md#auto-create-side-door) for the four-vertex cluster and the operator-side mitigation.

That sentence says "four" twice and lists five keys.

**Canonical-home evidence** — `management/namespaces.md`:
- `:60` — "**four sister services on the platform mint Namespace rows** through the side-door `NamespaceServiceImpl.getOrCreate(name)`". The four callers are then listed as a table (`:64-67`): Data Source service (`POST /api/datasources`, `PUT /api/datasources/{id}` → `DATA_SOURCE_CREATE`, `DATA_SOURCE_UPDATE`), Term service (`TERM_CREATE`), Collector service (`COLLECTOR_CREATE`), Data Entity Group service (`DATA_ENTITY_GROUP_CREATE`).
- `:74` — the mitigation lists **all five** permission keys to treat as implicit namespace-creation grants.

So the true shape is **four services / five permissions** (Data Source = CREATE + UPDATE). The Namespaces page is consistent (four services); `permissions.md` is the page to fix.

**Recommended fix:** on `permissions.md:93` change "four sister-service side-doors: four other parent permissions (...five keys...)" to "four sister services carry five parent permissions (...five keys...) that silently mint namespace rows" — or drop the service-count entirely and lead with "five parent permissions". Leave the Namespaces page as the canonical owner; `permissions.md` already cross-links to it.

Related (do not duplicate): **DOC-255** owns the Data-Sources-side `namespace_name` side-door caveat; this item is purely the count-label reconciliation on `permissions.md`, not a re-documentation of the side-door mechanism.

- Live: WebFetch of `https://github.com/opendatadiscovery/odd-platform/blob/main/odd-platform-specification/components.yaml` resolves HTTP 200 and the `Permission` enum (incl. `DATA_ENTITY_ADD_TERM`, `OWNER_ASSOCIATION_MANAGE`, `NAMESPACE_CREATE`, ~80 values) is present in that exact file.
- The `opendatadiscovery-specification` path in the workspace repo map is the **ingress API** spec, a different artefact — the `Permission` enum is correctly homed in `odd-platform`'s own `odd-platform-specification/`.
