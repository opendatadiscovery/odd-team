    - **The storage shape (per ReactiveCollectorRepositoryImpl sidecar `concepts.invariants.plaintext-storage` + bugs_limitations_corner_cases[0])**: 
      - `V0_0_28__add_token.sql:4` (verbatim per sidecar): `value varchar(40) NOT NULL` — 40-character varchar, NOT NULL, **no UNIQUE constraint** (verified — only the primary key `id` is unique).
      - `TokenGeneratorImpl.java:34-42` (per sidecar): `value = RandomStringUtils.randomAlphanumeric(40)` — produces a 40-char alphanumeric token; **NO hashing applied** before persistence. Written to TOKEN.value verbatim.
      - `ReactiveCollectorRepositoryImpl.java:94` (per sidecar): `addSoftDeleteFilter(TOKEN.VALUE.eq(token))` — the SQL MATCH is plaintext equality. Postgres compares the inbound token's plaintext bytes to the stored plaintext bytes.
      - `IngestionDataEntitiesFilter.java:55-58` (per sidecar): the application-side cross-check is `tokenPojo.getValue().equals(token)` — Java `.equals()` short-circuiting plaintext byte comparison.
    - **The threat model (per sidecar bugs_limitations_corner_cases[0])**: any DB-side reader recovers every live credential. Concrete attack surfaces:
      - **Replica reader**: a read-replica's PostgreSQL role can `SELECT id, value, created_at FROM token` and enumerate every live collector token.
      - **Backup / pg_dump**: a `pg_dump` snapshot contains every TOKEN row verbatim. Operators running nightly backups + retaining backups for 30 days have 30 days of live tokens in clear text in their backup storage.
      - **jOOQ debug logging**: if `org.jooq` logger is set to DEBUG level (a common debugging operation), every Postgres query is logged including the TOKEN.VALUE parameter values — application logs leak the credentials.
      - **Application logs**: if a maintainer adds a `log.debug("getByToken: %s", token)` to the filter layer (anti-pattern but possible), every ingestion request leaks the credential.
      - **Database introspection tools**: any operator using `psql` / `pgAdmin` / DBeaver with read access to the `token` table sees the plaintext values.
    - **The orphan-on-soft-delete (per sidecar bugs_limitations_corner_cases[1])**: when a Collector is soft-deleted via `delete(id)`, the FK `collector.token_id` remains pointing at a TOKEN row that is now orphaned. **No housekeeping job removes orphaned TOKEN rows**. The TOKEN.value persists. A DB-side reader can recover EVERY collector's token EVER ISSUED, including credentials for soft-deleted collectors. The lifetime of the leaked credential at rest is unbounded.
    - **The cross-collector sharing race (per sidecar security.known_security_gaps[2])**: TOKEN.value has no UNIQUE constraint. If two TOKEN rows happen to share a value (60+ bits of randomness in 40-char alphanumeric makes this practically impossible — but theoretical), `getByToken` returns the FIRST match non-deterministically (no ORDER BY). COLLECTOR_ID_SESSION_KEY becomes ambiguous. Cross-collector datasource registration is silently possible. A future bug in TokenGeneratorImpl that reduced entropy (e.g. PRNG seed bug, timestamp-only key, deterministic key derivation) would expose this gap immediately.
    - **The asymmetric auth opacity (per sidecar bugs_limitations_corner_cases[3])**: `getByToken` is called from the ALWAYS-ON `IngestionDataSourceFilter` (no `@ConditionalOnProperty`); `getDto` is called from the OPT-IN `IngestionDataEntitiesFilter` (gated by `auth.ingestion.filter.enabled`). Operators reading the Enable Security doc cannot infer that `/ingestion/datasources` is ALWAYS authenticated (token required) while `/ingestion/entities` is OPT-IN (token required only when `auth.ingestion.filter.enabled=true`). Per ReactiveCollectorRepositoryImpl sidecar `coherence_notes` to F-008: "The DISABLED bypass is real for the HTTP UI/API surface but does NOT apply to the always-on ingestion path."
    - **The UI tier composition (cross-link DOC-GAP-189)**: the SQL-tier plaintext-at-rest threat model COMPOUNDS with the UI-tier plaintext-at-DOM-render threat (DOC-GAP-189): the token is rendered into a DOM text node on creation/regeneration, where browser extensions / screenshot tools / accessibility readers can capture it; AFTER the page reload, the token is gone from the API response (masked as `******{last6}`) but it's STILL PLAINTEXT in the database. The two tiers together describe the full credential-exposure surface from authoring to indefinite-storage.
    - **The operator-side mitigation set** (per sidecar `doc_drift_findings[0]` + cross-sidecar synthesis):
      - **Disk/volume encryption at rest** (the only platform-independent defence against backup/pg_dump leaks).
      - **Restrict pg_dump access** to a specific role used only by the backup automation; rotate the credential.
      - **Restrict replica access** to a subset of trusted roles; do not expose replica connection strings to general developers.
      - **Configure backup retention** to less than the operator's preferred token-rotation cadence.
      - **Set jOOQ logger to INFO or above** in production deployments; never DEBUG.
      - **Audit `psql` / `pgAdmin` access logs** at the network layer (not the database layer; the database has no built-in audit for SELECTs).
      - **Rotate tokens periodically** even without a known compromise, on a cadence shorter than the backup retention window.
      - **Consider running a periodic `DELETE FROM token WHERE id NOT IN (SELECT token_id FROM collector WHERE deleted_at IS NULL)`** to purge orphaned token rows (operator-side maintenance — the platform does not provide this).
  - **Proposed doc action**: **Four-part action.**
    1. **Doc-side primary — extend `configuration-and-deployment/enable-security/README.md`** (or a dedicated `enable-security/token-storage-and-rotation.md` if the maintainer prefers): add a "Collector token storage and threat model" section: "**Collector tokens are stored as plaintext at rest in the PostgreSQL `token.value` column** (`varchar(40) NOT NULL`). The platform's SQL-tier authentication compares incoming tokens to the stored plaintext using SQL equality (`TOKEN.VALUE = ?`). The platform does NOT hash, encrypt, or otherwise transform tokens before storage. **This is a deliberate architectural choice** anchored on the assumption that collector tokens are deployment-internal shared secrets between operator-controlled Collectors and the operator-controlled Platform; storage-at-rest threats are addressed at the deployment-infrastructure layer (disk/volume encryption, backup access controls, replica access controls), not the application layer. **Threat model implications**: any database-side reader (PostgreSQL replica, `pg_dump` snapshot, application log leak with jOOQ DEBUG enabled, direct `psql` access) recovers every live collector token with a single `SELECT id, value FROM token`. Operators must defend the credential-at-rest surface via deployment-infrastructure controls. **Soft-deleted collectors leave their TOKEN row orphaned**: when a Collector is deleted (soft-delete via `UPDATE collector SET deleted_at = NOW()`), the FK reference from `collector.token_id` survives, but no housekeeping job purges the orphaned TOKEN row. The lifetime of leaked credentials at rest is unbounded. For long-running deployments, operators should periodically run `DELETE FROM token WHERE id NOT IN (SELECT token_id FROM collector WHERE deleted_at IS NULL)` to purge orphans. **Token value has no UNIQUE constraint** at the SQL layer — the security is anchored on the entropy of the generated value (40-char alphanumeric, ≈ 238 bits) rather than on a database-side uniqueness invariant. Future maintainers reducing the entropy of token generation (e.g. switching to a timestamp-based scheme, a deterministic key-derivation, or a lower-entropy PRNG) would expose a cross-collector token-sharing race; the database does not defend against this." Then add the operator-side mitigation checklist (the 8 items enumerated under Evidence).
    2. **Doc-side companion — `features/management.md`** (the Management Collectors tab description; extending DOC-GAP-189): expand the existing Collectors tab description with a Storage subsection: "**The token displayed on creation / regeneration is the SAME value stored at rest in the database.** No transformation, hashing, or encryption is applied. Treat tokens as you would any plaintext credential — store them in a secret manager on the collector deployment side; never commit them to git; rotate periodically; assume any database-side reader has recovered them. See [Token storage and threat model](../configuration-and-deployment/enable-security/README.md#collector-token-storage-and-threat-model) for the full operator-side mitigation list." 
    3. **Doc-side companion 2 — `developer-guides/build-and-run/custom-collectors.md`** (the custom-collector authoring guide): add a "Token handling on the collector side" admonition: "Treat the token as a long-lived bearer credential. The platform does NOT support OAuth token refresh, mTLS, or any other rotation-on-the-collector-side flow today. The 40-character token persists for the lifetime of the Collector entity in the platform; rotation is an operator-initiated action through the Management UI (or the `PUT /api/collectors/{id}/regenerate` endpoint with `COLLECTOR_TOKEN_REGENERATE` permission). On rotation, the prior token returns 401 immediately (no grace period — see DOC-GAP-189) and in-flight ingestion fails until the Collector is redeployed with the new value. Plan rotations during maintenance windows."
    4. **Code-side preferred long-term — introduce token hashing** (file `/log-issue odd-platform`): three ordered options. (a) **Minimum — at-rest hashing with version negotiation**: store BCrypt / Argon2 hash of the token instead of plaintext; extend `Token` schema with `value_hash varchar(64)` + keep `value varchar(40)` for backward-compat during the migration window; at filter time, compare the inbound token against the hash via `BCrypt.checkpw` instead of SQL equality; this defeats the DB-side-reader recovery attack at the cost of a per-request BCrypt computation (10-100ms per call, acceptable at ingestion-tier RPS). Backwards-compatible — issue new tokens with hashed-only storage; existing tokens continue to work via the plaintext column during the migration window. (b) **Medium — UNIQUE constraint on TOKEN.value (or TOKEN.value_hash) + soft-delete cascade housekeeping**: add `UNIQUE NULLS NOT DISTINCT` on the canonical token column; add a housekeeping job (extends EmptyPartitionsHousekeepingJob pattern) that runs `DELETE FROM token WHERE id NOT IN (SELECT token_id FROM collector WHERE deleted_at IS NULL)` on the 15-min cycle. Closes the orphan-at-rest gap. (c) **Architectural — externalise tokens to a deployment-managed secrets backend (AWS SSM / HashiCorp Vault / Azure Key Vault)**: the platform reads tokens via the secrets-backend client at request time; the database stores only a token-id reference. Closes the at-rest-in-postgres gap entirely; introduces an operational dependency. Trade-off: the platform's "single-process plus PostgreSQL" deployment posture (system-mission.md `metadata-store` architectural pillar) is broken by this option.
