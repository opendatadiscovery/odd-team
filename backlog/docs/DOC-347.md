## Description

ODD Platform ships an **undocumented connection-pool ceiling** that silently exhausts a default PostgreSQL `max_connections=100` at modest replica counts, and an **undocumented x2 doubling** that makes the obvious mitigation behave unexpectedly. Operators sizing a cluster from the docs underprovision Postgres and hit `FATAL: sorry, too many clients already` under load with no documented warning.

Two facts, both verified against code this session:

1. **Two R2DBC pools per replica, each at the framework default `max-size=10` → 20 connections per replica.** `R2DBCConfiguration.java` creates two `ConnectionPool` beans: the primary `connectionFactory` (`:27-52`, the main metadata pool, `max-size` applied at `:46`) and `customConnectionPool` / `databaseClientForCustomSchema` (`:54-87`, the `lookup_tables_schema` pool, `max-size` applied at `:80`). Neither `application.yml` nor any profile sets `spring.r2dbc.pool.*`, so the r2dbc-pool framework default (`max-size = 10`, r2dbc-pool 1.0.0.RELEASE) applies to **both**. That is ~20 server connections per replica at steady ceiling. **5 replicas x 20 = 100 = the default Postgres `max_connections`** — leaving zero headroom for `psql`, migrations, backups, or monitoring.

2. **One `R2dbcProperties.Pool` config feeds BOTH pools, so a `max-size` override yields 2N, not N.** Both beans read the same `properties.getPool()` (`:38` and `:72`) — the single `spring.r2dbc.pool.*` binding. So setting `spring.r2dbc.pool.max-size: 30` to "raise the pool to 30" actually provisions **60** connections per replica (30 main + 30 custom-schema). An operator tuning the obvious knob doubles their real footprint silently.

This is the same silent-default class as the attachment-ephemeral (LSN-001) and MinIO-region (LSN-002) cases: a framework default left unset, ships a cliff, our name on the guide.
