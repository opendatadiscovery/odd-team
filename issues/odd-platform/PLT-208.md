## What

The home-page "Popular" / "Recommended" data-entity strip is computed **catalog-wide**, not per user. Every signed-in user sees the **identical** list - the platform's globally most-viewed data entities, ordered by a shared `view_count` - regardless of their ownership, team, or activity. Because the surface is framed as a personal recommendation, this means entity names (and, via the same query, alert-state) belonging to **other teams' data assets** appear on a user's home page. There is no per-principal scoping, no "owned by me / my team" filter, and no personalisation signal in the query at all. This is a code-behaviour-vs-presentation contradiction: the code is global; the framing implies personal.

## Where

The endpoint takes only paging parameters - no principal, no owner:

`odd-platform-api/.../controller/DataEntityController.java:307-313`

```java

                                                            final Integer size,
                                                            final ServerWebExchange exchange) {
    return Mono.just(dataEntityService.listPopular(page, size))
        .map(ResponseEntity::ok);

```

The repository query orders the **whole** `DATA_ENTITY` table by `VIEW_COUNT` descending with no owner/principal condition:

`odd-platform-api/.../repository/reactive/ReactiveDataEntityRepositoryImpl.java:629-649`

```java
@Override
public Flux<DataEntityDto> listPopular(final int page, final int size) {
    final DataEntityCTEQueryConfig cteConfig = DataEntityCTEQueryConfig.builder()
        .limitOffset(new DataEntityCTEQueryConfig.LimitOffset(size, (page - 1) * size))
        .orderBy(DATA_ENTITY.VIEW_COUNT.sort(SortOrder.DESC))   // global view_count, no owner filter
        .build();
    ...
    final var select = DSL.with(deCteName)
        .as(dataEntitySelect)
        .select(deCte.fields())
        .select(hasAlerts(deCte))          // alert-state of arbitrary entities surfaces too
        .from(deCteName)
        .orderBy(getOrderFields(cteConfig, deCte));
    return jooqReactiveOperations.flux(select)
        .map(dataEntityDtoMapper::mapDtoRecordFromCTE);
}
```

## Why it matters

This is **silent** and affects **every** user. Two concrete consequences:

1. **Misleading framing.** Users reasonably read "Recommended"/"Popular for you" as personalised; in fact it is a single global leaderboard. A user with no relationship to the top-viewed entities sees them as if recommended to them.
2. **Cross-owner leakage onto the home page.** The strip surfaces other teams' entity **names** and **alert state** (`hasAlerts`) to any authenticated user on the first screen they see. In a multi-team deployment this is an information-exposure smell (entity existence + naming + alerting status of assets the viewer may have no business seeing), and at minimum it is a UX/consistency defect.

Severity **medium**: it is not destructive and (depending on auth posture) the entities may already be broadly listable, but the personalised framing on the platform's most prominent surface is actively misleading, and the cross-owner alert-state exposure deserves a deliberate decision rather than an accident of a global `ORDER BY`.

## Suggested fix

The primary fix is **documentation** - state plainly that Popular is a global, catalog-wide leaderboard, not a per-user recommendation (tracked doc-side; see *How discovered*). This issue exists for the **code-side** option if the project prefers a behavioural change instead of (or in addition to) the doc caveat:

- **Lowest-cost:** relabel the surface from any "Recommended/for you" framing to plainly "Most viewed across the catalog", so presentation matches the global query. (open to alternatives)
- **Higher-cost (true personalisation):** scope `listPopular` to the calling principal - accept the authenticated owner and add an ownership/association condition (mirroring the owner-aware queries already in `ReactiveDataEntityRepositoryImpl`, e.g. `findByState(..., OwnerPojo owner)` directly below `listPopular`), so the strip reflects entities the user owns or is associated with.

Pick per product intent; the relabel is the minimal honest fix if personalisation is out of scope.
