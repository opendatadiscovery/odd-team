## Description

The `/api/dataentities/my/upstream` and `/my/downstream` endpoints (F-015) project their derived oddrn set through `ReactiveDataEntityRepositoryImpl.listByOddrns` (`ReactiveDataEntityRepositoryImpl.java:228-253`). The query builder at lines 247-250 is:

```
DSL.selectFrom(DATA_ENTITY)
   .where(conditions)
   .limit(size != null ? DSL.val(size) : DSL.noField(Integer.class))
   .offset(page != null && size != null ? DSL.val((page - 1) * size) : DSL.noField(Integer.class));
```

There is **no `.orderBy(...)`** before the `LIMIT`/`OFFSET` (verified by read 2026-06-08). Postgres documents pagination without `ORDER BY` as undefined — the planner may return rows in heap-scan order, which can change across consecutive identical queries (especially under concurrent writes). So paging `/my/upstream?page=1&size=5` then `page=2&size=5` may return an entity on BOTH pages or NEITHER (duplicate/skip): the top-N is usually but not reliably stable. The CONTRAST is structural — the sibling `listByOwner` (the base `/my` path) DOES order: `.orderBy(jooqQueryHelper.getField(deCte, DATA_ENTITY.ID).desc())` at line 528.

The behaviour to guard: **`listByOddrns` produces no deterministic row order across pages** — the current, shipped (buggy) state. F-015's `F-015-UC-10` ("dependents pagination is stable across page loads — no duplicate, no skip") is `verdict: partial`, `coverage: unverified`, `test_demand: missing-functional` (`lineage/odd-platform/feature-flows/detail/F-015.yaml:624-632`).

TYPED GATE: **characterization-pin** (LSN-029). This pins the CURRENT incorrect behaviour — that `listByOddrns`'s generated SQL carries **no ORDER BY** (and/or that page membership is not guaranteed stable). The companion fix is a one-line `.orderBy(DATA_ENTITY.ID.asc())` before `.limit/.offset` (the canonical fix used elsewhere in the repository — cf. line 528). The pin goes RED the instant that ORDER BY is added; on RED the test is inverted to assert the deterministic ordering present + retagged as a regression guard per LSN-029. It is NOT `@Disabled`.
