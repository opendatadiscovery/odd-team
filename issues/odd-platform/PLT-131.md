## What

The Owner **list** path correctly hides soft-deleted Owners (`deleted_at IS NULL` from the soft-delete base class), but the **by-id** path does not: `ReactiveOwnerRepositoryImpl.getDto` issues `WHERE OWNER.ID = id` with **no** `deleted_at IS NULL` filter, and `switchIfEmpty(NotFoundException)` fires only when the id never existed. So a direct `GET /api/owners/{id}` for a soft-deleted Owner returns the row — including its name and previously-attached roles — instead of 404. Visibility is inconsistent across list (hidden) and by-id (visible). Combined with the ungated read posture (any authenticated user can read by id; anonymous under DISABLED), an operator's "deletion" is not the erasure they believe it is.

This is **net_new** — not in any existing PLT. (PLT-110 is the *Policy*-grant-path `deleted_at` omission; this is the *Owner* `getDto` read-path omission. SHB-095 seeded the GDPR-erasure scenario but filed no PLT.)

## Impact

(1) GDPR / right-to-erasure: an operator who deletes an Owner to satisfy an erasure request leaves the Owner's name + roles recoverable via a direct by-id read (and the `USER_OWNER_MAPPING` rows persist) — the deletion is not erasure. (2) Reconnaissance: a low-privilege user records ids during browsing (the read is ungated) and reads soft-deleted Owners by id after the operator "removes" them. (3) Operator confusion: "I deleted it but it's still there if I hit the id directly."

## Suggested fix

Per the reflection's `proposed_fix_anchor`: add `.where(OWNER.DELETED_AT.isNull())` to `ReactiveOwnerRepositoryImpl.getDto` (SHB-095 fix), and audit every `getDto`-style method in soft-delete repositories for the same omission. Distinct from PLT-110 (Policy grant-path).
