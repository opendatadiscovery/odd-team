## What

When email notifications are configured, the mail-sender bean only wires the SMTP authentication and STARTTLS flags if the configured `notifications.receivers.email.protocol` value is **exactly** the lowercase string `smtp` (`NotificationConfiguration.java:63`, case- and whitespace-sensitive `.equals`). Any other spelling - most plausibly the uppercase acronym `SMTP` - falls into the `else` branch, which copies the raw value into `mail.transport.protocol` and sets nothing else. The bean builds cleanly: boot-time validation checks only that the protocol is non-blank (`:47-49`), so there is **no warning at startup**.

What actually happens then is NOT the silent transport-security downgrade an earlier revision of this issue claimed. The fall-through value flows into Jakarta Mail's **case-sensitive** transport-provider lookup, which fails loudly on the first send:

- `NotificationConfiguration.java:51-71` never calls `setProtocol(...)`, so Spring's `JavaMailSenderImpl.getTransport(Session)` resolves the protocol from `mail.transport.protocol` (bytecode-verified in spring-context-support 6.2.11) and calls `session.getTransport("SMTP")`.
- Jakarta Mail registers transports under lowercase keys only (`protocol=smtp; ... SMTPTransport` / `protocol=smtps; ... SMTPSSLTransport` in `META-INF/javamail.default.providers`, jakarta.mail 2.0.4), and `Session.getProvider(String)` contains no case-normalisation (bytecode-verified: zero `toLowerCase` calls) -> **`NoSuchProviderException: No provider for SMTP`** on every send attempt.
- Spring wraps that in a `MailSendException` (a RuntimeException). `EmailNotificationSender.send` catches only `MessagingException | TemplateException | IOException` (`EmailNotificationSender.java:58-60`), so the MailException **escapes as an uncaught runtime exception**; the per-sender guard in the processor catches only `NotificationSenderException` (`AlertNotificationMessageProcessor.java:31`), so it escapes that too and kills the WAL stream iteration (`NotificationSubscriber.java:90-92`). The LSN is never flushed (`:83-84` is unreachable for that message), so on reconnect (~10s later) **the same alert replays - forever**: email never delivers, the notification pipeline makes no further progress, and any *other* configured receiver (Slack / generic webhook) **re-sends the same alert on every cycle**.

The genuinely-silent case is narrow: `protocol: smtps` does resolve (to the implicit-TLS `SMTPSSLTransport`), so it sends - over an encrypted channel by construction - while the operator's `smtp.auth`/`smtp.starttls` flags are silently unwired (they are only ever set in the exact-`smtp` branch). No cleartext results in any reachable configuration.

## Where

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/notification/config/NotificationConfiguration.java:63`

```java
if (emailProperties.getProtocol().equals("smtp")) {
    props.put("mail.transport.protocol", "smtp");
    props.put("mail.smtp.auth", emailProperties.getSmtp().getAuth());
    props.put("mail.smtp.starttls.enable", emailProperties.getSmtp().getStarttls());
} else {
    props.put("mail.transport.protocol", emailProperties.getProtocol());
}
```

The `.equals("smtp")` comparison is case- and whitespace-sensitive; the `if` body is the only place AUTH/STARTTLS are ever wired. Backing config class (`EmailSenderProperties.java`): `private String protocol; private SmtpProperties smtp;` with `Boolean auth; Boolean starttls;`. The blast-radius chain: `EmailNotificationSender.java:58-60` (catch clause misses `MailException`) -> `AlertNotificationMessageProcessor.java:29-34` (catches `NotificationSenderException` only) -> `NotificationSubscriber.java:83-84,90-92` (LSN flush skipped; generic catch restarts the stream on the unflushed LSN).

## User-facing impact

User: an operator who configures email notifications and writes the protocol as `SMTP` (the natural acronym spelling), `Smtp`, or any other non-exact-lowercase value.

What they observably get (verified by BE + bytecode trace 2026-06-10, labels below):

- **Boot:** clean start, zero warnings - the only protocol validation is non-blank (`NotificationConfiguration.java:47-49`). Statically settled.
- **First alert onward:** no email is ever delivered; the platform log repeats `Error occurred while subscribing` (`NotificationSubscriber.java:91`) with a `MailSendException` / `No provider for SMTP` cause about every 10s; and if Slack or a webhook receiver is also configured, **those channels deliver duplicate copies of the same alert on every retry cycle while all newer alerts queue behind it** (fan-out re-runs per replay, `AlertNotificationMessageProcessor.java:26-35`). Static trace consistent; not driven - the no-provider failure and catch-type gaps are settled by code + bytecode, but the replay loop additionally rests on slot-redelivery-of-unflushed-LSN semantics (observed live for the sibling PLT-139 path, `integration-tests/run-log/2026-06-02-feature-complete.md:42`, not for this one) - hence `user_facing_verified: false`. Remaining check: notifications-enabled stack with `protocol: SMTP` + any second receiver, insert one alert, observe the ~10s duplicate cycle.
- **No cleartext-credential exposure in any case:** uppercase values never produce a connected session at all; `smtps` produces implicit TLS. The original "credentials traverse the network in cleartext" scenario is unreachable. Statically settled (provider table + lookup bytecode).

## Why it matters

A one-character configuration spelling turns the whole notification subsystem into a duplicate-spamming retry loop with email permanently dead - and the root cause (`No provider for SMTP`) is buried in a generic subscriber error, nothing pointing the operator at the `protocol:` line. The fix is trivial and the trap is easy to hit. Severity regraded **high -> medium**: the original high rested on a silent STARTTLS/AUTH security downgrade with possible cleartext credentials, which the case-sensitive provider lookup makes unreachable (the misconfiguration fails loudly instead of downgrading silently); what remains is a robustness/diagnosability defect plus the `smtps` flag-unwiring wart.

## Suggested fix

1. Make the protocol comparison case-insensitive and trim-tolerant, e.g. `if ("smtp".equalsIgnoreCase(emailProperties.getProtocol().trim()))` - and normalise the value put into `mail.transport.protocol` to lowercase so the provider lookup always succeeds.
2. Handle `smtps` explicitly (wire `mail.smtps.auth` when configured) rather than letting it fall through with the operator's auth intent dropped.
3. Validate the protocol value at bean construction (`:47-49` already rejects blank) - reject or warn on anything that is not `smtp`/`smtps`, so a typo fails at boot with a pointed message instead of at send time with a buried one.
4. (Blast-radius hardening, shared with the PLT-016 poison-message class) catch `MailException` in `EmailNotificationSender.send` and rethrow as `NotificationSenderException`, so one receiver's persistent failure degrades that receiver only instead of wedging the WAL loop and duplicating other receivers' sends.

**How to verify:** unit test on the property-building path asserting `protocol: SMTP` yields a working lowercase transport protocol with `mail.smtp.auth`/`mail.smtp.starttls.enable` set; integration: with `protocol: SMTP` pre-fix, one alert insert produces the replay loop above.

## How discovered

Surfaced during a product-owner review of the email-notification flow (question: are STARTTLS/AUTH honoured when configured?); the "honoured when configured" expectation was traced to the protocol guard and found to depend on an exact-case string match. Confirmed by reading `NotificationConfiguration.java:63` and `EmailSenderProperties.java` directly.

**Corrected 2026-06-10 (user-facing verification sweep):** was "the mail sender connects without STARTTLS and without AUTH ... credentials traverse the network in cleartext ... completely silent"; actually a non-lowercase protocol value never connects at all - Jakarta Mail's provider lookup is case-sensitive (bytecode-verified: `jakarta.mail` 2.0.4 `Session.getProvider` has no `toLowerCase`; the provider registry keys are lowercase `smtp`/`smtps`; Spring's `JavaMailSenderImpl.getTransport` resolves via `mail.transport.protocol`), so the misconfiguration fails LOUDLY at send time with `NoSuchProviderException` - and, worse than drafted in a different direction, the uncaught `MailException` escapes both catch layers (`EmailNotificationSender.java:58-60`, `AlertNotificationMessageProcessor.java:31`) and poisons the WAL loop: permanent replay of the same alert, duplicate deliveries to other receivers, no forward progress. The silent-flag-loss claim survives only for `smtps` (implicit TLS, no cleartext). Severity high -> medium accordingly.

Related: **PLT-016** (WAL/notification hardening - the poison-message stall this misconfiguration instantiates), **PLT-139** (create-order wedge - the other way the subscriber loop wedges), **PLT-154** (sender-side 429 handling in the same sender hierarchy).
