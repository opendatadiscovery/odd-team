## What

**REJECT-CANDIDATE -- the defect as originally described does not exist.** The original draft claimed that hard-deleting a data entity leaves its activity rows physically present in the `activity` table but unreachable through the feed (because every read path inner-joins `data_entity`), so the audit history "survives in storage but is invisible." That is false on two independent counts, both verified against the real deletion path on 2026-06-10:

1. **There is no FK cascade.** `activity.data_entity_id` is a `NOT NULL` FK to `data_entity(id)` with **no `ON DELETE CASCADE`** (`V0_0_48__add_activity.sql:4,12`). A raw `DELETE FROM data_entity` against a row that still has activity rows would be *rejected* by the constraint, not silently cascade.
2. **The only hard-delete path deletes the activity rows first, in the same transaction.** Data entities are physically removed exclusively by `DataEntityHousekeepingJob`, which calls `deleteActivity(...)` -> `deleteFrom(ACTIVITY).where(ACTIVITY.DATA_ENTITY_ID.in(dataEntityIds))` (`DataEntityHousekeepingJob.java:113,228-232`) *before* it deletes the `data_entity` row (`:124-126`). So after a purge there are **no surviving activity rows** to be stranded -- the history is hard-deleted along with the entity, by design.

The inner join (`buildBaseQuery`, `ReactiveActivityRepositoryImpl.java:218`) is therefore consistent with the actual lifecycle: it never has the chance to "hide surviving rows," because no path ever leaves activity rows behind a removed entity. The soft-delete case (entity `STATUS=DELETED`, row retained) is also unaffected -- the row still exists, so the inner join still matches, and the activity remains visible. There is no read-path data-loss defect here.

What *is* true and is the only behaviour worth recording: the platform's audit history for a data entity is **intentionally hard-purged** when the entity is purged by the TTL housekeeping job (entities that have been `STATUS=DELETED` for `attachment`-independent `data-entity-delete-days`). That is a retention-policy fact (the TTL-purge class, same family as the LSN TTL findings), not a "rows stranded behind an inner join" bug. If audit-survival-past-entity-deletion is a desired property, it is a feature request against the housekeeping retention policy, not a join-style fix.

## Where

The inner join is real, but the deletion path makes it harmless. The base query (line 218, not 219 as the original draft cited):

```java
// ReactiveActivityRepositoryImpl.java:216-222 (buildBaseQuery)
final var query = DSL.select(selectFields)
    .from(ACTIVITY)
    .join(DATA_ENTITY).on(DATA_ENTITY.ID.eq(ACTIVITY.DATA_ENTITY_ID))   // :218 INNER JOIN
    .leftJoin(USER_OWNER_MAPPING)
    .on(...);
```

The deletion path that the original draft never traced -- activity rows are deleted BEFORE the entity row, in one transaction, because the FK has no cascade:

```java
// DataEntityHousekeepingJob.java:113  (ordering inside deleteDataEntities)
deleteActivity(dslContext, dataEntityIds);   // -> deleteFrom(ACTIVITY).where(DATA_ENTITY_ID.in(...))  :228-232
// ...
// DataEntityHousekeepingJob.java:124-126   (entity row removed only after its activity rows are gone)
dslContext.deleteFrom(DATA_ENTITY).where(DATA_ENTITY.ID.in(dataEntityIds)).execute();
```

```sql
-- V0_0_48__add_activity.sql:4,12  (NOT NULL FK, NO ON DELETE CASCADE)
data_entity_id  bigint NOT NULL,
CONSTRAINT activity_data_entity_id_fk FOREIGN KEY (data_entity_id) REFERENCES data_entity (id)
```

So the "activity row physically remains but the inner join hides it" scenario the original draft described cannot arise: by the time the `data_entity` row is gone, its activity rows are already gone too. (The count queries at :155, :176, :197 carry the same inner join, with the same harmless consequence.)

## User-facing impact

None of the kind originally claimed -- verified by BE trace 2026-06-10. There is no read path that drops "surviving" audit rows, because no deletion path leaves surviving audit rows: the sole hard-delete path (`DataEntityHousekeepingJob.java:113,124-232`) deletes the activity rows in the same transaction as the entity, and the FK (`V0_0_48__add_activity.sql:12`) has no cascade, so a delete that *would* strand activity rows is rejected outright. Soft-deleted entities keep their `data_entity` row (`ReactiveDataEntityRepositoryImpl.java:112` sets `STATUS=DELETED`, the row is retained), so the inner join still matches and their activity stays visible. The only real behaviour is the **intentional TTL hard-purge** of an entity's audit history when the entity itself is purged -- a retention-policy property, not a join defect, and not silent data loss behind a query.

## Why it matters

Reduced to **low** (REJECT-CANDIDATE): the original high-severity rationale ("silent, irreversible audit-history loss hidden behind an inner join") collapses once the deletion path is read -- the history is not hidden, it is deliberately purged with the entity, and there is no surviving-but-unreachable row class. The only residual is a documentation/retention question: whether ODD should retain audit history past entity TTL purge. If pursued, that is a housekeeping-retention feature request (and overlaps the TTL-purge documentation family), not the join-style code fix the original draft proposed. No code change is warranted on the read path.

## Suggested fix

No read-path fix. The inner join is correct given the lifecycle. If audit-survival-past-purge is desired, raise it as a retention-policy change against `DataEntityHousekeepingJob.deleteActivity` (e.g. preserve activity rows and null their entity ref, which would then require the very LEFT JOIN the original draft proposed) -- but that is a deliberate retention decision with storage-growth consequences, not a bug fix. Recommend closing this as not-a-defect unless the retention policy is revisited.
