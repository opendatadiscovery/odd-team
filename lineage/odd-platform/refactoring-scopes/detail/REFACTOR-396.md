- **REFACTOR-396** (NEW 2026-05-19O): OAuth handler dispatcher is FIRST-MATCH-WINS over an UNORDERED Spring bean list — `OAuthSecurityConfiguration.oidcUserHandlers : List<...>` collects every OIDC handler bean (Google/Cognito/Azure/Custom/ODD_IAM), and the dispatcher at lines 185-189 picks the FIRST `shouldHandle == true`. No `@Order` annotation pins the iteration order; Spring's default bean-declaration / class-file scan order is the de-facto contract. Today this works by luck because providers are uniquely-disjoint; a future overlapping handler (`OktaUserHandler` returning true for 'okta') would depend on Spring picking it BEFORE the catch-all `CustomOIDCUserHandler` which returns true for ANY not-in-Provider-enum provider
  - **Category**: refactor-risk
  - **Surfaced by**:
    - `GoogleUserHandler.md:bugs_limitations_corner_cases.[1]` (LOW)
  - **Statement**: `OAuthSecurityConfiguration.oidcUserHandlers : List<OAuthUserHandler<OidcUser, OidcUserRequest>>` (line 80) collects every OIDC handler bean — Google, Cognito, Azure, Custom-OIDC, ODD_IAM, plus any future `@Component` implementing the interface. The dispatcher at `OAuthSecurityConfiguration.java:185-189` picks the FIRST element whose `shouldHandle == true`. Spring's collection ordering for `List<T>` injection is BEAN-DECLARATION / CLASS-FILE SCAN order (no explicit `@Order` on any handler). The current bean set is uniquely-disjoint (each handler matches a distinct provider string — Google matches "GOOGLE", Cognito matches "COGNITO", etc.), so first-match-wins is SAFE today. BUT: `CustomOIDCUserHandler.shouldHandle` at line 28-34 returns `true` for ANY provider NOT in the `Provider` enum — so a future handler addition with overlapping coverage (e.g., a hypothetical `OktaUserHandler` returning true for 'okta') depends on Spring picking it BEFORE CustomOIDCUserHandler in the list. Today this works by luck (since no overlap exists); the fragility is latent — only triggers if overlap is introduced.
  - **Evidence**: `GoogleUserHandler.java:38-40` (`shouldHandle("google")` returns true) + `OAuthSecurityConfiguration.java:185-189` (the dispatcher's first-match-wins iteration) + `CustomOIDCUserHandler.java:28-34` (the catch-all that would overlap with any future provider)
  - **Existing-ADR-or-implied-prescription**: ADR-CANDIDATE-034 (OAuth provider-quirks strategy) — the chain-of-responsibility is the parent pattern; the unordered dispatch is the implementation detail. Adding `@Order` annotations is refactoring within existing structure.
  - **Proposed remedy**: Add explicit `@Order` annotations to OIDC handlers: `@Order(1)` on each specific-provider handler (Google, Cognito, Azure, ODD_IAM); `@Order(Integer.MAX_VALUE)` on `CustomOIDCUserHandler` to ensure the catch-all runs LAST. This pins the iteration order and eliminates the latent fragility. Alternatively, replace `List<>` injection with `Map<String, OAuthUserHandler>` keyed by `Provider.name()`; the dispatcher becomes O(1) lookup AND order-independent. The latter is more invasive but eliminates the entire class of order-dependent bug.
  - **Severity rationale**: LOW — latent. Only triggers if a future maintainer adds an overlapping handler without realizing the order-dependency. Not a bug today; a regression risk for future development.
  - **Suggested backlog grouping**: `OAuth2 hardening sprint` (composes with REFACTOR-113 — adding OktaUserHandler / KeycloakUserHandler must reckon with this ordering, so fix this first)
