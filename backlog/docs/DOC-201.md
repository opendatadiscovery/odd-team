## Description

Four UX hazards on the alerting surface that operators encounter in normal use, all silent in the live alerting page. Documenting these as known limitations today gives operators a fighting chance until code-side hardening (PLT-050, PLT-053) ships.

**Default-tab redirect lands every user on cross-owner feed (F-126a).** `AlertsRoutes.tsx:18` declares `<Route path='/' element={<Navigate to='all' replace />} />`. Any user reaching `/alerts` (toolbar link, bookmark) auto-redirects to `/alerts/all` — the cross-owner read endpoint. Combined with AlertsTabs hiding My/Dependents for users without ownership, the All tab is the ONLY visible tab and the implicit framing is "alerts = platform-wide" not "alerts I can action."

**Hidden tabs but routes remain navigable (F-126b).** AlertsTabs sets `hidden: !showMyAndDepends` on My Objects and Dependents tabs. The route paths `/alerts/my` and `/alerts/dependents` REMAIN mounted in AlertsRoutes (lines 10-21). A user with prior URL knowledge can reach them; page renders empty (no user_owner_mapping → empty result). Visually indistinguishable from "no alerts in window."

**Notification Settings dialog has no optimistic concurrency check (F-198a).** Two operators open the dialog simultaneously: A reads halt-until values v1, types changes, submits as v1+A. B's already-open dialog still holds v1; submits as v1+B. B's submission overwrites A's silently. No version field, no If-Match header, no concurrency warning.

**Alert Resolve/Reopen button has no confirmation dialog (F-198b).** `DataEntityAlertItem.tsx:113-118` dispatches `updateAlertStatus` immediately on click. Per the alerting page's existing workaround narrative ("export the alert audit data before manually resolving — manually-resolved alerts get hard-deleted by housekeeping"), an accidental click destroys audit history the very workaround is meant to mitigate. The doc names the workaround AND the housekeeping hard-delete but does NOT warn that the UI Resolve button is destructive in combination.
