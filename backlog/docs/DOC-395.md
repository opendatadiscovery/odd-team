## Description

The OpenAPI request schema for the per-entity metadata Update endpoint, `MetadataFieldValueUpdateFormData` (`odd-platform-specification/components.yaml:2144-2152`), declares two properties — `value` (required) and `origin` (`$ref` to `MetadataFieldOrigin`). An SDK client generated from the spec, or anyone reading the API reference, will reasonably believe they can set or change a value's `origin` on the `PUT /api/dataentities/{id}/metadata/{metadata_field_id}` call.

The implementation ignores `origin` entirely. `DataEntityServiceImpl.upsertMetadataFieldValue` (`DataEntityServiceImpl.java:292-294`) builds the persistence pojo from `dataEntityId`, `metadataFieldId`, and `formData.getValue()` only — it never reads `formData.getOrigin()`. The `origin` sent in the request body is silently dropped: no error, no warning, a `200` response, and the field's origin is unchanged.

This is the same drift class as the silent-no-op and dropped-`active` caveats already documented on `custom-metadata.md`: a request field that the schema advertises but the write path does not honour. The existing page mentions `origin` only as a field-catalogue attribute (INTERNAL vs EXTERNAL) — it does **not** mention that the request-body `origin` on the value-update form is a no-op. DOC-189 (done) created the page and documents `origin` as a schema/field concept; it does not cover this dropped-on-write behaviour.

Operator impact: a client trying to flip a value's origin (e.g. as part of a reconciliation that believes it can re-own an ingested value) gets a success response while nothing changed — a write that appears to take but does not.

- [ ] The caveat states the operator-side consequence: a client cannot change a value's origin through this endpoint; treat origin as not settable via the value-update API.
- [ ] The note is positioned alongside (and consistent with) the existing INTERNAL/EXTERNAL origin discussion so the page does not contradict itself — it distinguishes "origin as a field-catalogue attribute" from "the request-body `origin` on the value-update form, which is a no-op."
- [ ] A re-sweep of all surfaces returns zero residue — no doc surface implies the value-update API honours `origin`. (Verified: `custom-metadata.md` is the only page covering this endpoint's request body.)

## Context

Source features: **F-046**, **F-013** (custom metadata — per-entity value write path / metadata field model). Surfaced in the 2026-06-08 contradiction-harvest.

Known ref to cross-link: **DOC-189** (done, critical) — created `custom-metadata.md` and documents `origin` as an INTERNAL/EXTERNAL field-catalogue attribute, but not the request-body `origin` being dropped on upsert; this item extends that page.

Canonical code/spec truth — schema advertises `origin`, impl drops it:
- Spec: `odd-platform-specification/components.yaml:2144-2152` — `MetadataFieldValueUpdateFormData` = `{value (required), origin: $ref MetadataFieldOrigin}`.
- Code: `odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/service/DataEntityServiceImpl.java:292-294` — `new MetadataFieldValuePojo().setDataEntityId(dataEntityId).setMetadataFieldId(metadataFieldId).setValue(formData.getValue())`; `formData.getOrigin()` is never read.

Canonical home: `custom-metadata.md` is the single page documenting the per-entity metadata write endpoints and their request bodies (the Authoring per-entity values section + the Known limitations admonitions). No other doc surface carries this endpoint's request-body contract.

Low severity — a request-field-ignored caveat consistent with the other documented no-op behaviours on this surface; no data loss or security exposure beyond the "silent success" foot-gun the page already frames. The cleaner upstream fix is to either honour `origin` on write or drop it from the schema; if taken, log as a PLT issue and retract this note.
