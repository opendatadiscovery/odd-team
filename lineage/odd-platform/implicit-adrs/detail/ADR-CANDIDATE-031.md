The mode is positioned as developer-velocity-first; the live doc page repeatedly frames it as "dev/demo only"

  - **Decision statement**: ODD's LOGIN_FORM mode commits to a deliberately-stripped dev/demo posture: (a) credentials are plain-text strings in `application.yml` parsed at boot into an in-memory `MapReactiveUserDetailsService`; (b) every authenticated user is granted ADMIN role (hard-coded `getAuthorities(true)` at LoginFormSecurityConfiguration.java:81); (c) no user persistence, no rotation, no MFA, no per-user metadata; (d) the AuthorizationCustomizer is NOT wired (LoginFormSecurityConfiguration.java:55-57 vs OAuthSecurityConfiguration.java:98 + LDAPSecurityConfiguration.java:145) — the mode is consciously positioned outside the Policies/Permissions/Roles/Owners framework. The shipped default `application.yml:37` carries `admin:admin,root:root` — the maintainer's signal that this is an example-mode, not a production-mode. The live doc page repeats the dev-only framing throughout. The trade-off accepted: developer onboarding velocity (single-line config + 30s deployment) vs. production unsuitability — the choice is explicit, not hidden. Compose with ADR-CANDIDATE-029: DISABLED is the "no auth at all" onboarding default; LOGIN_FORM is the "minimum auth for local dev" default; OAUTH2/LDAP are the production-targeted modes.
  - **Wisdom test**: PASS. The triple intent-anchor (YAML comment + ADMIN-for-all literal + live-doc-dev-only framing) is unambiguous. The lack of AuthorizationCustomizer wiring is the structural choice that codifies the dev-mode positioning — every form-authenticated user bypasses the policy framework. The price of the design — production-deployed LOGIN_FORM is wide-open even for non-admin users — is captured at REFACTOR-099 + REFACTOR-103 (credential leak via `/actuator/env`) + REFACTOR-104 (no session cookie security flags) + REFACTOR-105 (CSRF disabled on session-cookie mode).
