## What

A Data Quality test that is **currently running** does not impact the catalog-wide **Quality Dashboard**
(`/data-quality`, the "Test Results Breakdown" ring and the per-category matrix). An in-flight run is silently
ignored by the dashboard's latest-run rollup, so:

- a test whose latest run is in flight keeps showing its **previous completed** status (stale), and
- a brand-new test whose only run is still in flight does **not appear on the dashboard at all**.

The root cause is an `end_time IS NOT NULL` filter when the platform records each test's "last run". A run
that is still running has no `end_time`, so it never becomes the test's last run, and the dashboard (which
reads only the last-run table) never counts it.

This also makes the dashboard's **"Running" status permanently report 0**. Once `RUNNING` is a Data Quality
run status the UI knows about, the dashboard lists "Running" as a status category, but its count is always 0
no matter how many tests are actually running -- it looks like in-flight tracking exists when it does not.

## Where

- `odd-platform-api/.../repository/reactive/ReactiveDataEntityTaskRunRepositoryImpl.java` --
  `insertLastRuns(...)`: `.filter(tr -> tr.getEndTime() != null)` (~line 103). This is the ONLY writer of
  `data_entity_task_last_run`; runs without an `end_time` are dropped, so an in-flight run never updates a
  test's last run. (Ingestion reaches it via
  `service/ingestion/processor/TaskRunIngestionRequestProcessor.process` -> `insertLastRuns(pojos)`.)
- `odd-platform-api/.../repository/reactive/ReactiveDataQualityRunsRepositoryImpl.java` --
  `getLatestDataQualityRunsResults(...)`: the dashboard breakdown reads `DATA_ENTITY_TASK_LAST_RUN.STATUS` and
  groups by it (it has no other run source), so anything excluded from last-run is invisible here.
- `odd-platform-api/.../mapper/DataQualityCategoryMapperImpl.java` -- `addMissingStatuses(...)` (~line 51)
  emits a 0-count entry for every `DataEntityRunStatus` value, which is why "Running" shows up as a 0 once it
  is part of the enum.
- Endpoint: `GET /api/dataqatests/runs` (operationId `getDataQualityTestsRuns`).

## User-facing impact

Reproduced live on a local stack (AUTH_TYPE=DISABLED), ingesting a DQ test (category "Assertion Tests") and
reading `GET /api/dataqatests/runs`:

1. Ingest one **completed** SUCCESS run (with `end_time`): dashboard shows `SUCCESS: 1, RUNNING: 0`.
2. Ingest an **in-flight** RUNNING run (no `end_time`) for the same test: dashboard is **unchanged** --
   `SUCCESS: 1, RUNNING: 0`. The running test is invisible; the dashboard still reports the old SUCCESS.
3. Ingest a RUNNING run **with** an `end_time`: dashboard becomes `SUCCESS: 0, RUNNING: 1`. The same RUNNING
   status is counted only because it has an `end_time` -- proving the exclusion is driven by `end_time`, not
   by the status.

So the operator's catalog-wide quality view cannot answer "which tests are running right now" and can show a
stale pass/fail for a test that is currently re-running.

## Why it matters

The Quality Dashboard is the primary cross-entity quality view. Filtering the data it shows on `end_time`
means in-flight work is excluded from the aggregate -- every test should contribute to the dashboard,
including one that is currently running. The newly-visible but always-zero "Running" slice is worse than
silent: it implies the platform tracks in-flight tests on the dashboard when it does not.

## Suggested fix

Treat the latest run as the latest run, in flight or not, for the last-run rollup that feeds the dashboard
(and the per-entity "latest run" surfaces that read the same table):

- Stop dropping `end_time IS NULL` rows in `insertLastRuns`; pick each test's latest run by
  `COALESCE(end_time, start_time)` (or by `start_time` when `end_time` is null), so an in-flight run becomes
  the current last run with status `RUNNING`, and is replaced by the terminal status when it completes.
- Keep the deterministic tiebreaker already used elsewhere (start_time, then id) so the choice is stable.

Alternative (smaller, but leaves the staleness): keep last-run as last-COMPLETED-run, but exclude `RUNNING`
from `addMissingStatuses` so the dashboard does not advertise a status it can never count. The first option is
preferred -- it makes in-flight tests actually visible, which is the reported expectation.

A product decision sits underneath: "last run" = "last completed run" (today) vs "latest run including
in-flight" (requested). The requested behaviour is the latter.

## How discovered

Noticed that the newest build shows a "Running" status on the DQ Dashboard (it is a 0-count entry that appears
once `RUNNING` joins the `DataEntityRunStatus` enum), which prompted checking whether a running test actually
counts. It does not: `insertLastRuns` filters `end_time != null`, and the dashboard reads only the last-run
table. Confirmed with the live ingest reproduction above.
