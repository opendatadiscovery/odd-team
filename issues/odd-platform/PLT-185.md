## What

When a user fills in the "Add datasource" / "Edit datasource" dialog and the backend **rejects** the save (validation error, duplicate ODDRN, server error), the form still resets every field - wiping all of the user's typed input. They are left with a transient error toast and an empty form, and must re-type everything from scratch. The reset fires on failure because the submit handler resets unconditionally on the dispatched promise's `.then(...)`, and the thunk wrapper resolves (rather than rejects) the dispatched promise even on error.

**Correction after reading the dialog component (2026-06-10):** the dialog does **not** close on a reject - only the fields are wiped while the dialog stays open. The earlier revision (and the source harvest line) claimed "the modal closes, everything typed lost." That is a backend/intuition-level extrapolation a frontend trace falsifies: `DialogWrapper` only closes when its `handleCloseSubmittedForm` prop flips, and that prop is wired to the redux `isLoaded` success flag (`isDataSourceCreated` / `isDataSourceUpdated`), which stays `false` on a reject - so the close `useEffect` never fires. The reset, however, runs unconditionally via `.then()`. Net user-facing symptom: an open dialog whose fields have been silently cleared, plus an error toast. The destructive-input-loss core of the issue holds; the "dialog closes" detail was wrong and is corrected below.

## Where

`odd-platform-ui/src/components/Management/DataSourcesList/DataSourceForm/DataSourceForm.tsx:78-80` - `clearState()` (which calls `reset()`) runs in `.then(...)`, with no success/failure branch:

```tsx
    ).then(() => {
      clearState();
    });
```

`clearState` is just a `reset()` (`DataSourceForm.tsx:65-67`). The dialog-close is driven separately: `handleCloseSubmittedForm={dataSource ? isDataSourceUpdated : isDataSourceCreated}` (`DataSourceForm.tsx:165`) - the redux `isLoaded` **success** flag. In `DialogWrapper` a `useEffect(() => { handleClose(); }, [handleCloseSubmittedForm, handleClose])` (`odd-platform-ui/src/components/shared/elements/DialogWrapper/DialogWrapper.tsx:81-83`) closes the dialog only when that flag changes - and on a reject the loaded flag stays `false`, so the dialog stays open. (`handleClose` itself, `DialogWrapper.tsx:56-62`, also calls `clearState`, but it is not invoked on a reject.) Hence on a reject only the `.then()`-fired `reset()` runs - fields wiped, dialog open.

The reason `.then()` runs even on failure is the shared thunk wrapper - `odd-platform-ui/src/redux/lib/handleResponseThunk.ts:34-42` - whose `catch` block calls `rejectWithValue`, which **resolves** the dispatched action promise (it does not re-throw), so the caller's `.then()` always fires:

```ts
    } catch (err) {
      const errResp = await getErrorResponse(err as Response);
      if (!options.switchOffErrorMessage) {
        await showServerErrorToast(err as Response);
      }
      return thunkAPI.rejectWithValue(errResp);
    }
```

(`registerDataSource` / `updateDataSource` both go through this wrapper - `odd-platform-ui/src/redux/thunks/datasources.thunks.ts:34-60`.)

## User-facing impact

Static code trace, not driven on a running stack (no reject reproduced live in this sweep). Verified by reading the full chain: submit handler (`DataSourceForm.tsx:69-81`) -> thunk wrapper `rejectWithValue` resolving the promise (`handleResponseThunk.ts:41`) -> the unconditional `.then(clearState)` (`DataSourceForm.tsx:78-80`) -> `clearState` = `reset()` (`:65-67`). On a backend reject the user sees: an error toast (from `showServerErrorToast`, `handleResponseThunk.ts:38`), an **open** Add/Edit Datasource dialog (the close `useEffect` does not fire - `DialogWrapper.tsx:81-83` keyed on the success flag), and **all fields cleared** (name, ODDRN, namespace, description). The most common trigger is a server-side validation failure the client cannot pre-empt (e.g. a duplicate ODDRN: `DATA_SOURCE_CREATE` POST -> `UniqueConstraintException` -> 400, `ControllerAdvice.java:36-40`). Remaining check to confirm on a running stack: that on a reject the dialog stays open with empty fields (predicted) rather than closing (the corrected-away claim).

## Why it matters

This is **loud** (the user sees a toast) but **destructive of their work**: on any reject - most commonly a server-side validation failure the client could not pre-empt, e.g. a duplicate ODDRN - the entire form is discarded. For the create flow the cost is re-entering the name, ODDRN, namespace, and description; for a user who carefully composed an ODDRN this is real friction and a likely source of abandonment. It affects every operator who registers or edits a data source and hits a backend-side validation error. No data loss in the database and no security impact, so severity is medium, but it is a clear correctness defect in the submit flow: a failed save must never clear the user's input.

## Suggested fix

Gate the reset/close on success, and surface the server error inline instead of only as a toast:

1. In `DataSourceForm.tsx`, branch on the dispatched result - use `.unwrap()` (or check `registerDataSource.fulfilled.match(result)`) and only call `clearState()` in the fulfilled branch; in the rejected branch keep the form populated. This is the single load-bearing fix - it stops the field wipe.
2. The dialog-close is already gated on the redux success flag (`handleCloseSubmittedForm`, `DialogWrapper.tsx:81-83`), so the modal correctly stays open on a reject today; just make sure the success-gated reset in (1) keeps that behaviour and the now-populated form is what the user returns to.
3. Show the rejected payload (`errResp`) as inline `errorText` on the form (`DialogWrapper` already renders an `errorText` prop, `DialogWrapper.tsx:121-125`) so the user sees *why* the save failed without losing context.

Alternatively (broader, affects all consumers), have the submit-site await `dispatch(...).unwrap()` inside a try/catch - but the minimal, local fix is the success-gated reset above.
