  - **STRENGTHENED 2026-05-19 batch M (DEG-anchored sibling — wider blast radius via co-membership leakage)**: `odd-platform__java__DataEntityController__controller-method__getDataEntityGroupsLineage.md:bugs_limitations_corner_cases.[1]` (HIGH) + `security.known_security_gaps.[1]` (HIGH) + `security.owner_scoping`. **Batch M surfaces the DEG-anchored sibling** of REFACTOR-203: `GET /api/dataentitygroups/{data_entity_group_id}/lineage` (`DataEntityController.getDataEntityGroupsLineage`) inherits the same cross-owner enumeration posture as the per-entity lineage endpoints — no SecurityRule entry, no `fetchAssociatedOwner()` call, no owner-scoping at the repository layer. The DEG-anchored vector is **materially wider** than per-entity lineage in one specific way: **CO-MEMBERSHIP LEAKAGE**. The per-connected-component partitioning at `LineageServiceImpl.establishDEGRelations` (lines 200-216) emits one stream per disjoint subgraph; for a multi-team DEG (e.g. a Domain organising entities owned by several teams), the response leaks "team A's entity X is on the same data-pipeline as team B's entity Y" even when the individual entities would not be cross-team searchable. The DEG itself is a CONCEPTUAL grouping — leaking "team A and team B both contribute to the Finance Domain" reveals organisational structure that the DEG was designed to represent but not necessarily to disclose to every authenticated user. The write-side / read-side authorization asymmetry sharpens the finding: `addDataEntityDataEntityGroup` (POST) is gated by `DATA_ENTITY_ADD_TO_GROUP` Permission (`SecurityConstants.java:228-231`); `deleteDataEntityFromDataEntityGroup` (DELETE) is gated by `DATA_ENTITY_DELETE_FROM_GROUP` Permission (`SecurityConstants.java:232-236`); but `getDataEntityGroupsLineage` (GET) is gated only by `.authenticated()`. An operator who expects "managing DEG membership requires DEG-related permissions" is surprised that READING the DEG's lineage requires none. The DEG-anchored sibling is now codified as REFACTOR-343 NEW (the per-DEG instance) — REFACTOR-203 covers the per-entity instance; REFACTOR-343 covers the DEG-anchored instance; together they map the lineage-graph-shaped cross-owner enumeration surface across the platform's two anchor types.
  - **Statement**: The controller method calls `LineageService.getLineage(dataEntityId, depth, expandedEntityIds, DOWNSTREAM)` with no `Authentication`/`Principal` argument (`DataEntityController.java:256-262`); the service implementation does not consume the reactor `Context` for the current user (`LineageServiceImpl.java:87-122`) and the repository walk filters only by `LINEAGE.IS_DELETED.isFalse()` (`ReactiveLineageRepositoryImpl.java:167, 174`). The returned graph therefore contains every data entity reachable via the lineage edges, including entities the caller has no owner relationship to. Combined with REFACTOR-024 (getAllAlerts cross-owner exposure), REFACTOR-053 (getActivity), REFACTOR-187 (SearchController), and REFACTOR-200 (centerpiece detail read), lineage is the **graph-shaped cross-owner enumeration vector**: an authenticated caller can pivot from any one accessible entity to its full reachable subgraph across owner boundaries. The graph shape is materially wider than search because lineage edges encode causal connections — leaking the existence of a downstream transformer or consumer can reveal another team's internal pipeline structure even if the team's individual entities are not separately enumerable. VALIDATES REFACTOR-044 from earlier batch (which speculated on a lineage cap as the structural mitigation).
  - **Evidence**: `DataEntityController.java:255-263` (no owner argument) + `LineageServiceImpl.java:87-122` (no owner filter) + `ReactiveLineageRepositoryImpl.java:122-176` (no owner column in lineage table; filter is `IS_DELETED.isFalse()` only) + (NEW 2026-05-19H) `V0_0_2__add_lineage.sql:1-7` + `V0_0_17__add_establisher_into_lineage.sql:1-2` + `V0_0_79__data_deprecation.sql:11-12` (the schema migrations that confirm the absence of an owner column) + (NEW 2026-05-19 batch M) `LineageServiceImpl.java:54-57` (no AuthIdentityProvider field on the service) + `LineageServiceImpl.java:59-85` (`getDataEntityGroupLineage` has no owner-resolution call) + `AuthorizationCustomizer.java:29-30` (catch-all `.authenticated()`) + `SecurityConstants.java` (no rule for `/api/dataentitygroups/{id}/lineage` path — verified via Grep `dataentitygroups.*lineage` returning zero matches).
