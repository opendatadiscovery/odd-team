# AlertServiceImpl — semantic understanding

## understanding

`AlertServiceImpl` is the Spring `@Service` hop between the controller layer (`AlertController` for the UI/API surface, `AlertManagerController` for the Prometheus AlertManager webhook, `DataEntityController` for per-entity tabs) and the data layer (`ReactiveAlertRepository`, `ReactiveDataEntityRepository`). The class owns three orthogonal concerns whose composition determines the F-007 (`P-07:F-001 AlertManager Integration`) drift surface: (1) **principal context** — `AuthIdentityProvider` is consulted at lines 84, 93, 117, 235 ONLY on the UI-driven read / mutate paths; the AlertManager-webhook write path (`handleExternalAlerts`, lines 151-191) does NOT consult any auth identity, making the cross_tenant_alert_creation facet observable at this tier. (2) **Transaction boundaries** — `handleExternalAlerts` (line 152) and `applyAlertActions` (line 201) carry `@ReactiveTransactional`; the user-driven `updateStatus` (line 111) does NOT and depends entirely on `ActivityAspect`'s AOP-synthetic transaction (`ActivityAspect.java:42`) to wrap the read-then-write reopen-guard composition (lines 124-131) — that composition is unfenced at every layer (no `FOR UPDATE`, no DB unique-partial-index, no advisory lock). (3) **Activity-feed emission** — `@ActivityLog` AOP for `updateStatus` (line 112) plus three manual `activityService.createActivityEvents(...)` call sites for the bulk-mutation paths (lines 258, 324). This class is also the **de-duplication boundary** between the two ingestion paths: `applyAlertActions` (line 222-227) consumes `AlertAction` discriminators already keyed by `AlertUniqueConstraint` from `AlertActionResolver`; `handleExternalAlerts` deliberately SKIPS the resolver and forwards every webhook element to the shared `createAlerts` private helper (line 261-300) which issues bulk `INSERT … RETURNING` with NO `.onConflict(...)` — confirming the F-007 `no_idempotency_no_audit` facet at the service tier. All THREE named F-007 drift facets are anchored to file:line evidence in `security.known_security_gaps` and `bugs_limitations_corner_cases` below; this batch S refresh strengthens them at the service tier with batch P's PRIMARY-SOURCE controller-method-tier confirmation already in the chain (F-007 chain hops 1, 1-method-tier, 2).

- invariants:
  - "**`@ReactiveTransactional` placement is asymmetric across mutation methods.** `handleExternalAlerts` (line 152) and `applyAlertActions` (line 201) are annotated; `updateStatus` (lines 111-113) is NOT. The activity emission for `updateStatus` runs INSIDE the `ActivityAspect`'s synthetic `@ReactiveTransactional` (`ActivityAspect.java:42`) that wraps the AOP-intercepted Mono, NOT in a service-declared transaction. Consequence: the reopen-conflict guard (lines 124-131) reads `openAlertWithTheSameTypeExistsForDataEntity` THEN writes `updateAlertStatus` inside the AOP's synthetic transaction, but no row-level lock is taken on either step."
  - "**`updateStatus` is the ONLY method on the class with `@ActivityLog` AOP** (line 112). The other state-changing paths (`handleExternalAlerts`, `applyAlertActions`, `automaticallyResolveAlerts`) emit activity events MANUALLY via `activityService.createActivityEvents(...)` (lines 258, 324) — they do not use the annotation because the AOP design is single-alert / single-event, whereas these paths emit N events per call. Cross-link batch R `ReactiveActivityRepositoryImpl` — those manual emissions reach the activity table via `save(List<ActivityPojo>)` batch path with `is_system_event=true` discriminator."
  - "**Reopen-conflict guard is server-enforced application logic, not a DB constraint** (lines 124-131). The `if (AlertStatusEnum.OPEN == status)` branch calls `alertRepository.openAlertWithTheSameTypeExistsForDataEntity(alertId)` and `sink.error(new BadUserRequestException(...))` if true. The literal English message is `Cannot reopen alert since the system already has an open alert of the same type` (lines 128-129). The check is unfenced: two concurrent reopen requests for sibling alerts of the same type can both pass."
  - "**`updateStatus` has two switchIfEmpty fallback steps** (lines 119-120). The first replaces the username-aware update with a `username=null` update for anonymous / system-context callers; the second emits `NotFoundException` if the alert does not exist. The 'anonymous still proceeds' path is reachable when `auth.type=DISABLED` OR when an upstream caller has no SecurityContext."
  - "**AlertManager webhook path hardcodes type=DISTRIBUTION_ANOMALY** (line 177). The AlertManager-side `alertname` / `severity` labels are ignored; every webhook payload becomes the same type regardless of provider configuration."
  - "**The chunk description for AlertManager-derived alerts is `Distribution Anomaly. URL: %s`** with the URL-encoded `generatorURL` + `g0.moment_input` + `g0.end_input` query params (lines 168-185). The generator URL is propagated verbatim from the webhook payload (untrusted)."
  - "**`createAlerts` private helper is shared by both ingestion paths** (lines 261-300). It chains: `repo.createAlerts(alerts)` → group chunks by `AlertUniqueConstraint` → flatten with `additionalChunks` → `repo.createChunks(chunks)` → `registerAlertCreatedEvents` (activity emission) → `repo.setLastCreatedAt(...)`. Activity emission for new alerts therefore lives in ONE place; the two callers diverge only at the `AlertAction` discriminator step. Crucially: NO `ON CONFLICT` clause at this helper (cross-ref batch H ReactiveAlertRepositoryImpl `createAlerts` SQL primary source)."
  - "**`handleExternalAlerts` constructs `AlertPojo` from the webhook payload with NO entity_oddrn validation** (line 178: `setDataEntityOddrn(externalAlert.getLabels().get(\"entity_oddrn\"))`). Three negations: (a) NO lookup against DATA_ENTITY to confirm the oddrn refers to a real entity; (b) NO caller-identity check (the AlertManager path is unauthenticated by design per batch P controller-method-tier confirmation); (c) NO ownership/permission check that the (anonymous-or-authenticated) caller is authorised to alert on the named entity. This is the F-007 `cross_tenant_alert_creation` facet PRIMARY-SOURCE at the service tier."
  - "**`handleExternalAlerts` SKIPS `AlertActionResolver`** — line 187 builds the unique-constraint key locally via `AlertUniqueConstraint.fromAlert(alert)` but never consults an open-alerts snapshot (which `AlertActionResolver` would provide via `getOpenAlertsForEntities` line 197). The `applyAlertActions` path (line 222-227) does pass through resolver-produced `AlertAction` objects — this is the de-duplication asymmetry that produces the F-007 `no_idempotency_no_audit` facet's idempotency gap at the service tier."
  - "**Activity emission for `applyAlertActions` is in TWO stages**: `createAlerts(...).then(automaticallyResolveAlerts(...))` (line 230). Each stage emits its own activity events: `registerNewAlertsActivityEvents` for OPEN_ALERT_RECEIVED / RESOLVED_ALERT_RECEIVED (lines 309-325), and `registerAutomaticallyResolvedAlertsActivityEvents` for ALERT_STATUS_UPDATED with `systemEvent=true` (lines 247-259). Per batch R `ReactiveActivityRepositoryImpl`: these reach the activity table via the batch `save(List<ActivityPojo>)` path with NO transaction wrap inside `executeInPartition` — partial-commit risk under partition rotation."

  - "Reactive WebFlux + Reactor throughout — non-blocking I/O, no thread held during DB await. Per-request thread cost is O(1). Throughput bounded by R2DBC connection pool size."

  - "**No outbound HTTP, no message-bus, no async-queue side-effects.** The service is fully in-process; the only network I/O is to the DB."

- **scaling_characteristics**:
  - "**Stateless — instances scale horizontally.** The service carries no instance state; the five injected fields (`alertRepository`, `dataEntityRepository`, `alertMapper`, `authIdentityProvider`, `activityService`) are Spring beans."
  - "**No advisory lock at the service layer.** The two `@ReactiveTransactional`-annotated methods (`handleExternalAlerts`, `applyAlertActions`) use ordinary read-committed transactions; row-level locks via `FOR UPDATE` only on the repo's `getOpenAlertsForEntities` (read INSIDE the transaction). No coordination between concurrent ingestion calls on the same data entity — concurrent ingestion of the same DQ test result from two sources could both pass the snapshot read, both call `applyAlertActions`, and produce duplicate alerts UNLESS the repo's `FOR UPDATE` line lock serialises them."
  - "**Reopen-conflict guard is application-level, not transactional.** Two concurrent reopen requests for sibling alerts of the same type on the same data entity can both pass.   - "**No retry / circuit-breaker / backoff** on any path. A transient DB failure surfaces as a Mono error; the caller (controller / ingestion processor) has no automatic retry."
  - "**Pagination passes through unmodified** — no upper bound on `size`. Cross-reference: `AlertController.getAllAlerts` REFACTOR-024 family. A caller passing `size=1_000_000` materialises a million-row response with no server-side cap. The cost lives at the repo (and on the wire); the service does not validate or clamp."
