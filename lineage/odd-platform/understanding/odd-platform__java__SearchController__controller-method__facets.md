# SearchController#facets (getSearchFacetList + getFiltersForFacet) — semantic understanding

## understanding

The "facets" surface on `SearchController` is realised by TWO sibling reactive endpoints that operate on the SAME `SearchFacets` session UUID: `getSearchFacetList` (`SearchController.java:42-47`, `GET /api/search/{search_id}` per `openapi.yaml:654-674`) returns the seven-facet aggregate counts + total entity counts for the session, and `getFiltersForFacet` (`SearchController.java:30-40`, `GET /api/search/{search_id}/facet/{facet_type}` per `openapi.yaml:702-732`) returns the paginated list of countable filter options for a single facet type (TAGS / OWNERS / TYPES / GROUPS / STATUSES per `MultipleFacetType`). Both delegate to `SearchServiceImpl` (`SearchServiceImpl.java:51-72`) which mints SQL via `ReactiveSearchFacetRepositoryImpl` — every facet count is computed CATALOG-WIDE with no `OWNERSHIP` join and no principal-derived predicate (`ReactiveSearchFacetRepositoryImpl.java:163-249, 339-407, 251-337, 409-452, 454-534`); only `getFacetsData`'s `myObjectsCount` (`SearchServiceImpl.java:128-130`) is owner-scoped, and even that is included as an ADDITIONAL count alongside the cross-owner `total`. The `search_id` is an opaque `gen_random_uuid()` row in the `search_facets` table whose schema has NO `owner_id` / `created_by` / `user_id` column (`V0_0_1__init.sql:204-211`) — any authenticated caller in possession of any other user's UUID can read, update, and drive the facet drill-down for that session.

## bugs_limitations_corner_cases

- "**`GET /api/search/{search_id}` and `GET /api/search/{search_id}/facet/{facet_type}` expose CROSS-OWNER catalog cardinality to any authenticated user via facet drill-down — the same cross-owner read posture as REFACTOR-024 / REFACTOR-340, applied to the facet-COUNTS surface.** Even if a future hardening were to add owner-scoping to the search RESULT list, facet counts on `OWNERS`, `NAMESPACES`, `TAGS`, `GROUPS`, `TYPES`, and `STATUSES` reveal the catalog cardinality across all owners — an attacker can drill `getFiltersForFacet(OWNERS)` to enumerate every owner name and the COUNT of entities each owns, then drill `getFiltersForFacet(NAMESPACES)` (NB: NAMESPACES is in `FacetType` but not in `MultipleFacetType`; the namespace facet appears via `getSearchFacetList`'s aggregate response) to enumerate every namespace. The aggregates are computed catalog-wide in `ReactiveSearchFacetRepositoryImpl.java:163-249` (entity class), `339-372` (owner), `374-407` (tag), `251-337` (type), `409-452` (group), `454-534` (status) — every aggregator joins to `SEARCH_ENTRYPOINT` + `DATA_ENTITY` and applies `getDataEntityDefaultConditions` (only `HOLLOW`, `STATUS != DELETED`, `EXCLUDE_FROM_SEARCH`) without any `OWNERSHIP` join or principal-derived predicate." — evidence: `SearchController.java:30-47` (no `@PreAuthorize`) + `SearchServiceImpl.java:51-72, 122-155` (no principal-derived filtering on counts) + `ReactiveSearchFacetRepositoryImpl.java:163-249, 251-337, 339-372, 374-407, 409-452, 454-534` (the facet SQL — no OWNERSHIP join, no caller-principal predicate) + `SecurityConstants.java` (no rule entry for any `/api/search/*` path) + WebFetch search page 2026-05-19 (silent on the cross-owner posture) — severity: HIGH

- "**The `search_facets` table has no user binding — any authenticated user in possession of any other user's `searchId` UUID can READ, UPDATE, and DRIVE that session.** Concrete impact: (a) an operator who copies a search URL into a bug report exposes their entire saved-filter state including `My Objects` posture; (b) a CSRF-style cross-tab actor with read access to URL bars in the browser can hijack the session; (c) an authenticated attacker can probe `GET /api/search/{guess}` UUIDs and either get `Search not found` (404) or read another user's session (200). The UUID space is 122-bit gen_random_uuid so brute-force is infeasible, but URL leakage is not. The schema (`V0_0_1__init.sql:204-211`) has TODOs for `more clever way to generate uuid` and `define TTL` but no maintenance has addressed the unscoped posture in any subsequent migration. Cross-link to batch E (SearchController.search session-UUID-has-no-per-user-binding finding)." — evidence: `V0_0_1__init.sql:204-211` (schema with no owner column + TODOs) + `SearchServiceImpl.java:84-96` (`updateFacets` accepts any caller for any UUID) + `SearchServiceImpl.java:157-160` (`fetchFacetState` does no ownership check) + `ReactiveSearchFacetRepositoryImpl.java:85-106` (`update` and `get` are raw UUID-keyed operations) — severity: HIGH

## security

- **auth_mode_relevance**: `LOGIN_FORM | OAUTH2 | LDAP` (the three modes that protect the UI/API surface this controller is mounted on). Under `DISABLED` both endpoints are anonymously reachable. The methods themselves carry no `@ConditionalOnProperty`; auth wiring is enforced globally by `LoginFormSecurityConfiguration` / `OAuthSecurityConfiguration` / `LDAPSecurityConfiguration` / `DisabledAuthSecurityConfiguration` (cross-reference: `AlertController.getAllAlerts` sidecar's verified auth-mode wiring). `S2S` is NOT relevant — S2S protects `/ingestion/entities` only, not `/api/search/*`.

- **ingestion_filter_relevance**: `NO — UI/API surface, not /ingestion/entities`. The `IngestionDataEntitiesFilter` matches `/ingestion/entities` POST only; `GET /api/search/{id}` and `GET /api/search/{id}/facet/{type}` do not match.

- **authorization_assertions**: [] — `SearchController.java:30-47` carries no `@PreAuthorize`, no `@Secured`, no programmatic `permissionService.hasPermission(...)` call. `SecurityConstants.SECURITY_RULES` (verified by `grep -in 'search\\|facet' <SecurityConstants.java>` returning zero matches) contains no entry for any `/api/search/*` path. The path falls through to `pathMatchers('/**').authenticated()` (`AuthorizationCustomizer.java:29-30`). Authentication is required; authorization is not enforced. Note also that **no row-level ownership check** is enforced — even with a permission gate, the missing `search_facets.owner_id` column would prevent enforcement; cross-link `bugs_limitations_corner_cases[1]`.

- **owner_scoping**: `BYPASSES — facet counts are computed catalog-wide`. Both endpoints pass only `(searchId, ...)` to `SearchServiceImpl` (`SearchController.java:38, 45`); the service issues `reactiveDataEntityRepository.countByState(state)` for catalog-wide `total` (`SearchServiceImpl.java:126`); the facet aggregators in `ReactiveSearchFacetRepositoryImpl` apply only `getDataEntityDefaultConditions` (HOLLOW=false, STATUS != DELETED, EXCLUDE_FROM_SEARCH NULL-or-false) with no `OWNERSHIP` join (`ReactiveSearchFacetRepositoryImpl.java:571-577`). ## performance

- **hot_paths**:
  - "Per-keystroke hot path on the ODD Platform UI's Catalog tab — every facet drill-down click fires either `getSearchFacetList` (when the user opens the Catalog tab) or `getFiltersForFacet` (when expanding a facet panel). With seven facets visible and one re-fetch per filter toggle, a single user session can issue dozens of facet queries per minute. On a multi-tenant platform with concurrent active users, the facet endpoints are among the most frequently hit catalog-side endpoints." — evidence: `SearchController.java:30-47` + WebFetch search page 2026-05-19 (Catalog tab facet sidebar)
  - "Each `getSearchFacetList` issues FOUR sequential-in-pipeline-but-concurrent-in-Reactor DB calls (the UPDATE-RETURNING on `search_facets` for `last_accessed_at` + entity-class facet aggregator + catalog-wide total count + owner-scoped my-objects count) via `Mono.zip` (`SearchServiceImpl.java:122-155`). Each `getFiltersForFacet` issues TWO DB calls (the UPDATE-RETURNING on `search_facets` + the facet aggregator)." — evidence: `SearchServiceImpl.java:51-72, 122-155, 157-160`

- **throughput_characteristics**:
  - "Single reactive call per endpoint — `Mono<ResponseEntity<...>>` / `Mono<ResponseEntity<Flux<...>>>`; non-blocking I/O; no thread is held during the DB await" — evidence: `SearchController.java:30-47`
  - "`getSearchFacetList`: 4 parallel-via-`Mono.zip` DB calls — entity-class aggregator + catalog-wide total + my-objects total + the UPDATE-RETURNING fetch of the session row. Reactor parallelism is the property of `Mono.zip`; actual SQL concurrency is bounded by the WebFlux jOOQ DB connection pool." — evidence: `SearchServiceImpl.java:122-155`
  - "`getFiltersForFacet`: 2 sequential DB calls — fetch session, then facet aggregator. The facet aggregator itself is a single jOOQ SQL select with LIMIT/OFFSET pagination." — evidence: `SearchServiceImpl.java:51-63` + `ReactiveSearchFacetRepositoryImpl.java:339-372` (owner facet representative shape)
  - "No bulk variant — each call is a per-session, per-facet-type aggregator" — evidence: `SearchController.java:30-47`

- **resource_allocation**:
  - "Per-request allocations bounded by `size` on `getFiltersForFacet` — the repository emits a `Map<SearchFilterId, Long>` whose entry count is at most `size`; the service then filters out already-selected filters and maps to `CountableSearchFilter`. With no upper bound on `size`, peak memory is proportional to the caller-supplied page size." — evidence: `ReactiveSearchFacetRepositoryImpl.java:131-132, 369-371` + `SearchServiceImpl.java:177-186`
  - "Pagination `OFFSET` is computed as `(page - 1) * size` (`ReactiveSearchFacetRepositoryImpl.java:129, 157, 315, 369, 404, 449, 515`) — for deep pages, Postgres must scan and discard `(page - 1) * size` rows before returning the requested window. Cost grows linearly with deep pagination; keyset pagination would be O(1) but is not implemented here."
  - "`getSearchFacetList`'s entity-class aggregator runs `unnest(DATA_ENTITY.ENTITY_CLASS_IDS)` over the FULL data-entity table when no facets are selected (`ReactiveSearchFacetRepositoryImpl.java:176-178, 229-231`) — on platforms with hundreds of thousands of data entities, this is a per-tab-load hot query"
  - "`getFiltersForFacet(OWNERS)` runs `OWNER LEFT JOIN OWNERSHIP LEFT JOIN SEARCH_ENTRYPOINT LEFT JOIN DATA_ENTITY` with `countDistinct(SEARCH_ENTRYPOINT.DATA_ENTITY_ID)` — a 4-way join over the largest catalog tables. On platforms with high catalog cardinality, owner-facet drill-downs are the dominant facet cost." — evidence: `ReactiveSearchFacetRepositoryImpl.java:339-372`

- **scaling_characteristics**:
  - "Stateless controller methods — horizontal scaling unconstrained at this layer" — evidence: `SearchController.java:30-47` (no instance state in the methods)
  - "Persistent session state in `search_facets` table — every `POST /api/search` adds a row; no TTL eviction (`V0_0_1__init.sql:206-207` TODOs); table grows unbounded. On long-running platforms the table can reach millions of rows; the `last_accessed_at` UPDATE on every read keeps every session 'hot' in the table" — evidence: `V0_0_1__init.sql:204-211` + `ReactiveSearchFacetRepositoryImpl.java:99-106` + `V0_0_52__introduce_housekeeping.sql` (no `search_facets` policy)

Under concurrent UI tabs on the same session, the row-lock contention can serialise the writes." — evidence: `ReactiveSearchFacetRepositoryImpl.java:99-106`
