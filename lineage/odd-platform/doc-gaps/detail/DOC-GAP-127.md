- **DOC-GAP-127**: LineageServiceImpl.replaceLineagePaths is `@ReactiveTransactional`-annotated but a future self-invocation would silently bypass the annotation — Spring's transactional proxy only applies on EXTERNAL calls; if a future method on `LineageServiceImpl` called `this.replaceLineagePaths(...)`, the annotation would NOT apply, and the delete+insert sequence would NOT be atomic; the standard Spring caveat is undocumented at the service (LOW — no current bug; future-refactor trap)

  - **Evidence**:
    - `LineageServiceImpl.java:124-133` — verbatim: `@ReactiveTransactional public Flux<LineagePojo> replaceLineagePaths(final List<LineagePojo> pojos) { final Set<String> establishers = pojos.stream().map(LineagePojo::getEstablisherOddrn).collect(Collectors.toSet()); return lineageRepository.batchDeleteByEstablisherOddrn(establishers).thenMany(lineageRepository.batchInsertLineages(pojos)); }`. The annotation is declared on the public method; Spring's proxy intercepts the call ONLY when it comes through the proxy (i.e. from an external bean's call site, e.g. `lineageService.replaceLineagePaths(...)` from `LineageIngestionRequestProcessor.process`).
    - **The Spring-proxy caveat**: a hypothetical future method `LineageServiceImpl.someNewMethod(...)` that calls `this.replaceLineagePaths(...)` would invoke the method DIRECTLY on the instance, bypassing the proxy entirely. The `@ReactiveTransactional` annotation would NOT apply; the batchDeleteByEstablisherOddrn and batchInsertLineages calls would run in TWO separate transactions; a failure between them would leave the lineage table in a partial state (delete committed, insert failed → lineage data destroyed).
    - **No current self-invocation** exists in `LineageServiceImpl.java:1-313` (verified by grep `this\.replaceLineagePaths` and grep `replaceLineagePaths` across the file — only one call site, at line 132 within the method body for the recursive shape, which is NOT a self-invocation of the annotated boundary).
    - **The refactor-trap shape**: a typical Spring refactor that introduces this bug:
      - Maintainer adds a helper method `private Mono<Void> replaceMultipleEstablishers(Map<String, List<LineagePojo>> byEstablisher) { return Flux.fromIterable(byEstablisher.entrySet()).flatMap(e -> this.replaceLineagePaths(e.getValue())).then(); }`. The helper calls `this.replaceLineagePaths(...)` — directly on the instance. The `@ReactiveTransactional` boundary is silently lost. Each per-establisher call now runs in ITS OWN transaction, and the COMPOSITE operation has no atomicity.
      - The bug is invisible at code-review without explicit knowledge of Spring's proxy semantics. The maintainer's intent (atomic batch) does NOT survive the refactor; the test suite (if any) may not exercise the failure path that would reveal it.
    - **The standard Spring caveat**: this proxy semantic is well-documented in Spring's reference docs but not in any code-comment in `LineageServiceImpl.java`. A maintainer onboarding to the codebase has no anchor for the gotcha.
    - **The Class-A failure mode**: combined with DOC-GAP-114 (silent lineage-edge-delete-on-absence), a partial-state self-invocation refactor produces silent lineage destruction at scale — the delete commits to multiple establishers, but the inserts are scoped to per-call transactions that fail individually. Operators see partial lineage loss with no log signal (DOC-GAP-114's no-log-warn).
