## What

`docs/data-modelling/relationships.md` says both of these, on the same page:

> **:40 (UI walkthrough)** — "Click a row to open the relationship's detail page; the platform routes to the
> `/api/relationships/erd/{id}` or `/api/relationships/graph/{id}` payload depending on the relationship type."

> **:86 (Known operator caveats)** — "**Clicking a row on the list opens the source entity's detail page — not
> a relationship-type-specific URL.** The row's Name link routes to `/dataentities/{id}` … on every click,
> regardless of relationship type. The two type-specific endpoints … are reached **from inside** the
> entity-detail page's relationship-card rendering, not from the row click on the list page."

`:86` is the correct one. `:40` describes behaviour the page itself then documents as not existing.

## Why it happened (so the fix does not recur)

`backlog/docs/DOC-229.md` (**status: `done`**) is titled for exactly this defect — it lists
*"row-click routing drift"* among six load-bearing operator caveats it added to this page. It **added the
caveat and never corrected the claim the caveat contradicts.** That is the "fix one surface, leave the other"
pattern (`memory/feedback_converge_claim_complete_not_instance_loop`): the item closed with the page in a
worse state than a single wrong sentence, because now the page argues with itself.

This is a NEW item rather than a re-open of DOC-229 because DOC-229's own acceptance was about *adding*
caveats, and it met that; what was never in scope was reconciling the prose those caveats falsify.

## A second instance of the same shape on the same page

`:90` — "The behaviour is consistent with how the platform models relationships as first-class entities, but
the framing on the page above (*'search input filtering by name across the visible set'*) does not call out
the scope." The caveat is **critiquing the page's own bullet at `:37` instead of fixing it.** A published
manual should not narrate its own editorial debt to the reader; `:37` should simply say *"a search input
filtering by relationship **name** across the visible set"*, and the caveat should then only carry the
consequence (that it will not match by source/target entity name).

## Acceptance

- [ ] `:40` no longer promises type-specific routing on row click; it says what actually happens
      (`/dataentities/{id}`) and points to where the type-specific payloads *are* reached.
- [ ] `:37` states the search scope inline ("by relationship name"), and `:90`'s caveat drops the
      "the framing on the page above … does not call out the scope" clause, keeping only the consequence.
- [ ] The page is read end-to-end once after the edit, to confirm no third passage still asserts the old
      routing.
