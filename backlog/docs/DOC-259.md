## Description

The live `/configuration-and-deployment/odd-platform` page (WebFetched 2026-05-27, 200 OK) DOES surface `notifications.wal.advisory-lock-id`, `datacollaboration.receive-event-advisory-lock-id`, and `datacollaboration.sender-message-advisory-lock-id` as configuration keys. It is **silent on `partition.advisory-lock-id`, on the no-central-registry framing, on the no-collision-validator, on `pg_advisory_lock` blocking forever with no timeout or fail-fast, on the partition-orchestrator deliberate-share exception, and on per-subsystem-readiness-probe degradation under collision**. Three operator-visible caveats need a new sub-section AND cross-mentions on the housekeeping / notifications / datacollaboration / partition-period sections.

**Caveat 1 — Four hand-numbered advisory-lock IDs with no central registry, no collision validator, no boot-time enumeration log (F-065a).** Four IDs (90, 100, 110, 120) are assigned in `application.yml` across three `@ConfigurationProperties` classes: `notifications.wal.advisory-lock-id: 100` (line 177), `partition.advisory-lock-id: 90` (line 198), `datacollaboration.receive-event-advisory-lock-id: 110` (line 201), `datacollaboration.sender-message-advisory-lock-id: 120` (line 202). NO central `AdvisoryLockId` enum, NO `@PostConstruct` cross-validator, NO startup INFO log enumerating "the platform's advisory-lock-id registry." Grep for `AdvisoryLockId` / `LockIdRegistry` returns zero matches in the codebase. Operators customising any via env var (typical enterprise hygiene — per-env overrides) can silently collide two subsystems; cross-subsystem collisions silently wedge one feature.

**Caveat 2 — `pg_advisory_lock` blocks forever; no timeout, no fail-fast, no readiness-probe degradation (F-065b — HIGH).** `PostgreSQLLeaderElectionManagerImpl.java:21-24` executes `pg_advisory_lock(advisoryLockId)` via raw `Statement.execute` — **the blocking variant**. NO `pg_try_advisory_lock` fast-path, NO `statement_timeout` setting, NO Spring bean readiness-probe degradation. On collision (Caveat 1 enables this), the second subsystem's acquire thread enters Postgres lock-wait state **forever**. The Spring container DOES NOT detect the wedge — bean construction returned; the worker thread is in WAIT via Postgres; `/actuator/beans` + `/actuator/health` report "running." Three of the four advisory locks live inside P-07 features (notifications WAL — F-009; data-collaboration receive + sender — F-038); a collision silently breaks one or more P-07 features with no diagnostic trail. Operators see one feature degrade silently while everything else looks healthy.

**Caveat 3 — `partition.advisory-lock-id` is undocumented in the live operator page; operator may remove it as "unused" (F-065c).** Live `/configuration-and-deployment/odd-platform` page lists 3 of the 4 keys; `partition.advisory-lock-id` does NOT appear in any documented config table. The Activity-Feed configuration section documents `odd.activity.partition-period` (the partition WIDTH key); it does NOT enumerate the partition orchestrator's leader-election lock. `ActivityTablePartitionManager` + `MessageTablePartitionManager` both acquire lock 90 at boot via `PostgreSQLLeaderElectionManagerImpl`. **Operators following the docs may consider the key undocumented-therefore-unused and remove it from their config overlay — breaking nightly partition creation silently** (the partition orchestrator wedges per Caveat 2's mechanism).
