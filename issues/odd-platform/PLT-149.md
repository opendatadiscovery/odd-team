## What

`GET /api/integrations/{integration_id}` for an **unknown** id returns **HTTP 200 with a zero-length body** - not 404. Verified live:

```
$ curl -s -D - -o /dev/null http://localhost:18080/api/integrations/this-does-not-exist
HTTP/1.1 200 OK
content-length: 0
```

(A known id at the same endpoint returns 200 + a ~3.3 KB JSON `Integration` body.)

Root cause: the registry lookup returns an empty reactive stream on a miss, and the controller maps it with `.map(ResponseEntity::ok)` - which is never invoked on an empty `Mono`, so Spring WebFlux completes the exchange with a default empty 200. There is no `switchIfEmpty(...)` translating the miss into a `NotFoundException`/404. Compare `MetadataFieldServiceImpl.get`, which does `switchIfEmpty(Mono.error(new NotFoundException(...)))` on a missing id.

Two consequences:

1. **No 404 for a missing resource.** A client cannot distinguish "integration does not exist" from "exists but empty body" by status code. Most generated SDK clients will try to deserialize the empty body as an `Integration` and fail (or yield a null object) rather than handle a not-found.
2. **Contract drift.** `openapi.yaml` for `getIntegration` declares only a `200` response (schema `Integration`); it documents neither the empty-body 200 that actually ships nor a `404`.

## Where

```
controller/IntegrationController.java:19-22
  getIntegration(): integrationService.get(integrationId).map(ResponseEntity::ok)
  - no switchIfEmpty; empty Mono -> default empty 200

integration/service/IntegrationServiceImpl.java (get)
  -> integrationRegistry.get(id)   (Mono.empty on miss; no error mapping)

integration/.../ResourceFilesIntegrationRegistry.java:15-17
  get(): Mono.justOrEmpty(registry.get(id))   - source of the empty Mono

contract: openapi.yaml (getIntegration) - declares only 200; no 404

contrast (correct pattern): service/MetadataFieldServiceImpl.get
  - switchIfEmpty(Mono.error(new NotFoundException(...)))
```

## Why it matters

`/api/integrations/{id}` is a public, anonymously-reachable surface (under `auth.type=DISABLED` it needs no credential). A 200-with-empty-body on a missing id is a contract trap for every API consumer and SDK generator: status-code-driven error handling sees "success", body-driven deserialization sees null/garbage. It also makes the wizard's free-form `String integrationId` path parameter a silent enumeration oracle (200-empty vs 200-body) with no logging. The fix is small and local.

## Suggested fix

1. Add `switchIfEmpty(Mono.error(new NotFoundException("Integration", integrationId)))` to `IntegrationServiceImpl.get` (or `ResourceFilesIntegrationRegistry.get`), mirroring `MetadataFieldServiceImpl.get`.
2. Declare the `404` response on `getIntegration` in `openapi.yaml`.

**How to verify:** `GET /api/integrations/{unknown-id}` returns 404; a known id still returns 200 + body.

## How discovered

Found while exercising the Integration Wizard manifest endpoints end-to-end against a running stack (`AUTH_TYPE=DISABLED`); the live `curl` above is the reproduction.
