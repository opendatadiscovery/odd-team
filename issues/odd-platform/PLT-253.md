> **CORRECTION -- READ FIRST.** This item was filed as issue #1867 with a headline claiming the Overview
> TERMS panel lists a term twice. **That claim is wrong.** It was derived from the SQL shape without
> tracing the read path through to the API response. Measured against merged main (see `## Correction`),
> the duplicate is absorbed before it reaches the client: the panel shows the term ONCE, the badge says 1,
> and they agree. What survives is a real but latent duplication inside the query. Severity corrected to
> low. Issue #1867 needs its title, impact section and milestone corrected -- or closing as not-a-defect.

## What is actually true

PR #1864 added `symmetricTermRelations()`, a derived table defined as

```
SELECT assigned_term_id, target_term_id, is_description_link FROM term_to_term
UNION ALL
SELECT target_term_id, assigned_term_id, is_description_link FROM term_to_term
WHERE is_description_link = false
```

`term_to_term` has `PRIMARY KEY (target_term_id, assigned_term_id)`, so `(X, Y)` and `(Y, X)` are two
distinct legal rows, and `linkTermWithTerm` inserts without checking for the reverse row. When a pair is
stored in both orientations the `UNION ALL` yields the counterpart **twice** for the Overview join
(`target_term_id = X`). That part is real and reproducible.

It is harmless today because every consumer collapses it:

- **Overview TERMS panel** -- `ReactiveTermRepositoryImpl.extractTerms()` collects into a `Set<TermPojo>`
  via `JooqRecordHelper.extractAggRelation` -> `extractSetRelation`, which de-duplicates twice over
  (`r.get(field, Set.class)`, then `Collectors.toSet()`). jOOQ codegen sets `pojosEqualsAndHashCode = true`
  (`odd-platform-api/build.gradle:99`), so two identical rows are equal POJOs and collapse to one.
- **Linked-terms badge** -- `countDistinct(...)`.
- **Linked-terms tab** -- `GROUP BY` on the term's own columns.

So the duplication is contained at the SQL layer. The cost is wasted work (rows materialized then
discarded) plus a latent trap: any FUTURE consumer of that derived table which does not collapse to a set
-- a `count(*)`, a list mapper, a new paginated endpoint -- would see doubles.

## Correction -- how this was measured (2026-08-30)

A throwaway integration test was run against merged main (`00b03129`) on a Testcontainers Postgres. It
seeds terms X and Y, creates the link from BOTH pages (`createRelationWithTerm(y, x)` and
`createRelationWithTerm(x, y)`, i.e. both orientations stored), then reads `getTermDetailsDto(X)` and
asserts on the **raw** DTO list rather than a `Set`, so nothing downstream could hide a duplicate:

```
PLT253_PROBE rawOverviewListSize=1 occurrencesOfY=1 badge=1
```

Panel entry count 1, badge 1 -- they agree, and no duplicate reaches the API response.

The earlier contrary claim came from simulating the query shape (`UNION ALL` + a non-distinct
`jsonArrayAgg`) and stopping there, without following `extractTerms` into its `Set`. The frontend was
also checked and is NOT what saves it: `TermLinkedTerms.tsx` does a plain `.map()` with `key={term.id}`
and no de-duplication, so had a duplicate reached it, it would have rendered twice.

## User-facing impact

**None observed.** Measured above: the panel and the badge agree at 1. An operator sees nothing wrong.
This is a code-health item, not a defect report.

## Suggested fix (low priority -- does not gate 1.0.0)

1. **`UNION` instead of `UNION ALL`** in `symmetricTermRelations()`. One word; removes the duplicate rows
   at the source and the latent trap with them.
2. **Guard the write.** `linkTermWithTerm` should treat an existing link in either orientation as
   already-linked, so no new both-orientation pairs are created.
3. **Optional cleanup** of pairs already stored twice (excluding description links, which are legitimately
   directional):

```sql
DELETE FROM term_to_term a
USING term_to_term b
WHERE a.is_description_link = false
  AND b.is_description_link = false
  AND a.target_term_id   = b.assigned_term_id
  AND a.assigned_term_id = b.target_term_id
  AND a.target_term_id   > a.assigned_term_id;
```

If (1) and (2) land, (3) is cosmetic -- the duplicate rows would be inert.

## Notes (adjacent, not part of this item)

- `symmetricTermRelations()` replaces a direct table reference in the term-detail query, the term LIST
  query `findByState`, and `listByTerm`. `term_to_term` has no index on `assigned_term_id` alone (the PK
  leads with `target_term_id`), so that join was already sequential; the union doubles a scan that was
  already unindexed. A constant factor at glossary scale.
- `term_to_term.deleted_at` exists in the schema with no readers or writers: term relations are hard
  deleted. Vestigial column.
