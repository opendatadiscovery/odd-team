## Description

**Failure shape: half-finished narrative / cross-audience absence.** The #1825 search overhaul is being documented
**per slice on the 1.0.0 train** — and the train stops after the two URL slices.

Verified by `grep -rl` over `backlog/docs/` on 2026-08-30:

| slice | issue / CTRIB | merged? | doc item |
|---|---|---|---|
| ST-1a — shareable `/search?q=` URL | #1825 / CTRIB-048 | yes | **DOC-495** (+ DOC-496) |
| ST-1b — facets in the URL | #1825 / CTRIB-049 | yes | **DOC-497** |
| ST-1c — home navigators onto the param URL | #1835 / CTRIB-052 | yes | **none** |
| ST-2a — status-priority browse default | #1836 / CTRIB-053 | yes | **none** |
| ST-2b — the global **Sort-by dropdown** | #1836 / CTRIB-054 | yes | **none** |
| ST-3 — **saved searches** | #1837 / CTRIB-055 | yes | **none** |
| ST-4 — **cross-kind unified results** | #1838 / CTRIB-056 | yes | **none** |
| ST-5a / ST-5b — index-backed sort, keyset pagination | #1839 / CTRIB-057, 058 | yes | **none** (internal — arguably none owed) |
| ST-5c — snapshotted `popularity_score` + the refresh job | #1839 / CTRIB-059 | PR #1862 draft | **none** |

Three of the undocumented slices are **directly user-visible**, and one is **operator-visible**:

1. **Saved searches (ST-3)** — a named, per-user, editable saved search on the main catalog search
   (`odd-platform-ui/src/components/Search/Results/SavedSearches/{SavedSearches,SavedSearchForm}.tsx`;
   `SavedSearchController` + `saved_search` table, `V0_0_97`). The published page says the `/search/{id}` URL is
   "**not** a saved search" and that "there is no *go back to my last search* affordance" — both become wrong.
2. **Cross-kind results (ST-4)** — `POST /api/search/assets` returns Data Entities + Terms + Query Examples in one
   ranked list (`Results.tsx` -> `assetSearch` thunks). The published page still says "The Catalog-level full-text
   search across data entities is exclusive to the Catalog tab" and documents nine class tabs, all data-entity classes.
3. **The global Sort-by dropdown (ST-2b)** + the status-priority browse default (ST-2a) — a new, server-side,
   URL-carried sort control on the result list. No page mentions sorting at all.
4. **The popularity snapshot job (ST-5c)** — `AssetPopularitySnapshotJob`, `@Scheduled(fixedRate = 15, MINUTES)` +
   `@SchedulerLock(name = "assetPopularitySnapshotJob", lockAtLeastFor/lockAtMostFor = 14m)`, always-on with **no
   config key** to disable or tune it, running one unbounded `UPDATE ... FROM` over the whole
   `asset_search_entrypoint x data_entity` join per tick. This is the platform's **fifth** `@Scheduled` job, and
   the other four are all documented with cadence + lock posture + an operator caveat:
   `data-discovery/statuses.md:42` (DataEntityStatusSwitchJob — 10 min / 9 min ShedLock / no batch cap),
   `configuration-and-deployment/odd-platform.md:846` (housekeeping — 15 min / ShedLock / `housekeeping.enabled`),
   `odd-platform.md:176` + `:872` (session housekeeping — hourly / no leader guard),
   `odd-platform.md:916` + the Advisory-lock registry table (partition orchestrator).

`data-discovery/search.md` on documentation `origin/main` (`8599b84`) is the page that carries most of the drift.
DOC-495 + DOC-497 already rewrite its URL-model section on the train; nothing covers the rest.

## Acceptance Criteria

- [ ] **ST-3 saved searches** documented on `release/1.0.0` — what a saved search is, per-user scope, how it differs
      from the shareable `?q=` URL — and the two now-false statements in `search.md` ("not a saved search",
      "no go-back-to-my-last-search affordance") corrected in the same commit.
- [ ] **ST-4 cross-kind results** documented — that the catalog result list now spans Data Entities + Terms +
      Query Examples; the "exclusive to the Catalog tab" / data-entity-only framing corrected.
- [ ] **ST-2a/2b sort** documented — the Sort-by control, its options, the browse default, and that sorting is
      server-side and carried in the URL.
- [ ] **ST-5c** given an operator-manual entry alongside its four documented siblings: cadence, ShedLock name +
      window, that it is always-on and not configurable, and that `popularity_score` is a **snapshot** (a bucketed
      log2 band of `view_count`, refreshed on the cadence) — so any popularity-ordered surface built on it lags the
      live counter by up to one tick. While in that section, note the platform-level fact this slice makes more
      load-bearing (pre-existing, NOT introduced by ST-5c): `spring.task.scheduling.pool.size` is unset, so Spring's
      default **single** scheduler thread is shared by all five `@Scheduled` jobs — a slow job delays the others.
      NOTE the boundary: `GET /api/dataentities/popular` (the Catalog Overview
      **Popular** column) is unchanged and still reads the live `view_count`; the snapshot feeds the search-side
      ordering that arrives with #1861, so do not describe the existing Popular column as snapshotted.
- [ ] Cross-checked at the 1.0.0 release gate (`playbooks/release-review.md` check 1 — release delta -> doc-coverage
      matrix): every merged #1825 slice either has a train doc commit or a recorded, justified "no doc owed".
