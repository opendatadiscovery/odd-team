# PopularStrip (OwnerEntitiesList "Popular" column) — semantic understanding

## understanding

**There is no dedicated `PopularStrip.tsx` component in this codebase as of `9ac6436e`** — the substrate's logical node "PopularStrip" maps to the **fourth column inside `OwnerEntitiesList.tsx`** (`odd-platform-ui/src/components/Overview/OwnerAssociation/OwnerEntitiesList/OwnerEntitiesList.tsx:99-105`). The Popular surface is rendered as one of four `DataEntityList` columns under the "Recommended" h1 heading, alongside "My Objects" / "Upstream dependents" / "Downstream dependents". The popular fetch fires **once on mount** of OwnerEntitiesList via `dispatch(fetchPopularDataEntitiesList({page: 1, size: 5}))` (`OwnerEntitiesList.tsx:58-64`, `useEffect` with `[]` deps array, no interval, no polling, no refetch on focus). Each rendered tile is a `react-router` `<Link>` to `dataEntityDetailsPath(item.id)` which defaults to `/dataentities/{id}/overview` (`DataEntityList.tsx:38` + `dataEntitiesRoutes.ts:66-73`) — clicking a Popular tile navigates to the entity's Overview tab, which (per the upstream batch-G sidecar `getDataEntityDetails`) is the read-as-write endpoint that increments `data_entity.view_count`. **This closes the F-001 view_count loop on the client side**: every click on a Popular tile increments the very signal that determines Popular ranking. The component is reachable **only when the signed-in user has an associated Owner** (`OwnerAssociation.tsx:84-86`: `if (identity && ownership) return <OwnerEntitiesList />`) AND the deployment has `appInfo.authType !== 'DISABLED'` (`Overview.tsx:25-27` + `:53-59`) — therefore on DISABLED-mode deployments the Popular column on the home page is NOT rendered at all, narrowing the inflation-exposure surface from "anonymous home-page caller" to "owner-associated authenticated user" for the UI path (the API path `/api/dataentities/popular` remains anonymous-reachable under DISABLED per the batch-G `getPopular` sidecar).

## downstream_side_effects

What this component / thunk chain causes when invoked — the outbound graph.

- **HTTP request fired**: `GET /api/dataentities/popular?page=1&size=5` (via `dataEntityApi.getPopular` at `thunks/dataentities.thunks.ts:182`). Server-side this resolves to `DataEntityController.getPopular` → `DataEntityServiceImpl.listPopular` → `ReactiveDataEntityRepositoryImpl.listPopular` (per batch-G `getPopular` sidecar). The repository runs a CTE select + ORDER BY view_count DESC + LIMIT 5 + the per-row `hasAlerts` EXISTS subquery — sequential scan + sort over `data_entity` (no index on view_count per the batch-G evidence).
- **Redux state mutation**: `state.dataEntities.popular` replaced wholesale with the response payload on `fulfilled` (`dataentities.slice.ts:205-208`); fetching-status flags transition pending → fulfilled in `state.loader[fetchMyPopularDataEntities]`.
- **Click side-effect (per Popular tile clicked) — FIRES THE F-001 LOOP**: navigation to `/dataentities/{id}/overview` mounts the entity-detail SPA route, which dispatches `fetchDataEntityDetails` (verified by grep on the route registration at `DataEntityDetailsRoutes.tsx:44` and the standard entity-detail mount path). That thunk calls `GET /api/dataentities/{id}` → `DataEntityController.getDataEntityDetails` → `dataEntityService.getDataEntityDetails(id, ...)` which fires `incrementViewCount` (`ReactiveDataEntityRepositoryImpl.java:173-180` per the batch-F sidecar). **Therefore every click from Popular increments the very signal that determines Popular ranking** — closing the F-001 loop on the client. No client-side debouncing, no idempotency key, no per-tab-per-entity caching of the detail-page mount.
- **Browser history push**: the `<Link>` push (DataEntityList.tsx:38) emits a `history.push('/dataentities/{id}/overview')` — the back-button returns to home, which **remounts OwnerEntitiesList** and **re-fires the popular fetch** (the `useEffect(..., [])` runs on every mount, and a back-button navigation in react-router-dom v6 unmounts then remounts the route component by default). Combined with the per-click view_count increment, **a user clicking Popular → back → clicking again from a remounted Popular** observes an **already-updated ranking** if their click+back round-trip incremented the clicked entity's view_count past a neighbour.
- **NO analytics event emitted** — verified by grep on `mixpanel|amplitude|segment|gtag|posthog|track\\(` against `<odd-platform-repo>/odd-platform-ui/src` returning ZERO matches. There is no separate client-side view-tracking signal on Popular click; the only view event is the server-side `view_count` increment on the destination's detail-read.
- **NO toast / no notification on success** — `fetchPopularDataEntitiesList` is declared with `{}` options at thunks.ts:184 (no `setSuccessOptions`), so successful fetch is silent. Errors surface via the global error toast (the default `handleResponseAsyncThunk` behaviour).
- **NO cache write to localStorage / sessionStorage / IndexedDB** — popular data lives in Redux memory only; a hard-reload re-fetches.

## performance

- **hot_paths**:
  - "Popular fetch fires on **every mount of OwnerEntitiesList** — which is every home-page visit and every back-button navigation from an entity detail page. For a user who navigates home → entity → home → entity → home in a single session, the popular call fires 3 times — and on each fire, the server runs the non-indexed `ORDER BY view_count DESC` query per batch-G `getPopular.md:scaling_characteristics[1]`. For a 100-user team home-page-refreshing every 30 seconds, that's 200 RPM against an unindexed sort." — evidence: OwnerEntitiesList.tsx:58-64 (the unconditional useEffect dispatch) + batch-G `getPopular.md:hot_paths[0]`
- **throughput_characteristics**:
  - "synchronous-from-the-user's-perspective — the four columns share a single loading skeleton (OwnerEntitiesList.tsx:68-73, gated by `isOwnerEntitiesListFetching` which is an OR of all four columns' isLoading flags via getIsOwnerEntitiesFetching). ## Maintainer notes

The substrate's node identifier "PopularStrip" does not map to a single dedicated component file in this codebase — the Popular surface is implemented as the fourth column of `OwnerEntitiesList.tsx`, alongside My Objects / Upstream / Downstream. If a future maintainer wants to extract a true PopularStrip component (e.g. to surface Popular outside the Recommended panel, or to allow operator tuning of the Popular column independently), the cleanest factoring is to split `DataEntityList.tsx` into a generic per-column renderer and a Popular-specific wrapper that holds the fetch logic.

The most consequential finding in this sidecar is **the Structure-vs-Overview navigation target doc-drift**. The live doc says clicking a Popular tile opens the entity's Structure page; the code opens its Overview tab. The choice matters because the Overview tab is the view_count-incrementing endpoint per F-001. If the docs are corrected to "Overview", the F-001 loop closure description must add that the UI click DELIBERATELY incrementions view_count via the destination's read-as-write side-effect (closing the loop). If the code is changed to navigate to "structure", the F-001 loop description must add that the structure tab does NOT increment view_count — and the inflation-via-UI path is closed at the navigation level. Either way, the gap between docs and code is real and surfaceable in a DOC-NNN follow-up.

The second consequential finding is **the DISABLED-mode rendering mismatch**. The live doc page asserts the Recommended panel renders under DISABLED auth; the code unconditionally hides it. This is a clean factual contradiction with file:line evidence on both sides.
