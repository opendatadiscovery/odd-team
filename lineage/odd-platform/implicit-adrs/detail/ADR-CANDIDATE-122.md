## ADR-CANDIDATE-122 — Catalog-wide facet counts are the DESIGN — `myObjectsCount` is an EXTRA opt-in scope ADDED ALONGSIDE the catalog-wide `total`, NOT a permission boundary that scopes the aggregate

**Classification**: promote
**Severity**: MEDIUM
**Pillars affected**: [P-01-data-discovery, P-09-security-access-control]
**Support**: 1 sidecar (batch M `SearchController.facets`) — composes with ADR-CANDIDATE-003 (read-collaborative GET extended to the aggregate layer); cross-link batch E `SearchController.search` (the original surfacing of the catalog-wide-vs-myObjects distinction at the result-list layer).
**Batch**: M (2026-05-19)

**Surfaced by**:
- `odd-platform__java__SearchController__controller-method__facets.md:implicit_adrs.[1]` (HIGH) — "Catalog-wide facet counts are the design — `myObjects` is an EXTRA opt-in scope, not a permission boundary. `SearchServiceImpl.getFacetsData` (lines 122-155) computes BOTH `allCount` (catalog-wide `reactiveDataEntityRepository.countByState(state)`, line 126) AND `myObjectsCount` (owner-scoped, lines 128-130) and returns BOTH in the `SearchFacetsData` payload as the `total` and `myObjectsTotal` fields (`SearchFacetsData` schema lines 147-153). The `myObjects` boolean (`FacetStateDto.myObjects`, `FacetStateDto.java:24`) is a UI-level toggle that controls which entities the user SEES in the result list (`SearchServiceImpl.java:105-111`) — it does NOT scope facet COUNTS. The structural choice to surface BOTH totals confirms the intent: 'show the user what their slice of the catalog is, AND what the whole catalog looks like'."

**Decision statement**: ODD's search-facet aggregation layer (`SearchController.getSearchFacetList` + `SearchController.getFiltersForFacet`) deliberately computes facet counts **catalog-wide**, regardless of the caller's owner or the session's `myObjects` toggle. The `myObjects` boolean (`FacetStateDto.myObjects`, `FacetStateDto.java:24`) is a UI-level result-list toggle, NOT a permission boundary that scopes the aggregate.

The architectural composition:
1. **`SearchServiceImpl.getFacetsData` returns BOTH counts**: lines 122-155 run a `Mono.zip` of four DB calls that include `allCount` (catalog-wide `reactiveDataEntityRepository.countByState(state)`, line 126) AND `myObjectsCount` (owner-scoped `authIdentityProvider.fetchAssociatedOwner() + countByState(state, owner)`, lines 128-130). BOTH values are returned in the response payload as `total` and `myObjectsTotal` fields (per `SearchFacetsData` schema in `components.yaml`).
2. **Facet aggregators have NO owner predicate**: Every facet SQL in `ReactiveSearchFacetRepositoryImpl` (`getEntityClassFacetForDataEntity` at lines 163-249, `getOwnerFacetForDataEntity` at 339-372, `getTagFacetForDataEntity` at 374-407, `getTypeFacetForDataEntity` at 251-337, `getGroupFacetForDataEntity` at 409-452, `getStatusFacetForDataEntity` at 454-534) joins to `SEARCH_ENTRYPOINT` + `DATA_ENTITY` and applies `getDataEntityDefaultConditions` (HOLLOW=false, STATUS != DELETED, EXCLUDE_FROM_SEARCH NULL-or-false) — NO `OWNERSHIP` join, NO principal-derived predicate.
3. **`myObjects` is the result-list toggle, not the aggregate scope**: At `SearchServiceImpl.java:105-111`, the `myObjects` flag drives which entities the user SEES in `GET /api/search/{id}/results`. Facet drill-down (`GET /api/search/{id}/facet/{type}`) ignores the flag at the aggregate layer.
4. **The structural choice surfaces BOTH counts simultaneously**: The `SearchFacetsData` payload has TWO total fields (`total` + `myObjectsTotal`). The maintainer deliberately rendered "the user's slice" alongside "the whole catalog" — the UI's facet sidebar shows e.g. "12 of 4,521 entities owned by you" as the canonical UX. The catalog-wide total is the primary number; the owner-scoped total is the secondary affordance.

The decision aligns with ADR-CANDIDATE-003 (read-collaborative GET — every authenticated user reads every detail payload + lineage + activity + catalog via search) extended to the aggregate / facet layer. Where ADR-CANDIDATE-003 says "any authenticated user can READ any catalog entity", this ADR says "any authenticated user can ENUMERATE catalog cardinality via facet drill-down — owners, namespaces, tags, groups, types, statuses".

**Wisdom test**: PASS on all three questions.
1. **Intentional?** YES — the `Mono.zip(entityClassFacet, allCount, myObjectsCount)` structure at `SearchServiceImpl.java:132-133` explicitly RETURNS both totals as separate response fields rather than choosing one based on `myObjects`. The presence of two fields in the OpenAPI `SearchFacetsData` schema is positive design evidence.
2. **Structural impact?** YES — affects the OpenAPI contract for two endpoints; affects the UI's facet-sidebar rendering model; affects every third-party API consumer building search-facet integrations; affects the cross-owner enumeration vector (REFACTOR-024 + REFACTOR-340 family).
3. **Adding owner-scoping to facet counts would be STRUCTURAL?** YES — would change the facet SQL (add `OWNERSHIP` join to all 6 facet aggregators); would change the response semantic from "catalog cardinality" to "user-visible cardinality"; would tighten the trust calculus to per-user; would require either removing the `total` field (back-compat break) or redefining `total` to mean "user-scoped" (silent semantic change for every consumer).

**Evidence**:
- SearchController.facets.md says: "`SearchServiceImpl.java:122-155` (the four-Mono zip with both `allCount` and `myObjectsCount`) + `FacetStateDto.java:21-29` (the `myObjects` is alongside `query`, NOT a scope predicate at the aggregate layer) + the OpenAPI `SearchFacetsData` schema's `total` + `myObjectsTotal` fields (`components.yaml`) — intent_anchor: the `Mono.zip(entityClassFacet, allCount, myObjectsCount)` structure (`SearchServiceImpl.java:132-133`) explicitly RETURNS both as separate fields rather than choosing one based on `myObjects`"

**Existing ADR**: none. **Composes with ADR-CANDIDATE-003** (read-collaborative GET — this ADR is the aggregate-layer extension of the same trust model). **Composes with ADR-CANDIDATE-121** (search-session bearer-token-shaped — sessions store the `myObjects` flag as session state; the aggregate layer ignores the flag for facet counts; the storage decision and the computation decision share the same trust calculus). **Composes with ADR-CANDIDATE-052** (search-session-as-server-state).

**Cross-link gaps** (refactoring-scopes anchored on consequences this ADR DOES NOT defend):
- **REFACTOR-024 STRENGTHENED** (batch M): the cross-owner enumeration surface widens at the facet layer — an authenticated user drills `getFiltersForFacet(OWNERS)` to enumerate EVERY owner name + per-owner entity count, then `getFiltersForFacet(NAMESPACES)` (via the aggregate `getSearchFacetList`), `getFiltersForFacet(TAGS)`, `getFiltersForFacet(GROUPS)` — the catalog cardinality is fully discoverable. The ADR endorses the read model; REFACTOR-024 captures the consequence as a separately-tracked gap.
- **REFACTOR-340 STRENGTHENED** (the per-entity alert read enumeration vector — same cross-owner read posture extended to alerts). The facet endpoints are a third surface in the same family.
- Doc-side: the live `/features/data-discovery/search` page lists the seven facets but is SILENT on whether facet counts respect any per-user / per-owner / per-tenant scope. The doc-drift is tracked under DOC-NNN follow-up linked from ADR-CANDIDATE-003's enumeration tranche.

**Proposed action**: Promote to `adrs/drafts/catalog-wide-facet-counts.md` (new ADR). Document: (a) the facet counts are catalog-wide by design; (b) `myObjects` is a result-list scope, NOT an aggregate scope; (c) the `total` + `myObjectsTotal` dual-field response shape is the architectural commitment; (d) the trust calculus alignment with ADR-CANDIDATE-003. Doc-side: the live `/features/data-discovery/search` page should explicitly disclose that facet counts reveal catalog cardinality across all owners, so operators understand the cross-owner enumeration consequence. Cross-link REFACTOR-024 (catalog-wide cross-owner reads as a family) and REFACTOR-340 (per-entity alert read enumeration).

**Severity rationale**: MEDIUM — aggregate-layer architectural decision extending ADR-CANDIDATE-003's trust model to facet counts; affects the OpenAPI contract for two endpoints + the UI's facet-sidebar UX + the cross-owner enumeration surface. Not HIGH because the consequence is already captured at the read-collaborative-posture ADR (-003) and the enumeration-vector refactor (REFACTOR-024); this ADR codifies the aggregate-layer-specific design that those entries describe at the system level.
