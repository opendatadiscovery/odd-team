## Description

The Query Examples stored-XSS `danger` hint (`query-examples.md:102-108`) states the mechanism imprecisely. It says a `<script>` tag pasted into the `definition` / `query` field *"round-trips through the API and fires for every authenticated viewer"* and lists *"a `<script>` tag, a `javascript:` href, or any HTML-embedded payload"* as equivalent vectors.

A `<script>` tag listed first as the headline vector is the **wrong** mechanism. The Query Example body is rendered by the platform's `Markdown` component, which uses `MDEditor.Markdown` (react-markdown under the hood) **without** the `rehype-raw` plugin. With no `rehype-raw`, react-markdown does **not** parse raw HTML — a literal `<script>…</script>` in the source is HTML-escaped and rendered as inert text, not executed. So the headline "literal `<script>` fires for every viewer" claim does not hold for this renderer.

The caveat itself (this is a stored-XSS surface) is correct and should stay — but the **live vector** is not a raw `<script>` tag. The concrete vector this renderer exposes is the custom `TermLink` anchor component: for any link whose href does not contain `terms`, it renders a raw `<a href={node.properties?.href}>` with **no URL-scheme check**, so a Markdown link with a `javascript:` href (`[click](javascript:alert(1))`) passes straight through. Image `onerror` / other event-handler vectors are likewise the realistic family, not a bare script tag.

This misleads a security-auditing operator two ways: (1) they may try to reproduce with a literal `<script>` payload, see it render inert, and wrongly conclude the surface is safe (false negative); (2) the remediation framing ("strip HTML / script payloads") points at the wrong layer — the gap is the unchecked `href` scheme in the link renderer, not raw-HTML passthrough.
