## What

`GET /api/dataentities/{data_entity_id}/runs` (the run/test-run history for a DataTransformer or DataQualityTest) accepts an unbounded `size` query parameter. For a valid transformer / quality-test entity id, the value flows unclamped from the controller through the service into the paginated SQL `LIMIT`, so a single request with `size=10000000` is honoured: one jOOQ query plus the full in-memory `DataEntityRunList` mapping, bounded only by Postgres and network buffers. There is no `@Max` on the controller parameter and no `maximum:` on the OpenAPI `SizeParam`, at any layer. (The service does guard the id first - unknown id -> 404, non-transformer/non-QT id -> 400; see ## Where.)

## Where

Controller - `size` is a bare `Integer` with no bound and is passed straight to the service:

```java
// odd-platform-api/.../controller/DataEntityRunController.java:18-26
public Mono<ResponseEntity<DataEntityRunList>> getRuns(final Long dataEntityId,
                                                       final Integer page,
                                                       final Integer size,        // :21 - no @Max / @Min
                                                       final DataEntityRunStatus status,
                                                       final ServerWebExchange exchange) {
    return dataEntityRunService
        .getDataEntityRuns(dataEntityId, status, page, size)                       // :25 - passed through unbounded
        .map(ResponseEntity::ok);
}
```

OpenAPI - the shared `SizeParam` used by this endpoint declares no `maximum:`:

```yaml
# odd-platform-specification/components.yaml:4222-4229
SizeParam:
  name: size
  in: query
  description: Size
  required: true
  schema:
    type: integer
    format: int32        # no minimum: / maximum:
```

(The `/runs` operation `/api/dataentities/{data_entity_id}/runs` references this exact `SizeParam`; the operation is declared at `odd-platform-specification/openapi.yaml:1363`.)

One precondition correction (verified by BE trace 2026-06-10): the value is not *completely* untouched - `DataEntityRunServiceImpl.getDataEntityRuns` (`DataEntityRunServiceImpl.java:32-38`) first does `dataEntityRepository.get(dataEntityId)` (unknown id -> `NotFoundException` -> 404 via the global `@RestControllerAdvice`) and requires the entity to be a `DATA_TRANSFORMER` or `DATA_QUALITY_TEST` (else `BadUserRequestException` -> 400). So the unbounded path requires a *valid* transformer / quality-test entity id; for such ids `size` then flows unclamped into the repository `LIMIT`. There is no ownership check anywhere on this chain, so any caller can target any such entity's history (cross-owner reach confirmed at `ReactiveDataEntityTaskRunRepositoryImpl.java:160-191` - the only predicate is `DATA_ENTITY.ID.eq(...)`).

## User-facing impact

- WHO: any API consumer that can reach `GET /api/dataentities/{id}/runs` for a valid DataTransformer / DataQualityTest id - including an unauthenticated caller under `auth.type=DISABLED` (the common evaluation posture), since `/api/**` is open in that mode.
- WHAT they do: issue one request with a large `size` (e.g. `size=10000000`) against a transformer / quality-test entity whose id they can learn from the catalog (no ownership needed).
- WHAT they observe / what the platform does: a single jOOQ query with an unbounded `LIMIT` plus the full in-memory `DataEntityRunList` mapping - heap pressure and response-size blow-up on the shared API process from one HTTP call. Verified by BE trace 2026-06-10: no `@Max`/`@Min` on the controller param (`DataEntityRunController.java:21`), no `minimum:`/`maximum:` on `SizeParam` (`components.yaml:4222-4229`), no clamp in the service (`DataEntityRunServiceImpl.java:32-38`) or repository before `paginate(..., size)` (`ReactiveDataEntityTaskRunRepositoryImpl.java:176-182`). The end-user UI is NOT the exposure surface (the FE `TestRunsHistory` requests a fixed small page); this is a direct-API / unauthenticated-DISABLED-mode DoS vector. Static trace consistent across all four layers; the heap/latency magnitude itself is the remaining runtime check (not driven here).

Repository sink - `size` becomes the SQL `LIMIT` with no clamp:

```java
// odd-platform-api/.../repository/reactive/ReactiveDataEntityTaskRunRepositoryImpl.java:176-182
final Select<? extends Record> query = jooqQueryHelper.paginate(
    baseQuery,
    DATA_ENTITY_TASK_RUN.END_TIME,
    SortOrder.DESC,
    (page - 1) * size,
    size                 // -> LIMIT; no upper bound
);
```

## Why it matters

This is a single-request denial-of-service vector: any caller (and, under `auth.type=DISABLED`, an unauthenticated one) can request an arbitrarily large page of run history, forcing an unbounded query and an arbitrarily large response body - memory and latency amplification on the platform with one HTTP call. It is amplified by cross-owner read (run history is not owner-scoped), so the attacker need not own the entity whose history they enumerate. Severity high: trivially exploitable, unauthenticated-reachable in a common deployment posture, and the impact (heap pressure / response-size blowup) hits the shared API process.

## Suggested fix

Clamp `size` to a platform-appropriate maximum. Add `@Max(...)` (and `@Min(1)`) to the controller parameter at `DataEntityRunController.java:21`, add `minimum:`/`maximum:` to `SizeParam` in `components.yaml:4222-4229`, and add a defensive clamp in `ReactiveDataEntityTaskRunRepositoryImpl.getDataEntityRuns` before the value reaches `paginate(...)` at `:176-182`. Structurally identical to the alert-read fix (see PLT-134) - open to reusing the same cap value for consistency.

## How discovered

Surfaced by the 2026-06-08 contradiction harvest (`lineage/odd-platform/harvest/2026-06-08-contradiction-harvest.md`, NOVEL-bug HIGH row "F-040 H-005 - per-entity run-history size unbounded"), triaged from feature reflection F-040, hypothesis H-005 (`lineage/odd-platform/feature-reflections/detail/F-040.yaml`).

Corrected 2026-06-10 (user-facing verification sweep): was "the value flows untouched through the controller and service"; actually the service guards the id first (404 for unknown, 400 for non-transformer/non-QT) and `size` flows unclamped only thereafter (`DataEntityRunServiceImpl.java:32-38`). Every citation re-verified against source: controller param unbounded (`DataEntityRunController.java:21`), repo `LIMIT` sink (`ReactiveDataEntityTaskRunRepositoryImpl.java:176-182`), spec `SizeParam` has no `maximum:` (`components.yaml:4222-4229`). No global clamp exists (ControllerAdvice / arg-resolver searched). The defect and high severity stand; user-facing impact section added (direct-API / DISABLED-mode DoS, not a UI surface).

**Relation to PLT-134 (same class, distinct endpoint):** PLT-134 caps the per-entity *alert* read (`GET /api/dataentities/{id}/alerts`). This is the **run-history** endpoint (`GET /api/dataentities/{id}/runs`) - a different controller, service, and repository family that shares the same unbounded-pagination defect but is not covered by PLT-134. The lineage record `SHB-011` (`lineage/odd-platform/shoebox/detail/SHB-011-runs-history-wire-enum-asymmetry.md`) staged the run-history surface but was never promoted to an upstream issue; this is that promotion for the size-cap defect.
