> **Re-audit note (2026-06-17, read-collaborative lens) -- PARTIAL: access-control framing WITHDRAWN, FE-consistency defect KEPT.** `ActivityController` is named read-collaborative in the ADR (`implicit-adrs.md:140`), so "the per-entity Activity read has no permission gate / no ownership join -> any authenticated user reads any entity's audit trail" is the documented posture, NOT a defect -- withdraw that framing. **The real, surviving finding is the soft-delete inconsistency:** Activity is the ONLY status-sensitive tab lacking the `isStatusDeleted` hide-gate that `/history`, `/linked-entities`, `/lineage`, `/discussions`, and `/alerts` all carry (`DataEntityDetailsTabs.tsx:91-94` has no `|| isStatusDeleted`; `DataEntityDetailsRoutes.tsx:105` mounts the route bare). That FE tab-consistency defect (tab stays visible on soft-deleted entities while siblings hide) is independent of the read posture. **Re-scope to the soft-delete tab-gate inconsistency only.**

## What

The per-entity Activity tab (every data-entity detail page) is mounted BARE in `DataEntityDetailsRoutes.tsx:105` - no `RestrictedRoute`, no `WithPermissionsProvider`. Contrast `/alerts` at lines 70-84 which uses BOTH (`RestrictedRoute` on `!isStatusDeleted` + `WithPermissionsProvider`), and `/history` / `/linked-entities` / `/lineage` / `/discussions` which use `RestrictedRoute` on `!isStatusDeleted`. **Among the status-sensitive tabs, Activity is the only one that lacks the `isStatusDeleted` gate** - its tab entry (`DataEntityDetailsTabs.tsx:91-94`) has no `hidden: ... || isStatusDeleted` clause (verified 2026-06-10: every other status-sensitive tab carries `isStatusDeleted` in its `hidden:`; Overview is the only other tab with no `hidden:` at all, but Overview is the safe landing page). So the Activity tab stays visible, and the bare route stays reachable, on soft-deleted entities.

Combined with the backend's cross-owner posture (the per-entity activity read has no ownership join - F-021 + F-014 family), **any authenticated user reads the audit trail for any data entity (including soft-deleted) via the per-entity Activity tab**.

The cross-channel reach is symmetric to F-014's `soft_delete_inclusive_existence_check` facet - audit trail visible while entity is hidden from catalog list endpoints.

## User-facing impact

- WHO: any authenticated user (and, under `auth.type=DISABLED`, effectively anyone) who can construct a data-entity detail URL. No ownership of the target entity is required.
- WHAT they do: navigate to `/dataentities/{id}/activity` (or click the Activity tab, which is always visible) - including for an entity that has been soft-deleted.
- WHAT they observe: the full audit trail (every recorded operator action) for that entity renders. Verified by FE/BE trace 2026-06-10: the route is bare-mounted with no gate (`DataEntityDetailsRoutes.tsx:105`); the tab has no `isStatusDeleted` hidden-clause (`DataEntityDetailsTabs.tsx:91-94`); the detail page renders the tab bar + routes unconditionally (`DataEntityDetails.tsx:104,115` - no deleted-entity early return); the `DataEntityActivity` component itself has no permission wrap (`DataEntityActivity.tsx`); and the backend serves it with no ownership and no soft-delete filter (`ActivityServiceImpl.java:119-136`, `ReactiveActivityRepositoryImpl.java:129-142` - only `DATA_ENTITY.ID.eq(dataEntityId)`). The contrast with the sibling tabs (all `isStatusDeleted`-gated; alerts additionally permission-gated) is the structural giveaway. Static trace fully settles the no-gate / cross-owner / soft-delete-reachable facts; the only data-dependent part is whether the soft-deleted entity's row still resolves in the page header query (the activity endpoint itself does not filter it) - exact behaviour for a UI-soft-deleted entity is the remaining drive (not run here). Whether "any authenticated user" collapses to "anyone" depends on the deployment auth mode (DISABLED vs LDAP).

## Why it matters

The per-entity Activity tab leaks audit history for entities the user has no business reading:

- **Soft-deleted entities** - visible in this tab; hidden from the catalog list endpoints. The intent of soft-delete is "out of sight"; the audit trail stays accessible.
- **Cross-owner entities** - same as the F-021 family: an authenticated user with no ownership of dataset X can navigate to `/dataentities/{xId}/activity` and read every operator action on the dataset.
- **The contrast with sibling tabs** is the giveaway: alerts uses `RestrictedRoute + WithPermissionsProvider`; history/linked-entities use `RestrictedRoute`; Activity uses neither. The pattern looks like an oversight, not an intentional design.

Operator-visible consequence is symmetric to F-014's soft-delete-inclusive existence check: when an entity is "deleted" in the UI, its audit history remains readable via this tab. A compliance audit ("can a user with no ownership read the history of a hidden dataset?") returns yes.

Severity is MEDIUM because:
- The cross-owner reach is the backend's existing posture (REFACTOR-024 family); fixing only the UI tab here doesn't close the underlying gap - but the UI tab's bare mount is a recognisable cosmetic-vs-structural divergence that operators will see.
- The soft-delete dimension is an intentional read-after-hide that may or may not be by design - needs an architectural-intent confirmation from the team.
- Doc-side mitigation (DOC-206) names the posture explicitly so operators are aware until the team decides the right shape.

## Suggested fix

**Two architectural options; the team needs to choose intent before code.**

**Option A - gate the tab with `RestrictedRoute` on `!isStatusDeleted` AND add a `hidden:` clause on `DataEntityDetailsTabs.tsx:91-94`.** Aligns the tab with the sibling tabs' pattern; soft-deleted entities no longer surface their audit history via the UI. The backend stays cross-owner - that's a REFACTOR-024 family decision, not this PLT's scope.

```tsx
// DataEntityDetailsRoutes.tsx:105
<Route path='/activity' element={
  <RestrictedRoute condition={!isStatusDeleted}>
    <DataEntityActivity />
  </RestrictedRoute>
} />

// DataEntityDetailsTabs.tsx:91-94
{ label: t('Activity'), path: 'activity', hidden: isStatusDeleted }
```

**Option B - explicit "audit history matters most on deleted entities - visible by design" framing, both in code and doc.** No code change; instead, formalise the intent as the platform's audit-retention contract. Operators rely on it for compliance reviews where they need post-deletion forensic access. Doc-side mitigation (DOC-206) already names the cross-channel posture; this option closes the loop with explicit architectural intent.

**Option C - RBAC posture decision (REFACTOR-024 family).** The cross-owner reach is the underlying gap; gate the BACKEND `getDataEntityActivity` with an `ENTITY_ACTIVITY_READ` permission + per-entity ownership check. Larger scope; coordinates with the platform-wide RBAC posture work.

Recommendation: **Option A** as the immediate ship; raise Option B vs Option C as the team architectural intent question at the next platform-wide RBAC review.
