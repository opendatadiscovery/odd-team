# ReactiveCollectorRepositoryImpl — semantic understanding

## understanding

The persistence-layer bean owning every read and write to the `collector` table — the table that pairs a Collector identity (name, namespace, oddrn) with its TOKEN row via `collector.token_id`, and whose `getByToken(String)` method is the SQL bridge query that resolves an inbound `Authorization: Bearer <plaintext>` header to a Collector. The file is a 127-line shell (`ReactiveCollectorRepositoryImpl.java:31-127`) layering exactly four collector-specific methods over the inherited `ReactiveAbstractSoftDeleteCRUDRepository` CRUD: `getDto(id)` and `listDto(page, size, nameQuery)` which LEFT JOIN `namespace` + `token` and project a `CollectorDto`, `getByToken(token)` which JOINs `TOKEN` and filters `addSoftDeleteFilter(TOKEN.VALUE.eq(token))`, and `existsByNamespace(namespaceId)` for cascade-delete prevention. Standard CRUD (`create / update / get / list / delete / bulkCreate / bulkUpdate`) is entirely inherited from the soft-delete base — `delete(id)` is an UPDATE setting `deleted_at = NOW()`, never a row deletion, and the canonical reads are auto-scoped to `WHERE deleted_at IS NULL` (`ReactiveAbstractSoftDeleteCRUDRepository.java:50-89`). The repository carries NO timing-attack defence, NO token hashing, NO uniqueness check on `TOKEN.value`, and NO transactional gating on the `getByToken → COLLECTOR_ID_SESSION_KEY` bridge query that `IngestionDataSourceFilter` (always-on) and `IngestionDataEntitiesFilter` (opt-in via `auth.ingestion.filter.enabled`) both consume.

## concepts

- entities: [CollectorPojo (jOOQ-generated row record — id, name, oddrn, description, namespace_id, token_id, is_deleted, deleted_at, created_at, updated_at), CollectorRecord (typed jOOQ record), COLLECTOR (jOOQ Tables constant referring to the `collector` table), TOKEN (jOOQ Tables constant — joined to project the collector's credential row), NAMESPACE (jOOQ Tables constant — joined for the dto label), TokenPojo (the joined value, value field is the 40-char plaintext credential per V0_0_28:1-9), TokenDto (TokenPojo + boolean showToken — the wrapper deciding whether the controller-layer mapper masks via `******{last6}` or returns full plaintext), CollectorDto (CollectorPojo + NamespacePojo + TokenDto — the triple projected by mapRecordToDto), `collector_cte` (the CTE alias used by listDto to paginate before joining), Page<CollectorDto> (paginated wrapper for listDto), `collector_token_unique` (the partial unique index on collector(token_id) per V0_0_33:1)]
- operations:
  - "getDto(id): `SELECT collector.* + namespace.* + token.* FROM collector LEFT JOIN namespace ON namespace.id = collector.namespace_id LEFT JOIN token ON token.id = collector.token_id WHERE collector.id = ? AND collector.deleted_at IS NULL` — returns Mono<CollectorDto> with the joined NamespacePojo + TokenPojo (note: TOKEN row is fetched unmasked at the SQL layer; masking is a service-layer concern via TokenDto.showToken)"
  - "listDto(page, size, nameQuery): CTE-paginated — first selects `collector_cte` filtered by inherited `listCondition(nameQuery)` (which the soft-delete base overrides at `ReactiveAbstractSoftDeleteCRUDRepository.java:87-89` to append `deleted_at IS NULL`) and paginated by `OrderByField(COLLECTOR.ID, ASC)` with `(page-1)*size, size`, then LEFT JOINs `namespace` and `token` and maps to Mono<Page<CollectorDto>>; same CTE-then-join shape as ReactiveRoleRepositoryImpl"
  - "getByToken(token): `SELECT collector.* FROM collector JOIN token ON token.id = collector.token_id WHERE token.value = ? AND collector.deleted_at IS NULL` — Mono<CollectorPojo> returning ONLY the collector pojo (no joined namespace/token); soft-delete filter applies to COLLECTOR, NOT to TOKEN; plaintext equality match against TOKEN.VALUE via `TOKEN.VALUE.eq(token)` at line 94 with NO `MessageDigest.isEqual` / constant-time comparison"
  - "existsByNamespace(namespaceId): `SELECT EXISTS(SELECT 1 FROM collector WHERE namespace_id = ? AND deleted_at IS NULL)` — Mono<Boolean> used by NamespaceServiceImpl to prevent cascade-delete of namespaces with live collector references"
  - "inherited create (INSERT INTO collector(name, oddrn, description, namespace_id, token_id, is_deleted, deleted_at, created_at, updated_at) VALUES ... RETURNING ALL — ReactiveAbstractCRUDRepository.java:103-105; no @ReactiveTransactional)"
  - "inherited update (UPDATE collector SET ... WHERE id = ? AND deleted_at IS NULL RETURNING ALL — ReactiveAbstractCRUDRepository.java:107-110 + ReactiveAbstractSoftDeleteCRUDRepository.java:77-79; non-updatable fields suppressed via getNonUpdatableFields override appending `deleted_at`)"
  - "inherited get (SELECT * FROM collector WHERE id = ? AND deleted_at IS NULL — ReactiveAbstractCRUDRepository.java:69-74 + soft-delete-base override; called nowhere in production but exists as the contract)"
  - "inherited delete (UPDATE collector SET deleted_at = NOW() WHERE id = ? AND deleted_at IS NULL RETURNING ALL — soft-delete via ReactiveAbstractSoftDeleteCRUDRepository.java:50-58); CollectorServiceImpl.delete first calls `dataSourceRepository.existsByCollector(id)` to prevent cascade-delete (CollectorServiceImpl.java:73-79)"
  - "inherited list / bulkCreate / bulkUpdate (@ReactiveTransactional only on bulk variants — ReactiveAbstractCRUDRepository.java:113, 129)"
- invariants:
  - "Every CRUD read AND the inherited delete are auto-scoped to `deleted_at IS NULL` by ReactiveAbstractSoftDeleteCRUDRepository.addSoftDeleteFilter (ReactiveAbstractSoftDeleteCRUDRepository.java:96-104). Custom `getDto` (line 54), `listDto` (line 62 via base override), and `getByToken` (line 94) ALSO apply the soft-delete filter on COLLECTOR. Soft-deleted collectors are invisible to every defined read path; `getByToken` of a soft-deleted collector's still-live TOKEN returns Mono.empty() → `AccessDeniedException` at the filter layer."
  - "The TOKEN join in `getDto` / `listDto` (lines 49-52, 73-77) and `getByToken` (line 93) has NO `token.deleted_at IS NULL` predicate. The TOKEN table has no soft-delete column (V0_0_28__add_token.sql:1-9 — only `id, value, created_at, created_by, updated_at, updated_by`); the soft-delete semantic lives on COLLECTOR alone. This is consistent — TOKENs live and die with their COLLECTOR via the FK at collector.token_id — but means there's no audit trail of historical TOKEN.value rows; `regenerateToken` MUTATES the row (`UPDATE token SET value = ?` per ReactiveTokenRepositoryImpl.java:33-36), losing the prior secret without history."
  - "TOKEN.value is stored in the SQL plaintext (V0_0_28:4 — `value varchar(40) NOT NULL`); the application-layer write path (TokenGeneratorImpl.java:34-42) sets `RandomStringUtils.randomAlphanumeric(40)` verbatim with no hashing, no salt, no `BCryptPasswordEncoder.encode`, no any-other-digest. Consequently `getByToken(token)` performs a PLAINTEXT EQUALITY match — `TOKEN.VALUE.eq(token)` at line 94 — which translates to `WHERE token.value = $1` at the R2DBC layer. A read of the `token` table by a DB-side actor (replica, backup, pg_dump operator, jOOQ-log-leak, application-log-leak) exposes the live credential in the clear. The application layer adds NO defence."
  - "`TOKEN.value` has NO UNIQUE constraint at the SQL layer. The only uniqueness anywhere in the token-collector relationship is the partial unique index `collector_token_unique ON collector(token_id) WHERE deleted_at IS NULL` (V0_0_33__add_token_constraints.sql:1) — i.e. one TOKEN row may NOT be bound to two LIVE collectors. But two TOKEN rows MAY share the same `value` (a collision from RandomStringUtils.randomAlphanumeric(40) is astronomically improbable, but no schema-level defence prevents it; no application-level check either). If `getByToken(t)` ever sees two rows matching `TOKEN.VALUE.eq(t)`, the jOOQ `mono(query)` returns the FIRST row's matched COLLECTOR with no determinism guarantee (no ORDER BY on the query at lines 90-94). The COLLECTOR_ID_SESSION_KEY then becomes ambiguous; cross-collector data-source registration is silently possible. Cross-reference: batch-P IngestionController.createDataSourceEntity:240 — same finding."
  - "`getByToken` returns ONLY a CollectorPojo (not a CollectorDto with the joined TokenDto). The filter layer (`IngestionDataSourceFilter.java:33`) needs only the Collector's id to set `COLLECTOR_ID_SESSION_KEY`; `IngestionDataEntitiesFilter` (which DOES need the token to do plaintext-equality validation) reaches `collectorRepository.getDto(dto.dataSource().getCollectorId())` for the token round-trip (`IngestionDataEntitiesFilter.java:49-52`). The two consumer paths therefore have asymmetric SQL costs and asymmetric exposure surfaces; the SQL bridge for the data-source-registration flow is `getByToken` (no token-cross-check) and the SQL bridge for the data-entity-ingestion flow is `getDtoByOddrn → getDto → tokenPojo.getValue().equals(token)` (token cross-check with .equals)."
  - "Single-statement INSERT / UPDATE on inherited `create` / `update` (ReactiveAbstractCRUDRepository.java:103-110) — NO @ReactiveTransactional on these inherited methods. Only `bulkCreate` / `bulkUpdate` are transactional (lines 113, 129). The Collector create / update / delete paths therefore commit per-statement; the service layer (CollectorServiceImpl.java:38-48, 50-69, 71-80) wraps create/update/delete in `@ReactiveTransactional` to make the TOKEN INSERT + COLLECTOR INSERT atomic (CollectorServiceImpl.java:39 `tokenGenerator.generateToken().flatMap(tokenRepository::create)` + line 47 `createCollector`). A service-bypassing caller would lose atomicity: a TOKEN row could be inserted with no COLLECTOR row, leaving an orphaned token in the table forever (the TOKEN table has no cleanup query / housekeeping job; V0_0_28:1-9 confirms — no janitor)."
  - "`regenerateToken` does NOT pass through THIS repository on the write path — it pulls a CollectorDto via `collectorRepository.getDto(collectorId)` for the existing token, hands the TokenPojo to `tokenGenerator.regenerateToken` (which mutates `TokenPojo.value` to a fresh 40-char string), then routes the persistence through `tokenRepository.updateToken` (CollectorServiceImpl.java:82-90). The COLLECTOR row is NOT touched; only the TOKEN row's `value` and `updated_at` are. This means a token rotation is invisible to the COLLECTOR table's `updated_at` — investigators forensically reconstructing 'when did this collector's credential last rotate' must read from TOKEN, not COLLECTOR."
- audiences: [CollectorServiceImpl (sole catalog-side caller for collectorRepository.listDto/getDto/delete/regenerateToken — CollectorServiceImpl.java:34/53/77/84), IngestionDataSourceFilter (the always-on filter on `POST /ingestion/datasources` — calls `collectorRepository.getByToken(token)` at IngestionDataSourceFilter.java:33 to resolve a Bearer token to a Collector id and bridge it into `COLLECTOR_ID_SESSION_KEY`), IngestionDataEntitiesFilter (the opt-in filter on `POST /ingestion/entities` gated by `auth.ingestion.filter.enabled` — calls `collectorRepository.getDto(collectorId)` at IngestionDataEntitiesFilter.java:49 to fetch the token for plaintext `.equals` comparison), CollectorController (HTTP surface for the entire CRUD via CollectorServiceImpl), NamespaceServiceImpl (transitive — for existsByNamespace cascade-delete prevention), database operators investigating the `collector` and `token` tables directly]

- "**TOKEN.value plaintext-at-rest with no UNIQUE constraint, no hashing, no timing-attack-safe equality.** The SQL-tier substrate of the bearer-token authentication shipped to the always-on `IngestionDataSourceFilter` and the opt-in `IngestionDataEntitiesFilter`.
