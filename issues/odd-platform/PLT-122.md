## What

When a brand-new user authenticates for the first time under OAUTH2 or LDAP, no `USER_OWNER_MAPPING` row is auto-created - the `OwnerAssociationRequest` request-and-approval round-trip is mandatory. `fetchAssociatedOwner` emits an **empty Mono** (no `switchIfEmpty`, `AuthIdentityProviderImpl.java:50-53`), so every owner-scoped consumer (My Objects, My Alerts, the MY_OBJECTS activity view, my discussions) degrades to **empty results with HTTP 200** - not 401/403/404.

**However, the in-product onboarding affordance is NOT absent** (corrected 2026-06-10 - the original "silently-empty platform, no affordance, user concludes it is broken" premise is falsified). The default landing route `/` is the Overview page (`App.tsx:60`), which renders the `OwnerAssociation` card whenever `auth.type != DISABLED` (`Overview.tsx:25-27,53-59`), and that card auto-shows the `OwnerAssociationForm` for any authenticated user that has an identity but no ownership (`OwnerAssociation.tsx:33-41`). `WithPermissionsProvider` is a context provider, not a render gate (`WithPermissionsProvider.tsx`), so the card renders regardless of the user's permissions. So a new SSO/LDAP user lands on a home page that directly prompts them to request owner association.

The residual gap is narrow: the empty *personalised* surfaces themselves (My Objects, My Alerts, MY_OBJECTS activity) carry no empty-state explanation or link back to that flow - a user who navigates straight to one of those tabs sees an unexplained empty list. This is **net_new** but low-severity after correction; the onboarding prompt already exists on Overview, so the ask is an empty-state hint on the personalised tabs that points to it. (The cross-mode association-migration angle is DOC-312.)

## User-facing impact

WHO: a brand-new OAUTH2/LDAP user with no owner mapping yet. WHAT THEY GET (verified by FE/BE trace 2026-06-10):

- **On the home page (`/` = Overview) they ARE prompted to associate an owner.** The `OwnerAssociationForm` auto-renders for an identity-without-ownership user when `auth.type != DISABLED` (`Overview.tsx:25-27,53-59` -> `OwnerAssociation.tsx:33-41`). So the original "no in-product explanation, user concludes the platform is broken" claim does not hold for the landing page. Verified by FE trace.
- **On the personalised surfaces (My Objects, My Alerts, MY_OBJECTS activity, discussions) the owner-scoped reads return empty + HTTP 200** (`fetchAssociatedOwner` empty -> caller `switchIfEmpty`, e.g. `SearchServiceImpl.getSearchResults:105-109`, `getFacetsData` myObjectsCount `:128-130`), and those surfaces carry no empty-state hint linking back to the association flow. A user who navigates straight to one of those tabs sees an unexplained empty list. This residual is the real, low-severity item. Verified by FE/BE trace.

The not-driven part is only the subjective "is the Overview prompt prominent enough that a new user notices it before wandering to an empty tab" - that would need a live drive, so `user_facing_verified` stays false.

## Suggested fix

Re-scoped after the 2026-06-10 correction: the Overview home page already prompts ownerless users to request association, so the gap is only on the empty personalised tabs. Minimum-viable: add an empty-state hint on the owner-scoped surfaces (My Objects, My Alerts, MY_OBJECTS activity) - when the list is empty and the current user has no owner mapping - that links to the existing `OwnerAssociation` request flow on Overview. Optionally emit a first-login WARN log at the `fetchAssociatedOwner` empty point (`AuthIdentityProviderImpl.java:50-53`). The doc-side first-login association step is a separate doc-gap (authentication page).
