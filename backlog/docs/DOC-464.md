## Description

The `enable-security/README.md` ingestion-whitelist discussion twice notes that under `auth.type=LOGIN_FORM` the uncovered `/ingestion/*` sibling paths are **session-gated** by the catch-all `.pathMatchers("/**").authenticated()` rule (unlike DISABLED/OAUTH2/LDAP, where the `/ingestion/**` whitelist glob makes them anonymously reachable) — and then **dismisses** that distinction with "but [LOGIN_FORM is documented as dev-only](authentication/login-form.md), so this distinction does not change the operational guidance below."

That dismissal rests on a premise the login-form page itself does not assert as a constraint. `login-form.md` frames dev-only as a **recommendation** ("not suitable for production deployments", "prefer OAUTH2 or LDAP", "dev/demo-oriented") — strong guidance, but operators **do** run LOGIN_FORM in production (it is a supported `auth.type`). For an operator who has chosen LOGIN_FORM, the session-gating distinction is *exactly* their operational reality and is favourable to them (the sibling ingestion paths are NOT anonymously reachable in their mode) — yet the README waves it away as not applicable. The reader who most needs the LOGIN_FORM behaviour stated is told it "does not change the guidance," which is both dismissive and, for that operator, the opposite of helpful.

This is a reader-flow / cross-audience defect: the README's all-mode security framing implicitly excludes the LOGIN_FORM operator from the one place their mode behaves differently, justified by a dev-only label the linked page presents as advice rather than a hard exclusion.

## Acceptance Criteria

- [ ] `README.md` (both the table cell ~`:24` and the bulleted prose ~`:56`) stops using "LOGIN_FORM is dev-only, so this distinction does not change the operational guidance" as the reason to skip the LOGIN_FORM case. Instead, state the behaviour plainly for LOGIN_FORM operators: under LOGIN_FORM the uncovered `/ingestion/*` sibling paths are session-gated (anonymous callers are redirected to `/login`), which also means collectors / push-clients that carry no UI session are blocked — so LOGIN_FORM is rarely the right mode for production *ingestion*, but the security posture of those paths is session-gated rather than anonymously reachable.
- [ ] The wording acknowledges LOGIN_FORM is a recommendation-against (not a hard constraint) for production, consistent with how `login-form.md` actually frames it — do not assert LOGIN_FORM "cannot" run in production.
- [ ] The two locations are reconciled to say the same thing (no residual "does not change the guidance" dismissal on either).
- [ ] Operator language only — no workspace IDs on the published page (Gate 11).
- [ ] Live-site verified post-merge: WebFetch `https://docs.opendatadiscovery.org/configuration-and-deployment/enable-security` and confirm the revised LOGIN_FORM framing renders.

## Context

Surfaced by the 2026-06-16 editorial audit of `enable-security/` during the CTRIB-018 review.

**Failure shape:** reader-flow defect — the page dismisses a load-bearing per-mode distinction by appeal to a "dev-only" status that the cited page frames as a recommendation, not a constraint, leaving the LOGIN_FORM operator's actual behaviour unstated.

**Verbatim passage** — `README.md` table cell (~`:24`):
> Under `auth.type=LOGIN_FORM`, sibling paths are instead **session-gated** by the catch-all `pathMatchers("/**").authenticated()` rule — but [LOGIN_FORM is documented as dev-only](authentication/login-form.md), so this distinction does not change the operational guidance below.

The later prose (~`:56`) does state the LOGIN_FORM session-gating cleanly ("the catch-all `.pathMatchers("/**").authenticated()` rule session-gates the siblings — an anonymous caller is redirected to `/login`. This blocks collectors and push-clients that do not carry a UI session, so LOGIN_FORM is rarely the right mode for production ingestion regardless.") — so the body already has the right framing; it is the **table cell's dismissal** that is the defect and should be brought in line with the prose.

**Counter-evidence on the "dev-only = constraint" premise** — `login-form.md:14,36,42`:
- `:14` — "For any production deployment, prefer OAUTH2 or LDAP" (a preference).
- `:36` — "`LOGIN_FORM` is dev/demo-oriented authentication." (a characterisation).
- The page never says LOGIN_FORM is disabled / blocked / unsupported in production — it is a supported `auth.type` with strong advice against it.

**Recommended fix:** drop the "so this distinction does not change the operational guidance" clause from the table cell; replace with the same session-gated framing the body prose at `:56` already uses (siblings are session-gated under LOGIN_FORM → anonymous callers redirected, collectors without a UI session blocked). This serves the LOGIN_FORM operator instead of waving them off.
