## What

`PUT /api/dataentities/{data_entity_id}/tags` is named `createDataEntityTagsRelations` and is summarised in the spec as "Creates tags relations for DataEntity entity" - language that reads as **additive** (add the tags I send, keep the rest). The implementation is **replace-all** for a data entity's internal tags: the request body carries the *complete* desired tag-name list, the service diffs it against the current internal-tag relations and **deletes every internal tag not present in the request**. A third-party API consumer who reads the spec and sends `{"tag_name_list": ["new-tag"]}` expecting to add one tag will silently delete every other internal tag on that data entity. The platform UI is shielded - it always submits the full current set plus/minus the edit, and its Redux action is even named `updateDataEntityTagsActionType` - so only direct API consumers reading the OpenAPI contract hit the trap.

## Where

Spec - `odd-platform-specification/openapi.yaml:1171-1192` (the create-language summary/description + `operationId`):

```yaml
  /api/dataentities/{data_entity_id}/tags:
    put:
      summary: Creates tags relations for DataEntity entity
      description: Creates tags relations tags for DataEntity entity. Also creates corresponding tags in the system if they don't exist.
      operationId: createDataEntityTagsRelations
```

Controller - `odd-platform-api/.../controller/DataEntityController.java:243-253` (method also named `create*`, delegates to `upsertTags`):

```java
    public Mono<ResponseEntity<Flux<Tag>>> createDataEntityTagsRelations(
        final Long dataEntityId,
        final Mono<TagsFormData> tagsFormData,
        final ServerWebExchange exchange
    ) {
        final Flux<Tag> tags = tagsFormData
            .flatMapMany(form -> dataEntityService.upsertTags(dataEntityId, form));
        return Mono.just(ResponseEntity.ok(tags));
    }
```

The replace-all logic - `odd-platform-api/.../service/TagServiceImpl.java:96-121` (diff against current relations, then delete the ones not in the new list):

```java
    public Mono<List<TagDto>> updateRelationsWithDataEntity(final long dataEntityId,
                                                            final Set<String> tagNames) {
        final Mono<List<TagToDataEntityPojo>> currentRelations = reactiveTagRepository
            .listTagRelations(List.of(dataEntityId))
            .filter(pojo -> !pojo.getExternal())
            .collectList();
        ...
        return Mono.zip(currentRelations, updatedRelations)
            .flatMap(function((current, updated) -> {
                final List<TagToDataEntityPojo> pojosToDelete = current.stream()
                    .filter(r -> !updated.contains(r))
                    .toList();
                return reactiveTagRepository.deleteDataEntityRelations(pojosToDelete)
                    .thenMany(reactiveTagRepository.createDataEntityRelations(updated))
                    .then(reactiveTagRepository.listDataEntityDtos(dataEntityId));
            }));
    }
```

(`DataEntityServiceImpl.upsertTags` at `DataEntityServiceImpl.java:356-376` is the thin wrapper between the controller and this worker.) Note the `.filter(pojo -> !pojo.getExternal())` - external/ingested tags are excluded from the diff and survive, so the replace-all applies to **internal** tags only.

## User-facing impact

Verified end-to-end on both ends:

- **In-app UI users are shielded - confirmed by reading the FE submit path, not assumed.** `odd-platform-ui/.../OverviewTags/TagsEditForm/TagsEditForm.tsx` opens the edit dialog by pre-loading the form's `tagNameList` with the **entire current tag set** (`onOpen`, `:42-51`, mapping every `dataEntityTags` entry including external/important flags) and submits the **full edited list** (`handleSubmit`, `:57-68`: `compact([...data.tagNameList.map(tag => tag.name)])`). The user adds/removes chips in place; the request always carries the complete desired set, so the replace-all diff is a no-op against unedited tags. The Redux action is named `updateDataEntityTags` / `updateDataEntityTagsActionType` (`redux/actions/dataentity.actions.ts:15-17`, `redux/thunks/dataentities.thunks.ts:44-48`) - i.e. the FE already models this as "update/replace," matching the behaviour.
- **Direct API consumers are not shielded.** A third party reading the OpenAPI contract sees `operationId: createDataEntityTagsRelations` + summary "Creates tags relations for DataEntity entity" (`openapi.yaml:1171-1192`) - additive language - and sends `{"tag_name_list": ["new-tag"]}` to add one tag. The service silently deletes every *other internal* tag on that entity (external/ingested tags survive the `!getExternal()` filter). The call returns 200 with the new set and no warning. Anyone holding `DATA_ENTITY_TAGS_UPDATE` triggers it; under `auth.type=DISABLED` (default: `permitAll` + synthetic admin) it is anonymous.

So the user-visible blast radius is confined to direct API consumers - silent, destructive tag loss driven by a verb that says the opposite of what it does. No UI surface exhibits it.

## Why it matters

The failure is **silent and destructive**: the call returns 200 with the new tag set, no warning that other tags were removed; the consumer only discovers the loss when something downstream is missing a tag. An ingestion or sync job by a third-party integrator that calls this endpoint per-entity with a partial list would steadily strip internal tag history across the catalog. Anyone holding `DATA_ENTITY_TAGS_UPDATE` on the entity can trigger it; under `auth.type=DISABLED` it is anonymous. It is not a security hole (the caller is authorised to edit tags) and the UI is immune, so severity is medium - but for a direct API consumer it is data loss with no signal, driven entirely by a contract whose verb says the opposite of what it does.

## Suggested fix

Two acceptable resolutions; pick one and make the spec, the `operationId`, and the controller method name agree with it:

1. **Make it additive** - add the requested tags to the existing internal set without deleting unlisted ones, and introduce a separate `DELETE /api/dataentities/{id}/tags/{tag_id}` (or a `replace` query flag) for removal. This matches the create-language and is the least surprising for API consumers.
2. **Keep replace-all but rename + document** - rename to `updateDataEntityTagsRelations` (matching the UI's own `updateDataEntityTagsActionType`), change the summary to "Replaces the internal tag set for a DataEntity," and document explicitly in the description that (a) unlisted internal tags are removed, (b) an empty `tag_name_list` clears all internal tags, and (c) external/ingested tags are preserved.

(Open to alternatives - but the spec verb and the behaviour must not continue to contradict each other.)
