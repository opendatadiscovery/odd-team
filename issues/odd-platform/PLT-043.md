## What

The live docs at `docs.opendatadiscovery.org/configuration-and-deployment/odd-platform` now warn that `auth.ingestion.filter.enabled` only guards `POST /ingestion/entities` and does not cover the other ingestion paths. **But the property declaration in `application.yml` has no in-line comment naming the narrow scope.** Operators auditing YAML files in isolation (a common pattern for security audits - offline, in a config-merge tool, in a CI-time review of Helm overrides) cannot reconstruct the narrow scope without leaving the file.

This is a follow-up to DOC-228 (the doc-side fix that ships the deployment matrix on `enable-security/README.md`) - operators who don't read the docs but DO read the YAML still need the warning at the YAML surface.

## Where

```
odd-platform-api/src/main/resources/application.yml:46-48   (nested under `auth:` -> full key auth.ingestion.filter.enabled)
  auth:
    ...
    ingestion:
      filter:
        enabled: false
```

The scope claim, verified 2026-06-10 against the filter classes (corrects the original draft's invented sibling list):

- `auth.ingestion.filter.enabled` is the `@ConditionalOnProperty(value = "auth.ingestion.filter.enabled", havingValue = "true")` guard on exactly ONE filter - `IngestionDataEntitiesFilter` (`auth/filter/IngestionDataEntitiesFilter.java:20`), which matches exactly `POST /ingestion/entities` (`:28`). When the property is `false` (the default) that filter bean is never created, so `POST /ingestion/entities` is unauthenticated.
- `POST /ingestion/datasources` has its OWN always-on filter, `IngestionDataSourceFilter` (`auth/filter/IngestionDataSourceFilter.java:16,20`) - a plain `@Component` with no `@ConditionalOnProperty`, so it is NOT controlled by this key.
- The remaining ingestion POST paths have NO ingestion-token filter at all: `POST /ingestion/alert/alertmanager`, `POST /ingestion/entities/datasets/stats`, `POST /ingestion/metrics` (paths confirmed by grep over the ingestion controllers/spec).

So the original draft's parenthetical sibling list was partly wrong: `entities/degs/children` is not an ingestion path; `/ingestion/datasources` is covered by a separate always-on filter, not left uncovered. The corrected list is below.

## Why

Same shape as LSN-001 - the operator-visible knob (the YAML key) and what the system actually does are not the same. An operator reading `auth.ingestion.filter.enabled: false` reasonably interprets it as "the ingestion-auth filter is off"; the actual semantic is "the token filter that protects ONLY `POST /ingestion/entities` is off - other ingestion POST paths are either covered by a different always-on filter (`/ingestion/datasources`) or not token-filtered at all." Without an in-line comment, the YAML name is the only signal - and the name reads as wider-than-the-implementation.

YAML caveats matter because YAML audits happen at sites where the doc site is not reachable (offline Helm-merge tools, CI pipelines, security-audit terminals on isolated networks). The doc-side warning is necessary; the YAML-side comment is sufficient for the audience that cannot reach the docs.

## How

One-line addition (wording load-bearing on the endpoint scope + the doc URL):

```yaml
auth:
  ...
  ingestion:
    filter:
      # Scope: this flag toggles token-auth for ONLY `POST /ingestion/entities`
      # (IngestionDataEntitiesFilter). `POST /ingestion/datasources` has a separate
      # always-on filter; `POST /ingestion/alert/alertmanager`, `/ingestion/entities/datasets/stats`,
      # and `/ingestion/metrics` are NOT token-filtered. See
      # docs.opendatadiscovery.org/configuration-and-deployment/enable-security for the per-endpoint matrix.
      enabled: false
```

(Wording can be tightened; the load-bearing pieces are the explicit `POST /ingestion/entities` scope, the note that other paths differ, and the doc URL pointer.)

## User-facing impact

Operator-facing config-comprehension gap (not an end-user UI surface). Verified 2026-06-10 by reading both ingestion filters and enumerating the ingestion POST paths: the YAML key `auth.ingestion.filter.enabled` genuinely controls only `IngestionDataEntitiesFilter` / `POST /ingestion/entities`, while three other ingestion POST paths are unfiltered and one (`/ingestion/datasources`) has an independent always-on filter - none of which is discoverable from the bare YAML key. An operator hardening ingestion from the YAML alone would reasonably believe flipping this one key secures "ingestion," which it does not. The inline comment is the fix for the YAML-only audience; this is a doc/comment adjustment with zero runtime change (the binder ignores comments). Severity MEDIUM stands - the gap is real and security-relevant, but it is a comprehension/documentation gap, not a code defect.

## Paired doc-side fix

**DOC-228** ships the per-endpoint deployment matrix on `enable-security/README.md` (the 80-cell-or-narrower table that operators auditing the YAML can be pointed at). DOC-228 lands the audience-on-the-doc-side surface; PLT-043 lands the audience-on-the-YAML-side surface.

## Tests

- Build-time check: the application.yml comment renders correctly via Spring Boot's relaxed config-binding (comments are ignored by the binder; this is a doc-string-only addition with no runtime effect).
- Regression check: no behavioural change. The filter still defaults to `false`; the YAML key still maps to `IngestionDataEntitiesFilter`'s `@ConditionalOnProperty`.
