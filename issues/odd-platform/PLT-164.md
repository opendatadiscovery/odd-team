## What

When a user assigns ownership and types a title (role) that does not yet exist, the platform silently mints a permanent, platform-wide row in the Title directory - with **no permission check, no allow-list, no length/charset bound, and no audit record of the mint**. Every other comparable vocabulary-minting surface in the product (Owner, Term, Namespace, Tag) is gated by a dedicated `*_CREATE` permission; Title alone is not - there is no `TITLE_CREATE` permission anywhere in the API contract or the code. Anyone who can attach an owner (to a data entity *or* to a term) can extend the shared Title vocabulary one free-form string at a time.

The Title (role) directory is **descriptive ownership-role vocabulary** -- the role label shown next to an owner (e.g. "Steward"), used in ownership display, search vectors, and alert/Slack notifications. The original draft called it "authorization-relevant ... the same `title` directory that filters reads elsewhere"; that is **not** supported by the code -- `title` / `title_id` does not appear in the `auth` or `permission` packages and is not an authorization input. So this is a governance/vocabulary-hygiene access-control gap, not a security-adjacent one.

## Where

`odd-platform-api/.../service/TitleServiceImpl.java:18-22` - `getOrCreate` inserts on miss with no authorization at all:

```java
@Override
public Mono<TitlePojo> getOrCreate(final String name) {
    return titleRepository.getByName(name)
        .switchIfEmpty(titleRepository.create(new TitlePojo().setName(name)));  // mint on miss, no perm check
}
```

Reached from the ownership-create flow, which calls it with the free-form `titleName` straight off the form:

```java
// odd-platform-api/.../service/OwnershipServiceImpl.java:52-53
return Mono.zip(ownerService.getOrCreate(formData.getOwnerName()),
        titleService.getOrCreate(formData.getTitleName()))   // :53 - caller, free-form title from form
```

`OwnershipServiceImpl.update` (`:106`) calls the same `getOrCreate` on the data-entity update path. The **term**-ownership path mints the same way -- `TermOwnershipServiceImpl.create` (`:36`) and `.update` (`:63`) also call `titleService.getOrCreate(formData.getTitleName())` with the free-form title. The `Permission` enum that gates every other directory mint defines `OWNER_CREATE`, `TERM_CREATE`, `NAMESPACE_CREATE`, `TAG_CREATE` (`odd-platform-specification/components.yaml:203-224`) but contains **no `TITLE_CREATE`** - a project-wide grep for `TITLE_CREATE` returns nothing.

The ownership create/update methods carry `@ActivityLog(OWNERSHIP_CREATED/UPDATED)` (`OwnershipServiceImpl.java:48,100`), but that audits the *ownership* event, not the *title mint* -- the new Title row carries no record of who created it or when. There is no `*_CREATED` activity event type for Title (`ActivityEventTypeDto` has no Title entry).

## User-facing impact

- **Unauthorized mint -- verified by BE trace 2026-06-10.** `TitleServiceImpl.getOrCreate` (`:18-22`) inserts on miss with no authorization. It is reached from four free-form-title call sites with no `TITLE_CREATE` gate: data-entity ownership create (`OwnershipServiceImpl.java:53`) and update (`:106`), and term ownership create (`TermOwnershipServiceImpl.java:36`) and update (`:63`). The data-entity ownership endpoints are gated by `DATA_ENTITY_OWNERSHIP_CREATE/UPDATE` and the term ones by `TERM_OWNERSHIP_CREATE/UPDATE` (`SecurityConstants.java`), but **none** of those is a Title-mint permission -- a user with ordinary ownership-assign rights mints platform-wide Title rows as a side effect. Under `auth.type=DISABLED` the gate is permitAll, so an unauthenticated caller can do it.
- **Unbounded + unaudited -- verified by BE trace 2026-06-10.** No length/charset bound on `titleName` (no `@Size`/`@Pattern` on the form field; `getOrCreate` takes the raw string), de-duplication is exact-name only (`Steward`, `steward`, `' steward '` are distinct permanent rows), and the mint emits no audit event (no Title `*_CREATED` in `ActivityEventTypeDto`; the `@ActivityLog` on the ownership method records the ownership change, not the title creation).
- **NOT authorization-relevant -- corrected 2026-06-10.** The original "Title filters reads / is authorization-relevant shared vocabulary" is not borne out by the code: `title`/`title_id` is consumed only by ownership display, search-vector building, and notification formatting (`Reactive*OwnershipRepositoryImpl`, `ReactiveSearchEntrypointRepositoryImpl.java:410`, `SlackMessageGenerator.java:205`), never by the `auth`/`permission` layer. It is a descriptive role label, not an access-control input.

Not driven against a live server; the mint path and the absence of `TITLE_CREATE`/bounds/audit are fully code-settled from the cites above.

## Why it matters

This is a governance / vocabulary-hygiene access-control gap. Anyone who can attach an owner (to a data entity or a term -- a common, low-privilege action) can permanently grow the platform-wide Title vocabulary one free-form string at a time, with no audit trail and no bound, and Title is the **one** minting surface that escaped the `*_CREATE` permission convention every sibling (Owner / Term / Namespace / Tag) follows. The directory becomes a pollution surface (near-duplicate rows) and the mint is unattributable. It is **not** a security/confidentiality defect -- Title is a descriptive role label, not an authorization input -- so the original "security-adjacent" framing is dropped.

Severity **medium** (was high): a real missing access control + missing audit on a shared persistent directory, consistent with its siblings being permission-gated, but the impact is governance/hygiene and minor privilege creep, not confidentiality or integrity of protected data. (The high rating assumed authorization-relevance that the code does not support.)

## Suggested fix

Bring Title in line with the other directory-minting surfaces: add a `TITLE_CREATE` permission to the `Permission` enum and enforce it on the title-mint path -- which must cover **both** ownership entry points that call `TitleServiceImpl.getOrCreate` (data-entity ownership at `OwnershipServiceImpl.java:53,106` and term ownership at `TermOwnershipServiceImpl.java:36,63`), or gate the mint inside `TitleServiceImpl.getOrCreate` itself so both callers are covered. Alternatively, gate the mint behind an allow-list of already-existing titles for users without the permission, falling back to "title not found" rather than silently creating. Emit an Activity/audit event on title creation so the mint is attributable. Add a server-side name bound (length + trim) while touching this path. Open to alternatives on permission-gated vs. allow-listed, but it must not remain unauthorized and unaudited.
