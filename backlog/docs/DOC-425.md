## Description

Two published reference pages name the data-entity **class** enum with the canonical `DATA_` prefix stripped. The real enum (`DataEntityClassDto`) values are `DATA_SET`, `DATA_TRANSFORMER`, `DATA_TRANSFORMER_RUN`, `DATA_QUALITY_TEST`, `DATA_QUALITY_TEST_RUN`, `DATA_CONSUMER`, `DATA_INPUT`, `DATA_ENTITY_GROUP`, `DATA_RELATIONSHIP` (ids 1–9). The docs render them as `SET` / `TRANSFORMER` / `TRANSFORMER_RUN` / `QUALITY_TEST` / `QUALITY_TEST_RUN` / `CONSUMER` / `INPUT` / `ENTITY_GROUP` / `RELATIONSHIP`. An operator who reads "Entities of class `SET`" and then greps the API contract, the database, or a collector payload for `SET` finds nothing — the canonical token is `DATA_SET`. This is wrong on 8 of the 9 class rows across the two tables (`DATA_INPUT` → `INPUT`, etc.; only the run/non-run split is internally consistent — every row drops `DATA_`).

Where it appears:
- **search.md** — "Result-class tabs" table (the nine-tab strip): `Datasets → class SET`, `Transformers → TRANSFORMER`, `Data Consumers → CONSUMER`, `Data Inputs → INPUT`, `Quality Tests → QUALITY_TEST`, `Groups → ENTITY_GROUP`, `Relationships → RELATIONSHIP`. (The `All` and `My Objects` tabs are not classes.)
- **entity-detail-page.md** — "Per-class panel matrix" table (all nine class rows: `SET` / `TRANSFORMER` / `TRANSFORMER_RUN` / `CONSUMER` / `INPUT` / `QUALITY_TEST` / `QUALITY_TEST_RUN` / `ENTITY_GROUP` / `RELATIONSHIP`), plus the "Class and type badges" prose and the warning hint that names `TRANSFORMER_RUN` / `QUALITY_TEST_RUN` as the run-classes with no stats panel.

**The nuance the implementer must get right (do not blindly find-replace).** There are two distinct correct things on these pages, and only the *enum-literal* one is wrong:
1. **Enum literal** — when the doc says "entities of class `X`" in code font, `X` must be the canonical enum value `DATA_SET` / `DATA_TRANSFORMER` / … (per `DataEntityClassDto.java:43-51`). This is what is wrong today.
2. **Display short-label** — the platform UI *does* show a short label. `DataEntityClassDto.resolveName()` (`DataEntityClassDto.java:93-98`) splits the enum name on `_`, lowercases, capitalises each word, and joins with a space — so `DATA_SET` renders as **"Data Set"**, `DATA_TRANSFORMER` as **"Data Transformer"**, `DATA_QUALITY_TEST` as **"Data Quality Test"**, etc. (NOT "Set"/"Transformer"). entity-detail-page.md:81 already references a short-label/long-label convention ("the short label is on the chip; the longer 'normal' label is in the tooltip"). The doc's stripped tokens (`SET`, `TRANSFORMER`) match **neither** the enum literal **nor** the `resolveName()` display label — they are a third, non-existent form.

The fix is therefore to use the canonical enum literal (`DATA_SET`, …) wherever the doc asserts "class `X`" in code font, and — if the page wants to show the human label — render it as the actual `resolveName()` output ("Data Set"), naming the canonical enum once so both forms are traceable. The tab/section display names already present (`Datasets`, `Transformers`, `Data Consumers`, …) are the UI tab strings and stay as-is.

This is why the UI label differs from both the enum literal and the doc's stripped token.
