## What

`GithubUserHandler.java` has two code-settled posture defects:

**Defect 1 - admin-principals BYPASSES org-name gate (F-084b).** In `enrichUserWithProviderInformation` (`:48-97`): if `provider.getAdminPrincipals()` is non-empty and the user's login/attribute matches (`:54-60`), the method returns an ADMIN `DefaultOAuth2User` at line 62 - BEFORE the organization-membership check, which only begins at line 68 (`if (StringUtils.isEmpty(provider.getOrganizationName()))`) and is enforced via the `/user/orgs` call at lines 76-91. So an operator setting `organization-name: my-corp` + `admin-principals: [external-consultant]` grants ADMIN to `external-consultant` without ever verifying `my-corp` membership. A typo in `admin-principals` that matches a username an attacker can register on github.com becomes a platform-ADMIN backdoor. (Order of evaluation is a static fact, independent of any running stack.)

**Defect 2 - GHES STRUCTURALLY LOCKED OUT (F-084c).** Line 39 hard-codes `private final WebClient webClient = WebClient.create("https://api.github.com")` - a field initializer with no `@Value` and no operator override; both the org call (`:76-78`) and the teams call (`:104-106`) use it. GitHub Enterprise Server deployments (API at e.g. `https://github.example.com/api/v3`) cannot retarget it; once `organization-name` is set, every GHES login hits public github.com and fails the membership lookup. (`GithubLogoutSuccessHandler.java:30` hard-codes the same base URL, so logout is GHES-locked too - see Adjacent.)

## User-facing impact

CODE-SETTLED wiring for both defects; the privilege/leak observable for Defect 1 needs a running OAUTH2 + GitHub stack.

- **Defect 1 ordering (verified-trace, static):** the admin-principals branch returns at `GithubUserHandler.java:62` before the org check at `:68` - read directly; the bypass is a settled control-flow fact, not an inference. This is why `user_facing_verified` can be `true`.
- **Defect 1 observable (static-not-driven; manifests under `auth.type=OAUTH2` with a GitHub client + `organization-name` set):** "a user listed in `admin-principals` but NOT in the org gets ADMIN" requires a live GitHub OAUTH2 login. Under the default `auth.type=DISABLED` (`application.yml:34`) the handler is never constructed (`@Conditional(GithubCondition.class)`), so nothing manifests. Remaining check = configure GitHub OAUTH2 with `organization-name` + an `admin-principals` entry that is not an org member, log in as that user, observe ADMIN.
- **Defect 2 (verified-trace, static):** the base URL is a hard-coded field initializer with no override path anywhere in the class - confirmed by full read. GHES being unusable once org-membership is required follows directly; no running stack needed to establish the absence of an override.

## Why it matters

**Defect 1** - the operator mental model "org-membership is the outermost guard" is wrong: admin-principals is evaluated first and short-circuits it. A single typo in `admin-principals` (a name an attacker can register on github.com) is a platform-ADMIN backdoor. Compounds with the substring-overpromotion concern tracked in PLT-081.

**Defect 2** - GHES operators hit org-membership failures with no documented cause and no config knob; self-hosted enterprise GitHub is silently outside ODD's OAuth2 support.

## Suggested fix

**Thread A - Reorder gates so org-name fires FIRST, then admin-principals only for org members (Defect 1):**

```java
// Pseudo-code; verify against current handler signature
return githubApi.fetchUserOrgs(userLogin)
    .flatMap(orgs -> {
        if (provider.getOrganizationName() != null 
            && !orgs.contains(provider.getOrganizationName())) {
            return Mono.error(new AccessDeniedException("User not in organization " + provider.getOrganizationName()));
        }
        // Org membership verified - NOW evaluate admin-principals
        if (provider.getAdminPrincipals().contains(userLogin)) {
            return adminUser(userLogin);
        }
        return regularUser(userLogin);
    });
```

The order matters: org membership is the outermost gate; admin-principals refines the role within that gate. Today's order treats admin-principals as a bypass.

Migration note: operators relying on the bypass today (admin-principals overriding org-membership) WILL break. Document the change in CHANGELOG; recommend operators verify their admin users are org members before the new release.

**Thread B - GHES config knob (Defect 2):**

```java
@Value("${auth.oauth2.client.{registrationId}.github-base-uri:https://api.github.com}")
private String githubBaseUri;

private final WebClient webClient = WebClient.create(githubBaseUri);
```

Doc-side: cross-link from `oauth2-oidc.md` GitHub section to the new config knob. Verify the GHES path conventions (typically `https://github.example.com/api/v3`); the platform should NOT rewrite the operator-supplied URI.
