  - **Decision statement**: Outbound Slack delivery is decoupled from the inbound HTTP request via a three-stage pipeline: (1) controller persists a `Message` row with state `PENDING_SEND` and immediately returns `202 Accepted`; (2) `DataCollaborationMessageSenderJob` (a single-thread background worker per JVM instance) acquires a Postgres advisory lock with id `datacollaboration.sender-message-advisory-lock-id` (default `120`, configurable per `application.yml:202` + `DataCollaborationProperties.java:10`); (3) the lock-holder drains the queue, calling Slack `chat.postMessage` with up to `datacollaboration.sending-messages-retry-count` retries (default 3). The advisory-lock pattern was deliberately chosen over Redis/Kafka/SQS to preserve the Postgres-as-only-dependency posture for ODD's deployment topology — operators don't need to provision a message broker to use Discussions.
  - **Wisdom test**: PASS. Both sub-decisions are intent-anchored: the 202-Accepted return is a deliberate UX choice (paired with the queue model, signalling "we accepted the message but delivery is asynchronous"); the advisory-lock-over-broker is structural (cross-instance ordering without external infrastructure). Structural impact: any future outbound-delivery feature must either reuse this pattern (and the lock-id namespace) or justify a different mechanism in an extension ADR.
