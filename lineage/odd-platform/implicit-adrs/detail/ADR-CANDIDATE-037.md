- **ADR-CANDIDATE-037** (NEW 2026-05-12C; STRENGTHENED 2026-05-12D — 2-sidecar from both consumer + properties-class sides): LDAP supports Active Directory as a dedicated provider branch (UPN-based bind via Spring `ActiveDirectoryLdapAuthenticationProvider(domain, url)`) rather than a generic LDAP+AD-flavoured config — operators choosing AD get Microsoft-specific bind semantics (UPN `user@domain`) bypassing `BindAuthenticator`'s DN-pattern / filter search
  - **Category**: promote

  - **Decision statement**: When the operator sets `auth.ldap.active-directory.enabled=true` (and supplies the `domain` field), `LDAPSecurityConfiguration.java:76-83` constructs `ActiveDirectoryLdapAuthenticationProvider(domain, url)` from Spring Security LDAP, bypassing the `BindAuthenticator` path used by generic LDAP. The provider uses Microsoft AD's UPN format (`user@domain`) for bind rather than DN-pattern or filter-search lookup; the operator-supplied `dn-pattern` / `user-filter` are silently ignored under AD mode (REFACTOR-122 captures the operator-confusion price — `ODDLDAPProperties.validate()` still requires one of the two, but they don't apply). The decision commits ODD to treating AD as a first-class LDAP variant with its own configuration nested class (`ODDLDAPProperties.ActiveDirectory`) and its own constructor path, rather than asking AD operators to configure DN-pattern matching AD's behaviour. The trade-off: simpler AD operator UX (just provide domain + url) vs. structural complexity (two LDAP-mode code paths to maintain).
  - **Wisdom test**: PASS. The dedicated nested config class + explicit branch + Microsoft-specific bind provider is the intent anchor; the alternative (asking AD operators to write DN-pattern that mimics UPN behaviour) would have been less ergonomic. Structural — every future Microsoft-AD-specific feature lives in this branch.
