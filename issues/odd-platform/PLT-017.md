## What

The Term Search component reconstructs its facet-update debouncer whenever the facet selection changes, defeating the 1500ms rate-limit it nominally enforces. The pattern is `useCallback(useDebouncedCallback(() => dispatch(updateTermSearch(...)), 1500, { leading: true }), [termSearchId, termSearchFacetParams])` - the `useCallback` deps include `termSearchFacetParams`, which changes on every facet click. An effect fires `updateSearchFacets()` on `[termSearchFacetParams]` change. So each facet click (a) produces a new `termSearchFacetParams`, (b) rebuilds the debouncer via `useCallback`, then (c) the effect invokes that brand-new debouncer. Because the debouncer is created with `{ leading: true }`, its **first** invocation fires on the leading edge - immediately. A debouncer that is freshly created on every click therefore fires immediately on every click; its 1500ms trailing window never coalesces anything.

**Effective behaviour: every facet click that leaves the search un-synced dispatches `updateTermSearch` IMMEDIATELY; the 1500ms debounce rate-limits nothing.** A user rapidly clicking 5 facets in 2 seconds dispatches up to 5 PUTs instead of the intended 1. (Verified 2026-06-10 by reading the component and its effect; see Where.)

A related debouncer-recreation pattern recurs at the term-search facet-options autocomplete - see Where for the corrected path and the (different) behavioural consequence there.

## Where

Primary site (the 1500ms leading-edge rate-limit that does nothing) - `odd-platform-ui/src/components/Terms/TermSearch/TermSearch.tsx:50-68` (path corrected 2026-06-10; the original `components/TermSearch/TermSearch.tsx` does not exist - the component lives under `Terms/`):

```tsx
// TermSearch.tsx:50-64 - debouncer rebuilt whenever termSearchFacetParams changes
const updateSearchFacets = React.useCallback(
  useDebouncedCallback(
    () => {
      const termSearchFormData = {
        query: termSearchQuery,
        filters: mapValues(termSearchFacetParams, values),
      };
      dispatch(updateTermSearch({ searchId: termSearchId, termSearchFormData }));
    },
    1500,
    { leading: true }
  ),
  [termSearchId, termSearchFacetParams]            // <-- termSearchFacetParams changes per facet click
);

// TermSearch.tsx:66-68 - the effect that invokes the (just-rebuilt) debouncer
React.useEffect(() => {
  if (!termSearchFacetsSynced) updateSearchFacets();
}, [termSearchFacetParams]);
```

Second site (corrected path + corrected behaviour) - `odd-platform-ui/src/components/Terms/TermSearch/TermSearchFilters/TermSearchFilterItem/MultipleFilterItem/MultipleFilterItemAutocomplete/MultipleFilterItemAutocomplete.tsx:97-122`:

```tsx
// :97-116 - handleFacetSearch: useCallback wrapping a 500ms debouncer, deps include searchText
const handleFacetSearch = useCallback(
  useDebouncedCallback(() => { ...dispatch(getTermsSearchFacetOptions({ ... query: searchText })) ... }, 500),
  [getTermsSearchFacetOptions, setFacetOptionsLoading, setFacetOptions, searchText]
);
// :118-122 - effect calls it when searchText (or open) changes
useEffect(() => { if (!autocompleteOpen) return; ...; handleFacetSearch(); }, [searchText, autocompleteOpen]);
```

Note the second site differs from the primary: it is **500ms and has NO `{ leading: true }`** (default trailing-edge). Recreating a trailing-only debouncer on each keystroke means each old debouncer's pending 500ms timer is dropped and a new one starts, so the request still fires ~500ms after the *last* keystroke as long as React reuses the timer across the rapid edits - the rate-limit is weakened/unreliable rather than fully nullified the way the leading-edge primary site is. Both should use a stable debouncer; the user-visible severity is dominated by the primary site.

## User-facing impact

Static-verified at the primary site; magnitude not driven. The leading-edge-fires-on-every-click mechanism is code-confirmed: `useCallback` deps include `termSearchFacetParams` (`TermSearch.tsx:63`), the effect calls the rebuilt debouncer on `[termSearchFacetParams]` (`:66-68`), and the debouncer is `{ leading: true }` (`:61`) so its first call after each rebuild dispatches immediately. The observable is a `PUT` per facet click during rapid faceting, instead of one coalesced PUT per 1.5s. No data corruption; the storm is bounded by the user's click cadence (client-driven, not a server runaway).

Not driven (runtime-only): the exact PUT count under a real click burst and any server-side slowdown on a large term catalog. Remaining check to quantify: open Term Search on a running instance, rapid-click several facets, and count `PUT` requests in the network panel; no workspace probe-run exists for this. The second site (autocomplete) is a weaker, separate effect (trailing 500ms, no leading) and is not the load-bearing claim.

## Why it matters

Operator-visible at the primary site:
- More API requests than the UI implies; potential server-side cost amplification on busy term catalogs (each facet click -> PUT on the term-search update endpoint)
- Rapid facet exploration sessions (the design intent for faceted search) generate disproportionate backend load
- On large term catalogs where each search-state update triggers a recursive query, the dispatch storm can slow the platform

Severity is MEDIUM because:
- No security impact
- No data corruption
- The dispatch storm is bounded by the user's click cadence (not a server-side runaway)
- The fix is a small, localized React change

But it IS a real UX defect - the debouncer was added to prevent this and currently does the opposite.

## Suggested fix

Replace the `useCallback`-wrapping-`useDebouncedCallback` pattern with a stable debouncer ref that does NOT depend on changing state. The captured state is read inside the debounced function at fire time, not at construction time.

```typescript
// TermSearch.tsx - use a ref to capture latest state without rebuilding the debouncer
const latestParamsRef = useRef({ termSearchId, termSearchFacetParams });
useEffect(() => {
  latestParamsRef.current = { termSearchId, termSearchFacetParams };
}, [termSearchId, termSearchFacetParams]);

const debouncedUpdate = useDebouncedCallback(
  () => {
    const { termSearchId, termSearchFacetParams } = latestParamsRef.current;
    updateTermSearch({ termSearchId, ...termSearchFacetParams });
  },
  1500,
  { leading: true }
);
// no useCallback wrapper - the debouncer is constructed once at mount

// at the call site:
const onFacetClick = () => {
  // update state; debouncer fires with latest values via ref
  setTermSearchFacetParams(next);
  debouncedUpdate();
};
```

Apply the same stable-debouncer pattern at the second site (`Terms/TermSearch/TermSearchFilters/TermSearchFilterItem/MultipleFilterItem/MultipleFilterItemAutocomplete/MultipleFilterItemAutocomplete.tsx:97-116`); there the captured value is `searchText` and there is no leading edge, so the fix is to construct the 500ms debouncer once and read `searchText` from a ref at fire time.

Add a unit test:

```typescript
it('rate-limits facet click bursts to one PUT per 1.5s window', async () => {
  const { result } = renderHook(() => useTermSearchDebouncer());
  for (let i = 0; i < 5; i++) {
    act(() => result.current.dispatch());
  }
  expect(updateTermSearchSpy).toHaveBeenCalledTimes(1);    // not 5
  await wait(1500);
  expect(updateTermSearchSpy).toHaveBeenCalledTimes(1);
});
```
