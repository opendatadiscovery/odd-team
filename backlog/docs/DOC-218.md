## Description

Live `/permissions` lines 81 + 86 (verbatim quoted in WebFetch result this session): `COLLECTOR_TOKEN_REGENERATE` — "Allows regenerating the security token for a collector"; `DATA_SOURCE_TOKEN_REGENERATE` — "Allows regenerating the security token for a data source". Both descriptions are minimal capability prose and silent on operational consequence.

Code reality (per F-163b verified this session — `DataSourceItemToken.tsx:37-49` + `CollectorItemToken.tsx:37-49`): regenerating a token immediately invalidates the prior token at the platform tier. The operator's running collector / data-source push-adapter is using the OLD token; the moment the rotation succeeds, every subsequent request 401s. Holders of these permissions are operationally privileged in a sense the permission description hides — granting them is granting the ability to cause a production-ingestion outage.

Operator-visible consequence: a Policy grant to a developer-tier role expecting "developer can rotate stale tokens" actually grants "developer can cause a production outage by rotating a live token." Permission editor in the UI inherits the OpenAPI description; operators tick the box trusting the description.
