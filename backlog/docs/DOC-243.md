## Description

The live `enable-security/authorization/permissions` page (WebFetched 2026-05-27) lists permissions verbatim from the `Permission` enum and groups them in FIVE conceptual categories (per the parent authorization page). The page is **silent on two architectural facts** that materially affect how third-party clients consume the permission read surface:

**Facet 1 — `MANAGEMENT` is a valid `PermissionResourceType` enum value in the OpenAPI spec but the runtime REJECTS it with HTTP 400 USR001 (F-090a, HIGH→CRITICAL).** `components.yaml:3381-3387` declares the `PermissionResourceType` enum with FOUR values, including `MANAGEMENT`. `PermissionServiceImpl.java:24-27` rejects `MANAGEMENT` calls with `BadUserRequestException("Resource type MANAGEMENT does not have context")` (HTTP 400 USR001) because management-scope permissions live on the COMPLEMENTARY endpoint (`/api/identity/whoami` → `Identity.permissions`). Third-party clients compiled from openapi.yaml building a 4-way switch over PermissionResourceType + sending `GET /api/resource/MANAGEMENT/0/permissions` receive unexpected HTTP 400. Integrators must read source to discover the two-endpoint orchestration. SPC-002 tightens the spec; this doc-side fix documents the orchestration **today** so operators reading the API contract have the WHY.

**Facet 2 — Five permission categories vs four PermissionResourceType enum values — Lookup Table folded into Management (F-090b, MEDIUM→HIGH).** The live `/authorization` page documents FIVE permission categories: Data Entity / Namespace / Term / Lookup Table / Management. `components.yaml:3381-3387` exposes FOUR `PermissionResourceType` values; `LOOKUP_TABLE_*` permissions are folded into the Management half (`PolicyPermissionDto.java:80-88`). Integrator building a 5-way UI dispatch from docs runtime-mismatches the 4-way enum. The doc framing is correct at the human-conceptual level (5 categories) but the API-contract framing is 4 resource types + Management's non-contextual subset (which contains Lookup Table operations).

- [ ] A new "## Permission read surface (two-endpoint orchestration)" sub-section is added on permissions.md covering:
  - **Two endpoints, two scopes** — explicit table:

    | Endpoint | Scope | Returns | Example PermissionResourceType values |
    |---|---|---|---|
    | `GET /api/resource/{type}/{id}/permissions` | Contextual / resource-scoped | Permissions the caller holds IN the named resource's context | `DATA_ENTITY` (entity-level), `TERM` (term-level), `QUERY_EXAMPLE` (query-example-level) |
    | `GET /api/identity/whoami` → `Identity.permissions` | Non-contextual / management-scope | Permissions the caller holds GLOBALLY for management operations | Policy/Role CRUD, Lookup Table CRUD, Owner/Datasource/Collector lifecycle, etc. |

  - **The MANAGEMENT spec-vs-runtime drift admonition**: "The OpenAPI spec's `PermissionResourceType` enum lists `MANAGEMENT` as a fourth value; the runtime endpoint `GET /api/resource/MANAGEMENT/0/permissions` returns HTTP 400 USR001 (`Resource type MANAGEMENT does not have context`). This is intentional but undocumented in older clients — management permissions are returned by the COMPLEMENTARY endpoint above. SPC-002 tightens the spec (either removing MANAGEMENT from PermissionResourceType + adding a separate operationId, or documenting `security: []` / runtime-only); until that ships, SDK code generating `MANAGEMENT`-typed calls against the runtime needs to route through whoami instead."

- [ ] The existing "five categories" framing is reconciled with the four-resource-type enum:
  - Insert a clarification: "Permissions are organised into **five conceptual categories** for operators (Data Entity / Namespace / Term / Lookup Table / Management); the underlying `PermissionResourceType` enum has **four values** — Lookup Table operations are stored within the Management category for the read endpoint. The two-endpoint orchestration above is how an integrator discovers a caller's Lookup Table permissions (they appear in `Identity.permissions` from `/api/identity/whoami`, NOT in `GET /api/resource/LOOKUP_TABLE/...`)."
