## Description

The local `documentation` clone is a single-branch clone:
`remote.origin.fetch = +refs/heads/main:refs/remotes/origin/main`. Consequence verified
during the CTRIB-006 review: `git fetch origin` exits 0 but NEVER updates
`origin/release/{version}`; the tracking ref only moves when a push happens from this
clone. The review initially observed a stale `origin/release/0.28.0` (= `1d43d6e`) while
the remote actually served `f61b9c2` — `git ls-remote origin release/0.28.0` was the
authoritative answer.

A future release-gate or review session that trusts `git fetch` + `git rev-parse
origin/release/{version}` will mis-read the train state (e.g., conclude a train commit
was never pushed, or verify against a stale tip).

## Acceptance criteria

- [ ] `playbooks/release-train-merge.md` names `git ls-remote origin release/{version}`
      (and `git ls-remote origin main`) as the authoritative ref checks, with one line on
      WHY (single-branch clones never fetch non-main tracking refs).
- [ ] Train-verification steps in the contributor/docs gates that say "fetch the branch"
      point at the ls-remote form (grep for `release/{version}` fetch wording and align).

## Context

Found during the CTRIB-006 `/review` Gate 8/G-C11 train verification. CTRIB-005's review
