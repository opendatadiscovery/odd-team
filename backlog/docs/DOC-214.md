## Description

Live `/user-owner-association` says "Select owner which you want to associate yourself with and press `Send request` button" — implying selection from an existing list. The page is silent on free-typed-name semantics.

Code reality (verified verbatim this session, `OwnerAssociationForm.tsx:190`): the Owner-name Autocomplete is `freeSolo`, meaning the user can TYPE a NEW owner name (not just select). On submit, the backend's `OwnerService.getOrCreate` MINTS the Owner row for that name (per F-075b composition — see DOC-209). The submitted name has only `required: true` validation (verified `OwnerAssociationForm.tsx:167-172`); no max length, no charset filter (Unicode emoji, control characters, leading/trailing whitespace all accepted), no case normalization. The catalog's Owner directory ACCRETES typos + variants over time; subsequent users searching for "John Smith" miss "john smith" / "John  Smith" / "John Smith " etc.

Operator-visible consequence: operator opens Management → Owners after a quarter of usage and finds 200 Owner rows that are really 50 distinct identities — operator-Tuesday-typo "Jonh Smith" sits alongside the canonical "John Smith". Cross-catalog: every Policy that pivots on `dataEntity:owner:name == 'X'` becomes brittle to the typo.
