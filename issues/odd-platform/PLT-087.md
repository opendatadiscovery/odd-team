## What

Three small-surface code defects on the DataSource lifecycle that share a shape: per-method cleanup gaps that the originating author left implicit. Each is operator-visible in a specific way; all three ship together.

**Defect 1 - `deleteDataSource` orphans the associated TOKEN row + does not clear the FTS `search_entrypoint` vector.** `DataSourceServiceImpl.java:85-96` (delete) blocks with `CascadeDeleteException` (HTTP 400) when a live `data_entity` child references the source; otherwise soft-deletes via `UPDATE data_source SET deleted_at = NOW()`. **The associated TOKEN row is orphaned** (TOKEN has no `deleted_at` column; F-020 sibling - see PLT-085 for the Collector parallel). **The FTS `search_entrypoint` vector is NOT cleared** (asymmetry with the update path, which DOES call `updateSearchVectors`); soft-deleted data-source names persist in catalog search until other events refresh the affected entries.

**Defect 2 - `regenerateDataSourceToken` is NOT `@ReactiveTransactional`.** `DataSourceServiceImpl.java:98-106` is **the only mutating method on this class without `@ReactiveTransactional`** (compare lines 52, 69, 86 which all carry it). If `tokenRepository.updateToken` fails after the `dataSourceRepository.getDto` read, partial state is undefined.

**Defect 3 - `regenerateDataSourceToken` returns the 40-char plaintext token in the response body with no `Cache-Control: no-store` header.** Intermediate proxies / browser history / corporate inspection appliances may cache. Combined with PLT-085 (plaintext-at-rest), the token has multiple persistence surfaces an operator did not authorise.

## Why it matters

**Defect 1**: Operators auditing `TOKEN` rows for orphans see growth without obvious source (the parent data-source is soft-deleted). Operators searching for a "deleted" data source find it surfacing in faceted catalog search until other events trigger a refresh.

**Defect 2**: Partial-state risk; manifests as inconsistent operator state on transient DB errors. Small probability per event, real cumulative risk.

**Defect 3**: Plaintext token caching by intermediate proxies extends the credential's exposure window beyond the operator's control. Operators rotating a leaked token expect tight blast radius - a cached response in a corporate proxy / browser tab history undermines that.

Severity MEDIUM because:
- None of the three is a security-defect-class on its own; all three are operator-trust / state-consistency caveats
- The three together are a small-surface hardening pass; an upstream maintainer can land them in a single small PR

## Suggested fix

### Defect 1 - delete should clean up TOKEN + FTS

```java
// DataSourceServiceImpl.java:85-96
@ReactiveTransactional
public Mono<Long> delete(final long id) {
    return dataSourceRepository.getDto(id)
        .flatMap(dto ->
            dataSourceRepository.delete(id)
                .then(Mono.justOrEmpty(dto.tokenId()))
                .flatMap(tokenRepository::delete)            // <- clear the TOKEN row
                .then(searchEntrypointService.updateSearchVectors(
                        ChangeContext.dataSourceDeleted(id))) // <- refresh FTS
                .thenReturn(id)
        );
}
```

(Exact wiring depends on whether TOKEN should be soft-deleted (adds `deleted_at`) or hard-deleted; recommend hard-delete since TOKEN has no historic value once the parent is gone. If hard-delete causes FK conflict, add `ON DELETE CASCADE` to the TOKEN->DATA_SOURCE FK in a follow-up migration.)

### Defect 2 - annotate regenerate

```java
// DataSourceServiceImpl.java:98-106
+ @ReactiveTransactional
  public Mono<DataSource> regenerateDataSourceToken(final long id) {
      return dataSourceRepository.getDto(id)
          .flatMap(dto -> tokenRepository.updateToken(...))
          .map(updated -> dataSourceMapper.mapDto(updated));
  }
```

One-line annotation; matches the 3 sibling methods.

### Defect 3 - Cache-Control on the rotation response

Controller-side:

```java
@PutMapping("/api/datasources/{id}/regenerateToken")
public Mono<ResponseEntity<DataSource>> regenerateDataSourceToken(@PathVariable long id) {
    return dataSourceService.regenerateDataSourceToken(id)
        .map(ds -> ResponseEntity.ok()
            .header(HttpHeaders.CACHE_CONTROL, "no-store, no-cache, must-revalidate")
            .header(HttpHeaders.PRAGMA, "no-cache")
            .body(ds));
}
```

(Apply the same pattern to the Collector token rotation response under PLT-085's scope OR file a separate one-liner.)
