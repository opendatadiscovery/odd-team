## Description

`docs/integrations/collectors/odd-collector.md` is the manual's per-adapter configuration reference for the
generic collector — 41 adapters, each with a `Field | Type | Required | Default | Description` table. Ten of
those rows say a field is **not required** when the Pydantic model makes it required. An operator who follows
the table and omits the field gets a collector that **fails to start** with a `ValidationError`, not the
behaviour the row describes.

The root cause is a **Pydantic v1 → v2 semantic change applied inconsistently within the same page**: in
Pydantic v2, `Optional[str]` *without* a default is a REQUIRED field (it may be `null`, but it must be
present). `odd-collector` pins `pydantic 2.7.1` (`poetry.lock`).

The nine `database` rows all inherit the field from a base class the subclass body does not restate:

```python
# odd-collector/odd_collector/domain/plugin.py
class DatabasePlugin(WithHost, WithPort):
    database: Optional[str]        # <- no default => REQUIRED under pydantic v2
    user: str
    password: str
```

`ClickhousePlugin`, `RedshiftPlugin`, `VerticaPlugin`, `SingleStorePlugin`, `MongoDBPlugin`, `CassandraPlugin`,
`ScyllaDBPlugin`, `TarantoolPlugin` and `Neo4jPlugin` all inherit it unchanged. (`PostgreSQLPlugin`,
`MySQLPlugin`, `MSSQLPlugin` and `CockroachDBPlugin` redeclare `database: str` — and those four rows are
correctly marked `yes`. `OdbcPlugin` inherits it unchanged and is *also* correctly marked `yes`, which is why
this reads as an oversight rather than a misunderstanding.)

**The page already knows the rule and applies it correctly elsewhere.** The Tableau block marks `site`, `user`,
`password`, `token_name` and `token_value` as `Required: yes` and spells the reason out in the cell: *"The
model is `Optional[str]` with no default — pass an explicit value."* The same construct, on the same page,
documented two different ways. The nine `database` rows were missed because the field is not visible in the
subclass body — it is inherited.

**The ClickHouse row is the worst of the ten** because it does not merely mis-mark the column, it describes a
behaviour that cannot happen:

> `| `database` | string or null | no | — | Database to scan. When unset, the connection's default database is used. |`

There is no "when unset" path. Unset is a start-up failure.

## Secondary (same page-family, same verification method, one fix pass)

* **`ingestion-filters.md` documents two of the filter's three keys.** `odd_collector_sdk/domain/filter.py`'s
  `Filter` model is `include` / `exclude` / **`ignore_case`** (`bool = False`, feeding `re.IGNORECASE`). The
  page's "Shape of a filter" section shows only `include` and `exclude`. Everything else on that page verifies
  clean against the model — the empty-`include` → `[".*"]` validator, the exclude-wins ordering in
  `is_allowed`, `re.search` (not `fullmatch`) semantics, and all four rows of the worked PostgreSQL example.
* **`cubejs.token`** is documented `Required: conditional` / `Default: null`, which is the operator-useful
  truth, but the `Default: null` implies omitting the key is safe. Under v2 it must be *present* (as `null`)
  even with `dev_mode: true`. One clause on the existing cell closes it.
* **Not a defect, recorded so it is not "fixed":** `postgresql.password` is marked `Required: yes` while the
  model carries `SecretStr("")` as a default. Documenting a password as required is the correct operator
  guidance; leave it.

## Why this is `high` and not `medium`

This is the `retrospectives/LSN-001` / `LSN-002` shape — the manual's guidance walks an operator into a
deployment failure. It is worse than a missing caveat: the row is *specific*, *actionable*, and *wrong*, and the
ClickHouse cell tells the operator what will happen instead of the `ValidationError` they will actually get. It
is not data loss, which is why it is `high` rather than `critical`.
