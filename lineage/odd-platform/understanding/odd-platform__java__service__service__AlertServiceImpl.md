# AlertServiceImpl — semantic understanding

## understanding

`AlertServiceImpl` is the Spring `@Service` hop between the controller layer (`AlertController` for the UI/API surface, `AlertManagerController` for Prometheus webhook ingestion, `DataEntityController` for per-entity tabs) and the data layer (`ReactiveAlertRepository`, `ReactiveDataEntityRepository`). It owns three orthogonal concerns: (1) **principal context** — resolves the current user / associated owner via `AuthIdentityProvider` for read-by-owner queries and audit-trail attribution on status mutations (lines 84, 93, 117); (2) **transaction boundaries** — class is unannotated, but `handleExternalAlerts` (line 152) and `applyAlertActions` (line 201) carry `@ReactiveTransactional`, while the user-driven `updateStatus` (line 111) deliberately does NOT, leaving the read-then-write reopen-guard composition (lines 124-131) unfenced; (3) **activity-feed emission** — manual `ActivityCreateEvent` construction for new-alert and auto-resolve paths (lines 247-258, 302-325), and `@ActivityLog`-AOP-bound emission for user-driven status updates (line 112). The class is also the de-duplication boundary between the two ingestion paths: `applyAlertActions` (used by `AlertIngestionRequestProcessor`) consumes resolved `AlertAction`s with `CreateAlertAction.chunks` already keyed by `AlertUniqueConstraint`, while `handleExternalAlerts` (used by `AlertManagerController`) does NO de-duplication and forwards every webhook payload to a raw INSERT — a structural asymmetry confirming the batch-H finding that the AlertManager webhook path has no idempotency guard.

- invariants:
  - "**`@ReactiveTransactional` placement is asymmetric across mutation methods.** `handleExternalAlerts` (line 152) and `applyAlertActions` (line 201) are annotated; `updateStatus` (lines 111-113) is NOT. The activity emission for `updateStatus` runs INSIDE the `ActivityAspect`'s synthetic `@ReactiveTransactional` (`ActivityAspect.java:42`) that wraps the AOP-intercepted Mono, NOT in a service-declared transaction. The asymmetry has a consequence: the reopen-conflict guard (lines 124-131) reads `openAlertWithTheSameTypeExistsForDataEntity` THEN writes `updateAlertStatus` inside the AOP's synthetic transaction, but no row-level lock is taken on either step."
  - "**`updateStatus` is the ONLY method on the class with `@ActivityLog` AOP** (line 112). The other state-changing paths (`handleExternalAlerts`, `applyAlertActions`, `automaticallyResolveAlerts`) emit activity events MANUALLY via `activityService.createActivityEvents(...)` (lines 258, 324) — they do not use the annotation because the AOP design is single-alert / single-event, whereas these paths emit N events per call."
  - "**Reopen-conflict guard is server-enforced application logic, not a DB constraint** (lines 124-131). The `if (AlertStatusEnum.OPEN == status)` branch calls `alertRepository.openAlertWithTheSameTypeExistsForDataEntity(alertId)` and `sink.error(new BadUserRequestException(...))` if true. The literal English message is `Cannot reopen alert since the system already has an open alert of the same type` (lines 128-129). The check is unfenced: two concurrent reopen requests for sibling alerts of the same type can both pass."
  - "**`updateStatus` has two switchIfEmpty fallback steps** (lines 119-120). The first replaces the username-aware update with a `username=null` update for anonymous / system-context callers; the second emits `NotFoundException` if the alert does not exist. The 'anonymous still proceeds' path is reachable when `auth.type=DISABLED` OR when an upstream caller has no SecurityContext."
  - "**AlertManager webhook path hardcodes type=DISTRIBUTION_ANOMALY** (line 177). The AlertManager-side `alertname` / `severity` labels are ignored; every webhook payload becomes the same type regardless of provider configuration."
  - "**The chunk description for AlertManager-derived alerts is `Distribution Anomaly. URL: %s`** with the URL-encoded `generatorURL` + `g0.moment_input` + `g0.end_input` query params (lines 168-185). The generator URL is propagated verbatim from the webhook payload (untrusted)."
  - "**`createAlerts` private helper is shared by both ingestion paths** (lines 261-300). It chains: `repo.createAlerts(alerts)` → group chunks by `AlertUniqueConstraint` → flatten with `additionalChunks` → `repo.createChunks(chunks)` → `registerAlertCreatedEvents` (activity emission) → `repo.setLastCreatedAt(...)`. Activity emission for new alerts therefore lives in ONE place; the two callers diverge only at the `AlertAction` discriminator step."
  - "**Activity emission for `applyAlertActions` is in TWO stages**: `createAlerts(...).then(automaticallyResolveAlerts(...))` (line 230). Each stage emits its own activity events: `registerNewAlertsActivityEvents` for OPEN_ALERT_RECEIVED / RESOLVED_ALERT_RECEIVED (lines 309-325), and `registerAutomaticallyResolvedAlertsActivityEvents` for ALERT_STATUS_UPDATED with `systemEvent=true` (lines 247-259)."
- audiences: [
    "AlertController (the four UI-facing read methods + the mutation method — lines 39, 47, 55, 25; the line numbers are AlertController.java references) — primary consumer of the read surface",
    "AlertManagerController (`AlertManagerController.java:24` — `alertService.handleExternalAlerts(req.getAlerts())`) — the unauthenticated AlertManager webhook surface",

  - `listAll`, `listByOwner`, `getTotals`, `updateStatus`, `getDataEntityAlerts`, `getDataEntityAlertsCounts`, `listDependentObjectsAlerts` — invoked from `AlertController` / `DataEntityController` (UI/API surface protected by SecurityWebFilterChain under `LOGIN_FORM | OAUTH2 | LDAP`; DISABLED skips auth)
  - `handleExternalAlerts` — invoked from `AlertManagerController` (`/ingestion/alert/alertmanager` — `/ingestion/**` whitelist; **NOT** covered by any of the four UI auth modes nor by the `auth.ingestion.filter.enabled` ingestion-auth filter)
  - `getOpenAlertsForEntities`, `applyAlertActions` — invoked from `AlertIngestionRequestProcessor` (per `AlertIngestionRequestProcessor.java:42`, this is the `FINALIZING` phase of the IngestionRequest pipeline; `POST /ingestion/entities` is gated by `IngestionDataEntitiesFilter` when `auth.ingestion.filter.enabled=true`)
  
  — evidence: `AlertServiceImpl.java:1-357` (no auth-conditional annotations on the class or methods) + `AlertController.java`, `AlertManagerController.java`, `DataEntityController.java`, `AlertIngestionRequestProcessor.java` (the four call-site files).

- **ingestion_filter_relevance**: SPLIT by method:
  - `handleExternalAlerts` — **YES, but NOT gated.** The AlertManager webhook lands at `/ingestion/alert/alertmanager` which IS in the `/ingestion/**` whitelist but is NOT matched by `IngestionDataEntitiesFilter` (the filter matches `/ingestion/entities` POST only, per prior batches). The webhook is therefore unauthenticated regardless of `auth.ingestion.filter.enabled`.
  - `getOpenAlertsForEntities`, `applyAlertActions` — **YES, gated when `auth.ingestion.filter.enabled=true`.** These are invoked downstream of `IngestionDataEntitiesFilter` via `AlertIngestionRequestProcessor` on the `/ingestion/entities` POST path.
  - All other methods — **NO, UI/API surface, not ingestion.**
  
  — evidence: `AlertManagerController.java:21` (path `ingestion/alert/alertmanager`, not `/ingestion/entities`) + `AlertIngestionRequestProcessor.java:42-49` (the `process` method invoked from the ingestion finalising phase) + cross-reference to `IngestionDataEntitiesFilter` path matcher (from prior batches).

## performance

- **hot_paths**:
  - "**`listAll` is the canonical UI-render path for the Alerts → All tab** (per the live alerting doc's 'Platform-wide triage' framing — neighbour sidecar inheritance). The service is a three-line pass-through; the cost lives at the repository (window-function COUNT + ROW_NUMBER pagination, see batch H). Per request: ONE DB round-trip." — evidence: `AlertServiceImpl.java:77-80` + batch H `performance.hot_paths[0]`
  - "**`getTotals` runs three concurrent count queries on every badge refresh.** `Mono.zipDelayError` (line 104) fires the three Monos in parallel; each is a separate DB round-trip. The badge refresh from the UI shell is frequent (per the typical SPA polling pattern); under heavy operator load the three count queries against the ALERT table become a measurable workload component." — evidence: `AlertServiceImpl.java:90-109`
  - "**`updateStatus` is single-item but the activity-emission AOP adds a hidden DB round-trip.** Per call: 1 conditional reopen-conflict read (status=OPEN only), 1 UPDATE, 1 refresh read, 1 activity-row INSERT via the AOP, PLUS the AOP's `getContextInfo` (a SELECT) BEFORE the update and `getUpdatedState` (another SELECT) AFTER. Five DB round-trips for a single user-driven status change. The activity-feed integration is the dominant cost." — evidence: `AlertServiceImpl.java:111-136` + `ActivityAspect.java:48, 85` (the getContextInfo + getUpdatedInfo round-trips) + `AlertStatusUpdatedHandler.java:30, 40` (the two SELECTs)
  - "**`getOpenAlertsForEntities` runs on every ingestion request that produces alert-relevant deltas.** It takes a `FOR UPDATE` lock on every matched OPEN alert for the duration of the ingestion's transaction window — a write-bottleneck on the ALERT table under high-ingestion-rate platforms." — evidence: `AlertServiceImpl.java:193-198` + batch H `performance.hot_paths[1]`
  - "**`applyAlertActions` is the bulk-write hot path for ingestion-derived alerts.** Per call: bulk INSERT ALERT (via `createAlerts`, partitioned at 1000), bulk INSERT ALERT_CHUNK (via `createChunks`), bulk UPDATE ALERT (via `setLastCreatedAt`), conditional bulk UPDATE ALERT (via `resolveAutomatically`), PLUS the activity-row INSERTs (one per created alert in `registerNewAlertsActivityEvents`, one per auto-resolved id in `registerAutomaticallyResolvedAlertsActivityEvents`). For N created alerts and M auto-resolved, the activity-feed emission contributes O(N+M) INSERTs." — evidence: `AlertServiceImpl.java:200-231, 247-258, 302-325`

- **throughput_characteristics**:
  - "Reactive WebFlux + Reactor throughout — non-blocking I/O, no thread held during DB await. Per-request thread cost is O(1). Throughput bounded by R2DBC connection pool size."
  - "**Single-item PUT for `updateStatus` — no bulk-status-change endpoint.** Operators triaging many alerts pay N round-trips for N alerts; the activity-feed emission compounds the cost. Cross-reference: `AlertController.changeAlertStatus` neighbour sidecar's `performance.known_performance_gaps[0]`." — evidence: `AlertServiceImpl.java:111-136` (no bulk method on the AlertService interface, verified by `AlertService.java:17-37`)
  - "**Bulk-write throughput for ingestion paths via `applyAlertActions` and `handleExternalAlerts`.** Both delegate to the shared `createAlerts` helper which partitions at 1000 rows per `executeInPartitionReturning` (per batch H). For a typical ingestion batch producing O(1)-O(100) alerts, one round-trip per partition."
  - "**`getTotals.zipDelayError` runs the three count queries CONCURRENTLY** — the wall-clock cost is `max(allCount, countByOwner, countDependent)`, not their sum. Helpful for badge refresh latency."

- **resource_allocation**:
  - "**No streaming on read** — `listAll` materialises a full `AlertList` page; for `size=N` the heap holds N AlertDto rows plus their chunks (`jsonArrayAgg` aggregation per batch H). No upper bound on `size` is enforced at this service (the controller passes it through, the repo executes it)." — evidence: `AlertServiceImpl.java:77-80` + batch H `performance.resource_allocation`
  - "**`handleExternalAlerts` materialises the entire `externalAlerts` list** in heap before issuing the bulk INSERT — the AlertManager webhook body is fully parsed and held in memory (lines 158-188). For a webhook posting 10K alerts in one request, the heap holds 10K `AlertPojo` + 10K `AlertChunkPojo`. The AlertManager-side payload size is bounded by Prometheus / AlertManager configuration; ODD does not limit it." — evidence: `AlertServiceImpl.java:158-188`
  - "**`applyAlertActions` materialises three local lists** (`alertsToCreate`, `idsToResolve`, `chunks` — lines 207-209) plus the `alertToChunks` SetValuedMap (lines 211-212) BEFORE the bulk INSERT. Bounded by the ingestion request's `AlertAction` count."
  - "**No outbound HTTP, no message-bus, no async-queue side-effects.** The service is fully in-process; the only network I/O is to the DB."

- **scaling_characteristics**:
  - "**Stateless — instances scale horizontally.** The service carries no instance state; the five injected fields (`alertRepository`, `dataEntityRepository`, `alertMapper`, `authIdentityProvider`, `activityService`) are Spring beans."
  - "**No advisory lock at the service layer.** The two `@ReactiveTransactional`-annotated methods (`handleExternalAlerts`, `applyAlertActions`) use ordinary read-committed transactions; row-level locks via `FOR UPDATE` only on the repo's `getOpenAlertsForEntities` (read INSIDE the transaction). No coordination between concurrent ingestion calls on the same data entity — concurrent ingestion of the same DQ test result from two sources could both pass the snapshot read, both call `applyAlertActions`, and produce duplicate alerts UNLESS the repo's `FOR UPDATE` line lock serialises them."
  - "**Reopen-conflict guard is application-level, not transactional.** Two concurrent reopen requests for sibling alerts of the same type on the same data entity can both pass. The current shape is incompatible with high-concurrency multi-operator deployments where multiple stewards may triage the same alert namespace simultaneously." — evidence: `AlertServiceImpl.java:124-131`
  - "**No retry / circuit-breaker / backoff** on any path. A transient DB failure surfaces as a Mono error; the caller (controller / ingestion processor) has no automatic retry."
  - "**Pagination passes through unmodified** — no upper bound on `size`. Cross-reference: `AlertController.getAllAlerts` REFACTOR-024 family. A caller passing `size=1_000_000` materialises a million-row response with no server-side cap. The cost lives at the repo (and on the wire); the service does not validate or clamp."

- **known_performance_gaps**:
  - "**No bulk-status-change method on `AlertService`.** Operators triaging many alerts issue N PUT requests, paying N × (1-3 DB reads + 1 UPDATE + 1 refresh + 2 activity-feed SELECTs + 1 activity-feed INSERT) = 6-8 round-trips per alert. A bulk method would reduce this to 1-3 round-trips for the entire batch. Cross-reference: `AlertController.changeAlertStatus` neighbour sidecar." — evidence: `AlertService.java:17-37` (no bulk method on the interface) — severity: LOW (UX nuisance, not a runtime hotspot)
  - "**Activity-feed AOP for `updateStatus` adds 2 SELECTs + 1 INSERT per call.** The `@ActivityLog` annotation triggers `ActivityAspect.monoActivityAspect` (`ActivityAspect.java:42`) which calls `activityService.getContextInfo` (1 SELECT) BEFORE proceed, `activityService.getUpdatedInfo` (1 SELECT) AFTER proceed, and `activityService::createActivityEvent` (1 INSERT) IF state changed. The dominant cost of `updateStatus`." — evidence: `AlertServiceImpl.java:112` + `ActivityAspect.java:42-58, 81-95` — severity: LOW
  - "**`handleExternalAlerts` materialises the entire webhook batch in heap** before INSERT (lines 158-188). For Prometheus deployments configured to coalesce many alerts into one webhook, the heap pressure is proportional to the AlertManager's `group_wait` / `group_interval` settings." — evidence: `AlertServiceImpl.java:158-188` — severity: LOW
  - "**Three concurrent count queries on `getTotals`** — for a platform with very large ALERT tables, the `total` query (`countAlertsWithStatusOpen`, a full ALERT scan with no owner index) dominates. The badge refresh is the user-facing latency surface; no caching." — evidence: `AlertServiceImpl.java:90-109` + cross-reference to batch H — severity: LOW
  - "**No method-level observability at this service.** No `@Timed`, no Micrometer counters, no structured log entries at operation boundaries; only `@Slf4j` is on the class (line 17) and there are zero `log.` call sites in the body. An operator investigating 'why are alerts slow today' has no per-method visibility into this service's contribution to overall latency." — evidence: `AlertServiceImpl.java:1-357` (no observability annotations, no log calls — verified by grep) — severity: LOW
