## What

ODD identifies a GitHub-authenticated user by the claim that `user-name-attribute` selects - the GitHub example configures `login` (the handler reads `provider.getUserNameAttribute()` with **no fallback**, so `login` is the configured value, not a code default) - and uses the `(username, "github")` tuple as the compound key for `USER_OWNER_MAPPING`. GitHub `login` is **mutable** (users can rename freely; the old login is released after 90 days). After a rename, the user signs in as a new identity (`alice2, github`); the prior `(alice, github)` mapping row is orphaned. There is no `id`-based fallback and no migration tool, so the user's **My Objects** goes empty and their ownership is stranded under the old name - silently.

> **Corrected 2026-05-30** (during the DOC-312 re-review): the original draft asserted "the default `user-name-attribute: login`". There is **no such code default** - `GithubUserHandler` reads `provider.getUserNameAttribute()` verbatim with no fallback (`GithubUserHandler.java:53`), the config POJO field has no default (`ODDOAuth2Properties.java:44`), and an unset value throws at `DefaultOAuth2User` construction. `login` is what the GitHub example configures, not a default. The orphan hazard is unchanged; only the false-default framing was corrected (same fix shipped to the paired doc, `backlog/docs/DOC-312.md`).

## User-facing impact

Static-trace-verified end-to-end (the identity key, the compound-key lookup, and the consumers that turn the mapping into UI were all read against source HEAD); not driven on a live GitHub-OAuth stack. Auth mode: applies only when ODD runs under **OAuth2 with the GitHub provider** (the affected handler is `@Conditional(GithubCondition.class)`); inert under DISABLED/LOGIN_FORM/LDAP.

- The owner association resolves through `AuthIdentityProviderImpl.fetchAssociatedOwner()` -> `getAssociatedOwner(username, provider)`, keyed on the GitHub `login`. After a username rename, `authentication.getName()` returns the new login, the `(OIDC_USERNAME, PROVIDER)` lookup misses the old row, and the user is treated as a brand-new identity with no owner.
- That association is consumed across multiple user surfaces - verified by grepping the consumers of `fetchAssociatedOwner`: **My Objects search + count** (`SearchServiceImpl.java:106,128`), **associated alerts** (`AlertServiceImpl.java:84,93,235`), **activity feed** (`ActivityServiceImpl.java:194,239`), data-collaboration, and data-entity relations. So a rename silently empties the renamed user's My Objects, their owned-alert views, and their activity scoping - no error, no re-link prompt.
- The pre-existing ownership rows (`USER_OWNER_MAPPING`, ownerships) strand under the old login; because GitHub releases a freed login after ~90 days, a third party could later claim it (lower-likelihood identity-reassignment concern). No migration tool exists; the durable fix is keying on the stable numeric `id`.

Remaining check before a definitive runtime claim: drive a GitHub-OAuth stack, associate an owner, rename the GitHub login, and confirm My Objects empties and the old `USER_OWNER_MAPPING` row is orphaned.

## Why it matters

A routine GitHub username change (rebrand, name change, handle cleanup) silently breaks a user's owner association - their personalised views empty out and their ownership records strand under a name they no longer use, with no error and no automatic re-link. Because the old login is later claimable by a third party, there is also a (lower-likelihood) identity-reassignment concern. The doc-side caveat (`backlog/docs/DOC-312.md`) warns operators, but the durable fix is a stable identity key.

## Suggested fix

- Key the identity / `USER_OWNER_MAPPING` on the **stable GitHub numeric `id`** (carry the `login` as a display attribute only), or
- Add an `id`-based fallback + a one-shot migration that re-links existing `(login, github)` rows to `id`, or
- At minimum, surface a maintenance action / documented `USER_OWNER_MAPPING` migration query for operators to run around a known rename (this is what DOC-312 will tell operators to do in the interim).
- The same mutable-key concern applies to other providers that default to a renameable principal - worth an audit across the `*UserHandler` family.
