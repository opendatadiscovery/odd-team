- **REFACTOR-407** (NEW 2026-05-19O): Azure post-logout redirect URI has NO platform-side allowlist — the redirect target is derived from the inbound Host header. A misconfigured reverse proxy that forwards a user-controlled Host or X-Forwarded-Host header without sanitization would propagate that into the Azure logout request. The only mitigation is Azure's own validation against the App Registration's registered Logout URLs
  - **Category**: open-redirect
  - **Surfaced by**:
    - `AzureLogoutSuccessHandler.md:bugs_limitations_corner_cases.[1]` (MEDIUM)
    - `AzureLogoutSuccessHandler.md:security.known_security_gaps.[1]` (MEDIUM)
  - **Statement**: `AzureLogoutSuccessHandler.java:40` derives the `post_logout_redirect_uri` from `UriUtils.getBaseUri(requestUri)` (the inbound HTTP request's URI). The Host header is operator-controlled at deployment (via the reverse proxy) but request-controlled at runtime — a forwarded `X-Forwarded-Host` that the proxy trusts and synthesises into the request URI propagates to the post-logout redirect. The platform does NOT carry an operator-side allowlist of valid post-logout-redirect URLs to cross-check against. The mitigation is that Azure validates `post_logout_redirect_uri` against the App Registration's registered Logout URLs and rejects unregistered targets (per Microsoft Entra ID standard behaviour) — so the Azure-side allowlist is the only protection against open-redirect via a forged Host header. An operator who has set up Azure to accept wildcard or multiple Logout URLs (e.g., for multi-environment App Registration sharing) removes that bound; the platform's contribution is the inbound Host header, which becomes the open-redirect target. The docs do not surface this dependency.
  - **Evidence**: `AzureLogoutSuccessHandler.java:40` + `UriUtils.java:11-22` + Grep of `application.yml` for `platform.base-url|odd.platform-url|allowed.redirect` returning no match
  - **Existing-ADR-or-implied-prescription**: ADR-CANDIDATE-133 NEW (post-logout redirect URI inbound-request-derived) — the architectural decision is documented; this gap is the open-redirect consequence. The maintainer accepts the reverse-proxy-trust delegation; the doc-side commitment is to flag the reverse-proxy Host-header policy.
  - **Proposed remedy**: Either (a) add an `odd.platform-url` config field and cross-check the inbound Host against it; reject mismatches with 400; (b) document the reverse-proxy-Host-header-trust requirement in the live OAuth2/OIDC page; (c) add a `WebFilter` that asserts `Host == configured-host` for sensitive paths (login, logout). Doc-only fix is fastest; cross-check fix is structural. The maintainer should pick based on the deployment-shape assumptions.
  - **Severity rationale**: MEDIUM — open-redirect via Host header forgery requires a misconfigured reverse proxy + a forgiving Azure allowlist. Bounded by Azure's standard validation; sharper risk in multi-tenant proxy setups.
  - **Suggested backlog grouping**: `OAuth2 hardening sprint` (paired with REFACTOR-403 Cognito dynamic logout_uri allowlist coupling + DOC-NNN on reverse-proxy Host-header policy)
