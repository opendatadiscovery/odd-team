## What

The token-reveal widget shared by **Collectors** and **Data Sources** (two near-identical components) has four distinct UX/security weaknesses that are best fixed as one cluster because they share the same code and the same data shape:

1. **No grace / "this breaks the running collector" warning on regenerate.** The regenerate confirmation dialog asks only "Are you sure you want to regenerate token for this datasource/collector?" — it does not tell the operator that the old token stops working immediately, so any currently-running collector using it will start failing auth.
2. **The one-shot plaintext token is fragile.** A freshly generated/regenerated token is the *only* time the real plaintext value is available from the server; after that the API returns a masked value. The component decides "masked vs plaintext" on **every render** by inspecting the token value, and the value lives in the same redux entity that the surrounding list refetches — so an ordinary list refresh replaces the plaintext with the masked value and the operator loses their one chance to copy it, with the only recovery being a **destructive re-rotation** (which itself invalidates the token they just created).
3. **Masked-vs-plaintext detection is a duplicated magic-string bet.** Both components independently decide the token is masked with `token.value.substring(0, 6) === '******'`. There is no shared constant and no server-provided "is masked" flag; the UI is reverse-engineering server state from the first six characters of a string in two places that can drift apart.
4. **Plaintext is rendered into a plain DOM text node and held in redux.** The token is printed directly as visible text (no `type="password"`, no reveal-on-hover/click affordance) and sits in the redux store as plaintext, so it is exposed to shoulder-surfing and to anything inspecting the DOM/store for as long as the row is shown unmasked.

## Where

Both components are byte-for-byte parallel on the relevant lines.

`components/Management/DataSourcesList/DataSourceItem/DataSourceItemToken/DataSourceItemToken.tsx:25-49`
`components/Management/CollectorsList/CollectorItem/CollectorItemToken/CollectorItemToken.tsx:25-49`

```tsx

  setIsHidden(dataSource.token.value.substring(0, 6) === '******');

```


## Why it matters

These are silent-until-painful failures on a security-sensitive surface (ingestion auth tokens). Half 1 + half 2 combine into a real foot-gun: an operator regenerates a token (no warning that the running collector will immediately 401), then loses the one-shot plaintext to a routine list refresh, and the *only* documented escape is to regenerate **again** — compounding the outage. Half 3 is a maintainability/correctness hazard: a server-side change to the masking prefix silently breaks the reveal logic in two un-linked places. Half 4 keeps a live secret as visible text in the DOM and in redux with no masking affordance. None of these loses data, so the cluster is medium — but on a credentials surface the cumulative UX is exactly the kind operators remember.

## Suggested fix

Consolidate the two components onto one shared token-reveal element and fix all four halves together:

1. Add a regenerate warning to the dialog text: the old token is invalidated immediately and any running collector/datasource using it will fail authentication until reconfigured.
2. Persist the one-shot plaintext locally (component/redux state keyed to "just generated") so a background list refetch does **not** clobber it; clear it only on an explicit dismiss/copy action.
3. Replace the `substring(0, 6) === '******'` bet with a single shared constant and, ideally, a server-provided `masked: boolean` (or equivalent) on the token DTO so the UI stops inferring server state from a string prefix.
4. Render the value through a masked affordance (`type="password"` / reveal-on-hover or reveal-on-click) rather than a plain visible text node, and avoid holding plaintext in the store longer than the reveal interaction needs.

Open to alternatives on the DTO change (a server `masked` flag is cleaner but is a contract change); the front-end halves (1, 2, 4) and the shared-constant part of half 3 can land without backend coordination.
