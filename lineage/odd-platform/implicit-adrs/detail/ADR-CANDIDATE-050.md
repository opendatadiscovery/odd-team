- **ADR-CANDIDATE-050** (NEW 2026-05-12E): Read-side permission discovery and write-side authorization enforcement share **ONE evaluation graph** — `PermissionController#getResourcePermissions` consumes the SAME `PermissionService` bean + the SAME `ContextualPermissionExtractor` chain that `AuthorizationCustomizer` consumes for mutation gating. The decision is structural: the platform deliberately exposes the policy-evaluation pipeline as a first-class endpoint so the UI does not have to reconstruct policy semantics client-side, AND every read returns AUTHORITATIVE results (the same set the mutation enforcer would compute), NOT a UI-only hint
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar (`getResourcePermissions`) but the structural shape is anchored across three independent code sites: (a) `PermissionController.java:17, 20-25` delegates to `permissionService`; (b) `OAuthSecurityConfiguration.java:87-98` wires the SAME `permissionService` bean into `AuthorizationCustomizer`; (c) `AbstractContextualPermissionExtractor.java:25-35` is the shared evaluation method used by both read and enforce paths. The cross-cutting reuse IS the design
  - **Surfaced by**:
    - `odd-platform__java__PermissionController__controller-method__getResourcePermissions.md:implicit_adrs.[0]` ("Read-side permission discovery is a first-class endpoint, not a derived computation client-side — the platform deliberately exposes the policy-evaluation pipeline as `GET /api/resource/{type}/{id}/permissions` so the UI does not have to reconstruct policy semantics. The decision is structurally visible: the same `PermissionService` bean and the same `ContextualPermissionExtractor`s are wired into `OAuthSecurityConfiguration.AuthorizationCustomizer` for mutation enforcement AND consumed by this controller for UI discovery — the read path and the enforcement path share one evaluation graph, which is the architectural decision." — intent_anchor: `new AuthorizationCustomizer(permissionService, extractors)` at OAuthSecurityConfiguration.java:98 + `private final PermissionService permissionService;` at AuthorizationCustomizer.java:16)
    - `odd-platform__java__PermissionController__controller-method__getResourcePermissions.md:implicit_adrs.[1]` ("Authoritative server-side evaluation, not UI-only hint — the response is the **same** permission set that would be enforced if the user attempted the mutation, computed via the **same** policy graph the mutation enforcer uses. The decision is to never trust a UI-shaped permission cache: every read recomputes against the live policy/role tables.")
  - **Decision statement**: ODD treats the policy-evaluation graph as the SINGLE source of truth for both read-side discovery ("what can this user do on this resource?") and write-side enforcement ("is this mutation request allowed?"). Concretely: (a) the same `PermissionService` Spring bean is injected into `PermissionController` (read) AND `AuthorizationCustomizer` (enforce); (b) the same `List<ContextualPermissionExtractor>` (DataEntityPermissionExtractor, TermPermissionExtractor, QueryExamplePermissionExtractor) is consumed in both paths; (c) `AbstractContextualPermissionExtractor.getContextualResourcePermissions` is the shared evaluation method that takes `(resourceId, policies)` and returns `Flux<Permission>` — read and enforce differ only in the consumer of the result (controller serialises; customizer matches against the request's required permission). The decision codifies: (1) UI button-enabled state reflects ACTUAL mutation rights, not approximations; (2) policy/role changes are reflected on the next call without cache invalidation; (3) a regression that diverged the read-path's evaluation from the enforce-path's would BREAK the platform's UI semantics — they cannot drift because they share the same code. Trade-off accepted: every UI page render triggers the full 4-query fan-out per resource (REFACTOR-191 captures the N+1 perf gap), traded for evaluation-consistency that the maintainer prioritises over latency.
  - **Wisdom test**: PASS. The shared-bean wiring is the intent anchor — the maintainer chose to NOT introduce a separate `PermissionDisplayService` for read-side hints; the maintainer chose to NOT cache the evaluation results. Both are structural choices visible at the dependency-injection layer. The alternative (UI-side permission caching or a separate display path) would be a structural change against this ADR.

  - **Severity rationale**: HIGH — security-architecture decision underlying every UI permission gate and every mutation enforcement. A future "let's add a UI permission cache" proposal is the kind of structural change this ADR forces a conversation about.
