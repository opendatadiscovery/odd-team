- **REFACTOR-410** (NEW 2026-05-19O): Multi-replica deployments without shared session store leave orphaned WebSessions on non-logout-handling pods. The default Spring in-memory WebSession store means a logout on pod A clears pod A's session, but pods B and C retain the user's session attributes if the user's load balancer routing differed earlier in the session
  - **Category**: no-multi-replica-session
  - **Surfaced by**:
    - `AzureLogoutSuccessHandler.md:performance.known_performance_gaps.[0]` (MEDIUM)
    - `CognitoLogoutSuccessHandler.md:performance.scaling_characteristics` (informational)
  - **Statement**: ODD Platform defaults to Spring's in-memory `WebSession` store (no `@EnableSpringWebSession` bean wired per `OAuthSecurityConfiguration.java:1-269`). For multi-replica deployments, the WebSession lives only on the pod that handled the original OAuth2 callback. If the logout request lands on a different pod (sticky-session misconfiguration, or load balancer routing change), `exchange.getExchange().getSession()` resolves an EMPTY session on the new pod, `WebSession::invalidate` is a no-op, and the user appears logged out on the original pod but their session persists silently on others until natural TTL. This is a deployment-time concern (operator must configure sticky sessions OR a shared session store like Redis); the platform does not enforce or document either.
  - **Evidence**: `AzureLogoutSuccessHandler.java:47` (the WebSession::invalidate call — assumes single-pod session) + `OAuthSecurityConfiguration.java:1-269` (no `@EnableSpringWebSession` bean, no Redis/Hazelcast session-store wiring) + the symmetric pattern across all 5 sibling logout handlers
  - **Existing-ADR-or-implied-prescription**: No existing ADR. The default Spring in-memory WebSession is the implicit choice; multi-replica deployment is a deployment-time concern the operator manages. The gap is doc-completeness AND a missing optional-config affordance for shared session stores.
  - **Proposed remedy**: Either (a) document the sticky-session OR shared-session-store requirement in the live deployment docs; (b) add optional shared-session-store wiring via `@ConditionalOnProperty` on a `spring.session.store-type` property (Spring Session supports Redis, JDBC, Hazelcast out-of-box); (c) at minimum, add a startup INFO log enumerating "WebSession in-memory; ensure sticky-session or shared store for multi-replica deployments". The maintainer should pick based on operational complexity tolerance.
  - **Severity rationale**: MEDIUM — affects multi-replica deployments (a real operator scenario). Symptom is subtle (user appears logged out on one tab but stays logged in on another); not security-critical (the user's intent is met for the active session); compliance-shaping for stringent immediate-cross-replica-logout requirements.
  - **Suggested backlog grouping**: `Deployment hardening sprint` + DOC-NNN (live deployment docs for multi-replica session-store guidance)
