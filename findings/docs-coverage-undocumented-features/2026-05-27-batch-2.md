#### Finding F-002a: REFACTOR-217 silent authorization bypass — SecurityConstants `/term` SINGULAR vs OpenAPI `/terms` PLURAL
- **Verdict**: STATIC-INFERRED · `drift` · **HIGH severity** · ontology-confirmed (substrate batch K + F-002 primary_drift_class)
- **Source-of-truth**: `Ontology[F-002:observed_vs_expected.facet=permission-gate enforcement under DISABLED]` → `Repo[odd-platform-api/src/main/java/.../auth/util/SecurityConstants.java:238, 241]` AND `Repo[odd-platform-specification/openapi.yaml:973, 1042]`
- **What the doc says**: implies the link operation is gated by `DATA_ENTITY_ADD_TERM`.
- **What the code does**: the SecurityRule path matcher binds to `/api/dataentities/{data_entity_id}/term` (singular) but the actual endpoint exposed via OpenAPI is `/api/dataentities/{data_entity_id}/terms` (plural). The matcher never fires; the gate falls through to global `.authenticated()`. Any authenticated user under LOGIN_FORM/OAUTH2/LDAP can link any term to any data entity regardless of `DATA_ENTITY_ADD_TERM`.
- **Operator-visible consequence**: deployments that allocated `DATA_ENTITY_ADD_TERM` to a restricted role believe the link operation is gated — every authenticated user can perform it.
- **Suggested fix**: Either (a) change SecurityConstants to PLURAL `terms` (aligns with the spec; minimal-risk fix); OR (b) add a build-time validator that compares SECURITY_RULES paths against OpenAPI paths (closes the entire path-mismatch CLASS — would also catch the symmetric DELETE half).
- **Dedup**: NEW at scanner level. Substrate identifies it but no DOC-GAP captures the live-doc-versus-code drift specifically.

#### Finding F-002b: Description-edit auto-link side-channel silently bypasses DATA_ENTITY_ADD_TERM (the API gate plus the side-channel)
- **Verdict**: STATIC-INFERRED · `missing-caveat` · MEDIUM severity · ontology-confirmed
