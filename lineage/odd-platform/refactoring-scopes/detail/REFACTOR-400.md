- **REFACTOR-400** (NEW 2026-05-19O): OAuth user handlers have NO null-guard on `provider` lookup — if `oAuth2Properties.getClient().get(registrationId)` returns null (theoretically a Spring framework guarantee violation but possible during dynamic reconfigure), the handler dereferences a null `provider` and throws NPE. Uniform across Google/GitHub/AbstractOIDCUserHandler/ODDIAMUserHandler
  - **Category**: missing-validation
  - **Surfaced by**:
    - `GoogleUserHandler.md:bugs_limitations_corner_cases.[4]` (LOW)
  - **Statement**: `GoogleUserHandler.java:46` (`final ODDOAuth2Properties.OAuth2Provider provider = oAuth2Properties.getClient().get(registrationId);`) — no null-guard. If `registrationId` isn't present in the map (a Spring framework guarantee violation, but possible during reconfigure-without-restart scenarios with dynamic Spring contexts), `provider` is null and line 50 (`provider.getAllowedDomain()`) throws NPE. The other handlers (`AbstractOIDCUserHandler.java:28`, `GithubUserHandler.java:52`, `ODDIAMUserHandler.java:35`) have the same pattern — uniformly no null-guard. The fragility is shared across all handlers, not specific to Google.
  - **Evidence**: `GoogleUserHandler.java:46-50` (no null-guard) + `AbstractOIDCUserHandler.java:28` + `GithubUserHandler.java:52` + `ODDIAMUserHandler.java:35` (4 handler files, same pattern, no guard)
  - **Existing-ADR-or-implied-prescription**: ADR-CANDIDATE-034 (OAuth provider-quirks strategy) — the chain-of-responsibility pattern delegates per-provider config lookups to each handler. The shared pattern is the maintainer-extension contract; adding a null-guard is refactoring within existing structure.
  - **Proposed remedy**: Add a null-guard at the top of `enrichUserWithProviderInformation` in each handler: `if (provider == null) return Mono.error(new OAuth2AuthenticationException("invalid_token", "OAuth2 client config missing for registrationId=" + registrationId));`. Better-yet, refactor to a shared utility `getProviderOrThrow(registrationId)` that the handlers consume. The fix is one helper + N call-site changes (small refactor).
  - **Severity rationale**: LOW — Spring guarantees `registrationId` is bound at `ClientRegistration` registration; only triggers in pathological reconfigure scenarios. Not security-critical; defensive-code-quality improvement.
  - **Suggested backlog grouping**: `OAuth2 hardening sprint` (paired with REFACTOR-396 — both are defensive-coding improvements for the handler family)
