## Description

Live `/user-owner-association` lines 22-23 imply happy-path completion: "After all these steps user will have an associated owner which can be used across the platform." Nothing about post-approval lifecycle.

Code reality (sidecar reference `OwnerAssociation.tsx:32-89`): once a user is bound (`identity && ownership`), the home-page OwnerAssociation surface renders the populated Recommended panel — there is NO "Disassociate" button, no "Re-request" affordance, no "switch Owner" link. The Branch 3 (DECLINED) flow shows the form again but does not pre-populate the previously-submitted name; the user starts from scratch. Lifecycle is effectively one-shot per outcome.

Operator-visible consequence: a user who picked the wrong Owner on first login has NO self-service recovery path; they must contact an admin who runs the F-173 Active-tab Remove flow (which itself is undocumented — see F-173a → DOC-222). Cascade discoverability gap: the user cannot google "how do I switch my owner association" because the docs are silent on both the absence of a self-service path AND the operator-side remove flow.
