## The root cause, captured from a Playwright trace rather than inferred

```
console  net::ERR_NETWORK_CHANGED
pageError TypeError: Failed to fetch dynamically imported module:
          http://localhost:18082/assets/Search-IgjLSmJj.js
```

Chromium aborts in-flight requests with `net::ERR_NETWORK_CHANGED` when the HOST's network configuration
changes. A full regression does that constantly: every suite and several individual specs create and destroy
their own compose networks (`probe-stacks_default`, `oddlf_default`, `oddemo154_default` all appear in one run's
log). When the abort lands on one of the SPA's code-split route chunks, React Router's lazy import rejects, and
because `odd-platform-ui` ships **no error boundary** the page renders BLANK.

Every locator on a blank page is absent. So the failure surfaces as whatever that spec happened to wait for -
`search-results-count`, `account of current user`, `Search terms...`, a row by name - which is why it has been
re-attributed, spec by spec, as an unrelated wait/isolation problem for months.

## Why this is worth an item: it is indistinguishable from a regression, and it is not rare

Measured on the CTRIB-067 regression (SUT built from the branch) against a `ref:main` A/B on the same box:

| set | count | what it is |
|---|---|---|
| fail on BOTH branch and main | 12 | the real baseline (TST-059's eleven + TST-057's swagger straggler) |
| fail on the BRANCH only | 7 | **all 7 pass on retry** - 32/32 green re-running the six specs |
| fail on MAIN only | 4 | same class, other side of the A/B |

The `main`-only column is the proof that this is noise rather than a change: nobody would claim a Last-viewed
search facet *fixed* `entity-alerts-display`, `entity-owners-display` or `term-linked-terms-tab`.

`multilingual-i18n` makes it sharpest - it failed at `:65` on one run and `:258` on the other. Different cases,
one per side.

`my-data-scope-narrows` looked genuinely branch-specific for three runs (`:434` failed on the branch 3/3 and
passed on main) until the trace was opened: `ERR_NETWORK_CHANGED` on `Search-*.js`. Its sibling `:388` shows the
mirror image on main. Both cases have now passed AND failed on identical code.

## The fix shape

`recently-viewed-facet.spec.ts` already carries the guard, written when this was first root-caused:

```ts
// reload ONCE on a "Failed to fetch dynamically imported module" page error, then wait again
page.on('pageerror', e => { if (/dynamically imported module/.test(e.message)) bootFailed = true; });
```

That is a retry of the NAVIGATION, not of an assertion - every oracle still runs exactly once, against a page
that actually rendered, and the suite keeps `retries: 0`.

Promote it to a **shared helper** (`helpers/`) and adopt it in the specs above. Three properties matter:
1. it must fire only on that specific page error, never on a generic timeout - otherwise it masks real failures;
2. it must reload rather than re-assert;
3. `retries: 0` stays, because a regression pin must never be masked by a blanket retry.

An alternative worth costing first: an **error boundary** in `odd-platform-ui`. A failed lazy import would then
render a retry affordance instead of a blank page, which fixes it for USERS on a flaky network as well as for the
suite. That is an upstream change (odd-platform), so it belongs in its own issue if taken.
