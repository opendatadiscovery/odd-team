## Description

The "Supported field types" table on `lookup-tables.md` (line 76) maps the `JSON` field type to PostgreSQL `json`. That is wrong: the platform stores it as `jsonb`.

`LookupTableColumnTypes.TYPE_JSON` is declared `TYPE_JSON(JSONB, "JSON", DataSetFieldType.TypeEnum.STRUCT, new LookupJSONBValidator())` — the first constructor arg is the jOOQ `DataType`, and it is `SQLDataType.JSONB` (LookupTableColumnTypes.java:48, import at line 24). The validator confirms it: `LookupJSONBValidator` imports `SQLDataType.JSONB` (LookupJSONBValidator.java:10) and returns `JSONB.defaultValue(...)` from `getDataTypeWithDefaultValue` (LookupJSONBValidator.java:15). So the user-facing field-type label `JSON` provisions a PostgreSQL `jsonb` column, not a `json` column.

This is not a cosmetic distinction for the audience this page explicitly serves — the page's "Direct database access" section (lines 109-140) tells BI / ETL / ad-hoc-SQL consumers to read these tables straight from PostgreSQL. `jsonb` and `json` are materially different storage types: `jsonb` is a decomposed binary form that does **not** preserve insertion order of object keys, strips insignificant whitespace, and keeps only the last value for duplicate keys; `json` preserves the input text verbatim. A consumer who relies on key order, byte-for-byte round-tripping, or duplicate-key semantics — or who casts/compares the column assuming `json` — will get different behaviour than the doc implies.
