- **REFACTOR-404** (NEW 2026-05-19O): Cognito logout has NO token-revocation step — the handler clears the local Spring WebFlux session and redirects to Cognito's `/logout`, but does NOT call Cognito's `/oauth2/revoke` endpoint. Spring's OAuth2 client retains the authorized-client record with a valid (until expiry) access token; an attacker who exfiltrated the access token before logout can continue using it. Asymmetric vs. Google + GitHub handlers which DO revoke server-side
  - **Category**: missing-defence-in-depth
  - **Surfaced by**:
    - `CognitoLogoutSuccessHandler.md:bugs_limitations_corner_cases.[3]` (MEDIUM)
    - `CognitoLogoutSuccessHandler.md:security.known_security_gaps.[0]` (MEDIUM)
  - **Statement**: `CognitoLogoutSuccessHandler.java:33-50` clears the local Spring WebFlux session and redirects to Cognito's `/logout` endpoint, but does NOT explicitly call Cognito's token-revocation endpoint at `https://<pool>.auth.<region>.amazoncognito.com/oauth2/revoke`. Spring's OAuth2 client may retain the authorized-client record in `ReactiveOAuth2AuthorizedClientService` with a valid (until expiry) access token. Compare with `GoogleLogoutSuccessHandler.java:43-54` which DOES call `https://oauth2.googleapis.com/revoke` to invalidate the access token, and `GithubLogoutSuccessHandler.java:51-63` which calls `DELETE /applications/{client_id}/grant` to revoke the grant. Cognito's handler does neither — relying entirely on Cognito's `/logout` endpoint to drop the User Pool session cookie. An attacker who exfiltrated the access token before logout can continue using it against Cognito-issued downstream APIs until the token expires (default 1 hour for Cognito access tokens). The Cognito User Pool session cookie is dropped, but the OAuth2 tokens are not revoked server-side.
  - **Evidence**: `CognitoLogoutSuccessHandler.java:33-50` (no /revoke call) + `GoogleLogoutSuccessHandler.java:43-54` (contrast: does call /revoke) + `GithubLogoutSuccessHandler.java:51-65` (contrast: calls grant delete) + AWS Cognito `/oauth2/revoke` docs (the endpoint EXISTS and could be called)
  - **Existing-ADR-or-implied-prescription**: ADR-CANDIDATE-132 NEW (per-provider revocation strategy — Google/GitHub explicit vs. Cognito/Azure/ODDIAM end-session-only) — this gap is consistent with the documented stance but inconsistent with what's TECHNICALLY POSSIBLE for Cognito. Cognito's `/oauth2/revoke` endpoint exists and could be called; the platform chose not to. The maintainer's intent: rely on Cognito's `/logout` (the end-session-redirect pattern). The gap is whether to add the optional `/oauth2/revoke` call for defence-in-depth.
  - **Proposed remedy**: Add an optional outbound POST to `https://<pool>.auth.<region>.amazoncognito.com/oauth2/revoke` BEFORE the local WebSession::invalidate. The revocation requires the access token (from the OAuth2AuthorizedClient) and is fire-and-forget (don't block the logout flow on its result). Compose with the existing redirect flow. Alternatively, document the choice and instruct operators with stringent compliance requirements to configure Cognito-side token TTLs to the minimum acceptable value.
  - **Severity rationale**: MEDIUM — asymmetric vs. siblings; security-architecture-defining (operators with stringent compliance requirements need to know which provider has stronger revocation). Not load-bearing security issue (the WebSession is invalidated; the token TTL is short); but a defence-in-depth opportunity.
  - **Suggested backlog grouping**: `OAuth2 hardening sprint` (paired with REFACTOR-402 Cognito federated-IdP signout + REFACTOR-408 Azure no revocation — the broader per-provider asymmetry surface)
