## What

The Resolve/Reopen button on the **global Alerts list** alert row implements **post-action permission discovery**: the button renders unconditionally enabled; clicking it dispatches `fetchResourcePermissions(...)`, then on success checks whether `[...globalPermissions, ...resourcePermissions]` includes `DATA_ENTITY_ALERT_RESOLVE` and either calls `dispatchUpdateAlertStatus()` OR sets `disableResolve=true` and renders a "No access!" caption inline. **Users learn permissions by clicking.**

**Correction (the load-bearing falsification).** An earlier revision claimed "the component is shared across the global Alerts list AND the per-entity Alerts tab; the anti-pattern surfaces wherever an alert row is rendered." That is FALSE - there are two *different* components:

- Global Alerts list (`Alerts/AlertsList/AlertItem/AlertItem.tsx`, rendered by `AlertsList.tsx:96`) - has the anti-pattern.
- Per-entity Alerts tab (`DataEntityDetails/DataEntityAlerts/DataEntityAlertItem/DataEntityAlertItem.tsx`, rendered by `DataEntityAlerts.tsx:79`) - does NOT. It wraps the Resolve button in `<WithPermissions permissionTo={DATA_ENTITY_ALERT_RESOLVE}>` (`DataEntityAlertItem.tsx:111-120`), so for an unprivileged user the button is simply HIDDEN. The route itself is additionally gated by `WithPermissionsProvider` + `RestrictedRoute` (`DataEntityDetailsRoutes.tsx:70-84`). No post-action discovery on this surface.

So the anti-pattern is confined to the GLOBAL Alerts list. The defect is real, re-scoped to that one surface.

## User-facing impact

- WHO: a user viewing the GLOBAL Alerts list (`/alerts`) whose role lacks `DATA_ENTITY_ALERT_RESOLVE` on some/all of the listed alerts' data entities. (The per-entity Alerts tab is NOT affected - its button is hidden for such users.)
- WHAT they do: click the always-enabled Resolve / Reopen button on a row to action the alert.
- WHAT they observe: a brief loading state (`isUpdating`), then - if not permitted - the button becomes disabled and a "No access!" caption appears inline; the alert is not resolved. Verified by FE trace 2026-06-10: `AlertItem.handleResolve` (`AlertItem.tsx:48-70`) renders the button enabled (`:158-165`), fetches resource permissions on click, and on a permission miss sets `disableResolve=true` -> "No access!" caption (`:166`). The action does not commit (the FE gate short-circuits before dispatch; the BE gate is also real), so no data is changed - this is a UX surprise, not a data-integrity issue. Pure code-structure fact on the global-list component; whether a given user lacks the permission depends on RBAC posture (only meaningfully enforced under LDAP / non-DISABLED auth locally), which is the only data-dependent part.

## Why it matters

Two operator profiles affected on the **global Alerts list**:

1. **Unprivileged user on the global Alerts list** clicks Resolve on each row to discover which ones they can action. Discovers the gate row-by-row. UX is "try, fail, learn, try next row."

2. **Privileged user whose role changed mid-session** clicks Resolve expecting success; instead sees a flash of the loading state followed by the "No access!" caption.

(The earlier "mixed-permission per-entity" profile and the "cross-cutting global + per-entity" compounding are dropped - the per-entity tab gates the button via `WithPermissions`, so it never exhibits this behaviour.)

The anti-pattern is recognisable industry-wide as "post-action authorization checking" - UI components that defer permission discovery until after the user commits an action. Standard practice is to render the button disabled-with-tooltip for unprivileged users + eagerly compute permissions for the visible rows on list-mount (exactly what the per-entity tab already does via `WithPermissions`).

Severity stays MEDIUM:
- The misclick doesn't destroy data (the FE short-circuits and the backend gate is real; the action is rejected); it's a UX surprise.
- It is now scoped to one surface (the global Alerts list), not two - but the global list is the primary alerts surface and the inconsistency with the per-entity tab's clean gating is itself the giveaway that this is an oversight.

## Suggested fix

**Three options, pick one:**

**Option A (recommended) - pre-fetch permission state for visible alerts on list-mount.** When the page renders, batch-fetch permissions for the rendered alerts; render each row's button disabled-with-tooltip for unprivileged rows.

```tsx
// AlertsList.tsx (parent)
const { data: alertPermissions } = useFetchAlertPermissions(alerts.map(a => a.id));

// AlertItem.tsx
const canResolve = alertPermissions[alert.id]?.canUpdate ?? false;
<Tooltip title={canResolve ? '' : t('You do not have permission to resolve this alert')}>
  <span>
    <Button onClick={handleResolve} disabled={!canResolve}>{t('Resolve')}</Button>
  </span>
</Tooltip>
```

**Option B - eagerly stamp the AlertList payload with a per-row `canResolve: boolean` field (backend computes once).** Smaller round-trip cost; backend already knows; UI renders cleanly.

```yaml
# components.yaml (AlertItem)
Alert:
  properties:
    ...
    canResolve:
      type: boolean
      description: "Whether the calling user has permission to resolve this alert"
```

**Option C - explicit empty-state framing - "you can view but cannot resolve" - replaces the per-row buttons for unprivileged users.** Less granular; might be the right shape when no alert in the visible page is resolvable.

Recommendation: **Option B** as the cleanest backend-led answer; Option A is the next-best if a payload-shape change is out of scope.
