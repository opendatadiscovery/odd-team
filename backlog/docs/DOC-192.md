## Description

The live `schema-diff.md` page (WebFetched 2026-05-27, 200 OK) covers revision creation on re-ingest, field-by-field comparison logic, and the UI-side compare workflow. The page is **silent on five load-bearing operator-visible behaviours** — three backend defects and two UI-tier amplifiers.

**Caveat 1 — Cross-dataset version-id leak (F-045a).** `ReactiveDatasetVersionRepositoryImpl.java:129` issues `.where(DATASET_VERSION.ID.eq(datasetVersionId))` — single predicate on `version_id` only. NO `data_entity_id` enforcement. The path component `data_entity_id` from `/api/datasets/{data_entity_id}/structure/{version_id}` is consumed by the controller and **dropped**. The `/diff` endpoint at lines 147-157 has the same predicate doubled. Any authenticated user enumerating `version_id`s reads any dataset's full schema (field names + types + descriptions + tags + terms + lookup-table definitions). Under `auth.type=DISABLED`, the leak is anonymous. The relationships page's "role-based visibility" claim (per F-045 facet) overstates the security model.

**Caveat 2 — UI URL-paste amplifier (F-191a).** `DatasetStructureCompare.tsx:24-26 + 30-35` reads `firstVersionId` and `secondVersionId` from `useQueryParams` and passes them directly into the fetch hook **WITHOUT** checking they appear in the loaded `datasetVersions` array. Paired with the backend leak, a pasted URL with version-ids from another dataset returns 200 with a structurally-valid but semantically-nonsense diff that the list-item renders blindly. The compare viewer is a TRUSTED audit surface; operators reasoning about "what changed between V1 and V2" can be misled by a forged URL from chat / docs / bookmark.

**Caveat 3 — Diff endpoint asymmetric error model (F-045b).** `DatasetVersionServiceImpl.java:69-71` throws bare `RuntimeException("Query returned %s rows for diff request")` when one or both ids don't exist → `ControllerAdvice` maps to 500. Identical version-ids get a clean `BadUserRequestException` → 400. A caller cannot distinguish "platform broken" (500) from "wrong id" (400) — common debugging workflow defeated.

**Caveat 4 — UI AppErrorPage swallows 4xx vs 5xx (F-191b).** `DatasetStructureCompare.tsx:46-51` catches all error states from the React Query hook into a single `<AppErrorPage>`. F-045b backend returns 500 on missing version-ids and 400 on identical version-ids; both bubble through this surface as the same AppErrorPage. A user typing a wrong id sees the same UI surface as a platform outage. The cross-link to F-045b is reader-load-bearing — the asymmetric backend defect is reachable via the UI but indistinguishable to the operator.

**Caveat 5 — "Latest" means max(version), not max(created_at) (F-045c).** `ReactiveDatasetVersionRepositoryImpl.java:160-217 (getLatestDatasetVersion)` at line 161: `Field<Long> dsvMaxField = max(DATASET_VERSION.VERSION).as("dsv_max")`. `created_at` is not referenced. Under normal ingestion (version monotonically increases) the two are equivalent; under manual SQL fixup or collector replay (operator re-ingests an old version), the two diverge. An operator reading `/api/datasets/{id}/structure` (no version_id) gets the max-VERSION row, which may be older than expected after a re-ingest scenario.
