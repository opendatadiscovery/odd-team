# DataEntityController#getMyObjectsWithUpstream — semantic understanding

## understanding

`getMyObjectsWithUpstream` (`GET /api/dataentities/my/upstream`) is a four-line controller pass-through (`DataEntityController.java:299-305`) — `(page, size, exchange) -> dataEntityService.listAssociated(page, size, LineageStreamKind.UPSTREAM).map(ResponseEntity::ok)` — that delegates to a **two-phase derived-set computation**: phase 1 is the **anchor set** (entities the user owns, resolved via `authIdentityProvider.fetchAssociatedOwner()` + `dataEntityRepository.listByOwner(ownerId)` at `DataEntityRelationsServiceImpl.java:26-28`); phase 2 is the **derived set** — the single-hop upstream lineage neighbours of the anchor set (computed by `lineageRepository.getLineageRelations(oddrns, LineageDepth.empty(), UPSTREAM)` at line 34, then explicitly **excluded** from the anchor set via `Predicate.not(oddrns::contains)` at line 37). The endpoint therefore returns **non-owned-but-reachable entities upstream of the user's owned set** — semantically the opposite of what the OpenAPI summary "Returns list of data entities owned by current user with upstream dependencies" claims (`openapi.yaml:843-844`). This is the **PRIMARY-SOURCE confirmation site** for REFACTOR-225 (anchor-set single-point-of-failure with no JOIN-side defence-in-depth) and DOC-GAP-099 (literal incorrectness of the OpenAPI summary); the UI consumer label `Upstream dependents` (`OwnerEntitiesList.tsx:87`) is semantically accurate, but the OpenAPI summary and live docs are not.

## bugs_limitations_corner_cases

- "**REFACTOR-225 PRIMARY-SOURCE confirmation: anchor-set single-point-of-failure with NO JOIN-side defence-in-depth.** The owner-scoping invariant for `/my/upstream` (and its `/my/downstream` sibling) is enforced at **exactly one site**: `DataEntityRelationsServiceImpl.java:26` (`authIdentityProvider.fetchAssociatedOwner()`). ## performance

- **hot_paths**:
  - "Per-caller anchor-set resolution + lineage CTE: each `/my/upstream` request issues (a) `SELECT owner.* FROM user_owner_mapping JOIN owner ...` (principal lookup), (b) `SELECT data_entity.* JOIN ownership WHERE ownership.owner_id = ?` (anchor-set materialisation), (c) the lineage-relations CTE base SELECT (`SELECT LINEAGE.* FROM LINEAGE WHERE CHILD_ODDRN IN (?, ?, ...)` for UPSTREAM, single-hop), (d) `SELECT data_entity.* WHERE oddrn IN (?, ?, ...) LIMIT ? OFFSET ?` (derived-set materialisation). Four DB round-trips per call. evidence: `DataEntityRelationsServiceImpl.java:26-34` + `DataEntityServiceImpl.java:223`"
  - "UI's `Recommended` panel mounts on every page load — `OwnerEntitiesList.tsx:58-64` fires `fetchMyDataEntitiesList`, `fetchMyUpstreamDataEntitiesList`, `fetchMyDownstreamDataEntitiesList`, `fetchPopularDataEntitiesList` in parallel; the four-DB-round-trip cost is paid per `/my/upstream` call alongside the other three concurrent endpoint calls"
- **throughput_characteristics**:
  - "single-call read — no batching across owners; each user's request is independent"
  - "reactive Flux response — entities stream from `jooqReactiveOperations.flux(...)` (`ReactiveDataEntityRepositoryImpl.java:252`); the response Mono completes once the Flux is wrapped"
  - "**in-memory derivation defeats reactive backpressure** — the lineage expansion at `DataEntityRelationsServiceImpl.java:35-38` (`.flatMap.distinct.filter.collectList()`) materialises the full deduplicated derived set in memory before passing to `listByOddrns`; for users with large anchor sets, the JVM holds the full derived oddrn list, then the SQL pagination is applied to that list"
- **resource_allocation**:
  - "no caching at the controller, service, relations service, or repository — every request hits Postgres four times (principal lookup + anchor materialisation + lineage CTE + derived-set materialisation)"
  - "the anchor-set query at `DataEntityRelationsServiceImpl.java:27` calls `listByOwner(o.getId())` with NO pagination — for a user with thousands of owned entities, ALL owned entity rows are fetched, the oddrn extracted, and the set materialised; only the FINAL derived-set is paginated by the `(page, size)` parameters"
  - "lineage CTE materialises a deduplicated parent_oddrn + child_oddrn set covering all single-hop neighbours of the anchor — width scales with anchor cardinality; the IN-clause cardinality is the gate"
- **scaling_characteristics**:
  - "stateless — instances scale horizontally"
  - "pagination via SQL `LIMIT/OFFSET` on the FINAL `listByOddrns` call (`ReactiveDataEntityRepositoryImpl.java:249-250`) — but the anchor and derived sets are materialised in full BEFORE pagination, so request cost is O(anchor-size + derived-size), not O(page-size)"
  - "no rate-limiting at the controller or service"
  - "**no ORDER BY on listByOddrns** — pagination is unstable across consecutive requests; for an entity set of size > page-size, repeated `page=1, size=5` and `page=2, size=5` may yield overlapping or missing entries"
- **known_performance_gaps**:
  - "**Anchor-set materialisation has no pagination.** `dataEntityRepository.listByOwner(o.getId())` at `DataEntityRelationsServiceImpl.java:27` fetches ALL owned entities for the user — for an admin owner or CI-bot owner owning thousands of entities, this fetches the entire owned-entity table-slice into the JVM before the lineage step. The cure is to either (a) cache the owned-oddrn set per-session (currently no caching), or (b) accept that this endpoint is meaningful only for small ownership cardinalities. severity: MEDIUM. evidence: `DataEntityRelationsServiceImpl.java:27` (no `(page, size)` parameters on the listByOwner call)"
  - "**Lineage IN-clause is unbounded.** `getLineageRelations(oddrns, LineageDepth.empty(), UPSTREAM)` constructs a CTE with `WHERE CHILD_ODDRN IN (?, ?, ...)` where the IN list is the full anchor-set oddrns. PostgreSQL has no hard limit on IN-list cardinality but planner cost is non-linear above ~1000 elements. severity: MEDIUM. evidence: `DataEntityRelationsServiceImpl.java:34` + `ReactiveLineageRepositoryImpl.java:160-176` (the CTE construction)"
  - "**In-memory deduplication defeats SQL pagination.** `.distinct().filter.collectList()` (`DataEntityRelationsServiceImpl.java:36-38`) materialises the full deduplicated derived-oddrn set in JVM memory before passing to `listByOddrns`. SQL `LIMIT 5 OFFSET 0` then slices the materialised list, but the cost-per-call is fixed by the unscoped derived set size. severity: MEDIUM. evidence: `DataEntityRelationsServiceImpl.java:35-38`"
  - "**No ORDER BY on listByOddrns produces unstable pagination.** `ReactiveDataEntityRepositoryImpl.java:247-250` builds `DSL.selectFrom(DATA_ENTITY).where(conditions).limit(size).offset(...)` with no `.orderBy(...)` call; Postgres does not guarantee order without an explicit ORDER BY. severity: MEDIUM (pagination correctness)."
