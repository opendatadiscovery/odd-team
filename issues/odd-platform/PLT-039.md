## What

The Management -> Associations -> "+ Create association" form (Branch C of the user-owner-association write-path family - see DOC-220) accepts any non-empty string in the `oidcUsername` field. There is:
- No format validation (it could be an email, a UUID, a free-text "alice", a typo)
- No existence check against the IdP
- No validation that the username corresponds to an actual identity record on file

The backend `POST /api/owners/mapping` then inserts the binding without resolving the username (the resolution semantics were not Read this session - even if the backend validates, the UI offers no feedback at submission time).

Outcome: an admin can bind an Owner to a username string that does not yet exist (or never will exist) in the IdP. The resulting `user_owner_mapping` row is an **orphan binding from day one**.

## Where

`odd-platform-ui/src/components/Management/OwnerAssociations/OwnerAssociationsHeader/OwnerAssociationForm/OwnerAssociationForm.tsx:62-76`


- `SecurityConstants.java:155-158` confirms the endpoint exists and is gated by `OWNER_RELATION_MANAGE`

## Why it matters

The downstream consumer of `user_owner_mapping` is `F-011` (Principal-to-Owner Resolution) - every authentication flow that maps an authenticated principal to their Owner row. With an orphan binding present (admin made a typo, or pre-bound a not-yet-onboarded user with a misspelled username), the intended user will silently NEVER be matched to the Owner the admin thought they bound. The user logs in, sees the home-page OwnerAssociation widget asking them to request a binding (because resolution missed them), submits a request - which the admin then approves - and now there are TWO `user_owner_mapping` rows for one human user, OR the original orphan blocks the new binding with a UNIQUE-constraint error (depends on the schema constraint - F-173c probe candidate).

Severity MEDIUM because:
- The defect is admin-side; end users are not directly affected
- BUT - orphan bindings accumulate quietly in the Owner-Association directory
- AND - the operator audit "who is bound to which Owner" returns rows that don't correspond to real users
- AND - composition with F-075b's self-mint side-door means a malicious admin (or one with a typo prone to a privileged username) can bind a real future username to a chosen Owner before that username arrives, pre-staging an attack on an OIDC-group-mapped principal

## Suggested fix

1. **Client-side validation pass**: add format validation appropriate to the deployment's identity-naming convention (email-shaped / non-whitespace string / charset filter). Provide an info hint in the form clarifying the expected format and naming the active IdP.
2. **Async existence check** (preferred when feasible): wire a backend endpoint (e.g. `GET /api/idp/users/{username}/exists` or a search-by-username surface) and call it on field blur. Show an existence warning when the username is not yet known to the IdP - but allow proceed (an admin may pre-bind a not-yet-onboarded user as a feature). The signal is a warning, not a hard error.
3. **Backend defensive validation**: at `POST /api/owners/mapping`, validate the format unconditionally; emit a 400 with a clear error code for typo'd usernames; emit a separate warning header / extended response body when the username is well-formed but unknown to the IdP at submit time.

Open to alternatives - the admin pre-staging use case is real (operators want to set up associations before a user logs in for the first time), so a hard-reject on missing IdP records is the wrong call.
