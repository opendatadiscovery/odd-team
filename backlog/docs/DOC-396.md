## Description

Custom-metadata field names are matched **case-insensitively** for the autocomplete suggestion list but **stored and resolved case-sensitively** against the catalogue. The two halves disagree: an operator who types `Cost_centre` gets a case-insensitive substring match for the *suggestion* list, but on accept the value is resolved (or auto-created) by **exact string**, so `cost_centre` and `Cost_centre` become two distinct `metadata_field` rows. There is no UI affordance to merge them and no normalisation on create — the duplicate is permanent until someone reconciles it at the database layer.

The live `custom-metadata.md` page already documents the asymmetry well (the "Field naming is case-sensitive" section states the suggestion list is a case-insensitive substring match while resolution is exact-string, and warns about case-drift duplicates). What it does **not** make explicit is (a) the underlying code that creates the asymmetry — the search predicate and the store predicate are two different jOOQ conditions on the same field — and (b) that there is **no merge path** once two case-variants exist, and (c) that a `normalise-on-create` fix is a roadmap candidate, not a current behaviour. An operator reading the current prose may assume "case-drift duplicates" are recoverable in-product; they are not. This item closes that residual gap and ties the prose to the consumer code so a future reader (and reviewer) can verify the claim.

This is the same class of asymmetry as Owner-name and Title-name duplicates (see owners.md "Lifecycle and known caveats" and DOC-397/DOC-398) — the cross-link makes the pattern legible without duplicating the explanation.

  - Search is case-INSENSITIVE — `ReactiveMetadataFieldRepositoryImpl.java:48`: `conditions.add(nameField.containsIgnoreCase(query));` inside `listInternalMetadata`, which powers the autocomplete suggestion list.
  - Store/resolution is case-SENSITIVE — `ReactiveMetadataFieldRepositoryImpl.java:65`: `METADATA_FIELD.NAME.eq(t.fieldName())` (exact equality) inside `listByKey`, the per-key catalogue resolution path. The ingest upsert (`ingestData`, lines 93-104) conflicts on the `IX_UNIQUE_EXTERNAL_NAME_TYPE` `(name, type)` index — i.e. uniqueness is by exact name, so `cost_centre` and `Cost_centre` do not collide and both persist.
  - No merge endpoint or normalisation-on-create exists on the metadata-field surface (no `merge`/`rename`/`normalise` in the repository or service tier).
