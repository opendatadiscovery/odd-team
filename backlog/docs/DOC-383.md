## ⚠️ VERIFICATION 2026-06-08 — BLOCKED — claim code-contradicted; do NOT implement as written

> **Adversarial fact-check (sev HIGH).** actuator/** is whitelisted ONLY under OAUTH2+LDAP (which wire AuthorizationCustomizer); under LOGIN_FORM only /actuator/health is open, the rest is authenticated() (LoginFormSecurityConfiguration.java:49-57). A "whitelisted in every mode" caveat is FALSE for LOGIN_FORM and contradicts login-form.md:40. Re-scope to oauth2-oidc.md + ldap.md only.
>
> Full report: `lineage/odd-platform/harvest/2026-06-08-doc-verification.md`.

## Description

`/actuator/**` is reachable **before** authentication in **every** auth mode — not only DISABLED — because `SecurityConstants.WHITELIST_PATHS` whitelists it (`SecurityConstants.java:96`: `{"/actuator/**", "/favicon.ico", "/ingestion/**", "/img/**", "/api/slack/events"}`). Under LOGIN_FORM, OAUTH2, and LDAP the rest of the app is `authenticated()` / OAuth-gated, but the whitelisted actuator paths bypass that gate the same way they do under DISABLED.

The exposure is **already documented in two places**: the `disabled-authentication.md` page (DOC-239, done) lists `/actuator/env` as one of the anonymously-reachable surfaces under DISABLED, and `odd-platform.md` (DOC-242, done) carries the canonical operator-side caveat + mitigation table ("Management endpoint exposure and credential hygiene": separate `management.server.port`, firewall `/actuator/**`, restrict `exposure.include`). What is **missing** is any pointer from the **other three auth-mode pages** — `login-form.md`, `oauth2-oidc.md`, `ldap.md` — so an operator who only reads their chosen mode's page never learns that turning auth on does **not** put actuator behind it. (Verified 2026-06-08: grep for `actuator` in all three pages returns nothing.)

**How this misleads an operator.** An operator who deploys LOGIN_FORM / OAUTH2 / LDAP reasonably believes "auth is on, so my endpoints are protected." The whitelisted `/actuator/**` is the exception, and their mode's page never tells them. The fix is a one-line cross-link from each of the three pages to the canonical caveat on `odd-platform.md`, so the operator lands on the mitigation table from whichever auth page they read.

**Scope note — do NOT over-state the exposure.** Per the 2026-05-29 correction recorded on both DOC-239 and DOC-242 (shipped as DOC-308): no `show-values` key is set anywhere, so Spring Boot 3.4.10's default `NEVER` applies — `/actuator/env` **masks every property value**. The real unauthenticated exposure is the **configuration-key schema** (which keys / property sources exist), **not** credential values and **not** the JDBC URL value. The cross-link prose must describe it as "configuration-key-schema exposure," never as "credentials/JDBC-URL leak."
