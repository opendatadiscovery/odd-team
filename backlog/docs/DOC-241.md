## Description

The live `configuration-and-deployment/odd-platform` page (WebFetched 2026-05-27 — DOC-059 baseline) documents the four session-provider options (IN_MEMORY / INTERNAL_POSTGRESQL / EXTERNAL_REDIS / EXTERNAL_POSTGRESQL) with their characteristics-and-caveats subsections. The page is **silent on four cookie / session-attribute / multi-replica caveats** that materially change what an operator deploying ODD must do at the proxy / cluster / cookie-stamp layer. Three of these are shipped defaults; one is a serialisation-format choice with deserialisation-gadget implications.

**Facet 1 — `spring.session.timeout: -1` shipped default — sessions NEVER expire (F-087a, HIGH→CRITICAL).** `application.yml:1-3` ships `spring.session.timeout: -1`. `JooqSessionRepository.java:138-148` computes `expiry_time = lastAccessedTime.plusSeconds(maxInactiveInterval.toSeconds())`; with negative timeout the expiry is effectively never reached. `PostgreSQLSessionHousekeepingJob.java:30` (`DELETE WHERE expiry_time < now()`) NEVER matches — `spring_session` table grows monotonically. Compromised cookies are valid indefinitely. A 1000-user platform with daily logins accumulates ~365K session rows annually under INTERNAL_POSTGRESQL; under IN_MEMORY the sessions live until JVM restart. **LSN-001-shape**: silent insecure default, doc-only warning absent, no programmatic guardrail.

**Facet 2 — No cookie attribute overrides — Secure/SameSite/HttpOnly delegated to proxy (F-087b, HIGH→CRITICAL).** `SessionConfiguration.java:1-65` has no `CookieWebSessionIdResolver` bean. Grep across the repo for `CookieWebSession|SameSite|HttpOnly|Secure.*cookie` returns ZERO matches. Secure flag, SameSite directive, HttpOnly override — all delegated to deployment topology. On a non-HTTPS deployment the cookie travels in clear; on a multi-tenant proxy with permissive `SameSite=Lax`, cross-site GET / top-level-navigation cookie leakage applies. No doc warns operators of this responsibility.

**Facet 3 — IN_MEMORY default breaks the collector session-bridge in multi-replica (F-087c, MEDIUM→HIGH).** `SessionConfiguration.java:28-30` makes `session.provider: IN_MEMORY` the shipped default. Multi-replica deployments behind non-sticky load-balancers see sessions per-process. The `/ingestion/datasources` collector-identity bridge (via `SessionConstants.COLLECTOR_ID_SESSION_KEY`) breaks on the second request hop, surfacing as HTTP 500 `IllegalStateException("Collector id is null")` (`IngestionController.java:50-58`). A multi-replica K8s deployment with default config sees flaky collector data-source registration.

**Facet 4 — Java-serialised session attributes under INTERNAL_POSTGRESQL — deserialisation gadget risk (F-087d, MEDIUM→HIGH).** `JooqSessionRepository.java:156, 188` uses `SerializationUtils.serialize/.deserialize`. Java native serialisation is deprecated in newer Spring versions for the deserialisation-gadget reason. A database compromise yields deserialisation gadgets on attribute-load.

## Acceptance Criteria

- [ ] The session-provider H2 cluster on odd-platform.md is extended with FOUR new caveats (extending — not replacing — the DOC-059 baseline characteristics-and-caveats subsections):
  - **A new "## Session lifetime and cookie posture" H2** (between the session-provider H3s and the next H2) covering:
    - **`spring.session.timeout` default is `-1`** — sessions never expire. Operators MUST set a finite value (recommendation: `30m` for an interactive UI; longer if S2S-driven). Document the housekeeping interaction: `PostgreSQLSessionHousekeepingJob` deletes via `expiry_time < now()`, which never matches a `-1` timeout. Until the upstream default ships (PLT-074), explicitly set `spring.session.timeout: 30m` in your deployment.
    - **Cookie attributes (Secure / SameSite / HttpOnly)** — NOT stamped by the platform. Operators are responsible for stamping at the reverse proxy or load balancer. Recommend: HTTPS termination at the proxy + proxy-side `Secure; HttpOnly; SameSite=Strict` for `SESSION` cookie. Track PLT-074 for in-platform default-stamping via `CookieWebSessionIdResolver` bean.
    - **Java-serialised session attributes under INTERNAL_POSTGRESQL** — `SerializationUtils.serialize/.deserialize` is used today. A database compromise yields deserialisation-gadget surface on attribute-load. Defence-in-depth recommendation: restrict DB write access to a single platform service account; deploy on Postgres with strong network segmentation. Track PLT-074 for migration to JSON serialisation.
  - **Multi-replica caveat moved INTO the existing IN_MEMORY H3** (DOC-059 already exists; this adds a sub-bullet): "IN_MEMORY is per-process. Multi-replica Kubernetes / docker-compose deployments behind non-sticky load-balancers will see flaky behaviour on flows that span requests (notably the `/ingestion/datasources` collector-id session bridge — symptom: HTTP 500 `Collector id is null`). For multi-replica deployments choose INTERNAL_POSTGRESQL or EXTERNAL_REDIS / EXTERNAL_POSTGRESQL." (Cross-reference DOC-059's existing IN_MEMORY characteristics text to ensure no duplication.)
