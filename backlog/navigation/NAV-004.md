## Description

The #1825 search overhaul shipped a **second, parallel search stack** into odd-platform across six PRs
(#1856/#1857/#1858 ST-4, #1859 ST-5a, #1860 ST-5b, #1862 ST-5c) — a new table (`asset_search_entrypoint`),
five migrations (`V0_0_96`..`V0_0_100`), a new controller/service/resolver/repository chain, a new scheduled
job, saved searches, and a FE redux slice. **None of it exists in the ontology.**

Verified 2026-08-30 (ctrib059):

- `lineage/odd-platform/understanding/` — 214 sidecars, **none** covering any unified-search file. The only
  search-adjacent sidecars are the LEGACY stack (`SearchController` class/methods, `Search.tsx`,
  `ReactiveTermSearchEntrypointRepositoryImpl`).
- `grep -rln "asset_search_entrypoint" lineage/` → **nothing**. `grep -rln "popularity_score" lineage/` → only
  an SME consultation note (`2026-06-30-first-class-search-sorting-design.md`), i.e. the design INPUT, never the
  as-built record.
- No `feature-flows/detail/F-NNN.yaml` composes the `POST /api/search/assets` flow, so the subsystem has **no
  promise layer / `use_cases` coverage** — the closure unit the tests pillar measures against.

## Why this matters (not cosmetic)

1. **The ontology now under-reports the system.** Any `/retrieve`, `/code-walk`, or impact assessment over the
   search area answers from the LEGACY stack only and will confidently miss the stack that actually serves
   `/api/search/assets`. That is the failure mode the ontology exists to prevent.
2. **The alignment scorecard is silently optimistic** — six PRs of code with no CODE↔DOC↔TEST edges do not
   appear as a gap; they appear as nothing at all.
3. **It compounds.** #1861 ("Most popular" sort) and ST-9 (Popular range facet) build directly on this
   substrate; each further slice widens the unmodelled area.
