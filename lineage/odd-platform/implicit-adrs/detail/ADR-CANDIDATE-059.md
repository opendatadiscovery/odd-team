- **ADR-CANDIDATE-059** (NEW 2026-05-12F): Multi-step per-data-entity write paths use a **service-layer `@ReactiveTransactional` boundary** with the annotation on the service method (NOT on the controller), keeping the controller as a thin reactive proxy while the service orchestrates atomic owner-upsert + title-upsert + ownership-insert + search-index-refresh + filled-flag-mark + optional DEG-propagation
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar (`createOwnership`) but the pattern is named explicitly as a cross-controller convention in the sidecar's implicit_adrs[2] (already documented in batch-E `OwnerController.createOwner` sidecar's implicit_adrs[2]). The cross-batch corroboration via the batch-E reference makes this a 2-sidecar consistent pattern
  - **Surfaced by**:
    - `odd-platform__java__DataEntityController__controller-method__createOwnership.md:implicit_adrs.[2]` ("Reactive transactional boundary at the service, not the controller — the controller is a thin reactive proxy (`DataEntityController.java:165-172`); the transaction annotation lives on `OwnershipServiceImpl.create` (`OwnershipServiceImpl.java:49`) so the owner upsert, title upsert, ownership-row insert, search-index refresh, `data_entity_filled.OWNERS` mark, and the optional DEG propagation are all atomic.   - **Decision statement**: ODD's multi-step per-data-entity write endpoints anchor the transaction at the service layer, not the controller. The convention applied: (a) controller method is the standard `Mono<ResponseEntity<T>>.map(ResponseEntity::ok)` thin-proxy shape (per ADR-CANDIDATE-001 + ADR-CANDIDATE-007); (b) the `@ReactiveTransactional` annotation lives on the SERVICE method (`OwnershipServiceImpl.create` at line 49, `DataEntityServiceImpl.getDetails` at line 197 per ADR-CANDIDATE-054, etc.); (c) the service orchestrates the multi-step atomic operation — for createOwnership: owner upsert (`getOrCreate(owner_name)`) + title upsert (`getOrCreate(title_name)`) + ownership-row insert + search-index refresh (`searchEntrypointService.updateSearchEntrypoint`) + `data_entity_filled.OWNERS` mark + optional DEG-propagation (`createOrUpdate` with `.onConflictOnConstraint(...).doUpdate()`). The decision codifies: (i) the controller is annotation-free for transaction management — it stays as a one-line reactive proxy; (ii) the service is the transactional boundary — orchestrating the full atomic write; (iii) the orchestration order is meaningful — a partial failure (e.g. search-index refresh after the row insert) rolls back the entity write to preserve consistency between the row and the search index. The pattern is consistent across `OwnershipServiceImpl.create`, `OwnerServiceImpl.create` (batch-E), `RoleServiceImpl.create` (batch-E), `PolicyServiceImpl.create` (batch-E), `DataEntityServiceImpl.getDetails` (batch-F per ADR-CANDIDATE-054), and `DataEntityInternalStateServiceImpl.changeStatusForDataEntities` (batch-F per updateStatus).
  - **Wisdom test**: PASS. The cross-batch consistency (2026-05-12E `OwnerController.createOwner` sidecar names the same convention; 2026-05-12F `createOwnership` re-anchors it) is the intent anchor; structural (the annotation placement determines the transaction boundary for every multi-step write in the platform). The alternative (annotating the controller with `@Transactional`) was deliberately not chosen — controllers stay as thin proxies per ADR-CANDIDATE-001.
