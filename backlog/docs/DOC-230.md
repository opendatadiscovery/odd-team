## Description

DOC-177 already covers the description-edit auto-link bypass (Caveat 2) and the cross-namespace pollution (Caveat 3) on the live Business Glossary page. This item adds three NET-NEW dimensions surfaced in the F-056 mode-B clue read — each a separate operator-load-bearing facet that the DOC-177 wording does not currently capture.

**Caveat 4 — Cross-time drain on term-create silently materialises auto-links to entities authored BY OTHER USERS WEEKS AGO; invisible to the term-creator's audit trail (F-056a).** `TermServiceImpl.createTerm` (lines 99-117; line 116 specifically) calls `resolveUnhandledDescriptionMentions`, which drains the `data_entity_description_unhandled_term` + `dataset_field_description_unhandled_term` staging tables (drain function: lines 421-442). A user creating term `X` today silently auto-links `X` to data-entities whose descriptions were written DAYS OR WEEKS AGO by users who never had `DATA_ENTITY_ADD_TERM`. The audit log shows only `TERM_CREATED` by the term-creator; the link's authorship is buried in the description-author's two-week-old description authorship time. For a popular term name (an enumeration that 50 entities mentioned over the past month), term-create silently writes 50 link rows. A compliance auditor reconstructing "who linked term X to entity Y" cannot answer the question.

**Caveat 5 — `is_description_link` invisible in the Term-side reverse-lookup (Linked Entities tab); auto-linked rows indistinguishable from manual ones; read-side preference flip hides manually-linked variants (F-056b).** Two distinct UI coverage gaps for the same `is_description_link` boolean: (a) Term-side panel on the Term overview (`TermLinkedTerms/TermItem.tsx:53`) renders `<LinkedTermIcon />` for description-links AND hides the X delete button (line 61) — operators on this surface CAN distinguish auto-linked vs manual. (b) Term-side reverse-lookup tab (`TermLinkedEntitiesList/LinkedEntity.tsx`) renders NO equivalent indicator and NO conditional delete affordance. Operators viewing a Term's linked entities cannot tell which rows were auto-linked via the description side-channel vs manually linked. Worse: `TermServiceImpl.java:444-448` `removeDuplicateNonDescriptionTerms` PREFERS the description-link variant when both exist — a manually-created link is HIDDEN by an auto-created description-link variant pointing at the same (entity, term) pair. The compliance question "show me all term-to-entity rows linked WITHOUT going through the description side-channel" is unanswerable from the UI.

**Caveat 6 — F-004 stored-XSS family extends to the unhandled-mention staging tables (F-056c — 7th surface of the family).** The mention regex `\[\[([^:]*?):([^\]]*?)\]\]` at `TermServiceImpl.java:67` consumes the raw Markdown body without sanitising the captured groups. A `<script>` payload inside `[[ns:term]]` markers parses through unchanged; the staging-table rows hold `term_name` / `term_namespace_name` columns verbatim. On the future `resolveUnhandledDescriptionMentions` drain (when a matching term materialises), the staged values flow through to the data-entity-to-term linkage path; if rendered, trigger the XSS. The staging table is a 7th attack surface of the F-004 family beyond the five already named in DOC-187 (the description-storage surfaces) + the Slack mrkdwn surface (PLT-016).
