## VERDICT: FALSIFIED -> REJECT-CANDIDATE (verified 2026-06-10, G11 falsification sweep)

The load-bearing claim - "`RandomStringUtils.randomAlphanumeric(40)` is backed by `ThreadLocalRandom`, not a CSPRNG" - is **false for the actually-resolved library version**. The codebase resolves `commons-lang3 = 3.18.0` (`gradle/libs.versions.toml:10`). In commons-lang3 **3.16.0+** the static `RandomStringUtils.randomAlphanumeric(int)` method was deprecated and **re-pointed to delegate to `RandomStringUtils.secure()`**, which is backed by `java.security.SecureRandom`. The draft inverted the version semantics: "3.16+" is exactly the range where the static API became SECURE, not insecure (pre-3.16 used the insecure default).

**Bytecode proof (decompiled from the resolved JAR, 2026-06-10):**

```
# commons-lang3-3.18.0.jar -> javap -c RandomStringUtils
public static java.lang.String randomAlphanumeric(int);
   0: invokestatic  #7   // Method secure:()Lorg/apache/commons/lang3/RandomStringUtils;
# secure() -> SECURE_SUPPLIER -> RandomUtils.secure() -> secureRandom() : java.security.SecureRandom
```

Both call sites (`TokenGeneratorImpl.java:39` and `:49`) use this static `randomAlphanumeric(40)`, so the collector token is generated from a **CSPRNG** today. There is no surviving generation-source defect. The only real token-shape concern (plaintext at rest, `token.value varchar(40)` no hash) is already tracked as **PLT-085**; nothing distinct remains for this item.

**Recommendation:** do NOT file. Close as not-a-defect. (If the team ever downgrades commons-lang3 below 3.16, re-open - but the current resolved version is secure.) Probe P-350 (skeleton, never run) is moot - its premise is disproven by the bytecode.

Severity high -> low and `security_sensitive` true -> false: the security rationale collapsed entirely.

No operator or API consumer is exposed to a predictable-token surface from this code path. The only surviving token concern is plaintext-at-rest, tracked separately as PLT-085.

## (Original draft below - retained for the record; superseded by the verdict above)


## What

The collector ingestion bearer token is generated with `RandomStringUtils.randomAlphanumeric(40)`. In commons-lang 3.16+ the default `RandomStringUtils` methods are backed by `ThreadLocalRandom`, **not** a cryptographically secure source - so the 40-character credential is drawn from a non-CSPRNG. A predictable / seed-recoverable generator on a security credential is a real entropy-source defect on the token-**generation** path.

This is **distinct from PLT-085**, which is the plaintext-**at-rest** storage-shape defect (varchar(40) no-hash, plaintext SQL equality). PLT-126 is the orthogonal generation-source defect. SHB-091 flagged it; it is not yet a standalone tracked item.

## Evidence

From the F-020 reflection (`lineage/odd-platform/feature-reflections/detail/F-020.yaml`), hypothesis H-013:

```
TokenGeneratorImpl.java:39   (@ ede5d277)
TokenGeneratorImpl.java:49   (@ ede5d277)
  // RandomStringUtils.randomAlphanumeric(40)
  // commons-lang 3.16+ -> ThreadLocalRandom (NOT SecureRandom)
```

The exact backing-RNG depends on the resolved commons-lang version; probe P-350 (`lineage/odd-platform/probes/P-350.yaml`) verifies the resolved version before the fix lands.

## Impact

Every live ingestion credential is generated from a non-cryptographic RNG. `ThreadLocalRandom` is not designed to resist seed/state recovery; an attacker who can observe or infer generator state could predict tokens. 40 alphanumeric characters is large, but the weakness is the source, not the length - a secure credential must come from a CSPRNG.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: mechanical one-line change at `TokenGeneratorImpl.java:39` and `:49` - replace with `RandomStringUtils.secure().nextAlphanumeric(40)` (or an explicit `SecureRandom`-backed generator). Verify the resolved commons-lang version via probe P-350 first (to confirm the current default is indeed `ThreadLocalRandom`). Distinct from PLT-085 (plaintext-at-rest).
