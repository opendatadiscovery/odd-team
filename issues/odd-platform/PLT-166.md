## What

The `/management/integrations` route is the only route under Management with no permission wrapper. Every other Management route is mounted inside a `WithPermissionsProvider` (or a `RestrictedRoute` gated by an explicit `hasAccessTo(...)`), so its child components see a permission context scoped to that route's own permissions. The integrations route is mounted bare, so its child renders under whatever permission context the surrounding chrome last established - in practice the `OWNER_ASSOCIATION_MANAGE` context of the adjacent associations route. There is no dedicated integration permission gating the route, which means the moment a real `hasAccessTo(<integration perm>)` check is added inside the Integrations UI it will deny-by-default (the integration permission is not in the inherited allow-list), silently shipping a dead/inert control.

## Where

`odd-platform-ui/src/components/Management/ManagementRoutes/ManagementRoutes.tsx:150` - the bare route (contrast every sibling, which wraps in `WithPermissionsProvider` with an explicit `allowedPermissions={[...]}`):

```tsx
// ...every other route is wrapped, e.g.:
//   <Route path='datasources' element={<WithPermissionsProvider allowedPermissions={[DATA_SOURCE_CREATE, ...]} .../>} />
//   <Route path='associations/*' element={<RestrictedRoute isAllowedTo={hasAccessTo(OWNER_ASSOCIATION_MANAGE)} .../>} />
<Route path='integrations/*' element={<Integrations />} />   // :150 - no WithPermissionsProvider, no RestrictedRoute
```

`odd-platform-ui/src/components/shared/contexts/Permission/PermissionProvider.tsx:27-32` - the deny-by-default access helper that the bare route's children will fall foul of (a permission must be in BOTH the global/resource grant AND the route's `allowedPermissions`; the bare route supplies no `allowedPermissions`, so any future integration-permission check resolves false):

```tsx
const getHasAccessTo = React.useCallback(
  (to: Permission) =>
    [...globalPermissions, ...resourcePermissions].includes(to) &&
    allowedPermissions.includes(to),                 // :29-31 - must also be in this route's allow-list
  [allowedPermissions, resourcePermissions, globalPermissions]
);
```

## Why it matters

Today the integrations screen is read-mostly (a manifest preview list + an integration detail view, `Management/Integrations/Integrations.tsx`), so the missing guard is latent rather than actively exploited. The defect is a structural inconsistency and a trap: the route does not declare which permission it requires, and it borrows whatever context the chrome happens to provide. The next engineer who adds an action behind `hasAccessTo(...)` inside the Integrations subtree will ship a control that is permanently disabled for everyone (because the inherited `allowedPermissions` does not include the integration permission), with no obvious cause - a dead control that looks like a bug report waiting to happen. Severity high tracks the access-control surface and the high likelihood of a silent regression the moment the screen gains a gated action; it is not a present data-exposure on its own.

## Suggested fix

Mount the route through the same permission machinery as its siblings: wrap it in a `WithPermissionsProvider` (or `RestrictedRoute`) with the correct integration permission in `allowedPermissions`, so its children get a route-scoped permission context. If integrations is intentionally meant to have no permission gate (a deliberate everyone-can-view screen), make that explicit - give it its own `WithPermissionsProvider` with an explicit (possibly empty, documented) permission set rather than letting it silently inherit the chrome's `OWNER_ASSOCIATION_MANAGE` context. Open to alternatives on which permission, but the route should declare its own contract rather than borrow one.
