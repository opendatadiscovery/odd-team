## What

The component that drives all alert notifications runs a single background worker thread (the WAL subscriber) and then forgets about it. `runNotificationSubscriber()` submits the `NotificationSubscriber` task to a single-thread executor and **discards the returned `Future`** - there is no supervisor, no liveness check, and no restart path. If that thread dies in-process (an uncaught exception, an unexpected error escaping the run loop, a decoder failure), the JVM is still running and still holds the PostgreSQL leader-election lock, so **no standby instance is promoted** and the dead leader is never noticed. The platform keeps serving the UI normally while every alert silently stops being delivered. Because the discarded `Future` is the only place the failure would have been observable, the death is completely silent.

## Where

**`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/notification/NotificationSubscriberStarter.java:21-35`:**
```java
private final ExecutorService executorService = Executors.newSingleThreadExecutor(
    r -> new Thread(r, "notification-subscriber-thread")
);
...
@EventListener(ApplicationReadyEvent.class)
public void runNotificationSubscriber() {
    log.debug("Notification subscription is enabled, starting WAL parser");
    executorService.submit(new NotificationSubscriber(            // line 33 - Future discarded
        notificationsProperties.getWal(), leaderElectionManager, messageDecoder, messageProcessor));
}
```

The `Future` returned by `executorService.submit(...)` at line 33 is never assigned, polled, or watched, and nothing re-submits the task if it completes (normally or exceptionally).

## Why it matters

Alert delivery is a safety surface - it is the channel operators rely on to learn that *something else* broke. A failure here is silent and total: the affected blast radius is **every notification on the instance**, and because the leader still holds its lock, a multi-instance deployment provides no redundancy - there is no standby promotion on in-process thread death (only on whole-process crash). Operators get no error, no log beyond the initial `debug` start line, and no metric; they discover the gap only when an incident they expected to be paged about goes unannounced. High severity: the failure is undetectable from the outside, defeats the redundancy operators believe they have, and degrades exactly when it is most needed.

## Suggested fix

Add supervision/liveness to the subscriber so death is observable and recoverable:

1. **Retain and watch the `Future`** (or wrap the task) so an exceptional completion is logged at `error` and surfaced to a health indicator / metric rather than swallowed.
2. **Restart or relinquish on death.** On the leader instance, either re-submit the subscriber task with backoff, or release the leader-election lock so a standby can promote - i.e. a dead subscriber thread must not leave the leader lock held indefinitely.
3. Expose subscriber liveness through the existing actuator/health surface so a dead alerting pipeline is alertable by external monitoring.

Open to alternatives on the exact supervision mechanism (self-restart vs. relinquish-and-failover), but in-process death must not be silent.

## How discovered

Surfaced during the 2026-06-08 contradiction harvest (`lineage/odd-platform/harvest/2026-06-08-contradiction-harvest.md`, finding **F-009 H-008 - "notification subscriber thread death undetected"**), a triage of contradicted product-owner hypotheses from the feature reflection `lineage/odd-platform/feature-reflections/detail/F-009.yaml` (alerting / notifications). `NotificationSubscriberStarter.java:33` was read directly in `../odd-platform` to confirm the discarded-`Future` / single-thread-executor / no-supervisor excerpt above.

Distinct from **PLT-139**, which is the *create-order wedge* on fresh boot (the replication slot is created before the publication, yielding "publication does not exist" with no recovery path) - a startup failure. PLT-153 is the *post-startup, in-process* failure: the subscriber started fine and later dies undetected. They are different failure points with different fixes. The existing integration test **IT-012** (`integration-tests/protocols/IT-012-notifications-wal-failover.md`) covers only whole-process **CRASH** failover, not silent in-process thread death, so PLT-153's scenario is currently unguarded.
