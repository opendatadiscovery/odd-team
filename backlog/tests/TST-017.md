## Description

`ReactiveDatasetFieldRepositoryImpl.listByTerm(termId, query, page, size)` builds its inner CTE select with **no `termId` predicate**: the `records` select reads `from(DATASET_FIELD)` filtered only by the optional free-text `query` (`DATASET_FIELD.NAME.containsIgnoreCase(query)`) and ordered by id (`ReactiveDatasetFieldRepositoryImpl.java:151-154`). That select is then wrapped `DSL.with(DATASET_FIELD_CTE_NAME).asMaterialized(records)` (`ReactiveDatasetFieldRepositoryImpl.java:191-192`), and the term narrowing — `DATASET_FIELD_TO_TERM.TERM_ID.eq(termId)` — is applied to the **outer** query (`ReactiveDatasetFieldRepositoryImpl.java:196`), i.e. AFTER the CTE materialises.

`asMaterialized` emits Postgres `WITH ... AS MATERIALIZED`, an optimisation fence: the planner is instructed NOT to push the outer `TERM_ID = ?` filter down into the CTE, so the full `dataset_field` table (optionally name-filtered) is materialised before the term join narrows it. On an instance with a large field corpus and a term linked to only a handful of fields, this is a full-table read where an index-narrowed read would suffice. The open question the report flags is whether the planner elides the fence in practice (Postgres can ignore `MATERIALIZED` for some shapes) — only a measured plan settles it.

**Typed gate: validates-feature (performance characterisation), probe-gated.** This is not a known-bug pin; it is a performance hypothesis that must be measured before it is asserted. The deliverable is the EXPLAIN ANALYZE evidence under PENDING-F-153-1, then a test that pins the observed plan shape (a Seq Scan / materialise step over `dataset_field` ahead of the term join) so a future query rewrite that fixes it goes RED and forces the assertion to be updated. If the probe shows the planner already narrows (no full scan), the finding is closed as a non-issue and recorded as such — do not author a failing test on an unmeasured assumption.
