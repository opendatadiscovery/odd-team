## Description

Two operational security caveats that recur across the deployment / collector-token surfaces and are currently absent or softened:

1. **Collector-token regeneration has no grace window.** Multiple pages frame regenerating a collector token as a benign recovery step. It is an **in-place UPDATE** of the token row with **no grace period**: the moment it is regenerated, any **running collector** using the old token gets **401** and ingestion **stops** until the collector is reconfigured with the new token and restarted/redeployed. The token is also stored **plaintext** at rest (TOKEN table) and **returned plaintext** in the API body, and rotation is **not audit-logged**. Operators treating rotation as a safe routine action will silently break in-flight ingestion.

2. **`/actuator/env` is exposed by default and leaks secrets over the quick-launch HTTP posture.** The deployment and EKS pages stop their security caveat at transport (HTTP vs HTTPS). They omit that `/actuator/env` is exposed by default and, under the quick-launch / demo auth posture (no auth), returns the resolved JDBC URL (host/port/db) and any Slack / webhook URLs **verbatim** to any caller on the HTTP port.

Both are High (security exposure + an operational footgun an operator triggers by following the docs). These map to the LSN-001/002 "default-with-consequence" class.

**Failure shape**: missing caveats (Gate 3 / Gate 6) on deploy + collector surfaces — security exposure and operational data-flow interruption.
