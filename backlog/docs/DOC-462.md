## Description

`user-owner-association.md:96` documents a real, operator-affecting permission inconsistency on the **Remove a binding** action: the UI enables the Remove button when the operator holds `OWNER_ASSOCIATION_MANAGE`, but the backend endpoint enforces `OWNER_RELATION_MANAGE`. The consequence: an operator holding only `OWNER_ASSOCIATION_MANAGE` sees the button and gets a backend rejection; an operator holding only `OWNER_RELATION_MANAGE` may not see the button but the backend would accept the call. The documented workaround is "**grant both permissions** to operators who need direct-bind authority until the inconsistency is resolved."

The Permissions page — the canonical enumeration where an operator decides which permission to grant — describes both permissions as cleanly gating their actions with **no mention of this mismatch**:
- `permissions.md:96` (`OWNER_ASSOCIATION_MANAGE`) — "approving or denying ... Also gates visibility of the Associations Management tab. Does not grant the admin direct-bind affordance — that requires `OWNER_RELATION_MANAGE`."
- `permissions.md:99` (`OWNER_RELATION_MANAGE`) — "directly creating or removing the binding ... the per-row **Remove** on the Active associations sub-tab."

An operator provisioning roles from the Permissions page (the natural place to do it) grants `OWNER_RELATION_MANAGE` for Remove, exactly as `:99` instructs, and then hits the UI-button-doesn't-appear / wrong-permission-gated failure that only the user-owner-association page warns about. The two surfaces disagree on whether Remove is cleanly gated.

## Context

Surfaced by the 2026-06-16 editorial audit of `enable-security/` during the CTRIB-018 review.

**Failure shape:** parallel-surfaces-with-drift. The caveat is correctly authored on the workflow page; the canonical permission-enumeration page (where the grant decision is actually made) is silent, so an operator following `permissions.md:99` literally hits the documented-elsewhere trap.

**Verbatim passage** — `user-owner-association.md:96`:
> The backend permission gate on this endpoint is `OWNER_RELATION_MANAGE`. On the current UI, the Remove button is enabled when the operator holds `OWNER_ASSOCIATION_MANAGE` — so an operator who holds only `OWNER_RELATION_MANAGE` may see the button but the backend will accept the call, and an operator who holds only `OWNER_ASSOCIATION_MANAGE` may click the button only to have the backend reject it. Until that inconsistency is resolved, grant both permissions to operators who need direct-bind authority.

**Silent surfaces** — `permissions.md:96` (`OWNER_ASSOCIATION_MANAGE`) and `permissions.md:99` (`OWNER_RELATION_MANAGE`) describe their gates with no mention of the UI/backend split. `owners.md` likewise references `OWNER_RELATION_MANAGE` for removal (`:35`) without the caveat.
