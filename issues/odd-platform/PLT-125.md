## What

The `OWNER_CREATE` permission gate is **path-anchored** on `POST /api/owners` only, so the `OWNER` table is writable from three service-tier `getOrCreate` side-doors that never touch `/api/owners`. `OwnerServiceImpl.getOrCreate` is reached from `OwnerAssociationRequestServiceImpl` (via `POST /api/owner_association_request` - which is **not** in `SECURITY_RULES`, so it is reachable by **any authenticated user**), from `OwnershipServiceImpl` (gated only by `DATA_ENTITY_OWNERSHIP_CREATE`), and from `TermOwnershipServiceImpl` (gated only by `TERM_OWNERSHIP_CREATE`). A caller supplying a never-seen `ownerName` mints a new `OWNER` row **without holding `OWNER_CREATE`**, and it appears in `GET /api/owners` immediately. The `/permissions` doc tells operators `OWNER_CREATE` controls owner creation; three paths bypass it. The mint is also audit-silent (see PLT-062).

This is **distinct from PLT-101 / PLT-059**, which track the TERM and NAMESPACE `getOrCreate` side-doors. This is the OWNER-side side-door, not tracked by any code-side PLT (only as a doc-gap extension, DOC-262 -> Owner side). It compounds with F-075 `DIRECT_OWNER_SYNC` self-mint-and-self-bind into a privilege chain.

## User-facing impact

**Verified end-to-end trace (FE form -> service -> Owner directory).** This side-door is reachable through normal UI, not only a crafted API call, and it surfaces in a directory an operator manages:

- **The minting path is the all-users "claim ownership" form.** `POST /api/owner_association_request` is the create endpoint; its controller method carries no `@PreAuthorize` (`OwnerAssociationRequestController.java:27-35`) and the path is absent from `SECURITY_RULES` (only GET/PUT are gated, `SecurityConstants.java:149,153`), so any authenticated user reaches it (anonymous under `DISABLED`). The FE entry point is `Overview/OwnerAssociation/OwnerAssociationForm` - available to every signed-in user. Inside, `createOwnerAssociationRequest` calls `ownerService.getOrCreate(ownerName)` (`OwnerAssociationRequestServiceImpl.java:57`) **before any approval branch**, so a never-seen `ownerName` mints an `OWNER` row immediately - whether or not the request is ever approved (verified by reading the full method `:54-75`: the `getOrCreate` runs unconditionally; only the bind differs by `DIRECT_OWNER_SYNC`).
- **`getOrCreate` has no permission check.** `OwnerServiceImpl.getOrCreate` (`:38-42`) is `getByName(name).switchIfEmpty(create(...))` - a plain service method, no `OWNER_CREATE` gate; the path-anchored rule sits only on `POST /api/owners` (`SecurityConstants.java:143`), which this path never touches.
- **The result is visible in the Owners management directory.** `Management/OwnersList/OwnersList.tsx` renders `GET /api/owners` (`fetchOwnersList`, `:45`). Sharpest UI-vs-reality inconsistency found while verifying: that same screen gates its "create owner" button behind `Permission.OWNER_CREATE` (`OwnersList.tsx:88`) - so the UI tells the operator owner-creation requires `OWNER_CREATE`, while the association form (open to all) silently writes the same directory. The two ownership-create siblings (`OwnershipServiceImpl.create` gated by `DATA_ENTITY_OWNERSHIP_CREATE`, `:50-52`; `term/TermOwnershipServiceImpl` gated by `TERM_OWNERSHIP_CREATE`, `:35`, rules at `SecurityConstants.java:216,177`) are the other two side-doors, both confirmed.

All load-bearing claims are code-settled (no probe needed); the user-visible consequence (directory pollution by non-`OWNER_CREATE` holders, reachable via the standard claim-ownership form) is traced FE->BE. `user_facing_verified` flipped false -> true.

## Impact

(1) Directory pollution: a caller holding only `DATA_ENTITY_OWNERSHIP_CREATE` - or merely authenticated, via the association-request POST - can spam the Owner directory with arbitrary names, none gated by `OWNER_CREATE`. (2) The `/permissions` doc is authoritatively wrong about what `OWNER_CREATE` controls. (3) Combined with audit-silence (PLT-062) and name-reuse, the side-door is a self-mint primitive in a privilege chain (compounds with F-075 `DIRECT_OWNER_SYNC` per SHB-087).

## Suggested fix

Per the reflection's `proposed_fix_anchor`: gate `OwnerServiceImpl.getOrCreate` at the service method (programmatic permission check), **or** document the side-door as intentional on `/permissions`. File as the Owner-side sibling of PLT-101 with the F-075 privilege-chain cross-link. Distinct from PLT-101 (TERM/NAMESPACE side-doors).

## How discovered

Surfaced by the Layer-4b feature-reflection over feature flow F-019 (Owner Lifecycle Management) on 2026-06-01 - hypothesis H-004. Reflection detail: `lineage/odd-platform/feature-reflections/detail/F-019.yaml`.

**User-facing verification (2026-06-10, G11 falsification sweep):** verdict HOLDS - all claims code-settled and the user-facing surface traced FE->BE. Confirmed: `getOrCreate` is an ungated service method (`OwnerServiceImpl.java:38-42`); all three callers reach it (`OwnerAssociationRequestServiceImpl.java:57`, `OwnershipServiceImpl.java:52`, `service/term/TermOwnershipServiceImpl.java:35`); `OWNER_CREATE` is path-anchored on `POST /api/owners` only (`SecurityConstants.java:143`); the association-request CREATE POST is absent from `SECURITY_RULES` (`:148-162`, only GET/PUT gated) and its controller has no `@PreAuthorize` (`OwnerAssociationRequestController.java:27-35`). Strengthened with two FE facts a backend-only read would miss: (1) the mint path is the standard, all-users `OwnerAssociationForm` (Overview), and `getOrCreate` runs BEFORE any approval branch (so the owner is minted even for a pending/rejected request); (2) the Owners management screen gates its create-owner button behind `OWNER_CREATE` (`OwnersList.tsx:88`) while the association form bypasses it - a real UI-vs-reality inconsistency. Minor citation fix: `TermOwnershipServiceImpl` lives in `service/term/`. `user_facing_verified` flipped false -> true. Severity stays high.
