## Description

Editorial-audit finding from `/review batch:feature/state-doc141-ia-refactor-2026-05-07` 2026-05-07.

The IA refactor batch (PR #65) shipped three new pillar landings (`data-quality.md`, `data-lineage.md`, `data-glossary.md`) plus updates to the existing `data-discovery.md`. Each carries a `## Why this is a separate pillar from {X and Y}` section that enumerates the six governance pillars and gives a one-line differentiation per pillar.

The four sections are conceptually consistent but **textually divergent** — the same six pillars are described with slightly different one-liners on each landing:

| Source | Data Discovery framing | Data Lineage framing | Data Quality framing |
|---|---|---|---|
| `data-discovery.md` L41-46 | "is about **finding** existing entities — search, browse, land." | "captures the *connection graph*…" | "captures the *correctness signal*…" |
| `data-lineage.md` L22-27 | "is **location-oriented** — finding existing entities by search, browse, or home-page surfacing." | "is **connection-oriented**…" | "is **correctness-oriented** — test results, anomaly classes, dataset SLAs." |
| `data-glossary.md` L25-30 | "is **location-oriented**…" | "is **connection-oriented**…" | "is **correctness-oriented**…" |
| `data-quality.md` L23-28 | "is **location-oriented**…" | "is **connection-oriented**…" | "is **correctness-oriented** — describing how trustworthy the data is at any given moment." |

Each pillar's one-liner reasonably captures the differentiation, but the same six concepts are restated four times across the doc tree. **This is parallel content with drift potential** — when one pillar's framing evolves (a new use case is added, a pillar's scope changes), four landings need to update in lockstep or the doc tree will diverge. The 2026-04-28 case-law on parallel content with drift (re-read the LSN catalogue under `retrospectives/` for prior instances) flags this shape as a maintenance hazard.

**Two design choices to evaluate:**

### Option A — Consolidate to a single canonical home

Move the six-pillar differentiation to `main-concepts.md` (which already hosts the `## Data Governance map` table at L62-67 — the most natural anchor for the differentiation prose). The four pillar landings collapse their `## Why this is a separate pillar` section to a one-line cross-link:

> *"For how Data Lineage relates to the other governance pillars, see [Main Concepts → Data Governance map](main-concepts.md#data-governance-map)."*

**Pro**: one source of truth, drift impossible by construction.
**Con**: a reader landing on `data-lineage.md` for the first time has to click through to grasp the differentiation (one extra hop in the reading flow), and the existing brief framing may be just enough to satisfy that reader without requiring the extra click.

### Option B — Accept the parallel as design intent

Keep each pillar's `Why this is a separate pillar` section as-is. Each landing is a self-contained reading surface for an operator focused on that pillar — having the differentiation inline serves that reader without an extra click. The drift potential is real but small; a /review-time editorial audit catches it.

**Pro**: each landing reads as a complete document for its target operator persona.
**Con**: cross-pillar drift requires editorial vigilance; four landings have to update together when the framing evolves.

### Recommendation

**Lean Option A** for the canonical differentiation prose, with a 1-2 sentence "what this pillar is" in each landing's intro that doesn't require cross-pillar comparison. The pillar landings already cross-link to `main-concepts.md#data-governance-map` ("Data Discovery's position among the other governance pillars" — `data-discovery.md` L9, etc.) — the consolidation reinforces that cross-link as the single canonical pivot. But this is a non-trivial editorial call; surface to maintainer before authoring.

## Context

- **Why low priority.** The current state is internally consistent enough — the parallel framings differ in style ("is X-oriented" vs "captures the X") but agree on substance. No reader is misled. The drift potential is real but slow-burning; this can be addressed deliberately rather than urgently.
- **Why worth filing.** Parallel content with potential drift is one of the failure shapes catalogued in `playbooks/doc-product-editorial-read.md`. Logging it on disk per the protocol is how the doc product stays honest about known maintenance hazards. The decision can wait until the next pillar lands (which would require a fifth restatement under Option B) or until a framing change forces the question.
- **Style note.** Whichever option the maintainer picks should be reflected in `pillars/_template/` (the new-pillar scaffold) so the pattern is consistent for future pillars. If Option A, the pillar template's landing skeleton should not include a `## Why this is a separate pillar` section; if Option B, it should.
