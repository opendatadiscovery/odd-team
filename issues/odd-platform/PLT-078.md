## What

`SecurityConstants.java:95-96` `WHITELIST_PATHS` contains `/actuator/**` - reachable BEFORE the auth chain in EVERY mode (DISABLED / LOGIN_FORM / OAUTH2 / LDAP), not just DISABLED. `application.yml:226-240` ships `management.endpoints.enabled-by-default: false` but explicitly enables and web-exposes `health, prometheus, env, info` (`:231` exposure-include; `:237-238` `env.enabled: true`; `:239-240` `info.enabled: true`).

**Corrected 2026-06-10:** the original draft claimed `show-values=WHEN_AUTHORIZED` and that `/actuator/env` leaks the JDBC URL `host:port:dbname` and other credential VALUES. Neither holds. There is NO `management.endpoint.env.show-values` key anywhere in the repo (grep verified), so Spring Boot's default `NEVER` applies - `/actuator/env` redacts **every** property VALUE (`******`) for every caller, including `spring.datasource.url` and `spring.datasource.password`. What an anonymous caller scraping `/actuator/env` DOES learn is the **configuration-key schema**: which property keys and sources are present - i.e. which OAuth2 providers are wired (by key prefix), whether LDAP is configured, whether REMOTE attachment storage is set up, that a JDBC datasource exists (the key, not its value). This is a recon/fingerprinting exposure, not a secret-value leak. (The live docs already state this correctly: `documentation/docs/configuration-and-deployment/odd-platform.md:106`.)

`/actuator/info` returns `{}` by default - no info contributors are configured in this repo (no `build-info`, no `git.properties`, and the env/java/os info contributors are disabled by default), so the original "`/actuator/info` leaks credential schema" claim is also false.

Combined with the shipped-default `spring.datasource.password=odd-platform-password` (PLT-080): the password VALUE is NOT readable via `/actuator/env` (masked), so the compromise path is the well-known default password itself plus a reachable/guessable DB host - the actuator exposure contributes the schema fingerprint, not the credential. The remaining hardening gap is real: a wide, anonymously-reachable actuator surface. Network-level mitigation (firewall / separate management port) is the operator's responsibility today; the platform default does not provide it.

## User-facing impact

The "user" is an operator (deployment posture) and a network-adjacent attacker (recon). The reachability + exposure facts are code-confirmed; the exact endpoint response is a runtime observable strongly determined by the framework default.

- **WHO/WHAT:** anyone who can reach the platform's HTTP port (no auth) can `GET /actuator/env`, `/actuator/info`, `/actuator/health`, `/actuator/prometheus` - confirmed by BE trace 2026-06-10 (`SecurityConstants.java:95-96` whitelists `/actuator/**` ahead of the auth chain in `AuthorizationCustomizer`; `application.yml:231` exposes the four endpoints).
- **WHAT they observably get from `/actuator/env`:** the property-key catalog with every VALUE masked `******` (Spring Boot `show-values` default = `NEVER`, no override exists) - so the recon yield is the *configuration-key schema* (which integrations are wired), not secrets. *Static trace consistent; not driven* - the exact `/actuator/env` body (masked values, key list) should be confirmed by `curl http://<host>/actuator/env` on a running stack.
- **WHAT `/actuator/info` returns:** `{}` (no info contributors configured) - *static trace consistent; not driven* (confirm via `curl /actuator/info`).
- **NOT exposed:** the datasource password / JDBC URL values (masked) - verified-by-config-trace 2026-06-10 (no `show-values` -> NEVER).

## Why it matters

A wide, anonymously-reachable actuator surface in every auth mode is a real hardening gap: the bypass is upstream of the SecurityWebFilterChain (`WHITELIST_PATHS`), so a passive scan over a network range with the platform port open returns the platform's configuration-key fingerprint (which integrations are wired) - useful recon for targeting follow-on attacks. It does NOT return credential values (masked by the `NEVER` default), which is why this is regraded **medium** rather than high: the original high rationale (credential-VALUE / JDBC-URL leak -> one-line-from-compromise) collapsed on verification. The default-tightening to `health, prometheus` remains correct defense-in-depth.

## Suggested fix

**Thread A - Tighten default exposure.**

```yaml
# application.yml
management:
  endpoints:
    web:
      exposure:
        include: health, prometheus    # was: env, info, health, prometheus, ...
  endpoint:
    env:
      enabled: false                   # require explicit opt-in
```

Operators opting in for `env, info` get them explicitly. Production-shaped defaults out-of-the-box.

**Thread B - Document `management.server.port` separation.**

The cleanest fix is BOTH platform-side default tightening AND operator-side `management.server.port` separation (run actuator on a separate port routed to an internal network). Doc-side guidance from DOC-242 already covers this; PLT-078's responsibility is the platform default.

**Thread C - Remove `/actuator/**` from WHITELIST_PATHS (stretch).**

Move `/actuator/health` and `/actuator/prometheus` to a narrower whitelist (only the two endpoints, not the wildcard). Keep `/actuator/env`, `/actuator/info`, etc. gated by the same auth chain as the rest of the platform. Useful for deployments that can't easily route to a separate port.

Recommended Thread A + B together - Thread A is the immediate operator-load-bearing default fix; Thread B is the doc-side guidance already shipping. Thread C is a follow-up.
