# DataEntityController#deleteDataEntityFromDataEntityGroup — semantic understanding

## understanding

`deleteDataEntityFromDataEntityGroup` is the reactive `DELETE /api/dataentities/{data_entity_id}/data_entity_group/{data_entity_group_id}` handler — six lines that call `dataEntityService.deleteDataEntityFromDEG(dataEntityId, dataEntityGroupId)`, drop the returned `Flux<GroupEntityRelationsPojo>` via `ignoreElements()`, and emit `204 No Content` (`DataEntityController.java:343-349`). The service loads both the data-entity pojo and the DEG pojo (filtering the latter for `manuallyCreated && contains(entityClassIds, DATA_ENTITY_GROUP.getId())`), then HARD-DELETES the `(groupOddrn, dataEntityOddrn)` row from `group_entity_relations` and — only if the entity no longer participates in any other manually-created DEG — toggles `data_entity_filled.CUSTOM_GROUP = false` (`DataEntityServiceImpl.java:411-438` + `ReactiveGroupEntityRelationRepositoryImpl.java:57-65`).

**Headline finding (HIGH severity, primary-source confirmed):** the DEG add/delete pair shows THREE asymmetries that the documentation does not surface — (1) different permissions gate the operations (`DATA_ENTITY_ADD_TO_GROUP` vs `DATA_ENTITY_DELETE_FROM_GROUP` per `SecurityConstants.java:228-236`; a Policy granting only ADD cannot remove, and vice versa, contradicting any operator mental model of a single "manage DEG membership" capability); (2) the ADD path raises `400 Bad Request "Data entity is already in this DEG"` on a duplicate (`DataEntityServiceImpl.java:402`), but the DELETE path returns `204 No Content` SILENTLY when the membership does not exist (`deleteRelationsReturning` returns an empty list which `collectList()` accepts without `switchIfEmpty`, see `DataEntityServiceImpl.java:421-426`) — DELETE is non-idempotent in side-effects (the conditional unfilled-marker check still runs) but idempotent in HTTP surface, while ADD is non-idempotent in BOTH; (3) NEITHER operation emits an activity-feed event (no `@ActivityLog` on `addDataEntityToDEG` or `deleteDataEntityFromDEG`, `DataEntityServiceImpl.java:388-438`) — DEG membership flips are unaudited, in contrast to TERM_ASSIGNMENT_UPDATED, TAG_ASSIGNMENT_UPDATED, OWNERSHIP_CREATED/UPDATED/DELETED. An operator opening `GET /api/dataentities/{id}/activity` to answer "who added/removed this entity from the Finance domain?" finds nothing. Additionally, the `data_entity_to_group` row removal is a HARD DELETE — distinct from the soft-delete path (`softDeleteRelationsForDeletedDataEntities`, `ReactiveGroupEntityRelationRepositoryImpl.java:92-101`) used by the entity-deletion cascade — so the cascade and the user-initiated removal have different durability semantics with no audit trail to distinguish them.

## bugs_limitations_corner_cases

- "**Activity-feed absence for DEG membership flips** — neither `addDataEntityToDEG` nor `deleteDataEntityFromDEG` is annotated with `@ActivityLog` (`DataEntityServiceImpl.java:388-408, 410-438`). - "**Silent-204 on no-op DELETE creates audit ambiguity** — when a caller issues `DELETE /api/dataentities/X/data_entity_group/Y` and the (X, Y) membership does not exist (already removed, never existed), the response is `204 No Content` — IDENTICAL to the successful-removal response. `DataEntityServiceImpl.java:421-426` issues `deleteRelationsReturning(...).collectList()` without `switchIfEmpty`; an empty list flows through to `Flux.fromIterable(emptyList)` which completes empty; `ignoreElements().thenReturn(noContent())` returns 204.
