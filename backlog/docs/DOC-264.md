## Description

The live `/data-discovery/metadata-stale` page (WebFetched 2026-05-27, 200 OK) describes the stale icon's UI placements, the `odd.data-entity-stale-period` config key + default 7 days, and the operator-side tuning advice. It is **silent on every load-bearing semantic of the stale-detection predicate** — what the predicate returns when the config key is unset (silent-disable, every entity reports fresh, indicator dies platform-wide), how the predicate handles entities that have never been ingested (returns `is_stale: false` — fresh-looking), what the MetadataStale widget renders when the signal is globally off (nothing — same DOM as a perfectly-healthy platform), the absence of per-source / per-tenant overrides (one global cadence has to fit every source), and the trust posture of the `last_ingested_at` write-path (ingestion-write capability forges freshness with no source-authenticity check). Five operator-visible behaviours need a Known Limitations section.

**Caveat 1 — Silent-default footgun: if `odd.data-entity-stale-period` is missing/null in the operator's overlay, the indicator dies platform-wide and no log / warning / startup signal surfaces (F-208a — CRITICAL, LSN-001/LSN-002 class).** `DataEntityStaleDetector.java:13-17` (verified this run): the predicate is `pojo.getLastIngestedAt() != null && stalePeriod != null && DateTimeUtil.generateNow().isAfter(pojo.getLastIngestedAt().plusDays(stalePeriod))`. If `stalePeriod` is null — config key removed from the operator's overlay (typo / explicit `null` / config-tooling stripping the line) — the predicate **returns `false` for every entity in the platform**. Stale indicators silently disappear from every list, every detail page, every lineage view. The platform looks perfectly healthy; collectors could be hours / days / weeks behind and no signal surfaces. The shipped default in the upstream `application.yml:211` IS `data-entity-stale-period: 7 # days` (verified this run) — the footgun materialises only when an operator's deployment overlay (Helm values, Docker `environment:`, K8s ConfigMap, config-templating tool) **deliberately removes the line** or sets it to an empty value. Same class-1 footgun pattern as LSN-001 (attachment-ephemeral default) and LSN-002 (minio-region-unset) — the SDK / Spring container accepts the missing config silently; no `@PostConstruct` validator, no startup INFO log, no admin signal. The compound failure: operator confidence in the platform's freshness signal becomes inversely correlated with how broken the signal is.

**Caveat 2 — An entity that has NEVER been ingested reports `is_stale: false` ("fresh"); the absence of staleness does not confirm freshness (F-208b).** `DataEntityStaleDetector.java:14` (verified this run): the predicate's first conjunct is `pojo.getLastIngestedAt() != null`. An entity with no ingestion history (manually-created in the UI, pending first collector pull, or one that the collector skipped on its first run) has `last_ingested_at` NULL — the predicate short-circuits to `false` and the entity reports `is_stale: false`. The UI shows no stale icon. The operator's mental model is "no stale icon = the catalog has fresh metadata" — but the actual semantic is "no stale icon = either (a) we have fresh metadata, OR (b) we have no metadata at all, indistinguishable from the UI side." Manually-created entities or pending-first-ingestion entities look as healthy as a recently-refreshed dataset.

**Caveat 3 — When the staleness signal is globally dead (Caveat 1 conditions), the MetadataStale widget renders the same DOM as a healthy platform — there is no diagnostic surface (F-208c).** `MetadataStale.tsx:20-31` (verified this run): `return isStale ? <AppTooltip>...<StaleIcon/></AppTooltip> : null;`. When `isStale=false` the widget renders null. Combined with Caveat 1: a deployment that unset `stale-period` shows ZERO stale icons across every list, detail page, and lineage surface; the UI looks indistinguishable from a deployment where every entity is genuinely fresh. There is no "staleness disabled" diagnostic banner, no admin-tab indicator, no per-page sentinel. The operator cannot tell "the signal is dead" from "everything is fresh" without inspecting backend config — and Caveat 1's class-1 footgun shape means the operator has no reason to inspect until something else breaks.

**Caveat 4 — `odd.data-entity-stale-period` is a single deployment-wide cadence; no per-data-source / per-namespace / per-class override exists (F-208d).** Per F-208 sidecar facet 5 — there is exactly one `@Value`-bound integer (`DataEntityStaleDetector.java:10-11`, verified this run) and exactly one `application.yml:211` key. Operators with heterogeneous source cadences (daily warehouse + streaming Kafka topic; weekly DBT models + hourly ingestion job) face an impossible choice: set the threshold to 7 days and the streaming topic flags as stale every hour it pauses; set the threshold to 1 hour and the weekly DBT models flag as permanently stale. There is no per-source `stale_period_days` column on the data-source schema, no per-namespace override key, no per-class default. The supported posture is "one global cadence."

**Caveat 5 — Anyone with ingestion-write capability on a data source can forge `last_ingested_at`; the staleness predicate has no source-authenticity check (F-208e).** `DataEntityStaleDetector.java:13-17` (verified this run): the predicate operates on `pojo.getLastIngestedAt()` with no integrity check on who wrote that timestamp. An actor (collector token, S2S API key, push adapter) with INGESTION_WRITE on a data source can emit an event with a current `last_ingested_at` for any entity in that source → the entity reports `is_stale: false`. The mechanism may be deliberate (the catalog trusts ingestion writes by design — read-collaborative posture's write-side counterpart) but it is undocumented. Operators using staleness as an SLA signal for collector health need to know that the signal is forgeable; operators using it as evidence in incident post-mortems need to know that "the entity reports fresh" does not establish that the source produced new data, only that something wrote a new timestamp.
