## What

The component that drives all alert notifications runs a single background worker thread (the WAL subscriber) and then forgets about it. `runNotificationSubscriber()` submits the `NotificationSubscriber` task to a single-thread executor and **discards the returned `Future`** - there is no supervisor, no liveness check, and no restart path on the instance. If that thread dies in-process, the platform keeps serving the UI normally while that instance's alert delivery stops, and the death is **completely silent**: because the task is started with `submit(...)` rather than `execute(...)`, any escaping `Throwable` is captured into the discarded `FutureTask` - so not even the JVM's default uncaught-exception handler prints a stack trace. The only log line the subsystem ever emits at start is a `debug`.

Two scoping corrections versus the original revision of this issue (see "How discovered"):

1. **A dead subscriber thread does NOT keep the leader lock.** The advisory lock is held by a raw JDBC connection opened inside `run()`'s try-with-resources (`NotificationSubscriber.java:47`); any `Throwable` escaping the thread unwinds that block, closing the unpooled `DriverManager` connection (`PGConnectionFactory.java:36`) and ending the PG session - which releases the session-scoped `pg_advisory_lock` (`PostgreSQLLeaderElectionManagerImpl.java:21-24`). A standby replica blocked inside `acquire(...)` would then take over (the standby parks in `SELECT pg_advisory_lock(100)` before ever touching the WAL stream - observed in the IT-012 runs, `integration-tests/run-log/2026-06-02-feature-complete.md:52`). So multi-replica deployments DO get promotion on in-process thread death (static trace; the thread-death case specifically has not been driven - IT-012 drives whole-process crash).
2. **The realistic in-process death paths are narrow.** The stream loop's `catch (Exception)` at `NotificationSubscriber.java:90-92` keeps the thread alive through ordinary failures (that resilience is exactly the PLT-139 retry-flap). What escapes the loop and kills the thread is only: a JVM `Error` (e.g. OOM raised on this thread), or the `InterruptedException -> NotificationSubscriberException` rethrows at `:87-89` and `:96-100`.

What fully survives verification: on the instance where the thread died, **nothing restarts it and nothing can notice it** - the only submission site is the `ApplicationReadyEvent` listener; there is no health indicator, no metric, no error log. On a single-instance deployment (the default docker-compose posture) that is a silent, total loss of alert delivery until the next full process restart.

## Where

**`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/notification/NotificationSubscriberStarter.java:21-35`:**

```java
private final ExecutorService executorService = Executors.newSingleThreadExecutor(
    r -> new Thread(r, "notification-subscriber-thread")
);
...
@EventListener(ApplicationReadyEvent.class)
public void runNotificationSubscriber() {
    log.debug("Notification subscription is enabled, starting WAL parser");
    executorService.submit(new NotificationSubscriber(            // line 33 - Future discarded
        notificationsProperties.getWal(), leaderElectionManager, messageDecoder, messageProcessor));
}
```

The `Future` returned by `executorService.submit(...)` at line 33 is never assigned, polled, or watched, and nothing re-submits the task if it completes (normally or exceptionally). Supporting chain: lock acquisition + try-with-resources at `NotificationSubscriber.java:46-47`; loop-survival catch at `:90-92`; thread-killing rethrows at `:87-89`/`:96-100`; raw connection at `PGConnectionFactory.java:36`; blocking `pg_advisory_lock` at `PostgreSQLLeaderElectionManagerImpl.java:21-24`. The actuator surface that could carry a liveness signal already exists (`application.yml:226-240` exposes `health` and `prometheus`) but has no notification wiring.

## User-facing impact

User: an operator who enabled notifications and relies on alert delivery; in the failure window, everyone subscribed to alerts.

What they observably get **if** the subscriber thread dies in-process: the UI and API behave completely normally; alerts continue to appear in the UI; no notification is delivered from that instance; **no log line, no metric, no health change records the death** (verified by code trace 2026-06-10: discarded `Future` at `NotificationSubscriberStarter.java:33`, `submit()`/`FutureTask` capture semantics, no other submission or watch site in `notification/`). On single-instance deployments this is a total alerting outage discovered only when an expected page never arrives. On multi-replica deployments a standby should take over (static trace via lock-release-on-unwind, `NotificationSubscriber.java:47` + `PostgreSQLLeaderElectionManagerImpl.java:21-24`; not driven - the remaining runtime check is killing the leader's subscriber thread in-process, e.g. via a forced Error, and observing standby promotion). The trigger itself (an `Error`/interrupt escaping the loop) is a runtime event whose frequency this trace cannot establish; what the trace settles is that *when* it happens, it is silent and unrecovered on that instance.

## Why it matters

Alert delivery is a safety surface - it is the channel operators rely on to learn that *something else* broke - and this failure mode is undetectable from the outside on the affected instance: no error, no metric, no restart. Severity regraded **high -> medium**: the original high rested on "the dead leader keeps the lock, so multi-instance redundancy is defeated", which the lock-scoping falsifies (the lock is released on unwind and a standby can promote), and the surviving single-instance window requires an `Error`-class escape that the loop's `catch (Exception)` makes rare. What remains is a real, cheap-to-close observability/supervision gap on a safety surface.

## Suggested fix

Add supervision/liveness to the subscriber so death is observable and recoverable:

1. **Retain and watch the `Future`** (or wrap the task) so an exceptional or normal completion is logged at `error` and re-submitted with backoff - in-process death must not be terminal for the instance when a restart would heal it.
2. **Expose subscriber liveness** through the existing actuator/health + prometheus surface (`application.yml:226-240`) so a dead or wedged alerting pipeline is alertable by external monitoring (this also surfaces the PLT-139 wedge-flap, which holds the lock but delivers nothing - a state lock-based checks cannot distinguish from healthy).
3. Optionally widen the loop's escape hatch logging: the `InterruptedException` rethrows at `NotificationSubscriber.java:87-89`/`:96-100` currently vanish into the discarded `Future`; at minimum they should log at `warn` before propagating.

Open to alternatives on the supervision mechanism (self-restart vs. health-gated), but in-process death must not be silent.

## How discovered

Surfaced during the 2026-06-08 contradiction harvest (`lineage/odd-platform/harvest/2026-06-08-contradiction-harvest.md`, finding **F-009 H-008 - "notification subscriber thread death undetected"**), a triage of contradicted product-owner hypotheses from the feature reflection `lineage/odd-platform/feature-reflections/detail/F-009.yaml` (alerting / notifications).

**Corrected 2026-06-10 (user-facing verification sweep):** was "the JVM ... still holds the PostgreSQL leader-election lock, so no standby instance is promoted and the dead leader is never noticed"; actually the lock is scoped to the try-with-resources connection inside `run()` (`NotificationSubscriber.java:47`), which every thread-death path unwinds - closing the raw `DriverManager` session (`PGConnectionFactory.java:36`) and releasing the session-level advisory lock (`PostgreSQLLeaderElectionManagerImpl.java:21-24`) - so standby promotion is expected, not defeated. Also narrowed the death-trigger set: the loop's `catch (Exception)` (`:90-92`) survives ordinary exceptions (including the PLT-139 decode failures); only `Error`s and the interrupt rethrows (`:87-89`/`:96-100`) kill the thread. The discarded-`Future` / no-supervision / no-restart / fully-silent core is confirmed - strengthened, in fact: `submit()` routes the `Throwable` into the discarded `FutureTask`, so even the default uncaught-exception handler never fires. Severity high -> medium accordingly.

Distinct from **PLT-139**, the *create-order wedge* on fresh boot (slot before publication -> "publication does not exist", thread ALIVE and flapping the lock). They are different failure points with different fixes: PLT-139's thread never dies (so this issue's supervision would not catch it via completion - hence the liveness metric in fix 2), while PLT-153's thread dies entirely. The existing integration test **IT-012** (`integration-tests/protocols/IT-012-notifications-wal-failover.md`) drives whole-process **CRASH** failover only; in-process thread-death failover remains statically-expected but undriven.
