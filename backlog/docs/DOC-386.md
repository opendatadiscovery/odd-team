## Description

The `[[namespace:term]]` description auto-link convention is parsed by **two different regular expressions** — one in the React editor, one in the backend term-handler — and they disagree on whether the namespace and term segments may be empty. The divergence is undocumented.

Verified by read:
- Backend — `TermServiceImpl.java:67`: `Pattern.compile("\\[\\[([^:]*?):([^\\]]*?)\\]\\]")`. Both capture groups are `*?` (zero-or-more, reluctant), so **empty segments match**: `[[:foo]]` (empty namespace), `[[foo:]]` (empty term), and even `[[:]]` are all matched by the backend pattern.
- UI — `lib/constants.ts:177`: `export const TERM_PATTERN = /\[\[([^:\]]+):([^\]]+)\]\]/g;`. Both groups are `+` (one-or-more), so an **empty segment does not match**: `[[:foo]]` and `[[foo:]]` are *not* recognised by the editor and render as literal text.

Operator-visible consequence: a description containing `[[:foo]]` (or any empty-segment mention) shows as plain bracketed text in the editor/preview and produces no term-link affordance — yet on save, the backend pattern *does* match it and feeds it to the term-resolution / unhandled-mention staging path. The two surfaces disagree about whether the marker is a term mention at all. For most real input (both segments non-empty) the patterns agree; the divergence bites only on malformed/edge markers, which is why it is low severity — but a programmatic caller hand-building description bodies (or a doc author copying the "syntax") needs to know the server contract is looser than the UI's.

The existing docs describe the `[[namespace:term]]` syntax (`business-glossary.md` Term-to-entity associations + Known operator caveats; `api-reference/glossary.md` term endpoints) but neither states the empty-group divergence. This item adds the caveat to both surfaces that carry the syntax.
