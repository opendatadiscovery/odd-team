    - **The threat model**: ODD ingests alerts from upstream collectors. The collectors are typically operator-deployed (data team writes a dbt project; CI/CD generates dbt test result rows; a `dbt-collector` reads the rows and POSTs `/ingestion/alerts/...`). The trust posture in ODD is "the collector is trusted because the operator deployed it" — but in practice the collector's INPUT is data-engineer-authored content (the dbt test's description field, the GE expectation's `result_message`). A malicious data engineer (or a compromised CI pipeline) can author a dbt test with description `"DB connection failed @channel <https://phish.attacker/|view incident details>"`. When the test fails, the alert chunk's description carries that string into Slack via THIS file's `markdownText(...)` call — Slack renders it AS markup: the `@channel` triggers a workspace-wide notification (worse than the alert itself); the `<...|view incident details>` renders as a clickable link to the attacker's domain (drive-by malware staging point).
    - **The receiver-side amplification**: Slack's `@channel` notifies every workspace member; the cost of a single mis-injected alert is amplified by workspace size. For a 500-member Slack workspace, ONE alert with `@channel` injection produces 500 phone-vibration notifications. The attacker-side ROI is high.
    - **The collector-trust narrative**: ODD's ingestion is "operator-controlled" in the sense that operators choose which collectors to run, but the IDENTITY of the alert content depends on the COLLECTOR'S input source. A dbt test description is authored by the data engineer who wrote the test; not the operator who deployed the dbt-collector. The trust chain is: data engineer → dbt repo → dbt CI → dbt-collector → ODD ingest → ODD WAL → Slack render. Each hop is asynchronous; the platform's render-as-markup step is the LAST defence against injection, and it is absent.
    - **Industry comparison**: Slack documents the `mrkdwn: false` option for messages that should render text-only; Slack Block Kit `plain_text` type signals "render this verbatim, no markup interpretation". ODD's `markdownText(...)` choice opted INTO markup interpretation for the description field. The fix could be: switch the description rendering to `plainText(...)` for the un-trusted segment, OR apply an `MrkdwnUtils.escape(...)` helper that backslash-escapes Slack's metacharacters (`*`, `_`, `~`, `<`, `>`, `@`).
