# metrics.storage (consumer at CounterTimeSeriesExtractor.java:20) — semantic understanding

## understanding

This `@ConditionalOnProperty(name = "metrics.storage", havingValue = "PROMETHEUS")` annotation gates whether the Spring container instantiates `CounterTimeSeriesExtractor` at all — the bean wires only when the operator sets `metrics.storage=PROMETHEUS` in `application.yml`. The class translates Prometheus-shaped `MetricType.COUNTER` points (a `total` value plus an optional `created` timestamp) into two `TimeSeries` proto records that `ExternalIngestionMetricsServiceImpl` Snappy-compresses and ships to the operator's external Prometheus via `/api/v1/write`. A mirror bean (`CounterMetricsSeriesExtractor`, in the sibling `extractors/internal/` package) carries the opposite condition `havingValue = "INTERNAL_POSTGRES", matchIfMissing = true` — meaning the **default** mode writes counter series to ODD's PostgreSQL via JOOQ, and only an explicit `metrics.storage=PROMETHEUS` flips the platform onto the remote-write path that wires this file.

## bugs_limitations_corner_cases

- "Read/write tenant-id label asymmetry on empty-string. Write side `AbstractTimeSeriesExtractor.java:60` uses `if (tenantId != null)` — an empty string passes the guard and writes a `tenant_id=\"\"` label onto every TimeSeries. Read side `ExternalMetricReader.java:111` uses `StringUtils.isNotEmpty(tenantId)` — an empty string fails the guard and the read filter omits the `tenant_id` clause. Net effect: if an operator supplies `ODD_TENANT_ID=` (env var set to empty) rather than leaving the variable unset, every write goes to a series tagged `tenant_id=\"\"` but reads query across all tenants. In a shared-Prometheus multi-tenant deployment this would either (a) bury this tenant's series under an unfilterable label that other tenants don't have, or (b) cause this tenant's reads to return series from co-tenants whose `tenantId` was `null`." — evidence: AbstractTimeSeriesExtractor.java:60 (`if (tenantId != null)`) + ExternalMetricReader.java:111 (`StringUtils.isNotEmpty(tenantId)`) + application.yml:210 (`tenant-id:` declared empty) — severity: HIGH
- "Tenant isolation is by-label-convention, not by enforcement. The `tenant_id` label is appended at the write layer using whatever string the operator provided in `odd.tenant-id` — there is no server-side validation, no allowlist, no uniqueness check across ODD Platform instances sharing the same Prometheus. If two ODD Platform deployments accidentally configure the same `odd.tenant-id` against the same `metrics.prometheus-host`, their series merge silently. If a single deployment's `odd.tenant-id` is changed mid-life (typo correction, rebrand), historical series at the old label become unreachable from `ExternalMetricReader` reads (which filter on the current value)." — evidence: AbstractTimeSeriesExtractor.java:60-62 (label-append, no validation) + ExternalMetricReader.java:107-115 (read filter uses current `tenantId` only) — severity: MEDIUM
- "`counterValue.getTotal() == null` throws `IllegalArgumentException` at request time, not at ingestion validation. A malformed `MetricPoint` reaches this point of the pipeline through `ExternalIngestionMetricsServiceImpl.writeRequest()` which iterates over every MetricFamily / Metric / MetricPoint in the request body — one bad point in a batch aborts the entire batch's `saveMetricsToPrometheus` chain (and therefore the entire ingestion request) because the exception escapes the `Mono` upstream of `webClient.post()`.
