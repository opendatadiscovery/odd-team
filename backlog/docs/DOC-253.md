## Description

The live `/features/data-discovery/attachments` page (WebFetched 2026-05-27, 200 OK) DOES document the LSN-001 LOCAL-ephemeral warning AND mentions the `us-east-1` AWS S3 constraint (LSN-002 doc-mitigated). It is **silent on three additional load-bearing operator caveats**.

**Caveat 1 — Chunk staging at `/tmp/odd/chunks` is hard-coded regardless of `attachment.storage` mode (F-027a — partial LSN-001 remediation).** `FileUtils.java:24` declares `private static final String CHUNK_BASE_PATH = "/tmp/odd/chunks";` and `getChunkDirectory(UUID)` (line 26) returns `Paths.get(CHUNK_BASE_PATH, uploadId.toString())` **independent of `attachment.storage` mode**. The 3-step chunked-upload protocol (initiate → upload-part(s) → complete) writes every part to the node-local `/tmp` directory; only at COMPLETE time does the REMOTE path stream the assembled file to S3. An operator running REMOTE persistence on a Kubernetes deployment with `spec.volumes` excluding `/tmp`, OR any container restart between initiate and complete, loses all in-flight upload state. **The LSN-001 remediation is PARTIAL**: the persistent-file path is REMOTE-safe; the in-flight-chunk window is LOCAL-ephemeral ALWAYS. Multi-hour large-file uploads (the chunked protocol's intended use case) can lose partial state on container restart even under REMOTE persistence.

**Caveat 2 — Mutation endpoints discard the URL's data-entity-id; cross-entity privilege escalation (F-027b — security HIGH).** The URL pattern is `/api/dataentities/{data_entity_id}/attachments/files/{file_id}`. `DataEntityAttachmentController.java` mutation methods receive BOTH path params but operate only on `fileId`; `dataEntityId` is discarded after the auth-gate evaluation. A user holding `DATA_ENTITY_ATTACHMENT_MANAGE` on entity A constructs a PUT against `/api/dataentities/{A_id}/attachments/files/{B_file_id}` — the auth gate sees entity A (allowed) but the mutation acts on entity B's file. Combined with the READ endpoints having NO SecurityRule entry (any authenticated user lists ANY data entity's attachments), the cross-entity scope is operator-invisible. Multi-tenant deployments lose attachment isolation by default. **Per-entity ownership boundaries are silently bypassed for attachments.**

**Caveat 3 — `MinioConfig` builder leaves three parameters unset; region is doc-mitigated; httpClient + credentialsProvider remain unmitigated (F-027c — IAM-role gap).** Per the Gate-5 unset-parameter audit on `MinioAsyncClient.builder()` at `MinioConfig.java:19-25`: (a) `.endpoint(attachment.remote.url)` configured ✓; (b) `.credentials(accessKey, secretKey)` configured ✓; (c) `.region(...)` **UNSET** — SDK defaults to `us-east-1`; the doc warns ✓ but there is no in-code fail-fast at `@PostConstruct`; no `attachment.remote.region` config key in the codebase (grep returns zero matches); (d) `.httpClient(...)` **UNSET** — SDK uses default OkHttpClient with default timeouts (~10s connect / 10s read / 10s write); a slow S3 endpoint stalls the upload thread without an operator-tunable hook; (e) `.credentialsProvider(...)` **UNSET** — **no IAM-role support**; operators on EKS with IRSA (IAM Roles for Service Accounts), or any AWS-native deployment expecting `DefaultCredentialsProvider`, MUST provide static access-key/secret-key — itself a credential-hygiene gap. The doc-side remediation is HEALTHY for (c); residue (d) + (e) are unmitigated and undocumented.
