## What

The Data Quality dashboard filter labelled **"Title"** does not filter by a dataset's title/name, as its bare label reads - it filters by the **ownership role** ("Title") that is assigned to an owner on a data entity (for example, "Data Steward"). The autocomplete is fed by the ownership-title list and the selected ids are bound at the SQL layer to `OWNERSHIP.TITLE_ID`. So an operator who opens the dashboard, picks a value under "Title" expecting to isolate a named dataset, instead narrows the three donut rings to only those datasets where *someone* holds that ownership role. The rings still render confidently - there is no error, no empty state, no qualifier on the label - so the operator reads a plausible-but-wrong aggregate and has no signal that the filter meant something other than what it said.

## Where

The filter renders with the bare i18n label `t('Title')` and reads the ownership-title list:

`odd-platform-ui/src/components/DataQuality/DataQualityFilters/FilterItem/TitleFilter.tsx:23,29`
```tsx
} = useFilter(useGetTitleList, filterKey);   // line 23 - ownership-title list, not datasets
...
name={t('Title')}                            // line 29 - bare "Title" label
```

The selected ids are bound to `OWNERSHIP.TITLE_ID` in the dashboard's filter-join builder:

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/repository/reactive/ReactiveDataQualityRunsRepositoryImpl.java:301,309`
```java
.and(OWNERSHIP.TITLE_ID.in(titleIds))                 // line 301 - combined Owner+Title arm
...
.on(OWNERSHIP.TITLE_ID.in(titleIds)                   // line 309 - Title-only arm
        .and(OWNERSHIP.DATA_ENTITY_ID.eq(DATA_ENTITY.ID)));
```

The OpenAPI operation that backs the dashboard exposes the parameter as `title_ids` with no description clarifying that "title" means the ownership role rather than the entity name, so the contract carries the same ambiguity as the UI label.

## Why it matters

This is a silent, confidently-wrong result - the worst class for a metrics surface. An operator using the DQ dashboard to answer "what is the health of dataset X" by typing X into "Title" gets a real, non-empty, plausible aggregate that is actually scoped to "datasets owned under role X". There is no error and no empty state to prompt a second look, so the wrong number is taken at face value and may drive a wrong operational decision (e.g. believing a dataset is healthy when the slice never included it). Medium severity: not data-loss or a security hole, but it actively misleads on a dashboard operators trust for go/no-go calls, and the autocomplete is the only (weak) hint that the value space is ownership roles rather than dataset names.

## Suggested fix

Relabel the filter to its real meaning and fix the contract description, rather than re-binding the query (the `OWNERSHIP.TITLE_ID` join is the intended behaviour - "Title" is ODD's ownership-role concept):

1. Change the UI label from `t('Title')` to something unambiguous - e.g. "Owner title" or "Ownership role" - in `TitleFilter.tsx:29` (and update the i18n key if a new string is introduced).
2. Add a `description` to the `title_ids` query parameter on the DQ-dashboard operation in `odd-platform-specification/openapi.yaml` stating that it filters by the ownership role (Title) assigned to owners, not by the data entity's name.

(Re-binding the filter to a dataset-name search would be a *different* feature, not a fix - the value space, the autocomplete source, and the SQL join all consistently mean the ownership role today.) Open to alternatives on the exact replacement wording.
