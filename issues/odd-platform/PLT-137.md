## What

The service-layer `!external` guard that protects Collector-pushed tags from overwrite (`TagServiceImpl.update` and `delete` both `.filter(tagDto -> !tagDto.external())`) reads the tag's `external` flag from `ReactiveTagRepositoryImpl.getDto`, which computes it **only** from the data-entity aggregate: `external = coalesce(boolOr(tag_to_data_entity.external), false)`, joining **only** `TAG_TO_DATA_ENTITY`. The `tag_to_dataset_field` table uses a separate `TagOrigin` enum (`INTERNAL` / `EXTERNAL` / `EXTERNAL_STATISTICS`) that `getDto` never joins. So a tag whose **only** Collector-set origin is an `EXTERNAL`/`EXTERNAL_STATISTICS` `tag_to_dataset_field` row (with no external data-entity relation) gets `external=false` from `getDto` and **passes** the guard - it can be renamed via `PUT /api/tags/{id}` or deleted via `DELETE /api/tags/{id}`.

**Reachability corrected on verification (2026-06-10): this is a direct-API / service-guard inconsistency, NOT reachable through the shipped UI.** The original draft claimed "any UI user holding `TAG_UPDATE`/`TAG_DELETE` can silently mutate it." That is false: the Management Tags list, which is what the UI renders edit/delete controls from, computes `external` **correctly** - `ReactiveTagRepositoryImpl.listMostPopular` (`:137-167`) unions a dataset-field branch via `getDataEntityWithDatasetFields` (`:373-392`) whose dataset-field side is `boolOr(tag_to_dataset_field.origin <> 'INTERNAL')` (`:385-386`), so a dataset-field-only external tag has `external=true` in the list. The UI then hides the edit/delete buttons: `EditableTagItem.tsx:36` renders them only `{!tag.external && (...)}`. So a normal UI user never sees the controls for such a tag. The defect is that the **service guard's own query (`getDto`) is inconsistent with the list query (`listMostPopular`)** - the write-path protection is incomplete, and a direct API client (or any future UI surface that drives update/delete off `getDto` instead of the list) bypasses it.

This is **net_new** - no existing item tracks the incompleteness of the guard's aggregate.

`TagOrigin` enum values confirmed: `INTERNAL`, `EXTERNAL`, `EXTERNAL_STATISTICS`. Note `listDatasetFieldDtos` (`:84-93`, the per-field detail view) treats only `ORIGIN.eq(EXTERNAL)` as external, whereas `getDataEntityWithDatasetFields` (the list) treats `ORIGIN <> INTERNAL` as external - a pre-existing minor inconsistency in what counts as "external" for `EXTERNAL_STATISTICS`; the guard fix should follow the list's `<> INTERNAL` (broader, safer) semantics.

## User-facing impact

Not reachable through the shipped UI: the Management Tags list and `EditableTagItem` correctly suppress the edit/delete controls for a dataset-field-only external tag (verified above), so an ordinary operator cannot trigger this by clicking. The real exposure is for **direct API / SDK / automation clients** that call `PUT`/`DELETE /api/tags/{id}` on such a tag: the service guard wrongly admits them, so the Collector-owned dataset-field tag can be renamed (breaking the Collector's next reconcile, which keys on the name) or deleted (so the next ingestion re-creates it, churning). It is also a latent defense-in-depth gap: the only thing preventing UI exposure today is a *different* (correct) query, so any future UI path that drives update/delete off `getDto` would inherit the hole. No data loss of catalog records and no security/permissions bypass (the caller still needs `TAG_UPDATE`/`TAG_DELETE`). Severity medium -> **low** (was framed as a broad UI-reachable silent mutation; it is a narrow API-only guard inconsistency with the UI already protected by a separate correct path).

## Suggested fix

Make the guard's query consistent with the list's: extend `ReactiveTagRepositoryImpl.getDto` (`:54-66`) so its `external` aggregate also ORs over the dataset-field origin - `boolOr(tag_to_dataset_field.origin <> 'INTERNAL')` (matching `getDataEntityWithDatasetFields:385-386`), i.e. left-join `TAG_TO_DATASET_FIELD` and treat `EXTERNAL`/`EXTERNAL_STATISTICS` as external. This closes the service-guard hole for direct-API callers and removes the latent UI risk, with no change needed in the UI (which is already correct).
