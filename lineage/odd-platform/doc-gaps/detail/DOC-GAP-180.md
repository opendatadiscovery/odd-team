#### Batch 2026-05-20-R STRENGTHENS — SQL-tier PRIMARY-SOURCE confirms partial-merge is a SERVICE-tier convention, NOT a REPOSITORY-tier enforcement + adds listDto pagination predicate divergence

- Batch R's `ReactiveDataSourceRepositoryImpl` repository sidecar adds the SQL-tier PRIMARY SOURCE behind the batch-P controller-method-tier finding:
  - **The partial-merge contract lives at the SERVICE tier, not the REPOSITORY tier** (per sidecar `coherence_check.strengthens[0]` and `invariants[3]`). The repository's inherited `bulkUpdate` (`ReactiveAbstractCRUDRepository.java:128-142 → updateMany at 203-223`) writes ALL non-non-updatable columns from the supplied records. The narrowing to ONLY name + description lives at `DataSourceIngestionServiceImpl.prepareForUpdate` (lines 74-92) via the copy-construct-then-setter pattern `new DataSourcePojo(a).setName(...).setDescription(...)`. **A service-bypassing caller invoking `dataSourceRepository.bulkUpdate(pojoListWithCollectorId=...)` WOULD overwrite the collector_id** — the cross-collector protection is a SERVICE-tier convention enforced via the `prepareForUpdate` copy-construct shape, NOT a schema-tier or repository-tier enforcement.
  - **The structural implication for maintainers**: a future maintainer adding a new payload-driven field to data_source MUST update `prepareForUpdate` to either propagate the field from payload OR explicitly preserve it. Otherwise the repository's `bulkUpdate` will write whatever the jOOQ record's default value is (Java `null` for object types) — silently NULLing the existing value. There is no schema-tier or repository-tier safeguard against this drift. This is a structural ADR-class statement that the original DOC-GAP-180 doc action does NOT capture — the doc-side fix at `custom-collectors.md` should be amended to surface the maintainer-side guidance: "If you add a new field to the DataSource ingestion payload, you MUST extend `DataSourceIngestionServiceImpl.prepareForUpdate` to either propagate or preserve it; the repository layer will silently overwrite otherwise."
  - **The cross-collector preservation is also a service-tier convention** (per sidecar invariants[4]): `prepareForUpdate` does NOT touch `collector_id` (the new pojo is a copy of the EXISTING pojo, which retains the original collector_id). So if collector A originally registered ODDRN X, and collector B's payload contains ODDRN X, the existing `collector_id` is preserved (from the copy-construct), and `bulkUpdate` does NOT overwrite it (because the service supplied the existing value). HOWEVER: if a service-bypassing caller DIRECTLY invoked `dataSourceRepository.bulkUpdate(List.of(pojoWithCollectorB))`, the `collector_id` WOULD be overwritten. The cross-collector protection is the SAME structural convention as the partial-merge.
