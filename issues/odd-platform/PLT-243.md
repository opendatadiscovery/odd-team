## Description

The authorization rules for the two Reference Data **column-mutation** endpoints are registered against the
**singular** path segment `/column/{column_id}`, but the live (OpenAPI + controller) route is the **plural**
`/columns/{column_id}`. The Spring path matcher therefore never fires for these two endpoints, and the request
falls through to the catch-all "any authenticated user" rule — so `LOOKUP_TABLE_DEFINITION_UPDATE` /
`LOOKUP_TABLE_DEFINITION_DELETE` are **not enforced**. Any authenticated caller can edit or delete lookup-table
columns regardless of whether they hold the permission.

Confirmed on `main` (verified during CTRIB-033):
- `auth/util/SecurityConstants.java:333` registers the **create-columns** rule on the PLURAL path —
  `"/api/referencedata/table/{lookup_table_id}/columns"` (POST) — **correct**.
- `auth/util/SecurityConstants.java:337` registers the **PATCH column** rule on the SINGULAR path —
  `"/api/referencedata/table/{lookup_table_id}/column/{column_id}"` (PATCH) — **wrong** (route is `/columns/`).
- `auth/util/SecurityConstants.java:341` registers the **DELETE column** rule on the SINGULAR path —
  `"/api/referencedata/table/{lookup_table_id}/column/{column_id}"` (DELETE) — **wrong**.
- The live route (openapi.yaml + `ReferenceDataController`): `/api/referencedata/table/{lookup_table_id}/columns/{column_id}`.

This is **already documented** as an operator caveat on `docs.opendatadiscovery.org`
(`developer-guides/api-reference/reference-data.md`) — but documenting it is not fixing it.

## Relationship to #1769 / CTRIB-033 (why it is NOT in that PR)

#1769 fixed two *contract* gaps (the create name-collision 500, and the column write endpoints dropping the path
table-id → cross-table mutation). CTRIB-033's column-belongs-to-table guard now blocks the *cross-table* vector
at the service layer — but it does **not** restore this permission gate (the guard runs after authn, regardless
of permission). So after #1769, a mismatched table-id is rejected, yet the endpoints remain authentication-only.

This is a **security-posture change** (G-C7): fixing it changes which requests are permitted (callers relying on
the current auth-only access would start getting 403). It was OUT of CTRIB-033's GATE-1-approved scope and needs
its own analysis/sign-off — hence a separate item, not folded into #1769.

## Suggested fix

Correct the two SecurityRule paths in `SecurityConstants.java:337,341` from `/column/{column_id}` to
`/columns/{column_id}` so the matcher fires and the `LOOKUP_TABLE_DEFINITION_UPDATE` / `_DELETE` permissions are
enforced. **Before shipping:** confirm the path-template matching semantics (how the registry matches `{column_id}`
templates against the request path) with a test that asserts an UNAUTHORISED caller gets 403 on PATCH/DELETE
column after the change; and decide (maintainer) whether the posture change needs a release note, since it tightens
access that was previously open. Consider a boot-time validator that asserts every registered SecurityRule path
matches a real route (this typo class is exactly what such a validator catches — cf. the boot-time
security-posture validator scope in `lineage/odd-platform/refactoring-scopes.md`, REFACTOR-073).
