## What

`NamespaceServiceImpl.delete` (and the analogous `OwnerServiceImpl.delete` + `DataSourceServiceImpl.delete`) implements a deterministic cascade-block contract - existence-predicates on referent tables; emit `CascadeDeleteException` if any predicate returns true; otherwise issue soft-delete UPDATE. The contract itself is sound. The implementation does a **check-then-act across separate reactive steps**: even within a single transaction, the EXISTS predicates and the parent UPDATE are distinct statements with no row-lock / `SELECT ... FOR UPDATE` / advisory lock between them. Under READ COMMITTED isolation a concurrent INSERT into a referent table BETWEEN the EXISTS predicates and the parent soft-delete can leave orphan rows pointing at a soft-deleted parent.

**The distinctive, code-settled finding (verified 2026-06-10) is narrower than the original draft:** of the three cascade-block sites, only `NamespaceServiceImpl.delete` is **not** annotated `@ReactiveTransactional` (`NamespaceServiceImpl.java:73-90` - contrast `update` at `:62-63`, which IS annotated). Both siblings ARE transactional: `OwnerServiceImpl.delete` carries `@ReactiveTransactional` (`OwnerServiceImpl.java:88`) and `DataSourceServiceImpl.delete` carries it too (`DataSourceServiceImpl.java:86`). So:

- **Namespace only:** missing `@ReactiveTransactional` means even single-thread partial failures (a network blip between the EXISTS checks and the UPDATE) leave the namespace in an inconsistent state, on top of the TOCTOU window. This is the strongest, surface-specific defect.
- **All three:** the check-then-act TOCTOU window (no row-lock between EXISTS and UPDATE) still applies, because a transaction under READ COMMITTED does not by itself serialize a concurrent referent INSERT against these reads. But for Owner/DataSource it is a within-transaction race, not an unprotected multi-statement sequence.

The original "3-surface **uniform** non-transactional" framing is **falsified**: the missing annotation is Namespace-only; the shared property is the check-then-act pattern, not the absence of `@ReactiveTransactional`.

## Where

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/service/NamespaceServiceImpl.java:73-90` - cascade-check + soft-delete chain, **no `@ReactiveTransactional`**, no row-lock. It is a **4-leg** check (`Mono.zip` of `dataSourceRepository.existsByNamespace`, `collectorRepository.existsByNamespace`, `termRepository.existsByNamespace`, `dataEntityRepository.existsNonDeletedByNamespaceId`) followed by `namespaceRepository.delete(id)` (`:74-89`).

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/repository/ReactiveAbstractSoftDeleteCRUDRepository.java:50-59` - soft-delete UPDATE site (cited from the original scan; not re-verified this session).

Sibling surfaces - same check-then-act pattern, but **both ARE `@ReactiveTransactional`** (correction 2026-06-10):
- `OwnerServiceImpl.java:87-100` - **has `@ReactiveTransactional` (`:88`)**; 3-leg cascade (`termOwnershipRepository.existsByOwner` + `ownershipRepository.existsByOwner` + `userOwnerMappingRepository.isOwnerAssociated`, `:90-91`); the 4th cascade-leg `owner_association_request` is missing per F-076c -> REFACTOR-427.
- `DataSourceServiceImpl.java:85-96` - **has `@ReactiveTransactional` (`:86`)**; single-predicate check (`dataEntityRepository.existsNonDeletedByDataSourceId`, `:88`) then soft-delete.

So the missing-annotation defect is unique to Namespace; the siblings share only the within-transaction TOCTOU window.

## User-facing impact

Static-verified at the code-structure level; the race outcome is runtime-only. Code-settled: `NamespaceServiceImpl.delete` lacks `@ReactiveTransactional` and performs a multi-step check-then-act (`:73-90`); the siblings are transactional but still check-then-act without a row-lock. These are the conditions under which a concurrent referent INSERT can orphan rows. There is no direct UI surface to this; the operator-visible end of it is the by-id read path (F-019 visibility-asymmetry) and audit/consistency of referent tables.

Not driven (runtime-only): whether the TOCTOU window is actually hit, and the orphan-accretion rate under concurrent admin-delete + ingestion-insert load - this is a race window whose magnitude depends on isolation level and timing. Remaining check to make it concrete: an integration test that races a cascade-check+soft-delete against a referent INSERT (described in Suggested fix #4); no such test or workspace probe-run exists yet, so the orphan is demonstrated by reasoning over the code, not observed.

## Why it matters

Under sustained admin-delete + ingestion-insert load, orphan referent rows accrete (FK passes at insert because the parent row exists at predicate-check time, but the parent is soft-deleted by the time the next reader looks). The orphan is hidden from list reads (soft-delete filter) but visible via direct by-id read - see the F-019 visibility-asymmetry facet for the read-side surface.

Operators trusting the cascade-block contract to keep referent tables consistent get silent data drift. The contract is RIGHT in spec; the implementation has a race window that breaks the spec under concurrency.

Severity MEDIUM because:
- The race window is narrow (millisecond-scale between EXISTS and UPDATE)
- The orphan rows do not cause user-visible failures except in the direct-by-id read path (which is a separate concern)
- BUT - at production-scale ingestion load (where many deployments live), the window is reliably hit

## Suggested fix

1. Add `@ReactiveTransactional` to `NamespaceServiceImpl.delete` - this is the missing-annotation defect, unique to Namespace (the Owner and DataSource `delete` methods already carry it).
2. For all three sites, close the TOCTOU window inside the transaction, either: (a) issue a SELECT FOR UPDATE on the parent row before the EXISTS predicates, OR (b) run the EXISTS predicates against the same snapshot via repeatable-read/serializable isolation, OR (c) hold a PostgreSQL advisory lock keyed on the parent table-id while the cascade-check + soft-delete fire. (Annotating Namespace alone fixes its partial-failure atomicity but not the concurrent-INSERT race - that needs a lock/isolation change on every site.)
3. Verify symmetric treatment across the 3 cascade-block sites (cross-link REFACTOR-430 if it remains open).
4. Add an integration test that exercises the race window - two concurrent transactions, one running cascade-check + soft-delete, the other inserting a referent row in between - assert the orphan does NOT materialize.

Open to alternatives - the right primitive depends on whether jOOQ-Reactive supports the chosen isolation mode out of the box for the target Postgres version.
