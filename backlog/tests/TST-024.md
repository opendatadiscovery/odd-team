## Description

Two adjacent gaps on the Discussions (Data Collaboration) send flow, both unverifiable from source alone:

**(a) Just-posted message may be hidden until reload (F-197 H-006).** After a successful send the messages list refetch is keyed on the `isMessageCreating` toggle, and it refetches with `lastMessageId = lastId` — where `lastId` after a successful send is the id of the just-created message, so the refetch can start AFTER the new message and omit it from the visible list until the user scrolls or reloads. Confirmed against `DataCollaboration.tsx`:
- `const { lastId, hasNext } = useAppSelector(getDataEntityMessagesPageInfo);` (line 27).
- `dispatch(fetchDataEntityMessages({ dataEntityId, channelId, size, lastMessageId: lastId }))` (line 37).
- the `useEffect` dep array is `[dataEntityId, channelId, isMessageCreating]` (line 43) — so the true→false toggle of `isMessageCreating` after a send re-fires the fetch with that `lastId`.
Whether `clearCollaborationState()` in the effect cleanup (line 41) resets `lastId` before the refetch depends on slice code not in the chain — hence the reflection's `partial` verdict.

**(b) ERROR_SENDING UI surfacing is unknown (F-197 H-011).** The send returns `202 Accepted` with the row in `PENDING_SEND`; a later delivery failure flips the row to ERROR_SENDING in the background sender. Confirmed against `DataCollaborationMessageSenderJob.java`: on a non-retryable failure, `dataCollaborationRepository.markMessageAsFailed(message.getUuid(), e.getMessage())` (line 62, inside the `else` of `shouldRetry`, lines 58-63). There is NO push/notification on the HTTP surface back to the original caller — the user must re-fetch to see status. Whether the UI's messages list renders the ERROR_SENDING state (a failed badge / retry affordance) cannot be determined from the chain — the message-rendering components (`MessagesList/Message`, `ThreadMessage/MainThreadMessage`) are sidecar-unresolved (F-197 VG-001). If the UI does not surface it, a user believes their message reached Slack when it silently failed.

**Typed gate.** (b) is a **characterization-pin** (LSN-029): the probe PENDING-F-197-1 forces ERROR_SENDING (revoke the token / target an archived channel after enqueue) and observes the UI; the IT pins whether the failed state renders today — if it does NOT, the IT asserts the CURRENT absence (no failed indicator on the row), GREEN now, RED the instant the UI starts surfacing ERROR_SENDING. (a) is a **validates-feature** guard for the documented happy-path promise (the just-posted message should be visible without a manual reload); since the message is only PENDING_SEND at navigation time it must show as pending, and the test pins whether the `isMessageCreating`/`lastId` refetch window hides it. Neither is `@Disabled` / `test.fixme`.

## Acceptance Criteria
- [ ] **(a) refetch window** — an e2e IT (datacollaboration.enabled=true + a stub/mock Slack provider) posts a message via the Share dialog, lands on the Discussions tab, and asserts the just-posted message is visible in the list WITHOUT a manual reload. If it is hidden by the `lastId` refetch window → assert that CURRENT behaviour (message absent until reload) as the characterized state with the LSN-029 flip note; if visible → assert the validated happy-path.
- [ ] **(b) ERROR_SENDING surfacing** — the probe PENDING-F-197-1 is run first: enqueue a message, force the sender to mark it ERROR_SENDING (`markMessageAsFailed`, `DataCollaborationMessageSenderJob.java:62`), open the Discussions tab, observe the UI. The IT then asserts the observed state:
  - [ ] If the UI does NOT surface ERROR_SENDING → assert the row renders with no failed indicator / no retry affordance (current behaviour — characterization pin).
  - [ ] If it DOES → assert the failed indicator renders (confirmed-good — regression guard).
- [ ] Both assertions carry in-spec comments naming F-197 H-006 / H-011 + PENDING-F-197-1 and the LSN-029 flip protocol.
- [ ] The IT is GREEN on the canonical `run-suite.sh`, is not skipped, and does not break the build.
