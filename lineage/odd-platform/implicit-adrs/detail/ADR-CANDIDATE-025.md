- **ADR-CANDIDATE-025** (NEW 2026-05-10B; STRENGTHENED 2026-05-12C): Spring `AnyNestedCondition` at `ConfigurationPhase.PARSE_CONFIGURATION` is the project's chosen idiom for OR-ing two or more `@ConditionalOnProperty` predicates at the earliest bean-graph phase — composing disjunctive `@Conditional` matching from declarative property checks
  - **Category**: promote
  - **Support**: surfaced by 2 sidecars across distinct features — `AuthorizationManagerCondition` (auth.type=OAUTH2 OR LDAP) and `SlackMessageGeneratorCondition` (the active-and-consumed sibling pattern, from batch A's `postMessageInSlack` chain). The two-feature corroboration elevates this from single-occurrence inference to "consistent project idiom". **STRENGTHENED 2026-05-12C** by the four `*SecurityConfiguration` sidecars (`DisabledAuthSecurityConfiguration.java:10` + `LoginFormSecurityConfiguration.java:31` + `OAuthSecurityConfiguration.java:71` + `LDAPSecurityConfiguration.java:51`) which use the SIBLING pattern: mutually-exclusive `@ConditionalOnProperty(value="auth.type", havingValue="...")` for mode-selection-by-enumeration. The combination of (a) `AnyNestedCondition` for declarative disjunction WHEN needed and (b) parallel `@ConditionalOnProperty` for declarative enumeration WHEN exclusive is the consistent project stance — see also ADR-CANDIDATE-030 (explicit-chain-construction as statement-of-intent) which composes with this idiom.
  - **Surfaced by**:
    - `odd-platform__java__AuthorizationManagerCondition__config-key-consumer__auth_type@L11.md:implicit_adrs.[1]` ("Spring `AnyNestedCondition` at `ConfigurationPhase.PARSE_CONFIGURATION` is the project's chosen idiom for OR-ing two `@ConditionalOnProperty` predicates at the earliest phase (before bean-definition registration). This is a consistent pattern in the codebase — the sibling `SlackMessageGeneratorCondition.java:8-19` uses the same `AnyNestedCondition` idiom (at `REGISTER_BEAN` phase) and IS consumed via `@Conditional` in `SlackMessageGeneratorConfiguration.java`." — intent_anchor: "extends AnyNestedCondition { ... super(ConfigurationPhase.PARSE_CONFIGURATION); }")
    - Cross-reference: `postMessageInSlack` sidecar (batch A) — the `SlackMessageGeneratorCondition` instance is alive and consumed; the idiom is therefore not isolated to AuthorizationManagerCondition.
  - **Decision statement**: When the project needs to compose two or more `@ConditionalOnProperty` checks as a disjunction (OR), it uses Spring's `AnyNestedCondition` as the canonical construction: declare a public class extending `AnyNestedCondition`, set the constructor's `ConfigurationPhase` (typically `PARSE_CONFIGURATION` for `@Configuration` gating, `REGISTER_BEAN` for `@Component` gating), and declare each disjunct as a static inner class annotated with `@ConditionalOnProperty(...)`. The composite returns TRUE when ANY nested class's condition returns TRUE. The pattern is applied consistently across at least two features (`AuthorizationManagerCondition` for auth-mode disjunction; `SlackMessageGeneratorCondition` for a feature-flag disjunction). The choice over alternative constructions (programmatic `SpringApplicationContextInitializer`, `@Conditional` with a custom `Condition` class implementing `matches(...)`, profile-based `@Profile`) is deliberate — `AnyNestedCondition` keeps the predicates declarative and discoverable in source-file vocabulary.
  - **Wisdom test**: PASS. The two-feature consistency is the intent anchor; structural (every future OR-of-conditional-property requires reusing this idiom or justifying a different mechanism); the pattern has measurable consequences (the `ConfigurationPhase` choice affects whether the Condition can gate `@Configuration` classes vs `@Component` classes).
  - **Evidence**:
    - AuthorizationManagerCondition.md says: "AuthorizationManagerCondition.java:6-18 (`public class AuthorizationManagerCondition extends AnyNestedCondition { ... @ConditionalOnProperty(name = \"auth.type\", havingValue = \"OAUTH2\") static class OAuthCondition {} @ConditionalOnProperty(name = \"auth.type\", havingValue = \"LDAP\") static class LDAPCondition {} }`)"
    - AuthorizationManagerCondition.md says: "SlackMessageGeneratorCondition.java:8-19 — same `AnyNestedCondition` idiom, at `REGISTER_BEAN` phase; IS consumed via `@Conditional` in `SlackMessageGeneratorConfiguration.java`."
  - **Existing ADR**: none.
  - **Co-surfaced gaps** (link from `refactoring-scopes.md`): REFACTOR-071 (`AuthorizationManagerCondition` is **dead code** — zero `@Conditional` consumers; the idiom is sound but this specific instance is vestigial), REFACTOR-072 (LOGIN_FORM mode bypasses the disjunctive matcher and runs WITHOUT `AuthorizationCustomizer` — no policy/permission enforcement under LOGIN_FORM).
  - **Proposed action**: Promote to `adrs/drafts/anynestedcondition-or-idiom.md` (new ADR). Document the canonical shape; capture both the `PARSE_CONFIGURATION` (for `@Configuration` gating) and `REGISTER_BEAN` (for `@Component` gating) phase choices. Note that the existence of `AuthorizationManagerCondition` as dead code is a signal the idiom was reached for but never wired — the maintainer should either wire it or delete it (REFACTOR-071). The ADR's existence does NOT defend the dead code; it defends the idiom.
  - **Severity rationale**: MEDIUM — pattern-shaping decision. A future contributor needing OR-of-conditional-property would either reuse this idiom (preserving consistency) or invent a new one (introducing inconsistency); the ADR forces the conversation.
