## Description

The live Activity Feed page (WebFetched 2026-05-27) lists 20 event types in 6 groups and mentions "a few additional internal event types are intentionally hidden from the global Activity filter" without enumerating them. The page is silent on (a) the structural data-entity-only audit scope, (b) the cross-owner read default, and (c) the anonymous-mutation null-actor behaviour under `auth.type=DISABLED`. Four corroborating facets need to land in one revision:

**Caveat 1 — Structurally data-entity-scoped audit (F-021a).** `V0_0_48__add_activity.sql:4, 12` declares `activity.data_entity_id NOT NULL FK to data_entity(id)`. RBAC mutations (Role / Policy / Owner-association CREATE/UPDATE/DELETE), Datasource registration, Collector token rotation, Integration Wizard config writes **cannot physically emit** even if a future `@ActivityLog` annotation were added — the schema prevents it. The doc's "records changes to data entities — description edits, ownership changes, tag and term assignments, custom-metadata edits, and alert lifecycle events" framing implicitly suggests platform-wide audit; the implementation is strictly data-entity-scoped. **Compliance auditors expecting platform-wide audit discover the gap only when they ask for RBAC-mutation history.** This is the structural root cause of the cross-pillar audit-asymmetry canonicalisation candidate in `system-mission.md`.

**Caveat 2 — 27 event types in code vs 20 documented (F-021b — dedups DOC-GAP-191).** `ActivityEventTypeDto.java:3-31` declares 27 enum constants. The doc lists 20. The seven undocumented: `DATA_ENTITY_OVERVIEW_UPDATED`, `DATA_ENTITY_METADATA_UPDATED`, `DATA_ENTITY_SCHEMA_UPDATED`, `DATA_ENTITY_RELATION_UPDATED`, `CUSTOM_METADATA_CREATED`, `CUSTOM_METADATA_UPDATED`, `CUSTOM_METADATA_DELETED`. The live page's hint about "additional internal event types" is the partial-disclosure half; the page does not enumerate which seven are hidden or why.

**Caveat 3 — Cross-owner read default (F-021c).** `ReactiveActivityRepositoryImpl` has no per-owner predicate on read default; every authenticated user sees every entity's activity. The `MY_OBJECTS` type parameter is owner-scoped, but it scopes by ENTITY-ownership (entities the caller owns), not actor-axis (events the caller PERFORMED). A reviewer asking *"what did Alice do?"* with `userIds=[alice]` gets activity on entities ALICE OWNS via the cross-mode-bleed-prone LEFT JOIN on `USER_OWNER_MAPPING.OIDC_USERNAME` — the same misleading-label-vs-implementation pattern as F-043 (LSN-020).

**Caveat 4 — Anonymous-mutation attribution gap under DISABLED (F-021d).** `ActivityServiceImpl` writes `created_by=null` for activity events generated by anonymous callers under `auth.type=DISABLED`. The UI renders these events visually indistinguishable from system-generated events. Operators auditing DISABLED-mode events cannot distinguish "anonymous user did X" from "platform did X".
