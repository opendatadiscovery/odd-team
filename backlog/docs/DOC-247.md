## Description

`OwnerFormData.roles` is OpenAPI-optional (`components.yaml:419-422`, no `required:` marker). `OwnerServiceImpl.java:117-122` `getRoleIdsList` method collapses both null AND empty list to `List.of()`. The update transaction then calls `deleteOwnerRelationsExcept(ownerId, List.of()).then(createRelations(ownerId, List.of()))` — the first half DELETES all current role-links (since no existing link is in the empty set); the second half INSERTS nothing.

**Operator-visible consequence**: an API consumer (script, integration, CI tool) issuing `PUT /api/owners/{id}` with body `{"name": "new_name"}` to rename ONLY — expecting unspecified fields to mean "leave unchanged" — instead **removes ALL role assignments** from the Owner. The UI in practice always sends the current `roles` list (read-modify-write pattern), so the hazard is MASKED in normal UI flows — but any direct API consumer is exposed.

The body shape is PUT-semantic (whole-resource replacement) but the field is OPTIONAL in the OpenAPI spec; consumers reading the spec reasonably infer PATCH-semantic ("absent field means leave unchanged"). This is a CRITICAL UX hazard: destructive AND silent AND visible only to direct-API consumers, not to UI-driven workflows.

## Acceptance Criteria

- [ ] The Owners page (`enable-security/authorization/owners.md`) gains a `## ⚠ Destructive API semantic: PUT with empty roles destroys all role bindings` H2 (or H3 within an existing CRUD section) covering:
  - **The hazard**: `PUT /api/owners/{id}` with body `{"name": "new_name"}` (omitting `roles`) **REMOVES ALL role assignments** from the Owner. The OpenAPI spec marks `roles` as optional but the runtime treats absent-or-empty identically — both mean "delete all role-links".
  - **Why this is silent**: the UI's read-modify-write pattern always sends the current `roles` array, so the hazard never surfaces via the Management UI. API consumers calling the endpoint directly (CI scripts, integration jobs, terraform-driven config) hit it on first omission.
  - **Operator action today**: ALWAYS include the full `roles` array in PUT requests, even for rename-only operations. If you want to LEAVE roles unchanged, fetch the Owner first and copy the existing `roles` value verbatim into the PUT body.
  - **Sample safe-pattern code**:
    ```bash
    OWNER=$(curl -X GET /api/owners/$ID | jq)
    NEW_NAME="new_name"
    NEW_BODY=$(echo "$OWNER" | jq --arg n "$NEW_NAME" '.name = $n')
    curl -X PUT /api/owners/$ID -d "$NEW_BODY"
    ```
  - **Track upstream**: PLT-066 (semantic fix — either make `roles` required in the spec OR add a `null` sentinel meaning "no change").

## Platform-side follow-up filed

- **PLT-066** — Owner update semantic fix: either (a) make `roles` REQUIRED in the OpenAPI spec (breaking change for API consumers); OR (b) introduce PATCH semantic where `null` means "no change" and an empty array means "remove all"; OR (c) keep PUT semantic but require `roles` array to be non-null in the request. Recommendation: option (b) — least-surprise PATCH semantic.
