## What

Editing a Lookup Table's **name** in the UI (a pure-metadata action, the operator's mental model) triggers a
physical `ALTER TABLE ... RENAME TO ...` on the public `lookup_tables_schema` Postgres relation that backs the
table. There is no warning dialog, no deprecation alias, and no activity/audit event. Every downstream
consumer still joining the old relation (`lookup_tables_schema.n_{ns}__{old_name}`) - dbt models, BI queries,
notebooks, views - breaks immediately with `relation "..." does not exist`. This is the same operator-harm
class as LSN-001 (attachment ephemeral default) and LSN-002 (MinIO region unset): a documented, reasonable
operator action quietly destroys a thing they depend on.

## Reproduced live (docker `:latest`, auth.type=DISABLED, 2026-06-07 - IT-048 UC-001)

1. Create lookup table `it048...` -> physical relation `lookup_tables_schema.n_1__it048...` exists.
2. `PUT /api/referencedata/table/{id}` with a changed `name` -> 200.
3. DB read-back: **old physical relation gone (`false`), new physical relation present (`true`)** - the
   rename cascaded to the physical table. A pre-existing join to the old name now errors.

A description-only edit (name unchanged) does **not** rename the physical table (IT-048 UC-002, the
harmless-edit guard, confirmed) - so the trigger is specifically the name change.

## Root cause

`ReferenceDataServiceImpl.updateLookupTable` (`odd-platform-api/.../service/ReferenceDataServiceImpl.java:106-124`)
derives the physical `tableName` from the business name via `buildTableName` (`:191-194`,
`"n_" + namespaceId + "__" + name.toLowerCase().replace(" ","_")`) and gates the physical update on a
name-changed check (`:119`: `table.tablesPojo().getTableName().equals(tableDto.getTableName()) ? Mono.empty()
: referenceDataRepository.updateLookupTable(...)`). When the derived name differs it calls
`ReferenceDataRepositoryImpl.updateLookupTable` (`:182-197`), which issues a jOOQ DDL **rename** against the
physical relation: `DSL.alterTable(table(DSL.name(<oldTableName>))).renameTo(dto.getTableName())` (`:192`,
schema `lookup_tables_schema`, `:57`), plus index/constraint renames (`:195-197`). Business-name and
physical-name are coupled 1:1 with no indirection.

## User-facing impact

**Verified-trace end-to-end** (FE + BE + driven), 2026-06-10. The Master Data -> Lookup Tables **Edit**
dialog (`odd-platform-ui/src/components/MasterData/LookupTableForm.tsx`) presents the name as a plain
editable `Input` labelled "Table name" (`:90`); the only action is a generic "Save lookup table" button
(`:129`) that fires `useUpdateLookupTable` -> `PUT /api/referencedata/table/{id}` (`:62-65`). There is **no
confirmation dialog, no warning copy, and no rename-specific affordance** anywhere in the form - the operator's
entire signal is a metadata-style text field, exactly matching the "I'm renaming a label" mental model. On
submit the BE issues the physical `ALTER TABLE ... RENAME` (above) and returns 200; every downstream consumer
joining the old physical relation (`lookup_tables_schema.n_{ns}__{old_name}`) - dbt models, BI queries,
notebooks, views - then fails with `relation "..." does not exist`. Silent, irreversible-at-the-data-layer,
no audit event. (Driven by IT-048/UC-001 on the running stack, in the passing feature-complete suite.)

## Fix options (per F-059 reflection)

- Decouple the business display-name from an immutable physical relation name (rename = metadata-only); **or**
- keep a deprecation **alias VIEW** at the old name on rename; **and**
- raise a UI confirm-dialog at rename-time + emit an `ActivityEvent` so the change is auditable.
