## What

The Swagger UI shell loads, but the OpenAPI document never loads - the page sits on **"Failed to load API definition."** The underlying spec request (the api-docs JSON) **hangs forever** (no response; CPU ~1%, so it's a dead thread, not a loop).

Root cause: **`springdoc-openapi` 2.2.0 is binary-incompatible with Spring Framework 6.2.x.** springdoc 2.2.0 calls `new ControllerAdviceBean(Object)` - a constructor Spring **removed** in 6.2. When springdoc walks the platform's `@ControllerAdvice` (to build response schemas), it throws:

```
java.lang.NoSuchMethodError:
  'void org.springframework.web.method.ControllerAdviceBean.<init>(java.lang.Object)'
    at org.springdoc.core.service.GenericResponseService...  [springdoc-openapi 2.2.0]
                                                             [spring-web 6.2.11 - the class's home jar]
```

The `NoSuchMethodError` kills the reactive worker thread, so the request's `Mono` never completes and the HTTP call hangs (observed 2026-06-04 against the running image). Both spec groups time out - `SwaggerUIConfiguration.java:11-21` defines exactly two (`platform-api`, `ingestion-api`).

## Where

- `gradle/libs.versions.toml:25` -> `springdoc-openapi = '2.2.0'` (pinned), consumed by `odd-platform-api/build.gradle:49`.
- Spring Boot **3.4.10** (`odd-platform-api/build.gradle:2` - `id 'org.springframework.boot' version '3.4.10'`) -> Spring Framework **6.2.x** (`spring-webflux = '6.2.11'` in `gradle/libs.versions.toml`).
- The swapped serving paths: `application.yml:22-26` - `springdoc.api-docs.path: /api/v3/swagger-ui.html` (the JSON) and `springdoc.swagger-ui.path: /api/v3/api-docs` (the UI).

**Bytecode proof (2026-06-10, from this build's own dependency cache):** `javap -c` on springdoc-openapi-starter-common 2.2.0's `GenericResponseService` shows `invokespecial org/springframework/web/method/ControllerAdviceBean."<init>":(Ljava/lang/Object;)V`; `javap` on spring-web 6.2.11's `ControllerAdviceBean` shows its ONLY remaining constructor is `(String, BeanFactory, ControllerAdvice)`. The `NoSuchMethodError` is therefore guaranteed on this dependency pair, not an environment artefact.

## User-facing impact

Users: operators and API/SDK consumers who open the platform's interactive API documentation; anyone following the docs' API Reference page to the live spec.

What they do / observably get (driven, not static - runtime evidence on disk):

- Open `{base}/api/v3/api-docs` (the Swagger UI route): a real 302 to the webjars shell, which renders - then the in-page spec fetch never returns and the UI sits on **"Failed to load API definition"** (`integration-tests/protocols/IT-042-swagger-openapi-discovery.md:23-30`).
- Fetch `{base}/api/v3/swagger-ui.html` (the OpenAPI JSON): hangs past any sane budget; no document within 8s (run record `integration-tests/run-log/2026-06-04-IT-042.md` - e2e PASS against stack `dd52f520`, where PASS = the characterization pin reproduced the failure: shell serves, spec does not load).
- Public demo (`demo.oddp.io`): NOT independently verifiable anonymously - probed 2026-06-10, both routes return `302 -> /login` (the demo gates the Swagger surface behind auth), so the in-UI failure there is inferred from the version pin, not observed.

## When / why it broke

Commit **`2033822e`** - *"fix(security): spring boot upgrade and dependency alignment (#1736)"* (2026-04-01) - bumped `spring-webflux` **6.1.14 -> 6.2.11** (and the Boot line to 3.4.10) for CVE fixes, but **left `springdoc-openapi` pinned at 2.2.0** (the commit's `libs.versions.toml` diff touches spring-webflux/spring-cloud-aws/spring-mail only). Before that commit, Spring 6.1.14 still shipped the deprecated single-arg constructor and Swagger worked. The security-driven Spring upgrade left springdoc behind; the current `:latest` image carries the broken combination.

- This is a **silent feature regression** that shipped undetected because **there was no test pinning the OpenAPI-spec endpoint.** An integration test now pins it: odd-team **IT-042** is an LSN-029-style characterization pin that is **GREEN while the bug exists** (asserting the spec does NOT load) and **flips RED the moment the fix lands** - at which point it gets inverted to assert the spec loads (`integration-tests/e2e/specs/swagger-openapi-discovery.spec.ts:48-57`). (An earlier revision of this issue called IT-042 "currently RED, flips green when fixed" - polarity inverted; corrected 2026-06-10.)
- The published docs page describing Swagger was also (separately) orphaned from `SUMMARY` and 404'd; recovered + caveated in `documentation` PR **#95** (`docs/recover-swagger-api-reference`, merged).

## Reproduce

```
curl -m 8 -i {base}/api/v3/swagger-ui.html     # the OpenAPI JSON spec -> HANGS (no response within 8s)
curl -i {base}/api/v3/api-docs                  # the UI -> 302 -> shell 200, but the in-page spec fetch hangs
```

(Local stack with `auth.type=DISABLED`; on auth-enabled deployments both routes 302 to /login first.)

## Fix

Bump springdoc to the Spring Boot 3.4 / Spring 6.2-compatible line in `gradle/libs.versions.toml`:

```
springdoc-openapi = '2.7.0'   # was 2.2.0
```

No code change needed - it's a stale-jar binary-compatibility problem. After the bump, verify the OpenAPI JSON returns and the Swagger UI loads the definition, and invert the IT-042 pin to lock the working state so a future Spring/springdoc drift is caught immediately rather than shipping silently.

## How discovered

Found during the 2026-06-04 integration-test grind (the Swagger discovery IT could not get a spec) plus maintainer investigation against the running `docker-odd-platform :latest` image, which captured the `NoSuchMethodError` and the dead-thread hang. Re-verified 2026-06-10 (user-facing verification sweep): every citation re-read on current `main` (8c142e15); the binary incompatibility proven from the dependency cache via `javap` (see "Where"); IT-042 polarity corrected (characterization pin is GREEN-while-broken, was described inverted); the demo claim downgraded to inferred (anonymously unverifiable - 302 -> /login, probed 2026-06-10); the stack-trace jar attribution corrected to `spring-web` 6.2.11 (the class's actual home; spring-webflux merely pulls it in).

## Footnote (usability, optional)

The springdoc paths are deliberately **swapped** in `application.yml:22-26`: Swagger **UI** -> `/api/v3/api-docs`, OpenAPI **JSON** -> `/api/v3/swagger-ui.html`. Even after the version fix, the intuitive `.../api-docs` serves the UI, not the spec - consider un-swapping for clarity (separate, optional change).
