## Description

Three small, low-risk pins around the feature-flag surface (F-034, hypotheses H-006 / H-007 / H-009). Each guards a current observable behaviour; none requires a code change now.

**Typed gate: characterization-pin (LSN-029)** for the enum-lockstep and disabled-affordance assertions (they assert the CURRENT shape and go RED the instant it drifts), with a **validates-feature** flavour on the WithFeature render contract.

1. **Anon-block 302-vs-401 posture (H-006).** `SecurityConstants.WHITELIST_PATHS` (`SecurityConstants.java:95-96`) is `{"/actuator/**", "/favicon.ico", "/ingestion/**", "/img/**", "/api/slack/events"}`. The feature-flag list endpoint is NOT whitelisted, so an unauthenticated caller is handled by the configured auth posture (LOGIN_FORM → browser-redirect 302 to the login page; OAUTH2/LDAP/DISABLED behave per their mode) rather than a uniform JSON 401. The pin records which paths bypass auth so a future whitelist edit (adding/removing a path, or flipping the feature endpoint to a hard 401) trips the test.

2. **Cross-repo Feature-enum lockstep (H-007).** The canonical `Feature` enum is the spec — `components.yaml:115-119` declares exactly `DATA_COLLABORATION` and `ALERT_NOTIFICATIONS`. The generated TS mirror `Feature.ts:20-23` declares the identical two members as a `const` object. These two must stay in lockstep (the TS file is OpenAPI-generated and hand-edits or a regen drift would silently desync the UI's `WithFeature` gate from the backend). The pin asserts both sources enumerate the same members.

3. **Disabled-affordance renders nothing (H-009).** `WithFeature.tsx:31-32` is `return isFeatureEnabled ? <>{children}</> : null;` — when a feature is OFF and `children` (not `renderContent`) is used, the component renders **null**: there is no "feature unavailable" placeholder, no upsell, no disabled-state affordance. The pin asserts this exact current UX (render nothing) so a future deliberate placeholder addition is a conscious RED, not an accident.
