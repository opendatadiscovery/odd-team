# i18n / Multilingual UI

Seven-language UI bootstrapped via `react-i18next` at app start. Default `en`; user choice persists in `localStorage('i18nextLng')`. No server-side rendering of locale. `fallbackLng: 'en'` (a missing key renders the English label, never a foreign-locale leak); `keySeparator/nsSeparator: false` (keys are English phrases that contain `:`/`.`).

## Code Entry Points (odd-platform — UI only; no server-side localization)

### Bootstrap
- `odd-platform-ui/src/locales/i18n.ts` — `i18n.use(initReactI18next).init({ resources, lng, fallbackLng: 'en', keySeparator: false, nsSeparator: false })`. `lng = localStorage.getItem('i18nextLng')` if it is one of the 7 supported locales, else `'en'`. `fallbackLng: 'en'` is the structural floor (was the multi-locale array — the #1564 Portuguese-leak, fixed by #1783); separators off so phrase-keys like `Source:` are looked up verbatim (#1751 / PLT-205).
- `odd-platform-ui/src/index.tsx:24` — `import 'locales/i18n';` (side-effect import; runs at app start before `<App />` renders).

### Translation resources (one JSON per locale, key-string pairs)
- `odd-platform-ui/src/locales/translations/{en,es,ch,fr,ua,hy,br}.json` — **SEVEN** locale catalogs (`br` = Brazilian Portuguese, added by #1564), each at **exact 612-key parity** with en (natural-keys: key === value in en). The historic "~70→84 keys missing from all non-en catalogs" gap (#1751) and the "~208 hardcoded strings bypassing `t()`" gap (PLT-205) are CLOSED — completeness is now enforced by the three guards below.

### Toolbar chrome consumer (the #1748 surface)
- `odd-platform-ui/src/components/shared/elements/AppToolbar/ToolbarTabs/ToolbarTabs.tsx:34-82` — all nine primary-nav tab labels through `t()` (unconditional `useMemo`, no feature-toggle filtering). The three pillar tabs (Data Quality :46 / Data Modelling :51 / Master Data :56) had no key in any catalog until odd-platform#1748 added 18 entries (3 keys × 6 catalogs, commit `3049b9af`); regression pinned by `integration-tests/protocols/IT-102-multilingual-i18n.md` case 4.

### Display names + locale type
- `odd-platform-ui/src/lib/constants.ts:158` — `LANGUAGES_MAP` (locale code → human-readable name shown in `<SelectLanguage>`)
- `odd-platform-ui/src/lib/interfaces/shared.ts:17` — `type Lang = keyof typeof LANGUAGES_MAP` (the typed locale-code union)

### UI surface — language switcher widget
- `odd-platform-ui/src/components/shared/elements/AppToolbar/SelectLanguage/SelectLanguage.tsx` — the dropdown.
- `odd-platform-ui/src/components/shared/elements/AppToolbar/AppToolbar.tsx` — mounts `<SelectLanguage>` inside the user menu (anchored on the toolbar profile button); reads `i18n.language` to render the currently-active locale name via `LANGUAGES_MAP`.

### Translation consumption pattern
- `useTranslation()` hook from `react-i18next` is the canonical access point in components. Example: `AppToolbar.tsx:3 — import { useTranslation } from 'react-i18next'`.
- Translation keys are referenced as `t('Select language')`, `t('Logout')`, etc. Keys without a translation fall through the `fallbackLng` chain.

## Caveats (consumer-read audit, 2026-05-08)

- **localStorage persistence is the only choice memory.** Cleared storage / new browser / incognito session → user reverts to default `en` silently. No server-side per-user preference.
- **Three automated guards enforce completeness** (`odd-platform-ui/src/locales/__tests__/i18n-key-parity.test.ts`, vitest): (1) **catalog-parity** — every non-en catalog must equal en's key set (missing OR orphan fails); (2) **no-unwrapped-attribute-literal** — every user-facing JSX attribute (`placeholder`/`label`/`title`/`aria-label`/…) must be `{t(...)}`, closing the hole the eslint `no-literal-string` rule silently misses for attributes (it covers JSX text nodes); (3) **symbolic-key value-hint** (added by #1776 / CTRIB-036) — for a symbolic key (en value ≠ key; today only `main search placeholder`, whose en value is the home-search hint), every non-en value must be a translated multi-item hint (≥2 list separators), not a literal gloss of the key. NOTE: the FE vitest/eslint gate is not yet wired into CI (`run-pr-tests.yaml` is backend-only; the bot cannot edit workflows) — PLT-215 #3, a maintainer step.
- **No locale-aware routing or `<html lang="...">` attribute switching.** SEO + a11y (screen readers signalling page language) are not addressed by the current bootstrap.
- **Seven-language scope is fixed at build time.** Adding an eighth locale requires: adding `translations/<lang>.json` (at full key-parity), a `LANGUAGES_MAP` + `LANG_TO_COUNTRY_CODE_MAP` entry, and the import + resource-map entry in `i18n.ts`. No runtime extension point. Do NOT add locales to `fallbackLng` (it must stay `'en'`).
- **`fallbackLng: 'en'`** — a key missing from the user's locale renders the **English** label (never another locale). The `<SelectLanguage>` picker is built from `Object.keys(LANGUAGES_MAP)`, NOT `i18n.languages` (which collapses to `['en']` under `fallbackLng:'en'` — the PLT-226 picker regression, fixed in #1785).
