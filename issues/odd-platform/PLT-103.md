## What

`/actuator/env` is exposed and enabled by default and, under the default quick-launch auth posture (`auth.type=DISABLED`), is reachable without authentication.

**Corrected 2026-06-10 (user-facing verification sweep):** the original draft's load-bearing claim - that `/actuator/env` returns `spring.datasource.url`, the LDAP bind password, and the Slack/webhook URLs **verbatim** because "Spring masks only keys named `password`" - is FALSE. Spring Boot's environment endpoint does NOT auto-mask by key-name pattern in this version; it masks **every** property VALUE unless `management.endpoint.env.show-values` is set to `ALWAYS` or `WHEN_AUTHORIZED`. The default is `NEVER`. There is **no `show-values` key anywhere in the repo** (grep-verified over `src/main/resources` + `src/main/java` - same finding as PLT-078), so the `NEVER` default applies and `/actuator/env` redacts every VALUE (`******`) for every caller - including `spring.datasource.url`, `auth.ldap.password`, and the Slack/webhook URLs. The "leaks JDBC URL / LDAP bind password / Slack/webhook URL" claim collapses: those appear only as masked entries.

What an anonymous caller scraping `/actuator/env` DOES learn is the **configuration-key schema**: which property keys and property sources are present - i.e. which OAuth2 providers are wired (by key prefix), whether LDAP is configured, whether REMOTE attachment storage is set up, that a JDBC datasource exists (the KEY, not its value). That is a recon / fingerprinting exposure, not a secret-value leak. (The live docs already document the masked-values reality at `documentation/docs/configuration-and-deployment/odd-platform.md:106`.)

This anonymous reachability is shipped via three defaults that compound:
- `management.endpoints.web.exposure.include: health, prometheus, env, info` (env exposed; `application.yml:230-231`),
- `management.endpoint.env.enabled: true` (env enabled; `application.yml:237-238`),
- under `auth.type=DISABLED` (the shipped default; `application.yml:51`), `DisabledAuthSecurityConfiguration` is `.anyExchange().permitAll()` - so the actuator surface is anonymous. (Note: `/actuator/**` is in `SecurityConstants.WHITELIST_PATHS:95-96`, so it is reachable pre-auth in EVERY auth mode, not only DISABLED - see PLT-078.)

Sources: HARVEST-012, HARVEST-016, HARVEST-022 (doc-understanding harvest, 2026-05-29). Doc caveat tracked at `backlog/docs/DOC-292.md`. **This is the same exposure surface as PLT-078** (which already carries the corrected masked-values framing and the default-tightening fix); PLT-103 and PLT-078 should be reconciled into one item before filing - see the note under "How discovered".

## User-facing impact

The "user" is an operator (deployment posture) and a network-adjacent attacker (recon). The reachability + exposure facts are code-confirmed; the exact `/actuator/env` body is a runtime observable strongly determined by the Spring Boot `show-values=NEVER` default.

- **WHO/WHAT:** anyone who can reach the platform's HTTP port under `auth.type=DISABLED` (the shipped default) can `GET /actuator/env` with no authentication - confirmed by BE trace 2026-06-10 (`DisabledAuthSecurityConfiguration.java:12-18` `.anyExchange().permitAll()`; `SecurityConstants.java:95-96` additionally whitelists `/actuator/**` pre-auth in every mode; `application.yml:231` exposes `env`).
- **WHAT they observably get:** the property-KEY catalog with every VALUE masked `******` (Spring Boot `show-values` default = `NEVER`; no override exists in the repo - grep-verified) - so the recon yield is the *configuration-key schema* (which integrations are wired), NOT the JDBC URL / LDAP password / Slack-URL values. *Static + config trace consistent; not driven* - the exact `/actuator/env` body should be confirmed by `curl http://<host>/actuator/env` on a running default-posture stack.
- **NOT exposed:** `spring.datasource.url`, `auth.ldap.password`, Slack/webhook URLs as VALUES (all masked) - verified-by-config-trace 2026-06-10 (no `show-values` key -> `NEVER`).

## Why it matters

A wide, anonymously-reachable actuator surface in the default posture is a real hardening gap: an operator who stands up the quick-launch / demo stack on a public LoadBalancer (mitigated only by source-ranges) exposes `/actuator/env` to anyone who can reach the HTTP port without authenticating. But the yield is the platform's **configuration-key fingerprint** (which integrations are wired) - useful recon for targeting follow-on attacks - NOT credential values, which are masked by the `show-values=NEVER` default. This is regraded **medium** rather than high because the original high rationale (verbatim JDBC URL + LDAP bind password + Slack/webhook URL leak -> "leak production infrastructure coordinates", LSN-001/002 class) collapsed on verification: those values are masked. The residual (unauthenticated config-key enumeration + defense-in-depth tightening) is a medium hardening gap, and the default-tightening fix is the same one PLT-078 already proposes.

## Suggested fix

(Same surface and fix as PLT-078 - reconcile before filing.)

- Restrict the default `management.endpoints.web.exposure.include` to `health, prometheus` (drop `env` and `info`) so the schema-fingerprinting endpoint is opt-in, not default. Production-shaped defaults out of the box.
- If `env` must stay available for operability, gate the actuator path so it is never anonymous even under `auth.type=DISABLED` (a dedicated actuator security chain rather than `permitAll()`, or remove `/actuator/**` from `WHITELIST_PATHS` and narrow it to `/actuator/health` + `/actuator/prometheus`).
- Document the residual reachability on the demo/quick-launch deployment options next to the existing HTTP-only caveat (DOC-242 already publishes the operator-facing mitigation table and is already correct on the masking point).

Note: there is **no value-unmasking to fix** (the original "add LDAP bind password + datasource URL to the sanitised-keys set" step is moot - they are already masked by the `NEVER` default; the gap is reachability and key-schema enumeration, not unmasked values).
