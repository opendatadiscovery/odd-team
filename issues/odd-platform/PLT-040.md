## What

The Management → Associations → Active tab's per-row Remove affordance uses ONE permission to enable the UI button and a DIFFERENT permission to gate the backend DELETE. The two permissions are semantically disjoint (per the F-172c correction — see DOC-221).

- **UI gate** (`ActiveAssociationRequest.tsx:91`, verified verbatim this session): `disabled={!hasAccessTo(Permission.OWNER_ASSOCIATION_MANAGE)}`
- **Backend gate** (`SecurityConstants.java:159-162`, verified verbatim this session): `DELETE /api/owners/mapping/{owner_id}` → `OWNER_RELATION_MANAGE`

These two permissions are NOT aliases. `OWNER_ASSOCIATION_MANAGE` is the triage permission (PUT `/api/owner_association_request/{id}`); `OWNER_RELATION_MANAGE` is the direct-write-and-delete permission (POST + DELETE `/api/owners/mapping/*`).

## Where

UI gate:
```tsx
// odd-platform-ui/src/components/Management/OwnerAssociations/OwnerAssociationsList/OwnerAssociationsActive/ActiveAssociationRequest/ActiveAssociationRequest.tsx:91
disabled={!hasAccessTo(Permission.OWNER_ASSOCIATION_MANAGE)}   // <— wrong permission for the underlying DELETE
```

Backend gate:
```java
// odd-platform-api/src/main/java/.../auth/util/SecurityConstants.java:159-162
new SecurityRule(HttpMethod.DELETE, "/api/owners/mapping/{owner_id}", "OWNER_RELATION_MANAGE")  // canonical gate
```

## Why it matters

Two operator-trap classes stacked:

1. **User has `OWNER_ASSOCIATION_MANAGE` but NOT `OWNER_RELATION_MANAGE`**: UI shows Remove enabled; operator clicks; backend returns 403; operator confused. Time-wasting failure, but at least observable.

2. **User has `OWNER_RELATION_MANAGE` but NOT `OWNER_ASSOCIATION_MANAGE`**: UI shows Remove DISABLED; operator believes they cannot remove the binding. But they CAN — directly via `DELETE /api/owners/mapping/{owner_id}` (e.g. via curl, the API console, or a script). **The UI HIDES a capability the backend grants.** This is the compounding security risk — a UI that under-states an operator's actual privileges defeats the principle of least surprise on the privilege model and makes audit / impact-analysis harder than it should be.

Severity HIGH because the asymmetry is on a load-bearing security permission and the second trap class is genuinely confusing for operators auditing "who can unbind users on this deployment". The fix is small.

## Suggested fix

Pick `OWNER_RELATION_MANAGE` as the canonical Remove gate (matching the backend) and align the UI:

```diff
- disabled={!hasAccessTo(Permission.OWNER_ASSOCIATION_MANAGE)}
+ disabled={!hasAccessTo(Permission.OWNER_RELATION_MANAGE)}
```

at `ActiveAssociationRequest.tsx:91`.

Rationale for picking `OWNER_RELATION_MANAGE` (rather than the other direction):
- The backend gate is the canonical security boundary; the UI gate is a UX hint
- Changing the backend gate would broaden the permission semantics in a way that pollutes `OWNER_ASSOCIATION_MANAGE` (triage) with a direct-write-and-delete capability
- The corrected `permissions.md` description (DOC-221) maps `OWNER_RELATION_MANAGE` to "direct-bind + unbind" cleanly; changing the UI to match preserves that clean semantic split

Optional follow-up: audit other admin affordances on this tab + sibling tabs for similar UI/backend permission asymmetries. Cross-link to a permission-gate-consistency sweep if other sites are found.
