- **ADR-CANDIDATE-047** (NEW 2026-05-12D): OAuth2 client configuration uses a `Map<String, OAuth2Provider>` keyed by Spring's `registrationId` — the map key IS the URL-path segment used in `/oauth2/authorization/{key}` and the OAuth2 callback `/login/oauth2/code/{key}`. Operators may declare any number of OAuth2/OIDC clients in the same deployment by extending the map; no fixed enumeration of provider slots constrains operator choice. The schema mirrors Spring Boot's own `spring.security.oauth2.client.registration.{id}` shape
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar (`ODDOAuth2Properties`) — single occurrence but schema-defining for the entire OAuth2 surface; cross-validated by the consumer-side iteration patterns (`ODDOAuth2PropertiesConverter.java:16-58` iterates the map via `forEach((key, provider) -> ...)`; `OAuthSecurityConfiguration.java:162-178` maps over the resulting `OAuth2ClientPropertiesMapper` output keyed by the same key set)
  - **Surfaced by**:
    - `odd-platform__java__org_opendatadiscovery_oddplatform_auth__config-properties-class__ODDOAuth2Properties.md:implicit_adrs.[0]` ("Per-client configuration is keyed via `Map<String, OAuth2Provider>` rather than a typed multi-tenant schema. The decision encodes: (a) the map key IS the Spring `registrationId` (used verbatim as the URL segment `/oauth2/authorization/{key}` and the OAuth2 callback `/login/oauth2/code/{key}`); (b) operators may declare any number of OAuth2/OIDC clients in the same deployment by extending the map; (c) no fixed enumeration of provider slots constrains operator choice. The intent is anchored by the consumer-side iteration patterns... The map shape is consistent with Spring Boot's own `spring.security.oauth2.client.registration.{id}` schema — ODD's `auth.oauth2.client.{key}` mirrors it." — intent_anchor: `private Map<String, OAuth2Provider> client = new HashMap<>();`)
  - **Decision statement**: ODD's OAuth2 client schema is a `Map<String, OAuth2Provider>` where the map key IS the Spring `registrationId` — used verbatim as the URL path segment in `/oauth2/authorization/{key}` (the OAuth2 authorization entry-point) AND `/login/oauth2/code/{key}` (the OAuth2 callback path). The decision has three structural consequences: (a) operators define new OAuth2 clients by extending the map (`auth.oauth2.client.google: ...` + `auth.oauth2.client.cognito: ...` + `auth.oauth2.client.azure: ...`), no fixed enumeration of slots; (b) the map key becomes part of the URL surface — choosing a key like `'corp-okta'` shapes the operator-facing login URL `/oauth2/authorization/corp-okta`; (c) the schema mirrors Spring Boot's own `spring.security.oauth2.client.registration.{id}` shape, leveraging the Spring binding-and-mapper machinery rather than authoring custom resolution. Trade-off: open extensibility (any operator can add Okta, Keycloak, custom OIDC) at the cost of zero compile-time enforcement of provider keys — a typo in the map key (e.g. `gogle` vs `google`) silently creates a deployment with a working but unintended OAuth2 client. The intent IS anchored by the consumer-side iteration pattern (`forEach((key, provider) -> ...)`) — the consumer trusts the map shape as the source of truth, not a typed enum.
  - **Wisdom test**: PASS. The choice of `Map<String, OAuth2Provider>` over a typed N-slot schema (e.g. `class OAuth2Clients { Provider google; Provider github; Provider cognito; Provider azure; }`) is a positive design decision — the alternative would have been more type-safe but less extensible. The schema-Spring-Boot-alignment evidence (mirroring `spring.security.oauth2.client.registration.{id}`) confirms the deliberate convention-over-custom-DSL choice. Structural — every OAuth2 client lives in this map; every consumer iterates this map.
