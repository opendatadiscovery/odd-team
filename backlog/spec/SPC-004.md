## Description

**The chain (corrected to the ESTABLISHED mechanism — the codegen repos publish via self-contained release
workflows, NOT contributor PRs):**
1. **opendatadiscovery-specification — PR #87 MERGED** (2026-06-18, `20e0f63d` on `main`) — `entities.yaml`
   (`ML_MODEL_ARTIFACT`/`_INSTANCE` + a schema description) + `specification.md` (the ML model brought into one
   ordered "ML entities" taxonomy; it was stale — ML models as DataConsumers only, ML experiments as transformers,
   no DataEntityGroup).
2. **opendatadiscovery-specification-contracts** — the MAINTAINER dispatches the `Maven Central release`
   (`workflow_dispatch`): it pulls spec `main`, regenerates the stubs, `bumpversion patch` (`0.1.41`->`0.1.42`),
   publishes `ingestion-contract-server` to Maven Central, and commits "Update submodule branch ref and bump
   package version". **Not a PR** — the workflow is self-contained; the bot lacks `actions:write` + Sonatype/signing
   secrets. **BLOCKED 2026-06-18 by the OSSRH sunset:** the workflow's `s01.oss.sonatype.org` publish returns HTTP
   402 (Sonatype OSSRH EOL'd 2025-06-30). Fixed by **opendatadiscovery-specification-contracts PR #7** (repoint to
   the Central Portal OSSRH Staging API, `ossrh-staging-api.central.sonatype.com`). Account-side (maintainer):
   generate a Central Portal user token, "Migrate Namespace" for `org.opendatadiscovery`, set the `SONATYPE_*`
   secrets to the token — then re-dispatch. (odd-models publishes to PyPI via `PYPI_*` creds, NOT Sonatype/OSSRH —
   unaffected by the sunset; dispatch it as-is.)
3. **odd-models-package** — the MAINTAINER dispatches `Build and publish PyPI artifact` (same shape: pulls spec
   `main`, the Dockerfile regenerates the Pydantic `models.py` via `datamodel-codegen`, `poetry version patch`,
   publishes to PyPI, commits). **Not a PR.**
4. **odd-platform** — once `0.1.42` is on Maven, the BOT bumps `gradle/libs.versions.toml`
   `ingestion-contract-server` (`0.1.40`->`0.1.42`) + verifies the regenerated ingestion-contract enum carries
   `ML_MODEL_ARTIFACT`/`_INSTANCE` (the `ff8f4bab`/#1631 shape), folded into PR #1790. Then the #1725 reporter
   sends `ML_MODEL_ARTIFACT` (mapped 1:1).

This is the **primary** spec-side fix for the reporter's consumer-model, paired with the ML-entity-taxonomy
decision (`adrs/drafts/ml-entity-taxonomy.md`, CTRIB-021, opendatadiscovery/odd-platform#1725). The platform fix
(PR #1790) adds `ML_MODEL` as a model-identity group and maps the contract type **1:1** (no payload-shape
inference — the spec is the contract); it fixes the `ML_MODEL` 500 platform-side, but a *consumer*-model can only
be sent once the contract exposes `ML_MODEL_ARTIFACT` (this item). The ingestion **specification** is the
collector-author's first contact with the vocabulary and is currently under-specified:

1. **No descriptions on the `DataEntityType` enum** (verified verbatim from `entities.yaml`, 2026-06-18) — a
   collector author cannot tell `ML_MODEL` from `ML_MODEL_TRAINING`. Add a `description:` to each ML value
   stating its meaning + the platform class, mirroring the taxonomy:
   - `ML_MODEL` — the model identity/family (a group). MLflow Registered Model / SageMaker Model Package Group / DataHub mlModelGroup.
   - `ML_MODEL_TRAINING` — a training job (transformer).
   - `ML_MODEL_ARTIFACT` — a trained model version/artifact (consumer).
   - `ML_MODEL_INSTANCE` — a deployed serving instance (transformer).
   - `ML_EXPERIMENT` — a group of training runs.
2. **Asymmetry to reconcile:** the ingestion spec has `ML_MODEL` + `ML_MODEL_TRAINING` but NOT
   `ML_MODEL_INSTANCE` / `ML_MODEL_ARTIFACT`, while the platform models all of them. Add `ML_MODEL_ARTIFACT`
   and `ML_MODEL_INSTANCE` to `entities.yaml`'s `DataEntityType` so collectors can emit the full lifecycle the
   platform understands (today they are platform-internal-only). This must stay backward compatible (additive).
3. **README** — add an "ML entities" section with the analogy table (the same content as the platform docs page
   DOC-468), so the spec README and the published manual agree.

The cross-platform grounding (10 MLOps platforms / catalogs, cited) is in
`adrs/drafts/research/ml-entity-taxonomy/` + `lineage/odd-platform/sme-consultations/2026-06-18-ml-model-type-taxonomy.md`.
