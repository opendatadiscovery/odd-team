## What

The owner-association request feature exposes three endpoints under `/api/owner_association_request`. Two of them - the pending-request list (`GET /api/owner_association_request`) and the approve/decline action (`PUT /api/owner_association_request/{id}`) - are guarded by the `OWNER_ASSOCIATION_MANAGE` permission. The third, the **activity (forensic history) log** `GET /api/owner_association_request/activity`, has **no `SecurityRule`** at all. It therefore falls through to the default catch-all rule, which only requires the caller to be authenticated - not to hold `OWNER_ASSOCIATION_MANAGE`. The result is a privilege mismatch: the *less* sensitive pending-list view is permission-gated, but the *more* sensitive endpoint - the full audit trail of who requested, approved, manually approved, declined, or manually declined every owner association (including approver usernames and timestamps) - is readable by any logged-in user. Under `auth.type=DISABLED` it is reachable with no credential at all.

## Where

The rule table guards the list and the update, but never the `/activity` path:

`auth/util/SecurityConstants.java:148-154`
```java
new SecurityRule(
    NO_CONTEXT, new PathPatternParserServerWebExchangeMatcher("/api/owner_association_request", GET),
    OWNER_ASSOCIATION_MANAGE),
new SecurityRule(
    NO_CONTEXT, new PathPatternParserServerWebExchangeMatcher(
    "/api/owner_association_request/{owner_association_request_id}", PUT),
    OWNER_ASSOCIATION_MANAGE),
// (no rule for "/api/owner_association_request/activity")
```

Because no rule matches `/activity`, it is caught by the default tail rule, which requires authentication only:

`auth/authorization/AuthorizationCustomizer.java:29-30`
```java
spec.pathMatchers("/**")
    .authenticated();
```

And the path is not whitelisted either, so it is not anonymous under enabled auth - it is authenticated-but-unprivileged:

`auth/util/SecurityConstants.java` (WHITELIST_PATHS)
```java
public static final String[] WHITELIST_PATHS =
    {"/actuator/**", "/favicon.ico", "/ingestion/**", "/img/**", "/api/slack/events"};
```

The endpoint that ships under this gap:

`controller/OwnerAssociationRequestController.java:47-53`
```java
@Override
public Mono<ResponseEntity<OwnerAssociationRequestActivityList>> getOwnerAssociationRequestActivityList(
    final Integer page, final Integer size, final OwnerAssociationRequestStatusParam status, final String query,
    final ServerWebExchange exchange) {
    return activityService.getOwnerAssociationRequestList(page, size, query, status)
        .map(ResponseEntity::ok);
}
```

The OpenAPI contract declares the path at `openapi.yaml` `/api/owner_association_request/activity` (line ~3392), alongside the gated list at `/api/owner_association_request` (line ~3349).

## Why it matters

This is a **silent** access-control gap - no error, no log; the endpoint simply returns data it should not. The activity log is administrative forensic content (approver identities, decision types, timestamps for every association request). An operator reasonably assumes that if the pending-request *list* requires `OWNER_ASSOCIATION_MANAGE`, the full *history* of those requests does too. Any authenticated user without the manage permission can page through the entire approval audit trail; under `auth.type=DISABLED` the data is fully public. Severity is medium rather than high because the leaked data is metadata (not credentials or entity payloads) and write paths remain correctly gated, but it is a genuine confidentiality regression versus the stated permission model and an inconsistency a security reviewer will flag.

## Suggested fix

Add a `SecurityRule` for the activity path mirroring its siblings, before the catch-all:

```java
new SecurityRule(
    NO_CONTEXT, new PathPatternParserServerWebExchangeMatcher("/api/owner_association_request/activity", GET),
    OWNER_ASSOCIATION_MANAGE),
```

Note the matcher ordering: `/api/owner_association_request/activity` must be registered with the same specificity as the existing `/{owner_association_request_id}` PUT rule so it is not shadowed. Open to alternatives if a distinct read-only permission for audit history is preferred - but the minimum correct behaviour is that the history endpoint is no less restricted than the list endpoint it mirrors. If a contract test enforces one GET rule per resource, update it to expect this new rule.

**How to verify:** a user without `OWNER_ASSOCIATION_MANAGE` receives 403 on `GET /api/owner_association_request/activity`; a user with the permission still receives 200.

## How discovered

Surfaced during a review of the owner-association approval flow and its audit surfaces; reading `SecurityConstants.java` confirmed the `/activity` path has no rule while its two siblings (the list GET and the approve/decline PUT) are gated by `OWNER_ASSOCIATION_MANAGE`. The fix is the single missing rule in `SecurityConstants.java`.
