- **REFACTOR-401** (NEW 2026-05-19O): Cognito empty `logout-uri` produces silent NO-OP — the user clicks logout, the request returns 200 with no body, NO redirect, and the local Spring WebFlux session is NOT invalidated. The user remains logged in. The defense-in-depth half (WebSession::invalidate) is gated on the first half (logoutUri presence) by Mono.empty() early-return; missing logoutUri DISABLES the local session clear
  - **Category**: buggy-default
  - **Surfaced by**:
    - `CognitoLogoutSuccessHandler.md:bugs_limitations_corner_cases.[0]` (HIGH)
    - `CognitoLogoutSuccessHandler.md:security.known_security_gaps.[1]` (HIGH)
  - **Statement**: `CognitoLogoutSuccessHandler.java:33-35` reads: `if (StringUtils.isEmpty(provider.getLogoutUri())) return Mono.empty();` — this returns BEFORE the redirect-header set AND BEFORE the WebSession::invalidate call at line 49. The user clicks logout, the request returns 200 with no body, no redirect, and the local session is NOT invalidated. The user remains logged in. There is no log message, no error, no operator-visible signal that logout is misconfigured. The only way an operator discovers this is by clicking logout and observing the user stays logged in. The defense-in-depth half — local session invalidation — is gated by the first half — logoutUri presence — by the same Mono.empty() short-circuit. This is the LSN-001-pattern miss applied to logout: defaulting to a permissive behaviour that hides operator misconfiguration AND defeats defense-in-depth.
  - **Evidence**: `CognitoLogoutSuccessHandler.java:33-35` (early Mono.empty() return) + line 49 (WebSession::invalidate that NEVER runs when logoutUri is empty) + the asymmetric absence of this guard in sibling Azure/Google/GitHub/ODDIAM handlers
  - **Existing-ADR-or-implied-prescription**: The Cognito handler's `isEmpty` guard appears to be an attempt at graceful-degradation, but the gating of WebSession::invalidate on logoutUri's presence DEFEATS the defense-in-depth that all other sibling handlers preserve (Azure NPE on null logoutUri vs. Cognito silent no-op — both are wrong but Cognito's is worse because it hides AND defeats the security boundary). The Cognito handler's intent is ambiguous: the maintainer wrote a guard but placed it BEFORE the WebSession::invalidate call. A reviewer cannot tell if this was deliberate (graceful-degradation) or unintentional (defense-in-depth defeat).
  - **Proposed remedy**: Re-order the handler: ALWAYS invalidate WebSession first (defense-in-depth invariant — local cleanup is non-conditional); THEN optionally short-circuit the redirect construction if logoutUri is empty. Better: validate logoutUri at boot (similar to REFACTOR-155 Azure pattern) — boot-time fail-fast prevents the silent-runtime no-op AND surfaces the misconfiguration as a clear deployment error. The choice between (a) per-handler boot-time validation OR (b) re-order-then-validate-logoutUri-at-runtime should reflect ADR-CANDIDATE-048's narrow-validator-scope; the maintainer should pick.
  - **Severity rationale**: HIGH — silent failure-mode of an operator-misconfigured default. The user clicks logout and stays logged in; the operator sees no error. Defense-in-depth defeat — the local session invalidation is gated by the redirect construction, which is wrong (the two should be independent).
  - **Suggested backlog grouping**: `OAuth2 hardening sprint` (paired with REFACTOR-155 Azure NPE on null logoutUri — the Azure/Cognito asymmetry is the same root cause: per-provider required-field validation deferred from boot to runtime, with inconsistent fallback shape)
