## Description

`authorization/owners.md` is 9 lines after batch-12 (DOC-207..224) shipped a 118-line `user-owner-association.md`. The owners page reads:

> ODD Platform allows to create platform-managed users — owners. Owners are Data Owners — people who manage and maintain a particular data entity or term.
>
> You can manage owners in the [Management → Owners](../../../management.md) tab.
>
> ...
>
> Every ODD Platform user should associate themselves with one of the existing owners. This process is described in the [User-owner association](user-owner-association.md) section.

This is structurally inconsistent with what the platform actually does and what the batch-12-expanded user-owner-association.md now describes:

1. **"Platform-managed users" is misleading.** Owners are NOT users — they are catalog identities that users bind to. A user has an OIDC/LDAP/S2S auth identity; an Owner is a separate, catalog-side row with its own name, roles, and lifecycle. The 1-to-1 binding between user and Owner is the bridge. The "platform-managed users" framing makes operators assume Owners are an auth-side construct.

2. **The Owner directory is freeSolo accreted, not curated.** The new user-owner-association.md describes the freeSolo Owner-name input (`OwnerAssociationForm.tsx:167-172`) + the `OwnerServiceImpl.getOrCreate` side-door (`OwnerServiceImpl.java:38-42`): typing a brand-new owner name on the home-page form mints a new Owner row. With `DIRECT_OWNER_SYNC` on the same caller, the new Owner is created AND bound in one POST. Owners.md is silent on this accretion model and on the cleanup recommendation.

3. **Owners.md doesn't enumerate the three write-paths to a binding.** The new user-owner-association.md describes self-request + DIRECT_OWNER_SYNC auto-approve + admin direct-bind as the three paths. Owners.md mentions only the self-request path implicitly via "every user should associate themselves".

4. **Owner roles are not mentioned.** Roles.md describes Owner roles as the bound user's effective role (superseding user roles), but Owners.md doesn't mention that an Owner CAN carry roles, or how to attach them.

5. **Permission gates on the Owner CRUD surface** (`OWNER_CREATE`, `OWNER_UPDATE`, `OWNER_DELETE`) are not named on owners.md. They are on permissions.md but a reader of owners.md has no hint they exist.
