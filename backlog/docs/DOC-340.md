## Description

`active-platform-features/alerting.md` line 17 states:

> The platform uses PostgreSQL logical replication to deliver alerts even when the alerting pipeline is briefly partitioned from the primary database — see the [PostgreSQL Configuration] operator guide for the database-side prerequisites.

Both halves of this sentence are wrong, and they mislead an operator on exactly the dimension they care about — durability under network failure:

1. **Alert *creation* has nothing to do with replication.** An alert is written by a plain `INSERT INTO alert` on the platform's own ingestion / evaluation path (`ReactiveAlertRepositoryImpl.createAlerts`). No WAL, no replication slot, no publication is involved in raising or storing an alert. Logical replication is a prerequisite for **Notifications** (the Slack / email / webhook *delivery* subsystem that tails the `alert` table via the Postgres WAL), and Notifications is **default-off** (`@ConditionalOnNotifications`). The page conflates "alerting" (always-on, INSERT-based) with "alert notifications" (opt-in, WAL-based).

2. **The replication subscriber READS FROM the primary** — so a partition from the primary *stops* it, it does not make it resilient. `NotificationSubscriber.run()` acquires a leader-election connection against the primary and opens a logical replication stream (`pgReplicationConnection.getReplicationAPI().replicationStream()...start()` → `stream.readPending()`) on that same connection. If the subscriber is partitioned from the primary, the stream cannot advance and notification delivery halts. The claim "delivers alerts even when ... partitioned from the primary" is the exact inverse of the behaviour: the WAL subscriber is wholly dependent on a live connection to the primary.

An operator reading line 17 would (a) believe alerting survives a primary partition when it does not, and (b) believe replication is an alerting-resilience feature rather than a Notifications-delivery prerequisite. The page already states the correct framing elsewhere — line 212 lists "the PostgreSQL replication prerequisite" under **Enable Alert Notifications** — so line 17 also contradicts the page's own later text.

## Context

**Source:** 2026-06-08 contradiction-harvest. The claim is internally self-contradicting (line 17 vs line 212) and contradicts the platform's actual alert-creation and WAL-subscriber code.

**Canonical code truth (verified 2026-06-08):**

- Alert creation is a plain INSERT, no replication — `ReactiveAlertRepositoryImpl.createAlerts` builds `DSL.insertInto(ALERT)...returning(...)` and runs it via jOOQ (`ReactiveAlertRepositoryImpl.java:324-342`).
- The WAL subscriber is Notifications-only and default-off — `NotificationSubscriberStarter` is annotated `@ConditionalOnNotifications` (`NotificationSubscriberStarter.java:17`).
- The subscriber reads FROM the primary — `NotificationSubscriber` extends `Thread` (`NotificationSubscriber.java:29`); `run()` acquires a connection via `leaderElectionManager.acquire(...)` (`NotificationSubscriber.java:47`), opens a logical replication stream on it (`NotificationSubscriber.java:53-60`), and pulls changes with `stream.readPending()` (`NotificationSubscriber.java:68`). A partition from the primary stalls `readPending()` and halts delivery.

**Cross-links:** `notifications.md` is the canonical home for the replication/WAL prerequisite; `configuration-and-deployment/odd-platform.md#enable-alert-notifications` is where the operator guide lives. No related backlog items.
