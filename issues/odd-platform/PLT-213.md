## What

The toolbar language switcher has a search box for filtering the list of available UI languages, but the filter matches only the **English friendly-name** of each language. A user whose only language is, say, Spanish or Ukrainian, who opens the switcher and types their language's native self-name - "Español", "Українська" - gets an **empty list**, because the filter compares their query against the strings `"Spanish"` and `"Ukrainian"`. The single control whose entire purpose is to let a non-English speaker escape the English UI is itself navigable only if the user already knows the English word for their own language.

## Where

`odd-platform-ui/src/components/shared/elements/AppToolbar/SelectLanguage/SelectLanguage.tsx:48-50`

```tsx
{i18n.languages
  .filter(lang =>
    LANGUAGES_MAP[lang as Lang].toLowerCase().includes(query.toLowerCase())
  )
```

`LANGUAGES_MAP` (in `odd-platform-ui/src/lib/constants.ts:158-165`) holds English friendly-names only:

```ts
export const LANGUAGES_MAP = {
  en: 'English',
  es: 'Spanish',
  ch: 'Chinese',
  fr: 'French',
  ua: 'Ukrainian',
  hy: 'Armenian',
} as const;
```

So the `.includes(query)` filter can never match a native-name query such as `español`, `українська`, `中文`, `français`, or `հայերեն`.

## Why it matters

Silent and self-defeating, affecting exactly the users the feature exists for: non-English speakers. The supported locales are es / ch / fr / ua / hy in addition to en, and a speaker of any of those who reaches for the search box by typing their language's own name finds nothing and may conclude their language is unavailable. Severity is low - the unfiltered list still shows every language with its flag, so a user who does not type (or who clears the box) can still pick visually - but the search affordance actively misleads precisely the audience it is meant to serve, which is a small but real UX defect in the internationalisation story.

## Suggested fix

Extend the filter to also match each language's native self-name. Add a native-name map alongside `LANGUAGES_MAP` (e.g. `{ en: 'English', es: 'Español', ch: '中文', fr: 'Français', ua: 'Українська', hy: 'Հայերեն' }`) and have the filter match if the query is a substring of either the English friendly-name **or** the native name:

```tsx
.filter(lang => {
  const q = query.toLowerCase();
  return (
    LANGUAGES_MAP[lang as Lang].toLowerCase().includes(q) ||
    LANGUAGES_NATIVE_MAP[lang as Lang].toLowerCase().includes(q)
  );
})
```

Rendering the native name next to (or instead of) the English label in the list would further help, but matching it in the filter is the minimal fix. Open to alternatives on presentation.

**How to verify:** typing a language's native name (e.g. "Español" or "Українська") matches and shows that language's row - a render test of `SelectLanguage` asserting a native-name query is non-empty.

## How discovered

Surfaced during a product-owner review of the language switcher (the one control meant to serve non-English speakers); confirmed by reading `SelectLanguage.tsx` and `LANGUAGES_MAP` in `constants.ts` - the filter compares only against the English friendly-name.
