## What

Four operator-visible defects on the Lookup Tables (Reference Data Management) feature. All four contradict the operator-facing promise of *"SQL-joinable schema-direct-access reference tables"* - the feature is documented as a stable, governable, multi-tenant-safe surface, but the implementation has caveats in all four dimensions.

**Defect 1 - `LOOKUP_TABLE_*` permissions are GLOBAL (NO_CONTEXT resolver), not per-table.** All 9 `LOOKUP_TABLE_*` SecurityRule entries (re-verified 2026-06-10: `SecurityConstants.java:114` LOOKUP_TABLE_CREATE + `:325-355` the other 8) wrap their matcher in the `NO_CONTEXT` resolver, NOT a table-id-aware scope extractor. Contrast in the same file: TERM rules use the `TERM` resolver (`:174-193`) and data-entity rules use the `DATA_ENTITY` resolver (`:195-242`), both of which thread the resource id into the permission check. **A Policy granting `LOOKUP_TABLE_UPDATE` therefore permits modifying ANY lookup table** - there is no per-table scoping concept for lookup tables at all, unlike terms and data entities.

**Defect 2 - Cascade orphan when parent DataEntity is deleted (citation corrected 2026-06-10; outcome static-plausible, not driven).** The `lookup_tables.data_entity_id` FK has NO `ON DELETE CASCADE` (`V0_0_86__create_schema_and_tables_for_custom_tables.sql:11-12` declares a plain `FOREIGN KEY ... REFERENCES data_entity (id)`), and there is no inverse cleanup hook: `LookupDataServiceImpl.deleteLookupTable` (`:112-118`) cleans up only when the delete is initiated FROM the lookup-table side (it deletes the search entrypoint, definitions, the `lookup_tables` row, then the data entity). The original citation pointed at this forward-direction method as if it were the gap - it is the opposite direction. The genuine concern is whether deleting/soft-deleting the parent data entity (e.g. ingestion TTL purge) leaves the `lookup_tables` row + the physical `lookup_tables_schema.n_*` table behind; that path was not traced end-to-end here, so the orphan outcome is structurally plausible (no cascade, no reverse hook) but NOT verified - it needs the data-entity-deletion path driven.

**Defect 3 - Rename ALTER TABLE silently breaks downstream BI/ETL pipelines.** The rename rebuilds the physical table name (`ReferenceDataServiceImpl.buildTableName` = `"n_" + namespaceId + "__" + name.toLowerCase().replace(" ", "_")`, `:191-194`) and, when it changes, `ReferenceDataRepositoryImpl.updateLookupTable` (`:180-202`) issues `ALTER TABLE ... RENAME TO` plus matching sequence/constraint renames (`:191-200`). Downstream pipelines that hardcoded the old table name (the SQL-joinable schema-direct-access contract the page promises) break silently on rename - no Postgres VIEW alias at the old name, no rename-blocker, no warning at the rename UI.

**Defect 4 - FALSIFIED 2026-06-10: lookup table values/column-names/table-name render React-escaped, NOT as HTML; there is no stored-XSS surface here.** `LookupCharValidator.getValue` does return the input verbatim (`:14-17`) - the BE stores values unsanitized - but the claim that this becomes stored XSS collapses at the render boundary: every lookup-table render site is plain React text interpolation, which auto-escapes. Row values: `<Typography variant='body1'>{initialValue}</Typography>` (`DatasetDataTableRowCellString.tsx:36-39`). Column headers: `<Typography variant='caption'>{name}</Typography>` (`DatasetData/.../hooks.tsx:75, 80`). Table name: `{item.name}` in the list (`LookupTablesList/LookupTablesListItem.tsx:31-32`). There is NO `dangerouslySetInnerHTML` anywhere in `odd-platform-ui/src` (grep, 0 matches) and NO Markdown/raw-HTML renderer on this surface (unlike Query Examples / PLT-018, which DO route through `rehype-raw`). A pasted `<script>` or `<img onerror=...>` displays as literal inert text. This facet is NOT part of the F-004 stored-XSS family.

## User-facing impact

- **Defect 1 (verified by BE trace 2026-06-10; static-settled):** an operator who grants `LOOKUP_TABLE_UPDATE` (or any `LOOKUP_TABLE_*`) to a role grants it across EVERY lookup table - there is no per-table scoping for lookup tables, where terms and data entities have it. A multi-team deployment cannot restrict a team to its own tables. The exploit (user with the grant editing another team's table) is observable only under a policy-configured non-DISABLED auth mode - not driven here.
- **Defect 2 (static-plausible; NOT driven):** consumer-visible effect WOULD be catalog/DB drift (a lookup table the catalog reports deleted whose physical `n_*` table BI keeps querying, or vice versa), but the parent-data-entity-deletion path was not traced end-to-end - keep `user_facing_verified: false`. Remaining check: delete/TTL-purge the parent data entity and inspect `lookup_tables` + `lookup_tables_schema`.
- **Defect 3 (verified by BE trace 2026-06-10; downstream break is runtime):** renaming a lookup table in the UI issues a physical `ALTER TABLE ... RENAME TO` with no compatibility alias - any external SQL/BI/dbt consumer pinned to the old name breaks at next run with no in-product warning. The break itself is on the external consumer (needs a real downstream to observe); the rename-without-alias is code-settled.
- **Defect 4 (FALSIFIED by FE trace 2026-06-10):** no user-facing XSS. A user pasting `<script>`/`<img onerror=...>`/an apostrophe into a row value, column name, or table name sees it rendered as literal escaped text; there is no script execution and no broken markup, because every render site is React text interpolation and nothing on this surface uses raw-HTML Markdown or `dangerouslySetInnerHTML`.

## Why it matters

The Lookup Tables feature is marketed (on the live doc page) as *"create a reference table that's SQL-joinable from downstream pipelines and governable from the ODD UI."* Operators adopting it for multi-team master-data scenarios hit all four defects in sequence:

1. They configure `LOOKUP_TABLE_UPDATE` for their team's tables (or so they think) - Defect 1 means they granted global table access
2. They delete a parent DataEntity to clean up - Defect 2 may leave orphan PostgreSQL tables that BI pipelines continue to query (catalog/DB drift; outcome plausible, not yet driven)
3. They rename a table from "Customer" to "CustomerV2" in the UI - Defect 3 silently breaks every BI dashboard, ETL job, and dbt model referencing the old name

Severity stays HIGH on Defects 1 + 3 alone: a global-RBAC surprise on a multi-tenant master-data feature, plus a UI action that silently breaks the feature's headline SQL-joinable contract. Defect 2 is an unverified data-integrity concern; Defect 4 (XSS) was FALSIFIED on verification (FE escapes on render) and no longer contributes to severity.

## Suggested fix

Four distinct fixes; recommend grouping into 2 PRs:

### PR-1 - RBAC + integrity (Defects 1 + 2)

**Defect 1 - introduce a `LookupTableResolver`** mirroring the TERM / DATA_ENTITY pattern:

```java
// new file: LookupTableResolver.java - extracts table-id from request path
public class LookupTableResolver implements PermissionResolver {
    public Mono<PermissionScope> resolve(ServerWebExchange exchange) {
        Long tableId = extractTableIdFromPath(exchange);
        return policyRepository.getEffectivePermissions(currentUser, LOOKUP_TABLE, tableId)
            .map(perms -> new PermissionScope(LOOKUP_TABLE, tableId, perms));
    }
}

// SecurityConstants.java:114, 326-354 - rewire LOOKUP_TABLE_* rules to use LookupTableResolver
- .resolver(NO_CONTEXT)
+ .resolver(LOOKUP_TABLE_RESOLVER)
```

Coordinate with the Policy editor UI to support per-table scope selection (mirror the per-entity flow).

**Defect 2 - enforce cascade-on-delete:**

```sql
-- migration to add FK with ON DELETE CASCADE on the lookup_tables -> data_entity inverse direction
ALTER TABLE lookup_tables
  ADD CONSTRAINT fk_lookup_tables_data_entity_cascade
  FOREIGN KEY (data_entity_id) REFERENCES data_entity(id)
  ON DELETE CASCADE;

-- AND a trigger to drop the lookup_tables_schema.n_* PostgreSQL table on lookup_tables row delete
CREATE FUNCTION drop_lookup_table_on_delete() RETURNS TRIGGER ...
```

Plus a `LookupDataServiceImpl.deleteByParentDataEntityId(...)` Java-side cleanup hook for cases where the FK CASCADE isn't sufficient (e.g., soft-delete TTL paths that don't trigger the FK).

### PR-2 - Naming stability (Defect 3; Defect 4 needs no code)

**Defect 3 - two options:**

- **Option A (recommended)** - block rename after external usage is detected. Add a `lookup_tables.first_external_use_at TIMESTAMP` column; populate it on first SQL access from outside the platform (requires query observability - see below). Block rename UI when first_external_use_at IS NOT NULL; surface a "this table has external consumers" warning.
- **Option B** - issue a Postgres VIEW with the old name pointing at the renamed table. Maintains backwards compatibility for old consumers; rename history grows linearly with rename count. Operationally simpler but accumulates VIEW debt.
- **Option C** - document the rename hazard verbatim and accept the silent-breakage. The default doc-only fix is **DOC-182 Caveat 3**; this option pushes the entire fix to the doc side.

Recommend Option A - operator-visible warning, no data-loss path.

**Defect 4 - no fix required (FALSIFIED).** The render boundary already escapes (React text interpolation at every lookup-table render site; no raw-HTML path). Do NOT add DOMPurify here - it would be dead defense against a non-existent surface, and the BE-verbatim storage is correct because the values are SQL data, not markup. If a future change introduces a Markdown/raw-HTML renderer for lookup values, re-open then. (The PLT-018 `rehype-sanitize` work is unrelated - that surface really does render raw HTML; this one does not.)
