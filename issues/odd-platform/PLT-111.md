## What

ODD identifies a GitHub-authenticated user by the GitHub `login` string (the default `user-name-attribute: login`), and uses the `(username, "github")` tuple as the compound key for `USER_OWNER_MAPPING`. GitHub `login` is **mutable** (users can rename freely; the old login is released after 90 days). After a rename, the user signs in as a new identity (`alice2, github`); the prior `(alice, github)` mapping row is orphaned. There is no `id`-based fallback and no migration tool, so the user's **My Objects** goes empty and their ownership is stranded under the old name — silently.

## Why it matters

A routine GitHub username change (rebrand, name change, handle cleanup) silently breaks a user's owner association — their personalised views empty out and their ownership records strand under a name they no longer use, with no error and no automatic re-link. Because the old login is later claimable by a third party, there is also a (lower-likelihood) identity-reassignment concern. The doc-side caveat (`backlog/docs/DOC-312.md`) warns operators, but the durable fix is a stable identity key.

## Suggested fix

- Key the identity / `USER_OWNER_MAPPING` on the **stable GitHub numeric `id`** (carry the `login` as a display attribute only), or
- Add an `id`-based fallback + a one-shot migration that re-links existing `(login, github)` rows to `id`, or
- At minimum, surface a maintenance action / documented `USER_OWNER_MAPPING` migration query for operators to run around a known rename (this is what DOC-312 will tell operators to do in the interim).
- The same mutable-key concern applies to other providers that default to a renameable principal — worth an audit across the `*UserHandler` family.
