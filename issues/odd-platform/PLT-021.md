## What

Two distinct defects on the DQ Test Run History endpoint surfaced by the same UI page (`/history` route - `TestRunsHistory.tsx`). The page is the operator's primary surface for diagnosing data-quality test outcomes; both defects degrade the surface exactly when operators need it most.

**Defect 1 - HTTP 500 during in-flight test runs (wire-vs-DB enum asymmetry).** The platform's DB-side test-run status enum (`IngestionTaskRun.java:28-36`) has **7 values** including `RUNNING`. The wire-side enum exposed via OpenAPI (`components.yaml:1407-1415`) has **6 values** with no `RUNNING`. The MapStruct mapper (`DataEntityRunMapper.java:13-14`) uses `Enum.valueOf` for String->enum mapping with no fallback. **Any result set containing a RUNNING row triggers `IllegalArgumentException` -> HTTP 500.** The page is UNAVAILABLE exactly when an operator most wants to see it (an in-flight test).

**Defect 2 - NULL end_time ordering puts RUNNING rows undated at top of list.** `ReactiveDataEntityTaskRunRepositoryImpl.java:178` issues `ORDER BY end_time DESC` with no `NULLS LAST`. Postgres default for `DESC` is `NULLS FIRST`. RUNNING rows (`end_time IS NULL`) appear at the TOP of the list. The UI labels each row by `startTime` with an empty Duration column when endTime is null - the operator sees an undated-looking row at the top with no signal it's in-flight.

(Defect 2 is bounded by Defect 1 today - when a RUNNING row enters the result set, the page 500s before rendering. But once Defect 1 is fixed, Defect 2 becomes operator-visible as a UX surprise.)

## Why it matters

The DQ Test Run History page is the operator's diagnostic surface for *"why did my DQ test fail / when did it last succeed / is it currently running."* The compound failure pattern:

- An operator sees a DQ alert; clicks through to the test's history page
- If the test is currently re-running (a common operator action - "retry the failed test"), the history page 500s
- Operator falls back to direct PostgreSQL query, breaking the abstraction the platform's UI is meant to provide

Severity is HIGH because:
- Defect 1 is a **complete page unavailability** during normal operational use
- The repair path is per-operator-manual-refresh-after-RUNNING-completes - not a graceful degradation
- Defect 2 (once Defect 1 is fixed) is operator-confusing in a way that erodes trust in the page

## Suggested fix

### Defect 1 - three options, all reasonable

**Option A (recommended) - add `RUNNING` to the wire enum:**

```yaml
# components.yaml:1407-1415
DataEntityRunStatus:
  type: string
  enum:
    - SCHEDULED
    - RUNNING       # <-- add
    - BROKEN
    - ABORTED
    - SUCCESS
    - FAILED
    - SKIPPED
```

Wire-side now matches DB-side; mapper succeeds; UI receives `RUNNING` and renders it appropriately (the UI already labels in-flight runs in the per-test report view, so the rendering pattern exists). Recommend this - surfaces the operator-visible reality.

**Option B - MapStruct `@ValueMapping` fallback:**

```java
@ValueMapping(source = "RUNNING", target = "BROKEN")
// or:
@ValueMapping(source = MappingConstants.ANY_UNMAPPED, target = "BROKEN")
```

Hides the in-flight reality from the wire / UI. Lossy. Not recommended.

**Option C - service-side filter excluding RUNNING:**

```java
// in DataEntityRunService
return repository.findByDataEntityId(id)
    .filter(run -> run.getStatus() != RUNNING)
    .collectList();
```

Also lossy; operator can't see in-flight runs at all. Not recommended.

### Defect 2 - one option:

```java
// ReactiveDataEntityTaskRunRepositoryImpl.java:178
- .orderBy(DATA_ENTITY_TASK_RUN.END_TIME.desc())
+ .orderBy(DATA_ENTITY_TASK_RUN.END_TIME.desc().nullsLast(),
+          DATA_ENTITY_TASK_RUN.START_TIME.desc())   // tiebreak with start_time for RUNNING rows
```

RUNNING rows now sort by start_time among themselves (newest in-flight first) and follow the completed rows. Operator-visible: in-flight rows are clearly grouped at the END of the list (or as a distinct visual section if the UI is updated).

Better UX (separate PR if desired): UI surface an in-flight section above the completed list.
