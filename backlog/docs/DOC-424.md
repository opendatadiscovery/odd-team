## Description

The LDAP config key `auth.ldap.base` is bound and consumed by the platform but is documented nowhere on `ldap.md`. The page lists `url` / `username` / `password` / `dn-pattern` / `user-filter` / `groups.*` / `active-directory.*`, and the **Final configuration example** (lines 187–214) enumerates every key an operator is expected to set — but `base` is absent from both the prose and the example. An operator configuring LDAP against a directory that requires a context base DN has no documented way to discover this knob; they would have to read the platform source to find it.

**Correction to the harvest line.** The harvest report stated this key "is shipped in the `application.yml` LDAP template (lines 50–65)" of `ldap.md`. That premise is inaccurate: `auth.ldap.base` appears **nowhere** in `ldap.md` (grep returns zero hits), and lines 50–65 are the env-var tab for the connect-to-server block plus the cleartext-transport warning hint — they contain no `base` key. The real finding is the inverse: `auth.ldap.base` is a **consumed-but-undocumented** key, a missing-documentation gap, not a documented-but-vestigial one. This item supersedes the harvest framing.

**The key is NOT vestigial — it is live.** `ODDLDAPProperties.java:16` declares `private String base;` under `@ConfigurationProperties("auth.ldap")` (so the bound key is `auth.ldap.base`), and `LDAPSecurityConfiguration.java:122` consumes it: `ctx.setBase(properties.getBase())` sets the base DN on the `LdapContextSource` bean. Spring LDAP's `LdapContextSource.setBase(...)` prepends this DN to every operation, so all subsequent DN-pattern, user-filter, and group-search DNs are resolved **relative to** `base`. Leaving it unset (the default) makes them resolve from the directory root — which is why the existing examples work without it — but a deployment that wants to scope all LDAP operations under a single base DN (e.g. `dc=mycompany,dc=com`) sets `auth.ldap.base` and then writes the rest of its DNs relatively. The fix is to **document** it, not remove it.

## Context

Source: 2026-06-08 contradiction-harvest, surfaced as a config-template-vs-doc gap on the LDAP authentication page.

Canonical code truth (read and confirmed 2026-06-08):
- `ODDLDAPProperties.java:9` — `@ConfigurationProperties("auth.ldap")`; line 16 — `private String base;` (Lombok `@Data` generates `getBase()`). This is the binding for `auth.ldap.base` / `AUTH_LDAP_BASE`.
- `LDAPSecurityConfiguration.java:117-124` — the `ldapContextSource()` bean: `ctx.setUrl(...)`, `ctx.setUserDn(...)`, `ctx.setPassword(...)`, and line 122 `ctx.setBase(properties.getBase())`. The context source is shared by the bind authenticator, the user search, and the authorities populator, so `base` scopes all three.
- `LDAPSecurityConfiguration.java:51` — the whole config is `@ConditionalOnProperty(value = "auth.type", havingValue = "LDAP")`, i.e. these keys apply only under `AUTH_TYPE=LDAP`.

Related (not duplicated here): the page already carries the `ldaps://` cleartext-transport warning (lines 58–60), the plaintext-password caveat (lines 62–64), and the AD `domain`-with-`enabled` caveat (lines 160–162); this item adds only the missing `base` key documentation and does not touch those.
