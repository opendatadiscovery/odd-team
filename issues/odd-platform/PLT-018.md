## What

Four operator-visible defects on the Query Examples feature surface. Listed in roughly decreasing security-criticality order:

**Defect 1 — Stored XSS via MDEditor.Markdown without rehype-sanitize.** Query Example `definition` and `query` fields are stored verbatim (`V0_0_84:5` declares `text NOT NULL`) and rendered through `@uiw/react-md-editor`'s `MDEditor.Markdown` component at two UI sites with no `rehype-sanitize` plugin configured. Operator-mutable text → unsanitized Markdown → stored XSS surface. **5th surface of the F-004 stored-XSS family.**

**Defect 2 — RBAC grid split across 3 controllers.** `SecurityConstants.java:112-113, 187-193, 312-317, 318-324` wires the 7 `QUERY_EXAMPLE_*` permissions across THREE controllers: `QueryExampleController` (CREATE/UPDATE/DELETE), `DataEntityController` (DATASET_CREATE/DELETE), `TermController` (TERM_CREATE/DELETE). Operators configuring permissions in one place miss four of seven gates.

**Defect 3 — 10 of 13 endpoints unscoped.** Only CREATE/UPDATE/DELETE are RBAC-gated. All reads + search-session endpoints (10 endpoints total) fall through to `.authenticated()`. Any authenticated user can read every Query Example in the platform regardless of Policy.

**Defect 4 — No `@ActivityLog` on any Query Example mutation.** Query Example create/update/delete/link operations are INVISIBLE on the global Activity Feed AND the per-entity Activity tab.

## Why it matters

**Defect 1 (XSS)** is the security-critical item — operators with `QUERY_EXAMPLE_CREATE` (a common grant for data analysts authoring usage examples) can plant stored XSS that fires on every viewer's session. Read access on the 10 unscoped endpoints means **every authenticated user is a viewer** — the XSS payload reaches the entire platform user base.

**Defect 2 + 3** (RBAC grid split + 10 unscoped) compound: even an operator carefully configuring Policies on QueryExampleController misses the dataset-link and term-link mutation gates AND has zero protection on reads. The Query Example surface is effectively platform-wide-readable + platform-wide-XSS-vulnerable.

**Defect 4 (audit silence)** has the same architectural root as F-021a (activity-feed schema-rooted constraint) — the `activity.data_entity_id NOT NULL FK` prevents non-data-entity-scoped events from emitting. Query Example mutations are conceptually associated with a Dataset or Term context; the audit-log integration requires either schema migration (to allow nullable `data_entity_id`) OR a per-context emit strategy (emit one activity row per linked entity).

Severity is HIGH because the compound (XSS + read-collaborative + audit silence) makes the feature unsafe for any deployment beyond a trusted-team-only scope.

## Suggested fix

Four distinct fixes; recommend grouping into 2 PRs:

### PR-1 — Security (Defects 1 + 3)

```typescript
// Markdown.tsx — add rehype-sanitize to the MDEditor.Markdown render
import rehypeSanitize from 'rehype-sanitize';

<MDEditor.Markdown
  source={text}
  rehypePlugins={[[rehypeSanitize]]}
/>
```

Validate the sanitizer schema covers Markdown's expected syntax (code blocks, inline code, links) while stripping `<script>`, `<iframe>`, event handlers, `javascript:` URLs.

```java
// Add @PreAuthorize / SecurityRule entries for the 10 unscoped endpoints.
// Default: require QUERY_EXAMPLE_READ for reads (new permission), QUERY_EXAMPLE_LIST for list/search.
// Alternative: keep reads permissionless but document the deliberate decision.

// SecurityConstants.java — new entries:
new PathPatternParserServerWebExchangeMatcher(
    "/api/queryexamples/**", GET)
    .requires(QUERY_EXAMPLE_READ),

new PathPatternParserServerWebExchangeMatcher(
    "/api/queryexamples/search/**", POST)
    .requires(QUERY_EXAMPLE_SEARCH),
```

### PR-2 — RBAC + audit consolidation (Defects 2 + 4)

**Defect 2 — consolidate the grid.** The split across three controllers reflects the underlying data model (a Query Example has links to Datasets and Terms; the link endpoints live on those controllers). Two options:

- **Option A** — keep the three controllers; add a single shared `QueryExampleResolver` that all three controllers reference for permission extraction. Document the 3-controller pattern explicitly in the resolver's Javadoc.
- **Option B** — introduce a unified `/api/queryexamples/{id}/datasets` and `/api/queryexamples/{id}/terms` endpoint family on QueryExampleController; deprecate the inverse-direction endpoints on DataEntityController and TermController. Backwards-compat break; coordinate with API consumers.

Recommend Option A — non-breaking, surfaces the pattern to operators auditing Policies.

**Defect 4 — add `@ActivityLog`** to the three mutation handlers. Acknowledge the activity-feed schema-rooted constraint per F-021a:

- For mutations tied to a single data entity context (dataset-link, term-link), emit one activity event per linked entity (uses the existing `data_entity_id FK`).
- For pure CRUD mutations (CREATE / UPDATE / DELETE without a context), the activity model cannot accept them today without a schema migration. Document this as a known limitation and coordinate with F-021a's broader schema-rooted constraint resolution.
