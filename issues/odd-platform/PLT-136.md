## What

**FALSIFIED on user-facing verification (2026-06-10) - REJECT-CANDIDATE.** The original claim was: `OwnerServiceImpl.delete` does not refresh the FTS search vectors (asymmetric with `update`, which calls `updateSearchVectors`), so after a delete the deleted owner's name keeps surfacing in catalog search. The code asymmetry is real, but it produces **no** user-facing bug, because the delete is **guarded** to only succeed when the owner has zero ownership relations - and the owner's FTS contribution is built **exclusively** from those relations. There is nothing stale left to refresh.

The proof is the delete guard combined with how the owner vector is constructed:

1. `OwnerServiceImpl.delete` (`OwnerServiceImpl.java:89-100`) refuses to delete unless **all three** of these are empty: `termOwnershipRepository.existsByOwner(id)`, `ownershipRepository.existsByOwner(id)`, `userOwnerMappingRepository.isOwnerAssociated(id)` (`:90-96`). If any resource is still attached, it errors with `CascadeDeleteException` ("Owner cannot be deleted: there are still resources attached"). So a delete that **succeeds** is, by construction, a delete of an owner with **zero** `OWNERSHIP` rows and **zero** `TERM_OWNERSHIP` rows.

2. The owner's contribution to the data-entity FTS index is built **only** through the `OWNERSHIP` join: `ReactiveSearchEntrypointRepositoryImpl.updateChangedOwnerVectors` (`:406-438`) selects `from(OWNER).join(OWNERSHIP).join(TITLE).join(DATA_ENTITY)` and upserts `SEARCH_ENTRYPOINT.OWNER_VECTOR` per data-entity that has an ownership row. The term-side mirror, `ReactiveTermSearchEntrypointRepositoryImpl.updateChangedOwnerVectors` (`:211-248`), is built **only** through the `TERM_OWNERSHIP` join.

Therefore an owner with zero ownership/term-ownership rows has **no** row anywhere in `search_entrypoint.owner_vector` (or `term_search_entrypoint.owner_vector`) carrying its name - there is nothing to leave stale. The `update` path calls `updateSearchVectors` (`OwnerServiceImpl.java:82`) because a **rename** must propagate to the entities the owner still owns; the `delete` path correctly omits it because a deletable owner owns nothing.

## Where

- `OwnerServiceImpl.java:89-100` - `delete`: the three-way `existsByOwner`/`isOwnerAssociated` guard at `:90-96` is the load-bearing fact the original issue missed.
- `OwnerServiceImpl.java:82` - `update` calls `updateSearchVectors`; `:109-114` is the helper (refreshes both `searchEntrypointRepository` and `termSearchEntrypointRepository` owner vectors).
- `ReactiveSearchEntrypointRepositoryImpl.java:406-438` - data-entity owner vector built only via `OWNER join OWNERSHIP`.
- `ReactiveTermSearchEntrypointRepositoryImpl.java:211-248` - term owner vector built only via `TERM_OWNERSHIP`.
- Guards: `ReactiveOwnershipRepositoryImpl.existsByOwner` (`:120-127`), `ReactiveTermOwnershipRepositoryImpl.existsByOwner` (`:74-80`), `ReactiveUserOwnerMappingRepositoryImpl.isOwnerAssociated` (`:88-96`).

(All line numbers verified against current HEAD `3049b9af`; the original `@ ede5d277` pin is stale but the code is unchanged.)

## User-facing impact

**None.** A deleted owner cannot appear in catalog search results, because an owner can only be deleted once it owns nothing, and an owner that owns nothing has no entry in any FTS owner-vector to begin with. The "ghost steward in search" scenario the original issue described is unreachable through the supported delete path. No data loss, no correctness gap, no freshness window.

The only residual is a defensible style note, not a defect: `delete` could call `updateSearchVectors` (or an explicit FTS-removal) anyway as belt-and-braces against a future code path that deletes an owner with relations still attached - but no such path exists today, and adding the call would be a no-op on every currently-reachable delete.

## How discovered

Surfaced by the Layer-4b feature-reflection over feature flow F-019 (Owner Lifecycle Management) on 2026-06-01 - hypothesis H-012 - as a claimed user-facing search-staleness bug. **Falsified 2026-06-10 during the user-facing verification sweep**: the reflection extrapolated a user bug from a backend `update`-vs-`delete` asymmetry without tracing the delete guard or how the owner vector is populated. Reading both falsifies the claim - the delete is gated on zero ownerships, and the owner vector exists only where ownerships exist, so a successful delete leaves nothing stale. Same corpus failure mode the PLT-167/PLT-176 lessons name: an asymmetry asserted as a user-facing defect from backend code alone.

This is now a REJECT-CANDIDATE (no user-facing defect). Kept on disk with the falsification recorded so the asymmetry is not re-reported by a future reflection pass.
