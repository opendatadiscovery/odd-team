## Description

The i18n configuration has no detection for missing or drifted keys, so localisation bugs ship silently. `i18n.ts:27-31`:

```
i18n.use(initReactI18next).init({
  resources,
  lng: savedLanguage,
  fallbackLng: ['en', 'es', 'ch', 'fr', 'ua', 'hy'],
});
```

There is **no `missingKeyHandler`, no `saveMissing`, no `returnEmptyString`/`parseMissingKeyHandler`** — so a `t('Some.Key')` whose key is absent from a bundle just renders the raw key string (or falls back through the chain) with no error, no warning, and no CI signal. `resources` wires six locales (`en, es, ch, fr, ua, hy` — `i18n.ts:10-17`); nothing enforces that they carry the same key set, and nothing enforces that every key referenced in code exists in the canonical `en.json`.

This is the **systemic root** behind a string of one-off i18n fixes: PLT-011 and PLT-092 each correct a specific bundle-drift / missing-key instance, and DOC-304 fixes the es-only untranslated `'Estado'` (a Spanish-bundle value that was left as a status literal). All three patch one instance; none adds the parity gate that would have caught them — and would catch the next one — at build time. This is the highest-leverage i18n item: one CI test replaces an open-ended stream of per-string bug reports.

**Typed gate: validates-feature** — it asserts a standing invariant of the localisation feature (F-043): the translation bundles are mutually complete and every code key is resolvable. (It is not a known-bug pin; it should be GREEN once the currently-known drifts from PLT-011/092/DOC-304 are resolved, and it then guards against regressions — so author it to FAIL on today's known gaps and pair the green-up with those fixes, OR seed it with a documented allowlist of the currently-known gaps that shrinks to empty as PLT-011/092/DOC-304 land.)

## Acceptance Criteria
- [ ] A parity test (`i18nParity.test.ts`, run in the UI Jest suite) loads the six locale JSON bundles wired in `i18n.ts` and asserts **locale↔locale parity**: every key present in the canonical `en.json` exists in each of `es/ch/fr/ua/hy` (flattened/nested keys compared structurally), and no locale carries keys absent from `en.json`. Failures name the offending `locale:key`.
- [ ] The test asserts **code↔resource parity**: every literal `t('…')` / `i18n.t('…')` key referenced in `src/**` resolves to a key present in `en.json` (static scan of the source for `t('…')`/`t("…")` call sites; dynamic/interpolated keys that cannot be statically resolved are explicitly listed as exclusions in-test, not silently skipped).
- [ ] The test documents that the root cause is the absent `missingKeyHandler`/`saveMissing` in `i18n.ts:27-31`, references the instances it generalises (PLT-011, PLT-092, DOC-304), and that it is the parity gate none of those items added.
- [ ] The gate is wired into the UI CI lane so a future bundle edit that drops/desyncs a key fails the build. If today's known gaps (PLT-011/092/DOC-304) are not yet fixed, the test ships with a documented, shrinking allowlist (or is landed together with those fixes) — not `@skip`ped.

- Source feature: **F-043** (internationalisation / localisation).
- known_refs: **PLT-011**, **PLT-092**, **DOC-304** — each fixes one i18n instance; this item adds the systemic parity gate behind all three.

## Implementation Notes

Medium (the code-scan half is the work). Locale↔locale parity is a straightforward deep-key-set diff over the imported JSON (reuse the same `import en from './translations/en.json'` paths `i18n.ts` uses; flatten nested objects to dotted keys). For code↔resource, a regex/AST scan over `src/**/*.{ts,tsx}` for `t('…')`/`t("…")` (and the `useTranslation` `t` alias) collecting string-literal keys is sufficient — keep it conservative: template-literal / variable keys are unresolvable statically, so collect them into an explicit `KNOWN_DYNAMIC_KEYS` exclusion list asserted to be the only exclusions. Consider extracting the flatten + scan helpers so the assertion bodies stay readable. This is plain Jest (no RTL render needed). Pair landing it green with PLT-011/092/DOC-304, or carry a shrinking allowlist commented with each item id.
