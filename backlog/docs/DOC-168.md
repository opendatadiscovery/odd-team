## Description

DOC-004 (done 2026-04-24) established the foundational `auth.ingestion.filter.enabled` coverage — security risk, default `false`, two-filter shape (`IngestionDataSourceFilter` always-on / `IngestionDataEntitiesFilter` conditional), and a forward-pointer to PLT-003 for the broader filter-coverage gap. The Mode B scan surfaced two architectural extensions DOC-004 did not state explicitly enough for operators to act on safely:

**Extension 1 — `auth.ingestion.filter.enabled` name misleads (F-008a).** The property name reads as "lock down ingestion" but its `PathPatternParserServerWebExchangeMatcher` at `odd-platform-api/src/main/java/.../auth/filter/IngestionDataEntitiesFilter.java:28` protects ONLY `POST /ingestion/entities` (exact-literal path). The sibling AlertManager webhook at `POST /ingestion/alert/alertmanager` (`AlertManagerController.java:21`) has no `@PreAuthorize` and is not covered by ANY filter. Cross-mode divergence: under `auth.type=LOGIN_FORM` the AlertManager path falls through to session-gated (401 for unauthenticated callers); under `auth.type=OAUTH2/LDAP` the `SecurityConstants.WHITELIST_PATHS` carries `/ingestion/**` (wildcard) → AlertManager is permitted (200). DOC-004 already names the sibling-path gap in passing, but does not flag the cross-mode behavioural divergence under different `auth.type` values.

**Extension 2 — asymmetric default between the two filters (F-008b).** `IngestionDataSourceFilter` is **unconditional `@Component`** (always-on for `POST /ingestion/datasources`). `IngestionDataEntitiesFilter` is `@ConditionalOnProperty("auth.ingestion.filter.enabled" havingValue="true")` (operator opt-in for `POST /ingestion/entities`). So setting `auth.ingestion.filter.enabled=true` to "secure ingestion" gets the operator the same security posture on `/ingestion/datasources` as before (always-on) and only changes posture on `/ingestion/entities`. The operator-facing mental model "the flag protects ingestion" is wrong — the flag protects **one of two** ingestion endpoints.
