# IngestionService — semantic understanding

## understanding

`IngestionServiceImpl` is the canonical service-layer worker behind `POST /ingestion/entities`: the controller (`IngestionController.postDataEntityList`) hands it a deserialised `DataEntityList`, and the service resolves the target datasource by ODDRN, partitions inbound entities into new-vs-existing by ODDRN match, bulk-INSERTs the new ones and bulk-UPDATEs the existing ones inside a single `@ReactiveTransactional` boundary, then runs a TreeMap-ordered three-phase processor chain (`INITIAL → MAIN → FINALIZING`) of 14 distinct `IngestionRequestProcessor` implementations that materialise lineage, metadata, dataset structure, FTS vectors, alerts, activity log entries, etc. The whole pipeline including OTLP metric export completes BEFORE the controller's 200 OK fires — there is no async-accept / 202 mode. The companion `ingestStats` method is a thin delegate to `DatasetFieldService.updateStatistics(...)` and is invoked from `POST /ingestion/entities/datasets/stats`; it is NOT wrapped in `@ReactiveTransactional` at this layer.

## concepts

- entities: [`DataEntityList` (request payload — `data_source_oddrn` + `items: List<DataEntity>`), `DataSourceId` (resolved via `SELECT id FROM data_source WHERE oddrn = ? AND deleted_at IS NULL FOR UPDATE`), `DataEntityIngestionDto` (mapped from incoming `DataEntity` minus JOB_RUNs), `IngestionTaskRun` (mapped from incoming JOB_RUN-typed entities — kept SEPARATE from the entity flow), `EnrichedDataEntityIngestionDto` (carries the DB `id` + previous-version `DataEntityPojo` for change detection), `DataEntitySpecificAttributesDelta` (per-existing-entity old-vs-new JSON delta — feeds the schema-diff alert path), `DataEntityTotalDelta` (aggregated count delta per entity-class × type — feeds `data_entity_statistics`), `IngestionRequest` (the union object passed to every processor — `newEntities + existingEntities + taskRuns + lineageRelations + dataQARelations + groupEntityRelations + groupParentGroupRelations + specificAttributesDeltas + entityTotalDelta + datasetSchemaChanged flag`), `LineagePojo` (lineage edges extracted from `dataSet.parentDatasetOddrn`, `dataTransformer.sourceList/targetList`, `dataConsumer.inputList`), `DataQualityTestRelationsPojo`, `GroupEntityRelationsPojo`, `GroupParentGroupRelationsPojo`, `IngestionProcessorChain` (TreeMap by `IngestionProcessingPhase.order`), `IngestionProcessingPhase` (enum INITIAL=1, MAIN=2, FINALIZING=3), `OTLPMetricService` (terminal step — exports per-request metrics via OTLP gRPC, or NoOp impl)]
- operations: [resolve-datasource-by-payload-oddrn-FOR-UPDATE, partition-job-runs-from-entities, partition-existing-vs-new-by-oddrn, bulk-update-existing, restore-soft-deleted-entities, bulk-insert-new, calculate-total-delta, extract-lineage-relations, extract-dq-test-relations, extract-group-entity-relations, extract-group-parent-group-relations, build-ingestion-request, run-processor-chain-by-phase, export-otlp-metrics, return-Mono-Void]
- invariants:
  - "Single Postgres transaction wraps the ENTIRE ingest pipeline. `@ReactiveTransactional` is declared on `ingest()` at IngestionServiceImpl.java:66 (`@Transactional(\"reactiveTransactionManager\")` via the meta-annotation at ReactiveTransactional.java:11). The transaction holds for: datasource lookup + entity bulkUpdate + entity restore + entity bulkCreate + processor chain (all 14 processors across all 3 phases) + OTLP export. One failure anywhere rolls back EVERYTHING — there is no per-entity isolation."
  - "Datasource lookup uses `SELECT ... FOR UPDATE` on `data_source` (ReactiveDataSourceRepositoryImpl.java:94-101). This serialises concurrent ingestions targeting the SAME datasource on Postgres row lock — collector A and collector B ingesting into the same datasource will block each other for the full pipeline duration; ingestions into DIFFERENT datasources proceed in parallel."
  - "Datasource scoping is **payload-driven, NOT principal-driven**. `dataSourceRepository.getIdByOddrnForUpdate(dataEntityList.getDataSourceOddrn())` (IngestionServiceImpl.java:68) reads the ODDRN from the request body. The service does NOT consult any `SecurityContext` / `ServerWebExchange` / current-user / collector-id principal. The only upstream check that constrains payload-to-datasource binding is `IngestionDataEntitiesFilter` (default OFF — see `auth.ingestion.filter.enabled@L20` sibling sidecar)."
  - "JOB_RUN-typed entities are SEPARATED from the entity-upsert path at IngestionServiceImpl.java:84-91: items with `type == JOB_RUN` are routed to `mapTaskRun(...)` and become `IngestionTaskRun` records (handled later by `TaskRunIngestionRequestProcessor` MAIN-phase, which writes to `data_entity_task_run` + `last_runs` tables); all other types are mapped to `DataEntityIngestionDto`. A single payload mixing JOB_RUN and other types is supported."
  - "De-duplication by ODDRN is at the application layer, NOT at the DB schema layer. `dataEntityRepository.listByOddrns(...)` (IngestionServiceImpl.java:93) fetches existing rows; `Collectors.partitioningBy(d -> existingPojoDict.containsKey(d.getOddrn()))` (line 98) splits the inbound DTOs. `bulkCreate` is a plain INSERT (`ReactiveAbstractCRUDRepository.bulkCreate`, AbstractCRUDRepository.java:114-126 — calls `insertManyReturning(records)` — no `ON CONFLICT` clause). The dedup-by-ODDRN guarantee depends on the partitioning being CORRECT; a race window exists between `listByOddrns` (line 93) and `bulkCreate` (line 142) if two concurrent ingestions target the same ODDRN in the same datasource — BUT the `getIdByOddrnForUpdate` row lock on the parent datasource forces serialisation, so this race is theoretically impossible in practice."
  - "Soft-deleted entity restore: existing entities whose `previousVersionPojo.getStatus() == DataEntityStatusDto.DELETED.getId()` (IngestionServiceImpl.java:127-131) are routed through `dataEntityInternalStateService.restoreDeletedDataEntityRelations(...)` (line 135-136), which un-archives related rows in the same transaction. An entity that the platform had soft-deleted (via `excludeFromSearch` flag) is silently restored when re-ingested — no separate confirmation, no operator visibility into the restore decision."
  - "MICROSERVICE-typed existing entities are EXCLUDED from the `specificAttributesDeltas` list (IngestionServiceImpl.java:103: `filter(e -> DataEntityTypeDto.MICROSERVICE != e.getValue().getType())`). This means schema-diff alert candidates are never raised on microservice entities even when their specific-attributes JSON changes. The exclusion is undocumented and there is no comment defending it."
  - "Schema-diff detection: the `DatasetStructureIngestionRequestProcessor.extractVersionsToCreate(...)` (DatasetStructureIngestionRequestProcessor.java:132-165) sets `dto.setDatasetSchemaChanged(true)` when the stored `versionHash` differs from the new `structureHash`. This flag is then consumed by `IngestionRequest.getChangedDatasetOddrns()` / `getChangedDatasetIds()` (IngestionRequest.java:66-78) which feeds `AlertIngestionRequestProcessor` FINALIZING-phase to raise BACKWARDS_INCOMPATIBLE_SCHEMA alerts via `AlertLocator.getAlertBISCandidates(...)`."
- audiences: [odd-collector / odd-collector-sdk HTTP clients pushing data entities, odd-platform operators standing up an ingestion pipeline, security reviewers auditing the S2S surface, performance reviewers analysing ingestion throughput, contributors writing new `IngestionRequestProcessor` implementations]

## downstream_side_effects

The transactional pipeline writes to MANY tables and emits MANY events per ingest. Categorised by the processor that owns the write:

- **Direct (within `IngestionServiceImpl.ingest` itself, before any processor runs)**:
  - `data_source` row lock acquired via `SELECT ... FOR UPDATE` (IngestionServiceImpl.java:68 → ReactiveDataSourceRepositoryImpl.java:94-101). Held until transaction commits/rolls back.
  - `data_entity` bulkUpdate of existing-ODDRN entities (IngestionServiceImpl.java:134) — updates name, externalDescription, sourceCreatedAt/UpdatedAt, entityClasses, typeId, specificAttributes JSONB, hollow=false.
  - `data_entity` bulkCreate of new-ODDRN entities (IngestionServiceImpl.java:142) — plain INSERT, no UPSERT.
  - Side-effect via `DataEntityInternalStateService.restoreDeletedDataEntityRelations(...)` (IngestionServiceImpl.java:135-136): if any existing-ODDRN entity's previous status was DELETED, re-instate it; this in turn calls `dataEntityStatisticsService.updateStatistics(+restoredCount, ...)` (DataEntityInternalStateServiceImpl.java:143) to bump the total-entity counters.
- **INITIAL phase processors** (`IngestionProcessingPhase.order = 1`):
  - `HollowDataEntityIngestionRequestProcessor.process(...)` (HollowDataEntityIngestionRequestProcessor.java:24-26) — for every ODDRN referenced in lineage edges or DQ-test datasets that is NOT in the current ingestion, INSERT a hollow `data_entity` row (`createHollow(...)`). Effect: lineage references to not-yet-ingested entities materialise placeholder rows that future ingestion will fill in.
- **MAIN phase processors** (`IngestionProcessingPhase.order = 2`):
  - `DatasetStructureIngestionRequestProcessor` (DatasetStructureIngestionRequestProcessor.java:42-48) — creates `dataset_version` rows for new datasets and for existing datasets whose `structureHash` has changed; populates `dataset_field` rows; sets `dto.datasetSchemaChanged=true` flag on the in-memory DTO when version increments (consumed later by Alert processor). Sub-steps: `datasetFieldMetadataIngestionService.ingestMetadata(...)` writes per-field metadata; `enumValuesIngestionService.ingestEnumValues(...)` writes per-field enum values.
  - `TaskRunIngestionRequestProcessor` (TaskRunIngestionRequestProcessor.java:25-48) — bulk-INSERT new task runs / bulk-UPDATE existing task runs (partitioned by `existsByOddrns`) into `data_entity_task_run`; then `insertLastRuns(...)` updates `last_runs` summary table. Declared `@ReactiveTransactional` again at line 24 — nests inside the outer transaction.
  - `MetadataIngestionRequestProcessor` (MetadataIngestionRequestProcessor.java:36-82) — for every metadata key on every entity in the payload: ensure `metadata_field` row exists; insert/update `metadata_field_value` rows; DELETE metadata_field_value rows that are no longer present in the payload (`bindingsToDelete = existingMetadataBindings.difference(currentBindings)`, line 72-74). **The DELETE-on-absence semantics is critical**: a collector that fails to re-send a metadata field for an entity SILENTLY REMOVES that field's value from the platform.
  - `LineageIngestionRequestProcessor` (LineageIngestionRequestProcessor.java:16-18) — `lineageService.replaceLineagePaths(request.getLineageRelations())`. **The verb is REPLACE, not MERGE**: every ingestion call replaces the lineage paths originating from this datasource's entities. A collector that forgets to re-emit a lineage edge silently removes it from the platform.
  - `DataQualityTestRelationIngestionRequestProcessor` — writes `data_quality_test_relations` (per-DQ-test dataset binding).
  - `GroupEntityRelationIngestionRequestProcessor` — writes `group_entity_relations` (per-DEG entity binding).
  - `GroupParentGroupIngestionRequestProcessor` — writes `group_parent_group_relations` (DEG → parent DEG binding).
  - `RelationshipIngestionRequestProcessor` — writes `erd_relationships` + `graph_relationships` (ERD/graph relationship types).
  - `ExternalTagIngestionRequestProcessor` — writes external tags.
  - `UsageReportIngestionRequestProcessor` (UsageReportIngestionRequestProcessor.java:16-20) — `dataEntityStatisticsService.updateStatistics(classesDelta.totalDelta(), classesDelta.entityDelta())` writes aggregated counters to `data_entity_statistics`. **Runs on EVERY ingestion** (`shouldProcess` returns `true` unconditionally — line 23-25), even if the delta is zero.
- **FINALIZING phase processors** (`IngestionProcessingPhase.order = 3`):
  - `FTSVectorsIngestionRequestProcessor` (FTSVectorsIngestionRequestProcessor.java:18-25) — `searchEntrypointRepository.recalculateVectors(idsToProcess)` — rebuilds Postgres FTS tsvector index for every non-JOB_RUN entity in the request. Hot path: O(N) writes to `search_entrypoint` table.
  - `ActivityIngestionRequestProcessor` (ActivityIngestionRequestProcessor.java:24-32) — for every NEW entity (existing entities don't emit), creates an `activity_event` row of type `DATA_ENTITY_CREATED`, marked `systemEvent: true`. **The activity log is the only audit trail of who-ingested-what**; existing-entity UPDATEs do NOT create an activity event (no `DATA_ENTITY_UPDATED` system event from ingestion — only the create path is audited).
  - `AlertIngestionRequestProcessor` (AlertIngestionRequestProcessor.java:50-66) — opens an alert-state snapshot, computes alert-action candidates from `request.getSpecificAttributesDeltas()` + `request.getChangedDatasetIds()` (backwards-incompatible schema changes) + `request.getTaskRuns()` (failed runs); resolves desired actions vs current open alerts + halt-config; applies actions via `alertService::applyAlertActions` → INSERT/UPDATE rows in `alert` + `alert_chunk` tables.
- **Terminal step** (in `IngestionServiceImpl.ingest`, after the chain):
  - `otlpMetricService::exportMetrics` (IngestionServiceImpl.java:72) — extracts metric data via every `MetricExtractor` and pushes via OTLP gRPC if `metrics.export.enabled=true` (OTLPMetricServiceImpl.java:24-32). When `metrics.export.enabled=false` (likely default — verify), `NoOpOTLPMetricService.exportMetrics` returns immediately (NoOpOTLPMetricService.java:11-14).

**One bad entity in a batch: NO per-entity isolation**. The transaction boundary is the entire `ingest(...)` call. A single failing processor (e.g. a constraint violation in `dataset_version`, an OOM in metadata processing, a deadlock against another concurrent ingestion) ROLLS BACK ALL of the above — the entire batch is lost. There is no DLQ, no partial-success response shape, no per-entity error reporting. The HTTP response is binary: 200 OK (all writes committed) or 5xx (everything rolled back).

- **hot_paths**:
  - "every `POST /ingestion/entities` call routes through `IngestionServiceImpl.ingest(...)` which executes (in order, all inside one Postgres transaction): (1) `getIdByOddrnForUpdate` — 1 SELECT FOR UPDATE on `data_source`; (2) `listByOddrns(...)` — 1 SELECT on `data_entity` for all inbound ODDRNs (single query, indexed on ODDRN); (3) Java-side partitioning of new-vs-existing — O(N) where N is payload size; (4) `bulkUpdate(entitiesToUpdate)` — 1 multi-row UPDATE; (5) `restoreDeletedDataEntityRelations(entitiesToRestore)` — N more SELECTs + UPDATEs + statistics increments; (6) `bulkCreate(pojosToCreate)` — 1 multi-row INSERT; (7) processor chain — 14 processors each running its own DB queries (most read-then-write patterns); (8) OTLP export. Total per-request DB query count scales roughly linearly with entity count and with the number of relevant processors (e.g. only entities with metadata trigger MetadataIngestionRequestProcessor's writes)." — evidence: IngestionServiceImpl.java:67-74 + ReactiveAbstractCRUDRepository.java:114-142 + each processor's process(...) method
  - "Schema-diff hot path (DatasetStructureIngestionRequestProcessor.java:80-105): for every existing DATA_SET entity in the payload, fetch the latest `dataset_version` row, compare `versionHash` vs payload's `structureHash`, and conditionally INSERT a new version + recompute the hash if the old version's hash was empty. This is O(N_datasets) extra queries per request — the hash recompute path (line 107-121) triggers ANOTHER set of queries (`getDatasetVersionFields(ids)` + `bulkUpdate(versionsWithoutHash)`) only on first-encounter of unhashed rows."
- **throughput_characteristics**:
  - "Synchronous per-request: the service holds the HTTP connection AND the Postgres transaction open for the entire pipeline duration. A 1000-entity payload with metadata, lineage, FTS recompute, alert resolution, and OTLP export typically takes seconds. Collectors batch their per-tick scans into one payload, so request count is low but per-request duration is high."
  - "Per-datasource row lock serialises concurrent ingestions targeting the same datasource. Cross-datasource ingestions scale linearly. The lock is held from `getIdByOddrnForUpdate` (line 68) to transaction commit — i.e. the entire pipeline."
  - "Within-phase parallelism: processors in the same phase run via `Mono.zip` (IngestionProcessorChain.java:36) — parallel reactive subscriptions. However, all share the same R2DBC connection bound to the outer transaction — there is no true I/O parallelism for DB operations on Postgres (single-connection sequential at the wire level), though independent CPU work (e.g. extracting metadata vs computing total deltas) can overlap on the reactor scheduler."
  - "`ingestStats` (POST /ingestion/entities/datasets/stats) is a SEPARATE flow not wrapped in `@ReactiveTransactional` at this layer — delegates entirely to `DatasetFieldService.updateStatistics(...)`. Throughput characteristics depend on that service's transaction semantics (not analysed here)."
- **resource_allocation**:
  - "Full payload buffered in heap (capped at 20 MB by `spring.codec.max-in-memory-size`, application.yml:14-15) as `DataEntityList`. The service then materialises: a `Map<String, DataEntityIngestionDto>` (line 83-86), a `List<IngestionTaskRun>` (line 88-91), an `existingPojoDict: Map<String, DataEntityPojo>` (line 93-94), the partitioned `Map<Boolean, List<DataEntityIngestionDto>>` (line 96-98), the `specificAttributesDeltas` list (line 100-113), the `enrichedExistingDtos` list (line 115-121), the `entitiesToUpdate` + `entitiesToRestore` + `pojosToCreate` lists (line 123-133). For a 20MB payload (likely thousands of entities), the heap footprint is multiple times the payload size — Jackson POJO, the contract DTOs, the internal DTOs, the POJOs, the partition maps, the delta lists."
  - "Per-request Postgres transaction held open for the pipeline duration. The transaction binds one R2DBC connection from the pool for its lifetime — fewer concurrent ingestions can be active than the pool's max size. Large/slow ingestions starve other request flows."
  - "FTS recompute on EVERY non-JOB_RUN entity in the payload (FTSVectorsIngestionRequestProcessor.java:18-25) writes O(N) rows to `search_entrypoint` per request, even if no searchable field changed."
  - "Per-entity `metadata_field_value` row churn: every metadata field on every entity is either created/updated/deleted (MetadataIngestionRequestProcessor.java:42-80). A 1000-entity payload with 20 metadata fields per entity = 20,000 row operations on `metadata_field_value`."
- **scaling_characteristics**:
  - "Stateless service — only injected dependencies (line 55-63), no instance state. Instances scale horizontally without coordination."
  - "Per-datasource row-level lock serialises concurrent ingestions targeting the SAME datasource. Different datasources scale linearly."
  - "Postgres-bound: the throughput ceiling is the database (transaction commit latency, lock contention, FTS recompute throughput, statistics-table contention via UsageReportIngestionRequestProcessor). The service has no caching layer — every request hits the DB."
  - "No payload-size streaming — entire payload buffered, entire result set materialised. A 50 MB collector tick must split into N ≤ 20 MB requests; the platform does not support chunked streaming ingestion."
- **known_performance_gaps**:
  - "FTS recompute runs on every entity in every ingest, even on no-op idempotent re-ingestions. A high-frequency idempotent collector (e.g. 30s tick interval, same payload) burns Postgres CPU recomputing identical tsvectors. A diff-aware FTS recompute (only recompute if name/description/oddrn changed) would cut a significant fraction of the per-request DB cost on the common case (re-ingestion of unchanged entities)." — evidence: FTSVectorsIngestionRequestProcessor.java:18-25 (no diff check) — severity: MEDIUM
  - "UsageReportIngestionRequestProcessor runs on every request (`shouldProcess` returns `true` unconditionally — UsageReportIngestionRequestProcessor.java:22-25). For zero-delta requests, this is a wasted write to `data_entity_statistics`." — evidence: UsageReportIngestionRequestProcessor.java:22-25 — severity: LOW
  - "Per-datasource serialisation via `SELECT ... FOR UPDATE`: the row lock is held for the ENTIRE pipeline duration (not just for the entity reads/writes). A 30-second ingestion blocks ALL concurrent ingestions on the same datasource for 30 seconds. Collectors that don't coordinate (or worse, retry on timeout) compound the contention. An advisory-lock-style coordination ('only-one-ingestion-at-a-time-per-datasource' BUT released after entity writes complete, allowing the processor chain to run without the lock) would reduce contention on busy datasources." — evidence: IngestionServiceImpl.java:68 (`getIdByOddrnForUpdate`) + IngestionServiceImpl.java:67-74 (lock spans full pipeline) — severity: MEDIUM
  - "No batch chunking / streaming: a payload at the 20 MB cap must be entirely materialised in heap (POJO graph + Jackson buffers + multiple internal Maps/Lists) before any work begins. Streaming-friendly schemas (NDJSON, chunked frames) would allow per-entity processing and bounded memory. The OpenAPI contract locks the request shape to a single `DataEntityList` JSON object, so this is contract-level, not just code-level." — evidence: application.yml:14-15 + IngestionServiceImpl.java:83-91 (full payload materialised before any DB write) — severity: MEDIUM
  - "OTLP export inside the per-request flow with no timeout / circuit-breaker visible at this layer (OTLPMetricServiceImpl.java:25-31 builds the metric list synchronously). A slow `MetricExtractor` (e.g. one that hits a separate DB) slows every ingestion request even when the OTLP export call itself is fire-and-forget. Decoupling metric extraction from the ingestion request would let the request return immediately and process metrics asynchronously." — evidence: OTLPMetricServiceImpl.java:25-27 (metric extraction inline) + IngestionServiceImpl.java:72 (OTLP step inside the ingest chain) — severity: LOW
