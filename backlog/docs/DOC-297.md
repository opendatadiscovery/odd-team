## Description

Two related, code-confirmed caveats about `view_count`:

1. **`view_count` is the sole, trivially-inflatable ranking signal for the Popular strip.** The catalog-overview "Popular" column is ranked by `view_count DESC` **alone**, and the count is incremented by a detail-page read that has **no rate-limit, no auth requirement, and no idempotency**. The loop is self-reinforcing: a scripted (or under `auth.type=DISABLED`, anonymous) caller can hammer the detail endpoint and push any entity to the top of Popular. The pages present "most-viewed" / "view count" as neutral display metadata with no caveat that it is a gameable ranking signal.

2. **Opening a detail page registers +2, not +1.** The entity-detail page's view counter increments by **2** per open, because the front-end fetches the entity twice (a `useEffect` whose dependency includes `status` fires the fetch twice — LSN-017). So the displayed count is roughly double the number of actual opens — relevant to anyone interpreting the number or comparing entities.

High — the page presents a gameable, inaccurate metric as trustworthy display metadata.

**Failure shape**: missing caveats (Gate 3/6) on a user-facing metric — gameability + a 2× inflation factor.
