## What

When a brand-new user authenticates for the first time under OAUTH2 or LDAP, no `USER_OWNER_MAPPING` row is auto-created — the `OwnerAssociationRequest` request-and-approval round-trip is mandatory. But `fetchAssociatedOwner` emits an **empty Mono** (no `switchIfEmpty`), so every owner-scoped consumer (My Objects, My Alerts, the MY_OBJECTS activity view, my discussions) degrades to **empty results with HTTP 200** — not 401/403/404 and not an onboarding prompt. The toolbar shows the user's name, the full navigation chrome renders, and every personalised surface is silently blank. There is no banner, toast, or empty-state message directing the user to the owner-association request flow. The `Overview` `OwnerAssociation` card exists but is gated on `auth.type` and is a separate surface the user must find.

This is **net_new** — no existing PLT proposes the in-product onboarding affordance. (The cross-mode association-migration angle is DOC-312; the first-login *silence* is its own code gap.)

## Impact

A new SSO user signs in successfully, sees the full navigation and their own name in the toolbar, but every personalised view is empty — with no in-product explanation that they must request an owner association. They reasonably conclude the platform is broken or that they have no access. The live docs are also silent on this onboarding step (a separate doc-gap), so neither user nor operator can discover the requirement from the documentation.

## Suggested fix

Per the reflection's `proposed_fix_anchor` (minimum-viable): emit a first-login WARN log and an in-product banner / empty-state on the owner-scoped surfaces when `fetchAssociatedOwner` is empty, linking to the `OwnerAssociation` request flow. `AuthIdentityProviderImpl.java:50-53` is the empty-Mono detection point. The doc-side first-login silence is a separate doc-gap (authentication page).
