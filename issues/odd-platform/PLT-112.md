## What

The platform's OpenAPI contract still declares the project's **pre-rebrand identity**. `info.title` is `ProspectLog data catalog HTTP API contract` (ProspectLog was the original internal codename) and `info.contact.url` is `https://provectus.com` (the company that first built the project), instead of the current **ODD Platform** / `opendatadiscovery.org` identity.

This is the single shared `openapi.yaml` that feeds both generators (the Java server interfaces and the TS client), so the stale identity propagates to anything that reads the spec - the **generated-client package metadata / API docs** and, where served, the **springdoc Swagger UI** header.

## Where

The entire `info` block carries the pre-rebrand identity, not just `title` + `contact.url` - verified by reading `odd-platform-specification/openapi.yaml:1-9` on 2026-06-10:

| File | Line | Content |
|------|------|---------|
| `odd-platform-specification/openapi.yaml` | 3 | `title: ProspectLog data catalog HTTP API contract` |
| `odd-platform-specification/openapi.yaml` | 4 | `description: ProspectLog data catalog HTTP API contract` |
| `odd-platform-specification/openapi.yaml` | 6 | `email: ndementev@provectus.com` (under `info.contact`) |
| `odd-platform-specification/openapi.yaml` | 7 | `url: https://provectus.com` (under `info.contact`) |
| `odd-platform-specification/openapi.yaml` | 8 | `name: Nikita Dementev` (under `info.contact`) |

Both consumers of this spec confirmed: the Java server-interface generator (`odd-platform-api-contract/build.gradle:12`, `inputSpec = "$projectDir/../odd-platform-specification/openapi.yaml"`) and the TS client generator (`odd-platform-ui/openapi-config.yaml`, `inputSpec: ./odd-platform-specification/openapi.yaml`, `generatorName: typescript-fetch`). Originally verified by the reviewer @ `ede5d277` via `grep -n "ProspectLog\|provectus" odd-platform-specification/openapi.yaml`.

## User-facing impact

**Spec content + propagation code-verified 2026-06-10; live Swagger-UI rendering NOT verified (and currently broken).** The load-bearing fact - the stale `info` block - is a pure source string and is settled (`openapi.yaml:3-8`). The "integrator-visible" claim splits:

- **Generated-client metadata (code-verified):** both the Java contract and the TS client are generated from this exact spec (`build.gradle:12`, `openapi-config.yaml`), so the `info` block is the canonical source any regenerated client/API doc copies. This propagation path is real and does not depend on a running server.
- **Swagger UI header (NOT currently observable):** springdoc IS a dependency (`odd-platform-api/build.gradle:49`), but the platform's Swagger UI is presently broken by springdoc 2.2.0 x Spring 6.2 (tracked as PLT-141), so the "renders in the Swagger UI header" claim cannot be driven against a live instance right now and is asserted from the spec + springdoc wiring, not from a fetched page. When PLT-141 is resolved the `info.title` would surface in the UI header. This is why this item stays `user_facing_verified: false`: the durable, code-settled surface is the generated clients, not a currently-renderable UI.
  [UPDATE 2026-06-12 — PLT-141 FIXED (#1759/CTRIB-008, springdoc 2.2.0 -> 2.8.17) and the hypothesis DRIVEN: the live served document's `info.title` is springdoc's DEFAULT ("OpenAPI definition"), NOT the spec file's "ProspectLog..." — springdoc generates the served doc from the controllers and no `OpenAPI`/`info` bean is configured, so the spec file's info block does NOT propagate to the Swagger UI at all. The ProspectLog exposure surface is therefore EXACTLY the generated clients + the published spec file (as this item's durable framing already said); the "renders in the Swagger UI header" half is falsified and can be dropped from the issue body if/when filed.]

Severity is unchanged (low / cosmetic-branding, no runtime behaviour), but the visible-surface framing is now scoped to what is actually verifiable.

## Why it matters

Low severity (cosmetic / branding - no runtime impact), but it is **publicly visible**: the OpenAPI `info` block renders in the Swagger UI header and is copied verbatim into generated API clients and their published docs. For an open-source project the stale codename + the original vendor's contact URL read as either abandonment or an unfinished rebrand to anyone integrating against the API. It is exactly the kind of detail an integrator notices first.

## Suggested fix

- Set `info.title` to the current product name (e.g. `ODD Platform HTTP API` / `Open Data Discovery Platform API`).
- Set `info.contact` to the project's canonical contact (`https://opendatadiscovery.org` / the GitHub org), not `provectus.com`.
- Audit the rest of the `info` block (`description`, `license`, `termsOfService` if present) for other pre-rebrand strings in the same pass.
- Grep the wider repo for other `ProspectLog` / `provectus.com` occurrences (READMEs, generated artefacts, helm charts) so the rebrand is closed consistently, not just in the spec `info` block.
