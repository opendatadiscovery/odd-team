## Findings (new — axes 4 + 5)

### Axis 4 — UI Shell

#### F-047: Multilingual UI completely undocumented (the i18n probe)
- **Location**: Missing from all documentation pages
- **Issue**: The platform UI ships **six languages** (English `en`, Spanish `es`, French `fr`, Ukrainian `ua`, Armenian `hy`, Chinese `ch`) bootstrapped at app start. Default is `en`; chosen language persists in `localStorage('i18nextLng')`; if storage is cleared (or user switches browser) the choice is lost. The `<SelectLanguage>` widget lives in the user-menu inside `AppToolbar`. Zero documentation exists — no operator knows the platform supports six locales, no contributor knows where to add a seventh, no user knows the menu exists.
- **Evidence**:
  - `odd-platform-ui/src/locales/i18n.ts` (37 lines) — bootstraps `react-i18next` with `resources = {en, es, ch, fr, ua, hy}`, `lng = localStorage.getItem('i18nextLng') || 'en'`, fallback chain.
  - `odd-platform-ui/src/locales/translations/{en,es,ch,fr,ua,hy}.json` — 6 translation resource files.
  - `odd-platform-ui/src/components/shared/elements/AppToolbar/SelectLanguage/` — the language-switcher widget.
  - `odd-platform-ui/src/components/shared/elements/AppToolbar/AppToolbar.tsx` lines ~75-95 — `<SelectLanguage>` mounted inside the user menu.
  - `odd-platform-ui/src/lib/constants.ts:158` — `LANGUAGES_MAP` (rendered names per locale).
  - `odd-platform-ui/src/index.tsx:24` — `import 'locales/i18n';` (the bootstrap entry).
- **Severity**: medium (not data-loss, but a six-language capability invisible to users + contributors)
- **Suggested fix**: A short page under "Configuration and Deployment" or "Features" titled "Localization (i18n)" covering: supported locales, default + fallback, persistence (and the localStorage caveat), how to contribute a new locale (PR adding `translations/<lang>.json` + `LANGUAGES_MAP` entry + `i18n.ts` resource entry).
- **Effort**: simple page

#### F-048: Application error page family undocumented
- **Location**: Missing from all documentation pages
- **Issue**: The platform has a dedicated error-page component (`AppErrorPage.tsx`) that renders for top-level routing/network failures. Users hitting an error page have no doc explaining what they'll see (UI elements, retry behavior) or how to capture the diagnostic for a bug report.
- **Evidence**:
  - `odd-platform-ui/src/components/shared/elements/AppErrorPage/AppErrorPage.tsx` — error component.
- **Severity**: low (UX nicety; not blocking)
- **Suggested fix**: A note in a Troubleshooting page (or fold into "Configure ODD Platform") describing what the error page surfaces and how to file a useful bug report from one.
- **Effort**: trivial

#### F-049: AppInfoMenu (in-platform docs/links/version chrome) undocumented as a navigation surface
- **Location**: Missing from all documentation pages
- **Issue**: The user-menu's "info" panel (`AppInfoMenu`) surfaces: the running platform version (linked to the GitHub repo), a link to `https://docs.opendatadiscovery.org/` (GitBook), a link to the public Slack workspace, a Product Hunt review entry, and any operator-configured **additional links** (`odd.links.*` config — the `AdditionalLinkProperties`-driven feature partially documented in `odd-platform.md` "Additional navigation links"). The panel's **role** as the in-app gateway to docs/community/version is not described anywhere in user-facing docs — operators configuring `odd.links` don't know where they'll appear.
- **Evidence**:
  - `odd-platform-ui/src/components/shared/elements/AppToolbar/AppInfoMenu/AppInfoMenu.tsx` (renders the menu; consumes `useAppInfo` + `useAppLinks` hooks).
  - `odd-platform-api/.../controller/AppInfoController.java` (serves `/api/appInfo` — version, build).
  - `odd-platform-api/.../controller/LinksController.java` (serves `/api/links` — additional links).
- **Severity**: medium (operators configuring `odd.links` need to know what UI surface their entries appear on — partially-orphan config doc)
- **Suggested fix**: Cross-reference in the `odd.links` config section: "Configured links appear in the user info menu (top-right of the toolbar) alongside the platform version, docs link, and Slack link."
- **Effort**: trivial (one paragraph cross-reference)

#### F-050: Active-features toggling surface (`/api/features/active`) undocumented as an operator capability
- **Location**: Missing from all documentation pages
- **Issue**: On every app load, the UI calls `fetchActiveFeatures()` against `FeatureController` (`/api/features/active`) which returns the set of currently-enabled features. This is the runtime feature-toggle surface — operators with the right config can enable/disable features per deployment, but the doc says nothing about what features are toggleable, where the toggles live, or how to read the active set from outside the UI.
- **Evidence**:
  - `odd-platform-api/.../controller/FeatureController.java` — exposes `/api/features/active`.
  - `odd-platform-ui/src/components/App.tsx:48` — `dispatch(fetchActiveFeatures())` on app init.
  - `odd-platform-ui/src/redux/thunks/` — thunk implementation.
- **Severity**: medium (operators don't know runtime toggles exist; debug-time discoverability is poor)
- **Suggested fix**: A short section under "Configure ODD Platform" titled "Runtime feature flags" listing toggleable features (genai, datacollaboration, notifications, housekeeping, auth.s2s, attachment.storage, etc.) and the `/api/features/active` endpoint operators can hit to verify the active set.
- **Effort**: simple section

#### F-051: Logout flow undocumented (paired with auth-disabled and auth-enabled modes)
- **Location**: Briefly implied by `enable-security/authentication/*` pages but not described
- **Issue**: The user menu carries a "Logout" entry (`AppToolbar.tsx` — `<AppMenuItem onClick={handleLogout}>`). With `auth.type=DISABLED`, the logout entry's behavior is undefined-from-the-doc-side. With `auth.type=LOGIN_FORM`/`OAUTH2`/`LDAP`, the redirect target depends on `auth.login-form-redirect` (only documented in YAML comment) or the OAuth2 provider's `logout-uri` (per-provider). No page describes the user-side logout UX.
- **Evidence**:
  - `odd-platform-ui/src/components/shared/elements/AppToolbar/AppToolbar.tsx` (Logout menu item).
  - `odd-platform-api/.../auth/logout/` directory — server-side handler.
  - `odd-platform-api/src/main/resources/application.yml:73` — `auth.login-form-redirect:` (commented out — undocumented in user-facing docs).
- **Severity**: medium
- **Suggested fix**: A "Logout flow" sub-section in each of `enable-security/authentication/{login-form,oauth2-oidc,ldap,disabled-authentication}.md` describing the redirect behavior + the relevant config key (`auth.login-form-redirect` or per-provider `logout-uri`).
- **Effort**: simple (one section per auth doc — 4 pages, 1 short section each)

### Axis 5 — Config Prefixes

#### F-052: `auth.ingestion.filter.enabled` undocumented (S2S ingestion-scope gate)
- **Location**: Missing from all documentation pages
- **Issue**: Setting `auth.ingestion.filter.enabled: true` activates `IngestionDataEntitiesFilter` — a scope gate that filters which data entities a server-to-server (S2S) authenticated request can ingest. This is a security/scoping primitive that an operator using S2S would want to know about. The `enable-security/authentication/s2s.md` doc covers token issuance but not the ingestion-scope filter.
- **Evidence**:
  - `odd-platform-api/.../auth/filter/IngestionDataEntitiesFilter.java:20` — `@ConditionalOnProperty(value = "auth.ingestion.filter.enabled", havingValue = "true")`.
  - `application.yml:44-47` — the YAML key (uncommented, default `false`).
- **Severity**: high (security-relevant: operators using S2S in multi-tenant deployments need this filter; not knowing it exists means they can't scope-gate ingestion)
- **Suggested fix**: A "Ingestion scope filter" section in `enable-security/authentication/s2s.md` describing the filter's purpose, when to enable it, and the data-entity scoping logic the filter implements (read filter source + decide what to expose).
- **Effort**: medium (requires reading the filter implementation to describe the scoping logic correctly)

#### F-053: `partition.advisory-lock-id` essentially undocumented
- **Location**: One token mention in `configuration-and-deployment/odd-platform.md`; no explanation
- **Issue**: `partition.advisory-lock-id` (default `90`) is a PostgreSQL advisory-lock ID used by `PostgreSQLPartitionCreationJob` to serialise the schedule that creates monthly partitions for activity / data-collaboration tables. **In multi-instance deployments two pods coordinate via this lock** — if two ODD Platform deployments share a database (rare but possible during blue/green or multi-tenant setups), the lock IDs MUST NOT collide with `notifications.wal.advisory-lock-id` (100), `datacollaboration.receive-event-advisory-lock-id` (110), or `datacollaboration.sender-message-advisory-lock-id` (120). None of this is documented.
- **Evidence**:
  - `odd-platform-api/.../partition/PostgreSQLPartitionCreationJob.java:26` — `@Value("${partition.advisory-lock-id}")`.
  - `application.yml:107` — `partition: { advisory-lock-id: 90 }`.
  - Sibling lock IDs in `application.yml`: `notifications.wal.advisory-lock-id: 100`, `datacollaboration.receive-event-advisory-lock-id: 110`, `datacollaboration.sender-message-advisory-lock-id: 120`.
- **Severity**: medium (footgun in shared-database deployments)
- **Suggested fix**: A "PostgreSQL advisory locks" section in `configuration-and-deployment/odd-platform.md` listing all four lock IDs (`partition.*`, `notifications.wal.*`, `datacollaboration.receive-event-*`, `datacollaboration.sender-message-*`), their defaults, and the constraint that in shared-database deployments each ODD Platform instance must use a unique set of IDs.
- **Effort**: simple section (one paragraph + a 4-row table)

#### F-054: `management.*` (Spring Boot Actuator) endpoints undocumented — `env` exposure has security implication
- **Location**: Missing from all documentation pages
- **Issue**: The default `application.yml` exposes Spring Boot Actuator endpoints `health`, `prometheus`, `env`, `info` via `management.endpoints.web.exposure.include`. Of these, **`/actuator/env` returns the platform's full resolved configuration including masked-but-present secret keys** — a production-relevant security exposure if Actuator is reachable from outside the cluster. Operators do not know which endpoints are exposed by default or that the default exposes `env`.
- **Evidence**:
  - `application.yml:233-242` — `management.endpoints.web.exposure.include: health, prometheus, env, info`; per-endpoint `enabled: true` for all four.
  - Spring Boot Actuator standard behavior — `/actuator/env` enumerates `Environment` `PropertySource`s.
- **Severity**: high (security-relevant default; operators with externally-reachable Actuator endpoints leak config)
- **Suggested fix**: A "Spring Boot Actuator endpoints" section in `configuration-and-deployment/odd-platform.md` listing the four exposed endpoints, their purpose, the `/actuator/env` exposure caveat, and the recommended mitigations (network-level isolation; `management.server.port`; `management.endpoints.web.exposure.include` override to drop `env` in prod).
- **Effort**: medium (requires the security caveat to be precise; recommend a Pre-authoring stance check before writing — Cornerstone 3 "configuration is a separate audience surface")

#### F-055: `springdoc.*` (Swagger UI mount paths) undocumented
- **Location**: Missing from all documentation pages
- **Issue**: `springdoc.api-docs.path: /api/v3/swagger-ui.html` and `springdoc.swagger-ui.path: /api/v3/api-docs` configure where the OpenAPI Swagger UI is mounted. Operators wanting to relocate the Swagger UI (or audit which paths are exposed) have no doc pointer.
- **Evidence**:
  - `application.yml:23-27` — `springdoc.api-docs.path` + `springdoc.swagger-ui.path`.
  - `developer-guides/api-reference.md` (no mention of these paths).
- **Severity**: low (operator-relevant but not security-critical)
- **Suggested fix**: A note in `developer-guides/api-reference.md` (or a sub-page) noting the default Swagger UI / OpenAPI doc paths and how to override them via `springdoc.*`.
- **Effort**: trivial

#### F-056: `spring.codec.max-in-memory-size` undocumented (request-size cap)
- **Location**: Missing from all documentation pages
- **Issue**: `spring.codec.max-in-memory-size: 20MB` caps the max request body the platform's WebFlux runtime will buffer in memory. Operators ingesting large data-entity batches via the Ingestion API or uploading large attachments **need to know this exists** — the wrong default surfaces as a `DataBufferLimitException` deep in the stack with no obvious fix. The 20MB default is not the same as `attachment.max-file-size` (also 20MB but a separate limit).
- **Evidence**:
  - `application.yml:14-15` — `spring.codec.max-in-memory-size: 20MB`.
  - WebFlux `CodecConfigurer` standard behavior.
- **Severity**: medium (operator confusion when the wrong default fires)
- **Suggested fix**: A note in `configuration-and-deployment/odd-platform.md` (or in the ingestion / attachment docs) explaining the 20MB request cap, its relationship to `attachment.max-file-size`, and how to raise it for high-volume ingestion deployments.
- **Effort**: trivial (one paragraph)

#### F-057: Top-level `housekeeping.enabled` undocumented (only `housekeeping.ttl.*` covered)
- **Location**: `configuration-and-deployment/odd-platform.md` "Housekeeping Settings Configuration" covers the TTL keys but not the master enable/disable flag
- **Issue**: `housekeeping.enabled: true` (default) is the master toggle for the housekeeping job. The TTL sub-keys (`housekeeping.ttl.{resolved_alerts_days, search_facets_days, data_entity_delete_days}`) are documented; the parent flag is not. Operators who want to disable housekeeping entirely don't have a doc pointer.
- **Evidence**:
  - `application.yml:101-106` — `housekeeping.enabled: true` + `housekeeping.ttl.*`.
  - `configuration-and-deployment/odd-platform.md` — covers TTL keys, no mention of `enabled`.
- **Severity**: low
- **Suggested fix**: Add `housekeeping.enabled` to the existing housekeeping config table.
- **Effort**: trivial

#### F-058: `notifications.wal.*` (PostgreSQL replication slot for alert notifications) undocumented
- **Location**: `configuration-and-deployment/odd-platform.md` "Enable Alert Notifications" covers receivers + `notifications.enabled` but not the WAL/replication-slot infrastructure
- **Issue**: `notifications.wal.{advisory-lock-id, replication-slot-name, publication-name}` configures the PostgreSQL logical-replication slot the alert subsystem reads from. Operators with PostgreSQL replication-slot ownership concerns (slot quotas; slot accumulation; cleanup on platform redeploy) need these names to be discoverable in docs. The slot is not auto-cleaned on platform shutdown.
- **Evidence**:
  - `application.yml:91-94` — `notifications.wal.{advisory-lock-id: 100, replication-slot-name: odd_platform_replication_slot, publication-name: odd_platform_publication_alert}`.
- **Severity**: medium (operator footgun — abandoned replication slots accumulate WAL on the source DB)
- **Suggested fix**: A "PostgreSQL replication slot" section in the notifications doc covering: slot name, publication name, advisory-lock-id (cross-link to F-053's advisory-lock table), what happens on platform shutdown, how to manually drop the slot if a redeploy doesn't reuse it.
- **Effort**: medium (needs a precise operational caveat)

#### F-059: Top-level `metrics.storage` undocumented (only `metrics.export.*` covered)
- **Location**: `configuration-and-deployment/odd-platform.md` "Enable Metrics" covers OTLP export and Prometheus scrape but the `metrics.storage` switch (`INTERNAL_POSTGRES` vs `PROMETHEUS`) is partially-implicit
- **Issue**: `metrics.storage: INTERNAL_POSTGRES | PROMETHEUS` selects which backend the platform reads metrics from for the per-entity Metrics UI tab. `INTERNAL_POSTGRES` (default) means metrics are pushed to the platform's own DB by collectors; `PROMETHEUS` means the platform queries an external Prometheus at `metrics.prometheus-host` for time-series data. Operators choosing between the two need a side-by-side comparison of trade-offs (query freshness, retention, scrape intervals) — currently each is mentioned in isolation.
- **Evidence**:
  - `application.yml:96-99` — `metrics.storage: INTERNAL_POSTGRES`, `metrics.prometheus-host: http://localhost:9090`.
  - `odd-platform-api/.../service/ExternalMetricReader.java:52` — consumes `${metrics.prometheus-host}` for the PROMETHEUS path.
- **Severity**: medium
- **Suggested fix**: A "Metric storage backends" sub-section comparing INTERNAL_POSTGRES vs PROMETHEUS (when to use which, retention implications, query freshness).
- **Effort**: simple

#### F-060: `notifications.message.downstream-entities-depth` undocumented
- **Location**: Missing from all documentation pages
- **Issue**: `notifications.message.downstream-entities-depth: 1` controls how many lineage hops deep the alert notification message walks when listing affected downstream entities. Default `1` (direct children only). Operators wanting "all downstream up to 3 hops" in alert messages (large lineage trees, business-impact emails) have no doc pointer.
- **Evidence**:
  - `application.yml:88-90` — `notifications.message.downstream-entities-depth: 1`.
- **Severity**: low
- **Suggested fix**: Add to the notifications config table.
- **Effort**: trivial
