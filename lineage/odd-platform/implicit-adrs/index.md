## ADR-CANDIDATE-038 — LDAP admin-group membership is decided by case-insensitive **substring containment** match (`containsIgnoreCase`) against the configured `admin-groups` allowlist, not by exact DN equality. Per the Rule-0 3-question wisdom test, **2 new ADR candidates** were minted and **2 existing ADRs strengthened**; 10 sidecar findings failed the wisdom test and were reclassified to refactoring-scopes (REFACTOR-592..605).

The batch is the first dashboard-feature-pillar entry in the catalog and reveals a coherent architectural commitment the codebase had developed without explicit framing: a two-store-system (redux + jotai) with per-feature-area choice, plus an enum-driven UI-side ordering primitive.

**2 new ADR candidates** (both PASS the wisdom test):

- **ADR-CANDIDATE-207** (HIGH — promote) — **`jotai` is the per-feature-store substrate when client state is feature-local; `redux` + `redux-thunk` remains the app-global store — the platform deliberately runs a TWO-store-system architecture, choosing per feature-area rather than enforcing one.** Anchored by 26 `jotai`-importing files across 4 feature areas (OwnerAssociations + DEGLineage + DatasetStructure + DataQuality) with byte-identical `*AtomProvider` wrappers. The DataQualityStore sidecar is the primary source; the cross-feature byte-identical wrapper shape is the intent_anchor. The decision encodes (a) the boundary between app-global redux and feature-local jotai; (b) the per-mount-reset contract for feature-local state; (c) the choice of subscription primitive (per-atom for jotai, per-slice-selector for redux). Composes with ADR-CANDIDATE-084 / -085 / -087 / -097 (the redux side) and ADR-CANDIDATE-091 (URL as source of truth for view state, which is the persistence channel for jotai feature-local state when needed). Cross-pillar reach: P-04 + P-05 + P-08 + P-01. **The strongest single-batch ADR candidate of batch ZC.**

- **ADR-CANDIDATE-208** (LOW — promote) — **Per-test-category result rows render run-status tiles in FIXED enum-declaration order (not server-supplied order, not count-descending) — the visual columns are deliberately comparable across category rows, achieved by re-sorting `results` via `Object.values(DataEntityRunStatus).map(find)` instead of a plain `results.map`.** Anchored by `TestCategoryResults.tsx:19-25` + `DataQualityContent.tsx:83-89` (the legend using the IDENTICAL enum iteration — the cross-component pairing IS the intent anchor). The pattern defends a cross-panel visual-comparability contract: every category's FAILED tile is in the same slot, the legend's FAILED chip corresponds to that slot. Local-scope decision (one feature surface); LOW severity but worth pinning to pre-empt a "let's sort by failure count" cleanup that would silently breach the contract.

**2 existing ADR candidates STRENGTHENED**:

- **ADR-CANDIDATE-003** (read-collaborative GET — the trust model) — STRENGTHENED to **14-sidecar** support. The `/data-quality` route at `App.tsx:73` is mounted as a bare `<Route>` with NO `WithPermissionsProvider` (contrast `/lookup-tables` at `App.tsx:75-88` immediately below — same screen, three lines apart, deliberately different choice). The dashboard's UI route mount is the **first frontend-route-layer primary source** in the read-collaborative family (every prior surface anchored on a Java controller method). The `DataQualityContent.md:implicit_adrs.[1]` explicitly names ADR-CANDIDATE-003 as the design framing. The deliberate-decision evidence is unusually clean — the two adjacent route registrations (lines 73 and 75-88) are visible together; impossible to read the route registry without seeing the choice. NEW cross-link gap added: REFACTOR-617 — the access-control silence on every live DQ doc page joins the family of read-collaborative surfaces whose live docs do not surface the blast radius (REFACTOR-024 / -187 / -200 / -053 / -057).

- **ADR-CANDIDATE-091** (URL as source of truth for view state) — STRENGTHENED. The dashboard's filter panel adopts the same architectural commitment with a feature-local variation: the URL holds the FILTER selection (`DataQualityFilters.tsx:28-54` — bidirectional `useSearchParams` ↔ `formFiltersAtom` sync with `replace: true` history hygiene). This is the literal realisation of the ADR's own severity rationale ("reusable for any future shareable canvas e.g. Quality Dashboard"). The cross-pillar reach increases from one pillar (P-05 Lineage) to **two pillars** (+P-04 Quality Dashboard). NEW cross-link gap added: REFACTOR-603 — the same JSON.parse-no-try/catch crash that REFACTOR-286 surfaced on LineageGraph repeats on the dashboard URL parser, confirming the ADR's "Proposed action" needs a codified `parseUrlValue<T>(value, schema)` primitive rather than per-call-site discipline (per-call-site discipline has now failed independently on TWO surfaces).

**Wisdom-test reclassifications (10 — all GAP-shaped, sent to `refactoring-scopes.md`)**: line-48 status-color crash (REFACTOR-592 HIGH — the latent dashboard-blanking TypeError); LSN-020 Title-filter drift (REFACTOR-593 HIGH — `OWNERSHIP.TITLE_ID` bind under bare 'Title' label); Namespace-filter datasource-inheritance widening (REFACTOR-594 MEDIUM — `OR DATA_SOURCE.NAMESPACE_ID`); per-mount filter reset (REFACTOR-595 MEDIUM — operator-loss on navigate-via-tab); no error UI (REFACTOR-596 MEDIUM — failed fetch indistinguishable from empty catalog); autocomplete keystroke list-API burst (REFACTOR-597 MEDIUM — no debounce); autocomplete first-30-only (REFACTOR-598 MEDIUM — no pagination, no truncation indicator); no debounce / no Apply gate on dashboard refetch (REFACTOR-599 MEDIUM — 4-chip filter = 4 wasted backend fetches); the doc-drift / doc-gap cluster on `dashboard.md` (REFACTOR-600 MEDIUM — 9 facets consolidated: 3/6-status, Healthy/Warning/Error labels, Unknown casing, empty-state, per-category row, filter interaction, Title binding, namespace widening, access-control silence); category-row ordering alphabetical-not-severity (REFACTOR-601 MEDIUM); MultipleFilterItemAutocomplete stale-closure (REFACTOR-602 LOW); URL-sync JSON.parse no try/catch (REFACTOR-603 LOW); zero test coverage entire DQ subtree (REFACTOR-604 MEDIUM — 21 source / 0 test); 10-facet LOW polish cluster (REFACTOR-605 LOW — locale-dep ordering, dead `!data` guards, unused `getFieldFilterAtom`, whole-atom subscription, `capitalizeFirstLetter` empty-string, missing i18n, negative-count display, no `staleTime`, `toSorted`-outside-`useMemo`, present-only flatMap silent drop, swappable filterKey props).

Each failed ≥2 of the 3 wisdom-test questions — the absence/issue has no stated rationale and addressing it is refactoring within the existing structure (e.g. the LSN-020 Title drift is a label-fix + doc-fix within the existing SQL bind; the autocomplete debounce is additive in the existing component; the doc-drift cluster is one DOC-NNN tranche).

**Borderline findings considered and NOT promoted**: (a) the dashboard's single-fetch projection (`DataQualityContent.md:implicit_adrs.[0]` — one `GET /api/dataqatests/runs` for the whole dashboard rather than three per-ring endpoints) — STRUCTURAL but already encoded in the existing OpenAPI contract + the backend zip-three-queries-into-one shape; not a NEW ADR candidate, it is a property of the existing F-032 design. Recorded in the F-032 feature-flow detail, not surfaced as ADR. (b) The "category labels are opaque backend strings, sorted client-side — UI carries no category taxonomy" finding (`DataQualityContent.md:implicit_adrs.[2]`) — MEDIUM-confidence; the UI's renderer-agnostic stance is incidental rather than deliberate (no comment defends "do not bake categories client-side"); recorded as a property of the design but does not pass the wisdom test for a standalone ADR.

**Cross-batch alignment**: ADR-CANDIDATE-207 (NEW — two-store-system) + ADR-CANDIDATE-091 STRENGTHENED (URL as source of truth) + ADR-CANDIDATE-208 (NEW — enum-order tiles) + ADR-CANDIDATE-003 STRENGTHENED (read-collaborative GET — dashboard route as 14th surface) together describe **the full architectural shape of the standalone Quality Dashboard**: jotai for the filter store, URL for the persistence channel, enum-driven UI ordering for cross-panel comparability, and the read-collaborative posture for who-can-see. The four ADRs together are what a future maintainer would need to make any compatible change to the dashboard surface; without them the design reads as scattered choices.
