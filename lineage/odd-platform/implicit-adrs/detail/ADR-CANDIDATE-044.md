- **ADR-CANDIDATE-044** (NEW 2026-05-12C): The Notifications subsystem follows the **lazy-create-no-drop** pattern for Postgres replication artefacts — the replication slot and publication are created on first leader run if absent, but are NEVER dropped by the platform. Operator-cleanup is the stated policy
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar (`NotificationsProperties`) but the pattern is **2-sidecar triangulated** by ADR-CANDIDATE-028 (range-partition lifecycle — partitions are lazy-created at boot via `CREATE TABLE IF NOT EXISTS`, NEVER dropped, operator-cleanup expected); the cross-feature pattern elevates this to a codebase-wide invariant for Postgres-resident artefacts
  - **Surfaced by**:
    - `odd-platform__java__org_opendatadiscovery_oddplatform_notification_config__config-properties-class__NotificationsProperties.md:implicit_adrs.[4]` ("Replication-slot and publication are **created lazily on first leader run** if absent, but are **never dropped** by the platform — encoding 'operator owns cleanup' as the stated policy.     - Cross-reference: ADR-CANDIDATE-028 (range-partition lifecycle) — the partition manager follows the same shape (`CREATE TABLE IF NOT EXISTS` at boot, never DROP)
  - **Decision statement**: ODD's Postgres-resident artefacts (range partitions, replication slots, publications) follow a **lazy-create-no-drop** lifecycle pattern. Each subsystem checks for artefact existence on its scheduled or boot trigger (`SELECT EXISTS ... pg_replication_slots WHERE slot_name = ?` for notifications at `NotificationSubscriber.java:99-122`; `CREATE TABLE IF NOT EXISTS` for partitions at `PostgreSQLPartitionCreationJob`), and creates the artefact only when absent. Once created, the artefact persists indefinitely — the platform has no DROP path, no retention policy, no garbage collection. Operator-cleanup is the stated policy, captured in live docs (Notifications page WebFetched 2026-05-12: "ODD Platform doesn't clean up replication slot it has created"). The decision has three structural consequences: (a) bounded growth requires operator intervention — REFACTOR-085 (no partition DROP — silent monotonic growth of activity table) and REFACTOR-139 (replication-slot orphan risk on rename — Postgres retains WAL for unused slot, risking primary disk exhaustion) both capture the prices; (b) idempotent boot — the platform can be restarted, redeployed, or scaled without changing existing artefacts; (c) operator-namespace ownership — by not dropping, the platform avoids accidentally removing artefacts an operator manually created or renamed. The trade-off: simpler-and-safer-to-implement vs. operational burden on operators.
  - **Wisdom test**: PASS. The cross-feature consistency (partitions + replication slots + publications) is the intent anchor; the live-doc statement "doesn't clean up" is the explicit rationale at the operator-facing layer. Structural for every future Postgres-resident-artefact subsystem (e.g., a hypothetical materialised-view-refresh job, a feature-flag-table seed job) — they should reuse this pattern with the operator-cleanup-doc-warning as the price.
