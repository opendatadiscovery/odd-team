## What

Five issues on the Term create / edit dialog. The real file is `odd-platform-ui/src/components/Terms/TermSearch/TermForm/TermsForm.tsx` (the original draft cited a non-existent `Terms/TermsForm/TermsForm.tsx` path and wrong line numbers throughout - all corrected below). Under the user-facing verification sweep the cluster is far less severe than originally filed: the security framing of Defects 4-5 was wrong, Defect 3 is backend-netted, and Defect 1 defers to the already-corrected canonical XSS anchor PLT-023.

**Defect 1 - Term definition is rendered through the unsanitized shared Markdown path. DEFER to PLT-023 (this is surface 3 of that family).** `TermsForm.tsx:183` renders the definition editor (`<Markdown {...field} editor height={200} />`); on save the string round-trips through `TermServiceImpl.createTerm`/`updateTerm` verbatim (no `Jsoup.clean`, no allowlist, no length cap - verified 2026-06-10); the read side `TermDefinition.tsx:45` renders it via `Markdown.tsx` with `rehype-raw` active (the `@uiw` library default) and no `rehype-sanitize`. **PLT-023 is the canonical anchor and was corrected in this same sweep**: the obvious vectors (`<script>`, `<img onerror>`, `<a href="javascript:">`) are BLOCKED by React + react-markdown's `uriTransformer` (static-settled there); the residual vectors (`<iframe src=javascript:>`, SVG event attributes, and a residual `TermLink` href path — precise mechanism held pre-disclosure under GHSA-mf43-2636-9289 / CTRIB-020) are UNMEASURED and need a live browser drive. So this is a missing-defense-in-depth posture, not a confirmed stored XSS that "triggers for every viewer" (the original draft's claim - withdrawn). Do not duplicate the fix here; it lands at `Markdown.tsx` per PLT-023 and is **not a one-liner**.

**Defect 2 - Typing a novel namespace in the term dialog creates it under TERM_CREATE, bypassing NAMESPACE_CREATE. HOLDS (BE trace); observable only under non-default auth.** `TermsForm.tsx:161-167` renders `<NamespaceAutocomplete controllerProps={field} />` (a `freeSolo` autocomplete). Typing a name not in the list and submitting sends `namespaceName`; the backend `TermServiceImpl.createTerm` -> `namespaceService.getOrCreate(namespaceName)` -> `namespaceRepository.createByName(...)` with NO permission check (`NamespaceServiceImpl.java:37-40`). The only security rule on `POST /api/terms` is `TERM_CREATE` (`SecurityConstants.java:111`), so a holder of `TERM_CREATE` creates namespaces without `NAMESPACE_CREATE`. Note: under the default `auth.type=DISABLED` there is no RBAC at all (everything `permitAll`), so the "bypass" is only observable under OAUTH2/LDAP with policies configured - static trace consistent; not driven (needs a non-default-auth stack).

**Defect 3 - Client duplicate-name check is CREATE-only and size-capped, but the backend is authoritative.** `TermsForm.tsx:72-74` fetches `fetchTermsSearchResults({ page: 1, size: 1000 })`; `:84` gates the client check on `if (!term?.id)` (CREATE only); the check is a `.find` over the fetched terms (`:85-94`). So (a) catalogs with >1000 terms can skip the client warning, and (b) EDIT-mode renames never run it. **But this is a UX nicety, not a data bug:** `createTerm` rejects duplicates server-side with a 400 `BadUserRequestException` ("Term with name X in namespace Y already exists", `TermServiceImpl.java:107-112`), and the `term_name_namespace_unique` index (`V0_0_35:16`) catches EDIT-mode rename collisions as a 400 `USR003` via `ExceptionUtils` (`:73`). The only impact of the client gaps is a less-friendly server toast instead of an inline pre-submit message.

**Defect 4 - On backend reject the error surfaces as a GLOBAL toast (not the inline dialog Alert); the dispatch chain also has a dangling promise. FALSIFIED as "silent failure".** `TermsForm.tsx:100-111` does `dispatch(...).unwrap().then(...)` with no `.catch`. The original draft claimed this makes failures silent with no error message - that is wrong: `createTerm`/`updateTerm` run through `handleResponseAsyncThunk`, whose `catch` calls `showServerErrorToast(err)` for every rejected backend call (`handleResponseThunk.ts:34-40`; no `switchOffErrorMessage` set on these thunks). So the user DOES get a server-error toast. What actually holds (re-scoped, low): the dialog's inline `Alert` (`:122-147`) is wired only to the client-side duplicate `error` state, not to backend errors; and the `.unwrap().then()` with no `.catch` leaves an unhandled promise rejection in the console. The dialog staying open with the form intact is arguably correct (retry-friendly).

**Defect 5 - In CREATE mode `queryClient.invalidateQueries({queryKey: ['term', termId]})` is a no-op, not a cache-corrupter. Re-scoped to cosmetic.** `TermsForm.tsx:106-108` invalidates by route `termId`, which is `parseInt(undefined, 10) = NaN` in CREATE mode (`termsRoutes.ts:60`). `invalidateQueries` only marks MATCHING cached queries stale; no query has key `['term', NaN]`, so it matches nothing - it does NOT "accumulate dead entries" (the original draft's claim - withdrawn; `invalidateQueries` never creates cache entries). User impact is negligible: the success path immediately `navigate(termDetailsPath(response.id))` and the detail page's `useGetTermByID` fetches `['term', response.id]` fresh anyway (`lib/hooks/api/terms.ts:45-48`). The correct key to invalidate would be `['term', response.id]` (or the term list).

## User-facing impact

- WHO: an operator authoring a glossary term via the Add/Edit term dialog (Dictionary / term detail header).
- Defect 1: WHAT a later viewer of the term gets is governed by PLT-023 - raw HTML in the definition is parsed and rendered (no sanitizer), but the obvious script vectors are blocked by React + uriTransformer; the residual vectors are unmeasured. Static trace consistent; not driven (browser payload drive owed by PLT-023). `user_facing_verified: false`.
- Defect 2: WHAT happens when the operator types a brand-new namespace - it is created on submit. The UI DOES signal it (corrected): the dropdown shows "No result. Create new custom namespace \"X\"" (`AutocompleteSuggestion.tsx:23-27`), so the original "UI gives no signal" claim is false. The RBAC bypass (creating it without `NAMESPACE_CREATE`) is real in code but observable only under OAUTH2/LDAP + policies - static trace consistent; not driven.
- Defect 3: WHAT the operator gets on a duplicate name - an inline warning if the catalog is <=1000 terms and it is CREATE mode; otherwise a server-error toast from the backend 400. No duplicate term is ever persisted (BE + unique index, verified by BE trace). Net: cosmetic UX gap, not data loss.
- Defect 4: WHAT the operator gets on any backend reject - a global server-error toast (verified by FE trace: `handleResponseThunk.ts:38` -> `errorHandling.tsx:48-67`), the dialog stays open with the form intact, and an unhandled-rejection logs to the console. NOT a silent failure.
- Defect 5: WHAT the operator gets after creating a term - the new term's detail page, freshly fetched (the no-op invalidation has no visible effect because navigation triggers a fresh query). Cosmetic.

## Why it matters

The TermsForm is the primary glossary-authoring surface, so even small UX gaps recur on every create/edit. But the original CRITICAL grade rested on (a) a "confirmed stored-XSS that triggers for every viewer" and (b) an RBAC bypass "on documented public surfaces" - (a) is downgraded to PLT-023's medium missing-defense posture (obvious vectors blocked, residual unmeasured), and (b) is real but non-default-auth-only. Defects 3-5 substantially collapsed under FE/BE trace (BE-netted duplicate, toast-not-silent, no-op invalidate). The honest aggregate is **medium**: the load-bearing residue is the unsanitized render layer (owned by PLT-023) plus the TERM_CREATE -> namespace-create RBAC bypass; both need a live drive to confirm the user-facing effect, so `user_facing_verified` stays `false`.

## Suggested fix

- **Defect 1**: no separate fix - it lands at `Markdown.tsx` via **PLT-023** (surfaces 1-3 share that anchor; explicit `rehypeRaw` + `rehypeSanitize` ordering, not a one-liner). Optionally add a BE length cap on definitions in `TermServiceImpl`.
- **Defect 2**: have `NamespaceServiceImpl.getOrCreate` (or the term-create path) require `NAMESPACE_CREATE` before creating a novel namespace, or gate the autocomplete's "create new" affordance on the permission. Mirror the same pattern for tag-create (PLT-060).
- **Defect 3**: optional - keep the client pre-check as a convenience but rely on the BE 400 as the authority (it already is); if a friendlier message is wanted, surface the backend error in the inline `Alert` (see Defect 4) rather than growing the client-side fetch.
- **Defect 4**: add a `.catch` to the dispatch chain (`:100-111`) that routes the backend error into the dialog's `setError`/`Alert` (so the message is inline, not only a global toast) and clears the dangling rejection.
- **Defect 5**: invalidate `['term', response.id]` (CREATE) / the term list, instead of the route `termId`.
