## What

`application.yml:7` ships `spring.datasource.password=odd-platform-password` as the default DB password. An operator forgetting to override deploys with a public well-known credential.

Combined with `/actuator/env` exposure of the JDBC URL (PLT-078), deployments are one-operator-override-skip away from full PG compromise.

**LSN-001-pattern family**: silent insecure default, doc-only warning absent, no programmatic guardrail.

## User-facing impact

Verified-trace (code+config settled; no UI surface - this is a deployment/config defect). The shipped default is real: `application.yml:7` is `password: odd-platform-password` (url=`:5`, username=`:6`, password=`:7`). The composition with the actuator surface (PLT-078) holds end-to-end:

- The shipped default `auth.type: DISABLED` (`application.yml:34`) selects `DisabledAuthSecurityConfiguration`, whose filter chain is `anyExchange().permitAll()` (`DisabledAuthSecurityConfiguration.java:16`) - so on a default deployment `/actuator/env` is anonymously reachable. Even under LDAP/OAUTH2, `/actuator/**` is in `SecurityConstants.WHITELIST_PATHS` (`:96`) and permitAll'd by `AuthorizationCustomizer` (`:22-23`), so the actuator stays anonymous across all auth modes; only LOGIN_FORM narrows it (it permits `/actuator/health` only, `LoginFormSecurityConfiguration.java:50`).
- `management.endpoints.web.exposure.include` lists `env` and `endpoint.env.enabled: true` (`application.yml:226-239`), so `/actuator/env` is live.

One correction to the failure narrative: Spring Boot's default `/actuator/env` *sanitizes* keys matching `password`/`secret`/`key`/`token` (no `management.endpoint.env.show-values` override exists in the repo - grep is zero), so the password value renders as `******`, NOT in clear. What leaks is the JDBC URL (`spring.datasource.url`, unsanitized) - host/port/db. The attack the draft describes does not need the password to leak: it leaks the URL, and the *password is well-known* (this issue's whole point), so an attacker tries `odd-platform-password` against the discovered Postgres. The chain is intact; the only edit is that the password is guessed-from-default, not scraped-from-env.

## Why it matters

Sequence of failure: (a) operator runs trylocally docker-compose, sees it work; (b) operator follows the same compose file structure to deploy to a more-public environment; (c) operator overrides `host`, `port`, `username`, but not `password`; (d) the platform connects to the operator's Postgres using the literal `odd-platform-password` (which the operator has set on Postgres because they followed the trylocally guide); (e) attacker scrapes `/actuator/env`, learns JDBC URL + LDAP / OAuth schema, attempts the well-known password, gains DB shell.

Five-step chain, zero mistakes by the operator beyond "I forgot to set a password". Every step is documented; the trap is the COMPOSITION.

## Suggested fix

**Thread A - Drop the shipped default.**

```yaml
# application.yml - before
spring:
  datasource:
    password: odd-platform-password

# application.yml - after
spring:
  datasource:
    password: ${SPRING_DATASOURCE_PASSWORD}    # operator-required; no default
```

Spring will fail-fast at startup if `SPRING_DATASOURCE_PASSWORD` is unset. The trylocally compose file (`docker-compose.yaml` and friends) needs to set `SPRING_DATASOURCE_PASSWORD: odd-platform-password` explicitly so trylocally continues to work.

**Thread B - Startup self-check (defence-in-depth).**

```java
@PostConstruct
void warnIfWellKnownDbPassword() {
    if ("odd-platform-password".equals(dataSourceProperties.getPassword())) {
        log.warn("spring.datasource.password is set to the trylocally well-known default 'odd-platform-password'. Override before production deployment.");
    }
}
```

Or fail-fast if the deployment is running in a non-trylocally context (e.g., presence of `PROD=true` env var). Less invasive: warn only.

**Thread C - Audit other shipped credential defaults.**

`spring.custom-datasource.password` (the custom-datasource block) - checked 2026-06-10: the entire `custom-datasource` block is *commented out* in `application.yml` (`:8-11`), so it ships no credential default. No fix needed there; flagged only so a future uncomment does not reintroduce the pattern.

Any other shipped credential defaults: ingestion-filter API key, S2S key, etc. - not audited in this issue; track separately if a sweep is run.
