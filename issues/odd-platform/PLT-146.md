## Two distinct defects in the Reference Data (Lookup Tables) write API, same subsystem.

### (a) Name-normalisation collision -> raw 500 SYS001 instead of 409

`buildTableName` lossily normalises a lookup-table name (`toLowerCase`, space->underscore), and
`ReferenceDataServiceImpl.createLookupTable` does **no uniqueness pre-check** before issuing the physical
`CREATE TABLE`. Two distinct display names that normalise to the same physical name in one namespace
(e.g. `My Table` and `my_table`) therefore fail at the DDL layer with a generic **500 `SYS001`
"Internal Server Error"** instead of an actionable **409 / "lookup table already exists in namespace"**.

Reproduced live (IT-050 UC-007): second create normalising to an existing physical name -> 500 SYS001.

Fix: add a normalised-name uniqueness pre-check in `createLookupTable` and map the collision to a 409 with a
clear message.

### (b) `PATCH /referencedata/table/{lookupTableId}/column/{columnId}` discards the path table-id

`ReferenceDataController.updateLookupTableField` (odd-platform-api/.../controller/ReferenceDataController.java:133-139)
calls `referenceDataService.updateLookupTableField(columnId, item)` - it passes **only `columnId`** and drops
the path `lookupTableId`. So a caller addressing table **A**'s column-id that actually belongs to table **B**
mutates **B**'s schema. The READ path (`getLookupTableField`) correctly enforces the column-belongs-to-table
linkage; the WRITE path is asymmetric and unguarded.

Reproduced live (IT-050 UC-010): `PATCH /table/{A}/column/{col_of_B}` -> 200 and table B's physical column was
renamed. (Verified at the contract level: the controller signature discards the path table-id.)

Fix: mirror the read-side belongs-to-table guard on the write path - reject (400/404) when `columnId` does not
belong to `lookupTableId`.

## User-facing impact

Both defects are verified by BE trace AND driven live in the workspace (IT-050, F-026 UC-007/UC-010 - LSN-029 characterization pins, GREEN 2026-06-10):

- **(a) collision -> 500:** Verified by BE trace 2026-06-10 - `buildTableName` (`ReferenceDataServiceImpl.java:191-193`) lossily normalises (`name.toLowerCase().replace(" ", "_")`, prefixed `n_<namespaceId>__`), and `createLookupTable` (`:73-84`) issues the physical create with no uniqueness pre-check. Driven in IT-050 UC-007 (`e2e/specs/lookup-tables-rdm.spec.ts:117-141`): a second create normalising to an existing physical name returns **500 with code `SYS001`** (asserted), no actionable message. User-facing: a cataloguer creating "My Table" after "my_table" already exists in the same namespace gets a generic Internal Server Error instead of "already exists" - they cannot tell it is a name collision. (The prefix means the collision is per-namespace, matching the draft's qualifier.)
- **(b) cross-table PATCH:** Verified by BE trace 2026-06-10 - `ReferenceDataController.updateLookupTableField` (`ReferenceDataController.java:131-141`) takes `lookupTableId` AND `columnId` but calls `referenceDataService.updateLookupTableField(columnId, item)` (`:139`), dropping the path table-id; the service (`ReferenceDataServiceImpl.java:127-130`) fetches by `columnId` alone with no table cross-check, whereas the READ path `getLookupTableField` (`:58-66`) DOES enforce `field.tablesPojo().getId().equals(lookupTableId)` and throws `BadUserRequestException` (400) on mismatch. Driven in IT-050 UC-010 (`:144-173`): `PATCH /table/{A}/column/{col_of_B}` returns **200 and renames table B's physical column** ("bcol_renamed"), while the sibling READ correctly 400s. User-facing: a caller editing table A's column can silently rename a column on a DIFFERENT table B's physical relation - a cross-tenant/cross-table write through an asymmetric guard.
- Auth mode: the Reference Data write API is gated by the relevant management permissions (any auth mode granting them; DISABLED's synthetic admin holds all). The defects are in the write contract itself, independent of auth mode.
