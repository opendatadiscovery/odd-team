## What

When the platform is started with `auth.type=DISABLED` (a shipped, supported authentication mode), **every** HTTP exchange is permitted with no credential - including the RBAC mutation endpoints. That means any unauthenticated caller who can reach the platform can `POST` a new policy granting `MANAGEMENT`/`ALL` permissions and a new role bound to it, i.e. grant themselves (or any owner) full administrative control. There is no separate gate keeping the security-administration surface behind even a nominal check when auth is disabled; "disabled auth" is implemented as "permit everything," and that includes writing the authorization model itself.

## Where

**`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/config/DisabledAuthSecurityConfiguration.java:16`:**
```java
@Configuration
@ConditionalOnProperty(value = "auth.type", havingValue = "DISABLED")
public class DisabledAuthSecurityConfiguration {
    @Bean
    public SecurityWebFilterChain securityWebFilterChainDisabled(final ServerHttpSecurity http) {
        return http
            .csrf(ServerHttpSecurity.CsrfSpec::disable)
            .authorizeExchange(authorizeExchangeSpec -> authorizeExchangeSpec.anyExchange().permitAll())  // line 16
            .build();
    }
}
```

`anyExchange().permitAll()` blankets the entire API, so the Role/Policy create endpoints (`RoleServiceImpl.create` / `PolicyServiceImpl.create`) are reachable with no authentication and no authorization check.

**This is a DISABLED-specific divergence, not a universal gap - which is exactly why it bites.** Under the non-DISABLED auth configs these endpoints ARE gated: `SecurityConstants.SECURITY_RULES` (`SecurityConstants.java:163-164,169`) declares `POST /api/policies -> POLICY_CREATE` and `POST /api/roles -> ROLE_CREATE`, and `AuthorizationCustomizer` (`AuthorizationCustomizer.java:24-30`) installs those rules plus a closing `.pathMatchers("/**").authenticated()`. But `AuthorizationCustomizer` is wired ONLY in `OAuthSecurityConfiguration` and `LDAPSecurityConfiguration` (verified: those are its only two usages). `DisabledAuthSecurityConfiguration` does NOT use it - so under DISABLED the entire `SECURITY_RULES` table (including `POLICY_CREATE`/`ROLE_CREATE`) is inert, and there is no `.authenticated()` fallthrough. Independently confirmed by IT-009's own scope note ("DISABLED does `anyExchange().permitAll()`... SECURITY_RULES are inert").

**And the create call actually succeeds** (it does not merely reach a handler that then errors): `RoleServiceImpl.create` (`:51-61`) and `PolicyServiceImpl.create` (`:62-69`) do NOT call `getCurrentUser()` or otherwise depend on the security context (unlike the owner-association writes in PLT-148 that 500 under DISABLED) - they go straight `mapToPojo -> repository.create`. So an anonymous POST under DISABLED writes a real policy + role row. The takeover primitive is complete, not partial.

## User-facing impact

**Verified-trace** (code-settled; reachability runtime-anchored by IT-009), auth mode: `auth.type=DISABLED`. The full chain is established from source: (1) only `DisabledAuthSecurityConfiguration` is active under DISABLED (`@ConditionalOnProperty havingValue=DISABLED`), and it permits all exchanges with no `AuthorizationCustomizer` (`:13-18`); (2) the `POLICY_CREATE`/`ROLE_CREATE` rules that would gate these endpoints exist but are wired only into the OAuth/LDAP configs, so they are inert here (`SecurityConstants.java:163-169`, `AuthorizationCustomizer.java`); (3) `PolicyServiceImpl.create`/`RoleServiceImpl.create` have no security-context dependency, so the write succeeds. IT-009 (validates ADR-0074, in the passing feature-complete suite) drives the *authentication-boundary* half live - a non-whitelisted endpoint is anonymously reachable under DISABLED and rejected under LOGIN_FORM - which is the reachability precondition for this takeover.

Operator-visible consequence: anyone who can reach a DISABLED-mode instance on the network can `POST /api/policies` (a `MANAGEMENT`/`ALL` policy) then `POST /api/roles` (a role bound to it) and attach it to an owner - a silent, full administrative-control takeover, with no credential and no audit trail. Remaining check to promote to fully-driven: a single live `POST /api/policies` + `POST /api/roles` under DISABLED asserting `200` + the rows written (the authentication-reachability half is already driven by IT-009; the create-succeeds half follows deterministically from the code above).

## Why it matters

This is a **security** issue: under DISABLED mode the RBAC-write surface is anonymously reachable, which is a full-takeover primitive (mint a `MANAGEMENT`/`ALL` policy + role, attach it to an owner). The failure is silent - the request simply succeeds. Operators reasonably reach for `auth.type=DISABLED` in evaluation, demo, and internal-network deployments, and the existing guidance documents *other* DISABLED-mode exposures but not this one, so an operator who has accepted "read access is open in DISABLED mode" has not been told that the *authorization model itself is writable* by anyone. High severity: anonymous control over the permission system is the worst case for an access-control surface, and the mode that exposes it is one operators deliberately enable.

## Suggested fix

The root cause is intentional (DISABLED == permit-all), so the remediation is two-sided:

1. **Code-side (preferred):** even under `auth.type=DISABLED`, gate the RBAC-write surface (policy/role create/update/delete) so it is not anonymously mutable - e.g. require the operation to originate from the synthetic admin identity rather than blanket-permitting `anyExchange()` for the security-administration paths. At minimum, the management/security endpoints should not inherit `permitAll()`.
2. **Doc-side (caveat):** because the maintainers may choose to keep DISABLED as a deliberate "no security at all" mode, ship an explicit caveat on the disabled-authentication documentation stating that **the RBAC model is anonymously writable under DISABLED - do not expose a DISABLED-mode instance on any reachable network.** The auth-mode *reachability* boundary that this exploit rides on is pinned by **IT-009** (DISABLED open vs LOGIN_FORM authenticated), so the caveat can be tied to a green test; note IT-009 pins the authentication boundary, not the RBAC-write step specifically (see the remaining-check in User-facing impact).

Open to alternatives on whether the fix is a code gate, a documented caveat, or both - but the current "no warning + anonymous RBAC write" state should not stand.
