## Description

Two operator caveats on the S2S X-API-Key authentication flow. The page already accurately describes the global ADMIN scope (per Mode B verification WebFetched 2026-05-27); these caveats live inside that scope.

**Caveat 1 — ADMIN username collision (F-088a).** `S2sAuthenticationFilter.java:31-34` builds the synthetic principal as `User.withUsername("ADMIN").password("").roles("ADMIN").build()` — literal uppercase `ADMIN`. The repository at `ReactiveUserOwnerMappingRepositoryImpl.java:116-127` uses case-sensitive `eq` (not `equalsIgnoreCase`). An operator who has named a real LOGIN_FORM or LDAP user `ADMIN` (uppercase) sees the S2S caller **inherit that user's `USER_OWNER_MAPPING` row** — cross-mode bleed via username + provider=null. Activity-feed mutations attributed to the X-API-Key surface look like they came from the operator-named user; any Owner association the operator created on user-`ADMIN` becomes the S2S agent's Owner.

**Caveat 2 — `auth.s2s.enabled=true` silently inert under DISABLED (F-088b).** `DisabledAuthSecurityConfiguration.java:13-18` does NOT read `auth.s2s.enabled`. An operator setting `auth.type=DISABLED + auth.s2s.enabled=true` gets the property accepted but no filter wired. Combined `DISABLED + S2S enabled` is silently identical to `DISABLED` alone. No boot warning, no doc warning today. An operator migrating from DISABLED to a real auth mode who pre-configures `auth.s2s.enabled=true` expecting it to take effect when they flip `auth.type` gets neither a confirmation nor a warning that S2S is dormant under DISABLED.

## Acceptance Criteria

- [ ] The S2S page documents the **ADMIN username collision** explicitly with a recommendation: do not name operator-managed `LOGIN_FORM` / `LDAP` users with the case-sensitive literal `ADMIN`. Cross-link to the operator-side mitigation (rename the user, or wait for the upstream code-side fix that renames the synthetic principal — see below).
- [ ] The S2S page documents the **DISABLED-mode dormancy** of `auth.s2s.enabled`. Frame it as a configuration-stage warning: the property is accepted under DISABLED but has no effect until `auth.type` is flipped to `LOGIN_FORM` / `OAUTH2` / `LDAP`. Operators pre-configuring for a planned auth migration get the property in their YAML; document that it's inert until the migration completes.
