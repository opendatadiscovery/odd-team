    - **The OpenAPI contract** (per sidecar primary source — `components.yaml:64-70`): the `IntegrationPreview` schema declares `installed` as a REQUIRED boolean field with the implicit description "whether the integration is installed". The contract claim is a meaningful state field; operators reading the spec reasonably expect `installed: true` for some integrations (e.g., the ones for which a corresponding datasource has been registered) and `installed: false` for others. The runtime delivers a constant; the contract is structurally violated in spirit even though the type-level schema is satisfied.
    - **The UI consequence** (per sidecar evidence — `IntegrationPreviewItem.tsx:44-51`): the UI conditionally renders an "Integrated" badge gated on `{installed && (...)}`. Per the hardcoded constant, the gate is always false; the badge is dead UI. The component file remains in the codebase, the conditional remains in the JSX, the badge styling remains in the design system — all collectively dead. A future maintainer reading the UI sees "the system has an integrated/non-integrated distinction" and may design new features around it; the system does not.
    - **The semantic intent (per sidecar bugs_limitations_corner_cases[0])**: the field appears to have been designed for "an integration is 'installed' when a datasource of matching id/family exists". This is a reasonable semantic — the platform's Datasource ↔ Integration relationship is family-by-type (a PostgreSQL integration is "installed" once any postgres datasource exists). But: (a) no detection code exists — `IntegrationServiceImpl.java:20-23` returns the wizard registry directly; (b) `grep installed` in `<odd-platform-repo>/odd-platform-api/src/main` returns ONLY the two mapper lines; (c) no consumer code, no detection helper, no relationship-resolution. The field is structurally dead, not just behaviourally dead.
    - **The contract violation framing** (alternative reading): per the principle of least astonishment, a REQUIRED boolean field that is always `false` violates the contract's implicit promise. Type-system-wise the contract is satisfied (`installed: false` is a valid `boolean`); semantically the contract is broken (a field that is always the same constant carries zero information; the contract claims an information-bearing field). The OpenAPI spec is the lying half; the runtime is the honest half (it always returns the same value).
