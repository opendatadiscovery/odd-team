## Description

When the platform returns the Query Examples linked to a glossary **term**, the list mapper hard-codes the pagination flag to `false`. `QueryExampleMapper.mapListToQueryExampleList` (`QueryExampleMapper.java:70-75`) builds its `PageInfo` as:

```java
public QueryExampleList mapListToQueryExampleList(
    final List<QueryExampleDto> queryExampleDtos) {
    return new QueryExampleList()
        .items(mapToQueryExampleList(queryExampleDtos))
        .pageInfo(new PageInfo().total((long) queryExampleDtos.size()).hasNext(false));
}
```

`total` is set to `queryExampleDtos.size()` (the size of the in-hand slice) and `hasNext` is the literal `false`. Contrast the genuinely-paginated mappers in the same class — `mapToRefPage` (`:57-61`) and `mapPageToQueryExample` (`:63-68`) — which both read `page.getTotal()` and `page.isHasNext()` from a real `Page`. So the **by-term query-example list always presents as a single, complete page**: there is no "more available" signal and the total reflects only the returned slice, never the true count.

This misleads operators (and any API consumer) reading the query examples linked to a popular term: if the list is sliced server-side, the response declares itself complete (`hasNext: false`) while silently omitting the rest, and the total under-reports. The query-examples page documents the *Linked Terms badge* understating (`query-examples.md:75`) and the per-entity/per-term lookup endpoints generally (`:46`), but nothing documents that the **by-term query-example list itself carries no pagination** — it is hard-`false`. DOC-232 / DOC-233 cover **other** paging surfaces on this feature; the by-term list is untracked.
