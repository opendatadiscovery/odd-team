## What

When the platform runs with `auth.type=DISABLED` (the bundled out-of-the-box default), the top-right user cluster in the toolbar renders the literal username **`admin`** to every anonymous network caller - with no banner, badge, or warning that authentication is switched off. The backend serves a synthetic owner named `admin` carrying the **entire** permission set, so the chrome presents an unauthenticated viewer as a fully-privileged admin. Anyone who can reach the URL sees a UI that looks like a logged-in administrator's, and a screenshot of that UI is indistinguishable from a genuinely-authenticated admin session.

## Where

The toolbar renders whatever identity the backend returns, unconditionally - `odd-platform-ui/src/components/shared/elements/AppToolbar/AppToolbar.tsx:74`:

```tsx
<S.UserName>{owner?.name ?? identity?.username}</S.UserName>
```

Under DISABLED, `whoami` short-circuits to a synthetic owner whose username is `admin` and whose permissions are the full enum - `odd-platform-api/.../controller/IdentityController.java:30-33`:

```java
private AssociatedOwner dummyOwner() {
    return new AssociatedOwner().identity(
        new Identity().username("admin").permissions((Arrays.asList(Permission.values()))));
}
```

(`whoami`, same file lines 24-27, does `.switchIfEmpty(Mono.just(new ResponseEntity<>(dummyOwner(), HttpStatus.OK)))` - so the dummy owner is returned for the credential-less DISABLED case.) There is no UI element anywhere in `AppToolbar.tsx` that keys off the auth mode to surface "authentication is disabled".

## Why it matters

This is the UI symptom of an already-known backend posture: under `auth.type=DISABLED` every request is `permitAll` and is served as the all-permissions `admin`. The danger here is specifically the **deception**: the chrome gives an operator (or anyone glancing at a screen/screenshot) zero signal that the auth wall is down. An admin who briefly stands up a DISABLED instance "just to try it" and exposes it on a network has a UI that looks fully locked-down-and-logged-in, masking that it is wide open to any anonymous caller. Medium severity because the underlying wide-open posture is the documented behaviour of DISABLED (and tracked elsewhere); the novel gap this issue raises is purely that the UI fails to warn.

## Suggested fix

Render a persistent, unmissable auth-disabled banner (e.g. a top ribbon: "Authentication is disabled - every visitor has full admin access") whenever the platform is in DISABLED mode, and/or visually mark the synthetic `admin` identity as a system placeholder rather than a real user. The mode is already discoverable client-side (the `whoami` response is the all-permissions `admin`); a dedicated auth-mode/`is-auth-disabled` signal on the identity payload would let the UI render the banner deterministically. Open to alternatives on the exact treatment.
