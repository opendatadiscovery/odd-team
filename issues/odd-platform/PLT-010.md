## What

When `datacollaboration.enabled=false` (the default), the **Discussions** tab on every data-entity detail page is **still rendered and clickable** - only the API routes return `404 Not Found`. The Discussions tab is gated only on the entity's status (`isStatusDeleted`), not on the data-collaboration feature flag. An operator who has not configured Data Collaboration sees a tab that loads a component that fails to fetch its data; the user-visible result is a broken or empty Discussions surface on every catalog page.

**The fix is trivial because the feature-flag plumbing already exists - it is just not applied to this one tab.** The platform already exposes the active-feature set to the UI (`GET /api/features` -> `FeatureList`, backed by `FeatureResolverImpl`), the UI already loads it into redux (`fetchActiveFeatures` thunk -> `getActiveFeatures` selector), and there is already a `WithFeature` component plus a `Feature.DATA_COLLABORATION` enum value. The **Share** button in the very same entity-detail surface already gates on it (`DataEntityDetailsHeader.tsx:132-144`, `<WithFeature featureName={Feature.DATA_COLLABORATION}>`). Only the Discussions **tab** (and its route) was never wrapped. So this is a one-line omission, not a missing capability - the original draft's framing ("the UI does not consult the flag", "add a flag to the bootstrap response") was wrong on mechanism and is corrected below.

## Where

Tab definition - `odd-platform-ui/src/components/DataEntityDetails/DataEntityDetailsTabs/DataEntityDetailsTabs.tsx:96-99`:

```tsx
{
  name: t('Discussions'),
  link: dataEntityDetailsPath(dataEntityId, 'discussions'),
  hidden: isStatusDeleted,        // <-- only hidden for deleted entities; no feature-flag check
},
```

Route definition - `odd-platform-ui/src/components/DataEntityDetails/DataEntityDetailsRoutes/DataEntityDetailsRoutes.tsx:106-117`:

```tsx
<Route
  path='discussions/*'
  element={
    <RestrictedRoute
      isAllowedTo={!isStatusDeleted}     // <-- only restricted for deleted entities
      redirectTo='../overview'
      component={DataCollaboration}
    />
  }
>
  <Route path=':messageId' />
</Route>
```

The feature-flag mechanism that the tab SHOULD use (and that the Share button already uses):

```tsx
// DataEntityDetailsHeader.tsx:132-144 - the Share button in the same surface already gates correctly
<WithFeature featureName={Feature.DATA_COLLABORATION}>
  <CreateMessageForm ... btnCreateEl={<Button text={t('Share')} .../>} />
</WithFeature>
// WithFeature.tsx: const activeFeatures = useAppSelector(getActiveFeatures);
//                  isFeatureEnabled = activeFeatures.includes(featureName);
```

Backend (correct, for contrast) - the per-entity messaging controllers are gated by `DataCollaborationFeatureCondition` (`@Conditional`, reads `datacollaboration.enabled`, default `false`), so `/api/dataentities/{id}/messages`, `/api/datacollaboration/...` return `404 Not Found` when disabled. The same flag is also surfaced to the UI: `FeatureResolverImpl` (`odd-platform-api/.../service/feature/FeatureResolverImpl.java:22-23`) adds `Feature.DATA_COLLABORATION` to the active-feature list iff `datacollaboration.enabled=true`, served by `FeatureController.getActiveFeatures`. The UI already consumes it everywhere except this tab.

## User-facing impact

Confirmed by tracing both ends 2026-06-10. On a default deployment (`datacollaboration.enabled=false`) the **Discussions** tab renders on every data-entity detail page (`DataEntityDetailsTabs.tsx:96-99`, gated only on `isStatusDeleted`). Clicking it routes to `DataCollaboration`, whose data fetch hits a controller that returns `404` (the controller is `@Conditional` on `datacollaboration.enabled`). The operator sees a tab that produces no content rather than a feature they could enable. Impact is cosmetic/first-launch-UX (low): no security or data-integrity consequence, and the API is correctly gated. The asymmetry is operator-visible because the sibling **Share** button on the same page IS correctly hidden via `WithFeature` - so a disabled deployment shows "no Share button, but a dead Discussions tab," which reads as a bug rather than a turned-off feature.

## Why it matters

- **First-launch experience is broken by default.** A fresh ODD Platform deployment ships with `datacollaboration.enabled=false`. Every operator opening any catalog entity for the first time clicks through the entity tabs to learn the surface - the Discussions tab loads, the network call returns 404, and depending on the loading-state handling in `DataCollaboration.tsx` the user sees either an infinite spinner, an empty state, or an error banner. None of those communicates "this is a feature you can turn on" - they all communicate "this is broken".
- **Operators planning to disable the feature have no clean rollback.** If a team enables Data Collaboration, gathers some discussions, then later sets `datacollaboration.enabled=false` (e.g., to migrate Slack workspaces), the Discussions tab on every entity still appears in the UI but cannot fetch the (still-stored) message history. There is no "feature disabled" state.
- **Inconsistent with how other conditional features behave on the platform.** The pattern elsewhere (e.g., the `Test reports` tab is hidden if the entity is not a dataset or has no test runs; the `Linked entities` tab is hidden if `!dataEntityDetails?.hasChildren`) is to hide a tab when its content would be empty or unavailable. Discussions does not follow this pattern.
- **Severity is low** because the API itself is correctly gated (no security or data-integrity issue) and the workaround for operators is "ignore the broken tab". But the first-launch UX is real.

## Suggested fix

The feature flag is **already exposed to the UI** (`getActiveFeatures` / `WithFeature` / `Feature.DATA_COLLABORATION`); no new backend endpoint is needed. Two UX options - both small:

**Option A - gate the tab on the existing flag (recommended; invisible-when-off).** Read the active features in `DataEntityDetailsTabs.tsx` and add the same condition the Share button already uses:

```tsx
// DataEntityDetailsTabs.tsx
const activeFeatures = useAppSelector(getActiveFeatures);
const isDataCollaborationEnabled = activeFeatures.includes(Feature.DATA_COLLABORATION);
// ...
{
  name: t('Discussions'),
  link: dataEntityDetailsPath(dataEntityId, 'discussions'),
  hidden: isStatusDeleted || !isDataCollaborationEnabled,
},
```

This is the same shape as `hidden: !isDataset` and other content-aware conditionals already in the file. The route in `DataEntityDetailsRoutes.tsx` should mirror the guard (gate the `discussions/*` `RestrictedRoute` on the flag too) so a deep-link to `/discussions` redirects instead of mounting a component whose fetch 404s.

**Option B - render a "feature disabled" placeholder inside the tab.** Keep the tab visible (it advertises the feature's existence to operators evaluating the platform), but render a lightweight "Data Collaboration is not enabled. Ask your operator to set `datacollaboration.enabled=true`. See [docs link]." panel in `DataCollaboration.tsx` when the feature is off. The placeholder doubles as feature discovery for evaluators.

Pick based on UX intent - Option A is invisible-when-off (consistent with the rest of the tab pattern and with the Share button on the same page); Option B is discovery-friendly but accepts the broken-tab anti-pattern in exchange.

## How discovered

Surfaced during implementation of DOC-091 (Author Data Collaboration on Features.md) on 2026-05-03. The DOC-091 implementer was verifying the user-facing tab name (`'Discussions'`) for the Features.md showcase content and noticed the route's only guard was `isStatusDeleted`, with no `datacollaboration.enabled` check anywhere in the UI tree.

**User-facing re-verification (2026-06-10).** Re-traced both ends to falsify the original framing. The tab-visibility defect HOLDS (`DataEntityDetailsTabs.tsx:96-99` is gated only on `isStatusDeleted`). But the original draft's claim that "the UI does not gate... on the data-collaboration feature flag" / "add a global boolean to the bootstrap response" was wrong on mechanism: the flag is already exposed (`FeatureController.getActiveFeatures` <- `FeatureResolverImpl:22-23`), already in redux (`getActiveFeatures`), already consumed by `WithFeature`, and the Share button on the SAME page already gates on `Feature.DATA_COLLABORATION` (`DataEntityDetailsHeader.tsx:132-144`). Rewritten to the verified truth: the defect is a one-line omission (the tab + route were never wrapped with the existing flag), severity confirmed low, suggested fix corrected to use the existing plumbing rather than build new backend.

**Canonical for the Discussions-tab defect.** PLT-032 Defect 1 (found 2026-05-27) restates this same tab-visibility defect and is therefore a duplicate of this item; PLT-010 is the earlier, single-claim canonical issue. PLT-032's distinct Thread.tsx silent-navigation finding (its Defect 2) is unrelated and stays on PLT-032.

The doc-side handling: DOC-091's Features.md section documents the API-level behavior accurately ("when `datacollaboration.enabled=false`, the per-entity messaging routes return `404 Not Found`") and adds a brief operator-facing note that the Discussions tab is currently shown regardless of the flag, with a pointer back to this issue draft for the upstream fix. No doc-side claim presupposes the tab is hidden when disabled - so a future platform fix that hides the tab won't invalidate the doc.
