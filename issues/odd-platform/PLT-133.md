## What

`TagServiceImpl.delete` is doubly asymmetric and leaves debris. It soft-deletes the tag row but hard-deletes only `tag_to_term` and `tag_to_data_entity` (via `Flux.zip`); `tag_to_dataset_field` is **never touched** (`deleteDatasetFieldRelations(long)` exists but is not called) - so a tag attached to dataset fields leaves orphan `tag_to_dataset_field` rows pointing at the soft-deleted tag id, persistent forever (no reaper). Separately, the delete refreshes only the **term-side** FTS vector, not the data-entity-side `search_entrypoint.tag_vector` (update refreshes all three) - and the one term-side refresh it does run executes **after** the `tag_to_term` rows are already deleted, so its discovery CTE finds nothing and re-indexes zero terms (a no-op). The deleted tag name therefore stays searchable on both the entity and term surfaces until an unrelated write happens to refresh each row.

This is **net_new** - distinct from **PLT-044** (which references `deleteDatasetFieldRelations` on the *ingestion-stats* destructive replace path, a different code path and failure mode). This is the directory-CRUD `deleteTag` cascade omission + FTS staleness.

## User-facing impact

Static-trace-verified end-to-end against source HEAD (the delete cascade, the un-called `deleteDatasetFieldRelations`, the term-side FTS refresh's discovery CTE, and the update-path's three-vector refresh were all read directly); the two probes are defined but not yet run. No auth-mode dependency - tag delete/search behave the same under every auth mode.

- **Orphan `tag_to_dataset_field` rows - confirmed.** `TagServiceImpl.delete` (L57-70) hard-deletes only `tag_to_term` + `tag_to_data_entity` via `Flux.zip` (L64-65); `deleteDatasetFieldRelations(long)` exists at `ReactiveTagRepositoryImpl:299-306` but is **not called** from delete (its only callers are `DatasetFieldServiceImpl` and `ExternalTagIngestionRequestProcessor`). So a tag attached to dataset fields leaves orphan rows pointing at the soft-deleted tag id, persistent forever (no reaper).
- **Deleted tag name stays searchable - confirmed on both surfaces.** (a) The entity-side vector is never refreshed on delete: `delete` calls only `reactiveTermSearchEntrypointRepository.updateChangedTagVectors` (L68), never the data-entity-side `reactiveSearchEntrypointRepository.updateChangedTagVectors` (`ReactiveSearchEntrypointRepositoryImpl:319`), so `search_entrypoint.tag_vector` keeps the deleted name until an unrelated write touches each entity. (b) The one term-side refresh it does run is a **no-op**: `ReactiveTermSearchEntrypointRepositoryImpl.updateChangedTagVectors` (L136) discovers affected terms via a CTE over `TAG_TO_TERM` (L141-144 `select TERM_ID from TAG_TO_TERM where TAG_ID = tagId`), but `delete` already removed those `tag_to_term` rows at L64 - so the CTE finds zero terms and re-indexes nothing. A global full-text search for the deleted tag name still surfaces the previously-tagged entities AND terms for an unbounded per-row window.
- User-visible consequence: an operator who deletes a tag to retract a mistakenly-applied label (e.g. `pii`) finds the name still searchable across both entity and term search - undermining the point of the delete.

Remaining check before a definitive runtime claim: run P-032 (assert orphan `tag_to_dataset_field` rows remain after delete) and P-033 (assert the deleted tag name still matches in entity + term FTS immediately after delete).

## Impact

After a delete: (1) orphan `tag_to_dataset_field` rows accumulate silently, consuming space and risking confusion if the soft-deleted tag id is ever reused; (2) a global full-text search for the deleted tag name still surfaces previously-tagged data entities AND terms - the index is stale for an unbounded per-entity window. An operator who deletes a tag to retract a mistakenly-applied `pii` label finds the name still searchable, undermining the point of the delete.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: call `deleteDatasetFieldRelations(tagId)` (`ReactiveTagRepositoryImpl.java:299-306`) inside `TagServiceImpl.delete`'s `Flux.zip`; compute affected term ids **before** the relation delete and refresh all three search vectors symmetric with update. P-032 + P-033 pin. Distinct from PLT-044 (ingestion-stats replace path).
