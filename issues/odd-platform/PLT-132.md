## What

`OwnerServiceImpl.delete` runs a cascade-block over three referencing relations (`termOwnership.existsByOwner` + `ownership.existsByOwner` + `userOwnerMapping.isOwnerAssociated`) and raises HTTP 400 USR004 if any is live - but the **fourth** relation, `owner_association_request`, is **not** checked. Its FK to `owner(id)` has no `ON DELETE` clause, and because Owner uses soft-delete the FK is never consulted. So a PENDING/APPROVED association request for the deleted Owner persists as an **orphan pointing into soft-deleted space**, and the next `GET /api/owner_association_request` returns it. Approving such an orphan creates a `USER_OWNER_MAPPING` pointing at a soft-deleted Owner (no liveness cross-check on the approve path).

This is **net_new** - not in any existing PLT. (PLT-087 is the *DataSource*-side orphan TOKEN; this is the Owner-side `owner_association_request` orphan.)

## Impact

(1) After deleting an Owner, the Associations tab still shows a request for it; if the name was re-used (a fresh Owner with a new id), the orphan request is not re-linked and points into soft-deleted space with no UI signal. (2) Approving such an orphan mints a `USER_OWNER_MAPPING` to a dead Owner. (3) The vague USR004 message forces the operator to manually find which relation blocks a delete. (4) Persistence-technique surface: a caller with `OWNER_ASSOCIATION_*` can plant orphan rows that survive directory churn.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: add a 4th cascade leg checking `owner_association_request`, **or** set an `ON DELETE` behaviour on the FK (`V0_0_51:11`), **or** cross-check `getOwnerId().deleted_at` on the approve path (`OwnerAssociationRequestServiceImpl.java:184-190`). File alongside the F-076 cross-Management cascade structural-class. Distinct from PLT-087 (DataSource orphan token).
