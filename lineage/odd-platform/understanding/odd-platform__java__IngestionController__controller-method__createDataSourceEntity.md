# IngestionController.createDataSource — semantic understanding

## understanding

`createDataSource` (mapped to the `POST /ingestion/datasources` operation defined in the upstream `opendatadiscovery-specification` Ingestion API contract — the JVM method name is `createDataSource` per `IngestionApi`; the substrate's node-id label `createDataSourceEntity` is a synonym for the same controller method at lines 47-73) is the S2S boot-of-collector endpoint: a Collector POSTs a `DataSourceList` payload to register or update the datasources it will subsequently ingest into. Authentication is handled by the SIBLING `IngestionDataSourceFilter` (unconditional `@Component`, NOT gated by `auth.ingestion.filter.enabled`) which validates the `Authorization: Bearer <token>` header against the COLLECTOR table and writes the matched `collectorId` into the WebSession's `COLLECTOR_ID_SESSION_KEY` attribute before the request reaches this controller. The controller then reads that session attribute (lines 50-58 — fail-loud `IllegalStateException("Collector id is null")` if missing), validates that every payload item has non-empty `name` + `oddrn` (lines 97-102), and delegates to `DataSourceIngestionServiceImpl.createDataSources(collectorId, ...)` which upserts by ODDRN inside a single `@ReactiveTransactional` boundary. The asymmetry with the sibling `postDataEntityList` method is load-bearing: `/ingestion/datasources` is ALWAYS authenticated (filter is unconditional, no opt-in); `/ingestion/entities` is authenticated ONLY when `auth.ingestion.filter.enabled=true` (default `false` per `application.yml:48`). Both share the same `/ingestion/**` whitelist (SecurityConstants.java:96), so the four UI auth modes do not layer additional defense for either path.

## concepts

- entities: [`DataSourceList` (request body — list of `DataSource` items each with `name`, `oddrn`, `description`, `connectionUrl`, `type`, etc.), `Mono<DataSourceList>` (reactive request shape), `collectorIdMono` (extracted from session — line 50), `CollectorDto` (resolved by id at the service layer, line 42), `NamespacePojo` (inherited from the Collector's namespace, NOT from the payload), `DataSourcePojo` (the persistence row), `Mono<ResponseEntity<Void>>` (response — always 200 OK on success, line 72), `BadUserRequestException` (HTTP 400 for invalid datasources), `IllegalStateException` (HTTP 5xx for missing session attribute)]
- operations: [extract-collector-id-from-websession, fail-loud-on-missing-collector-id, validate-payload-non-empty-name-and-oddrn, delegate-to-service-with-collector-id, upsert-datasources-by-oddrn-merge-name-and-description, return-200-on-success]
- invariants:
  - "Controller has no `@PreAuthorize`, no programmatic `permissionService.hasPermission(...)`. Authentication is delegated to `IngestionDataSourceFilter` (sibling unconditional filter) which validates the bearer token against the COLLECTOR table and writes `COLLECTOR_ID_SESSION_KEY` into the session BEFORE this method runs. If the filter rejects, the controller never executes."
  - "Collector identity propagates via WebSession, NOT via principal / SecurityContext. The filter sets `session.getAttributes().put(SessionConstants.COLLECTOR_ID_SESSION_KEY, collectorId)` (IngestionDataSourceFilter.java:37-38); the controller reads it via `exchange.getSession().map(ws -> ws.getAttribute(...))` (IngestionController.java:50-57). The session is in-memory by default (`session.provider: IN_MEMORY` per application.yml:30 + `spring.session.timeout: -1` for unlimited duration). On a clustered deployment with sticky sessions disabled, the second hop request might land on a different node with no session — but every collector request hits `/ingestion/datasources` first (which sets the session) and is typically followed by `/ingestion/entities` on the same connection."
  - "If `COLLECTOR_ID_SESSION_KEY` is `null` (filter didn't run, session expired, session attribute lost), the controller throws `IllegalStateException(\"Collector id is null\")` (line 54) — which propagates to the default reactive error handler as HTTP 500 Internal Server Error. There is no 401 conversion. An operator probing the endpoint without going through the filter cannot distinguish 'session missing' from 'server crashed'."
  - "Payload validation is two-field-only: every `DataSource` item must have non-empty `name` AND non-empty `oddrn` (line 100-101: `Stream.of(ds.getName(), ds.getOddrn()).allMatch(string -> string != null && StringUtils.isNotEmpty(string.trim()))`). Missing description, type, connection_url, namespace — all silently allowed as null/empty. The check uses `handle((dsList, sink) -> ...)` (line 61-68) so an invalid payload triggers `sink.error(new BadUserRequestException(\"Ingestion Data Sources' payload is invalid\"))` — surfaced as HTTP 400."
  - "Response code is HARD-CODED 200 OK (`Mono.just(ResponseEntity.ok().build())`, line 72). The upstream `opendatadiscovery-specification` OpenAPI contract for `POST /ingestion/datasources` (the Java method imports `IngestionApi` from `org.opendatadiscovery.oddplatform.ingestion.contract.api`) declares the success response — but the contract file lives in an external Gradle dep (`io.github.opendatadiscovery:opendatadiscovery-specification`), not in this repository's source tree. The Java return type is `Mono<ResponseEntity<Void>>` (line 48) — the controller does NOT echo the registered datasource list back to the caller, even though the service layer returns `Flux<DataSource>` (DataSourceIngestionServiceImpl.java:41). The `flatMapMany` at line 70 consumes the Flux for its side effects only; `.then(Mono.just(ResponseEntity.ok().build()))` drops the result."
  - "Merge semantics on UPDATE: `DataSourceIngestionServiceImpl.prepareForUpdate` (lines 74-92) preserves the existing `DataSourcePojo` and OVERWRITES only `name` + `description` from the new payload. The existing `connection_url`, `active` flag, `type`, `namespace_id`, `collector_id`, `token_id`, soft-delete flag, all `created_at` / `updated_at` timestamps — all preserved. An operator who renames a datasource in the UI and then re-runs the collector will see their UI-side rename OVERWRITTEN by the collector's payload (the collector wins). No log records this overwrite."
  - "Namespace is INHERITED from the COLLECTOR, not the payload. `mapDataSources` (line 99-111) maps every payload item through `dataSourceIngestionMapper.mapIngestionModel(ds, MappingUtils.extractFieldFromNullableObject(c.namespace(), NamespacePojo::getId), c.collectorPojo().getId())` — the namespace_id comes from `CollectorDto.namespace()` (the Collector's pre-configured namespace), NOT from any namespace field on the `DataSource` payload. If the payload contains a `namespace_name` (the upstream Ingestion API contract has this field), it is SILENTLY IGNORED. The collector's namespace wins."
- audiences: [odd-collector + odd-collector-sdk processes at startup (registering their datasources), odd-platform operators standing up collectors via the Integration Wizard, the Platform's Datasources tab (P-08 — the post-registration audit surface), security reviewers auditing the S2S surface]

- coupling:
  - "Path mapping is OpenAPI-contract-driven (NO `@PostMapping` on the controller). Consistent with other `IngestionApi` methods in this controller (`postDataEntityList`, `getDataEntitiesByDEGOddrn`, `postDataSetStatsList`, `ingestMetrics` — all `@Override` of generated interface methods, no per-method path annotations).   - "Response shape is `Mono<ResponseEntity<Void>>` (line 48) — the registered datasource list is NOT echoed back. The service layer returns `Flux<DataSource>` (DataSourceIngestionServiceImpl.java:41) which carries the created/updated DataSource shapes back, but the controller's `.then(Mono.just(ResponseEntity.ok().build()))` (line 72) discards the result. A caller that needs the platform-assigned `id` of the registered datasource must call back to `GET /api/datasources` (the UI-side endpoint, different controller, requires UI auth) — an awkward two-step round-trip. The upstream OpenAPI contract may declare the response body type; the Java return type is hard-coded `Void` regardless."
  - "Session-based state coupling between filter and controller. The filter writes one key; the controller reads it via stringly-typed lookup (`SessionConstants.COLLECTOR_ID_SESSION_KEY` is `public static String COLLECTOR_ID_SESSION_KEY = \"collectorId\"`, NOT `final` — see SessionConstants.java:4). There is no shared interface or constant import enforcement (the controller imports the constant by name)."
  - "Asymmetry with sibling `postDataEntityList` (lines 38-45): both methods share the same controller class, both implement OpenAPI-generated interface methods, but their auth model differs fundamentally. `postDataEntityList` has NO session-attribute dependency (the entities ingestion identifies the target datasource by `dataSourceOddrn` IN THE PAYLOAD); `createDataSource` REQUIRES the filter-set `COLLECTOR_ID_SESSION_KEY` (the datasource creation identifies the parent collector via SESSION STATE). The two endpoints use different ENTIRELY DIFFERENT identity-resolution mechanisms — session-vs-payload — even though they share the same `IngestionController` class and the same `/ingestion/*` path family."
