## What

The activity feed joins the tag and owner association tables to support the `tag_ids` and `owner_ids` filters, but never de-duplicates the result. When a caller supplies both filters (or any filter where the entity carries several matching association rows), the LEFT JOIN multiplicity multiplies each activity event N x M times (N = matching tags, M = matching owners) - same id, timestamp, payload, actor. The defect is present on BOTH the list endpoint (`GET /api/activity`) and the count endpoint (`GET /api/activity/counts`); neither applies `DISTINCT`.

## Where

List query - the per-filter joins are added with no de-duplication, and the final select has no `DISTINCT`:

`odd-platform-api/.../repository/reactive/ReactiveActivityRepositoryImpl.java:237-241` (joins) and `:290-294` (select)
```java
// addJoins(): one leftJoin per filter, against a one-to-many association table
if (CollectionUtils.isNotEmpty(tagIds))   query.leftJoin(TAG_TO_DATA_ENTITY).on(TAG_TO_DATA_ENTITY.DATA_ENTITY_ID.eq(DATA_ENTITY.ID));
if (CollectionUtils.isNotEmpty(ownerIds)) query.leftJoin(OWNERSHIP).on(OWNERSHIP.DATA_ENTITY_ID.eq(DATA_ENTITY.ID));
// findActivities(): no DISTINCT, and .limit(size) is applied to the fanned-out row set
baseQuery.where(conditions).orderBy(ACTIVITY.CREATED_AT.desc(), ACTIVITY.ID.desc()).limit(size);
```

Count query - the SAME fan-out, counted with `selectCount()` (no `DISTINCT`), so the count is inflated by the same N x M factor. This is in all three count methods:

`getTotalActivitiesCount` (`:145-163`), `getMyObjectsActivitiesCount` (`:166-184`), `getDependentActivitiesCount` (`:187-206`) -> each calls `addJoins(...)` then `getActivityCount` (`:297-302`, `selectCount()`).

## User-facing impact

Verified live (running stack; one entity seeded with 2 tags + 2 owners; filtered `tag_ids=1,2` and `owner_ids=1,2` on the global Activity page, "All" tab):

- The "All" tab count badge shows **20**, but the list shows only **5** distinct events. On screen, the count contradicts the list the user is looking at.
- Mechanism, end to end: `GET /api/activity/counts` returns `total_count=20` (the fanned-out count -> the badge). The list endpoint returns 20 rows (5 distinct x 2 tags x 2 owners), but the front end **de-duplicates by id**, so the user sees 5 cards. So the bug does NOT show up as visibly duplicated rows - it shows up as the **count badge disagreeing with the visible list**. (Front-end/back-end contradiction: the back end returns duplicates; the front end hides them in the list but cannot hide them in the count.)
- Second-order harm: `.limit(size)` is applied BEFORE the client de-dup. A page of `size=N` returns N rows that collapse to fewer cards, so on a busy feed a `size=30` page can render far fewer than 30 distinct events and push genuinely older events off the page - the user sees an under-filled feed and may conclude activity has ended when it has not.
- Who hits this: anyone narrowing the Activity feed by tag AND owner (an audit/triage flow) - exactly the "narrow it down" path. Reachable by any authenticated user; anonymously under `auth.type=DISABLED`.

## Why it matters

The activity feed is an audit surface; a count that says 20 while the list shows 5 reads as broken and erodes trust in the feed (the operator cannot tell whether events are missing or miscounted). The list endpoint also over-ships the payload (N x M rows on the wire for the same events), and the pre-de-dup `LIMIT` silently truncates real history. Medium severity: read-side correctness, no data loss or security exposure, but a visible self-contradiction on a core surface.

## Suggested fix

Return one row per activity regardless of join multiplicity, on BOTH paths:

- Preferred: restructure the tag/owner predicates as `EXISTS` subqueries (or `IN (SELECT ...)`) so the association tables filter without fanning out the row count. This fixes the list AND all three count methods at once, with no `DISTINCT` needed.
- Minimal: add `SELECT DISTINCT` to the list query, and change `selectCount()` to `countDistinct(ACTIVITY.ID)` in `getTotalActivitiesCount`, `getMyObjectsActivitiesCount`, and `getDependentActivitiesCount`. (A list-only fix is incomplete - it leaves the count badge wrong.)

The fix must hold for the both-filters-set case on a multi-match entity, which is the only case current tests do not cover.

**How to verify:** seed one entity with 2 tags + 2 owners, then `GET /api/activity?...&tag_ids=<both>&owner_ids=<both>&type=ALL` and `GET /api/activity/counts?...` with the same filters - both must report the distinct number (5), not the fanned-out number (20). Confirmed before/after target on the live stack: 20 rows / count 20 -> 5 / 5.

## How discovered

Surfaced during a product-owner review of the activity feed, then characterized end to end against a running stack: with an entity carrying 2 tags + 2 owners and both filters set, the list endpoint returns 20 rows / 5 distinct, `GET /api/activity/counts` returns `total_count=20`, and the UI shows 5 cards under an "All 20" badge - confirming the count/list contradiction and that the front end de-dupes the list rows. The count-query fan-out and the de-dup mismatch were both found by driving the UI, not by reading the back-end query alone. Scope note: result correctness under multi-filter; distinct from the unbounded-`size` clamp on the same endpoint.
