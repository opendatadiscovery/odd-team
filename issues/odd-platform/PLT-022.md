## What

REJECT-CANDIDATE for the original framing. An earlier revision claimed `data_entity.exclude_from_search=true` is an operator-facing "hide this entity from discovery" toggle and that 9 list surfaces "leak" hidden entities - a security/compliance defect (severity high). The user-facing verification sweep (2026-06-10) falsifies the premise on three independent points; what survives is a narrow, debatable, low-severity consistency question.

**1 - There is no operator toggle and the flag is not in the API contract.** No `excludeFromSearch` / `exclude_from_search` reference exists anywhere in the frontend, and the field is absent from the generated FE client (verified by grep 2026-06-10). Operators cannot set this flag from the UI at all - so "an operator toggles it to hide an entity" describes an affordance that does not exist.

**2 - The flag means "this entity is a member of a Data Entity Group", set at ingestion.** It is set by `IngestionMapperImpl.isExcludedFromSearch(dto)` (`IngestionMapperImpl.java:401-407`), which returns true exactly when the ingested entity has a group parent (`dto.getDataEntityGroup().groupOddrn() != null`); wired in at `:185`. Manually-created entities are set false (`DataEntityMapperImpl.java:195,213`); hollow stubs are set true (`ReactiveDataEntityRepositoryImpl.java:863`). So the flag's real job is to keep GROUP-MEMBER (child) entities out of the FLAT full-text-search results so the search box is not polluted with sub-entities, while they stay reachable through their parent group / term / owner navigation.

**3 - The live docs already say exactly this, and were corrected away from the draft's premise.** `documentation/docs/data-discovery/search.md:100-102` and `catalog-overview.md:65` now state verbatim: "`exclude_from_search` is a full-text-search signal only - it does not hide entities from ... any other list surface ... treat the flag as a search-engine signal, not a platform-wide hide signal." The DOC-186 companion this issue cites as "pending" has effectively shipped, and it documents the search-only behaviour as the contract - not as a leak.

Given (2), the list surfaces NOT applying the predicate is largely INTENTIONAL: `getDEGExperimentRuns` lists a group's child runs, `listByTerm` lists term-linked entities including group members, the `getDimensions`/`getDetails` paths resolve a specific entity - all of these SHOULD surface group members. Lifting the predicate into the shared helper (the earlier "recommended" fix) would make `getDEGExperimentRuns` return empty and would hide group members from term/owner navigation - a regression, not a fix.

What actually happens, mechanically (verified 2026-06-10):

`ReactiveDataEntityRepositoryImpl.cteDataEntitySelect` (def at `:909`; body `:916-918`) applies `addSoftDeleteFilter` (`:916`) + `DATA_ENTITY.HOLLOW.isFalse()` (`:918`) and does NOT apply an `EXCLUDE_FROM_SEARCH` predicate. EIGHT methods route through it:

1. `listPopular` (`:630`, calls helper at `:637`)
2. `listByOwner` (`:516`, helper at `:518` - My Objects)
3. `listByTerm` (`:537`, helper at `:556`)
4. `getDEGExperimentRuns` (`:344`, helper at `:349`)
5. `getDimensions(long id)` (`:183` -> `baseDimensionsSelect` `:872` -> helper `:874`)
6. `getDimensions(Collection<String> oddrns)` (`:194`, same chain)
7. `getDimensionsByIds(Set<Long> ids)` (`:205`, same chain)
8. `getDetails(long id)` (`:217`, same chain - direct entity-detail GET)

The 9th method the earlier revision listed, `getQuerySuggestions` (`:471`), does NOT use `cteDataEntitySelect` - it builds its own FTS-backed query (`:478-512`) that applies `HOLLOW.isFalse()` + `STATUS.ne(DELETED)` but no `EXCLUDE_FROM_SEARCH` predicate. So it is a SEPARATE path, and notably it IS a full-text-search surface (autocomplete suggestions) - the one place where, by the flag's own search-dedup intent, applying the predicate would arguably be correct.

The predicate IS applied at the true FTS search path (`findByState` via `JooqFTSHelper.resultFacetStateConditions:149`) and at the count/statistics path (`getDataEntityDefaultConditions`, `ReactiveDataEntityRepositoryImpl.java:974`).

## User-facing impact

- **WHO actually sets this flag:** nobody, interactively. There is no UI toggle (verified by FE grep 2026-06-10) and the field is not in the generated FE client. The flag is set automatically at ingestion when an entity belongs to a Data Entity Group (`IngestionMapperImpl.java:401-407`).
- **WHAT an operator observes:** a group's member entities are excluded from the flat full-text search results (so a search for the parent group does not also dump every child row), but those same members still appear when the operator navigates INTO the group, opens a linked term, or views an owner's objects. This is the intended, documented behaviour - `documentation/docs/data-discovery/search.md:100-102` and `catalog-overview.md:65` describe it verbatim as a search-only signal.
- **NOT what the earlier revision claimed:** there is no operator who "toggles exclude_from_search to hide a staging/internal entity," no multi-team hide-from-discovery control, and no compliance leak - because the affordance to set the flag for those purposes does not exist. The `auth.type=DISABLED` "amplifies the leak to anonymous" point is moot: there is no operator-intended hide to leak.
- **The one debatable residual (low):** `getQuerySuggestions` (autocomplete) is itself a full-text-search surface and arguably SHOULD honour the flag for parity with the main search box, since it does not - a group member can appear in autocomplete but not in full search. This is the only place where applying the predicate would be consistent with the flag's own intent; it is a minor UX-parity nit, not a security/compliance defect. Verified by code trace 2026-06-10 (`:478-512` omits the predicate on an FTS path).

## How to reproduce (corrected scope)

The original repro assumed an operator sets the flag via UI to hide an entity - not possible. The accurate observation:

1. Ingest a Data Entity Group with member entities (members get `exclude_from_search=true` automatically).
2. `GET /api/dataentities/search?query=...` (FTS) and the count/stats aggregates omit the members - correct, by design.
3. The members still appear via `GET /api/dataentities/popular`, `/my`, `/byTerm/{id}`, the DEG-experiment-runs view, and direct GET-by-id - which is the intended reachability of group members through navigation.
4. The members also appear in `getQuerySuggestions` autocomplete - the one FTS-shaped surface that does not honour the flag (the only arguable inconsistency).

## Suggested fix

Do NOT lift the predicate into `cteDataEntitySelect`. Because the flag marks group members (`isExcludedFromSearch` = has-group-parent), adding `.and(DATA_ENTITY.EXCLUDE_FROM_SEARCH.isFalse())` to the shared helper would make `getDEGExperimentRuns` return an empty child list and would hide group members from term/owner navigation - a regression. The earlier "Option A (recommended), one line, large leverage" recommendation is withdrawn.

The only defensible code change (low priority, optional):

- **Honour the flag on `getQuerySuggestions` for FTS parity.** Add the `EXCLUDE_FROM_SEARCH` predicate to the autocomplete query (`ReactiveDataEntityRepositoryImpl.java:478-487`) so the suggestion list and the full search box agree. This is the only surface where applying the predicate is consistent with the flag's search-dedup intent. No spec/contract change; no doc change (the docs already describe the search-only contract).

If the project decides it WANTS an operator-facing hide-from-everywhere capability, that is a NEW feature (new column or repurpose with a UI affordance + contract field + audit), not a bug fix on this flag - and it should be designed separately, since reusing the DEG-membership flag for it would conflate two meanings.

## Operator impact

Re-scoped: the original security/compliance/multi-team impact does not exist (no operator sets this flag; it is an ingestion-time DEG-membership marker). The residual impact is a minor UX inconsistency: a group-member entity can surface in the autocomplete suggestion list while being absent from the main full-text search results.
