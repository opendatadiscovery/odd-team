#### Finding F-010a: jOOQ operator-precedence bug — doc acknowledges but no code-side comment / no test / no tracking issue
- **Verdict**: STATIC-INFERRED · `missing-caveat` · MEDIUM severity · ontology-confirmed (substrate batch K)
- **Source-of-truth**: `Ontology[F-010:observed_vs_expected.facet=jooq_operator_precedence_bug_with_doc_acknowledgement_no_test]` → `Repo[odd-platform-api/src/main/java/.../housekeeping/job/AlertHousekeepingJob.java:28-34]`
- **What the doc says (verbatim, live)**: "a known platform bug currently exempts manual resolutions from the retention check — manual `RESOLVED` alerts are hard-deleted on the next housekeeping run regardless of this value."
- **What the code does**: `.where(STATUS.eq(RESOLVED)).or(STATUS.eq(RESOLVED_AUTOMATICALLY)).and(STATUS_UPDATED_AT.lessOrEqual(...))` — jOOQ fluent-builder precedence binds `.and(...)` to the most recent `.or(...)`. Emitted SQL: `WHERE (STATUS='RESOLVED') OR (STATUS='RESOLVED_AUTOMATICALLY' AND STATUS_UPDATED_AT <= cutoff)`. Manual RESOLVED rows skip the TTL check entirely. ZERO `// TODO` / `// BUG` / `// FIXME` comments at the source. ZERO test files matching `Housekeeping*`. ZERO open GitHub-issue cross-reference in the live doc.
- **Operator-visible consequence**: Compliance frameworks requiring alert-retention (SOC2 / SOX / HIPAA) cannot rely on `resolved_alerts_days` for manual-resolved rows. The doc-side acknowledgement makes this a known-defect contract; a passive operator does not know what to do about it.
- **Suggested fix**: One-line jOOQ parenthesisation `.where(STATUS.eq(RESOLVED).or(STATUS.eq(RESOLVED_AUTOMATICALLY))).and(STATUS_UPDATED_AT.lessOrEqual(cutoff))` + one regression test. The doc-side caveat then moves from "known platform bug" to "fixed in version X" once the regression test pins behaviour.
