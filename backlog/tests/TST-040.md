## Description

`SearchResultsTabs` computes which tab is highlighted from the active `searchClass`:

```
React.useEffect(() => {
  setSelectedTab(searchClass ? tabs.findIndex(tab => tab.value === searchClass) : 0);
}, [tabs, searchClass]);          // SearchResultsTabs.tsx:68-70
```

When `searchClass` is truthy, `selectedTab` is `tabs.findIndex(...)`. `Array.findIndex` returns **-1** when no tab's `value` equals `searchClass`, and there is **no fallback** for the -1 case (the ternary's fallback only covers a falsy `searchClass`, which maps to `0`). The class tabs build their `value` from `totals[ClassEnum]?.id` (`SearchResultsTabs.tsx:30-62`) — optional-chained, so a tab's `value` is `undefined` until the totals payload carries that class's id. So a user who arrives with a saved/deep-linked class selection whose corresponding tab value is still `undefined` (or otherwise unmatched at that render) gets `selectedTab = -1`: **no tab is visually highlighted** even though that class's results are showing (F-148 / H-006 neighbourhood).

**Typed gate: regresses-bug / characterization-pin** (LSN-029). This asserts the CURRENT (incorrect) behaviour — `findIndex` yields `-1` and no tab is selected for an unmatched/undefined-value class — and is designed to go RED the instant a fallback is added (e.g. `const idx = tabs.findIndex(...); setSelectedTab(idx === -1 ? 0 : idx)`), which is the natural fix and could be folded into the H-006 work. It is GREEN today as a tripwire and is NOT `@Disabled` (a disabled test would hide the regression direction). The user-facing fix (a `-1` fallback so the saved class's tab highlights) is the tracked counterpart.

## Acceptance Criteria

- [ ] A test renders `<SearchResultsTabs>` (or unit-tests the index computation) with a `searchClass` that matches NO tab `value` — e.g. a class id that is present as `searchClass` but whose `totals[ClassEnum]?.id`-derived tab `value` is `undefined`/absent — and asserts the CURRENT behaviour: the computed `selectedTab` is `-1` (equivalently: no tab is rendered in the selected/highlighted state).
- [ ] A companion assertion documents the boundary the code DOES handle: a falsy `searchClass` yields `selectedTab === 0` (the ternary's only fallback), so the test makes clear that ONLY the unmatched-truthy case falls through to -1.
- [ ] In-source documentation: this pins the missing `-1` fallback in `SearchResultsTabs.tsx:68-70` (F-148 / H-006), asserts the current incorrect "no tab highlighted" state, and states the LSN-029 flip protocol (on RED: a fallback was added → invert to assert the saved class's tab is selected, retag `regresses-bug` against the fix; could be folded into the H-006 fix).
- [ ] Not `@Disabled`/skipped; runs in the UI suite; does not break the build.

## Implementation Notes

Small. Read `SearchResultsTabs.tsx:24-70` to confirm: tabs build `value` from `totals[...]?.id` (can be `undefined`), and the `selectedTab` ternary only falls back to `0` for a falsy `searchClass` — leaving the unmatched-truthy path on raw `findIndex` (-1). Easiest assertion path is to drive the component with a `totals` object missing the relevant class id and a `searchClass` set to that class, then assert no tab is in the selected state (inspect the `selectedTab` prop passed to `AppTabs`, or query the rendered selected-tab marker).
