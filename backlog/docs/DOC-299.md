## Description

A cluster of RBAC / authorization caveats across the data-collaboration and glossary surfaces, all code-confirmed:

1. **No RBAC on any data-collaboration endpoint.** None of the four DC endpoints (`/datacollaboration`, `/messages`, `/slack/events`, …) carry a SecurityRule — they fall through to `authenticated()`, and under `auth.type=DISABLED` all four are **anonymously reachable**. Both the api-reference page and the feature page frame the `datacollaboration.enabled` flag as if it were the access gate; it only toggles the feature, it does not authorize callers.

2. **Slack `/api/slack/events` webhook does no signature verification.** The api-reference documents the webhook in detail but omits that it performs **no Slack request-signature verification** (no `X-Slack-Signature` HMAC check), which the Slack Events API contract mandates. Any caller can POST forged Slack events.

3. **Term writes are a NAMESPACE_CREATE side-door.** `POST/PUT /api/terms` both invoke `namespaceService.getOrCreate`. A caller holding only `TERM_CREATE` / `TERM_UPDATE` can create a **platform-wide namespace** without `NAMESPACE_CREATE` — an RBAC side-door the glossary page does not mention.

4. **`addDataEntityTerm` gate is registered on the wrong path.** The permission `DATA_ENTITY_ADD_TERM` is registered at the **singular** `/term`, but the actual route is the **plural** `/terms`. The path-matcher never matches, so the gate **never fires** — the operation is effectively ungated. The glossary page presents it as gated by `DATA_ENTITY_ADD_TERM`.

High — multiple false/absent authorization guarantees across primary API surfaces.

**Failure shape**: missing + false security caveats (Gate 3/6) across the DC + glossary RBAC model.
