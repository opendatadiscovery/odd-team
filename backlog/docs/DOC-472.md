## Description

The CTRIB-024 fix (odd-platform #1757, milestone 0.29.0) adds `RUNNING` as a first-class run status
(wire enum `DataEntityRunStatus` + FE `palette.runStatus`/`reportStatus`). The paired docs update
([[DOC-471]]) revised `docs/data-quality/test-run-history.md` so its per-test status filter now lists
**seven** statuses (adds **Running**, since the History endpoint lists in-flight runs). The **sibling** page
`docs/data-quality/dashboard.md` was not updated and its cross-reference now self-contradicts once 0.29.0
publishes:

- `dashboard.md:22` stated the Test Results Breakdown ring renders "the full set is **Success, Failed,
  Skipped, Broken, Aborted, and Unknown** (the **same six statuses** as the per-test [Test Run History]
  status filter)". After 0.29.0 the linked History filter has **seven** statuses, so "the same six statuses"
  is factually wrong and two linked pages of the published manual disagree.

This is the LSN-006 / LSN-007 "locally well-executed, globally drift-producing" class: the run-status-set
change was correct on its own page but left a linked sibling enumerating the set against a now-stale claim.

**Verified-and-corrected scope (consumer-read during the fix).** The first draft of this item also claimed
the dashboard could now *render a Running slice* (because #1757 added a `RUNNING` palette key). **That was
wrong** — reading the writer settled it: the dashboard's Breakdown reads each test's latest run from
`data_entity_task_last_run`, and the only writer (`ReactiveDataEntityTaskRunRepositoryImpl.insertLastRuns`,
line 103) filters `tr.getEndTime() != null`. An in-flight `RUNNING` run has `end_time = NULL`, so it is
**never** written to `data_entity_task_last_run` and **can never be a dashboard slice**. The dashboard
legitimately shows the **six terminal** statuses; `RUNNING` is a History-only, in-flight status. The fix is
therefore a precise cross-reference correction that *explains the difference*, not an "add Running to the
dashboard" change.

## Resolution

Fixed on the `release/0.29.0` train (commit `23d7a3c`, **corrected** by `19f49b7`). Pushed to
`origin/release/0.29.0`. Self-verified branch sub-checks: PyYAML parses, `description` 159 ≤ 200, Gate 11
clean, tree-relative links only. Live-site verification is owed at the 0.29.0 release gate
(`/review release:0.29.0`), same as [[DOC-471]].

**Important correction (2026-06-19, live-reproduced).** The first dashboard.md fix (`23d7a3c`) said the
dashboard "never shows Running" — that was wrong. Driving the running stack (`GET /api/dataqatests/runs`)
showed the dashboard breakdown **does list `Running`** once `RUNNING` joins the wire enum (0.29.0): the mapper
`DataQualityCategoryMapperImpl.addMissingStatuses` emits a 0-count entry for every `DataEntityRunStatus`
value. So the dashboard shows `Running` — but its count is **always 0**, because the breakdown reads
`data_entity_task_last_run` and an in-flight run (no `end_time`) is never written there
(`insertLastRuns` filters `end_time != null`). `19f49b7` rewrites `dashboard.md:22` to say so accurately
(seven statuses matching History; the breakdown reflects each test's latest **completed** run; `Running`
reads 0 for in-flight tests). The underlying behaviour — in-flight tests don't impact the dashboard — is a
real platform bug filed as **PLT-230** (`issues/odd-platform/PLT-230.md`); this doc item only describes the
current behaviour accurately.
