## What

The dedicated `WebClient` the platform uses to call the external GenAI service (`genAiWebClient`) is built with no codec configuration, so it inherits Spring WebFlux's **default 256 KB in-memory buffer limit** for decoding the response body. Any GenAI answer larger than 256 KB therefore fails with `DataBufferLimitException` ("Exceeded limit on max bytes to buffer"), which `GenAIServiceImpl` wraps in a `GenAIException` and surfaces to the caller as a generic HTTP 500.

This is an **inbound/outbound asymmetry**: the platform's app-wide `spring.codec.max-in-memory-size: 20MB` (`application.yml:14-15`) governs **server-side** request decoding (the prompt a caller sends *in*), but a `WebClient.builder()` constructed by hand does **not** pick up that property - it only configures the auto-configured `WebClient.Builder` bean and the server codecs, not a static-factory builder. So the platform accepts a 20 MB prompt but can only decode a 256 KB **answer** from the external service before failing.

**Correction (2026-06-10) - the "code vs docs contradiction" premise is FALSIFIED.** An earlier revision claimed "the GenAI feature documentation frames the answer-size ceiling as 'governed only by the global WebFlux limit (default 20 MB)'" and asserted an "80x gap between documented and actual behaviour". That is **not** what the docs say. Every `spring.codec.max-in-memory-size: 20MB` reference in the docs is about the **inbound request** path: `active-platform-features/genai.md:109` is in the security-posture section and is explicitly about the "request-body size cap" on "large free-form prompts"; the other mentions (`odd-platform.md:1036-1045`, `metrics-ingestion.md:54`, `integrations/README.md:147`, `attachments.md:62`) are all about inbound upload/ingest bodies. **No doc claims the GenAI answer (outbound response) ceiling is 20 MB**, and the quoted string "governed only by the global WebFlux limit (default 20 MB)" appears nowhere in the docs. The genai.md inbound-prompt claim is in fact **correct** (the server codec is the 20 MB one). The defect here is therefore a genuine but **latent code asymmetry**, not a code-vs-docs contradiction.

## Where

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/config/WebClientConfiguration.java:26-29`

```java
return WebClient.builder()
    .clientConnector(connector)
    .baseUrl(genAIProperties.getUrl())
    .build();
```

No `.codecs(c -> c.defaultCodecs().maxInMemorySize(...))` call - so the WebFlux default (`262144` bytes = 256 KB) governs response decoding for `genAiWebClient`. Verified there is **no** global override that would lift it: no `CodecCustomizer`, `WebClientCustomizer`, or `WebFluxConfigurer` bean exists anywhere in `odd-platform-api/src/main/java` (grep, 2026-06-10), and the project is on Spring Boot 3.4.10 / Spring 6.x (`odd-platform-api/build.gradle:2`), whose WebFlux default in-memory limit is 256 KB. The app-wide `spring.codec.max-in-memory-size: 20MB` (`application.yml:14-15`) is applied by Spring Boot to the **server** codecs and the **auto-configured** `WebClient.Builder` bean - **not** to a `WebClient.builder()` called directly, as it is here.

## User-facing impact

API-consumer-facing only - not visible in the shipped ODD UI (GenAI is API-only; no view calls `GenaiApi.ts`; `active-platform-features/genai.md:9,97,128`). A consumer driving `POST /api/genai/ask` whose external service returns an answer larger than 256 KB gets an HTTP 500 (`GenAIException` wrapping `DataBufferLimitException`) instead of the answer. The 256 KB outbound ceiling is **code-settled** (no codec override on the builder, no global customizer, confirmed default for Spring 6.x). The **runtime magnitude** - how often a real answer exceeds 256 KB - is integration-dependent and **not yet probed** (`PENDING-F-039-2`); most prose answers are well under 256 KB, so this is an edge case for large structured/long-form outputs.

## Why it matters

A latent ceiling on long-form answers. A GenAI answer over 256 KB (a multi-page summary, a large generated table) fails with an opaque HTTP 500 (the `DataBufferLimitException` wrapped as `GenAIException`) instead of returning the full answer. Because the inbound prompt cap is 20 MB but the outbound answer decode is 256 KB, the limits are asymmetric and the smaller one is invisible from request-path tracing. Severity is **low**: it requires an unusually large single answer to trigger, causes a failed request (not data loss or a security issue), and - because GenAI is API-only today (no shipped UI calls it) - the affected consumer is an API/script caller, not an end user. Note this is **not** the code-vs-docs gap the original draft claimed (the docs never promised a 20 MB *answer*); it is a real-but-narrow code defect on its own merits, worth fixing for symmetry and a clearer failure than an opaque 500.

## Suggested fix

Add an explicit codec override to the `genAiWebClient` builder, sizing the in-memory buffer to match the answer ceiling the platform intends to support (e.g. the 20 MB the docs reference, or a deliberately chosen value):

```java
return WebClient.builder()
    .clientConnector(connector)
    .baseUrl(genAIProperties.getUrl())
    .codecs(c -> c.defaultCodecs().maxInMemorySize(/* intended ceiling, e.g. 20 MB */))
    .build();
```

No documentation correction is needed for an outbound ceiling (the docs do not currently state one - see the falsification in **What**). If a value other than the inbound 20 MB is chosen, *then* the GenAI page's known-limitations list should gain a one-line note on the answer-size ceiling so the inbound/outbound asymmetry is explicit. Open to alternatives on the exact byte limit - the point is that the outbound decode limit should be a deliberate, documented choice rather than the silent 256 KB default.
