## Description

`integrations/README.md` makes two universal claims that do not hold for one of the integrations it lists in the same tables.

**Claim 1 — universal collector token (lines 122, 124-131).** "Every integration — pull or push — authenticates to the platform with a **collector token** issued by the ODD Platform." But:
- **`odd-tracing-gateway`** (listed as a push / standalone-gateway integration at lines 12 and 29) uses **no collector token**. It is **absent from the token table** (lines 124-131) — the table has rows for `odd-collector*`, `odd-airflow-2`, `odd-dbt`, `odd-spark-adapter`, `odd-great-expectations`, and `odd-cli`, but no row for the gateway. So the page's own table silently refutes its own "every integration" sentence.
- **`odd-spark-adapter`** carries the explicit footnote "**no static token** — the JAR identifies itself by `oddrn.key`" (line 129), which already contradicts "authenticates with a collector token" for that row.

**Claim 2 — universal datasource registration (line 133).** "On the platform side, **every integration registers its data sources via `POST /ingestion/datasources`**." But `odd-tracing-gateway` does not call `/ingestion/*` at all — the **Platform PULLs** microservice metadata from the gateway via **`GET /entities`** (the gateway exposes an endpoint the platform scrapes; it does not push to the Ingress API). Calling it a "push" integration that "registers via `POST /ingestion/datasources`" is doubly wrong for the gateway.

An operator deploying `odd-tracing-gateway` reads "every integration authenticates with a collector token" and "registers via `POST /ingestion/datasources`," then hunts for where to put the token and why the gateway never calls the registration endpoint — chasing a configuration that does not exist. The universal phrasing is true for pull collectors and for the Ingress-API push adapters, but not for the tokenless pull-receive gateway.
