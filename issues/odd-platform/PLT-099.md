## What

The Data Collaboration feature exposes four routes - the outbound message + history routes (`/api/datacollaboration/**`, `/api/messages/**`) and the inbound Slack webhook (`POST /api/slack/events`) - with two security gaps:

1. **No Slack request-signature verification on the inbound webhook.** `EventApiController.handleSlackEvent` (`EventApiController.java:23-25`) deserialises `@RequestBody Mono<String>` and reads no headers; `SlackEventParser.parse` (`SlackEventParser.java:22-23`) goes straight to JSON deserialisation with no timestamp/signature check. Slack's Events-API contract mandates HMAC-SHA256 verification of the `X-Slack-Signature` header against the signing secret; the codebase has **zero** matches for `X-Slack-Signature` / `signing.secret` / `verifySignature` / `HmacSha256` (grep over `odd-platform-api/src`, verified 2026-06-10). Any caller who can reach the endpoint can forge Slack events.
2. **No RBAC gate on the outbound + history routes; the inbound webhook is explicitly whitelisted (not merely ungated).** Two distinct postures, both verified against `AuthorizationCustomizer.customize` (`AuthorizationCustomizer.java:20-31`):
   - `/api/datacollaboration/**` and `/api/messages/**` (the outbound message + history routes) have **zero** `SecurityConstants.SECURITY_RULES` entries and are **not** in `WHITELIST_PATHS`, so they fall through to the `/**` -> `.authenticated()` catch-all (`AuthorizationCustomizer.java:29-30`). Under `auth.type=DISABLED` (no principal) they are anonymously reachable; under any real auth mode they require only a logged-in session, not a Data-Collaboration-specific permission.
   - **`/api/slack/events` is in `WHITELIST_PATHS`** (`SecurityConstants.java:96`), which `AuthorizationCustomizer.java:22-23` maps to `.permitAll()`. The webhook is therefore **unauthenticated by design** (Slack cannot carry an ODD session) - it does **not** fall through to `.authenticated()`. CORRECTION vs the original draft, which said "all fall through to `.authenticated()`": that is true for the outbound/history routes but false for the webhook, which is *more* exposed (permit-all). This makes HMAC signature verification the **only** possible defence for the inbound webhook - there is no session gate to lean on.

   The `datacollaboration.enabled` feature flag (`@ConditionalOnDataCollaboration`, `ConditionalOnDataCollaboration.java`) gates the controllers as beans, so all four routes 404 when the feature is off - but when it is on, the flag provides no access control. The doc framing implies that flag is the access gate; it is not.

Sources: HARVEST-039, HARVEST-040, HARVEST-007 (doc-understanding harvest, 2026-05-29). Doc caveat tracked at `backlog/docs/DOC-299.md`.

## User-facing impact

VERIFIED end-to-end (BE wiring + grep), 2026-06-10. This is a wiring-settled security posture, code-confirmed, not a runtime extrapolation:

- **Inbound webhook `POST /api/slack/events` is anonymously reachable in EVERY auth mode when Data Collaboration is enabled** - it is in `WHITELIST_PATHS` (`SecurityConstants.java:96`) -> `.permitAll()` (`AuthorizationCustomizer.java:22-23`), independent of `auth.type`. With no HMAC check (`EventApiController.java:23-25`, `SlackEventParser.java:22-23`; zero repo matches for any signature primitive), any network-reachable party can POST a forged `event_callback`. The parser only accepts `message` events that are thread replies (`SlackEventParser.java:56-105`), so the forgeable surface is: inject/modify thread-reply messages attributed to Slack into a data entity's Discussions, with attacker-chosen text and thread target.
- **Outbound + history routes (`/api/datacollaboration/**`, `/api/messages/**`) require only `.authenticated()`** - no Data-Collaboration permission. Under `auth.type=DISABLED` (the shipped default for demos) there is no principal, so they too are anonymous; the synthetic-admin posture (see PLT-072) means a DISABLED deployment exposes the full read/write Discussions surface to anyone.
- Auth mode: the webhook gap is auth-mode-independent (whitelisted). The outbound/history gap is `.authenticated()`-gated, so it bites hardest under DISABLED and degrades to "any logged-in user" under LOGIN_FORM/OAUTH2/LDAP regardless of intended DC scoping.
- Remaining-check (not driven on a running stack this pass): the exact downstream side effects of a forged message event (notification fan-out, child-message materialisation) were not exercised live; the *reachability* and *absence of verification* are fully code-settled. A forged-event probe against a local DC-enabled stack would close this.

## Why it matters

An unverified Slack webhook lets any network-reachable party POST forged `event_callback` payloads into the platform's collaboration pipeline - injecting messages attributed to Slack, or driving whatever side effects the event handler performs - with no authentication. Combined with the zero-RBAC posture, under the shipped `auth.type=DISABLED` default an anonymous caller reads and writes the entire Discussions surface. This is the LSN-002 class (an SDK/integration that ships an open door behind a flag that looks like a lock): an operator who enables Data Collaboration believes the feature flag gates it, and gets a publicly writable Slack ingress instead.

## Suggested fix

- Add HMAC-SHA256 verification to `handleSlackEvent`: read `X-Slack-Signature` + `X-Slack-Request-Timestamp`, compute `v0:{timestamp}:{body}` HMAC with a configured `datacollaboration.slack.signing-secret`, constant-time compare, reject (401) on mismatch or stale timestamp. (Keep the existing `url_verification` challenge handshake.)
- Add `SECURITY_RULES` entries gating the outbound + history routes behind a Data-Collaboration read/write permission rather than bare `.authenticated()`; the inbound webhook stays signature-gated rather than session-gated.
