## What

Two endpoints in `SecurityConstants.SECURITY_RULES` are wired to the WRONG permissions today. The docs declare permission X; the code grants the endpoint on permission Y. The mismatch surfaces as silent separation-of-duties leak (one Permission grants more capability than its name implies) and silent capability denial (operators with the documented permission find their action blocked).

**Defect 1 - `POST /api/datasetfields/{dataset_field_id}/terms` mis-routes to `DATA_ENTITY_ADD_TERM` instead of `DATASET_FIELD_ADD_TERM`.** The live `enable-security/authorization/permissions` page documents `DATASET_FIELD_ADD_TERM` as the permission for "linking a business glossary term to a specific field within a dataset". `DATA_ENTITY_ADD_TERM` is documented separately as the entity-level grant. The two are documented as DISTINCT separation-of-duties grants. `SecurityConstants.java:297-299` wires the dataset-field term-add endpoint to `DATA_ENTITY_ADD_TERM` (permission token on line 299), not `DATASET_FIELD_ADD_TERM`. Operators with `DATA_ENTITY_ADD_TERM` (entity-scope intended) get unintended field-level term-link capability (via direct API call - see User-facing impact); operators with `DATASET_FIELD_ADD_TERM` find their granted action 403s.

**Defect 2 - `PUT /api/alerts/{alert_id}/status` mis-routes to `DATASET_FIELD_ADD_TERM` (copy-paste from the preceding block).** `SecurityConstants.java:295-296` wires the alert-status endpoint to `DATASET_FIELD_ADD_TERM`. A copy-paste bug from the dataset-field block (the rule's `AuthorizationManagerType` is correctly `ALERT` with `alert_id` extraction; only the permission token is wrong). Any user holding `DATASET_FIELD_ADD_TERM` can resolve alerts; users holding `DATA_ENTITY_ALERT_RESOLVE` (the documented + FE-gated alert-resolve permission) but lacking `DATASET_FIELD_ADD_TERM` cannot. NOTE: there is **no** `ALERT_PROCESSING_*` permission family in `PolicyPermissionDto` (corrected 2026-06-10); the alert-resolve permission is `DATA_ENTITY_ALERT_RESOLVE` (`PolicyPermissionDto.java:27`).

Both shape-match the REFACTOR-217 path-mismatch pattern that already produced PLT-012 (batch-2 F-002a). This is a CLASS of defect - silent authorization mismatch via `SecurityConstants` line-position copy-paste - that the codebase needs a build-time validator for.

## User-facing impact

This is a two-sided authorization mismatch: the front end gates each action's button on the *documented* permission, while the back end enforces a *different* permission on the same endpoint. Both ends' code is settled by trace; the resulting 403 / privilege-leak is only observable under non-default RBAC (see the static-only note below).

- **WHO:** an operator/admin who assigns custom roles (policies) under LDAP or any non-DISABLED auth mode (under `auth.type=DISABLED` a synthetic admin holds every permission, so neither mismatch surfaces - `PermissionProvider.tsx:19-32` resolves access from the user's permission set).
- **Defect 1, dataset-field term add:** the Add-term button on a dataset field is rendered only for holders of `DATASET_FIELD_ADD_TERM` (`DatasetFieldTerms.tsx:76-77`, `WithPermissions permissionTo={Permission.DATASET_FIELD_ADD_TERM}`) - verified by FE trace 2026-06-10. The endpoint it calls enforces `DATA_ENTITY_ADD_TERM` (`SecurityConstants.java:297-299`) - verified by BE trace 2026-06-10. So a `DATASET_FIELD_ADD_TERM` holder sees an enabled button whose request is denied; a `DATA_ENTITY_ADD_TERM`-only holder sees no field-level button but can add field terms via a direct `POST` (privilege leak). The denial status itself is *static trace consistent; not driven* - requires two distinct custom roles under LDAP to observe the 403.
- **Defect 2, alert resolve:** the Resolve/Reopen button is rendered only for holders of `DATA_ENTITY_ALERT_RESOLVE` - on the global Alerts list (`AlertItem.tsx:50-68`, which both gates the action and re-checks `DATA_ENTITY_ALERT_RESOLVE` on click before dispatching the status update) and on the entity Alerts tab (`DataEntityAlertItem.tsx:111`, `WithPermissions permissionTo={Permission.DATA_ENTITY_ALERT_RESOLVE}`) - verified by FE trace 2026-06-10. The endpoint enforces `DATASET_FIELD_ADD_TERM` (`SecurityConstants.java:295-296`) - verified by BE trace 2026-06-10. So a `DATA_ENTITY_ALERT_RESOLVE` holder sees the Resolve button and gets a 403 on click; a `DATASET_FIELD_ADD_TERM` holder (a glossary curator) can resolve any alert via direct `PUT` (privilege leak). The 403 / leak is *static trace consistent; not driven* - requires custom roles under LDAP.
- **Already documented:** the live permissions page ships both mis-gates as operator caveats today (`permissions.md:41`), so the doc is correct and this PLT unblocks it - verified 2026-06-10.

## Why it matters

**Defect 1 - separation-of-duties leak**: A team lead given `DATA_ENTITY_ADD_TERM` to enable entity-level glossary curation also gets undeclared field-level term-link capability. Conversely, a data-steward role narrowly bound to `DATASET_FIELD_ADD_TERM` (intentional fine-grained access) finds their access broken - the runtime expects the wrong permission name.

**Defect 2 - alert-triage role doesn't work**: An alert-triage role bound to an actual `ALERT_PROCESSING_*` permission cannot resolve alerts; an unrelated data-steward role bound to `DATASET_FIELD_ADD_TERM` can. This is a silent capability shift that no doc nor RBAC review surfaces.

The bigger class concern: the codebase has a path-position-driven authorization configuration with NO validator pairing each `PathPatternParserServerWebExchangeMatcher` path with the OpenAPI operationId's documented permission. PLT-012 (batch-2 F-002a) is the same family; if this is the THIRD or FOURTH instance of the same shape, the next round of audits will find more.

## Suggested fix

**Thread A - Defect 1 (one-line):**

```java
// SecurityConstants.java:299 (before)
new PathPatternParserServerWebExchangeMatcher("/api/datasetfields/{id}/terms", POST), DATA_ENTITY_ADD_TERM,
// (after)
new PathPatternParserServerWebExchangeMatcher("/api/datasetfields/{id}/terms", POST), DATASET_FIELD_ADD_TERM,
```

**Thread B - Defect 2 (one-line):**

```java
// SecurityConstants.java:295-296 (before)
new SecurityRule(ALERT, new PathPatternParserServerWebExchangeMatcher("/api/alerts/{alert_id}/status", PUT),
    DATASET_FIELD_ADD_TERM),
// (after) - DATA_ENTITY_ALERT_RESOLVE is the documented + FE-gated alert-resolve permission
new SecurityRule(ALERT, new PathPatternParserServerWebExchangeMatcher("/api/alerts/{alert_id}/status", PUT),
    DATA_ENTITY_ALERT_RESOLVE),
```

(Add the `DATA_ENTITY_ALERT_RESOLVE` static import; the `ALERT` context type + `alert_id` extractor are already correct - only the permission token changes.)

**Thread C - Class-level fix (recommended follow-up issue, not blocking the two one-liners):** add a build-time validator (Java compile-time annotation processor or Maven enforcer rule) that pairs each `SECURITY_RULES` entry with the OpenAPI operationId at the same path + verb, and fails the build if the documented permission tag in OpenAPI does not match the SecurityConstants wiring. Catches the WHOLE family at CI time.

**Corrected 2026-06-10 (user-facing verification sweep):** the original draft's suggested fix for Defect 2 named `ALERT_PROCESSING_RESOLVE` / an `ALERT_PROCESSING_*` "family"; no such permission or family exists in `PolicyPermissionDto` (verified by reading the enum) - the alert-resolve permission is `DATA_ENTITY_ALERT_RESOLVE` (`PolicyPermissionDto.java:27`), which is also what the FE gates on and what the live doc names. Also corrected: the dataset-field path is `/api/datasetfields/{dataset_field_id}/terms` (not `{id}`), the Defect-1 rule spans `:297-299` (permission token on :299). Added the FE trace (both buttons gate on the documented permissions, turning a BE-only assertion into a verified FE/BE mismatch) and the RBAC-runtime caveat (the actual 403 / leak is observable only under custom roles in a non-DISABLED auth mode). The structural mismatch is fully settled by code; `user_facing_verified` stays `false` because the observable 403 needs a live RBAC drive.

Doc-side caveat: the live `permissions` page already documents BOTH mis-gates as operator caveats (`permissions.md:23,26,41`); no doc-side fix is needed because the docs are correct - the code is wrong. PLT-061's fix unblocks the existing doc.
