## ⚠️ VERIFICATION 2026-06-08 — CLARIFY before implementing

> **Adversarial fact-check (sev MEDIUM).** Two mechanism errors: endpoint is GET /api/titles (not /api/owners/titles); server DOES name-filter (containsIgnoreCase + SearchParam). Real cause: UI fetches once on dropdown-open with empty query + client-filters the 30-row id-ASC window. Fix the endpoint + reframe the mechanism.
>
> Full report: `lineage/odd-platform/harvest/2026-06-08-doc-verification.md`.

## Description

When an operator assigns an Owner role ("title", e.g. `Steward`, `Subject Matter Expert`, `On-call`) on a data entity, the title field is a free-text autocomplete backed by `GET /api/owners/titles`. Two facts combine into an operator-visible trap:

1. The **server hardcodes id-ASC ordering** (oldest title first) on the paginated list query — there is no name match or relevance sort on the server side; the `query` is applied as a name filter but the page is ordered by `id` ascending.
2. The **UI fetches only the first page, `size=30`**, and does the query filtering client-side over that 30-row window.

The consequence: in any deployment that has accumulated more than 30 titles, the 31st-oldest title onward is **unreachable by the autocomplete regardless of what the operator types** — the matching row may exist in the database but never enters the 30-row window the client filters. The operator sees no suggestion, assumes the title does not exist, and (because the field is free-text / freeSolo) types it again — minting a duplicate title row. This is a silent feeder for the title-duplication problem and is undocumented today. The Owner-name autocomplete has the same shape; owners.md already documents Owner-name case/whitespace duplicates but not the title-window-clipping mechanism.
