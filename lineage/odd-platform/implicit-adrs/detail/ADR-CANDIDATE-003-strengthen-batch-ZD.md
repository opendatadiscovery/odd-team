## STRENGTHENS — Batch ZD (RBAC reads + Integration wizard + PermissionController class-level — 4 new read-surfaces join the read-collaborative-GET family)

**Four new read-surface sidecars promote ADR-CANDIDATE-003's support count from 13 (post batch-M) to 17.** The pattern is now anchored across detail / lineage / attachments / directory / alerts / activity / search / facets / permissions discovery / identity / integrations / policy management — i.e. EVERY major read surface in the platform.

**New surfaces (batch ZD)**:
- **PermissionController.getResourcePermissions (CLASS-LEVEL)** — class-scope confirmation of batch-E's controller-method finding. The 27-line file is uniformly `@PreAuthorize`-free; `SecurityConstants.java:98-355` contains zero entries for `/api/resource/.../permissions`. Per `implicit_adrs[1]`: "Read-side endpoint is intentionally NOT in `SECURITY_RULES` — the read-collaborative posture. Any authenticated user can query their own permissions on any resource because the response reveals only what the policy graph would already grant them."
- **PolicyController read endpoints (CLASS-LEVEL)** — THREE separate read endpoints (`getPolicyDetails`, `getPolicyList`, `getPolicySchema`) share the read-collaborative posture. NONE has a SECURITY_RULES entry. Per `bugs_limitations_corner_cases[3]`: "Read-side authorization gap is class-wide. Three of the six controller methods have NO entry in `SecurityConstants.SECURITY_RULES`. They fall through to `AuthorizationCustomizer.java:29-30`'s catch-all and are gated only by AUTHENTICATION, NOT by any Permission. Any authenticated user can: (a) enumerate every policy by id and read every policy's statements; (b) hit `GET /api/policies` and see policy NAMES; (c) hit `GET /api/policies/schema` and read the full JSON-Schema document including the entire Permission enum partition." — this is the **widest read-collaborative blast radius observed for the RBAC management surface itself**: any authenticated low-privilege user can read MANAGEMENT/ALL policy statements, learning the platform's RBAC structure.
- **IntegrationController.getIntegration + getIntegrationPreviews (CLASS-LEVEL)** — TWO read endpoints; NO `INTEGRATION_*` permission exists in `PolicyPermissionDto` (grep returns zero matches); both fall through to `.authenticated()`. Per `implicit_adrs[1]`: "The wizard surface is open-read by design — neither `SecurityConstants.SECURITY_RULES` nor `PolicyPermissionDto` defines an `INTEGRATION_*` permission, despite the parallel pattern of explicit SecurityRule entries for the namespace, datasource, term, tag, query-example, reference-data, owner-association, role, and policy controllers. This aligns with the live wizard doc's framing of the wizard as a copy-paste affordance for collector setup."
- **IdentityController.whoami (CLASS-LEVEL)** — surfaced indirectly: the controller deliberately omits `@PreAuthorize` per `implicit_adrs[1]` — "whoami is the SOURCE of authorization, not a gated operation". Whoami occupies a special place in the read-collaborative-GET family: it is the META-read whose response shape DEFINES the policy graph for every other read. Different in kind from the resource-data reads (alerts/activity/search/etc.) but in the same architectural family.

**New surfaced_by entries**:
- `odd-platform__java__PermissionController__controller-class__PermissionController.md:implicit_adrs.[1]` ("Read-side endpoint is intentionally NOT in `SECURITY_RULES` — the read-collaborative posture. The decision is consistent across the controller package: `SecurityConstants.SECURITY_RULES` overwhelmingly enumerates mutations (POST/PUT/PATCH/DELETE); read endpoints fall through to `authenticated()` unless they expose data that the user's policies should gate. This endpoint is the canonical case of 'reads return what the policy resolves; gating the read would be tautological'.")

- `odd-platform__java__IntegrationController__controller-class__IntegrationController.md:implicit_adrs.[1]` ("The wizard surface is open-read by design — neither `SecurityConstants.SECURITY_RULES` nor `PolicyPermissionDto` defines an `INTEGRATION_*` permission")

**New cross-link gap** (the PolicyController surface is the most-sensitive read-collaborative case):
- **REFACTOR-617 NEW** — PolicyController.getPolicyDetails confidentiality exposure: any non-admin user can iterate policy ids and read MANAGEMENT/ALL policy statements via `GET /api/policies/{id}`. The blast radius is the RBAC system's own configuration — useful reconnaissance for credential-theft escalation. Same shape as REFACTOR-024 (alerts) / REFACTOR-053 (activity) / REFACTOR-187 (search) / REFACTOR-200 (detail) / REFACTOR-203 (lineage) but pointing at the META-LAYER (the policies themselves) rather than at platform data.

**Architectural refinement**: The four new surfaces extend the read-collaborative-GET coverage to:
- **Permission discovery (meta-layer)**: `getResourcePermissions` confirms at class scope; the architectural commitment that "reads reveal what the policy already grants" is whole-file.
- **RBAC management read surface (meta-meta layer)**: PolicyController's THREE reads reveal the RBAC system's own configuration to any authenticated caller — the widest meta-layer blast radius.
- **Integration wizard surface**: a NEW axis joining the family — wizard manifests are documentation artefacts authored by collector developers; the open-read posture aligns with the wizard's framing as a copy-paste affordance.
- **Identity meta-read**: the special whoami case — the SOURCE of authorization, deliberately rule-free.

**Updated support count**: 17-sidecar coverage (was 13 after batch M). The pattern now covers nearly every read surface in the platform.

**Severity unchanged**: HIGH — security-posture decision affecting every read endpoint.
