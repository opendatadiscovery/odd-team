## What

A namespace name is stored in a `varchar(64)` column with no application-level length validation. If a user submits a namespace name longer than 64 characters, Postgres raises a "value too long for type character varying(64)" error; the platform does not translate this into a clean `400 Bad Request`, so the caller gets an opaque `500` (`DatabaseException`) with no indication that they hit a length cap. Worse, namespaces are created inline through a "select-or-create" combo box embedded on several other forms (Add-datasource, term, data-entity-group, collector, lookup-table): there, an over-long name doesn't just fail the namespace step - it propagates the 500 and **aborts the parent entity's save**, so the operator loses the whole form with an error that names neither the field nor the cause.

## Where

The database column has no length declared in the model and no `maxLength` validation upstream - the only cap is the column width:

`odd-platform-api/.../db/migration/V0_0_1__init.sql:10-17`
```sql
CREATE TABLE IF NOT EXISTS namespace
(
    id         bigserial PRIMARY KEY,
    name       varchar(64),          -- <- only length cap; no app-level validation
    is_deleted boolean NOT NULL DEFAULT FALSE,
    ...
);
```

The exception translator only handles integrity-constraint violations (SQL state class C23). A value-too-long error is SQL state class **C22** (data exception), which is **not** matched, so it falls through to a generic `DatabaseException` (HTTP 500):

`odd-platform-api/.../repository/util/ExceptionUtils.java:30-36`
```java
public static ExceptionWithErrorCode translateDatabaseException(final DataAccessException e) {
    if (e.sqlStateClass() == SQLStateClass.C23_INTEGRITY_CONSTRAINT_VIOLATION) {
        return new UniqueConstraintException(formatMessage(e.getCause().getMessage()));
    }
    log.error("Database exception", e);
    return new DatabaseException();   // <- C22 value-too-long lands here -> opaque 500
}
```

The namespace service writes the name straight through with no length guard on any path - `create` (`NamespaceServiceImpl.java:55-60`), `update` (`:64-71`), and the combo-box create path `getOrCreate` -> `namespaceRepository.createByName(name)` (`:37-39`), which is what the embedding forms hit.

The OpenAPI contract confirms no upstream cap: `NamespaceFormData.name` and `NamespaceUpdateFormData.name` are bare `type: string` with no `maxLength` (`odd-platform-specification/components.yaml:262-276`), so no bean-validation `@Size` is generated and `WebExchangeBindException` never fires for over-length input - the value reaches Postgres unguarded.

## User-facing impact

The "user" is any operator creating/renaming a namespace, or creating one inline via the select-or-create combo box embedded on the data-source / term / data-entity-group / collector / lookup-table forms.

- **WHO/WHAT (the 500):** an operator who submits a namespace name >64 chars gets a generic `500` with body code `DATABASE_EXCEPTION` and no field-level guidance. Verified end-to-end by BE trace 2026-06-10: `varchar(64)` (`V0_0_1__init.sql:13`) -> Postgres "value too long" = SQL-state class **C22**; `ExceptionUtils.translateDatabaseException` only matches **C23** integrity-constraint violations, so C22 falls through to `new DatabaseException()` (`repository/util/ExceptionUtils.java:30-36`); `DatabaseException extends ExceptionWithErrorCode`, and `ControllerAdvice` has **no** handler for `DatabaseException`/`ExceptionWithErrorCode`, so it lands on `@ExceptionHandler(Exception.class)` -> `HttpStatus.INTERNAL_SERVER_ERROR` (`controller/exception/ControllerAdvice.java`). The 500 verdict HOLDS (it just reaches 500 via the generic `Exception` fallback, not a dedicated `DatabaseException` handler - a minor precision; the user-facing result is identical).
- **The combo-box parent-save-abort (the high-severity driver) is NOT driven:** the claim that an over-long inline namespace name aborts the *parent* entity's save (losing the whole form) is a strongly-implied consequence - `getOrCreate` runs inside the parent create flow and its error propagates - but it is a UI/transaction-flow assertion that has not been exercised on a running stack. *Static trace consistent; not driven* - drive Add-datasource (and one other embedding form) with a >64-char inline namespace and confirm the parent save fails with the same opaque 500 and no field message.
- **Auth note:** namespace create requires the `NAMESPACE_CREATE` permission (`SecurityConstants.java`), so this is an authenticated-operator UX defect, not an anonymous surface.

## Why it matters

This is a loud-but-misleading failure that degrades a routine, high-frequency workflow. An operator typing a long namespace name (a paste, a descriptive label) gets a generic server error with no field-level guidance, and on the combo-box forms the failure cascades - the namespace create blows up the parent save (new data source, term, collector, etc.), so the user loses unrelated form input with a 500 that doesn't mention "name" or "length." A `500` also reads as "the server is broken" rather than "your input was invalid," inviting bug reports and eroding trust in the platform. Severity **high** because the combo box makes namespace creation a sub-step of several core create flows, so a single over-long string can abort an otherwise valid parent-entity save.

## Suggested fix

Two complementary changes:

1. **Validate length at the boundary** so a clean `400` is returned before the DB is touched - add `maxLength: 64` to the `NamespaceFormData` / `NamespaceUpdateFormData` `name` schema in the OpenAPI contract (and/or a `@Size(max = 64)` bean-validation constraint), and apply the same cap on the `getOrCreate` combo-box path so inline creation fails fast with a field-scoped message.
2. **Translate value-too-long defensively** in `ExceptionUtils.translateDatabaseException` so any C22 data exception that still reaches the repository becomes a 400-class error rather than a 500:
   ```java
   if (e.sqlStateClass() == SQLStateClass.C22_DATA_EXCEPTION) {
       return new BadUserRequestException("A submitted value is too long for its field");
   }
   ```

The validation (1) is the primary fix; the translation (2) is a backstop so the same class of overflow on any other `varchar`-bounded field never surfaces as a raw 500. Open to alternatives on the exact validation mechanism (contract `maxLength` vs bean validation).
