- **ADR-CANDIDATE-036** (NEW 2026-05-12C): The Authorization framework is mode-agnostic — the same `AuthorizationCustomizer(permissionService, extractors)` + `SecurityConstants.WHITELIST_PATHS` + `SECURITY_RULES` chain is reused VERBATIM in OAUTH2 and LDAP modes. Only the AUTHENTICATION mechanism varies between modes; AUTHORIZATION wiring is invariant
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar (`LDAPSecurityConfiguration.auth.type@L51`) but cross-validated by the parallel-structure across OAuthSecurityConfiguration.java:98 + LDAPSecurityConfiguration.java:145 (both call `.authorizeExchange(new AuthorizationCustomizer(permissionService, extractors))` with identical signatures); the LDAP sidecar EXPLICITLY names this as the mode-agnostic stance. STRENGTHENS ADR-CANDIDATE-002 from the per-mode wiring perspective: ADR-CANDIDATE-002 codifies "SECURITY_RULES is the central authz table"; THIS ADR codifies "every authentication mode that wants AUTHZ wires the same customizer".
  - **Surfaced by**:
    - `odd-platform__java__LDAPSecurityConfiguration__config-key-consumer__auth_type@L51.md:implicit_adrs.[0]` ("LDAP auth is wired through the same `AuthorizationCustomizer` + `SecurityConstants.WHITELIST_PATHS` + `SECURITY_RULES` chain that OAuth2 and LoginForm use — the authorization layer is mode-agnostic, only the authentication mechanism varies." — intent_anchor: `.authorizeExchange(new AuthorizationCustomizer(permissionService, extractors))` parallel across three SecurityWebFilterChain factories)
    - `odd-platform__java__LDAPSecurityConfiguration__config-key-consumer__auth_type@L51.md:implicit_adrs.[1]` ("LDAP authentication is treated as an enterprise / on-prem alternative to OAuth2 — both are protected by the same `@Order(Ordered.HIGHEST_PRECEDENCE)` chain and both route through `AuthorizationCustomizer`. The choice between LDAP and OAUTH2 is the operator's identity-source choice; the rest of the platform behaves identically.")
  - **Decision statement**: ODD's authorization framework is INVARIANT across authentication modes that wire it. The OAUTH2 mode (`OAuthSecurityConfiguration.java:98`) and the LDAP mode (`LDAPSecurityConfiguration.java:145`) BOTH call `.authorizeExchange(new AuthorizationCustomizer(permissionService, extractors))` with identical constructor signatures — the customizer walks `SecurityConstants.WHITELIST_PATHS` (permitAll), then `SecurityConstants.SECURITY_RULES` (per-rule Policy/Permission/Role/Owner gates), then falls through to `.pathMatchers("/**").authenticated()`. Both modes are marked `@Order(Ordered.HIGHEST_PRECEDENCE)` (LDAP at line 136), positioning LDAP as an enterprise/on-prem sibling of OAuth2 — operators choose between them based on identity-source preference, and the rest of the platform's authorization behaviour is identical. The LOGIN_FORM mode does NOT wire the customizer (LoginFormSecurityConfiguration.java:55-57 — see REFACTOR-099); the DISABLED mode does NOT wire it either (`.anyExchange().permitAll()`). The decision codifies "authorization is a posture, not a per-mode policy"; future authentication mode additions (SAML, JWT) should reuse the same customizer construction.
  - **Wisdom test**: PASS. The verbatim parallel structure across two production-targeted modes (OAUTH2 + LDAP) is the intent anchor; the same `@Order(Ordered.HIGHEST_PRECEDENCE)` ordering placement signals the mode-agnostic positioning. Structural — every future production-targeted mode must either reuse the customizer or justify a different authorization model.
