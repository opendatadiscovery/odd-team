## Description

The Term Detail tags-edit form dispatches its save with a bare `.then()` and **no `.catch()`** (`TagsEditForm.tsx:138-149`):

```tsx
const handleSubmit = (data: TermDetailsTagsFormType) => {
  dispatch(
    updateTermDetailsTags({ termId, tagsFormData: { tagNameList: ... } })
  ).then(() => {
    clearFormState();
  });
};
```

When the `updateTermDetailsTags` thunk rejects (backend 4xx/5xx, validation reject), the `.then` cleanup never runs, no rejection is handled, and — because the dialog close is driven off success (`handleCloseSubmittedForm={isTagsUpdated}` at line 124) — the operator sees the dialog stay open with the form still filled and **no error surfaced**. The save silently did nothing.

This is the same silent-failure-no-catch UX class already tracked elsewhere: PLT-059 Defect 4 (TermsForm) and PLT-060 Defect 2 (AssignTermQueryExampleForm). The Term `TagsEditForm` save path is a sibling instance that none of those items covers — PLT-060's four defects on this very file are key-on-definition, the AssignTermQueryExampleForm no-catch, slice-then-sort, and the tag-create RBAC bypass (Defect 4 touches `TagsEditForm`, but for the `TAG_CREATE` bypass, not the missing `.catch`). So this `.then`-without-`.catch` instance is genuinely untracked and the right home is to fold it into PLT-060 as an additional defect.

**Typed gate: characterization-pin (known bug), per LSN-029.** The save-with-no-catch is current, unfixed behaviour. This PINS it with a test that asserts the CURRENT (incorrect) behaviour — on a rejected dispatch, no error is shown and the dialog/form is NOT cleared — GREEN today, RED the instant a `.catch` (error toast / inline error) is added. Not `@Disabled`; a live tripwire that flips when the fix lands.
