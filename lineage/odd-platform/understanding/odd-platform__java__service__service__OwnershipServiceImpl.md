# OwnershipServiceImpl — semantic understanding

## understanding

`OwnershipServiceImpl` is the **service-tier owner of the ownership lifecycle** — three reactive transactional methods (`create`, `delete`, `update`) that bind an Owner to a Data Entity via a Title, plus a private `propagateIfDEG` helper that cascades the operation to every child of a Data Entity Group. The class is THE single service entry point for the three `POST/PUT/DELETE /api/dataentities/{data_entity_id}/ownership` controller methods on `DataEntityController.createOwnership/deleteOwnership/updateOwnership` (`<odd-platform-repo>/odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/controller/DataEntityController.java:165-191`), and the load-bearing semantics it embodies are: (1) **NO permission gate at the service** — authorization is enforced upstream at the `SecurityConstants.SECURITY_RULES[215-227]` SecurityRule chain; the service trusts the controller pipeline has already evaluated `DATA_ENTITY_OWNERSHIP_CREATE/UPDATE/DELETE` per-data-entity, and there is **no fall-back `OWNER_CREATE` check** even though the service can mint new Owner directory rows via `ownerService.getOrCreate(formData.getOwnerName())` at line 52 (REFACTOR-199 anchor); (2) **owner + title both auto-create on miss** at lines 52-53, expanding both the Owner directory and the Title directory with caller-supplied free-text names and emitting **no `@ActivityLog`** on the directory mutations themselves; (3) **`@ReactiveTransactional` boundary lives at the service, not the controller or the repository** (lines 49, 78, 101) — the owner-upsert + title-upsert + ownership-row INSERT + DEG-propagation + search-vector refresh + `data_entity_filled.OWNERS` mark are atomic per request; (4) **duplicate-prevention surfaces as HTTP 400 USR003**, NOT 5xx as the batch-F `DataEntityController.createOwnership` sidecar incorrectly claimed — the path is `ReactiveOwnershipRepositoryImpl.create` (plain INSERT) → DB-level `UNIQUE (data_entity_id, owner_id)` violation → `JooqReactiveOperations.mono(...).onErrorMap(DataAccessException.class, ExceptionUtils::translateDatabaseException)` → `UniqueConstraintException("Ownership for this data entity and owner already exists")` (`ExceptionUtils.java:69-71`) → `ControllerAdvice.handleUniqueConstraint` → `HttpStatus.BAD_REQUEST` (`ControllerAdvice.java:36-40`); (5) **`@ActivityLog(event = OWNERSHIP_*)`** annotates each public method (lines 48, 77, 100), emitting per-method audit-feed events captured by the three `*ActivityHandler` siblings via BEFORE/AFTER `getOwnershipsByDataEntityId` calls — but the DEG-propagation cascade (lines 121-149) inserts/deletes N child ownership rows with NO per-child activity emission (only the parent event fires); (6) **DEG-propagation is `propagate: Boolean` opt-in** at the form-data level (line 62), is gated by `DATA_ENTITY_GROUP` entity-class membership (lines 124-131), and uses **title-overwriting** UPSERT semantics on existing child rows (`createOrUpdate` → `onConflictOnConstraint(...).doUpdate().set(TITLE_ID, EXCLUDED.TITLE_ID)` per the batch-H `ReactiveOwnershipRepositoryImpl` sidecar).
