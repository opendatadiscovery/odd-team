## Description

The `PUT /api/dataentities/{id}/description` response is built from the **request payload**, not from the value the database actually stored — the two can diverge, and the entity-description page does not warn a programmatic caller about it.

`DataEntityServiceImpl.upsertDescription` (`DataEntityServiceImpl.java:325-332`) returns `new InternalDescription(formData.getInternalDescription(), linkedTerms)` (line 331) — i.e. it echoes back the exact `internal_description` string the caller submitted. Meanwhile the persistence layer normalises before writing: `ReactiveDataEntityRepositoryImpl.setInternalDescription` (line 431) does `final String newDescription = StringUtils.isEmpty(description) ? null : description` and writes `newDescription` to the column. So a caller who submits an **empty string** (`""`) receives a `200` whose `internal_description` is `""`, while the row stores `NULL`. (`StringUtils.isEmpty` tests only null/zero-length, so a whitespace-only body such as `"   "` is *not* collapsed — it is stored verbatim; the divergence that the code guarantees is specifically the empty-string → NULL collapse.)

The in-app UI never observes the divergence because it re-fetches the entity on the next page load and renders the GET (canonical, persisted) value. A third-party API client that trusts the PUT response as the persisted state — e.g. caching it, or asserting on it in a test — will hold a value the platform did not store. DOC-187 documents the empty-string → NULL collapse as a persistence fact ("mapping the empty string to `null`", `entity-description.md:25`) but does **not** note that the PUT response is decoupled from that collapse. This item adds the decoupling caveat.
