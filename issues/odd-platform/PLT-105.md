## What

Several feature/notification config keys are bound with bare SpEL placeholders that carry no in-expression default, so the documented default value lives ONLY in the shipped `application.yml` — and an operator who writes a minimal externalised config that omits the key bricks startup with an opaque `BeanCreationException: Could not resolve placeholder`, not the documented default:

1. **`${datacollaboration.enabled}` / `${notifications.enabled}`** are bound in `FeatureResolver` / `FeatureResolverImpl` without a `:false` SpEL default. Omitting either key in an override config fails JVM startup. (The Features page documents these as boot-immutable `@Value` flags and recommends "edit config and restart" — exactly the workflow that triggers the crash.)
2. **`notifications.message.downstream-entities-depth`** is bound in `NotificationConfiguration` with no `@Value` default (the documented default `1` lives only in shipped `application.yml`). An operator who sets `notifications.enabled=true` but omits the depth key in an override gets a startup failure.

Stock installs are safe because the bundled `application.yml` supplies the defaults; the trap is sprung only on a minimal externalised config — i.e. the production hardening path.

Sources: HARVEST-002, HARVEST-010 (doc-understanding harvest, 2026-05-29). Doc caveats tracked at `backlog/docs/DOC-295.md` and `backlog/docs/DOC-296.md`.

## Why it matters

The recommended way to enable/disable these features is to externalise config and restart — which is precisely the path that omits a key and crashes the boot. The failure is opaque (`Could not resolve placeholder`), gives no hint which feature key is missing, and prevents the platform from starting at all. An operator hardening a production deployment by trimming `application.yml` to only the keys they intend to set hits a wall the docs actively steer them toward. This is the LSN-001/002 class: a default-handling gap that converts a routine config edit into a non-starting platform.

## Suggested fix

- Add explicit SpEL defaults: `${datacollaboration.enabled:false}` and `${notifications.enabled:false}` in `FeatureResolver` / `FeatureResolverImpl`, and a default on `notifications.message.downstream-entities-depth` (`@Value("${...:1}")`) in `NotificationConfiguration` — matching the values currently only in the bundled `application.yml`.
- As a general pattern, audit `@Value`/`${...}` bindings for missing `:default` segments across the config classes; a startup self-check or a test that boots with a minimal config would catch the class.
