## What

Policies use soft-delete (`deleted_at`). The **list** path (`PolicyServiceImpl.list` → `policyRepository.list`) inherits the soft-delete base-class filter (`WHERE deleted_at IS NULL`), so a deleted policy disappears from the Policies tab. But the **grant** path `getRolesPolicies` does **not** filter `deleted_at`:

```java
// ReactivePolicyRepositoryImpl.getRolesPolicies (@ ede5d277)
final SelectConditionStep<Record> query = DSL.select(POLICY.fields())
    .from(POLICY)
    .join(ROLE_TO_POLICY).on(ROLE_TO_POLICY.POLICY_ID.eq(POLICY.ID))
    .where(ROLE_TO_POLICY.ROLE_ID.in(roleIds));   // no deleted_at IS NULL
```

So a role still bound to a soft-deleted policy **keeps being granted that policy's permissions** on every authorized request. The policy is invisible in the UI but live in the permission resolver — a catalogue-vs-grant asymmetry.

## Where

| File | Lines | Role |
|------|-------|------|
| `odd-platform-api/src/main/java/.../repository/reactive/ReactivePolicyRepositoryImpl.java` | `getRolesPolicies` (≈ L32-38) | grant-path join over `POLICY` ⋈ `ROLE_TO_POLICY` with **no** `deleted_at IS NULL` predicate |
| (contrast) the same class's `list` / soft-delete base class | — | list path filters `deleted_at IS NULL`, so the UI hides the deleted policy |

Verified by the triager @ ede5d277.

## Why it matters

An operator who deletes a policy through the UI sees it vanish and reasonably concludes the access it granted is revoked. It is not — every role still bound to it keeps the permissions until the binding is removed by hand. This is a silent no-op of the operator's security intent (LSN-001 shape): the deletion appears to succeed but does not revoke. In a least-privilege / offboarding workflow this leaves stale grants live indefinitely.

## Suggested fix

- Add `POLICY.DELETED_AT.isNull()` to the `getRolesPolicies` query (and audit any other grant/permission-resolution query that joins `POLICY` / `ROLE_TO_POLICY` for the same omission).
- Alternatively, hard-revoke: on policy soft-delete, also remove its `ROLE_TO_POLICY` bindings (so the UI delete matches the grant effect) — but the filter is the smaller, safer change.
- Add a test: bind a role to a policy, soft-delete the policy, assert the role no longer resolves that policy's permissions.
