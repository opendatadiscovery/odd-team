- **ADR-CANDIDATE-042** (NEW 2026-05-12C): Notification fan-out is **fail-soft per channel** — a sender exception is caught at the processor layer, logged at ERROR, and the loop continues to the next sender. The next WAL message is still processed. This encodes a "one bad channel does not block the others" stance, but also means a misconfigured webhook is invisible to operators outside log inspection
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar (`NotificationsProperties`) but the pattern matches ADR-CANDIDATE-028's continue-on-failure orchestration for partitions — codebase-wide convention for multi-target operations
  - **Surfaced by**:

  - **Decision statement**: The `AlertNotificationMessageProcessor.process` method iterates `List<NotificationSender>` for each `AlertNotificationMessage`, calling `.send(...)` per sender inside a `try/catch (NotificationSenderException)` block. On exception, the failure is logged at ERROR level naming the failing channel's `receiverId()` and the loop continues. The next sender in the list is still invoked; the next WAL message is still processed. The decision codifies "one bad channel does not block the others" as the operational stance — a misconfigured webhook does not stop email or Slack from working, and a temporary Slack outage does not stop the WAL from progressing past the alert. The trade-off: silent partial-failure outside log inspection (the platform has no DB record that delivery failed, no metric counter, no Prometheus gauge — REFACTOR-127 captures this gap). The pattern parallels ADR-CANDIDATE-028's continue-on-failure orchestration for partition managers; both encode "best-effort across a list of independent operations" as the project's convention for fan-out-shaped problems.
  - **Wisdom test**: PASS. The explicit try/catch-log-continue construction is the intent anchor; the alternative (fail-stop on first exception, no further senders invoked) would be simpler to implement and the maintainer chose the more-complex try/catch precisely to encode the fail-soft posture. Structural for every future notification channel addition.

  - **Existing ADR**: none. Composes with ADR-CANDIDATE-028 (continue-on-failure orchestration for partitions) — folding both into a unified "best-effort-fan-out" project convention ADR is a maintainer triage option.
