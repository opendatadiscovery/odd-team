## What

The lookup-table **edit** form reuses the **create**-shaped form data type and therefore carries a `namespaceName` field on the wire, even though namespace is not editable on update. In the UI the namespace control is **disabled** in edit mode (greyed out, pre-filled with the current namespace), so the operator cannot change it - yet the field is still part of the submitted payload. On the contract side the UPDATE schema (`LookupTableUpdateFormData`) has only `name` and `description`; it has no `namespace_name` property. So the disabled namespace value the form sends is **silently discarded by the server** - there is no error and no confirmation. The end behaviour (namespace is immutable on edit) is honest, but the path is confusing: the form ships a value the contract drops on the floor, which is easy to misread (in code or by a future maintainer) as "namespace can be changed on edit" when it cannot.

## Where

The edit form is typed with the **create** shape `LookupTableFormData` and submits the whole `data` object (including `namespaceName`) as the update payload:

`odd-platform-ui/src/components/MasterData/LookupTableForm.tsx:49,60-66`
```tsx
const { handleSubmit, control, reset, formState } = useForm<LookupTableFormData>({  // line 49 - CREATE shape, has namespaceName
  ...
});
...
const onSubmit = useCallback(
  (data: LookupTableFormData) => {
    const mutation$ = lookupTable
      ? editLookupTable({
          lookupTableUpdateFormData: data,        // line 63 - full create-shaped data sent as the UPDATE body
          lookupTableId: lookupTable.tableId,
        })
      : addLookupTable({ lookupTableFormData: data });
```

The namespace control is disabled (and un-required) precisely in edit mode (`LookupTableForm.tsx:119-121`: `disabled={!!lookupTable}` / `rules={{ required: !lookupTable }}`), confirming it is non-editable on update - yet its value still rides along in `data`.

The UPDATE contract has no `namespace_name`, so the server discards it:

`odd-platform-specification/components.yaml:3853-3862`
```yaml
LookupTableUpdateFormData:
  type: object
  properties:
    name:
      type: string
    description:
      type: string
  required:
    - name
```

(Contrast the CREATE shape immediately above it, `LookupTableFormData` at `components.yaml:3840-3851`, which declares `name`, `description`, **and** `namespace_name`, with `name` + `namespace_name` required.)

## Why it matters

This is a contract/UI honesty defect, not a data-loss or security hole: namespace is genuinely immutable on update and the server's discard makes that true. The cost is confusion and fragility - the wire payload carries a field the contract ignores, the form is typed as the create shape on an update path, and a reader cannot tell from the form code alone whether namespace edits are honored or dropped. It is the kind of quiet mismatch that misleads the next maintainer and produces "I changed the namespace and it didn't save, with no error" reports. Medium severity, pending the discard-vs-reject decision below.

## Suggested fix

Decide between two honest contracts and align the form to it:

- **Discard (status quo, made explicit):** keep namespace immutable on update, but type the edit form to the UPDATE shape (`LookupTableUpdateFormData`) so `namespaceName` is never submitted on edit - i.e. split the form data type rather than reusing `LookupTableFormData` for both create and update (`LookupTableForm.tsx:49,60-66`). Optionally document the immutability as an operator caveat.
- **Reject:** if sending a non-editable field should be a contract error, have the UPDATE endpoint reject an unexpected `namespace_name` (or a changed value) rather than silently dropping it.

The discard-vs-reject choice gates the final severity; it is being resolved by probes `PENDING-F-058-1` / `PENDING-F-026-1` (lookup-table create/update round-trip), referenced in the F-058/F-026 feature flows. This may legitimately land as a documentation caveat plus the form-type split rather than a server change. Open to alternatives.
