## What

Five UX defects on the alerting surface that together make alerts impractical at scale. Each is small in isolation; together they push operators to direct API calls. Doc-side mitigation (DOC-200 + DOC-201) names these as known limitations today. All five re-verified 2026-06-10 against the components (line numbers corrected; the "unprivileged" framing on Defects 2-3 corrected to ownership-based - see below).

**Defect 1 - Per-entity Alerts tab hardcoded `size=30`, no filter UI, no export.** `DataEntityAlerts.tsx:31` hardcodes `const size = 30`; the render (`:51-90`) is just a header + infinite-scroll list with no filter / sort / status selector and no export affordance. HOLDS.

**Defect 2 - Bare-`/alerts` auto-redirect lands every user on the cross-owner All tab.** `AlertsRoutes.tsx:18` declares `<Route path='/' element={<Navigate to='all' replace />} />`. Every user lands on `/alerts/all` (cross-owner feed). For users with no ownership association (not "unprivileged" - see Defect 3), All is the ONLY visible tab. HOLDS (framing corrected).

**Defect 3 - AlertsTabs `hidden` hides the My/Dependents tabs but their routes remain navigable.** `AlertsTabs.tsx:30, :36` set `hidden: !showMyAndDepends` on the My Objects / Dependents tabs. `showMyAndDepends` is `!!useAppSelector(getOwnership)` (`Alerts.tsx:20,27`) - i.e. it is driven by whether the current user has an OWNERSHIP association, NOT by RBAC permission. The routes `/alerts/my` and `/alerts/dependents` remain mounted unconditionally in `AlertsRoutes.tsx:13-16`, so a user who knows the URL reaches them even when the tab is hidden; the list then renders via the my/dependents thunk and is typically empty for a user with no ownership - visually indistinguishable from "no alerts." HOLDS (the "no user_owner_mapping -> empty" outcome is the runtime consequence of the ownership-gated tab; the structural facts - tab hidden, route still mounted - are code-confirmed).

**Defect 4 - Global Alerts list has no filter UI.** `AlertsList.tsx` (`:83-106` render) has no status / type / date / entity-name filter; `const size = 30` is hardcoded at `:72`. HOLDS. (The original draft's "sibling Activity page has a 7-facet filter panel" is a comparison aside, not load-bearing; the load-bearing fact is that Alerts has no filter UI, which holds.)

**Defect 5 - Global Alerts list has no bulk-resolve, no export, no search-by-entity-name.** `AlertsList.tsx:95-97` maps `alerts` to one `<AlertItem>` per row with no bulk-select scaffolding; `AlertItem.tsx` is a single-row Resolve/Reopen (`AlertItem.tsx:158-166`). HOLDS.

## User-facing impact

WHO: any operator on the Alerts surface. WHAT they do / observe (verified by FE/BE trace 2026-06-10):
- The "My Objects" and "Dependents" tabs are gated on `!!getOwnership` (an OWNERSHIP association), NOT on RBAC (`Alerts.tsx:20,27`; `AlertsTabs.tsx:30,36`). An operator with no owner association sees only the "All" (cross-owner) tab; a shared `/alerts/my` link still mounts the route (`AlertsRoutes.tsx:12-18`) and renders an empty list with no "you have no ownership" empty-state.
- The list page size is a hardcoded `const size = 30` (`AlertsList.tsx:72`; per-entity `DataEntityAlerts.tsx:31`) with no filter UI, no sort control, and no bulk-select/bulk-resolve (`AlertsList.tsx:83-106`, `:95-97`) - one `AlertItem` per row, single-row Resolve only. A team with hundreds of open alerts cannot scan or triage by status/type/entity/time, and the doc-suggested audit-export workaround has no UI affordance.
All five are pure FE code-structure facts settled by reading the components; no runtime drive needed (flag flipped true).

## Why it matters

Alerts are an operator's primary diagnostic surface. The five defects compound: the doc-recommended audit-export workaround cannot be exercised through the UI; users without an ownership association land on the cross-owner feed with no path to a scoped view; shared links to `/alerts/my` reach empty pages with no diagnostic (no "you have no ownership" empty-state); teams with hundreds of open alerts cannot scan by status / type / entity / time.

## Suggested fix

**Defect 1** - status filter on per-entity tab + page-size selector + Export button on the API workaround.

**Defect 2** - `AlertsDefaultRedirect` component reading `getOwnership`:
```tsx
- <Route path='/' element={<Navigate to='all' replace />} />
+ <Route path='/' element={<AlertsDefaultRedirect />} />
// ownership present -> 'my'; otherwise 'all'; /alerts/my surface gets empty-state CTA
```

**Defect 3** - give `/my` and `/dependents` an ownership-aware empty-state (a "you have no owned objects" CTA) rather than a blank list; optionally redirect to `/all` when ownership is absent. (Note: this is an ownership-scope UX gap, not an RBAC bypass - the my/dependents lists are owner-scoped server-side regardless of the tab being hidden.)

**Defect 4** - Filters component analogous to Activity (minimum: status + type).

**Defect 5** - bulk-select + bulk-resolve UI (backend already supports per-alert PUT; per-row permission re-check, as `AlertItem.handleResolve` already does for the single-row case).
