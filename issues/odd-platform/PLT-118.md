## What

Attachment chunked-upload staging is **node-local** and there is **no configuration key** to change it. The chunk base path is a hard-coded constant; the per-upload chunk directory is created at *initiate* time on whichever replica handled that request, and each chunk POST is written to `/tmp/odd/chunks/{uploadId}/{index}` on whichever replica receives it. This applies to **both** `attachment.storage=LOCAL` and `attachment.storage=REMOTE` — the chunk-staging path is upstream of the storage-backend dispatch, so even REMOTE (S3/MinIO) uploads are assembled on the container's local filesystem first.

In the standard multi-replica Kubernetes posture (N API replicas behind a normal, non-sticky load balancer), this breaks: if `initiate` and the chunk POSTs land on different replicas without a shared volume backing `/tmp/odd/chunks`, the chunk write hits a directory that does not exist on that replica (`NoSuchFileException`), or chunks scatter across replicas and `complete` finds an incomplete set. The failure is intermittent and non-deterministic — an upload "sometimes" fails with an opaque 500 and succeeds on retry only if the retry happens to hit the initiating replica. It is invisible to operators who validated uploads on a single-replica dev stack.

**Scope vs. existing items — this is the multi-replica dimension, not the restart dimension.** The container-restart / ephemeral-`/tmp` case (an upload lost when a single container restarts mid-upload) is already documented in **DOC-253** (Caveat 1) and the chunk-staging persistent-volume question was explicitly declared *out of scope* in **PLT-086** ("persistent chunk staging volume — a deployment-time / packaging decision, not a code defect"). PLT-118 is the distinct, not-yet-covered failure: **multi-replica request routing**, where the upload fails even with zero restarts because two requests of the same upload land on two different replicas. PLT-086's "it's a Helm/packaging concern" framing does not address this — a shared volume alone is insufficient without either sticky routing or an application-level change, and there is no config key to point staging at that shared volume regardless. This argues for an application-code fix (below), not only a chart change.

## Why it matters

Multi-replica behind a round-robin load balancer is the **most common production deployment** of the platform. In exactly that posture, attachment uploads fail intermittently with opaque 500s — a maddening, non-deterministic user experience that operators cannot reproduce on a single-replica dev stack. REMOTE operators are doubly surprised: they paid for S3 persistence expecting it to remove local-disk dependence, but the chunk window still pins each upload to one replica. The absence of any config key (`attachment.chunk.path` or equivalent) means an operator cannot even point staging at a shared volume as a stopgap without changing the constant in source.

Severity **medium** (data-loss-adjacent, not a security issue): uploads fail or lose in-flight chunk state, but no persisted data is corrupted and no data is exposed. It is an availability/reliability defect in the standard HA topology.

## Suggested fix

The reflection's `proposed_fix_anchor` offers two routes; either resolves it at the code level rather than punting to packaging:

1. **Bake chunk staging into the storage strategy** — for REMOTE, stream chunks directly to an S3/MinIO multipart upload (the SDK supports server-side multipart assembly), removing local staging from the REMOTE path entirely. This eliminates the multi-replica failure for REMOTE deployments outright.
2. **Parameterise the chunk path** — replace the hard-coded `CHUNK_BASE_PATH` constant (`FileUtils.java:24`) with an `attachment.chunk.path` config key so operators can point staging at a shared (RWX) volume, AND document the shared-volume + sticky-routing requirement for the LOCAL path.

Preferred: (1) for REMOTE (it is the deployment that most expects local-disk independence) plus (2) for LOCAL. Open to alternatives.

This is the **upstream code companion** to **DOC-319** — the operator-facing deployment caveat documenting the node-local chunk-staging limitation + the shared-volume / sticky-routing requirement while this fix is in flight.
