## Description

The platform's list endpoints share an undocumented pagination-validation gap, confirmed across multiple features by the feature-reflection pass. No layer (controller `@Min`/`@Max`, OpenAPI `minimum`/`maximum`, or repository clamp) bounds the page parameters:

- **`size` is unbounded.** `size=1000000` / `size=MAX_VALUE` issues a wide scan; `size=null` on some endpoints returns the entire table. A DoS / latency-cliff surface on large deployments — and several docs nudge operators toward large sizes for export.
- **`page=0` produces a negative OFFSET → opaque HTTP 500**, not a clean 400. The platform uses 0-indexed pagination internally but the public convention is 1-indexed; a caller following the 0-indexed habit gets a server error with no actionable message. `page=null` NPEs on some endpoints.

This is a platform-wide pattern, not a single-endpoint bug. Per-endpoint code-fix instances are already filed (PLT-134 — per-entity alerts; PLT-050 — alerts size-30; PLT-037-adjacent — namespace surface). This item documents the operator-facing contract as a known limitation; the platform-wide `@Min(1)`/`@Max` + repo-clamp code fix is a follow-up upstream epic (see Implementation Notes).

Affected loci (feature-reflection): F-037/H-010 (relationships `page=0` negative OFFSET + `page=null` NPE), F-021/H-012 (activity `size` unbounded), F-028/H-010 (namespaces `size=100000`), F-174/H-006 (owner_association_request/activity no page-size cap, page size 30), F-014/H-003 (per-entity alerts — PLT-134), F-031 (datasource search).
