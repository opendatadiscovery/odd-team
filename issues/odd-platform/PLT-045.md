## What

`POST /ingestion/entities` is the load-bearing collector ingestion endpoint. Three orthogonal defects on the error-contract + observability surface mean custom-collector authors writing retry-with-backoff get the wrong signals - every distinguishable client-error condition currently surfaces as HTTP 5xx, the row-lock contract has no signal for contended writes, and the rollback-path logs are empty.

**Defect 1 - 3 client-error conditions all surface as HTTP 5xx (F-096a).** Verified at primary source:
- **Duplicate ODDRN in batch** -> `Collectors.toMap(DataEntityIngestionDto::getOddrn, identity())` at `IngestionServiceImpl.java:86` uses the DEFAULT throwing merger -> `IllegalStateException: Duplicate key` -> no `@ExceptionHandler` advice on the ingestion controller -> HTTP 5xx.
- **Unknown `data_source_oddrn`** -> `dataSourceRepository.getIdByOddrnForUpdate(...).switchIfEmpty(Mono.error(() -> new NotFoundException(...)))` at `IngestionServiceImpl.java:68-69` raises `NotFoundException` -> uncaught at the ingestion controller -> HTTP 5xx.
- **Oversized payload** -> Spring's body codec raises `DataBufferLimitException` -> HTTP 5xx.

A collector author following the integrations doc writes retry-with-backoff on 5xx; the retry storm against a duplicate-ODDRN payload pegs the platform for the entire retry budget. Same shape for unknown-datasource.

**Defect 2 - `data_source_oddrn` row-lock held for FULL pipeline duration (F-096b).** `dataSourceRepository.getIdByOddrnForUpdate(...)` at `IngestionServiceImpl.java:66-68` issues a Postgres `SELECT ... FOR UPDATE` against the `data_source` row at the head of the `@ReactiveTransactional ingest(...)` pipeline; the lock is held for the FULL pipeline duration (datasource resolution + 14-processor chain + OTLP export). Two concurrent collectors emitting to the SAME datasource serialise on the lock; the loser may exceed the transaction timeout -> 5xx with **no `Retry-After` header**, no 429 signal.

**Defect 3 - Zero `log.*` calls in the ingest body (F-096c).** `@Slf4j` annotation at `IngestionServiceImpl.java:53` materialises a `log` reference. The `ingest(...)` method body at lines 65-94 has ZERO `log.*` invocations - even at DEBUG. Operators looking at platform logs see only the exception trace, not the discriminator (collector-id, datasource-oddrn, entity count). The SRE response window is doubled: needs platform-side application-log access to find the actual exception.

## Why

Custom-collector authors write retry-with-backoff against the public ingestion contract. The platform currently returns the same status (5xx) for "your batch had a duplicate ODDRN" (client bug) and "the platform crashed" (platform bug). Retry storms against the former pile on the platform for the entire retry budget; retry storms against the latter never recover.

The row-lock contention dimension compounds this: under any concurrent-collector deployment (the platform's expected pattern), two collectors emitting to the same datasource serialise. Without a 429 + `Retry-After`, the loser's retry storm worsens the contention.

The logging absence makes SRE response 2-3x slower - the only signal in collector logs is "HTTP 500"; the actual exception (and the discriminator that scopes the failure to a specific batch / datasource / entity count) only lives in the platform application log, which collector-side responders typically can't reach.

## How

Per-defect fix:

**Defect 1 - structured error responses:**

```java
// In IngestionServiceImpl.ingest, change the duplicate-key merger:
.map(dtos -> dtos.stream()
    .collect(Collectors.toMap(
        DataEntityIngestionDto::getOddrn,
        identity(),
        (a, b) -> {
            throw new BadUserRequestException(
                "Duplicate ODDRN in batch: " + a.getOddrn());
        }
    )))

// Add @ExceptionHandler advice on the ingestion controller (or a sibling controller-advice):
@ExceptionHandler(NotFoundException.class)
public ResponseEntity<ErrorEnvelope> handleNotFound(NotFoundException e) {
    return ResponseEntity.status(HttpStatus.NOT_FOUND)
        .body(new ErrorEnvelope("DATASOURCE_NOT_FOUND", e.getMessage()));
}

@ExceptionHandler(DataBufferLimitException.class)
public ResponseEntity<ErrorEnvelope> handlePayloadTooLarge(DataBufferLimitException e) {
    return ResponseEntity.status(HttpStatus.PAYLOAD_TOO_LARGE)  // 413
        .body(new ErrorEnvelope("PAYLOAD_TOO_LARGE", "Increase spring.codec.max-in-memory-size or reduce batch size"));
}
```

**Defect 2 - narrow the lock scope OR ship a 429 signal:**

Option A (preferred): narrow the lock scope. Resolve the datasource id BEFORE entering the `@ReactiveTransactional` boundary (un-`FOR UPDATE` lookup), then start the transaction with just the id - no row-lock for the pipeline body.

Option B (fallback): catch the transaction-timeout exception and surface as HTTP 429 with `Retry-After`:
```java
.onErrorMap(TransactionTimeoutException.class, e -> 
    new ResponseStatusException(HttpStatus.TOO_MANY_REQUESTS, "Datasource ingestion serialised; retry with backoff", 
        Map.of("Retry-After", "30")))
```

**Defect 3 - structured logging on every rollback path:**

```java
// In IngestionServiceImpl.ingest, after the row-lock entry:
.doOnNext(id -> log.info("ingest start collector={} datasource_oddrn={} entity_count={}",
    collectorId, dataEntityList.getDataSourceOddrn(), dataEntityList.getItems().size()))
.doOnError(e -> log.warn("ingest rollback collector={} datasource_oddrn={} entity_count={} cause={}",
    collectorId, dataEntityList.getDataSourceOddrn(), dataEntityList.getItems().size(), e.getMessage(), e))
```

(`collectorId` requires plumbing - substrate-batch finding F-097c also hits this; consider a request-scoped `IngestionContext` bean.)

## Tests

- Integration test on duplicate-ODDRN in batch: POST with `{ items: [{oddrn: X, ...}, {oddrn: X, ...}] }` returns 400 with `error_code: DUPLICATE_ODDRN`.
- Integration test on unknown-datasource: POST with `{ data_source_oddrn: "unknown" }` returns 404 with `error_code: DATASOURCE_NOT_FOUND`.
- Integration test on oversized payload: POST > `spring.codec.max-in-memory-size` returns 413.
- Concurrent-collector test (Option A): 10 concurrent POSTs to the same datasource succeed without serialisation; OR (Option B): contended POSTs return 429 with `Retry-After`.
- Log-assertion test: ingestion success emits an `INFO ingest start` log line; ingestion failure emits a `WARN ingest rollback` log line; both lines include collector-id + datasource-oddrn + entity-count.
