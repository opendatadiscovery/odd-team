## What

`RequestStatus.tsx` (the status badge component on the Owner-Association History tab) implements a 3-way if-chain that silently mislabels any unknown enum value as lowercase `'pending'`:

```tsx
// odd-platform-ui/src/components/Management/OwnerAssociations/OwnerAssociationsList/OwnerAssociationsResolved/ResolvedAssociationRequest/RequestStatus/RequestStatus.tsx:9-15
if (status === APPROVED) return 'Approved';     // capitalized; literal string; no i18n key
if (status === DECLINED) return 'Declined';     // capitalized; literal string; no i18n key
return 'pending';                                // lowercase; literal string; no i18n key
```

Three issues stacked:
1. **Silent unknown-enum fallback** — any future status value (`SUPERSEDED`, `EXPIRED`, `REVOKED`, ...) will silently render as "pending" with no diagnostic affordance.
2. **Casing inconsistency** — Approved / Declined are capitalized; `'pending'` is lowercase.
3. **No i18n** — all three labels are literal strings, bypassing whatever i18n system the rest of the UI uses (the codebase has translation keys for some Owner-Association strings already).

## Where

`odd-platform-ui/src/components/Management/OwnerAssociations/OwnerAssociationsList/OwnerAssociationsResolved/ResolvedAssociationRequest/RequestStatus/RequestStatus.tsx:9-15`

Verified verbatim this session (3-way if-chain + lowercase `'pending'` fallback as shown above).

## Why it matters

The defect is operator-LOW today because the OwnerAssociationRequest status enum has only 3 values (PENDING / APPROVED / DECLINED) and the 3-way chain covers all of them. It surfaces in two future scenarios:

1. **Enum extension** — the moment someone adds `SUPERSEDED` / `EXPIRED` / etc. to the enum, History will silently mislabel them. Without an explicit `default` case that logs / throws / surfaces an "Unknown status: X" string, the bug will land in production untested.

2. **Locale switch** — the next i18n pass on the Owner-Association tab will discover three literal strings that need to be threaded through the locale system. They will be missed because they don't match the codebase's normal pattern.

Severity LOW — file as adjustment, not bug. Ship with the next Owner-Association touch.

## Suggested fix

Replace the if-chain with a `switch` carrying an explicit `default` case, route the labels through the existing i18n keys, and normalize casing:

```tsx
switch (status) {
  case OwnerAssociationRequestStatus.APPROVED:
    return t('ownerAssociation.status.approved');
  case OwnerAssociationRequestStatus.DECLINED:
    return t('ownerAssociation.status.declined');
  case OwnerAssociationRequestStatus.PENDING:
    return t('ownerAssociation.status.pending');
  default:
    // Log + emit a visible diagnostic string instead of silently coercing to 'pending'
    console.warn(`RequestStatus: unknown status value '${status}'`);
    return t('ownerAssociation.status.unknown', { value: status });
}
```

(i18n key names are illustrative; align with the codebase's existing key conventions.)

Open to alternatives — if `OwnerAssociationRequestStatusDto` is a TypeScript string-literal union (exhaustively checked by the compiler), the `default` case is dead code at compile time; in that case, the switch + exhaustiveness check still beats the silent fallback because the typecheck will catch future enum extensions.
