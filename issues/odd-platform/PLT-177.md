## What

On a data-quality test's detail overview, the **Severity** control is a plain dropdown that persists its value the instant it changes. There is no Save button, no confirmation, and no pending/disabled state: every `onChange` immediately dispatches the `setDataQATestSeverity` mutation. A single mis-click - opening the dropdown and brushing past an entry - reclassifies the test's severity with no chance to cancel. Worse, the dispatch is fire-and-forget (the returned promise is never awaited), so the UI optimistically reflects the newly-selected severity even if the backend `PUT` fails; the displayed severity can diverge from what was actually stored. Because the control is an **uncontrolled** select (`defaultValue`, not `value`), the displayed value is also driven by local UI state rather than the persisted record, which reinforces the divergence.

**Verified in the running UI (2026-06-10, maintainer):** the divergence is not limited to the edited test. On a data entity with more than one DQ test, setting the severity for ONE test makes every SIBLING test display that same severity: clicking another test in the Test Reports list updates every other field on the overview panel (name, last execution, parameters), but the Severity select keeps showing the value just chosen for the previous test. Only a full page refresh (remount + test-list refetch) restores each test's own severity. Two further root causes compose with the uncontrolled select: (1) `TestReportDetails` renders the overview route element with no `key` tied to `dataQATestId`, so switching tests re-renders the same mounted component instance and MUI keeps the select's internal state (`defaultValue` is read once, at first mount); (2) `setDataQATestSeverity.fulfilled` is never reduced into the store - the slice handles only the three fetch thunks - so even the edited test's stored record keeps the pre-edit severity until the next full test-list refetch. The same mechanism misrenders on mere navigation (code-derived): with tests of differing severities, every test visited after the first renders the first-mounted test's severity; the after-edit bleed is the maintainer-observed variant.

## Where

The change handler dispatches the mutation directly, with no submit/confirm gate and without awaiting the result:

`odd-platform-ui/src/components/.../TestReportDetailsOverview/TestReportDetailsOverview.tsx:42-52`
```tsx
  const handleSeverityChange = (e: SelectChangeEvent<unknown>) => {
    const severity = e.target.value as DataQualityTestSeverity;

    dispatch(
      setDataQATestSeverity({
        dataEntityId,
        dataqaTestId: dataQATestId,
        dataQualityTestSeverityForm: { severity },
      })
    );
  };
```

The select is uncontrolled (`defaultValue`) and wires the handler straight to `onChange`, with no Save affordance anywhere in the render tree:

`odd-platform-ui/src/components/.../TestReportDetailsOverview/TestReportDetailsOverview.tsx:81-86`
```tsx
                <AppSelect
                  disabled={!isAllowedTo}
                  size='small'
                  defaultValue={qualityTest?.severity || DataQualityTestSeverity.MAJOR}
                  onChange={handleSeverityChange}
                >
```

The slice never consumes the mutation's result - `extraReducers` registers cases only for the three fetch thunks (`fetchDataSetQualityTestReport`, `fetchDataSetQualitySLAReport`, `fetchDataSetQualityTestList`); there is no case for `setDataQATestSeverity.fulfilled`, so the `PUT` response (the updated entity) is discarded and `qualityTestsById[testId].severity` keeps the pre-edit value even after a successful save:

`odd-platform-ui/src/redux/slices/dataQualityTest.slice.ts:107-133`

The overview is rendered through the route tree with no `key` tied to `dataQATestId`; switching tests re-renders the same mounted component (no remount, so the uncontrolled select's `defaultValue` is never re-read):

`odd-platform-ui/src/components/.../TestReportDetails/TestReportDetails.tsx:88-105`

This is the **same control** reached through two feature flows (the test-report detail view and the test-run severity view); they render the identical `TestReportDetailsOverview` severity select, so both inherit the defect from one component.

## User-facing impact

Verified end-to-end by the maintainer on a running instance (2026-06-10): on a data entity with several DQ tests, set Severity on one test, then click any sibling test in the list. The sibling's Severity select displays the value just set for the first test while every other field on the panel correctly shows the sibling's data; ALL siblings render that same severity until a full page refresh. Backend per-test values stay correct (the `PUT` targets one test id) - the defect is display - but an operator who reads a sibling's severity from this panel acts on a wrong signal, and one who "corrects" a sibling based on the misrendered value persists a genuinely wrong severity through the same no-confirm control. The severity e2e protocol (IT-057) asserts `PUT` status, SLA colour, and the DB row only - it would not catch this render bleed.

## Why it matters

Test severity is not cosmetic - it feeds the dataset's SLA roll-up and the RED/ORANGE/GREEN health colour an operator trusts at a glance. An accidental, unaudited reclassification can flip a dataset's SLA state, and because the mutation is unawaited and the select is uncontrolled, the operator can be looking at a severity the backend never accepted. Feedback is misleading rather than absent: a success toast fires ("Severity successfully updated.", `dataQualityTest.thunks.ts:66-69`) and a server-error toast fires on failure (`handleResponseThunk.ts:28-31,37-39`), but the displayed value is never rolled back on failure, never re-synced from the store on success (the store itself is never updated - see Where), and there is no "unsaved changes" guard. For a multi-tenant install, a careless brush of the dropdown can change the health signal other teams depend on, with nothing in the UI flow to make the change deliberate or reversible. Medium severity: not destructive of data rows, but a one-gesture, unconfirmed, optimistically-displayed mutation of a signal that drives downstream SLA colour - now compounded by a verified display bleed that misreports every sibling test's severity (while the success toast tells the operator all is well) until a refresh.

## Suggested fix

Gate the mutation behind an explicit, deliberate action. Concretely: convert the select to a **controlled** component (`value={severity}` bound to local state) plus a **Save** (or inline confirm) button that only dispatches on click; **await** the dispatch and reconcile UI state from the result (revert on failure, surface a success/error toast). Until Save is clicked, the displayed value is local edit state; after a successful save it reflects the persisted record. Open to alternatives on the exact affordance (Save button vs. confirm dialog vs. optimistic-with-rollback), but the three non-negotiables are: (1) no persistence without a confirming gesture; (2) the dispatch is awaited and its fulfilled payload is reduced into `qualityTestsById` (add the missing `setDataQATestSeverity.fulfilled` case to `dataQualityTest.slice.ts`) so the store reflects the save without a refetch and the UI cannot show an unsaved severity as if it were stored; (3) the rendered value always derives from the CURRENT route's test record - a controlled `value={qualityTest?.severity}` (or at minimum `key={dataQATestId}` on the route element to force a remount) - so navigating between tests can never display another test's severity.

## How discovered

Surfaced in the 2026-06-08 contradiction-harvest while reflecting on features **F-022** (data-quality test report) hypothesis H-007 and **F-057** (test-run severity) hypothesis H-010 - both reflections independently flagged the same severity control, confirming it is one component reached by two flows (deduped here into a single issue). The harvest also notes this compounds two adjacent findings on the same surface: the audit-silence of the severity change (no record of who reclassified) and the cross-origin SLA colour flip the reclassification can cause. This is a UI-side defect distinct from any backend pagination/bounds issue.

2026-06-10: the maintainer reproduced the stronger symptom in the running UI (severity set on one test rendered for all sibling tests until refresh); code-read traced it to the uncontrolled select + the no-key route render + the missing fulfilled-reducer. A graph retrieval over the ontology confirmed neither the bleed symptom nor the missing-reducer cause was tracked anywhere else, so this issue was extended rather than filing a new one (same control, same fix surface). The generic no-re-sync behaviour is pinned as a characterization test by TST-031 item 3 (F-057 H-011).
