## Description

The live `/authorization/owners` page (WebFetched 2026-05-27, 200 OK) describes Owners as a concept and points operators at the Management → Owners tab. It is **silent on every lifecycle facet**: permission gates per verb, the auto-create side-channel, the empty-roles UPDATE hazard, the audit posture, the unauthenticated-read default, DISABLED-mode anonymity. Four operator-visible behaviours need a Known Limitations sub-section.

**Caveat 1 — Forensic silence: Owner CRUD emits no Activity Feed event AND the schema makes adding one structurally impossible (F-019a).** `OwnerServiceImpl.java:38-122` runs create / update / delete / getOrCreate inside `@ReactiveTransactional` but carries NO `@ActivityLog` on any method. Adding one would fail at the schema layer: `V0_0_48__add_activity.sql:4,12` declares `activity.data_entity_id NOT NULL FK to data_entity(id)` — Owner CRUD has no data-entity context to populate (DOC-GAP-192 / DOC-181). Combined with: (a) the role-binding HARD-delete on the delete path (`deleteOwnerRelationsExcept(id, List.of())` at line 97), (b) the partial-unique-index pattern enabling name re-use after soft-delete (V0_0_64) — an operator can delete Alice, re-create Bob with the name "Alice", and there is NO trace anywhere operator-readable except the soft-deleted row's `deleted_at` timestamp. Compliance frameworks requiring identity-change audit (SOX records of identity-management changes; NIST 800-53 AU-2 audit events) cannot be satisfied; "who renamed Owner X from Alice to Bob at T" has no record.

**Caveat 2 — `GET /api/owners` is unauthenticated-read; any authenticated user enumerates the Owner directory (and anonymous under DISABLED) (F-019b).** Grep `/api/owners` in `SecurityConstants.java` finds POST/PUT/DELETE entries (lines 143-146) — **no GET entry**. `getOwnerList` (`OwnerController.java:30-38`) has no programmatic auth check, no `@PreAuthorize`, no SecurityRule. Any authenticated user under LOGIN_FORM/OAUTH2/LDAP enumerates the entire Owner directory including PII (`alice@acme.com`, `[Pseudonymous Researcher]`, internal team-name strings). Under `auth.type=DISABLED` the endpoint is anonymously reachable. There is no `OWNER_READ` permission in `Permission.java`; read-side authorization is "any authenticated user reads everything" — consistent with the collaborative read posture (ADR-CANDIDATE-003 / DOC-GAP-082 META) but operator-invisible.

**Caveat 3 — `getOrCreate` side-door: three service-tier callers mint Owner rows without `OWNER_CREATE` (F-019c).** `OwnerServiceImpl.getOrCreate` (lines 38-42) is `getByName.switchIfEmpty(create)`. The auto-create path runs WITHOUT the caller holding `OWNER_CREATE` — the SecurityRule at `SecurityConstants.java:143` gates `POST /api/owners` only, not the service method. Three permission-paths reach it: (a) `POST /api/owner_association_request` (any authenticated user; no SecurityRule entry) — `OwnerAssociationRequestServiceImpl.java:57`; (b) `POST /api/dataentities/{id}/ownerships` (gated by `DATA_ENTITY_OWNERSHIP_CREATE`) — `OwnershipServiceImpl.java:52`; (c) `POST /api/terms/{id}/ownerships` (gated by `TERM_OWNERSHIP_CREATE`) — `TermOwnershipServiceImpl.java:35`. A caller holding only `DATA_ENTITY_OWNERSHIP_CREATE` supplies a never-seen `ownerName`; the service silently inserts a new OWNER row; the new Owner appears in `GET /api/owners` immediately. Operators configuring strict RBAC see `OWNER_CREATE: "Allows creating a new owner entity"` on `/permissions` — they assume the explicit POST is the sole path. The Owner directory is silently writable from three additional paths.

**Caveat 4 — Empty-roles PUT silently wipes all role bindings (F-019d).** `OwnerServiceImpl.update` (lines 68-85) calls `getRoleIdsList(updateEntityForm)` (line 70) → helper at lines 117-122 collapses both `null` AND empty `List` to `List.of()`. Subsequent `deleteOwnerRelationsExcept(owner.getId(), newRoles)` (line 77) with an empty `newRoles` issues `DELETE FROM OWNER_TO_ROLE WHERE OWNER_ID = ?` (the jOOQ `notIn(emptyCollection)` folds to a tautology) — wiping ALL role bindings. `createRelations(owner.getId(), newRoles)` (line 80) then inserts nothing. The Owner persists; every role-binding is gone. API consumers omitting the `roles` field (PATCH-style mental model) silently strip all role bindings. The UI (`OwnerForm.tsx:77`) only validates `name`; removing all role chips and saving triggers the destructive path with NO confirmation modal — three clicks from the Owners list (per DOC-GAP-188). `components.yaml:419-422` declares `OwnerFormData.roles` OpenAPI-optional with no `required` marker.
