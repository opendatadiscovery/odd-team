## What

The remaining "consumer-model" path split out of opendatadiscovery/odd-platform#1725: collectors still cannot
ingest the finer ML lifecycle subtypes `ML_MODEL_ARTIFACT` and `ML_MODEL_INSTANCE`, even though odd-platform
models them internally and the specification now defines them. (The reported 500 on `type: ML_MODEL` is fixed
and ships in 0.29.0 via #1790 -- `ML_MODEL` is now a model-identity Data Entity Group.)

## Where

- `opendatadiscovery-specification` -- `entities.yaml` `DataEntityType` already exposes `ML_MODEL_ARTIFACT` +
  `ML_MODEL_INSTANCE` (merged in opendatadiscovery-specification#87, 2026-06-18).
- `opendatadiscovery-specification-contracts` -- the Maven Central release of `ingestion-contract-server` has
  NOT run since #87; the published artifact is still `0.1.41` (verified on Maven Central), whose wire
  `DataEntityType` enum does not contain the two subtypes.
- `odd-platform` -- `gradle/libs.versions.toml` pins `ingestion-contract-server` `0.1.40`; the ingestion
  `DataEntityType` a collector can deserialize against is whatever that pinned artifact defines.

## User-facing impact

A collector author who sends `type: ML_MODEL_ARTIFACT` (or `ML_MODEL_INSTANCE`) to `POST /ingestion/entities`
gets `HTTP 400` `{"code":"USR001","message":"Failed to read HTTP message"}` -- the value is rejected at JSON
deserialization because the published ingestion contract (`0.1.41`) does not contain it. (Verified live during
CTRIB-021, 2026-06-18; the gating state -- published contract `0.1.41` -- is unchanged as of 2026-06-25.) Today
a collector can register an ML model identity (`ML_MODEL`, the group) and a training job (`ML_MODEL_TRAINING`),
but not a trained artifact/version or a deployed serving instance.

## Why it matters

The full ML lifecycle -- model identity -> training job -> trained artifact -> deployed instance -- is the value
proposition of ML model cataloging. Until the contract is republished and consumed, two of the four lifecycle
types are platform-internal-only and unreachable from any collector, so an MLOps user cannot represent model
versions or deployments in the catalog.

## Suggested fix (the chain; step 1 is blocked on infrastructure)

1. `opendatadiscovery-specification-contracts` -- dispatch the `Maven Central release` workflow to publish
   `ingestion-contract-server` `0.1.42` (carrying `ML_MODEL_ARTIFACT`/`_INSTANCE`). BLOCKED: the publish path
   migrated from the sunset Sonatype OSSRH to the Central Portal; it needs a Central Portal user token + a
   namespace migration for `org.opendatadiscovery`. (`-contracts` PR #7 repoints the workflow to the Central
   Portal Staging API; it cannot run until those credentials exist.)
2. `odd-platform` -- bump `gradle/libs.versions.toml` `ingestion-contract-server` `0.1.40` -> `0.1.42` and
   verify the regenerated ingestion `DataEntityType` enum carries `ML_MODEL_ARTIFACT`/`_INSTANCE`.
3. `odd-models` -- dispatch `Build and publish PyPI artifact` (PyPI is unaffected by the OSSRH sunset; can run
   any time).

After the chain, a collector sends `type: ML_MODEL_ARTIFACT` with a `data_consumer` payload (the common
"register my model version" case) and it ingests (200), readable in the catalog as an ML model artifact.

## How discovered

Split from opendatadiscovery/odd-platform#1725 during `/contribute` CTRIB-021. The platform-side 500 fix (#1790)
shipped to 0.29.0; this consumer-model path is deferred because step 1 is blocked on the Sonatype Central Portal
migration. Workspace tracking: `backlog/spec/SPC-004` (the specification reconciliation, spec content merged via
#87) + the ml-entity-taxonomy ADR (`adrs/drafts/ml-entity-taxonomy.md`).
