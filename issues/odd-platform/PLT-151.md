## What

The predefined-name protection on roles and policies is incomplete and internally inconsistent across the three CRUD verbs. `create()` performs **no** reserved-name check at all on either `Policy` or `Role`, while `update()` and `delete()` each guard against the privileged "Administrator" name - but they do not agree on how to compare it. The result is two operator-visible holes:

1. **Re-minting the exact trusted name - reachable only after the seed is gone (partially masked by a DB index).** `create()` never inspects the name, so it imposes no application guard against a role/policy literally named `Administrator`. **However**, a partial unique index blocks the *exact* name while the seeded row is live: `role_name_unique ON role (name) WHERE deleted_at IS NULL` and `policy_name_unique ON policy (name) WHERE deleted_at IS NULL` (`V0_0_55__add_policies_and_roles.sql:30,42`; re-asserted `V0_0_64__remove_is_deleted_field.sql:90`). So while the seeded `Administrator` exists, a second active `Administrator` fails at the DB layer, not at the (absent) application guard. The exact-name re-mint becomes reachable only once the seed is soft-deleted out-of-band (a migration / direct DB action - `delete()` itself refuses to remove it, case-insensitively, `:81-82`). This corrects the earlier revision, which presented exact-name re-mint as freely reachable; it is index-gated in the normal case.
2. **A case-variant that is creatable, editable, and permanently undeletable - reachable with no precondition.** The partial unique index is on the literal string, so a lowercase `administrator` is a *different* key and is **freely creatable** today (no seed removal needed). It then slips past `update()` and `delete()` differently: `update()` compares case-**sensitive** `.equals("Administrator")` (so the lowercase variant passes the filter and IS editable), but `delete()` compares case-**insensitive** `.equalsIgnoreCase(...)` against every `UserProviderRole` value (so the lowercase variant matches and is rejected as "predefined and cannot be deleted"). The same row is thus simultaneously editable and undeletable - a wedge clearable only by direct DB surgery. This is the immediately-reachable defect and the strongest part of this finding.


**`odd-platform-api/.../service/RoleServiceImpl.java:81-82` - `delete()` is case-INSENSITIVE:**

```java
.filter(role -> Stream.of(UserProviderRole.values())
```

(`PolicyServiceImpl` shows the mirror gap on the Policy side: `update()` at `:76` and `delete()` at `:87` both compare with case-sensitive `.equals(ADMINISTRATOR_POLICY)`, so a lowercase `administrator` policy is fully unguarded by either verb - creatable, editable AND deletable - and `create()` at `:63` is unguarded entirely. The Policy side has NO editable-but-undeletable wedge because both verbs agree (case-sensitive); the wedge is Role-specific, from the update/delete sensitivity disagreement.)

## User-facing impact

**Static-not-driven** (code-settled; not exercised on a running stack in this sweep). The guards and the case asymmetry are pure source facts verified 2026-06-08/2026-06-10 (`RoleServiceImpl.java:51-61,68,81-82`; `PolicyServiceImpl.java:62-69,76,87`; partial unique index as above). The operator-visible consequences, by reachability:

- **Immediately reachable (no precondition):** create a Role named lowercase `administrator` via the Management -> Roles UI (or `POST /api/role`); it succeeds, is editable, and the Delete action fails permanently with "Role is predefined and cannot be deleted" - an unremovable row that *looks* like the privileged built-in to any operator scanning the roles list. Clearable only by direct DB surgery.
- **Reachable only after out-of-band seed removal:** an exact-name `Administrator` re-mint with attacker-chosen policy bindings (the partial unique index blocks it until the seeded row is soft-deleted, which the app refuses to do).

Remaining check to promote to fully-driven: on a running stack, (a) `POST /api/role {name:"administrator"}` -> 200, then `DELETE` -> 400 "predefined"; (b) confirm `POST {name:"Administrator"}` is rejected by the unique index while the seed exists (expected DB unique violation -> 500 or `UniqueConstraintException` -> 400). Both follow deterministically from the code above but were not run here.

## Why it matters

This is an integrity / privilege-escalation hole on the RBAC surface, which is exactly the surface that is supposed to be the hardest to tamper with. The failure is **silent** - no error, no log, no audit trail (the audit-silence on these methods is tracked separately as PLT-062). An operator who believes "Administrator is a protected, immutable, seeded identity" is wrong: a near-identical case variant behaves inconsistently enough to leave an unremovable, trusted-looking row (immediately reachable), and the exact name becomes re-mintable under attacker control once the seed is removed out-of-band. Anyone able to reach Role/Policy create (which, under `auth.type=DISABLED`, is *anyone unauthenticated* - see PLT-152) can exploit the create-side gap. Severity stays HIGH: the case asymmetry is a reachable latent footgun on the most privileged built-in identity even for legitimate admins, and the create-guard absence removes the application-layer backstop entirely (leaving only an incidental DB index between an attacker and a trusted-name role once the seed is gone).

## Suggested fix

Treat all three verbs as one name-guard cluster and make them uniform:

1. Add a reserved-name guard to **both** `PolicyServiceImpl.create` and `RoleServiceImpl.create` that rejects any attempt to create a role/policy whose name collides with a predefined name (`Administrator` / the `UserProviderRole` values), raising `BadUserRequestException`.
2. Make the comparison **case-insensitive in all three verbs** (`create`/`update`/`delete`) - `equalsIgnoreCase` (or normalise to a canonical case before comparison) - so a lowercase `administrator` cannot diverge into the editable-but-undeletable state. Pick one comparison helper and use it everywhere.
3. Apply the same fix symmetrically on the Policy side (the `ADMINISTRATOR_POLICY` constant comparison at `PolicyServiceImpl.java:76,87`).

Open to alternatives on exactly where the reserved-name set is centralised, but the invariant must hold identically across create/update/delete.
