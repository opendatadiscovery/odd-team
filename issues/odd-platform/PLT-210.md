## What

`AppInfoMenu` consumes the app-info and app-links queries by destructuring **only** their `data`. It never inspects `isError` or `isLoading`. When the `/api/links` request **fails** (network error, 5xx, auth expiry), the hook returns `data === undefined`, and the component's `projectLinks` render guard (`if (!links || links.length === 0) return null;`, `:56`) treats that failure **identically** to a correctly-empty configuration: it renders nothing. There is no error indicator and no loading state, so an operator who has configured links but whose request is failing sees an empty menu and cannot tell a broken fetch from "no links configured". The same blindness applies to the app-info (version) query, whose `projectVersion` guard (`if (!appInfo?.projectVersion) return null;`, `:38`) likewise collapses a failed/loading fetch into the no-version case.

## Where

`odd-platform-ui/src/components/shared/elements/AppToolbar/AppInfoMenu/AppInfoMenu.tsx:17-18`

```tsx
const { data: appInfo } = useAppInfo();   // line 17: no isError / isLoading
const { data: links } = useAppLinks();    // line 18: no isError / isLoading
```

and the conflated empty/error guard downstream (`:55-56`):

```tsx
const projectLinks = React.useMemo(() => {
  if (!links || links.length === 0) return null;   // failure (undefined) == empty config
  ...
}, [links]);
```

The `useAppInfo` / `useAppLinks` hooks live at `odd-platform-ui/src/lib/hooks/api` (imported at `AppInfoMenu.tsx:12`); both are react-query hooks, so on a failed fetch `data` is `undefined` (react-query swallows the error - it does not throw into render), which is exactly why the `data`-only destructure silently degrades.

## User-facing impact

Confirmed by reading the full component (`AppInfoMenu.tsx:16-124`). The menu always renders its four hardcoded entries (Documentation, Slack, version, Leave a feedback) - the version row and the operator-configured links are the only data-driven parts. On a failed `/api/links` fetch the operator sees the menu **without** their configured links and **without any error or loading affordance**, indistinguishable from a deployment that has configured no links. Same for the version row on a failed `/api/info`. Non-destructive (the menu is auxiliary toolbar chrome), but a real backend problem is masked as "nothing configured", which makes it hard to notice and hard to diagnose. The defect is code-settled: there is no `isError`/`isLoading` read anywhere in the component.

## Why it matters

**Silent.** A failed links/app-info fetch is indistinguishable from a healthy-but-empty state, so a real backend problem is masked as "nothing to show". Operators relying on the configured links (or the version badge) get a silently-degraded menu with no signal that something is wrong, which makes the failure hard to notice and hard to diagnose. Severity **low** - the menu is auxiliary chrome and the failure is non-destructive - but the conflation of error and empty is a genuine UX defect worth a small fix.

## Suggested fix

Read `isError` / `isLoading` from both hooks and render distinct states (open to alternatives):

```tsx
const { data: appInfo, isError: appInfoError } = useAppInfo();
const { data: links, isError: linksError, isLoading: linksLoading } = useAppLinks();
// in projectLinks: distinguish loading (spinner/skeleton) and error (small inline error)
// from the legitimately-empty case before returning null.
```

Keep it lightweight - a brief loading affordance and a small inline error suffice for an auxiliary menu; the key change is that an errored fetch no longer renders as "empty".
