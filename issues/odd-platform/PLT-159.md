## What

The three read-side attachment endpoints - list a data entity's attachments, get its upload options, and download one of its files - have **no authorization rule**. Every mutating attachment endpoint (upload / update-link / delete) is gated by a `SecurityRule` that requires the `DATA_ENTITY_ATTACHMENT_MANAGE` permission, but the GET endpoints were never added to that list. As a result any authenticated user - and, under `auth.type=DISABLED`, any unauthenticated caller - can list and download **any** data entity's attachments simply by knowing (or enumerating) its numeric id. There is no per-entity ownership check on the read path.

## Where

The authorization rules live in `SecurityConstants.java`. Only POST / PUT / DELETE are present for the attachment surfaces (lines 249-275); there is **no** entry for any of the three GET paths:

`odd-platform-api/.../auth/util/SecurityConstants.java:249-275`
```java
new SecurityRule(DATA_ENTITY,
    new PathPatternParserServerWebExchangeMatcher("/api/dataentities/{data_entity_id}/files/**", POST),
    DATA_ENTITY_ATTACHMENT_MANAGE),
new SecurityRule(DATA_ENTITY,
    new PathPatternParserServerWebExchangeMatcher("/api/dataentities/{data_entity_id}/files/**", PUT),
    DATA_ENTITY_ATTACHMENT_MANAGE),
new SecurityRule(DATA_ENTITY,
    new PathPatternParserServerWebExchangeMatcher("/api/dataentities/{data_entity_id}/files/{file_id}", DELETE),
    DATA_ENTITY_ATTACHMENT_MANAGE),
new SecurityRule(DATA_ENTITY,
    new PathPatternParserServerWebExchangeMatcher("/api/dataentities/{data_entity_id}/links", POST),
    DATA_ENTITY_ATTACHMENT_MANAGE),
// ...PUT/DELETE on links - but NO GET rule anywhere
```

The three unprotected operations (paths + operationIds from `odd-platform-specification/openapi.yaml`):

```
GET /api/dataentities/{data_entity_id}/attachments        operationId: getAttachments      (openapi.yaml:1566-1580; returns DataEntityAttachments = files AND links)
GET /api/dataentities/{data_entity_id}/files/uploads      operationId: getUploadOptions    (openapi.yaml:1582-1596)
GET /api/dataentities/{data_entity_id}/files/{file_id}    operationId: downloadFile        (openapi.yaml:1669-1690; returns application/octet-stream)
```

The handlers in `DataEntityAttachmentController.java` confirm the read path does no entity-scoped authz of its own - `getAttachments` / `getUploadOptions` / `downloadFile` simply delegate to the service and map to `ResponseEntity.ok` (lines 30-80). `downloadFile` in particular streams the raw file bytes back keyed only on `fileId` (line 76: `attachmentService.downloadFile(fileId)`), ignoring the path's `dataEntityId`.

## Why it matters

This is a silent, multi-tenant data-confidentiality defect. In a deployment where different teams own different data entities, an attacker with any account (or, under `DISABLED`, no account) can:

- enumerate `GET /api/dataentities/{id}/attachments` to discover which entities carry files/links and read every link URL, then
- pull the file bytes directly via `GET /api/dataentities/{id}/files/{file_id}`.

There is no audit trail and no permission check, so the exposure is operator-invisible until proven by an attacker. Attachments commonly hold sensitive material (data dictionaries, sample extracts, internal runbooks), so this is a confidentiality breach by default. Severity **high**: unauthenticated/low-privilege read of arbitrary tenant data, no logging, trivially exploitable by id enumeration.

## Suggested fix

Add a `SecurityRule` for each of the three GET endpoints, mirroring the existing mutation rules, gated on an appropriate read permission (introduce `DATA_ENTITY_ATTACHMENT_READ` if a dedicated read grant is wanted, or reuse `DATA_ENTITY_ATTACHMENT_MANAGE` / the data-entity read permission if a separate read grant is overkill):

```java
new SecurityRule(DATA_ENTITY,
    new PathPatternParserServerWebExchangeMatcher("/api/dataentities/{data_entity_id}/attachments", GET),
    DATA_ENTITY_ATTACHMENT_READ),
new SecurityRule(DATA_ENTITY,
    new PathPatternParserServerWebExchangeMatcher("/api/dataentities/{data_entity_id}/files/uploads", GET),
    DATA_ENTITY_ATTACHMENT_READ),
new SecurityRule(DATA_ENTITY,
    new PathPatternParserServerWebExchangeMatcher("/api/dataentities/{data_entity_id}/files/{file_id}", GET),
    DATA_ENTITY_ATTACHMENT_READ),
```

Open to alternatives on the exact permission name; the load-bearing requirement is that these three reads stop being anonymously/any-user reachable. (The `DISABLED`-mode anonymous-read posture is a separate, broader concern, but a real `SecurityRule` here is what brings the read path back under the same authorization model as the write path.)

## How discovered

Surfaced in the 2026-06-08 contradiction harvest (`lineage/odd-platform/harvest/2026-06-08-contradiction-harvest.md`, NOVEL bug queue, F-027 H-004) from the product-owner feature reflection of the attachment lifecycle (`lineage/odd-platform/feature-reflections/detail/F-027.yaml`).

Distinct from **PLT-086**: PLT-086 hardens the attachment *mutation* endpoints (cross-entity `data_entity_id` discard) and the MinioConfig builder, and its fix sketch explicitly scopes the read endpoints **out** ("Read endpoints get their own treatment ... separate PLT if ever filed"). The doc-side caveat for this gap shipped as **DOC-253** (Caveat 2 notes the read endpoints have no `SecurityRule`), but the code fix was left untracked. This issue is that untracked code fix.
