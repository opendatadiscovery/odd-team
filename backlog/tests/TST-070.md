## What happens

`integration-tests/e2e/playwright.config.ts:18` pins the JSON reporter to a **fixed** path:

```ts
reporter: [['list'], ['json', { outputFile: 'results.json' }]],
```

`run-regression.sh` then runs the four suites **in sequence against the same working directory**, so each suite
overwrites the previous one's `results.json`. After a full run only the LAST suite's per-spec record survives.
`run-suite.sh` writes a run-log entry per suite, but it fills only the mechanical fields (SUT description, image
digest, protocol list, `outcome:`) — `runner:` and `evidence/notes:` are left as literal placeholders for a human
to type. The pass/fail counts therefore exist **only** in the process's stdout.

Measured this session, twice, by two different sessions:

- The `ctrib066` implement run's `run-log/2026-09-06-known-bugs.md` has two entries; the second (the one whose
  digest matches the image the accepted regression actually ran on) is an **unfilled template** —
  `runner: (fill: AI-assisted <model> | human <name>)`, `evidence/notes: <captured values from the probe-run yaml
  / Playwright report; or the manual observation>`. The result quoted in the item's test ledger comes from the
  FIRST entry, which ran on a different (earlier) build of the same commit.
- This `/review` ran the full four suites with the command's stdout piped to `tail -120`, which by construction
  emits nothing until the whole run ends — so `feature-complete`'s counts were gone by the time the run
  finished, and the suite had to be **re-run alone (≈45 min)** purely to recover a number the harness had
  already computed and thrown away.

## Why it matters

The maintainer's 2026-06-11 directive is that regression is **measured, not inferred**, and `/review`'s own rule
is to read actual pass/fail counts rather than exit codes (`run-regression.sh:96` says so in its own message:
*"read the run-log / log for actual pass-fail counts — exit code is not the verdict"*). The harness makes the
compliant path expensive: either keep a terminal open for an hour, or re-run. The predictable outcome is what
the run-log already shows — entries that carry a digest and an `outcome:` but no counts, and a reader six months
later cannot tell whether a suite was 339/12 or 300/51.

It also silently weakens the SET-EQUALITY check the feature-complete baseline depends on. That check ("my 12
failures are exactly TST-059's eleven + TST-057's one, by spec:line") is only possible with the per-spec list;
without it a reviewer falls back to "the suite completed", which is not the same claim.

## Fix direction

1. **Parameterise the reporter output.** `PW_JSON_OUT` env var honoured by `playwright.config.ts`
   (`outputFile: process.env.PW_JSON_OUT ?? 'results.json'`), set by `run-suite.sh` to
   `run-log/artifacts/{date}-{suite}.json`. One line each side; nothing else changes.
2. **Fill the run-log from it.** `run-suite.sh` already writes the entry — have it derive
   `evidence/notes: **N passed / M failed (Xm)**` plus the failing `spec.ts:line` list straight from that JSON,
   and set `runner:` from the invoking context instead of a placeholder. A human/agent can still append prose;
   the counts stop depending on someone remembering to paste them.
3. **Then** the set-equality assertion becomes a two-line diff against the tracked baseline rather than a
   hand-transcribed list, which is also what makes it re-checkable at the release gate.
