# ReactiveUserOwnerMappingRepositoryImpl — semantic understanding

## understanding

The persistence-layer bean owning every read and write to the `user_owner_mapping` table — the catalog-side bridge that turns an authenticated principal `(oidc_username, provider)` into a single active `OwnerPojo` row. This file is the **primary source for the LOGIN_FORM ↔ LDAP cross-mode bleed**: the `getConditions(oidcUsername, provider)` helper at lines 116-127 builds the WHERE clause `OIDC_USERNAME.eq(oidcUsername) AND DELETED_AT.isNull() AND (provider non-empty ? PROVIDER.eq(provider) : PROVIDER.isNull())` — a case-sensitive `.eq()` predicate on `oidc_username` with a null-or-equal branch on `provider`. The class exposes six method-level operations: three writes (`createRelation` line 41 / `deleteRelation` line 54 / `deleteActiveRelationByOwner` line 65) that always mark soft-delete via `DELETED_AT = generateNow()`, plus three reads (`getAssociatedOwner` line 77 — the `USER_OWNER_MAPPING JOIN OWNER ON OWNER_ID` lookup consumed by `AuthIdentityProviderImpl.fetchAssociatedOwner`; `isOwnerAssociated` line 88 — boolean existence check used by `OwnerServiceImpl.delete` for cascade-block; `getUserRolesByOwner` line 99 — the 4-way JOIN `ROLE ← ROLE_TO_POLICY ← OWNER_TO_ROLE → USER_OWNER_MAPPING` that drives `RoleServiceImpl.getCurrentUserRoles` and feeds the RBAC permission evaluator). The class is a thin jOOQ DSL builder; it has no service-layer logic, no validation, no error handling — `createRelation` calls `deleteActiveRelationByOwner(ownerId).then(insert)` so the (owner_id) partial unique index never fires (the clear-active-then-insert pattern enforces "at most one active row per owner" application-side, complemented by DB-side partial unique indexes at `V0_0_89__update_user_owner.sql:9-15`). The persistence-level provider semantics are the source of three load-bearing implicit ADRs and three known security gaps that propagate through every owner-scoped read in the platform.

- invariants:
  - "**Soft-delete only — no DELETE FROM anywhere in this class.** All three 'delete' methods (deleteRelation, deleteActiveRelationByOwner, the embedded one in createRelation) are UPDATE statements setting `DELETED_AT = generateNow()` (lines 56-62, 65-74). A direct `DELETE FROM user_owner_mapping` lives nowhere in odd-platform-api — verified via Grep. The persistence-layer contract is: rows are never removed; they accumulate with monotonically-increasing soft-delete timestamps."
  - "**Clear-active-then-insert pattern, NOT upsert.** `createRelation` (lines 47-51) first calls `deleteActiveRelationByOwner(ownerId)` to soft-delete any active row for the same owner THEN inserts a new row. This enforces 'one active mapping per Owner' application-side. The DB-side partial unique index `unique_deleted_at_per_owner` (V0_0_89__update_user_owner.sql:9-11) would catch a violation but the clear-active step removes the conflict before INSERT. NOTE: `UserOwnerMappingServiceImpl.createRelation` (UserOwnerMappingServiceImpl.java:15-18) ALSO calls `deleteRelation(username, provider)` FIRST (clearing active rows for the SAME (username, provider) tuple), making it a TWO-STEP clear: first clear by (username, provider) at the service layer, then clear by owner_id at the repository layer, then insert. The two clears together enforce both partial unique indexes."
  - "**Case-sensitive `.eq()` on oidc_username AND provider.** Line 119 uses `USER_OWNER_MAPPING.OIDC_USERNAME.eq(oidcUsername)` (case-sensitive equality, not `equalIgnoreCase`); line 122 uses `USER_OWNER_MAPPING.PROVIDER.eq(provider)` (case-sensitive equality). This is the contract every consumer relies on — a username 'Alice' and 'alice' are distinct USER_OWNER_MAPPING rows."
  - "**Empty/null provider collapses to `PROVIDER IS NULL`.** Line 121-125: `if (StringUtils.isNotEmpty(provider)) PROVIDER.eq(provider) else PROVIDER.isNull()`. The branch fires on null AND on empty-string — both produce the `IS NULL` predicate. This is the LOGIN_FORM/LDAP/S2S cross-mode bleed mechanism: all three non-OAuth2 auth flows produce `provider=null` at AuthIdentityProviderImpl.java:32, and all three resolve to the same `WHERE PROVIDER IS NULL` query against this table."
  - "**Positional INSERT column order.** Line 45: `.values(ownerId, oidcUsername, provider, DSL.val(null, DATE))` — the values are passed positionally without column names. The schema order MUST be (owner_id, oidc_username, provider, deleted_at) for this to be correct. Per V0_0_4__add_user_owner_mapping.sql:3-4 + V0_0_55__add_policies_and_roles.sql:1-2 + V0_0_89__update_user_owner.sql:1-2 the actual current order is (owner_id, oidc_username, provider, deleted_at) — matches. But future migration that reorders columns would silently break this INSERT (jOOQ codegen would keep working; the values() call would target wrong columns). The `DSL.val(null, DATE)` for deleted_at is type-pinned as DATE, but the schema declares `TIMESTAMP WITHOUT TIME ZONE` (V0_0_89__update_user_owner.sql:2) — this is a TYPE MISMATCH that jOOQ/Postgres tolerates because both NULL values cast cleanly."
  - "**JOINs intentionally include the `DELETED_AT IS NULL` filter on USER_OWNER_MAPPING.** Both `getAssociatedOwner` (line 82 via getConditions) and `getUserRolesByOwner` (line 108) carry the `USER_OWNER_MAPPING.DELETED_AT.isNull()` predicate either inline or via getConditions. Soft-deleted mappings are invisible to authorization. NOTE: callers OUTSIDE this file (ReactiveAlertRepositoryImpl.java:83-86, ReactiveActivityRepositoryImpl.java:156-158, ReactiveOwnerAssociationRequestRepositoryImpl.java:80-84, ReactiveOwnerRepositoryImpl.java:77-78) also LEFT JOIN USER_OWNER_MAPPING with `DELETED_AT IS NULL` — but they JOIN ONLY ON OIDC_USERNAME (no provider clause) for display-name resolution. That is a SEPARATE invariant — see bugs_limitations_corner_cases."
  - "**No race-window-safe primitives.** Two concurrent `createRelation(alice, null, X)` calls would BOTH execute their own `deleteActiveRelationByOwner` UPDATE, both succeed (the UPDATE is a no-op if no row matches; succeeds if one matches), then both INSERT. The DB-side partial unique index `unique_deleted_at_per_owner` SHOULD catch the second INSERT — but only if the first INSERT's row is visible to the second transaction. The reactive `.then()` operator does not imply transactional isolation; the two writes happen across two distinct R2DBC connections unless an enclosing `@ReactiveTransactional` is applied. ALL three writer methods on this repository have NO @ReactiveTransactional annotation; the service layer (UserOwnerMappingServiceImpl) is annotation-free as well. Atomicity relies on the partial unique index — the second INSERT will raise UniqueConstraintException via JooqReactiveOperations.translateDatabaseException."

## downstream_side_effects

- **INSERT into `user_owner_mapping`** (createRelation, line 44-46): writes a new row with `(owner_id, oidc_username, provider, deleted_at=null)`. Side-effects: (a) increments the table's row count permanently (no DELETE FROM ever runs); (b) the partial unique indexes (`unique_deleted_at_per_owner` and `user_owner_mapping_oidc_username_provider_deleted_key`) WILL block a second concurrent INSERT if the clear-active steps fail to land first; (c) NO trigger, no audit log, no activity-feed entry — the write is invisible to the global Activity feed (per the audit-log-presence-asymmetry pattern documented at `lineage/odd-platform/concepts/detail/invariants/audit-log-presence-asymmetry-2-tier-audit-story.yaml`).
- **UPDATE `user_owner_mapping SET deleted_at = NOW()`** (deleteRelation lines 56-60, deleteActiveRelationByOwner lines 66-70): soft-delete by setting `deleted_at = generateNow()`. Side-effects: (a) the row is invisible to all subsequent `getAssociatedOwner` / `isOwnerAssociated` / `getUserRolesByOwner` reads (the WHERE-clause filter); (b) the affected user's `My Objects` / `My Alerts` / `MY_OBJECTS` activity views collapse to empty Mono / Flux; (c) any in-flight reactive chains that have ALREADY resolved the user→owner mapping for the same request CONTINUE with the stale OwnerPojo until completion (no in-memory invalidation); (d) NO trigger, no audit log.
- **SELECT JOIN OWNER** (getAssociatedOwner lines 79-84): reads a single OwnerPojo by JOIN'ing user_owner_mapping to owner on `OWNER_ID = OWNER.ID`. No side-effects; pure read.
- **SELECT EXISTS** (isOwnerAssociated lines 89-95): boolean existence check; consumed by OwnerServiceImpl.delete to raise CascadeDeleteException if any active mapping exists for the owner. The OwnerService.delete code path that fails on `true` returns HTTP 400 to `DELETE /api/owners/{id}`.
- **SELECT 4-way JOIN** (getUserRolesByOwner lines 99-114): reads the caller's effective Role bundle including each role's policy array (jsonArrayAgg). Side-effects in callers: (a) RoleServiceImpl.getCurrentUserRoles uses the result to filter the `/api/role` list view; (b) indirectly drives the RBAC permission evaluator's permission set on every authorized HTTP request via PolicyServiceImpl.getCurrentUserPolicies.
