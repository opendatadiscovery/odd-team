## What

`Provider.java:3-5` declares a FIVE-value enum (COGNITO / GITHUB / GOOGLE / ODD_IAM / AZURE). The live oauth2-oidc page lists SEVEN providers (Cognito / GitHub / Google / Azure AD / Okta / Keycloak / Custom OIDC). Okta + Keycloak fall through `CustomOIDCUserHandler.java:28-34` (`shouldHandle = NOT in Provider enum`), which has NO admin-group mapping, NO provider-specific claim handling.

Every Okta + Keycloak user is granted USER role at login. ADMIN promotion requires manual Owner-Role binding through the Management UI by an existing administrator. Operators following the doc + configuring `admin-groups: [some-group]` for Okta or Keycloak see ZERO admin path — the configuration binds successfully but the handler ignores it.

## Why it matters

This is a doc-vs-code first-class-vs-fall-through divergence. Operators picking Okta or Keycloak for their SSO based on the live doc's enumeration expect the same admin-detection knobs they see for Cognito / GitHub / Azure. The configuration binds; the handler ignores; admin users never resolve to ADMIN.

## Suggested fix

Two paths — non-exclusive; (a) is the immediate operator-load-bearing fix, (b) is the strategic feature:

**Option A — Add OktaUserHandler + KeycloakUserHandler with provider-specific admin-detection (recommended).**

Each handler reads the appropriate provider-specific group claim:

- **Okta**: groups claim is typically `groups` (configurable in the Okta admin console). Read claim → exact-match against `admin-groups`. Pattern-mirror Cognito's handler.
- **Keycloak**: realm roles or client roles claim. Both `realm_access.roles` (realm-level) and `resource_access.{client_id}.roles` (client-level) — operator config should choose which. Read claim → exact-match against `admin-groups`. Pattern-mirror Cognito's handler.

Add the two enum values to `Provider.java`. Wire the new handlers in the OAuth2 user-resolution chain.

**Option B — Provide a generic OIDC-group-claim handler usable across Okta + Keycloak + Custom OIDC (longer-term).**

A `GenericOIDCUserHandler` parameterised on `groups-claim-name` (default `groups`, override per provider). One handler, many providers. Pros: future-proof for new OIDC providers. Cons: requires more provider-specific knob (claim-name).

Recommended Option A as the immediate ship — Okta + Keycloak are first-class providers the docs already claim; ship full-parity. Option B is a refactor opportunity once a third silent-no-op provider surfaces.
