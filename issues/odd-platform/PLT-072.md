## What

Three related defects on the Identity Probe / DISABLED-mode synthetic admin surface:

**Defect 1 - Synthetic admin with DYNAMIC blast radius (F-085a).** `IdentityController.java:23-33` returns `new Identity().username("admin").permissions((Arrays.asList(Permission.values())))` to anonymous callers under DISABLED. `Permission.values()` dynamically expands - adding a new Permission to the OpenAPI spec AUTOMATICALLY enters the DISABLED-mode admin grant. ZERO authentication + ZERO audit + DYNAMIC blast radius. Operators who flip DISABLED on for a quick demo and forget have a one-line-anonymous-API surface.

**Defect 2 - Auth-mode fingerprint in ONE call (F-085b).** `whoami` is NOT in `WHITELIST_PATHS`. Under LOGIN_FORM the SecurityWebFilterChain returns 302; under OAUTH2/LDAP it returns 401; under DISABLED 200+admin. Four response shapes ARE the fingerprint.

**Defect 3 - admin/ADMIN literal collision (F-085c).** `IdentityController.java:32` literal `"admin"` (lowercase); `S2sAuthenticationFilter.java:31-34` literal `"ADMIN"` (uppercase). Two distinct identity surfaces; both undocumented; both case-collidable with operator-named users.

## Why it matters

DISABLED mode is dev/demo-only per docs, but the synthetic-admin shape means a deployment that accidentally inherits DISABLED from a template has ZERO defence - and the dynamic blast radius means future Permission additions silently enter the grant. The auth-mode fingerprint reduces attacker recon to one GET. The admin/ADMIN literal collision is a footgun for any deployment naming an Owner `admin` or `ADMIN`.

## Suggested fix

**Thread A - Explicit DISABLED acknowledgment (Defect 1).**

Require an explicit environment variable to enable DISABLED mode beyond `auth.type=DISABLED` alone:

```java
@Value("${odd.disabled-auth-ack:}")
private String disabledAuthAck;

@PostConstruct
void validateDisabledAuthAck() {
    if ("DISABLED".equalsIgnoreCase(authType)
        && !"I_ACCEPT_NO_AUTH_NO_AUDIT".equals(disabledAuthAck)) {
        throw new IllegalStateException(
            "auth.type=DISABLED requires explicit acknowledgment via env var ODD_DISABLED_AUTH_ACK=I_ACCEPT_NO_AUTH_NO_AUDIT. " +
            "DISABLED grants synthetic ADMIN with ALL permissions to anonymous callers; see " +
            "https://docs.opendatadiscovery.org/configuration-and-deployment/enable-security/authentication/disabled-authentication");
    }
}
```

Operators inheriting DISABLED from a template fail-fast on boot with a clear message pointing to the doc that enumerates the reachable surfaces.

**Thread B - Uniform 401 for whoami across non-DISABLED modes (Defect 2).**

Under LOGIN_FORM, configure `whoami` to return 401 instead of redirect to login - anonymous reconnaissance no longer distinguishes LOGIN_FORM from OAUTH2/LDAP via response code. The SPA bootstrap path already handles 401 (treats as "not logged in"), so the user-visible behavior is unchanged.

**Thread C - Shared SystemUsers constants (Defect 3).**

```java
// New file: odd-platform-api/src/main/java/.../auth/SystemUsers.java
public final class SystemUsers {
    public static final String DISABLED_DUMMY = "admin";
    public static final String S2S_PRINCIPAL = "ADMIN";
    
    private SystemUsers() {}
}
```

Update `IdentityController.java:32` and `S2sAuthenticationFilter.java:31-34` to use these constants. Add a doc admonition that these literals are reserved + that Owner provisioning should avoid them.
