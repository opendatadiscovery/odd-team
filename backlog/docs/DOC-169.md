## Description

The live page at `docs.opendatadiscovery.org/features/data-quality/sla-statuses` describes `GET https://{platform_url}/api/datasets/{data_entity_id}/sla` as returning a **JSON `DataSetSLAReport`** ("SLA colour, severity weights breakdown, slaRef self-link"), explicitly targeting the **BI-tools audience** ("BI tools can fetch this endpoint per dataset and render the colour as a one-glance trust signal next to dashboard tiles").

The OpenAPI spec at `odd-platform-specification/openapi.yaml:1883-1894` declares `getSLA` returning `content: image/png` (a 1-2 KB PNG badge). The JSON `DataSetSLAReport` is returned by the **sibling** operation `getDatasetSLAReport` at `openapi.yaml:1901-1909`, path `/api/datasets/{id}/sla_report`.

This is the canonical "operator follows our guide off a cliff" failure mode for the audience the doc explicitly names. A BI engineer writing a JSON-parsing client per the doc verbatim hits the PNG endpoint, receives a 1-2 KB binary stream, and fails to deserialise it as JSON. The doc page targets BI tools by name; the wrong URL is the first thing they'd copy.

## Acceptance Criteria

- [ ] The SLA Statuses page names **two endpoints**, not one:
  - `GET /api/datasets/{id}/sla` — returns `Content-Type: image/png` — the **PNG badge** for direct-render embedding (BI tools that can render an image).
  - `GET /api/datasets/{id}/sla_report` — returns the JSON `DataSetSLAReport` (colour, severity weights breakdown, slaRef) — for BI tools that parse JSON.
- [ ] The audience-targeting paragraph that previously named only `/sla` is rewritten to route each BI-tool integration path to the correct endpoint (image rendering vs JSON consumption).
- [ ] No remaining sentence on the page claims `/api/datasets/{id}/sla` returns JSON.
- [ ] `Consumer-read:` footer cites `odd-platform-specification/openapi.yaml:1883-1894` (PNG operation) and `:1901-1913` (JSON operation + schema).
- [ ] Live-site verification post-merge: WebFetch `docs.opendatadiscovery.org/features/data-quality/sla-statuses` and confirm both endpoints render with correct `Content-Type`.
