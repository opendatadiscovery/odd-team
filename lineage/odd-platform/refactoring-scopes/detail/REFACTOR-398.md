- **REFACTOR-398** (NEW 2026-05-19O): Google `admin-attribute` config accepts ANY claim string — no whitelist, no schema check. An operator with `admin-attribute: emale` (typo for `email`) reads `token.getClaim('emale')` which returns null; `containsIgnoreCase(adminPrincipals, null)` returns false; isAdmin stays false. Silent no-op on typos; no admin is ever assigned
  - **Category**: missing-validation
  - **Surfaced by**:
    - `GoogleUserHandler.md:bugs_limitations_corner_cases.[5]` (LOW)
  - **Statement**: `GoogleUserHandler.java:56-64` reads `provider.getAdminAttribute()` (with `email` default per `GOOGLE_EMAIL = "email"` constant) verbatim as the claim name to look up at line 59 (`token.getClaim(adminPrincipalAttribute)`). An operator with `admin-attribute: emale` (typo for `email`) reads `token.getClaim('emale')` → null → `containsIgnoreCase(adminPrincipals, null)` returns false → isAdmin stays false. The handler does NOT validate the claim name against any whitelist of known Google ID-token claims (`email`, `sub`, `name`, `hd`, etc.). The behavior is consistent with the broader `OAuth2Properties` pattern of unvalidated-string-config (REFACTOR-152 + REFACTOR-154 capture this class) — but the silent-no-op-on-typo is operator-debug-hostile.
  - **Evidence**: `GoogleUserHandler.java:56-64` (no claim-name validation; verbatim usage of `provider.getAdminAttribute()`)
  - **Existing-ADR-or-implied-prescription**: ADR-CANDIDATE-048 (narrow-validator at `@PostConstruct` — only validates structural-config-faults, not semantic-correctness). The maintainer accepted the price (semantic typos manifest at runtime as silent no-op). The fix is to widen the validator OR to add a warn-log at handler initialisation.
  - **Proposed remedy**: Either (a) add a startup warn-log when `provider.adminAttribute` is set to a value not in the well-known Google claim set (`email`, `sub`, `name`, `hd`, `picture`); (b) widen the boot-time validator at `ODDOAuth2Properties.validate()` to reject configurations with unknown adminAttribute values for known providers; (c) add a doc warning to the live OAuth2/OIDC page about claim-name typo silent-no-op risk. The maintainer should pick based on whether the silent-no-op is acceptable for non-Google providers (which the same pattern applies to).
  - **Severity rationale**: LOW — uncommon (typos are rare; operators usually copy from docs). Silent no-op behaviour is consistent with the broader unvalidated-string-config pattern.
  - **Suggested backlog grouping**: `OAuth2 hardening sprint` (paired with REFACTOR-152 + REFACTOR-154 — the unvalidated-string-config family)
