## What

The language switcher (user menu -> "Select language") lists **only English** on `main` (ships in 0.28.0).
Every non-English locale (es, ch, fr, ua, hy, br) has vanished from the picker, so a user has **no way to
change the UI language** through the interface.

Root cause: `SelectLanguage.tsx:48` builds the picker list from **`i18n.languages`** -- the i18next *runtime
fallback chain*, not the supported-locale set. PR #1783 (`9c6fb074`, the foreign-language-leak fix) changed
`i18n.ts` `fallbackLng` from the seven-element array `['en','es','br','ch','fr','ua','hy']` to **`'en'`**
(correctly -- that array-as-fallback WAS the Portuguese-leak bug). But with `lng:'en'` + `fallbackLng:'en'`,
`i18n.languages` collapses to `['en']`, so the picker -- which iterated that array -- now renders one row.

The #1783 author fixed the *validation* path (`i18n.ts:25` `savedLanguage` uses the separate
`languages = Object.keys(resources)` list, so a locale persisted in `localStorage` still loads) but missed
the *picker* path, which still read `i18n.languages`. So a user who already has `i18nextLng=es` persisted
still sees Spanish; but nobody can SELECT a non-English locale anymore.

## Where

- `odd-platform-ui/src/components/shared/elements/AppToolbar/SelectLanguage/SelectLanguage.tsx:48` --
  `{i18n.languages.filter(...).map(...)}` -- the ONLY consumer of `i18n.languages` in the codebase
  (grep-verified: one hit).
- `odd-platform-ui/src/locales/i18n.ts:36` -- `fallbackLng: 'en'` (#1783; correct, must stay).
- `odd-platform-ui/src/locales/i18n.ts:21` -- `const languages = Object.keys(resources)` -- the CORRECT
  supported-locale list (all 7), already used for validation, NOT exported / NOT used by the picker.
- `odd-platform-ui/src/lib/constants.ts:158` -- `LANGUAGES_MAP` (all 7: en/es/ch/fr/ua/hy/br).

## User-facing impact (VERIFIED on the running system)

Live a11y snapshot captured by the IT-102 run (working-tree SUT @ origin/main + the CTRIB-014 catalogs):
opening the user menu -> "Select language" renders the `dialog "Select language"` with a "Search ..." box and
exactly ONE language row: `menuitem "English"` (flag + "English"). Spanish/Chinese/French/Ukrainian/Armenian/
Portuguese are absent. Four IT-102 cases (UC-1 switch-to-Spanish, UC-2 persistence, #1748 toolbar-tabs-under-ua,
#1751 feature-keys-under-es) all time out at the language-pick step for this reason; the one non-switch case
(unknown-locale -> English) passes.

Net: 0.28.0 would ship a multilingual platform whose language selector offers only English. Ironically this
also makes the #1751 catch-up translations (es/ch/fr/ua/hy/br now complete) unreachable for any user who has
not already persisted a non-English locale.

## Reproduce

1. Build/run `main` (or any build with #1783) under `odd-minimal` (AUTH_TYPE=DISABLED).
2. Open the UI -> user menu (top-right "admin" cluster) -> "Select language".
3. OBSERVE: the dialog lists only "English". EXPECTED: all seven languages (English, Spanish, Chinese,
   French, Ukrainian, Armenian, Brazilian Portuguese).

Regression proof: `git show 9c6fb074^:.../i18n.ts` = `fallbackLng: ['en','es','br','ch','fr','ua','hy']`
(picker showed 7) vs `git show 9c6fb074:.../i18n.ts` = `fallbackLng: 'en'` (picker shows 1). Not in any
release tag (latest stable 0.27.13 predates #1783) -> ships in 0.28.0 unless fixed.

## Suggested fix (small, localized, verified-feasible)

`SelectLanguage.tsx` should iterate the SUPPORTED-locale set, not the runtime fallback chain. `LANGUAGES_MAP`
is already imported, so:

```
-      {i18n.languages
+      {(Object.keys(LANGUAGES_MAP) as Lang[])
         .filter(lang => LANGUAGES_MAP[lang as Lang].toLowerCase().includes(query.toLowerCase()))
         .map(lang => ( ... ))}
```

(Equivalently, export `languages` from `i18n.ts` and iterate that.) Independent of `fallbackLng`, so it
cannot re-break if the fallback policy changes again. Pair with a unit/IT guard that the picker lists every
`LANGUAGES_MAP` entry (the IT-102 switch cases already exercise the path once the picker is fixed).
