## Description

ODD Platform ships a working health-check / monitoring surface, but the documentation never introduces it. The shipped `application.yml:226-245` disables all actuator endpoints by default and then explicitly enables and web-exposes exactly four: `health`, `prometheus`, `env`, `info`. `/actuator/**` is whitelisted ahead of the authentication chain in every auth mode (`SecurityConstants.java:96`), so `/actuator/health` and `/actuator/prometheus` are reachable unauthenticated — which is what load balancers, Kubernetes probes, and Prometheus scrapers need.

Today the manual covers this surface only negatively or in passing:

- `configuration-and-deployment/odd-platform.md:102-113` documents the actuator namespace from the **security** angle (the `/actuator/env` key-schema exposure and its mitigations) — it never says `health` exists or what it is for.
- `odd-platform.md:887` mentions `/actuator/health` incidentally inside the advisory-lock-wedge caveat.
- No SUMMARY entry, no page anywhere documents the health endpoint, the Prometheus endpoint, or how to wire liveness/readiness probes. The shipped compose files (`odd-platform/docker/demo.yaml`, `docker/examples/*`) define no `healthcheck:` blocks either, so the docs entry is the operator's only guidance.

Backlog item DOC-373 (pending) already presupposes operators pointing readiness probes at `/actuator/health` — a caveat about an endpoint the manual never introduces. This item creates the positive entry that DOC-373's caveat (and the line-887 wedge caveat) can anchor against.

The page is the canonical home for **operational monitoring guidance** (a content type with no home today — Gate 10 outcome "new canonical home"). Security caveats about the actuator namespace remain canonical in `odd-platform.md`'s existing section; the new page links to them, never duplicates them.
