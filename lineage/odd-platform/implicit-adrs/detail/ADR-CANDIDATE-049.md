- **ADR-CANDIDATE-049** (NEW 2026-05-12E): Owner-directory CRUD is **identity-decoupled** by design — `POST /api/owners` creates an Owner row from `OwnerFormData` (`name` + optional `roles`) without ever reading the caller's identity; the user→owner association is a separate flow handled by `OwnerAssociationRequestController`. The two-controller split codifies "directory CRUD ≠ user claim": an Owner is a platform-managed object an admin creates; a user later claims an Owner through an explicit association-request flow
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar (`createOwner`) but cross-validated by the dedicated `OwnerAssociationRequestController` + `OwnerAssociationRequestServiceImpl` + the live owners-doc statement "Every ODD Platform user should associate themselves with one of the existing owners" (WebFetched 2026-05-12 status 200). The two-controller separation is structural, not accidental — the sidecar enumerates four entry points (`OwnerController`, `OwnerAssociationRequestController`, `UserOwnerMappingService`) that maintain the boundary across the codebase
  - **Surfaced by**:
    - `odd-platform__java__OwnerController__controller-method__createOwner.md:implicit_adrs.[1]` ("Owner-creation is decoupled from user identity by design — the request body contains only `name` and optional `roles`; the controller never reads the `ServerWebExchange`'s security context; the service `OwnerServiceImpl.create` accepts only `OwnerFormData` (`OwnerServiceImpl.java:55-66`); the user→owner mapping is created only through the explicit association-request flow (`OwnerAssociationRequestServiceImpl.java:52-76`). An admin-style caller creates an Owner as a directory entry; the Owner is then claimed via a separate flow. The naming convention (`OwnerController` for the directory CRUD; `OwnerAssociationRequestController` for the user-claim flow) reinforces the separation." — intent_anchor: separation visible across three sibling controllers)
  - **Decision statement**: ODD's Owner model is a two-stage commitment: (a) `POST /api/owners` creates a directory entry (a platform-managed Owner row) from `OwnerFormData(name, roles[])` — the controller never reads `ServerWebExchange`'s security context; the service has no principal parameter; no user→owner mapping is created at this endpoint; (b) `POST /api/owner_association_request` creates the user→owner edge through the explicit association-request flow (`OwnerAssociationRequestServiceImpl.java:52-76` invokes `getOrCreate` if needed, but the canonical create path is the dedicated controller). The decision codifies a deliberate model: an Owner is a *role / persona* a platform admin defines; a user claims an Owner role through an association request that the platform-admin (or `OWNER_RELATION_MANAGE` holder) approves. The live `/configuration-and-deployment/enable-security/authorization/owners` page corroborates the model ("Every ODD Platform user should associate themselves with one of the existing owners"). The trade-off accepted: ODD's auth modes (LDAP / OAuth2 / LOGIN_FORM) all map directory groups to `UserProviderRole.ADMIN` / `.USER`, NOT to platform Owner rows — there is no auto-create-Owner-on-first-login. Operators bridging directory identities to ODD ownership must run a deliberate association step. The consequence is captured in REFACTOR-198 (no auto-owner-creation on login is an onboarding friction that REFACTOR-188's "no audit log" amplifies).
  - **Wisdom test**: PASS. The two-controller / two-service split is structural (`OwnerController` + `OwnerAssociationRequestController` + `UserOwnerMappingService` form a triad with non-overlapping responsibilities); the absence of identity reads in the create path is intent-anchored (`OwnerServiceImpl.create` signature has no principal parameter); the live doc corroborates the model. The alternative — auto-creating an Owner per first-time login — would be a structural change against this ADR.
  - **Evidence**:
    - createOwner.md says: "OwnerController.java:22-27 (no security-context read) + OwnerServiceImpl.java:55-66 (no principal parameter) + OwnerAssociationRequestServiceImpl.java:52-76 (the separate user→owner flow)"
    - createOwner.md says: "WebFetch live owners doc 2026-05-12 ('Every ODD Platform user should associate themselves with one of the existing owners') + AuthIdentityProviderImpl.java:23-53 (no owner auto-creation) + LDAPSecurityConfiguration.java / OAuthSecurityConfiguration.java batch-C sidecars (no `OwnerService` injection)"
  - **Existing ADR**: none. Composes with ADR-CANDIDATE-002 (centralised SECURITY_RULES — `OWNER_CREATE` is the gate) and contrasts with ADR-CANDIDATE-015 (DataEntity owner-scoped reads use the reactor `Context` to resolve identity AT QUERY TIME) — for owner-directory CRUD, identity is decoupled; for owner-scoped reads of OTHER tables, identity flows through reactor `Context`. The maintainer's signal: identity belongs to the query path, not the directory-CRUD path.
  - **Co-surfaced gaps** (link from `refactoring-scopes.md`): REFACTOR-198 (no auto-Owner-on-first-login — onboarding friction; LOW; price of the deliberate decoupling), REFACTOR-188 (no audit log on OwnerServiceImpl.create — operator cannot reconstruct "who created this Owner directory entry" — HIGH; cross-cutting with PolicyService.create + RoleService.create), REFACTOR-199 (Owner sprawl unbounded — no per-tenant/per-day cap; LOW; mitigated by OWNER_CREATE gate), REFACTOR-200 (non-partial `name UNIQUE` blocks soft-delete recovery — MEDIUM; operational gap), REFACTOR-201 (no `@ActivityLog` on OwnerServiceImpl.create — activity feed cross-owner consequence — MEDIUM).

Document the two-stage commitment (directory CRUD then user claim) + the deliberate absence of auto-create-on-login + the consequence for operators (a deliberate association step is required, no shortcut). Cross-link with ADR-CANDIDATE-015 (the contrasting "identity-via-reactor-Context" pattern for owner-scoped reads). Doc-side: the live owners page should explicitly enumerate the two-stage onboarding (currently the page says owners "associate themselves" but does not name `POST /api/owner_association_request` as the mechanism).
  - **Severity rationale**: MEDIUM — onboarding-architecture decision; affects every fresh deployment's user provisioning flow.
