- **REFACTOR-412** (NEW 2026-05-19O): IngestionDataEntitiesFilter buffers up to 20MB before checking the token — an attacker submitting 20MB invalid-token requests forces the platform to allocate + Jackson-parse the body before token rejection. Heap-pressure DoS vector with low attacker effort. No rate-limit, no concurrent-request cap, no per-IP throttle
  - **Category**: body-before-auth
  - **Surfaced by**:
    - `IngestionDataEntitiesFilter.md:bugs_limitations_corner_cases.[4]` (MEDIUM)
    - `IngestionDataEntitiesFilter.md:security.known_security_gaps.[3]` (MEDIUM)
    - `IngestionDataEntitiesFilter.md:performance.known_performance_gaps.[2]` (MEDIUM)
  - **Statement**: `IngestionDataEntitiesFilter.java:37-60` orders operations as: (1) `super.getBody().collectList()` — buffer the entire reactive Flux of DataBuffers into a List; (2) `readBody(dataBuffer, DataEntityList.class)` — Jackson-parse to extract `dataSourceOddrn`; (3) `resolveToken(exchange.getRequest())` — extract the Authorization Bearer header; (4) DB lookup + `String.equals` token comparison. Steps (1) and (2) precede the auth check. An attacker submitting maximum-size 20MB invalid-token payloads forces the platform to allocate + Jackson-parse the body BEFORE rejecting. Repeated bad requests can saturate heap. There is no rate-limit, no concurrent-request cap, no per-IP throttle on `POST /ingestion/entities`. The DoS amplification ratio (per-request cost vs. per-request attacker effort) is approximately 20MB of heap + Jackson parse vs. 20MB of network payload — a 1:1 amplification for memory; the parse CPU is the actual amplification (potentially 100s of ms per request).
  - **Evidence**: `IngestionDataEntitiesFilter.java:37-60` (body-first ordering) + `application.yml:14-15` (`spring.codec.max-in-memory-size: 20MB`)
  - **Existing-ADR-or-implied-prescription**: ADR-CANDIDATE-138 NEW (body-buffered-before-auth is structural — the Ingestion API wire contract embeds datasource identity in payload) — the ordering is structurally forced; the DoS surface is the documented cost. The fix MUST work within the existing ordering: add rate-limiting / per-IP throttle / circuit-breaker BEFORE the filter.
  - **Proposed remedy**: Add a `RateLimiter` filter (e.g., resilience4j) BEFORE `IngestionDataEntitiesFilter` in the chain: per-IP throttle (e.g., 100 requests / minute per IP for `/ingestion/entities`); reject excess with 429. Alternatively, add a circuit-breaker on the heap-pressure dimension (Reactor Netty's `MaxConnections` or similar). Doc-side: instruct operators to deploy ODD behind a reverse proxy with rate-limit + per-IP throttling for ingestion paths.
  - **Severity rationale**: MEDIUM — DoS amplification is real; mitigated by operator network controls + max-in-memory-size cap. Not a security boundary failure, but a resource-exhaustion surface that should be defended.
  - **Suggested backlog grouping**: `Ingestion hardening sprint` (paired with REFACTOR-204 / REFACTOR-205 / REFACTOR-185 — the broader ingestion-auth-default-off family)
