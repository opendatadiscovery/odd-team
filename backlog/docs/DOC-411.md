## Description

On the Query Examples create/edit dialog, the **Query** field — the one an operator expects to hold a SQL/KQL/Spark snippet — is authored through the platform's generic **Markdown prose editor**, not a code or SQL editor. `QueryExampleForm.tsx:105-110` renders the `query` field as `<Markdown value={field.value} onChange={...} editor height={200} />` (the same `components/shared/elements` `Markdown` component used for free-text prose), with no SQL syntax highlighting, no monospace code affordance, and no language mode. An operator pasting a multi-line SQL statement gets a prose-Markdown editing experience (where, e.g., leading whitespace and blank lines are Markdown-significant), not the code-editor experience the field's purpose implies.

This is an SME-comparative caveat: the feature page already explains that the `query` body is *rendered* through the Markdown renderer on the details page (and DOC-183/DOC-232 cover the XSS family that follows from that). What is not stated is the **authoring-time** reality that the input control itself is a prose Markdown editor — i.e., this is a "code field that is actually a prose field" mismatch the operator should know before composing a snippet.

The dialog's no-dirty-form-warning behaviour rides alongside: `DialogWrapper` (`QueryExampleForm.tsx:128-141`) has no dirty-form detection / navigation guard, so closing mid-edit discards the draft. **That half is already documented** — DOC-232 Caveat 6 ("Dialog close loses Markdown drafts silently", Escape / outside-click / browser-back). DOC-411 must cross-link DOC-232 Caveat 6 for the draft-loss half and NOT re-author it (Cornerstone 5); the net-new content here is solely the "Query field is a prose Markdown editor, not a code editor" clarification.

How it misleads: an operator opens the dialog expecting a SQL editor (syntax highlighting, code formatting), authors a snippet as if in a code surface, and is surprised by prose-Markdown behaviour both while typing and on the rendered details page.
