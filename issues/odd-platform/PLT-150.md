## What

Two related defects on the search-session deep-link path (a bookmarked / shared / TTL-expired
`/search/{id}` URL):

1. **API (backend):** the **filters** read of a missing session returns **HTTP 500 `SYS001`**, while
   the facets + results reads correctly return **404 USR002 "Search not found"**. Inconsistent: the same
   missing-session condition is a clean 404 on two endpoints and an Internal Server Error on the third.
2. **UI (UX):** navigating to `/search/{missing}` renders the generic SPA error boundary
   **"Unknown Error / Return to the Home Page"** instead of a graceful "this search has expired - start a
   new one." Even on the correct 404s the SPA does not distinguish "session expired" from a real fault.

## Reproduced live (docker `:latest`, auth.type=DISABLED, 2026-06-08, undisturbed stack)

```
GET /api/search/{missing}                         -> 404  {"code":"USR002","message":"Search not found"}
GET /api/search/{missing}/results?page=1&size=30  -> 404  {"code":"USR002","message":"Search not found"}
GET /api/search/{missing}/filters/entityClasses   -> 500  {"code":"SYS001","message":"Internal Server Error"}
UI  /search/{missing}                             -> "Unknown Error / Return to the Home Page"
```
(NB: an earlier probe saw 500 on /results too - that was a concurrency-overloaded stack, not the real
behaviour; on an undisturbed stack /results + facets are correctly 404.)

## Root cause

Verified end-to-end against the source (read 2026-06-10):

`SearchServiceImpl` (`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/service/search/SearchServiceImpl.java`)
- the not-found origin is shared by all three reads: `fetchFacetState` (`:157-160`) does
  `searchFacetRepository.get(searchId).switchIfEmpty(Mono.error(() -> new NotFoundException("Search not found")))`.
- `getFacets` (`:66`) and `getSearchResults` (`:99`) return **Mono** - the `NotFoundException` propagates
  before the response is built -> `ControllerAdvice.handleNotFound` (`ControllerAdvice.java:30-34`) maps it
  to 404 USR002.
- `getFilterOptions` (`:51`) returns **Flux**.

`SearchController.getFiltersForFacet` (`controller/SearchController.java:29-40`) wraps that Flux as
`Mono.just(searchService.getFilterOptions(...)).map(ResponseEntity::ok)` - so the `ResponseEntity` (HTTP
**200**) is constructed and the status line commits *before* the inner Flux is subscribed. By the time the
Flux's `fetchFacetState` emits `NotFoundException` during streaming, the 200 is already on the wire, so the
advice cannot rewrite it to 404 -> WebFlux degrades it to a 500 SYS001. The two Mono controller paths
(`getSearchFacetList` `:42-47`, `getSearchResults` `:49-57`) `.map(ResponseEntity::ok)` directly on the
Mono, so the error short-circuits before any status is chosen -> clean 404. The fix is to resolve the
session existence as a Mono first (or `switchIfEmpty`/`onErrorResume` mapping `NotFoundException`) before
committing the response.

## User-facing impact

Verified by FE/BE trace 2026-06-10 + runtime-backed by IT-125 (search-session-not-found, `run-log/2026-06-10-feature-complete.md`, e2e PASS). A bookmarked or shared search URL becomes inconsistent once the ephemeral session is TTL-evicted: a 500
on the filters call + a generic "Unknown Error" SPA state that reads as a platform fault, not "your link
expired." Erodes trust in shareable search links.

## Fix

- Backend: give `getFilterOptions` the same not-found handling as the Mono paths so a missing session is a
  404 USR002 (resolve `fetchFacetState` existence before the controller commits 200).
- Frontend: on a search-session 404 render a "search expired - start a new search" state instead of the
  generic error boundary.

500-vs-404 inconsistency and the generic SPA state are both code-settled AND runtime-confirmed -
`user_facing_verified: true`.
