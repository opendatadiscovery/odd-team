## Description

The scheduled-job subsystem has operability characteristics that are silently wrong on the default config and undocumented (confirmed by the feature-reflection pass):

- **Single executor thread (F-121/H-001)** — four `@Scheduled` jobs share ONE thread (Spring default `poolSize=1`; no `spring.task.scheduling.pool.size`, no `TaskScheduler` bean) and serialise. A 14-min housekeeping cycle delays the 10-min status-switch job. Mitigation `spring.task.scheduling.pool.size: 4` is undocumented.
- **Lock window too tight (F-121/H-002, F-010/H-008)** — housekeeping `lockAtMostFor=14m` is only 60s below `fixedRate=15m`; a ≥14-min cycle releases the lock before commit and can run concurrently on a second replica. Safer guidance: `lockAtMostFor >= 2 × fixedRate`.
- **No graceful drain on SIGTERM (F-121/H-010)** — await-termination unset; SIGTERM mid-housekeeping rolls back safely but leaves the ShedLock row held ~14m, pausing housekeeping cluster-wide for the lock-hold window. Operators should expect up to ~14m of housekeeping pause per rolling restart.

This documents the operator-facing tuning + expectations. The boot-WARN-on-misconfig and a custom `TaskScheduler` + Micrometer instrumentation (F-121/H-009) are operability code enhancements — follow-up upstream items, not part of this doc.
