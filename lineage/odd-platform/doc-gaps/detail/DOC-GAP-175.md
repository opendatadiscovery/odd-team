The Azure handler IS structurally constrained (Azure AD v2.0 has no RFC 7009 endpoint) — the GAP is documentation, not code. Cognito IS code-fixable (Cognito DOES expose `/oauth2/revoke`).

This compounds the revocation-asymmetry: even where Cognito's `/logout` end-session works, downstream federated IdP sessions persist.
  - **Proposed doc action**: Three-part fix on `configuration-and-deployment/enable-security/authentication/oauth2-oidc.md`. (1) Add a top-of-page "**Logout behaviour matrix**" section enumerating per-provider logout semantics: **Google** — actively revokes the OAuth2 access token via `oauth2.googleapis.com/revoke`; local WebSession invalidated. **GitHub** — actively revokes the OAuth2 grant via `DELETE /applications/{client_id}/grant`; local WebSession invalidated. **Azure** — redirects to Azure's end-session endpoint (operator-configured `logout-uri`); local WebSession invalidated; **tokens remain valid at Azure until their natural TTL expires (typically 60-90 minutes for access tokens, up to 90 days for refresh tokens)**; Azure AD v2.0 does not expose RFC 7009 token revocation. **AWS Cognito** — redirects to Cognito's `/logout` end-session endpoint (User Pool session cookie dropped); local WebSession invalidated; **tokens NOT revoked server-side** (the platform does NOT call `/oauth2/revoke`); **federated upstream IdPs (Google/Facebook/SAML brokers) are NOT signed out — the user's session at the upstream IdP remains active**. **ODD_IAM** — local WebSession only; no revocation; relies on operator-side IdP session management. (2) For deployments with stringent compliance requirements (immediate revocation on logout), document the gap explicitly: "If you require immediate IdP-side token revocation on logout for Azure or Cognito deployments, the current implementation does NOT provide it. The local platform session is invalidated; the IdP-issued tokens remain valid until natural TTL. For Cognito specifically (which DOES expose RFC 7009 revocation), this is a known gap — file an upstream issue to request handler-side revocation." (3) Code-side preferred long-term: file `/log-issue odd-platform` upstream to add Cognito revocation (Cognito exposes the endpoint; one-line addition) AND document Azure's structural limitation (Microsoft v2.0 limitation, not ODD-fixable).

  - **Severity rationale**: MEDIUM — security-compliance gap with operator-segment-specific impact. Operators with stringent immediate-revocation requirements (regulated industries, financial services, healthcare) deploying Azure or Cognito need to know the platform does NOT enforce immediate revocation; their compliance posture depends on the IdP-side TTL bound. Operators without such requirements (the majority) are unaffected — the natural TTL expiry is operationally adequate. The federated-IdP cleanup gap for Cognito is a sharper edge: a deployment federating Cognito → Google sees the user "logged out" but a returning user skips the upstream password prompt — a noticeable UX surprise even outside the compliance audience. Severity stays MEDIUM (not HIGH) because the Azure half is structurally bound (Microsoft doesn't expose RFC 7009 in v2.0) and the Cognito half has a known doc-fix path.
