## What

The GenAI "Ask a question about your data" feature unwraps the external AI service's HTTP response by stripping leading/trailing double-quote characters and unescaping Java escape sequences, then returning the result as `GenAIResponse.body`. This silently assumes the external service always returns a **bare JSON-quoted string** (e.g. `"42 datasets match"`). If the configured `genai.url` service instead returns a structured JSON object - `{"answer":"42 datasets"}` - the quote-trim has nothing to strip from the ends of `{...}`, so the **raw JSON object is passed through verbatim** and the caller receives `{"body":"{\"answer\":\"42 datasets\"}"}` with an HTTP 200. The failure is silent: no error, no log, just a wrong-looking answer body.

**Scope note (corrected 2026-06-10):** GenAI is **API-only today** - the platform UI ships a generated client (`GenaiApi.ts`) but **no shipped view, button or panel calls it** (verified by grep across `odd-platform-ui/src` excluding `generated-sources/`; confirmed by the feature docs at `active-platform-features/genai.md:9,97,128`). So the consumer that sees the malformed answer is an **API/script consumer** (curl, an internal app, a fork's custom UI), not an end user in the shipped ODD UI. An earlier revision framed this as "the user sees `{...}` rendered as their answer" - there is no such render site in the shipped product. The defect is a real **API-contract correctness trap**; it is not a shipped-UI user-facing bug.

The response-shape contract **is now documented** (it was undocumented when this issue was first drafted on 2026-06-08): `active-platform-features/genai.md:19-20,43,62` and `developer-guides/api-reference/genai.md` both specify the external service must return a "raw JSON-encoded string" and even give a conforming Flask example (`return app.response_class(json.dumps(answer), ...)`). The remaining defect is that the **code does not enforce** that contract: a backend that returns a JSON envelope still silently leaks its raw payload at HTTP 200 with no validation and no clear error.

## Where

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/service/genai/GenAIServiceImpl.java:46-47`

```java
.bodyToMono(String.class)
.map(item -> new GenAIResponse()
    .body(StringEscapeUtils.unescapeJava(CharMatcher.is('\"').trimFrom(item))))
```

`CharMatcher.is('"').trimFrom(item)` only removes `"` characters from the two ends of the string - correct for a bare quoted string `"x"`, a no-op for an object `{"answer":"x"}`. The result is then `unescapeJava`'d and stored directly on the response body. `GenAIResponse.body` is a plain `String` (verified in the generated contract model `odd-platform-api-contract/.../GenAIResponse.java`; `odd-platform-ui/src/generated-sources/models/GenAIResponse.ts`). The endpoint is `POST /api/genai/ask` (operation `genAiQuestion`), `bodyToMono(String.class)` decodes the entire upstream payload as one string regardless of its JSON structure.

## User-facing impact

API-consumer-facing only - **not** visible in the shipped ODD UI (no view calls `GenaiApi.ts`; `active-platform-features/genai.md:9,97,128`). A consumer driving `POST /api/genai/ask` against a `genai.url` whose `/query_data` returns a JSON envelope (`{"answer":...}`) receives that raw object as the `body` string at HTTP 200 - an ugly, non-prose answer with no error signal. Non-destructive (no data loss, no security exposure). Were a UI affordance ever wired up, it would render the `body` via React, which **escapes** the string (so the raw JSON would display as inert text, not execute) - confirming there is no XSS dimension, only a correctness/quality one. The behavior is code-settled (the quote-trim is unconditional); the "which backends actually do this" magnitude is integration-dependent and not yet probed (`PENDING-F-039-1`).

## Why it matters

Silent correctness trap on the integration story. Any operator who points `genai.url` at an AI backend whose `/query_data` endpoint replies with a JSON envelope (a very common shape - OpenAI-style, LangChain-style, and most "structured output" services wrap the answer in an object) gets raw JSON back instead of prose, with no signal that anything is wrong. The contract is now documented (see What), but the code does **not enforce** it - so a non-conforming backend fails silently rather than with a clear error pointing the integrator at the contract. Severity is low: it only manifests against a non-bare-string backend, produces an ugly-but-non-destructive answer (no data loss, no security exposure), and the feature is API-only today.

## Suggested fix

Make the now-documented bare-string contract **enforced** rather than implied by a quote-trim: deserialize the external response as a `JsonNode` (or a small typed DTO), validate it is the expected shape, extract the answer text, and raise a clear `GenAIException` (or fall back gracefully) when the shape is unexpected - instead of passing the raw payload through. (The doc side is already done: `active-platform-features/genai.md:30-67` specifies the bare-JSON-encoded-string contract with a conforming example; this issue is now purely the code-side enforcement of that contract, not a documentation gap.) Open to alternatives on the exact contract (keep bare-string, or move to `{ "answer": ... }`) - the key point is that whatever the contract, the code should validate it and fail loudly, not leak a malformed answer at HTTP 200.
