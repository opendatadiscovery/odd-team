## Description

The 2026-06-08 contradiction-harvest finding for F-040 asserted that the run-history surface diverges from its F-022 sibling because "bare `get()` excludes soft-deleted; the sibling uses `existsIncludingSoftDeleted` → per-test soft-deleted run history 404s." **Reading the code shows the premise is inverted, so this item documents the actual behaviour rather than the claimed 404.**

What the code actually does:

- `DataEntityRunServiceImpl.getDataEntityRuns(...)` resolves the entity via `dataEntityRepository.get(dataEntityId)` (`DataEntityRunServiceImpl.java:32`).
- That single-id `get(long id)` is `selectFrom(DATA_ENTITY).where(DATA_ENTITY.ID.eq(id))` with **no** soft-delete filter (`ReactiveDataEntityRepositoryImpl.java:126-129`). It therefore resolves DELETED (soft-deleted) entities too — it does **not** 404 on a soft-deleted test.
- The F-022 sibling surface (data-quality test report-creation / dataset linkage, `DataQualityServiceImpl.java:55-96`) gates on `existsIncludingSoftDeleted` (`ReactiveDataEntityRepositoryImpl.java:150-155`), which likewise counts soft-deleted entities.

So on the soft-delete axis the two surfaces are **aligned**: both include soft-deleted entities. There is no per-test 404 divergence.

The genuine, documentable behaviour is a **UI-vs-API** divergence, and the existing page already half-states it: `test-run-history.md` says the History tab is "hidden when the test entity's status is `DELETED` — the route redirects to the entity's Overview." That is a front-end route guard. The backend `GET /api/dataentities/{id}/runs` has no such guard and will return the run list for a DELETED entity. An operator reading the page today could reasonably infer the endpoint itself rejects DELETED entities (since the documented UI behaviour is a redirect); the page should make explicit that the guard is UI-only and the endpoint still serves run history for soft-deleted tests.
