## What

A Query Example (the Data Modelling snippet that pins "how a dataset is meant to be queried" to a dataset/term) has **no `name` field anywhere in the implementation** — not in the OpenAPI schema, not in the request body, not in the database table, and not in the authoring UI. Yet the published documentation describes a Query Example as having "a name, a description, and the query body." The result is a three-field mental model in the manual against a two-field implementation (`definition` + `query`). A user who reads the docs and then opens the create dialog (or calls the API directly) finds no way to give a snippet a name, and a catalog list that shows snippets identified only by their free-text `definition`.

## Where

The schema that every surface (API consumer, generated UI client, generated server controller) derives from declares only `definition` and `query` — no `name`:

`odd-platform-specification/components.yaml:2799-2808` (the create/update request body):

```yaml
    QueryExampleFormData:
      type: object
      properties:
        definition:
          type: string
        query:
          type: string
      required:
        - definition
        - query
```

`odd-platform-specification/components.yaml:2757-2776` (the read model — also no `name`):

```yaml
    QueryExample:
      type: object
      properties:
        id:
          type: integer
          format: int64
        definition:
          type: string
        query:
          type: string
        linked_entities:
          $ref: '#/components/schemas/DataEntityRefList'
        linked_terms:
          $ref: '#/components/schemas/LinkedTermList'
```

(`QueryExampleRef` at `components.yaml:2729-2742` is the same — `id`/`definition`/`query` only.)

The database table has no `name` column either — `odd-platform-api/src/main/resources/db/migration/V0_0_84__create_query_example.sql:1-10`:

```sql
CREATE TABLE IF NOT EXISTS query_example
(
    id           bigserial PRIMARY KEY,
    definition   text                        NOT NULL,
    query        text                        NOT NULL,
    ...
);
```

The controller is a transparent pass-through of the generated `QueryExampleFormData` (`odd-platform-api/.../controller/QueryExampleController.java:25-42` — `createQueryExamples` / `updateQueryExample` both `flatMap` the form straight into the service), so it carries exactly the fields the schema defines and needs no change beyond the regenerated DTO. The authoring UI likewise renders only the two fields — `odd-platform-ui/src/components/DataModelling/QueryExampleForm/QueryExampleForm.tsx:79-113` has Controllers named `definition` and `query` and nothing else.

## Why it matters

The gap is **silent**: there is no error, just an absence. Two concrete consequences. (1) The documentation promises a field that does not exist; a reader following the manual cannot reproduce what it describes, which is exactly the "docs lie" failure mode that erodes trust in a published manual. (2) Snippets in the catalog list and in the per-dataset / per-term "Query Examples" tabs are identifiable only by their `definition` prose — there is no short human label to scan, so a catalog with many snippets is hard to navigate. Severity is medium: no data loss and no security exposure, but it is a real product gap (the documented feature is partly fictional) that touches the spec, the persistence layer, and the UI together. The cleanest resolution aligns the implementation to the documented model rather than rewriting the manual down to two fields, because a name is genuinely useful for catalog scannability.

## Suggested fix

Add an optional `name` field end-to-end so the implementation matches the documented model:

1. `components.yaml` — add `name: { type: string }` to `QueryExampleFormData`, `QueryExample`, and `QueryExampleRef` (keep it optional, i.e. not in `required`, to stay backward-compatible with existing clients and existing rows).
2. A new Flyway migration adding a nullable `name text` column to `query_example` (and have `QueryExampleMapper` / `QueryExampleServiceImpl` read and write it).
3. UI — add a `name` Controller to `QueryExampleForm.tsx` and surface it as the snippet's display label in the catalog list and the detail page.

(Open to alternatives — if the maintainers prefer to keep Query Examples two-field, the equivalent fix is a documentation correction; this issue is filed against the code because the missing name is genuinely useful and is the lower-friction surface to align.)

## How discovered

Surfaced during the 2026-06-08 feature-reflection contradiction harvest while reconciling F-029, F-025, and F-131. The F-025 reflection (`Query Examples (CRUD + Faceted Search)`) and the F-131 reflection (`Query Example Authoring Dialog`) both record the same residual drift: the live page still describes snippets as having "a name, description, and the query body" while the form and the schema carry exactly two fields (`definition`, `query`). This issue is the code-side locus of that drift. The documentation-side correction is tracked separately as DOC-232 / DOC-GAP-125 (the live-page text edit); they share the same root cause (the missing `name`) but are distinct work items — one is a spec/persistence/UI change here, the other is a manual edit in the `documentation` repo.
