## STRENGTHENS — batch ZH (UI Routes 1) — 2026-05-26

**Trigger**: terms-route sidecar (`odd-platform__ts__routes__route__terms.md`) + management-route sidecar (`odd-platform__ts__routes__route__management.md`) enriched at substrate commit `80637ed` / `4ec2b20`.

**Strengthen delta**: DOC-GAP-138 was authored as the DataEntityDetails NaN coercion finding (`useDataEntityRouteParams()` calls `parseInt(dataEntityId, 10)` with no `Number.isNaN` guard; the parsed `NaN` flows into `fetchDataEntityDetails({dataEntityId: NaN})` and produces a generic AppErrorPage instead of a "URL is malformed" message). batch ZH surfaces TWO additional instances of the SAME class — establishing a CROSS-ROUTE-MODULE pattern, not a per-route-module isolated finding. The catalog now has **3-instance cluster coverage** at the type-assertion-lie pattern: (a) DataEntityDetails (batch J — original), (b) Terms (`useTermsRouteParams()` at batch ZH), (c) Management (`useIntegrationRouteParams()` at batch ZH).

**New structural anchors surfaced (per the two route-module sidecars)**:

- **Instance 2 — `useTermsRouteParams()`** at `termsRoutes.ts:54-63`:
  - Code: `useParams<keyof TermsRouteParams>()` (line 55) → `as TermsRouteParams` (line 57) → `parseInt(termId, 10)` (line 60).
  - The `<keyof TermsRouteParams>` generic strips the `Partial<>` wrapper that react-router-dom v6's `useParams` returns by default. The cast asserts `termId` is always a defined string.
  - At runtime: URL `/terms/foo/overview` → `useParams()` returns `{termId: 'foo'}` → `parseInt('foo', 10) = NaN`. The hook returns `{termId: NaN, termSearchId: undefined}` typed as `{termId: number, termSearchId: string}`.
  - Downstream: `TermDetails.tsx:25` consumes; `TermDetails.tsx:38` dispatches `fetchTermDetails({termId: NaN})` → backend `GET /api/terms/NaN` returns 404 → UI surfaces `<AppErrorPage>` at TermDetails.tsx:80-83. SAME UX failure mode as DataEntityDetails.
  - **NEW corner-case discovered by terms-route sidecar** (`bugs_limitations_corner_cases.[useTermsRouteParams cross-route reuse]`): the hook is REUSED outside the `/terms/:termId/*` subtree at `TermSearch.tsx:26` (inside the `/termsearch/:termSearchId` subtree). In that context, `useParams()` returns `{termSearchId: ...}` without `termId`; the destructure produces `termId = undefined`, `parseInt(undefined, 10) = NaN`, and TermSearch.tsx happens to IGNORE the `termId` field. The hook "works" by accident. A future consumer of TermSearch.tsx that mistakenly reads `termId` would silently get `NaN`. This is a SUBTLER drift than DataEntityDetails's — the hook's return shape is dishonest in the wrong-route-subtree context.

- **Instance 3 — `useIntegrationRouteParams()`** at `managementRoutes.ts:43-44`:
  - Code: `useParams<keyof IntegrationRouteParams>() as IntegrationRouteParams`.
  - The cast strips the `Partial<>` wrapper; `integrationId` is asserted as a defined string.
  - At runtime: if a caller invokes the hook OUTSIDE a route that has `:integrationId` in its path, `useParams` returns `{}`, the destructure produces `{integrationId: undefined}`, the cast SILENTLY removes the `undefined`-handling at the type system, and any consumer that does `const { integrationId } = useIntegrationRouteParams(); fetchIntegration(integrationId);` (no null-check) crashes at runtime with the URL parameter undefined.
  - The single in-repo caller (`IntegrationHeader.tsx`) is grep-confirmed to be inside an `:integrationId` route, so the assertion holds today — but the assertion is a type-system lie waiting for the next caller (the management-route sidecar `bugs_limitations_corner_cases.[useIntegrationRouteParams type-asserts]` records this as LOW).
  - **The Integrations sub-route's permission-wrapping asymmetry** (per management-route sidecar `bugs_limitations_corner_cases.[1]`): the `/management/integrations` and `/management/integrations/:id` routes have NO `WithPermissionsProvider` wrapping at all (`ManagementRoutes.tsx:150`). If the Integration list/detail components rely on `usePermissions()` for any internal gating, those calls fall back to the OUTER Management.tsx context (which carries only `[OWNER_ASSOCIATION_MANAGE]`), producing surprising deny-by-default for any integration-specific permission check. This is the SAME class of "type-assertion-lie meets context-fall-through" that the original DOC-GAP-138 surface didn't have — NEW DIMENSION via the management-route sidecar.

- **The CROSS-ROUTE-MODULE pattern is consistent**: all three instances are typed wrappers around `useParams<T>()` that perform an `as T` cast stripping `Partial<>`; none of the three implement `Number.isNaN` / `isUndefined` / `isNullish` guards; all three produce silent runtime failures (NaN propagating, undefined propagating) that surface as generic backend 404/500 errors at the UI's AppErrorPage layer rather than at the parameter-decode layer.

- **The CONVENTION is structural**: the patterns are not bugs in isolation — they reflect a deliberate ergonomic choice (consumers don't want to write `const params = useParams(); if (!params.termId) return null;` boilerplate). The drift is the documentation-vs-runtime gap: the type signature promises a non-undefined / non-NaN value, but the cast erases the runtime check the type system DID provide. The CONSISTENT shape across 3 route modules suggests this is platform convention, not isolated oversight; a single utility `useStrictParams` that enforces the cast WITH a runtime guard would close all 3 instances in one place.

**Proposed action — UPDATE to DOC-GAP-138's original proposed action**:

The original DOC-GAP-138 proposed (A) a code fix at `DataEntityDetails.tsx` adding `Number.isFinite(dataEntityId)` guard OR (B) a doc note in `developer-guides/contributing/testing-the-ui.md`. The batch-ZH strengthen extends BOTH options:

- **Option A-EXTENDED (code fix)**: Add a utility `useStrictParams<T>(parser?)` at `components/shared/contexts/RouteParams/useStrictParams.tsx` that wraps `useParams<keyof T>()` + applies the cast + runs a configurable parser/validator (e.g. `parseInt + isFinite`) + returns a guarded result OR throws/redirects to `<NotFoundPage>` when the params are not valid. The 3 call-sites (`useDataEntityRouteParams`, `useTermsRouteParams`, `useIntegrationRouteParams`) become 3-line wrappers around `useStrictParams`. Single fix closes 3 instances + future-proofs the convention.
- **Option B-EXTENDED (doc note)**: Replace the developer-guide note with a META section in `developer-guides/contributing/testing-the-ui.md` (the page DOC-GAP-137 proposed) titled "Route-params hooks must validate, not just cast" listing the 3 known instances + the type-system-lie pattern + the recommended `useStrictParams` utility.
