## What

The `collector` table soft-deletes rows (`is_deleted boolean NOT NULL DEFAULT FALSE`) rather than hard-deleting them, but `name` carries a **full, unconditional** `UNIQUE` constraint. As a result, once an operator deletes a collector, its name is occupied **forever** by the soft-deleted row: any attempt to create a new collector reusing that name (the obvious "I deleted it, let me recreate it the same way" workflow, and any idempotent provisioning/IaC that recreates collectors by name) fails on a unique-constraint violation. The same trap applies to `oddrn`. The name is never freed, even though the entity is logically gone from the user's perspective.

## Where

`odd-platform-api/src/main/resources/db/migration/V0_0_29__add_collector.sql:4` (constraint), with the soft-delete column at `:9`:

```sql
CREATE TABLE IF NOT EXISTS collector
(
    id           bigserial PRIMARY KEY,
    name         varchar(255) UNIQUE,          -- line 4: full, unconditional UNIQUE
    oddrn        varchar(255) UNIQUE,           -- line 5: same trap on oddrn
    description  varchar(255),
    namespace_id bigint,
    token_id     bigint,
    is_deleted   boolean                     NOT NULL DEFAULT FALSE,   -- line 9: rows are soft-deleted, not removed
    ...
);
```

Because `name` is `UNIQUE` over **all** rows (including `is_deleted = true`), the soft-deleted row keeps the name reserved and blocks any recreate-by-name.

## Why it matters

This is a **loud, permanent** failure on a first-class user workflow. Delete a collector, then try to recreate one with the same name - the platform rejects it with a database unique-violation, and there is no way for the operator to free the name short of editing the database directly (un-deleting or physically removing the soft-deleted row). It breaks:

- the basic delete-then-recreate-by-name flow in the UI;
- any declarative/idempotent provisioning that recreates collectors by a stable name after a teardown;
- migration/re-import scenarios where collectors are re-established with their original names.

Severity is **high**: it is not data loss, but it is a hard, unrecoverable-via-UI block on an expected lifecycle operation, and the error surfaces as an opaque constraint violation rather than an actionable message.

## Suggested fix

Make the uniqueness predicate soft-delete-aware so that only **live** rows must be unique, freeing the name once a collector is soft-deleted. A PostgreSQL partial unique index is the standard approach (open to alternatives):

```sql
-- replace the table-level UNIQUE on name (and oddrn) with partial unique indexes
ALTER TABLE collector DROP CONSTRAINT IF EXISTS collector_name_key;
ALTER TABLE collector DROP CONSTRAINT IF EXISTS collector_oddrn_key;

CREATE UNIQUE INDEX collector_name_active_uq
    ON collector (name)  WHERE is_deleted = false;
CREATE UNIQUE INDEX collector_oddrn_active_uq
    ON collector (oddrn) WHERE is_deleted = false;
```

(The exact auto-generated constraint names should be confirmed against the running schema before dropping.) This mirrors the soft-delete-aware uniqueness pattern used elsewhere in the schema for entities that are deactivated rather than removed. If the project prefers, an alternative is to clear/namespace the `name` on soft-delete instead of changing the index - but the partial-index approach keeps the audit trail intact and is the least invasive.
