## What

Operational hardening epic for the WAL-driven notification subsystem. Six distinct defects, each load-bearing for operators running notifications at scale. (The 7th defect - Slack mrkdwn injection - is filed separately as **PLT-015** because it is a SECURITY issue with a one-line sanitization fix; the six below are reliability + privacy issues with deeper architectural shape.)

**Defect 1 - Poison-message WAL replay loop.** `NotificationSubscriber.run()` calls `messageProcessor.process(decodedMessage.get())` (`NotificationSubscriber.java:80`) with no try/catch around that call; only the outer loop has a catch-all (`:90`) that logs, releases the lock, and re-enters the `while` loop. Because `setAppliedLSN`/`setFlushedLSN` (`:83-84`) are reached only on success, a persistent-bad ALERT row throws, the LSN is never advanced, and the loop retries it forever - blocking all subsequent delivery. Operator sees notifications silently stop; no error surface beyond a log line; only diagnosis is reading Postgres logical replication state.

**Defect 2 - Cross-channel abort when EmailNotificationSender wraps as RuntimeException.** `EmailNotificationSender.send` wraps SMTP/template errors as `RuntimeException` (`EmailNotificationSender.java:58-60`), not `NotificationSenderException`. The dispatcher's per-sender catch handles ONLY `NotificationSenderException` (`AlertNotificationMessageProcessor.java:29-34`), so the RuntimeException escapes the for-loop over senders entirely and propagates to the subscriber's outer catch. If email is earlier in iteration order and SMTP is failing, fan-out aborts for subsequent senders (Slack, webhook never attempted) - AND the escaped throw is itself a poison message (Defect 1), pinning the LSN.

**Defect 3 - Empty-channels DB cost.** When notifications are ENABLED (`NOTIFICATIONS_ENABLED=true`) but no outbound channel (email/webhook/Slack) is configured, the translator still runs the recursive-CTE downstream-lineage walk on every alert WAL event - `AlertNotificationMessageTranslator.translate` unconditionally calls `fetchDownstream` (`AlertNotificationMessageTranslator.java:80`, the `fetchDownstream` at `:148-185`; it short-circuits only when the configured `downstreamEntitiesDepth == 0`). Operators who turn the feature on but have not (yet) wired a channel pay the lineage-walk cost per alert with no delivery. (Note: when `NOTIFICATIONS_ENABLED=false` the whole subsystem is conditional-ed out via `NotificationsFeatureCondition`, so this is specifically the enabled-but-no-channel window, not the default-off state.)

**Defect 4 - No idempotency / no DLQ / no audit on delivery.** `PostgresWALMessageProcessor` SPI has void-return - the dispatcher cannot signal partial-failure / requires-replay. Failed deliveries are lost without trace; operators cannot diagnose which alerts were delivered to which channel without inspecting downstream channel state.

**Defect 5 - PII passthrough to every channel.** The translator aggregates each entity's owners (`OWNER.NAME` + `TITLE.NAME`) into the `AlertedDataEntity` and attaches both the alerted entity and its `downstream[]` lineage entities (each with their owners) to the `AlertNotificationMessage`, which is serialized verbatim to Slack/webhook/email - no redaction (`AlertNotificationMessageTranslator.java:118-145, 148-185`). Cross-team owner identities reach every configured notification channel.

**Defect 6 - Webhook signing absence.** `WebhookNotificationSender.send` (`WebhookNotificationSender.java:18-24`) POSTs notifications with only `.uri()` and `.POST(body)` - no `Authorization`, no `X-ODD-Signature`, no HMAC. Operator's receiver cannot verify the message came from their ODD Platform.

## User-facing impact

All six are operator-facing reliability/privacy defects on the alert-notification delivery path (this subsystem has no end-user UI surface of its own - the "user" is the on-call operator / receiver-system owner). Structural facts are code-settled; the observable symptoms are timing/config/data dependent (flagged below).

- D1 (poison loop): WHO - operators relying on alert delivery (Slack/email/webhook). They OBSERVE all notifications stopping after one un-processable alert, with no surfaced error. Code path settled (`NotificationSubscriber.java:80,83-84,90`); the trigger (a row that makes `translate`/`send` throw) and timing are runtime-dependent - the exact poison input needs a live drive.
- D2 (cross-channel abort): operators OBSERVE Slack/webhook going silent while the real fault is SMTP, if email iterates first. Settled that a RuntimeException escapes the dispatcher catch (`EmailNotificationSender.java:58-60` vs `AlertNotificationMessageProcessor.java:29-34`); sender ordering and an actual SMTP failure are the runtime variables.
- D3 (empty-channel DB cost): operators who set `NOTIFICATIONS_ENABLED=true` without a channel OBSERVE per-alert recursive-CTE lineage load for nothing. Settled at `AlertNotificationMessageTranslator.java:80,148-185` (runs unless `downstreamEntitiesDepth==0`); load magnitude is data/depth dependent.
- D4 (no DLQ/audit): operators cannot tell which alert reached which channel; a failed send is logged and dropped (`AlertNotificationMessageProcessor.java:29-34`, void SPI). Settled by code structure.
- D5 (PII passthrough): a receiver-system owner (and anyone with channel access) SEES every alerted/downstream entity's owner names + titles in the payload, including cross-team identities. Settled - owners are serialized verbatim (`AlertNotificationMessageTranslator.java:118-145,148-185`); whether that is "PII" depends on the deployment's owner-naming.
- D6 (no webhook signing): a webhook receiver cannot authenticate the sender (no `Authorization`/signature). Settled - the POST carries no auth header (`WebhookNotificationSender.java:18-24`).

The notification subsystem is the **load-bearing operator-visible surface** for alerts, on-call paging, and incident response. Each defect erodes operator trust in a different dimension:

- Defect 1 -> notifications silently stop; on-call doesn't get paged; incident response degrades
- Defect 2 -> notifications partially-stop; operators believe Slack is broken when SMTP is actually the culprit
- Defect 3 -> cost / capacity-planning surprise; small-cluster evaluations see disproportionate DB load
- Defect 4 -> no observability into delivery; operators cannot diagnose which alerts reached which channel
- Defect 5 -> privacy / compliance issue; cross-team owner identities reach every channel
- Defect 6 -> operators cannot validate webhook payloads at the receiver - open to replay / forge

Severity is MEDIUM (not HIGH) because each individual defect is operational, not security-critical; the compound is severe but no single defect rises to LSN-001/002 threshold on its own. (The exception, Slack mrkdwn injection, is HIGH and filed separately as PLT-015.)

## Suggested fix

Six distinct fixes; could be one epic PR or six independent PRs. Recommend grouping into **3 PRs** by architectural shape:

### PR-1 - Subscriber + dispatcher hardening (Defects 1 + 2 + 4)

```java
// NotificationSubscriber.java:77-91 - wrap with try/catch and route bad messages to a DLQ
try {
    messageProcessor.process(record);
} catch (Throwable t) {
    log.error("poison message at LSN {}; routing to DLQ", record.getLsn(), t);
    deadLetterQueue.accept(record, t);
    // ACK so the slot advances even on failure
}

// EmailNotificationSender.java:58-60 - wrap as NotificationSenderException, NOT RuntimeException
- throw new RuntimeException(e);
+ throw new NotificationSenderException("SMTP send failed", e);

// PostgresWALMessageProcessor - change SPI return type
- void process(ChangeRecord record);
+ ProcessResult process(ChangeRecord record);  // SUCCESS | PARTIAL_FAILURE | REQUIRES_REPLAY
```

The DLQ in this context can be a Postgres table (`notification_dead_letter`) the operator queries to see what was dropped. Combined with the SPI return type change, the dispatcher has full observability into delivery state.

### PR-2 - Empty-senders short-circuit (Defect 3)

```java
// NotificationSubscriber - short-circuit if no senders are configured
if (configuredSenders.isEmpty()) {
    log.debug("no notification senders configured; skipping translator");
    return Mono.empty();   // skip the recursive-CTE walk
}
return translator.translate(record).flatMap(this::dispatch);
```

One-config-check at the subscriber boundary; saves the downstream-lineage walk entirely when no channels are active.

### PR-3 - Privacy + signing (Defects 5 + 6)

```java
// Defect 5 - introduce a PII redaction policy at the message-builder boundary
//   - new config: notifications.pii-redaction.enabled (default: false for compat)
//   - notifications.pii-redaction.fields: [owners, downstream-entities, owner-emails]
//   - operators opt in for compliance posture; default unchanged

// Defect 6 - webhook HMAC signing
// new config: notifications.webhook.signing-secret (operator-configured)
HttpHeaders headers = new HttpHeaders();
headers.set("X-ODD-Signature", "sha256=" + hmacSha256(signingSecret, body));
headers.set("X-ODD-Webhook-Id", webhookId);     // for replay protection
```

Document the signature format on the notifications doc page so operator receivers can validate.
