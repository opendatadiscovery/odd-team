## Description

`AppErrorPage` renders a status-code column and a status-text headline from its optional `error` prop. `AppErrorPage.tsx:24-29`:

```
<Typography variant='errorCode' ...>{error?.status}</Typography>
...
<Typography variant='h1'>{error?.statusText ?? t('Unknown Error')}</Typography>
```

When a caller passes `showError` but **omits** the `error` prop, the status-code column renders empty (`error?.status` is `undefined`) and the headline falls back to the literal `t('Unknown Error')` — the operator sees a content-free error page that cannot tell them what failed (was it 403? 500? a network drop?).

`OwnerAssociationsActive.tsx:99` does exactly this: `<AppErrorPage showError={isError} offsetTop={182} />` — **no `error` prop**. The harvest notes this pattern is shared by 3 Owner-Association callers (the active/new/resolved association lists, which render structurally identical error footers). The asymmetric counter-example is `IntegrationPreviewList.tsx:70`: `<AppErrorPage showError={isError} error={error as ErrorState} offsetTop={120} />` — it DOES forward the error, but via an unchecked `error as ErrorState` cast (the query error is force-cast rather than validated, so a non-`ErrorState` shape would still type-check and could render `undefined` fields at runtime).

So the same component is fed two different degraded contracts: one branch drops the error entirely; the other casts an unvalidated error in.

**Typed gate: characterization-pin (LSN-029).** This asserts the CURRENT (degraded) behaviour — Owner-Association error pages show an empty status code + "Unknown Error" — and goes RED the instant a caller starts forwarding a real error object (the intended fix). It does NOT @Disable and does not assert the desired end state.
