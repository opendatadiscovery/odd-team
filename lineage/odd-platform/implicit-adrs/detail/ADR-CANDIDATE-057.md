  - **Decision statement**: ODD's lineage endpoint composes two architectural decisions: (a) **single-query recursive-CTE traversal** — `ReactiveLineageRepositoryImpl.java:122-176` builds a Postgres `WITH RECURSIVE` CTE that walks the lineage graph depth-bounded in ONE DB round-trip, using `UNION ALL` for recursion + an outer `selectDistinct` for deduplication. The alternative (BFS with one round-trip per node) would have manifested as N round-trips in the impl and was deliberately avoided. (b) **Client-driven progressive expansion** — the endpoint accepts TWO independent parameters: `lineage_depth` (a recursion-depth ceiling, e.g. 3 for the default canvas render) and `expanded_entity_ids` (a list of node IDs whose immediate downstream neighbours should ALSO be merged in, regardless of the depth ceiling). The service signature carries both parameters explicitly (`LineageServiceImpl.java:87-122`) rather than collapsing them into a single "effective-depth" input. The decision encodes the UI canvas UX: the initial render asks for a shallow tree (depth=3); subsequent user clicks expand specific subgraphs by adding the clicked node's ID to the `expanded_entity_ids` list and re-requesting. The merge at `lineageRelations.mergeWith(expandedRelations).distinct()` (line 102) handles the union. **NEW 2026-05-19I**: the service-tier sidecar adds a third confirming sub-decision — the count queries (`getChildrenCount`, `getParentCount`) run CONCURRENTLY with the main lineage fetch via `Mono.zip(repositoryMapsMono, getChildrenCount, getParentCount)` (lines 113-114). The Mono.zip parallelism is the one place where the otherwise-sequential pipeline fans out — a deliberate optimisation for the canvas render latency. Trade-off accepted: simpler-and-more-flexible canvas UX vs the structural consequence that an authenticated caller can drive arbitrarily-expensive queries by setting `lineage_depth=10000` (REFACTOR-202's no-upper-bound gap) or by submitting a 30K-element `expanded_entity_ids` list (REFACTOR-205's `IN`-clause Postgres-parameter-limit gap).
  - **Wisdom test**: PASS. The dual-parameter signature on the service is the intent anchor (the alternative — a single effective-depth — would have been simpler but precludes the canvas UX). The recursive-CTE choice over BFS is structural — it commits ODD to Postgres-specific SQL (the CTE is hand-written via JOOQ `withRecursive`), parallel to ADR-CANDIDATE-020 / -043's "Postgres-as-only-dependency" posture for advisory locks. The batch-I service-tier confirmation reinforces the design: the two-query split is visible at the service method, not just the repository. Structural for every future graph-shaped endpoint on the platform.
