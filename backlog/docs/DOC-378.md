## Description

The platform's deletion semantics are **not uniform across resource types**, and nothing in the published docs states the per-resource contract in one place. The entity-level model is well documented (`data-discovery/statuses.md` + ADR-0058: deleting an *entity* is a soft delete — status → `DELETED`, recoverable during a housekeeping TTL window, physically purged after). But that soft-delete model is **entity-scoped only**. Sub-resources delete with different semantics:

- **Ownership** is a **hard delete**. `ReactiveOwnershipRepositoryImpl.delete(...)` issues a physical `DSL.deleteFrom(OWNERSHIP)` — the row is gone immediately, no status flag, no TTL window. The **only** recovery trail is the Activity Feed's `OWNERSHIP_DELETED` event, which records that the deletion happened — and that trail is itself TTL-bounded (the activity feed is not retained forever). So an operator who removes an owner cannot "restore" it the way they restore a soft-deleted entity; they can only read *that* it was removed from the feed, while the feed still holds the event.

This asymmetry is a foot-gun: an operator who has internalised "deletion is soft and recoverable" from the entity-status docs will reasonably assume the same for an owner they removed by mistake, and be wrong. The fix is a **per-resource deletion-contract table** that states, for each user-deletable resource, whether the delete is soft (status flip, TTL-recoverable) or hard (immediate row removal), and what the recovery path is. The table's canonical home is `data-discovery/statuses.md`, which already owns the soft-delete narrative — extending it to "and here is how *other* resources delete" keeps the whole deletion story in one place.

Scope note: the `collector.name` and `INTERNAL metadata_field` deletion-bug halves from the same harvest finding (F-123) are filed as **PLT** code-fix items, not here — this DOC item is the documentation-contract half (the table + the ownership-via-activity-feed recovery caveat). The metadata-mutation forensic-silence (no activity event on custom-metadata delete) is already documented on `data-discovery/custom-metadata.md`; the table should cross-link it rather than restate it.
