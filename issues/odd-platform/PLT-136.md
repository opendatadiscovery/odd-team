## What

`OwnerServiceImpl.delete` does **not** refresh the FTS search vectors - asymmetric with `update`. `OwnerServiceImpl.update` calls `updateSearchVectors(owner)`, refreshing both the `searchEntrypointRepository` and `termSearchEntrypointRepository` vectors inside the transaction; `OwnerServiceImpl.delete` has **no** `updateSearchVectors` call. So after a successful delete, catalog search continues to surface the deleted owner's name (matching against `search_entrypoint.search_vector` for the data entities the owner bore) until those entities are otherwise modified. The create path also omits the refresh (lazy FTS seeding), so the asymmetry is create+delete (no refresh) vs update (refreshes).

This is **net_new** - not in any existing PLT. (PLT-087 names the *DataSource*-side FTS-not-cleared asymmetry; this is the Owner-side delete-vs-update asymmetry.) It mirrors the F-006 batch-K `delete_search_vector_not_refreshed` facet on a sibling delete path.

## Evidence

From the F-019 reflection (`lineage/odd-platform/feature-reflections/detail/F-019.yaml`), hypothesis H-012:

```
OwnerServiceImpl.java:82, 109-114   (@ ede5d277)
  // update calls updateSearchVectors(owner) -> refreshes both FTS vectors in-transaction

OwnerServiceImpl.java:87-100   (@ ede5d277)
  // delete has NO updateSearchVectors call -> deleted owner name stays in the index
```

## Impact

(1) A deleted Owner's name keeps appearing in catalog search results for an unbounded window (until each affected data entity is independently re-indexed), so operators and users see a "ghost" steward. (2) Combined with name re-use, search can show both the soft-deleted old Owner's stale match and the new Owner with the same name, confusingly. Correctness/freshness gap, not data loss.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: call `updateSearchVectors(owner)` (or an FTS-removal equivalent) in `OwnerServiceImpl.delete` inside the transactional boundary, **or** document the stale-index window. Sibling of the F-006 batch-K `delete_search_vector_not_refreshed` facet - consider a cross-feature "delete-path FTS hygiene" sweep. Distinct from PLT-087 (DataSource-side).
