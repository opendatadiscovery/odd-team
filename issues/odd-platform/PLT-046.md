## What

The OpenAPI spec-discovery surface (the raw OpenAPI JSON **and** the Swagger UI) lives under `/api/**` - NOT under `/ingestion/**` - so `SecurityConstants.WHITELIST_PATHS` does not cover it. Reachability depends on the `SecurityWebFilterChain` wiring per `auth.type` (DisabledAuthSecurityConfiguration permits everything; LOGIN_FORM / OAUTH2 / LDAP configurations may or may not gate it per their wiring - the 4-cell matrix is not enumerated in-repo or in-docs).

**Path precision (corrected 2026-06-10):** the original draft called `/api/v3/api-docs` "the Swagger UI / OpenAPI spec discovery endpoint", conflating two distinct URLs whose springdoc paths are **swapped** in this repo (`application.yml:22-26`): `springdoc.api-docs.path: /api/v3/swagger-ui.html` (this serves the raw **OpenAPI JSON spec**) and `springdoc.swagger-ui.path: /api/v3/api-docs` (this serves the **Swagger UI** HTML). So the machine-readable spec is at `/api/v3/swagger-ui.html` and the UI is at `/api/v3/api-docs` - both are under `/api/**`, both are NOT in `WHITELIST_PATHS`, and both share the same per-auth-mode gating, so the finding (the discovery surface is reachable, with no dedicated toggle) is unchanged - only the URL labels are corrected. The grouped spec is registered by `SwaggerUIConfiguration` (`config/SwaggerUIConfiguration.java:10-15`, group `platform-api` over `/api/**`).

Operators with separation-of-duties concerns expect to gate the spec endpoint separately from the API endpoints. Today they must use a reverse-proxy layer (NGINX, Envoy, AWS ALB) to block `/api/v3/api-docs` and accept that:
- They can't gate per-auth-mode at the platform layer.
- An operational deployment that forgets the reverse-proxy rule exposes the full 194-operation API surface to unauthenticated network callers ("reconnaissance-via-spec").

A platform-level toggle (`auth.swagger.enabled` defaulting to `true` for backward compatibility) lets operators explicitly opt out of public spec discoverability without leaving the platform's auth model.

## User-facing impact

The "user" is an operator with separation-of-duties expectations about who can see the API surface, and (negatively) a network-adjacent attacker doing reconnaissance.

- **Code-settled half (under the shipped default `auth.type=DISABLED`):** the spec JSON (`/api/v3/swagger-ui.html`) and Swagger UI (`/api/v3/api-docs`) are reachable anonymously - `DisabledAuthSecurityConfiguration.securityWebFilterChainDisabled` is `.anyExchange().permitAll()` (`config/DisabledAuthSecurityConfiguration.java:12-18`) and neither path is in `WHITELIST_PATHS` (so they ride the same permit-all chain). Verified by BE trace 2026-06-10. There is **no platform-level toggle** to gate the spec surface separately from `/api/**` (grep-verified: no `auth.swagger` key exists) - so the feature request is valid: today the only opt-out is a reverse proxy.
- **NOT-yet-traced half (load-bearing for the recon framing):** the draft's "reachability differs across the 4 auth configs / the matrix is not enumerated" is itself unverified here - I did not trace `LoginFormSecurityConfiguration` / OAUTH2 / LDAP to determine whether they already require auth on `/api/**` (which includes the spec surface). Under LOGIN_FORM/OAUTH2/LDAP the spec surface is very plausibly already behind auth (those chains gate `/api/**`), in which case the anonymous-recon risk is specific to the DISABLED default. *This matrix must be enumerated before filing* - it determines whether the toggle's value is "defense-in-depth for DISABLED demos" or "a real gap in authenticated modes too."
- Because the non-DISABLED matrix is the part that sizes the risk and is not yet traced, `user_facing_verified` stays **false**.

## Why

Reconnaissance-via-spec is a real failure shape in published-API deployments. The Swagger UI exposes all 194 operations with their parameters, response shapes, and security framing - enough for an attacker to enumerate every authenticated endpoint and probe each one. A separation-of-duties-conscious organisation expecting "Swagger UI is admin-only" cannot verify the assumption today against the docs; they fall back to reverse-proxy layers that are easy to forget.

A platform-level toggle is the operator-visible answer. Backwards-compatible (`true` default), one line in YAML to opt out, and surfaces correctly in the per-auth-mode matrix that DOC-196 ships on `developer-guides/api-reference.md`.

## How

Three-piece change:

**1. Config key**:
```yaml
auth:
  swagger:
    enabled: true   # set false to require authentication on /api/v3/api-docs
```

**2. SecurityWebFilterChain wiring** (in each of the 4 auth-mode configs, OR centralised in a single bean post-`auth.type` resolution):

```java
@Bean
@ConditionalOnProperty(value = "auth.swagger.enabled", havingValue = "false")
public SecurityWebFilterChain swaggerAuthFilterChain(ServerHttpSecurity http) {
    return http
        .securityMatcher(ServerWebExchangeMatchers.pathMatchers("/api/v3/api-docs", "/api/v3/api-docs/**"))
        .authorizeExchange(spec -> spec.anyExchange().authenticated())
        .build();
}
```

When `auth.swagger.enabled=true` (default), the chain falls through to the existing per-auth-mode wiring - backwards-compatible.

**3. Documentation**: paired DOC-196 names the toggle's existence + cross-links the per-auth-mode matrix.

## Paired doc-side fix

**DOC-196** ships the operator-facing per-auth-mode reachability matrix on `developer-guides/api-reference.md`. The matrix can be derived from code today (each `SecurityWebFilterChain` config class has a `securityMatcher` + decision); the matrix landing makes the un-toggled state visible to operators and points at PLT-046 for the opt-out story.

## Tests

- Unit test on the conditional bean: `auth.swagger.enabled=false` registers the chain; `=true` (default) does not.
- Integration test: with the toggle off, anonymous GET on `/api/v3/api-docs` returns 401 (under LOGIN_FORM) / 403 (under OAUTH2) - depending on the existing auth-mode wiring's response shape.
- Regression check: with the toggle at default (`true`), all existing integration tests still pass; no change to current behaviour.
