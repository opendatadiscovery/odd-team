## What

A user who opened a dataset, term, query example or lookup table yesterday has to re-search for it today --
ODD Platform keeps no per-user history. Add **Recently Viewed**: when a user opens an asset's detail page it is
recorded; the user's recently-opened assets are shown as a 5-item panel on the main page (with a "View all"
link) and as a new filterable top-level **Recently Viewed** tab, most-recent-first. The user can remove any
entry. Recently Viewed is **per user** -- keyed on the logged-in identity `(oidc_username, provider)`, NOT the
internal Owner -- so every user gets it, including users with no Owner. When `auth.type=DISABLED` (no
authenticated principal) it backs a single shared instance-wide bucket, labelled "Recently Viewed (shared)".

**This issue depends on PLT-249 (Favorites)**, which ships the shared foundation both features reuse: the
identity resolver (with the DISABLED sentinel), the polymorphic `(asset_kind, asset_id)` asset model, the
`getAlertsList`-shaped faceted list endpoint, the reusable main-page panel slot, and the top-level tab + facet
sidebar + "Asset type" facet. This issue adds the view-recording signal, the `recently_viewed` store, removal,
and a retention job on top of that foundation.

## User-facing impact

- A user opens an asset detail page; it is recorded as recently viewed. Re-opening it moves it to the top
  (deduped -- one row per asset, newest timestamp).
- On the main page the user sees a "Recently Viewed" panel with their 5 most-recent assets and a "View all"
  link to the tab.
- On the Recently Viewed tab the user filters by Namespace, Datasource, Tag, Owner and Asset type
  (multi-select, default All), most-recent-first, paginated, and can remove individual entries.
- A user with no Owner gets the feature. Under DISABLED auth it is labelled "Recently Viewed (shared)" with a
  shared-bucket subtext -- never presented as private history.

`user_facing_verified: false` -- not-yet-built feature; behaviour above is the intended design.

## Why it matters

"Take me back to what I was just looking at" is core catalog navigation, and ODD has no history at all. Combined
with Favorites (PLT-249) it gives every user -- crucially including the large audience that never completes
Owner association -- a useful personal landing page. Recently Viewed is distinct from Popular (which is a
global, shared `view_count` ranking, not personal) and from Alerts (no notifications).

## Suggested fix

Open to refinement; researched design (PRD-0001), reviewed for security and performance. Builds on the
PLT-249 shared foundation.

### Recording (the load-bearing performance + privacy decision)

- **Do NOT record a view as an implicit side effect of `GET /api/dataentities/{id}`.** That endpoint is already
  hit by panels, lineage expansion, polling and prefetch, and already carries the `incrementViewCount` write;
  widening its side effects compounds a hot path and miscounts machine traffic.
- Record from a **deliberate signal** -- `POST /api/recently-viewed {asset_kind, asset_id}` -- fired by the
  frontend when a detail page opens (debounced/deduped client-side). This also uniformly covers terms, query
  examples and lookup tables, which have no `view_count`.
- The backend write is **fire-and-forget** (the response is never gated on it) and **must resolve
  `(oidc_username, provider)` inside the request chain first, then hand the value to the async writer** -- a
  bare `.subscribe()` loses the Reactor security context and drops the principal. Never block the event loop
  (WebFlux/R2DBC). The write is an idempotent UPSERT (`ON CONFLICT ... DO UPDATE SET last_viewed_at = now()`)
  -- move-to-top, no append/dedup churn.

### Store, removal, retention

- **Data model** (migration `V0_0_94`, shared with PLT-249; UTC timestamps; no FK to asset tables):

  ```
  recently_viewed(id bigserial pk, oidc_username varchar(512), provider varchar(255),
                  asset_kind varchar(64), asset_id bigint,
                  last_viewed_at timestamp NOT NULL default (now() at time zone 'UTC'),
                  unique (oidc_username, provider, asset_kind, asset_id))   -- UPSERT target
  index on (oidc_username, provider, last_viewed_at DESC)                   -- list/panel ordering
  ```

- **Remove** -- `DELETE /api/recently-viewed/{asset_kind}/{asset_id}` (per-row, hard delete; cold path).
  "Clear all history" is a recommended fast-follow (per-row remove is the MVP control).
- **Retention (unbounded growth otherwise)** -- add `RecentlyViewedHousekeepingJob implements HousekeepingJob`
  following the existing pattern: trim to the newest N per user, delete rows older than
  `housekeeping.ttl.recently_viewed_days` (~90), and purge orphans (assets hard-deleted by
  `DataEntityHousekeepingJob`). Add the day field to `HousekeepingTTLProperties` + `application.yml`. The job is
  ShedLock-guarded for multi-instance safety; eviction stays off the request hot path.

### List + visibility (reuses the foundation)

- `GET /api/recently-viewed/list` -- same facets/page/size as Favorites, ordered `last_viewed_at DESC`; the
  panel calls it with `size=5`; `size` capped server-side.
- Resolve titles by semi-joining `(asset_kind, asset_id)` onto each kind's existing query (no denormalisation),
  so deleted/hidden assets drop out automatically.

### Security & privacy

- Recently Viewed is a per-user browsing history (PII-adjacent; `username` is often an email). **Principal-scoped
  reads only** -- a user reads only their own `(username, provider)` rows; ODD's read-collaborative posture must
  NOT extend to browsing history. Identity from the security context only.
- **Erasure** -- provide the per-row delete + the fast-follow "clear all", and hook an operator-side erase for a
  `(username, provider)` onto the existing owner-mapping deletion path.
- **DISABLED shared bucket** -- the muddiest cell ("recently viewed by everyone"). Keep it (per requirement) but
  label "Recently Viewed (shared)", never as personal history; provide a `recently-viewed.enabled` flag
  (defaults on) so an operator can hide the surface, plus a docs caveat.

### Cross-cutting (do not silently defer)

OpenAPI (new paths + reuse of the shared schemas) -> regenerate BOTH clients; backend
controller/service/repository(+Impl)/mappers + JOOQ regen; the housekeeping job + TTL config; frontend Redux
slices/thunks/selectors, the detail-open POST hook, the panel, the tab, the facet sidebar, the per-row remove
control, the route, the nav entry; i18n in all six locales (en/es/fr/ua/hy/ch); user docs (Features). No
activity-log entry.
