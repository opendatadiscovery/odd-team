## Description

`Features.md` documents the platform feature flags (`datacollaboration.enabled`, `notifications.enabled`, etc.) without warning that they are **bare SpEL placeholders with no default**. In `FeatureResolverImpl`, these are resolved as `${datacollaboration.enabled}` / `${notifications.enabled}` with **no `:false` (or any) default**. The values live only in the shipped `application.yml`.

The consequence: an operator who supplies their own configuration (a common production pattern — externalised config, a trimmed `application.yml`, env-var-only config) and **omits one of these keys bricks platform startup** — Spring cannot resolve the placeholder and the context fails to initialise. The platform does not start with the feature merely "off"; it does not start at all. This is the LSN-001/002 "default-with-consequence" class (REFACTOR-625), and it is silent until the operator restarts with their own config.

High — a startup footgun an operator hits by doing normal config externalisation, with no doc warning.

**Failure shape**: missing caveat (Gate 3/6) — a boot-failure behaviour of documented config flags is undocumented.
