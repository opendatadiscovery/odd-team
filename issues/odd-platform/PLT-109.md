> ⚠️ **SECURITY — responsible disclosure.** This describes an **unfixed, exploitable SQL-injection**. Do **not** open this as a public GitHub issue and do **not** publish the vector in the docs until a fix ships. File it via the repo's **private GitHub Security Advisory** flow. The paired doc item (`backlog/docs/DOC-313.md`) is deliberately constrained to a non-disclosing perimeter caveat for the same reason.

## What

The search-result **highlight** endpoint builds a raw SQL string by interpolating both the catalog-supplied `text` and the **user-supplied** `tsQuery` directly into a `ts_headline(...)` call with no escaping or bind parameters:

```java
// ReactiveDataEntityRepositoryImpl.java:801-802 (@ ede5d277)
final String sql = "ts_headline('english', '%s', to_tsquery('%s'), 'HighlightAll=true')"
    .formatted(text, tsQuery);
```

`tsQuery` derives from the persisted `search_facets.query_string` (user-controlled) after tokenisation; `text` is catalog content. Neither is escaped before interpolation, so a crafted query that later flows through the highlight path executes arbitrary SQL on the read connection — not merely a `to_tsquery` syntax error (that DoS angle is already documented and is a separate, lesser issue).

| `odd-platform-api/src/main/java/.../controller/SearchController.java` | (class) | `highlightDataEntity` → `getHighlightedResult` chain reaches the above; route `GET /api/search/{search_id}/data_entities/{data_entity_id}/highlights` |

Verified by the triager @ ede5d277 (current `odd-platform` HEAD).

## Why it matters

Arbitrary read-side SQL via a catalog search is a critical vulnerability. Under `auth.type=DISABLED` (the shipped default) the search surface is **anonymously reachable**, so the injection is exploitable without authentication; in any multi-tenant deployment an authenticated low-privilege user can reach data across tenants. The catalog DB connection has broad read access. This is squarely the "guidance is the cliff" class — operators trust catalog search to be safe.

## Suggested fix

- Do **not** interpolate `text`/`tsQuery` into SQL. Pass them as **bind parameters** to `ts_headline` / `to_tsquery` (jOOQ `DSL.val(...)` / `inline=false`), or use the jOOQ `ts_headline`/`tsquery` DSL so the values are parameterised.
- Add a focused test that a query containing SQL metacharacters (`'`, `;`, `--`, `)`) is treated as data, not SQL.
- Consider a repository-wide audit for other `String.format`/`.formatted(`/string-concatenation SQL assembly (grep `\.formatted(` + `"SELECT`/`"select` near `+`).
