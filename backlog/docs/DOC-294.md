## Description

The reference-data API reference and the lookup-tables feature page both overstate the access-control model for lookup tables. Two code-confirmed problems:

1. **No per-table RBAC; READ is ungated.** `api-reference/reference-data.md` opens with "All endpoints require auth and respect per-table RBAC." False on two counts: (a) there is **no `LOOKUP_TABLE_*_READ` permission at all** — the 6 read + 4 search endpoints carry no SecurityRule and fall through to `authenticated()`, so reads are ungated (and anonymous under `auth.type=DISABLED`); (b) the 9 `LOOKUP_TABLE_*` rules that *do* exist use the `NO_CONTEXT` resolver — they are **not per-table / per-owner scoped**. `LOOKUP_TABLE_UPDATE` permits modifying **any** table. The lookup-tables page's "9 permissions on three surfaces" framing carries the same false per-table assumption and leaves an operator believing reads are gated when they are not.

2. **Cross-table column-PATCH via URL spoofing.** `api-reference/reference-data.md` documents `PATCH .../lookup-tables/{lookup_table_id}/columns/{column_id}` as scoped to `{lookup_table_id}`. The code (`updateLookupTableField(columnId, item)`) **drops the `{lookup_table_id}` path param entirely** — it operates on `columnId` alone. So a caller authorized to update table A can PATCH a column belonging to table B simply by spoofing the URL's table id. With the global (non-scoped) `LOOKUP_TABLE_DEFINITION_UPDATE`, this is an authorization-boundary violation.

Critical — the page makes a positive false security guarantee ("per-table RBAC") that an operator designs their access model around.

**Failure shape**: code-doc drift (false positive security claim) + missing hazard caveat (cross-table column jump).
