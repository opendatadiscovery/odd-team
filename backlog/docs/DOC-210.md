## Description

Live `/user-owner-association` lines 7-13 (verbatim): "**Admin** — Association process for admins is straightforward. 1. After logging in you will see modal dialog in the bottom of the main page. 2. Select owner which you want to associate yourself with and press `Associate` button." The description is factually wrong about two things at once:

1. **Wrong affordance** — the admin's direct-bind affordance is the "+ Create association" button on Management → Associations → Header, NOT the home-page widget. The home-page widget (`OwnerAssociationForm.tsx:121-129` home-page version, verified this session) routes through `OwnerAssociationRequest` → emits a PENDING row → requires a second admin to approve. The admin-direct path uses `useCreateUserOwnerMapping` → `POST /api/owners/mapping` (gated by `OWNER_RELATION_MANAGE` per `SecurityConstants.java:155-158`, verified) and creates the binding DIRECTLY.
2. **Wrong framing** — "modal dialog in the bottom of the main page" misnames the home-page widget UI shape (the widget is an inline section, not a modal — see DOC-217).

Operator-visible consequence: an admin reading the doc forms a wrong mental model, expects a "modal dialog in the bottom of the main page" as their admin-side binding affordance. They use the home-page widget, which actually puts them in the PENDING workflow that then requires their own approval (or another admin's). Meanwhile the actual admin-direct affordance (the Management → Associations → "+ Create association" header button) is undocumented entirely. Two mismatches stacked, both factual.
