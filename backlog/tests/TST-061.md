# TST-061 — concurrent unit builds starve each other, and the symptom mimics a product defect

## What happened

`playbooks/stream-coordination.md` serialises the **heavy e2e regression** behind a machine-wide `flock`, and
states that "the cheap buckets (unit via `ODD_PLATFORM_DIR`, a targeted API stack on your ports) parallelise
freely."

That is true for CPU and **false for memory on this machine**. During CTRIB-062, two contributor streams ran
`scripts/run-platform-tests.sh` concurrently:

- `ctrib061`: four gradle test-worker JVMs, ~4.6 GB, plus five Testcontainers `ryuk` containers
- `ctrib062`: the same shape

On a 15 GB box that left **~2 GB available**, and the result was **not** an OOM kill or any obvious
infrastructure error. It was two test failures:

```
OpenApiDocsContractTest.platformApiGroupDocumentLoads()   IllegalStateException: Timeout on blocking read for 60 s
LoadIngestionTest.testInjectingManyDataEntities()          IllegalStateException: Timeout on blocking read for 60 s
```

Both are `WebTestClient` tests with a 60-second client timeout, and `OpenApiDocsContractTest` is the regression
guard for **PLT-141**, whose real failure mode is *a spec request that hangs forever*. So the contention
signature is **byte-identical to the product bug the test exists to catch**.

## Why it matters

The cost is not the lost minutes; it is the false lead. The failure was investigated as a probable regression
in the branch under test — including tearing down that stream's own stacks, re-running "in isolation" (which
was not isolated, because the neighbour's build was invisible), and standing up a clean `origin/main` worktree
for an A/B. The contention was only found by reading `ps aux --sort=-%mem` on a hunch.

The next stream to hit this will draw the same false conclusion, and the one after that may draw a worse one —
"the PLT-141 guard is flaky" — and weaken or disable a test that protects a shipped outage.

## Suggested direction

1. **Make the contention visible.** `run-platform-tests.sh` can detect another `-Dorg.gradle.internal.worker.tmpdir=*/odd-platform-*/build/tmp/test/work` process, or free memory below a threshold, and refuse (or warn loudly) before spending 30+ minutes producing an uninterpretable result.
2. **Register it.** `state/active-streams.yaml` has no "unit build in progress" signal, so a starting stream cannot see what the machine is already doing. A `wants: unit-build` entry would at least make it readable.
3. **Correct the playbook.** Replace "parallelise freely" with the measured truth: the unit bucket is CPU-parallel but memory-serial on a box this size, and a second concurrent run produces timeouts that mimic real defects.

Whether to add a second `flock` for the unit bucket is a maintainer call — it trades throughput for signal
quality, and with 3-4 streams the current arrangement may already be past the point where the trade pays.

## Relationship to TST-060 — same gap, different resource

**`TST-060` (filed by the `ctrib060` stream the same night) is the sibling of this item and should be read
with it.** That one covers the *e2e* face of the gap: the heavy-e2e flock serialises the regression but **not
stack bring-up**, so a second platform can start inside another stream's e2e window — and it produced 20 of
339 spec failures, all 60 s timeouts, on a SUT that answered the same calls with 200s on direct `curl`.

This item is the **unit-bucket face of the same gap**: no flock at all, no registry signal, and two
Testcontainers-backed gradle suites starving each other's memory. The two share a root cause — *the
coordination substrate serialises named activities, not machine resources* — and a fix that addresses only one
leaves the other live.

They are filed separately rather than merged because the remedies differ: TST-060 wants the flock to cover
bring-up and `run-suite.sh` to refuse a SUT/stack mismatch; this one wants the unit runner to detect a
competing build before spending 30+ minutes producing an uninterpretable result.

**Honest note on provenance:** `TST-060` records `ctrib062-*` containers appearing inside `ctrib060`'s flock
window — i.e. *this* stream contributed to the contention it documents. That is not a dispute of their
finding; it is corroboration from the other side of the same collision.

## Third face — a shared `pkill -f` pattern kills OTHER streams' runs (confirmed cross-stream, 2026-08-31)

Disclosed unprompted by the `ctrib061` stream, and **corroborated from this side**: to stop its own build it
twice ran

```
pkill -f 'scripts/run-platform-tests'
```

That pattern is **not stream-scoped**. Every stream invokes the same script path from its own worktree, so the
pattern matches *every* concurrent run on the box. This stream's `isolate.log` is timestamped **10:37**, inside
the disclosed 10:35-10:50 window, and is the run that terminated with no failure output and was recorded as
"killed, cause unknown". One run lost; the A/B pair at 11:46 / 11:57 fell outside the window and was degraded
by CPU contention rather than killed.

This is the same root cause as the two faces above, reaching a third resource: the substrate scopes
*worktrees*, *SUT tags*, *ports* and *compose projects* per stream, but a **process-kill pattern** is global and
nothing in the registry makes another stream's processes identifiable as someone else's. The failure is
strictly worse than contention, because a killed run leaves no evidence that it was killed — it reads as an
unexplained death and invites exactly the "flaky guard" conclusion this item warns about.

**It is a substrate defect, not a lapse by that stream.** Any stream needing to stop its own build reaches for
the same pattern, and the workspace never gave it a scoped one.

## Acceptance criteria

- [ ] `run-platform-tests.sh` refuses (or warns loudly) when another
      `-Dorg.gradle.internal.worker.tmpdir=*/odd-platform-*/build/tmp/test/work` process is live, or free
      memory is below a threshold — before spending 30+ minutes on an uninterpretable result.
- [ ] The runner writes a **stream-scoped, greppable marker** into its own process line (e.g.
      `-Dodd.stream=<id>`), and `playbooks/stream-coordination.md` mandates killing by **PID** or by that
      scoped pattern — never by a bare script path that matches every stream.
- [ ] `state/active-streams.yaml` carries a machine-resource signal (`wants: unit-build`) so a starting stream
      can see what the box is already doing; "no co-active stream at intake" is recorded as having a shelf life.
- [ ] `playbooks/stream-coordination.md` states the measured truth: the unit bucket is CPU-parallel but
      **memory-serial** on a box this size, and a second concurrent run produces timeouts that mimic defects.

**Interim convention, agreed stream-to-stream 2026-08-31 (ctrib061 <-> ctrib062) pending the above:** hold
`state/locks/heavy-e2e.lock` around a bare `gradlew` / `run-platform-tests.sh` invocation, and **release it
before** invoking `run-regression.sh`, which acquires the same flock internally. Never nest the two, or the
first regression after adopting the rule deadlocks.
