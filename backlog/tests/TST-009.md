## Description

The activity-feed keyset cursor and the `ORDER BY` it pages against are at **different time granularities**, so two rows that fall in the same wall-clock second but differ at sub-second precision can be returned out of cursor order across a page boundary under sustained writes.

In `ReactiveActivityRepositoryImpl.findActivities` (`ReactiveActivityRepositoryImpl.java:284-292`):

```java
if (lastEventDateTime != null && lastEventId != null) {
    final LocalDateTime truncated = DateTimeUtil.mapUTCDateTime(lastEventDateTime)
        .truncatedTo(ChronoUnit.SECONDS);                                  // cursor → SECOND
    conditions.add(
        row(trunc(ACTIVITY.CREATED_AT, DatePart.SECOND), ACTIVITY.ID).lessThan(truncated, lastEventId));
}
final var finalQuery = baseQuery.where(conditions)
    .orderBy(ACTIVITY.CREATED_AT.desc(), ACTIVITY.ID.desc())               // ORDER BY → full (µs) precision
    .limit(size);
```

The keyset predicate compares `(trunc(CREATED_AT, SECOND), ID)` — second precision — while the `ORDER BY` sorts on the **untruncated** `CREATED_AT` (microsecond precision in Postgres `timestamp`). When the last row of a page and the first row of the next page share the same second but differ in microseconds, the `<` (truncated-second, id) cursor can re-admit or skip a row relative to the microsecond sort order. ADR-0021 (cursor pagination via `(lastEventId, lastEventDateTime)`) fixes the cursor SHAPE and that shape is contract-tested; the no-skip / no-duplicate ORDERING BEHAVIOUR under concurrent INSERT is not asserted anywhere (`feature-flows/detail/F-021.yaml:1703` — *"the cursor SHAPE is ADR-contract-tested; the no-skip / no-dup BEHAVIOUR under concurrent writes is probe-needed (PENDING-F-021-1)"*).

**Typed gate: characterization-pin (LSN-029).** This pins the CURRENT cursor-vs-ORDER-BY granularity mismatch. The behavioural reproduction is probe-gated (PENDING-F-021-1 needs a live stack under >=100 INSERT/sec). The low-cost source pin asserts the asymmetry that *causes* the skew — the cursor uses `ChronoUnit.SECONDS` / `DatePart.SECOND` while the `ORDER BY` uses the untruncated column — and goes RED the moment the two are reconciled (the planned fix: truncate the `ORDER BY` to the same second, or carry the cursor at microsecond precision so both sides match).
