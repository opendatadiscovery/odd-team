## Description

The Activity Feed configuration documentation describes `odd.activity.partition-period` as controlling "retention and partitioning" of the activity data. The code uses it **only** to set the partition **width** (how wide each time-partition of the activity table is). There is **no retention / DROP / eviction path** anywhere — old partitions are never dropped, so the activity table grows **monotonically** for the life of the deployment.

An operator who reads "retention" reasonably assumes setting `partition-period` bounds how much activity history is kept and therefore caps storage growth. It does not. On a busy platform this is a slow-burn storage exhaustion the operator has no warning about and believes they have already mitigated by setting the key. This is in the LSN-001 "default-with-consequence" class (a config key that appears to bound resource use but does not).

**Failure shape**: code-doc drift — a config key's documented purpose (retention) overstates its actual effect (partition width only).
