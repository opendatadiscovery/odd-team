## What

CTRIB-023 / #1753 added a `LOOKUP_TABLE_RENAMED` activity event so a rename is audited. But the
ReferenceData service emits NO activity event for any of the OTHER lookup-table mutations:

- `createLookupTable` (a new reference table appears with no audit trail)
- `deleteLookupTable` (a reference table - and its physical Postgres table - is dropped, unaudited)
- `addColumnsToLookupTable` / `updateLookupTableField` / `deleteLookupTableField` (schema changes)
- `addDataToLookupTable` / `updateLookupTableRow` / `deleteLookupTableRow` (row-level data edits)

So "who changed this reference data, and when" is answerable ONLY for renames. For a feature whose
rows are a documented public Postgres surface that downstream BI / ETL pipelines JOIN against, the
create/delete/schema/data mutations are at least as audit-worthy as the rename.

## Why it is NOT in CTRIB-023 (and needs its own design)

CTRIB-023 was bounded to the issue's stated fix (rename only). Auditing the full mutation surface is a
larger, cross-cutting decision, not a one-liner:

- It is the same audit-asymmetry pattern as F-057 (DQ severity audit silence) and the Query-Examples
  audit silence - a lookup-table-audit POLICY should be decided once (which mutations, what state
  shape, one event type per mutation vs a generic LOOKUP_TABLE_UPDATED), ideally alongside those
  siblings, so the platform's audit posture is coherent rather than per-bug-report.
- Each new event needs: a spec ActivityEventType value (additive), an ActivityEventTypeDto value, an
  ActivityMapper case + state DTO, an ActivityHandler, the @ActivityLog wiring, FE rendering + the
  existing i18n labels, and unit + integration tests - the established 27/28-event pattern, repeated.
- Deletes are the hard case: the activity aspect captures NEW state by re-reading the entity AFTER the
  method runs, but a deleted entity is gone - the handler/aspect contract for delete-shaped events
  needs deciding (capture-before-only, or a different shape). That is the ADR-worthy part.

## Suggested approach (for the design)

Decide the lookup-table audit policy once (an ADR), then add events per the established pattern. Reuse
`LookupTableRenamedActivityHandler` / `LookupTableNameActivityStateDto` (CTRIB-023) as the template for
the name/metadata-shaped events; design the delete-shaped contract separately.

## Acceptance criteria

- A decision (ADR or a documented policy) on which lookup-table mutations are audited and the
  event/state shape, conforming to the existing activity-event pattern.
- The chosen mutations emit activity events, verified end-to-end (the event renders in the feed) by an
  integration test that drives the REAL mutation via the API (the aspect is profile-gated off in the
  in-process JUnit profile - see IT-137).
- No regression to the existing 28 events.
