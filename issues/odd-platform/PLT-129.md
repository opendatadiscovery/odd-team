## What

`GET /api/messages/{uuid}/url` issues an HTTP 302 to the URL returned by Slack's `chat.getPermalink` **verbatim** - no host allowlist, no scheme check, no structure validation before emitting the redirect. That makes it an open-redirect surface (and a `javascript:`-scheme XSS surface if the permalink value can be influenced), inheriting the trust of "the ODD platform redirected me here."

This is **distinct from PLT-009** (which tracks only the 302-vs-301 *status-code* drift on the same endpoint, not the URL-validation gap) and from **PLT-054 Defect 1** (which mentions `javascript:` URLs as a consequence of forged *events* on the inbound webhook - a different locus). The open-redirect class on the redirect endpoint itself is untracked.

## Evidence

From the F-038 reflection (`lineage/odd-platform/feature-reflections/detail/F-038.yaml`), hypothesis H-004:

```
DataCollaborationController.java:42-48   (@ ede5d277)
  // GET /api/messages/{uuid}/url -> 302 to the chat.getPermalink value verbatim
  // no host allowlist, no scheme check, no structure validation before the redirect
```

## Impact

A crafted or compromised permalink value lands a user who clicked an ODD-internal message-link on an attacker-controlled host (open redirect), or - if a non-https / `javascript:` scheme survives - executes in the user's session (XSS), with the redirect carrying the platform's trust.

## User-facing impact

- Verified by BE trace 2026-06-10: `DataCollaborationController.redirect` (`DataCollaborationController.java:42-48`) builds the response as `ResponseEntity.status(HttpStatus.FOUND)` (302) with `headers.setLocation(URI.create(providerUrl))` - no host allowlist, no scheme check, no structural validation. `providerUrl` is the Slack `chat.getPermalink` value verbatim: `DataCollaborationServiceImpl.resolveMessageUrl` (`:72-77`) -> `SlackMessageProviderClient.resolveMessageUrl` (`:64-66`) -> `SlackAPIClientImpl.exchangeForUrl` (`:84-94`) returns `response.getPermalink()` (`:93`) with no validation. Static trace consistent; not driven (needs a connected Slack workspace) - remaining check: a live request to capture the actual `Location` header on the 302.
- Trust-boundary scope (precision): under normal operation `providerUrl` is whatever Slack's API returns for a message the platform itself stored, so the host is `*.slack.com`; exploitation requires the permalink value to be attacker-influenced (a compromised/spoofed Slack API response, or tampering with the stored provider message identity feeding `chat.getPermalink`). So this is an unvalidated-external-redirect / defense-in-depth gap (the platform forwards an external value into a redirect it stamps with its own origin), real but not a one-click open redirect from arbitrary user input. The `javascript:`-scheme XSS escalation is contingent on such a value surviving, which Slack permalinks would not normally be.
- Auth mode: the endpoint sits behind `@ConditionalOnDataCollaboration` (Slack feature enabled) and the deployment's auth chain (any of LOGIN_FORM/OAUTH2/LDAP); the redirect itself performs no per-target authorization.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: validate `providerUrl` host against a `slack.com` allowlist and reject any non-https scheme before emitting the 302 (`DataCollaborationController.java:42-48`). Distinct from PLT-009 (status-code drift) - both fixes land on the same endpoint.
