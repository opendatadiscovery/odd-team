# DOC-509 — the pillar landing page describes the Alerts view two releases out of date

## Failure shape

**Internal contradiction** + **parallel surfaces with drift**. The pillar landing page and the canonical
feature page it links to describe the same control differently, and the canonical page explicitly states that
the landing page's version is the *previous* release's behaviour.

## The passages, verbatim

`docs/active-platform-features.md:15` (the Alerting subsection blurb):

> The **Alerts** section in the navigation pane (with **All / My Objects / Dependents** tabs) lists **open**
> alerts only; resolved history is read on each entity's own Alerts tab.

`docs/active-platform-features/alerting.md:54` — the page that bullet links to:

> ## Alert views — All, My Objects, Downstream, Upstream

`docs/active-platform-features/alerting.md:82-84`:

> **The global views default to `OPEN`, and resolved alerts are reachable via the Status filter.** ... To read
> resolved history platform-wide, change **Status** to `RESOLVED` or `RESOLVED_AUTOMATICALLY` ... **(In the
> previous release the global tabs were hardwired to `OPEN` and resolved history was reachable only
> per-entity; the Status filter removes that restriction.)**

So the landing page states, as current behaviour, exactly the restriction the canonical page says was removed.

## Two separate stale claims, not one

1. **The tab set.** `All / My Objects / **Dependents**` — the old three-tab shape. The shipped view has
   **four** tabs: `All / My Objects / Downstream / Upstream`. Corroborated on every other surface:
   `alerting.md:54/:61/:86/:91/:100/:104/:204/:214`, `Features.md:84` ("four navigation views (All / My
   Objects / Downstream / Upstream)"), and `developer-guides/api-reference/alerts.md:7`.
2. **"lists open alerts only; resolved history is read on each entity's own Alerts tab."** Directly refuted by
   `alerting.md:82-84` above.

## Why it survived two fixes

This is a residue defect — the claim was corrected on every surface *named in the tracking items* and left
standing on the one that was not:

- `DOC-291` (done) corrected the open-vs-resolved claim; its `affected_files` names
  `active-platform-features/alerting.md` and `developer-guides/api-reference/alerts.md` only.
- `DOC-474` (done, milestone 0.29.0) shipped the hardened four-tab + Status-filter view.

Neither lists `docs/active-platform-features.md`. The landing page was never in scope, so it kept the
pre-0.29.0 description through both passes. Same class as the CTRIB-062 C2/C2b residue sweep, and the reason
the converge directive asks for a tree-wide claim sweep rather than a per-file fix.

## Reader harm

The landing page is the entry point into the pillar — a reader arriving from `SUMMARY.md` reads this bullet
before the feature page. An operator hunting resolved alert history reads "resolved history is read on each
entity's own Alerts tab", concludes there is no global view of resolved alerts, and stops looking — when the
Status filter on the global view does exactly what they want. The tab-name error compounds it: they go
looking for a `Dependents` tab that does not exist, on a view that actually has two tabs (`Downstream`,
`Upstream`) covering that ground.

## Recommended fix direction

Rewrite the one bullet to match `alerting.md`: four tabs (`All / My Objects / Downstream / Upstream`), the
`OPEN` default stated as a *default* rather than a restriction, and the Status filter named as the way to read
resolved history globally. Keep the bullet a pointer — the lifecycle detail belongs on `alerting.md`, which
already carries it.

**Routing.** This describes *released* behaviour (0.29.0 shipped the four-tab view) that the landing page
states incorrectly, so it is a released-truth correction → documentation `main`, not the `release/1.0.0` train.
