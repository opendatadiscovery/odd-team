## What

A request that OMITS a `required: true` query parameter returns **HTTP 500 `SYS001` "Internal Server Error"**
instead of the correct **400 BAD_REQUEST**. The client made a malformed request (their fault, fixable by
them) but the platform reports an internal server error (its fault, unfixable by them) — so the response's
`resolvable=false, retryable=false` is wrong, and the error is logged at ERROR severity as if it were a
platform fault.

Reproduced live (docker `:latest`, auth.type=DISABLED, 2026-06-07):

```
$ curl -s -o /dev/null -w "%{http_code}\n" \
    "http://localhost:18080/api/owner_association_request/activity?page=1&size=10"
500
$ curl -s "http://localhost:18080/api/owner_association_request/activity?page=1&size=10"
{"code":"SYS001","message":"Internal Server Error","retryable":false,"resolvable":false,"details":null}

# add the required status param → correct 200:
$ curl -s -o /dev/null -w "%{http_code}\n" \
    "http://localhost:18080/api/owner_association_request/activity?page=1&size=10&status=APPROVED"
200
```

Server log for the 500:

```
ERROR ... o.o.o.c.exception.ControllerAdvice : Internal server error
org.springframework.web.server.MissingRequestValueException: 400 BAD_REQUEST
    "Required query parameter 'status' is not present."
```

The framework itself classifies this as `400 BAD_REQUEST` (the exception message even says so), but the
platform's `ControllerAdvice` has **no handler** for `MissingRequestValueException` (a subclass of
`ServerWebInputException` / `ResponseStatusException`), so it falls through to the catch-all
`@ExceptionHandler(Exception.class)` → `@ResponseStatus(INTERNAL_SERVER_ERROR)` → `SYS001`.

This is a **generic error-mapping defect**, not specific to the OAR endpoints. It affects EVERY endpoint with
a `required: true` query/header param when the client omits it — `status` on `GET /api/owner_association_request`
and `GET /api/owner_association_request/activity` (`status` is `required: true` at
`odd-platform-specification/openapi.yaml:3401-3405`) are just the surfaces this was found on. Any
`ServerWebInputException` (type-mismatched param, unreadable body, etc.) is similarly mis-mapped to 500.

## Why it matters

- **Wrong error contract for API consumers.** A generated client (or a human) that omits `status` is told
  the platform broke (`SYS001`, `resolvable=false, retryable=false`) when in fact the request is malformed
  and the client can fix it (`USR001`, resolvable). Clients that branch on the error code will mis-handle
  it — e.g. surface "server error, contact support" instead of "you forgot the status filter", or trigger
  a futile retry/backoff path.
- **Log noise / false alerting.** Every such client mistake is logged at ERROR by the catch-all handler
  ("Internal server error" + a full stack trace), polluting platform logs and potentially tripping
  error-rate alerts for what is a routine 4xx.
- **Class, not instance.** Because it is a missing generic handler, it silently mis-classifies the entire
  family of `ServerWebInputException`s (missing/typed-wrong params, unreadable bodies) across every
  controller — not just the two OAR endpoints.

## Suggested fix

Add a handler in `ControllerAdvice` for `ServerWebInputException` (covers `MissingRequestValueException`,
`TypeMismatchException`-wrapped, etc.) mapping to `400` with `ErrorCode.BAD_REQUEST`, logged at WARN not
ERROR:

```java
@ExceptionHandler(ServerWebInputException.class)
@ResponseStatus(HttpStatus.BAD_REQUEST)
public ErrorResponse handleWebInput(final ServerWebInputException e) {
    log.warn("Bad request input: {}", e.getReason());
    final ErrorResponse error = new ErrorResponse();
    error.setMessage(e.getReason() != null ? e.getReason() : "Bad request");
    error.setCode(ErrorCode.BAD_REQUEST.getValue());
    error.setResolvable(ErrorCode.BAD_REQUEST.isResolvable());
    error.setRetryable(ErrorCode.BAD_REQUEST.isRetryable());
    return error;
}
```
