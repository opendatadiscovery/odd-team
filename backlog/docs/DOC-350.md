## Description

The "Status changes propagate to data sources" section of `data-discovery/statuses.md` (the section heading + its single paragraph) claims:

> *"If the status of a data entity and its parent data source are both set to `DELETED` and an operator then flips the entity status back to a visible state, the data source itself reverts to its original (non-deleted) condition. The platform mirrors entity-level status changes back up the data-source row when the two are in lockstep."*

There is **no such mirroring** in the platform. The status-change consumer, `DataEntityInternalStateServiceImpl.changeStatusForDataEntities` (and the `restore(...)` it calls), writes nothing to any DataSource row. On a restore (flip out of `DELETED`), `restore()` (DataEntityInternalStateServiceImpl.java:131-153) touches exactly:

- `lineageRepository.restoreLineageRelations(oddrns)`
- `groupEntityRelationRepository.restoreRelationsForDataEntities(oddrns)`
- `groupParentGroupRelationRepository.restoreRelationsForDataEntities(oddrns)`
- `dataEntityStatisticsService.updateStatistics(...)` (re-increments the entity-class/type counts)
- `markEntityFilled(..., MANUALLY_CREATED)` for manually-created DEGs

No `DataSource` table is read or written anywhere in this service — not in `restore()`, not in `softDeleteDataEntities()`, not in the non-DELETED branch of `changeStatusForDataEntities()`. And the status enum itself, `DataEntityStatusDto`, carries only `id` and `isSwitchable` (DataEntityStatusDto.java:11-27) — there is no DataSource coupling on the status type at all.

This misleads an operator into expecting that restoring an entity will resurrect a soft-deleted parent data source "in lockstep." It will not. An operator who soft-deletes a data source and then restores a child entity expecting the data source to come back will be left in a broken state with no platform signal.
