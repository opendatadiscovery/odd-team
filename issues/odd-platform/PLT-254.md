## Summary

`POST /ingestion/datasources` is token-gated by `IngestionDataSourceFilter`. When the bearer token is
absent, or present but unknown, the caller gets:

```
HTTP 500
{"code":"SYS001","message":"Internal Server Error","retryable":false,"resolvable":false,"details":null}
```

...and the platform logs a full Reactor stack trace at ERROR. The intended response is **401** with the
real reason -- `AbstractIngestionFilter` contains the code to produce exactly that
(`writeResponse` sets `HttpStatus.UNAUTHORIZED` and writes the exception message) -- but that code never
runs. So the platform reports an operator configuration mistake as an internal server fault, and tells
the client it is neither retryable nor resolvable, when the resolution is "configure a token".

## Reproduce (30 seconds, no collector needed)

Against any running platform (this was run against the stock `docker/demo.yaml` stack):

```
# no token at all
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:8080/ingestion/datasources \
  -H 'Content-Type: application/json' -d '{"items":[]}'
# -> 500

# a syntactically fine bearer token that does not exist
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:8080/ingestion/datasources \
  -H 'Content-Type: application/json' -H 'Authorization: Bearer deadbeef-not-a-real-token' \
  -d '{"items":[]}'
# -> 500
```

Both return the SYS001 body above. Expected: 401 for the missing token, 401/403 for the unknown one.

## User-facing impact

VERIFIED end to end, not inferred from the code.

This is the **first thing a new user hits** when following `docker/README.md`. The demo compose starts
`odd-collector` alongside the platform, and `docker/config/collector_config.yaml` ships `token: ""`
(README Step 2 is where you create a collector and paste its token in). So on a plain
`docker compose -f docker/demo.yaml up`, the collector immediately restart-loops on:

```
odd-collector-1  | ERROR | odd_collector_sdk.collector:run:140 - Platform response:
                 |   {'code': 'SYS001', 'message': 'Internal Server Error', 'retryable': False,
                 |    'resolvable': False, 'details': None}.
                 | Exception message: 500, message='Internal Server Error',
                 | url=URL('http://odd-platform:8080/ingestion/datasources')
```

while the platform log fills with `AccessDeniedException: Token is missed` stack traces. Nothing in either
message says "token". A user reasonably concludes the platform is broken and files a bug (or leaves),
when the actual fix is one line of their own config. The `resolvable: false` flag actively points them
away from the fix.

Note the asymmetry that makes this specifically a *datasources* problem: `IngestionDataEntitiesFilter` is
`@ConditionalOnProperty(value = "auth.ingestion.filter.enabled", havingValue = "true")` and that property
defaults to `false` (`application.yml:51-53`), so `/ingestion/entities` is not token-checked out of the
box -- but `IngestionDataSourceFilter` is a plain `@Component` with no condition, so
`/ingestion/datasources` is **always** token-gated. Whether that asymmetry is intended is a separate
question; this issue is only about the response it produces.

## Root cause

Two independent reasons the intended 401 never happens.

**1. The exception is thrown lazily, downstream of the filter's own error handler.**
`AbstractIngestionFilter.filter` guards the chain with

```java
.flatMap(ignored -> chain.filter(exchange.mutate().request(getRequestDecorator(exchange)).build()))
.onErrorResume(AccessDeniedException.class, e -> writeResponse(exchange, e.getMessage()));
```

but `resolveToken` is not called there -- it is called inside the decorator's `getBody()`
(`IngestionDataSourceFilter:31`), which is only subscribed later, while the controller
(`IngestionController#createDataSource`) is reading the request body. By then the failure is a
handler-time error: `ControllerAdvice` maps it first, and `onErrorResume` is left with an already-handled
exchange. `ControllerAdvice` has no `@ExceptionHandler` for `AccessDeniedException`, so the catch-all
`@ExceptionHandler(Exception.class)` with `@ResponseStatus(INTERNAL_SERVER_ERROR)` produces SYS001.

**2. The unknown-token branch throws the wrong exception class.**
`IngestionDataSourceFilter` imports `java.nio.file.AccessDeniedException` (line 3) and uses it for
`"Collector with such token doesn't exist"`, while `AbstractIngestionFilter.onErrorResume` matches
`org.springframework.security.access.AccessDeniedException`. Even if reason 1 were fixed, that branch
would still fall through to the 500 handler. This looks like an accidental auto-import.

## Suggested fix (direction, not a prescription)

Resolve the token **before** handing the request to the chain -- i.e. in `filter()`, where the existing
`onErrorResume` can see it -- rather than inside the lazily-subscribed body decorator; and make both
branches throw the same Spring Security `AccessDeniedException`. Alternatively add an explicit
`@ExceptionHandler(AccessDeniedException.class)` returning 401 to `ControllerAdvice`, which also covers
any other filter that throws it. Either way the response body should carry a code and message that name
the token, and `resolvable` should be `true`.

Worth covering with a test in the same pass: `POST /ingestion/datasources` with (a) no header,
(b) a non-bearer header, (c) a bearer token with no matching collector -- each asserting the status and
the error code, so the contract is pinned rather than incidental.

## Evidence

| what | where |
|---|---|
| the intended 401 | `AbstractIngestionFilter.writeResponse` -- `response.setStatusCode(HttpStatus.UNAUTHORIZED)` |
| the throw site | `AbstractIngestionFilter.resolveToken:48` -- `throw new AccessDeniedException("Token is missed")` |
| lazy subscription | `IngestionDataSourceFilter:28-31` -- `resolveToken` inside `getBody()` |
| wrong exception class | `IngestionDataSourceFilter:3` -- `import java.nio.file.AccessDeniedException` |
| no 401 mapping | `ControllerAdvice` -- handlers exist for BadUserRequest / NotFound / UniqueConstraint / CascadeDelete / WebExchangeBind / GenAI / ResponseStatus, then a catch-all `Exception` -> 500 |

| observed live | 500 + SYS001 for both the missing-token and unknown-token calls, run against a stock demo stack 2026-08-30 |
