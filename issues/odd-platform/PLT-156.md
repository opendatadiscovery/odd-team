## What

The Activity feed resolves the actor ("who did this") of each activity row by joining the activity's `created_by` username to the `user_owner_mapping` table and then to the `owner` it points at. That join carries an extra predicate, `user_owner_mapping.deleted_at IS NULL`. The activity row itself is keyed only by `created_by` (the raw username string) at write time; the human-readable *owner* is reconstructed at read time through this mapping join.

There are two cases, and only one of them is a real user-facing defect (the original draft overstated the first):

- **Soft-delete a user->owner mapping (NOT authorless -- falls back to the username).** When a mapping's `deleted_at` is set, the join finds no surviving mapping and the resolved owner comes back null. But the feed does **not** then show the row as authorless: the UI renders `createdBy.owner.name || createdBy.identity.username`, so it falls back to displaying the raw `created_by` username. The displayed attribution degrades from the owner's display name to the login username -- it does not vanish. This arm is cosmetic, not integrity loss.
- **Reassign a username to a different owner (the real defect -- silent misattribution).** Re-pointing the same `oidc_username` to a new owner is implemented as soft-delete-then-create (`UserOwnerMappingServiceImpl.createRelation` deletes the old mapping and inserts a new one). The actor-resolution join matches on `oidc_username` with `deleted_at IS NULL`, so it now finds the **new** mapping and resolves the **new** owner for *all* of the original person's past activity. The feed confidently displays those historical actions under the new owner's name. This is the dangerous case: the audit trail does not blank out, it names the wrong person.

## Where

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/repository/reactive/ReactiveActivityRepositoryImpl.java:220-222`

```java
.leftJoin(USER_OWNER_MAPPING)
.on(USER_OWNER_MAPPING.OIDC_USERNAME.eq(ACTIVITY.CREATED_BY)
    .and(USER_OWNER_MAPPING.DELETED_AT.isNull()))
.leftJoin(OWNER).on(OWNER.ID.eq(USER_OWNER_MAPPING.OWNER_ID));
```

The link from a historical activity to the *owner* who performed it is only as durable as the current mapping row, because the join is gated on `DELETED_AT IS NULL`. The same gated join appears on the count paths (`:155-158`, `:176-179`, `:198-200`).

The reassignment path that produces the misattribution -- re-pointing a username soft-deletes the old mapping then creates a new one, so the same `oidc_username` now resolves to a different owner:

```java
// UserOwnerMappingServiceImpl.java:15-18
public Mono<UserOwnerMappingPojo> createRelation(final String username, final String provider, final Long ownerId) {
    return userOwnerMappingRepository.deleteRelation(username, provider)   // soft-delete: sets DELETED_AT (repo :54-57)
        .then(userOwnerMappingRepository.createRelation(username, provider, ownerId));
}
```

The actor display site -- note the `|| ... .identity.username` fallback that the original draft missed:

```tsx
// odd-platform-ui/.../Activity/ActivityResults/ActivityItem/ActivityItem.tsx:77
{activity.createdBy?.owner?.name || activity.createdBy?.identity.username}
```

`createdBy` is built by `ActivityMapper.mapUser` (`ActivityMapper.java:307-310`) from the resolved owner (the join) AND the raw `created_by` string identity, so when the owner is null the username survives.

## User-facing impact

- **Reassignment misattribution -- HOLDS, verified by FE+BE trace 2026-06-10.** After a username is re-pointed to a new owner (`UserOwnerMappingServiceImpl.java:15-18` soft-delete-then-create), the actor-resolution join (`ReactiveActivityRepositoryImpl.java:219-222`) matches the new non-deleted mapping for that `oidc_username` and resolves the new owner; `ActivityItem.tsx:77` then renders the new owner's name for the original person's past activity. The Activity feed shows past actions attributed to the wrong person. This is silent (no error, no annotation). Applies to any deployment that re-points owner mappings (staff turnover, role changes).
- **Soft-delete "authorless" claim -- FALSIFIED, verified by FE trace 2026-06-10.** When a mapping is soft-deleted with no reassignment, the join resolves owner=null but `ActivityItem.tsx:77` falls back to `createdBy.identity.username`, so the feed shows the raw login username, not a blank/authorless row. `created_by` is a stable identity string, so the fallback is a reasonable (if less friendly) attribution. The original draft's "the actor disappears... read as authorless" does not occur in the shipped UI.

Auth note: reaching either case requires `OWNER_RELATION_MANAGE` on the mapping endpoints (`SecurityConstants.java:155-162`); under `auth.type=DISABLED` that gate is permitAll.

## Why it matters

The Activity feed is the platform's audit/attribution surface - where an operator goes to answer "who changed this dataset's description / tags / ownership, and when". The genuine, user-visible defect is the **reassignment** arm: re-pointing an `oidc_username` to a different owner retroactively rewrites the *displayed* actor of all that username's prior activity to the new owner -- a silent misattribution on an audit surface. The soft-delete arm is **not** integrity loss (the UI falls back to the username), so the original "orphans past activity / authorless" framing is dropped.

Severity **high** for the surviving reassignment arm: it actively misattributes historical actions to the wrong named person on an audit surface, silently. (The cosmetic owner-name->username degradation on plain soft-delete, on its own, would be low.)

## Suggested fix

Make actor attribution stable against reassignment of an `oidc_username` (the real defect). Open to alternatives:

1. **Snapshot the actor at write time** - denormalise the resolved owner (and/or a stable owner id) onto the activity row when the event is created, so reads never re-resolve through the mutable mapping. This is the robust fix for an audit surface and is the only one that fully prevents the reassignment misattribution; it is a larger change (new column + write path + backfill consideration).
2. **Resolve the actor against the mapping that was active at the event's `created_at`**, not the currently-active one - i.e. join on the mapping whose `[created_at, deleted_at)` window contains `ACTIVITY.CREATED_AT`. This keeps history pointing at the owner who actually held the username at the time, without a schema change, but is more complex SQL and depends on mapping rows being retained (they are -- soft-delete keeps them).

Note: simply dropping `DELETED_AT IS NULL` does **not** fix the reassignment case (multiple non-deleted-or-deleted mappings for one username would now all match, fanning out / picking arbitrarily) and would re-expose soft-deleted owners as active; it is not recommended. The soft-delete-only arm needs no fix -- the username fallback (`ActivityItem.tsx:77`) is acceptable behaviour.

This is **distinct from `PLT-065`** (cross-auth-mode owner-identity bleed, a different root cause in how identities are matched across auth modes) and **distinct from `PLT-031`**: this issue is specifically the reassignment-driven retroactive rewrite of the *displayed* actor via the `oidc_username` actor-resolution join.
