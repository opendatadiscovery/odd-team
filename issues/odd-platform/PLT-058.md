## What

Eight UI defects on the Term Detail page composition + the three reverse-lookup tabs (Linked Entities / Linked Columns / Linked Terms) + the per-tab error/empty-state handling. These ship as a single hardening epic because they all share state-management patterns that need unification.

> **Resolution status (2026-06-22, CTRIB-028):** Defects **1, 2, 4, 5, 6, 7** are being resolved together in
> one PR (`contrib/CTRIB-028-term-detail-hardening`, milestone 0.29.0). Defects **3** → **PLT-235** (dual-surface
> — product/UX decision) and **8** → **PLT-236** (state-pattern unification — needs `adrs/drafts/ui-state-management.md`)
> are carved out for later. Adjacent finding **PLT-237** (orphan-column linked-columns NPE 500). See
> `contributor/CTRIB-028.md`.

**Defect 1 - Term Overview double-fetches the 13-JOIN hot path (F-151a).** `TermDetails.tsx:37-45` dispatches `fetchTermDetails({termId})` on mount via Redux thunk (`terms.thunks.ts:82` -> `termApi.getTermDetails`). The Overview sub-route (the default landing per `TermDetailsRoutes.tsx:46`) fires its own `useGetTermByID({termId})` via tanstack-query (`Overview.tsx:19-21`; `lib/hooks/api/terms.ts:45-50` -> the SAME `termApi.getTermDetails`). Same endpoint, two independent caches (redux store + tanstack) - `GET /api/terms/{term_id}` executes twice per Term URL open. The backend chain is `TermController.getTermDetails` (`:93-95`) -> `TermServiceImpl.getTermDetails` (`:148`) -> `ReactiveTermRepositoryImpl.getTermDetailsDto` (`:194-238`) - re-verified 2026-06-10: 13 JOINs (1 inner + 12 left) + 7 jsonArrayAgg + 4 countDistinct in one grouped query. The permissions endpoint is double-fetched the same way (shell redux `fetchResourcePermissions`, `TermDetails.tsx:39-44`, + tanstack `useResourcePermissions` in `Overview.tsx:22-25` / `TermDetailsRoutes.tsx:21-24`).

**Defect 2 - Tabs auto-hide on zero count obscures capability discoverability (F-151b).** `TermDetailsTabs.tsx:24, 30, 36` set `hidden: !termDetails?.entitiesUsingCount` etc. A Term with zero linked entities silently has NO "Linked entities" tab; same for columns / terms. Operators new to ODD cannot tell whether linking IS supported until at least one link exists. The Query Examples tab is ALWAYS shown - correct shape; the three reverse-lookup tabs disagree.

**Defect 3 - Overview TERMS panel duplicates Linked-Terms tab with inconsistent affordances (F-151c).** Overview tab carries a TERMS mini-panel with Add/Delete affordances (`Overview.tsx:65-73` renders `TermLinkedTerms` gated by TERM_UPDATE; Add via `LinkedTermTermForm`, per-item delete via `removeTerm` - `TermLinkedTerms/TermLinkedTerms.tsx`). The Linked-Terms tab (`TermLinkedTermsList/LinkedTermsList.tsx`) shows the same relation with search but no Add/Delete. Operators learn one affordance set on Overview and cannot perform Add/Delete on the tab where they look for bulk operations.

**Defect 4 - LinkedColumnsList silently caps at 50 columns; the tab badge shows the real count (F-153a - LSN-024-class silent-empty).** `LinkedColumnsList.tsx:77` wires `<InfiniteScroll next={() => {}}>` (noop), and the hook pins `page: 1` with a plain `useQuery` - no `fetchNextPage` exists (`LinkedColumnsList.tsx:27`; `lib/hooks/api/terms.ts:36-43`, `enabled: false` + fixed page). The backend truly truncates: `ReactiveDatasetFieldRepositoryImpl.listByTerm` applies `limit(size) offset((page-1)*size)` (`:199-200`). Corrected 2026-06-10: the original claim that `hasMore={pageInfo.hasNext}` (line 78) "promises more pages while the trigger does nothing" is FALSE - the backend mapper hardcodes `hasNext=false` and `total = <returned page size>` for this endpoint (`DatasetFieldListMapperImpl.java:23, 47-49`), so `hasMore` is always false, the noop `next` is unreachable dead code, and the list renders zero pagination affordance. The user-visible contradiction is cross-endpoint instead: the "Linked columns" TAB BADGE shows the REAL total (`TermDetailsTabs.tsx:29` renders `columnsUsingCount`, fed by `countDistinct(DATASET_FIELD_TO_TERM.DATASET_FIELD_ID)` in `ReactiveTermRepositoryImpl.java:214`) - so a Term with 120 linked columns shows a tab badge "120" over a list that silently stops at 50.

**Defect 5 - LinkedTermsList shows a synthesised 500 page while LOADING and swallows REAL errors into the empty state (F-152a; FIXME on line 87 confirms author awareness).** `LinkedTermsList.tsx:85-95` renders `<AppErrorPage showError={!isLinkedListFetched}>` with a synthesised `{status: 500, statusText: 'Unknown Error'}`. Corrected 2026-06-10 - the original claim ("a 403 renders as Internal Server Error") has the condition INVERTED: tanstack's `isFetched` flips true after an error too (`dataUpdateCount > 0 || errorUpdateCount > 0`, vendored `@tanstack/query-core@5.17.19` `queryObserver.js:318`), so after a real API failure the error page DISAPPEARS and the tab renders the "No linked entities" empty state instead (`:80-84` - `isContentLoaded={isLinkedListFetched}` is true, `isContentEmpty={!total}` is true because no data arrived); the destructured `error` (`:27`) is never displayed. The synthesised 500 block actually renders during every LOADING window - initial mount and every query-key change - stacked under the skeleton (`AppErrorPage.tsx:20-37` renders purely on `showError`; no loading guard). Net effect: users see a fake 500 while the list loads, and see "no linked terms" when the request actually failed.

**Defect 6 - LinkedTermsList renders "No linked entities" empty-state on the LINKED TERMS tab (F-152b; copy-paste).** `LinkedTermsList.tsx:81` - `EmptyContentPlaceholder text="No linked entities"` on the LINKED TERMS tab.

**Defect 7 - LinkedTermsList search fires UN-debounced on every keystroke (F-152c).** Corrected 2026-06-10 - the original claim ("operators expecting type-to-search see no response") is backwards. `LinkedTermsList.tsx:40-49` updates `query` state per keystroke, and the hook's queryKey INCLUDES `query` (`lib/hooks/api/terms.ts:79`), so every keystroke re-keys the infinite query and triggers a fresh fetch - live search DOES happen, with no debounce (one request per keystroke), and each re-key flips `isFetched` false, re-flashing the Defect-5 synthesised 500 block mid-typing. The icon-click `refetch()` (`:48`) is redundant. There is still no Enter handler, unlike both siblings (LinkedEntitiesList debounces 500ms + Enter, `:62-68`; LinkedColumnsList Enter + icon-only fetch, `:33-35` - its queryKey omits `query` and is `enabled: false`, so IT truly fetches only on demand). Three siblings, three different search behaviours.

**Defect 8 - Three sibling tabs use TWO state-management patterns (F-152d - ADR-DRAFT candidate).** LinkedTermsList = tanstack-query (`useInfiniteQuery`); LinkedEntitiesList = redux thunks (`fetchTermLinkedList`); LinkedColumnsList = tanstack-query (`useGetTermLinkedColumns`). State-shape and cache-invalidation drift across three sibling components in the same parent. Mid-migration drift; operator-invisible but a maintenance defect.

## User-facing impact

- **Defect 1 (verified by FE+BE trace 2026-06-10; not driven):** every Term page open issues `GET /api/terms/{term_id}` twice (redux shell fetch + tanstack Overview fetch, separate caches) - the user sees nothing; the operator's database executes the page's most expensive grouped query twice per open. Latency/load amplification is the consequence; the doubling itself is static-settled, the magnitude is runtime.
- **Defect 2 (verified by FE trace 2026-06-10):** a user opening a Term with zero linked entities/columns/terms sees NO tab for those capabilities at all (`TermDetailsTabs.tsx:24,30,36`) - linking looks unsupported until the first link exists by some other path. Query examples tab always shows (`:38-41`).
- **Defect 4 (verified by FE+BE trace 2026-06-10):** a compliance user auditing "which columns reference PII?" on a Term with >50 linked columns sees the tab badge with the true count (e.g. "120", from `columnsUsingCount`) but a list that silently ends at 50 - no loader, no "load more", no error. The badge-vs-list disagreement is the only signal.
- **Defect 5 (verified by FE trace + vendored tanstack source 2026-06-10; flash duration is runtime):** while the Linked-terms tab loads (and on every keystroke in its search box), a "500 Unknown Error" block renders below the skeleton; when the request REALLY fails, the error block disappears and the user sees "No linked entities" - a real outage reads as an empty relation.
- **Defect 7 (static trace consistent - tanstack key-change refetch; not driven):** typing in the Linked-terms search fires one un-debounced request per keystroke; the search icon is redundant; Enter does nothing.
- **Defects 3/6/8 (verified by FE trace 2026-06-10):** affordance asymmetry between Overview panel and tab; "No linked entities" copy on the linked-TERMS tab; three sibling tabs on three different state stacks.

## Why it matters

Operator-visible impact, sorted by severity:

- **Defect 4 (LSN-024-class silent-empty pagination)**: a glossary-governance scenario (compliance team auditing "what columns reference the term 'PII'?") silently truncates after 50, with the tab badge contradicting the list - the truncation IS the failure mode, and the fix needs BOTH ends (FE pagination + the BE's hardcoded `hasNext=false` pageInfo).
- **Defect 1 (latency doubling)**: heavily-linked Terms double the platform's most expensive backend query for every page open. Operators tuning PostgreSQL miss the amplification factor.
- **Defects 5 / 6 / 7**: per-tab UX hazards that erode trust in the surface - a fake 500 during loading, real failures masquerading as empty relations, keystroke-spam search.
- **Defect 8 (state-pattern drift)**: a maintenance defect - the team is mid-migration from redux to tanstack-query; the drift is visible across siblings (and Defects 4/5/7 are all expressions of it).

Severity is CRITICAL (Defect 4 is the LSN-024 silent-empty class on a documented public surface, verified end-to-end 2026-06-10); the cluster collectively represents the Term Detail page's overall hardening state.

## Suggested fix

Recommend three PRs:

### PR-1 - Pagination + double-fetch (Defects 1 + 4)

**Defect 1 - share the shell-level cache:**

```tsx
// Option A: Overview reads from redux-cached termDetails (already loaded by shell)
// Option B: shell + Overview share the same tanstack-query queryKey
// Option C: document the double-fetch as intentional with the latency contract (cheap, but bad)
```

Recommend Option B - migrate the shell-level fetch to tanstack-query with `['term', termId]` key; Overview reads from same key.

**Defect 4 - migrate LinkedColumnsList to `useInfiniteQuery` + wire `fetchNextPage`, AND fix the BE pageInfo:**

```tsx
// LinkedColumnsList.tsx
- const { data, ... } = useGetTermLinkedColumns({termId, page:1, size, query});
+ const { data, fetchNextPage, hasNextPage, ... } = useInfiniteGetTermLinkedColumns({termId, size, query});
- <InfiniteScroll next={() => {}} hasMore={pageInfo.hasNext} ... />
+ <InfiniteScroll next={fetchNextPage} hasMore={hasNextPage} ... />
```

Mirror `useGetTermLinkedTerms` (`lib/hooks/api/terms.ts:75-93`) including its full-page heuristic (`hasNext = items.length === size`), because the FE cannot trust this endpoint's `pageInfo`: `DatasetFieldListMapperImpl.java:47-49` hardcodes `hasNext=false` and reports `total` as the returned page size. The clean fix is BE-side - return the real windowed total + hasNext (the `jooqQueryHelper.pageifyResult` pattern used elsewhere) - then `hasMore={pageInfo.hasNext}` becomes trustworthy.

### PR-2 - Per-tab UX hygiene (Defects 5 + 6 + 7)

**Defect 5 - gate the error page on the ERROR, not on `!isFetched`:**

```tsx
// LinkedTermsList.tsx:85-95 - match the LinkedEntitiesList.tsx:148-152 pattern
- <AppErrorPage showError={!isLinkedListFetched} error={{ status: 500, ... }} ... />
+ <AppErrorPage showError={!!error} error={mapToErrorState(error)} ... />
```

This fixes BOTH halves of the inversion: no fake 500 during loading, and real failures stop rendering as the empty state (the empty placeholder must also require `!error`).

**Defect 6 - one-line fix:**

```tsx
// LinkedTermsList.tsx:81
- <EmptyContentPlaceholder text='No linked entities' />
+ <EmptyContentPlaceholder text={t('No linked terms')} />
```

**Defect 7 - debounce the keystroke-triggered refetch + add Enter:**

```tsx
// LinkedTermsList.tsx - the queryKey already re-fetches on query change (terms.ts:79);
// debounce the STATE update so the key changes at most ~2x/sec, and add Enter for parity:
+ const debouncedSetQuery = useDebouncedCallback(setQuery, 500);
+ <Input onKeyDown={(e) => e.key === 'Enter' && refetch()} onChange={(e) => debouncedSetQuery(e.target.value)} ... />
```

(Align with `LinkedEntitiesList.tsx:62-68`, which already debounces 500ms + handles Enter.)

### PR-3 - Auto-hide vs empty-state + state-pattern unification (Defects 2 + 3 + 8)

**Defect 2 - empty-state instead of hidden:**

```tsx
// TermDetailsTabs.tsx - show tabs always; render empty-state inside
- { label: 'Linked entities', hidden: !termDetails?.entitiesUsingCount, ... }
+ { label: 'Linked entities', count: termDetails?.entitiesUsingCount ?? 0, ... }
// each LinkedXxxList component renders empty-state hint with the "how to link" pointer
```

**Defect 3 - Overview TERMS panel consolidation:**

Either:
- (a) Overview panel becomes a summary + "see all" link to the tab; tab carries all affordances (Add/Delete/Search).
- (b) Document the dual-surface intent (rename Overview panel to "Recent linked terms"; clarify in UX that Linked-Terms tab is the canonical surface for browse, Overview panel for quick-add).

**Defect 8 - state-pattern unification ADR:**

The team is mid-migration from redux thunks to tanstack-query. Complete the migration: LinkedEntitiesList -> tanstack-query (mirroring LinkedTermsList + LinkedColumnsList). Document the chosen pattern in an ADR (`adrs/ui-state-management.md`) to prevent further drift.
