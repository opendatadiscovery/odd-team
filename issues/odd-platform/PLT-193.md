## What

ODD's GitHub OAuth handler calls the GitHub REST API to (a) confirm the user belongs to the configured organization and (b) detect whether the user is in an admin team. Both calls (`GET /user/orgs`, `GET /user/teams`) require the token to carry the `read:org` scope. Nothing in the handler validates that scope - at startup or at login - and the two failure modes diverge confusingly:

- **Organization name configured** (`auth.oauth2.client.<id>.organization-name` set): if the token lacks `read:org`, GitHub returns 403 for `/user/orgs`. The handler has no `onErrorResume`, so the error propagates out of `enrichUserWithProviderInformation` and the **entire login fails** - for every user, with an opaque OAuth error, even though their credentials are valid.
- **Organization name NOT set:** the handler takes an early return that skips the org/team calls entirely. Admin-group detection (`admin-groups`) is then a **silent no-op** - no user is ever promoted to admin, with no warning that the configured `admin-groups` are being ignored.

There is no boot-time check that the configured combination (organization-name and/or admin-groups present) is compatible with the token scope the OAuth app actually grants.

## Why it matters

The two outcomes are both bad and neither is diagnosable from the symptom:

- **Loud-but-opaque** (org-name set, token missing `read:org`): a misconfigured GitHub OAuth app takes down login for everyone with a generic `invalid_token` / OAuth error that gives the operator no hint that the *token scope* - not the user, not the secret - is the cause.
- **Silent** (org-name unset, admin-groups set): operators configure `admin-groups` expecting team-based admin promotion; it never happens and nothing tells them the setting is dead because no organization name was configured to anchor the team lookup.

Either way the operator burns hours on a configuration that the platform could have rejected at boot. Severity is medium: it does not corrupt data and is a configuration-edge issue, but it directly defeats a security-relevant feature (admin promotion / org gating) with no signal.

## Suggested fix

1. **Fail loud, early.** Add an `onErrorResume` (or explicit status handling) on the `/user/orgs` and `/user/teams` calls that maps a 403/insufficient-scope response to a clear `OAuth2AuthenticationException` whose message names the missing `read:org` scope, instead of letting a raw error propagate.
2. **Boot validation.** At startup, if `organization-name` or `admin-groups` is configured for a GitHub client, validate (or at minimum log a prominent warning documenting) that the OAuth app must grant `read:org`, and warn when `admin-groups` is set but `organization-name` is empty (the silent no-op case), since team detection cannot run without an org anchor.

Open to alternatives on where boot validation lives; the goal is that neither failure mode reaches a user as an unexplained login break or a silently-ignored setting.

## How discovered

Surfaced by the 2026-06-08 feature-reflection contradiction harvest (harvest report under `integration-tests/run-log/`, 2026-06-08) across feature reflections F-084 (GitHub OAuth provider handler) and F-124 (admin/role-promotion config surfaces): the reflections disagreed on whether `admin-groups` always takes effect, and reading `GithubUserHandler.java` showed both the org-name-unset silent no-op and the missing `onErrorResume` on the scope-dependent calls.

This is net-new work under the **PLT-082 / PLT-069 boot-validation theme** (validating provider/auth configuration at startup rather than failing at first use). It is distinct from those items' specific subjects - this adds GitHub `read:org` scope validation plus the `onErrorResume` on the org/team calls.

Cross-feature cluster note: same defect viewed from two reflection angles (this finding and F-124 H-003); both loci are in `GithubUserHandler.java`.
