# DataEntityController#getDataEntityGroupsLineage — semantic understanding

## understanding

`getDataEntityGroupsLineage` is the reactive `GET /api/dataentitygroups/{data_entity_group_id}/lineage` handler — a six-line pass-through (`DataEntityController.java:275-281`) that calls `lineageService.getDataEntityGroupLineage(dataEntityGroupId)` and lifts the `Mono<DataEntityGroupLineageList>` to `200 OK`. The endpoint is the **DEG-anchored sibling** of the per-entity lineage endpoints (`getDataEntityDownstreamLineage` / `getDataEntityUpstreamLineage`): instead of rooting at a single data entity, it roots at a `Data Entity Group` (DEG) and returns the lineage relationships **among the entities that belong to the given group** (per the OpenAPI summary `openapi.yaml:2420-2421`: "Gets DataEntityGroup lineage graph, which shows lineage for DEG children"). The service implementation (`LineageServiceImpl.java:59-85`) resolves the DEG-member oddrn set via `groupEntityRelationRepository.getDEGEntitiesOddrns(dataEntityGroupId)` (a recursive CTE that **does** walk nested DEGs at the SQL layer per `ReactiveGroupEntityRelationRepositoryImpl.java:177-204`), then filters out edges where either endpoint is itself a DEG (`LineageServiceImpl.java:71-75` with the comment `// Remove this when we will support inner DEGs for DEG lineage` — the explicit deferred-feature anchor), assembles per-DEG-member connected-component streams via in-memory BFS (`establishDEGRelations` lines 200-216 + `getRelationsForEntities` lines 218-233), and returns a `List<DataEntityLineageStreamDto>` wrapped in `DataEntityGroupLineageList`. The endpoint is **DEG-anchored** but inherits the same cross-owner enumeration posture as the per-entity lineage endpoints — no SecurityRule entry exists (`SecurityConstants.java:98-...` no DEG-lineage path); it falls through to `pathMatchers("/**").authenticated()` (`AuthorizationCustomizer.java:29-30`) and the service performs no `fetchAssociatedOwner()` call.

## bugs_limitations_corner_cases

- "Anchor-set defence-in-depth is NOT applied — `getDataEntityGroupLineage` accepts the DEG ID from the controller path and resolves the member set via `groupEntityRelationRepository.getDEGEntitiesOddrns(dataEntityGroupId)` (LineageServiceImpl.java:61) WITHOUT calling `authIdentityProvider.fetchAssociatedOwner()` or any owner check.
