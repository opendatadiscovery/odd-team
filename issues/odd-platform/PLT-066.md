## What

`OwnerServiceImpl.getRoleIdsList` (`:116-122`) collapses both a NULL and an empty `roles` list to `List.of()` (it tests `CollectionUtils.isEmpty(formData.getRoles())`). The `update` transaction (`:70-85`) then runs, in order, `deleteOwnerRelationsExcept(owner.getId(), newRoles)` (`:77`) `.then(createRelations(owner.getId(), newRoles))` (`:80`) with `newRoles = List.of()`. The delete is `DSL.delete(OWNER_TO_ROLE).where(OWNER_TO_ROLE.OWNER_ID.eq(ownerId).and(OWNER_TO_ROLE.ROLE_ID.notIn(roleIds)))` (`ReactiveOwnerToRoleRepositoryImpl.java:52-56`); jOOQ renders `field.notIn(<empty collection>)` as an always-true predicate, so the WHERE reduces to `OWNER_ID = ?` and DELETES every role-link for that owner. The follow-on `createRelations` short-circuits on the empty collection (`ReactiveOwnerToRoleRepositoryImpl.java:26-28` returns `Mono.empty()`), so nothing is re-inserted. Net effect: all of the owner's role bindings are gone.

An API consumer (script, integration, CI tool) issuing `PUT /api/owners/{id}` with body `{"name": "new_name"}` to rename ONLY - expecting unspecified fields to mean "leave unchanged" - instead REMOVES ALL role assignments. The UI sends the current `roles` list (read-modify-write), so the hazard is MASKED in normal UI flows; any direct API consumer is exposed.

## User-facing impact

CODE-SETTLED, and auth-mode-INDEPENDENT (this is a data-mutation hazard, not an RBAC observable).

- **Destruction (verified-trace, static):** for `roles` null-or-empty, the role bindings are deterministically deleted - traced through `OwnerServiceImpl.java:116-122,77,80` -> `ReactiveOwnerToRoleRepositoryImpl.java:52-56` (`notIn(empty)` tautology) -> `:26-28` (empty insert is a no-op). The behaviour does not depend on auth mode: the `OWNER_UPDATE` SecurityRule (`SecurityConstants.java:144-145`) gates *who may call* `PUT /api/owners/{id}`, but once the call is authorized the destruction is unconditional, including under the default `auth.type=DISABLED` (`application.yml:34`) where the caller is the synthetic admin.
- **Who sees it:** a direct API consumer that PUTs without re-sending the `roles` array; the bindings vanish silently (HTTP 200, no warning). The independent draft PLT-084 (rejected as a duplicate of this item) reached the same `notIn(emptyCollection)` tautology conclusion, corroborating the read.
- Not exercised against a running instance in this sweep, but the outcome follows deterministically from the SQL; no policy-configured stack is needed to establish it. (A confirming run: `PUT /api/owners/{id}` with `{"name":"x"}` on an owner that has roles, then GET the owner and observe `roles: []`.)

## Why it matters

Destructive AND silent AND invisible in the UI's own flows. An operator running a CI pipeline that periodically refreshes Owner display names without re-sending the (untouched) role array strips ALL those Owners of their Role bindings - typically discovered only after a permission-related incident.

## Suggested fix

Three options, in order of decreasing breaking-change risk:

**Option A (recommended) - PATCH semantic with `null`-sentinel.** Treat `null` `roles` as "no change"; treat empty array `[]` as "remove all". Doc-side adjustment to OwnerFormData makes the semantic explicit.

```java
// OwnerServiceImpl.java - note the current signature takes OwnerFormData, not List<RoleFormData>
private List<Long> getRoleIdsList(final OwnerFormData formData) {
    return formData.getRoles() == null
        ? null  // sentinel: leave existing bindings unchanged
        : formData.getRoles().stream().map(Role::getId).toList();
}

// In update transaction:
if (roleIds == null) {
    return updateOwnerCoreFields(owner);  // skip role-link delta
} else {
    return updateOwnerCoreFields(owner)
        .then(deleteOwnerRelationsExcept(owner.id(), roleIds))
        .then(createRelations(owner.id(), roleIds));
}
```

**Option B - Make `roles` REQUIRED in the spec.** Breaking change for existing API consumers (clients omitting `roles` get 400 instead of silent destruction). Requires deprecation period + client migration. Doc-side spec change in `opendatadiscovery-specification` (cross-link to SPC-002 scope).

**Option C - Keep PUT semantic, validate at controller layer.** Reject the request with HTTP 400 if `roles` is absent (return clear error: "OwnerFormData.roles is required; to remove all role bindings, send an empty array explicitly"). Less Spring-idiomatic than Option A but simpler to implement.

Recommended Option A - least-surprise for existing API consumers + least-breaking-change.
