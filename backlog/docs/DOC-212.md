## Description

Live `/catalog-overview` lines 58-62 frame the home-page OwnerAssociation surface as a simple invite-to-request: "When authentication is enabled and the signed-in user is not yet linked to an Owner, this section invites them to request the link. The request surfaces in Management → Associations for an operator with the `OWNER_ASSOCIATION_MANAGE` permission to approve. On auth-disabled deployments the section is hidden."

Code reality (sidecar reference `OwnerAssociation.tsx:19-92`): the home-page OwnerAssociation surface is a 4-branch state machine, NOT a single form:
- (1) `identity && !ownership && !requestStatus` → form (the invite)
- (2) `identity && !ownership && status=PENDING` → waiting screen
- (3) `identity && !ownership && status=DECLINED` → dismissable banner + form
- (4) `identity && ownership` → 4-column Recommended panel (My / Upstream / Downstream / Popular)

The page's framing as "invite them to request" misses three of four branches.

Operator-visible consequence: a user who got `DECLINED` from a previous admin sees an unfamiliar dismissable banner with no contextual help; the doc does not explain what they're seeing. A user in `PENDING` sees a "Request being checked" screen with no escape; the doc does not explain it's a one-shot wait. The reader's mental model is "either I see the form or I see Recommended," whereas reality is four states.
