- **ADR-CANDIDATE-053** (NEW 2026-05-12E): Policy document JSON Schema validation is enforced **at WRITE time, not at READ time** — `PolicyJSONValidator` loads `schema/policy_schema.json` once at construction (V2019-09 `JsonSchemaFactory`) and validates the inbound `policy` text per `create` / `update` invocation, raising `IllegalArgumentException` on schema violations BEFORE any DB write. The persisted `policy` text column is schema-valid by construction; read paths can trust the shape without re-validation
  - **Category**: promote
  - **Support**: surfaced by 2 sidecars (`createPolicy` batch E + `PolicyServiceImpl` batch I primary source) — the structural shape applies to every persistence path through `PolicyServiceImpl` (the validator runs unconditionally on both `create` at line 64 and `update` at line 73)

  - **Decision statement**: ODD treats the policy JSON document as a structured DTO subject to JSON Schema validation at every persistence boundary. The validator is a Spring `@Component` (`PolicyJSONValidator`) that loads `schema/policy_schema.json` once at construction using `JsonSchemaFactory.getInstance(SpecVersion.VersionFlag.V201909)`. Both `PolicyServiceImpl.create` (line 64) and `PolicyServiceImpl.update` (line 73) call `policyJSONValidator.validate(...)` BEFORE invoking the repository. On non-empty validation errors, the validator throws `IllegalArgumentException("Policy is not valid: " + errors)` — the request is rejected before any DB write. The decision codifies: (a) the `policy` text column is schema-valid by construction across all rows ever persisted; (b) read paths (`getPolicy`, `getPolicyList`, the `getCurrentUserPolicies` join in `PolicyServiceImpl.java:103-107`) can trust the shape WITHOUT re-validation; (c) operators authoring policies via the UI's `Management → Access Management → Policies` editor receive immediate schema-validation feedback; (d) **NEW 2026-05-19I**: the validator is invoked SYNCHRONOUSLY on the WebFlux event-loop thread BEFORE any `Mono.just(formData)` composition. This is a deliberate fail-fast choice; the alternative (`Mono.fromCallable(() -> { validator.validate(...); return formData; }).subscribeOn(boundedElastic)`) is structurally available and not used. The synchronous placement is appropriate for sub-millisecond schema validations on typical-size policies but becomes a cost for pathological-size bodies (per REFACTOR-271). Trade-off accepted: any future schema change (e.g. adding a new `permission` constant to the schema's `MANAGEMENT` enum) requires either backwards-compatibility in the schema OR a migration step to re-validate existing rows. Composing with ADR-CANDIDATE-002 (centralised SECURITY_RULES — the validator's error path) and ADR-CANDIDATE-048 (narrow-validator scope at the @ConfigurationProperties layer — the same maintainer's discipline of "validate the shape that determines the behaviour"). The validator's choice of `IllegalArgumentException` over the project's `BadUserRequestException` (used in `PolicyServiceImpl` on lines 13, 77, 88) is the gap captured at REFACTOR-208 / REFACTOR-268 — the framing is "the request was syntactically invalid" but the response code may surface as 500 rather than 400.
  - **Wisdom test**: PASS. The validator is a positive design choice (named explicitly, `@Component`-managed, invoked at both write paths, with a schema bundled in the build). The choice of write-time over read-time is structural (the validator's responsibility is the "policies persisted are always schema-valid" invariant). The schema bundled at `schema/policy_schema.json` (V2019-09) is the contract. The batch-I sidecar confirms at primary source + adds the synchronous-vs-async sub-decision.
