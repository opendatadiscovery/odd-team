## Description

Live `/features/management` rows for Owners / Namespaces / Datasources are silent on the cascade-block behaviour that prevents deletes when dependent rows reference the parent. Code reality (sidecar refs `OwnerServiceImpl.java:88-100` + `NamespaceServiceImpl.java:73-90` + `DataSourceServiceImpl.java:85-96`): each of these delete paths runs a `Mono.zip` of existence-predicates on referent tables BEFORE issuing the soft-delete UPDATE. If ANY predicate returns true, the chain emits `CascadeDeleteException` (USR004). The UI's ConfirmationDialog says only "Are you sure?" + "X will be deleted permanently" — silent on the conditional outcome. The `/Roles` page is the only Management cascade-block surface that is explicitly documented today (DOC-GAP-275 — Roles cascade; DOC-GAP-073 — Policies cascade-on-Role-attach).

Operator-visible consequence: operator clicks Delete on a Namespace with 100 entities under it, gets a ControllerAdvice toast on rejection. The UI implies the delete is unconditionally destructive; reality is "either delete OR fail with CascadeDeleteException." Same shape for Owner-with-ownership, Namespace-with-DEG, DataSource-with-entities.
