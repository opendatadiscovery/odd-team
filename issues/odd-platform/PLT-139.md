## What

On a fresh boot, `NotificationSubscriber` creates the logical-replication **slot before the publication** (ADR-0044 lazy create-order: `registerReplicationSlot` then `registerPublication`). PostgreSQL's `pgoutput` logical decoding requires the publication to exist **as of the LSN being decoded**. If any WAL change lands at an LSN between slot-creation and publication-creation, the replication stream fails in the change callback with:

```
ERROR: publication "odd_platform_publication_alert" does not exist
  Where: slot "odd_platform_replication_slot", output plugin "pgoutput", in the change callback, associated LSN 0/19xxxxx
  at org.opendatadiscovery.oddplatform.notification.NotificationSubscriber.run(NotificationSubscriber.java:68)
```

The slot cannot advance past that LSN, so the subscriber **retries the same failing change forever** (`active=false` on the slot; no notifications delivered). Because there is **no DROP/recreate path** anywhere in `notification/` (ADR-0044 "lazy-create, no-drop"), a **container restart does NOT recover it** — the slot persists at the bad `restart_lsn` and re-wedges. Notifications are silently dead until an operator manually drops the slot.

This is **flaky / timing-dependent**: it triggers only when a WAL write occurs in the (sub-millisecond) window between slot- and publication-creation. On boots with no such write the chain works (an alert delivers to a webhook in ~4s). Observed both outcomes across fresh boots this session.

## Where

```
odd-platform-api/.../notification/NotificationSubscriber.java
  run() :47        leaderElectionManager.acquire(advisoryLockId=100, blocking)
       :104-126    registerReplicationSlot  — creates the slot FIRST (pg_create_logical_replication_slot, pgoutput)
       :128-158    registerPublication      — creates "CREATE PUBLICATION ... FOR TABLE alert" SECOND
       :68         the replication-stream read loop where the decode fails ("publication does not exist")
odd-platform-api/src/main/resources/application.yml:177-179
  notifications.wal.replication-slot-name = odd_platform_replication_slot
  notifications.wal.publication-name      = odd_platform_publication_alert
```

The create-order (slot @ :104-126 before publication @ :128-158) is the root cause; the no-DROP design (ADR-0044) is why it is unrecoverable.

## Why it matters

Silent, permanent notification death on a fraction of fresh boots / redeploys — exactly the LSN-class failure ODD's quality bar exists to catch (operator follows the docs, enables notifications, and after some deploy they silently stop, with no error surfaced to the UI and no recovery short of `SELECT pg_drop_replication_slot('odd_platform_replication_slot')` by hand). Severity HIGH: it is reachable in any notifications-enabled deployment, intermittently, and self-perpetuating across restarts.

## Suggested fix

Any of (in order of preference):

1. **Create the publication BEFORE the replication slot.** If the publication exists when the slot is created, the slot's snapshot includes it and no change can be decoded against a catalog where it is absent. (Reorder `registerPublication` before `registerReplicationSlot` in `run()`.)
2. **Controlled recovery on the wedge:** catch the `publication does not exist` (SQLState 42704) on the stream and drop + recreate the slot once (a bounded, logged recovery — relaxing the strict no-drop for this provably-recoverable case). Pairs with the silent-thread-death detection (TEST-GAP-796).
3. Create both atomically / ensure no published-table writes between the two creations.

## How discovered

Building the I3 notifications-WAL integration test (`integration-tests/`, IT-011) on 2026-06-02. The happy-path (insert an alert → WAL subscriber → webhook stub) delivered reliably in some fresh boots (~4s) but on others the subscriber wedged with the error above; a platform restart did not recover it (`pg_replication_slots.active` stayed false). The deterministic ADR-0040/0044 lifecycle pin shipped instead (IT-011); this wedge is filed as the finding. Run-log: `integration-tests/run-log/2026-06-02-feature-complete.md`.
