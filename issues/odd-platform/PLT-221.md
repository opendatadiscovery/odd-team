## What

The i18n catalogs use the natural-keys pattern (key == English text) everywhere EXCEPT one
symbolic key: `main search placeholder`. Its English VALUE is the long hint text:

    en.json:387  "main search placeholder": "Search data tables, feature group, jobs and ML models via keywords"

Every non-English catalog translated the KEY literally instead of the value -- the
translators never saw the English value, only the key:

| locale | line | current value | back-translation |
|--------|------|---------------|------------------|
| es.json | 382 | "espacio para busqueda principal" (sic) | "main search space" |
| fr.json | 383 | "espace de recherche principal" | "main search space" |
| ch.json | 383 | "主搜索占位符" | "main search placeholder" (the i18n jargon word) |
| ua.json | 382 | "основний покажчик пошуку" | "main search pointer" |
| hy.json | 382 | "հիմնական որոնման փոխարինող" | "main search substitute" |
| br.json (PR #1564) | 385 | "local de busca principal" | "main search location" |

(Native-language strings quoted verbatim -- the ASCII rule's native-content exception.)

Second group -- pt-BR value defects found while reading PR #1564's br.json end-to-end
(line numbers = the file as merged):

- line 424: "Total entities" -> "Toal de entidades" -- typo, should be "Total de entidades"
- line 40: "...excluir esta rótulo?" -- gender disagreement, "rótulo" is masculine ->
  "este rótulo" (same sentence pattern as the other delete confirmations)
- line 166 vs 165/310: "History" -> "História" but "Hide history"/"Show history" ->
  "histórico". "Histórico" is the correct UI term; "História" reads as "the story".
- terminology collision (polish, needs a native-speaker decision): Label and Tag both
  render as "Etiqueta" on some screens (e.g. "Label": "Etiqueta", "Tag": "Etiqueta",
  "Label Name" and "Tag Name" both -> "Nome da Etiqueta") while other Label keys use
  "Rótulo" ("Create Label": "Criar Rótulo"). ODD treats labels (dataset-field level) and
  tags (entity level) as distinct concepts; suggest Label -> "Rótulo", Tag -> "Etiqueta"
  consistently.

## Where

- `odd-platform-ui/src/components/shared/elements/MainSearchInput/MainSearchInput.tsx:63`
  -- `const mainSearchPlaceholder = t('main search placeholder');` rendered as the
  placeholder of the main catalog search input.
- `odd-platform-ui/src/locales/translations/{es,fr,ch,ua,hy,br}.json` at the lines above.

## User-facing impact

User: any non-English operator, on the FIRST surface they meet -- the main catalog search
box on the home page. Instead of the hint explaining WHAT can be searched ("Search data
tables, feature group, jobs and ML models via keywords"), they see a meaningless literal
("main search space" / "main search pointer" / the word "placeholder" itself in Chinese).
The hint is the only in-product explanation of the search scope; non-English users simply
never get it. Render path is single-hop (catalog value -> placeholder prop, file:line
above); the catalog-lookup mechanism itself was live-verified under the ua locale during
the #1748 reproduction.

The pt-BR typos ship with PR #1564: "Toal de entidades" appears in the entity-count
caption; the gender slip in a delete-confirmation dialog.

## Why it matters

Same trust mechanics as #1751 but inverted: #1751 is keys that fall back to English;
this is keys that render WRONG text in the user's own language -- worse, because it looks
intentional. It also shows the contribution workflow's blind spot: translators work from
the key list alone, so any symbolic key (key != value) gets a literal key translation.
All six translators independently made the identical mistake.

## Suggested fix

1. One small PR editing six catalog values for `main search placeholder` to translate the
   en VALUE. pt-BR suggestion: "Busque tabelas de dados, grupos de features, jobs e
   modelos de ML por palavras-chave". Other locales need a native-speaker pass (or at
   minimum a machine translation OF THE VALUE, which is still strictly better than the
   current literal key translations).
2. Fix the three pt-BR value defects (lines 424, 40, 166) in the same PR; decide the
   Label/Tag terminology split with a Brazilian Portuguese speaker (fredguth, the PR
   #1564 author, is the natural reviewer to ping).
3. Prevention: when the CI key-parity guard from #1751 lands, add a lint warning for any
   catalog entry whose value case-insensitively equals its key in a non-en catalog when
   the en value differs from the key -- that is exactly the literal-key-translation
   signature (would have flagged all six locales here).
