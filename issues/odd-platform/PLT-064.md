## What

`LoginFormSecurityConfiguration.java` has one genuine LOGIN_FORM-specific security-posture defect (Defect 1) plus two weaker concerns that the 2026-06-10 re-verification downgraded after reading the OAUTH2 / LDAP siblings and the redirect's actual source. The shipped docs (DOC-234 caveat companion) acknowledge LOGIN_FORM as dev/demo.

**Defect 1 - `SECURITY_RULES` is INERT under LOGIN_FORM (CODE-SETTLED).** The LOGIN_FORM chain (lines 53-59) builds its own `.authorizeExchange(spec -> spec.pathMatchers(permittedPaths).permitAll().pathMatchers("/**").authenticated())` (lines 55-57) and never registers the per-path permission rules. The OAUTH2 (`OAuthSecurityConfiguration.java:98`) and LDAP (`LDAPSecurityConfiguration.java:145`) chains instead pass `new AuthorizationCustomizer(permissionService, extractors)` as the `.authorizeExchange(...)` customizer; `AuthorizationCustomizer.customize` (`AuthorizationCustomizer.java:20-31`) iterates `SecurityConstants.SECURITY_RULES` (the ~80 per-path `permission`-gated rules at `SecurityConstants.java:98-355`) and binds each to `.access(manager(...))`. LOGIN_FORM never invokes that loop, so SECURITY_RULES gate nothing under LOGIN_FORM. Compounded by every LOGIN_FORM user being ADMIN-authority (line 81: `.authorities(grantedAuthorityExtractor.getAuthorities(true))`, and `GrantedAuthorityExtractor.getAuthorities(true)` returns the `ADMIN` authority), an operator who authors Policies via the Management UI in LOGIN_FORM mode gets a fully-built RBAC configuration that the live auth chain silently ignores. The *wiring* is a static, code-settled fact (verifiable without running any auth mode); the *observable* "operator's Policies have no effect / everyone is admin" needs a LOGIN_FORM stack with Policies configured (see User-facing impact).

**Defect 2 (downgraded) - CSRF disabled, but NOT a LOGIN_FORM divergence.** Line 54: `.csrf(ServerHttpSecurity.CsrfSpec::disable)`. The original draft framed this as a LOGIN_FORM-specific gap versus OAUTH2/LDAP; that is FALSE - re-verified 2026-06-10: OAUTH2 (`OAuthSecurityConfiguration.java:96`) and LDAP (`LDAPSecurityConfiguration.java:143`) ALSO call `.csrf(ServerHttpSecurity.CsrfSpec::disable)` unconditionally. CSRF-disabled is a platform-wide posture (the SPA is a same-origin bearer/session client), not a divergence the operator can be surprised by per-mode. Retained only as a platform-wide hardening note, not a LOGIN_FORM cluster member.

**Defect 3 (re-characterized) - `auth.login-form-redirect` is an unvalidated DEPLOY-TIME config value, not a per-request open-redirect.** Line 41 reads `@Value("${auth.login-form-redirect:}")` (empty default); line 43 calls `parseURI(redirectURIString)`; `parseURI` (lines 88-90) does `URI.create(redirectUri)` with no scheme/host allowlist. But this value is the post-login success-redirect target wired once at bean-construction (line 45-47), derived from operator configuration - it is NOT request-derived and an external attacker cannot influence it per-request. The risk is "a mis-templated `auth.login-form-redirect` in a Helm values pipeline sends authenticated users to the wrong host", i.e. a config-hardening / fail-fast concern, not the classic open-redirect (unlike PLT-075's logout handlers, which DO derive the target from the inbound request URI). Downgraded accordingly.

## User-facing impact

RUNTIME-ONLY for the observable; CODE-SETTLED for the Defect 1 wiring.

- **Defect 1 wiring (verified-trace, static):** LOGIN_FORM's filter chain never registers `SECURITY_RULES`, verified by reading `LoginFormSecurityConfiguration.java:53-59` against `AuthorizationCustomizer.java:20-31` + `SecurityConstants.java:98-355`. No auth mode needs to run to establish that the per-path permission rules are absent from the LOGIN_FORM chain and that LOGIN_FORM users carry `ADMIN` authority (`:81` + `GrantedAuthorityExtractor.java:12-17`).
- **Defect 1 observable (static-not-driven; manifests under `auth.type=LOGIN_FORM`):** "operator-authored Policies have no gating effect; every login-form user can perform every action" requires a running LOGIN_FORM stack with non-empty Policy/Role tables and a non-admin-intended user. Under the default `auth.type=DISABLED` (`application.yml:34`) the whole chain is permitAll + synthetic admin, so nothing manifests there either. Not driven in this workspace; remaining check = boot LOGIN_FORM, create a Policy denying an action, confirm the action still succeeds for a form user.
- **Defect 2 (verified-trace, refuted as divergence):** CSRF-disabled is identical across LOGIN_FORM (`:54`), OAUTH2 (`OAuthSecurityConfiguration.java:96`) and LDAP (`LDAPSecurityConfiguration.java:143`); there is no per-mode surprise. Any CSRF hardening is platform-wide.
- **Defect 3 (verified-trace, re-characterized):** the redirect target is bean-construction config (`:41,43,45-47,88-90`), not request-derived; no external per-request control. Concern is operator-misconfiguration, not an attacker open-redirect.

## Why it matters

Defect 1 is the load-bearing finding: an operator who turns on LOGIN_FORM and then invests in the RBAC Policy/Role UI gets a security model that is silently a no-op (everyone is admin, no path is permission-gated). That is exactly the LSN-001/LSN-002 family - the platform accepts and stores configuration it never enforces, with no boot warning. The fix (warn-or-wire) closes that gap.

Defects 2 and 3 are retained for completeness but are NOT LOGIN_FORM-specific cluster members: CSRF-disabled is a deliberate platform-wide posture (identical in all three modes), and the redirect is deploy-time config rather than a per-request open-redirect. The original "triple compounding under LOGIN_FORM" framing does not survive reading the sibling configs.

## Suggested fix

**Thread A - Wire AuthorizationCustomizer OR fail-fast (Defect 1).**

Option A1 - wire AuthorizationCustomizer in LOGIN_FORM the same way OAUTH2/LDAP do. Replace the inline lambda spec (lines 55-57) with the same customizer the siblings use:

```java
// LoginFormSecurityConfiguration: replace the .authorizeExchange(spec -> ...) lambda with
.authorizeExchange(new AuthorizationCustomizer(permissionService, extractors))
```

This requires injecting `PermissionService` + `List<ResourceExtractor>` into the config (as OAUTH2/LDAP already do) and reconciling the LOGIN_FORM `permittedPaths` list (line 49-51) with `AuthorizationCustomizer`'s `SecurityConstants.WHITELIST_PATHS` (`SecurityConstants.java:95-96`) - they differ (LOGIN_FORM permits `/actuator/health`, the customizer permits `/actuator/**`, `/img/**`). Side-effect: Policy/Role tables become live in LOGIN_FORM, and because every form user currently carries ADMIN authority (`:81`), admin-gated paths still pass for all of them unless the ADMIN-for-all behaviour is also revisited. So Option A1 alone changes per-path *permission* gating but not the everyone-is-admin posture.

Option A2 - fail-fast on boot if Policies exist:

```java
@PostConstruct
void warnIfPoliciesExist() {
    long policyCount = policyRepository.count().block();
    if (policyCount > 0) {
        log.warn("LOGIN_FORM auth-mode is dev/demo only. Policies exist ({}), but AuthorizationCustomizer is NOT wired in LOGIN_FORM. Switch to OAUTH2 or LDAP.", policyCount);
    }
}
```

Recommended: Option A2 first (low-risk warn-only); Option A1 as a follow-up when the warn-period reveals zero impact OR after operator migration plan.

**Thread B - Conditional CSRF enable (Defect 2).**

Replace the unconditional `.csrf(...::disable)` with a conditional CSRF that's enabled by default and disable-able via `@ConditionalOnProperty(name = "auth.login-form.csrf.enabled", havingValue = "false")`. Requires SPA-side handling - either double-submit cookie OR `X-Requested-With: XMLHttpRequest` header on all state-changing requests.

Realistic phasing: ship the CSRF token endpoint + SPA-side handling first; THEN enable conditional CSRF in a later release.

**Thread C - Allowlist `auth.login-form-redirect` (Defect 3).**

```java
@Value("${auth.login-form-redirect:}")
private String redirectUri;
@Value("${auth.login-form-redirect.allowlist:}")
private List<String> redirectAllowlist;  // host:port entries, comma-separated

private URI parseRedirectUri() {
    if (redirectUri.isEmpty()) return null;
    URI uri = URI.create(redirectUri);
    if (!redirectAllowlist.isEmpty() && !redirectAllowlist.contains(uri.getHost() + ":" + uri.getPort())) {
        throw new IllegalStateException("Redirect host " + uri.getHost() + " not in auth.login-form-redirect.allowlist");
    }
    return uri;
}
```

Boot-time validation rather than per-request - the redirect target is configuration-time, not request-time.
