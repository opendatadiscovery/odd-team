## What

Four hand-numbered advisory-lock IDs are assigned across three `@ConfigurationProperties` classes with NO central registry, NO `@PostConstruct` cross-validator, NO startup INFO log enumerating "the platform's advisory-lock-id registry," AND the lock acquisition path uses the **blocking** variant of `pg_advisory_lock(N)` with NO timeout / NO fail-fast / NO readiness-probe degradation. The compound: an operator misconfigures one ID to collide with another (typical enterprise hygiene — per-env env-var overrides), and one subsystem silently wedges forever while `/actuator/health` reports "running."

**Defect 1 — No central registry / no collision validator (F-065a).** Four IDs are scattered across `application.yml`:
- `notifications.wal.advisory-lock-id: 100` (line 177) — in NotificationsProperties.wal
- `partition.advisory-lock-id: 90` (line 198) — in the partition properties class (shared between ActivityTablePartitionManager + MessageTablePartitionManager — deliberate)
- `datacollaboration.receive-event-advisory-lock-id: 110` (line 201) — in DataCollaborationProperties
- `datacollaboration.sender-message-advisory-lock-id: 120` (line 202) — in DataCollaborationProperties

Grep for `AdvisoryLockId` / `LockIdRegistry` returns zero matches. No `@PostConstruct` cross-class validation. No startup log enumeration.

**Defect 2 — `pg_advisory_lock` blocks forever; Spring container never detects the wedge (F-065b — HIGH).** `PostgreSQLLeaderElectionManagerImpl.java:21-24` executes `pg_advisory_lock(advisoryLockId)` via raw `Statement.execute` — the **blocking** variant. NO `pg_try_advisory_lock` fast-path, NO `statement_timeout`, NO Spring bean readiness-probe degradation. On collision, the second subsystem's acquire thread enters Postgres lock-wait state FOREVER. The Spring container DOES NOT detect the wedge — bean construction returned; the worker thread is in WAIT via Postgres; `/actuator/beans` + `/actuator/health` report "running."

Three of the four advisory locks live inside P-07 features (notifications WAL — F-009; data-collaboration receive + sender — F-038); a collision silently breaks one or more P-07 features with no diagnostic trail.

## Why it matters

The compound failure pattern:
1. Operator runs ODD alongside a different Postgres-using application on the same DB instance (common — corporate Postgres clusters host multiple apps)
2. Operator sets `NOTIFICATIONS_WAL_ADVISORY_LOCK_ID` to a value that ALREADY belongs to the sibling app
3. ODD starts, NotificationSubscriber tries `pg_advisory_lock(N)` — blocks forever
4. Spring container reports "started"; `/actuator/health` reports "UP"
5. Notifications silently never send; no error trail anywhere
6. Operator investigates: bean is constructed, health is green, no exceptions in logs. Discovery takes hours-to-days.

OR the intra-platform variant:
1. Operator copies env vars across environments
2. One env has `NOTIFICATIONS_WAL_ADVISORY_LOCK_ID=100` (correct) but another env (Helm overlay) reused `DATACOLLABORATION_RECEIVE_EVENT_ADVISORY_LOCK_ID=100` (typo / copy-paste bug)
3. Same outcome: one subsystem wedges silently

This is the operator-trust-failure class — operators see green health and one specific feature broken; the diagnostic trail does not point at advisory-lock-id collision.

Severity HIGH because:
- Silent wedge with no health-probe degradation is the worst observability defect class
- The fix is a small wrapper + a registry enum, low risk-of-regression
- Operator-side workarounds are difficult (requires pg_locks inspection, deep platform-internal knowledge)

## Suggested fix

Five small additions; all ship in one PR.

### (a) Central registry

```java
// new file: AdvisoryLockId.java
public enum AdvisoryLockId {
    PARTITION_LEADER(90),
    NOTIFICATION_WAL(100),
    DATACOLLABORATION_RECEIVE(110),
    DATACOLLABORATION_SEND(120);

    private final long id;
    AdvisoryLockId(long id) { this.id = id; }
    public long id() { return id; }
}
```

(Keep the YAML-overridable per-key configuration; map operator-supplied values back through this enum at startup.)

### (b) `@PostConstruct` cross-validator

```java
// in a @Configuration bean that depends on all four @ConfigurationProperties classes
@PostConstruct
void validateAdvisoryLockIdsAreDistinct() {
    final Map<Long, List<String>> byId = Map.of(
        notificationsProperties.getWal().getAdvisoryLockId(), List.of("notifications.wal"),
        partitionProperties.getAdvisoryLockId(), List.of("partition (shared by activity + message partition managers)"),
        datacollaborationProperties.getReceiveEventAdvisoryLockId(), List.of("datacollaboration.receive-event"),
        datacollaborationProperties.getSenderMessageAdvisoryLockId(), List.of("datacollaboration.sender-message")
    );
    final List<Long> ids = List.of(/* all four */);
    final long distinct = ids.stream().distinct().count();
    if (distinct != ids.size()) {
        throw new IllegalStateException(
            "Advisory-lock-id collision detected: " + byId
            + ". Each subsystem requires a distinct ID (partition managers intentionally share)."
        );
    }
}
```

Boot fails-fast on collision; the operator sees the message naming the colliding keys.

### (c) Replace blocking acquire with try + timeout + readiness-probe degradation

```java
// PostgreSQLLeaderElectionManagerImpl.java
public boolean acquireLock(final long advisoryLockId) {
    final int timeoutMs = 30_000;
    final long deadline = System.currentTimeMillis() + timeoutMs;
    try (final Connection conn = connectionFactory.getConnection();
         final Statement st = conn.createStatement()) {
        while (System.currentTimeMillis() < deadline) {
            try (ResultSet rs = st.executeQuery(String.format(
                    "SELECT pg_try_advisory_lock(%d)", advisoryLockId))) {
                if (rs.next() && rs.getBoolean(1)) {
                    log.info("Acquired advisory lock {}", advisoryLockId);
                    leaderStateGauge.labels(String.valueOf(advisoryLockId)).set(1);
                    return true;
                }
            }
            Thread.sleep(1_000);
        }
        log.warn("Failed to acquire advisory lock {} within {}ms — subsystem degraded",
                 advisoryLockId, timeoutMs);
        leaderStateGauge.labels(String.valueOf(advisoryLockId)).set(0);
        return false;
    } catch (final Exception e) {
        log.error("Advisory lock acquisition error for {}: {}", advisoryLockId, e.getMessage());
        leaderStateGauge.labels(String.valueOf(advisoryLockId)).set(0);
        return false;
    }
}
```
