## What

`POST /ingestion/alert/alertmanager` - the Prometheus AlertManager webhook endpoint that ingests external alerts as Distribution Anomaly alerts - is reachable **without any authentication** in 3 of the 4 auth modes, including the default:

- `auth.type=DISABLED` (default): everything is `permitAll` (`DisabledAuthSecurityConfiguration.java:16`) - **driven 2026-06-07/06-10 (IT-115): anonymous POST -> 200, alert row created.**
- `auth.type=OAUTH2` / `LDAP`: the path is inside the `/ingestion/**` whitelist that `AuthorizationCustomizer.java:21-23` marks `permitAll()` - anonymous reach, verified by code trace (not driven).
- `auth.type=LOGIN_FORM` is the exception: its hand-rolled permit list names only `/ingestion/entities` + `/ingestion/datasources` (`LoginFormSecurityConfiguration.java:48-56`), so the alertmanager path falls through to `.pathMatchers("/**").authenticated()` - the webhook then demands a session, which also means **the AlertManager integration cannot work at all under LOGIN_FORM** (AlertManager carries no session cookie); static trace, not driven.

In all modes, `auth.ingestion.filter.enabled` is irrelevant to this path - neither ingestion filter matches it.

Anyone with network reach can POST arbitrary AlertManager-shaped payloads and create alerts on any **existing** data entity whose ODDRN they can name. The `alert.data_entity_oddrn` FK to `data_entity(oddrn)` (V0_0_12 migration) means a non-existent ODDRN is rejected with 400 `USR003` and no row (driven, IT-115 step 5) - so the forge requires a real ODDRN, which collector-produced ODDRNs make guessable (`//postgresql/host/.../tables/orders`). Each accepted POST creates `alert` + `alert_chunk` rows with `status = OPEN`, filling the Alerts UI with noise until an operator resolves them.

## Where

Three files participate in the gap:

- `odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/auth/util/SecurityConstants.java:95-96` - `/ingestion/**` is in `WHITELIST_PATHS`, bypassing Spring Security's permission chain:
  ```java
  public static final String[] WHITELIST_PATHS =
      {"/actuator/**", "/favicon.ico", "/ingestion/**", "/img/**", "/api/slack/events"};
  ```

- `odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/auth/filter/IngestionDataEntitiesFilter.java:20,28` - the only filter conditional on `auth.ingestion.filter.enabled`, scoped to `/ingestion/entities` only:
  ```java
  @ConditionalOnProperty(value = "auth.ingestion.filter.enabled", havingValue = "true")
  public class IngestionDataEntitiesFilter extends AbstractIngestionFilter {
      public IngestionDataEntitiesFilter(...) {
          super(new PathPatternParserServerWebExchangeMatcher("/ingestion/entities", HttpMethod.POST));
          ...
      }
  }
  ```

- `odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/auth/filter/IngestionDataSourceFilter.java:20` - the second ingestion filter, always active (no @ConditionalOnProperty), scoped to `/ingestion/datasources`:
  ```java
  public IngestionDataSourceFilter(final ReactiveCollectorRepository collectorRepository) {
      super(new PathPatternParserServerWebExchangeMatcher("/ingestion/datasources", HttpMethod.POST));
      ...
  }
  ```

Neither filter covers `/ingestion/alert/alertmanager`, so `AlertManagerController.java:21` (`@PostMapping(path = "ingestion/alert/alertmanager")`) carries no auth enforcement of its own; reachability per auth mode is as in `## What` (the security chains: `DisabledAuthSecurityConfiguration.java:16`, `AuthorizationCustomizer.java:21-23` wired by `OAuthSecurityConfiguration.java:98` / `LDAPSecurityConfiguration.java:145`, `LoginFormSecurityConfiguration.java:48-57`).

## User-facing impact

- WHO: any unauthenticated network caller (attacker or misconfigured scanner); the victims are operators reading the Alerts UI.
- WHAT they do: POST an AlertManager-shaped JSON body with a real `entity_oddrn` label to `/ingestion/alert/alertmanager`, no credential.
- WHAT they observably get: **200, and one OPEN DISTRIBUTION_ANOMALY alert row attributed to an entity they do not own** - driven on the running stack 2026-06-07..06-10 (protocol `integration-tests/protocols/IT-115-alertmanager-webhook-ungated.md`; latest full-suite PASS incl. `alertmanager-webhook-ungated.spec.ts`: `integration-tests/run-log/2026-06-10-feature-complete.md`, SUT e9673a89). The chunk description stores the attacker-supplied `generatorURL` host verbatim (driven, same run). A non-existent ODDRN -> 400 USR003, no row (driven).
- Operators then see the forged alert in the UI: the platform-wide All alerts tab lists every OPEN alert (`AlertServiceImpl.listAll` -> `listAllWithStatusOpen`, verified by FE/BE trace 2026-06-10: `AlertItem.tsx:136` renders the type title, `:184-186` the chunk description text), indistinguishable from a real one (cross-owner visibility posture is PLT-121). The entity-level Alerts tab shows it too (`DataEntityAlertItem.tsx`).
- Cleanup burden is manual: housekeeping deletes only `RESOLVED`/`RESOLVED_AUTOMATICALLY` alerts past the TTL (`AlertHousekeepingJob.java:28-34`, verified by FE/BE trace 2026-06-10) - forged alerts stay `OPEN` forever until a human resolves each one.
- Under LOGIN_FORM the anonymous POST is instead rejected by the auth chain (static trace consistent; not driven - remaining check: observe the 401/302 shape on a LOGIN_FORM stack).

## Why it matters

- **Default-deploy security regression when the endpoint is documented.** ODD Team's DOC-019 (AlertManager integration) shipped to `docs.opendatadiscovery.org` on 2026-04-24, advertising the endpoint publicly for the first time. Before DOC-019, the endpoint was discoverable only by source-reading; after DOC-019, every operator running ODD Platform knows it exists and knows its path. Anyone scanning a public ODD Platform URL now has a known unauthenticated write endpoint.
- **The sibling endpoints are better guarded.** `/ingestion/datasources` is always token-protected (`IngestionDataSourceFilter` is unconditional); `/ingestion/entities` is token-protected when `auth.ingestion.filter.enabled=true`. Operators reading DOC-004 (pending) or the sibling code will reasonably expect `/ingestion/alert/alertmanager` to follow the same model.
- **Writes have side effects.** Each POST creates `ALERT` + `ALERT_CHUNK` rows, routed by the `entity_oddrn` label. An attacker who can guess ODDRN patterns (e.g. `//postgresql/host/db/schemas/public/tables/orders`) can fabricate Distribution Anomaly alerts on production entities.
- **Housekeeping does not garbage-collect these alerts at all while they are OPEN.** The housekeeping job deletes only `RESOLVED` / `RESOLVED_AUTOMATICALLY` alerts older than `housekeeping.ttl.resolved_alerts_days` (default 30) - corrected 2026-06-10: an earlier revision cited a suspected SQL-precedence bug here (PLT-005); that claim was falsified (jOOQ renders the intended grouping), so resolved fakes age out normally. Fake `OPEN` alerts created via this unauthenticated endpoint stay forever until an operator resolves them.

## Suggested fix

The simplest fix is to extend `IngestionDataEntitiesFilter` (or add a parallel `IngestionAlertManagerFilter`) so that `/ingestion/alert/alertmanager` (POST) is also matched when `auth.ingestion.filter.enabled=true`. The filter should require a valid token via the `Authorization: Bearer <token>` header - that IS the existing ingestion auth model (`AbstractIngestionFilter.resolveToken`, `AbstractIngestionFilter.java:45-51`; corrected 2026-06-10: an earlier revision said `X-API-Key`, which no ingestion filter reads). AlertManager can carry it via `http_config.authorization`. The LOGIN_FORM permit-list should also be reconciled (it currently blocks the webhook entirely - see `## What`).

Option A - extend the existing filter path matcher to cover both paths:
```java
public IngestionDataEntitiesFilter(...) {
    super(new OrServerWebExchangeMatcher(
        new PathPatternParserServerWebExchangeMatcher("/ingestion/entities", HttpMethod.POST),
        new PathPatternParserServerWebExchangeMatcher("/ingestion/alert/alertmanager", HttpMethod.POST)
    ));
    ...
}
```
(adjusts naming: rename filter or accept the slight naming drift.)

Option B - add a new `IngestionAlertManagerFilter` in the same package, same `@ConditionalOnProperty` gate, scoped to `/ingestion/alert/alertmanager`. Body-decorator logic can reject requests without a valid `X-API-Key`.

Option C (defense-in-depth, additional to A or B) - remove `/ingestion/**` from `SecurityConstants.WHITELIST_PATHS` and explicitly list `/ingestion/entities`, `/ingestion/datasources`, `/ingestion/alert/alertmanager` instead, so future endpoints added under `/ingestion/*` do not silently inherit whitelist coverage.

Documentation (DOC-065) should ship alongside the code fix so operators upgrading to the fixed version understand the new filter coverage, and operators on older versions know to apply perimeter controls.

## How discovered

Surfaced during `/review DOC-019` (2026-04-24) - the review's Gate 4 consumer-read audit cross-checked the doc's authentication claim against `IngestionDataEntitiesFilter`, `IngestionDataSourceFilter`, `S2sAuthenticationFilter`, and `SecurityConstants.WHITELIST_PATHS`. DOC-004 (pending) already describes the `/ingestion/entities`-only scope of `auth.ingestion.filter.enabled` - DOC-019 contradicted DOC-004 by asserting the flag guards the AlertManager endpoint.

**Corrected 2026-06-10 (user-facing verification sweep):** was "unauthenticated in every deployment regardless of `auth.ingestion.filter.enabled`"; actually anonymous under DISABLED (driven, IT-115) + OAUTH2/LDAP (whitelist trace) but BLOCKED under LOGIN_FORM (`LoginFormSecurityConfiguration.java:48-57` omits the path from its permit list), where the integration cannot function at all. Also: the suggested header was `X-API-Key`, but the ingestion auth model reads `Authorization: Bearer` (`AbstractIngestionFilter.java:45-51`); and the housekeeping bullet's PLT-005 SQL-precedence claim was falsified (see PLT-005). The core defect - the webhook is anonymous in the default deployment and forges real OPEN alerts - HOLDS and is driven (IT-115).
