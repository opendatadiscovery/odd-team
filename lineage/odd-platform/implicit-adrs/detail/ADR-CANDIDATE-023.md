- **ADR-CANDIDATE-023** (NEW 2026-05-10A): Chunked-upload session identity is the server-issued `uploadId` (UUID) — controllers bind the path's `dataEntityId` for routing/authorisation but never propagate it to the service; the service resolves the file row by `uploadId` only
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar (`uploadFileChunk`) — the convention is consistent across `uploadFileChunk` AND `completeFileUpload`, both of which bind `dataEntityId` from the path and discard it before the service call
  - **Surfaced by**:
    - `odd-platform__java__DataEntityAttachmentController__controller-method__uploadFileChunk.md:implicit_adrs.[1]` ("The chunked-upload session is keyed by `uploadId` alone; the path's `data_entity_id` is captured for routing/authorisation but is not propagated to the service. Both `uploadFileChunk` (DataEntityAttachmentController.java:54-62) and `completeFileUpload` (DataEntityAttachmentController.java:65-70) ignore `dataEntityId` after binding it." — intent_anchor: "service signature `Mono<Void> uploadFileChunk(final UUID uploadId, final Part file, final int index)` at AttachmentService.java:30 — the `dataEntityId` parameter is intentionally omitted from the service contract")
  - **Decision statement**: The chunked-upload state machine (`initiateFileUpload` → N × `uploadFileChunk` → `completeFileUpload`) is keyed by the server-issued UUID `uploadId` alone. Controllers BIND the path's `dataEntityId` (because the OpenAPI spec declares both `data_entity_id` and `upload_id` as path parameters at openapi.yaml:1618-1645), and the path's `dataEntityId` IS used by the SECURITY_RULES path-matcher gate (ADR-CANDIDATE-002) to evaluate `DATA_ENTITY_ATTACHMENT_MANAGE` against the URL's entity. But controllers do NOT FORWARD `dataEntityId` into the service; the service signature `Mono<Void> uploadFileChunk(UUID uploadId, Part file, int index)` (`AttachmentService.java:30`) intentionally lacks the parameter. The service resolves the file row via `FileRepository.getFileByUploadId(uploadId)` (`FileServiceImpl.java:94`) — `uploadId` is the authoritative session key by design.
  - **Wisdom test**: PASS. The convention is consistent across two methods (uploadFileChunk + completeFileUpload), is anchored at the service interface (the parameter is intentionally absent), and matches the service-side resolution shape (resolve by uploadId, not by entity). The maintainer made a structural choice to scope the session to the UUID rather than to a (entity, uuid) pair.
  - **Evidence**:
    - uploadFileChunk.md says: "DataEntityAttachmentController.java:54-62 + DataEntityAttachmentController.java:65-70 + AttachmentService.java:30 + AttachmentServiceImpl.java:71-73 + FileServiceImpl.java:93-102"
  - **Existing ADR**: none. (Composes with ADR-CANDIDATE-002 — the SECURITY_RULES gate evaluates against the path's `dataEntityId` while the chunk lands against the `uploadId`'s entity — the two-stage decoupling is the architectural shape, but it produces the cross-entity-hijack vulnerability captured at REFACTOR-010.)
  - **Co-surfaced gaps** (link from `refactoring-scopes.md`): REFACTOR-010 (cross-entity uploadId hijack — the ADR-shape's price; a caller with `DATA_ENTITY_ATTACHMENT_MANAGE` on entity X can post chunks to entity Z's session if they obtain Z's uploadId — strengthened by 2026-05-10A sidecar). REFACTOR-058 (chunk staging path is `attachment.storage`-INDEPENDENT; per-instance local fs regardless of LOCAL/REMOTE backend — NEW from 2026-05-10A).
  - **Proposed action**: Promote to `adrs/drafts/chunked-upload-uploadid-session-key.md` (new ADR). Document the trade-off: the uploadId-as-session-key shape allows the service to be entity-agnostic (cleaner separation of concerns) but produces the cross-entity-hijack failure mode (REFACTOR-010) when the SECURITY_RULES gate evaluates against the URL while the file lands against the `uploadId`'s original entity. The fix to REFACTOR-010 is to add a service-layer cross-validation `assert filePojo.dataEntityId == path.dataEntityId` — that fix preserves the ADR's shape and closes the gap.
  - **Severity rationale**: MEDIUM — API-shape + security-coupling decision. Defines how every future stateful-multi-call protocol on the platform should be keyed.
