## What

All 5 logout handlers derive the redirect target from the inbound request URI (`exchange.getExchange().getRequest().getURI()`) via `UriUtils.getBaseUri`: `AzureLogoutSuccessHandler.java:40` (`post_logout_redirect_uri`), `CognitoLogoutSuccessHandler.java:43` (`logout_uri`), `GoogleLogoutSuccessHandler.java:40` (`setLocation`), `GithubLogoutSuccessHandler.java:45` (`setLocation`), `ODDIAMLogoutSuccessHandler.java:39` (`logout_uri`). `UriUtils.getBaseUri` (`UriUtils.java:11-23`) rebuilds the URL from `requestUri.getScheme()/getHost()/getPort()` with no host validation and no scheme enforcement.

**Correction to the original draft (2026-06-10):** the claim that grepping for `platform.base-url` / `odd.platform-url` / `allowed.redirect` "returns ZERO matches" is FALSE. `odd.platform-base-url` already exists as a config property and is consumed (with defaults) in three places - `NotificationConfiguration.java:105` (`:http://localhost:8080`), `SlackMessageGeneratorConfiguration.java:15` (`:http://localhost:8080`), `StaticArgumentMappingContext.java:16` (`:http://your.odd.platform`) - and is documented (commented) at `application.yml:209`. The defect is therefore NOT "no canonical-URL property exists"; it is "the logout handlers don't USE the existing `odd.platform-base-url` and instead trust the request URI." That changes the fix from "add a new property" to "consult the property the platform already defines."

**Attack preconditions (the observable is conditional, not unconditional):** `getBaseUri` reads `requestUri.getHost()`. Spring WebFlux only folds `X-Forwarded-*` into the request URI when `server.forward-headers-strategy` is set (FRAMEWORK/NATIVE) - and that property is NOT set anywhere in this codebase (verified 2026-06-10). So the specific `X-Forwarded-Host` vector requires the operator to have enabled forwarded-headers (or to front the app with a proxy that rewrites the literal `Host` header). Given that, AND an IdP whose post-logout allowlist is permissive (e.g. `https://*.example.com/`), a crafted Host lands the user on an attacker host after logout. Single-host deployments behind a Host-pinning proxy are not exposed.

## User-facing impact

RUNTIME-ONLY and multi-precondition; the redirect-derivation code path is CODE-SETTLED.

- **Derivation (verified-trace, static):** all 5 handlers build the IdP redirect from the inbound request URI via `UriUtils.getBaseUri`, with no allowlist - confirmed by reading each handler + `UriUtils.java:11-23`. Settled without running anything.
- **`odd.platform-base-url` exists (verified-trace, static):** confirmed three live consumers + the commented yml key; the original "zero matches" grep claim is falsified.
- **Open-redirect observable (static-not-driven; manifests only under a precondition stack):** requires (1) `auth.type=OAUTH2` (the handlers are `@Conditional` on a provider; under the default `DISABLED` at `application.yml:34` they are never constructed), (2) forwarded-headers enabled OR a Host-rewriting proxy (no `server.forward-headers-strategy` is set by default), and (3) an IdP post-logout allowlist permissive enough to accept the injected host. None of these were stood up in this sweep. Remaining check = OAUTH2 stack + `server.forward-headers-strategy=FRAMEWORK`, send `X-Forwarded-Host: evil.example.com` on logout, observe the IdP redirect carrying the attacker host.

## Why it matters

Even when it fires, the user is redirected AFTER session invalidation, so the direct impact is a phishing landing page on a look-alike host rather than a session takeover. It compounds with the token-revocation gaps tracked in PLT-073 (captured IdP tokens stay valid for their TTL). Real, but gated behind operator-enabled forwarded-headers + a permissive IdP allowlist - hence severity reduced from high to medium and the fix reframed to "use the existing `odd.platform-base-url`."

## Suggested fix

Reuse the EXISTING `odd.platform-base-url` property (already consumed by notifications/Slack/integration code; see Where) rather than introducing a new one - and add boot-time validation. The yml key is already present (commented) at `application.yml:209`:

```yaml
# application.yml (already documented at :209, currently commented)
odd:
  platform-base-url: "https://your.odd.platform"
```

```java
@Value("${odd.platform-base-url:}")
private String platformBaseUrl;

@PostConstruct
void requirePlatformBaseUrl() {
    if (platformBaseUrl.isBlank() && authType != AuthType.DISABLED) {
        log.warn("odd.platform-base-url is unset. Post-logout redirect derives target from inbound Host header - at risk of X-Forwarded-Host hijack. Set odd.platform-base-url to your platform's canonical URL.");
        // Optionally fail-fast for OAUTH2 mode where logout-redirect is most operator-load-bearing
    }
}

// In each *LogoutSuccessHandler, replace:
//   String redirectTo = UriUtils.getBaseUri(exchange.getRequest().getURI());
// with:
//   String redirectTo = platformBaseUrl;   // configured at deployment time, not derived
```

Migration note: operators with multi-env deployments using the same App Registration need to deploy the same `odd.platform-base-url` ALONGSIDE the auth-mode config. Doc-side cross-link from DOC-236 explains this.

Alternative - keep Host derivation but validate against allowlist:

```java
@Value("${odd.platform-base-url.allowlist:}")
private List<String> baseUrlAllowlist;   // host:port entries

private String safeRedirectTarget(URI requestUri) {
    String inbound = UriUtils.getBaseUri(requestUri);
    if (baseUrlAllowlist.isEmpty() || baseUrlAllowlist.contains(URI.create(inbound).getHost())) {
        return inbound;
    }
    throw new IllegalStateException("Host " + URI.create(inbound).getHost() + " not in odd.platform-base-url.allowlist");
}
```

Recommended single-value `odd.platform-base-url` first - simpler operator story; allowlist is a follow-up for multi-host deployments.
