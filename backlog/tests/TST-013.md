## Description

The external-statistics tag reconcile in `DatasetFieldServiceImpl` is a per-request read-modify-write (RMW), not an atomic compare-and-set across POSTs. The reconcile reads the current relations, diffs them against the relations the incoming request implies, then deletes-the-stale-and-creates-the-new in two separate reactive repository calls — there is no row lock, version column, or transactional fence spanning the read and the write (`DatasetFieldServiceImpl.java:217-228`):

```java
return reactiveTagRepository
    .listTagsRelations(datasetFieldIds, TagOrigin.EXTERNAL_STATISTICS)   // READ
    .collectList()
    .flatMap(existingRelations -> {
        final List<TagToDatasetFieldPojo> relationsToDelete = existingRelations.stream()
            .filter(r -> !relationsToCreate.contains(r))                  // DIFF (in app memory)
            .toList();
        return reactiveTagRepository
            .deleteDatasetFieldRelations(relationsToDelete)               // WRITE 1
            .then(reactiveTagRepository.createDatasetFieldRelations(relationsToCreate).collectList()); // WRITE 2
    });
```

For a single ingestion caller replaying the same dataset's statistics, the operation is idempotent and safe. But two ingestion POSTs for the SAME dataset field set that interleave between the `listTagsRelations` READ and the `delete/create` WRITE produce last-writer-wins: each request computed `relationsToDelete`/`relationsToCreate` against the relation snapshot it read, so the second writer can re-create relations the first writer just deleted, or delete relations the first writer just created — the final tag set reflects whichever request's WRITE landed last, not a merge of both.

**Typed gate: validates-feature (probe-gated).** This is NOT a known-bug characterization pin — single-caller ingestion (the normal collector path) is correct, so there is no current-incorrect-behaviour to freeze. The behaviour to guard is the documented/intended contract of the external-statistics tag reconcile under the realistic single-writer-per-dataset assumption, plus the explicit boundary: concurrent writers for the same field set are last-writer-wins. The probe establishes whether concurrent same-field POSTs actually interleave into a lost-update on a live stack before we decide whether to harden (add a transaction / row lock / version) or document the single-writer assumption as a caveat.
