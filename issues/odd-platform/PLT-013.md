## What

Two operator-trust hardening items on the Term subsystem. Distinct but adjacent - both subvert the Business Glossary's implied "namespace-scoped, permission-gated" framing.

**Defect 1 - Description-edit auto-link side-channel.** Editing an entity description with `[[term-namespace:term-name]]` syntax automatically creates a Term-to-Entity link row (`data_entity_to_term` with `is_description_link = true`) as a side-effect of the description-update flow. The auto-link path **does not check `DATA_ENTITY_ADD_TERM`** - it is gated only by the description-update permission. The explicit link endpoint `POST /api/dataentities/{id}/term` IS gated by `DATA_ENTITY_ADD_TERM` (`SecurityConstants.java:237-239`), so the two paths that create the same row class have different permission requirements - a separation-of-duties policy expecting term-link to be a distinct grant leaks. (Independent of PLT-012; even if the SecurityConstants `/term` path mismatch is fixed, this side channel remains until this PLT lands.)

**Defect 2 - Cross-namespace term enumeration / pollution.** The Business Glossary page claims *"Searches and term-to-entity link operations resolve within the namespace by default."* `ReactiveTermRepositoryImpl` has **zero per-namespace filter** at any read site (per substrate batch N audit - `zero odd.tenant-id references; zero per-namespace filter at any read site`). Multi-namespace deployments see ALL terms from ALL namespaces; namespace is informational on the response payload, not a filter on the SQL.

## Where

### Defect 1 - auto-link bypass

```
odd-platform-api/.../service/DataEntityServiceImpl.java:323-333         (upsertDescription)
odd-platform-api/.../service/term/TermServiceImpl.java:201-205          (handleDataEntityDescriptionTerms)
odd-platform-api/.../service/term/TermServiceImpl.java:362-388          (updateDataEntityDescriptionTermsState -> createRelationsWithDataEntity)
odd-platform-api/.../auth/util/SecurityConstants.java:237-239           (DATA_ENTITY_ADD_TERM gates ONLY POST /api/dataentities/{id}/term)
```

Verified by BE trace 2026-06-10: the description-update flow `DataEntityServiceImpl.upsertDescription` (`:323-333`, `@ReactiveTransactional`) updates the description, then calls `termService.handleDataEntityDescriptionTerms(dataEntityId, formData.getInternalDescription())` (`:328`) in the SAME transaction. That walks the description for `[[ns:term]]` tokens (`findTermsInDescription`) and, via `updateDataEntityDescriptionTermsState` (`TermServiceImpl.java:362-388`), calls `termRelationsRepository.createRelationsWithDataEntity(...)` (`:384`) creating `data_entity_to_term` rows with `is_description_link = true` - WITHOUT any `DATA_ENTITY_ADD_TERM` evaluation. The platform's authz is path-based `SecurityRule` matchers (not inline annotations), and there is no rule binding the description-update path to `DATA_ENTITY_ADD_TERM`; that permission is bound only to the explicit `POST .../term` endpoint (`SecurityConstants.java:237-239`). (Correction: the earlier revision pointed at `TermAssignmentActivityHandler.java`, which is a READ-ONLY activity-state snapshotter - it has no write/link creation; the real write path is the chain above.)

### Defect 2 - cross-namespace pollution

```
odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/repository/reactive/ReactiveTermRepositoryImpl.java
```

19 public methods (verified 2026-06-10) across single-row lookups, paginated lists, FTS-ranked suggestions, faceted search, and the `hasDescriptionRelations` rename-protection guard. No per-namespace/tenant filter is applied at the read sites - `NAMESPACE_ID` appears only in a JOIN to surface the namespace name into the response DTO, never as a tenant-scoping WHERE predicate (grep 2026-06-10: no `odd.tenant-id` reference anywhere; the lone `NAMESPACE_ID.eq` is not a per-caller scope). Namespace is informational on the payload, not a filter on the SQL.

## User-facing impact

**Defect 1 (authorization asymmetry).**
- WHO: an operator who configured RBAC expecting term-linking to be a distinct grant from description-editing (e.g. analysts edit descriptions; curators decide term links).
- WHAT they do: a user with only the description-update grant edits an entity description containing `[[ns:term]]`.
- WHAT they observe: a Term-to-Entity link is created and shown on the entity, even though that user was never granted `DATA_ENTITY_ADD_TERM`. Verified by BE trace 2026-06-10: `upsertDescription` -> `handleDataEntityDescriptionTerms` -> `createRelationsWithDataEntity` (`DataEntityServiceImpl.java:328`, `TermServiceImpl.java:362-388`) with no `DATA_ENTITY_ADD_TERM` rule on that path, while the explicit endpoint IS gated (`SecurityConstants.java:237-239`). The asymmetry is a pure code-structure fact, fully settled. (The FE renders the resulting `linkedTerms` returned by `upsertDescription` - the link is user-visible on the entity's terms.)

**Defect 2 (cross-namespace enumeration).**
- WHO: an operator of a multi-namespace deployment who believes term browse/search is namespace-scoped.
- WHAT they do: browse / search / get term suggestions in the Business Glossary.
- WHAT they observe: terms from ALL namespaces, not just their own. Static trace consistent (no tenant filter at any `ReactiveTermRepositoryImpl` read site, verified 2026-06-10); but the user-visible symptom only manifests in a deployment that actually has more than one namespace AND a posture expecting isolation - that multi-namespace condition is the remaining check (not driven here). Single-namespace deployments observe nothing.

**Defect 1** silently widens the surface of any `DATA_ENTITY_DESCRIPTION_UPDATE` grant. An operator configuring fine-grained RBAC (e.g., "let analysts edit data entity descriptions but require curators for term-link decisions") gets both capabilities in one grant. Compliance audits looking for explicit term-link grant trails won't find the side-channel writes. Medium severity because (a) the bypass is per-edit (not bulk), (b) it requires description-edit access (a meaningful gate), (c) the side-channel writes still emit activity events so post-hoc audit is possible - but the operator's *expectation* of separation is broken.

**Defect 2** depends on deployment model. Single-namespace deployments are unaffected. Multi-namespace / multi-tenant deployments hit it the moment a second namespace exists - every term browse, search, and suggestion list mingles all namespaces. The doc-side claim contradicts implementation; operators believing namespace isolation is enforced get a leaky abstraction. Medium severity because the platform's multi-tenancy story is itself ambiguous (no documented `odd.tenant-id` boundary) and this defect IS the canonical answer (there isn't one at the term layer).

## Suggested fix

### Defect 1 - auto-link bypass

Two options:

**Option A (recommended)** - explicit permission check at the auto-link path:

```java
// TermAssignmentActivityHandler - pseudo-code, adapt to actual handler shape
private Mono<Void> createAutoLinks(DataEntityDescription desc) {
    List<TermLink> linksToCreate = parseDescriptionForTermTokens(desc);
    return permissionService
        .hasPermission(currentUser, DATA_ENTITY_ADD_TERM, dataEntityId)
        .flatMap(allowed -> allowed
            ? termRelationsRepository.createLinks(linksToCreate)
            : Mono.empty()                              // skip auto-links; description-update succeeds
        );
}
```

The description update still succeeds; only the auto-link side-effect is gated. Existing description editors see no behavioural change unless they were relying on the side-effect for term creation - that pattern is the exact one the defect documents as a leak.

**Option B** - keep the side-channel but **emit a distinct activity event type** (`DATA_ENTITY_TERM_AUTO_LINKED`) and document the side-channel explicitly. This preserves backwards behaviour and explicitly surfaces the side-channel in audit. Recommend Option A; this is a fallback if option A breaks any documented workflow.

### Defect 2 - cross-namespace pollution

Larger architectural question: does ODD Platform intend to support per-namespace tenancy at the term layer?

- **If YES** -> introduce a per-namespace WHERE clause at every `ReactiveTermRepositoryImpl` read site (15 methods). Likely involves threading a `current-namespace-context` (or `current-namespaces-the-user-can-see`) through `PermissionExtractor` or a new `TenancyContext`. Substantial change; coordinate with security architecture.
- **If NO** -> leave the code unchanged and fix the documentation instead (per DOC-177 Caveat 3). This is a deliberate-design statement, not a defect.

Recommend opening a design discussion before coding Defect 2. The doc-side warning (DOC-177) lands either way.

## How discovered

Surfaced during the Mode B run of `docs/coverage/undocumented-features` on 2026-05-27 (substrate `F-002` - Term-to-Entity Linkage). Substrate batch K identified the auto-link side-channel; substrate batch N's primary-source audit of `ReactiveTermRepositoryImpl` confirmed the zero-per-namespace-filter pattern.

Corrected 2026-06-10 (user-facing verification sweep): Defect 1's cited file was `service/term/TermAssignmentActivityHandler.java`; actually that class is a read-only activity-state snapshotter with no link creation. The real auto-link write path is `DataEntityServiceImpl.upsertDescription` (`:328`) -> `TermServiceImpl.handleDataEntityDescriptionTerms` (`:201`) -> `updateDataEntityDescriptionTermsState` (`:362-388`) -> `createRelationsWithDataEntity`, gated by the description-update permission and never by `DATA_ENTITY_ADD_TERM` (which gates only `POST .../term`, `SecurityConstants.java:237-239`). Defect 1 HOLDS (real authz asymmetry) with the corrected citation. Defect 2: method count corrected 15 -> 19; the no-tenant-filter pattern HOLDS; symptom is multi-namespace-deployment-dependent. Both defects survive; medium severity stands. User-facing impact section added. `user_facing_verified` left false because Defect 2's user-visible symptom requires a multi-namespace deployment (not a pure code-settled fact).
