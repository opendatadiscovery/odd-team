## Description

Three tracked artefacts name a **`NAMESPACE`** contextual permission resource type and **drop the real `QUERY_EXAMPLE`** when enumerating the valid `type` values for `GET /api/resource/{type}/{id}/permissions`. The code truth is that the contextual (`hasContext = true`) resource types are **`DATA_ENTITY`, `TERM`, `QUERY_EXAMPLE`** — there is **no `NAMESPACE`** resource type on this endpoint, and `MANAGEMENT` is the single non-contextual one.

Implementing any of the `NAMESPACE` variants verbatim adds a **non-dispatchable** `NAMESPACE` value (no contextual extractor exists for it, so `getResourcePermissionsForCurrentUser` would throw `IllegalArgumentException` "No extractor for resource type NAMESPACE") **and** silently drops `QUERY_EXAMPLE`, which is a real, dispatchable contextual type. The most dangerous instance is **SPC-002 Facet 2**, which is **still `pending`** and instructs the implementer to set the OpenAPI `PermissionResourceType` enum's three contextual values to "`DATA_ENTITY`, `NAMESPACE`, `TERM`" — shipping that corrupts the spec↔runtime contract directly.

Code truth (verified by reading source):

- `PolicyTypeDto` (`PolicyTypeDto.java:9-12`) — `DATA_ENTITY(true)`, `TERM(true)`, `QUERY_EXAMPLE(true)`, `MANAGEMENT(false)`. The boolean is `hasContext`; there is no `NAMESPACE` constant.
- `PermissionServiceImpl.getResourcePermissionsForCurrentUser` (`PermissionServiceImpl.java:24-29`) maps the inbound `PermissionResourceType` to `PolicyTypeDto`, rejects `!hasContext` with `BadUserRequestException` (USR001), then dispatches to the matching `ContextualPermissionExtractor`.
- The three contextual extractors are `DataEntityPermissionExtractor` → `DATA_ENTITY` (`DataEntityPermissionExtractor.java:46`), `TermPermissionExtractor` → `TERM` (`TermPermissionExtractor.java:38`), `QueryExamplePermissionExtractor` → `QUERY_EXAMPLE` (`QueryExamplePermissionExtractor.java:58`). `ManagementPermissionExtractor` → `MANAGEMENT` is the **non-contextual** one. There is no `NamespacePermissionExtractor`.

Status of the three artefacts (verified): the **published** `permissions.md` "Permission read surface" section (DOC-243 output) already shipped **correctly** — line 139 lists `DATA_ENTITY`, `TERM`, `QUERY_EXAMPLE`, and line 143 correctly enumerates the four spec values as `DATA_ENTITY`, `TERM`, `QUERY_EXAMPLE`, `MANAGEMENT`. The `NAMESPACE` error survives only in the **backlog records**: SPC-002 Facet 2 (line 43, **pending** — live risk) and the now-stale `done` AC text of DOC-240 (line 33) and DOC-243 (line 32). This item closes the whole class so a future implementer of SPC-002 cannot re-introduce the error and the records match the already-correct live page.
