## What

Three security/integrity defects on `POST /ingestion/metrics` that expose a default-config deployment to unauthenticated metric injection from any network-reachable caller. Doc-side mitigation ships as DOC-202; structural hardening is this PLT.

**Defect 1 - `/ingestion/metrics` is whitelisted under ALL auth modes.** `SecurityConstants.java:96` - `/ingestion/**` is in `WHITELIST_PATHS` (permitAll, bypasses user auth in every `auth.type`). The only token-based ingestion filters are `IngestionDataEntitiesFilter` (matches `/ingestion/entities`, `:28`) and `IngestionDataSourceFilter` (matches `/ingestion/datasources`, `:20`) - verified 2026-06-10 these are the ONLY `AbstractIngestionFilter` subclasses, and BOTH are `@ConditionalOnProperty(auth.ingestion.filter.enabled=true)` which defaults to **false** (`application.yml:46-48`). NO filter matches `/ingestion/metrics`, and there is no `@PreAuthorize` on the handler (`IngestionController.ingestMetrics:90`). So `/ingestion/metrics` is anonymously reachable on default config AND even with `auth.ingestion.filter.enabled=true` (that filter only guards `/ingestion/entities`).

**Defect 2 - Tenant isolation NONEXISTENT on default INTERNAL_POSTGRES.** `odd.tenant-id` is appended as a Prometheus label only - extractor-tier coupling on the PROMETHEUS path (`CounterTimeSeriesExtractor.java:22-25`). Verified 2026-06-10: the metrics schema (`db/migration/V0_0_67__add_metrics.sql`) defines `metric_entity` / `metric_series` / `metric_point` with NO `tenant_id` column, and `grep tenant_id db/migration` returns nothing across all migrations. Two unrelated deployments writing to a shared Postgres conflate metrics namespaces; an operator's `odd.tenant-id=teamA` setting silently does NOTHING on the INTERNAL_POSTGRES path (no column to persist it).

**Defect 3 - No payload-side ODDRN existence validation.** Verified 2026-06-10: `InternalIngestionMetricsServiceImpl:86-88` calls `metricEntityRepository.registerMetricEntityOddrns(request.metricRelatedOddrns())` with no existence filter; the repo (`MetricEntityRepositoryImpl.registerMetricEntityOddrns:23-43`) blindly upserts each oddrn (`INSERT ... ON CONFLICT (entity_oddrn) DO UPDATE`). `metric_entity` has only `UNIQUE (entity_oddrn)` and NO foreign key to `data_entity` (`V0_0_67__add_metrics.sql:3-8`). Combined with Defect 1, any caller mints arbitrary `metric_entity` rows / series for non-existent ODDRNs (cardinality blast on `metric_label_value`).

## User-facing impact

This is a BE/security/schema issue; the "user" is an operator deploying the platform and any network-reachable caller of `POST /ingestion/metrics`. All three are pure code-structure / schema ABSENCE facts, settled by reading the auth wiring + the migration (no live drive needed to establish the missing control).

- **Defect 1 (anonymous reach) - verified by BE trace 2026-06-10.** `/ingestion/metrics` is in the permitAll whitelist (`SecurityConstants.java:96`) and matched by NO ingestion token-filter (the only two match `/ingestion/entities` and `/ingestion/datasources`, and default off). A security-conscious operator who enables every auth knob still exposes this endpoint to unauthenticated POSTs - the control simply does not exist on this path. (The successful anonymous POST itself is the deterministic consequence; not separately driven.)
- **Defect 2 (no tenant isolation) - verified by schema trace 2026-06-10.** `metric_entity/series/point` have no `tenant_id` column (`V0_0_67__add_metrics.sql`), so an operator who sets `odd.tenant-id=teamA` expecting isolation on INTERNAL_POSTGRES gets none - the value has nowhere to be persisted/filtered; two deployments on a shared Postgres conflate metrics. Settled by the migration.
- **Defect 3 (no existence validation) - verified by BE/schema trace 2026-06-10.** `registerMetricEntityOddrns` blind-upserts any oddrn (`MetricEntityRepositoryImpl.java:23-43`); `metric_entity` has no FK to `data_entity`. A caller (anonymous, via Defect 1) mints arbitrary `metric_entity` rows / series for non-existent ODDRNs that never get GC'd - cardinality blast. Settled by code + schema.

## Why it matters

Three operator profiles affected: (1) security-conscious operators enabling all three auth knobs believe their `/ingestion/*` is gated, but `/ingestion/metrics` is not; (2) multi-tenant operators reading "set `odd.tenant-id=teamA`" reasonably assume isolation but get silent cross-tenant conflation (LSN-001/LSN-002 sibling); (3) phantom `metric_entity` rows from typo'd ODDRNs linger forever (no GC; cardinality blast).

Severity HIGH: Defect 1 enables anonymous-write on default config; Defect 2 is a multi-tenant data-leak invited via the `tenant-id` config; Defect 3 is data-integrity hygiene.

## Suggested fix

**Defect 1 - close auth gap (Option A):**
```java
// IngestionDataEntitiesFilter.java
- private static final String INGESTION_PATH = "/ingestion/entities";
+ private static final String INGESTION_PATH_PREFIX = "/ingestion/";
// widen matcher; closes alertmanager + metrics + stats gap.
```

**Defect 2 - tenant_id on Postgres metric tables:**
```sql
ALTER TABLE metric_entity ADD COLUMN tenant_id TEXT;
ALTER TABLE metric_series ADD COLUMN tenant_id TEXT;
ALTER TABLE metric_point ADD COLUMN tenant_id TEXT;
-- propagate from extractor; filter all reads WHERE tenant_id = currentTenantId()
```

**Defect 3 - payload-side existence check:**
```java
final var existingOddrns = dataEntityRepository.existsByOddrns(request.metricRelatedOddrns());
final var validSubset = request.metricRelatedOddrns().stream()
    .filter(existingOddrns::contains)
    .toList();
// log + skip unknown; return partial-success
```
