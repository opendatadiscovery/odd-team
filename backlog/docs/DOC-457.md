## Description

`Architecture.md:43` links to `configuration-and-deployment/odd-platform.md#attachment-storage`, but the
target heading is `## Attachment Storage Configuration` (`odd-platform.md:1031`), which GitBook slugifies
to `attachment-storage-configuration`. `#attachment-storage` matches **no** heading on the page, so the
anchor is dead — the reader lands at the page top, not the storage section.

Architecture.md is the lone outlier: every other reference (`data-discovery/attachments.md`, `Features.md`,
ADR-0012 ×2 — 6 occurrences total) links correctly to `#attachment-storage-configuration`. The other two
odd-platform.md anchors in Architecture.md (`#enable-alert-notifications`, `#enable-data-collaboration`)
DO resolve, so this is a one-off typo, not a slug-convention misunderstanding.

**Folded finding (was editorial F3, low):** because Architecture.md presents `REMOTE` as the unqualified
durability answer ("Switch to `REMOTE`... for any deployment where attachments must persist") and points
to this link "for the operator caveats", the broken anchor means a reader seeking the REMOTE caveats
(node-local chunk staging even under REMOTE; the AWS S3 region constraint) reaches nothing. Fixing the
anchor restores the path to the caveats — no need to duplicate them on the Architecture summary.
