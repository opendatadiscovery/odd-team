# DOC-510 — the ingestion-auth fix shipped in 0.29.0; six pages still tell operators it did not

## Failure shape

**Internal contradiction** (two pages contradict themselves) + **parallel surfaces with drift** (the corrected
and superseded versions of one claim are both live) — on a **security control**, which makes it Critical under
the priority order: *"Incorrect documentation (actively misleading) — including any caveat that would lead to
data loss or security exposure in a default deployment."*

## What is actually true (verified in source, not inferred)

`IngestionAuthenticationFilter` authenticates **all of `/ingestion/**`** when `auth.ingestion.filter.enabled=true`,
excluding only the two paths that already have dedicated filters:

- `odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/auth/filter/IngestionAuthenticationFilter.java:57-64`
  — matcher = `pathMatchers("/ingestion/**")` AND NOT (`/ingestion/entities` OR `/ingestion/datasources`);
  `@ConditionalOnProperty(value = "auth.ingestion.filter.enabled", havingValue = "true")` at `:49`.
- Its own javadoc `:29-40` names the previously-uncovered routes it closes: `/ingestion/entities/datasets/stats`,
  **`/ingestion/metrics`**, the `GET /ingestion/entities/degs/children` read, and states
  *"The Prometheus Alertmanager webhook (`/ingestion/alert/**`) is covered too."*
- The check is **eager** (in `filter`, not in a body decorator), so body-less GETs are covered too (`:44-46`).

**Released, not pending.** Added by `4028b4a6` (2026-06-22, *"fix(ingestion-auth): authenticate the whole
/ingestion/** surface when the flag is on (#1740) (#1799)"*); `git tag --contains 4028b4a6` → **`0.29.0`**, the
latest published release (`git tag --sort=-creatordate | head -1` → `0.29.0`).

## The contradiction is live, on one page, 73 lines apart

`https://docs.opendatadiscovery.org/configuration-and-deployment/odd-platform` — both passages render on the
**same published page** (verified 2026-09-01 via `curl -sL` on the live site, not only in the repo):

> **:640-641 (correct)** — "By default (`auth.ingestion.filter.enabled=false`) it is unauthenticated… **From
> 0.29.0, `auth.ingestion.filter.enabled=true` requires a token** on this webhook like every other ingestion
> route ([ADR-0079]). Configure AlertManager to send a registered collector/datasource token via its
> `http_config`."

> **:713 (superseded)** — "the ingestion auth filter controlled by `auth.ingestion.filter.enabled` only guards
> `/ingestion/entities` (POST) — it does **not** cover `/ingestion/alert/alertmanager`. … **Toggling
> `auth.ingestion.filter.enabled` has no effect on this endpoint.**"

One tells the operator how to configure the token; the other tells them the toggle is useless. Both are on the
page an operator opens to configure exactly this.

## Why it survived — and the lesson for the fix

`DOC-479` (done, milestone 0.29.0) is the item that shipped ADR-0079's doc half. Its `affected_files` named
`enable-security/README.md`, `odd-platform.md`, `notifications.md`, `ingestion-filters.md` and the ADR — and
its post-merge Gate-8 verification checked that the **new** text renders. It never checked that the **old**
text was gone, so on `odd-platform.md` and `notifications.md` the corrected passage was *added* while the
superseded one stayed; and `metrics-ingestion.md`, `active-platform-features.md`, `odd-collector-profiler.md`
and `alerting.md` were never in scope at all.

This is presence-verification without absence-verification — the same residue class CTRIB-062's own C2b sweep
hit (two of six pages were found only by grepping the claim tree-wide *after* the per-file fix). **Close this
one with the tree-wide sweep, not a per-file edit**, and re-run the grep to zero residue before flipping it:

```
grep -rnE "only guards|only matches the exact path|only ever covers|until it lands|no effect on this endpoint" docs/
```

## Reader harm

Two directions, both real:

1. **Wasted work / false alarm.** An operator who already set `auth.ingestion.filter.enabled=true` reads
   `odd-platform.md:713` and concludes their AlertManager webhook is still wide open, then builds perimeter
   authentication they do not need — or files a bug against a control that works.
2. **The dangerous direction.** An operator weighing whether to turn the flag on reads *"Toggling
   `auth.ingestion.filter.enabled` has no effect on this endpoint"* and *"until it lands, perimeter
   authentication is the only protection"*, concludes the flag would not help their exposed surfaces, and
   **leaves it off** — keeping `/ingestion/metrics`, `/ingestion/alert/alertmanager` and the stats path open
   when one config line would have closed all three.

## Recommended fix direction

Adopt the `enable-security/README.md:51` wording as the canonical phrasing and propagate it: state the
default-off exposure, then *"from 0.29.0, `auth.ingestion.filter.enabled=true` requires a registered
collector/datasource token on this route (ADR-0079)"*, and link the ADR. Delete every "only guards
/ingestion/entities", "only ever covers", "until it lands" and "has no effect on this endpoint" clause.
`metrics-ingestion.md:78`'s prediction of *"a dedicated metrics-ingestion filter mirroring
`IngestionDataEntitiesFilter`"* should be corrected to what actually shipped — one filter over the whole
namespace — so a reader comparing the doc to the source finds the class they are told to look for.
