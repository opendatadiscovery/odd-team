## Description

Live `/user-owner-association` is silent on the History tab. Code reality (sidecar reference `OwnerAssociationsResolved.tsx:30-35`): the History tab consumes `GET /api/owner_association_request/activity` (UNGATED per F-074 — reachable to any authed user) and renders a paginated 7-column list (username / ownerName / role / provider / resolvedBy / status / resolvedAt). Read-only surface; status badge via `RequestStatus` component (silently falls back to 'pending' lowercase for unknown values — see PLT-041).

Operator-visible consequence: an admin auditing "who approved Alice's binding to Owner-X last Tuesday?" navigates Management → Associations → History by trial-and-error. The doc could have surfaced this in one sentence.

Audit incompleteness (F-174b, probe-needed): the History tab feeds from `owner_association_request_activity`, which is written by `OwnerAssociationRequestService` on APPROVE/DECLINE. Direct-bind events (F-172/Branch C) + unbind events (F-173) use a different controller (`/api/owners/mapping/*`) and likely do NOT emit to the activity table. This is a probe candidate (P-NNN-B per the findings file). Even with `@ActivityLog` annotation, DOC-GAP-192 captures that the `activity` table cannot physically capture rows without `data_entity_id NOT NULL`.
