## What

The `metadata_field` table supports soft-delete (it has a `deleted_at` column), but two places treat the column as if it did not exist, producing two operator-visible defects from one root cause:

1. **Permanent re-create block.** The unique indexes on `metadata_field` filter only on `origin`, not on `deleted_at`. So a soft-deleted custom-metadata field still occupies its name in the unique index. After an operator soft-deletes an INTERNAL custom-metadata field, attempting to create a new field with the **same name** fails with a unique-constraint violation - permanently - even though the original is "deleted" from the user's point of view. (The same holds for the EXTERNAL/typed index.)

2. **Ghost fields render on entity pages.** The query that loads a data entity's custom-metadata fields joins `metadata_field` without any `deleted_at IS NULL` predicate, so **soft-deleted fields still render** on the entity's metadata panel - ghosts that the operator believed they had removed.

The tell is that the *sibling* tables fixed exactly this in the same migration: when soft-delete was consolidated (V0_0_64), `tag`, `owner`, `role`, and `title` had their unique indexes dropped and re-created with `WHERE ... deleted_at IS NULL`. `metadata_field` got the `deleted_at` column added but its unique indexes were never updated - and its read query was never filtered.

## Where

**Locus 1 - unique index predicate is origin-only (never made soft-delete-aware).** `odd-platform-api/src/main/resources/db/migration/V0_0_1__init.sql:242-244`:

```sql
CREATE UNIQUE INDEX ix_unique_internal_name
    ON metadata_field USING btree (name)
    WHERE ((origin)::text = 'INTERNAL'::text);     -- no `AND deleted_at IS NULL`
```

(The companion index has the same gap - `V0_0_1__init.sql:238-240`, `ix_unique_external_name_type ... WHERE ((origin)::text <> 'INTERNAL'::text)`.)

`V0_0_64__remove_is_deleted_field.sql:41-42` adds the column but **does not** touch either index:

```sql
ALTER TABLE metadata_field
    ADD COLUMN IF NOT EXISTS deleted_at timestamp without time zone;
-- ...no DROP/CREATE of ix_unique_internal_name or ix_unique_external_name_type anywhere in this file
```

Contrast - the same migration DOES make the sibling tables' unique indexes soft-delete-aware (`V0_0_64__remove_is_deleted_field.sql`):

```sql
-- tag (lines 103-105):
DROP INDEX IF EXISTS tag_name_unique;
CREATE UNIQUE INDEX IF NOT EXISTS tag_name_unique ON tag (name) WHERE tag.deleted_at IS NULL;
-- owner (68-70), role (88-90), title (126-128): same DROP + re-CREATE WHERE ... deleted_at IS NULL
```

**Locus 2 - read query has no `deleted_at` filter.** `odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/repository/reactive/ReactiveMetadataFieldRepositoryImpl.java:112-121`:

```java
public Mono<List<MetadataDto>> getDtosByDataEntityId(final long dataEntityId) {
    final var query = DSL.select(METADATA_FIELD.fields())
        .select(METADATA_FIELD_VALUE.fields())
        .from(METADATA_FIELD_VALUE)
        .join(METADATA_FIELD).on(METADATA_FIELD.ID.eq(METADATA_FIELD_VALUE.METADATA_FIELD_ID))   // :116
        .where(METADATA_FIELD_VALUE.DATA_ENTITY_ID.eq(dataEntityId));                              // :117 - no deleted_at predicate
    return jooqReactiveOperations.flux(query)
        .map(this::metadataDto)
        .collectList();
}
```

## Why it matters

Both manifestations are operator-visible and both are **loud** in the sense that the operator sees a wrong result:

- **Re-create block (Locus 1):** an operator who deletes a custom-metadata field and tries to recreate it under the same name gets a hard failure they cannot work around (the name is taken forever by a row they can no longer see). This is a permanent, irrecoverable-via-UI state - the closest thing to data-corruption here without being data loss.
- **Ghost render (Locus 2):** soft-deleted fields keep appearing on entity metadata panels, so "delete" does not visibly remove the field - undermining trust in the delete action and cluttering the entity view.

Affects any operator using custom (especially INTERNAL) metadata fields with delete+recreate workflows. No security/data-loss framing, but it is a correctness defect in the soft-delete contract that the rest of the schema already honours. Medium.

## Suggested fix

Treat `deleted_at` as part of the uniqueness and read contracts, matching the sibling tables fixed in V0_0_64:

1. New forward migration: drop and re-create both `metadata_field` unique indexes with the soft-delete predicate appended, e.g.
   `CREATE UNIQUE INDEX ix_unique_internal_name ON metadata_field (name) WHERE (origin = 'INTERNAL' AND deleted_at IS NULL);`
   and the analogous `AND deleted_at IS NULL` on `ix_unique_external_name_type`. (Audit for pre-existing soft-deleted name collisions before re-creating the unique index.)
2. Add `.and(METADATA_FIELD.DELETED_AT.isNull())` to the join/where in `getDtosByDataEntityId` (and review any other `metadata_field` reads that should exclude soft-deleted rows). Open to alternatives on whether the predicate sits on the join vs. the where.

## How discovered

Surfaced in the 2026-06-08 feature-reflection contradiction harvest - `lineage/odd-platform/harvest/2026-06-08-contradiction-harvest.md`. Three independent feature reflections converged on the same root cause (the `metadata_field` soft-delete gap), which is why this is filed as one clustered issue rather than three:

- F-046 (`lineage/odd-platform/feature-reflections/detail/F-046.yaml`)
- F-013 (`lineage/odd-platform/feature-reflections/detail/F-013.yaml`)
- F-123 (`lineage/odd-platform/feature-reflections/detail/F-123.yaml`)

Confirmed by reading V0_0_64 directly: the migration adds `metadata_field.deleted_at` but, unlike `tag`/`owner`/`role`/`title` in the very same file, never rebuilds the `metadata_field` unique indexes to be soft-delete-aware - and the read query was never filtered.
