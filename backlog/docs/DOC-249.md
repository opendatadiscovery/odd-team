## Description

`PolicyServiceImpl.java:102-107` `getCurrentUserPolicies` is invoked from `ManagementPermissionExtractor.java:33` + `AbstractContextualPermissionExtractor` on EVERY authorized HTTP request. Cost per call: 2 JOIN roundtrips (5-table JOIN at `ReactiveUserOwnerMappingRepositoryImpl` + 2-table JOIN at `ReactivePolicyRepositoryImpl`). NO request-scoped cache, NO user-scoped cache. For a busy platform with N req/s this is **2N JOINs/s for permission resolution alone** — the platform's RBAC stack has a structural per-request cost.

The Policies page is silent on this performance characteristic; operators sizing the Postgres connection pool, JVM, or Postgres CPU budget based on application-logic-only req/s underprovision.

## Acceptance Criteria

- [ ] Policies page (`enable-security/authorization/policies.md`) gains a `## Performance characteristics` sub-section covering:
  - **Per-request authorization cost**: every authenticated request requires a Policy resolution. Cost is 2 JOIN roundtrips against Postgres (5-table user→owner→policy chain + 2-table policy detail), executed via reactive R2DBC. There is no in-process request-scoped or user-scoped cache today.
  - **Throughput implication**: for a platform receiving N authenticated requests/sec, the authorization hot-path generates ~2N Postgres queries/sec — over and above the application-logic queries. Size the Postgres connection pool (`spring.r2dbc.pool.max-size`) and database CPU accordingly. A practical sizing heuristic: target 4-5 concurrent JOIN queries per peak-authenticated-request-rate, plus headroom for application-logic queries.
  - **Per-request cache opportunity (operator-side mitigation today)**: none — there is no operator-tunable knob today.
  - **Track upstream**: PLT-063 — add a request-scoped cache for `getCurrentUserPolicies`.
