## What

The platform UI bootstraps i18next at `odd-platform-ui/src/locales/i18n.ts:30` with:

```ts
fallbackLng: ['en', 'es', 'ch', 'fr', 'ua', 'hy'],
```

i18next walks this array **in order** on a missing-key lookup. A user whose active locale is French and is hitting a key that is missing from `fr.json` will try `es.json` FIRST (Spanish), then `ch.json` (Chinese), then `fr.json` (already missed), then `ua.json` (Ukrainian), then `hy.json` (Armenian), and finally `en.json` (English).

For ANY key present in `es.json` or `ch.json` but absent in `fr.json` / `ua.json` / `hy.json`, the user sees **Spanish or Chinese strings mid-page** in their otherwise-French/Ukrainian/Armenian UI.

## Where

- `odd-platform-ui/src/locales/i18n.ts:30` - the `fallbackLng` array literal that ships to production.
- `odd-platform-ui/src/locales/translations/{en,es,ch,fr,ua,hy}.json` - the six locale files; partial-coverage keys are commonplace today (per finding F-043a - DOC-171 - there are 12+ missing keys including top-level navigation tabs).

## Why it matters

Cross-locale surprise. The intent is almost certainly *"fall back to English when the active locale is missing a key"*. The current array shape is what i18next calls a **chain** - every entry in the array is tried in order - not a **single fallback**. The contributor very plausibly mistook `fallbackLng` for `supportedLngs` (which IS a chain of which-locales-exist-at-all; `fallbackLng` is the lookup-fallback-chain for missing-key recovery).

Severity is medium because (a) the bug is fully exposed only when a user picks a non-English locale AND lands on a partial-coverage key - both common today but not catastrophic; (b) the fix is a one-line change with no behavioural risk; (c) until the fix lands, the workaround for English-locale users is invisible (they don't fall through at all).

## Suggested fix

```ts
// odd-platform-ui/src/locales/i18n.ts:30
- fallbackLng: ['en', 'es', 'ch', 'fr', 'ua', 'hy'],
+ fallbackLng: 'en',
```

`fallbackLng: 'en'` matches the documented i18next pattern for *"fall back to English when a key is missing"*. The list-of-locales semantics belong on `supportedLngs`, which is a separate i18next option for input-validation of the user-selected locale and has no effect on missing-key fallback resolution.

## How discovered

Surfaced during the Mode B run of the `docs/coverage/undocumented-features` scanner on 2026-05-27 (substrate `F-043` - Multilingual UI). The scanner's primary-source verification of `i18n.ts` flagged the array shape; the cross-locale-surprise consequence comes from the substrate's facet enumeration on F-043.

## Doc-side handling

The doc-side response is paired with **DOC-171** (the multilingual UI feature page that does not yet exist). DOC-171's "Known caveats" section names the cross-locale-fallback behaviour explicitly until this code fix lands and ships in a release. After the fix lands, the doc caveat is removed in a follow-up.
