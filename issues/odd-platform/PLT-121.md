## What

The global Alerts page tab labelled **"All"** shows only **OPEN** alerts. `ReactiveAlertRepositoryImpl.listAllWithStatusOpen` hard-filters `ALERT.STATUS = OPEN`, and the sibling My Objects and Dependents queries carry the identical hard-coded `STATUS=OPEN` filter - so `RESOLVED` and `RESOLVED_AUTOMATICALLY` alerts never appear on **any** of the three global tabs. The data is not gone (a single entity's Alerts tab uses `getAlertsByDataEntityId`, which has no status filter), but the global page cannot surface it: there is no `status` query parameter on `getAllAlerts` / `getAssociatedUserAlerts` / `getDependentEntitiesAlerts`, and `ALERT.STATUS` is an available-but-unused column on the list API. This is the same Category-B name-vs-behaviour class as LSN-019 (`TagController.listMostPopular`).

This is **distinct from PLT-050** (the Alerts UX cluster: hardcoded size-30, no filter UI, no bulk-resolve, default-tab redirect, hidden-but-navigable tabs), which does not cover the "All"-label name-drift or the missing status filter. The DOC side is already corrected (the live alerting page documents the OPEN-only behaviour; DOC-291 done). The code-side relabel / status-param remains.

## User-facing impact

WHO: a steward / any user on the global Alerts page. WHAT THEY DO: open the Alerts page and look at the tab labelled "All". WHAT THEY OBSERVE (verified by FE/BE trace 2026-06-10):

- The "All" tab (label literally `t('All')`, `AlertsTabs.tsx:22`) lists only OPEN alerts: `getAllAlerts` (`AlertController.java:36-41`) -> `listAll` -> `listAllWithStatusOpen` (`ReactiveAlertRepositoryImpl.java:142-145`) hard-filters `ALERT.STATUS = OPEN`. The sibling My Objects (`listByOwner`, filter at `:166`) and Dependents (`listDependentObjectsAlerts`, filter at `:230`) queries carry the identical `STATUS = OPEN` filter, so RESOLVED / RESOLVED_AUTOMATICALLY alerts appear on NONE of the three global tabs.
- There is no `status` query parameter on `getAllAlerts` / `getAssociatedUserAlerts` / `getDependentEntitiesAlerts` (`AlertController.java:36-57`), so the FE cannot request resolved alerts on the global page.
- The badge agrees with the list (both OPEN-only): the "All" hint is `totals.total` (`AlertsTabs.tsx:23`), fed by `getAlertTotals` -> `countAlertsWithStatusOpen`. So there is no badge-vs-list contradiction here (unlike PLT-167) - the defect is purely that the tab labelled "All" lists only the OPEN subset.
- A resolved alert is still viewable, but only via the specific entity's Alerts tab: `getAlertsByDataEntityId` (`:182-199`) applies NO status filter. A steward who resolved an alert cannot find it on the global Alerts page and reasonably concludes it was purged - they must know which entity to open.

All load-bearing facts are pure code structure (a hard `WHERE STATUS=OPEN` with no parameter to change it, plus a literal `'All'` label), fully settled by FE+BE trace; pre-existing probe P-194 pins the same drift. The UI label "All" actively misrepresents the population it shows.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: add an optional `status` query param on `getAllAlerts` / `getAssociatedUserAlerts` / `getDependentEntitiesAlerts` (`AlertController.java:36-57`) and plumb it to `ReactiveAlertRepositoryImpl.listAllWithStatusOpen` (drop the hard-coded `eq(OPEN)`, default to OPEN); **or** relabel the tab from "All" to "Open" to match the behaviour. DOC side already corrected (DOC-291).
