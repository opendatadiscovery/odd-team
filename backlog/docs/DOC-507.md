# DOC-507 — two reader traps in `developer-guides/**`

## 1. The Swagger UI and the OpenAPI JSON are served at each other's conventional paths, and the page never says so

**Failure shape: reader-flow defect (a counter-intuitive fact stated without the disambiguation that makes it readable).**

`developer-guides/api-reference.md` tells the reader two things, ~10 lines apart:

> **Swagger UI Access**: The Swagger UI can be accessed on your deployed ODD platform at
> `{platform-base-url}/api/v3/api-docs`.

> … the raw OpenAPI JSON is served at `{platform-base-url}/api/v3/swagger-ui.html` (per-definition documents
> at `/platform-api` and `/ingestion-api`).

**Both sentences are correct.** Verified against `odd-platform-api/src/main/resources/application.yml`:

```yaml
springdoc:
  api-docs:
    path: /api/v3/swagger-ui.html     # the JSON document root
  swagger-ui:
    path: /api/v3/api-docs            # the interactive UI
```

The platform deliberately swaps the two springdoc defaults. The platform's own regression test says so in as
many words (`OpenApiDocsContractTest`: *"Note the deliberately swapped serving paths (application.yml):
`springdoc.api-docs.path = /api/v3/swagger-ui.html` is the JSON document root."*) — but the **published page
does not**.

**Why it matters.** Every reader who knows springdoc (i.e. the audience of a developer guide) will read
`/api/v3/api-docs` as "the JSON" and `swagger-ui.html` as "the UI", conclude the page has a copy-paste error,
and swap them back — landing on an HTML shell when they wanted a machine-readable spec to generate a client
from. The page is accurate and still misleads, which is the worst combination: nothing to grep for, and no
error message when the reader guesses.

**Recommended fix.** One clause where the paths are first introduced — that ODD deliberately inverts the two
springdoc defaults, so `/api/v3/api-docs` is the **UI** and `/api/v3/swagger-ui.html` is the **JSON**. A small
two-row table (`what you want` → `path`) reads better than prose here.

## 2. Two pages promise a complete repository inventory; the inventory is 16 of 35

**Failure shape: half-finished narrative / false completeness claim.**

* `developer-guides/how-to-contribute.md:13` — *"OpenDataDiscovery GitHub organization has over 20 repositories
  … The [GitHub organization overview](github-organization-overview.md) lists **every repository** with a
  one-line summary."*
* `integrations/README.md` (Where to next) — *"**Existing repository overview** — [GitHub organization
  overview] lists **every ODD repo** with one-line summaries."*

`github-organization-overview.md` lists **16** repositories. The org has **35** public repositories (verified
2026-09-01 via `GET /orgs/opendatadiscovery` → `public_repos: 35`). "Over 20" is true; "lists every
repository" is not.

**Why it matters.** A contributor looking for the repo that owns a surface (say `odd-collector-sdk`, or the
Helm `charts` sibling) reads the overview, does not find it, and concludes the repo does not exist — because
the page told them the list was exhaustive. A partial list that says it is partial costs nothing; a partial
list that claims completeness sends people to the wrong conclusion.

**Recommended fix.** Pick one and make the page honest either way:

* **Either** re-scope the two claim sentences to what the page actually is — "the repositories a contributor
  is most likely to touch" — and add a line pointing at
  <https://github.com/orgs/opendatadiscovery/repositories> for the full list; **or**
* complete the inventory (35 entries is a large page and most of the tail is archived / example repos, so the
  re-scope is the better-value option).

The overview page itself should also say which it is in its own lead, so the next editor does not re-introduce
the completeness claim.
