  - **Evidence**:
    - **The principal-aware fork** (per sidecar primary source — `RoleServiceImpl.java:40-47` referenced by the controller-class sidecar): the service tier branches on the caller's ADMIN status (resolved via `AuthIdentityProvider.getCurrentUser` → user's role bindings → ADMIN check); ADMIN callers fall through to `roleRepository.listDto(page, size, query)` (the paginated DB query); non-ADMIN callers fall through to `filterUserRoles(currentUserRoles, query)` — an in-memory filter over the user's CURRENTLY-ATTACHED role set (typically 1-3 items per user), with the page + size parameters discarded and `hasNext=false` returned. The contract documented on the spec layer ("paginated list of roles") is honored only for ADMIN.
    - **The page/size discard for non-ADMIN**: per sidecar's `name_behavior_pairs[getRolesList]` analysis, a non-ADMIN caller passing `?page=2&size=20` does NOT receive page 2; they receive their full attached-role list (in-memory filtered by `query`) regardless of `page` / `size`. There is no `416 Requested Range Not Satisfiable` or `400 Bad Request` to surface the contract divergence; the response is simply a 200 with the always-one-page payload.
    - **The OpenAPI contract claim**: per `openapi.yaml:3601-3679` (per sidecar primary source for the RoleApi interface): the spec declares `GET /api/roles` with `page: integer required`, `size: integer required`, `query: string optional` parameters; the response is a `RoleList` shape `{items: Role[], pageInfo: PageInfo}`. The contract implies pagination uniformly; it does not signal "behaviour varies by caller role". A typed SDK client generated from the spec will pass `page` and `size` to every call; the SDK has no mechanism to detect that the server discards them for non-ADMIN callers.
    - **The UI-side breakage scenario**: an operator authors a custom React component that paginates `GET /api/roles` for the platform's Management UI (replacing or extending the seeded RolesList — per batch Q sibling sidecar). The component renders correctly when the operator is logged in as ADMIN (test environment); ships to production; non-ADMIN users navigating to the Management/Roles tab see "1-3 items, page indicator says 1 of 1" and assume the platform legitimately only has those roles. The platform's actual role catalog (which may have dozens of roles) is silently invisible to them. The bug is invisible from server logs (200 success) and from client logs (a valid paginated response is returned, just with fewer items than expected).
    - **The PolicyController symmetric pattern** (per sidecar `coherence_check.strengthens[batch-E]`): `PolicyServiceImpl.getPolicyList` exhibits the same fork — ADMIN callers see the full paginated catalog; non-ADMIN callers see policies bound to the roles they hold (filtered in-memory). This was surfaced in batch E + I as a controller-method-tier finding but not previously cataloged as a doc-product gap.
    - **The security framing**: per sidecar `implicit_adrs`, the principal-aware fork is the platform's deliberate "read-collaborative posture" applied to RBAC reads — users see roles + policies they are themselves bound to, hiding the platform-wide catalog from non-ADMIN callers (preventing privilege enumeration). The intent is correct (per implicit_adr[2] in the sidecar). The DOC-PRODUCT gap is that the intent is encoded behaviourally without operator-facing documentation:
      - operators reading `/authorization/roles` do not learn that `GET /api/roles` returns different content per caller;
      - third-party integrators reading the spec do not learn that pagination is conditional;
      - UI authors testing as ADMIN do not learn that non-ADMIN renders look different.
    - **Live doc verification** (per sidecar `inferred_docs[0]` WebFetch 2026-05-25 status 200): `/configuration-and-deployment/enable-security/authorization/roles` — the live Roles page describes the role concept and the two predefined roles (USER / ADMIN); it does NOT mention: (a) the GET /api/roles principal-aware fork; (b) the pagination asymmetry between ADMIN and non-ADMIN callers; (c) the "you see only the roles you hold" non-ADMIN visibility model; (d) the implicit read-collaborative posture intent.
    - **The composition with DOC-GAP-082 (DISABLED bypass)**: under `auth.type=DISABLED`, the dummyOwner fallback per the IdentityController returns `identity.permissions = [all 70+ Permission values]` (per the sibling NEW DOC-GAP-273/274 + DOC-GAP-082 META). Under DISABLED, the `getCurrentUser()` chain emits empty BEFORE the ADMIN check is reached; the non-ADMIN branch is taken; the response is `Flux.empty()` (no attached roles can be resolved against the empty SecurityContext) — operators see an EMPTY response under DISABLED while the UI simultaneously shows `identity.permissions = [all]`. The non-ADMIN-vs-ADMIN fork in this finding compounds the DOC-GAP-187 UI-vs-API asymmetry shape — but at the LIST-READ surface rather than the MUTATION surface.
  - **Proposed doc action**: **Three-part action — doc-side primary + spec-side annotation + cross-link to the Policies symmetric page**.
    1. **Doc-side PRIMARY — `configuration-and-deployment/enable-security/authorization/roles.md`**: add a "Read posture" sub-section: "**The role-list endpoint returns different content depending on the caller's role.** `GET /api/roles` is open to any authenticated user (no `ROLE_READ` permission gate), but the response content is conditioned on the caller's ADMIN status:
       - **ADMIN callers** (users bound to a role with `MANAGEMENT/ALL` permissions, or under `auth.type=LOGIN_FORM` where every user is ADMIN): receive the paginated full catalog. The `page` and `size` query parameters are honored.
       - **Non-ADMIN callers**: receive only the roles they themselves are bound to (typically 1-3 items per user). The `page` and `size` query parameters are IGNORED; the response is a single-page `RoleList` with `hasNext=false`.
       This is the platform's read-collaborative posture: non-ADMIN users see their own role bindings only, not the platform-wide catalog. **Implication for client authors**: any UI paginator or third-party SDK consuming this endpoint must either (a) restrict the feature to ADMIN-known callers, or (b) tolerate the absence of pagination for non-ADMIN responses (treat `hasNext=false` as authoritative regardless of the requested page count). The same posture applies to [Policies](policies.md) — `GET /api/policies` exhibits the symmetric fork."
