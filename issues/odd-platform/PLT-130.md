## What

`AzureLogoutSuccessHandler` calls `URI.create(provider.getLogoutUri())` with **no null-guard**, and the OAuth2 props validator checks `clientId` + `provider` but **not** `logoutUri`. So an Azure-SSO operator who omits the optional-looking `logout-uri` boots successfully and then hits an NPE → HTTP 500 on the **first logout attempt** — the failure appears only at runtime, not at boot. The sibling `CognitoLogoutSuccessHandler` carries the `StringUtils.isEmpty` early-return guard; Azure does not. Separately, the handler invalidates only the local Spring `WebSession` — no token is revoked at Azure, so the IdP session stays valid until its natural TTL.

This is **distinct from PLT-075** (logout-handler open-redirect: no base-url allowlist across all 5 handlers) — a different defect. The Azure NPE-on-null-logoutUri + no-revoke is not tracked by PLT-075.

## Impact

(a) An Azure operator following the docs but omitting the optional-looking `logout-uri` ships a deployment where every Logout click returns a 500 — users cannot log out at all, and the failure surfaces only at runtime. (b) Even when `logout-uri` is set, the local-only logout means a user on a shared workstation who clicks Logout still has a live Azure session — a real security-posture gap the UI gives no signal about.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: add the `StringUtils.isEmpty` early-return guard at `AzureLogoutSuccessHandler.java:39` matching Cognito (`CognitoLogoutSuccessHandler.java:33-35`), and add `logoutUri` to `ODDOAuth2Properties.validate` when `provider=azure`; document the no-token-revoke caveat. Distinct from PLT-075 (logout open-redirect).
