## Description

While authoring the ingestion-grade dataset-pipeline e2e (**IT-145**), the Phase C deletion
step measured ODD's behavior when a source object disappears and the pull collector re-runs:

- Seed: a `categories` table in the source postgres → ingested as a dataset.
- Mutate: `DROP TABLE categories` in the source.
- Re-collect: restart the real `odd-collector` (forces an immediate fresh pull; the next
  `DataEntityList` no longer contains `categories`).
- **Observed:** the `categories` dataset **PERSISTS** in ODD — it still resolves
  (`GET /api/dataentities/{id}` → 200), `status` stays `UNASSIGNED`, and `hollow` is false.
  It is neither removed nor flagged deleted/stale.

So a pull re-ingest does **not** reconcile **entity-level** source deletions. For an operator
this means: **dropping (or renaming) a source table leaves a stale dataset in the ODD catalog
indefinitely** — search, lineage, and the catalog keep showing an object that no longer exists
upstream. That is exactly the class of silent drift the workspace exists to surface (cf.
`retrospectives/LSN-001`, `LSN-002` — operators trusting the catalog off a cliff).

This is **characterized, not yet classified.** IT-145 pins the *current* behavior (the test
asserts persistence and flips the day ODD gains deletion reconciliation). What is NOT yet
established — and must be, per Gate 9, before any operator-facing claim — is whether this is:

1. **Intended** (ODD deliberately never auto-removes on absence, to protect manual curation /
   history) → then the deliverable is a clear **operator caveat** in the docs + possibly a note
   on how stale entities *are* meant to be cleaned up (a housekeeping TTL? a manual delete? an
   explicit collector deletion signal?); or
2. **A gap** (the platform should reconcile but doesn't on the pull path) → then it is platform
   refactoring scope (NOT an ADR — per the ADR-vs-refactoring wisdom test), and IT-145's pin
   becomes the regression guard for the fix.
