## What

Collector tokens (the 40-char authentication secret used by every deployed ODD collector to POST to `/ingestion/*`) are stored verbatim plaintext in the `TOKEN.VALUE` column. Every DB-side reader (pg_dump, replica, backup, jOOQ log leak, application-log leak) recovers every live credential. The validation path uses plaintext SQL equality on the read side AND non-constant-time `.equals` on the application side.

Four facets compound:
1. **No hashing column.** `V0_0_28__add_token.sql:4` declares `value varchar(40) NOT NULL` - no `value_hash`, no `salt`. `TokenGeneratorImpl.java:34-42` writes `RandomStringUtils.randomAlphanumeric(40)` verbatim INSERT.
2. **Plaintext SQL match.** `ReactiveCollectorRepositoryImpl.java:94` does `TOKEN.VALUE.eq(token)` - the query embeds the operator-supplied token plaintext.
3. **Non-constant-time application equality.** `IngestionDataEntitiesFilter.java:55-58` does `tokenPojo.getValue().equals(token)` - Java `String.equals` short-circuits on first byte mismatch. A network attacker with timing measurement can extract the token byte-by-byte.
4. **No UNIQUE on `TOKEN.VALUE`.** Two TOKEN rows MAY share the same value (no UNIQUE constraint). Plus soft-deleted Collectors leave their TOKEN row orphaned (TOKEN has no `deleted_at` column) - historical credentials accumulate.

## Why it matters

Operators running PgBackup / pgaudit / Datadog DB observability / read-replica pipelines have production credentials in their logs and backup archives. A compromised backup, a leaked replica snapshot, a careless `pg_dump` artefact dropped on a Slack channel - any of these immediately exposes every live collector's credential. Recovery requires rotating every token AND treating every backup-history reader as a compromise event.

The non-constant-time application equality (facet 3) is the lower-magnitude but real concern - extractable over slow networks with millions of attempts, but real attackers patient enough to do this exist when the target is a data catalog with operator-significant data.

Severity HIGH because:
- The credentials are operator-significant (each gates `/ingestion/*` POSTs that write to the data catalog)
- Discovery does not require attacker reach to the platform - backup pipelines + replica readers are sufficient
- The platform actively encourages multi-instance / multi-replica deployments (notifications, datacollaboration, partition coordination) - each replica is another credential-recovery surface
- Industry-standard fix (hash at rest, validate by hash) is well-trodden

## Suggested fix

Standard secret-handling migration. Lifts a one-time UX cost (existing operators must re-issue tokens) for permanent hardening.

**Schema migration:**

```sql
-- V0_0_NEW__hash_token.sql
ALTER TABLE TOKEN ADD COLUMN VALUE_HASH VARCHAR(255);
-- VALUE_HASH stores bcrypt or argon2 of the token value
-- value_hash NULL is the "legacy plaintext" state during migration
```

**Generator path:**

```java
// TokenGeneratorImpl.java
public Mono<TokenPojo> generateToken() {
    final String value = RandomStringUtils.randomAlphanumeric(40);
    final String hash = bcrypt.hash(value);                  // bcrypt 10-12 rounds
    final TokenPojo token = new TokenPojo();
    token.setValueHash(hash);
    // NOTE: value is NOT persisted; returned ONLY in the one-shot response body
    return tokenRepository.insert(token)
        .map(saved -> { saved.setValue(value); return saved; });   // attach for one-shot reveal
}
```

**Validation paths (filter + repository):**

```java
// IngestionDataEntitiesFilter.java
- if (!tokenPojo.getValue().equals(token)) { ... }
+ if (!bcrypt.verify(token, tokenPojo.getValueHash())) { ... }   // constant-time

// ReactiveCollectorRepositoryImpl.java
// remove the TOKEN.VALUE.eq(token) lookup; instead:
// 1. fetch ALL active tokens (small set, single-digit-K typical)
// 2. iterate, bcrypt.verify each - first match wins
// OR (better for scale):
// 1. store a non-secret prefix-hash + the bcrypt hash; look up by prefix-hash, verify by bcrypt
```

**Migration of existing operators:**

- One-shot bulk-migration script reads every existing plaintext `TOKEN.VALUE`, computes `VALUE_HASH`, writes the hash, then NULLs out `TOKEN.VALUE`.
- Boot-time check: if any `TOKEN.VALUE IS NOT NULL`, log WARN; fail-fast if a future flag is enabled.

**UI one-shot reveal:**

- `TokenGenerationModal` shows the plaintext value once with copy-to-clipboard + "you will not see this token again" warning (Stripe / GitHub PAT pattern).

**Defaults migration timing:**

- 1 minor version: dual-write (plaintext + hash) so existing collectors keep working.
- Next minor version: drop the plaintext column entirely.
