## Description

The live published [Data Modelling](https://docs.opendatadiscovery.org/data-modelling) page's **UI entry points** table says (`data-modelling.md:21-22`):

- `/data-modelling/query-examples` — "RBAC-gated by `QUERY_EXAMPLE_CREATE`."
- `/data-modelling/query-examples/{id}` — "RBAC-gated by `QUERY_EXAMPLE_UPDATE` + `QUERY_EXAMPLE_DELETE`."

This corrects a wrong claim on a live page. The route mounts are **not** permission-guarded: the list view and the per-example details view render for any authenticated user. The named permissions gate only the **Add** button (list page) and the **edit/delete** actions (details page) — not read access. An operator reading the intro table will believe `QUERY_EXAMPLE_CREATE` is required to even view the list, and may grant that write permission to read-only roles to "unlock the page" — over-provisioning a mutation right to satisfy a read need that has no gate. The already-corrected child page contradicts this intro table (see Context).

Canonical code truth (verified this session by reading the files):
- `DataModellingRoutes.tsx:17-39` mounts both routes inside `WithPermissionsProvider` with `allowedPermissions=[QUERY_EXAMPLE_CREATE]` (list) / `[QUERY_EXAMPLE_UPDATE, QUERY_EXAMPLE_DELETE]` (details). But `WithPermissionsProvider` / `PermissionProvider` do **not** block rendering — `PermissionProvider.tsx:39-43` unconditionally renders its children/`render()` and merely supplies `isAllowedTo` / `getHasAccessTo` via React context. `allowedPermissions` only scopes *which* permissions descendant `WithPermissions` components are allowed to check; it is not a route guard.
- The actual gating is per-affordance, inside the rendered pages: `QueryExamples.tsx:36` wraps the Add button in `<WithPermissions permissionTo={QUERY_EXAMPLE_CREATE}>`; `QueryExampleDetailsContainerActions.tsx:40,53` wrap edit/delete in `<WithPermissions permissionTo={QUERY_EXAMPLE_UPDATE}>` / `{QUERY_EXAMPLE_DELETE}>`. `WithPermissions.tsx:27-29` returns `null` when the permission is absent — hiding the control, not the page.
- Server-side confirms read-open: the already-published child page states all read/search/listing endpoints fall through to the "any authenticated user" rule (`query-examples.md:97-99`).
