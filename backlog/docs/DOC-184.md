## Description

The live GenAI page (per DOC-045, shipped 2026-04-30) DOES disclose the **platform-to-EXTERNAL** posture: no authentication to the LLM provider, no retry, no prompt modification, and the LSN-002-style misconfiguration warning that *"the platform accepts the misconfiguration at startup and fails at first request"* + *"setting `0` means immediate timeout."* The page is silent on the **platform-to-USER** posture — the surface operators actually need to harden when enabling GenAI. Two facets:

**Caveat 1 — Platform-to-user posture is wide open (F-039a).** `GenAIController.java:13-24` carries no `@PreAuthorize`, does not reference `ServerWebExchange`, and `SecurityConstants.java:98-355` has **no `/api/genai/**` entry**. The endpoint falls through to global `.authenticated()` under LOGIN_FORM/OAUTH2/LDAP, and to **anonymous** under `auth.type=DISABLED`. Operator-visible:
- **any authenticated user (or any anonymous caller under DISABLED) can drive arbitrary cost on the operator's external LLM account** — the platform does not rate-limit, throttle, or enforce per-user quotas
- no in-platform record of who asked what (no audit log; the activity-feed schema-rooted constraint per F-021a means this can't even be added without a schema change)
- no PII scrubber — entity owner names, lineage entity names, free-form chat content flow verbatim to the external LLM
- no request-body size cap — large free-form prompts pass through unbounded
- under DISABLED, no per-user attribution at all

An operator enabling GenAI sees the doc disclose external-side posture and reasonably assumes platform side IS gated. Reality: the doc tells half the story.

**Caveat 2 — `genai.url` is operator-config SSRF surface (F-039b).** `GenAIProperties.java:10` declares `String url` with no `@URL` constraint, no `@Pattern` scheme/host allowlist. Operator (or attacker with config-write access) can point outbound POST at any reachable URL **including the platform's own internal network**. The WebClient runs in the platform's JVM — requests originate from the platform's egress identity (private subnets, internal services, cloud-metadata endpoints). Classic config-driven SSRF.

- [ ] The GenAI page gains a new **"## Platform-to-user security posture"** sub-section, distinct from the existing "Platform-to-external" coverage. Frame it as a complement to the existing external-side disclosure — *"The previous section described the platform's posture toward the external LLM. This section describes the platform's posture toward the user calling the platform."*
- [ ] **Caveat 1 framing** enumerates the five sub-gaps (no authz beyond authenticated / no rate-limit / no audit / no PII redaction / no body-size cap) as a bulleted operator caveat list. Operator mitigation today: place a rate-limiting proxy in front of `/api/genai/**`; do not enable GenAI under `auth.type=DISABLED`; restrict who is `.authenticated()` if the platform is fronted by a permissive auth mode; treat the platform's external LLM bill as user-driven cost. Cross-link to PLT-020.
- [ ] **Caveat 2 framing** names the SSRF surface explicitly: *"The `genai.url` configuration accepts any URL with any scheme. Operators with config write-access (or attackers who reach the config) can point GenAI outbound at the platform's own internal network — including cloud metadata endpoints. Treat `genai.url` as a privileged config value and restrict who can modify it."* Cross-link to PLT-020.
- [ ] The existing "Platform-to-external" coverage on the page is **preserved** (do not replace; this item extends).
- [ ] `Consumer-read:` footer cites `GenAIController.java:13-24` (no annotations), `SecurityConstants.java:98-355` (grep for `/api/genai` returns zero), `GenAIProperties.java:10` (`String url` no constraint).
