## What

A `data_entity.exclude_from_search` flag toggled to `true` reasonably hides the entity from operator-visible listing surfaces - that is the operator-facing contract implied by the column name, the UI toggle, and the doc page (per WebFetch 2026-05-27 of `docs.opendatadiscovery.org/features/data-discovery/catalog-overview`). In the current implementation the flag affects **full-text search only** - 9 distinct list-shape methods all share a SQL helper that **does not apply the `EXCLUDE_FROM_SEARCH` predicate**.

`ReactiveDataEntityRepositoryImpl.cteDataEntitySelect` (lines 909-939) applies:
- Line 916: `addSoftDeleteFilter`
- Line 918: `DATA_ENTITY.HOLLOW.isFalse()`

It does NOT apply `DATA_ENTITY.EXCLUDE_FROM_SEARCH.isFalse()` (or equivalent). The helper feeds 9 consumer methods, every one of them affected:

1. `listPopular` (line 633)
2. `listByOwner` (lines 526-527 - My Objects)
3. `listByTerm` (By-Term lists)
4. `getDEGExperimentRuns`
5. `getDimensions(id)`
6. `getDimensions(oddrns)`
7. `getDimensions(ids)`
8. `getDetails(id)` - direct entity-detail GET
9. `getQuerySuggestions`

The filter IS applied at `findByState` (FTS search; `JooqFTSHelper.resultFacetStateConditions:149`) and `getDataEntityDefaultConditions:974` (count/statistics paths) - so the flag works for the FTS search box but leaks via every other listing surface and via the entity-detail GET.

## How to reproduce

1. Create or ingest two data entities, A and B.
2. Set `exclude_from_search = true` on entity A (via the platform UI toggle OR direct DB UPDATE on `data_entity.exclude_from_search`).
3. Observe expected behaviour: entity A is hidden from operator-visible listings.
4. Observe actual behaviour:
   - `GET /api/dataentities/popular` returns A in the response.
   - `GET /api/dataentities/my` (with A's owner) returns A.
   - `GET /api/dataentities/{A.id}` returns A's full details.
   - `GET /api/dataentities/byTerm/{term.id}` (where A is term-linked) returns A.
   - `GET /api/dataentities/search?query=...` (FTS) correctly omits A - the only surface where the flag works.

## Suggested fix

**Option A (recommended) - lift the predicate into the helper.** Add `.and(DATA_ENTITY.EXCLUDE_FROM_SEARCH.isFalse())` to `cteDataEntitySelect` (line 918 area) so all 9 consumers inherit the filter automatically. ONE LINE of code change, LARGE leverage.

**Option B - opt-out per-consumer**. If a future surface intentionally wants to surface hidden entities (e.g. an admin "show all" view), pass an `IncludeExcluded` flag through the helper signature; default `false`.

The fix should ship with a CHANGELOG entry stating the behaviour change so operators relying on the (currently broken) leak don't get surprised - though anyone today following the doc page's framing expects Option A's behaviour.

## Operator impact

- **Multi-team deployments** relying on `exclude_from_search` to hide staging / internal entities discover them leaking via `/api/dataentities/popular`, `/api/dataentities/my`, term-linked lists, DEG-experiment runs, and direct GET-by-id.
- **Compliance-driven hide-from-discovery policies** are silently false for 9 of 11 catalog surfaces.
- **Under `auth.type=DISABLED`** every list endpoint is anonymous - the leak amplifies to anonymous-readable.
