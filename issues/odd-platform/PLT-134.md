## What

`GET /api/dataentities/{id}/alerts` has no pagination bounds at any layer: the controller params are bare `Integer page` / `Integer size` with no `@Min`/`@Max`, the OpenAPI `PageParam`/`SizeParam` carry no `minimum:`/`maximum:`, and the repository computes `OFFSET = (page-1)*size` with no clamp. `size=1000000` triggers a single jOOQ query + in-memory `AlertList` mapping bounded only by Postgres/network buffers; `page=0` produces a negative `OFFSET` that Postgres rejects with "OFFSET must not be negative" - surfacing as a 500-class error, not a clean 400. The alerting documentation explicitly **nudges operators toward large sizes** ("set size=1000 for full audit windows") for the audit-export workaround, so operators are pushed toward exactly the unbounded request.

## Why it matters

The documentation recommends a large `size` for audit exports to minimise round-trips - so a careless or malicious `size=1000000` on a high-volume entity produces an arbitrarily large response body and an unbounded query (memory/latency amplification). A `page=0` request returns an opaque server error instead of a clear validation message - the first boundary an integration author hits. Medium severity: a request-DoS amplifier plus a poor error contract, reachable by any authenticated caller (anonymously under `auth.type=DISABLED`).

## Suggested fix

Add `@Max` (a platform-appropriate cap, e.g. 1000) + `@Min(1)` on the controller params at `DataEntityController.java:317-318`; add `minimum:`/`maximum:` to `PageParam`/`SizeParam` in `components.yaml:4213-4229`; add a defensive clamp at `ReactiveAlertRepositoryImpl.java:189` before computing `OFFSET` so `page=0` (and any negative offset) is rejected as a 400 rather than a 500.

**How to verify:** a `size` above the cap is clamped (or 400'd) instead of running unbounded; `page=0` returns HTTP 400, not 500 - a controller validation test on both boundaries.

## How discovered

Surfaced during a product-owner review of the per-entity alert read; confirmed by reading the controller params, the OpenAPI `PageParam`/`SizeParam`, and the repository `OFFSET` computation. Scope note: structurally the same unbounded-pagination class as the lineage-depth cap, but a distinct endpoint family (this one caps the per-entity alert read).
