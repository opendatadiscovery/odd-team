# DataEntityAttachmentController.uploadFileChunk — semantic understanding

## understanding

`uploadFileChunk` is the middle step (POST `/api/dataentities/{data_entity_id}/files/uploads/{upload_id}/chunks`) of the chunked-upload state machine: a client calls it once per chunk between an `initiateFileUpload` (issues `uploadId`) and a final `completeFileUpload` (assembles + persists). The controller body is a single reactive `flatMap` — it parses the `index` query param via `Integer.parseInt`, then delegates to `attachmentService.uploadFileChunk(uploadId, file, index)` and lifts the resulting `Mono<Void>` into a `200 OK ResponseEntity` (DataEntityAttachmentController.java:53-62). The method does no validation: it does not check chunk size against the `attachment.max-file-size` cap, does not verify that `uploadId` belongs to the path's `dataEntityId`, does not enforce ordering / uniqueness on `index`, and does not translate the `NumberFormatException` from `Integer.parseInt`. Storage-backend awareness, status-machine state checks (`PROCESSING`), and chunk persistence happen in `FileServiceImpl.uploadFileChunk` (FileServiceImpl.java:58-67) which writes via `FilePart.transferTo` to a hardcoded `/tmp/odd/chunks/{uploadId}/{index}` staging path.

## performance

- **hot_paths**: [
    "`uploadFileChunk` is on the request critical path — for an N-MB file at chunked-upload's per-chunk size, this method is invoked N times per upload.
