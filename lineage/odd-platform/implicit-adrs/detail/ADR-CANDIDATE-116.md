## ADR-CANDIDATE-116 — Soft-delete-inclusive existence check (`existsIncludingSoftDeleted`) is the deliberate guard for per-entity audit / lifecycle reads; the helper-name naming pair (`existsIncludingSoftDeleted` vs `existsNonDeletedByDataSourceId`) encodes the two-posture convention at the repository layer

**Classification**: promote
**Severity**: MEDIUM
**Pillars affected**: [P-07-active-platform-features, P-01-data-discovery]
**Support**: 1 sidecar (`getDataEntityAlerts`); confirmed by structural naming-pair at `ReactiveDataEntityRepositoryImpl.java:150-160` and cross-link to `getDataEntityDetails` neighbour sidecar (batch F — same soft-delete-inclusive read posture for the detail page)
**Batch**: L (2026-05-19)

**Surfaced by**:
- `odd-platform__java__DataEntityController__controller-method__getDataEntityAlerts.md:implicit_adrs.[1]` (HIGH) — "Soft-delete-inclusive existence-check is the deliberate guard for per-entity alert reads — `AlertServiceImpl.getDataEntityAlerts` (line 140) and `getDataEntityAlertsCounts` (line 147) both gate on `checkDataEntityExistence` (lines 327-335), which calls `dataEntityRepository.existsIncludingSoftDeleted(dataEntityId)`. The repository helper name (`existsIncludingSoftDeleted`) and its sibling (`existsNonDeletedByDataSourceId`, line 158 — which DOES apply `addSoftDeleteFilter(...)`) demonstrate that the codebase distinguishes the two soft-delete postures by helper name. The deliberate choice of `existsIncludingSoftDeleted` for the alert-read path is consistent with the `getDataEntityDetails` neighbour sidecar's observation that soft-deleted entities ARE returned by the detail page — the pattern is: 'soft-deleted entities remain readable for audit / housekeeping use cases'"

**Decision statement**: ODD's per-entity read surfaces use one of TWO existence-check helpers depending on the read's semantic role: (a) **lifecycle / audit reads** use `ReactiveDataEntityRepositoryImpl.existsIncludingSoftDeleted(id)` at `:150-155` — a `selectExists` over `DATA_ENTITY` with NO soft-delete filter; admits IDs of entities whose `deleted_at IS NOT NULL`. Consumers: `AlertServiceImpl.checkDataEntityExistence` (`:327-335`, gating `getDataEntityAlerts` + `getDataEntityAlertsCounts`); `DataEntityServiceImpl.getDetails` (via `.includeDeleted(true)` per ADR-CANDIDATE-055); the alerting audit-export workaround per the live alerting doc. (b) **active-inventory reads** use `existsNonDeletedByDataSourceId(id)` at `:158-160` — the sibling helper that DOES apply `addSoftDeleteFilter(query)` (adding `WHERE deleted_at IS NULL`). Consumers: ingestion-pipeline validations (entity must be active before bind), datasource-scoped lookups. The naming-pair convention (`existsIncludingSoftDeleted` vs `existsNonDeletedByDataSourceId`) encodes the architectural decision at the method-naming layer — a maintainer reading the code knows the posture from the helper name without inspecting the SQL. Composes with **ADR-CANDIDATE-068** (two-tier soft-delete inheritance taxonomy — `ReactiveAbstractSoftDeleteCRUDRepository` provides `addSoftDeleteFilter`; the helper-pair convention uses or skips it deliberately). Composes with **ADR-CANDIDATE-055** (`.includeDeleted(true)` on by-id reads with the `isStale` flag as the paired response contract). Composes with **ADR-CANDIDATE-058** (soft-delete-as-state — DELETED is a state, not a row removal; the existence-inclusive read is the operator-side counterpart to the soft-delete-as-state ADR). Trade-off accepted: any caller who knows or guesses the ID of a soft-deleted entity can read its alert history (cross-link REFACTOR-340) — useful for audit exports and housekeeping diagnostics, security-leaky for an enumeration attacker.

**Wisdom test**: PASS on all three questions. (1) **Intent stated**: the helper-name `existsIncludingSoftDeleted` itself encodes the intent — the maintainer named the method to signal what posture it implements; the sibling `existsNonDeletedByDataSourceId` does the same in the opposite direction. (2) **Structural impact**: the choice cascades into every per-entity audit/lifecycle read; reverting to a single existence-check helper would force every call-site to choose either inclusive or exclusive, losing the readability/intent encoding at the helper-name layer. (3) **Adding/removing the helper-pair convention would be structural**: collapsing to a single `exists(id)` with a boolean parameter would lose the readability; adding a third helper (e.g., `existsIncludingHardDeleted` once we acquire a hard-delete model) would extend the convention.

**Evidence**:
- getDataEntityAlerts.md says: "`AlertServiceImpl.java:327-335` (the existence-check body) + `ReactiveDataEntityRepositoryImpl.java:150-155` (the helper's body — no soft-delete predicate) + `ReactiveDataEntityRepositoryImpl.java:158-160` (the sibling that DOES apply the filter; the naming pair is the convention) + `getDataEntityDetails` neighbour sidecar `invariants[1]` (same soft-delete-inclusive pattern documented for the detail page)"

**Existing ADR**: none. **Composes with ADR-CANDIDATE-055** (soft-delete by-id read with `isStale` flag — the existence-inclusive helper is what enables `.includeDeleted(true)` paths to succeed). **Composes with ADR-CANDIDATE-068** (two-tier soft-delete inheritance taxonomy — the helper-pair convention is the read-side counterpart to the lifecycle-aware delete-side override). **Composes with ADR-CANDIDATE-058** (soft-delete-as-state).

**Cross-link gaps** (refactoring-scopes anchored on consequences this ADR DOES NOT defend):
- The audit-export use case enables cross-channel disclosure: soft-deleted entities' alert history is reachable via the alerts endpoint even though the catalog list filters them out. Surface as a doc-drift candidate at the live alerting page (it names the audit-export workaround without disclosing the soft-delete-inclusive behaviour).
- An attacker with prior knowledge of a soft-deleted entity's ID (from a leaked audit log, prior credentials, or monotonically-increasing ID enumeration) can read alert history thought to be hidden. The ADR endorses the read posture; defending against the enumeration is a separate gap (cross-link REFACTOR-340).

**Proposed action**: Promote to `adrs/drafts/soft-delete-inclusive-existence-check.md` (new ADR). Document: (1) the helper-naming convention (`existsIncludingSoftDeleted` vs `existsNonDeletedByDataSourceId`) as the architectural decision at the method-name layer; (2) the consumers (alerts read path, detail read path); (3) the cross-channel disclosure trade-off. Cross-link with ADR-CANDIDATE-055 (by-id include-deleted CTE), ADR-CANDIDATE-068 (two-tier soft-delete taxonomy), ADR-CANDIDATE-058 (soft-delete-as-state). Doc-side: the live alerting page's audit-export workaround section should describe the soft-delete-inclusive behaviour.

**Severity rationale**: MEDIUM — pattern-shaping decision visible at the helper-name layer; load-bearing for the audit-export workaround use case named verbatim in the live alerting doc. Not HIGH because the security consequence is cross-linked at REFACTOR-340 rather than the ADR itself; the ADR is a positive architectural choice while the consequence is a separately-tracked gap.
