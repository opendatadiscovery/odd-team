## Description

The live `groups-domains.md` page (WebFetched 2026-05-27, 200 OK) describes the DEG concept — manual vs ingested DEGs, the Domain flag, Catalog Overview tile visibility — but is **completely silent** on membership-write semantics. Operators discover behaviour by trial. Three corroborating facets land in one revision:

**Facet 1 — DEG membership management is structurally undocumented (F-012a).** Two endpoints (`POST /api/dataentities/{id}/data_entity_group` + `DELETE /api/dataentities/{id}/data_entity_group/{group_id}`) verified at `DataEntityServiceImpl.java:387-438`. Two distinct permissions (`DATA_ENTITY_ADD_TO_GROUP` + `DATA_ENTITY_DELETE_FROM_GROUP` — independently grantable). Ten substantive behavioural drifts (the eight listed below + the soft-delete-blocks-re-add + HARD-vs-soft cascade nuances from the substrate) — ALL undocumented.

**Facet 2 — Write-collaborative posture by design — no DEG-side authorization (F-012b).** `SecurityConstants.java:228-236` registers both permission entries with `DATA_ENTITY` as the scope path component — bound to the CHILD `data_entity_id`, NOT the parent `data_entity_group_id`. `PolicyPermissionDto.java:22-23` declares both ADD and DELETE as `DATA_ENTITY`-scoped — there is no DEG-side enum. A caller with `DATA_ENTITY_ADD_TO_GROUP` on entity X can place X into ANY manually-created DEG in the catalog, including DEGs owned by unrelated organisational silos. Combined with the Catalog Overview's Domain tiles surfacing the DEG roster, a multi-team deployment configuring "Finance Domain" and "Marketing Domain" as DEGs cannot prevent the Marketing team from placing arbitrary entities into the Finance Domain.

**Facet 3 — Forensic silence (membership writes emit no activity event) — verified.** `@ReactiveTransactional` is present on both methods (line 388, 411). `@ActivityLog` is **absent**. The `ActivityEventTypeDto` enum carries a `DATA_ENTITY_RELATION_UPDATED` value that is **dead** — no code path ever emits it (cross-link to DOC-181 / F-021b's 27-vs-20 enum coverage). An auditor querying activity for a DEG's membership history finds nothing; an operator with `DATA_ENTITY_ADD_TO_GROUP` discovers that membership changes are not visible on the per-entity Activity tab either.

**Facet 4 — Idempotence asymmetry (F-012c).** ADD raises 400 on duplicate (line 402: `.switchIfEmpty(Mono.error(new BadUserRequestException("Data entity is already in this DEG")))`). DELETE silently returns 204 on no-op (line 424: `.collectList()` flows to `ignoreElements().thenReturn(noContent())` — no `.switchIfEmpty`). Reconciliation scripts face asymmetric error-handling on the two endpoints; combined with the forensic silence, the caller cannot tell from HTTP response or activity feed whether anything changed.

Additional under-the-section caveats from the substrate (file in same revision as one-line callouts): (a) optional `data_entity_group_id` validation absence → "id null" error message; (b) empty DEG persists after the last member is removed — no auto-cleanup; (c) DISABLED auth bypass — the membership endpoints are reachable anonymously under `auth.type=DISABLED`; (d) conflated 400 error message on three distinct failure modes (already-in-DEG, target is not a manually-created DEG, invalid request body shape).
