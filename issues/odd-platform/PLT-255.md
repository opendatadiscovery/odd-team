## Summary

Two independent defects in the local demo stand (`docker/demo.yaml` + `injector/`), both of which a
first-time evaluator hits on their very first run:

1. **The enricher loses a start-up race with the platform**, exits 1, and injects nothing -- so
   `localhost:8080` shows an empty catalog, which is the opposite of the documented Step 1 result.
2. **`08_s3_ingestion.json` never loads** because its `data_source_oddrn` does not match any entry in
   `datasources.json`, so the README's "10 predefined data sources" is really 9.

## Defect 1 -- the enricher's readiness budget is shorter than the platform's start-up

`injector/inject.py` polls `/actuator/health` with `REACH_TRIES_NUMBER = 20` and `time.sleep(2)` between
attempts: a **~40 second** budget. `docker/demo.yaml` gives `odd-platform-enricher` a plain
`depends_on: [odd-platform]`, which in compose only orders *container start*, not readiness -- so the
clock starts while the platform is still booting.

A cold platform start is comfortably longer than that. Observed on this run:

```
odd-platform-enricher-1  | Waiting for the platform to be able to receive requests: 1
odd-platform-enricher-1  | Couldn't reach the platform
odd-platform-enricher-1  | Exception: Couldn't reach the platform in 20 tries
odd-platform-enricher-1 exited with code 1
odd-platform-1           | Started ODDPlatformApplication in 65.346 seconds (process running for 71.754)
```

The enricher died **four seconds** before the platform was ready. That is not an unlucky machine: a first
boot applies 100 Flyway migrations against an empty database, so ~65s is ordinary, and anything slower
(CI, a laptop under load, a locally built image) loses the race every time. The failure is also silent in
the sense that matters -- the user is left with a healthy platform, an empty catalog, and an exit-1
container they have already scrolled past.

**Proof that the race is the whole story:** re-running `docker compose -f docker/demo.yaml up
odd-platform-enricher` after the platform was up succeeded on the FIRST poll and injected everything --
9 data sources and 466 catalog entities, verified via `GET /api/datasources` and `POST /api/search`.

Fix direction: give the platform a real healthcheck and make the enricher wait on it
(`depends_on: {odd-platform: {condition: service_healthy}}`), and/or raise the budget to something that
cannot lose (e.g. 60 tries x 5s) and make the failure message say what to do next. A healthcheck is the
better half of the fix: it is the mechanism compose already has for exactly this, and it also fixes the
same race for `odd-collector`.

## Defect 2 -- the S3 sample is dead data (an oddrn mismatch)

`inject.py` looks each sample's `data_source_oddrn` up in `datasources.json` and skips it when there is
no match. The two files disagree by one path segment:

| file | oddrn |
|---|---|
| `docker/config/injector/samples/08_s3_ingestion.json` | `//s3/cloud` |
| `docker/config/injector/datasources/datasources.json` | `//s3/cloud/aws` |

so every run prints

```
Skipping //s3/cloud. Define DataSourceFormData in order to inject from the json file
```

and drops the sample's 2 entities. `datasources.json` has 10 entries, the catalog ends up with **9** data
sources, and `docker/README.md` says "You should be able to see 10 predefined data sources in the list".
A one-token edit to either file fixes it; the sample file is the likelier culprit since the datasource
list is otherwise consistent.

## User-facing impact

VERIFIED, not inferred. On a stock `docker compose -f docker/demo.yaml up`:

- the catalog is **empty** (`GET /api/datasources` returned `0` items), which is precisely the state the
  demo exists to avoid;
- `odd-platform-enricher` has exited 1 and `odd-collector` is restart-looping (the collector loop is a
  separate report -- see PLT-254 for the 500-instead-of-401 that makes it unreadable);
- a user comparing what they see against the README's "You should be able to see 10 predefined data
  sources" has no path from the symptom to either cause.

After re-running the enricher by hand: 9 data sources, 466 entities, catalog populated. So the platform
itself is healthy in both cases -- everything here is demo-stand wiring.

## Suggested fix (one pass)

- Add a `healthcheck` to the `odd-platform` service in `docker/demo.yaml` (it already exposes
  `/actuator/health`) and switch the enricher and the collector to
  `depends_on: {odd-platform: {condition: service_healthy}}`.
- Raise `REACH_TRIES_NUMBER` / the sleep in `injector/inject.py` so the script is safe even when run
  without compose, and make the give-up message name the likely cause.
- Align the S3 oddrn between `08_s3_ingestion.json` and `datasources.json`, then confirm the run reports
  10 data sources so the README's promise is true again.
