## Description

The class badge (`EntityClassItem`) is the most-seen widget in the catalog — it renders on Search result rows, the Directory list, the detail header, Linked-Entities lists, Lineage node cards, and per-entity Alert rows (F-206 `contributing_nodes`). Its chip colour is keyed off the wire enum: `backgroundColor: $entityClassName ? theme.palette.entityClass[$entityClassName] : ''` (`EntityClassItem.styles.ts:16`). When `$entityClassName` is truthy but **absent from the palette** (`theme.palette.entityClass`, `palette.ts:103-113`), the expression yields `undefined` — and the **only** way a class renders with no colour is enum drift: the OpenAPI codegen adds a `DataEntityClassNameEnum` member (`generated-sources/models/DataEntityClass.ts:53-63`) that the hand-maintained 9-entry palette and the 9-entry `DataEntityClassLabelMap` (`lib/constants.ts`, per F-206 reflection line 74) do not yet cover. There is **no fallback colour and no guard** — the F-206 reflection flags this as edge case (3) (`entity_class_palette_baked_into_theme_not_data_driven`) and facet `ui_class_palette_non_bijective_colour_collision_across_classes`. The missing-key path at `styles.ts:16` is unreachable today and stays unreachable until the next enum addition silently ships a colourless (or unlabelled) badge.

**Already covered — do NOT re-author (LSN-009 grep-the-backlog-first):** the per-surface badge render is e2e-verified — IT-018 (`e2e/specs/entity-class-type-badge.spec.ts`) covers the **detail header** (F-177) and IT-073 (`e2e/specs/entity-class-type-badge-list.spec.ts`, F-206 UC-7) covers the **Search result row**, both `ready` and PASS as of 2026-06-07. The existing unit test (`EntityClassItem/__tests__/EntityClassItem.test.tsx`) asserts the short/normal label + colour for two specific classes. The harvest one-line ("no e2e exercises the badge on a Search/Directory row") is therefore **stale for the Search row** — IT-073 already exists. The genuine residual gap is the **lockstep guard**: no test fails when the enum and the palette/label-map drift apart. That is what this item adds.

**Typed gate: validates-feature (the data-driven-encoding invariant) + guards-refactor.** The test encodes the F-206 promise that the badge is class-driven, not a constant chip, by asserting the lookup tables are total over the enum. It is GREEN today (all 9 members covered) and goes RED the instant codegen introduces an uncovered member — catching the colourless-badge regression at unit time, before it reaches any of the 6 surfaces. This is not a known-bug pin (the tables are correct today); it is a drift tripwire.

## Acceptance Criteria
- [ ] A unit test iterates **every** value of `DataEntityClassNameEnum` (`Object.values(DataEntityClassNameEnum)`) and asserts, for each member: (a) `theme.palette.entityClass[member]` is a defined, non-empty colour string (closes the `styles.ts:16` `: ''` fallback), and (b) `DataEntityClassLabelMap.get(member)` returns an entry with a non-empty `short` and `normal` label.
- [ ] The test imports the enum and palette from source (not a hand-copied list), so adding an enum member without a palette/label entry turns it RED — the assertion is the lockstep, not a fixed count.
- [ ] (Optional, same file) a render assertion that `EntityClassItem` renders a non-empty `background-color` for a representative class (mirrors the existing `EntityClassItem.test.tsx` style) to pin that the truthy-branch of `styles.ts:16` actually reaches the palette.
- [ ] The test runs in the odd-platform-ui Jest/RTL suite (CI `:odd-platform-ui` test task), is not skipped, and carries an in-source note referencing F-206 + the `styles.ts:16` unreachable-fallback rationale.
