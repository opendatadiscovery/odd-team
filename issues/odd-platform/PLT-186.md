## What

On a data quality test's "Runs History" view, the status filter (All / Success / Failed / etc.) is held in local React component state, not in the URL query string. So if a user filters to, say, "Failed", then copies the link and shares it - or simply refreshes the page - the filter silently resets to "All" and the recipient (or the same user post-refresh) sees the unfiltered list. The view they thought they were sharing is not the view that loads. This is inconsistent with the platform's own Activity tab, which keeps its filters in the URL via `useQueryParams`, so users reasonably expect filter state to survive a link share.

## Where

`odd-platform-ui/src/components/DataEntityDetails/QualityTestRunsHistory/TestRunsHistory.tsx:29-31` - the status filter is `useState`, with no URL backing:

```tsx
  const [alertStatus, setAlertStatus] = React.useState<DataEntityRunStatus | 'All'>(
    'All'
  );
```

That `alertStatus` is what drives the fetch (`status: alertStatus === 'All' ? undefined : alertStatus`, `TestRunsHistory.tsx:49`) and is re-initialised to `'All'` on every mount, so a refresh or a fresh navigation always starts unfiltered.

Contrast - the Activity feature reads its filters from the URL (`odd-platform-ui/src/components/Activity/ActivityResults/ActivityResults.tsx:15,26`):

```tsx
import { useQueryParams } from 'lib/hooks';
...
  const { queryParams } = useQueryParams<ActivityQuery>(defaultActivityQuery);
```

## Why it matters

The failure is **silent**: no error, the filter just isn't there. The concrete impact is collaboration friction - an operator triaging a flaky data quality test filters to failed runs and pastes the link into a ticket or chat; the colleague who clicks it lands on the full unfiltered history and has to re-derive the filter, or worse, misreads the shared link as showing everything. The same loss happens on an accidental refresh mid-investigation. It affects anyone who shares or bookmarks a filtered Runs History link. No data loss or security impact, so severity is medium - but it is a real, fixable usability defect and an internal inconsistency with how the rest of the platform (Activity) treats filter state.

## Suggested fix

Move the status filter into the URL query params, mirroring the Activity tab's pattern. Replace the `useState<DataEntityRunStatus | 'All'>('All')` with `useQueryParams` (from `lib/hooks`) keyed on a `status` query param defaulting to `'All'`; read the active status from `queryParams` and write it via the params setter from the `AppMenuItem` `onClick` handlers (`TestRunsHistory.tsx:61-71`). The fetch effect already keys on the status value, so a URL-driven value flows through unchanged and the filter becomes shareable and refresh-stable.

## How discovered

Surfaced during the 2026-06-08 feature-reflection contradiction harvest on F-040 (data quality test runs). The reflection flagged the asymmetry between this view's `useState`-held filter and the URL-backed filter pattern the Activity tab already uses, as a shared/refreshed-link correctness gap. No prior PLT covers this filter; it is a new finding.
