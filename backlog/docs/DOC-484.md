## Description

The Reference Data API page publishes a `{% hint style="danger" %}` whose first paragraph documents the **#1769
defect (b)**: the column `PATCH`/`DELETE` endpoints ignored the path `{lookup_table_id}` and could mutate a column
on a *different* table ("the platform never checks that the column actually belongs to the named table").

odd-platform#1769 / CTRIB-033 (milestone 0.29.0) closes this: both column write endpoints now validate the
column-to-table relationship and reject a mismatch with `400`, mirroring the read endpoint. Once 0.29.0 ships, the
first paragraph of that caveat is FALSE.

The edit (already on `release/0.29.0` @ `4dddcb7`):
- Rewrote the danger hint to drop the cross-table-mutation paragraph (fixed) and keep only the **separate,
  still-live** permission-gate path-mismatch issue (the rule is on singular `/column/`, the route is plural
  `/columns/`, so the gate doesn't fire — NOT fixed by #1769; tracked as PLT-243).
- Added to the `PATCH`/`DELETE` column rows: "`{column_id}` must belong to the `{lookup_table_id}` … or 400".
- Added to the `POST /table` row: the name-normalisation collision now returns `400` ("already exists").

## Why on the release train (not docs main)

The corrections describe **0.29.0 behaviour** (the fix is unreleased). Publishing them to docs `main` now would make
the live manual describe behaviour the latest published release (0.28.0) does NOT have — the live 0.28.0 still has
the cross-table-mutation bug, so the current caveat is correct for it. The corrected text rides `release/0.29.0` and
publishes exactly when 0.29.0 ships (`adrs/drafts/release-train-doc-gating.md`, G-C11).
