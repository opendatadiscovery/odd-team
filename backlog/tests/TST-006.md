## Description

F-014's audit-export compound (`F-014-UC-10`) is the doc-recommended workaround for the alert auto-cleanup bug: an operator exports a data-entity's alert history via `GET /api/dataentities/{id}/alerts` before manually resolving. The promise per the live alerting page is "operators with access to the data-entity can export the alert audit data." Three facets stack on this single endpoint, each verified by read on 2026-06-08:

1. **Cross-owner read** — `ReactiveAlertRepositoryImpl.getAlertsByDataEntityId` (`ReactiveAlertRepositoryImpl.java:182-199`) is `WHERE DATA_ENTITY.ID = :id` with **no OWNERSHIP join** (contrast the sibling `listByOwner` at lines 160-178 which DOES `.join(OWNERSHIP)`), and the GET path has no entry in `SecurityConstants.SECURITY_RULES` — any authenticated caller reads any entity's alert history.
2. **Soft-delete-inclusive** — `AlertServiceImpl.getDataEntityAlerts` gates on `existsIncludingSoftDeleted` (`AlertServiceImpl.java:327-335` → `ReactiveDataEntityRepositoryImpl.existsIncludingSoftDeleted`, no soft-delete filter), so a soft-deleted entity (hidden from the catalog UI) still serves its pre-deletion alert history.
3. **Unbounded size** — no `minimum`/`maximum` on the OpenAPI Page/Size params and no clamp at the repository (`OFFSET = (page - 1) * size`, line 189) — `size=1_000_000` is accepted; `page=0` yields a negative OFFSET.

The gap this item closes: the compound is **statically contradicted but never measured**. `F-014-UC-10` carries `test_demand: "PENDING-F-014-1 (probe; parallel-safe — local docker-compose; not yet minted)"` (`lineage/odd-platform/feature-flows/detail/F-014.yaml:695-701`) — there is **no `P-NNN.yaml` skeleton, no `probe-runs/` artefact, and no characterization test on disk**. This item mints the genuinely-novel pin: a measured probe that drives the three-facet compound against a local ephemeral docker-compose mirror and captures an observation trace as a committed artefact, so the compound's CURRENT (contradicted-but-shipped) behaviour is pinned rather than asserted only on paper.

TYPED GATE: **characterization-pin** (LSN-029). The probe + its trace assert the CURRENT behaviour — cross-owner read SUCCEEDS (200 with the owner-B history to a user-A caller), the soft-deleted entity's alerts ARE returned, and `size=1_000_000` is accepted unclamped. These are known, intentionally-shipped postures (the audit-export workaround relies on the cross-owner + soft-delete reads), so the pin goes RED the instant any of them is tightened (an OWNERSHIP join added, a soft-delete filter added, a size clamp added) — at which point the artefact is re-baselined per the LSN-029 flip protocol (invert to assert the tightened behaviour + retag from characterization to the corresponding fix's regression guard). It is NOT `@Disabled`.
