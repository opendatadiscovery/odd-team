- **REFACTOR-397** (NEW 2026-05-19O): Google personal-account rejection emits literal `null` in the error message — `"Domain null doesn't match with allowed domain odd.com"` is shown to the user. The `hd` claim is null for personal `@gmail.com` accounts; the error message interpolates the null value directly. UX gap; correct behaviour wrapped in operator-unhelpful message
  - **Category**: ux-bug
  - **Surfaced by**:
    - `GoogleUserHandler.md:bugs_limitations_corner_cases.[2]` (LOW)
    - `GoogleUserHandler.md:security.data_exposure.[0]` (LOW info-disclosure — operator's allowedDomain is leaked to any failed-login attempt)
    - `GoogleUserHandler.md:security.known_security_gaps.[2]` (LOW UX + minor info-disclosure)
  - **Statement**: When a non-Workspace user tries to log into an `allowedDomain`'d deployment, the `hd` claim is null (Google emits `hd` ONLY for Workspace accounts, never for personal `@gmail.com`). The error path at `GoogleUserHandler.java:52-54` reads: `String.format("Domain %s doesn't match with allowed domain %s", domain, provider.getAllowedDomain())`. The interpolated `domain` is literally `null` → the user sees `"Domain null doesn't match with allowed domain odd.com"`. The rejection itself is correct; the message is operator-unhelpful (leaks 'null' as an implementation detail) and a minor info-disclosure (the operator's `allowedDomain` is exposed to any failed-login attempt — though it's already inferable from the `?hd=odd.com` query parameter on the authorize URL).
  - **Evidence**: `GoogleUserHandler.java:52-54` (the literal `String.format("Domain %s doesn't match with allowed domain %s", domain, provider.getAllowedDomain())` — no null-branch)
  - **Existing-ADR-or-implied-prescription**: ADR-CANDIDATE-134 NEW (Google two-layer hd-claim defence-in-depth) — the rejection vector is correct security behaviour; the error message UX is a refinement, not a structural change.
  - **Proposed remedy**: Add a `domain == null` branch: `return Mono.error(() -> new OAuth2AuthenticationException(new OAuth2Error("invalid_token", domain == null ? "Your account is not part of an allowed organization" : String.format("Domain %s doesn't match with allowed domain %s", domain, provider.getAllowedDomain()), "")));`. The friendlier message offers a path forward (the user understands their account is the issue, not a system error). Optionally, drop the allowedDomain interpolation entirely to avoid info-disclosure (`"Domain mismatch — contact your administrator"` is sufficient).
  - **Severity rationale**: LOW — UX quality; correct rejection but unhelpful message. Minor info-disclosure (already inferable from the URL).
  - **Suggested backlog grouping**: `OAuth2 hardening sprint` (UX polish; composed with REFACTOR-395 + REFACTOR-398 Google-handler-family + DOC-NNN on operator-facing personal-account rejection semantic)
