## What

Collector tokens (the 40-char authentication secret used by every deployed ODD collector to POST to `/ingestion/*`) are stored verbatim plaintext in the `TOKEN.VALUE` column. Every DB-side reader (pg_dump, replica, backup, jOOQ log leak, application-log leak) recovers every live credential. The validation path uses plaintext SQL equality on the read side AND non-constant-time `.equals` on the application side.

Four facets compound:
1. **No hashing column (load-bearing).** `V0_0_28__add_token.sql:4` declares `value varchar(40) NOT NULL` - no `value_hash`, no `salt` (verified by BE trace 2026-06-10: grep for `value_hash`/`VALUE_HASH` across `src/main` returns zero hits; later token migrations `V0_0_33` and `V0_0_75` add no hashing). `TokenGeneratorImpl.generate` (`:34-42`) and `regenerate` (`:44-52`) build the `TokenPojo` with `RandomStringUtils.randomAlphanumeric(40)` as the literal `value`; the caller persists it verbatim.
2. **Plaintext SQL match.** `ReactiveCollectorRepositoryImpl.getByToken` (`:88-96`) does `TOKEN.VALUE.eq(token)` at `:94` (wrapped in `addSoftDeleteFilter`, so soft-deleted collectors' tokens don't match) - the query compares the operator-supplied token against the stored plaintext.
3. **Non-constant-time application equality [non-default path].** `IngestionDataEntitiesFilter.java:56` does `dto.tokenPojo().getValue().equals(token)` - `String.equals` short-circuits on first mismatch. This filter is `@ConditionalOnProperty("auth.ingestion.filter.enabled" == "true")` (`:20`), which ships **disabled** (`application.yml:46-48`, `auth.ingestion.filter.enabled: false`), and `/ingestion/**` is anonymous-whitelisted by default (`SecurityConstants.java:96`) - so the timing surface exists only when an operator enables ingestion auth filtering, and even then the comparison is over a fetched-then-compared value. A patient network attacker could in principle extract the token byte-by-byte; lower-magnitude than facet 1 and non-default.
4. **No UNIQUE on `TOKEN.VALUE` (narrow).** The only token-related uniqueness is `V0_0_33__add_token_constraints.sql` - a partial UNIQUE index on `collector(token_id) WHERE deleted_at IS NULL`, i.e. one live collector per token *row*, NOT uniqueness of the secret value. Two TOKEN rows could in theory share a value (practically irrelevant for random 40-char strings). The real sub-point: `TOKEN` has no `deleted_at` and no cascade, so soft-deleting a collector leaves its plaintext token row orphaned - historical credentials accumulate in the table (and thus in every backup).

## User-facing impact

The "user" here is the operator running backups/replicas/DB observability, and the API consumer (a collector). The load-bearing claim is a pure schema/code fact; the UI surface that displays the token was also traced.

- **At-rest exposure (load-bearing, verified by schema + BE trace 2026-06-10):** the collector token is stored as plaintext in `TOKEN.VALUE varchar(40)` with no hash column anywhere. A `pg_dump`, a read-replica, a backup archive, or a DB-observability pipeline therefore contains every live collector credential in cleartext. This needs no runtime drive - a plaintext column is, by definition, present in any dump of the table. Recovery from a leak requires rotating every token and treating every backup-history reader as compromised.
- **UI/API display surface (verified by FE/BE trace 2026-06-10 - already masked):** the token value returned over the API is masked everywhere except a one-shot reveal. `TokenMapper.mapValue` returns the full value only when `TokenDto.showToken()` is true, otherwise `"******" + <last 6 chars>` (`TokenMapper.java:15-18`). `showToken=true` is constructed only on token create/regenerate (`ReactiveTokenRepositoryImpl.java:26,38`); all list/get paths (`ReactiveDataSourceRepositoryImpl.java:167,177`, `ReactiveCollectorRepositoryImpl.java:114,124`) default `showToken=false` -> masked. So an authenticated UI user does NOT see a re-retrievable plaintext token; the GitHub-PAT-style one-shot reveal already exists. This means the surviving issue is strictly at-rest storage, not UI over-exposure.
- **Timing extraction (facet 3):** static trace consistent; not driven - and gated behind the non-default `auth.ingestion.filter.enabled=true`. The remaining check is whether an enabled-filter deployment leaks measurable timing over the network; lower priority than the at-rest leak.

## Why it matters

Operators running PgBackup / pgaudit / Datadog DB observability / read-replica pipelines have production credentials in their logs and backup archives. A compromised backup, a leaked replica snapshot, a careless `pg_dump` artefact dropped on a Slack channel - any of these immediately exposes every live collector's credential. Recovery requires rotating every token AND treating every backup-history reader as a compromise event.

The non-constant-time application equality (facet 3) is the lower-magnitude but real concern - extractable over slow networks with millions of attempts, but real attackers patient enough to do this exist when the target is a data catalog with operator-significant data.

Severity HIGH because:
- The credentials are operator-significant (each gates `/ingestion/*` POSTs that write to the data catalog)
- Discovery does not require attacker reach to the platform - backup pipelines + replica readers are sufficient
- The platform actively encourages multi-instance / multi-replica deployments (notifications, datacollaboration, partition coordination) - each replica is another credential-recovery surface
- Industry-standard fix (hash at rest, validate by hash) is well-trodden

## Suggested fix

Standard secret-handling migration. Lifts a one-time UX cost (existing operators must re-issue tokens) for permanent hardening.

**Schema migration:**

```sql
-- V0_0_NEW__hash_token.sql
ALTER TABLE TOKEN ADD COLUMN VALUE_HASH VARCHAR(255);
-- VALUE_HASH stores bcrypt or argon2 of the token value
-- value_hash NULL is the "legacy plaintext" state during migration
```

**Generator path:**

```java
// TokenGeneratorImpl.java
public Mono<TokenPojo> generateToken() {
    final String value = RandomStringUtils.randomAlphanumeric(40);
    final String hash = bcrypt.hash(value);                  // bcrypt 10-12 rounds
    final TokenPojo token = new TokenPojo();
    token.setValueHash(hash);
    // NOTE: value is NOT persisted; returned ONLY in the one-shot response body
    return tokenRepository.insert(token)
        .map(saved -> { saved.setValue(value); return saved; });   // attach for one-shot reveal
}
```

**Validation paths (filter + repository):**

```java
// IngestionDataEntitiesFilter.java
- if (!tokenPojo.getValue().equals(token)) { ... }
+ if (!bcrypt.verify(token, tokenPojo.getValueHash())) { ... }   // constant-time

// ReactiveCollectorRepositoryImpl.java
// remove the TOKEN.VALUE.eq(token) lookup; instead:
// 1. fetch ALL active tokens (small set, single-digit-K typical)
// 2. iterate, bcrypt.verify each - first match wins
// OR (better for scale):
// 1. store a non-secret prefix-hash + the bcrypt hash; look up by prefix-hash, verify by bcrypt
```

**Migration of existing operators:**

- One-shot bulk-migration script reads every existing plaintext `TOKEN.VALUE`, computes `VALUE_HASH`, writes the hash, then NULLs out `TOKEN.VALUE`.
- Boot-time check: if any `TOKEN.VALUE IS NOT NULL`, log WARN; fail-fast if a future flag is enabled.

**UI one-shot reveal (ALREADY IMPLEMENTED - do not rebuild):**

- The one-shot reveal already exists: `TokenMapper.mapValue` returns the full value only when `showToken=true` (create/regenerate), else `"******" + <last 6 chars>` (`TokenMapper.java:15-18`; `showToken=true` only at `ReactiveTokenRepositoryImpl.java:26,38`). The fix does NOT need to add this. NOTE: the current `"******" + last-6` masking reads the plaintext from the row, so moving to hash-at-rest must either drop the last-6 hint or persist a non-secret suffix alongside the hash.

**Defaults migration timing:**

- 1 minor version: dual-write (plaintext + hash) so existing collectors keep working.
- Next minor version: drop the plaintext column entirely.

Severity stays HIGH on the strength of the at-rest plaintext storage.
