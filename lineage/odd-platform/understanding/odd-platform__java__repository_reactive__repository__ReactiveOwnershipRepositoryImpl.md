# ReactiveOwnershipRepositoryImpl — semantic understanding

## understanding

`ReactiveOwnershipRepositoryImpl` is the **persistence boundary for the `OWNERSHIP` edge table** — eight thin jOOQ-reactive methods (get, create, createOrUpdate, delete, deleteByDataEntityAndOwner, updateTitle, existsByOwner, getOwnershipsByDataEntityId) that together hold the entire write surface for the `(data_entity_id, owner_id, title_id)` triple and the `ownership-by-data-entity` read surface used by the activity-feed handlers. The repository **does NOT participate in the owner-scoping JOIN for `/my` reads** — that JOIN is built locally inside `ReactiveDataEntityRepositoryImpl#listByOwner` at lines 526-527 (`<odd-platform-repo>/odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/repository/reactive/ReactiveDataEntityRepositoryImpl.java:526-527`), not via this class. The repository's design embodies five deliberate decisions: (1) hard-delete by default, no soft-delete column on `ownership` table (V0_0_3__add_ownership.sql:10-22); (2) duplicate prevention is delegated to the `UNIQUE (data_entity_id, owner_id)` DB constraint, with the violation translated to a `UniqueConstraintException` (`USR003`, HTTP 400) via `JooqReactiveOperations.mono(...).onErrorMap(...)` → `ExceptionUtils.translateDatabaseException` → "Ownership for this data entity and owner already exists" (`<odd-platform-repo>/odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/repository/util/ExceptionUtils.java:69-71`); (3) batch creates use `onConflictOnConstraint(...).doUpdate().set(TITLE_ID, excluded)` semantics for DEG propagation (lines 77-80), making `createOrUpdate` title-overwriting; (4) batch deletes build an OR-chain of `(data_entity_id, owner_id)` equality conditions reduced over `Condition::or` (lines 98-101) — the only operator-precedence-sensitive jOOQ predicate in this file, and the only one where a reordering of the `.eq(...).and(...)` clauses would silently change semantics; (5) no method takes an authentication/owner/principal parameter — the principal-derived owner-id reaches this layer pre-resolved at the service via `authIdentityProvider.fetchAssociatedOwner()`, with this class operating purely on Long ids.
