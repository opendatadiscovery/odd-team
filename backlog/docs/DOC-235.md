## Description

The live `enable-security/authentication/oauth2-oidc` page (WebFetched 2026-05-27) lists seven OAuth2/OIDC providers (AWS Cognito / GitHub / Google / Azure AD / Okta / Keycloak / Custom OIDC) and documents admin-groups for Cognito, GitHub teams, and Azure roles/groups. The page is **silent on five admin-detection divergences** that materially change which users become ADMIN. The `ODDOAuth2Properties` POJO binds the same fields uniformly across providers, but the runtime handlers consume them very differently.

**Facet 1 — Google admin-groups silent no-op (F-084a, HIGH→CRITICAL).** `GoogleUserHandler.java` (74 lines, full re-read this run) does NOT extend `AbstractOIDCUserHandler` and NEVER calls `provider.getAdminGroups()`. Admin detection consults only `adminPrincipals` (full-string equality against `email` claim via `GOOGLE_EMAIL = "email"` at line 31, unless overridden by `adminAttribute`). The field binds successfully; no boot warning, no error. An operator configuring `auth.oauth2.client.google.admin-groups: [workspace-admins]` sees ZERO behaviour change.

**Facet 2 — GitHub admin-principals BYPASSES `organization-name` gate (F-084b, HIGH→CRITICAL).** `GithubUserHandler.java:54-67` returns early at line 62 (`return Mono.just(new DefaultOAuth2User(...))`) BEFORE the org-name check at line 68 when `provider.getAdminPrincipals()` is non-empty. An operator configuring `organization-name: my-corp` + `admin-principals: [external-consultant]` grants ADMIN to `external-consultant` even though they are NOT a member of `my-corp`. A typo in `admin-principals` matching a username an attacker can register on github.com becomes a platform-ADMIN backdoor.

**Facet 3 — GHES STRUCTURALLY LOCKED OUT (F-084c, MEDIUM→HIGH).** `GithubUserHandler.java:39` hard-codes `WebClient.create("https://api.github.com")` with no `@Value`, no operator override. GHES deployments at `https://github.example.com/api/v3` cannot use the handler; every login fires DNS/cert errors. The live oauth2-oidc docs imply GitHub provider support is generic; GHES is an undocumented limitation.

**Facet 4 — Provider enum has 5 values, docs claim 7 providers — Okta + Keycloak fall through `CustomOIDCUserHandler` with no admin-detection (F-084d, HIGH→CRITICAL).** `Provider.java:3-5` declares a FIVE-value enum (COGNITO / GITHUB / GOOGLE / ODD_IAM / AZURE). Okta + Keycloak fall through `CustomOIDCUserHandler` which has NO admin-group mapping, NO provider-specific claim handling — every Okta + Keycloak user is USER, no admin path. Docs lead operators to assume parity that does not exist.

**Facet 5 — GitHub admin-groups SUBSTRING overpromotion (F-124b, HIGH→CRITICAL, NEW NOT IN SUBSTRATE).** Verified this run at `GithubUserHandler.java:119` — `containsIgnoreCase(provider.getAdminGroups(), userTeam)` — same case-insensitive SUBSTRING containment as LDAP (F-124a, covered by DOC-238). Operator config `admin-groups: ['admins']` against GitHub teams `team-admins`, `admins-readonly`, `data-admins` silently promotes EVERY member of EVERY one of those teams to ADMIN. The doc explicitly mentions GitHub admin-groups but does not warn about substring-match — operator mental model "GitHub admin-groups is exact-team-name match" is wrong.
