## What

`application.yml:22-26` deliberately swaps the two springdoc serving paths:

```
springdoc:
  api-docs:
    path: /api/v3/swagger-ui.html   # the OpenAPI JSON document
  swagger-ui:
    path: /api/v3/api-docs          # the interactive Swagger UI
```

So the intuitive URL `/api/v3/api-docs` serves the UI (302 to the webjars shell), and the
UI-shaped URL `/api/v3/swagger-ui.html` serves the raw JSON. Anyone who knows springdoc's
defaults (`/v3/api-docs` = JSON) gets the opposite of what they expect; tooling pointed at
"the api-docs URL" receives HTML.

Verified live 2026-06-12 (post-PLT-141-fix verification run): both routes work; the naming
inversion is the only residue.

## Why it matters (and why it is NOT a plain rename)

- Confusing for API/SDK consumers and for anyone cross-reading springdoc docs.
- BUT: the current URLs are load-bearing - the published docs page
  (developer-guides/api-reference) and operator bookmarks/scripts target
  `/api/v3/api-docs` as "the Swagger UI", and the demo links do too. Un-swapping is a
  breaking URL change for existing consumers.

## Suggested direction

Decide deliberately, as its own change:

1. Un-swap to springdoc-conventional paths AND keep the old URLs working (springdoc only
   supports one path each, so compatibility needs a redirect at the routing layer), with a
   deprecation note in the release notes + docs update; or
2. Keep the swap and document it prominently as intentional (one sentence on the
   api-reference page: "note: the UI is at api-docs, the JSON at swagger-ui.html").

Option 2 is the zero-breakage floor; option 1 is the long-term clean state.
