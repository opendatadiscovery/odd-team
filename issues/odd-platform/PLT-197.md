## What

On the **Management → Owner Associations** screen (the page where an administrator reviews "New requests", "Active associations", and "History" of owner-to-entity association requests), switching between the three tabs **silently clears the username search box**. An admin who has typed a username to narrow a long list of requests, then clicks another tab, loses the filter: the search term is reset to empty and the full unfiltered list is re-fetched. Because the search term is held only in client state with no URL backing, there is also nothing to restore it from (a back/forward navigation or a refresh cannot bring it back either). The reset is invisible — no toast, no indication the filter was dropped — so the admin sees a different result set and must retype the search on every tab change.

## Where

`odd-platform-ui/src/components/Management/OwnerAssociations/OwnerAssociationsTabs/OwnerAssociationsTabs.tsx:44-47` — the tab-change handler unconditionally empties the shared query atom and invalidates the list query:

```tsx
const onTabChange = React.useCallback(() => {
    setQuery('');
    queryClient.invalidateQueries({ queryKey: ['ownerAssociationRequestList'] });
}, [size]);
```

`setQuery` writes the `queryAtom` (`../OwnerAssociationsStore/OwnerAssociationsAtoms`, imported at `:8`) — the same atom the search input reads/writes — so emptying it on every tab click wipes whatever the admin typed. The search term lives purely in this jotai atom; the tab links carry only the tab name (`associationsPath('new'|'active'|'history')`, `:30/:34/:38`) and no `?query=` parameter, so there is no URL cushion to preserve or restore the search across the tab switch.

## Why it matters

This degrades a **privileged triage flow**: Owner Associations is an admin-facing approval queue, and on a busy deployment the request lists are long, so search is the primary way an admin finds the specific user or request to action. Forcing a re-type on every tab change (e.g. compare a user's pending request under "New requests" with their prior approvals under "History") is a real, repeated friction in exactly the workflow where precision matters. It is silent (no signal the filter was dropped), affecting any admin who searches and then changes tabs. Severity is medium: no data is lost or mis-actioned, but it is a recurring usability defect in a sensitive administrative surface, and the lack of any URL backing means the state is unrecoverable by normal browser navigation.

## Suggested fix

Preserve the search across the tab switch, ideally with a URL cushion so it also survives refresh/back-forward:

1. Lift the username search term into the URL as a query parameter (e.g. `?query=`) for the Owner Associations route, and have the search input read/write it; the tab links then carry the term across, and a refresh/back restores it.
2. As a minimum, stop clearing the atom in `onTabChange` — drop the `setQuery('')` call so the typed term carries over between tabs (keep the `invalidateQueries` so each tab re-fetches with the preserved term). The URL approach is preferred because it also fixes the unrecoverable-on-refresh aspect. Open to alternatives.
