## Description

The live oauth2-oidc page (WebFetched 2026-05-27) documents only Azure AD's `logout-uri` parameter; it does NOT describe per-provider token-revocation semantics, residual-token-validity windows, UI feedback on logout outcome, or where the platform derives `post_logout_redirect_uri` from. An operator using a shared workstation expects logout to terminate IdP-issued tokens; the platform delivers that only for Google and GitHub. Compounding: the post-logout redirect target is derived from the inbound `Host` header with no platform.base-url allowlist.

**Facet 1 — Cognito revocation endpoint EXISTS but handler does NOT call it (F-086a, HIGH→CRITICAL).** AWS documents Cognito's `/oauth2/revoke` endpoint as available on every User Pool. `CognitoLogoutSuccessHandler.java:33-50` issues session-only invalidation; contrast `GoogleLogoutSuccessHandler.java:43-54` which POSTs to `oauth2.googleapis.com/revoke`. One-line code addition closes the gap. Operator logging out from a shared workstation expects token revocation; instead the access token (1h TTL) + refresh token (up to 90 days on Cognito) remain valid.

**Facet 2 — 60min–90day post-logout token exfiltration window across Azure / Cognito / ODD_IAM (F-086b, HIGH→CRITICAL).** `AzureLogoutSuccessHandler.java:31-48` + `CognitoLogoutSuccessHandler.java:33-50` + `ODDIAMLogoutSuccessHandler.java:30-46` all session-only. Azure AD v2.0 does NOT expose RFC 7009 revocation (protocol-real limitation); Cognito does but handler doesn't call (Facet 1); ODD_IAM is session-only. A user logging out from a public terminal does NOT terminate IdP-issued OAuth2 tokens; previously-captured tokens remain usable.

**Facet 3 — UI no feedback on revocation outcome (F-086c, MEDIUM→HIGH).** `AppToolbar.tsx:35-37` issues `window.location.href = '/logout'` without surfacing any feedback distinguishing "successful local logout, no IdP revocation" (Azure / Cognito / ODD_IAM) from "successful logout + IdP token revoked" (Google / GitHub). Operators on shared workstations may believe they've fully logged out when the IdP-issued tokens still work.

**Facet 4 — `post_logout_redirect_uri` derived from inbound `Host` header (F-089a, HIGH→CRITICAL).** All 5 logout handlers derive the redirect target from `exchange.getRequest().getURI()` via `UriUtils.getBaseUri` (`AzureLogoutSuccessHandler.java:38-44`, `Cognito :43`, `Google :40`, `Github :45`, `ODDIAM :38`). NO platform.base-url allowlist; NO Host validation; NO scheme enforcement. Grep across the repo for `platform.base-url` / `odd.platform-url` / `allowed.redirect` returns ZERO matches. A reverse proxy that trusts and forwards user-controlled `Host` or `X-Forwarded-Host` headers propagates that value into the IdP's logout redirect chain. Multi-env Azure tenant with wildcard logout allowlist `*.example.com` + attacker `X-Forwarded-Host: attacker.example.com` → user lands on attacker domain after successful authenticated logout.

**Facet 5 — Facets 1-3 compound with Facet 4 (F-089b, HIGH→CRITICAL).** Even if the open-redirect is exploited and the user lands on attacker domain post-logout, the IdP-issued OAuth2 tokens (if previously captured) remain valid against IdP-protected resources for the rest of their TTL. The attacker's residual exploitation window benefits from the revocation gap. F-086 and F-089 form a single security cluster.

## Acceptance Criteria

- [ ] A new "## Logout token-revocation matrix" H2 section is added on oauth2-oidc.md with a table:

  | Provider | Local session invalidated | IdP token revoked | Residual token validity if NOT revoked |
  |---|---|---|---|
  | AWS Cognito | yes | **NO (handler does not call `/oauth2/revoke`)** — see PLT-073 | access ~1h, refresh up to ~90d |
  | GitHub | yes | yes (`token-revocation-uri`) | — |
  | Google | yes | yes (`oauth2.googleapis.com/revoke`) | — |
  | Azure AD | yes | NO (Azure v2.0 lacks RFC 7009 revocation — protocol-real) | access ~1h, refresh per policy |
  | ODD_IAM | yes | NO (session-only by design) | — |
  | Okta / Keycloak | — | falls through Custom OIDC (no logout handler) | — |

- [ ] A new "## Post-logout redirect derivation" H2 section documents:
  - The 5 logout handlers derive `post_logout_redirect_uri` from the inbound request's URI via `UriUtils.getBaseUri` — the redirect TARGET is whatever Host the browser presents.
  - **Reverse-proxy-trust caveat (admonition)**: If your deployment terminates TLS at a reverse proxy that trusts and forwards user-controlled `Host` or `X-Forwarded-Host` headers, the post-logout redirect chain can be hijacked. Mitigations: configure the reverse proxy to STRIP or REWRITE the inbound Host header before forwarding; configure the IdP's `post_logout_redirect_uri` allowlist with the most-specific host(s), not wildcards.
  - **Compounding caveat (admonition)**: For providers in the matrix above where IdP tokens are NOT revoked (Azure / Cognito / ODD_IAM), an open-redirect lands the user on the attacker domain WHILE captured tokens remain valid against IdP-protected resources. Track upstream PLT-075 (platform-base-url allowlist).
- [ ] A short "## UI feedback on logout outcome" sub-section documents that the SPA's logout flow does NOT distinguish "logged out + IdP token revoked" from "logged out + IdP token still valid". Recommend operators on shared/public terminals (a) sign out from the IdP directly (e.g., the Cognito UI / Azure portal) in addition to ODD logout, OR (b) wait for PLT-073 to add per-provider feedback.
- [ ] `Consumer-read:` footer cites `CognitoLogoutSuccessHandler.java:33-50` (no revoke), `GoogleLogoutSuccessHandler.java:43-54` (revoke contrast), `AzureLogoutSuccessHandler.java:31-48`, `ODDIAMLogoutSuccessHandler.java:30-46`, all 5 handlers' redirect-derivation lines (`Azure :38-44`, `Cognito :43`, `Google :40`, `Github :45`, `ODDIAM :38`), `UriUtils.java:11-23` (no host validation), `AppToolbar.tsx:35-37` (no UI feedback).
