# DataEntityController#getMyObjectsWithDownstream — semantic understanding

## understanding

`getMyObjectsWithDownstream` (`GET /api/dataentities/my/downstream`) is the symmetric sibling of `getMyObjectsWithUpstream` and the **POSITIVE-case anchor-set defence-in-depth surface** for downstream lineage — the third member of the `/my*` triplet on `DataEntityController` (`DataEntityController.java:291-297`). The method body is a four-line pass-through — `(page, size, exchange) -> Mono.just(dataEntityService.listAssociated(page, size, LineageStreamKind.DOWNSTREAM)).map(ResponseEntity::ok)` — that takes NO principal parameter; the principal flows through the reactor `Context` and is resolved at `DataEntityServiceImpl.listAssociated(page, size, streamKind)` (`DataEntityServiceImpl.java:218-225`) which delegates to `DataEntityRelationsServiceImpl.getDependentDataEntityOddrns(LineageStreamKind.DOWNSTREAM)` (`DataEntityRelationsServiceImpl.java:25-31`). That orchestrator (a) resolves the caller's owner via `authIdentityProvider.fetchAssociatedOwner()`, (b) lists the owner's owned data entities via `dataEntityRepository.listByOwner(ownerId)` (the no-page overload at `ReactiveDataEntityRepository.java:83-86`), (c) collects their oddrns into a `Set<String>`, (d) traverses one lineage hop in the DOWNSTREAM direction via `lineageRepository.getLineageRelations(oddrns, LineageDepth.empty(), DOWNSTREAM)` (`DataEntityRelationsServiceImpl.java:33-39`), (e) flattens the resulting `LineagePojo` rows into the union of `parentOddrn` + `childOddrn` distinct strings, (f) filters out the originally-owned oddrns (`Predicate.not(oddrns::contains)` at line 37), and (g) returns the resulting non-owned-but-reachable oddrn list. Then `DataEntityServiceImpl.java:223` calls `reactiveDataEntityRepository.listByOddrns(oddrns, false, false, page, size)` — which has NO `ownership.owner_id` JOIN at the SQL layer (`ReactiveDataEntityRepositoryImpl.java:228-253`). **The owner-scoping invariant for this endpoint is SINGLE-POINT-OF-FAILURE at `DataEntityRelationsServiceImpl.java:26`** — the anchor set is owner-scoped, but the downstream-lineage expansion and the final `listByOddrns` projection are owner-blind, exactly mirroring the sibling `getMyObjectsWithUpstream` pattern documented at REFACTOR-225 and DOC-GAP-099.

## performance

- **hot_paths**:
  - "Per-caller principal resolution: each `/my/downstream` request issues the AuthIdentityProvider SELECT on `user_owner_mapping JOIN owner` (per batch K AuthIdentityProviderImpl sidecar - no caching). The query is small (single-row) but uncached - every request triggers a DB round-trip."
  - "Owned-entity list (no-page overload): `listByOwner(ownerId)` at DataEntityRelationsServiceImpl.java:27 fetches ALL owned entities (no pagination) to build the anchor oddrn set. For a user owning many entities (admin / service account scenarios), this materialises the full ownership-joined CTE - the same CTE backing `listByOwner(ownerId, page, size)` (ReactiveDataEntityRepositoryImpl.java:515-534) - without pagination. The page/size on the controller is applied LATER at `listByOddrns` (DataEntityServiceImpl.java:223), NOT at the anchor step."
  - "Recursive lineage CTE (cross-link DOC-GAP-105): the CTE has no cycle clause, no upper bound. `LineageDepth.empty()` terminates after seed step yielding only one-hop edges, but the breadth at the seed step is unbounded (proportional to anchor-set cardinality * average out-degree)."
  - "Final projection: `listByOddrns(oddrns, false, false, page, size)` does the page/size clipping at the controller-supplied bounds; the IN-clause cardinality is bounded by the lineage CTE's output."

- **throughput_characteristics**:
  - "single-call read - no batching"
  - "reactive Flux response - entities are streamed back as they materialise from jOOQ's reactive pipeline (ReactiveDataEntityRepositoryImpl.java:252); but the upstream chain (`.collect(Collectors.toSet())` + `.collectList()` at DataEntityRelationsServiceImpl.java:29, 38) materialises intermediate state in heap before the final projection streams"
  - "the chain has THREE buffering points: (a) oddrns Set<String> from owned entities, (b) distinct oddrns List<String> from lineage edges, (c) DataEntityPojo Flux from final projection. The first two are bounded by user ownership + lineage out-degree; the third is bounded by page+size"

- **resource_allocation**:
  - "no client-side caching at the controller, service, relations service, or repository - every request executes four DB round-trips: principal lookup + owned-entity scan + lineage CTE + listByOddrns projection"
  - "the `.collect(Collectors.toSet())` and `.collectList()` operators materialise intermediate state in JVM heap; for an admin-mapped user owning 10k entities, the intermediate Set<String> is 10k * average-oddrn-length bytes"
  - "the lineage CTE (per batch H DOC-GAP-105) has no cycle clause and grows as O(B^N) for diamond DAGs - but with `LineageDepth.empty()` (one-hop only), the intermediate row count is bounded by anchor-set cardinality * out-degree"

- **scaling_characteristics**:
  - "stateless controller and service - instances scale horizontally"
  - "pagination at the final stage only (`listByOddrns` page+size) - the anchor-set scan and lineage CTE are NOT paginated; large anchor-set users pay the full anchor-fetch and CTE-expansion cost regardless of the controller-supplied `size`"
  - "no rate-limiting at the controller or service - repeated requests from a single client hit the DB at request rate; the 4-DB-round-trip cost per request is high"

- **known_performance_gaps**:
  - "**Anchor-set scan is unpaginated.** `listByOwner(ownerId)` (no-page overload at ReactiveDataEntityRepository.java:83-86) materialises ALL owned entities to build the oddrn Set. For admin-mapped users owning many entities, the anchor scan is the dominant cost. Pagination at the controller does not reduce this. severity: MEDIUM (insider amplification; bounded by ownership cardinality)" - evidence: DataEntityRelationsServiceImpl.java:27 + ReactiveDataEntityRepository.java:83-86
