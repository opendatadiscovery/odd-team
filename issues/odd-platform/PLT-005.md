## What

**The originally filed defect does not exist.** This draft previously claimed that `AlertHousekeepingJob`'s fluent chain

```java
.where(ALERT.STATUS.eq(RESOLVED))
.or(ALERT.STATUS.eq(RESOLVED_AUTOMATICALLY))
.and(ALERT.STATUS_UPDATED_AT.lessOrEqual(cutoff))
```

renders to flat SQL subject to SQL operator precedence (`WHERE status = 2 OR status = 3 AND aged`), so that every manually-RESOLVED alert would be hard-deleted on the next housekeeping run regardless of the `housekeeping.ttl.resolved_alerts_days` retention (default 30).

That claim is false. jOOQ's fluent API builds an expression tree, not SQL text: each `or()`/`and()` on `SelectConditionStep` combines the ENTIRE accumulated condition with the new one (`ConditionProviderImpl.addConditions(Operator, Condition)` -> `DSL.condition(operator, getWhere(), newCondition)`, verified by decompiling the shipped jar). Rendering the platform's exact chain with the platform's exact jOOQ version (3.18.4, `gradle/libs.versions.toml:15`) produces:

```
select alert.id from alert where ((alert.status = 2 or alert.status = 3) and alert.status_updated_at <= timestamp '...')
```

i.e. the INTENDED predicate, explicitly parenthesised. Both manually-RESOLVED (status=2) and auto-RESOLVED (status=3) alerts are deleted only after the TTL. Retention behaves exactly as documented.

Verification method (reproducible): jshell against the Gradle-cache jar `org.jooq:jooq:3.18.4`, same `DSL.using(POSTGRES).select(...).from(...).where(A).or(B).and(C)` chain as `AlertHousekeepingJob.java:28-34`, output via `q.getSQL(ParamType.INLINED)` - captured 2026-06-10. No jOOQ version ever rendered this chain flat: the combine-whole-condition semantics are structural in `ConditionProviderImpl`.

## Where

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/housekeeping/job/AlertHousekeepingJob.java:28-34` - the select; chunk rows are deleted before alert rows at `:36-43` (FK-safe order, also correct).

The chain reads ambiguously to a human (the `.or()` at the step level LOOKS like it could regroup), which is what produced the false finding. The unambiguous equivalent is:

```java
.where(ALERT.STATUS.in(
    AlertStatusEnum.RESOLVED.getCode(),
    AlertStatusEnum.RESOLVED_AUTOMATICALLY.getCode()))
.and(ALERT.STATUS_UPDATED_AT.lessOrEqual(...))
```

## User-facing impact

None. Verified by FE/BE trace + jOOQ render 2026-06-10: a manually resolved alert is retained the full `housekeeping.ttl.resolved_alerts_days` (default 30, `application.yml:165-170`), symmetric with auto-resolved alerts. Operators relying on the documented 30-day retention (postmortems, incident reviews, compliance windows) get exactly that. The shipped docs (DOC-009 -> `odd-platform.md`, DOC-021 retention paragraph) are CORRECT as written; the caveats this draft previously demanded must NOT ship.
