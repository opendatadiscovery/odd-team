## Description

Live `/permissions` line 95 (verbatim): `OWNER_RELATION_MANAGE`. "Allows accepting or declining ownership association requests."

Code reality (verified this session, `SecurityConstants.java:155-158` + `:159-162`): `OWNER_RELATION_MANAGE` gates TWO endpoints — `POST /api/owners/mapping` (admin direct-bind, F-172) and `DELETE /api/owners/mapping/{owner_id}` (active-tab Remove, F-173). NEITHER endpoint is "accepting or declining ownership association requests." The triage actions (Accept/Reject on PENDING `owner_association_request` rows) are gated by `OWNER_ASSOCIATION_MANAGE` (PUT `/api/owner_association_request/{id}` at `SecurityConstants.java:151-154`, verified). The two permissions are SEMANTICALLY DISJOINT — `OWNER_ASSOCIATION_MANAGE` is the triage permission; `OWNER_RELATION_MANAGE` is the direct-write-and-delete permission. The live `/permissions` description CONFLATES the two.

Operator-visible consequence: an admin granting `OWNER_RELATION_MANAGE` to a Policy expecting "this lets them approve pending requests" actually grants admin direct-bind + unbind capability — including the DIRECT_OWNER_SYNC composition hazard (DOC-209) if the holder also has that permission. Permission editor in the UI inherits the OpenAPI description; operators tick the box trusting the description.
