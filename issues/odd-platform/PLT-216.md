## What

The housekeeping subsystem permanently deletes data every 15 minutes (resolved alerts,
search-facet history, soft-deleted data entities with ~25 cascading child tables including
S3/MinIO attachment objects, empty activity/message partitions), yet it exposes no
operational telemetry at all:

- No Micrometer instrumentation. A package-wide grep of `housekeeping/` for
  `MeterRegistry | Counter | @Timed | meterRegistry` returns nothing -- no deletion
  counter, no per-job duration timer, no backlog gauge. The platform already ships
  micrometer-registry-prometheus and exposes /actuator/prometheus, so the registry is
  one constructor injection away.
- No audit event. Deletions are not recorded as structured audit records; there is no
  durable "what was deleted, when, how many" trail an operator can point a compliance
  auditor at.
- DEBUG-only logs. Every per-job deletion count is logged at log.debug, while the
  bundled application.yml ships the package at `info` -- so a default deployment emits
  NOTHING on a successful cycle. Only failures log at ERROR.

## User-facing impact

An operator of a default deployment cannot (a) observe that deletions are happening or
at what volume, (b) detect a stuck/wedged housekeeping cycle (e.g. blocked behind a held
advisory lock -- there is no gauge or last-success timestamp that would reveal it), or
(c) satisfy a "deletions are logged/audited" compliance requirement. The docs now carry
this as an operator caveat (Configuration and Deployment -> Configure ODD Platform ->
Housekeeping Settings Configuration), but the caveat is a workaround description, not a
fix: raising the log level to debug yields best-effort log lines, not telemetry or audit.

## Where

- HousekeepingJobManager.java:30 -- only normal-path log line is
  log.debug("Running housekeeping jobs"); :37 and :45 log failures at ERROR. No metric
  emission, no audit write on the success path.
- Per-job deletion counts, all log.debug: AlertHousekeepingJob.java:45,
  SearchFacetsHousekeepingJob.java:29, EmptyPartitionsHousekeepingJob.java:25,29,
  DataEntityHousekeepingJob.java:69,87,128.
- application.yml:254 -- org.opendatadiscovery.oddplatform.housekeeping: info (the
  bundled default that filters the DEBUG lines out).
- build.gradle:29 -- micrometer-registry-prometheus already on the classpath;
  application.yml:229-238 already exposes /actuator/prometheus.

## Proposed fix

1. Add a `housekeeping_deleted_total` Micrometer counter tagged by job
   (resolved_alerts, search_facets, data_entities, activity_partitions,
   message_partitions), incremented with the per-job deletion count each cycle, plus a
   `housekeeping_cycle` timer (or at minimum a last-success-epoch gauge) so a wedged
   cycle is detectable by alerting on staleness.
2. Emit a structured deletion audit record on the success path of each job (count +
   entity ids where bounded, cutoff used, duration). The existing activity/audit
   infrastructure may be a natural home; if not, an INFO-level structured log line is
   the minimum viable step.
3. Consider raising the per-job deletion-count log lines from DEBUG to INFO -- a
   subsystem that irreversibly deletes data should say so at the default log level.

Items 1 and 3 are small and self-contained; item 2 is the compliance-grade piece and can
ship separately.
