## Description

`activity-feed.md` line 116 tells the operator that under `auth.type=DISABLED` an anonymous mutation "render[s] visually identical to system events" — specifically "the UI shows these alongside the auto-resolved-alert-style 'system event' lozenge." That is the right *operator conclusion* (you cannot reliably tell anonymous-user from platform), but it mis-describes the **render mechanism**, and the mis-description is what an operator will check the UI against.

The actor block in `ActivityItem` keys solely on the boolean `activity.systemEvent`, not on whether `createdBy` is present:

- `activity.systemEvent === true` → `<GearIcon />` (the system-event glyph).
- `activity.systemEvent === false` → `<UserIcon stroke='black' />` followed by `{activity.createdBy?.owner?.name || activity.createdBy?.identity.username}`.

An anonymous mutation under DISABLED mode is **not** a system event (`systemEvent` is false), so it takes the second branch: it renders the **UserIcon** with a **blank name** (both `createdBy.owner.name` and `createdBy.identity.username` resolve falsy when `created_by` is null). So the three states are: (1) system event → GearIcon; (2) attributed user → UserIcon + name; (3) anonymous DISABLED-mode user → UserIcon + *blank* name. State (3) is a UserIcon with an empty label, which is visually distinct from the GearIcon system-event glyph the doc points operators at — an operator following the current text will look for a gear and instead find a nameless person icon, and may wrongly conclude the feed is broken rather than that the actor is anonymous.

This is a render-state refinement of the existing, already-shipped DISABLED null-actor caveat — fold it into that same admonition; do not open a new section. The same `ActivityItem` logic backs both the global Activity Feed and the per-entity Activity tab (identical `systemEvent ? GearIcon : UserIcon + name` block in both files), so one doc edit covers both surfaces.
