- **REFACTOR-399** (NEW 2026-05-19O): Google handler's `userNameAttribute` resolution path is INCONSISTENT vs. sibling OIDC handlers — GoogleUserHandler reads `request.getClientRegistration().getProviderDetails().getUserInfoEndpoint().getUserNameAttributeName()` (Spring auto-discovery + ClientRegistrationProperties binding), while Cognito/Azure/Custom-OIDC/ODD_IAM read `provider.getUserNameAttribute()` directly from the ODD POJO. Same config field, DIFFERENT read paths — architectural irregularity
  - **Category**: misleading-code
  - **Surfaced by**:
    - `GoogleUserHandler.md:bugs_limitations_corner_cases.[6]` (LOW)
  - **Statement**: `GoogleUserHandler.java:66-68` reads the userNameAttribute via Spring's `ClientRegistration.ProviderDetails.UserInfoEndpoint.getUserNameAttributeName()` — which comes from Spring's auto-discovery (via `issuer-uri` / `.well-known/openid-configuration`) OR from explicit `auth.oauth2.client.{id}.user-name-attribute` YAML binding through Spring's `ClientRegistrationProperties` class. All OTHER OIDC handlers (Cognito at `CognitoUserHandler.java`, Azure at `AzureUserHandler.java`, ODD_IAM at `ODDIAMUserHandler.java`, Custom OIDC at `CustomOIDCUserHandler.java`) read `provider.getUserNameAttribute()` directly from the ODD-specific `ODDOAuth2Properties.OAuth2Provider` POJO field. The two paths converge to similar behaviour TODAY (both bind from the same YAML key), but the resolution mechanism is different — a maintainer reading the Google handler vs. the others sees different code shapes for the same config field. Future maintenance hazard: if Spring's ClientRegistration metadata format changes (e.g., a Spring upgrade alters how `user-name-attribute` is exposed), the Google handler's behaviour diverges from the others.
  - **Evidence**: `GoogleUserHandler.java:66-68` (Spring's ClientRegistration-based read with fallback to `IdTokenClaimNames.SUB`) + `AbstractOIDCUserHandler.java:29-30` (the abstract base's POJO-field-based read) + `GithubUserHandler.java:53` (`provider.getUserNameAttribute()` for GitHub)
  - **Existing-ADR-or-implied-prescription**: ADR-CANDIDATE-137 NEW (Google bespoke vs. AbstractOIDCUserHandler) — the divergence is part of the bespoke decision; the maintainer COULD have read `provider.getUserNameAttribute()` to match siblings but chose the Spring auto-discovery path. The choice is not defended by a comment; it's an implementation-irregularity not a design statement.
  - **Proposed remedy**: Align the Google handler with the project convention: read `provider.getUserNameAttribute()` if non-empty, else fall back to Spring's ClientRegistration auto-discovery (preserving today's behaviour for issuer-uri-only deployments), else default to `IdTokenClaimNames.SUB`. The three-tier fallback matches the sibling handlers' pattern. Alternatively, document the divergence in a class-level Javadoc comment so future maintainers understand the intent.
  - **Severity rationale**: LOW — latent. Both paths converge to similar behaviour today; the irregularity is a future-maintenance hazard.
  - **Suggested backlog grouping**: `OAuth2 hardening sprint` (composed with REFACTOR-395/397/398 + ADR-CANDIDATE-137 codification of the extend-or-bespoke rule)
