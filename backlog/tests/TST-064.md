# TST-064 — IT-153's readiness failure: measured, instrumented, unexplained

## The measurement, with its denominator

`my-data-scope-narrows.spec.ts:259` — IT-153's R2 case, the one proving "My Objects" stops returning other
people's terms — has failed **once in six** whole-suite `multi-stack` runs, across three sessions and three
independently-built SUT images:

| run | session | `:259` |
|---|---|---|
| 1 | ctrib062rework (§24) | green |
| 2 | review-ctrib062-2 | **RED** |
| 3 | review-ctrib062-2 (re-run) | green |
| 4, 5 | ctrib062g (Phase G) | green, green |
| 6 | ctrib062g (after the S7 fix) | green |

It has **never** failed in a targeted run. It fails only in suite context, which is what makes it expensive:
each sample costs a ~10-minute whole-suite run.

## What it looks like when it fails

```
READINESS: the seeded fixture "it153mydata_21530" never became searchable on the freshly-booted
LOGIN_FORM stack within 90s.
  last observed page state: header="0 results" renderedRows=[]
```

## Three root causes argued and ruled out BY THE SOURCE

Recorded so the next person does not re-derive them:

1. **A background indexing race.** No. `V0_0_98` maintains `asset_search_entrypoint` with **synchronous**
   `AFTER INSERT/UPDATE/DELETE` triggers on `search_entrypoint`, so the seed's own transaction populates it.
2. **A NULL-propagating generated column.** No. `search_entrypoint.search_vector` is
   `GENERATED ALWAYS AS (coalesce(data_entity_vector,'') || …)` — `V0_0_14` wrapped every term in `coalesce`
   precisely so one absent vector cannot null the whole thing. Seeding `data_entity_vector` alone suffices.
3. **A lax readiness probe letting the seed land before migrations.** No. `management.endpoint.health.show-details`
   is unset, so Spring's default `never` applies and the body is exactly `{"status":"UP"}` — there are no
   components for a substring test to half-match. (`composeUp` was hardened to parse the status anyway, as a
   latent trap, not as a fix.)

`lfQuery` also opens a fresh `Client` per call, so a stale connection pool is out too.

## The standing hypothesis, unproven

Three specs share **one** compose project on **one** fixed port — `loginform-stack.ts` pins `PROJECT='oddlf'`
and `:18082` — and `stack.ts`'s `composeDown` is `docker compose … down -v`, destroying the volume. `IT-009`
(`auth-mode-boundary`) tears it down; `IT-153` boots it cold behind `ldap-rbac-enforcement`. A readiness probe
against a **fixed port** cannot distinguish "my new stack is up" from "the previous spec's stack has not
finished dying", so a seed could in principle land in a database that is about to be replaced. Consistent with
the symptom and with the intermittency — but **not demonstrated**, and `composeDown` is synchronous, which
argues against it.

## What is already in place

The next occurrence should identify itself. `waitUntilSearchable` now probes every layer **at the moment of
failure, while the stack is still up** — `flyway_schema_history` (is this database fully migrated?), the
`data_entity` row and the three columns the ranked query filters on, `search_entrypoint` and whether its
generated vector matches, `asset_search_entrypoint` and whether the AFTER trigger propagated it, and
`POST /api/search/assets` directly. Previously `afterAll` destroyed the evidence before anyone could look.
There is also a post-seed postcondition asserting all five fixtures reached the unified index.

## How to close this

- **Cheapest path:** the next time any suite run goes red on `:259`, read the layer probe — it names the layer
  that lost the row, and that should be enough to fix it directly.
- **Deterministic path (if it is worth an hour):** loop `run-regression.sh <id> multi-stack` until it
  reproduces (expected ~6 runs at the observed rate) and read the probe.
- **Structural path, valid regardless:** give IT-153 its own compose project + ports so no sibling spec can
  tear its stack down, or make `upLoginFormStack()` prove it is talking to its **own** freshly-migrated stack
  (a canary written after bring-up and read back) rather than trusting a health probe on a shared port.

**Do not close this by bumping the 90s bound.** The bound is not the problem, and CTRIB-062 §24 already
recorded why "flake, bump the timeout" was the wrong answer for the previous instance of this same test.
