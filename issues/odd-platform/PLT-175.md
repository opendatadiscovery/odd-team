## What

`GET /api/activity` (the platform-wide activity feed) applies the caller-supplied `size` parameter directly as the SQL `LIMIT` with no upper clamp at any layer. A caller can request `size=2147483647` and the platform issues a single query bounded only by Postgres/network buffers and the size of the `activity` table - an unbounded, expensive read available to any authenticated caller. The same parameter is also passed boxed (`Integer size`) into the jOOQ query builder; when it arrives `null`, jOOQ emits **no `LIMIT` clause at all** and the query returns the entire result set. There is no `@Min`/`@Max` on the controller parameter and no `minimum:`/`maximum:` in the OpenAPI `SizeParam`, so neither the framework nor the spec defends against an oversized or absent value.

## Where

```

`odd-platform-specification/components.yaml:4222-4229`

    SizeParam:
      name: size
      in: query
      description: Size
      required: true
      schema:
        type: integer
        format: int32
```
(`required: true` on the wire, but no `minimum:`/`maximum:`.)

```java

```

`odd-platform-api/.../repository/reactive/ReactiveActivityRepositoryImpl.java:290-294`
```java

            .orderBy(ACTIVITY.CREATED_AT.desc(), ACTIVITY.ID.desc())
            .limit(size);
        return jooqReactiveOperations.flux(finalQuery)
            .map(this::mapDto);
```
`org.jooq.SelectLimitStep#limit(Integer)` with a `null` argument produces a query with **no** `LIMIT` - i.e. the whole table.

## Why it matters

`/api/activity` is reachable by any authenticated caller (and anonymously under `auth.type=DISABLED`). The activity table grows monotonically with every catalog mutation, so on a mature install it is one of the largest tables. A single `size=2147483647` request - or a malformed client that drops the `size` query parameter and reaches the `null` path - turns one HTTP call into a full-table scan plus an in-memory map-and-serialize of every row into an `Activity` array. The cost is loud (latency, memory, DB load) but trivially triggered, with no audit of who triggered it: a denial-of-service amplification primitive available to any logged-in user. Severity is medium: not data-loss, not a credential bypass, but a cheap-request -> expensive-work asymmetry on a public, always-present endpoint with no rate or size ceiling.

## Suggested fix

Clamp `size` to a sane maximum at the service layer (e.g. `Math.min(size == null ? DEFAULT_SIZE : size, MAX_SIZE)` with a documented default and ceiling), so the value reaching `.limit(...)` is always a bounded positive integer. Belt-and-braces: add `minimum: 1` / `maximum: <ceiling>` to the `SizeParam` schema (or a dedicated activity size param) in `components.yaml` so the contract advertises the bound and the generated controller can enforce it. Open to alternatives on where the clamp lives, but the service tier is the one layer common to both `getActivityList` and `getMyActivity`, so it is the safest single point.

## How discovered

Surfaced in the 2026-06-08 contradiction-harvest (`integration-tests/run-log/` / feature-reflection triage) while reflecting on feature **F-021** (activity feed). This is the **same class** as the already-drafted pagination-bound issues **PLT-134** (per-entity alert read - `GET /api/dataentities/{id}/alerts`, unbounded `size`, negative `OFFSET`) and **PLT-042** (lineage depth - controller `@Max` + UI clamp), but it is a **distinct endpoint and parameter**: neither of those touches `GET /api/activity`, and the activity path additionally has the `null`-size -> no-`LIMIT` whole-table behaviour because the parameter is boxed and unvalidated. It is filed separately so the fix lands on the activity service rather than being folded into an unrelated endpoint's PR.
