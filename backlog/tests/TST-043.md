## Description

Observed during the 2026-06-11 full-regression runs of `feature-complete` (both rails:
P-001 api probe + 100+ e2e specs):

1. **Double build.** Run 1 produced TWO images for the same working tree @ 93cb5252:
   the api rail built digest `ed4638e7…`, the e2e rail built `12b67d0d…` (docker builds
   are not byte-reproducible, so each build gets a fresh digest).
2. **Mid-suite stack recreate.** The e2e global-setup compares the running container's
   image to ITS freshly-built digest -> mismatch -> "recreating with the SUT image" ->
   the stack (and DB state) is wiped BETWEEN the api rail and the e2e rail of one
   logical suite run, adding ~40s and discarding any cross-rail state.
3. **Inconsistent double logging.** Run 1 appended TWO run-log entries for the one
   invocation (one per rail, different digests, identical outcome line); run 2 appended
   ONE (digest `4a71e3b4…`) and printed no recreate line. The entry count per invocation
   is therefore nondeterministic — confusing for anyone auditing the log (it reads as
   two runs).

## Fix direction

Read the script's rail orchestration end-to-end first (the exact build/log flow was
inferred from observed entries, not from the code). Then: build the SUT image once per
invocation, pass the resulting image id to both rails (api probe runtime + e2e
global-setup) so the recreate check compares against the same digest, and emit exactly
one run-log entry per invocation summarising both rails.

## Acceptance Criteria

- [ ] One `run-suite.sh feature-complete` invocation performs exactly one SUT image
      build; both rails run against that image id.
- [ ] No stack recreate between rails of the same invocation (recreate only when the
      tree actually changed vs the running image).
- [ ] Exactly one run-log entry per invocation, covering both rails' outcomes.
- [ ] The double-entry pair from 2026-06-11 run 1 is annotated (not deleted — run-log
      history is point-in-time truth).
