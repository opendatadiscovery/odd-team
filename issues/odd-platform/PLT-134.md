## What

`GET /api/dataentities/{id}/alerts` has no pagination bounds at any layer: the controller params are bare `Integer page` / `Integer size` with no `@Min`/`@Max`, the OpenAPI `PageParam`/`SizeParam` carry no `minimum:`/`maximum:`, and the repository computes `OFFSET = (page-1)*size` with no clamp. `size=1000000` triggers a single jOOQ query + in-memory `AlertList` mapping bounded only by Postgres/network buffers; `page=0` produces a negative `OFFSET` that Postgres rejects with "OFFSET must not be negative" — surfacing as a 500-class error, not a clean 400. The live alerting doc explicitly **nudges operators toward large sizes** ("set size=1000 for full audit windows") for the audit-export workaround, so operators are pushed toward exactly the unbounded request.

This is **net_new** — structurally identical to PLT-100's lineage-depth `@Max`+clamp but a **distinct endpoint family** (PLT-100 caps lineage depth; no item caps the per-entity alert read). DOC side already done (DOC-200 documents the shape + recommends size=1000).

## Impact

The doc recommends a large `size` for audit exports to minimise round-trips — so a careless or malicious `size=1000000` on a high-volume entity produces an arbitrarily large response body and an unbounded query (memory/latency amplification). A `page=0` request returns an opaque server error instead of a clear validation message — the first boundary an integration author hits.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: add `@Max` (platform-appropriate, e.g. 1000) + `@Min(1)` on `DataEntityController.java:317-318`; add `minimum:`/`maximum:` to `PageParam`/`SizeParam` in `components.yaml:4213-4229`; add a defensive clamp at `ReactiveAlertRepositoryImpl.java:189` before computing OFFSET. Structurally identical to PLT-100's lineage-depth fix; distinct endpoint family.
