## What

`ODDLDAPProperties.java:10, 13` carries `@Data` + a `password` field. `ODDOAuth2Properties.java:30, 34` carries `@Data` on the nested `OAuth2Provider` with a `clientSecret` field. `EmailSenderProperties.java:7, 10` carries `@Data` + a `password` field. `@Data` generates a `toString()` including the credential verbatim. NO `@ToString.Exclude` on any password / secret / key / token field anywhere in `odd-platform-api` (verified: a repo-wide grep for `ToString.Exclude` returns zero matches).

This is a **latent** log-hygiene gap, not an active leak. There is no current code path that logs any of these property objects - confirmed 2026-06-10 (see User-facing impact). The risk is a future `log.info("loaded properties: {}", properties)` line, an exception handler that serialises the bean for diagnostics on boot failure, or Spring Boot's `--debug`/actuator env dump - any of which would emit the credential in cleartext to log infrastructure because the generated `toString()` includes it.

## User-facing impact

Not user-facing today; latent operator/security exposure if a log sink is ever added. Verified 2026-06-10 by tracing every consumer of these three property objects: the credentials are READ and passed to framework sinks - `LDAPSecurityConfiguration.java:121` `ctx.setPassword(properties.getPassword())`, `ODDOAuth2PropertiesConverter.java:23` `registration.setClientSecret(provider.getClientSecret())`, `NotificationConfiguration.java:57-58` `mailSender.setPassword(emailProperties.getPassword())` - but NONE of these (nor any other class) ever passes the whole properties object to a logger or calls `toString()` on it. A grep for `log.*[Pp]roperties` / `toString` over the property objects returns no credential-emitting sink. So no operator currently sees a leaked secret in logs. The defect is the open surface: `@Data`'s `toString()` would expose the secret the moment any future diagnostic line serialises the bean. Adding `@ToString.Exclude` is cheap defence-in-depth that removes the foot-gun before it fires; it is correctly scoped MEDIUM/latent, not an active high-severity leak.

## Why it matters

Defence-in-depth gap. The platform doesn't INTENTIONALLY log properties today (confirmed above), but the surface is open - exception handlers that serialise the context for diagnostics, future log lines added during incident debugging, and standard Spring Boot `--debug` flag / actuator env state all emit `toString()` output. One added log line in a hot path leaks LDAP password / OAuth secret / SMTP password to log aggregators.

This is the same family as PLT-080 (well-known DB default password) - credential hygiene defaults.

## Suggested fix

Class-wide pass via:

```bash
cd odd-platform-api
find . -name '*Properties.java' -exec grep -l '@Data' {} \;
# For each file, identify password / secret / key / token / credential fields
# Add @ToString.Exclude on each
```

Examples:

```java
// ODDLDAPProperties.java
@Data
public class ODDLDAPProperties {
    private String url;
    @ToString.Exclude  // NEW
    private String password;
    // ...
}

// ODDOAuth2Properties.java
@Data
public class ODDOAuth2Properties {
    public static class OAuth2Provider {
        private String clientId;
        @ToString.Exclude  // NEW
        private String clientSecret;
        // ...
    }
}
```

Confirmed in scope (2026-06-10 grep): the three `@Data` + credential classes above are `ODDLDAPProperties` (password), `ODDOAuth2Properties.OAuth2Provider` (clientSecret), and `EmailSenderProperties` (password). Also worth a defensive pass while open:
- Datasource properties (custom-datasource password) - note these are bound via Spring Boot's `DataSourceProperties`, not a local `@Data` class
- Slack / webhook properties (signing-secrets, bot-tokens), if/when added
- Any S3 / cloud-storage properties (access-key-id, secret-access-key), if/when added
- Custom collector / S2S keys

The class-wide pass is a small PR touching the three confirmed files (plus any of the above that exist); small individual changes; bundled atomic commit.
