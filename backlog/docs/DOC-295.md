## Description

Three code-confirmed corrections on the notifications page:

1. **SMTP protocol value is case-sensitive lowercase.** The code branches on the protocol with `.equals("smtp")` (exact, lowercase). The page's Gmail example writes the protocol as **`SMTP`** (uppercase). An operator who copies the example verbatim hits the **else** branch — **STARTTLS and AUTH never engage**, and there is **no boot warning**. Mail silently fails to send (or sends without TLS/auth). The page must specify lowercase `smtp`.

2. **Poison-message loop is at the translation stage, not the dispatch call.** The page's poison-message caveat attributes the WAL-replay loop to the dispatch call. The dispatch **has a try/catch**. The real uncaught failure is the **translation step** (`AlertNotificationMessageTranslator`) that runs **before** fan-out — an exception there is not caught, the message is re-read on WAL replay, and the loop repeats. The loop is real and HIGH, but the page points at the wrong stage, so an operator debugging it looks in the wrong place.

3. **`downstream-entities-depth` has no `@Value` default in code.** The page says the default is `1`. That `1` lives **only** in the shipped `application.yml`; `NotificationConfiguration.java` has **no `:1` (or any) default on the `@Value`**. So an operator who provides their own override config and omits the key gets a **startup failure** (Spring cannot resolve the placeholder), not a fallback to `1`. This is the LSN-001/REFACTOR "bare-`@Value` boot-failure" class.

High — #1 silently breaks notifications, #2 misdirects debugging of a real data-loss loop, #3 is a startup footgun.

**Failure shape**: code-doc drift on three distinct claims on one page (case-sensitivity, failure-stage attribution, default-source).
