## What

`GET /api/alerts/associated` (the My Objects alert list) returns a misleading `pageInfo.total` in exactly one case: when the returned page is EMPTY. `ReactiveAlertRepositoryImpl.listByOwner` passes the platform-wide `countAlertsWithStatusOpen()` as the empty-page fallback counter to `pageifyResult`, instead of the owner-scoped `countAlertsWithStatusOpenByOwner(ownerId)` that already exists in the same class. A user who owns no alerting entities gets `{ items: [], pageInfo: { total: <platform-wide open count>, hasNext: false } }`.

When the page is non-empty the fallback counter is never consulted: `pageifyResult` takes `total` and `hasNext` from the window fields (`total_rows`, `row_number`) that `jooqQueryHelper.paginate` embeds in the paginated query itself, so non-empty responses are correct.

**This does not reach the UI.** An earlier revision of this issue claimed the My Objects tab badge shows the platform-wide count ("empty list under a tab reading Alerts (137)"). That claim is false - checked 2026-06-10: the Alerts tab badges are fed by the separate, owner-scoped totals endpoint, and the list's `pageInfo.total` is never rendered anywhere in the Alerts UI (only `hasNext` and `page` drive the infinite scroll). The defect is an API-contract inconsistency visible to direct API consumers only.

## Where

The mismatched empty-page counter - the only one of the four list methods in this class whose fallback counter does not match its list predicate (`listAllWithStatusOpen`, `getAlertsByDataEntityId`, and `listDependentObjectsAlerts` all pass matching counters):

```java
// ReactiveAlertRepositoryImpl.java:160-179 - listByOwner: records ARE owner-scoped...
.flatMap(records -> jooqQueryHelper.pageifyResult(
    records,
    r -> mapRecordToDto(r, query.getRight()),
    countAlertsWithStatusOpen())   // line 177: platform-wide; consulted ONLY when records is empty
);
```

Why it only bites on empty pages - `pageifyResult` uses the supplied counter solely in the empty branch; otherwise total/hasNext come from the windowed query:

```java
// JooqQueryHelper.java:92-117
if (records.isEmpty()) {
    return Page.<T>builder().data(emptyList())
        .total(emptyRecordTotalCounter.get())   // <- the only use of the passed counter
        .hasNext(false).build();
}
...
.total(records.get(0).get(PAGE_METADATA_TOTAL_FIELD, Long.class))  // window field from paginate()
```

The owner-scoped counter already exists 90 lines below and already powers the tab badge:

```java
// ReactiveAlertRepositoryImpl.java:269-279
public Mono<Long> countAlertsWithStatusOpenByOwner(final long ownerId) {
    ... .join(OWNERSHIP) ... .where(OWNERSHIP.OWNER_ID.eq(ownerId)).and(ALERT.STATUS.eq(OPEN)) ...
}
```

Call chains: list = `AlertController.getAssociatedUserAlerts` (`AlertController.java:44-47`) -> `AlertServiceImpl.listByOwner` (`AlertServiceImpl.java:83-85`) -> repo `listByOwner`. Badge = `AlertController.getAlertTotals` (`AlertController.java:30-31`) -> `AlertServiceImpl.getTotals` (`AlertServiceImpl.java:90-96`, uses `countAlertsWithStatusOpenByOwner`) -> `AlertsTabs.tsx:23,28,34` (`totals.total` / `totals.myTotal` / `totals.dependentTotal`).

## User-facing impact

None in the shipped UI - verified 2026-06-10 by tracing the frontend: the Alerts tab hints all come from `getAlertTotals` (owner-scoped `myTotal`, `AlertsTabs.tsx:28`), and the alert list components read only `pageInfo.hasNext` and `pageInfo.page` (`AlertsList.tsx:75-90`); no Alerts surface renders the list's `pageInfo.total`. The empty-page `hasNext` is `false`, so infinite scroll terminates correctly. Impact is confined to direct consumers of `GET /api/alerts/associated`, which see `total = <platform-wide>` on an empty owned list.

One real (small) badge-vs-list edge case surfaced while verifying: `countAlertsWithStatusOpenByOwner` does NOT exclude `DATA_ENTITY.STATUS = DELETED` (`ReactiveAlertRepositoryImpl.java:269-279`), while the `listByOwner` query does (`:167`). An owner whose alerting entities are soft-deleted sees a My Objects badge counting alerts the list (correctly) hides. Same one-line family of fix; noted here rather than filed separately.

## Why it matters

Low severity, but worth the one-line fix: (1) the API contract misleads non-UI consumers - a `total` that does not describe the returned collection's scope; (2) it is the lone fallback-counter inconsistency among the four list methods in the class; (3) the matching counter already exists, so the fix has no design cost. The badge/list DELETED-exclusion drift (above) is the only part with any user-visible surface, and only in the soft-deleted-entity edge case.

## Suggested fix

One line in `listByOwner` (`ReactiveAlertRepositoryImpl.java:177`): pass the existing owner-scoped counter:

```java
countAlertsWithStatusOpenByOwner(ownerId))   // instead of countAlertsWithStatusOpen())
```

And for exact badge/list agreement, add the `DATA_ENTITY.STATUS.ne(DELETED)` exclusion to `countAlertsWithStatusOpenByOwner` so the counter's predicate matches `listByOwner`'s (`:167`) - this also fixes the badge edge case above. (The earlier revision of this issue proposed writing `countAlertsWithStatusOpenByOwner` as a NEW method; it already exists at `:269-279` and is exercised by `getTotals`.)

## How discovered

Surfaced during the 2026-06-08 contradiction-harvest (feature-reflection triage, F-126) as a claimed user-facing badge bug. **Corrected 2026-06-10 after the maintainer challenged it**: the original revision asserted the My Objects tab badge displays the platform-wide count - a backend-only extrapolation that a single frontend trace falsifies (the badge uses the owner-scoped totals endpoint; the list's `pageInfo.total` has no render site). Rewritten to the verified facts: empty-page-only `pageInfo.total` contract wart, severity high -> low, suggested-fix corrected to use the counter that already exists, plus the genuinely user-visible DELETED-exclusion badge drift found during verification. Same failure mode as the PLT-176 lesson: a UI claim shipped without reading the frontend.
