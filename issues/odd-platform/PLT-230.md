## What

#1757 added `RUNNING` as a Data Quality run status. The catalog-wide **Quality Dashboard** (`/data-quality`)
does not correctly account for it. There are two distinct problems.

### 1. Test Results Breakdown shows `Running`, but its count is always 0

The "Test Results Breakdown" chart now **displays a `Running` status** -- once `RUNNING` joined the run-status
enum it became one of the statuses the chart renders, so you can see it in the chart. But its **count is
always 0**. The breakdown is computed from each test's *last run* (`data_entity_task_last_run`), and an
in-flight run has no `end_time`, so it is never recorded there (`insertLastRuns` filters `end_time != null`).
A test that is actually running contributes nothing -- so `Running` reads 0 even while tests are running, and
a test whose latest run is in flight keeps showing its previous completed status.

**Expected:** an in-flight run should count as the test's latest run, so `Running` in the breakdown reflects
the tests that are actually running.

### 2. Table Health methodology is wrong and does not account for all statuses

Table Health classifies each table from its tests' latest-run statuses. It should be a **priority cascade --
the highest-severity status present on any of the table's tests wins**:

- **Error** -- at least one `Failed`;
- **Warning** -- at least one `Broken` (and no `Failed`);
- **Unknown** -- at least one `Unknown` (and no `Failed`, no `Broken`);
- **Healthy** -- none of the above (only `Success` / `Skipped` / `Aborted` / `Running`).

Today it does something different: **Healthy** only if *every* latest run is `Success`; **Error** if any is
`Failed` OR `Broken`; **Warning** otherwise; and there is **no `Unknown` table-health state at all**. So:

- a `Broken` test wrongly reads **Error** (should be **Warning**);
- a `Skipped` / `Aborted` / `Running` (and no `Failed` / `Broken`) makes a table **Warning** (should be
  **Healthy**); and
- a table with an `Unknown` test has no correct bucket (today it falls into **Warning**; it should be a
  distinct **Unknown** table-health state).

The two problems share a root in part: because in-flight runs are excluded from the last-run rollup, a
running test does not factor into Table Health at all (the table reflects its previous run). Fixing the
rollup (count the in-flight run) makes `Running` a real latest-run status, which then must be classified as
non-failing (Healthy) by the corrected Table Health rules above.

## User-facing impact

Reproduced live on a local stack (AUTH_TYPE=DISABLED), via `POST /ingestion/entities` + `GET /api/dataqatests/runs`.

**Test Results Breakdown (Assertion Tests category):**

1. one **completed** SUCCESS run (has `end_time`): `SUCCESS: 1, RUNNING: 0`.
2. an **in-flight** RUNNING run (no `end_time`) for the same test: **unchanged** -- `SUCCESS: 1, RUNNING: 0`.
   The running test is not counted.
3. a RUNNING run **with** an `end_time`: `SUCCESS: 0, RUNNING: 1` -- counted only because it has an `end_time`,
   proving the exclusion is driven by `end_time`, not by the status.

**Table Health (`tables_dashboard.tables_health`):**

- a table whose only test's latest run is **Broken**: classified **Error** (should be **Warning**).
- a table whose only test's latest run is **Skipped**: classified **Warning** (should be **Healthy**).
- a table whose only test's latest run is **Failed**: classified **Error** (correct).

## Where

- `odd-platform-api/.../repository/reactive/ReactiveDataEntityTaskRunRepositoryImpl.java` --
  `insertLastRuns(...)`: `.filter(tr -> tr.getEndTime() != null)` (~line 103). The only writer of
  `data_entity_task_last_run`; in-flight runs are dropped here, which drives problem 1 (and starves Table
  Health of the running state).
- `odd-platform-api/.../repository/reactive/ReactiveDataQualityRunsRepositoryImpl.java` --
  `getLatestDataQualityRunsResults(...)` builds the Test Results Breakdown from `DATA_ENTITY_TASK_LAST_RUN.STATUS`;
  `getLatestTablesHealth(...)` builds Table Health -- its `healthyTables` uses `STATUS NOT IN (SUCCESS)` and its
  `errorTables` uses `STATUS IN (BROKEN, FAILED)`, which is the wrong classification.
- `odd-platform-api/.../mapper/DataQualityCategoryMapperImpl.java` -- `addMissingStatuses(...)` (~line 51)
  emits a 0-count entry for every `DataEntityRunStatus` value, which is why `Running` is displayed at all.
- Endpoint: `GET /api/dataqatests/runs` (operationId `getDataQualityTestsRuns`).

## Suggested fix

1. **Count in-flight runs in the last-run rollup.** Stop dropping `end_time IS NULL` in `insertLastRuns`; pick
   each test's latest run by `COALESCE(end_time, start_time)` (or `start_time` when `end_time` is null), so an
   in-flight run becomes the current last run with status `RUNNING` and is replaced by the terminal status on
   completion. This makes `Running` count real in the breakdown and makes the running state available to Table
   Health.
2. **Correct `getLatestTablesHealth`** to the priority cascade above: Error = at least one `Failed`;
   Warning = at least one `Broken` and no `Failed`; **Unknown = at least one `Unknown` and no `Failed`/`Broken`**;
   Healthy = none of those (only `Success`/`Skipped`/`Aborted`/`Running`). The `Unknown` table-health state is
   new -- the ring and `TablesDashboardMapper` (currently `GOOD_HEALTH`/`WARNING_HEALTH`/`ERROR_HEALTH`) need an
   `UNKNOWN_HEALTH` slice + colour on the Table Health chart.

## How discovered

After #1757 added `RUNNING`, the DQ Dashboard began showing a `Running` status in the Test Results Breakdown.
Driving the running stack showed that count is always 0 (in-flight runs are not recorded in the last-run
table), and that Table Health misclassifies `Broken` and the non-failing statuses. Confirmed with the live
reproductions above.
