## What

The notification sender posts one HTTP request per alert synchronously, with no batching and no rate-limit handling. When the receiver (e.g. Slack) responds with `429 Too Many Requests` — which it will under any burst of alerts — the sender treats that status identically to any other non-200: it throws a generic `NotificationSenderException` and moves on. The `Retry-After` header that the receiver returns to tell the client how long to wait is **never read**, and there is no back-off or retry. The practical effect during an alert storm (exactly when notifications matter most) is that the receiver rate-limits the platform and **most of the burst is silently dropped** rather than delayed-and-delivered.

## Where

**`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/notification/sender/AbstractNotificationSender.java:16-30`:**
```java
protected void sendAndValidate(final HttpRequest httpRequest)
        throws NotificationSenderException, InterruptedException {
    final HttpResponse<String> response;
    try {
        response = httpClient.send(httpRequest, HttpResponse.BodyHandlers.ofString());
    } catch (final IOException e) {
        throw new NotificationSenderException("Couldn't send HTTP request", receiverId(), e);
    }

    if (response.statusCode() != HttpStatus.OK.value()) {                 // line 26
        throw new NotificationSenderException(
            "Notification sender response didn't complete with 200 status code", receiverId());
    }
}
```

Line 26 collapses every non-200 — `429`, `4xx`, `5xx` alike — into a single thrown exception. `429` is not distinguished, `response.headers()` (and thus `Retry-After`) is never inspected, and the call is a blocking 1:1 `httpClient.send(...)` per message with no coalescing.

## Why it matters

This degrades alerting precisely under load. The failure is **silent at the delivery boundary**: the throw is internal, so from the operator's side a chunk of an alert burst simply never arrives, with no indication that rate-limiting (rather than a real outage) was the cause. The affected parties are everyone subscribed to notifications during any high-volume event — which is the scenario alerting exists for. Because `429` is the receiver explicitly saying "slow down, retry after N seconds" and the code does the opposite (drop and continue), correctly-deliverable alerts are lost. High severity: lost alerts during a storm is a worst-case behaviour for a notification system, and the fix is a standard, well-specified protocol behaviour the sender currently ignores.

## Suggested fix

1. **Differentiate `429`** from other non-200 statuses in `sendAndValidate`.
2. **Read the `Retry-After` header** from the response (`response.headers().firstValue("Retry-After")`) and back off for the indicated duration (supporting both the delta-seconds and HTTP-date forms), then retry the send up to a bounded number of attempts.
3. Consider **coalescing/batching** bursts and applying a client-side rate limit so the platform does not hammer the receiver into `429` in the first place.

Open to alternatives on the back-off/retry policy details (max attempts, jitter, per-receiver queueing), but `Retry-After` must be honoured rather than discarded.
