## What

The Resolve/Reopen button on every alert row implements **post-action permission discovery**: the button renders unconditionally enabled; clicking it dispatches `fetchResourcePermissions(...)`, then conditionally calls `dispatchUpdateAlertStatus()` OR sets `disableResolve=true` and renders a "No access!" caption inline. **Users learn permissions by clicking.**

The component is shared across the global Alerts list AND the per-entity Alerts tab; the anti-pattern surfaces wherever an alert row is rendered.

## Why it matters

Three operator profiles affected:

1. **Unprivileged user on the global Alerts list** clicks Resolve on each row to discover which ones they can action. Discovers the gate row-by-row. UX is "try, fail, learn, try next row."

2. **Privileged user reading documentation that says 'click Resolve to mark the alert resolved'** clicks expecting success; instead sees a flash of action followed by a permission warning if the user's role changed mid-session.

3. **Mixed-permission deployments** (where some alerts are on entities the user owns and others aren't) — the user sees a row of identical-looking buttons that behave differently. UX is unpredictable.

The anti-pattern is recognisable industry-wide as "post-action authorization checking" — UI components that defer permission discovery until after the user commits an action. Standard practice is to render the button disabled-with-tooltip for unprivileged users + eagerly compute permissions for the visible rows on list-mount.

Severity is MEDIUM because:
- The misclick doesn't destroy data (the backend gate is real; the action is rejected); it's a UX surprise.
- The cross-cutting nature (global + per-entity) compounds operator friction.

## Suggested fix

**Three options, pick one:**

**Option A (recommended) — pre-fetch permission state for visible alerts on list-mount.** When the page renders, batch-fetch permissions for the rendered alerts; render each row's button disabled-with-tooltip for unprivileged rows.

```tsx
// AlertsList.tsx (parent)
const { data: alertPermissions } = useFetchAlertPermissions(alerts.map(a => a.id));

// AlertItem.tsx
const canResolve = alertPermissions[alert.id]?.canUpdate ?? false;
<Tooltip title={canResolve ? '' : t('You do not have permission to resolve this alert')}>
  <span>
    <Button onClick={handleResolve} disabled={!canResolve}>{t('Resolve')}</Button>
  </span>
</Tooltip>
```

**Option B — eagerly stamp the AlertList payload with a per-row `canResolve: boolean` field (backend computes once).** Smaller round-trip cost; backend already knows; UI renders cleanly.

```yaml
# components.yaml (AlertItem)
Alert:
  properties:
    ...
    canResolve:
      type: boolean
      description: "Whether the calling user has permission to resolve this alert"
```

**Option C — explicit empty-state framing — "you can view but cannot resolve" — replaces the per-row buttons for unprivileged users.** Less granular; might be the right shape when no alert in the visible page is resolvable.

Recommendation: **Option B** as the cleanest backend-led answer; Option A is the next-best if a payload-shape change is out of scope.
