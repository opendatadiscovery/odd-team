## What

`POST /ingestion/entities/datasets/stats` is unauthenticated under every supported configuration (the `/ingestion/**` namespace is whitelisted; the `auth.ingestion.filter.enabled` flag only covers `/ingestion/entities`). Two write-shape defects on this endpoint, both exploitable by any caller knowing a field's ODDRN:

**Defect 1 - Cross-dataset write (no parent-child validation).** `DatasetFieldServiceImpl.updateStatistics` (line 160-181) flattens ALL items' `fields` maps into one global field-ODDRN map (`:161-166`, dropping which `datasetOddrn` each field was declared under) and resolves writes BY FIELD ODDRN ONLY - `getLastVersionDatasetFieldsByOddrns(statistics.keySet())` (`:173`) queries the field table by ODDRN with no JOIN to the declared parent's dataset_id. The endpoint accepts a payload `{ items: [{ datasetOddrn: A, fields: { <oddrn-of-field-in-dataset-B>: stat } }] }` and writes the `stat` JSONB to dataset B's field rows while triggering FTS recompute on dataset A (the declared parent, `:179`). Net: **any caller can poison any dataset's field statistics by knowing the field's ODDRN through any other dataset's parent declaration**.

**Defect 2 - Replay-with-fewer-tags silently destroys EXTERNAL_STATISTICS-origin tags.** `DatasetFieldServiceImpl.updateFieldsTags` (line 191-226) calls `reactiveTagRepository.deleteDatasetFieldRelations(relationsToDelete)` (`:226`) for tags absent from the new payload, where `relationsToDelete` = the set of existing EXTERNAL_STATISTICS-origin relations not in the new set. A re-POST with FEWER tags silently removes the absent tags. Same destructive-replace shape as F-008's batch-replace contract but applied to per-field tags. No `replace_tags: bool` flag, no merge-semantics opt-in.

## User-facing impact

- **WHO:** any user viewing a dataset's Structure tab (and any BI/automation reading `dataset_field.stats`); the attacker is any caller on the network (no auth required).
- **No frontend is involved in the WRITE** - this is an ingestion API, not a UI action. The user-facing consequence is on the READ side: poisoned per-field statistics RENDER on the Dataset Structure tab with no provenance indicator. Verified by FE trace 2026-06-10: `DatasetFieldStats.tsx:101,105` renders `fieldStats?.uniqueCount`, `fieldStats?.nullsCount` (and siblings) straight from the field's stats.
- **The write is genuinely unauthenticated and cross-dataset** - verified by BE trace 2026-06-10: `/ingestion/**` is whitelisted (`SecurityConstants.java:96`); the only ingestion auth filter is conditional and matches `/ingestion/entities` POST only (`IngestionDataEntitiesFilter.java:20,28`), so `/ingestion/entities/datasets/stats` is reachable anonymously under every configuration; the controller has no `@PreAuthorize` (`IngestionController.java:82-86`); and the service writes by field ODDRN with no parent-child check (`DatasetFieldServiceImpl.java:160-181`). So a viewer of dataset B can be shown statistics an anonymous caller wrote by declaring dataset A. This is the LSN-001/LSN-002 class (operator trusts a rendered value that is attacker-controlled).
- **Defect 2 is a collector-correctness consequence, not an attack:** an operator's own collector replaying a stats payload with fewer tags silently loses the EXTERNAL_STATISTICS tags absent from the replay (`:226`); the user later sees fewer tags on the field than they ingested, with no error. Verified by BE trace 2026-06-10.

## Why

**Defect 1**: a security-critical write surface that accepts cross-dataset writes by design. Downstream consumers (Quality Dashboard rings F-022/F-032, Dataset Structure tab, BI tools reading `dataset_field.stats`) render attacker-controlled values without indicator. Combined with the endpoint being unauthenticated under every configuration, this is a trivial data-integrity attack on any dataset's field statistics that anyone on the network can execute. Falls into the same priority class as LSN-001 / LSN-002 - operator-following-guide-off-cliff territory.

**Defect 2**: same destructive-replace shape as F-008 (batch ingestion's silent_destruction_replace_not_merge class). Operators replaying stats payloads (a routine collector behaviour for at-least-once delivery) silently lose tags absent from the new payload. The default should be merge; destructive replace should be opt-in.

## How

**Defect 1 - one-line repo-query change** (preferred direction):

Change the field lookup to filter by **parent** as well as by field-ODDRN. Concretely, in `updateStatistics`:

```java
// instead of resolving by FIELD ODDRN with no parent validation, look up child fields BY PARENT:
return Flux.fromIterable(datasetStatisticsList.getItems())
    .flatMap(item -> reactiveDatasetFieldRepository
        .getLastVersionDatasetFieldsForParentOddrn(item.getDatasetOddrn(), item.getFields().keySet()))
    .collectList()
    .flatMap(resolvedFields -> {
       // ... apply stats; FTS recalc on item.getDatasetOddrn() is now AUTHORITATIVE
    });
```

The repository method's SQL becomes:
```sql
SELECT df.* FROM dataset_field df
JOIN data_entity de ON de.id = df.dataset_id
WHERE de.oddrn = :parent_oddrn
  AND df.oddrn = ANY(:field_oddrns)
  AND df.is_current_version = true;
```

Alternative (less surgical): add an assertion at the service tier - `assert resolved_field.dataset_id == declared_dataset_id` for each field; on mismatch, raise `BadUserRequestException`.

**Defect 2 - opt-in destructive replace**:

Add a flag to the payload schema (`DatasetStatistics.replace_tags: bool`, defaulting to `false`). When `false`, the `updateFieldsTags` method becomes append-only (no `deleteDatasetFieldRelations` call); when `true`, current destructive-replace behaviour. Update the spec at `opendatadiscovery-specification/openapi.yaml` accordingly.

Alternative: switch the default to merge-only and provide a separate `POST /ingestion/entities/datasets/stats/replace` endpoint for the destructive variant.
