## Description

The live Housekeeping section on `/configuration-and-deployment/odd-platform` (WebFetched 2026-05-27) DOES document the 15-minute cadence, the ShedLock-guarded multi-instance posture, and the three TTL keys with `Defaults to 30`. The page already partially discloses the jOOQ-precedence bug ("a known platform bug currently exempts manual resolutions from the retention check"). **Four facets remain undocumented or under-disclosed:**

**Caveat 1 — Java-side TTL defaults are zero; partial override silently zeroes the safety floor (F-010c — LSN-001 shape, HIGHEST).** `HousekeepingTTLProperties.java:8-12` declares `private int resolvedAlertsDays / searchFacetsDays / dataEntityDeleteDays` with **no field initialisers**. Spring binds primitive `int` default `0` if an operator overrides `application.yml` and forgets to re-supply the `housekeeping.ttl.*` block (typical Helm-chart values overlay, `--spring.config.location=` to a profile that omits the block, Spring Cloud Config slice, Kubernetes ConfigMap mount). The next 15-minute housekeeping cycle computes `cutoff = now() - 0 days = now()` and the predicate `STATUS_UPDATED_AT <= cutoff` matches **every row**. `DataEntityHousekeepingJob.java:99-126` cascades the delete through ~25 child tables; `fileUploadService.deleteFiles(...).block()` at line 142 deletes the corresponding S3 attachments. Recovery requires Postgres point-in-time restore + S3 versioning replay. No boot warning, no log line above DEBUG, no Prometheus counter — the live `Defaults to 30` framing is true only when the bundled `application.yml` is the resolved configuration. This is the exact LSN-001 (attachment-storage default) failure shape: silent default + destructive action + no preview + no metric.

**Caveat 2 — jOOQ operator-precedence bug — published acknowledgement but no tracking-issue link, no test, no `// BUG` annotation in code (F-010a).** The live page already states the bug; what's missing is a cross-link to a tracking issue so operators can subscribe to its fix. `AlertHousekeepingJob.java:28-34` is `.where(STATUS.eq(RESOLVED)).or(STATUS.eq(RESOLVED_AUTOMATICALLY)).and(STATUS_UPDATED_AT.lessOrEqual(cutoff))`. jOOQ fluent-builder precedence binds `.and(...)` to the most recent `.or(...)`. Emitted SQL: `WHERE (STATUS='RESOLVED') OR (STATUS='RESOLVED_AUTOMATICALLY' AND STATUS_UPDATED_AT <= cutoff)`. Manual RESOLVED rows skip the TTL check entirely; compliance frameworks requiring alert-retention (SOC2 / SOX / HIPAA) cannot rely on `resolved_alerts_days` for manual-resolved rows.

**Caveat 3 — "Three cleanup tasks" framing omits the two empty-partition reapers (F-010b).** `HousekeepingJobManager.java:23` injects `List<HousekeepingJob>` — Spring picks up **five** `@Component` classes: AlertHousekeepingJob, SearchFacetsHousekeepingJob, DataEntityHousekeepingJob (the three the doc names), plus ActivityEmptyPartitionsHousekeepingJob and MessageEmptyPartitionsHousekeepingJob. The two partition reapers inherit from `EmptyPartitionsHousekeepingJob` and drop empty past partitions of the `ACTIVITY` and `MESSAGE` tables respectively; neither consumes a `housekeeping.ttl.*` field — they are partition-rotation reapers, not TTL-driven row reapers. Combined with `odd.activity.partition-period` implying it controls "retention and partitioning" (per DOC-GAP-041), an operator's mental model of platform-data-retention is materially incomplete.

**Caveat 4 — Spring session housekeeping has no `@SchedulerLock` (F-010d).** `PostgreSQLSessionHousekeepingJobHandler.java:13` is `@Scheduled(fixedRate = 1, timeUnit = TimeUnit.HOURS)` with NO `@SchedulerLock` annotation, NO advisory-lock pattern, NO `@ConditionalOnProperty` leader-election guard. INCONSISTENT with the 5 HousekeepingJobManager-orchestrated jobs (`housekeepingJob` ShedLock at `HousekeepingJobManager.java:26`), NotificationSubscriber (`notifications.wal.advisory-lock-id`), the two DataCollaboration jobs, and `ActivityTablePartitionManager` (`partition.advisory-lock-id`). On an `INTERNAL_POSTGRESQL` deployment with N replicas, every replica runs `DELETE FROM SPRING_SESSION WHERE expiry_time < now()` hourly: N× redundant DB load. Deletes are idempotent so correctness is preserved, but the inconsistency with the documented "advisory-lock everywhere" pattern raises incident-response cost.
