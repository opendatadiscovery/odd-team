## What

`documentation@release/1.0.0 docs/data-discovery/favorites.md:33` promises that the Favorites surface lists
assets **"most-recently-favorited first"**. CTRIB-061 (#1841, ST-7) retires the tab that delivered that
ordering and replaces it with a search filter, which orders by the standard search ordering. The ordering is
restored by ST-7b (`issues/odd-platform/PLT-257`, a paste-ready sub-issue awaiting the maintainer's filing).

So the page's claim is true if and only if **both** slices ship in 1.0.0. This item exists so the 1.0.0
release gate is forced to decide which, rather than publishing whichever sentence happens to be on the branch.

## Why it needs a tracked item rather than a note

The seam is invisible to every other mechanism. The release gate derives its manifest by grepping
`backlog/` + `contributor/` for `milestone: "1.0.0"` (`playbooks/release-train-merge.md`), so a note in a
CTRIB record that has already flipped to `pending-release` would not surface it. This item's `milestone:`
line is the only thing that makes the gate look.

## Resolution — decide at the gate, from what actually merged

| If, at the 1.0.0 gate… | Then |
|---|---|
| **ST-7b has merged** | Keep the ordering claim. Rewrite `:31-33` from "the Favorites tab" to the Favorites filter, retaining "most-recently-favorited first" as the default ordering when the filter is on. |
| **ST-7b has NOT merged** | **Drop the ordering claim** from the rewritten prose — do not publish it. Say the filter narrows the catalog to starred assets, and say nothing about order. Re-open this item against the next milestone so the claim returns with ST-7b. |

Either way `:2` (the frontmatter `description:` — this is the published `<meta name="description">` and the
og:description, so it is reader-visible SEO text, not an internal comment), `:7` (the intro) and `:29` (the
panel paragraph's "View all link to the Favorites tab"), plus `catalog-overview.md:43`, must stop asserting a
top-level Favorites tab, because ST-7 removes it regardless.

The round-2 review of odd-platform#1875 + documentation#112 found three Gate-6 completeness gaps on exactly

### G1 — `search.md:182`'s canonical "what travels with the link" list omits `favorites`

The bullet enumerates *"the sidebar facet selections, the Asset-type and Data-entity-type filters, the active
ordering, and the **My data** scope with its per-direction depths"*. `favorites` is the fifth URL-only
dimension and **this change added it** — the new Favorites section at `:132` says so explicitly ("It rides the
URL as `/search?favorites=yes`, so a filtered view is bookmarkable and shareable"). So the page now asserts
two different lists of what a shared link carries. A reader building a share-link mental model from the
canonical enumeration gets a wrong one.

**Fix:** add `favorites` to the `:182` enumeration.

### G2 — the `favorites=no` state is user-reachable and documented nowhere

The parser keeps it, the projection sends `false`, the backend anti-joins, and the control deliberately renders
**indeterminate** for it (`FavoritesFilter.tsx:47`). A user who opens a shared or hand-edited `?favorites=no`
link sees a half-ticked checkbox over a narrowed list with no explanation anywhere in the manual. VERIFIED:
`git grep -iE "favorites=no|favorites=false|not starred|un-starred|unstarred"` over
`origin/docs/CTRIB-061-favorites-filter -- docs/` returns **zero hits**.

**Fix:** one sentence in the Favorites section, or a Known-limitations bullet. Note the negative direction also
carries the measured ~27x performance cliff (the draft filed by CTRIB-061), so a Known-limitations bullet is
the better home — it can carry both facts at once.

### G3 — `favorites.md` contradicts itself about what can be starred from a result row

`:18` says *"Catalog Search result rows — star **a data entity** straight from the results list"*; `:52` — a
line **this change wrote** — says *"where you can star **an asset** straight from a result row"*. `:52` is the
correct one: `ResultItem.tsx:108` renders `<FavoriteStar assetKind={asset.assetKind} …>` for every kind,
guarded only by `hasRef`, and the backend resolver is polymorphic across all three kinds (VERIFIED first-hand:
`FavoriteAssetResolver.java:34-38` maps `dataEntity` / `term` / `queryExample`). The change created the
contradiction by fixing one half of it.

**Fix:** `:18` -> "star **an asset**", matching `:52` and the page's own opening sentence at `:7`.
