## Description

Two auth modes present a **UI that contradicts the backend grant**, in opposite directions. Operators reason about "who can do what" from the buttons they see in the SPA; in both modes the buttons lie.

**DISABLED — empty-button UI, wide-open API.** Under `auth.type=DISABLED` the security filter chain is `.authorizeExchange(... .anyExchange().permitAll())` (`DisabledAuthSecurityConfiguration.java:16`) — **every** endpoint, including all mutating `/api/**` writes, is permitAll. Meanwhile the SPA gates each edit control through `WithPermissions`, which renders its children only when `hasAccessTo(permissionTo)` is true and returns `null` otherwise (`WithPermissions.tsx:28-29`). Depending on the whoami permission set the UI may show **no** mutation affordances, so an operator glancing at the catalog concludes it is "locked down / read-only." It is the opposite: any HTTP client (curl, a script, a browser bypassing the disabled buttons) can POST/PUT/DELETE freely. The empty-button UI is the most dangerous possible signal — it implies safety while the API is fully open.

**LOGIN_FORM — every credential is ADMIN, every button shown, RBAC inert.** Under `auth.type=LOGIN_FORM` every static credential parsed from `auth.login-form-credentials` is built with `.authorities(grantedAuthorityExtractor.getAuthorities(true))` (`LoginFormSecurityConfiguration.java:74-82`, the grant at line 81). The `true` argument is `isAdmin` (`GrantedAuthorityExtractor.getAuthorities(final boolean isAdmin)` — `GrantedAuthorityExtractor.java:12`), so **every** form-login user is a full admin regardless of which username they used. Consequently the SPA shows **every** mutation button to every logged-in user, and any RBAC Policy/Role the operator authors to *revoke* a permission is a **no-op** — the admin authority set already contains everything. An operator who creates a "read-only" policy and assigns it to a login-form user will still see — and be able to use — every control.

**How this misleads an operator.** In DISABLED, the UI under-reports reach (looks locked, is open). In LOGIN_FORM, the UI over-reports the effect of RBAC (every button visible, revocation policies silently ignored). Both pages today describe the **backend** posture but not this **UI-vs-grant** mismatch — which is exactly the lens an operator uses when they "check what the user can do" by clicking around.
