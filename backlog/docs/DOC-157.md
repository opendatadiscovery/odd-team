## Description

Editorial-audit finding from `/review feature/docs-features-md-carve-out-2026-05-07` (2026-05-07).

The Features.md carve-out (PR #68) shipped 8 new dedicated detail pages under their canonical bucket landings (Cornerstone 2). Each new page **forward-links** to the operator-side configuration sections, RBAC permissions, and integration / alerting references that gate its runtime behaviour. The reverse direction — from the operator-side surfaces back to the new feature pages — is missing on every site.

This is **Cornerstone 3** (Configuration is a separate audience surface — bidirectional cross-links between feature pages and configuration sections are mandatory) **and Cornerstone 6** (bidirectional code↔doc coverage) applied to a broader set of cross-link types: feature ↔ config, feature ↔ RBAC, feature ↔ alert rule, feature ↔ adapter coverage. The pre-existing pattern (the 2026-04-28 user spot-check on `features#id-6fbe` ↔ `odd-platform#attachment-storage-configuration` is the canonical case) has been **multiplied** by 8 new feature pages, all of which inherit the same gap shape.

The carve-out itself is correct (Features.md is now the index; canonical homes are the new detail pages). What the carve-out surfaced is the legacy pattern that operator-side surfaces never back-linked to feature anchors on the old monolithic Features.md (anchors changed when Features.md was reorganized; the back-links rotted away over time). With dedicated detail pages now stable, the time is right to land the reciprocal direction.

## Inventory of missing back-links

### 1. `configuration-and-deployment/odd-platform.md` → 3 missing back-links

- L745 (`housekeeping.ttl.data_entity_delete_days` config key) → no back-link to `../data-discovery/statuses.md`. The new `statuses.md` L29 forward-links here for the soft-delete TTL operator reference; reverse direction missing.
- L777 (`### Detecting stale metadata`) → no back-link to `../data-discovery/metadata-stale.md`. The new `metadata-stale.md` L30 + L46 forward-link here; reverse direction missing.
- L879 (`## Attachment Storage Configuration`) → no back-link to `../data-discovery/attachments.md`. The new `attachments.md` L10 + L52 + L62 forward-link here; reverse direction missing. (This is the literal 2026-04-28 user-spot-check case; the carve-out makes the gap re-surface.)

### 2. `configuration-and-deployment/enable-security/authorization/permissions.md` → 4 missing back-links

The new feature pages each name an RBAC permission and forward-link to `permissions.md` for the full permission list. The reverse direction (permissions.md → feature page using the permission) is missing for:

- `DATA_ENTITY_STATUS_UPDATE` — `data-discovery/statuses.md` L57
- `DATA_ENTITY_ATTACHMENT_MANAGE` — `data-discovery/attachments.md` L58
- `DATA_ENTITY_INTERNAL_NAME_UPDATE` — `data-discovery/business-names.md` L47
- `DATASET_FIELD_INTERNAL_NAME_UPDATE` — `data-discovery/business-names.md` L47

The pre-existing `permissions.md` likely lacks back-links for many other permissions too — this item logs the new gaps surfaced by the carve-out; a full sweep is out of scope and should be its own larger item if the broader pattern is worth fixing systematically.

### 3. `active-platform-features/alerting.md` → 1 missing back-link

- L91 (`## Backwards-incompatible schema change — what triggers it`) → no back-link to `../data-discovery/schema-diff.md`. The new `schema-diff.md` L7 + L9 + L41 + L50 forward-link here; reverse direction missing. Operators reading the alert rule should be able to reach the user-facing diff surface in one click.

### 4. `integrations/collectors/odd-collector.md` → 2 missing back-links

- The PostgreSQL adapter section → no back-link to `../../data-discovery/vector-stores.md` for the `Vector Store` dataset type / `Vector` column data type recognition that the PostgreSQL adapter surfaces. ## Context

- **Why medium priority.** This isn't actively misleading content, but the gap is a Cornerstone-3 violation that the user has flagged as canonical (the 2026-04-28 attachment-config spot-check). With 8 new feature pages now stable, the carve-out is the right moment to land the reciprocal links — operator workflows benefit immediately (config reader → feature reader; permission reader → feature reader; alert rule reader → diff surface reader).
- **Why this is in scope as one item, not eight.** All 8 sites are the same shape — a one-line cross-link sentence on the operator-side surface — and they all touch one of three files (`odd-platform.md`, `permissions.md`, `alerting.md`, `odd-collector.md`). Bundling avoids per-site PR overhead; the work is small in aggregate.
- **Why this is not "fix on the same PR as the carve-out".** The carve-out's announced scope was Features.md → 8 new detail pages + index; expanding scope to also touch `odd-platform.md`, `permissions.md`, `alerting.md`, `odd-collector.md` (4 additional files) would have ballooned the PR review surface. The editorial audit caught the gap at the right phase — surface follow-up work without blocking the per-item flip.
- **Pre-existing pattern, multiplied by carve-out.** The same gap exists on many other features that pre-date the carve-out (the cross-link coverage scanner is on the documentation pillar's roadmap per Cornerstone 3). This item closes the gap for the **8 new pages**; a separate larger item or the cross-link coverage scanner closes the gap for the rest of the doc tree.

## Implementation Notes

- Pre-authoring stance check on each site: confirm the canonical-home target for each cross-link before adding (per Cornerstone 5 — the home is the dedicated detail page).
- Each cross-link is a one-line sentence. Pattern: "For the user-facing X surface, see [`{page-name}`](../{path}).". Keep prose terse.
- The `permissions.md` row updates are typically inside table cells (Description column). Add a parenthetical "(see [Feature](../path/to/feature.md))" rather than a full sentence.
- Live-site verification covers the 4 affected files; spot-check via WebFetch.
