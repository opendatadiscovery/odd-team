## Summary

The #1755 fix (CTRIB-009) null-guarded the class branches of `mapPojo` and `mapDtoDetails` -
the two surfaces that issue named and reproduced (search results + entity detail). The SAME
defect shape exists on a third method of the same mapper, deliberately left out of that PR
to keep the diff bounded:

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/mapper/DataEntityMapperImpl.java`
`mapDataQualityTest` (`:362-383` pre-#1755-fix numbering) does:

```java
final DataQualityTestDetailsDto dqDto = dto.getDataQualityTestDetailsDto();
final DataEntityRun latestRun = dqDto.latestTaskRun() != null ? ... : null;   // <- NPE if dqDto null
return mapPojo(dto)
    .suiteName(dqDto.suiteName())
    ...
```

It null-checks `latestTaskRun()` INSIDE the DTO but never the DTO itself. A
`DATA_QUALITY_TEST`-class entity whose `specific_attributes` JSONB lacks the quality-test
block (the entity_class_ids-vs-attributes-keys hydration mismatch root-caused on #1755)
reaches this method with `dqDto == null` -> NPE -> 500 for the whole response.

## Reachability (NOT yet reproduced - verify before filing)

`mapDataQualityTest` / `mapDataQualityTests` serve the data-quality LIST surfaces (e.g. the
dataset's quality-test list / DQ dashboard chains), which are fed by the DQ repository path +
the same `enrichEntityClassDetails` hydration. Reproduction should mirror #1755's: seed a
searchable `entity_class_ids='{4}'` row with NULL `specific_attributes`, then drive the DQ
list endpoints that route through `mapDataQualityTest` and capture the 500 + the log frame.
If those endpoints only ever receive entities hydrated FROM the dq-test attributes (i.e. the
null is unreachable), close this as not-a-bug with the trace recorded.

## Fix shape (if reproduced)

Same as #1755: skip the dq-specific mapping when `dqDto == null` (return `mapPojo(dto)`
unadorned), or guard per-field - consistent with the mapPojo/mapDtoDetails guards the #1755
fix introduced.
