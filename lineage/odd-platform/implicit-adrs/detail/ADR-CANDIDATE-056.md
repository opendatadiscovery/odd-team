- **ADR-CANDIDATE-056** (NEW 2026-05-12F): Centerpiece composite reads use **multi-stage zip-merge enrichment** — `getDataEntityDetails` orchestrates a base CTE select followed by parallel `Mono.zip(...)` enrichment across 5+4 sub-queries (entity-class details + details-enrichment) rather than a single fat JOIN — trading query simplicity for reactive parallelism + per-stage isolation
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar (`getDataEntityDetails`) but pattern-anchored across two parallel `Mono.zip(...)` constructions (5-way + 4-way) within the same orchestration; the consistency across two phases within the same method confirms it's a deliberate pattern
  - **Surfaced by**:
    - `odd-platform__java__DataEntityController__controller-method__getDataEntityDetails.md:implicit_adrs.[3]` ("Detail orchestration is a multi-stage zip-merge enrichment rather than a single fat query — five parallel lookups for entity-class details (dependencies + last task runs + DEG children + DEG children count + consumers count), four parallel lookups for details specifics (metadata + dataset versions + terms + tags), plus the parent-DEG lookup and the view-count UPDATE. The decision: trade query simplicity for reactive parallelism; one stage's slow query does not block the others." — intent_anchor: "the consistent `Mono.zip(...)` pattern with `function(...)` consumer applied across both enrichment phases")
  - **Decision statement**: ODD's centerpiece composite read (`getDataEntityDetails`) is implemented as a multi-stage zip-merge enrichment rather than a single hand-rolled JOIN. The orchestration shape at `DataEntityServiceImpl.java:198-208` is: (1) base CTE select via `ReactiveDataEntityRepositoryImpl.getDetails(id)` (one DB round-trip with `WITH RECURSIVE` for lineage shortcuts); (2) entity-class enrichment via 5-way `Mono.zip` at lines 513-531 (dependencies + last task runs + DEG children + DEG children count + consumers count — all fired in parallel against the connection pool); (3) parent-DEG enrichment via `enrichParentGroups` at lines 604-614; (4) details enrichment via 4-way `Mono.zip` at lines 617-622 (metadata + dataset versions + terms + tags); (5) `incrementViewCount` (per ADR-CANDIDATE-054); (6) `mapDtoDetails` final assembly. The decision has structural consequences: (a) the connection pool sees ~10 round-trips per detail render (perf cost — REFACTOR-200's "N+1-style enrichment chain" gap); (b) reactor's zip parallelises pairs, so wall-clock latency is roughly max(per-stage latency) per stage rather than a sum (perf benefit); (c) per-stage isolation — a failure in one zip leg fails the whole detail render (correctness consequence; no partial-detail mode). Trade-off accepted: simpler-and-readable per-stage code (each enrichment is its own `repository.method(id)` call) vs the absence of a single fat-JOIN query that would amortise the round-trip cost. The pattern is deliberately reused at the second phase (4-zip) — the same maintainer chose zip over JOIN twice in the same method, signalling intentional convention.
  - **Wisdom test**: PASS. The pair of parallel `Mono.zip` constructions within the same orchestration method is the intent anchor; the maintainer could have rolled a single 9-way zip (less readable) or a hand-crafted JOIN query (fewer round-trips, less parallelism). Choosing two 5+4 zips reflects a deliberate separation: entity-class enrichment is structurally distinct from details enrichment (entity-class depends on the entity's class membership; details enrichment depends on the entity's existence). Structural for every future composite-read endpoint on the platform.

    - getDataEntityDetails.md says: "DataEntityServiceImpl.java:197-208 (orchestration chain: read → enrich-class → enrich-parents → enrich-details → incrementViewCount → map)"
