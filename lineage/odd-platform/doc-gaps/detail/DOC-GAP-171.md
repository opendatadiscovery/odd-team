  - **Proposed doc action**: **Three-part action**.
    1. **Doc-side primary — `configuration-and-deployment/enable-security/authorization/user-owner-association.md`**: add two subsections:
       - **"How user-owner associations are stored"**: "Mappings are stored in the `user_owner_mapping` table with a `deleted_at` soft-delete timestamp; deleting or replacing an association is a SOFT-DELETE (the row remains with `deleted_at = NOW()`). Two partial unique indexes enforce 'at most one active mapping per owner' (`unique_deleted_at_per_owner`) and 'at most one active mapping per (username, provider)' (`user_owner_mapping_oidc_username_provider_deleted_key`). Consequence: the table grows monotonically — a user mapped → unmapped → remapped 100 times leaves 100 rows (99 soft-deleted). Deployments tracking storage should plan for slow growth proportional to operator-association churn. No automated truncation is provided; operators wishing to compact may issue a DB-side `DELETE FROM user_owner_mapping WHERE deleted_at IS NOT NULL AND deleted_at < NOW() - INTERVAL '1 year'` (verify with `SELECT count(*) FROM user_owner_mapping WHERE deleted_at IS NOT NULL` first; the seeded retention policy is operator-controllable, not platform-managed)."
       - **"Cross-provider username collisions in the UI"**: "Several UI surfaces (Alerts list, Activity Feed list, Owner-association Requests list, Owners list) display the Owner-name of the user who created or last-updated each row by JOIN'ing `user_owner_mapping` on `oidc_username` alone — without the `provider` field. If your deployment has had BOTH LOGIN_FORM and OAUTH2 active concurrently AND a user named `alice` exists in BOTH (e.g., a local user `alice` plus a GitHub OAuth user `alice` mapped to different Owners), these list surfaces will show non-deterministic Owner names for `alice`-created rows AND in the case of Alerts: row duplication (each alert appears once per matching mapping). The collision is rare in practice but materially affects display correctness. Recommended migration audit before promoting auth-mode changes: `SELECT oidc_username, count(distinct provider) AS distinct_providers FROM user_owner_mapping WHERE deleted_at IS NULL GROUP BY oidc_username HAVING count(distinct provider) > 1;` — any rows returned indicate a deployment where the UI display gap is reachable."
