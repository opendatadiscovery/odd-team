## Description

Live `/user-owner-association` enumerates exactly 2 flows — admin "Select owner...press Associate" (which DOC-210 corrects as factually wrong) + user "Send request → admin approves". The page is silent on a third branch that bypasses the request flow entirely.

Code reality (verified this session): an admin with `OWNER_RELATION_MANAGE` sees a "+ Create association" button on Management → Associations Header (`OwnerAssociationsHeader.tsx:29-39` — `<WithPermissions permissionTo={OWNER_RELATION_MANAGE}>` HIDES the affordance when permission absent). Clicking opens a modal form (ownerId / oidcUsername / provider — all free-text / autocomplete, `required: true` only — see PLT-039). On submit, POST `/api/owners/mapping` with `UserOwnerMappingFormData` payload (`OwnerAssociationForm.tsx:42-46` Management/header version, verified) — the platform inserts a `user_owner_mapping` row DIRECTLY, NO PENDING intermediate, NO triage step, NO operator-approve roundtrip. Backend gate `SecurityConstants.java:155-158` confirmed: `POST /api/owners/mapping` → `OWNER_RELATION_MANAGE`.

Operator-visible consequence: operators reading the doc cannot discover that this write-path exists. The capability is gated by a different permission (`OWNER_RELATION_MANAGE`, not `OWNER_ASSOCIATION_MANAGE` — see DOC-221). Operators auditing "who can bind users to owners on this deployment?" must enumerate BOTH the holders of `DIRECT_OWNER_SYNC` (DOC-209) AND the holders of `OWNER_RELATION_MANAGE` — neither was named in the doc before this batch.
