## Description

Editorial-audit finding from `/review batch:feature/docs-doc149-cleanup-batch-2026-05-07` 2026-05-07.

Two narrative use-case pages cross-link past the doc product's canonical homes and point operators at GitHub repo URLs instead. This is the same failure shape that `retrospectives/LSN-003-dbt-wrong-repo-link.md` documents at the integration level, applied to use-case narrative — when a cross-link bypasses the doc-product canonical home and points at GitHub, (a) the doc product loses control of cross-link consistency (a renamed repo silently breaks the link, an org migration breaks it twice over), and (b) the reader leaves the doc product mid-narrative for a less-curated surface (a GitHub repo's README is not the doc-product's canonical-home content).

### Site 1 — `use-cases/dq-visibility.md` L7

> *"The ODD Platform ingests test results from [Great Expectations](https://github.com/opendatadiscovery/odd-great-expectations) and [dbt tests](https://github.com/opendatadiscovery/odd-dbt) (both push-clients), plus statistical profiles from [odd-collector-profiler](https://github.com/opendatadiscovery/odd-collector-profiler) (powered by Capital One's [DataProfiler](https://github.com/capitalone/DataProfiler)). Teams with a custom DQ framework can push results through the `POST /ingestion/entities/datasets/stats` endpoint of the [ODD Specification](../main-concepts.md#odd-specification). See the [Test Results Import](../data-quality/test-results-import.md) page under [Data Quality](../data-quality.md) for the platform-side view."*

Three GitHub-direct integration links bypass the canonical doc-home cross-links:

| Anchor text | Current target | Canonical home (per `pillars/documentation/canonical-homes.md` Integrations row) |
|---|---|---|
| `Great Expectations` | `https://github.com/opendatadiscovery/odd-great-expectations` | `integrations/push-adapters/odd-great-expectations.md` |
| `dbt tests` | `https://github.com/opendatadiscovery/odd-dbt` | `integrations/push-adapters/odd-dbt.md` |
| `odd-collector-profiler` | `https://github.com/opendatadiscovery/odd-collector-profiler` | `integrations/collectors/odd-collector-profiler.md` |

The fourth link (`Capital One's [DataProfiler](https://github.com/capitalone/DataProfiler)`) is an external upstream library, not an ODD-managed integration — that link to GitHub is correct and should stay.

The fifth link (`[ODD Specification](../main-concepts.md#odd-specification)`) is a correct cross-link to the canonical home (Specification's canonical home is the GitHub repo per `main-concepts.md` Terms & Aliases — that's recorded by design, see Cornerstone 5 / canonical-homes.md). Keep as-is.

The sixth link (`[Test Results Import](../data-quality/test-results-import.md)`) and the seventh (`[Data Quality](../data-quality.md)`) are correct canonical-home cross-links.

The page already demonstrates the right pattern at the end of L7 (the Test Results Import + Data Quality cross-links); the three integration cross-links at the start of L7 should adopt the same pattern.

### Site 2 — `use-cases/service-presales.md` L10 + L19

L10:
> *"The ODD Platform provides an [API](https://github.com/opendatadiscovery/odd-platform/tree/main/odd-platform-specification) to gather details on existing architectural landscape and toolset available in organization, so that I have better planning and therefore better customer relations."*

L19:
> *"To improve my Pre-sales processes I ask my clients to integrate the ODD [API](https://github.com/opendatadiscovery/odd-platform/tree/main/odd-platform-specification) with their data landscapes."*

Both `[API]` cross-links point at the platform's spec source (a tree URL on GitHub) rather than the canonical doc-home for the API surface. Per `pillars/documentation/canonical-homes.md` "API reference" row, the canonical home is `developer-guides/api-reference` — the hub page (`api-reference.md`) plus per-feature sub-pages — and the page already opens with: *"This page is the canonical reference hub for every HTTP endpoint exposed by the ODD Platform."*

A service-provider audience landing on this use-case page is precisely the audience the `developer-guides/api-reference.md` hub serves — they want a developer-facing index of every endpoint with operation IDs, not a tree URL of YAML source files. The fix is to retarget both links to `../developer-guides/api-reference.md`.

The page also references `[lineage](../data-lineage/microservices.md)` in keywords (L3) and `[ODD Specification](../main-concepts.md#odd-specification)` could replace the GitHub-direct API link if "the spec" is actually what the prose means. But the prose says "API" which most naturally maps to `developer-guides/api-reference.md`; "API" is not a synonym for "the OpenAPI spec source files" in operator-facing context.

Note: L3 keywords list also has `[lineage](../data-lineage/microservices.md)` — this is a correct cross-link to the canonical home for microservices lineage, no fix needed there.

## Context

- **Why low priority.** Both pages are narrative use-case scenarios (operator persona stories), not authoritative reference. A reader hitting either link arrives at correct destination content — the GitHub repo for an integration does carry correct configuration / setup info; the spec tree URL does carry the OpenAPI YAML. The defect is *cross-link consistency* and *audience targeting* (the GitHub URL is a contributor-facing surface; the doc-home page is the operator-facing one). Bumping above low if a similar pattern recurs across more use-case pages or other narrative surfaces.
- **Why this is the right finding to log.** Cornerstone 5 (one canonical home per content type) + `pillars/documentation/canonical-homes.md` Integrations and API reference rows are explicit on this. The doc product carries dedicated pages for every push-adapter, every collector, and the full API surface; a use-case page must cross-link to those canonical homes, not bypass them to GitHub. The same shape recurred at scale on `Features.md` (DOC-149 / DOC-154 cleanup) — bucket landings reverse-linking to Features.md anchors instead of canonical-home detail pages. This item is the analogous finding on the use-case narrative surface.
- **Why this slipped through prior `/review`s.** The use-case pages predate the IA refactor / canonical-homes table (DOC-049 vintage). The cleanup wasn't part of any prior batch's scope, and the editorial audit on DOC-153 / DOC-150 / DOC-149 focused on the structural cross-link shape (Features.md reverse-links) rather than walking each use-case narrative for canonical-home compliance. Per `playbooks/doc-product-editorial-read.md` "Token budget is intentionally not a constraint", the editorial audit can and should cover the use-case subtree on the next pass.
- **Pre-existing defect, not introduced by this batch.** This finding documents long-standing cross-link inconsistency. DOC-149/151/152/153/154 did not touch these pages' GitHub links; the editorial audit ran on the post-cleanup state and surfaced the pattern.
