## What

The "User" filter on the global Activity Feed AND on every per-entity Activity tab is **type-confused end to end**: the UI labels it "User" and the operator expects "events PERFORMED by the selected user," but (a) the autocomplete options are loaded from the **Owners** list, not a users list, and (b) the `userIds` query param is bound at SQL to `USER_OWNER_MAPPING.OWNER_ID`. So the operator picks an OWNER from a dropdown labelled "User," and the backend keeps activity rows whose ACTOR (`activity.created_by`) maps - via `USER_OWNER_MAPPING.OIDC_USERNAME` - to an owner whose `OWNER_ID` is in the selected set.

Net semantic (verified by FE+BE trace 2026-06-10): "activity PERFORMED by people associated with the selected OWNER(s)." That is NOT "events performed by user X" - a user with no owner association is unfilterable, and a user whose owner mapping changes over time is mis-attributed (the two failure modes the maintainer's LSN-020 report names). It is ALSO not "events on entities owned by X" - an earlier revision of this issue described an entity-ownership axis with a `data_entity_owner` subquery; that SQL does not exist (corrected below).

A compliance reviewer auditing "what did Bob the user do last week" cannot even express the question: the picker lists owners, the only "Owner" filter sitting right above it (`ownerIds`) filters by ENTITY ownership, and the "User"-labelled filter actually filters by ACTOR-via-owner-mapping. The two adjacent filters both pick from the same Owners list but bind to two different axes.

The doc-side framing (DOC-206) is the first mitigation. This PLT ships the structural fix.

Backend - the `userIds` predicate and the JOIN that fixes the axis to the ACTOR column:

```java
// ReactiveActivityRepositoryImpl.java:274-276  (the LSN-020 bind; was :272-273 in the retro, lines shifted)
if (CollectionUtils.isNotEmpty(userIds)) {
    conditions.add(USER_OWNER_MAPPING.OWNER_ID.in(userIds));   // values are OWNER ids, not user ids
    conditions.add(USER_OWNER_MAPPING.DELETED_AT.isNull());
}

// ReactiveActivityRepositoryImpl.java:156-158 (and :177-179, :198-200, :219-222) - the LEFT JOIN
.leftJoin(USER_OWNER_MAPPING)
    .on(USER_OWNER_MAPPING.OIDC_USERNAME.eq(ACTIVITY.CREATED_BY)  // joins on the ACTOR column
        .and(USER_OWNER_MAPPING.DELETED_AT.isNull()))
```

For contrast, the adjacent `ownerIds` filter binds to ENTITY ownership (`ReactiveActivityRepositoryImpl.java:268-273`): `DSL.exists(... OWNERSHIP.DATA_ENTITY_ID.eq(DATA_ENTITY.ID).and(OWNERSHIP.OWNER_ID.in(ownerIds)))`. The actor column `activity.created_by` is read in the JOIN + SELECT but is never bound by any WHERE predicate - so there is no actor-axis filter at all today.

(The earlier SQL pseudocode in this section asserted a `data_entity_owner` subquery joining `user_owner_mapping` on `user_id` - that query does not exist anywhere in the file; corrected 2026-06-10.)

## User-facing impact

- **WHO:** any operator using the Activity Feed (global `/activity` or the per-entity Activity tab) - most acutely a compliance / audit reviewer or a team lead trying to attribute activity to a person.
- **WHAT they do:** they open the filter labelled "User," expecting to pick a person and see what that person did. Verified by FE trace 2026-06-10: the dropdown is populated from the OWNERS list (`MultipleFilter.tsx:32-34`, `MultipleFilterAutocomplete.tsx:44-46`), so they are actually choosing an OWNER; their selection's `id` (an owner id) is stored as `userIds` (`MultipleFilterAutocomplete.tsx:83`).
- **WHAT they observe:** the feed narrows to "activity whose actor (`created_by`) is associated, via `USER_OWNER_MAPPING`, with the selected owner" - verified by BE trace 2026-06-10 (`ReactiveActivityRepositoryImpl.java:274-276` bind + `:156-158` actor JOIN). Concrete consequences, each code-settled:
  - A user who PERFORMED actions but has NO owner association is invisible to this filter (no `USER_OWNER_MAPPING` row -> never matches). This is the maintainer's first reported failure mode (LSN-020).
  - If a user's owner mapping changed over time, their past activity is attributed to whatever owner they currently map to. Second LSN-020 failure mode.
  - The operator cannot pick "a user" at all - the only thing selectable is an owner, and the "Owner" filter directly above (`ownerIds`) already exists but filters a DIFFERENT axis (entity ownership, `:268-273`). Two adjacent owner-populated filters, two different meanings, neither of which is "by user."
- **NOT what an earlier revision claimed:** it does NOT return "events on entities OWNED BY the selected user." There is no entity-ownership subquery on the `userIds` path (verified: the only entity-ownership predicate is the separate `ownerIds` filter). The mis-description is corrected in `## Where`.

## Why it matters

**Compliance / audit workflows are broken.** "What did Bob do" cannot be asked: the picker offers owners, not users; selecting Bob's owner returns "activity by anyone mapped to that owner," and a user with no owner mapping is unfilterable. A team lead asking "what did my team do this week" gets a result keyed on owner-mapping membership, not authorship.

**The doc has now been corrected (DOC-206).** But the UI label is still "User," it still picks owners, and operators who don't read the doc will continue to misread it as an actor filter. The structural fix is required to close the LSN-020 loop.

**LSN-020 class anchor.** This is the FIRST live-doc-tier confirmation of the LSN-020 family. The DQ Title filter (DOC-GAP-264) is structurally the same class. Fixing this surface is the canonical case of doc + code alignment on filter-axis semantic.

Severity is HIGH because:
- Compliance / audit use cases produce confidently-wrong answers.
- The same misleading framing surfaces at TWO entry points (global + per-entity) so the gap compounds.
- Doc mitigation is only as good as the operator's read-the-doc discipline; the structural fix closes the gap for everyone.

## Suggested fix

The clean ship is a real actor-axis filter that picks USERS (not owners) and binds to `activity.created_by`. Note this requires a USER-list source for the dropdown - today there is no user-list fetch on this filter at all (it reuses `fetchOwnersList`), so the FE work is more than a relabel.

**Option A - relabel to the truth (smallest, no real fix).** Change the UI label from "User" to something like "Owner (of actor)" and correct the OpenAPI param doc + live doc (DOC-206 does the doc part). Honest, but the filter remains owner-populated and owner-mapping-keyed - it still cannot answer "what did user X do," so this is a stop-gap, not a fix.

**Option B - add a true actor-axis filter alongside the existing one.** Introduce `actorUserIds` bound at SQL to `ACTIVITY.CREATED_BY` (the column is already JOINed/SELECTed, just never filtered), with a dropdown sourced from the platform's USER/identity list. Leave the current owner-mapping filter in place (renamed honestly). Operator picks the axis explicitly.

**Option C (recommended) - replace the mislabelled filter with the actor-axis one.** Rebind `userIds` (or a new `actorUserIds`) to `ACTIVITY.CREATED_BY`, source its options from users, and rename the existing owner-mapping-keyed filter to a non-"User" label if it is worth keeping at all:

```java
// ReactiveActivityRepositoryImpl.java - actor-axis predicate (created_by is already in scope)
if (CollectionUtils.isNotEmpty(actorUserIds)) {
    conditions.add(ACTIVITY.CREATED_BY.in(actorUsernames));   // resolve ids -> usernames, or bind usernames directly
}
```

```tsx
// the actor filter must source USERS, not owners:
<MultipleFilter filterName='actorUserIds' name={t('Performed by user')} /* fetch USERS */ />
```

The typical use case ("what did Alice do") becomes the default behaviour of the obviously-named filter. Spec change requires a sibling commit on `opendatadiscovery-specification` (param rename + new param). Backwards-compat: a temporary shim mapping the old `userIds` onto whatever the owner-mapping filter is renamed to would let existing API clients survive one release. (Earlier revisions of this section called the current `userIds` an "entity-ownership-axis filter" - it is not; it is an actor-via-owner-mapping filter. Corrected 2026-06-10.)

## How discovered

Doc-side correction ships via DOC-206 in the same triage batch. Confirmed against the maintainer's LSN-020 report (`retrospectives/LSN-020-*.md`).

Corrected 2026-06-10 (user-facing verification sweep):
- The mechanism was wrong: the `## Where` SQL pseudocode claimed `userIds` joins `data_entity_owner` and filters by entity ownership ("events on entities OWNED BY the user"). That query does not exist. Actual: `USER_OWNER_MAPPING.OWNER_ID.in(userIds)` over a LEFT JOIN on `USER_OWNER_MAPPING.OIDC_USERNAME = ACTIVITY.CREATED_BY` (`ReactiveActivityRepositoryImpl.java:274-276`, `:156-158`) - i.e. actor-via-owner-mapping, not entity-ownership.
- New load-bearing finding from the FE trace: the "User" filter's dropdown is populated from the OWNERS list (`MultipleFilter.tsx:32-34`), so the operator picks an owner, and the selected owner id is sent as `userIds` (`MultipleFilterAutocomplete.tsx:83`). The draft had not traced the FE options source.
- Stale line numbers refreshed (retro's `:272-273` is now `:274-276`).
- Severity unchanged (HIGH): the core mismatch HOLDS and the FE-picks-owners finding makes the trap worse, not better. The headline and `## Suggested fix` were rewritten to the verified mechanism. Same failure mode as the PLT-176 lesson: a UI-semantic claim partially shipped without tracing the FE options source and with a fabricated SQL shape.
