## What

When email notifications are configured, the mail-sender bean only applies the SMTP authentication and STARTTLS flags if the configured `notifications.receivers.email.protocol` value is **exactly** the lowercase string `smtp`. Any other spelling — most notably the uppercase `SMTP`, which is the conventional protocol identifier in JavaMail / Jakarta Mail (`Transport.send` examples, `mail.transport.protocol`, and most operator-facing SMTP documentation) — falls through to the `else` branch. The `else` branch sets `mail.transport.protocol` to the supplied value but **never sets `mail.smtp.auth` or `mail.smtp.starttls.enable`**. The result is a mail sender that connects without STARTTLS and without AUTH, even though the operator explicitly configured `smtp.auth: true` and `smtp.starttls: true`. There is no boot-time warning or log line — the misconfiguration is completely silent, and the operator only finds out when credentials traverse the network in cleartext or the SMTP relay rejects the unauthenticated session.

## Where

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/notification/config/NotificationConfiguration.java:63`

```java
if (emailProperties.getProtocol().equals("smtp")) {
    props.put("mail.transport.protocol", "smtp");
    props.put("mail.smtp.auth", emailProperties.getSmtp().getAuth());
    props.put("mail.smtp.starttls.enable", emailProperties.getSmtp().getStarttls());
} else {
    props.put("mail.transport.protocol", emailProperties.getProtocol());
}
```

The `.equals("smtp")` comparison is case- and whitespace-sensitive. The properties it gates are the only place STARTTLS and AUTH are ever enabled — see the backing config class:

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/notification/config/EmailSenderProperties.java`

```java
private String protocol;
private SmtpProperties smtp;

@Data
public static class SmtpProperties {
    private Boolean auth;
    private Boolean starttls;
}
```

## Why it matters

This is a **silent security downgrade**. An operator who writes `protocol: SMTP` (the documented JavaMail convention) together with `smtp: { auth: true, starttls: true }` reasonably believes they have a TLS-protected, authenticated mail path. In reality the bean starts cleanly, the application boots without warning, and notification email is sent over an unencrypted, unauthenticated channel:

- **Credentials may be transmitted in plaintext.** With AUTH silently disabled, the configured SMTP username/password is either not sent at all (relay rejects, notifications fail loudly) or — for relays that accept AUTH on an already-open plaintext connection — sent without the STARTTLS upgrade the operator asked for.
- **No diagnostic.** There is no boot warning and no log entry indicating STARTTLS/AUTH were dropped. The failure mode is invisible until a packet capture or a relay rejection surfaces it.
- **Affects every email-notification deployment** that uses anything other than the exact token `smtp`. Because the standard JavaMail/Jakarta Mail spelling is uppercase, this trap is easy to fall into.

Severity **high**: a configuration the operator explicitly set for transport security is silently ignored, with a plausible cleartext-credential exposure and no signal that anything is wrong.

## Suggested fix

1. Make the protocol comparison case-insensitive and trim-tolerant, e.g. `if ("smtp".equalsIgnoreCase(emailProperties.getProtocol().trim()))`. The `smtps` protocol should be handled explicitly as well rather than silently falling through (it currently lands in the `else` branch with no auth/STARTTLS wiring).
2. Add a boot-time warning when the resolved protocol disables STARTTLS or AUTH while the operator has set `smtp.auth`/`smtp.starttls`, so a downgrade is never silent. Logging the effective `mail.smtp.auth` / `mail.smtp.starttls.enable` values at startup would make the active posture auditable.

Open to alternatives — the core requirement is that an operator's STARTTLS/AUTH intent is never dropped without a loud signal.
