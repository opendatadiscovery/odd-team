## Description

Live `/permissions` line 88 documents `DIRECT_OWNER_SYNC` with a twelve-word description: "Allows associating a user with an owner without an approval request." This description omits a load-bearing security composition: when a `DIRECT_OWNER_SYNC`-holder POSTs `/api/owner_association_request` with an `ownerName` that does NOT exist in the catalog, `OwnerAssociationRequestServiceImpl` calls `OwnerService.getOrCreate(ownerName)` — a service-tier permission-bypass side-door (F-019 root facet `service_tier_get_or_create_permission_bypass_owner_create_side_door`, ref `OwnerServiceImpl.java:38-42`). The Owner row is minted; the permission check then auto-approves; `user_owner_mapping` is written. The requester is now bound to an Owner THEY THEMSELVES created with the name they chose.

Operator-visible consequence: operators reading the `/permissions` description grant `DIRECT_OWNER_SYNC` to non-admin Policies (e.g., a service-account Policy) with the mental model "this just speeds up the admin-approval step." Reality: the holder can also self-mint arbitrary Owner names and self-bind. Cascade hazard — subsequent Policy `dataEntity:owner == 'X'` conditions become attacker-controllable (the attacker picks `X`).
