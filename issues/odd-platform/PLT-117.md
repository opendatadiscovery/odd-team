## What

The platform's backend deliberately PRESERVES per-dataset Data Quality (DQ) history for **soft-deleted** datasets — every DQ read path resolves existence with `existsIncludingSoftDeleted` (not `exists`), an explicit forensic-preservation choice so an operator can answer "what was this dataset's DQ state just before it was deprecated/deleted?". But the **UI route silently undoes that choice for the human operator**: the `test-reports/*` route is wrapped in a `RestrictedRoute` gated on `isAllowedTo={!isStatusDeleted}` with `redirectTo='../overview'`. An operator who navigates to the "Test reports" tab on a soft-deleted dataset is bounced to the Overview tab with no explanation — the API would serve the forensic data, but the screen that requests it is unreachable.

The result is a **cross-channel inconsistency**: two operators looking at the same soft-deleted dataset get different answers — a UI user sees no DQ history (redirected away), while a direct API caller gets the full history the backend preserves. The exact audit/forensic workflow the `existsIncludingSoftDeleted` design pays for is defeated at the surface the operator actually uses.

This is purely a UI-routing defect; the backend is correct and is the positive half of the contradiction.

## Why it matters

A core operator workflow — "the dataset was deprecated and soft-deleted; what was its DQ history just before deletion?" — is unreachable for a human operator through the UI. They are bounced to Overview with no message explaining why the Test-reports tab vanished. The platform built and pays for forensic preservation in the backend (`existsIncludingSoftDeleted` on every read) and then hides it from the one surface most operators use.

The silent cross-channel split is the sharper hazard: a UI user concludes "this deleted dataset has no DQ history" while the same data is one `curl` away via the API. An operator cannot trust the UI as a complete view of what the platform retains.

Severity **medium**: no data is lost or exposed (the backend still serves it; reads were already cross-owner/read-collaborative, so the redirect does not gate anything that the API gates), and the workaround (call the API directly) exists — but it defeats a deliberately-built capability at the human surface and produces a confusing, unexplained redirect.

## Suggested fix

Two options (the reflection's `proposed_fix_anchor`):

1. **Align the UI with the backend** — drop the `isAllowedTo={!isStatusDeleted}` gate on the `test-reports/*` route in `DataEntityDetailsRoutes.tsx:56-69` so the tab renders for soft-deleted datasets, matching the backend's `existsIncludingSoftDeleted` preservation. (Preferred — it makes the UI honour the capability the backend already provides.)
2. **Document the asymmetry as intentional** — if hiding the tab for soft-deleted datasets is a deliberate product choice, surface it (e.g. render the tab in a read-only "archived" state, or show an explicit "DQ history for deleted datasets is available via the API" message instead of a silent redirect), and document it.

Open to alternatives — the load-bearing requirement is that the human operator can reach the DQ history the backend preserves, or is told clearly why they cannot.
