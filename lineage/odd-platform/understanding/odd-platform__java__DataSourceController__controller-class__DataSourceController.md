# DataSourceController — semantic understanding

## understanding

The thin REST controller (60-line implementation at `DataSourceController.java:1-60`) backing the Management → Datasources tab of the ODD Platform UI. It implements the OpenAPI-generated `DataSourceApi` interface (line 18) for the 5 operations defined in `odd-platform-specification/openapi.yaml:425-527`: list (`getDataSourceList` lines 22-28), create (`registerDataSource` lines 30-36), update (`updateDataSource` lines 38-45), delete (`deleteDataSource` lines 47-51), and token regeneration (`regenerateDataSourceToken` lines 53-59). Every handler is a 3-5 line proxy that extracts inputs from the OpenAPI-generated method signatures, delegates to a single `DataSourceService` (constructor-injected at line 19), and wraps the reactive result in `ResponseEntity::ok` — there is NO business logic at the controller layer, NO programmatic permission checks, NO request validation beyond what `DataSourceFormData` / `DataSourceUpdateFormData` schemas declare. Authorization is path-based via `SecurityConstants.SECURITY_RULES` (4 entries at SecurityConstants.java:116-126: `DATA_SOURCE_CREATE` on POST, `DATA_SOURCE_UPDATE` on PUT, `DATA_SOURCE_DELETE` on DELETE, `DATA_SOURCE_TOKEN_REGENERATE` on PUT /token) — but **`GET /api/datasources` has NO matching rule**, so listing falls through to the `pathMatchers("/**").authenticated()` catch-all at AuthorizationCustomizer.java:29-30. ANY authenticated UI user can list all datasources in the catalog regardless of their role/policy — the read-collaborative posture of P-09 (Security pillar) extends here. **The load-bearing architectural distinction this controller embodies**: it is DISJOINT FROM the S2S ingestion path `IngestionController.createDataSourceEntity` (batch-P sidecar primary source) — same underlying `data_source` table on the persistence side, but completely separate request paths (`/api/datasources/*` vs `/ingestion/datasources`), separate auth filters (UI auth chain + RBAC permission vs `IngestionDataSourceFilter` + collector token in `Authorization: Bearer`), separate service classes (`DataSourceServiceImpl` vs `DataSourceIngestionServiceImpl`), separate mutation semantics (full-form REPLACE via MapStruct's `@MappingTarget` for the UI update vs UPSERT-by-ODDRN narrowing to ONLY name+description for the S2S path — the SOURCE OF the silent-overwrite class of operator surprise per REFACTOR-423). This 5th-vertex sidecar completes the ADR-CANDIDATE-142 triangulation by COUNTERFACTUAL: the S2S partial-merge narrowing is a path-specific choice, not a global one — UI operators have FULL CONTROL of every form field; collectors have CONSTRAINED CONTROL of identity + 2 mutable fields. The intent visible across this 5-vertex evidence: collectors are tenants in the data-source space; operators are admins.

## performance

- hot_paths:
  - "getDataSourceList (lines 22-28): runs synchronously per request; paginated (page/size); the SQL is a CTE + 2-LEFT-JOIN against NAMESPACE + TOKEN (per batch-R sidecar primary source ReactiveDataSourceRepositoryImpl.listDto lines 58-82). For typical catalog sizes (<500 datasources), sub-100ms. The count query (REFACTOR-425) runs in parallel with the page query inside `jooqQueryHelper.pageifyResult`. For >5k datasources, the JOIN cost grows linearly; no index on `name` for the FTS-bypassed startsWithIgnoreCase predicate (the FTS vector exists but listDto bypasses it)."
  - "updateDataSource (lines 38-45): @ReactiveTransactional holds 1 R2DBC connection for the duration; the chain is `getDto → namespaceService.getOrCreate (writes if absent) → updateDataSource (writes) → updateSearchVectors (writes 2 FTS rows)`. Worst-case 4 sequential DB calls inside the transaction; for typical operator-edits with no namespace change, 2 sequential DB calls."
  - "regenerateDataSourceToken (lines 53-59): NOT @ReactiveTransactional — the 3-call chain `getDto → tokenGenerator.regenerateToken (CPU only) → tokenRepository.updateToken (DB write)` is not isolated; failures between steps 2 and 3 leave the in-memory state ahead of DB."
- throughput_characteristics:
  - "single-item PER REQUEST per endpoint — there is no bulk-create / bulk-update / bulk-delete surface on the UI side"
  - "The list endpoint is paginated; clients must iterate pages to enumerate the catalog"
  - "All endpoints are reactive Mono/Flux — non-blocking but per-call DB round-trip"
- resource_allocation:
  - "Per-handler memory: small — only the FormData / DataSourceList objects fit in memory; payloads are KB-sized typically"
  - "R2DBC connection: 1 per @ReactiveTransactional service call (3 of 5 endpoints)"
  - "No outbound HTTP calls (no external service integration on this controller; the token generator is local CPU; the FTS update is in-DB)"

- known_performance_gaps:
