- **ADR-CANDIDATE-061** (NEW 2026-05-12F): The ingestion data-entity endpoint follows the **OpenAPI-contract-driven path** with **controller-side semantic validation** — `IngestionController.postDataEntityList` is `@Override` on `IngestionApi` (no `@PostMapping`), and the empty-payload guard is a one-line `.filter(...).switchIfEmpty(...)` on the controller body, NOT delegated to OpenAPI schema validation. The split codifies "schema describes shape, code enforces semantics"
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar (`postDataEntityList`) but the pattern composes with ADR-CANDIDATE-001 (OpenAPI-contract-driven path) and explicitly contrasts with the schema-side absence of `minItems: 1` for the `items` array — the maintainer's decision was to enforce non-emptiness in code, not in the schema
  - **Surfaced by**:
    - `odd-platform__java__IngestionController__controller-method__postDataEntityList.md:implicit_adrs.[2]` ("Empty-payload validation is co-located with the controller (one-line guard), not delegated to OpenAPI schema validation" — evidence: `IngestionController.java:40-42` (`.filter(del -> CollectionUtils.isNotEmpty(del.getItems())).switchIfEmpty(Mono.error(() -> new BadUserRequestException(\"Ingestion payload is empty\")))`) + odd_api.yaml:64-76 (`DataEntityList` schema — `data_source_oddrn` is `required: true`, `items` is NOT declared `minItems: 1`) — intent_anchor: the OpenAPI schema does NOT enforce `items: minItems: 1` — the maintainer chose to enforce non-emptiness in code instead. This is a deliberate "schema describes shape, code enforces semantics" split.)
  - **Decision statement**: ODD's ingestion endpoint applies a two-layer validation discipline: (a) **schema layer** — `odd_api.yaml:64-76` declares `DataEntityList.data_source_oddrn: required: true` (shape constraint enforced by OpenAPI-generator + Spring's `@Valid`); the `items` array is NOT declared `minItems: 1` because the OpenAPI generator's emit-side enforcement would surface as a generic 400 "Validation failed" with no operator-friendly message; (b) **controller layer** — a one-line guard at `IngestionController.java:40-42` (`.filter(del -> CollectionUtils.isNotEmpty(del.getItems())).switchIfEmpty(Mono.error(() -> new BadUserRequestException("Ingestion payload is empty")))`) intercepts empty payloads BEFORE the service call, with a precise application-specific error message and HTTP 400. The decision codifies: (i) schema-validation owns shape (types, required fields, format) that is generic-and-machine-checkable; (ii) controller-side validation owns semantics (non-emptiness, application-specific invariants) with operator-friendly error messages; (iii) the two layers compose — a payload that passes schema validation may still be rejected by controller validation. Trade-off: a consumer validating against the published OpenAPI schema would PASS an empty `items: []` payload — the platform rejects it. The reverse is not true (a valid schema payload always passes the code check). The split is intentional — the maintainer chose application-specific error messages over generic schema-validation noise, accepting that consumers cannot rely solely on the published schema to know what the platform will accept.
  - **Wisdom test**: PASS. The deliberate one-line `.filter(...).switchIfEmpty(...)` construction is the intent anchor — the maintainer could have added `minItems: 1` to the schema (declarative + machine-checkable + spec-aligned) or relied on the downstream service to reject empty lists. The choice to enforce at the controller boundary with an application-specific error message is the positive design decision. Structural for every future ingestion endpoint on the platform.
