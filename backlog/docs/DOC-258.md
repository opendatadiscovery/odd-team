## Description

The live `/authorization/policies` page (WebFetched 2026-05-27, 200 OK) mentions `dataEntity:owner:title` exactly once ("data entity's owner title") in the Policy-conditions list. It is **silent on where Title vocabulary comes from, that any authenticated user can mint a new Title by typing it into an ownership form, that the directory is case-sensitive and unbounded, and that there is NO Management UI tab for Titles**.

**Caveat 1 — Title is a free-text auto-create surface that silently defeats Policy conditions referencing `:owner:title` (F-036a).** `TitleServiceImpl.java:18-22` is `getOrCreate(name)` = `getByName.switchIfEmpty(create)` — accepts any string verbatim. NO `@Pattern`, NO `@Size`, NO normalisation (case-folding, trimming, slug-deduping). Two operators typing `'Data Steward'`, `'data steward'`, `'DATA STEWARD'`, `' Data Steward '`, `'data-steward'` each accumulate as **distinct rows** in the `TITLE` table. A Policy condition `dataEntity:owner:title == 'Data Steward'` silently misses every other-casing variant — every operator carrying the lowercase variant gets access denied with NO operator-visible signal. `V0_0_3__add_ownership.sql:1-8` declares `title.name varchar(128)` with **no CHECK constraint**.

The two production callers (`OwnershipServiceImpl.java:53,107` + `TermOwnershipServiceImpl.java:35`) reach the auto-create path from `POST /api/dataentities/{id}/ownerships` and `POST /api/terms/{id}/ownerships` — gated by `DATA_ENTITY_OWNERSHIP_CREATE` / `TERM_OWNERSHIP_CREATE`. **Any user holding either permission mints new Title rows** that immediately become part of the Policy-condition vocabulary.

**Caveat 2 — There is NO Management UI tab for Titles; the directory grows monotonically; no admin curation surface (F-036b).** `ManagementTabs.tsx:19-50` enumerates 9 tabs (Namespaces / Datasources / Integrations / Collectors / Owners / Tags / Associations / Roles / Policies) — **NO Titles entry**. `managementRoutes.ts:4-14` declares 9 ManagementRoutes — NO Titles entry. The closest operator-visible Title surface is the TitleFilter in `/data-quality/runs` (a READ surface). All title mutations happen via the side-channel — typing a never-seen string into an ownership-grant modal mints a row. **Operators cannot review / merge / delete duplicate or typo'd titles via the UI; the directory grows monotonically.**

## Acceptance Criteria

- [ ] `policies.md` extends the `dataEntity:owner:title` condition row with a **multi-paragraph Known Limitation block** covering both caveats:
  - Caveat 1 — name where Title vocabulary comes from (the `TITLE` table); name the auto-create side-channel via the two ownership endpoints; explicitly state the case-sensitivity + no-normalisation behaviour; give the concrete failure example (`'Data Steward'` vs `'data steward'` — Policy silent miss). Recommend operators (a) author Policy conditions to enumerate variants explicitly (`title IN ('Data Steward', 'data steward', 'DATA STEWARD')`), OR (b) restrict the two `*_OWNERSHIP_CREATE` permissions to vocabulary stewards, OR (c) deploy a periodic SQL job to consolidate typo-variants until a curated allowlist ships.
  - Caveat 2 — name the missing Management UI surface; clarify operators must SSH to the database to inspect / curate the title vocabulary today. Recommend treating any new Title-related operator workflow as a future-feature dependency.
