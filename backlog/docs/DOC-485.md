## Description

The Alerting page's **## Known UX limitations** section publishes a `{% hint style="warning" %}` documenting the
**#1803 Defect 2**: *"Clicking the `Resolve` button on an alert immediately fires the status change — there is no
confirmation dialog … an accidental click on `Resolve` destroys the audit history."*

odd-platform#1803 / CTRIB-034 (milestone 0.29.0) closes this: a confirmation dialog now guards Resolve/Reopen on
**both** the per-entity Alerts tab and the global `/alerts` page, and the per-entity tab reflects the status change
in place without a refresh (Defect 1). Once 0.29.0 ships, the "there is no confirmation dialog" statement is FALSE.

The edit (already on `release/0.29.0` @ `ae43375`):
- Rewrote the warning hint (now `info`) to describe the new safeguard — a confirmation dialog before the flip +
  the per-entity tab reflecting the change without a reload.
- Preserved the export-before-resolve advice, re-scoped to a **deliberate** resolve: the confirmation guards an
  *accidental* resolve, but the **manual-resolve retention bug** above (lines 127-133, unchanged by #1803) still
  hard-deletes a deliberately-resolved alert on the next housekeeping cycle, so the audit-export advice stands.

## Why on the release train (not docs main)

The correction describes **0.29.0 behaviour** (the fix is unreleased). The latest published release (0.28.0) still
has NO confirmation dialog, so the live caveat is TRUE for it; publishing the correction to docs `main` now would
make the live manual describe behaviour 0.28.0 does not have. It rides `release/0.29.0` and publishes when 0.29.0
ships (`adrs/drafts/release-train-doc-gating.md`, G-C11).
