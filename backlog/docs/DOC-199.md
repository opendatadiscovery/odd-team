## Description

The live Business Glossary page is silent on the TermsForm (create / edit) authoring behaviour and on the Term Overview right-rail tag/owner editor affordances. Six NET-NEW caveats land here — three are security caveats (Markdown XSS, namespace bypass, tag bypass) and three are operator-UX correctness caveats (duplicate-check fragility, silent failure on reject, queryClient invalidate of undefined). Together they form the "TermsForm / right-rail" extension of DOC-177's operator-caveats H2.

**Caveat 11 — Term definition Markdown editor accepts `<script>` payloads — 3rd Term-specific surface of the F-004 stored-XSS family (F-154d).** `TermsForm.tsx:168-186` renders the definition field as `<Markdown {...field} editor height={200} />`. The editor accepts arbitrary Markdown including raw HTML and inline JavaScript. On submit, the raw string round-trips through `TermServiceImpl.createTerm` / `updateTerm` (no sanitisation per F-002 batch U + F-004 batch U). The render side (TermDefinition.tsx → Markdown.tsx) does no rehype-sanitize. Any operator with `TERM_UPDATE` permission can plant `<script>` payloads via this dialog; the F-004 family stored-XSS triggers for every authenticated viewer of the Term overview. 3rd Term-specific surface (term overview render, the rev-13 dictionary description, and now the authoring entry); 6+th overall F-004 family surface.

**Caveat 12 — NamespaceAutocomplete silently creates novel namespaces; TERM_CREATE bypasses NAMESPACE_CREATE (F-154e).** `TermsForm.tsx:161-167` renders `<NamespaceAutocomplete>` with no creation gate. A user typing a namespace name not in the dropdown submits the form; on the backend, the string flows to `namespaceService.getOrCreate(namespaceName)` — bypassing `NAMESPACE_CREATE`. The UI gives no signal that typing a novel namespace will create one. An operator granted `TERM_CREATE` but explicitly not `NAMESPACE_CREATE` (separation of duties) can still mint namespaces this way.

**Caveat 13 — TagsEditForm silently creates novel tags; TERM_TAGS_UPDATE bypasses TAG_CREATE (F-156b).** `TagsEditForm` is the AUTHORING entry point for the F-002 batch K facet `tag_create_bypass_via_upsert_tags`. An operator with `TERM_TAGS_UPDATE` (but without `TAG_CREATE`) types a novel tag name in the edit form; the backend `tagService.getOrCreateTagsByName` silently creates a tag. UI provides no signal. Same architectural class as Caveat 12 (namespace bypass); reflects a platform-wide "soft-create on read-binding" pattern that operators authoring RBAC policies need to know about.

**Caveat 14 — TermsForm duplicate check is fragile at scale and CREATE-mode-only (F-154a).** `TermsForm.tsx:71-75` dispatches `fetchTermsSearchResults({searchId, page: 1, size: 1000})` on mount; line 84 gates the duplicate detector on `if (!term?.id)` — CREATE-mode only. Three stacking issues: (a) `size: 1000` is hardcoded — catalogs of 1001+ terms silently skip the check for the 1001th term; (b) the check ONLY fires in CREATE mode — the EDIT path can rename a term to collide with another in the same namespace without warning; (c) the backend uniqueness constraint is the authoritative gate but the service has no graceful-error path documented, so the client check is the only operator-visible signal.

**Caveat 15 — TermsForm dispatch chain has no .catch handler; dialog stays open on backend reject (F-154b).** `TermsForm.tsx:100-111` runs `dispatch(createTerm|updateTerm).unwrap().then(...)` with NO `.catch(...)`. If the backend rejects (uniqueness violation, validation failure, RBAC mismatch), the chain rejects silently; the dialog stays open with the form filled in and no error message renders. LSN-024-shaped silent-empty class. The Alert component scaffolding already exists at `TermsForm.tsx:50, 122-147` — the failure mode is purely a missing wire-up.

**Caveat 16 — `queryClient.invalidateQueries({queryKey: ['term', termId]})` uses route termId in CREATE mode where termId is `undefined` (F-154c).** `TermsForm.tsx:105-108` invalidates by route termId in both CREATE and EDIT modes. In CREATE mode, the route termId is `undefined` / `NaN` (per F-024 batch ZH parseInt propagation). The invalidate fires for `['term', undefined]` — invalidates nothing OR invalidates the wrong cache slot. Future cached lookups for `['term', undefined]` accumulate dead cache entries.
