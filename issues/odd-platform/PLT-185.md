## What

When a user fills in the "Add datasource" / "Edit datasource" dialog and the backend **rejects** the save (validation error, duplicate ODDRN, server error), the form still resets every field and the dialog closes - wiping all of the user's typed input. They are left with only a transient error toast and an empty (or closed) form, and must re-type everything from scratch. The reset fires on failure because the submit handler resets unconditionally on the dispatched promise's `.then(...)`, and the thunk wrapper resolves (rather than rejects) the dispatched promise even on error.

## Where

`odd-platform-ui/src/components/Management/DataSourcesList/DataSourceForm/DataSourceForm.tsx:78-80` - `clearState()` (which calls `reset()`) runs in `.then(...)`, with no success/failure branch:

```tsx
    ).then(() => {
      clearState();
    });
```

`clearState` is just a `reset()` (`DataSourceForm.tsx:65-67`), and the dialog is told to close on the "submitted" flag derived from the redux loaded-status (`handleCloseSubmittedForm={dataSource ? isDataSourceUpdated : isDataSourceCreated}`, `DataSourceForm.tsx:165`).

The reason `.then()` runs even on failure is the shared thunk wrapper - `odd-platform-ui/src/redux/lib/handleResponseThunk.ts:34-42` - whose `catch` block calls `rejectWithValue`, which **resolves** the dispatched action promise (it does not re-throw), so the caller's `.then()` always fires:

```ts
    } catch (err) {
      const errResp = await getErrorResponse(err as Response);
      if (!options.switchOffErrorMessage) {
        await showServerErrorToast(err as Response);
      }
      return thunkAPI.rejectWithValue(errResp);
    }
```

(`registerDataSource` / `updateDataSource` both go through this wrapper - `odd-platform-ui/src/redux/thunks/datasources.thunks.ts:34-60`.)

## Why it matters

This is **loud** (the user sees a toast) but **destructive of their work**: on any reject - most commonly a server-side validation failure the client could not pre-empt, e.g. a duplicate ODDRN - the entire form is discarded. For the create flow the cost is re-entering the name, ODDRN, namespace, and description; for a user who carefully composed an ODDRN this is real friction and a likely source of abandonment. It affects every operator who registers or edits a data source and hits a backend-side validation error. No data loss in the database and no security impact, so severity is medium, but it is a clear correctness defect in the submit flow: a failed save must never clear the user's input.

## Suggested fix

Gate the reset/close on success, and surface the server error inline instead of only as a toast:

1. In `DataSourceForm.tsx`, branch on the dispatched result - use `.unwrap()` (or check `registerDataSource.fulfilled.match(result)`) and only call `clearState()` in the fulfilled branch; in the rejected branch keep the form open and populated.
2. Drive the dialog-close flag off the same success signal so the modal does not close on a reject.
3. Show the rejected payload (`errResp`) as inline `errorText` on the form so the user sees *why* the save failed without losing context.

Alternatively (broader, affects all consumers), have the submit-site await `dispatch(...).unwrap()` inside a try/catch - but the minimal, local fix is the success-gated reset above.

## How discovered

Surfaced during the 2026-06-08 feature-reflection contradiction harvest on F-031 (Data Source management). The reflection flagged the clear-on-failure behaviour as a user-facing contradiction: the success-only intent of "clear the form after submit" against a thunk wrapper that resolves on error. DOC-334 tracks the **symptom** on the documentation side (a note that a failed save loses input) but explicitly declines the code fix; this issue is the code-side fix DOC-334 deferred, and is therefore distinct from it.
