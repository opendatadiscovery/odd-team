  - **Decision statement**: ODD's data-entity lifecycle is a four-decision composition: (1) **status-as-settable-property** — `PUT /api/dataentities/{id}/statuses` accepts a target enum value in the body; there are NO per-transition endpoints (no `/deprecate`, `/delete`, `/restore`). The operation summary reads "Update status to data entity / Update deprecation status to data entity" — framing it as a setter, not a transition. (2) **closed five-member enum** — `UNASSIGNED, DRAFT, STABLE, DEPRECATED, DELETED` (`DataEntityStatusEnum.java:24-34` + `DataEntityStatusDto.java:11-27` + `components.yaml:802-820`); clients cannot introduce new states without an OpenAPI + DTO change. (3) **`isSwitchable` flag-encoded auto-transition** — `DataEntityStatusDto` carries a second constructor arg `isSwitchable` (`DRAFT(2, true)`, `STABLE(3, false)`, `DEPRECATED(4, true)`, `DELETED(5, false)`). When `isSwitchable=true`, the status carries a `statusSwitchTime` field; at the time threshold, the auto-flip-to-DELETED fires via the scheduled `DataEntityStatusSwitchJob` (every 10 minutes, ShedLock-elected). (4) **soft-delete-as-deletion-model** — `DELETED` is a state in the database, not a row removal. `DataEntityInternalStateServiceImpl.softDeleteDataEntities` (line 106) flips the entity's status to DELETED + cascades to lineage/group-relations/statistics. The physical purge (hard DELETE on the row) is deferred to `DataEntityHousekeepingJob` after the operator-configurable TTL window (`housekeeping.ttl.data-entities-days`, default 30). Trade-off accepted: (i) the status-flip-vs-physical-purge separation enables soft-delete recovery (via `restoreDataEntities`) and audit-trail preservation; (ii) the `isSwitchable` flag's structural encoding makes the auto-transition rule self-documenting at the enum layer (vs. a runtime config); (iii) the closed-enum forecloses extensibility but enables compile-time exhaustiveness checking. Composes with ADR-CANDIDATE-055 (soft-deleted entities readable by-id with `isStale=true`) — together they describe the lifecycle from soft-delete to TTL-purge. **(NEW 2026-05-19H batch H)** ADR-CANDIDATE-068 (two-tier soft-delete inheritance taxonomy) is the architectural generalisation — this ADR is the canonical RICH-LIFECYCLE OVERRIDE case study; the override pattern at `ReactiveDataEntityRepositoryImpl.java:103, 109-123` is the implementation-side intent anchor for both ADRs.
