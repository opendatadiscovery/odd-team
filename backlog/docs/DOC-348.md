## Description

Tag names accepted by the platform are stored **verbatim** with no server-side validation on any of the write paths — no trim, no length cap, and no charset / pattern restriction. The OpenAPI schema for the create form imposes nothing either (`TagFormData.name` is a bare `type: string`, components.yaml:337-345 — no `maxLength`, no `pattern`). The service helper that materialises tag rows (`TagServiceImpl.divideTagsByExistence`, TagServiceImpl.java:144-159) takes each incoming name `n` and builds `new TagPojo().setName(n).setImportant(false)` directly — the raw string is written as the directory row's name.

Consequences for an operator:

- **Distinct-row pollution from whitespace / casing.** Because the name is stored as-is and matched by exact-equality (`listByNames` / `existingTagNames.contains(n)`), `' tag '` (leading/trailing space) and `'tag'` mint two separate directory rows. The page already documents the case-sensitivity sibling of this (`finance` vs `Finance`, tagging.md:87), but not the whitespace / unbounded-length / arbitrary-charset surface.
- **Directory as a pollution / DoS surface.** Four write paths reach this same unvalidated helper, and none of the non-`TAG_CREATE` paths require the stewardship permission. An over-long or junk-charset name (or a flood of near-identical whitespace variants) lands in the global `GET /api/tags` directory, the Catalog Overview "Top tags" strip, and the Search Tag-facet seed list — surfaces every user sees. There is no cap to bound this.

The four tag write paths that share the unvalidated helper (already enumerated on the page's five-mint-paths table, tagging.md:73-81): `POST /api/tags` (`bulkCreate`, TagServiceImpl.java:38), `PUT /api/dataentities/{id}/tags` and the collector ingestion path (both via `getOrCreateTagsByName`, TagServiceImpl.java:80-86), `PUT /api/terms/{id}/tags` (`getOrInjectTagByName` / `getOrCreateTagsByName`), and `PUT /api/datasetfields/{id}/tags`. All converge on `divideTagsByExistence` → `setName(n)` with no normalisation.

This is **not** the same surface as PLT-142 (the dataset-**statistics** ingestion endpoint, `POST /ingestion/entities/datasets/stats`, validation gaps). PLT-142 is cross-linked as a related platform-side validation gap, but the fix is independent.
