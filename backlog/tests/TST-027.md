## Description

`DataQualityController.getSLA` returns the dataset's SLA-colour badge as an `image/png` `Resource` wrapped in a bare `ResponseEntity::ok` (`DataQualityController.java:42-48`) — it sets **no** `@CrossOrigin`, **no** `X-Frame-Options`, and **no** `Cache-Control: private`. The resolver it delegates to (`CachingByteArraySLAResourceResolver.resolve`, `CachingByteArraySLAResourceResolver.java:18-42`) returns a classpath PNG with no response headers either. Meanwhile the platform installs a **global** CORS `WebFilter` that unconditionally adds `Access-Control-Allow-Origin: *` to every response with no `Access-Control-Allow-Credentials` (`CORSConfiguration.java:24-27`). The harvest concern: under cookie-based auth, the SLA badge — which leaks a dataset's trust signal (RED/YELLOW/GREEN, F-022) — is exposed to an embedding page. A plain `<img>`/`<iframe>` embed is not subject to CORS at all and, with no `X-Frame-Options`, an attacker page can frame the badge and (combined with the absent `Cache-Control: private`) the user's browser may cache and render the authenticated colour cross-origin. This is the F-022 facet `sla_badge_png_no_etag_no_cache_control_bi_dashboard_refetch_every_render` (hypothesis H-009) extended to its security edge.

**Why this is a probe, not a filed bug (auth-mode + CORS dependent).** Whether the colour actually leaks depends on the deployment's auth posture: under `AUTH_TYPE=DISABLED` the endpoint is anonymous and the badge is public by design (no exposure beyond what's intended); under LOGIN_FORM/OAUTH2/LDAP the cookie-scoped badge with wildcard-origin + no frame/cache headers is the exposure vector. The wildcard `Access-Control-Allow-Origin: *` (`CORSConfiguration.java:24`) cannot be combined with credentials per the Fetch spec, so a credentialed cross-origin `fetch()` is browser-blocked — but framing/`<img>` is not. The probe must MEASURE which surfaces leak under which auth mode before any code change or caveat is asserted; the harvest assigns it `PENDING-F-022-4`.

**Typed gate: characterization-pin (LSN-029).** No upstream fix is in flight; the test pins the CURRENT header posture. It asserts that `getSLA` responds with **no** `X-Frame-Options` and **no** `Cache-Control: private` header (the present-day state). It goes RED the instant a hardening fix adds those headers (or scopes the wildcard CORS), at which point the assertion inverts to `@regresses` per the LSN-029 flip protocol. Never `@Disabled`.
