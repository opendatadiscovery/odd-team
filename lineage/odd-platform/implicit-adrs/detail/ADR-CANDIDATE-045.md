- **ADR-CANDIDATE-045** (NEW 2026-05-12D): Housekeeping is a separate subsystem from partition management — the codebase deliberately splits the `housekeeping/` package (schedule-driven cleanup of rows by TTL) from the `partition/` package (structural range-partition lifecycle), with two distinct schedulers, two distinct ShedLock names, and two distinct advisory-lock contexts. The two-package coupling is encoded explicitly at type level: `EmptyPartitionsHousekeepingJob extends ... implements HousekeepingJob` (participates in housekeeping scheduler but consumes `PartitionService`)

  - **Decision statement**: ODD's data-lifecycle architecture is split into two subsystems: (a) `housekeeping/` — TTL-driven row cleanup, scheduled every 15 minutes via Spring `@Scheduled(fixedRate=15, MINUTES)` + ShedLock name `housekeepingJob`, deletes individual rows by age (`AlertHousekeepingJob`, `SearchFacetsHousekeepingJob`, `DataEntityHousekeepingJob`); (b) `partition/` — structural range-partition lifecycle, scheduled nightly at `00:01` via cron + ShedLock name `partitionCreationJob` + Postgres advisory lock id 90 at boot, creates new partitions ahead of cadence (`ActivityTablePartitionManager`, `MessageTablePartitionManager`). The two subsystems intersect at one place: `EmptyPartitionsHousekeepingJob` (an abstract `housekeeping/job/` class that consumes `PartitionService` — the type signature explicitly names BOTH concerns) and its two concrete subclasses (`ActivityEmptyPartitionsHousekeepingJob`, `MessageEmptyPartitionsHousekeepingJob`) which run on the housekeeping cadence but invoke partition-empty-detection logic. The intentional split codifies "row-level cleanup ≠ structural lifecycle" — partition CREATE is deployment-time-critical (no partition for tomorrow's date = boot-time failure), partition DROP-when-empty is best-effort cleanup. Trade-off accepted: more package complexity in exchange for explicit responsibility boundaries; a future maintainer who proposes "consolidate all delete-by-age operations into housekeeping" must contend with this ADR's structural separation.
  - **Wisdom test**: PASS. The two-package coupling at type level (`EmptyPartitionsHousekeepingJob extends ... implements HousekeepingJob`) is the intent anchor — the maintainer could have either (a) folded partition-empty-drop into the partition manager (single package, single scheduler), or (b) kept it entirely inside housekeeping and reimplemented partition-detection. The choice to live IN housekeeping but CONSUME partition is the deliberate "two concerns, one intersection" structural decision. Structural for every future delete-shaped subsystem.
