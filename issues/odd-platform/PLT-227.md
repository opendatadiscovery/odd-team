## What

Several **operator-facing, data-entity-scoped mutations emit no Activity event** - they carry no `@ActivityLog` annotation and make no programmatic activity call - so they are invisible on both the global Activity Feed and the per-entity **Activity** tab. There is no in-platform record of who performed them or when.

This is the **Class A** half of the platform's audit gap, and it is distinct from the schema-rooted Class B gap tracked in **PLT-062**:

- **Class A (this item) - the mutation already binds to a `data_entity`, so the existing audit schema fully supports it.** The `activity` table requires `data_entity_id bigint NOT NULL` (`V0_0_48__add_activity.sql`); these mutations already have that id. Closing the gap is the **cheap pattern**: add `@ActivityLog` + a new *data-entity-scoped* `ActivityEventTypeDto` value, mirroring the existing audited services (`DataEntityServiceImpl`, `TermServiceImpl` term-*assignment* ops, `OwnershipServiceImpl`). **No schema migration, no ADR.**
- **Class B (PLT-062) - the subject is NOT a data entity** (Policy / Role / Owner-lifecycle / Term-lifecycle / Namespace / Datasource / Collector). The `NOT NULL` FK structurally rejects those rows; closing that gap needs an ADR + schema migration + a ~21-value enum extension. Heavier, later.

The maintainer's canonical example is Class A: **adding an attachment link to a data entity generates no audit trail.** Verified - the `link` table carries `data_entity_id` (CTRIB-019 reproduced `SELECT ... FROM link WHERE data_entity_id=1`), yet `LinkServiceImpl` has zero `@ActivityLog`.

## Where - verified Class A gaps (the seed; the full enumeration is the work)

`@ActivityLog`-coverage sweep of `odd-platform-api/.../service/**ServiceImpl.java` (2026-06-17). Audited universe today = 10 services / ~10 distinct wired event types; `ActivityEventTypeDto` declares 27 values, all data-entity-scoped. The Class A gaps below are mutations that **touch a `data_entity_id` but emit nothing**:

| Surface | Service (no `@ActivityLog`, no programmatic emit) | Mutating methods | data-entity binding |
|---|---|---|---|
| **Attachment links** (the maintainer's example) | `service/attachment/LinkServiceImpl.java` | `save`, `update`, `delete` | `link.data_entity_id` (proven, CTRIB-019) |
| **Attachment files** | `service/attachment/AttachmentServiceImpl.java`, `service/attachment/FileServiceImpl.java` | `saveLinks`/`updateLink`/`deleteLink`/`deleteFile` | scoped to the parent data entity |
| **Query Example <-> Dataset/Term relationships** | `service/QueryExampleServiceImpl.java` | `createQueryExampleToDatasetRelationship`, `deleteQueryExampleDatasetRelationship`, `removeTermFromQueryExample` | the linked Dataset/Term IS a data entity (same shape as the audited `TERM_ASSIGNMENT_UPDATED`) |

## Enumeration method (how to complete the Class A list before implementing)

The sweep above is the seed, not the closed set. To finalize the list, for every service mutation:
1. **Does it touch a `data_entity_id`?** (grep the repository/pojo for `data_entity_id`.) -> Class A candidate. If the subject is not a data entity -> it's Class B (route to PLT-062).
2. **Does it already emit?** Check for `@ActivityLog(...)` AND for a programmatic `ActivityService`/`ActivityCreateEvent` call (some events are emitted in code, not via the annotation - do not infer absence from the missing annotation alone; `feedback_verify_absence_by_reading_config`).
3. **Is it operator-meaningful?** Exclude query-time/facet ops (`updateFacets`, `removeUnselected`), internal counters (`DataEntityStatisticsServiceImpl.updateCounts`), collector-driven ingestion writes (metrics/ERD/graph ingestion), and low-level storage ops (`LocalFileUploadServiceImpl`) - these surfaced in the raw sweep but are not user mutations.
4. Confirm by **driving the running feature**: perform the mutation, open the entity's Activity tab, confirm nothing appears (the remaining live-drive check; see User-facing impact).

## User-facing impact

Code-settled (the absence is verified by reading the services + the schema): the listed mutations carry no `@ActivityLog` and no programmatic activity emit, so they cannot produce an `activity` row. **Not yet driven on a running instance** (`user_facing_verified: false`): the operator-visible confirmation - attach a link to a data entity, open its **Activity** tab, observe no entry - is the remaining check (a quick live drive, the audit analogue of PLT-018's runtime XSS check). What an operator/auditor cannot answer today: *"who attached this link / linked this query example to this dataset, and when?"* - there is no Activity Feed entry, no Activity-tab row, no platform log.

## Why it matters

These are the **cheap, high-value audit wins**: unlike PLT-062 (which needs an ADR + schema migration before a single event can fire), every Class A gap is closeable with a one-annotation + one-enum-value change that conforms to an existing, shipped pattern. Attachments and query-example links are routine collaborator actions on shared data assets; an operator investigating a change, or meeting an audit obligation (SOC2/GDPR change-history), currently has no trail for them even though the platform's audit infrastructure already supports the row. Closing Class A in 0.29.0 materially improves the audit posture without waiting on the heavier Class B migration.

## Suggested fix

Per Class A gap, mirroring `DataEntityServiceImpl` / `TermServiceImpl` assignment audit:
1. Add a new **data-entity-scoped** value to `ActivityEventTypeDto` (e.g. `ATTACHMENT_LINK_UPDATED`, `ATTACHMENT_FILE_UPDATED`, `QUERY_EXAMPLE_RELATION_UPDATED`) - these fit the existing `NOT NULL data_entity_id` schema; **do not** confuse with the Class B enum extension in PLT-062.
2. Annotate the mutation handler with `@ActivityLog(event = ...)` and supply the `data_entity_id` via the existing AOP parameter-extraction pattern (the annotated service captures old/new state the same way `DataEntityServiceImpl` does).
3. Add behavioural unit coverage (Mockito/StepVerifier asserting the activity event is produced) per gap, and one integration check that the Activity tab surfaces the new event.

No schema migration. No ADR (this conforms to the shipped `@ActivityLog` pattern; PLT-062 carries the architectural decision for the non-data-entity subjects).
