## What

Two defects in the housekeeping subsystem that ship together - one is data-loss-class (LSN-001 shape), one is consistency-with-platform-pattern. Both are small-surface code changes. A third surface (the `AlertHousekeepingJob` jOOQ operator-precedence bug) is **already covered by PLT-005** (filed 2026-04-25 during DOC-021 review); coordinate the fixes.

**Defect 1 - Java-side TTL fields default to 0; partial config override silently wipes RESOLVED alert history, search-facet history, soft-deleted-entity data, and cascading S3 attachments within 15 minutes of restart (HIGHEST - LSN-001 shape).** `HousekeepingTTLProperties.java:8-12` declares the three TTL fields as primitive `int` with **no initialiser**. Spring binds primitive `int` default `0` if an operator overrides `application.yml` and forgets to re-supply the `housekeeping.ttl.*` block (Helm chart values overlay, `--spring.config.location=` to a different profile, Spring Cloud Config slice, Kubernetes ConfigMap mount). The next 15-minute housekeeping cycle computes `cutoff = now() - 0 days = now()` and deletes EVERYTHING. `DataEntityHousekeepingJob.java:99-126` cascades through ~25 child tables; `fileUploadService.deleteFiles(...).block()` at line 142 deletes the corresponding S3 attachments. Recovery requires Postgres PITR + S3 versioning replay. No boot warning, no log line above DEBUG, no Prometheus counter.

**Defect 2 - `PostgreSQLSessionHousekeepingJobHandler` has no `@SchedulerLock` (multi-replica Nx DB load).** `PostgreSQLSessionHousekeepingJobHandler.java:13` is `@Scheduled(fixedRate = 1, timeUnit = TimeUnit.HOURS)` with NO `@SchedulerLock` annotation. INCONSISTENT with every other `@Scheduled` job in the codebase - the 5 HousekeepingJobManager-orchestrated jobs (ShedLock at `HousekeepingJobManager.java:26`), NotificationSubscriber (`notifications.wal.advisory-lock-id`), the two DataCollaboration jobs, ActivityTablePartitionManager (`partition.advisory-lock-id`). On a multi-replica `INTERNAL_POSTGRESQL` deployment, every replica runs `DELETE FROM SPRING_SESSION WHERE expiry_time < now()` hourly: Nx redundant DB load. Deletes are idempotent so correctness is preserved; the issue is wasted DB load + inconsistency-with-pattern + incident-response surprise.

## Why it matters

**Defect 1** is the failure mode of LSN-001 repeated on a different config family. The 2026-04 attachment-storage-default case wiped production data; this is the same shape on housekeeping (and the cascading attachment delete on `DataEntityHousekeepingJob` line 142 makes it worse - the data-entity-delete path also wipes the corresponding S3 attachments). Operators deploying via Helm with a values overlay that drops the housekeeping block - a common pattern when standardising per-env overlays - get silent total data wipe within 15 minutes of their first restart.

**Defect 2** is operator-cost not correctness - but the inconsistency-with-pattern is a debugger trap (operators reading `application.yml` see 4 `*.advisory-lock-id` keys; an additional Nx DB load on `SPRING_SESSION` doesn't trace back). Default `spring.session.timeout: -1` (never-expire) renders the job a no-op today; the moment an operator sets a finite timeout, the Nx load surfaces.

## Suggested fix

### Defect 1 - two options, both reasonable

**Option A (recommended) - field initialisers:**

```java
// HousekeepingTTLProperties.java:8-12
@Setter @Getter @ConfigurationProperties("housekeeping.ttl")
public class HousekeepingTTLProperties {
-    private int resolvedAlertsDays;
-    private int searchFacetsDays;
-    private int dataEntityDeleteDays;
+    private int resolvedAlertsDays = 30;
+    private int searchFacetsDays = 30;
+    private int dataEntityDeleteDays = 30;
}
```

Minimal-risk. Matches the safety floor in `application.yml`. Partial overrides no longer wipe everything.

**Option B - validators + fail-fast:**

```java
@Setter @Getter @Validated @ConfigurationProperties("housekeeping.ttl")
public class HousekeepingTTLProperties {
    @Min(1) private int resolvedAlertsDays = 30;
    @Min(1) private int searchFacetsDays = 30;
    @Min(1) private int dataEntityDeleteDays = 30;

    @PostConstruct
    void validate() {
        // hard-fail boot if 0 explicitly set
    }
}
```

More opinionated; rejects the (rare but possible) operator who actually wants `0` for one of the keys.

### Defect 2 - one option

```java
// PostgreSQLSessionHousekeepingJobHandler.java:13
+ import net.javacrumbs.shedlock.spring.annotation.SchedulerLock;
  ...
  @Scheduled(fixedRate = 1, timeUnit = TimeUnit.HOURS)
+ @SchedulerLock(name = "sessionHousekeepingJob", lockAtMostFor = "PT55M")
  public void cleanup() { ... }
```

Aligns with the 5 HousekeepingJobManager-orchestrated jobs. Pick a lockName distinct from `housekeepingJob` so the two don't share.
