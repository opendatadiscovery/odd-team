## What

The Reference Data / Lookup Tables surface (`ReferenceDataController`, `/api/referencedata/`) advertises a per-table RBAC model that the code does not enforce. Four distinct holes compound:

1. **Reads are ungated end-to-end.** There is no `LOOKUP_TABLE_*_READ` permission anywhere in the repo; only 9 `LOOKUP_TABLE_*` rules exist and all cover mutating endpoints. The 6 read endpoints + 4 search endpoints carry no `SecurityRule` and fall through to the global `.authenticated()` filter - so under `auth.type=DISABLED` they are anonymously reachable. The H1 "X lookup tables overall" counter leaks the platform-wide table population to every caller.
2. **Permissions are NO_CONTEXT (global), not per-table/per-owner.** A holder of e.g. `LOOKUP_TABLE_UPDATE` can modify *any* lookup table, not just those they own.
3. **Cross-table column PATCH via discarded path param.** `updateLookupTableField` drops the `{lookup_table_id}` path parameter - the controller calls the service with `columnId` only - so a caller authorized on table A can PATCH a column belonging to table B by spoofing the URL.
4. **Column PATCH/DELETE security-rule path mismatch (singular/plural).** The spec + controller serve `.../columns/{column_id}` (plural) but `SecurityConstants` registers the `LOOKUP_TABLE_DEFINITION_UPDATE`/`_DELETE` rules under `.../column/{column_id}` (singular). The path-matcher never matches the real request path, so those two gates never fire.

Sources: HARVEST-045, HARVEST-046, HARVEST-047, HARVEST-048, HARVEST-060, HARVEST-061 (doc-understanding harvest, 2026-05-29). Doc caveat tracked at `backlog/docs/DOC-294.md`.

## User-facing impact

Verified-trace 2026-06-10 (controller + SecurityConstants + generated contract all read); every one of the four holes is code-settled wiring. Auth-mode note: holes 2/3/4 are RBAC privilege-escalation surfaces that become *observable* only under a non-DISABLED auth mode (LDAP gives per-user roles locally); under the shipped default `auth.type=DISABLED` everything is permitAll, so hole 1's "reads anonymously reachable" is literally true and the mutation holes collapse into "anyone can do anything." The wiring is settled regardless of mode.

- **Hole 1 (reads ungated):** confirmed - the 9 `LOOKUP_TABLE_*` rules (`SecurityConstants.java:114, 325-354`) are all POST/PUT/PATCH/DELETE; there is no `LOOKUP_TABLE_*_READ` permission and no rule for `getLookupTableById`/`getLookupTableField`/`getLookupTableRowList`/the three search endpoints, so they fall through to `.authenticated()` (anonymous under DISABLED).
- **Hole 2 (NO_CONTEXT global):** confirmed - all 9 rules use `NO_CONTEXT` (the resolver import at `:11`), so a single `LOOKUP_TABLE_UPDATE` grant edits any table.
- **Hole 3 (cross-table column PATCH/DELETE):** confirmed - `updateLookupTableField` (`ReferenceDataController.java:131-141`) calls `referenceDataService.updateLookupTableField(columnId, item)` (`ReferenceDataServiceImpl.java:127`) discarding `lookupTableId`; `deleteLookupTableField` (`:160-164` -> service `:162`) does the same. Contrast `updateLookupTable` (`:122-129`, passes the id) and `updateLookupTableRow` (`:143-151`, passes both).
- **Hole 4 (singular/plural path mismatch):** confirmed and verified against the generated contract - `SecurityConstants` registers the column PATCH/DELETE rules at singular `.../column/{column_id}` (`:337, :341`), but the real spec/controller route is plural `.../columns/{column_id}` (generated `ReferenceDataApi` `updateLookupTableField`=`:604`, `deleteLookupTableField`=`:234`, `getLookupTableField`=`:343`). The path-matcher never matches, so `LOOKUP_TABLE_DEFINITION_UPDATE`/`_DELETE` never fire - the column-mutation gates are dead. (The columns *POST* rule at `:333` correctly uses plural `/columns`, so only the `{column_id}` rules are mismatched.)

No running-stack drive was required - these are path-matcher / resolver / param-passing facts visible in source. The remaining runtime check (optional) is an LDAP-mode integration test proving a table-A-scoped grant PATCHes a table-B column.

## Why it matters

The published API-reference page opens with "All endpoints require authentication and respect the per-table RBAC permissions." An operator reasoning additively from that sentence authors a separation-of-duties policy that the platform silently does not honour: reads are visible to everyone (anonymous under `DISABLED`), a single `LOOKUP_TABLE_UPDATE` grant edits every table, and two of the documented column gates never execute. The cross-table column-jump (hole 3) and the never-firing column rules (hole 4) are privilege-escalation surfaces - a caller scoped to one table mutates another's columns. This is the LSN-002 class: the guidance is the cliff. Master Data Management is a single-surface pillar, so this is the entirety of that pillar's access control.

## Suggested fix

- Add a `LOOKUP_TABLE_*_READ` permission family (or, minimally, gate the read + search endpoints behind the existing authenticated filter *plus* an owner/namespace predicate) so reads are not ungated.
- Replace `NO_CONTEXT` with a per-table/per-owner `SecurityResolver` for the `LOOKUP_TABLE_*` rules so a grant scopes to owned tables.
- In `updateLookupTableField`, pass `lookupTableId` through to the service and assert the column belongs to that table before mutating (mirrors the `updateLookupTable` shape).
- Reconcile the column-rule path: register the `SecurityConstants` rules under the plural `.../columns/{column_id}` to match spec + controller (or change all three to agree). A build-time validator that asserts every `SecurityConstants` path matches a live controller route would catch this class.
