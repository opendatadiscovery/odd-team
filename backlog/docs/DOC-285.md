## Description

The Data Quality hub page (`data-quality.md`) tells operators that the Dataset Quality Statuses feature exposes `/api/datasets/{id}/sla` for importing SLA data into a BI report. That endpoint returns **`image/png`** — it serves one of three hardcoded badge images (`sla_red.png` / `sla_yellow.png` / `sla_green.png`). The JSON payload a BI client actually needs is served by the **sibling endpoint `/api/datasets/{id}/sla_report`**.

A BI integrator who follows the page wires their client to `/sla` and gets a PNG back where they expected JSON; the client fails to parse and the integration silently produces no data. This is Critical (incorrect documentation an integrator builds against).

**Failure shape**: code-doc drift — wrong endpoint named for a documented integration use; the named endpoint returns a different content type than the page implies.

## Acceptance Criteria

- [ ] `data-quality.md` directs BI-report / JSON SLA consumers to `GET /api/datasets/{data_entity_id}/sla_report` (the JSON endpoint), not `/sla`.
- [ ] If the page still references `/sla`, it is described accurately as the badge-image endpoint returning `image/png` (one of `sla_red/yellow/green.png`), distinct from the JSON `sla_report`.
- [ ] The two endpoints are disambiguated on the page so a reader cannot confuse the PNG-badge route with the JSON-report route.
- [ ] Implementer cites in the commit `Sources:` footer the controller `file:line` for both `/sla` (returns the PNG) and `/sla_report` (returns the JSON), confirming the content types before authoring.
- [ ] Live-site verification post-merge: WebFetch `docs.opendatadiscovery.org/features/data-quality` and confirm the BI-import path now names `sla_report`.
