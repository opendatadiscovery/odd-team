## What

`GET /api/dataentities/{data_entity_id}/runs` (the per-test/per-transformer **Run History** surface — the `/dataentities/{id}/history` tab + the test-report-details first-10-runs preview) returns **HTTP 500 `SYS001`** whenever the result set contains a run whose status is `RUNNING`. The page therefore **becomes unavailable exactly while a test is in flight** — the moment an operator most wants to watch it.

Root cause: an **enum asymmetry between the DB and the API wire contract**.

- The DB column `data_entity_task_run.status` stores the **7-value** `IngestionTaskRunStatus` enum: `SUCCESS | FAILED | SKIPPED | BROKEN | ABORTED | RUNNING | UNKNOWN`. A collector writes a `RUNNING` row (with `end_time = NULL`) for an in-flight execution — this is a normal, expected DB state.
- The API wire enum `DataEntityRunStatus` declares only **6 values** — `RUNNING` is **absent**.
- `DataEntityRunMapper` flat-maps each DB `status` String into the wire enum via MapStruct's default `Enum.valueOf()` strategy, which throws `IllegalArgumentException` on the unknown `RUNNING` literal → `ControllerAdvice` catch-all → HTTP 500.

This is the **availability** half of the run-history enum-asymmetry finding. (The separate "filter by an unmappable status value 500s instead of 400" half — e.g. `?status=RUNNING` or `?status=BANANA` — is the request-binding `ServerWebInputException`→500 class already filed as **PLT-143**; the run-history filter is a new invocation site of it.)

```

#    VALUES ('<dq_oddrn>/run/INFLIGHT','<dq_oddrn>', now(), NULL, 'RUNNING', 'DATA_QUALITY_TEST_RUN', 'inflight');
# 2. read the history (id = the DQ test's data_entity id):

```

Confirmed live 2026-06-07 against `ghcr.io/opendatadiscovery/odd-platform:latest` (stack `dd52f520`). Pinned by odd-team integration test **IT-059** (`dq-run-history.spec.ts`, CORNER 1) — currently GREEN asserting the *incorrect* 500; the pin RED-flips the instant this is fixed.

## Why it matters

- The Run History page is **dead during the exact window it matters** — while a run is executing. The operator's reflex ("refresh") only succeeds once the run completes, so they get no in-flight visibility at all.
- **Timing-dependent**, so it passes casual smoke testing: a test that finishes before the page is opened renders fine; the failure manifests only when a `RUNNING` row is present at read time. This is precisely why it shipped undetected — there was no test exercising an in-flight row.

## Suggested fix

Primary (closes the availability defect) — add `RUNNING` to the wire enum and regenerate:

```
# odd-platform-specification (components.yaml, DataEntityRunStatus):
enum: [SUCCESS, FAILED, SKIPPED, BROKEN, ABORTED, RUNNING, UNKNOWN]
```

MapStruct then resolves the new literal; the mapper stops throwing. Adding `RUNNING` strictly improves the situation — clients already hit the same `Enum.valueOf` failure today, so there is no behaviour to break. (The UI can then render an explicit in-flight badge.)

Alternative / defence-in-depth (lower impact, loses the in-flight distinction): `@ValueMapping(source = MappingConstants.ANY_REMAINING, target = "UNKNOWN")` on `DataEntityRunMapper` so unknown DB literals degrade to `UNKNOWN` instead of 500ing.

## Regression guard

The right unit-tier guard is a `DataEntityRunMapper` test mapping a `RUNNING`-status pojo (assert it resolves once fixed) plus a `@WebFluxTest(DataEntityRunController.class)` returning 200 with the in-flight row present; flip the IT-059 pin from characterization once this lands.
