  - **Proposed doc action**: **Three-part action**.
    1. **Doc-side primary — `features/data-discovery/tagging.md`**: add a "Inline tag creation and the global vocabulary" subsection: "**Creating a new tag inline from an entity detail page (the 'create a new tag inline' UI flow above) requires `DATA_ENTITY_TAGS_UPDATE` on the entity — NOT `TAG_CREATE`.** This is intentional: operators with permission to label a single entity can extend the catalog vocabulary as part of their entity-curation workflow. The consequence: any operator authorized to attach tags on ANY data entity can mint rows in the platform-wide `tag` directory; the new tag is immediately visible to every other user via the [Top tags](#tag-driven-discovery) chip strip on Catalog Overview, the Tag facet on [Search](search.md), and the autocomplete on every other entity's tag-attach control. **Deployments that want a curated vocabulary** should either (i) restrict `DATA_ENTITY_TAGS_UPDATE` to a small group of stewards via Policies (the per-entity permission ALSO acts as the directory-write permission); (ii) accept the open-vocabulary posture as a design choice and rely on the Important flag at [Management → Tags](../management.md) to govern visibility; or (iii) file an upstream feature request to separate the two surfaces (REFACTOR-223 tracks this)."
    2. **Doc-side companion — `configuration-and-deployment/enable-security/authorization/permissions.md`**: update the `DATA_ENTITY_TAGS_UPDATE` row description from "Allows editing a data entity's tags" to "Allows editing a data entity's tags. **This permission ALSO authorizes minting new rows in the global Tag directory** when the operator types a previously-unknown tag name in the inline create UI — the directory-write side-effect is intentional but operators should know about it.
