## Description

The demo stand's Step-1 command now **blocks** until the Platform is healthy, because `docker/demo.yaml`
gained a healthcheck the enricher waits on (`condition: service_healthy`). Measured: `up -d
odd-platform-enricher` returns in 2s on the old stand and 62-86s on the new one. That is the fix working —
but with no word about it on the page, a reader who opens `localhost:8080` while the command is still
running sees an empty catalog and reasonably concludes the demo failed.

Authored and committed on the train (not merely drafted):

- **branch** `docs/CTRIB-063-demo-stand-first-run`, off `origin/release/1.0.0` @ `379baf3`
- **commits** `b270da6` — *"docs(trylocally): the first run waits for the Platform, and it takes about a minute"*
  and **`7cfac8f`** — *"docs(demo): say what the first run actually does, on every page that starts it"* (round 2:
  corrects the first commit's claim that `up -d` returns only after injection, and widens the change from one
  page to four; see `CTRIB-063` `## Rework — round 2`)

Four pages, one behaviour (round 2 widened this from the single page round 1 authored):

1. **`trylocally.md`** — a Step-1 hint block naming the wait, its cause (the Platform applies its whole
   migration set against an empty database before serving) and what to do if the catalog is still empty
   a minute later (`logs odd-platform-enricher`); Prerequisites stop saying "preferably the latest
   docker-compose" and name the real floor — `docker compose` v2, or `docker-compose` 1.27.0+, because
   the long-form `depends_on` condition was only re-supported by V1 from 1.27.0. "Preferably" is not a
   version constraint, and a reader on an older binary silently gets the old racing behaviour back.
2. **`deployment.md`** — Option 1 hands the reader the same command: it gains the wait note (pointing at
   Try locally for the walkthrough), the same compose floor in its Prerequisites, and its Verify line loses
   the "~" that only existed because the shipped stand delivered nine.
3. **`health-and-monitoring.md`** — "the images and Compose files distributed with the platform define no
   health checks themselves" is false as of this release: the **image** declares none (measured with
   `docker image inspect`), the demo stack ships one. The page's rival Compose recipe is replaced by the
   shipped one, with the `depends_on: condition: service_healthy` half and the v2 / 1.27.0+ floor.
   **Round 3** corrects the rationale sentence next to it: by default the health body is only
   `{"status":"UP"}` / `{"status":"DOWN"}` (`management.endpoint.health.show-details` is unset, so Spring's
   `never` applies) — the earlier text claimed a DOWN body carries per-component `"status":"UP"` entries,
   which the shipped configuration never emits and which line 11 of the same page contradicted.
4. **`build-and-run-odd-platform.md`** — the injector's environment is a table now (it omitted
   `REACH_TRIES_NUMBER` / `REACH_RETRY_DELAY_SECONDS`, the two knobs the give-up message tells the reader
   to raise); the frontend-engineer path names the wait; and the "replace odd-platform image" snippet no
   longer reproduces the whole service block minus the healthcheck (pasting that made Compose refuse to
   start the enricher at all).

Round 3 also adds, on the three pages that carry the compose floor (`trylocally.md`, `deployment.md`, and
the repo `docker/README.md`), the one sentence that bridges it to the commands beneath it: they are written
for the `docker-compose` binary, and with the v2 plugin the same commands work as `docker compose …`.

**The page's "10 predefined data sources" line is deliberately NOT edited.** It was always the intent; the
shipped stand delivered 9 because `08_s3_ingestion.json` named a data source `datasources.json` does not
define. The code fix on this same release makes the existing sentence true. Recorded in `CTRIB-063` as an
accepted, time-boxed falsehood whose expiry is this release gate — if #1870 does not ship in 1.0.0, the
correct move flips to correcting the number on docs `main`.
