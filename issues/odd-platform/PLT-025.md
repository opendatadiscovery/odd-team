## What

Custom Metadata is a paired feature surface - F-013 (per-entity VALUE write) + F-046 (FIELD catalogue read). Five operator-visible defects span both halves. The OpenAPI contract, the UI toast, the schema-default convention, and the audit-feed enum surface all silently lie about the implementation's actual behaviour.

**Defect 1 - Silent UPDATE-not-UPSERT (F-013b).** `ReactiveMetadataFieldValueRepositoryImpl.java:94-104` is pure UPDATE:
```java
DSL.update(METADATA_FIELD_VALUE)
   .set(VALUE, pojo.getValue())
   .set(ACTIVE, pojo.getActive())
   .where(METADATA_FIELD_ID.eq(?).and(DATA_ENTITY_ID.eq(?)))
   .returning()
```
Missing `(entity_id, field_id)` pair -> zero-row UPDATE -> Mono empty -> silent 200 OK with empty body. UI displays "Metadata successfully updated." (`metadata.thunks.ts:51-54`). OpenAPI declares operationId "upsert" - implies replace-or-create semantics. **Reconciliation pipelines silently lose writes.**

**Defect 2 - ACTIVE column dropped to NULL on every UPDATE (F-013c).** Line 98: `.set(ACTIVE, pojo.getActive())`. The caller (`DataEntityServiceImpl.java:292-295`) never calls `.setActive(true)` on the pojo. `pojo.getActive()` returns boxed `Boolean` null. UPDATE writes explicit NULL. DB DEFAULT TRUE only applies on INSERT (`V0_0_1__init.sql:180`). Any platform code filtering `WHERE active = TRUE` (rather than `IS DISTINCT FROM FALSE`) silently drops edited rows. **Latent invisibility bug.** The platform's downstream consumers of `active` are unverified - if any reader filters strictly TRUE, every edit hides the row.

**Defect 3 - pageInfo theatre + no LIMIT on catalogue read (F-046a).** `MetadataFieldMapperImpl.java:28-33` constructs `new PageInfo().total((long) pojos.size()).hasNext(false)` - total is items.length, hasNext is hardcoded false. SQL at `ReactiveMetadataFieldRepositoryImpl.java:44-56` is unbounded (no LIMIT/OFFSET/ORDER BY). Production deployments with 10K+ INTERNAL fields see a 1-2 MB response on every autocomplete keystroke. SDK clients written from the OpenAPI spec build "load more" workflows that never fire.

**Defect 4 - No CUSTOM_METADATA_FIELD_READ permission (F-046b).** `GET /api/metadata/fields` has NO entry in `SecurityConstants.SECURITY_RULES` - falls through to `.authenticated()`. Under `auth.type=DISABLED`, anonymous callers enumerate every INTERNAL field name in the deployment. Multi-team deployments expose operator-named field schemas (`finance_cost_centre`, `marketing_attribution`, `pii_redaction_rule`) across team boundaries. Compounds with the auto-create-on-miss side-channel: any user with `DATA_ENTITY_CUSTOM_METADATA_UPDATE` on ONE entity can MINT new catalogue entries visible to every authenticated user.

**Defect 5 - Dead CUSTOM_METADATA_* ActivityEventTypeDto enum values.** `ActivityEventTypeDto.java` carries `CUSTOM_METADATA_CREATED`, `CUSTOM_METADATA_UPDATED`, `CUSTOM_METADATA_DELETED` - all three are **dead** (no code path emits them). Auditors querying activity for custom-metadata mutations find nothing despite the surface API suggesting otherwise.

## Suggested fix (five independent threads)

**Thread A - True UPSERT semantics (Defect 1).** Either:
- Switch to `INSERT ... ON CONFLICT (data_entity_id, metadata_field_id) DO UPDATE` (the right shape for the operationId).
- Rename operationId to "updateMetadataFieldValue" + add `.switchIfEmpty(Mono.error(new NotFoundException(...)))` -> 404 on missing pair. Less invasive but is a breaking change for SDK consumers.

Option A1 (true UPSERT) preserves the OpenAPI contract.

**Thread B - Preserve ACTIVE (Defect 2).** Two options:
- `pojo.setActive(true)` in the service before the UPDATE (preserves DEFAULT TRUE semantics).
- Surgical UPDATE excluding the ACTIVE column when not explicitly set.

Option B1 is simpler. After the fix, audit downstream consumers of `active` to confirm no `IS NULL` filters were being relied upon as a deactivation signal.

**Thread C - Real pagination (Defect 3).** Implement LIMIT/OFFSET at SQL + accurate total via `COUNT(*)` over the filtered set + truthful hasNext. OR drop PageInfo from the OpenAPI schema if pagination is genuinely not desired (and document the unbounded contract). Recommend real pagination - the autocomplete keystroke load is operator-load-bearing.

**Thread D - Read permission (Defect 4).** Introduce `CUSTOM_METADATA_FIELD_READ` permission OR document the catalog-wide enumeration posture explicitly. Recommend the permission - the catalogue carries operator-named vocabulary that can encode PII (per the F-046b finding's enumeration example). Backwards-compat: default existing Policies grant the new permission to anyone who previously held `DATA_ENTITY_CUSTOM_METADATA_UPDATE` (the operator likely already had implicit read).

**Thread E - Revive CUSTOM_METADATA_* events (Defect 5).** Add `@ActivityLog(event = CUSTOM_METADATA_CREATED, ...)` etc. to the service methods. Emit before/after payloads in the DatasetField pattern (cross-link PLT-024 + PLT-026 for cross-pillar harmonisation). The enum values exist; the work is annotating the call sites.

## Operator impact

- Reconciliation pipelines silently lose writes - Defect 1.
- Custom-metadata edits silently invisible to platform readers filtering `WHERE active = TRUE` - Defect 2.
- Autocomplete keystroke load on multi-team deployments - Defect 3.
- Multi-team vocabulary leakage + drive-by catalogue minting - Defect 4.
- Compliance auditors find no record of custom-metadata mutations - Defect 5.
