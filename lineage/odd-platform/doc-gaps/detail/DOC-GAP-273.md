    - **The leakage scenarios**:
      - (a) **Browser back/forward cache**: a user signs out and another user signs in on the same browser; the back button serves the previous user's whoami response from disk cache (the HTTP/1.1 cookie-bearing heuristic for cacheability).
      - (b) **Shared HTTP intermediate**: an enterprise deployment behind a transparent corporate proxy keyed by URL alone (the platform's `/api/identity/whoami` path is identical across users); without `Vary: Cookie` and without `Cache-Control: no-store`, the proxy may cache and serve. The Vary header is also not set (the response uses bare `ResponseEntity.ok()` — no header customisation at all).
      - (c) **Mobile carrier transparent proxy**: similar to (b); legacy mobile carriers cache aggressively on URL alone, especially under HTTP (DISABLED-default deployments behind operator-managed TLS termination).
      - (d) **CDN misconfiguration**: a future maintainer fronting the platform with a CDN (Cloudflare, Akamai) using URL-only cache keys (no `Cookie` in cache key) would serve cross-user identity bodies if no `Cache-Control: no-store` is set.
    - **The under-DISABLED-amplification**: when `auth.type=DISABLED`, the SecurityWebFilterChain is wired with `.anyExchange().permitAll()` (per `DisabledAuthSecurityConfiguration.java:11-19`); Spring Security's stock `WebFluxSecurityHeadersConfiguration` is bypassed; the response carries NO default no-cache headers at all (verified statically; PROBE P-124 confirms empirically). Under LOGIN_FORM / OAUTH2 / LDAP, Spring Security's default header writer MAY inject `Cache-Control: no-cache, no-store, max-age=0, must-revalidate` for authenticated requests — but this is framework-default behaviour that the controller does not assert and cannot rely on across framework upgrades. The controller itself emits nothing.
    - **The standards-canonical case**: per RFC 7234 §5.2.2.3 and OWASP Authentication Cheat Sheet, authentication / identity responses are THE canonical case for `Cache-Control: no-store, no-cache, must-revalidate` + `Pragma: no-cache`. The platform's most user-specific response body is the one that needs the headers most. The absence is not a corner-case nicety; it is the canonical industry counter-example to good practice.
