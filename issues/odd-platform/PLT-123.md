## What

The `ActivityEmptyPartitionsHousekeepingJob` empty-check (`SELECT count(*) = 0`) and the `DROP TABLE` (no `IF EXISTS`) are **two separate statements on the shared connection**, not wrapped in a transaction and holding no pre-emptive lock — unlike `AlertHousekeepingJob` / `DataEntityHousekeepingJob`, which `transaction(...)`-wrap their deletes. An `INSERT INTO activity` that lands **after** the count-zero check but **before** the DROP commits on the writer's autocommit connection, and then `DROP TABLE` destroys the just-inserted row with no re-check and no error to the original caller. The class name promises it only drops *empty* partitions; the race makes that promise unsafe against in-flight writes.

This is **net_new** at the code-fix level: it is carried only as a feature-flow drift facet plus probe P-022; no `issues/` or `backlog/` item tracks the defect. (F-021 / VAL-LSN-019-B surfaced the same race from the Activity-Feed side but filed no PLT.) Filing is gated on P-022 confirming reachability — the probe pins whether the window is hittable under realistic write timing.

## Evidence

From the F-010 reflection (`lineage/odd-platform/feature-reflections/detail/F-010.yaml`), hypothesis H-007:

```

  //   SELECT count(*) = 0  (empty-check)
  //   DROP TABLE <partition>   (no IF EXISTS, no recheck under lock)
  // EmptyPartitionsHousekeepingJob does NOT wrap in transaction(...)
```

Probe P-022 (`lineage/odd-platform/probes/P-022.yaml`) is the existing activity check-then-drop race probe; P-012 is a sibling. Static analysis says the race window is real (Q-E.3 / Q-B.2); reachability requires running the system.

## Impact

If reachable: silent loss of an audit-trail row that the writing code saw as committed-success — the worst kind of audit defect (the record the operator believes was saved is gone, with no error and no compensating undo). Severity HIGH if the probe confirms reachability.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: wrap the `getEmptyPastPartitions` empty-check and `dropPartition` in a single transaction taking an `ACCESS EXCLUSIVE` lock **before** the count check, **or** re-check emptiness under the lock immediately before DROP (`PartitionServiceImpl.java:108-127`). Gate the fix on P-022's reachability outcome.
