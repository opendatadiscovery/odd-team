## Rejection

Rejected as a false positive (2026-06-10 sweep). The proposed soft-delete-aware partial unique index already exists: `collector_name_unique ... WHERE deleted_at IS NULL` was created in V0_0_31 (the full key was dropped at the same time), so delete-then-recreate-by-name already works; the `is_deleted` and `oddrn` columns the draft references no longer exist. The draft was authored from the V0_0_29 birth migration, ignoring 8 later collector migrations. (The partial-index convention itself is a candidate implicit-ADR datum, noted in the sweep file.)

## What

**FALSIFIED 2026-06-10 (user-facing verification sweep) -> REJECT-CANDIDATE. There is no defect.** The original draft asserted that `collector.name` carries a full, unconditional `UNIQUE` constraint over a soft-deleting table (`is_deleted boolean`), so a deleted collector's name is "occupied forever" and recreate-by-name fails. Both halves of that premise are stale - the draft cited only the original `V0_0_29__add_collector.sql` migration and never followed the migration trail:

1. **The constraint is already a partial, soft-delete-aware unique index.** `V0_0_31__add_deleted_at_field.sql:31` runs `CREATE UNIQUE INDEX IF NOT EXISTS collector_name_unique ON collector (name) WHERE deleted_at IS NULL;` and `:33-34` `DROP CONSTRAINT IF EXISTS collector_name_key;` - i.e. it replaced the original full `collector_name_key` with exactly the partial index this draft proposes to add. The generated jOOQ catalog confirms it is the live constraint: `Indexes.COLLECTOR_NAME_UNIQUE` over `Collector.NAME` (`build/generated-jooq/.../model/Indexes.java:55`). So a soft-deleted collector (`deleted_at IS NOT NULL`) is excluded from the uniqueness predicate, and the name is freed the moment the collector is deleted. **Delete-then-recreate-by-name already works.**

2. **The `is_deleted` boolean column no longer exists on `collector`.** `V0_0_64__remove_is_deleted_field.sql:6-7` `ALTER TABLE collector DROP COLUMN IF EXISTS is_deleted;`. Soft-delete is `deleted_at`-based (set by `ReactiveAbstractSoftDeleteCRUDRepository.getDeleteChangedFields()`, which writes `deleted_at = now()`, `:106-110`). The draft's quoted DDL (`is_deleted boolean NOT NULL DEFAULT FALSE` at "line 9") is the pre-V0_0_31 schema, not the live one.

3. **The `oddrn` column no longer exists on `collector`.** `V0_0_32__remove_oddrn_from_collector.sql:1-2` `ALTER TABLE collector DROP COLUMN IF EXISTS oddrn;`. The generated `Collector.java` columns are `id, name, description, namespace_id, token_id, created_at, updated_at, deleted_at` - no `oddrn`, no `is_deleted`. So the draft's "same trap applies to `oddrn`" is moot: there is no `oddrn` column and no `oddrn` UNIQUE to fix.

The proposed fix is therefore already shipped (and has been since `V0_0_31`), against columns that for the most part no longer exist. No code change is warranted.

## User-facing impact

**None - the workflow the draft claims is broken already works.** Verified by reading the full collector migration trail + the generated jOOQ catalog 2026-06-10: an operator who deletes a collector and recreates one with the same name succeeds, because the live uniqueness predicate is `collector_name_unique ... WHERE deleted_at IS NULL` (`V0_0_31:31`) and `delete` sets `deleted_at` (soft-delete via `ReactiveAbstractSoftDeleteCRUDRepository:106-110`), so the soft-deleted row is outside the uniqueness scope. Idempotent recreate-by-name provisioning and migration/re-import flows likewise succeed.

*Not driven on a running stack* - this is a schema-trace verdict (migrations + generated jOOQ are authoritative for the index predicate). A `curl`-level confirmation (delete a collector, POST a new one with the same name, expect 200) would close the loop, but the partial-index DDL settles it at the schema layer.

Footnote on the original "opaque constraint violation" claim: even in the falsified scenario the error would NOT have been opaque - `ExceptionUtils.formatMessage` already maps `COLLECTOR_NAME_UNIQUE` to the message "Collector with this name already exists" and `translateDatabaseException` returns a `UniqueConstraintException` (HTTP 400), not a raw 500 (`repository/util/ExceptionUtils.java`).

## Suggested fix

None - REJECT-CANDIDATE. The partial unique index this draft proposes already exists (`collector_name_unique`, `V0_0_31:31`). Close without filing.

If anything, the *general* soft-delete-aware-uniqueness pattern is worth noting as a confirmed, deliberately-applied convention (`V0_0_31` and `V0_0_64` convert `owner`, `role`, `tag`, `title`, `data_source`, `namespace`, `collector` to partial `WHERE deleted_at IS NULL` indexes) - i.e. the platform already does the right thing here; it is a candidate datum for the implicit-ADR catalogue, not a bug.
