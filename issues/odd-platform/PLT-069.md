## What

`GoogleUserHandler.java` (74 lines, full re-read this run) does NOT extend `AbstractOIDCUserHandler` and NEVER references `provider.getAdminGroups()`. Its `enrichUserWithProviderInformation` (`:42-73`) reads `provider.getAllowedDomain()` (`:50`), `provider.getAdminPrincipals()` (`:56`) and `provider.getAdminAttribute()` (`:57`) only; admin detection is full-string equality of `adminPrincipals` against the `email` claim (`GOOGLE_EMAIL = "email"`, `:31`) unless `adminAttribute` overrides the claim name. The `adminGroups` field binds successfully - it is a unified field on the shared POJO `ODDOAuth2Properties.OAuth2Provider` (`ODDOAuth2Properties.java:48`) - with no boot warning and no error.

The contrast that proves intent-vs-reality: `AbstractOIDCUserHandler.enrichUserWithProviderInformation` (`AbstractOIDCUserHandler.java:44-55`) DOES read `provider.getAdminGroups()` and promote group members to ADMIN. Google is the one OIDC provider whose handler is hand-rolled and skips that branch. So an operator configuring `auth.oauth2.client.google.admin-groups: [workspace-admins]` sees ZERO behaviour change - the user expected to be admin remains USER.

## User-facing impact

CODE-SETTLED. The no-op is a static fact (the handler never references the field); only the end-to-end "I set it and nothing changed" demonstration needs a running OAUTH2/Google stack.

- **No-op (verified-trace, static):** `GoogleUserHandler.java:42-73` contains no reference to `getAdminGroups`; full-file read confirms admin is decided solely by `adminPrincipals` (`:56-64`). `adminGroups` binds (`ODDOAuth2Properties.java:48`) but is never consulted for Google. This is settled without running anything - hence `user_facing_verified: true`.
- **Operator observable (static-not-driven; manifests under `auth.type=OAUTH2` with a Google client):** "a Google Workspace admin who is in `admin-groups` but not in `admin-principals` logs in as USER, not ADMIN." Requires a live OAUTH2 Google login; not driven here. Remaining check = configure Google OAUTH2 with `admin-groups` set and `admin-principals` empty, log in as a group member, observe USER role.

## Why it matters

Silent operator hazard: the platform accepts and binds `admin-groups` for Google with no warning, but the Google code path ignores it, so the operator's intended privilege grant never happens. Compounds with the unified-POJO design (same field name across providers, semantically different per-provider). The cheap fix is a boot-time warn/fail when `provider == GOOGLE` and `adminGroups` is non-empty.

## Suggested fix

**Option A - boot-time cross-field validation (recommended).**

Add `@PostConstruct` on `ODDOAuth2Properties` that fails-fast or warns when `provider == GOOGLE` AND `adminGroups` is non-empty:

```java
@PostConstruct
void validateProviderConfig() {
    for (var provider : client.values()) {
        if (Provider.GOOGLE.name().equalsIgnoreCase(provider.getProvider())
            && provider.getAdminGroups() != null
            && !provider.getAdminGroups().isEmpty()) {
            log.warn("auth.oauth2.client.{}.admin-groups is set but GoogleUserHandler does NOT consult admin-groups. Use admin-principals (email) or admin-attribute (custom claim) instead.",
                provider);
            // OR: throw new IllegalStateException(...) for fail-fast
        }
    }
}
```

Recommended warn-first; promote to fail-fast in a later release after the warn-period reveals zero accidental config.

**Option B - implement admin-groups support for Google (feature, larger scope).**

Google's OAuth2 access token does NOT carry group membership; admin-groups for Google requires a separate Workspace Admin SDK call with elevated scopes. Substantially larger code change; track as a separate feature request if there's operator demand.

Recommended Option A as the immediate closure; Option B is gated on actual operator demand.
