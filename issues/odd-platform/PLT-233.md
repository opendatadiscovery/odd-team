## Description

Sibling of **#1766** (CTRIB-027), which fixed the **mutateAsync** arm of the shared `ConfirmationDialog`
(the stuck-spinner). This item is the **redux-thunk** arm, deliberately left out of #1766's scope.

~13 `ConfirmationDialog` consumers wire `onConfirm` as a bare `dispatch(someThunk(...))` with **no
`.unwrap()`** (e.g. `DataSourceItem.tsx:31`, `EditableNamespaceItem.tsx`, `EditableOwnerItem.tsx`,
`CollectorItem`, `RoleItem`, `PolicyItem`, `MetadataItem`, `OwnershipDeleteForm`, …). A redux-toolkit
dispatch promise **RESOLVES even when the API call fails** (`handleResponseThunk.ts:41` returns
`thunkAPI.rejectWithValue(...)`, a resolved rejected-action), so `ConfirmationDialog.onClose`'s `.then`
branch runs: the spinner clears and **the modal closes exactly as on success**. On a failed destructive
action (cascade-block `USR004`, RBAC 403, 500), the only signal the operator gets is that the row is still
in the list after the modal closes — failure is presented as success.

**Verified live (CTRIB-027, 2026-06-22):** forced a 500 on `DELETE /api/datasources/{id}` and drove the
Management → Datasources delete dialog → the modal closed, the datasource row remained, and (post-#1771) an
error toast appeared. Evidence: `integration-tests/e2e/evidence/ctrib027-arm2-silent-close.png`.

Note: #1771 already made `showServerErrorToast` unwrap `ResponseError`, so an error toast now DOES render on
this arm — which is why the severity is **medium**, not high: failure is no longer entirely invisible, but
the modal closing-as-success on a destructive action is still wrong UX.

## Suggested fix

Make the thunk consumers reject-on-failure so they flow through the same path #1766 fixed for mutateAsync —
the codebase's **established idiom** (`.unwrap()` is already used across the shared Autocompletes):

- In each consumer's `onConfirm`, `await dispatch(thunk(...)).unwrap()` so a `rejectWithValue` becomes a
  rejection → `ConfirmationDialog`'s `.catch` (post-#1766) clears loading + shows the inline error + keeps
  the dialog open; OR
- alternatively, have `ConfirmationDialog` inspect the resolved action with `isRejectedWithValue` before
  treating it as success (one shared place, but couples the generic `shared/elements` component to
  `@reduxjs/toolkit`, which it currently does not import — the `.unwrap()` consumer fix is the more
  consistent choice).

Scope note: the **term-delete navigate-away** (a worse instance of this class — it navigates to term-search
as if the delete succeeded) is tracked separately as **PLT-234**.

## Acceptance

- A failed thunk-backed confirm keeps the dialog open with an inline error (parity with the mutateAsync arm
  fixed in #1766); the success path is unchanged.
- An integration test (odd-team, alongside IT-138) drives a thunk-arm delete under a forced failure and
  asserts the modal does NOT close-as-success.
