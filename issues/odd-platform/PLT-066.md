## What

`OwnerFormData.roles` is OpenAPI-optional (`components.yaml:419-422`, no `required:` marker). `OwnerServiceImpl.java:117-122` `getRoleIdsList` method collapses both NULL AND empty list to `List.of()`. The update transaction then calls `deleteOwnerRelationsExcept(ownerId, List.of()).then(createRelations(ownerId, List.of()))` - the first half DELETES all current role-links (since no existing link is in the empty set); the second half INSERTS nothing.

An API consumer (script, integration, CI tool) issuing `PUT /api/owners/{id}` with body `{"name": "new_name"}` to rename ONLY - expecting unspecified fields to mean "leave unchanged" - instead REMOVES ALL role assignments. The UI in practice always sends the current `roles` list (read-modify-write pattern), so the hazard is MASKED in normal UI flows; any direct API consumer is exposed.

## Why it matters

Critical UX hazard: destructive AND silent AND visible only to direct-API consumers. Operator running a CI pipeline that periodically refreshes Owner display names without re-sending the (un-touched) role array discovers ALL Owners stripped of their Role bindings - typically only after permission-related incidents.

## Suggested fix

Three options, in order of decreasing breaking-change risk:

**Option A (recommended) - PATCH semantic with `null`-sentinel.** Treat `null` `roles` as "no change"; treat empty array `[]` as "remove all". Doc-side adjustment to OwnerFormData makes the semantic explicit.

```java
// OwnerServiceImpl.java
private List<Long> getRoleIdsList(@Nullable List<RoleFormData> roles) {
    return roles == null
        ? null  // sentinel: leave existing bindings unchanged
        : roles.stream().map(RoleFormData::getId).toList();
}

// In update transaction:
if (roleIds == null) {
    return updateOwnerCoreFields(owner);  // skip role-link delta
} else {
    return updateOwnerCoreFields(owner)
        .then(deleteOwnerRelationsExcept(owner.id(), roleIds))
        .then(createRelations(owner.id(), roleIds));
}
```

**Option B - Make `roles` REQUIRED in the spec.** Breaking change for existing API consumers (clients omitting `roles` get 400 instead of silent destruction). Requires deprecation period + client migration. Doc-side spec change in `opendatadiscovery-specification` (cross-link to SPC-002 scope).

**Option C - Keep PUT semantic, validate at controller layer.** Reject the request with HTTP 400 if `roles` is absent (return clear error: "OwnerFormData.roles is required; to remove all role bindings, send an empty array explicitly"). Less Spring-idiomatic than Option A but simpler to implement.

Recommended Option A - least-surprise for existing API consumers + least-breaking-change.
