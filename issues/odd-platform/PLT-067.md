## What

The `/api/dataentities/my/upstream` + `/my/downstream` lineage triplet has two structural defects: a single-point-of-failure architecture where owner-scoping is enforced at exactly ONE site with NO downstream JOIN-side defence-in-depth, AND an unbounded anchor-set IN-clause fan-out that materially affects DB cost for owners with thousands of entities.

**Defect 1 - Anchor-set single-point-of-failure (F-015a).** Owner-scoping is enforced at `DataEntityRelationsServiceImpl.java:26` (`authIdentityProvider.fetchAssociatedOwner()`). Downstream the lineage CTE (`ReactiveLineageRepositoryImpl.java:122-176`) has NO OWNERSHIP join NO owner predicate; the final projection `listByOddrns` (`ReactiveDataEntityRepositoryImpl.java:228-253`) is a pure `WHERE DATA_ENTITY.ODDRN IN (...)` scan with no owner JOIN. CONTRAST with the base `/my` endpoint's `listByOwner` (`:515-534`) which DOES JOIN OWNERSHIP. A regression at the anchor (fallback owner-id under DISABLED, a misordered WebFilter dropping SecurityContext, USER_OWNER_MAPPING corruption returning wrong owner, flatMap-vs-map typo) silently leaks the lineage neighbourhood of an unintended owner.

**Defect 2 - Unbounded anchor-set IN-clause fan-out (F-015c).** `dataEntityRepository.listByOwner(o.getId())` fetches ALL owned entities with NO pagination (`:27`). Then `getLineageRelations(oddrns, LineageDepth.empty(), UPSTREAM)` constructs a CTE with `WHERE CHILD_ODDRN IN (?, ?, ...)` cardinality = full anchor-set size. Memory + DB-CPU scale with anchor set, NOT with the requested page size. Postgres planner cost is non-linear above ~1000 IN elements; jOOQ does not paginate the IN clause. An admin owner or CI-bot owner owning thousands of entities triggers O(anchor) memory + DB-CPU on every `/my/upstream` call even for `size=5`.

## Why it matters

**Defect 1** - today's code is correct; the architecture provides ZERO defence against a future regression at the single load-bearing call site. Combined with F-011d's provider-null cross-mode bleed at USER_OWNER_MAPPING (PLT-065), a multi-mode deployment with username collision is one regression away from cross-owner lineage neighbourhood leak.

**Defect 2** - performance hazard. The Recommended panel on the Catalog Overview home page (F-141) fires this endpoint on every SPA mount. Admin-owned-everything deployments see O(anchor) cost on every SPA reload by every operator.

## Suggested fix

**Thread A - JOIN-side defence-in-depth (Defect 1).**

Add `listByOddrnsAndOwner(oddrns, ownerId)` repository method that JOINs OWNERSHIP with `WHERE OWNERSHIP.OWNER_ID = ?` as belt-and-braces filter:

```java
// ReactiveDataEntityRepositoryImpl.java - add
public Flux<DataEntityPojo> listByOddrnsAndOwner(List<String> oddrns, Long ownerId) {
    return jooq.selectFrom(DATA_ENTITY)
        .innerJoin(OWNERSHIP).on(OWNERSHIP.DATA_ENTITY_ID.eq(DATA_ENTITY.ID))
        .where(DATA_ENTITY.ODDRN.in(oddrns))
        .and(OWNERSHIP.OWNER_ID.eq(ownerId))   // belt-and-braces
        .and(OWNERSHIP.IS_DELETED.isFalse())
        .fetchAsFlux();
}
```

Update `DataEntityRelationsServiceImpl.java` to use the new method. The semantic doesn't change today (operator owns all the entities they're querying); the architecture gains defence-in-depth.

**Thread B - Bound the anchor (Defect 2).**

```java
// Application config knob with sensible default
@Value("${odd.platform.my-lineage.anchor-max:1000}")
private int anchorMax;

// DataEntityRelationsServiceImpl.java
public Mono<...> getLineageRelations(...) {
    return dataEntityRepository.listByOwner(o.getId(), anchorMax)
        .switchIfEmpty(Mono.error(new BadUserRequestException(
            "Owner anchor set exceeds odd.platform.my-lineage.anchor-max=" + anchorMax + 
            ". Reduce owned-entity count or increase the limit.")))
        .flatMapMany(oddrns -> ...);
}
```

Doc-side: surface the new config knob on `odd-platform.md`; recommend operators move large-anchor accounts (admin / CI-bot) to a separate service-account pattern with narrower ownership.

**Thread C - In-SQL pagination for the derived set (stretch).**

Push the pagination into the derived-set SQL instead of in-memory filtering after the CTE. The CTE is structurally tough to paginate (it includes the anchor set); a follow-up architectural improvement, not blocking Thread B's bound.
