# SHB-111 — Soft-deleted Policy still grants permissions (catalogue-vs-grant asymmetry)

**Category**: open
**Severity**: HIGH

## Hypothesis

Operators deleting an RBAC Policy via `DELETE /api/policies/{id}` see it disappear from the Management → Access Management → Policies LIST and from the policy-detail page — but the **policy continues to grant its statements to every user attached via any surviving Role**. The list view (`PolicyController.getPolicyList`) routes through `policyRepository.list` which auto-applies `deleted_at IS NULL` via the soft-delete base class; the authorization HOT PATH (`getCurrentUserPolicies` → `getRolesPolicies` JOIN at `ReactivePolicyRepositoryImpl.java:32-35`) does NOT filter `deleted_at IS NULL`. The cascade-delete defence at `PolicyServiceImpl.java:89-92` is INTENDED to prevent this state — but the defence is service-tier-only and non-atomic with the soft-delete (lines 89 + 93 are two separate R2DBC calls outside any transaction). The feature is **"RBAC soft-delete visibility-vs-grant inconsistency"** — catalogue shows policy as gone, runtime authorization still honours it.

## Evidence

- `odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/service/PolicyServiceImpl.java:83-95` — delete flow: get(id) → switchIfEmpty NotFoundException → filter !=Administrator → switchIfEmpty BadUserRequestException → `roleToPolicyRepository.isPolicyAttachedToRole(id)` (line 89) → filter true → flatMap raise `CascadeDeleteException("Policy is attached to a role")` (line 91) → `policyRepository.delete(id)` (line 93 — soft-delete via base class). **NO `@ReactiveTransactional` annotation** at line 83.
- `odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/repository/reactive/ReactivePolicyRepositoryImpl.java` (per batch-H sidecar evidence) — `getRolesPolicies` JOIN does NOT filter `policy.deleted_at IS NULL`. Per batch-H known_security_gaps[0]: soft-deleted policies appear in the JOIN output and are evaluated by the permission framework. The repository-tier defect is anchored in F-006.
- `odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/service/PolicyServiceImpl.java:102-107` — `getCurrentUserPolicies()` is the authorization HOT PATH. Invoked from `ManagementPermissionExtractor.getNonContextualPermissions` and `AbstractContextualPermissionExtractor.getContextualResourcePermissions` on EVERY authorized request that traverses the permission framework. Per-request DB roundtrip; no caching; soft-deleted policy is silently returned and evaluated.
- Race window: three concurrent clients — client A `DELETE /api/policies/{id}`, client B `POST /api/roles/{r}/policies` (adds binding to the same policy), client C `GET /api/policies/{id}`. A reads `isPolicyAttachedToRole=false` at line 89; B inserts the binding; A continues to soft-delete at line 93. The result is a soft-deleted policy WITH a surviving role binding — exactly the orphan state the defence intended to block. C sees 404 on read (policy gone), but the binding still grants the policy's statements to every user attached to role `r`.
- `odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/controller/PolicyController.java:52-57` — the DELETE controller method. No `@PreAuthorize` (gated upstream by `SecurityConstants.SECURITY_RULES:163-168` POLICY_DELETE entry); no `@Slf4j`; no audit log; returns 204 No Content on success. The forensic silence pattern: a privileged caller invokes DELETE; no application log line; the orphan-binding state forms silently.
- Live `/configuration-and-deployment/enable-security/authorization/policies` docs WebFetched 2026-05-25 status 200 — describes the policy JSON shape but is silent on the lifecycle: NO mention of soft-delete semantics, NO mention of cascade-delete behaviour, NO mention of catalogue-vs-grant visibility asymmetry, NO mention that DELETE on a policy still bound to any role raises HTTP 400 with `"Policy is attached to a role"`.

## Notes

- **Operator threat model**: a security incident necessitates removing a privileged policy. The operator clicks DELETE in the Management UI. The UI shows the policy is gone. The operator believes the privilege is revoked. The actual state: the policy row has `deleted_at = NOW()` but the `role_to_policy` binding (and consequently every user attached to any binding role) still resolves the policy's statements via `getRolesPolicies`. The incident response is incomplete; the privilege grant persists. This is the LSN-001-shape (silent inconsistency that the docs do not surface as a caveat) applied to security-relevant RBAC mutations.
- The race window above is the EVEN MORE SUBTLE failure mode. The cascade-defence is correct IF nothing else mutates concurrently. The platform offers no transactional isolation here. `RoleServiceImpl` mutations DO carry `@ReactiveTransactional` (lines 50, 64, 77 per RoleServiceImpl sidecar) — the asymmetry between Role-side (transactional) and Policy-side (not transactional) is a recurring drift pattern across the RBAC service tier.
- Cross-link with F-006 (RBAC policy lifecycle — soft-delete with permission-grant persistence). F-006 anchors the soft-delete-still-grants finding at the repository tier (batch-H). This thread is an ENRICHER at the catalogue-vs-grant axis: F-006 captures WHY (the JOIN doesn't filter); SHB-111 captures the operator-visible asymmetry between UI and runtime authorization.
- Cross-link with batch-Q PolicyList UI tier — the UI does NOT re-fetch policies-by-id from server on every render; it relies on the LIST endpoint (which DOES filter soft-deleted). So the UI catalogue is correct (the LIST endpoint is the load-bearing surface). The runtime authorization is incorrect (the GRANT endpoint via `getCurrentUserPolicies` does NOT filter). Two surfaces, two different soft-delete filters, different operator-visible outcomes.
- Caveat: the cascade-defence at PolicyServiceImpl.java:89-92 is the SOLE service-layer protection against the orphan-binding state. ANY code path that bypasses the service (a future repository-direct caller, a DB-direct hot-fix `UPDATE policy SET deleted_at = NOW()`, a `delete()` refactor that drops this filter) re-opens the gap. The defence is fragile.
- Caveat: the cascade-defence is also the only place an operator gets feedback that delete failed because of bindings. A scripted cleanup that catches the HTTP 400 must detach roles FIRST (PUT on the ROLE side to drop the policy binding) THEN delete the policy. The docs don't document this dependency.
- The PolicyServiceImpl class is forensically dark: no @Slf4j, no Logger, no log call on create/update/delete (verified — 117-line class, zero log statements). Combined with the parallel silence at the controller (PolicyController per batch E + batch-ZD) and repository (batch H) tiers, the entire Policy mutation stack emits NO application logs. Aligns with the F-006 facet `forensic_silence_on_rbac_mutations`.
- This is an ENRICHER for F-006 — the existing flow captures the soft-delete-still-grants defect at the repository tier. This thread reframes it as the operator-visible "I clicked DELETE and the grant persists" experience AND adds the race-window dimension AND the catalogue-vs-grant UI asymmetry that F-006 does not currently name.
