## Description

The `getPopularTagList` operation (`GET /api/tags`) takes an optional `ids` query parameter. In the OpenAPI spec that parameter reuses the **shared** `IdsParam` component, whose description is the generic **"Entity ids"** (`components.yaml:4239-4248`; the operation references it at `openapi.yaml:351`). But the parameter does not filter by entity id — it filters by **tag id**: `ReactiveTagRepositoryImpl.java:141-142` does `if (CollectionUtils.isNotEmpty(ids)) { conditions.add(TAG.ID.in(ids)); }` on the `TAG` table.

**Operator-visible consequence.** A direct-API or SDK consumer reading "Entity ids" reasonably supplies **data-entity** ids to narrow the popular-tags list to a set of entities. Because the query matches `TAG.ID IN (...)`, those entity ids almost never coincide with tag ids, so the call returns an **empty (or nonsensical) tag list** with no error — a silent wrong-result. The label actively misleads: the parameter is a tag-id whitelist, not an entity filter.

There is no dedicated tags api-reference sub-page today (the API-reference hub explicitly defers the tag family to the OpenAPI spec / Swagger UI — `api-reference.md:22`). The operator-facing home for tag-API behaviour caveats is the existing **"Known limitations and operator caveats"** section on `tagging.md`, which already documents this same endpoint's popularity-ordering quirk (`tagging.md:62-68`). This item adds the `ids`-semantics caveat alongside it.

The **root-cause** fix is a spec change — give the operation its own `TagIdsParam` (description "Tag ids") or an operation-level parameter description — which belongs in the `opendatadiscovery-specification` repo; cross-link the SPC spec-hygiene items. This documentation item closes the operator-facing gap regardless of when the spec fix lands.
