## What

A user who holds the `DIRECT_OWNER_SYNC` permission can, in a single `POST /api/owner_association_request`, (1) create a brand-new `Owner` of any name they choose and (2) bind their own identity to it as an approved association - without ever passing the `OWNER_CREATE` gate that the dedicated owner-creation endpoint (`POST /api/owners`) enforces, and without any cross-check that the requested owner name corresponds to a group the user actually belongs to in the identity provider. The owner name is taken verbatim from the request body and `getOrCreate(...)` mints it if it does not already exist; the same call then auto-approves the association purely on the presence of the `DIRECT_OWNER_SYNC` permission. This is the "direct sync" fast-path intended for trusted SSO-group provisioning, but as written it is an open self-service owner-mint-and-claim for anyone granted that one permission.

## Why it matters

This is a **silent privilege escalation within the owner/ownership model.** `DIRECT_OWNER_SYNC` is conceptually "let my SSO group map to an owner automatically"; in practice it lets the holder fabricate any owner (e.g., one named after a sensitive team) and immediately become a member of it, gaining whatever ownership-scoped access that owner confers - without holding `OWNER_CREATE` and without the system verifying the owner name against the user's real IdP groups. Because the association is returned already approved, no second admin ever sees or signs off on it. The blast radius is bounded by who is granted `DIRECT_OWNER_SYNC`, so this is medium rather than high; but the two safeguards a reviewer expects on an owner-mint path - the `OWNER_CREATE` gate and an identity-provider group cross-check - are both absent on this branch, which contradicts the rest of the ownership model.

## Suggested fix

Two changes, addressing the two halves of the chain:

1. **Gate the mint.** Require `OWNER_CREATE` (in addition to `DIRECT_OWNER_SYNC`) before `getOrCreate(ownerName)` is allowed to create a *new* owner on the direct-sync path - or restrict `getOrCreate` here to *resolve-only* (fail if the owner does not already exist) so direct sync can bind to provisioned owners but not invent them.
2. **Cross-check the bind.** On the auto-approve branch, verify that `ownerName` corresponds to a group/claim the authenticated user actually carries from the OIDC token before calling `createRelation(...)` + `mapToApprovedRequest(...)`. If it does not, fall through to the normal request-for-approval branch rather than auto-approving.

Open to alternatives on the exact mechanism; the invariant is that no single POST under one permission should both create an arbitrary owner and self-bind to it without an identity cross-check.

## How discovered

Surfaced by the 2026-06-08 feature-reflection contradiction harvest (harvest report under `integration-tests/run-log/`, 2026-06-08) over feature reflection F-075 (owner-association / direct-owner-sync flow): the reflection's product-owner hypotheses ("a direct-sync user can only map to owners that already exist / that match their IdP groups") were contradicted by reading `OwnerAssociationRequestServiceImpl.java` - both assumptions are false on the `permissions.contains(DIRECT_OWNER_SYNC)` branch.

Distinct from **PLT-125**, which addresses only the *mint half* (the `getOrCreate` create-an-arbitrary-owner concern). The `createRelation`-under-permission auto-approve/self-bind branch - and the absent OIDC group cross-check - is not covered by PLT-125 and is the additional defect tracked here.
