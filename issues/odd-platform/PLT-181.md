## What

`GET /api/messages/{message_id}/url` - the "Open in Slack" redirect behind each Discussion message - does not 404 when the message id does not exist. The handler resolves the message's provider URL and, only on a hit, maps it to a 302 redirect; on a **miss** the reactive stream is empty and Spring WebFlux completes the exchange with a default **HTTP 200 and an empty body** (no redirect, no error). Two consequences for the operator: (1) the "Open in Slack" button silently does nothing for a message that has gone away (the browser navigates to an empty 200 instead of being redirected to Slack), and (2) because the endpoint is reachable by any authenticated user with no read/ownership scope, the 200-empty-vs-302 distinction is an existence oracle - a caller can probe arbitrary message UUIDs and learn which ones exist from the status/redirect alone.

## Where

The redirect handler maps only the present-value path and never translates a miss into a 404:

`odd-platform-api/src/main/java/org/opendatadiscovery/oddplatform/datacollaboration/controller/DataCollaborationController.java:42-49`
```java
public Mono<ResponseEntity<Void>> redirect(final UUID messageId, final ServerWebExchange exchange) {
    return dataCollaborationService.resolveMessageUrl(messageId)
        .map(providerUrl -> ResponseEntity
            .status(HttpStatus.FOUND)                       // 302 only on a hit
            .headers(headers -> headers.setLocation(URI.create(providerUrl)))
            .build()
        );
    // no switchIfEmpty -> empty Mono completes as a default empty 200 on a miss
}
```

There is no `switchIfEmpty(Mono.error(new NotFoundException(...)))`, so an unresolved id falls through to WebFlux's default empty-200 completion.

Contract drift on the same operation: the OpenAPI spec declares **only `301`** (and the impl actually returns `302`), and documents no `404`:

`odd-platform-specification/openapi.yaml:1776-1791`
```yaml
/api/messages/{message_id}/url:
  get:
    operationId: redirect
    parameters:
      - name: message_id
        schema: { type: string, format: uuid }
    responses:
      '301':                       # spec says 301; impl sends 302; no 404 declared
        description: Moved Permanently
```

The `Message.url` field that the UI button follows is itself this endpoint (`components.yaml:3434-3450`, `Message.url: string`), so a stale/deleted message id hits exactly this dead-end. (`message_id` is `format: uuid`, so a syntactically-invalid path segment is rejected at binding; the gap is a *well-formed but non-existent* UUID, which silently 200-empties.)

Confirmed the empty-Mono mechanism end-to-end (read 2026-06-10): `redirect` -> `resolveMessageUrl` (`DataCollaborationServiceImpl.java:72-77`) -> `reactiveMessageRepository.getMessageProviderIdentity(messageId)` (`ReactiveMessageRepositoryImpl.java:172-185`), a jOOQ `mono(query)` selecting on `MESSAGE.UUID.eq(messageId)` (plus `MESSAGE.CREATED_AT.eq(extractDateTimeFromUUID(messageId))`). A missing id makes the jOOQ Mono empty -> the service's `.flatMap` never fires -> the controller's `.map` never fires -> the outer Mono completes empty -> WebFlux's default empty-200. (The extra `CREATED_AT` predicate means a well-formed but non-UUIDv1 id, whose embedded timestamp will not match a stored row, also misses and 200-empties - the same dead-end.) There is no global WebFlux filter that rewrites an empty redirect Mono to 404 - the only not-found mapping is `ControllerAdvice.handleNotFound` (`ControllerAdvice.java:30-34`), which requires a `NotFoundException` the handler never raises.

## User-facing impact

Static code+spec trace, not driven on a running stack in this sweep. Verified across the chain (file:line above): the "Open in Slack" button (`Message.url` -> `GET /api/messages/{message_id}/url`) on a message whose backing row is gone returns an empty HTTP 200 - the browser navigates to a blank page rather than being redirected to Slack or shown an error. Security-shaped, but bounded: the endpoint is in the authenticated bucket (no whitelist entry; not anonymous under enabled auth) and carries no per-message read/ownership check, so the 200-empty (miss) vs 302 (hit) split is an **authenticated** message-existence-by-id oracle over the UUID space, with no logging - a low-bandwidth confidentiality leak, not data loss. Auth mode: under `auth.type=DISABLED` every caller is the synthetic admin so the oracle is trivially reachable; under enabled auth any logged-in principal can probe it regardless of permissions. Remaining check: drive a missing well-formed UUID on a running stack and confirm the 200-empty (predicted) and the dead button.

## Why it matters

Two real impacts. **Operator-facing:** the "Open in Slack" button on a message whose backing record is gone does nothing visible - the browser lands on a blank 200 rather than getting an error or being told the message no longer exists. **Security-shaped:** the endpoint is in the authenticated bucket but carries no per-message read/ownership check, so the 200-empty (miss) vs 302 (hit) split is an authenticated message-existence-by-id oracle over the whole UUID space, with no logging. Medium severity: low-bandwidth oracle and a degraded-but-not-destructive UX, not data-loss; the fix is small and local.

## Suggested fix

1. Add `switchIfEmpty(Mono.error(new NotFoundException("Message", messageId)))` to the redirect handler (or to `resolveMessageUrl`) so a missing/unresolvable id returns **404**, mirroring the not-found guard the sibling list-children service method already has.
2. Fix the contract on `redirect` in `odd-platform-specification/openapi.yaml`: declare the `404`, and reconcile the success status with the implementation (the impl sends `302 Found`, the spec says `301 Moved Permanently` - pick one and make both agree). Open to alternatives.
