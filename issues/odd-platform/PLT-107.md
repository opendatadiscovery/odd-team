## What

The SMTP protocol selector in `NotificationConfiguration` is a case-sensitive lowercase comparison — `.equals("smtp")`. The operator-facing Gmail configuration example writes the protocol value as `SMTP` (uppercase). An operator copying the documented example verbatim falls through to the ELSE branch: `mail.smtp.auth` and `mail.smtp.starttls.enable` are never set regardless of the configured `smtp.auth` / `smtp.starttls` keys, so STARTTLS does not engage and SMTP AUTH does not negotiate. There is no boot warning — the misconfiguration is silent until mail delivery fails (or silently sends unauthenticated/unencrypted, depending on the relay).

Sources: HARVEST-009 (doc-understanding harvest, 2026-05-29). Doc caveat tracked at `backlog/docs/DOC-295.md`.

## Why it matters

This is a copy-the-example-and-it-silently-half-works trap. The platform's own documented Gmail example uses a value (`SMTP`) that the code does not recognise, so the operator believes they have configured authenticated, STARTTLS-encrypted mail and instead gets the unconfigured branch with no error at boot. Depending on the relay, alert emails either fail to send (notifications silently lost) or are sent without AUTH/TLS. Medium severity because it requires the email channel to be configured and only the documented-uppercase value triggers it — but the failure is silent and the docs themselves point operators at the failing value.

## Suggested fix

- Make the protocol comparison case-insensitive: `"smtp".equalsIgnoreCase(protocol)` (and normalise/trim the value). Optionally validate the protocol value at boot and log a warning (or fail fast) on an unrecognised value rather than silently selecting the ELSE branch.
- Independently, correct the documented Gmail example to the value the code accepts (lowercase `smtp`) so doc and code agree even before the code fix lands.
