## What

`PUT /api/dataentities/{data_entity_id}/description` against a data-entity id that **does not exist** (e.g. a typo'd or stale id) returns **HTTP 200 OK** with the submitted description echoed back in the body - as if the write succeeded - when in fact nothing was written. The UPDATE matches zero rows, so the `setInternalDescription` Mono emits empty; the missing `switchIfEmpty` means the no-op is never converted to a `404`. The `DESCRIPTION_UPDATED` activity event is correctly skipped (its `@ActivityLog` method emits no element), so the discarded write also leaves no trace in the activity feed. The **sibling** endpoint for dataset-field descriptions, written in the same style, correctly returns `404` for a missing field.

Verified mechanism (2026-06-10): the response is **not** a WebFlux default empty 200 - it is a fully-populated `200 InternalDescription` body. `DataEntityServiceImpl.upsertDescription` (`:325-333`) chains `dataEntityInternalStateService.updateDescription(...).then(termService.handleDataEntityDescriptionTerms(...)).map(...)`. Reactor's `Mono.then(other)` runs `other` on the **completion** of the (empty) source, so even though `updateDescription` wrote nothing and emitted empty, `handleDataEntityDescriptionTerms` still runs and emits a (typically empty) term list, and the trailing `.map(...)` rebuilds an `InternalDescription(submittedDescription, [])`. The controller's `.map(ResponseEntity::ok)` therefore receives an element and returns `200` with the submitted text echoed - making the discarded write look definitively saved. (Side effect worth noting: because `handleDataEntityDescriptionTerms` runs, its own `TERM_ASSIGNMENT_UPDATED` `@ActivityLog` can fire even though the entity does not exist; only the `DESCRIPTION_UPDATED` event is skipped.)

## Where

The miss is a missing `switchIfEmpty` on the entity-description update. Chain, top to bottom (line numbers verified against current HEAD `3049b9af`):

```java
// controller/DataEntityController.java:208-210 - returns 200 with the re-materialised body (see below)
return internalDescriptionFormData
    .flatMap(form -> dataEntityService.upsertDescription(dataEntityId, form))
    .map(ResponseEntity::ok);
```

```java
// service/DataEntityServiceImpl.java:325-333 - .then(...).map(...) re-materialises an element even on a no-op update
public Mono<InternalDescription> upsertDescription(final long dataEntityId, final InternalDescriptionFormData formData) {
    return dataEntityInternalStateService.updateDescription(dataEntityId, formData)   // emits EMPTY on missing id
        .then(termService.handleDataEntityDescriptionTerms(dataEntityId, formData.getInternalDescription()))  // .then runs on empty completion
        .map(terms -> new InternalDescription(formData.getInternalDescription(), ...));  // -> populated 200 body
}
```

```java
// service/DataEntityInternalStateServiceImpl.java:56-59 - @ActivityLog DESCRIPTION_UPDATED; never fires on a no-op (no element emitted)
@ReactiveTransactional
@ActivityLog(event = ActivityEventTypeDto.DESCRIPTION_UPDATED)
public Mono<DataEntityPojo> updateDescription(... final long dataEntityId, ...) {
    return dataEntityRepository.setInternalDescription(dataEntityId, formData.getInternalDescription())
        .flatMap(pojo -> ...)   // no switchIfEmpty -> empty Mono propagates; this flatMap never runs
        ...
}
```

```java
// repository/reactive/ReactiveDataEntityRepositoryImpl.java:430-437 - UPDATE ... WHERE id = ? RETURNING
@Override
public Mono<DataEntityPojo> setInternalDescription(final long dataEntityId, final String description) {
    final String newDescription = StringUtils.isEmpty(description) ? null : description;
    final var query = DSL.update(DATA_ENTITY)
        .set(DATA_ENTITY.INTERNAL_DESCRIPTION, newDescription)
        .where(DATA_ENTITY.ID.eq(dataEntityId))   // <-- 0 rows on a missing id
        .returning();
    return jooqReactiveOperations.mono(query)     // <-- emits EMPTY, not an error, on 0 rows
        .map(r -> r.into(DataEntityPojo.class));
}
```

Contrast - the dataset-field sibling, identical shape but with the guard present, so it **does** 404:

```java
// service/DatasetFieldInternalInformationServiceImpl.java:32-33
return reactiveDatasetFieldRepository.updateDescription(datasetFieldId, formData.getDescription())
    .switchIfEmpty(Mono.error(new NotFoundException("DatasetField", datasetFieldId)))   // <-- the guard PLT-169 is missing
    .flatMap(pojo -> ...);
```

## User-facing impact

A client (or generated SDK) that PUTs a description to a wrong/stale data-entity id receives a `200 OK` whose body **echoes the submitted description** (with an empty terms list), so it looks definitively saved - but nothing was written and no `DESCRIPTION_UPDATED` event was recorded. An operator correcting documentation against a stale id believes their edit landed; it silently did not, and the activity feed shows no trace of the discarded write to reconstruct it later. In the shipped UI this is low-frequency (the editor PUTs the id of the entity the user is viewing, so a missing id is hard to hit interactively), but it is real for any API/SDK/automation client and is an inconsistent contract: the dataset-field description sibling 404s for the identical case. Not data loss (no existing data overwritten) and not a security hole, but a write endpoint that returns success for a write that never happened. Severity medium (held).

## Why it matters

The platform already proves it knows the right pattern one endpoint over (the dataset-field sibling 404s). The entity-description endpoint diverges, so a client cannot rely on uniform not-found semantics across the description APIs, and the 200-with-echoed-body actively misleads. The activity-feed gap means the discarded write cannot be audited after the fact.

## Suggested fix

Add the same guard the dataset-field path already has, so a missing entity becomes a real not-found:

```java
// DataEntityInternalStateServiceImpl.updateDescription (or in DataEntityRepositoryImpl.setInternalDescription)
return dataEntityRepository.setInternalDescription(dataEntityId, formData.getInternalDescription())
    .switchIfEmpty(Mono.error(new NotFoundException("DataEntity", dataEntityId)))
    .flatMap(pojo -> ...);
```

This both restores the 404 and lets the `@ActivityLog`/downstream chain behave correctly (it simply never runs on the error path, which is correct). Note the `404`-vs-caveat decision is a maintainer call - if upsert-on-missing is ever intended to be a legitimate create, that should be explicit and documented rather than a silent 200 no-op; the dataset-field sibling's 404 is the strong precedent for choosing 404. Open to alternatives.

## How discovered

Surfaced during the 2026-06-08 contradiction-harvest (feature-reflection triage), from the F-004 reflection's product-owner read of the entity-description write path. The cross-endpoint contrast (entity description 200s on a missing id, dataset-field description 404s) is exactly the kind of intent-vs-implementation drift the reflection pass is built to catch.

**Verified end-to-end 2026-06-10 (user-facing verification sweep) - verdict HOLDS, mechanism corrected.** Traced controller -> `DataEntityServiceImpl.upsertDescription` -> `DataEntityInternalStateServiceImpl.updateDescription` -> repo `setInternalDescription`. The defect (200 on a missing id, no write, no `DESCRIPTION_UPDATED` event) is real. The original draft's mechanism was inaccurate: it claimed `.map(ResponseEntity::ok)` is never invoked so WebFlux returns a default **empty** 200. In fact `upsertDescription`'s `.then(handleDataEntityDescriptionTerms(...)).map(...)` re-materialises an element on the empty completion, so the controller returns a **populated** `200 InternalDescription` echoing the submitted text (and the term-assignment handler still runs, so its `TERM_ASSIGNMENT_UPDATED` event can fire even though only `DESCRIPTION_UPDATED` is skipped). Corrected above; the missing-`switchIfEmpty` root cause and the 404 fix are unchanged.
