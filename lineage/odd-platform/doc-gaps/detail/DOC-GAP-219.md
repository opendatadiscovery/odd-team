    - **The operator-impact migration narrative**: an operator runs ODD with `auth.type=LOGIN_FORM` for an internal-team pilot with `auth.login-form-credentials: alice:secret,bob:secret,...`. Each operator creates an Owner row via the Management UI and attaches `alice` to the `OwnerAlice` Owner with the `Admins` Role. The team then migrates to `auth.type=LDAP` against the corporate directory. The LDAP `alice` (CN=alice / DN=cn=alice,ou=engineers,dc=corp) authenticates successfully → `AuthIdentityProviderImpl` returns `UserDto("alice", null)` → repository looks up by `PROVIDER IS NULL AND OIDC_USERNAME = 'alice'` → finds the OLD LOGIN_FORM-era association → grants the OLD `Admins` Role's permissions. **The operator has not authored any LDAP-side association** but the LDAP user inherits the LOGIN_FORM-era binding.
    - **The operator-impact concurrent-mode narrative**: ODD doesn't support simultaneously running LOGIN_FORM and LDAP (the four `auth.type` modes are mutually-exclusive `@ConditionalOnProperty` gates), so the concurrent-mode case is technically impossible. But the migration case IS the operational reality — operators DO move from LOGIN_FORM to LDAP, and the bleed surfaces silently on the first LDAP login that happens to share a username with a previous LOGIN_FORM credential.
    - **The security-relevant inverse**: a LOGIN_FORM user `admin` with the platform's seeded credentials `admin:admin` creates Owner associations + ROLE bindings during the LOGIN_FORM phase. Migration to LDAP: any LDAP-authenticated user with username `admin` (a common username) inherits ALL the LOGIN_FORM-era admin's associations. The credentials-shipping default `admin:admin,root:root` (`application.yml:37`) makes `admin` and `root` the two highest-risk inherited usernames.
    - **The structural insight (cross-batch composition)**: this finding is the AUTH-MODE-TIER VIEW of the same mechanism the batch-N repository-tier sidecar surfaced. The repository tier knows about `IS NULL` matching; the auth-mode wiring tier knows about `provider=null` injection. Neither layer alone surfaces the OPERATOR-IMPACT shape (migration / shared keyspace); the cross-layer composition surfaces it.
    - **The fix-decision spectrum**: a code-side fix could (a) write a literal string `"LOGIN_FORM"` / `"LDAP"` into the provider field at the auth-mode wiring layer, distinguishing the two modes at the database keyspace; or (b) write `null` deliberately (the current state, documented as intentional) and rely on operators to not share usernames across modes; or (c) add a migration that re-keys existing `user_owner_mapping` rows. The intentional-vs-oversight question is open — there's no in-code comment, no ADR, no live doc clarifying the design intent.
