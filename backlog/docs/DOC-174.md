## Description

The live Management page (WebFetched 2026-05-27) accurately describes the architectural shape — *"Tab visibility is permission-aware (Associations is the explicit case today; other tabs are visible to any signed-in operator and the per-tab actions enforce permission checks)"*. It does **not** name the operator-visible consequence: that this constitutes **reconnaissance information disclosure** for a separation-of-duties-conscious org.

**Surface 1 — Read-collaborative posture's operator-visible consequence (F-105a).** `ManagementRoutes.tsx:102-110` wraps `RestrictedRoute` around `/associations/*` only. The other 8 sub-routes (Policies, Roles, Owners, Namespaces, DataSources, Collectors, Tags, Integrations) use `WithPermissionsProvider` (context-only — not a rendering gate per DOC-GAP-254) OR no wrapper at all. A non-ADMIN reader deep-linking to `/management/policies/{id}` reads the **full Policy JSON** (permission grants, ODDRN selectors, role bindings). Under DISABLED auth, this extends to anonymous network callers.

**Surface 2 — `/management/integrations` bare route (F-105b).** `ManagementRoutes.tsx:150` (`<Route path='integrations/*' element={<Integrations />} />`) has no `WithPermissionsProvider` wrapper at all. Inner `usePermissions().hasAccessTo(...)` calls for any integration-specific permission resolve via the wrong context (the outer `Management.tsx` seeds only `OWNER_ASSOCIATION_MANAGE`) — surprising deny-by-default. Compound failure: the list IS readable; the action is denied via wrong context.

## Acceptance Criteria

- [ ] The Management page gains a **visibility-vs-mutability matrix** listing the 9 sub-areas (Associations, Policies, Roles, Owners, Namespaces, DataSources, Collectors, Tags, Integrations) with two columns: READ exposure (any-authenticated-user / ADMIN-only / etc.) + MUTATE gate (RBAC permission name + enforcement mechanism — controller-level `@PreAuthorize` / route-level RestrictedRoute / HOC-level WithPermissions).
- [ ] The page explicitly states the **read-collaborative posture for Management reads**: only `/associations/*` is route-gated; the other 8 sub-area read surfaces are accessible to any authenticated user (and to anonymous callers under DISABLED). Operators wanting per-team read-isolation need a network-perimeter mitigation; the platform's authorization layer does not gate these reads today.
- [ ] The page documents the **`/management/integrations` permission-context fall-through caveat**: any integration-specific permission check defaults to deny because the outer context seeds only `OWNER_ASSOCIATION_MANAGE`. If a future integration ships a feature gated by a different permission, operators will see deny-by-default until the route's wrapper is fixed. Cross-reference DOC-GAP-254 for the cross-cutting "context-not-gate" architectural pattern.
- [ ] `Consumer-read:` footer cites `ManagementRoutes.tsx:30-149` (the 8 context-only routes), `ManagementRoutes.tsx:102-110` (the lone RestrictedRoute on associations), and `ManagementRoutes.tsx:150` (the bare integrations route).
- [ ] Live-site verification post-merge.
