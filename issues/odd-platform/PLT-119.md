## What

`POST /api/datacollaboration/providers/slack/messages` lets **any authenticated user** attach a Data Collaboration message to **any `data_entity_id` in any bot-joined Slack channel** - there is no owner check, no per-entity read-scope check, and no RBAC permission gate on the route. The message is posted into Slack as the shared workspace bot, so one user can inject messages onto another team's entity discussion and into a channel that user has no relationship with. This is a cross-tenant write / data-isolation breach on the outbound path.

This is **distinct from PLT-054** (which covers the *inbound* `/api/slack/events` webhook signature-verification and the at-least-once duplicate-message defects) and from the DOC-204 caveat (which documents the general no-RBAC posture). Neither item proposes a gate - or an explicit read-collaborative ADR - for the *outbound* cross-owner write. The `postMessageInSlack` sidecar flags the gap (`security.known_security_gaps[0,2]`) but no PLT/REFACTOR owns the decision.

## User-facing impact

The "user" is any authenticated platform user in a multi-team / multi-tenant deployment with Slack Data Collaboration enabled (`datacollaboration.enabled=true`; off by default).

- **WHO/WHAT:** any authenticated user can `POST /api/datacollaboration/providers/slack/messages` naming an arbitrary `data_entity_id` and an arbitrary `channel_id`, and the platform posts the message - as the shared workspace bot - onto that entity's Discussions thread and into that Slack channel, with no check that the caller owns/can-read the entity or has any relationship to the channel. Verified by BE trace 2026-06-10 (table above): the request's `dataEntityId`/`channelId` are honoured directly; the sole guards are existence-of-entity and resolvability-of-channel.
- **Confidence:** the authorization-gap is **code-settled** (no SecurityRule for the route + no owner/read-scope check in the service - both read directly, not inferred). What is not driven is the live cross-tenant demonstration (post onto another team's entity on a running multi-tenant stack); the gap itself does not depend on that - it is the absence of a check, which the static read settles. Auth mode is irrelevant to the gap (it exists under every mode that reaches the route as `.authenticated()`); it only matters that the deployment has more than one owner/team.
- **NOT a default-deployment issue:** Data Collaboration ships disabled, and a single-team deployment has no cross-owner boundary to breach - so the impact lands specifically on multi-team deployments that enabled the feature.

## Impact

In a multi-team / multi-tenant deployment, any authenticated user can post a message - visible in Slack and in the entity's Discussions tab as the trusted platform bot - onto an entity owned by another team, in a channel they have no business in. There is no namespace read-isolation on the write. This is arbitrary cross-owner content injection attributed to the platform's own bot identity; combined with the unauthenticated inbound webhook (PLT-054) the Discussions surface has no isolation on either direction.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: either add a read/owner-scope check on `data_entity_id` in `DataCollaborationServiceImpl.createAndSendMessage` (plus an `(entity, allowed-channels)` mapping so a message cannot be posted to an arbitrary channel), **or** record an explicit read-collaborative ADR that accepts cross-owner posting by design and documents it. The reflection recommends an SME consult to choose between gate and documented-by-design.
