- **ADR-CANDIDATE-018** (NEW 2026-05-10A; STRENGTHENED 2026-05-12C; FURTHER STRENGTHENED 2026-05-12D — now 5-sidecar cross-feature): Outbound-integration-required configuration is fail-fast at boot — Slack OAuth token is checked non-empty in the bean factory, raising `IllegalArgumentException` on empty/missing, rather than degrading silently to a runtime failure
  - **Category**: promote
  - **Support**: surfaced by 5 sidecars cross-feature (`postMessageInSlack` + `NotificationsProperties` from batch C + **NEW 2026-05-12D**: `EmailSenderProperties` (`NotificationConfiguration.java:39-49` throws `IllegalArgumentException` for blank `sender` / `host` / `protocol`) + `ODDLDAPProperties` (`ODDLDAPProperties.java:40-49` `@PostConstruct validate()` throws `IllegalStateException` for empty URL + missing-search-method) + `DataCollaborationProperties` (`DataCollaborationProperties.java:14-20` `@PostConstruct validate()` throws `IllegalStateException` for `sendingMessagesRetryCount < 0`)). The 5-sidecar consistency is the cross-feature convention: every `@ConfigurationProperties` POJO that gates an outbound integration / boot-critical wiring uses imperative `@PostConstruct` validation throwing on bean-construction failure — NEVER deferring to runtime first-use. The exception-type framing is itself a convention: `IllegalArgumentException` for bean-factory empty-checks (DataCollaboration + EmailSender) vs `IllegalStateException` for `@PostConstruct` validators (LDAP + DataCollab). The maintainer's signal: bean-factory failures are arguments-class; @PostConstruct failures are deployment-state-class. The pattern parallels the established GenAI-opt-in pattern (ADR-CANDIDATE-004) — the difference is that GenAI fails fast at *first request* via `null` URL, while Data Collaboration + Notifications + Email + LDAP all fail fast at *boot* via explicit throws on critical configuration

  - **Decision statement**: Bean factories AND `@ConfigurationProperties` POJOs that gate outbound-integration / boot-critical wiring raise an exception at construction time (or @PostConstruct) when their required fields are empty/invalid, rather than returning a degraded client or deferring the failure to first use. The pattern lives in five distinct surfaces: (a) `DataCollaborationConfiguration.java:21-25` for Slack OAuth token (IllegalArgumentException at bean-factory); (b) `NotificationConfiguration.java:46-48 / 75-77` for Slack webhook URL + webhook URL (IllegalArgumentException at bean-factory); (c) `NotificationConfiguration.java:39-49` for email `sender` / `host` / `protocol` blank-check (IllegalArgumentException at bean-factory); (d) `ODDLDAPProperties.java:40-49` for LDAP URL + search-method (IllegalStateException in @PostConstruct); (e) `DataCollaborationProperties.java:14-20` for retry-count non-negativity (IllegalStateException in @PostConstruct). The exception-type framing is itself a convention: `IllegalArgumentException` for bean-factory empty-checks (the argument was empty); `IllegalStateException` for @PostConstruct validators (the deployment state is wrong). Composed with the disabled-by-default family (ADR-CANDIDATE-004 / -019 / -029 / -040), the maintainer-intended deployment story is: feature is off by default → operator opts in → operator MUST set the required configuration or the platform refuses to boot.
  - **Wisdom test**: PASS. The 5-sidecar cross-feature consistency is the intent anchor — five independent `@ConfigurationProperties` / bean-factory surfaces author the SAME imperative validation pattern with the same exception-type discipline. The explicit `throw new IllegalArgumentException(...)` / `throw new IllegalStateException(...)` constructions are positive design decisions, not the absence of a feature. Structural: every future outbound-integration credential and every boot-critical `@ConfigurationProperties` field should follow the same pattern, and the maintainer has five concrete references.
