## Description

`/api/appInfo` returns deployment introspection — including the active `auth.type` (the value the SPA reads to decide whether to render a login form, an OAuth redirect, etc.). Three facts about it are untracked on the doc side:

1. **`/api/appInfo` is NOT whitelisted, so under every non-DISABLED mode it sits behind the login wall.** `SecurityConstants.WHITELIST_PATHS` is `{"/actuator/**", "/favicon.ico", "/ingestion/**", "/img/**", "/api/slack/events"}` (`SecurityConstants.java:96`) — `appInfo` is absent. Under `LOGIN_FORM` the chain is `.pathMatchers("/**").authenticated()` (`LoginFormSecurityConfiguration.java:55-57`, with a narrower permit-list that also excludes appInfo). So the endpoint an unauthenticated client would use to *discover the auth mode* is itself only reachable **after** the client has authenticated. DOC-239 (done) documents that appInfo is anonymously reachable under `DISABLED`; the inverse — that it is gated under `LOGIN_FORM`/`OAUTH2`/`LDAP` — is the untracked half and is the operator-relevant one (anyone reasoning about a pre-login bootstrap call gets the posture backwards otherwise).

2. **The spec operation has no `security:` element.** `openapi.yaml:2704-2717` (`getAppInfo`) declares no `security:`, so the machine-readable contract does not encode any posture at all — a reader/codegen sees an unmarked endpoint and may assume it is open, or assume it is auth'd, with nothing to ground either. This is tracked spec-side as **SPC-002 Facet 3** (pending — add `security: []` to denote "open by design under DISABLED"); DOC-409 is the doc-side companion and must NOT re-do the spec edit, only point at it.

3. **The SPA caches appInfo with no `staleTime`, so auth-mode UI lags within a live session.** `useAppInfo()` is a bare `useQuery({ queryKey: ['appInfo'], queryFn: () => appInfoApi.getAppInfo() })` with no `staleTime` (`appInfo.ts:4-8`). Combined with components that keep the query mounted, the auth-mode-derived UI reflects the value captured at first fetch; if the deployment's `auth.type` changes under the running session the UI will not re-derive until a refetch trigger fires. A LOW-severity staleness caveat, but real for an operator flipping auth modes and expecting the open tab to follow.

How it misleads: a reader designing a client bootstrap assumes appInfo is a public "what mode am I in" probe (it is, but only under DISABLED), and an operator changing `auth.type` expects an already-open SPA session to reflect the new mode.
