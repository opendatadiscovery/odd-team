    1. **Doc-side PRIMARY — `documentation/docs/configuration-and-deployment/odd-platform.md`** under the "Metric Storage Backend" section, add a "Metrics ingestion endpoint" sub-section:

Collectors push per-entity metric series via `POST /ingestion/metrics` with a `MetricSetList` payload (a list of `MetricSet`, each carrying an entity ODDRN + one or more `MetricFamily` records in OpenMetrics shape — `COUNTER` / `GAUGE` / `HISTOGRAM` / `SUMMARY` / `GAUGE_HISTOGRAM`).        >
       > **Security model — UNAUTHENTICATED IN EVERY DEPLOYMENT POSTURE**: this endpoint is in `SecurityConstants.WHITELIST_PATHS` (`/ingestion/**`), so UI auth modes (OAUTH2/LDAP/LOGIN_FORM) do NOT protect it. The `auth.ingestion.filter.enabled` toggle does NOT protect it (the filter binds the exact-literal `/ingestion/entities` POST only). S2S `auth.s2s.enabled=true` does NOT protect it (the `/ingestion/**` whitelist short-circuits before the S2S filter). To restrict access, deploy a network-level control (firewall, reverse-proxy ACL, mTLS). There is NO `auth.*` toggle that fail-closes this endpoint.
       >
       > **Tenant isolation BYPASSED on INTERNAL_POSTGRES storage** (the shipped default): the `odd.tenant-id` mechanism appends `tenant_id={value}` as a Prometheus label ONLY on the PROMETHEUS storage path. The INTERNAL_POSTGRES path has NO `tenant_id` column on `metric_series` / `metric_point` tables — multi-tenant isolation is NONEXISTENT on the default backend. A deployment configured with `odd.tenant-id=tenantA` AND `metrics.storage=INTERNAL_POSTGRES` still writes all metrics into one untyped Postgres namespace; the `odd.tenant-id` value is silently ignored.
       >
       > **No ODDRN existence validation**: the platform creates a `metric_entity` row for any ODDRN string the caller submits, regardless of whether a `data_entity` row with that ODDRN exists. Attackers can mint thousands of fake-ODDRN metric_entity rows or fake-ODDRN Prometheus series — Postgres or Prometheus cardinality DoS.
       >
       > **PII label propagation**: metric labels are propagated verbatim from the ingestion payload to the storage backend with no allowlist or sanitisation. Collectors emitting labels with PII (e.g. `user_email=`) will persist that PII verbatim in `metric_label_value` (INTERNAL_POSTGRES) or in the external Prometheus.
       >
       > **Cross-storage migration is one-way and lossy**: switching `metrics.storage` from INTERNAL_POSTGRES to PROMETHEUS in a running deployment makes pre-switch historical `metric_series` rows in Postgres UNREADABLE (the PROMETHEUS-side read controller routes through `ExternalMetricReader` which queries Prometheus, not Postgres). Going the other direction (PROMETHEUS → INTERNAL_POSTGRES) makes pre-switch metric labels in Prometheus orphaned. There is NO migration tooling. See LSN-001 / LSN-002 for the related attachment-storage and minio-region classes."
