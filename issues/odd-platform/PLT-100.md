## What

The three lineage read endpoints (`getDataEntityDownstreamLineage`, `getDataEntityUpstreamLineage`, `getDataEntityGroupsLineage` on `DataEntityController`) carry two operator-critical defects:

1. **Unset `lineage_depth` -> NPE -> HTTP 500.** The controller passes a boxed `Integer` while `LineageServiceImpl.getLineage` takes a primitive `int`; a missing `lineage_depth` autoboxes `null` and throws `NullPointerException` *before* the service body runs, surfacing as HTTP 500. The OpenAPI spec declares the parameter `required: false`, so a spec-compliant caller that omits it gets a 500 - not a default-depth graph. There is also no `@Max` cap (only `@Min(1)`), so an arbitrarily large `?d=` value is forwarded unclamped into the recursive CTE, and the CTE has no cycle guard and `.collectList()`-materialises the full graph in JVM heap - a memory/CPU amplification vector on branchy/diamond topologies.
2. **No authorization on any lineage endpoint.** None of the three has a `SECURITY_RULES` entry; all fall through to the catch-all `.pathMatchers("/**").authenticated()`, and neither service performs an owner/anchor check (`LineageServiceImpl` has no `AuthIdentityProvider` field). Any authenticated user who knows an entity-id or DEG-id reads the full reachable cross-owner lineage subgraph (other teams' pipeline structure). Under `auth.type=DISABLED` this is anonymously reachable. The DEG `/lineage` path is strictly wider blast radius - it enumerates the cross-owner co-membership graph of the whole catalogue.

Sources: HARVEST-030, HARVEST-031, HARVEST-032, HARVEST-043, HARVEST-044 (doc-understanding harvest, 2026-05-29). Doc caveat tracked at `backlog/docs/DOC-293.md`.

## Why it matters

A third-party API consumer following the published reference (which advertises `lineage_depth` as optional and softens the unset case to "undefined today") makes a spec-compliant call and gets an opaque HTTP 500 in production - the most common first call against the endpoint fails. Separately, the zero-RBAC posture means lineage - which reveals the shape of other teams' data pipelines - is readable by any authenticated user, and anonymously under the shipped `DISABLED` default. The DEG endpoint widens this to whole-catalogue co-membership enumeration. The unbounded depth + no-cycle-guard recursion is a denial-of-service amplifier on real DAGs. This is the LSN-001/002 class on both the crash and the silent over-exposure.

## Suggested fix

- Make the controller parameter a boxed `Integer` end-to-end and either (a) supply a server-side default depth when null, or (b) reject null with a 400 and a clear message - never let it reach the primitive and NPE. Document whichever behaviour ships.
- Add `@Max(...)` on the controller parameter and a defensive clamp at the service tier; add a cycle guard / visited-set to the recursive CTE so diamond topologies terminate without row amplification.
- Add `SECURITY_RULES` entries (or a programmatic owner-scope check via `AuthIdentityProvider`) on all three lineage endpoints; the DEG endpoint in particular should be owner/anchor-scoped given its wider blast radius.
