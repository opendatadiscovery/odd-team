## Description

The Policies **list** path filters soft-deleted rows (`WHERE deleted_at IS NULL`, soft-delete base class), so a deleted policy disappears from the Policies tab. But the **grant** path `getRolesPolicies` (`ReactivePolicyRepositoryImpl`, verified @ ede5d277) joins `POLICY` with **no `deleted_at` filter** — so a role still bound to a soft-deleted policy **keeps being granted that policy's permissions** on every authorized request. An operator who "deletes" a policy through the UI sees it gone and reasonably believes access is revoked — but it is not. This is a security-relevant catalogue-vs-grant asymmetry (a silent no-op of the operator's intent).

**Failure shape**: security exposure / actively-misleading absence — the operator believes a delete revoked access when it did not.

## Review (2026-05-30, session: review-doc312-314 — separate from /implement `958b470`)
- **Result**: REJECTED → `blocked`. **The caveat is actively misleading and is currently LIVE on `docs.opendatadiscovery.org`.** Priority class: "Incorrect documentation (actively misleading)" — the top of the Priority Order.

- **The defect.** The caveat claims: *"Removing a policy through the UI takes it off the Policies tab, but any role still bound to that policy keeps granting its permissions."* The code does the **opposite**: a policy bound to **any** role **cannot be deleted at all**. `PolicyServiceImpl.delete` (`:83-94`) calls `roleToPolicyRepository.isPolicyAttachedToRole(id)` and, if true, terminates the chain with `Mono.error(new CascadeDeleteException("Policy is attached to a role"))` — the soft-delete (`policyRepository.delete(id)`, the only caller) never runs. `isPolicyAttachedToRole` (`ReactiveRoleToPolicyRepositoryImpl.java:44-49`) returns true if **any** `ROLE_TO_POLICY` row references the policy. The single delete route is `PolicyController.deletePolicy:52-57` → `policyService.delete`; there is no bulk/alternate path. So the operator **cannot** "remove a bound policy from the Policies tab" — the UI rejects it with *"Policy is attached to a role."* The documented scenario is **unreachable** via the UI/API. VERIFIED via read of all five files @ ede5d277 (= odd-platform HEAD).

- **Why the implementer missed it.** The grant-path observation is *correct* — `getRolesPolicies` (`ReactivePolicyRepositoryImpl.java:32-35`) omits `deleted_at IS NULL` while the list/get path inherits it (`ReactiveAbstractSoftDeleteCRUDRepository.addSoftDeleteFilter` → `deletedAtField.isNull()`, `:96-103`; `listCondition`/`idCondition` `:77,87`). But the **operator-facing inference** ("delete via UI leaves bound roles granting") was never traced through the delete path's cascade guard. Classic Gate 4 incompleteness: the grant query was read; the delete consumer was not.

- **Internal contradiction (editorial).** ODD's own docs **two files over** already document this exact guard pattern correctly: `permissions.md:94` (`NAMESPACE_DELETE` — "the delete is **blocked** with `CascadeDeleteException` … when any … referent tables still references the namespace") and `permissions.md:98` (`OWNER_DELETE` — "gated on no remaining … relations … operators see a `CascadeDeleteException`"). Policy delete uses the identical mechanism; `policies.md:12` asserts the reverse. The correct prose was in the sibling file.

- **The genuine (narrow) residual.** A deleted-policy-still-granting state IS reachable, but only off the UI path: soft-delete an **unbound** policy (allowed), then re-attach its id to a role via role create/update — `createRelations` (`:25-41`) does **not** validate the policy is live, and `getRolesPolicies` omits the `deleted_at` filter. The UI role policy-picker is fed by the soft-delete-filtered list, so it never offers deleted policies; this requires a raw API call with a known-deleted policy id. That is **not** what the caveat describes, and is much lower severity.

### Required fix — choose one (content call; lean toward (A)):
**(A) Reject this caveat as a false-positive doc gap, and (optionally) replace it with the *true* useful note.** ODD already enforces detach-before-delete via the cascade guard; the normal flow has no silent stale grant. A genuinely useful, code-true note would mirror the sibling pattern, e.g.:

> **Deleting a policy is blocked while it is attached to a role.** ODD refuses to delete a policy that any role still references (you'll see *"Policy is attached to a role"*, a `CascadeDeleteException`). To delete a policy, first detach it from every role on the **Roles** tab; the delete then succeeds and the grant is gone. (This mirrors the namespace and owner cascade-delete guards — see [Permissions](permissions.md).)

**(B)** If the team wants to document the genuine residual, describe *that* path precisely (re-attaching a soft-deleted policy id via the API) — but it is esoteric and is better handled as the PLT-110 code hardening than as an operator caveat.

### PLT-110 must be re-scoped before filing (it is still `draft`):
Its "Why it matters" ("An operator who deletes a policy through the UI sees it vanish … It is not") is contradicted by the same cascade guard.
