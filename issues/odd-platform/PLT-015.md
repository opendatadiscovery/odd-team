## What

`SlackMessageGenerator` renders `AlertChunkPojo.description` (operator-supplied / ingestion-supplied text) verbatim into the Slack mrkdwn payload it POSTs to the operator's Slack webhook. Slack's mrkdwn syntax interprets the following tokens as control sequences:

- `<!channel>` and `@channel` -> broadcast notification to every member of the receiving Slack channel
- `<https://attacker.example|click here>` -> renders as "click here" hyperlink, target URL hidden from casual readers
- `<!here>` -> broadcast notification to online members
- `<!subteam^SUBTEAM_ID>` -> broadcast notification to a Slack subteam

Combined with **PLT-014 Defect 1** (AlertManager webhook is unauthenticated and accepts unvalidated `entity_oddrn`), a remote caller can POST a forged AlertManager payload whose alert description contains `<!channel>` or fake-link markup; the platform writes the alert; the notification fan-out POSTs it to every configured Slack channel; Slack broadcasts `@channel` to every member or displays a fake-link to attacker-controlled destinations.

## Why it matters

The compound surface (unauthenticated webhook -> forged alert description -> Slack mrkdwn -> workspace-wide broadcast) is the operator-visible failure pattern. The maximum-impact scenario: an attacker discovers an exposed `/ingestion/alert/alertmanager` endpoint (no auth, default deployment pattern); POSTs a few crafted payloads per minute with `entity_oddrn` pointing at a high-visibility data entity AND `description: "<!channel> URGENT incident - click <https://attacker.example|here> to acknowledge"`; the platform persists the forged alerts; the notification subsystem fans them out to every Slack channel that subscribes to the entity; every Slack member sees `@channel` + a fake link in their workspace.

Severity is HIGH because:
- The compound is **fully remote, fully unauthenticated** under any default deployment
- `@channel` broadcasts are noisy, social-engineering-effective, and difficult to take back
- Fake links bypass the user's trust model (the link came from "the platform's Slack integration")
- The fix is a **one-line sanitization helper** - extremely low risk-of-regression for a high-impact gain

## Suggested fix

Add a `MrkdwnUtils.escape(...)` helper and apply it at every description embedding site:

```java
// new file: odd-platform-api/.../notification/sender/slack/MrkdwnUtils.java
public final class MrkdwnUtils {
    private MrkdwnUtils() {}

    private static final Map<String, String> ESCAPES = Map.of(
        "<",  "&lt;",
        ">",  "&gt;",
        "&",  "&amp;"
    );

    /**
     * Escape Slack mrkdwn control characters in user-supplied text.
     * Slack's mrkdwn treats <text> and &channel-style sequences as control tokens;
     * escaping &lt;/&gt;/&amp; neutralises @channel broadcast, fake-link injection,
     * and subteam-ping injection.
     */
    public static String escape(String text) {
        if (text == null) return null;
        String result = text;
        for (Map.Entry<String, String> e : ESCAPES.entrySet()) {
            result = result.replace(e.getKey(), e.getValue());
        }
        return result;
    }
}
```

Then at every description embedding site in `SlackMessageGenerator`:

```java
// SlackMessageGenerator.java:77 (and the two sibling sites at 95-101)
- text(description)
+ text(MrkdwnUtils.escape(description))
```

The helper handles the three operator-visible attack tokens. Apply to **every** field that originates from untrusted ingest (`AlertChunkPojo.description`, `AlertChunkPojo.url`, `dataEntity.externalName` if surfaced).

Add a unit test:

```java
@Test
void escapeNeutralizesBroadcastTokens() {
    assertThat(MrkdwnUtils.escape("<!channel> urgent")).isEqualTo("&lt;!channel&gt; urgent");
    assertThat(MrkdwnUtils.escape("<https://x|y>")).isEqualTo("&lt;https://x|y&gt;");
}
```
