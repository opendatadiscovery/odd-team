## What

Four related session-posture defects ship with the platform default:

**Defect 1 - `spring.session.timeout: -1` default (F-087a) [re-scoped 2026-06-10].** `application.yml:2-3` ships `spring.session.timeout: -1` (confirmed). The originally-claimed effect ("sessions never expire; `spring_session` table grows monotonically") is NOT settled by static trace and needs a runtime drive: (a) it is provider-conditional - the shipped default provider is `IN_MEMORY` (`application.yml:30`), under which there is NO `spring_session` table and NO housekeeping job at all (the job bean is `@ConditionalOnProperty INTERNAL_POSTGRESQL`, `SessionConfiguration.java:37-43`), so "table grows" applies only to operators who switch to `INTERNAL_POSTGRESQL`; (b) even then, the custom repositories are constructed with no max-inactive-interval setter and `JooqSessionRepository.createSession()` returns a default `new MapSession()` (30-min default interval), so it is unclear `-1` reaches the stored `expiry_time` at all; (c) `PostgreSQLSessionHousekeepingJob.runHousekeeping()` reaps rows where `EXPIRY_TIME < now()` (`:27-30`, then deletes via `:40-46`) - if `-1` produced a negative interval, `expiry_time = lastAccess + (-1)` lands in the PAST, which would make the job delete *immediately* rather than never (the opposite of the draft's claim). The net effect must be observed on a running `INTERNAL_POSTGRESQL` stack, not asserted. **LSN-001 shape only IF the never-expire mechanism is confirmed at runtime.**

**Defect 2 - Session cookie `Secure` not forced (F-087b) [re-scoped 2026-06-10].** `SessionConfiguration.java` defines no custom `CookieWebSessionIdResolver` bean (confirmed - grep `CookieWebSession|SameSite|HttpOnly|Secure` over `src/main` returns zero hits), so the SESSION cookie is written by Spring WebFlux's default resolver. On the shipped Spring Framework 6.2.x (`spring-webflux 6.2.11`, `gradle/libs.versions.toml:49`) that default already sets `HttpOnly=true` and `SameSite=Lax`; the genuine gap is that `Secure` is NOT forced (it is request-derived, so a deployment terminating TLS at a proxy and speaking plain HTTP to the platform emits a non-`Secure` session cookie). The original "Secure / SameSite / HttpOnly all absent" framing overstates it - only `Secure` is the load-bearing gap. The exact emitted flags must be read from the live `Set-Cookie` header (runtime).

**Defect 3 - IN_MEMORY default breaks multi-replica (F-087c).** `application.yml:28-30` ships `session.provider: IN_MEMORY` as the default (the IN_MEMORY repository bean is `SessionConfiguration.java:45-49`; the INTERNAL_POSTGRESQL bean is `:28-35`). Multi-replica deployments behind a non-sticky LB get per-process sessions; the collector bridge `POST /ingestion/datasources` (`IngestionController.createDataSource`) reads the collector id from the WebSession (`IngestionController.java:49-57`) and throws `IllegalStateException("Collector id is null")` at `:54` when the second hop lands on a replica that never saw the registration. That maps to HTTP 500 via `ControllerAdvice.java:61-66` (`@ExceptionHandler(Exception.class)` + `INTERNAL_SERVER_ERROR`). NOTE: the literal `"Collector id is null"` is server-side LOG only; the HTTP client receives a generic `{ "message": "Internal Server Error", code: SERVER_EXCEPTION }` body (`ControllerAdvice.java:63-66`).

**Defect 4 - Java-serialised session attributes (F-087d).** `JooqSessionRepository.java:156` (`SerializationUtils.serialize`) and `:188` (`SerializationUtils.deserialize`) use Java native serialisation for session attribute bytes (confirmed). Java native deserialisation has known deserialisation-gadget surface; a DB-write compromise yields an RCE-class attack on attribute-load. (Security property; not a UI/consumer-visible symptom.)

## User-facing impact

This is a back-end / operator-facing hardening epic; there are no UI rendering claims. The "users" are the operator (deployment posture) and the collector / API consumer (HTTP behaviour). Every observable below is topology- or runtime-dependent, so `user_facing_verified` stays `false`.

- **Defect 3 (multi-replica collector bridge), API consumer:** a collector that registers (sets the session) and then `POST`s `/ingestion/datasources` on a second request will, on a multi-replica non-sticky deployment, hit a replica without the session attribute and receive **HTTP 500** with body `{ "message": "Internal Server Error" }` (BE trace verified 2026-06-10: throw at `IngestionController.java:54` -> `ControllerAdvice.java:61-66`). The diagnostic string `"Collector id is null"` is in the server log, not the response (verified by BE trace 2026-06-10). The multi-replica/non-sticky condition itself is *static trace consistent; not driven* - requires a >=2-replica stack behind a round-robin LB to observe.
- **Defect 2 (cookie posture), browser user:** the SESSION cookie's `Secure` attribute is not forced, so under TLS-terminating-proxy + plain-HTTP-to-platform topologies the cookie can be emitted without `Secure` (BE trace: no custom resolver bean). HttpOnly / SameSite=Lax are framework defaults on Spring 6.2.x and are likely present. *Static trace consistent; not driven* - the exact flags must be read from the live `Set-Cookie` header.
- **Defect 1 (session lifetime), operator:** under the shipped `IN_MEMORY` default there is no session table to grow; the data-growth scenario applies only after an operator selects `INTERNAL_POSTGRESQL`, and even then the never-expire mechanism is unverified (see Defect 1). *Needs a runtime drive on an `INTERNAL_POSTGRESQL` stack* - do not assert table growth.
- **Defect 4 (deserialization), attacker model:** no consumer-visible symptom; a security property that manifests only given DB-write compromise.

## Why it matters

LSN-001 family in spirit: several defects are insecure-or-surprising defaults that doc-only warnings miss. The load-bearing, code-confirmed pieces are Defect 4 (Java-native deserialisation of session attributes) and Defect 3 (multi-replica 500 under the IN_MEMORY default). Defect 2 narrows to `Secure` not being forced; Defect 1 narrows to a runtime-verification task on the non-default INTERNAL_POSTGRESQL provider. Severity stays HIGH on the strength of Defects 3 + 4.

## Suggested fix

**Thread A - Sensible session-timeout default.**

```yaml
# application.yml
spring:
  session:
    timeout: 30m   # sensible interactive UI default; operator-overridable
```

Add `@PostConstruct` warning if the value is unset or negative.

**Thread B - Default cookie posture.**

```java
@Bean
public WebSessionIdResolver webSessionIdResolver() {
    CookieWebSessionIdResolver resolver = new CookieWebSessionIdResolver();
    resolver.addCookieInitializer(cookie -> cookie
        .secure(true)
        .httpOnly(true)
        .sameSite("Strict"));
    return resolver;
}
```

For deployments terminating TLS at a proxy without HTTPS to the platform process, expose an opt-out: `odd.session.cookie.secure: false`. Default to safe-mode.

**Thread C - Multi-replica IN_MEMORY warning.**

```java
@PostConstruct
void warnMultiReplicaInMemory() {
    String provider = environment.getProperty("session.provider", "IN_MEMORY");
    if ("IN_MEMORY".equalsIgnoreCase(provider)) {
        log.warn("session.provider=IN_MEMORY is per-process. Multi-replica deployments behind non-sticky load-balancers will see session-bridge failures (HTTP 500 'Collector id is null' on /ingestion/datasources). Switch to INTERNAL_POSTGRESQL or EXTERNAL_REDIS / EXTERNAL_POSTGRESQL for multi-replica deployments.");
    }
}
```

Alternative: fail-fast if a `kubernetes.io/cluster-name` env var is present + IN_MEMORY is configured. Less invasive: log only.

**Thread D - JSON session-attribute serialisation.**

Migrate from `SerializationUtils.serialize/.deserialize` to a Jackson-based JSON serializer. Schema-migration: new column `attribute_bytes_json BYTEA` parallel to existing `attribute_bytes`; reader reads both with version flag; writer writes JSON; cleanup step deletes Java-serialised column after the cluster runs the migration through.

Larger thread - gated on a coordinated release. Until it ships, Thread B + C + the doc-side mitigation (DOC-241) carry the load.
