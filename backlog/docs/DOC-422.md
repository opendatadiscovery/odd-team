## Description

`metrics-ingestion.md` line 7 states: "The platform supports the [OpenMetrics](https://openmetrics.io/) metric model — five metric types (`COUNTER`, `GAUGE`, `HISTOGRAM`, `SUMMARY`, `GAUGE_HISTOGRAM`) …". Two issues:

1. **The list is ODD's own enum, not "the OpenMetrics metric model."** These five values are exactly ODD's `MetricType` enum, defined in the platform's own ingestion contract (`odd-platform-specification/components.yaml`). The doc presents them as if ODD adopts the OpenMetrics model wholesale, when in fact ODD defines its own closed five-value enum and the ingestion mappers switch on those five values directly.
2. **It is a subset, not the model.** OpenMetrics defines **eight** metric types — `unknown`, `gauge`, `counter`, `stateset`, `info`, `histogram`, `gaugehistogram`, `summary` (per the OpenMetrics 1.0 spec). ODD supports five of them; it omits `info`, `stateset`, and `unknown`. Calling the five-value set "the OpenMetrics metric model" and linking openmetrics.io implies full conformance and that any OpenMetrics type is accepted — an operator pushing an `Info` or `StateSet` family from an OpenMetrics-conformant producer would reasonably expect it to ingest, and it will not (the type is not in ODD's enum).

(Note: the 2026-06-08 harvest line that prompted this item asserted "`GAUGE_HISTOGRAM` is not an OpenMetrics type." That specific justification is **incorrect** — `gaugehistogram` *is* a valid OpenMetrics 1.0 type. The real defect is the subset-vs-whole and own-enum-vs-external-spec attribution above, not that any single one of the five values is foreign to OpenMetrics. Verified against the OpenMetrics 1.0 spec, see Sources.)

The fix is a precise attribution: describe the type set as **ODD's own metric model (OpenMetrics-inspired)** drawn from the platform's ingestion contract, optionally noting it is a subset of OpenMetrics' types. Keep the openmetrics.io link only as an "inspired by / see also," not as the authority for what ODD accepts.
