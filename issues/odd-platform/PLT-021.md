## What

Two distinct defects on the DQ Test Run History endpoint surfaced by the same UI page (`history` route - `TestRunsHistory.tsx`). The page is the operator's primary surface for diagnosing data-quality test outcomes.

**Defect 1 - HTTP 500 during in-flight test runs (wire-vs-DB enum asymmetry). HOLDS - driven on the running stack.** The DB-side test-run status enum `IngestionTaskRun.IngestionTaskRunStatus` (`IngestionTaskRun.java:28-36`) has **7 values**: `SUCCESS, FAILED, SKIPPED, BROKEN, ABORTED, RUNNING, UNKNOWN`. The wire-side enum `DataEntityRunStatus` (`components.yaml:1407-1415`) has **6 values**: `SUCCESS, FAILED, SKIPPED, BROKEN, ABORTED, UNKNOWN` - **`RUNNING` is the lone value present in the DB enum but absent from the wire enum** (both share `UNKNOWN`; neither has `SCHEDULED` - corrected from an earlier revision that listed `SCHEDULED` in both). The generated MapStruct mapper does `DataEntityRunStatus.valueOf(...)` with no fallback (`DataEntityRunMapperImpl.java:42` - the source annotation is `DataEntityRunMapper.java:13-14`). A result set containing a `RUNNING` row therefore throws `IllegalArgumentException` -> HTTP 500. DRIVEN 2026-06-07 (`integration-tests/protocols/IT-059-dq-run-history.md`, run-log `2026-06-07-IT-059.md`): inserting one `data_entity_task_run` with `status='RUNNING'` makes `GET /api/dataentities/{id}/runs` return 500; `status=RUNNING`/`status=BANANA` filters also 500 at param-binding.

**Defect 2 - NULL end_time ordering puts RUNNING rows at top of list.** The repository sorts by `END_TIME DESC` with no `NULLS LAST` (`ReactiveDataEntityTaskRunRepositoryImpl.java:177-181` passes `DATA_ENTITY_TASK_RUN.END_TIME` + `SortOrder.DESC` to `jooqQueryHelper.paginate`, which builds the sort via `getOrderFields` -> `field.sort(order)` with no null-ordering, `JooqQueryHelper.java:158`). Postgres default for `DESC` is `NULLS FIRST`, so RUNNING rows (`end_time IS NULL`) sort to the TOP. (Corrected: an earlier revision cited a literal `.orderBy(...END_TIME.desc())` at `:178`; the ordering actually flows through `paginate()`.)

(Defect 2 is masked by Defect 1 today - while a RUNNING row is in the set the request 500s before any ordering is observable. It becomes user-visible only after Defect 1 is fixed and `RUNNING` is mappable.)

## User-facing impact

- WHO: an operator diagnosing a data-quality test (sees a DQ alert, clicks through to the test's run history `history` tab).
- Defect 1 - WHAT they observably get: when the test has an in-flight (`RUNNING`) run - exactly the common "I just retried the failed test" case - **the runs list never loads: the endpoint 500s** (driven, IT-059) and the FE shows an error toast + an empty list, not the runs. Verified by FE trace 2026-06-10: `fetchDataEntityRuns` routes through `handleResponseAsyncThunk`, whose `catch` calls `showServerErrorToast` and `rejectWithValue` (`handleResponseThunk.ts:34-40`; `errorHandling.tsx:48-67` -> toast "Internal Server Error"); `TestRunsHistory.tsx` then renders the header + status filter but `dataQATestRunsList` stays empty -> `EmptyContentPlaceholder` (`:116-118`). So it is not a white-screen crash; it is "header + filter render, runs area empty, red error toast" - the diagnostic content is unavailable while the test runs.
- Defect 2 - WHAT they would get after Defect 1 is fixed: in-flight rows (null end_time) sorted to the TOP of the list. The row shows its `startTime` and a status badge (`TestRunItem.tsx:26-33`, `TestRunStatusItem` renders `typeName.toLowerCase()`), with a blank Duration column (`formatDistanceStrict` only runs when both endTime && startTime, `TestRunItem.tsx:52-58`). Static trace consistent; not driven (masked by Defect 1 today) - remaining check: after adding RUNNING to the wire enum, load the page with a RUNNING row and confirm position + blank duration. (Corrected: the row is NOT "undated" - `startTime` renders; the status badge does signal the state once RUNNING is mappable.)

## Why it matters

The DQ Test Run History page is the operator's diagnostic surface for *"why did my DQ test fail / when did it last succeed / is it currently running."* The failure pattern:

- An operator sees a DQ alert; clicks through to the test's history page
- If the test is currently re-running (a common operator action), the runs list 500s and never populates (driven)
- Operator falls back to direct PostgreSQL query, breaking the abstraction the platform's UI is meant to provide

Severity stays HIGH on Defect 1 (driven):
- Defect 1 makes the runs list **unavailable during normal operational use** (in-flight test); the recovery is manual-refresh-after-the-run-completes, not graceful degradation
- Defect 2 (post-fix) is a lesser UX surprise, not a failure

## Suggested fix

### Defect 1 - three options, all reasonable

**Option A (recommended) - add `RUNNING` to the wire enum:**

```yaml
# components.yaml:1407-1415
DataEntityRunStatus:
  type: string
  enum:
    - SCHEDULED
    - RUNNING       # <-- add
    - BROKEN
    - ABORTED
    - SUCCESS
    - FAILED
    - SKIPPED
```

Wire-side now matches DB-side; mapper succeeds; UI receives `RUNNING` and renders it appropriately (the UI already labels in-flight runs in the per-test report view, so the rendering pattern exists). Recommend this - surfaces the operator-visible reality.

**Option B - MapStruct `@ValueMapping` fallback:**

```java
@ValueMapping(source = "RUNNING", target = "BROKEN")
// or:
@ValueMapping(source = MappingConstants.ANY_UNMAPPED, target = "BROKEN")
```

Hides the in-flight reality from the wire / UI. Lossy. Not recommended.

**Option C - service-side filter excluding RUNNING:**

```java
// in DataEntityRunService
return repository.findByDataEntityId(id)
    .filter(run -> run.getStatus() != RUNNING)
    .collectList();
```

Also lossy; operator can't see in-flight runs at all. Not recommended.

### Defect 2 - one option:

```java
// ReactiveDataEntityTaskRunRepositoryImpl.java:178
- .orderBy(DATA_ENTITY_TASK_RUN.END_TIME.desc())
+ .orderBy(DATA_ENTITY_TASK_RUN.END_TIME.desc().nullsLast(),
+          DATA_ENTITY_TASK_RUN.START_TIME.desc())   // tiebreak with start_time for RUNNING rows
```

RUNNING rows now sort by start_time among themselves (newest in-flight first) and follow the completed rows. Operator-visible: in-flight rows are clearly grouped at the END of the list (or as a distinct visual section if the UI is updated).

Better UX (separate PR if desired): UI surface an in-flight section above the completed list.
