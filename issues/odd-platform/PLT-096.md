## What

Three defects on the entity detail page's Overview sidebar list truncation (Tags / Terms / Groups columns) — one real semantic bug where slice-then-sort silently defeats the importance-aware comparator, one undefined-behaviour cleanup where a bare `.sort()` on a struct array is a no-op, and one truncation-affordance gap where `View All (N)` only reveals the full count after click.

**Defect 1 — slice-then-sort defeats importance ordering on Tags (F-179a — MEDIUM semantic bug).** `OverviewTags.tsx:54-65`: `tags.slice(0, visibleLimit).sort(tagsCompare).map(...)`. **`.slice` runs FIRST; `.sort` only orders the truncated window.** The `tagsCompare` comparator at lines 26-32 promises "important tags first, then alphabetical" but only WITHIN the visible window. An entity with 25 tags where important ones sit at indices 22-24 renders the top-20 in array order with NO important tag visible.

**Defect 2 — Bare `.sort()` no-op on OverviewGroups (F-179b — LOW cleanup).** `OverviewGroups.tsx:49-54`: `dataEntityGroups.slice(0, visibleLimit).sort().map(...)`. Bare `.sort()` on `DataEntityRef[]` → JavaScript's default comparator stringifies via `toString()` → all elements compare equal → the sort is a silent no-op. Misleading to readers who infer "sort happens here."

**Defect 3 — `View All (N)` count only visible after click (F-179c — LOW UX).** `OverviewTags.tsx:85`: `text={viewAll ? t('Hide') : \`${t('View All')} (${tags?.length})\`}`. The `(25)` suffix is the ONLY signal there are MORE than 20 tags. If the operator does not notice the parenthetical count (small text, end of label), they conclude the entity has 20 tags. Sibling shape at `OverviewGroups.tsx:71-73`.

## Why it matters

- **Defect 1 is the real semantic bug** — the importance-aware comparator is product-level user intent ("important tags rise to the top"); slice-then-sort silently disregards that intent for any entity with >20 tags. Operators tagging 30+ entities in a domain see "important" tags get hidden behind the 20-row cap; the affordance the platform promises is broken.
- **Defect 2 is misleading code** — the `.sort()` call signals to a reader that ordering happens; in fact nothing happens. A future maintainer touching `OverviewGroups.tsx` may assume the sort is meaningful and refactor incorrectly.
- **Defect 3 is a polish defect** — the `(25)` count after the View All label is too subtle. Operators reading the page rapidly skip it. The fix is one inline `Showing 20 of 25` row above the list.

Severity MEDIUM driven by Defect 1; Defects 2 + 3 are cleanup / polish.

## Suggested fix

### (a) Defect 1 — Sort BEFORE slice

```tsx
// OverviewTags.tsx:54-65
[...tags].sort(tagsCompare).slice(0, visibleLimit).map(tag => (
  <TagItem key={tag.id} tag={tag} />
))
```

The spread is necessary because `.sort` mutates; we need to leave the source array untouched.

Apply the same fix shape to `OverviewTerms.tsx` if it carries a similar slice-then-sort (verify and patch if so).

### (b) Defect 2 — Remove the no-op OR supply a comparator

Two paths:

**(b1) Remove the bare `.sort()`** if the underlying repository already returns groups in a meaningful order (verify the wire payload):

```tsx
// OverviewGroups.tsx:49-54
dataEntityGroups.slice(0, visibleLimit).map(group => (
  <GroupItem key={group.id} group={group} />
))
```

**(b2) Supply a comparator** (e.g., by group name) if there is no upstream ordering guarantee:

```tsx
const groupsCompare = (a: DataEntityRef, b: DataEntityRef) =>
  (a.internalName ?? a.externalName).localeCompare(b.internalName ?? b.externalName);

[...dataEntityGroups].sort(groupsCompare).slice(0, visibleLimit).map(...)
```

(Prefer (b2) for consistency with the OverviewTags fix shape.)

### (c) Defect 3 — Inline "Showing 20 of 25" affordance

```tsx
// OverviewTags.tsx — above the list:
{!viewAll && tags && tags.length > visibleLimit && (
  <S.TruncationHint variant="caption" color="text.secondary">
    {t('Showing {{visible}} of {{total}}', { visible: visibleLimit, total: tags.length })}
  </S.TruncationHint>
)}
```

The `View All (N)` button can keep the count suffix for redundancy; the inline hint is the visible signal.
