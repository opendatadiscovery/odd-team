## What

Two defects on the per-entity Discussions tab — one acknowledged in the live docs (F-197a) but not fixed, one undocumented (F-197b).

**Defect 1 — Discussions tab visible when feature disabled (F-197a).** The live data-collaboration doc explicitly states: "The Discussions tab is visible even when Data Collaboration is disabled. The tab itself is currently rendered regardless of the flag (only hidden when the entity status is deleted)." The doc acknowledges the bug ("currently rendered regardless of the flag") which is honest but operator-confusing — clicking Discussions on a disabled deployment shows an empty UI. The doc's framing as "currently" suggests known-but-unfixed.

**Defect 2 — Thread.tsx silently navigates away on relatedMessagesError (F-197b).** `Thread.tsx:31-34` — on `relatedMessagesError`, navigates to the parent discussions list URL with NO error toast / NO inline banner. The operator's "open a thread" click silently rewrites the URL. The operator can't tell whether (a) they clicked something wrong, (b) the thread was deleted, or (c) the platform is partially down.

## Why it matters

Defect 1 is a UI/feature-flag misalignment: the backend returns 404 on `/api/datacollaboration/*` when disabled, but the UI shows the tab anyway, then renders an empty UI on click. The doc-side acknowledgement ("currently rendered regardless of the flag") is operator-honest but is fixing a structural code defect with doc copy. The fix is in the UI's feature-flag consultation.

Defect 2 is small but representative of a broader UX pattern in the data-collaboration surface: errors silently degrade rather than surfacing diagnostic context. Operators don't know whether they did something wrong or the platform is failing.

Severity is LOW for the pair because:
- Defect 1 is honest-in-doc; operators on a disabled deployment learn to ignore the tab quickly.
- Defect 2 is a thread-load failure mode that's rare (the thread message-fetch error path only fires on backend transient errors or a deleted thread the user has stale state for).

## Suggested fix

**Defect 1 — feature-flag check in the UI:**

```tsx
// DataEntityDetailsTabs.tsx
// the platform already exposes /api/datacollaboration/health or similar feature-flag-detection endpoint?
// if not, the simplest add is a `/api/app-info` -> { features: { dataCollaboration: true|false } }
// the UI tab definitions check this:
const dataCollaboration = useAppInfo().features.dataCollaboration;
{ label: t('Discussions'), path: 'discussions', hidden: !dataCollaboration || isStatusDeleted }
```

Once shipped, the doc-side acknowledgement in `data-collaboration.md` updates to remove the "currently" framing.

**Defect 2 — Thread.tsx error context:**

```tsx
// Thread.tsx:31-34 (current)
- useEffect(() => {
-   if (relatedMessagesError) {
-     navigate(`/dataentities/${dataEntityId}/discussions`);
-   }
- }, [relatedMessagesError, dataEntityId, navigate]);

// proposed:
+ useEffect(() => {
+   if (relatedMessagesError) {
+     showErrorToast(t('Failed to load thread — returning to discussions list'));
+     navigate(`/dataentities/${dataEntityId}/discussions`);
+   }
+ }, [relatedMessagesError, dataEntityId, navigate, t]);
```

Or — show an inline error banner in place of the silent navigation; let the operator choose to go back or retry.
