## What

Two related concurrency defects in `PolicyServiceImpl`, both stemming from missing transaction boundaries:

1. **Lost update on `update`.** Updating a policy is a read-then-write sequence (`get(id)` -> validate/apply -> `update`) with **no transaction** around it. Two concurrent edits to the same policy both read the old row and both write, so the second writer silently clobbers the first writer's change - a classic lost update. The same service's `RoleServiceImpl.update` **is** `@ReactiveTransactional`; policy was left unprotected.

2. **TOCTOU in the cascade-delete defence.** `delete` guards against orphaning by checking "is this policy attached to a role?" and then deleting only if not - but the check and the delete are **two separate, non-transactional** R2DBC round-trips. A role can be bound to the policy in the window between the check and the delete, so the delete proceeds and the policy is removed (soft-deleted) while a role still references it - defeating the very `CascadeDeleteException` guard that exists to prevent it.

Authorization policies are the platform's access-control rules, so both defects sit on a security-relevant surface.

## Where

`service/PolicyServiceImpl.java`. Note the class has **no** `ReactiveTransactional` import and **no** transaction annotation on either method.

Lost-update - `update` is read-then-write with nothing holding the two together:

```java
// PolicyServiceImpl.java:72 - NOT @ReactiveTransactional (contrast RoleServiceImpl below)
@Override
public Mono<PolicyDetails> update(final long id, final PolicyFormData formData) {
    policyJSONValidator.validate(formData.getPolicy());
    return policyRepository.get(id)                       // READ
        .switchIfEmpty(Mono.error(new NotFoundException("Policy with id %d hasn't been found".formatted(id))))
        .filter(policy -> !policy.getName().equals(ADMINISTRATOR_POLICY))
        .switchIfEmpty(Mono.error(new BadUserRequestException("Administrator policy cannot be updated")))
        .map(pojo -> policyMapper.applyToPojo(formData, pojo))
        .flatMap(policyRepository::update)                // WRITE - gap between READ and WRITE is unguarded
        .map(policyMapper::mapToDetails);
}
```

TOCTOU - the attach-check and the delete are two separate non-transactional calls:

```java
// PolicyServiceImpl.java:84 - delete: check-then-delete with no shared transaction
@Override
public Mono<Policy> delete(final long id) {
    return policyRepository.get(id)
        .switchIfEmpty(...).filter(...).switchIfEmpty(...)
        .then(roleToPolicyRepository.isPolicyAttachedToRole(id))   // line 89: TIME-OF-CHECK
        .filter(Boolean::booleanValue)
        .flatMap(isAttached -> Mono.error(
            new CascadeDeleteException("Policy is attached to a role")))
        .then(policyRepository.delete(id))                         // line 93: TIME-OF-USE - race window between 89 and 93
        .map(policyMapper::mapToPolicy);
}
```

The intended contract is already met by the sibling service:

```java
// service/RoleServiceImpl.java:64 / :77 - Role DOES wrap update and delete in a transaction
@ReactiveTransactional
public Mono<Role> update(final long id, final RoleFormData formData) { ... }

@ReactiveTransactional
public Mono<Void> delete(final long id) { ... }
```

(`RoleServiceImpl` imports `org.opendatadiscovery.oddplatform.annotation.ReactiveTransactional`; `PolicyServiceImpl` does not.)

Verified against current HEAD `3049b9af`: `PolicyServiceImpl` has no `ReactiveTransactional` import and no annotation on `update` (`:72`) or `delete` (`:84`); `RoleServiceImpl.update` (`:65`) and `RoleServiceImpl.delete` (`:78`) are both `@ReactiveTransactional` (`:64`, `:77`). The Role-vs-Policy asymmetry is exactly as described.

## User-facing impact

Authorization policies are the platform's access-control rules, edited by admins via the Management UI (`PUT`/`DELETE /api/policies/{id}`), so both defects sit on a security-relevant surface - but both are **concurrency-only** and intermittent, so neither reproduces in normal single-actor UI use:

- **Lost update (`update`):** two admins (or an admin + a programmatic client) editing the same policy concurrently can have one edit silently overwritten - the loser gets a `200` and no error, but their change is gone. On an access-control object this means the effective permission boundary is not what the operator who "saved last and saw success" believes it is. No visible error to either party; only an audit/diff of the policy body would reveal it.
- **Cascade-delete TOCTOU (`delete`):** the `CascadeDeleteException` guard ("Policy is attached to a role") can be bypassed if a role is bound to the policy in the window between the attach-check (`:89`) and the delete (`:93`), leaving a role pointing at a soft-deleted policy. The blast radius is access-control integrity.

Both need concurrent operations on the same policy to manifest, which is why they survive casual/manual testing; on a small single-admin deployment the practical exposure is low, rising with multiple admins or automation. Severity medium (held).

## Why it matters

Neither is classic bulk data-loss; both are **silent corruption of authorization state** under concurrency, which is why they survive casual testing and warrant a code fix rather than a doc caveat. The intended contract already exists one class over (`RoleServiceImpl`), so leaving `PolicyServiceImpl` unprotected is an unambiguous, low-cost-to-close inconsistency on a security surface. (Per-defect user impact is detailed under User-facing impact above.)

## Suggested fix

A single, consistent fix closes both: bring `PolicyServiceImpl` in line with `RoleServiceImpl` by adding the transaction boundary.

1. Import `org.opendatadiscovery.oddplatform.annotation.ReactiveTransactional`.
2. Annotate `update(...)` with `@ReactiveTransactional` so the `get` -> `update` read-modify-write executes in one transaction (lost-update protection).
3. Annotate `delete(...)` with `@ReactiveTransactional` so `isPolicyAttachedToRole(id)` and `delete(id)` execute atomically, closing the check-then-delete window.

This mirrors the established `RoleServiceImpl` pattern exactly, so it is the lowest-risk, most consistent change. (If `@ReactiveTransactional` alone does not give a strong enough isolation guarantee against the lost update under the deployment's DB isolation level, a row-level guard - `SELECT ... FOR UPDATE` on the policy in the same transaction - is the fallback; open to that alternative.)

## How discovered

Surfaced during the 2026-06-08 contradiction-harvest (feature-reflection triage), from the F-006 reflection's product-owner read of the policy lifecycle. The intra-codebase inconsistency - Role's update/delete are transactional, Policy's are not, on the same kind of access-control object - is the contradiction the reflection pass flags; no single sidecar sees the Role-vs-Policy asymmetry in isolation.

**Verified 2026-06-10 (user-facing verification sweep) - verdict HOLDS.** Read both services at current HEAD `3049b9af`: `PolicyServiceImpl` has no `ReactiveTransactional` import and no annotation on `update`/`delete`; the read-then-write in `update` (`:74-80`) and the check-then-delete in `delete` (`:85-94`) are exactly as described; `RoleServiceImpl.update`/`delete` are both `@ReactiveTransactional`. All cited line numbers confirmed.

**Distinct from PLT-087.** PLT-087 concerns the DataSource tier, not `PolicyServiceImpl`. This (PLT-170) is the policy update/cascade-delete transactionality in the service layer; tracked separately so the `@ReactiveTransactional` fix lands on the right class.
