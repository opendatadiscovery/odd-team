- **ADR-CANDIDATE-021** (NEW 2026-05-10A): Activity streams use cursor pagination via `(lastEventId, lastEventDateTime)` — append-only audit data; no offset/limit support; the same shape is reused across `getActivity` and `getDataEntityActivity`
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar (`getActivity`) but the convention is observed across multiple endpoints per `concepts.yaml:108`
  - **Surfaced by**:
    - `odd-platform__java__ActivityController__controller-method__getActivity.md:implicit_adrs.[0]` ("Activity stream uses cursor pagination (`lastEventId` + `lastEventDateTime`) rather than offset/limit — appropriate for append-only audit data and avoids deep-offset performance cliffs." — intent_anchor: "The parameter pair appears as `lastEventId` + `lastEventDateTime` — the same cursor shape is reused at `getDataEntityActivity` (DataEntityController.java:351-365 per concepts.yaml:108), establishing 'cursor pagination for activity streams' as a cross-controller convention.")
  - **Decision statement**: Audit-trail / activity-stream endpoints use cursor pagination via the parameter pair `(lastEventId, lastEventDateTime)` rather than offset+limit (the latter is used elsewhere in the platform — e.g. `AlertController.getAllAlerts` uses `page+size` per ADR-CANDIDATE-002 and REFACTOR-024 / REFACTOR-020). The decision is appropriate for append-only audit data: cursor pagination scales linearly with page count for the requesting client, while offset pagination would degrade quadratically for deep pages. The convention is reused at `getActivity` (ActivityController.java:34-35) AND `getDataEntityActivity` (DataEntityController.java:351-365), establishing it as a cross-controller pattern for activity streams (NOT a global pagination convention — list endpoints like `getAllAlerts`, `getDataEntityList` continue to use offset+limit).
  - **Wisdom test**: PASS. Deliberate (cursor over offset for append-only data is a positive design choice, consistent across two endpoints); structural (every activity-stream endpoint follows the shape; future activity-stream additions should reuse it). The differentiation from offset+limit elsewhere in the platform is itself a structural signal — pagination shape follows data semantics.
  - **Evidence**:
    - getActivity.md says: "ActivityController.java:34-35 (the two cursor parameters as a pair) + ActivityServiceImpl.java:179-180 (`findAllActivities(... lastEventId, lastEventDateTime)`) + lineage/odd-platform/concepts.yaml:108 (the same pattern is observed and labelled across the codebase)"
  - **Existing ADR**: none.
  - **Co-surfaced gaps** (link from `refactoring-scopes.md`): REFACTOR-053 (typo `lasEventId` on the public API contract — the convention's intent is preserved at the service interface but the controller variable name leaked the typo to the OpenAPI-generated client), REFACTOR-056 (composite-cursor SQL predicate index requirements not documented — out-of-scope-for-controller but architecturally relevant).
  - **Proposed action**: Promote to `adrs/drafts/cursor-pagination-for-activity-streams.md` (new ADR). Document the rule: append-only audit data uses cursor pagination; aggregate / mutable listings use offset+limit. Future audit-stream features (e.g. an "Alert change history" feed) should reuse the cursor parameters; future aggregate listings should reuse offset+limit. The `lasEventId` typo is the canonical regression case the ADR's "name parameters consistently" guidance prevents.
  - **Severity rationale**: MEDIUM — pagination-architecture pattern; affects every future activity-stream / audit-feed endpoint.
