## What

Deleting a data source that still has data entities attached is correctly refused by the backend (HTTP 400 cascade-block), but the UI reports nothing: the confirmation modal closes exactly as it does on success, no error toast appears, and the data source simply remains in the list. The operator's only clue that the delete failed is noticing the row is still there. There is also no pre-flight indication (no disabled-with-tooltip Delete, no in-dialog forewarning) that the delete of an entity-bearing source will be refused.

An earlier revision of this issue claimed the opposite failure shape - a stuck-open modal with a frozen spinner and a "raw-jargon toast". Both details are false for this screen (see "How discovered"); the verified behaviour is a *silent no-op that looks like a success*.

Mechanics, all on current `main` (8c142e15):

- BE: `DataSourceServiceImpl.delete` (`:87-96`) checks `dataEntityRepository.existsNonDeletedByDataSourceId(id)` and errors with `CascadeDeleteException("Data source cannot be deleted: there are still data entities attached")`; `ControllerAdvice.java:42-46` maps it to **400** with that message in the body. (Note: the guard is "any non-deleted entities attached", not "actively ingested" - a long-stopped source that once ingested is blocked the same way.)
- FE: `DataSourceItem.tsx:31` wires `onConfirm` as a bare `dispatch(deleteDataSource(...))` with no `.unwrap()`. The thunk wrapper catches the API error and returns `thunkAPI.rejectWithValue(...)` (`handleResponseThunk.ts:34-42`), so the dispatch promise RESOLVES; `ConfirmationDialog.tsx:29-32` runs its `.then` branch - spinner clears, modal closes. The `.catch(() => {})` at `:33` never fires on this path.
- The toast that should have shown the 400 message is dead: `handleResponseThunk.ts:38` passes the generated client's `ResponseError` (thrown at `runtime.ts:140`; the real `Response` is at `err.response`, `:260-264`) into `showServerErrorToast`, whose `if (response.status)` gate (`errorHandling.tsx:65`) reads `undefined` on that wrapper - so no toast is ever rendered. Nothing else surfaces the rejected action (`DataSourceItem` reads no error selector).

## User-facing impact

User: an operator on Management -> Data Sources deleting a data source that still has (non-deleted) data entities - which is the normal state of any source that has ever been ingested.

What they do: click Delete -> confirm in the "Are you sure you want to delete this datasource?" dialog.

What they observably get: the dialog briefly shows its progress bar, then closes; **no error message, no toast, no visual change except that the data source is still in the list** (verified by FE/BE trace 2026-06-10: BE 400 at `ControllerAdvice.java:42-46`; FE close-on-failure at `handleResponseThunk.ts:41` + `ConfirmationDialog.tsx:29-32`; toast suppression at `errorHandling.tsx:65`). An operator who does not re-scan the list walks away believing the source is gone. The backend's perfectly good explanation ("there are still data entities attached") never reaches them. All facts above are settled by the code structure; the one behaviour not driven live is the exact visual timing of the progress bar (cosmetic, not load-bearing).

## Why it matters

A destructive control that reports failure as success is actively misleading - the operator either re-attempts later (confused), or worse, proceeds on the belief the source and its token are gone. The platform has a precise refusal message and drops it on the floor. Severity regraded **high -> medium**: the original high rested on a frozen-modal-with-no-recovery claim that is structurally impossible on this arm (thunk promises never reject); what remains is a silent-failure UX defect with no data loss and a correct server-side guard.

## Suggested fix

1. **Error surfacing (root cause, shared):** covered by **PLT-163** - fix the `ResponseError` unwrap in `lib/errorHandling.tsx` (+ the dialog `.catch`), so the 400 message renders as a toast/inline error. With just that fix this screen becomes "modal closes + clear error toast", which is acceptable.
2. **DataSource-specific UX (this issue):** pre-flight the cascade state - disable Delete with a tooltip ("This source still has data entities attached") or add an `additionalContent` forewarning in the dialog (the same `existsNonDeletedByDataSourceId` check the delete already runs, exposed read-only), so the operator learns the constraint *before* confirming a destructive action that will be refused.

## How discovered

Surfaced by the Layer-4b feature-reflection over feature flow F-031 (DataSource Lifecycle) on 2026-06-01, hypothesis H-005 (`lineage/odd-platform/feature-reflections/detail/F-031.yaml`).

**Corrected 2026-06-10 (user-facing verification sweep):** was "the ConfirmationDialog swallows the rejection, never resets isLoading, and stays stuck-open with a raw-jargon toast and no recovery path"; actually the DataSource delete arm is redux-thunk-wired (`DataSourceItem.tsx:31`), whose dispatch promise always resolves (`handleResponseThunk.ts:41`), so the modal CLOSES on failure and the `.catch(() => {})` is unreachable here - and no toast (jargon or otherwise) appears at all, because `showServerErrorToast` never fires for the `ResponseError` wrapper (`errorHandling.tsx:65`, `runtime.ts:140`). The reflection's stuck-modal hypothesis was a backend-plus-component extrapolation that the consumer wiring falsifies; the stuck-modal defect is real only on TanStack-`mutateAsync` surfaces and is owned by **PLT-163**.
