## What

Three operator-visible defects on the Manual Object Tagging feature surface. Each contradicts an operator-facing contract (the spec promise, the documented permission model, the audit-feed expectation).

**Defect 1 - `listMostPopular` returns OLDEST-by-id, not most popular (LSN-019).** `ReactiveTagRepositoryImpl.java:147-148`:
```java
paginate(homogeneousQuery,
         List.of(new OrderByField(TAG.ID, SortOrder.ASC)),
         (page - 1) * size, size)
```
The inner pagination orders by `TAG.ID ASC` BEFORE the COUNT aggregation. The outer `cteSelect.orderBy(field(COUNT_FIELD).desc())` at line 158 re-ranks only within the already-truncated window. For deployments with >30 tags, the most-popular tags created LATEST never reach page 1.

Maintainer empirical test (retrospectives/LSN-019:23-32, 2026-05-20): 35 tags all equally popular, size=30 -> response = 30 OLDEST by `tag.id` ASC; 5 youngest absent despite equal usage. The OpenAPI spec at `openapi.yaml:344-346` describes `getPopularTagList` as "sorted by popularity". The method name + spec promise + UI label ("Top Tags") are the operator-facing contract; the implementation cannot satisfy it without an SQL restructure.

**Defect 2 - Five side-channel mints into the global Tag directory (REFACTOR-223 + DOC-GAP-168).** The TAG_CREATE permission is documented as the canonical write path. It is **one of five**:

| # | Endpoint | Permission gate | Code path |
|---|----------|-----------------|-----------|
| 1 | `POST /api/tags` | `TAG_CREATE` | `TagController.createTag` |
| 2 | `setDataEntityTags` (PUT `/api/dataentities/{id}/tags`) | `DATA_ENTITY_TAGS_UPDATE` | `DataEntityController` -> `TagServiceImpl.getOrCreateTagsByName` |
| 3 | `createTermTagsRelations` (POST `/api/terms/{id}/tags`) | `TERM_TAGS_UPDATE` (`SecurityConstants.java:185-186`) | `TermController` -> `TagServiceImpl.getOrCreateTagsByName` |
| 4 | `updateDatasetFieldTags` (PUT `/api/datasetfields/{id}/tags`) | `DATASET_FIELD_TAGS_UPDATE` (`SecurityConstants.java:288-290`) | `DatasetFieldController` -> `TagServiceImpl.getOrCreateTagsByName` |
| 5 | External tag ingestion | NO auth at this layer | `ExternalTagIngestionRequestProcessor` |

`TagServiceImpl.getOrCreateTagsByName:80-86, 144-159` silently creates new tag rows for novel names. An operator restricting `TAG_CREATE` to "vocabulary stewards" discovers any user with per-entity tag-update on a single entity can mint arbitrary tag names visible to every user via `GET /api/tags`. The "Top Tags" UI inflates with un-stewarded entries; the Tag-facet search becomes polluted.

**Defect 3 - Three-way activity-audit asymmetry across the three tag-assign endpoints.** Three nominally-symmetric surfaces have THREE different audit-log behaviours:

| Endpoint | Service method | Audit behaviour |
|----------|----------------|------------------|
| Data Entity tags | `DataEntityServiceImpl.upsertTags:358` | `@ActivityLog` with `dataEntityId` only - no payload diff |
| Dataset Field tags | `DatasetFieldServiceImpl.updateDatasetFieldTags:117-132` | `@ActivityLog DATASET_FIELD_TAGS_UPDATED` with full before/after |
| Term tags | `TermServiceImpl.upsertTags:254-264` | NO `@ActivityLog` |

An auditor querying activity for a term's tag changes finds nothing; for an entity, finds an event with no payload diff; for a dataset-field, finds full diff. Building "who changed which tags when" reports requires three different decoders.

## Suggested fix (three independent threads)

**Thread A - Restructure the listMostPopular SQL.** Move `ORDER BY usage_count DESC` OUTSIDE the paginate primitive: compute COUNT over the FULL tag directory (no inner pagination), THEN apply ORDER BY DESC, THEN truncate by LIMIT/OFFSET. Either:
- Refactor `listMostPopular` to bypass the `paginate` helper and issue the SQL directly with the correct shape.
- Add a `paginateAfterAggregation` variant to `JooqQueryHelper` that takes the aggregation expression as a parameter; rewire `listMostPopular` to use it.

Recommend the second - the variant has other potential consumers (any paginated aggregation today is similarly broken). After the fix, the LSN-019 maintainer test on 35-equally-popular-tags returns a deterministic deterministic-by-ID-tiebreak result.

**Thread B - Lift TAG_CREATE consultation into `getOrCreateTagsByName`.** One-line fix at `TagServiceImpl:80-86`: check the principal's permission set inside `getOrCreateTagsByName` BEFORE the auto-create branch. If the caller lacks `TAG_CREATE`, raise `AccessDeniedException` instead of minting. Closes all four side-doors at the primitive. The collector-ingestion path (surface 5) needs separate handling - either grant the system-principal `TAG_CREATE` explicitly, or bypass the check via a `internalCallContext` marker. Recommend the latter.

After the fix:
- A multi-team deployment can restrict `TAG_CREATE` to vocabulary stewards.
- Per-entity tag-update operators can still ASSIGN existing tags but not MINT new ones.
- The collector-ingestion path continues to mint as the source of truth for new vocabulary.

**Thread C - Harmonise tag-assign audit emission.** Bring `DataEntityServiceImpl.upsertTags` + `TermServiceImpl.upsertTags` up to the DatasetField pattern: emit full before/after via `@ActivityLog`. Reuses the existing `TAG_ASSIGNMENT_UPDATED` event (which the live tagging.md page already documents on the entity path) - the work is on the term path (revives the dead pattern) and the entity path (upgrades from id-only to full payload).

## Operator impact

- "Top Tags" UI and the Tag-facet search render OLDEST tags, not popular - Defect 1.
- Multi-team deployments cannot restrict vocabulary minting today - Defect 2.
- Auditors reconstructing "who changed which tags when" need three different decoders today - Defect 3.
