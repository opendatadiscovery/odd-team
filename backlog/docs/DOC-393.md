## Description

The Dictionary results view renders a single empty-state placeholder — `No matches found` — for two semantically different situations:

1. **Fresh / empty catalog** — a day-one deployment with no terms authored yet, where the right next action is "add your first term."
2. **Filtered-zero** — a populated catalog where the current query or facet filter matched nothing, where the right next action is "broaden or clear the search."

The UI does not differentiate them: `TermSearchResults.tsx:105-107` shows the same `EmptyContentPlaceholder text={t('No matches found')}` whenever `!isTermSearchFetching && !total`, with no branch on whether any query/facet is active or whether the catalog is empty. A new operator who opens the Dictionary on a fresh install sees "No matches found" and reasonably concludes their search missed — when in fact there is nothing to find yet and they should be authoring the first term.

This compounds an existing documented behaviour: `business-glossary.md` already notes (around line 28) that the Dictionary is a server-side faceted-search session and shows an empty results table on first visit *even on a populated catalog* until a query or facet is applied. So an operator can hit an empty table in three distinct states (fresh-empty, populated-but-unqueried, filtered-zero) with no on-screen disambiguation.

## Acceptance Criteria

- [ ] The note states the consequence accurately: the placeholder does not distinguish "add your first term" from "your search missed."
