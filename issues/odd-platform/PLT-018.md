## What

Three operator-visible security defects on the Query Examples feature surface, in decreasing security-criticality order:

**Defect 1 - Stored XSS surface via raw-HTML Markdown without rehype-sanitize (the GHSA-bound facet).** Query Example `definition` and `query` fields are stored verbatim and rendered through the shared `Markdown` element at two UI sites (`QueryExampleDetailsOverview.tsx:19, 25` render `<Markdown value={definition} />` / `<Markdown value={query} />`; the wrapper calls `MDEditor.Markdown` at `Markdown.tsx:113-124`). That wrapper passes NO `rehypePlugins` at all - no `rehype-sanitize` - AND the underlying `@uiw/react-markdown-preview@4.2.2` (the `MDEditor.Markdown` export) defaults `skipHtml=true`, which makes it inject `rehype-raw` into the pipeline (`esm/preview.js:42`, `rehypePlugins.push(raw)`), with an `allowElement` filter that admits any alphanumeric tag name including `script`/`img` (`esm/index.js:36-39`). This is precisely the react-markdown-documented XSS footgun: `rehype-raw` WITHOUT `rehype-sanitize` re-enables raw HTML (`skipHtml` does not save it, because `rehype-raw` converts raw HTML into real element nodes before react-markdown@8.0.7's `skipHtml` check at `ast-to-react.js:149` ever runs). So the surface is real, not merely "no sanitizer configured." Whether a specific payload executes in the browser is the one part not settleable from code (see User-facing impact). **5th surface of the F-004 stored-XSS family - and all surfaces share ONE root fix (the shared `Markdown.tsx` wrapper); see Suggested fix.**

**Defect 2 - RBAC permission grid split across 3 controllers.** `SecurityConstants.java:112-113, 187-193, 312-317, 318-324` wires the 7 `QUERY_EXAMPLE_*` permissions across THREE controllers: `QueryExampleController` (CREATE/UPDATE/DELETE), `DataEntityController` (DATASET_CREATE/DELETE), `TermController` (TERM_CREATE/DELETE). Operators configuring permissions in one place miss four of seven gates.

**Defect 3 - 10 of 13 endpoints unscoped (broken access control; count re-verified 2026-06-10).** The `/api/queryexample*` paths expose 13 operations (`openapi.yaml:2089-2310`: GET+POST on `/api/queryexample`, GET+PUT+DELETE on `/{example_id}`, POST `/search`, GET+PUT `/search/{search_id}`, GET `/search/{search_id}/results`, GET `/dataset/{id}`, GET `/term/{id}`, GET `/search/suggestions`). Only the 3 mutations CREATE/UPDATE/DELETE carry SecurityRules (`SecurityConstants.java:112-113, 312-317`); the other 10 (all reads + the 4 search-session ops) have no entry and fall through to `.authenticated()` (`AuthorizationCustomizer.java:29-30`). Any authenticated user can read every Query Example in the platform regardless of Policy. (Under `auth.type=DISABLED` everything is anonymous anyway, `DisabledAuthSecurityConfiguration.java:16`.) This is what makes Defect 1's payload reach the entire authenticated user base.

## User-facing impact

- **Defect 1 - the dangerous configuration is verified by FE+vendored-source trace 2026-06-10; payload execution is RUNTIME-ONLY.** A data analyst with `QUERY_EXAMPLE_CREATE` can store arbitrary Markdown/HTML in `definition`/`query`; it renders to every viewer through a `rehype-raw`-without-`rehype-sanitize` pipeline (the canonical react-markdown XSS hole). What is NOT settleable from code: whether a concrete vector (`<img src=x onerror=...>`, `<script>`, `javascript:` href) actually fires under react-markdown@8.0.7's React-element construction - that needs a live drive (paste a payload into a query example, open the detail page, observe). Remaining check (for the GHSA reproduction): drive `<img src=x onerror=alert(document.domain)>` and a `[x](javascript:alert(1))` link through the detail Overview.
- **Defects 2 + 3 - verified by BE trace 2026-06-10 (static settled).** Every authenticated user can read every Query Example (10 unscoped read/search endpoints) and the XSS payload above therefore reaches the entire authenticated user base; an operator configuring Policies on `QueryExampleController` alone also misses the 4 dataset/term link gates that live on `DataEntityController`/`TermController` (`SecurityConstants.java:188-193, 318-324`).

## Why it matters

**Defect 1 (XSS)** is the security-critical item - operators with `QUERY_EXAMPLE_CREATE` (a common grant for data analysts authoring usage examples) can plant stored XSS that fires on every viewer's session. Read access on the 10 unscoped endpoints means **every authenticated user is a viewer** - the XSS payload reaches the entire platform user base.

**Defects 2 + 3** (RBAC grid split + 10 unscoped) compound: even an operator carefully configuring Policies on QueryExampleController misses the dataset-link and term-link mutation gates AND has zero protection on reads. The Query Example surface is effectively platform-wide-readable + platform-wide-XSS-vulnerable.

Severity is HIGH because the compound (XSS + read-collaborative) makes the feature unsafe for any deployment beyond a trusted-team-only scope.

## Suggested fix

### Defect 1 - sanitize the shared Markdown wrapper (closes the whole F-004 family)

```typescript
// Markdown.tsx - add rehype-sanitize to the MDEditor.Markdown render
import rehypeSanitize from 'rehype-sanitize';

<MDEditor.Markdown
  source={text}
  rehypePlugins={[[rehypeSanitize]]}
/>
```

Because every F-004 markdown-XSS surface (this item + PLT-015 / PLT-019 / PLT-023) renders through this **one** shared `Markdown.tsx` wrapper, a single `rehype-sanitize` addition here closes all of them simultaneously - this is the natural unit of the GHSA fix. Validate the sanitizer schema covers Markdown's expected syntax (code blocks, inline code, links) while stripping `<script>`, `<iframe>`, event handlers, `javascript:` URLs. Research the standard before inventing a custom schema (cf. the CTRIB-019 `@braintree/sanitize-url` precedent - adopt the vetted default, do not hand-roll).

### Defect 3 - scope the 10 unscoped endpoints

```java
// SecurityConstants.java - add SecurityRule entries for the 10 unscoped endpoints.
// Default: require QUERY_EXAMPLE_READ for reads (new permission), QUERY_EXAMPLE_SEARCH for list/search.
// Alternative: keep reads permissionless but document the deliberate read-collaborative decision.
new PathPatternParserServerWebExchangeMatcher("/api/queryexamples/**", GET).requires(QUERY_EXAMPLE_READ),
new PathPatternParserServerWebExchangeMatcher("/api/queryexamples/search/**", POST).requires(QUERY_EXAMPLE_SEARCH),
```

### Defect 2 - consolidate / surface the RBAC grid

The split across three controllers reflects the data model (a Query Example links to Datasets and Terms; the link endpoints live on those controllers). Recommend **non-breaking**: add a single shared `QueryExampleResolver` referenced by all three controllers for permission extraction, and document the 3-controller pattern explicitly in its Javadoc so operators auditing Policies see it. (A unified `/api/queryexamples/{id}/datasets|terms` endpoint family is the breaking alternative - coordinate with API consumers; not recommended.)
