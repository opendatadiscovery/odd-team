## What

`GET /api/datasets/{data_entity_id}/dataqatests` returns the complete list of a dataset's data-quality tests as a single, unbounded payload. There is no `page`/`size` parameter at any layer - not in the OpenAPI spec, not in the controller, not in the service query - and the UI renders every returned row. For a dataset with thousands of tests (large dbt/Great Expectations suites routinely produce these), one request materializes every test plus its dimensions and severities into one in-memory `DataEntityList`, serializes it whole, and ships it to the browser, which then lays out every row at once.

## Where

The OpenAPI operation declares only the path id - no pagination parameters and a single unbounded `200`:

`odd-platform-specification/openapi.yaml:1932-1947`
```yaml
  /api/datasets/{data_entity_id}/dataqatests:
    get:
      summary: Get DataEntity's related DataQualityTests
      description: Gets DataEntity's related DataQualityTests
      operationId: getDataEntityDataQATests
      parameters:
        - $ref: './components.yaml/#/components/parameters/DataEntityIdParam'
      responses:
        '200':
          description: OK
          content:
            application/json:
              schema:
                $ref: './components.yaml/#/components/schemas/DataEntityList'
      tags:
        - dataQuality
```

The controller method takes only the id - no page/size:

`odd-platform-api/.../controller/DataQualityController.java:25-31`
```java
    public Mono<ResponseEntity<DataEntityList>> getDataEntityDataQATests(final Long dataEntityId,
                                                                         final ServerWebExchange exchange) {
        return dataQualityService
            .getDatasetTests(dataEntityId)
            .map(ResponseEntity::ok);
    }
```

The service query collects **all** test oddrns, then **all** severities and **all** dimensions, with no `LIMIT`/`OFFSET`:

`odd-platform-api/.../service/DataQualityServiceImpl.java:38-50`
```java
    public Mono<DataEntityList> getDatasetTests(final long datasetId) {
        return dataQualityRepository.getDataQualityTestOddrnsForDataset(datasetId)
            .switchIfEmpty(...)
            .collectList()
            .flatMap(oddrns -> {
                final Mono<List<DataQualityTestSeverityPojo>> severities = dataQualityRepository
                    .getSeverities(oddrns, datasetId)
                    .collectList();
                final Mono<List<DataEntityDimensionsDto>> dimensions = dataEntityService.getDimensions(oddrns);
                return Mono.zip(severities, dimensions);
            })
            .map(function((severities, dimensions) -> dataEntityMapper.mapDataQualityTests(dimensions, severities)));
```

## Why it matters

The cost scales linearly with the number of tests on a dataset, and a dataset's test count is operator-controlled and unbounded - a maturing data-quality program only adds tests. On a heavily-tested dataset the request is loud and expensive on every load of the test report (large query, large response body, large client-side render), with no way for a client to ask for a window. The failure mode is gradual: the endpoint is fine for the first hundred tests and degrades as the suite grows, so it tends to surface in production on exactly the mature installs that invested most in data quality. No data loss; medium severity for the unbounded read amplification and the client-side render cost on a feature that is expected to grow over time.

## Suggested fix

Add `page`/`size` pagination across the stack: declare the `PageParam`/`SizeParam` (with `minimum:`/`maximum:` bounds) on `getDataEntityDataQATests` in `openapi.yaml`; thread them through the controller; apply `LIMIT`/`OFFSET` in `getDataQualityTestOddrnsForDataset` (and return a total count for the UI); and update the test-report UI to render a paged list. Open to alternatives on the page shape (offset vs. keyset), but the bound must exist at the query layer - capping only the UI still ships the unbounded query and payload.

## How discovered

Surfaced in the 2026-06-08 contradiction-harvest while reflecting on feature **F-022** (data-quality test report). Same broad class of "unbounded read" as PLT-134 / PLT-175, but a distinct endpoint family with **no** pagination parameter at all (the others have a `size` that merely lacks an upper bound; here there is no `page`/`size` to bound), so it is filed separately and its fix adds pagination rather than clamping an existing parameter.
