## Description

The per-entity Activity tab fires one backend query per filter change with **no debounce and no AbortController**, so a slow response for a superseded filter can land after a fast response for the current filter — and whether the redux reducer accepts the latest-arriving response (showing the user results for a filter they already moved off) depends on reducer correlation logic that is not statically determinable.

Confirmed against source (`DataEntityActivity/ActivityResults/ActivityResults.tsx` — the per-entity tab, NOT the global `Activity/ActivityResults`):
- `React.useEffect(() => { dispatch(fetchDataEntityActivityList({ ...queryParams, dataEntityId, isQueryUpdated: true })); }, [queryParams, dataEntityId]);` (lines 41-45).
- The dispatch is unconditional on every `queryParams` change; there is no debounce wrapper and no AbortController to cancel an in-flight fetch when the filter changes again.
- `isQueryUpdated: true` signals the reducer to REPLACE (not append) results.

Per F-196 H-005, the win-condition — does the reducer stamp/guard responses against the current query, or blindly accept the latest arrival? — lives in the redux slice + thunk, which are NOT in the reflection's chain, so the operator-visible outcome cannot be pinned from static reading. Lower amplitude than the global feed (1 query per twiddle vs the global feed's 4-count + 1-list), but the same race class. On an audit surface a stale result is actively misleading ("these are the events for THIS window" when they are not).

**Typed gate: characterization-pin (per LSN-029).** No debounce/cancel will be added as part of this item. The probe PENDING-F-196-1 drives rapid filter changes with a delayed slow response and observes whether the stale result wins. The IT pins that outcome: if the reducer accepts the late superseded response (stale results displayed), the IT asserts that CURRENT racy behaviour — GREEN now, RED the instant a debounce / AbortController / response-correlation guard is added. If the reducer already guards (current filter always wins), the IT pins that confirmed-good behaviour as a regression guard. Not `@Disabled` / `test.fixme`.
