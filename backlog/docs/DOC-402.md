## Description

The `GET /api/titles` (`getTitleList`) operation in the OpenAPI spec declares only a `200` response — no `403`. That is, by happenstance, **correct**: `TitleController.getTitleList` has no permission gate (no `@PreAuthorize`, no `RestrictedRoute`; it just calls `titleService.list(...).map(ResponseEntity::ok)`), so the endpoint is read-collaborative — any authenticated caller can read the titles list and the platform never returns a `403` on it. The problem is that the spec never *states* this intent. An integrator generating a client from the spec sees an endpoint with a lone `200` and no documented auth posture, and may either (a) add dead `403`-handling defensively (a code path that can never fire), or (b) wrongly assume the omission is a spec gap and that a `403` could appear after a future change. Neither is what the platform does. The no-read-gate posture is real and deliberate (it matches the rest of the read-collaborative read surface — see `reference-data.md`, where the read/search endpoints "require only authentication"), but it is implicit.

This is an optional, thin caveat: document the titles read endpoint's posture once so integrators do not write dead error-handling. The titles endpoint is currently **undocumented** in the api-reference (the only `titles` mention there is the unrelated query-example "snippet titles" typeahead), so the cleanest home is a one-line note alongside the existing read-collaborative reference-data surface.
