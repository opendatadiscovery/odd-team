## Description

Fifteen `feature-complete` specs fail on **both** the CTRIB-059 branch and plain `origin/main` — an identical
15/15 set, so they are entirely unrelated to ST-5c. They are **stale specs, not a product defect.**

**Root cause.** ST-4 (#1856, `ef2b34bb`) repointed the Search page's result fetch at the new unified cross-kind
endpoint. Captured from the browser's own network trace against a stack running `main @ 00b03129`:

```
POST 200  /api/search                    (session/facet state - still used)
POST 200  /api/search/assets?size=30     <-- ST-4: where results now come from
```

`GET /api/search/{search_id}/results` is **never called**. It still exists in the OpenAPI spec (unchanged, kept
for back-compat per ADR `unified-asset-search` D9) — but nothing in the UI calls it. Every one of the 15 specs
gates on a helper shaped like:

```ts
page.waitForResponse(r =>
  /\/api\/search\/[0-9a-f-]+\/results/.test(new URL(r.url()).pathname) &&
  r.request().method() === 'GET' && r.ok())
```

That promise can never resolve, so each spec burns its full 60s timeout.

## The product is FINE — verified by driving it, not by reading code

Against `main @ 00b03129` (stack up, entity ingested through the **real** `/ingestion/entities` API):

- `POST /api/search` -> 200 with a session + facet state; `GET /api/search/{sid}/results` -> 200, `total: 1`,
  the ingested entity returned. The legacy endpoint still works when called directly.
- The **rendered Search page** (Playwright page snapshot at the moment of failure) is fully healthy: the query
  sits in the search box, the tab strip correctly reads `All 0` for a non-matching query, the Filters rail
  (Asset type / Data entity type / Datasource / Owner / Tag / Groups / Statuses) renders, and ST-2b's
  `Sort by: Relevance` plus ST-3's `Save current search` / `Saved searches` are present and live.
- A DB-direct seed (the `seedSearchableEntity` helper's exact SQL) is **also** found by search, and ST-4's
  `asset_search_entrypoint` union row is correctly populated by the V0_0_98/V0_0_99 trigger.

So search works; only the specs' network oracle is stale.

## Why it went unnoticed for 8 weeks

The last recorded `feature-complete` baselines are 336/1 and 335/2, both from **2026-07-03** — which predates
ST-2a/ST-2b/ST-3/ST-4/ST-5a/ST-5b entirely. Six PRs repointed this surface with no e2e run in between (the same
ledger gap that produced the CTRIB-052..059 hole). The suite has been 15-RED ever since and nobody saw it.

## Acceptance Criteria
- [ ] Repoint the shared `resultsLoaded()` oracle at what the app actually calls — `POST /api/search/assets` —
  rather than deleting the wait (the wait is what makes these specs deterministic; removing it re-introduces the
  settle races TST-057 tracks). Both spec files define their own copy; consider ONE shared helper so the next
  endpoint move is a one-line fix.
- [ ] Do **NOT** weaken any assertion to get green (G-C15): the specs must still fail if search returns the wrong
  rows. Fix the *wait*, not the *oracle*.
- [ ] Re-run full `feature-complete` and confirm 337/0 (or that every residual failure is separately tracked).
- [ ] Add a guard so an endpoint move cannot silently blind the suite again — e.g. a spec that asserts the Search
  page issues a recognised results call at all, so a future repoint fails LOUDLY instead of timing out.
- [ ] Check whether the same stale-oracle pattern exists in term/query-example search specs.
