## What

Slack's Events API delivers events at-least-once (Slack's own published semantic — retries on missed 2xx ACK within ~3s; retries continue for up to ~3-5 attempts over ~60s). The platform's Slack-events processing pipeline has **no platform-side dedup**:

- `message_provider_event` table (`V0_0_59__data_collaboration.sql:25-39`) has NO UNIQUE constraint on `(provider, event_id)`; the only PK is `id BIGSERIAL`.
- `ReactiveMessageRepositoryImpl.createMessageEvent` (line 136-155) issues `DSL.insertInto(MESSAGE_PROVIDER_EVENT).set(record)` with NO `.onConflict(...)` clause.

Result: duplicate Slack retries (which happen routinely) insert duplicate rows; the downstream processor materialises N child `message` rows for one logical event. Operator-observable: the same message appears twice (or more) on the data-entity Discussions tab.

This is orthogonal to (and tracked separately from) the no-inbound-signature-verification defect on the same endpoint (DOC-GAP-290, separate fix).

## Why

Duplicate Discussion messages are operator-visible. Workspace admins seeing the same Slack message rendered 2-4× on the same data-entity Discussions tab lose confidence in the integration. The root cause (Slack's published at-least-once semantic + zero platform-side dedup) is benign-to-fix but corrosive-to-trust if unfixed.

The signature-absence defect (DOC-GAP-290) lets ANY anonymous caller emit synthetic Slack events; combined with the no-dedup defect, an attacker can replay a captured Slack event N times to amplify the corruption. The two defects compound; fixing each one independently shrinks the attack surface and the trust-loss surface respectively.

## How

Two-piece change:

**1. Flyway migration** (new `V0_0_NN__message_provider_event_unique.sql`):

```sql
-- Make (provider, event_id) the natural dedup key for at-least-once Slack delivery.
ALTER TABLE message_provider_event
ADD CONSTRAINT message_provider_event_provider_event_id_unique
UNIQUE (provider, event_id);
```

(If existing duplicate rows are present from prior at-least-once activity, the migration may need a `DELETE FROM ... USING ...` cleanup pass first — verify against a representative production-shaped dataset.)

**2. Repository INSERT — add ON CONFLICT DO NOTHING**:

```java
public Mono<Void> createMessageEvent(final MessageProviderEventPojo eventPojo) {
    return Mono.from(DSL.using(dsl)
        .insertInto(MESSAGE_PROVIDER_EVENT)
        .set(record)
        .onConflictOnConstraint(DSL.name("message_provider_event_provider_event_id_unique"))
        .doNothing()
    ).then();
}
```

(jOOQ's `.onConflict(...)` syntax is straightforward; the constraint-name lookup keeps the DDL the single source of truth for the dedup key.)

Alternative: compute a hash from the event payload + provider + parent_message_uuid as a logical idempotency key (slower; closer to a forensic-trail solution). Recommended primary fix is the schema-level UNIQUE + ON CONFLICT DO NOTHING — narrowest change, fastest dedup.
