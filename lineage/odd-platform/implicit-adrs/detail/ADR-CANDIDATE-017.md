- **ADR-CANDIDATE-017** (NEW 2026-05-10A; STRENGTHENED 2026-05-10B): Collector tokens are rotated **in-place** (UPDATE-not-INSERT), returned plaintext on rotation, masked on read, and authenticated via plaintext String-equals against the in-DB value (no hashing layer)
  - **Category**: promote
  - **Support**: surfaced by 2 sidecars (`regenerateCollectorToken` from the rotate side + STRENGTHENED 2026-05-10B by `IngestionDataEntitiesFilter` from the verify side at `IngestionDataEntitiesFilter.java:56` — two-independent-sidecar corroboration of the plaintext-equality model; the rotate side establishes the storage shape, the verify side confirms the comparison shape, together they compose the full shared-secret S2S model)

  - **Decision statement**: ODD's Collector token model is a **40-character alphanumeric shared secret**, persisted in the `TOKEN` table as plaintext, authenticated by `IngestionDataEntitiesFilter` via direct `String.equals(...)` against the in-DB value. Token rotation is an **in-place UPDATE** of the existing TOKEN row (not an INSERT-new + REVOKE-old transition), keyed 1:1 to the Collector via `CollectorPojo.tokenId`. The new value is returned in plaintext in the rotation response (`TokenDto.showToken=true`); list/get reads mask via `mapValue` to `******{last6}` (`TokenDto.showToken=false` default). The composition is deliberate: a single mutable shared-secret with TLS as the only confidentiality boundary.
  - **Wisdom test**: PASS. The four sub-decisions are all anchored in **vocabulary** (method names, repository method names, factory method names, constructor defaults) and **structure** (1:1 schema relationship, no hashing column, single-value equality). The rationale "long-random opaque string over TLS" is implicit but consistent. The trade-offs are real and structural: rotating one token requires a coordinated client-side restart (no grace window); a DB backup carries credentials; an SQL-injection at the TOKEN table escalates to platform-wide ingestion compromise.
