## Description

The live `sla-statuses.md` page explicitly states that changing a test's severity from Major to Critical can flip the dataset's SLA colour from Yellow to Red **without any test pass/fail status changing**. The page is silent on whether the platform records WHO changed the severity, WHEN, or what the prior severity was.

**F-057a — Severity mutation emits NO activity event (HIGH; strengthens DOC-GAP-083 META + DOC-GAP-149 META).** `DataQualityServiceImpl.java:62-81` (`setDataQualityTestSeverity`) is `@ReactiveTransactional`; no `@ActivityLog`; no `activityRepository` reference; no notification dispatch. The PUT mutation is gated by `DATASET_TEST_RUN_SET_SEVERITY` permission but emits NO ActivityEvent row. NO `last_modified_by`, NO version increment, NO Slack/webhook notification. The UPSERT (`ReactiveDataQualityRepositoryImpl.java:87-102` — onDuplicateKeyUpdate, no last_modified_by, no version) is idempotent in OUTCOME (row converges to new severity) but loses HISTORY (prior severity overwritten).

**Operator-visible consequence**: A compliance reviewer auditing "who changed this dataset's SLA to Red on May 14?" cannot answer from the platform without DB inspection. An operator triaging a dashboard flip cannot tell whether (a) a test result changed or (b) someone reclassified a test's severity. **BI tools embedding the SLA colour see the cross-origin flip with NO platform-side signal of who triggered it** — blast radius wider than the F-019 owner-lifecycle audit-silence case because the change is consumed OUTSIDE the platform UI (Confluence, Notion, Excel, Looker tiles).
