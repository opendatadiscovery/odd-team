## What

Two defects on the ERD/Graph Relationships surface (`RelationshipController`):

1. **Detail endpoints silently translate the path param to `data_entity.id`.** `GET /api/relationships/erd/{relationship_id}` and `/graph/{relationship_id}` document the parameter as `relationship_id` (and name the operations `getERDRelationshipById` / `getGraphRelationshipById`), with no caveat that the param is *not* the `relationships`-table PK. The SQL filters on `DATA_ENTITY.ID = relationshipId` and the list mapper surfaces `id = data_entity.id`, so a third-party consumer who reads the reference literally and supplies an actual `relationships.id` gets HTTP 404 (`NotFoundException`). The in-product UI is masked from this because its own list mapper also emits `data_entity.id`.
2. **`GET /api/relationships` applies none of the catalog-visibility predicates `/api/dataentities` applies.** The list selects only by `entity_class_ids=[9]` + an optional `external_name` match - no `EXCLUDE_FROM_SEARCH`, no `HOLLOW=false`, no `STATUS != DELETED`, no ownership join, no datasource/cross-tenant filter. Relationships whose data_entity is `exclude_from_search=true`, `HOLLOW`, soft-DELETED, or owned by another tenant *are* returned - states operators believe are hidden. (Secondary: the `query=` free-text matches only the relationship-row `external_name`, not source/target entity names - an API consumer expecting entity-name search is not warned.)

Sources: HARVEST-049, HARVEST-050 (doc-understanding harvest, 2026-05-29). Doc caveat tracked at `backlog/docs/DOC-300.md`.

## User-facing impact

Verified-trace 2026-06-10 (controller, both repositories, mapper, `DataEntityClassDto`, SecurityConstants, generated `RelationshipApi` all read). Both defects are code-settled.

- **Defect 1 (param translated to data_entity.id -> 404 on a real PK):** confirmed. The detail query filters `.where(relationshipsDataEntity.field(DATA_ENTITY.ID).eq(relationshipId))` (`ReactiveRelationshipsRepositoryImpl.java:194`) - the path param is matched against `DATA_ENTITY.ID`, not `RELATIONSHIPS.ID`. A consumer who reads the published `relationship_id` contract (`GET /api/relationships/erd/{relationship_id}`, generated `RelationshipApi:64`) and supplies a real `relationships.id` gets an empty result -> `NotFoundException` (`RelationshipsServiceImpl.java:40,47`) -> HTTP 404. **The UI is masked** because the list mapper emits `id = item.dataEntityRelationship().getId()` (the data_entity id, `RelationshipMapper.java:53`), so the UI fetches detail with the same data_entity id it was given and round-trips consistently. Confirmed by tracing; no run needed.
- **Defect 2 (list applies none of the catalog-visibility predicates):** confirmed. `ReactiveDataEntityRelationshipRepositoryImpl.getRelationships` (`:56-79`) builds its condition list from only (a) optional `DATA_ENTITY.EXTERNAL_NAME.containsIgnoreCase(inputQuery)` (`:69`) and (b) `DATA_ENTITY.ENTITY_CLASS_IDS.eq([DATA_RELATIONSHIP.getId()])` (`:72`). `DATA_RELATIONSHIP` id = 9 (`DataEntityClassDto.java:51`), so the draft's `[9]` is correct. There is NO `EXCLUDE_FROM_SEARCH`, NO `HOLLOW`, NO `STATUS != DELETED`, NO ownership/tenant join - so relationships whose data_entity is excluded/hollow/soft-deleted/cross-tenant are returned. There is NO SecurityRule on any `/api/relationships` route (grep `relationship` in SecurityConstants = 0), so this is an enumeration surface readable by any authenticated user (anonymous under the shipped `auth.type=DISABLED` default). The secondary claim holds too: `query=` matches only `EXTERNAL_NAME` (`:69`), not source/target entity names.

No FE drive needed beyond the masking trace (the mapper emits data_entity.id, which is why the UI never sees the 404). Remaining optional runtime check: a probe creating an `exclude_from_search` relationship entity and confirming `/api/relationships` returns it while `/api/dataentities` hides it.

## Why it matters

A developer integrating against the relationships API by its published contract supplies the documented `relationship_id` (the real PK) and gets a 404 for a record that exists - a silent, confusing translation (Category-F, LSN-002 class). Worse, the list endpoint is an enumeration surface: it returns relationships for entities that catalog policy hides everywhere else (`EXCLUDE_FROM_SEARCH`, soft-deleted, cross-tenant), so an authenticated user (anonymous under `DISABLED`) can enumerate hidden/other-tenant entity structure through `/api/relationships` that they cannot see through `/api/dataentities`. The asymmetry is invisible because the UI round-trips consistently.

## Suggested fix

- Either accept the real `relationships.id` on the detail endpoints (and adjust the SQL + mapper), or rename the parameter to `data_entity_id` in spec + docs and add an explicit caveat - pick one and make spec/code/doc agree. (PLT-056 already queues the `relationship_id` semantic-alias decision.)
- Lift the `/api/dataentities` visibility predicates (`EXCLUDE_FROM_SEARCH`, `HOLLOW=false`, `STATUS != DELETED`, ownership/cross-tenant filter) into the relationships list query so the two surfaces are symmetric - ideally via the shared select helper so the predicate cannot drift again.
