## What

The shared `ConfirmationDialog` (the "Are you sure?" dialog behind every destructive action - 23 consumer components) discards any rejection from its `onConfirm` promise: only the `.then(...)` branch clears the loading state and closes the modal; the `.catch(() => {})` does nothing (`ConfirmationDialog.tsx:28-33`). Whether that swallow ever fires, however, depends on which of TWO wiring styles the consumer uses - and the consequences split the corpus in half:

1. **TanStack Query `mutateAsync` consumers (10 components, 11 dialogs) - the swallow fires and the modal wedges.** `mutateAsync` returns a promise that REJECTS on any non-2xx (the generated client throws `ResponseError` at `runtime.ts:140`). On rejection `isLoading` is never reset, and `DialogWrapperStyles.ts:34` sets `pointerEvents: 'none'` on the whole dialog while loading - so the modal is left spinning and completely mouse-dead (the title X button and backdrop-click close are unreachable).

2. **Redux-thunk consumers (13 components) - the swallow NEVER fires; the failure is a silent close instead.** Every thunk arm passes a bare `dispatch(someThunk(...))` with no `.unwrap()` (e.g. `DataSourceItem.tsx:31`, `EditableNamespaceItem.tsx:21-24`, `EditableOwnerItem.tsx:27-30`). A redux-toolkit dispatch promise RESOLVES even when the API call fails (`handleResponseThunk.ts:41` returns `thunkAPI.rejectWithValue(...)`, which is a resolved rejected-action), so the `.then` branch runs: spinner clears, modal closes, and the failed action looks exactly like a successful one.

Compounding both arms: **no error toast appears on either path.** The error handlers (`handleResponseThunk.ts:38` for thunks; the global mutation default at `index.tsx:44-46` for mutations) pass the thrown `ResponseError` to `showServerErrorToast`, which expects a raw `Response`: `response.json()` throws (caught), and the `if (response.status)` gate at `errorHandling.tsx:65` reads `undefined` on a `ResponseError` (the real `Response` sits one level down at `err.response`, `runtime.ts:260-264`) - so the toast is never shown. No FE code unwraps `.response` anywhere.

An earlier revision claimed the stuck modal was "confirmed live on the three Management cascade-delete arms (Owner, Namespace, DataSource)". That is false - all three are thunk-wired, where the stuck modal is structurally impossible; see the correction note below.

## User-facing impact

User: any operator confirming a destructive/mutating action in the UI when the backend refuses it (cascade-block 400, RBAC 403, 500, network error).

- **Lookup-table / query-example / owner-association / attachment surfaces (the 11 mutateAsync dialogs):** the operator clicks the confirm button, the dialog shows the linear progress bar, and on failure it stays open, spinning, with every mouse interaction dead (`pointerEvents: 'none'` while loading - `DialogWrapperStyles.ts:34`); no error message appears anywhere (toast suppressed; verified by FE trace 2026-06-10: `index.tsx:44-46` -> `errorHandling.tsx:65` gate is falsy for `ResponseError`). Escape should still close the dialog (keyboard events are not pointer events; MUI's default escape-close path at `DialogWrapper.tsx:99,64-74`) - static trace consistent; not driven. Even after an Escape-close, the dialog instance keeps `isLoading=true` (state lives in the still-mounted `ConfirmationDialog`, reset only on unmount - `ConfirmationDialog.tsx:64`), so reopening it presents a born-locked dialog; recovery requires navigating away or reloading. Remaining runtime check: drive one rejecting surface (e.g. lookup-table delete under a forced 500) and confirm Escape behaviour + the born-locked reopen.
- **Management delete/regenerate arms and the other 13 thunk surfaces:** the modal closes exactly as on success, no toast, no error state - the only signal that the action failed is that the row is still in the list after the modal closes (verified by FE trace 2026-06-10: `handleResponseThunk.ts:34-42` resolves, `ConfirmationDialog.tsx:29-32` then-branch runs). For the term-delete arm the UI additionally navigates to the term-search page as if deletion succeeded (`TermDetails.tsx:47-53`).

## Why it matters

Both failure shapes are the worst-feedback versions of the highest-consequence actions, and both are invisible: one arm freezes a modal with no message, the other reports failure as success. The platform's own guardrails (cascade-block, RBAC denial) trigger these paths in normal operation. Severity stays **high**: the stuck-spinner arm (11 dialogs, no feedback, no mouse recovery) plus the silent-success arm (13 surfaces, failure indistinguishable from success on destructive actions) together degrade every confirm-and-mutate flow in the product.

## Suggested fix

Three layers, smallest first:

1. **`ConfirmationDialog.tsx:33`** - in the `.catch`, call `setIsLoading(false)` and surface the error (inline error region in the dialog, or rethrow to the toast channel) instead of discarding it. This unfreezes the mutateAsync arm.
2. **`lib/errorHandling.tsx`** - make `getErrorResponse`/`showServerErrorToast` unwrap `ResponseError` (`err instanceof ResponseError ? err.response : err`) so thunk and mutation failures produce the error toast they were designed to produce. Without this, fix 1 still has no message to show and the thunk arm stays silent.
3. **Thunk consumers** - either `.unwrap()` the dispatch in `onConfirm` (so the dialog can distinguish failure) or have the dialog inspect the resolved action (`isRejectedWithValue`) before treating it as success; otherwise the modal keeps closing on failure even after 1+2.

## How discovered

Surfaced by the 2026-06-08 contradiction harvest (`lineage/odd-platform/harvest/2026-06-08-contradiction-harvest.md`, NOVEL-bug HIGH row "F-031 H-005 / F-076 H-003 - ConfirmationDialog swallows rejection"), triaged from feature reflections F-031 (`lineage/odd-platform/feature-reflections/detail/F-031.yaml`) and F-076 (`.../F-076.yaml`).

**Corrected 2026-06-10 (user-facing verification sweep):** was "every consumer inherits the stuck modal; confirmed live on the three Management cascade-delete arms (Owner, Namespace, DataSource)"; actually those three arms - and 10 more consumers - pass bare `dispatch(thunk)` promises that always RESOLVE (`handleResponseThunk.ts:41` + redux-toolkit semantics, no `.unwrap()` at any of the 23 call sites), so on those surfaces the modal closes silently on failure and the stuck spinner is impossible. The stuck-spinner claim holds only for the 10 TanStack-`mutateAsync` consumers (`LookupTablesListItem.tsx:20`, `LinkAttachment.tsx:22`, etc.). Verification also found the failure feedback is worse than drafted on BOTH arms: no error toast ever appears, because `showServerErrorToast` receives the generated client's `ResponseError` wrapper and its `response.status` gate (`errorHandling.tsx:65`) is falsy - the real `Response` is at `err.response` (`runtime.ts:140,260-264`) and nothing unwraps it. The "no way forward except reloading the page" claim is softened: Escape still closes the wedged dialog (static trace; not driven), but the dialog instance remains locked-loading until unmount.

**Relation to PLT-128 (distinct, *narrower*):** PLT-128 is the DataSource-delete arm of the thunk class - corrected the same day to the silent-close behaviour plus the missing pre-flight/forewarning UX on `DataSourceItem`. This issue owns the shared-component fix (dialog catch + toast unwrap + thunk-arm wiring); PLT-128 owns the DataSource-specific UX asks.
