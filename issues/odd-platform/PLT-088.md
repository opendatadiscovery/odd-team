## What

Three defects on the chrome surface that share the AppInfoMenu / Additional-Links theme. All three are small-surface fixes; ship together. All three re-verified 2026-06-10 against the source (`AdditionalLinkProperties.java` + `AppInfoMenu.tsx`); line numbers and the icon-button element corrected below.

**Defect 1 - `AdditionalLinkProperties` has no validation (Java).** `AdditionalLinkProperties.java:6-9` is `record AdditionalLinkProperties(List<Link> links) { record Link(String title, String url) {} }` under `@ConfigurationProperties("odd")` - no `@NotBlank` / `@URL` / `@Pattern` / `@Validated` / `@PostConstruct validate()` / compact-constructor check. Accepts: missing title, missing url (`<a href=null>`), `javascript:alert(1)`, `data:text/html,...`, `file:///etc/passwd`, relative paths. Nothing fails at config-load - bad operator-supplied data ships silently into the UI. HOLDS. (Note: the binding prefix is `odd` and the bound field is `links`, so the property path is `odd.links[].{title,url}`.)

**Defect 2 - `AppInfoMenu` reverse-tabnabbing on 5 link sites (frontend).** `AppInfoMenu.tsx:41, 61, 95, 103, 112` - 5 `<Link ... target='_blank'>` sites render WITHOUT `rel='noopener noreferrer'`. An attacker controlling any destination (compromised wiki, future XSS, operator-supplied bad link from Defect 1) can `window.opener.location = ...` from the opened tab. Compound with Defect 1: an unvalidated operator-link becomes a reverse-tabnab vector. HOLDS - all five line numbers verified exactly (41 = version/GitHub, 61 = operator links map, 95 = Documentation, 103 = Slack, 112 = "Leave a feedback"/review).

**Defect 3 - `AppInfoMenu` open-control keyboard- and touch-inaccessible despite declaring ARIA support (WCAG 2.1 SC 2.1.1).** `AppInfoMenu.tsx:74-82` - the open control declares `aria-haspopup='true'` (`:80`) + `aria-controls={menuId}` (`:79`) but wires ONLY `onMouseEnter={handleAppMenuOpen}` (`:81`). NO `onClick`, NO `onKeyDown`, NO `onFocus`. Touch users (iOS Safari, Android Chrome) generate no mouseenter; keyboard/AT users cannot open the menu. The Documentation / Slack / Feedback / Version / operator-link surface is unreachable without a mouse. HOLDS. (Element correction: the open control is the project's custom `<Button>` wrapper - `components/shared/elements/Button/Button` - rendered with an `icon` prop, NOT a raw MUI `<IconButton>` as the original draft wrote. The accessibility gap is identical; only the element name was wrong.)

## User-facing impact

Verified 2026-06-10 by reading `AdditionalLinkProperties.java` + `AppInfoMenu.tsx` end-to-end:

- **Defect 1 (operator-supplied, latent):** the `odd.links` record has zero validation, code-confirmed - a malformed operator entry (blank title, `javascript:`/`data:`/`file:` URL, relative path) binds and ships into the AppInfoMenu without a boot-time error. Blast radius is limited to operator/teammate-authored config (no anonymous-attacker path), which is why it is MEDIUM. The specific browser outcomes per scheme (React neutralising `javascript:`, browser sandboxing `data:`, etc.) are runtime/browser behaviours stated as rationale, not separately driven here; the load-bearing, code-settled fact is "no config-load validation," which holds.
- **Defect 2 (active, defence-in-depth):** code-confirmed - all 5 `target='_blank'` links lack `rel='noopener noreferrer'`. The reverse-tabnabbing reachability depends on the destination being attacker-controlled AND the user's browser not applying the modern implicit `noopener` default (most browsers since ~2020 do, which caps real-world severity); the correct hardening is to set `rel` explicitly rather than rely on the browser default. Code-settled that the attribute is absent; the exploit path is the standard `window.opener` vector, browser-dependent.
- **Defect 3 (active, accessibility):** code-confirmed and the most concretely user-facing - the menu's open control has only `onMouseEnter`, so a keyboard-only or touch user cannot open the App Info menu at all (Documentation / Slack / Feedback / Version / operator links become unreachable for them). This is directly observable: tab to the control and press Enter/Space -> nothing happens; on touch, tap -> nothing happens. WCAG 2.1 SC 2.1.1 violation in shipped code.

Severity MEDIUM (each defect) stands; Defect 3 is the one with a clear, reproducible end-user symptom today.

## Why it matters

**Defect 1** is operator-trust + security: the `odd.links` config is operator-authored, but the platform offers no input validation. Operators trusting "the platform will reject bad input" discover the gap when a junior teammate's PR adds a malformed entry that ships to production.

**Defect 2** is the security amplifier - most browsers default `target='_blank'` to `noopener` since 2020, but compatibility-trailing browsers + the React Router `<Link>` abstraction may not honour the modern default. Adding `rel='noopener noreferrer'` explicitly is the correct hardening.

**Defect 3** is WCAG-violation in shipped code. ODD deployments serving accessibility-required audiences (US federal, EU public sector, enterprise compliance frameworks) cannot meet accessibility standards with the current AppInfoMenu. The Documentation / Slack / Feedback / Version / operator-link surface is inaccessible to keyboard-only + screen-reader users.

Severity MEDIUM (each defect individually) because:
- Defect 1 is operator-supplied input - limited blast radius (no random-attacker path)
- Defect 2 is most browsers' default - defense-in-depth, not a primary vulnerability
- Defect 3 is a compliance gap, not a runtime defect

Combined the three give a tight UI / config-validation hardening PR.

## Suggested fix

### Defect 1 - validation on AdditionalLinkProperties

```java
// AdditionalLinkProperties.java  (prefix is "odd"; the list field is "links" -> odd.links[])
@Validated
@ConfigurationProperties("odd")
public record AdditionalLinkProperties(
    @Valid List<Link> links
) {
    public record Link(
        @NotBlank String title,
        @NotBlank @Pattern(regexp = "^https?://.*", message = "url must be http or https")
        String url
    ) {
        // Additional defensive validation in compact constructor:
        public Link {
            if (url != null
                && (url.toLowerCase().startsWith("javascript:")
                    || url.toLowerCase().startsWith("data:")
                    || url.toLowerCase().startsWith("file:")
                    || url.toLowerCase().startsWith("vbscript:"))) {
                throw new IllegalArgumentException(
                    "odd.links url scheme not allowed: " + url);
            }
        }
    }
}
```

Boot fails-fast on bad operator input; reports the specific bad URL.

### Defect 2 - rel="noopener noreferrer" on the 5 AppInfoMenu link sites

```tsx
// AppInfoMenu.tsx - apply to each of lines 41, 61, 95, 103, 112
- <Link to={url} target="_blank">{label}</Link>
+ <Link to={url} target="_blank" rel="noopener noreferrer">{label}</Link>
```

Five mechanical edits. Could be made a project-wide lint rule (`react/jsx-no-target-blank`) in a follow-up PR.

### Defect 3 - keyboard handlers on the AppInfoMenu icon button

```tsx
// AppInfoMenu.tsx:74-82  (the custom <Button> wrapper, rendered with an icon prop)
<Button
  aria-label='app info menu'
  aria-controls={menuId}
  aria-haspopup='true'
- onMouseEnter={handleAppMenuOpen}
+ onClick={handleAppMenuOpen}
+ onKeyDown={(e) => {
+   if (e.key === 'Enter' || e.key === ' ') {
+     e.preventDefault();
+     handleAppMenuOpen(e);
+   }
+ }}
+ onMouseEnter={handleAppMenuOpen}
/>
```

Keep `onMouseEnter` for hover-discoverability; add `onClick` + `onKeyDown` for keyboard + touch. (Confirm the custom `Button` wrapper forwards `onKeyDown`/`onClick` to the underlying element; if not, that prop pass-through is part of the fix.) Menu close should likewise be reachable via Escape - the MUI `AppMenu` already wires `onClose` (`AppInfoMenu.tsx:93`), which MUI fires on Escape, so close is handled.
