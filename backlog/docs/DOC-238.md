## Description

The live `enable-security/authentication/ldap` page (WebFetched 2026-05-27) tells operators "ODD platform can get LDAP groups ... Thus it is possible to define which groups will grant admin privileges" — language that implies exact group-membership semantic. The code does NOT enforce exact matching, and a separate silent-USER-only path exists when groups configuration is omitted.

**Facet 1 — Substring overpromotion (F-124a, HIGH→CRITICAL).** `LDAPSecurityConfiguration.java:96` uses `containsIgnoreCase(properties.getGroups().getAdminGroups(), authority)` — case-insensitive SUBSTRING containment, not equality. Operator config `admin-groups: ['ops']` against LDAP groups `devops`, `noops`, `appops`, `dataops` silently promotes EVERY member of EVERY one of those groups to ADMIN. Mitigation today is operator-side (use long admin-group names like `ODD_PLATFORM_ADMINS`). A security audit assuming exact-match semantics misses entire user populations granted ADMIN via short admin-group tokens. This is the HIGHEST-severity LDAP finding in the batch and the originating instance of the cross-provider pattern that also affects GitHub (F-124b — covered by DOC-235).

**Facet 2 — Silent USER-only path when `auth.ldap.groups` is unset (F-124c, MEDIUM→HIGH).** `LDAPSecurityConfiguration.java:91-93` returns a USER-only authority for every authenticated user when `auth.ldap.groups` is null OR `admin-groups` is empty. An operator who uncomments LDAP but forgets `groups.admin-groups` has NO path to ADMIN via LDAP AND no error message tells them. The doc neither warns about the requirement nor recommends what to do.

## Acceptance Criteria

- [ ] A new "## Admin promotion (substring overpromotion warning)" H2 (or H3 within an existing Admin section) is added on ldap.md covering:
  - **Substring overpromotion**: `admin-groups` uses case-insensitive SUBSTRING containment, NOT exact equality. `admin-groups: [ops]` matches `devops`, `noops`, `appops`, `dataops`. Use long full-group-name tokens like `ODD_PLATFORM_ADMINS`. Sample LDAP group naming → operator action table:

    | LDAP group examples | `admin-groups` value | Effect today (SUBSTRING) | Effect after PLT-081 (exact) |
    |---|---|---|---|
    | `devops`, `noops`, `dataops` | `ops` | All 3 groups → ADMIN (overpromotion) | None → ADMIN |
    | `admins`, `team-admins`, `readonly-admins` | `admins` | All 3 groups → ADMIN | Only literal `admins` → ADMIN |
    | `odd-platform-admins-team` | `odd-platform-admins-team` | Exact group → ADMIN (no overpromotion) | Same |

  - **Silent USER-only path**: If `auth.ldap.groups` is unset OR `admin-groups` is empty, every authenticated user is granted USER role — there is NO admin path via LDAP. Combined with the platform's lack of post-boot self-checks, an operator who uncomments LDAP but forgets the groups configuration has a deployment with no possible admin. Recommend setting `admin-groups` to a known-empty placeholder (and tracking PLT-077 for boot-time validation).

## Correction (2026-06-08, via DOC-336)

The "case-insensitive **substring** overpromotion" framing in this item's title is **wrong** — the platform uses full case-insensitive equality on every handler (`OperationUtils.containsIgnoreCase` = `equalsIgnoreCase`), not substring. Cross-reference DOC-336 (the GitHub correction). **Verified 2026-06-08:** the live `ldap.md` (line ~220) already reads "compared **case-insensitively on the whole name** … not a substring or prefix match", so there is **no live residue** on the LDAP page — do not "re-fix" a correct page.
