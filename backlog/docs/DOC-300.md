## Description

Two code-confirmed caveats on the relationships API reference:

1. **`{relationship_id}` is not the relationships PK.** `GET /api/relationships/erd/{relationship_id}` and `.../graph/{relationship_id}` present the path param as the relationship id, but the code **translates it to `data_entity.id`** — it expects an **entity** id, not a relationships PK. A caller who supplies an actual `relationships.id` (the obvious reading of the doc) gets a **404**. This is the harvest's "Category-F silent translate" — the param means something other than its name says, and the failure is a confusing 404 on a correct-looking request.

2. **`GET /api/relationships` applies no catalog-visibility predicates.** The plain list endpoint applies **none** of the catalog-visibility predicates that `GET /api/dataentities` applies. Relationships whose entity is `exclude_from_search`, `HOLLOW`, soft-`DELETED`, or cross-tenant **are returned**. A consumer who assumes the relationships list respects the same visibility rules as the entity catalog leaks hidden/deleted/cross-tenant relationships into their view.

High — a 404 footgun on a primary endpoint plus a visibility-bypass on a list endpoint.

**Failure shape**: code-doc drift (param semantics) + missing caveat (visibility asymmetry).
