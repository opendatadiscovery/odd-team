## Instance 3 — and the ROOT CAUSE (2026-09-07, CTRIB-067 Phase D)

**The answer this item was waiting for.** Every prior instance was a CI failure, where "the assert hides the
cause". This one happened in a LOCAL full build with `testLogging.showStandardStreams = true`, so the server-side
exception is in the log:

```
java.lang.IllegalArgumentException: Unexpected value for timestamp 1788815968
    at PrometheusMetricsMapperImpl.getTimestampValue(PrometheusMetricsMapperImpl.java:219)
    at PrometheusMetricsMapperImpl.enrichMetric(PrometheusMetricsMapperImpl.java:97)
    ... Handler DataEntityController#getDataEntityMetrics(Long, ServerWebExchange)
```

**It is not a transient. It is a type bug with a timing-shaped trigger.**

`PrometheusMetric.value` is a `List<Object>`, filled by Jackson from Prometheus's instant-query shape
`"value": [<unix_time>, "<sample_value>"]`. `getTimestampValue` accepts **only** `String` or `Double` and throws
on anything else. Prometheus prints the timestamp as seconds *with a fractional part when it has one* — so a
sample whose timestamp lands on a whole second serialises as the bare integer `1788815968`, Jackson binds that
into `Object` as an **`Integer`**, and the mapper throws. The 500 follows from `ControllerAdvice`.

**The exception message is its own proof of type.** It is built with `"...%s".formatted(object)`: a `Double`
would have printed `1.788815968E9`, and a `String` would have taken the first branch. A bare `1788815968` can
only be an `Integer` (or `Long`).

That is why it looks random: the test drives a REAL `prom/prometheus:v2.42.0` container
(`PrometheusMetricsIngestionTest:35-40`) and reads back whatever timestamp the sample happened to get. Whole-second
timestamps are rare, so the failure is rare — and it is rare in exactly the same way for an OPERATOR reading the
metrics tab of a data entity.

**Instance details:** 2026-09-07, local CI-replica build on `contrib/CTRIB-067-recently-viewed-facet` (single-worker,
`--no-parallel`), 859 tests / 1 failure — `testGaugeAndCount()` this time, where instances 1 and 2 were
`testHistogramAndSummary()`; the two share `BaseIngestionTest.assertMetrics`. The class then passed **2/2 in
isolation**, matching the CTRIB-025 observation and ruling the CTRIB-067 diff out (it touches search, not metrics).

**Filed upstream:** [odd-platform#1887](https://github.com/opendatadiscovery/odd-platform/issues/1887)
(`PLT-270`) — the test is a messenger; the fix belongs in `PrometheusMetricsMapperImpl`, not in the test.
