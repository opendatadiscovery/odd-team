## What

Deleting a data source that is still actively ingested triggers a backend cascade-block (HTTP 400), but the UI `ConfirmationDialog` **swallows the rejection** (`.catch(() => {})`), never resets `isLoading`, and stays stuck-open - the operator gets only a raw-jargon toast and no recovery path. There is no pre-flight cascade check, no disabled-with-tooltip Delete, and no forewarning that the source is in use. The operator is left with a frozen modal on a destructive action they cannot complete or cleanly cancel.

This is **distinct from PLT-087** (which covers the *backend* delete cleanup - orphan token + uncleared FTS - not the UI-tier failure) and from **PLT-038** (which is dialog *text* grammar/guidance, not the swallow/stuck behaviour). DOC-255 Caveat 2 documents the backend semantics only. The stuck-modal + no-recovery + no-forewarning is a net_new UI bug.

## Impact

An operator trying to delete a data source that is still in use clicks Delete, the modal spins, then sticks open with a cryptic toast and no way forward except reloading the page. The most-destructive affordance on the Management -> Data Sources screen gives the worst feedback. Combined with the REPLACE-not-merge edit semantics on the same screen, the data-source lifecycle UI is hostile precisely where it should be most careful.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: surface the error inline + reset `isLoading` + keep the modal open on rejection (`ConfirmationDialog.tsx:28-34`); **or** add a pre-flight cascade check / disabled-with-tooltip Delete + an `additionalContent` forewarning on `DataSourceItem`. Distinct from PLT-087 (backend cleanup) and PLT-038 (dialog text).
