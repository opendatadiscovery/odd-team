## Description

`session.provider` is matched by exact string literal. A value that is neither `IN_MEMORY`, `INTERNAL_POSTGRESQL`, nor `REDIS` (a typo like `POSTGRES`, `postgresql`, `IN-MEMORY`) matches no provider branch — the platform wires **no session repository bean**, emits **no WARN**, and the operator's intended provider silently does not take effect.

Mechanism in `SessionConfiguration` (`SessionConfiguration.java`):

- The non-Redis providers are gated by `SpringWebSessionCondition`, whose `matches(...)` returns `"INTERNAL_POSTGRESQL".equals(sessionProvider) || "IN_MEMORY".equals(sessionProvider)` — exact-literal equality (`SessionConfiguration.java:55-57`). A misspelled value makes this condition false, so the `SpringWebSessionConfiguration` block (which contributes the `INTERNAL_POSTGRESQL` and `IN_MEMORY` repository beans) is not registered.
- The Redis branch is `@ConditionalOnProperty(prefix = "session", name = "provider", havingValue = "REDIS")` (`SessionConfiguration.java:62`) — again only the exact literal `REDIS` activates it.
- There is no `@ConditionalOnProperty(..., matchIfMissing = ...)` fall-through, no `else` branch, and no validation/`WARN` for an unrecognised value. The shipped default is `session.provider: IN_MEMORY` (`application.yml:30`), so an **unset** value resolves to IN_MEMORY by config default — but a **misspelled** value is unrecognised and gets no bean at all.

**How it misleads an operator.** An operator who sets `SESSION_PROVIDER=POSTGRES` (intending `INTERNAL_POSTGRESQL`) gets a platform that boots cleanly with no error and no warning. They believe sessions are persisted to PostgreSQL; in reality the typo silently broke the wiring, and the failure only surfaces later as a downstream session symptom (e.g. an authentication/session resolution failure, or sessions not persisting across restart) far from the misconfigured key — exactly the silent-misconfig class the workspace exists to catch. The fix is documentation: tell operators the value is matched literally and that a typo fails silent, so they verify the effective provider after deploy.

This is a different config family from PLT-089 (a separate session-config upstream item); the gap here is specifically the absent fail-fast on an unrecognised `session.provider` literal.
