## Description

`odd-platform-specification/openapi.yaml` declares only success responses for its operations; no endpoint
documents its error responses (400 `USR001`, 404 `USR002`, 400 `USR003/004`, 500 `SYS001`, the shared
`ErrorResponse` schema). The runtime error contract is real and centralised (`ControllerAdvice` +
`ErrorCode`, ADR-0007) but invisible in the published contract — generated clients and API consumers have
no typed error model.

Surfaced while fixing #1762: making `POST /api/policies` return 400 on invalid policy JSON would ideally be
reflected in the spec, but adding a 400 to that one operation while every other operation declares none
would be inconsistent — so it was deferred to this platform-wide item rather than done piecemeal.

## Suggested approach

Add a shared, referenceable error-response component (the existing `ErrorResponse` schema + a small set of
`responses:` like `BadRequest`/`NotFound`/`ServerError`) and reference it from operations, ideally driven
from the actual `ControllerAdvice` mapping so the spec and code stay in sync. Scope/sequencing is a
maintainer call (it touches the generated BE + FE clients). This is hygiene/completeness, not a runtime bug.

## Why it matters

The error contract is part of the public API; documenting it gives consumers a typed error model and keeps
the generated clients honest. It also makes future per-endpoint error-status changes (like #1762) a spec
change, not just a code change.
