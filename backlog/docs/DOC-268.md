## Description

`authorization/roles.md` is 25 lines and carries two inconsistencies after batch-12 (DOC-207..224) shipped:

**Inconsistency 1 — internally redundant admonition.** Lines 19-25 say (paraphrased):

> When user is associated with owner ..., he will inherit owner roles, ignoring previously assigned user roles, e.g. user was logged in and got ADMIN role. After that he associated himself with owner, which has Data Engineer role. He will lose his admin privileges and have Data engineer role.
>
> {% hint style="warning" %}
> Be careful and don't associate user with admin role with non-admin owner. You need to create owner with admin role first and then associate your admin user with this owner.
> {% endhint %}

The "Be careful" hint is a special case of the immediately-preceding precedence rule — it doesn't add new information, just emphasises the precedence's most-painful consequence. A reader who already understood line 21 finds the hint at line 24 redundant; a reader who didn't understand line 21 finds the hint adds no clarification ("Be careful" assumes the precedence is already understood).

**Inconsistency 2 — silent on the admin direct-bind path.** The hint's recommendation is "create owner with admin role first and then associate your admin user with this owner." After batch-12, the recommended admin path is to use the **Create association** button (Management → Associations header, `OWNER_RELATION_MANAGE`-gated — see [user-owner-association.md → Creating a binding directly](user-owner-association.md#creating-a-binding-directly-create-association)) which:
  - Does not require the admin to be signed in as the target user
  - Bypasses the request-then-approve workflow entirely
  - Is the natural admin setup path

The current roles.md hint implicitly assumes only the self-request path exists, which is the user-side path. An admin reading roles.md to learn how to set up an initial admin binding doesn't see the dedicated admin-direct-bind affordance.

**Inconsistency 3 — the "Be careful" hint orphans the role-attachment surface.** Roles.md says nothing about HOW to attach a role to an Owner (the Management → Roles surface? the Management → Owners surface? both?). The Owner entity in the catalog has a roles array, and the role-attach affordance lives somewhere — but roles.md doesn't say where. The reader following the hint's recommendation ("create owner with admin role first") has no pointer to where the role-attach happens.
