# RolesList — semantic understanding

## understanding

The Management → Roles tab — the SPA route at `/management/roles` (`ManagementRoutes.tsx:112-125`) — implemented by a 137-line functional component (`RolesList.tsx:27-134`) that lists every Role visible to the signed-in user, with infinite-scroll pagination (`size=100`), a debounced search box (500 ms), a per-row Edit / Delete affordance via `RoleItem`, and a "Create role" button conditionally rendered through `<WithPermissions permissionTo={Permission.ROLE_CREATE}>` (`RolesList.tsx:92-102`). On mount the component dispatches `fetchRolesList({page: 1, size: 100})` (`RolesList.tsx:40-42`) — which calls `GET /api/roles` → `RoleController.getRolesList` → `RoleServiceImpl.list`, where a server-side principal-aware fork either (a) returns only the signed-in user's attached roles when the caller is non-ADMIN, or (b) returns the full paginated role catalog when the caller IS ADMIN (`RoleServiceImpl.java:40-47` — the `noneMatch UserProviderRole.ADMIN` branch). The component is UNAWARE of this fork; it renders whatever payload the API returns. The route itself is wrapped in `<WithPermissionsProvider allowedPermissions={[ROLE_CREATE, ROLE_UPDATE, ROLE_DELETE]}>` (`ManagementRoutes.tsx:115-122`), but per `WithPermissionsProvider.tsx:30-38` the provider only INJECTS permission context — it does NOT gate route rendering — so any signed-in user reaching `/management/roles` sees the page; the only thing permission-gated client-side is the Create / Edit / Delete buttons.

## downstream_side_effects

What this component / thunk chain causes when invoked — the outbound graph.

- **HTTP request fired**: `GET /api/roles?page={p}&size=100&query={q}` (via `roleApi.getRolesList`). Server-side resolves to `RoleController.getRolesList` (RoleController.java:28-34) → `RoleServiceImpl.list` (RoleServiceImpl.java:40-47) → either (a) `filterUserRoles(currentUserRoles, query)` for non-ADMIN callers (in-memory filter over the caller's own attached roles), or (b) `roleRepository.listDto(page, size, query)` for ADMIN callers (paginated CTE over the full role catalog). Per batch-N ReactiveRoleRepositoryImpl sidecar, the listDto query is a CTE: first paginate ROLE by ID ASC + soft-delete filter, THEN LEFT JOIN role_to_policy + policy and aggregate via `jsonArrayAgg(POLICY.*)`. **CRITICAL DOWNSTREAM DEPENDENCY**: the JOIN against POLICY has NO `policy.deleted_at IS NULL` predicate — soft-deleted Policies bound via surviving `role_to_policy` edges WILL appear in the rendered chips of each `RoleItem.policies.map(...)`.
- **Redux state mutation**: `state.roles` via `rolesAdapter.setAll` (page=1) or `setMany` (page>1); `state.roles.pageInfo` set wholesale (roles.slice.ts:24).
- **NO write side-effects on the LIST path** — this page is read-only at the network layer; writes happen via the embedded RoleForm + RoleItem (createRole / updateRole / deleteRole thunks).
- **Create-role write side-effect (via RoleForm.tsx:62)**: `POST /api/roles` body `{name, policies: [{id}]}` → `RoleController.createRole` (RoleController.java:19-25) → `RoleServiceImpl.create` (RoleServiceImpl.java:50-61) → INSERT `role` + INSERT N `role_to_policy` rows + re-read RoleDto. **No client-side validation for the predefined-name asymmetry** — batch-E sidecar bugs_limitations_corner_cases[0] surfaces that `RoleServiceImpl.create` has NO `UserProviderRole.values()` check, unlike `.update` and `.delete`. The UI provides NO protection either: a user typing 'Administrator' or 'User' into the new-role name field will succeed if the seeded rows have been soft-deleted via direct SQL (the partial unique index `role_name_unique WHERE deleted_at IS NULL` permits it). The RoleForm `Input` has `rules={{required: true, validate: value => !!value.trim()}}` (RoleForm.tsx:85) — no length cap, no charset filter, no case-insensitive predefined-name reject.
- **NO analytics event emitted** — verified by grep on `mixpanel|amplitude|segment|gtag|posthog|track\(` across `<odd-platform-ui>/src` returning ZERO matches.
- **NO toast on successful list fetch** — the fetchRolesList thunk's `setSuccessOptions` is `{}` (roles.thunks.ts:24).
- **Toast on successful create / update / delete** — `createRole` emits `Role {name} successfully created.` (roles.thunks.ts:31-32); `updateRole` emits `Role {name} successfully updated.` (line 42-43); `deleteRole` emits `Role successfully deleted.` (line 56-57). - **hot_paths**:

## Maintainer notes

This sidecar is the UI tier of the F-006 (P-09:F-001 Role-Based Access Control) feature flow, closing the 5-sidecar arc started by RoleController batch E + PolicyController batch E + ReactivePolicyRepositoryImpl batch H + ReactiveRoleRepositoryImpl batch N + (now) RolesList batch Q. The arc spans controller → service → repository → UI for both Policy and Role halves of the RBAC mutation surface.

The CRITICAL question (a) — "does the role list include soft-deleted roles?" — ANSWER: **NO at the role-table level, YES at the policy-table level inside each role's chip list**. Soft-deleted ROLES are auto-filtered by `ReactiveAbstractSoftDeleteCRUDRepository.listCondition` override (per batch-N invariants[0]). Soft-deleted POLICIES bound to a live role STILL appear in `RoleItem.tsx:42-48`'s chip list (the F-006 drift_class `role_repo_left_join_no_policy_deleted_at_filter_mirror` UI manifestation).

The CRITICAL question (b) — "admin-only?" — ANSWER: **NO at the page level, YES-ish at the data level**. The page is reachable to any signed-in user (the WithPermissionsProvider injects context but does NOT gate the route). Server-side `RoleServiceImpl.list` returns a principal-aware filtered set — non-ADMIN callers see only their own attached roles. The UI does NOT communicate this filter, creating a UX defect (header reads `<N> roles overall` where N is the filtered count, with no 'showing N of M' messaging).

The CRITICAL question (c) — "does the role-create form prevent reserved-name collisions like `Administrator`/`User`?" — ANSWER: **NO**. The RoleForm declares only `required + validate: trim` (RoleForm.tsx:85). No predefined-name reject. No length cap. No charset filter. Combined with the partial unique index + `RoleServiceImpl.create`'s absence of `UserProviderRole.values()` check, this UI is the viable exploit path for the F-006 `role_create_administrator_name_asymmetry_mirror` drift.

The CRITICAL question (d) — "useEffect dep-array LSN-017 shape — multiple fetches per page-open?" — ANSWER: **NO**. The useEffect at `RolesList.tsx:40-42` has deps `[fetchRolesList, query]`, BUT the dispatch is GUARDED by `if (!query)`. The `fetchRolesList` reference is stable (Redux thunk identity) so the effect's dep change is driven only by `query`. The effect fires on initial mount (query starts at `''`) AND whenever query transitions back to `''`. It does NOT fire on every keystroke. The LSN-017 anti-pattern (where `details.status?.status` was both fetched-by-the-effect and IN the deps array) does NOT apply here because the deps array contains only the thunk reference and the local state `query` — neither is mutated by the fetch response. **One fetch per page-open under normal usage.**
