> **Re-scoped 2026-05-30.** The original draft claimed an operator who *deletes a policy through the UI* leaves bound roles still granting. That is **wrong**: policy deletion is cascade-blocked while the policy is attached to any role (`PolicyServiceImpl.delete` throws `CascadeDeleteException("Policy is attached to a role")`), so the "delete via UI -> silent grant" path is unreachable. The genuine issue is narrower and is defense-in-depth - described below. Paired doc item `backlog/docs/DOC-314.md` now documents the actual behaviour (delete is blocked while bound).

## What

Two grant-path omissions combine to let a **soft-deleted** policy still grant permissions, by a path that does **not** go through the UI policy delete:

1. **The grant/authorization path does not filter `deleted_at`.** `ReactivePolicyRepositoryImpl.getRolesPolicies` (the query behind `PolicyServiceImpl.getCurrentUserPolicies`, consumed by the permission extractors) joins `POLICY`  join  `ROLE_TO_POLICY` with no soft-delete predicate, whereas the list/get path inherits `WHERE deleted_at IS NULL` from the soft-delete base class:

```java
// ReactivePolicyRepositoryImpl.getRolesPolicies, method @ L27-39 (join+where @ L32-35), re-read @ HEAD
final SelectConditionStep<Record> query = DSL.select(POLICY.fields())
    .from(POLICY)
    .join(ROLE_TO_POLICY).on(ROLE_TO_POLICY.POLICY_ID.eq(POLICY.ID))
    .where(ROLE_TO_POLICY.ROLE_ID.in(roleIds));   // no POLICY.DELETED_AT.isNull()
```

(Note: `ReactivePolicyRepositoryImpl` extends `ReactiveAbstractSoftDeleteCRUDRepository`, whose `idCondition`/`listCondition` add `deleted_at IS NULL` via `addSoftDeleteFilter` - so `get`/`list` are filtered, but `getRolesPolicies` is a hand-rolled query that bypasses those conditions. The asymmetry is real and verified.)

2. **The role->policy attach path does not validate that the policy is live.** `ReactiveRoleToPolicyRepositoryImpl.createRelations` (used by role create/update) inserts `ROLE_TO_POLICY` rows for whatever policy ids the form supplies, with no check that each policy exists / is not soft-deleted.

**Reachable sequence** (note: NOT the UI delete path, which is cascade-blocked):
- Soft-delete an **unbound** policy `P` - allowed, because `isPolicyAttachedToRole(P)` is false at that moment.
- Create/update a role `R` with `policies: [P.id, ...]` via the API -> `createRelations` inserts `ROLE_TO_POLICY(R, P)` even though `P` is soft-deleted.
- Any user holding `R` -> `getRolesPolicies([R])` returns the soft-deleted `P` -> its permissions are granted.

The UI never offers a deleted policy in the role policy-picker (that list is soft-delete-filtered), so this requires a **raw API call** referencing a known-deleted policy id. The actor must already hold role-management permission - so the practical impact is **obscurity, not privilege escalation** (an admin who can attach policies can already grant permissions directly). The real harm is a permission that is **invisible in the Policies tab yet live in the resolver** - a correctness / least-privilege-hygiene gap, not an exploitable escalation.

## User-facing impact

Static-trace-verified end-to-end (both the grant query and its permission-extractor consumers read against source HEAD); not driven on a live stack. Auth mode: RBAC permissions are only meaningful under a **non-DISABLED** auth mode (LOGIN_FORM / OAUTH2 / LDAP) where roles and policies actually gate requests; under the shipped `DISABLED` default there is no policy resolution at all, so this defect is inert. Under an enabled mode:

- The grant path (`getRolesPolicies`) is reached on every authorization decision via `ManagementPermissionExtractor` / `AbstractContextualPermissionExtractor` (both call `getCurrentUserPolicies` -> `getRolesPolicies`), so a `ROLE_TO_POLICY` row pointing at a soft-deleted policy **does** resolve that policy's permissions at runtime - confirmed by reading the two extractors, not extrapolated.
- The reachability is narrow and admin-gated: the actor must hold role-management permission and must issue a **raw API role create/update referencing a known soft-deleted policy id** (the UI policy-picker is soft-delete-filtered, so the UI never offers it). An admin who can attach policies can already grant permissions directly, so this is **least-privilege hygiene / auditability, not privilege escalation**: the live permission is invisible in the Policies tab yet active in the resolver.
- The originally-claimed "delete a policy in the UI -> bound roles still grant" path is **unreachable** (correctly re-scoped in the draft): `PolicyServiceImpl.delete` cascade-blocks while the policy is attached to any role (`CascadeDeleteException("Policy is attached to a role")`, verified L89-92).

Remaining check before a definitive runtime claim: drive an enabled-auth stack, soft-delete an unbound policy, attach it to a role via the API, and assert the holder resolves its permissions (the two tests the Suggested fix already enumerates).

## Why it matters

A soft-deleted policy that still resolves permissions is invisible in the Policies tab but live in the permission resolver - an operator auditing "what does this role grant" via the UI cannot see it. It is reachable only by re-attaching a deleted policy id through the API (admin-level), so it is not a privilege-escalation vector, but it is a real grant-path correctness defect and a least-privilege-hygiene surprise. Fixing it also makes the grant path consistent with the list path and with the cascade-delete guards already enforced for namespaces and owners.

## Suggested fix

- Add `POLICY.DELETED_AT.isNull()` to the `getRolesPolicies` join (and audit any other permission-resolution query that joins `POLICY` / `ROLE_TO_POLICY` for the same omission).
- Validate policy liveness in the role->policy attach path (`createRelations` / role create+update): reject or ignore `ROLE_TO_POLICY` inserts that reference a non-existent or soft-deleted policy.
- Add tests: (a) soft-delete an unbound policy, attach it to a role via the service, assert the role does **not** resolve its permissions; (b) assert the attach path rejects a deleted policy id.
