## What

The platform stores operator-authored Markdown verbatim (no `Jsoup.clean`, no `Encode.html`, no length cap, no allowlist) and renders it via `@uiw/react-md-editor`'s `MDEditor.Markdown` (non-editor branch at `Markdown.tsx:113-124`). Raw embedded HTML **is** parsed and rendered, and there is **no `rehype-sanitize` / no app-level allowlist policy** - but the mechanism is not what the original revision claimed (corrected 2026-06-10; see ## How discovered). The pattern spans 6 surfaces. Surfaces 1-3 share `Markdown.tsx` as a single SPA-tier fix anchor. Surfaces 4-6 have separate fix anchors and live on companion issues.

**How raw HTML gets rendered (verified 2026-06-10 by tracing the installed deps).** `Markdown.tsx` passes NO `rehypePlugins` prop. `@uiw/react-markdown-preview@4.2.2` (the package behind `MDEditor.Markdown`, via `react-md-editor@3.25.6`) defaults `skipHtml: true` and - counterintuitively - **pushes `rehype-raw` into the plugin list when `skipHtml` is true** (`react-markdown-preview/lib/preview.js:40-41, 68-70`). `react-markdown@8.0.7` runs `remark-rehype` with `allowDangerousHtml: true` (`react-markdown/lib/react-markdown.js:89-92`), so `rehype-raw` parses operator HTML into real element nodes. There is no sanitizer in the chain.

## User-facing impact

WHO: any authenticated user with description/definition-edit permission is the author; any user who later views that entity Overview / dataset-field / term page is the victim. WHAT they do: paste HTML into a Markdown description and save; the stored string is rendered to every later viewer via `Markdown.tsx`.

- **Static trace consistent, partially settled:** raw HTML IS parsed and rendered (no sanitizer in the chain - verified by tracing `react-markdown-preview@4.2.2` + `react-markdown@8.0.7` deps 2026-06-10). The obvious vectors are blocked by code structure I fully settled: `<script>` is inert under React; string `onerror`/`onclick` are not attached as handlers; standard `<a href="javascript:...">` is rewritten to `javascript:void(0)` by react-markdown's `uriTransformer`.
- **NOT driven - static trace only, user_facing_verified: false:** whether a viewer's browser actually executes attacker script via the residual classes (`<iframe src=javascript:>`, SVG `<animate onbegin>`/`<set>` event attributes, and a residual `TermLink` href path — precise mechanism held pre-disclosure under GHSA-mf43-2636-9289 / CTRIB-020) is unmeasured. The exact remaining check: stand up the stack, save each payload class as an entity description, open the Overview page as a second user, and observe whether script runs. Until then this is a missing-defense-in-depth posture, not a confirmed stored XSS - which is why severity is medium, not high, and `user_facing_verified` stays false.

No claim here is "the user sees XSS execute"; the settled facts are the absence of a sanitizer and the specific barriers that exist, and the residual surface is explicitly labelled not-driven.

## Defensive partial-mitigation envelope (verified 2026-06-10)

There is no `rehype-sanitize` and no server CSP (grep of `odd-platform-api/src/main/java` for `Content-Security-Policy`: zero hits). The barriers that DO exist are library/framework defaults, not an auditable app-layer XSS policy, and they block the obvious vectors but not all:

- **`allowElement` allowlist (weak).** `react-markdown-preview` passes `allowElement = (el) => /^[A-Za-z0-9]+$/.test(el.tagName)` (`preview.js:60-66`, applied by `react-markdown/lib/rehype-filter.js:24-65`). This only strips tags whose name is non-alphanumeric (e.g. hyphenated custom elements). It **allows** `script`, `img`, `svg`, `iframe`, `animate`, `a`, etc. - it is not an XSS filter.
- **React does not execute DOM-inserted `<script>`.** `<script>` rendered via `React.createElement` is inert (browser behaviour for reconciler-inserted scripts). Real, not happy-accident.
- **React's typed event system blocks string event handlers.** A raw `onerror="..."` / `onclick="..."` becomes a string-valued prop; React refuses to attach a string as a listener, so `<img src=x onerror=...>` does **not** fire. Real, not happy-accident.
- **react-markdown's default `uriTransformer` neutralises `javascript:` on `a` href** (`uri-transformer.js:44` rewrites it to `javascript:void(0)`) - BUT `Markdown.tsx`'s custom `TermLink` has a residual code path that can read a **raw** `node.properties.href` (`Markdown.tsx:50,54,66`) rather than the transformed prop, partially re-exposing an un-sanitised URL. (The precise branch + trigger condition are held pre-disclosure under GHSA-mf43-2636-9289 / CTRIB-020 until 0.28.0.)

**Genuinely unmeasured (need a live payload drive):** element tags `allowElement` permits whose attributes neither React's event system nor `uriTransformer` neutralise - `<iframe src="javascript:...">`, `<svg><animate onbegin=...>`/`<set>` SVG event vectors, `<style>` exfiltration, and the residual `TermLink` href path above. These are the residual stored-XSS surface; none is confirmed to execute without a runtime drive.

## How to reproduce (surface 1 - entity description)

1. As an authenticated user with `DATA_ENTITY_DESCRIPTION_UPDATE`, navigate to any entity's Overview tab.
2. Click "Edit" on the Description panel. The MDEditor opens.
3. Paste a raw-HTML payload (the obvious textbook vectors, or any of the unmeasured vector classes above; literal payloads held pre-disclosure under GHSA-mf43-2636-9289 / CTRIB-020).
4. Save. The PUT body is stored verbatim via `setInternalDescription`.
5. Read-back via `GET /api/dataentities/{id}` returns the verbatim string.
6. UI Preview renders via `Markdown.tsx` with `rehype-raw` active (library default) and no sanitiser. Outcome depends on the vector class: `<script>`, `<img onerror=...>` and standard `<a href="javascript:...">` are blocked by React + `uriTransformer` (verified static trace); `<iframe src=javascript:>`, SVG event attributes, and the residual `TermLink` href path are unmeasured and need a live drive to confirm.

## Suggested fix

**Option A (recommended) - SPA-tier hardening at `Markdown.tsx:113-124`. NOT a one-liner - plugin ORDER is the trap.** The library auto-appends `rehype-raw` AFTER any user-supplied `rehypePlugins` (`preview.js:59,68-70`), so naively passing `rehypePlugins={[rehypeSanitize]}` runs sanitize BEFORE raw - it sees opaque `raw` string nodes, does nothing, and the unsanitised HTML is then parsed. The correct fix takes control of the order:

```tsx
import rehypeRaw from 'rehype-raw';
import rehypeSanitize from 'rehype-sanitize';
// on the non-editor <MDEditor.Markdown>:
skipHtml={false}                       // stop the library auto-pushing rehypeRaw
rehypePlugins={[rehypeRaw, rehypeSanitize]}   // raw THEN sanitize - order is load-bearing
```

Additionally fix `TermLink` (`Markdown.tsx:49-69`) to render the transformed/validated href rather than raw `node.properties.href`, so the `terms` branch cannot re-expose a `javascript:` URL. This closes surfaces 1-3 because all three render via this component. Surface 4 (Query Examples - separate MDEditor.Markdown call site) needs the equivalent fix on PLT-018; surface 5 (Lookup Tables - verbatim Char render) needs `Encode.html` at storage on PLT-019; surface 6 (Slack mrkdwn) needs `MrkdwnUtils.escape` at `SlackMessageGenerator.markdownText:77` on PLT-016.

**Option B - write-time `Jsoup.clean` at the three storage call sites.** More invasive (3 files) and incurs storage normalisation cost; rejected in favour of Option A for leverage.

The fix should ship with a `rehype-sanitize` allow-list tuned to the platform's actual Markdown corpus - start with the package default + ODD's `[[Namespace:Term]]` term-mention syntax (see DOC-177 / F-002b) + the standard Markdown subset.

## Operator impact

- Stored XSS class is currently mitigated only by happy-accident browser + React behaviour.
- Security-conscious operators have no documented framework today for assessing the risk (DOC-187 closes the doc-side caveat).

## How discovered

Surfaced during Mode B batch-10 triage (2026-05-27, finding F-004b) as the canonical 6-surface stored-XSS anchor. **Corrected 2026-06-10 (user-facing verification sweep): was "renders via `Markdown.tsx:113-124` with `rehype-raw` enabled in a `rehypePlugins` configuration block and `rehype-sanitize` NOT configured ... one config-line change closes all three"; actually `Markdown.tsx` passes no `rehypePlugins` at all - `rehype-raw` is active because `@uiw/react-markdown-preview@4.2.2` defaults `skipHtml: true` and pushes `rehype-raw` for that case (`preview.js:40-41, 68-70`), and the "one-line" fix is ineffective because the library appends `rehype-raw` after user plugins, so `rehype-sanitize` must be ordered explicitly after a manually-supplied `rehype-raw` (`skipHtml={false}` + `rehypePlugins={[rehypeRaw, rehypeSanitize]}`).** Verification also settled that the obvious vectors (`<script>`, `<img onerror>`, standard `<a href="javascript:">`) are blocked by React + `uriTransformer`, so the confirmed-stored-XSS framing was downgraded to a missing-sanitizer-policy hardening gap (severity high -> medium; `user_facing_verified` stays false pending a payload drive of the residual `<iframe>`/SVG/`TermLink` classes). The real defect - no `rehype-sanitize`, no CSP, a near-useless `allowElement` allowlist, and a `TermLink` raw-href bypass - survives.
