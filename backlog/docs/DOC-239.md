## Description

The live `enable-security/authentication/disabled-authentication` page (WebFetched 2026-05-27) contains exactly ONE warning sentence: "**DO NOT** use this method in your production environment!" — and is **silent on every concrete surface** an operator would need to enumerate to understand what they are exposing. The page tells operators a verdict without giving them the surface area. F-085 + F-119 + F-122 surface five anonymously-reachable mechanisms under DISABLED that compound: an attacker on the network can confirm-ODD + version + auth-mode + credential-schema + obtain ADMIN-with-all-permissions in roughly FOUR unauthenticated GET requests.

**Facet 1 — Synthetic admin with DYNAMIC blast radius (F-085a, HIGH→CRITICAL).** `IdentityController.java:23-33` fires `.switchIfEmpty(Mono.just(... dummyOwner()))` when the principal Mono is empty (DISABLED-mode condition). `dummyOwner` constructs `new Identity().username("admin").permissions((Arrays.asList(Permission.values())))` — `Permission.values()` dynamically expands to whatever enum values exist. **Adding a new Permission to the OpenAPI spec AUTOMATICALLY enters the DISABLED-mode admin grant**, with no code change in the controller. ZERO authentication + ZERO audit + DYNAMIC blast radius. The SPA's `WithPermissionsProvider` trusts the whoami response verbatim — every Permission-gated UI control unlocked.

**Facet 2 — Auth-mode fingerprint in ONE call (F-085b, MEDIUM→HIGH).** `whoami` is NOT in `WHITELIST_PATHS` (`SecurityConstants.java:95-96`). Under LOGIN_FORM the SecurityWebFilterChain returns 302; under OAUTH2/LDAP it returns 401; under DISABLED it returns 200+`admin`. Four response shapes — 200+admin → DISABLED; 302 → LOGIN_FORM; 401 → OAUTH2/LDAP — are themselves the fingerprint. Anonymous reconnaissance discovers the deployment's active auth-mode without needing valid credentials.

**Facet 3 — `/api/appInfo` fingerprint (F-119a, HIGH→CRITICAL).** `AppInfoController.java:18-29` has no `@PreAuthorize`. Under DISABLED's `.anyExchange().permitAll()` (`DisabledAuthSecurityConfiguration.java:13-18`), `/api/appInfo` returns both the precise platform version (CVE-scoping) and the auth-mode value to any unauthenticated caller. The `authType` field name is ODD-specific (no other product ships that exact shape) — passive scanner can confirm-ODD + version + auth-mode in ONE GET.

**Facet 4 — `/actuator/**` whitelisted (F-122a, HIGH→CRITICAL).** `SecurityConstants.WHITELIST_PATHS` contains `/actuator/**` — reachable BEFORE auth in EVERY mode, not just DISABLED. `application.yml:226-242` enables `management.endpoint.env.enabled=true` + `show-values=WHEN_AUTHORIZED`. An attacker scraping `/actuator/env` learns the SCHEMA of configured credentials: which OAuth2 providers are wired (Google/Azure/Cognito key prefixes), whether LDAP is configured, the JDBC URL host:port:dbname. (Cross-reference: DOC-242 covers this as an operator-config caveat on odd-platform.md; this page covers it as one of the reachable surfaces under DISABLED.)

**Facet 5 — `admin` lowercase vs `ADMIN` uppercase reserved-username collision (F-085c, LOW→MEDIUM).** `IdentityController.java:32` literal `"admin"` (lowercase) for the DISABLED dummyOwner; `S2sAuthenticationFilter.java:31-34` literal `"ADMIN"` (uppercase) for the S2S filter. Operator-named LOGIN_FORM/LDAP user `admin` (lowercase) collides with DISABLED-mode fallback; operator-named user `ADMIN` (uppercase) collides with S2S filter.

## Correction (2026-05-29, via DOC-308)
The `/actuator/env` facet above states `application.yml` enables `endpoint.env.enabled=true` **with `show-values=WHEN_AUTHORIZED`** and that an anonymous caller learns the JDBC URL `host:port:dbname`. Verified **false** against odd-platform @ `ede5d277`: no `show-values` key is set anywhere (Spring Boot 3.4.10 default `NEVER` applies), so `/actuator/env` masks every property **value** — including `spring.datasource.url` — for all callers. The real unauthenticated exposure is the **configuration-key schema** (which keys / property sources exist), not credential values or the JDBC URL value. The published correction shipped via **DOC-308** (`odd-platform.md`). Do not re-propagate the `WHEN_AUTHORIZED` / "learns the JDBC URL host:port:dbname" framing.

## Editorial follow-up (2026-06-16, CTRIB-018 review) — the shipped "Reserved usernames" prose contradicts itself on the admin/ADMIN collision

The 2026-06-16 editorial audit found the **shipped** `disabled-authentication.md` "Reserved usernames" section (`:51-53`) — the section this item authored — has drifted into an internal contradiction. This item is `done`; the live page needs a small correction so its prose matches the (correct) mechanism this item's own AC and Facet 5 described.

**The contradiction (audit finding F5).** `disabled-authentication.md:53` states both:
1. "The platform's user-to-owner mapping table compares names **case-sensitively**." (true)
2. "Avoid provisioning operator-managed users with either of these literal names ... **a user named `admin` or `ADMIN` collides with the synthetic identities**" — phrased as if a single real user could collide with both synthetic principals.

Those two clauses are inconsistent. With **case-sensitive** matching: lowercase `admin` collides with the **DISABLED** synthetic identity only (`IdentityController.java:32` literal `"admin"`); uppercase `ADMIN` collides with the **S2S** filter identity only (`S2sAuthenticationFilter.java:31` literal `"ADMIN"`). A single real user can collide with **at most one** of the two synthetics, never "the synthetic identities" (plural) as the current prose implies. The sibling page `s2s.md:84` gets it right (uppercase `ADMIN` → S2S only), and this item's **own** Facet 5 / AC (`:48`) state the split correctly — so the live page drifted from its own intended wording during authoring.

**Verbatim passage** — `disabled-authentication.md:53`:
> The DISABLED-mode synthetic identity uses the literal lowercase string `admin`; the S2S authentication filter uses the literal uppercase string `ADMIN`. The platform's user-to-owner mapping table compares names case-sensitively. Avoid provisioning operator-managed users with either of these literal names in `LOGIN_FORM`, `LDAP`, or any OAuth2 provider — a user named `admin` or `ADMIN` collides with the synthetic identities and inherits whatever owner mapping the synthetic principal resolves to.

**Required fix (small):**
- [ ] Correct `disabled-authentication.md:53` to pair each literal with its single synthetic, consistent with case-sensitivity and with `s2s.md:84`: a user named **`admin` (lowercase)** collides with the **DISABLED** synthetic identity; a user named **`ADMIN` (uppercase)** collides with the **S2S** filter identity — not "either name collides with the synthetic identities". (The `:59` migration bullet — "existing `Owner` rows whose `OIDC_USERNAME` matches the literal `admin` or `ADMIN`" — should likewise be phrased so each maps to its own synthetic, or kept generic without implying a single user hits both.)
- [ ] Confirm the two literals against code at fix time (`IdentityController.java:32` lowercase `admin`; `S2sAuthenticationFilter.java:31` uppercase `ADMIN`) and confirm the mapping comparison is still case-sensitive.
- [ ] Live-site verify the corrected "Reserved usernames" prose on `https://docs.opendatadiscovery.org/configuration-and-deployment/enable-security/authentication/disabled-authentication`.
