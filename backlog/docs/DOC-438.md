## Description

`Features.md:146` frames `/api/datasets/{id}/sla` as the endpoint "downstream BI reports import directly" to get the dataset-level SLA colour:

> "...aggregated into a single dataset-level **SLA colour** (Green / Yellow / Red) that downstream BI reports import directly via the `/api/datasets/{id}/sla` endpoint."

This is the same PNG-vs-JSON imprecision that DOC-169 already corrected on the dedicated sub-page. Per the OpenAPI spec, `getSLA` at `/api/datasets/{data_entity_id}/sla` returns **`image/png`** (a pre-rendered SLA **badge**) — it is not a machine-readable colour/data import. The JSON report a BI tool would consume programmatically is `getDatasetSLAReport` at the sibling `/api/datasets/{data_entity_id}/sla_report` (returns `application/json` → `DataSetSLAReport`).

How it misleads an operator: a BI engineer reading the parent Features landing page is told to "import" SLA colour via `/sla`, follows that to a PNG badge (not the structured `DataSetSLAReport` they need to parse the colour/severity weights), and is sent to the wrong integration. The sub-page (`sla-statuses.md`) and the section index (`data-quality.md:17`) already get this right (both list the two endpoints with their content types); only the top-level Features.md pointer still carries the old conflation. This is code-doc accuracy drift on a published page — actively misleading, even if low-severity because the corrected sub-pages exist one click away.
