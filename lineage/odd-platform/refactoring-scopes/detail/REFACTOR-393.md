- **REFACTOR-393** (NEW 2026-05-19O): GitHub outbound calls have NO retry, NO timeout, NO rate-limit handling. GitHub's 5000-req-per-hr rate limit can be exhausted by a high-traffic login surface; secondary rate limits trigger on abuse. A 403/429 response surfaces as a hard login failure with no fallback to cached membership signal
  - **Category**: missing-retry
  - **Surfaced by**:
    - `GithubUserHandler.md:bugs_limitations_corner_cases.[5]` (LOW)
    - `GithubUserHandler.md:performance.known_performance_gaps.[0]` (LOW)
  - **Statement**: The two outbound calls in `GithubUserHandler` (`/user/orgs` at lines 76-85 + `/user/teams` at lines 104-113) have no `.retryWhen`, no `.timeout`, no `.onErrorResume`. GitHub's REST API enforces a 5000-req-per-hr rate limit per authenticated token (per-user); secondary rate limits trigger on abuse. A platform deployment behind a shared NAT IP egress (a common enterprise configuration) MAY trip secondary rate limits during high-traffic login surges. A 403 with `X-RateLimit-Remaining: 0` or a 429 surfaces as `WebClientResponseException` propagated to the OAuth2 login flow — the user sees a generic login failure with no actionable signal. NO fallback to cached membership; the prior login's enrichment is not retained. NO `.timeout(...)` configured on the WebClient — relies on Reactor Netty defaults (~60s by default); a GitHub-side hang propagates to the entire login flow.
  - **Evidence**: `GithubUserHandler.java:76-85` (no `.retryWhen` / `.timeout` / `.onErrorResume`) + `GithubUserHandler.java:104-113` (same) + `GithubUserHandler.java:39` (`WebClient.create(...)` with no `.responseTimeout(...)` configuration) + GitHub REST API rate-limit docs (5000/hr authenticated, secondary rate limits for abuse)
  - **Existing-ADR-or-implied-prescription**: ADR-CANDIDATE-135 NEW (GitHub OAuth2 + two-pass HTTP) and the "no-cache stance across auth surface" implicit pattern (per AuthIdentityProviderImpl batch K implicit_adrs[3]) both accept the per-login cost. No comment or commit message defends the absence of retry/timeout; the gap is implementation-omission rather than design-choice.
  - **Proposed remedy**: Add retry-with-backoff for transient failures: `.retryWhen(Retry.backoff(2, Duration.ofSeconds(1)).filter(WebClientResponseException::is5xxServerError))` — retry on 5xx only, NOT on 4xx (don't retry rate-limit failures). Add an explicit `.timeout(Duration.ofSeconds(10))` on each call to bound login latency. Optionally add `.onErrorResume(WebClientResponseException.TooManyRequests.class, e -> Mono.error(new OAuth2AuthenticationException("rate_limit", "GitHub rate limit exhausted; retry in 1 hour")))` for a clearer rate-limit error message.
  - **Severity rationale**: LOW — uncommon (rate-limit exhaustion requires sustained login traffic against a shared NAT IP). When it triggers, the user sees a generic login failure; not security-critical, but operator-debug-hostile.
  - **Suggested backlog grouping**: `OAuth2 hardening sprint` (paired with REFACTOR-390/391/392/394)
