## Description

The live `developer-guides/api-reference` page (WebFetched 2026-05-27) enumerates 9 endpoint groups but is **silent on three families** that are central to the platform's auth + introspection + permission machinery. Two are reachable under DISABLED-mode anonymously (cross-link DOC-239); the third is the read surface for runtime permissions an operator-built API client needs to consult. Third-party API consumers reading the page have no signal that these endpoints exist; SDK consumers compiling from OpenAPI get the contract but readers of the prose reference do not.

**Family 1 — `/api/identity/whoami` (F-085a cross-reference).** `IdentityController.java:23-33` — returns the current Identity (username + permissions) OR the synthetic admin (DISABLED mode). Operator-facing SDKs need to call this on SPA boot to know what permissions the current user has. The API reference does NOT enumerate it. Under DISABLED mode, this endpoint returns `{"username":"admin","permissions":[Permission.values()]}` anonymously — the DOC-239 caveat is the security framing; this DOC-240 is the API-surface enumeration.

**Family 2 — `/api/appInfo` (F-119a cross-reference).** `AppInfoController.java:18-29` — returns platform version + auth-mode + login-form-redirect URL. Used by the SPA on boot to decide which Owner-Association card to show (Overview.tsx:25-27 reads `appInfo.authType`). API consumers building SPA-equivalent client logic need this endpoint. The API reference does NOT enumerate it. Anonymously reachable in DISABLED mode (cross-link DOC-239).

**Family 3 — `/api/resource/{type}/{id}/permissions` + `/api/identity/whoami` (F-090a cross-reference).** The permission read surface is **bifurcated** across two endpoints (contextual + non-contextual) and the bifurcation is undocumented. `PermissionServiceImpl.java:24-27` rejects `MANAGEMENT` (a 4th value in the OpenAPI PermissionResourceType enum) with HTTP 400 USR001 because management-scope permissions live on the COMPLEMENTARY endpoint (`/api/identity/whoami` → Identity.permissions). Third-party clients compiled from openapi.yaml building a 4-way switch over PermissionResourceType + sending `GET /api/resource/MANAGEMENT/0/permissions` receive unexpected HTTP 400 — must read source to discover the actual mechanism. The spec/runtime drift is being fixed in SPC-002; the API reference needs the prose two-endpoint orchestration NOW.

- [ ] A new "## Permission read surface (two-endpoint orchestration)" sub-section explicitly describes the bifurcation:
  - **Contextual permissions**: `GET /api/resource/{type}/{id}/permissions` — for resource-scoped types (DATA_ENTITY, NAMESPACE, TERM). Returns the caller's permissions in the named resource's context. Valid `type` values per code: `DATA_ENTITY`, `NAMESPACE`, `TERM` (NOT `MANAGEMENT`).
  - **Non-contextual / management-scope permissions**: `GET /api/identity/whoami` — Identity.permissions enumerates the caller's MANAGEMENT-scope permissions (Policy/Role CRUD, Lookup Table CRUD, etc.).
  - **Drift admonition (today)**: the OpenAPI spec's `PermissionResourceType` enum lists `MANAGEMENT` as a fourth value, but `GET /api/resource/MANAGEMENT/0/permissions` returns HTTP 400 (USR001 — "Resource type MANAGEMENT does not have context"). This is intentional (the spec exposes the type symbol but the read endpoint rejects it); SPC-002 tightens the spec. SDK code generating MANAGEMENT-typed calls against the runtime needs to route them through whoami instead.

## Implementation Notes

The api-reference page is a reference page, not a tutorial — the goal is enumeration + brief operational note + cross-link to deeper coverage. Resist embedding the security framing of DISABLED here (that's DOC-239's job); just say "behaviour varies by auth mode — see DOC-239" with a link.

The Permission-read-surface section is the most novel content — operators reading this for the first time learn that what looks like a 4-way switch in the OpenAPI spec is actually a 3-contextual + 1-bifurcated-to-whoami architecture. Worth a small ASCII-diagram or a 4-row table making the two-endpoint orchestration explicit.
