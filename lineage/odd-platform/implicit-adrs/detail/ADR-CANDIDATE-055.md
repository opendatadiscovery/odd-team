- **ADR-CANDIDATE-055** (NEW 2026-05-12F): Soft-deleted data entities ARE returned by the detail read by design via `.includeDeleted(true)` on the CTE config + the `DataEntityDetails.isStale` flag — the platform deliberately exposes lifecycle-deleted entities to enable UI rendering of the soft-delete state (so users can see/restore/diagnose deleted entities), in contrast to the list/search/lineage paths which filter soft-deletes out
  - **Category**: promote
  - **Support**: surfaced by 1 sidecar (`getDataEntityDetails`) but cross-validated by the deliberate asymmetry between `getDetails` (`.includeDeleted(true)`), `getDimensions` (`.includeDeleted(true)`), `getDimensionsByIds` (`.includeDeleted(true)`) on the by-id paths vs `getDataEntityList` and search which apply `addSoftDeleteFilter` to exclude deleted rows — the asymmetry IS the deliberate decision
  - **Surfaced by**:
    - `odd-platform__java__DataEntityController__controller-method__getDataEntityDetails.md:implicit_adrs.[1]` ("**Soft-deleted entities ARE returned by the detail view, by design.** `ReactiveDataEntityRepositoryImpl.java:217-225` builds the CTE config with `.includeDeleted(true)`; combined with the CTE select at lines 909-917 which bypasses `addSoftDeleteFilter` when `isIncludeDeleted()` is true. The UI needs this to render lifecycle-deleted entities (so users can see/restore them, see the `isStale` flag, etc.); contrasted with the search/list paths which set `includeDeleted(true)` only for the by-id path (`getDimensions` at line 186, `getDimensionsByIds` at line 208, `getDetails` at line 220). The deliberate-asymmetry is the implicit ADR." — intent_anchor: "the deliberate `.includeDeleted(true)` + the `isStale` response field as a paired contract")
  - **Decision statement**: ODD's data-entity read paths split on soft-delete handling by access mode. The by-id read paths (`getDetails`, `getDimensions(id)`, `getDimensionsByIds(ids)`) set `.includeDeleted(true)` on the CTE config (`ReactiveDataEntityRepositoryImpl.java:186, 208, 220`) — these paths return soft-deleted rows so the UI can render their lifecycle state. The `DataEntityDetails.isStale` field (`DataEntityDetails.java:86`) is the paired contract: the response includes a boolean signal so the UI knows to render the "deleted" badge / disable mutation buttons / surface a restore option. The list / search / lineage / by-class enumeration paths apply `addSoftDeleteFilter` (which adds `WHERE deleted_at IS NULL`) to exclude soft-deleted rows — these paths are the catalog's "active inventory" view. The decision codifies: (a) soft-delete is a state, not a removal — the row stays in the table with `deleted_at != NULL`; (b) by-id reads always succeed if the entity ever existed (even after soft-delete) — enabling "restore" UX; (c) enumeration reads default to active-only — preventing zombie entries in lists; (d) the `isStale` flag in the response is the canonical signal for "this exists but is lifecycle-deleted." Trade-off accepted: any caller with the ID of a soft-deleted entity reads its full payload (REFACTOR-200's centerpiece gap is amplified here — the deleted entity's owner/description/metadata are still readable post-soft-delete).
  - **Wisdom test**: PASS. The deliberate `.includeDeleted(true)` + the paired `isStale` field + the asymmetry with the enumeration paths is the intent anchor. Composes with ADR-CANDIDATE-058 (soft-delete-as-deletion-model) — together they describe the data-entity lifecycle: a soft-deleted entity is queryable by ID with `isStale=true` until the housekeeping TTL fires hard-delete. Structural for every future by-id read on a soft-deletable resource.
