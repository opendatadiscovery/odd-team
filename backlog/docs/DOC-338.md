## Description

This item **reopens / retracts** the soft-delete-TTL conclusion shipped under **DOC-191 / DOC-293 / DOC-GAP-088**. Three published surfaces tell operators that the 30-day hard-delete TTL **"does not fire today"** and that `DELETED` entities **"persist indefinitely / forever,"** i.e. that `DELETED` is a safe long-term parking state. That conclusion is **inverted and dangerous**: it invites operators to leave production data (and its S3/MinIO attachment objects) sitting in `DELETED` on the belief it is permanent, when in fact a default install **does** hard-delete it after 30 days with **no restore path**. (DOC-293 reportedly overrode a verification agent that had reached the correct conclusion — so the inversion is in the tracked record, not just the prose.)

Code truth (verified by reading source):

- **Soft-delete stamps the retention clock.** The CRUD soft-delete (`ReactiveAbstractSoftDeleteCRUDRepository.delete(...)` at `:51-52` / `:62-67`) applies `getDeleteChangedFields()`, and the `DataEntity` override writes `STATUS = DELETED` **and `STATUS_UPDATED_AT = generateNow()`** (`ReactiveDataEntityRepositoryImpl.java:112-113`). The status-switch job and the UI delete both route through this delete path: `DataEntityInternalStateServiceImpl.changeStatusForDataEntities` sends any transition **to** `DELETED` through `softDeleteDataEntities(...)` → `dataEntityRepository.delete(ids)` (`DataEntityInternalStateServiceImpl.java:78-80, 106-109`).
- **Housekeeping hard-deletes on that clock, by default, irreversibly.** `DataEntityHousekeepingJob` computes `deleteTime = now() - data_entity_delete_days` and selects `WHERE STATUS = DELETED AND STATUS_UPDATED_AT <= deleteTime` (`DataEntityHousekeepingJob.java:73-77`), then `deleteDataEntities(...)` issues real `DELETE`s across ~25 child tables — lineage, metadata, ownerships, alerts, messages, metrics, tags, terms, group/parent-group relations, task runs, dataset structure/enum values — and **deletes the entity's attachment objects from S3/MinIO** via `fileUploadService.deleteFiles(...)` (`DataEntityHousekeepingJob.java:142`). The default `data_entity_delete_days` is **30** and `housekeeping.enabled` is **true** (`application.yml:165-170`). There is no restore after the row and its objects are gone.
- **The narrow, real defect is in `applyStatus`, not in the purge.** `DataEntityMapperImpl.applyStatus` sets `pojo.setStatus(statusDto.getId())` first (`:247`) and then guards `setStatusUpdatedAt(now())` with `if (statusDto.getId() != pojo.getStatus())` (`:249-250`) — which is **always false** because `getStatus()` was just set equal to `statusDto.getId()`. So `status_updated_at` is **never refreshed on `applyStatus` transitions** (the non-`DELETED` status changes — `DRAFT` / `STABLE` / `DEPRECATED` / restore — that go through `bulkUpdate(applyStatus(...))` at `:89-92`). This does **not** affect hard-delete retention, because the `DELETED` transition does **not** use `applyStatus` — it uses the `delete()` path that stamps `status_updated_at` correctly.
- **The published "manual cleanup" SQL matches ZERO rows.** Every soft-delete sets `STATUS_SWITCH_TIME = null` (`ReactiveDataEntityRepositoryImpl.java:114`). The recipe in `statuses.md` filters `WHERE status = 5 AND status_switch_time IS NOT NULL AND status_switch_time < now() - interval '30 days'` — since `status_switch_time` is NULL on every soft-deleted row, this matches **nothing**, and the claim that it is "the closest available proxy" is wrong. The correct retention column is `status_updated_at`.

So all three surfaces invert the operator's actual risk. The fix: state that the 30-day purge **is active and irreversible (including object storage)** on a default install; scope the `applyStatus` caveat narrowly; and drop the dead manual-cleanup SQL (or re-key any surviving diagnostic query on `status_updated_at`, not `status_switch_time`).

## Acceptance Criteria

- [ ] **`statuses.md` DANGER block (lines ~31-62) rewritten**: the 30-day hard-delete purge **is active by default and irreversible** — once the housekeeping run hard-deletes a `DELETED` entity older than `data_entity_delete_days`, the row, its ~25 cascading child-table rows, **and its S3/MinIO attachment objects** are gone with no restore path. Remove the "TTL does not fire today / persists indefinitely / persists forever" claim and the "every `DELETED` row stays in the database forever" language.
