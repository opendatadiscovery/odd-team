# TST-065 — one of the two integration rails does not run, and its red is background noise

## What happens

`run-suite.sh` has two rails: the **API-probe rail** (`P-NNN` → `probe-runtime/runner.py`) and the **UI e2e
rail** (Playwright). `feature-complete` declares `P-001` on the probe rail. Every run, the probe rail dies
before executing a single probe:

```
+ (cd .../lineage/_extractor && uv run python probe-runtime/runner.py P-001 --allow-stale)
  Building lineage-extractor @ file:///.../lineage/_extractor
  x Failed to build `lineage-extractor`
  ├─▶ The build backend returned an error
  ╰─▶ Call to `hatchling.build.build_editable` failed (exit status: 1)
      ValueError: Readme path must be within the project directory: ../README.md
```

`run-suite.sh:190` maps that non-zero exit to `api_outcome="FAIL"`, so the run-log line reads
`outcome: api:FAIL e2e:...`.

## Root cause — one line

`lineage/_extractor/pyproject.toml:9`:

```toml
readme = "../README.md"
```

Hatchling refuses a `readme` outside the project directory. The package therefore cannot build in editable
mode, so `uv run` never reaches `runner.py`. This is a packaging-metadata defect, not a probe defect — no probe
has misbehaved; none has executed.

## It is pre-existing and change-independent

`outcome: api:FAIL` appears on **every** recorded `feature-complete` entry across three sessions and three
independently-built SUT images:

| run-log | sessions | `outcome:` |
|---|---|---|
| `run-log/2026-08-31-feature-complete.md` (3 entries) | ctrib062 / ctrib062rework | `api:FAIL e2e:FAIL` on all three |
| `run-log/2026-09-01-feature-complete.md` (2 entries) | review-ctrib062-2 / ctrib062g | `api:FAIL e2e:FAIL` on both |

`lineage/_extractor/pyproject.toml` was last touched by `6203db36` (CTRIB-027) and the graph-query-layer
build-steps — **not** by CTRIB-062. Reproduced first-hand in `review-ctrib062-3`'s own confirmation run
(SUT `odd-platform:odd-team-sut-revctrib0623`, `sha256:82983e32`).

## Why this matters more than one broken probe

1. **A declared rail is silently not running.** `P-001` is registered against `feature-complete` and has never
   executed in any run this workspace has on record. Whatever it asserts is unguarded, and the suite reports
   as if it had been considered.
2. **A permanent red trains readers to ignore the field.** Every `outcome:` line has said `api:FAIL` for days,
   and every human-readable `evidence/notes:` entry discusses only the e2e counts. That is precisely the
   argument the CTRIB-062 re-review made against tolerating an intermittent red (*"the next reader who sees it
   red will assume 'that one's flaky' and stop reading, which is how a suite stops catching things"*) — here it
   is not intermittent, it is constant.
3. **It makes `run-regression.sh`'s exit code meaningless for the api rail**, reinforcing the standing rule to
   read pass/fail counts rather than exit codes (`feedback_canonical_suite_run_is_the_gate`).

## Fix direction

1. **The one-line fix.** Either copy/symlink a `README.md` into `lineage/_extractor/`, or drop the `readme`
   key, or switch to `readme = {file = "README.md"}` with a local file. Verify with
   `cd lineage/_extractor && uv run python probe-runtime/runner.py P-001 --allow-stale --dry-run`.
2. **Then decide what `P-001` should assert**, and whether it still earns its slot — a probe that has not run
   since it was written needs re-blessing (`/probe-run`) before its green means anything.
3. **Make a dead rail loud rather than routine.** `run-suite.sh` should distinguish "the probe rail could not
   START" (a harness defect — fail the run explicitly, with the cause on its own line) from "a probe ran and
   misbehaved" (a real regression signal). As written, both render as `api:FAIL` and neither gets read.

## Not a CTRIB-062 defect

Recorded here so the `api:FAIL` on `review-ctrib062-3`'s confirmation run is **attributed, not unattributed**.
CTRIB-062's regression verdict is read from the e2e rail's pass/fail counts, with `api:FAIL` accounted for by
this item.

## Adjacent, found in the same pass: the run-log corpus is largely unfilled

Filling in this review's own four entries surfaced the scale of the same defect across the corpus:

```
grep -rc "captured values from the probe-run" integration-tests/run-log/*.md   ->  855 unfilled placeholders
```

`run-suite.sh` appends a templated entry per run and leaves `evidence/notes:` as
`<captured values from the probe-run yaml / Playwright report; or the manual observation>` for a human or agent
to fill. **855 entries were never filled** — mostly the 2026-06 per-protocol logs. Those records exist, are
committed, and say nothing; a reader looking for what a protocol actually observed finds the template.

This is the corpus-scale version of the CTRIB-062 re-review's **M10** (which caught three unfilled entries in
one slice). It is recorded here rather than as its own item because the fix is the same harness change: the
Playwright JSON reporter already holds the pass/fail counts and the failing `spec:line` list, so `run-suite.sh`
can write the `evidence/notes:` line itself instead of emitting a placeholder that depends on someone
remembering. Do that once and the class closes for every future run; back-filling 855 historic entries is not
worth it and should not be attempted — mark the pre-2026-08 ones as unreconstructable if anything.

**This review's own four entries (`run-log/2026-09-01-*`) were filled by hand before commit** rather than left
as a 856th through 859th instance.
