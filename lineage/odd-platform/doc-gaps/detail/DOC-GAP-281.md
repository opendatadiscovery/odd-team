  - **Evidence**:
    - **The fail-fast intent** (per sidecar `implicit_adrs` reading): the platform deliberately chose fail-fast at boot rather than skip-and-warn. The author's reasoning (inferable from the explicit error messages): "the registry is loaded as a coherent set or not at all" — partial loads would mean some wizards are unavailable + operators have no signal which ones; full-fail makes the misconfiguration visible.
    - **The architectural trade-off**:
      - **Pro fail-fast**: the operator notices immediately (boot fails); no silent partial-load; the error message names the resource filename for fast root-cause.
      - **Con fail-fast**: a single bad YAML in any overlay jar TAKES THE ENTIRE PLATFORM DOWN. The wizard surface is a non-critical UI affordance — losing it should NOT block the platform's core operation (ingestion, catalog, RBAC). The platform's broader pattern is fail-fast for critical-config (e.g., DB connection) and degrade-gracefully for non-critical-config (e.g., notification sender, GenAI provider) — the wizard registry sits in the latter category but is wired with fail-fast semantics.
    - **The composition with DOC-GAP-280 (case-insensitive id collision)**: an operator authoring an overlay jar (case-variant override) AND introducing a YAML typo in their overlay would: (a) silently win the case-collision; (b) THEN fail-boot on the YAML parse error; (c) the operator's diagnostic surface is "the platform won't start" — but the platform-without-overlay would have started; (d) the operator suspects the platform; (e) the actual cause is their overlay. The fail-fast amplifies the diagnostic latency.
    - **The bundled-deployment perspective**: a default ODD deployment ships ZERO wizards (the platform repo has no `META-INF/wizard/*.yaml` files per sidecar Glob); the fail-fast is dormant. The blast radius activates only when overlays are added. This bounds the operator population to "deployments with overlays" — typically integrator-organisations.
    - **The error message quality** (per sidecar `implicit_adrs` reading): the message is GOOD — `"Couldn't read wizard manifest: <filename>"` names the resource directly. Operators receive an actionable diagnostic. The IMPROVEMENT path is not the error message; it's the semantic (skip vs fail).
    - **The alternative architectures**:
      - **Option A (warn-and-omit)**: catch the IOException in `readManifest`, log.warn the filename + the parse error, return Optional.empty; the registry contains only successfully-parsed manifests. Operators see the warning in boot logs; the platform starts; the broken wizard is missing from the UI.
      - **Option B (warn-and-stub)**: same as A but populate a placeholder Integration with `id=<filename>`, `name="(malformed)"`, `description="Wizard manifest failed to parse — check boot logs"`; the broken wizard is VISIBLE in the UI with a clear error indicator. Highest operator-clarity.
      - **Option C (current — fail-fast)**: catch and rethrow; boot fails. Current implementation.
    - **The live doc silence** (per sidecar `inferred_docs[0]` WebFetch 2026-05-25 status 200): the wizard doc page describes the manifest-load-from-classpath mechanism but does NOT mention: (a) the platform fails to boot on a single corrupt YAML; (b) the recommended overlay-validation practice (parse the YAML locally before deploying); (c) the difference between bundled wizards (none in the platform repo) and overlay wizards (operator-shipped). Operators authoring overlays do not learn about the fail-fast risk until they hit it.
    - **The cross-pillar pattern**: the platform's fail-fast-on-startup behaviour has multiple instances:
      - This finding (wizard YAML — fail-fast).
      - `notifications.message.downstream-entities-depth` (per DOC-GAP-226) — `@Value` with no default; boot fails if property unset.
      - Various `@ConfigurationProperties` validation chains.
      Some are documented (`@ConfigurationProperties` validators surface in property-reference); some are not (wizard YAML — this finding). The doc-product silence on boot-failure modes is a broader gap covered by the DOC-GAP-009 + DOC-GAP-226 family.
  - **Proposed doc action**: **Two-part action — doc-side primary (caveat + best-practice) + code-side optional (graceful-degradation)**.
    1. **Doc-side PRIMARY — `integrations/integrations/integration-wizard.md` (live page)**: add a "Boot-time behaviour" sub-section after the "Authoring wizard manifests" sub-section (proposed in DOC-GAP-280): "**A single malformed wizard YAML prevents the platform from starting.** The wizard registry is loaded at boot from `classpath*:META-INF/wizard/*.yaml`; if any matched resource fails to parse (invalid YAML syntax, missing required fields), the platform throws `IllegalStateException(\"Couldn't read wizard manifest: <filename>\")` and the Spring application context construction fails. Operators adding wizard overlays SHOULD: (a) parse-validate each YAML locally before deploying (e.g., `yq eval . my-wizard.yaml` or a similar schema check); (b) deploy overlay jars one at a time to a staging environment, verifying boot succeeds; (c) if boot fails after deploying multiple overlay jars, the error message names the offending resource filename — remove or fix the named file.
