## Description

The live `enable-security/authentication/login-form` page (WebFetched 2026-05-27) documents the headline ADMIN-for-all stance ("All users authenticated through this method receive ADMIN privileges in the platform") but is **silent on three second-order consequences** that materially change operator behaviour. The page is suitable as dev/demo guidance today; it does not tell an operator how LOGIN_FORM diverges from OAUTH2 / LDAP / DISABLED in terms of authorization machinery, CSRF posture, and redirect-target safety.

**Facet 1 — `SecurityConstants.SECURITY_RULES` is INERT under LOGIN_FORM (F-011a, HIGH→CRITICAL).** `LoginFormSecurityConfiguration.java:55-57` calls `.authorizeExchange(spec -> spec.pathMatchers(permittedPaths).permitAll().pathMatchers("/**").authenticated())` and stops — no chained `.authorizationCustomizer(...)`. Contrast `OAuthSecurityConfiguration.java:98` + `LDAPSecurityConfiguration.java:145` which both wire `new AuthorizationCustomizer(permissionService, extractors)`. The Policy / Permission / Role tables an operator builds via Management UI in LOGIN_FORM mode are **never consulted by the live auth chain**. Since every LOGIN_FORM user is granted ADMIN authority (line 81: `.authorities(grantedAuthorityExtractor.getAuthorities(true))`), there's no observable error — but a tester verifying "does my non-admin Policy work?" finds it doesn't work in LOGIN_FORM mode because no policy is consulted.

**Facet 2 — CSRF unconditionally disabled (F-011c, HIGH→CRITICAL).** `LoginFormSecurityConfiguration.java:54` `.csrf(ServerHttpSecurity.CsrfSpec::disable)` unconditionally disables CSRF. A logged-in browser session is the canonical CSRF target (state-changing POST/PUT/DELETE rides automatically with the session cookie). The platform disables CSRF AND ships with no `SameSite=Strict` directive (F-087b — covered by DOC-241) AND ships with non-Secure cookies on non-HTTPS deployments. Triple compounding under LOGIN_FORM.

**Facet 3 — `auth.login-form-redirect` open-redirect (F-011b, MEDIUM→HIGH).** `LoginFormSecurityConfiguration.java:41` reads `@Value("${auth.login-form-redirect:}")` with empty default; line 43 invokes `parseURI(redirectUri)`; line 88-90 calls `URI.create(redirectUri)` with no scheme/host allowlist. The live page does **not** mention this property at all. Helm-chart deployments where this value is templated from environment substitution (K8s ConfigMap, Docker env vars driven by upstream pipelines) have no boundary that rejects an attacker-controlled value if upstream provenance is less trusted.

## Acceptance Criteria

- [ ] A new "## Authorization posture under LOGIN_FORM" H2 section is added on `login-form.md` covering:
  - **`SECURITY_RULES` is inert** — the `AuthorizationCustomizer` is NOT wired in LOGIN_FORM mode; every authenticated user is granted ADMIN authority, so the Policy/Role table an operator authors via Management UI does NOT gate the live auth chain. Operators evaluating Policies for non-admin role testing must switch to OAUTH2 or LDAP.
  - **CSRF is disabled** — `.csrf(ServerHttpSecurity.CsrfSpec::disable)` is unconditional in this mode. Combined with non-Secure default session cookies + no `SameSite=Strict` directive, a logged-in operator visiting an attacker-controlled page can trigger state-changing requests to ODD on their behalf. Recommend LOGIN_FORM ONLY for dev/demo over HTTPS terminating at a proxy that stamps Secure + SameSite=Strict externally.
  - **`auth.login-form-redirect` redirect target is operator-trusted, not platform-validated** — documents the property, the empty default, and the responsibility that operators templating this value from upstream env-var pipelines must ensure provenance. Recommend explicit allowlist documentation (or wait for upstream allowlist validation — see PLT-064).
- [ ] All three facets are written as **operator-facing caveats** with concrete recommendations (use OAUTH2/LDAP for Policy testing; terminate TLS at proxy; check redirect provenance). The framing is "what an operator running LOGIN_FORM in their environment must know", not a bug list.
- [ ] `Consumer-read:` footer cites `LoginFormSecurityConfiguration.java:54` (csrf disable), `:55-57` (no AuthorizationCustomizer), `:81` (literal `true` granting ADMIN), `:41, :43, :88-90` (redirect target derivation), and the contrast `OAuthSecurityConfiguration.java:98` + `LDAPSecurityConfiguration.java:145`.
- [ ] Live-site verification post-merge: WebFetch the login-form page; new subsection renders; cross-links to oauth2-oidc + LDAP pages resolve.
