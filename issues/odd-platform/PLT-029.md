## What

Five operator-visible defects on the Dataset Field per-Column Annotation surface — three backend (one of which is two adjacent SecurityConstants wiring bugs), two UI composition shell hazards.

**Defect 1 — TWO SecurityConstants wiring bugs at adjacent lines (F-047a; the headline).** Verified verbatim at `SecurityConstants.java:295-299`:

| Line | SecurityRule | Declared scope | Actual permission gate | Bug |
|------|--------------|----------------|------------------------|-----|
| 295-296 | `PUT /api/alerts/{alert_id}/status` | `ALERT` | `DATASET_FIELD_ADD_TERM` | Alert-status mis-gated by field-term-add permission |
| 297-299 | `POST /api/datasetfields/{dataset_field_id}/terms` | `DATASET_FIELD` | `DATA_ENTITY_ADD_TERM` | Field-term-add mis-gated by entity-term-add permission |

**Operator-visible consequence of Bug 2** (the higher-severity of the two): the UI uses the documented `DATASET_FIELD_ADD_TERM` for the field-level Add-term button. The button is ENABLED for users with `DATASET_FIELD_ADD_TERM`. The server requires `DATA_ENTITY_ADD_TERM` for the same endpoint. Click → 403 → `TermItem` catch swallows the error silently → operator sees the button work-ish but the term doesn't appear. **A user granted the permission documented for the action silently cannot perform the action.**

**Defect 2 — `createEnumValue` is BULK-REPLACE not CREATE (F-047b).** `EnumValueServiceImpl.java:91-122`:
- Items with `id != null` → bulkUpdate.
- Items with `id == null` → bulkCreate.
- Rows whose id is NOT in `idsToKeep` → `softDeleteExcept(datasetFieldId, idsToKeep)`.

OpenAPI operationId says `createEnumValue` (singular CREATE verb at `openapi.yaml:2536-2554`). The schema name `BulkEnumValueFormData` is honest about the bulk shape but the operation name hides it. A third-party API consumer (or a future UI refactor) sending only one new item to a field with three existing items **soft-deletes the other two silently**. The DatasetFieldEnumsForm UI at lines 90-105 correctly sends the FULL `data.enums` array (avoiding the trap); the UI is the only protection.

**Defect 3 — `updateDatasetFieldTags` is delete-all-then-recreate (F-047c).** `DatasetFieldServiceImpl.java:117-132` calls `deleteDatasetFieldInternalRelations(datasetFieldId)` FIRST — UNCONDITIONAL DELETE filtered by `origin = INTERNAL` (per `ReactiveTagRepositoryImpl.java:289-295`) — then re-inserts the submitted set. Submitting `tags: []` clears every INTERNAL tag silently. EXTERNAL_STATISTICS tags survive — but the operator may not realise the surviving rows belong to a different channel. Unlike `TagServiceImpl.updateRelationsWithDataEntity` which computes a true diff.

**Defect 4 — Composer no-unsaved-changes-warning on field switch (F-192a; UI tier).** `DatasetFieldOverview.tsx:54-98` mounts sub-editors unconditionally. When an operator clicks a different field row while a sub-editor (e.g. `TagsEditForm`) is open, the dialog stays open but `selectedFieldIdAtom` updates. The dialog's internal `useForm` state was initialised from the previous field's tags. Submit on this dialog might submit the previous field's tags against the new field's id — depends on closure-capture vs re-render timing. **Latent data-corruption hazard on fast-switching workflow.** Marked `ui_unverified: true` pending runtime probe.

**Defect 5 — Composer uses split state management (F-192b; UI tier).** Description / tags / enums dispatch Redux thunks; business-name / term-add / term-delete use React Query mutations. Mixed-paradigm composition within a single feature surface. Optimistic-update + error-rollback semantics differ across sub-editors; stale-cache risk if Redux update succeeds but React Query cache is unaware.

## Suggested fix (five threads)

**Thread A — SecurityConstants line one-liners (Defects 1; the cheap fix).** Two one-line edits:

- **Line 296**: Replace `DATASET_FIELD_ADD_TERM` with the correct alert-side permission. Need to disambiguate against the substrate's F-007 lineage — likely `DATA_ENTITY_ALERT_RESOLVE` or similar. Cross-check `PolicyPermissionDto` for the alert-resolve enum value before committing.

- **Line 299**: Replace `DATA_ENTITY_ADD_TERM` with `DATASET_FIELD_ADD_TERM`. Direct one-character swap.

After the fix, the silent-403 UX mismatch (Bug 2) is closed — `DATASET_FIELD_ADD_TERM` becomes effective for the field-level Add-term button.

**Thread B — `createEnumValue` rename + true CREATE split (Defect 2).** Two options:
- **Option B1** — Rename operationId to `replaceEnumValues` (matches the BULK-REPLACE semantic) + document the bulk-replace contract in the OpenAPI description. Breaking change for SDK consumers but the honest semantic.
- **Option B2** — Split into a true `createEnumValue` (single CREATE; no soft-delete) + `replaceEnumValues` (the existing bulk-replace shape).

Recommend Option B2 — preserves the semantic of the CREATE verb for clients who want it; bulk-replace is opt-in. Backwards-compat: keep the old operationId behaviour at `replaceEnumValues` for a deprecation window.

**Thread C — `updateDatasetFieldTags` true-diff semantic (Defect 3).** Compute the diff between the submitted tags and the current INTERNAL tag set; apply ADD + REMOVE deltas. Mirrors `TagServiceImpl.updateRelationsWithDataEntity`. The behaviour change: submitting `tags: []` continues to clear all (this is the documented operator intent for "deselect all"); submitting a partial set adds the new ones + removes any not in the set + leaves untouched ones alone — closer to operator mental model.

If preserving the "deselect all" affordance via empty array is desired, ship a separate `DELETE /api/datasetfields/{id}/tags` endpoint as the explicit clear path + change the UI deselect-all click to use it.

**Thread D — Composer unsaved-changes warning (Defect 4).** Add `confirmOnClose` / "unsaved changes" warning at `DatasetFieldOverview.tsx:54-98` when the field selection changes with an open sub-editor dialog. Two patterns:
- Modal confirmation when `selectedFieldIdAtom` changes mid-edit.
- React Router-style "block navigation when form is dirty" inside the dialog's lifecycle.

The runtime probe (substrate batch-K pending) should confirm whether closure-capture or re-render timing causes the form-state mis-binding before the fix lands — the data-corruption hazard is `ui_unverified: true`; if the probe confirms it's a real bug, the fix becomes critical.

**Thread E — State-management paradigm unification (Defect 5; ADR-shaped).** This is a multi-PR refactor, not a single fix. Draft an ADR proposing one paradigm (Redux thunks OR React Query) for the per-column composer; migrate sub-editors one PR at a time. Document the transition state in `pillars/_template/cornerstones.md` style or similar contributor-facing artefact so the multi-paradigm state is intentional and tracked.

Recommend React Query — newer pattern, better optimistic-update semantics for the composer's per-sub-editor lifecycle.

## Operator impact

- A user granted `DATASET_FIELD_ADD_TERM` cannot use the field-level Add-term button — Defect 1 Bug 2.
- A user granted `DATASET_FIELD_ADD_TERM` can silently resolve any alert — Defect 1 Bug 1.
- SDK consumers sending partial enum-value payloads silently destroy existing data — Defect 2.
- UI deselect-all on dataset-field tags clears every INTERNAL tag silently — Defect 3.
- Fast-switching across field rows may submit previous field's data — Defect 4.
- Contributors face mixed paradigms within one composition surface — Defect 5.
