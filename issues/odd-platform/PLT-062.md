## What

The platform's audit posture is BIFURCATED. The POSITIVE half - Owner-Association Request workflow - has a dedicated typed-event audit table (`owner_association_request_activity` with 5-value typed enum). The NEGATIVE half - RBAC mutations + Owner / Term / Namespace / Datasource / Collector lifecycle - has NO recoverable audit trace anywhere on the platform, and the gap is **schema-rooted, not negligence-rooted**.

The schema migration `V0_0_48__add_activity.sql` declares `activity.data_entity_id bigint NOT NULL` with a FK to `data_entity(id)` (verified verbatim 2026-06-10). The audit table STRUCTURALLY CANNOT store events that are not scoped to a single data entity. The 27-value `ActivityEventTypeDto` enum (`dto/activity/ActivityEventTypeDto.java`; exactly 27 members, every one a data-entity attribute) has no values for RBAC / Owner / Term / Namespace lifecycle. Adding `@ActivityLog(POLICY_CREATED)` to `PolicyServiceImpl.create` would NOT compile (no such enum value), and even with a new value the `NOT NULL` FK would reject a row that names no data entity.

Verification (re-checked 2026-06-10) confirmed audit silence on the **lifecycle / RBAC mutation** surface - `PolicyServiceImpl.create/update/delete`, `RoleServiceImpl.create/update/delete`, `OwnerServiceImpl.create/update/delete`, `TermServiceImpl.createTerm/updateTerm/delete`, plus the Policy/Role controllers, repositories, and UI sites (`PolicyList.tsx`, `RolesList.tsx`): none of these carry `@ActivityLog`, `@Slf4j`, or any audit call.

**One nuance corrected from an earlier revision:** `TermServiceImpl` is *not* fully audit-silent - it carries `@ActivityLog` on **term-assignment** operations (`linkTermWithDataEntity`, `removeTermFromDataEntity`, `linkTermWithDatasetField`, etc., events `TERM_ASSIGNMENT_UPDATED` / `DATASET_FIELD_TERM_ASSIGNMENT_UPDATED`, `service/term/TermServiceImpl.java:169-244`). Those operations *are* data-entity-scoped, so they fit the existing schema. What has no audit is the **Term entity lifecycle** itself - `createTerm` (`:101`), `updateTerm` (`:121`), `delete` (`:155`) carry no `@ActivityLog`. The gap is precisely the non-data-entity-scoped subjects; the term-assignment exception actually reinforces the schema-rooted framing. (The companion doc `audit-trail-scope.md` already states this correctly: "Term *assignments* on data entities ARE audited; the Term entity itself is not.")

**Operator consequence (the compliance picture):** an attacker with brief admin access can delete the seeded Administrator role, recreate it with attacker-chosen policy bindings (the partial-unique-index allows re-use of seeded names), and leave NO trace except an orphaned `owner_to_role` row. Compliance auditors expecting "who renamed Owner-X from Alice to Bob at T" have NO recoverable trace anywhere on the platform.

## User-facing impact

This is an absence-of-feature (compliance) gap, not a broken surface, so the "user-facing" impact is what an operator/auditor *cannot* observe. Verified 2026-06-10 across schema, enum, services, and the companion doc: there is no platform UI, API, or log that surfaces "who created/renamed/deleted which Policy, Role, Owner, Term, or Namespace, and when". An operator opening the Activity Feed sees only data-entity events (the 27 data-entity-scoped event types); RBAC and lifecycle mutations are simply not represented anywhere. The compliance consequence (an attacker with brief admin access can delete + recreate the seeded Administrator role leaving only an orphaned `owner_to_role` row) is structurally enabled by this silence. The gap is **code-settled** (it is a property of the schema + enum + un-annotated services, all read directly); what is *not* in scope of code verification is the operator's compliance obligation itself, which is deployment-specific. The doc-side mitigation `audit-trail-scope.md` already documents the bifurcation and compensating controls (pg_audit, K8s API-server audit) for operators who need a trail today.

## Why it matters

This is the most-compliance-load-bearing defect in batch-4. Operators with audit obligations (SOX, HIPAA, GDPR, SOC2) cannot trust the platform's audit trail for RBAC + Owner / Term / Namespace operations today. The current doc-side mitigation (DOC-246 - new `audit-trail-scope.md` page) names the gap explicitly + recommends compensating controls (pg_audit, K8s API-server audit), but those are external-to-platform.

The fix is large (architectural ADR + schema migration + enum extension + ~25 service-method annotations). The cost is justified by the compliance load.

## Suggested fix (3-tier coordinated migration - needs an ADR)

This is an ADR-class change, not a bug fix. The maintainer should publish a draft ADR in the documentation repo's `architecture-decisions/` directory FIRST and resolve the two structural choices before code writing begins:

**ADR choice 1 - extend `activity` table OR add a separate `platform_event` table.**

- **Option A (extend `activity`)** - make `activity.data_entity_id` NULLable + add `subject_kind` ENUM (`DATA_ENTITY` / `POLICY` / `ROLE` / `OWNER` / `TERM` / `NAMESPACE` / `DATASOURCE` / `COLLECTOR`) + add `subject_id` BIGINT. Pros: unified activity feed; existing reader code adapts via predicate. Cons: schema-evolution risk; existing 27-value enum + reader paths assume data-entity scoping.
- **Option B (separate `platform_event` table)** - keep `activity` strict-data-entity; add `platform_event(id, event_type, actor_owner_id, subject_kind, subject_id, payload jsonb, created_at)`. Pros: clean separation; less risk to existing readers. Cons: two activity-shaped tables on the platform; admin UI requires UNION read for combined views.

Recommended: **Option A** if combined UI views are central to the operator experience; **Option B** if the UI ships a separate "Platform Activity" admin tab.

**ADR choice 2 - synchronous `@ActivityLog` annotation vs out-of-band event-bus dispatch.**

- **Option A (annotation-driven, synchronous)** - extend the existing `@ActivityLog` AOP aspect to handle non-data-entity subjects. Pros: consistent with the current architecture; visible at call site. Cons: write contention against the activity table on RBAC mutations.
- **Option B (event-bus, async)** - introduce a `PlatformEvent` publisher + Spring `@TransactionalEventListener` consumer. Pros: decouples write paths from audit infrastructure; supports future external sinks (Kafka, ELK). Cons: new infrastructure; eventual consistency.

Recommended: **Option A** as the minimum-viable; **Option B** if the platform already plans to introduce event-bus infrastructure for unrelated reasons.

**3-tier migration plan (after ADR is resolved):**

1. **Schema migration** (one Flyway script): either NULLable `data_entity_id` + new columns (Option 1A) OR new `platform_event` table (Option 1B).
2. **Enum extension** (~21 new values): RBAC x CRUD (4x3=12) - POLICY_CREATED / POLICY_UPDATED / POLICY_DELETED / ROLE_*; Owner lifecycle (3): OWNER_CREATED / OWNER_UPDATED / OWNER_DELETED; Owner-Role binding (2): OWNER_ROLE_ATTACHED / OWNER_ROLE_DETACHED; Term lifecycle (3); Namespace lifecycle (3); Datasource lifecycle (3); Collector token-rotation (1). Verify the exact list against the actual mutation surface.
3. **ActivityHandler / `@ActivityLog` instrumentation** across ~25 service methods. Pattern-mirror existing `@ActivityLog` users (e.g., `DataEntityServiceImpl`).
