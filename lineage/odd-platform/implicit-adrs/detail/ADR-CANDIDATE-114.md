## ADR-CANDIDATE-114 — Read-cardinality split: BATCH alert reads are owner-scoped via reactor `Context`; PER-ENTITY alert reads are deliberately UNSCOPED because the caller has already named the entity — the structural asymmetry between `listByOwner` and `getAlertsByDataEntityId` SQL shapes encodes the decision

**Classification**: promote
**Severity**: MEDIUM
**Pillars affected**: [P-07-active-platform-features, P-09-security-access-control]
**Support**: 1 sidecar (`getDataEntityAlerts`) — single-sidecar but structurally confirmed by SQL-shape asymmetry against the sibling `listByOwner` query at the same repository
**Batch**: L (2026-05-19)

**Surfaced by**:
- `odd-platform__java__DataEntityController__controller-method__getDataEntityAlerts.md:implicit_adrs.[2]` (MEDIUM) — "Read-cardinality split between batch and per-entity reads — the platform separates the alert read surface into TWO classes of endpoints: (a) batch reads (`getAllAlerts`, `getAssociatedUserAlerts`, `getDependentEntitiesAlerts`) which are owner-scoped via reactor `Context` at `AlertServiceImpl.listByOwner` (line 84-86) / `listDependentObjectsAlerts` (line 235-237) — except `listAll` which is unscoped (REFACTOR-024); and (b) per-entity reads (`getDataEntityAlerts`, `getDataEntityAlertsCounts`) which are unscoped by design — the caller already names the `dataEntityId` so there is no 'which entities should I see' question to answer. The implicit ADR is: 'per-entity alert reads are unscoped because the caller has already chosen the entity'. The decision-shape is visible structurally: the only filter applied at `ReactiveAlertRepositoryImpl.java:182-199` is `DATA_ENTITY.ID = :id`; there is no `OWNERSHIP` join (compare `ReactiveAlertRepositoryImpl.java:165` for `listByOwner` which DOES `.join(OWNERSHIP)`)"

**Decision statement**: ODD's alert read surface splits on cardinality: BATCH endpoints (those returning alerts across many entities) take a principal-derived owner scope at the service layer — `AlertServiceImpl.listByOwner` reads the owner from reactor `Context` at line 84-86 and pushes it into the repository's `getAlertsByOwner(ownerId, ...)`, which builds `SELECT ALERT.* FROM ALERT JOIN DATA_ENTITY ON ... JOIN OWNERSHIP ON DATA_ENTITY.ID = OWNERSHIP.DATA_ENTITY_ID WHERE OWNERSHIP.OWNER_ID = :ownerId` at `ReactiveAlertRepositoryImpl.java:160-178`. PER-ENTITY endpoints (those returning alerts for a single, caller-named entity) DO NOT take a principal; the service signature `getDataEntityAlerts(long dataEntityId, int page, int size)` accepts only the entity ID, and the repository query at `ReactiveAlertRepositoryImpl.java:182-199` is `SELECT ALERT.* FROM ALERT JOIN DATA_ENTITY ON ... WHERE DATA_ENTITY.ID = :id` with no `OWNERSHIP` join, no principal-derived predicate. The structural asymmetry between the two SQL shapes at the same repository file (the `listByOwner` query at line 160-178 DOES join OWNERSHIP; the `getAlertsByDataEntityId` query at line 182-199 does NOT) is the architectural statement: "per-entity alert reads are unscoped because the caller already chose the entity." The decision is paired with **ADR-CANDIDATE-003** (read-collaborative GET — every authenticated user can enumerate the catalog) — together they imply: any authenticated user can discover any entity's alerts by ID enumeration. Trade-off accepted: (a) the audit-export workaround use case (the live alerting doc names this endpoint as the documented operator workaround for the housekeeping-bug — "GET /api/dataentities/{data_entity_id}/alerts returns the open and recently-resolved set including chunks and status history") works for any owner exporting THEIR own entity's alerts; (b) but the same endpoint is also an enumeration vector — an authenticated caller who knows or guesses `data_entity_id` values can read alerts for entities they don't own. The maintainer chose simplicity (callers already have the ID, owner-scoping would be redundant) over defence-in-depth (a per-entity owner-scope filter would prevent the enumeration).

**Wisdom test**: PASS — but borderline. (1) **Intent stated**: the SQL-shape difference at the same file is structural evidence; the helper-method naming (`listByOwner` carries the owner in the name; `getAlertsByDataEntityId` does not) reinforces the convention. No inline comment defends the asymmetry as intentional, but the dual-method pair at the same repository class makes the pattern visible. (2) **Structural impact**: the alert-read posture cascades into the audit-export workaround use case AND the enumeration-vector security gap; the decision determines who can read which alerts catalog-wide. (3) **Adding owner-scoping at the per-entity path would be a structural change**: tightening the per-entity read to owner-only would break the documented audit-export workaround AND require corresponding doc updates and operator migrations. Refactoring within structure (e.g., adding caching, observability, or rate-limiting) would not change the ADR.

**Evidence**:
- getDataEntityAlerts.md says: "`ReactiveAlertRepositoryImpl.java:182-199` (no OWNERSHIP join) + `ReactiveAlertRepositoryImpl.java:160-178` (`listByOwner` DOES OWNERSHIP join — structural asymmetry confirms the per-entity-reads-are-unscoped pattern) + `AlertServiceImpl.java:138-143` (no principal pass-through on the per-entity service method) + `AlertServiceImpl.java:84-86, 235-237` (the batch reads DO read reactor Context)"

**Existing ADR**: none. **Composes with ADR-CANDIDATE-003** (GET endpoints intentionally outside SECURITY_RULES — the read-collaborative posture). **Composes with ADR-CANDIDATE-015** (owner-scoped routes via reactor Context — the BATCH-read tier of this ADR uses the same mechanism). **Contrasts with REFACTOR-024** (`listAll` is unscoped — anomaly within the batch-read tier; the per-entity tier is unscoped by design while the batch tier is owner-scoped EXCEPT for `listAll`).

**Cross-link gaps** (refactoring-scopes anchored on consequences this ADR DOES NOT defend):
- **REFACTOR-340 (NEW batch L)** — Cross-owner read of per-entity alerts: the unscoped per-entity tier means any authenticated user can `GET /api/dataentities/{id}/alerts` for any entity, enabling alert-content enumeration. The ADR endorses the unscoped read; the gap is that the live alerting doc names this endpoint as the audit-export workaround WITHOUT clarifying that cross-owner access is intentional.
- **Doc-gap candidate**: the live alerting page is silent on the cross-owner read posture for the per-entity endpoint.
- **REFACTOR-024 cross-link**: the BATCH `listAll` is unscoped — anomaly within this ADR's batch-tier where every OTHER batch read IS owner-scoped via reactor Context.

**Proposed action**: Promote to `adrs/drafts/alert-read-cardinality-split.md` (new ADR). Document: (1) the cardinality-driven scoping convention (BATCH→owner-scoped, PER-ENTITY→caller-chosen); (2) the SQL-shape asymmetry as the structural anchor at `ReactiveAlertRepositoryImpl`; (3) the trade-off (audit-export workaround simplicity vs enumeration-vector cost); (4) the documented exception (`listAll` — REFACTOR-024 is the maintainer's anomaly within the batch tier). Cross-link with ADR-CANDIDATE-003 (read-collaborative GET — the per-entity tier inherits the catch-all posture), ADR-CANDIDATE-015 (the batch tier uses the principal-flow mechanism this ADR contrasts with), REFACTOR-024 (`listAll`), REFACTOR-340 (the per-entity cross-owner enumeration consequence). Doc-side: the live alerting page should clarify the read posture for the documented audit-export workaround.

**Severity rationale**: MEDIUM — pattern-shaping decision that affects every alert-read surface; not load-bearing security architecture (already covered by ADR-CANDIDATE-003) but a positive structural choice that distinguishes the two read tiers. A maintainer reading the codebase needs to understand WHY per-entity reads have no OWNERSHIP join.
