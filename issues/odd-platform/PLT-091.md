## What

Four UX defects on the Catalog search surface that compound into "users with large catalogs lose facet options" + "routine browsing inflates the Popular ranking" + "keyboard-only users cannot reach result rows" + "double-navigate hazard on inner clickable children."

**Defect 1 - Filters.tsx silently truncates datasource + namespace facet options at 100 (F-017e).** `Filters.tsx:32-33` hardcodes `dispatch(fetchDataSourcesList({ page: 1, size: 100 })); dispatch(fetchNamespaceList({ page: 1, size: 100 }));`. Deployments with >100 datasources or namespaces silently lose options past index 100, with no "+N more" affordance, no pagination, no search-within-dropdown.

**Defect 2 - Result-row click writes +2 view_count per click (F-147a - the search-side closure of the F-001 / LSN-017 inflation loop).** `ResultItem.tsx:42, :72-76` mounts the entire row as an `onClick` navigating to `/dataentities/{id}/overview`. The destination's `useEffect`-doubling pattern (LSN-017 / F-001 chain) writes `view_count +2` per navigation; empirically pinned at `+2 xhr` + `+2 db delta` per click via the F-001 P-004 probe. Routine search browsing inflates the Catalog Overview's "Recommended" / "Popular" ranking - one teammate re-reading a search result twice writes that entity's popularity by +4.

**Defect 3 - Result row has no a11y semantics; keyboard-only users cannot reach result rows (F-147b).** `ResultItem.tsx:72-76` renders the row as `<S.Container container onClick={...}>` - no `<a>` / `<button>`, no `tabindex`, no `role`, no `aria-label`, no `onKeyDown` for Enter/Space. Screen readers do not announce the row as actionable; keyboard navigation skips every result row.

**Defect 4 - Inner clickable children have no stopPropagation audit (F-147c).** `ResultItem.tsx:87-90, :102-104, :106` mount `<MetadataStale>`, `<AppTooltip><QuestionIcon/></AppTooltip>`, and `<DataEntityDetailsPreview>` inside the row. None visibly call `event.stopPropagation()` at the consumer site. A click on the inner tooltip / preview bubbles to the row-level `onClick` and double-navigates - at minimum a duplicate write to view_count (Defect 2 compound), at worst a fail-then-restore visual flicker.

## Why it matters

- **Defect 1** turns the Filters sidebar from a precision tool into a 100-row sample for any operator running ODD in an enterprise (40+ data sources from the standard collector matrix; 50+ namespaces is common in multi-team deployments).
- **Defect 2** is the search-side trigger for the F-001 / F-003 Popular ranking inflation loop documented in DOC-260's Caveat 5. The Recommended panel on the home page surfaces "most popular" entities; routine browsing from search silently inflates the popularity score by +2 per click. The Popular ranking becomes an artifact of how operators search, not what they actually value.
- **Defect 3** locks out keyboard-only operators from the search surface entirely - they can type a query, see the results render, and have no way to open a result without a mouse. WCAG 2.1.1 (Keyboard).
- **Defect 4** doubles the inflation rate of Defect 2 whenever an operator hovers a tooltip child first; the visual flicker from the double-navigate is also a polish defect.

Severity MEDIUM because none are critical security defects; all reduce to UX class. Defect 2 is the highest-impact (it pollutes a metric operators rely on); Defect 3 is the highest a11y blocker.

## Suggested fix

### (a) Defect 1 - Paginate / search-within-dropdown the Filters sidebar

```tsx
// Filters.tsx - fetch on dropdown open with a debounced query input
const [dsQuery, setDsQuery] = useState('');
const dsQueryDebounced = useDebounce(dsQuery, 250);
useEffect(() => {
  dispatch(fetchDataSourcesList({ page: 1, size: 50, query: dsQueryDebounced }));
}, [dsQueryDebounced, dispatch]);
// (same for namespace)
```

Backend endpoints `/api/datasources` and `/api/namespaces` already accept `query` for substring matching; this is a one-component change.

### (b) Defect 2 - Debounce / dedup view_count writes at the F-001 chain

Two options; pick one:

**(b1) Debounce at the write source.** In the Overview-mount effect (the LSN-017 doubling site), wrap the view_count POST in a per-entity-per-session sentinel so a single tab can write at most +1 for a given entity per browsing session.

**(b2) Drop the search-row-click trigger.** Treat the search-row click as a navigation only; the Overview's first mount writes the count. The current `+2` shape is a useEffect-doubling artifact that should be removed regardless (LSN-017 already documented this).

Either fix eliminates Defect 4's amplification too.

### (c) Defect 3 - Semantic markup + keyboard handler

```tsx
// ResultItem.tsx:72-76
<S.Container
  container
  component="a"
  href={detailsLink}
  role="link"
  aria-label={`Open ${searchResult.dataEntity.externalName ?? searchResult.dataEntity.internalName}`}
  tabIndex={0}
  onClick={(e) => { e.preventDefault(); navigate(detailsLink); }}
  onKeyDown={(e) => { if (e.key === 'Enter' || e.key === ' ') { e.preventDefault(); navigate(detailsLink); } }}
>
```

Renders as a real `<a>` so middle-click / right-click / browser-bookmark behaviour works as expected. Same fix shape as the existing F-001 PopularStrip a11y backlog.

### (d) Defect 4 - Audit inner clickable children for stopPropagation

Cheapest variant: change the row-level onClick to `if (e.target === e.currentTarget) navigate(detailsLink)` so only direct row clicks navigate. Inner children continue working with their own click handlers and no propagation.

A cleaner variant: each inner clickable child explicitly calls `e.stopPropagation()` in its consumer at `ResultItem.tsx`, or the `MetadataStale` / `DataEntityDetailsPreview` / `AppTooltip` wrappers stop propagation internally.
