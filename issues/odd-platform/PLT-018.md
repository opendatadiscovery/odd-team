On maintainer review, two of those facets were **withdrawn as non-issues** (see *Withdrawn facets* below): the "10 of 13 endpoints unscoped" and "RBAC grid split across 3 controllers" framings described **by-design behaviour**, not defects. A third facet (no `@ActivityLog` audit trail) was **moved to `PLT-227`** (the data-entity-scoped audit-coverage item, 0.29.0). **This item is now scoped to the one real defect: the stored XSS** - the GHSA-bound facet for 0.28.0.

## What

**Stored XSS surface via raw-HTML Markdown without rehype-sanitize.** Query Example `definition` and `query` fields are stored verbatim and rendered through the shared `Markdown` element at two UI sites (`QueryExampleDetailsOverview.tsx:19, 25` render `<Markdown value={definition} />` / `<Markdown value={query} />`; the wrapper calls `MDEditor.Markdown` at `Markdown.tsx:113-124`). That wrapper passes NO `rehypePlugins` at all - no `rehype-sanitize` - AND the underlying `@uiw/react-markdown-preview@4.2.2` (the `MDEditor.Markdown` export) defaults `skipHtml=true`, which makes it inject `rehype-raw` into the pipeline (`esm/preview.js:42`, `rehypePlugins.push(raw)`), with an `allowElement` filter that admits any alphanumeric tag name including `script`/`img` (`esm/index.js:36-39`). This is precisely the react-markdown-documented XSS footgun: `rehype-raw` WITHOUT `rehype-sanitize` re-enables raw HTML (`skipHtml` does not save it, because `rehype-raw` converts raw HTML into real element nodes before react-markdown@8.0.7's `skipHtml` check at `ast-to-react.js:149` ever runs). So the surface is real, not merely "no sanitizer configured." Whether a specific payload executes in the browser is the one part not settleable from code (see User-facing impact).

**5th surface of the F-004 stored-XSS family - and all surfaces share ONE root fix (the shared `Markdown.tsx` wrapper); see Suggested fix.**

## User-facing impact

- **The dangerous configuration is verified by FE+vendored-source trace 2026-06-10; payload execution is RUNTIME-ONLY.** A data analyst with `QUERY_EXAMPLE_CREATE` can store arbitrary Markdown/HTML in `definition`/`query`; it renders to every viewer through a `rehype-raw`-without-`rehype-sanitize` pipeline (the canonical react-markdown XSS hole). What is NOT settleable from code: whether a concrete vector (`<img src=x onerror=...>`, `<script>`, `javascript:` href) actually fires under react-markdown@8.0.7's React-element construction - that needs a live drive (paste a payload into a query example, open the detail page, observe). Remaining check (for the GHSA reproduction): drive `<img src=x onerror=alert(document.domain)>` and a `[x](javascript:alert(1))` link through the detail Overview.
- **Blast radius is every authenticated user - this is by design, not a second bug.** ODD is **read-collaborative by design** (`lineage/odd-platform/implicit-adrs.md:140`: `SECURITY_RULES` holds only mutation matchers; GET endpoints fall through to `.authenticated()`). Any authenticated user can read any Query Example, so a stored payload reaches the whole authenticated user base (and is anonymous under `auth.type=DISABLED`). The read posture is the documented ODD model; it is cited here only because it sets the XSS blast radius, NOT as an access-control defect.

## Why it matters

Operators with `QUERY_EXAMPLE_CREATE` (a common grant for data analysts authoring usage examples) can plant stored XSS that fires on every viewer's session. Because the catalog is read-collaborative by design, **every authenticated user is a viewer** - the payload reaches the entire platform user base. Severity is HIGH (a stored-XSS family surface on a routine collaborator action).

## Suggested fix - sanitize the shared Markdown wrapper (closes the whole F-004 family)

```typescript
// Markdown.tsx - add rehype-sanitize to the MDEditor.Markdown render
import rehypeSanitize from 'rehype-sanitize';

<MDEditor.Markdown
  source={text}
  rehypePlugins={[[rehypeSanitize]]}
/>
```

Every F-004 markdown-XSS surface (this item + PLT-015 / PLT-019 / PLT-023) renders through this **one** shared `Markdown.tsx` wrapper, so a single `rehype-sanitize` addition here closes all of them simultaneously - the natural unit of the GHSA fix. Validate the sanitizer schema covers Markdown's expected syntax (code blocks, inline code, links) while stripping `<script>`, `<iframe>`, event handlers, `javascript:` URLs. Research the standard before inventing a custom schema (cf. the CTRIB-019 `@braintree/sanitize-url` precedent - adopt the vetted default, do not hand-roll).

## Withdrawn facets (2026-06-17, maintainer review)

The original 4-facet cluster carried two framings that are **NOT defects** and have been removed:

- **"10 of 13 endpoints unscoped (broken access control)" - WITHDRAWN.** ODD is **read-collaborative by design** (`implicit-adrs.md:140`). GET/search/list endpoints intentionally fall through to `.authenticated()` across the whole platform (DataEntityController, AlertController, ActivityController, SearchController, ...). Query Examples behaving the same way is the platform model, not a hole.
- **"RBAC permission grid split across 3 controllers" - WITHDRAWN.** The 7 `QUERY_EXAMPLE_*` permissions are configured by **name** in the policy editor (they are `PolicyPermissionDto` values); which controller hosts each endpoint is an invisible implementation detail. A feature whose mutations are gated by more than one permission is normal policy composition, not a misconfiguration trap.
- **Verified the only real authz test passes:** every Query Example **mutation** IS permission-gated - all 7 POST/PUT/DELETE matchers are present in `SecurityConstants.java:112-113, 188-193, 312-324` (CREATE/UPDATE/DELETE + DATASET_CREATE/DELETE + TERM_CREATE/DELETE). No mutation reaches shared platform data without a permission. There is no access-control defect here.
