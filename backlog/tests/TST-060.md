## Description

Three `/contribute` streams ran concurrently on one machine tonight (`ctrib060` = #1840, `ctrib061` = #1841,
`ctrib062` = #1842). Two defects in the coordination substrate turned that into an unreadable e2e verdict.

**1. The flock guards the regression, not the stacks.** `ctrib060` held `state/locks/heavy-e2e.lock` for its
`feature-complete` run (started 23:39:22; `ctrib062`'s own ledger entry at 23:47 records seeing it hold the
flock). `ctrib062` was in Phase A/C — which the protocol says is READ-ONLY and takes no flock — yet
`ctrib062-odd-platform` + `ctrib062-database` were **created at 23:43:11**, inside that window. A second
platform + Postgres competing for the box while 339 browser tests run is exactly the load the flock exists to
prevent, and the flock did not see it because bring-up is not what it guards.

**Symptom it produced:** 20 of 339 `feature-complete` specs failed, every one on a 60 s `waitForResponse` /
`waitForURL` timeout, across a heterogeneous set that includes `swagger-openapi-discovery` (no relation to the
change under test) — while the same SUT answered `POST /api/search`, `GET /{id}/results` and an operator query
with 200s on direct `curl`. Attributability then costs a full second regression run (~70 min) to settle.

**2. Intake cannot see a stream that registers later.** `ctrib060` verified "NO co-active stream" at intake and
was correct at that moment; `ctrib061` and `ctrib062` registered afterwards. Nothing re-checks, so a long
Phase-D run has no idea the box filled up behind it.

**3. `run-suite.sh` warns and proceeds on a stack/SUT mismatch.** When a leftover stack is "already healthy" it
is reused, and a digest mismatch prints
`WARNING: the e2e stack is running image , which does NOT match the SUT digest ...` — then runs anyway. This
session hit it: a spec run intended for the CTRIB-060 SUT actually drove a build of the old
`contrib/CTRIB-026-…` branch, producing a screenshot with the pre-ST-4 nine-tab class strip and a
`waitForURL(?q=)` timeout that looked exactly like a regression in the change under test. Only the fact that
the rendered tab strip contradicted the source caught it.

## Acceptance criteria

- [ ] Stack bring-up takes the same machine-wide lock as the regression (or a second, stack-scoped lock), so no
      stream can start a platform inside another's e2e window.
- [ ] A stack/SUT digest mismatch is a **hard failure**, not a warning — running the wrong artefact silently is
      the LSN-033 class and must abort.
- [ ] A long Phase-D run re-reads `state/active-streams.yaml` at suite boundaries and records co-active streams
      in its run-log, so an e2e verdict carries the contention context that decides how to read it.
- [ ] `playbooks/stream-coordination.md` states that "no co-active stream at intake" has a shelf life, and that
      an e2e verdict taken under contention is not a verdict.

## Related

`TST-042` already records that `feature-complete` carries specs with non-robust waits that **flake under
full-set sequential load** (view-count, global-alerts, data-entity-overview). That is the same failure surface
seen from the single-stream side; this item is the multi-stream cause that makes it far worse and, unlike
TST-042, makes the flake indistinguishable from a real regression in the change under test.

## Notes

The cost is not hypothetical: this slice's e2e gate needed a full A/B against a `ref:main` SUT purely to
establish that 20 failures were environmental — roughly 70 minutes of machine time to answer a question the
harness could have answered by refusing to run two stacks at once.
