  - **Proposed doc action**: Two-part fix. (1) Doc-side on `configuration-and-deployment/enable-security/authentication/oauth2-oidc.md`, in the GitHub provider section, add a "**Username stability**" admonition: "**GitHub login renames orphan the user's catalog identity.** The platform uses GitHub's `login` (the mutable username) as the user-identity key in `USER_OWNER_MAPPING`. GitHub allows users to rename their `login` freely; the old name enters a 90-day escrow then becomes available to others. If a user renames their GitHub login from `alice` to `alice2`, their next login authenticates as `(alice2, github)` and the prior `(alice, github)` USER_OWNER_MAPPING row is orphaned (the renamed user loses their owner-linkage, owner-scoped reads, and any catalog rights attached to the prior identity). The platform does NOT consult GitHub's stable numeric user `id` as a fallback. **Recovery requires operator intervention**: an administrator must either (a) update the orphaned mapping row's `oidc_username` to the new login (direct SQL on `USER_OWNER_MAPPING`), or (b) re-attach the user to their existing Owner via the user-owner-association API after the renamed user authenticates. There is no migration tool today." (2) Code-side preferred long-term: file `/log-issue odd-platform` upstream to add an optional `user-name-attribute: id` mode for GitHub (using the stable numeric id as the identity key), or add a fallback resolver that consults GitHub's `id` when `login` lookup fails. The doc admonition is also a cross-link to `configuration-and-deployment/enable-security/authorization/user-owner-association.md` where the broader compound-key + rename consequence applies across all OAuth2 providers (though GitHub's login mutability is the highest-risk case among the 5 documented providers).

  - **Severity rationale**: HIGH — security-adjacent silent data-loss with operator-segment-specific impact. The orphaning is silent (no log, no email, no audit), latent (only manifests on rename — rare but not negligible for engineering teams), and unrecoverable without operator intervention. The recovery path requires direct SQL or an out-of-band API call — neither is documented. Severity is HIGH because (a) the data-loss is real (catalog rights, owner-scoped reads, ownership of curated metadata), (b) the fix path is opaque to the affected user (they cannot recover themselves), (c) the rename event is plausible (engineers renaming for personal preference, marriage, brand-name changes), (d) the same gap exists for other providers if the operator chose a mutable `user-name-attribute` but GitHub's `login` is the documented default — the gap ships out-of-the-box. The fix shape is documentation + optional code path (use `id` as the key) — relatively low-cost; the impact-vs-cost ratio justifies the HIGH classification.
