- **ADR-CANDIDATE-048** (NEW 2026-05-12D): `@ConfigurationProperties` validators have NARROW SCOPE BY DESIGN — `@PostConstruct validate()` methods check ONLY the fields required for Spring to construct the bean / wire the downstream consumer at all. Provider-conditional fields (e.g. Azure `logoutUri`, GitHub `scope` containing `read:org`), URL-format validation, enum-membership constraints, cross-field invariants, and operator-policy assertions are DEFERRED to runtime usage-sites or to Spring's downstream validation. The validator's job is to fail-fast on STRUCTURAL CONFIGURATION FAULTS that prevent bean construction, not to enforce semantic correctness of all field values
  - **Category**: promote
  - **Support**: surfaced by 2 sidecars consistent at the validator-narrowness pattern (`ODDOAuth2Properties` validator at lines 16-28 checks only `clientId` + `provider` non-empty — a 2-field validator on a 21-field POJO; `ODDLDAPProperties` validator at lines 40-49 checks only `url` non-empty AND `dnPattern XOR userFilter` — a 2-check validator on a 14-field POJO including 3 nested-class fields). The same maintainer authored both POJOs in the same `org.opendatadiscovery.oddplatform.auth` package — the consistency is intentional
  - **Surfaced by**:
    - `odd-platform__java__org_opendatadiscovery_oddplatform_auth__config-properties-class__ODDOAuth2Properties.md:implicit_adrs.[1]` ("Fail-fast validation is intentionally narrow: only `clientId` and `provider` are enforced non-empty at `@PostConstruct`.   - **Decision statement**: ODD's `@ConfigurationProperties` validators are intentionally NARROW. Their job is to fail-fast on STRUCTURAL CONFIGURATION FAULTS that prevent bean construction — NOT to enforce semantic correctness of all field values. Concretely: (a) ODDOAuth2Properties.validate() at lines 16-28 checks ONLY `clientId` + `provider` non-empty across 21 OAuth2 fields; (b) ODDLDAPProperties.validate() at lines 40-49 checks ONLY `url` non-empty AND `dnPattern XOR userFilter`; (c) EmailSenderProperties' validation (in NotificationConfiguration.java:39-49, bean-factory rather than @PostConstruct) checks ONLY `sender` / `host` / `protocol` non-blank; (d) DataCollaborationProperties.validate() at lines 14-20 checks ONLY `sendingMessagesRetryCount >= 0`. The exception type encodes the framing: `IllegalStateException` for `@PostConstruct` validators (deployment-state class) vs `IllegalArgumentException` for bean-factory checks (argument class). What is INTENTIONALLY NOT validated at boot: (1) URL format on URI fields — typos like `htp://example` boot successfully and fail at first OAuth2 callback or first SMTP send; (2) enum membership for free-String provider fields — typos like `provder: google` bind cleanly and silently route to generic OIDC; (3) provider-conditional required fields — Azure `logoutUri` is documented as required but unvalidated, producing NPE on first logout (REFACTOR-155); GitHub `scope: read:org` is documented as required for admin-group lookup but unvalidated; (4) cross-field invariants — DataCollaboration sender + receiver lock-IDs could collide silently (REFACTOR-175); admin-group set could be empty under LDAP (REFACTOR-120). The trade-off accepted: validators stay small + readable + maintainable, at the cost of operator-visible-only-at-runtime misconfigurations. The maintainer's signal: validators catch BOOT-WIRING failures; runtime first-use catches SEMANTIC-CORRECTNESS failures.
  - **Wisdom test**: PASS. The 2-sidecar consistency across two distinct `@ConfigurationProperties` POJOs (OAuth2 + LDAP) authored by the same maintainer in the same package is the intent anchor. Both validators are explicit two/three-check bodies with named exception messages — the maintainer could have either authored declarative `@NotBlank` / `@URL` annotations (Spring Boot supports this via `@Validated` + jakarta.validation) OR authored richer imperative validators with provider-conditional branches. The choice to author NEITHER is consistent and structural — narrow-validator-by-design is the pattern. Composes with ADR-CANDIDATE-018 (fail-fast at boot) — that ADR codifies WHEN to validate; this ADR codifies HOW MUCH to validate.
