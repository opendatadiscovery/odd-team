## Description

Updating an ownership on a Data Entity Group (DEG) with `propagate=true` re-writes the ownership on every member entity — including the **title** (Owner role). `OwnershipServiceImpl.update` propagates via `propagateIfDEG` → `propagateOwnership`, which builds a fresh `OwnershipPojo` per child carrying the parent's `ownerId` **and `titleId`** and persists them with `createOrUpdate`. Only the parent `update` method carries `@ActivityLog(event = OWNERSHIP_UPDATED)`; the private `propagateOwnership` has **no** `@ActivityLog`, so the per-child title change emits **no Activity Feed event**. An auditor reading a child entity's Activity tab sees nothing when that child's owner *role/title* changes via group propagation — only the parent group's single `OWNERSHIP_UPDATED` event exists.

The activity-feed page already documents the general shape of this for owner add/remove: *"Owner changes on a Data Entity Group cascade to the group's members, but only the group emits an event — the member entities do not."* (`activity-feed.md:56`). That caveat is correct and largely covers this case. The residual gaps this item closes: (1) the **ownership canonical home (owners.md)** — where an operator goes to understand titles/Owner roles — carries **no** mention of this audit blind spot, and (2) the existing activity-feed wording is phrased around an owner being *added or removed*; a **title change with the owner unchanged** is the same propagation path and the same no-per-child-event outcome, and should be explicitly in scope. Cross-reference F-006 (Data Entity Groups) so the propagation mechanics are findable.

Neither private method is annotated, so no child-level event is emitted.
