## What

Six operator-visible gaps on the GenAI Assistant feature surface, grouped as two related defects. The platform-to-EXTERNAL posture (toward the LLM provider) is already documented (per DOC-045 / live page WebFetched 2026-05-27). The **platform-to-USER posture** is undocumented and undefended.

**Defect 1 - Platform-to-user posture is unrestricted.** `GenAIController.genAiQuestion` (re-verified 2026-06-10) carries no `@PreAuthorize`; it takes a `ServerWebExchange` parameter (the generated signature) but never uses it for any security check; and `SecurityConstants.java` has **no `/api/genai` entry anywhere** (grep over the 356-line file returns zero matches) and `/api/genai` is NOT in `WHITELIST_PATHS` (`:95-96`). So the endpoint falls through to `.pathMatchers("/**").authenticated()` (`AuthorizationCustomizer.java:29-30`) under LOGIN_FORM / OAUTH2 / LDAP, and to **anonymous** under `auth.type=DISABLED` (`DisabledAuthSecurityConfiguration.java:16`). Five sub-gaps, all confirmed at the controller/service:

- **(a) Any authenticated user can drive cost** on the operator's external LLM account - no rate-limit, no throttle, no per-user quota (the controller is a bare passthrough; the service only checks the global `enabled` flag, `GenAIServiceImpl.java:36-38`)
- **(b) No audit** - no `@ActivityLog`, no in-platform record of who asked what (and the activity-feed schema-rooted constraint per F-021a means this can't be added without a schema migration)
- **(c) No redaction of the request body** - `GenAIServiceImpl.java:41-43` POSTs `{"question": request.getBody()}` verbatim to the external LLM. Corrected 2026-06-10: the platform does NOT server-side enrich the prompt with owner/lineage names - only the user-supplied `body` is sent - so what reaches the LLM is exactly what the caller/FE puts in the body, unredacted (PII exposure depends on the caller's content, not on server-added context)
- **(d) No request-body size cap** - no `@Size`/`@Valid` bound on `GenAIRequest`; large free-form prompts pass through unbounded
- **(e) Under `auth.type=DISABLED`** - no per-user attribution at all; anonymous callers drive cost

**Defect 2 - `genai.url` is operator-config SSRF surface.** `GenAIProperties.java:10` declares `private String url;` with no `@URL` constraint and no `@Pattern` scheme/host allowlist (the class also has `enabled` and `requestTimeout`, neither relevant here). That value is used verbatim as the WebClient base URL - `WebClientConfiguration.java:28` `.baseUrl(genAIProperties.getUrl())` - and the service POSTs to `{genai.url}/query_data` (`GenAIServiceImpl.java:21, 41-42`). An operator (or an attacker with config-write access) can point the outbound POST at any reachable URL **including the platform's own internal network** - private subnets, internal services, cloud-metadata endpoints (e.g., `http://169.254.169.254/latest/meta-data/iam/security-credentials/`). The WebClient runs in the platform's JVM, so requests originate from the platform's egress identity.

## User-facing impact

This is a back-end / operational posture issue - there is no UI-rendering subtlety. The "users" are the operator (who pays the LLM bill and owns the egress identity) and any caller of `/api/genai/ask`.

- **Unauthenticated/unauthorized reach - verified by BE trace 2026-06-10 (static settled):** with no SecurityRule and no whitelist entry, the endpoint requires only a valid session under LOGIN_FORM/OAUTH2/LDAP, and is fully anonymous under `auth.type=DISABLED`. WHO: any session-holder (or any visitor under DISABLED). WHAT they can do: call `POST /api/genai/ask` directly.
- **Cost amplification (1a/1e) - static trace consistent; NOT driven:** no per-user/global rate limit exists in the controller or service, so a caller can loop requests; each forwards to the external LLM (`GenAIServiceImpl.java:41-42`). The actual bill impact needs a live LLM + `genai.enabled=true` to observe (the service errors out when disabled, `:36-38`).
- **No attribution (1b) - verified by BE trace 2026-06-10:** an operator investigating an LLM cost spike has no in-platform record of who asked what (no audit emission).
- **Prompt content to third party (1c) - verified by BE trace 2026-06-10:** the user-supplied `body` is sent verbatim to the external LLM with no redaction; consumer-visible effect is that whatever a caller types leaves the platform boundary unfiltered.
- **SSRF (Defect 2) - static trace consistent; NOT driven:** `genai.url` flows unvalidated into the WebClient base URL, so a misconfigured/hostile value makes the platform JVM POST to an internal/metadata address. Reaching a real credentials endpoint needs a cloud deployment + config-write access - not driven here.

## Why it matters

GenAI is a **cost-amplification surface**. The operator pays per token on the external LLM bill. The platform proxies user prompts through their account with no upper bound on per-user activity.

The compound failure mode: operator enables GenAI; user discovers the endpoint (UI button or `/api/genai/ask`); user (or compromised user-credential-holder) loops requests; LLM bill explodes; operator has no audit trail to identify the culprit.

Severity is HIGH because:
- Cost-injection is a financial impact (real money, not just compute time)
- The compound with `auth.type=DISABLED` (used in dev / evaluation deployments) is **fully unauthenticated** cost injection
- SSRF via `genai.url` enables credentials-exfiltration on cloud deployments (instance-metadata access)
- The fix is multiple small changes, but each is well-bounded

## Suggested fix

### PR-1 - Authentication + authorization (Defect 1a + 1e)

```java
// SecurityConstants.java - add /api/genai/** to the SECURITY_RULES list
new PathPatternParserServerWebExchangeMatcher("/api/genai/**", POST)
    .requires(GENAI_USE),

// new permission: GENAI_USE - operator grants this to roles allowed to invoke GenAI
// pair with a new GENAI_ADMIN permission for any future config / model selection endpoints
```

Default: deny under `auth.type=DISABLED` unless explicit `genai.allow-disabled-mode: true` opt-in. Document the new permission in `permissions.md`.

### PR-2 - Rate limiting (Defect 1a)

```java
// new config: genai.rate-limit.per-user-per-minute (default: 10)
// new config: genai.rate-limit.platform-per-minute (default: 100)
// implementation: Bucket4j or Redis-backed token bucket keyed by username + global

// GenAIController.java
@PostMapping("/api/genai/ask")
public Mono<GenAIResponse> ask(@RequestBody GenAIRequest req, ServerWebExchange exchange) {
    return rateLimitService.tryAcquire(currentUser(exchange))
        .flatMap(allowed -> allowed
            ? genaiService.ask(req)
            : Mono.error(new RateLimitedException("rate limit exceeded"))
        );
}
```

### PR-3 - Audit (Defect 1b)

Two options given the activity-feed schema-rooted constraint:

- **Option A** - emit a non-activity-feed audit event to a new `genai_request_log` table. Operator can query this for cost-attribution.
- **Option B** - extend the activity-feed schema (relates to F-021a) to support nullable `data_entity_id`. Larger architectural change; not in scope of this PLT.

Recommend Option A for this PLT; revisit Option B at the F-021a resolution.

### PR-4 - PII redaction + body-size cap (Defect 1c + 1d)

```java
// new config: genai.pii-redaction.enabled (default: true - opinionated default for safety)
// new config: genai.max-request-body-size-bytes (default: 16384 = 16KB)

// GenAIController.java - body-size enforcement
@PostMapping("/api/genai/ask")
public Mono<GenAIResponse> ask(@RequestBody @Size(max = 16384) GenAIRequest req) { ... }

// GenAIService - PII redaction
//   - identify owner-email patterns, owner-name patterns (configurable allow-list of known-safe identifiers)
//   - replace with [REDACTED-EMAIL], [REDACTED-OWNER] tokens
//   - log the redaction count for operator observability
```

### PR-5 - SSRF allowlist (Defect 2)

```java
// GenAIProperties.java
public class GenAIProperties {

    @NotBlank
    @Pattern(regexp = "^https?://[^/]+(/.*)?$")
    private String url;
}

// new config: genai.url-allow-list (default: empty - accepts any URL matching the @Pattern)
// operators with stricter posture configure: genai.url-allow-list: ["api.openai.com", "internal-llm.corp.example"]
// implementation: validate parsed URL host against the allow-list before instantiating WebClient
```

## How discovered

Surfaced during the Mode B run of `docs/coverage/undocumented-features` on 2026-05-27 (substrate `F-039` - GenAI Assistant). Defect 1 (5 sub-gaps) from F-039a; Defect 2 from F-039b.

Re-verified 2026-06-10 (user-facing verification sweep): both defects confirmed by trace. Corrections: the controller DOES take a `ServerWebExchange` param (it just never uses it for auth) - was "NO ServerWebExchange parameter"; the SSRF path is now fully traced (`GenAIProperties.url` -> `WebClientConfiguration.java:28` baseUrl -> `GenAIServiceImpl.java:41-42` POST `{base}/query_data`); sub-gap (c) narrowed - the platform sends only the user-supplied `body` verbatim, it does not server-side add owner/lineage names, so PII exposure is caller-content-dependent. `user_facing_verified` stays false: cost amplification and SSRF-to-metadata are both runtime observables (need a live LLM / a cloud deployment with config-write).
