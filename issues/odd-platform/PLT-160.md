## What

When a user saves or edits a data-entity "link" attachment, the supplied URL is persisted verbatim - there is no validation of the URL scheme. A caller can store a `javascript:...` or `data:text/html;...` URI as a link `url`. The UI later renders these links as clickable anchors keyed off the stored value, so a hostile URL becomes a **stored cross-site-scripting** vector: any user who views that data entity's attachments and clicks the link executes attacker-controlled script in their authenticated session. Only `http`/`https` (and arguably `mailto`/`ftp`) should be acceptable for a link.

## Where

`LinkServiceImpl` persists the form data through a plain MapStruct mapper with no scheme check on either the create or the update path:

`odd-platform-api/.../service/attachment/LinkServiceImpl.java:41-45`
```java
public Mono<DataEntityLink> update(final long linkId, final DataEntityLinkFormData formData) {
    return linkRepository.get(linkId)
        .switchIfEmpty(Mono.error(() -> new NotFoundException("Link", linkId)))
        .map(pojo -> linkMapper.applyToPojo(formData, pojo))   // <- url copied raw, no scheme validation
        .flatMap(linkRepository::update)
        .map(linkMapper::mapToDto);
}
```

The create path is the same - `save(...)` maps each item via `linkMapper.mapToPojo(link, dataEntityId)` and bulk-inserts (lines 31-38). The mapper itself is a bare MapStruct interface with no custom logic, so nothing intercepts the `url` field:

`odd-platform-api/.../mapper/LinkMapper.java:13-16`
```java
LinkPojo mapToPojo(final DataEntityLinkFormData formData, final long dataEntityId);
LinkPojo applyToPojo(final DataEntityLinkFormData formData, @MappingTarget final LinkPojo pojo);
```

Reached via `DataEntityAttachmentController.saveLinks` / `updateLink` -> `AttachmentService` -> `LinkServiceImpl`.

## Why it matters

Stored XSS is one of the highest-impact web defects: the payload is persisted once and fires for every subsequent viewer, in their own authenticated context, with no further action by the attacker. Any user who can create or edit a link attachment (a routine collaborator action) can plant a `javascript:` link that, when another user clicks it from the entity's attachments panel, runs in that victim's session - enabling session/token theft, CSRF-style actions, or pivoting to admin operations if the victim is privileged. Because the value is stored, it persists across restarts and is invisible until triggered. Severity **high**: persistent XSS reachable by ordinary authenticated users, affecting every viewer of the entity.

## Suggested fix

Validate the URL scheme on both the create (`save`) and update (`update`) paths before persisting, rejecting anything outside an allow-list:

```java
private static final Set<String> ALLOWED_SCHEMES = Set.of("http", "https");

private void validateScheme(final String url) {
    final String scheme;
    try {
        scheme = URI.create(url).getScheme();
    } catch (final IllegalArgumentException e) {
        throw new BadUserRequestException("Link URL is malformed");
    }
    if (scheme == null || !ALLOWED_SCHEMES.contains(scheme.toLowerCase(Locale.ROOT))) {
        throw new BadUserRequestException("Link URL scheme is not allowed");
    }
}
```

Apply it in `LinkServiceImpl.save` (per item) and `LinkServiceImpl.update` before the mapper call (or as a `@Mapping`-level qualifier / bean-validation constraint on `DataEntityLinkFormData.url`). The UI should additionally treat stored link URLs as untrusted when rendering, but the server-side allow-list is the authoritative fix. Open to alternatives on the exact allowed set (`mailto`/`ftp` may be desirable).
