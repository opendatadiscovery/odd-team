- **ADR-CANDIDATE-032** (NEW 2026-05-12C): S2S authentication composes (additively) with every interactive auth mode — `auth.s2s.enabled=true` does NOT replace `auth.type=LOGIN_FORM/OAUTH2/LDAP` but adds the `S2sAuthenticationFilter` at the `SecurityWebFiltersOrder.HTTP_BASIC` slot in the chosen mode's chain. The composition produces an X-API-Key authentication surface that grants `ADMIN` across the ENTIRE `/**` surface (not just `/ingestion/**`), creating a deliberate-yet-broad privilege escalation vector when composed with any non-DISABLED interactive mode

  - **Decision statement**: S2S authentication is wired as an ADDITIVE filter, NOT a substitute auth.type value. Operators enable it via `auth.s2s.enabled=true` (default `false` per `application.yml:40-41`) and the `S2sAuthenticationFilter` is conditionally inserted into the chosen interactive-mode's `SecurityWebFilterChain` at `SecurityWebFiltersOrder.HTTP_BASIC` (the highest-priority pre-authentication slot). The filter checks `X-API-Key` on every request; on match, `S2sAuthenticationFilter.java:31-39` injects a synthetic `User.withUsername("ADMIN").roles("ADMIN")` principal into the security context for the ENTIRE request lifecycle — including all `/api/**` UI surfaces, not just `/ingestion/**`. The decision is structural for three reasons: (1) it commits S2S to "API-key authentication that complements interactive auth" rather than "API-key authentication for ingestion only" — the live `/enable-security/authentication/s2s` page corroborates ("complements any of the above" + "they can call any endpoint that admins can call"); (2) the four `*SecurityConfiguration` classes encode the composition rule identically across LOGIN_FORM/OAUTH2/LDAP and explicitly ABSENT under DISABLED — the pattern is intentional; (3) the consequence — an X-API-Key request inherits ADMIN across `/**` — is the maintainer's deliberate trade-off (a single shared-secret with broad scope, vs. per-endpoint API key scoping which would be a different architectural model). The trade-off is real and unwarned at the doc layer: REFACTOR-108 captures the gap where the documentation does not surface the cross-`/**` blast radius (operators reading "S2S for server-to-server clients" may assume `/ingestion/**` scoping).
  - **Wisdom test**: PASS. The cross-mode consistency (3-of-4 modes wire identically; 4th mode explicitly absent) is the intent anchor; structural for every future auth-architecture change. The live-doc statement "they can call any endpoint that admins can call" CONFIRMS the broad-scope-by-design intent. The trade-off (broad scope) is the maintainer's deliberate model — the gap (docs do not surface the implication) is REFACTOR-108.
