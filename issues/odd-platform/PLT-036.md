## What

Two DEG-read endpoints on the same platform return **opposite contracts** for the same semantic condition (DEG exists but has zero members):

- `GET /api/dataentitygroups/{id}/lineage` - raises **404 NotFoundException** (verified 2026-06-10 at `LineageServiceImpl.java:60-62`: `getDEGEntitiesOddrns(...).switchIfEmpty(Flux.error(new NotFoundException("Data entity group", dataEntityGroupId)))` - the source flux is empty both when the DEG id is unknown AND when it exists with zero member entities, so empty-DEG maps to 404).
- `GET /ingestion/entities/{degOddrn}/children` - returns **200 OK** with empty `CompactDataEntityList` (verified 2026-06-10). The controller `IngestionController.getDataEntitiesByDEGOddrn` (`IngestionController.java:76-78`) delegates to `dataEntityGroupService.listEntitiesWithinDEG`, which has **no** `switchIfEmpty`/error branch: it maps the (possibly empty) entity list straight into `new CompactDataEntityList().items(entityList)` (`DataEntityGroupServiceImpl.java:93-108`). An empty DEG yields `200` with `items: []`.

A collector author probing both with the same DEG ODDRN writes two different error-handling code paths. Reconciliation scripts face asymmetric error-handling on the two endpoints. The asymmetry IS the contract - but the contract is operator-debug-surprising and breaks the "same condition, same response" expectation that REST consumers carry.

## User-facing impact

API-contract defect, not a UI surface; "user" here is the API/collector consumer. Both contracts are code-settled (verified 2026-06-10): empty-DEG -> 404 on the lineage endpoint (`LineageServiceImpl.java:60-62`) and 200 + `items: []` on the membership endpoint (`DataEntityGroupServiceImpl.java:92-108`, no error branch). So a consumer that probes both with the same DEG ODDRN must write two different error-handling paths - the asymmetry is real and traceable in code.

What is not driven (would round-trip with consumers): whether any shipped collector actually depends on the 200-empty membership shape (the backward-compat question that decides Option A vs B). Remaining check: grep the collector repos for the membership endpoint usage (listed under Tests below); no such cross-repo sweep was run this session. There is no end-user UI consequence either way.

## Why

REST consumers (collector authors, third-party integrators, internal scripting) reasonably expect "same condition, same shape". When one endpoint returns 404 for empty and the sibling returns 200, callers must implement endpoint-specific dispatch logic - and they must DISCOVER the asymmetry, because no doc captures it.

The operator-debug-expectation is **empty -> 404** (matches the lineage endpoint's current behaviour). The lineage endpoint's 404 is doc-anchored - the live API reference doc treats empty-DEG as a not-found condition. The sibling membership endpoint's 200-empty is the outlier.

## How

Two options, each load-bearing:

**Option A (preferred) - align the membership endpoint to 404 on empty.** The membership endpoint's behaviour lives in `DataEntityGroupServiceImpl.listEntitiesWithinDEG` (`:92-108`), which maps `reactiveDataEntityRepository.getDEGEntities(degOddrn)`. Add an error branch so an empty/unknown DEG raises `NotFoundException`:

```java
// DataEntityGroupServiceImpl.listEntitiesWithinDEG
public Mono<CompactDataEntityList> listEntitiesWithinDEG(final String degOddrn) {
    return reactiveDataEntityRepository.getDEGEntities(degOddrn)
        .filter(list -> !list.isEmpty())                 // getDEGEntities returns the full list, so guard on emptiness
        .switchIfEmpty(Mono.error(new NotFoundException("Data entity group", degOddrn)))
        .map(entityList -> /* existing CompactDataEntity mapping */ ...)
        .map(entityList -> new CompactDataEntityList().items(entityList));
}
```

(`getDEGEntities` returns the whole entity list as a single emission, so the empty case is an empty list, not an empty `Flux` - guard with `.filter(list -> !list.isEmpty())` before `switchIfEmpty`. Exact placement vs the existing `.map` chain is an implementation detail.)

This breaks backward compatibility for any collector that depends on 200-empty (verify with a substrate scan: are there collector tests asserting 200 with empty items?). If yes, deprecation cycle: announce on the doc + ship a future-deprecation header + change the contract in the next major.

**Option B (less surgical) - align the lineage endpoint to 200-empty on empty.** Replace the `switchIfEmpty(Flux.error(NotFoundException))` with a `defaultIfEmpty(EmptyDataEntityGroupLineage)` that returns an empty graph. Operationally easier (no breaking change for membership consumers; the lineage endpoint's existing 404 callers will simply receive 200 with empty graph instead). Trade-off: the lineage endpoint's existing doc framing ("DEG not found -> 404") needs updating to disambiguate the three condition classes (DEG missing -> 404; DEG empty -> 200-empty; wrong entity type -> 400-validation).

Recommendation: **Option A** if collector backward-compat is acceptable (the user-debug-expectation is empty -> 404); **Option B** if backward-compat is strict.
