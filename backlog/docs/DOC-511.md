# DOC-511 — the housekeeping reference is one job and two keys behind, and the gap is the dangerous kind

## The gap

`docs/configuration-and-deployment/odd-platform.md` (housekeeping section) states:

> "…iterates through **five** cleanup tasks: resolved alerts, search-facet history, soft-deleted data
> entities, empty `activity` table partitions, and empty `message` table partitions. **The first three consume
> the `housekeeping.ttl.*` keys below**; the two partition reapers do not consume any TTL key"

Both counts are now wrong. `odd-platform-api/.../housekeeping/job/` holds **seven** `HousekeepingJob`
implementations (six jobs + the interface), including `RecentlyViewedHousekeepingJob`, and
`HousekeepingTTLProperties` declares **five** fields, not three:

```java
@ConfigurationProperties("housekeeping.ttl")
public class HousekeepingTTLProperties {
    private int resolvedAlertsDays;
    private int searchFacetsDays;
    private int dataEntityDeleteDays;
    private int recentlyViewedDays;          // documented NOWHERE in docs/**
    private int recentlyViewedMaxPerUser;    // documented NOWHERE in docs/**
}
```

`grep -rn "recently_viewed" docs/` returns **zero hits across the entire manual**. `application.yml` ships
`housekeeping.ttl.recently_viewed_days: 90` and `housekeeping.ttl.recently_viewed_max_per_user: 200`.

## Why this is more than a missing-coverage gap

The same page carries a `danger` admonition — correctly — about the primitive-`int` binding hazard:

> "**The Java-side default for every `housekeeping.ttl.*` key is `0`. A partial-override deployment silently
> wipes historical data on the next 15-minute cycle.** … the `HousekeepingTTLProperties` class declares the
> fields as `private int` with no field initialiser…"

and then gives the operator this remediation block to carry forward:

```yaml
  ttl:
    resolved_alerts_days: 30
    search_facets_days: 30
    data_entity_delete_days: 30
```

**Three keys. The class has five.** An operator who follows this page's own fix binds `recentlyViewedDays` and
`recentlyViewedMaxPerUser` to `0`. Read `RecentlyViewedHousekeepingJob.doHousekeeping` for what `0` does:

```java
deleteFrom(RECENTLY_VIEWED)
  .where(RECENTLY_VIEWED.LAST_VIEWED_AT.lessOrEqual(now().minusDays(getRecentlyViewedDays())))   // 0 -> cutoff = NOW
...
.where(ranked.field(rowNumber).greaterThan(maxPerUser))                                          // 0 -> rn > 0 = every row
```

- `recently_viewed_days: 0` → cutoff is **now**, so every row is deleted every cycle.
- `recently_viewed_max_per_user: 0` → `rn > 0` matches **every** row, deleting whatever the first pass left.

Result: the Recently Viewed feature is permanently empty on a 15-minute cycle, with no boot warning and
nothing above `log.debug`. The page's remediation for a silent-data-loss hazard *causes* the same hazard on a
feature the page never mentions — which is the `retrospectives/LSN-001` shape (a silent default that destroys
user data) reproduced through the documentation rather than the code.

## Fix direction

On the `release/1.0.0` train, in the housekeeping section:

1. **Five tasks → six**, and "the first three consume the `housekeeping.ttl.*` keys" → **five keys**.
2. **Add the two bullets**, matching the existing style:
   - `housekeeping.ttl.recently_viewed_days` — how many days a Recently-Viewed entry is kept past
     `last_viewed_at`. Integer, days. Defaults to `90`.
   - `housekeeping.ttl.recently_viewed_max_per_user` — the newest-N cap applied per user (per
     `oidc_username` + `provider`) after the TTL sweep. Integer. Defaults to `200`.
3. **Extend the danger admonition to all five keys** and state the specific `0` behaviour for these two — a
   `0` cap is not "no cap", it is "keep nothing", which is the counter-intuitive half.
4. **Fix the YAML block** so the copy-paste remediation carries all five keys. This is the load-bearing edit:
   the prose can be read past, the snippet gets pasted.
5. Cross-link the user-facing Recently Viewed surface so the retention behaviour is discoverable from the
   feature as well as the config reference (Cornerstone 3 — configuration is a separate audience surface).
