## Rejection

Rejected as a false positive (2026-06-10 sweep). The premise is inverted: `WithPermissions` (`shared/contexts/Permission/WithPermissions.tsx:28`) IS a synchronous render-gate that returns `null` on an absent permission; it consumes context via `usePermissions`, does not provide one, and has no loading/success/error branches and so cannot flash. There is no defect.

## What

**REJECT-CANDIDATE - the defect described below does not exist. The entire premise was a backend-style extrapolation that a single read of the component falsifies.**

The original draft claimed `WithPermissions` "is named like a render-gate but behaves as a permission-context provider" - that "ALL THREE branches render children; the wrapper is a context, not a gate," exposing permission state via a `PermissionContext.Provider` that descendants must consult defensively, with a child briefly flashing to unprivileged users before context hydration.

**Read of the actual component (verified 2026-06-10) shows the opposite: `WithPermissions` is a real, synchronous render-gate that returns `null` when the permission is absent.** It does NOT provide a context, has no loading/success/error branch, and does not flash the child. The described code does not exist anywhere in the file.

## Where

```
odd-platform-ui/src/components/shared/contexts/Permission/WithPermissions.tsx:11-32
  // const { hasAccessTo } = usePermissions();           // :17 - reads ancestor PermissionContext
  // if (renderContent)                                   // :19 - render-prop variant

  //   return hasAccessTo(permissionTo) && extraCheck ? <>{children}</> : null;
  // if (children)                                        // :27 - the common case
  //   return hasAccessTo(permissionTo) ? <>{children}</> : null;   // <- GATE: null when not allowed
  // return null;                                         // :31 - fail-closed default
```

Three corrections to the original draft, all load-bearing:

1. **Wrong path.** The component lives at `shared/contexts/Permission/WithPermissions.tsx`, NOT `shared/elements/WithPermissions/WithPermissions.tsx`. There is no `WithPermissions` directory under `elements/`.
2. **Wrong behaviour.** Every branch that has `children` returns `hasAccessTo(permissionTo) ? <>{children}</> : null` (`:24`, `:28`). When the permission is absent the wrapper renders `null` - the child is never mounted. This is a hard gate, not a passthrough.
3. **Wrong mechanism.** `WithPermissions` does NOT create a `PermissionContext.Provider`. It CONSUMES the context via `usePermissions()` (`lib/hooks/usePermissions.ts`), whose `getHasAccessTo` is supplied by an ancestor provider mounted once for the app. The permission set is resolved before `WithPermissions` renders, so there is no per-wrapper async window and no flash.

The PLT-034 corpus note ("a `WithPermissions` wrapper is a permission CONTEXT, NOT a hard render-block - verify it against the wrapper's implementation") is itself the trap: the implementation blocks children. The corpus note's framing was the hypothesis to falsify, and it is falsified.

## User-facing impact

None - there is no defect. Verified 2026-06-10 by reading the component end-to-end: a control wrapped in `<WithPermissions permissionTo={X}>` is rendered if and only if `hasAccessTo(X)` is true at render time; otherwise the wrapper returns `null` and nothing is mounted. No flash-of-gated-control path exists, because the permission set is consulted synchronously from already-resolved context rather than fetched per-wrapper. The "control briefly visible to unprivileged users" symptom the original draft asserted cannot occur via this component.

(Aside, not a defect: `AlertItem.tsx` in the global Alerts list takes a different, more conservative path - it does NOT wrap the Resolve button in `WithPermissions` at all; it dispatches `fetchResourcePermissions` on click and re-checks `DATA_ENTITY_ALERT_RESOLVE` before mutating, showing a "No access!" caption on denial - `AlertItem.tsx:48-70,158-166`. Per-entity `DataEntityAlertItem.tsx:111-120` DOES use the `WithPermissions` gate. Both are correct; neither leaks.)

## Why it matters

Nothing to fix. The original draft was a structural-defect claim built without reading the component. Keeping it open would burn maintainer time chasing a non-existent class of bug and risk a "fix" (Option B's fail-closed rewrite) that re-implements behaviour the component already has. Closing it is the correct outcome.

If a genuine flash-of-unauthorized-control is ever observed at a specific call site, that is a real finding - but it would belong to that call site's data-loading sequence, not to `WithPermissions`, which gates synchronously.
