  - **Proposed doc action**: **Three-part action**.
    1. **Doc-side primary — `configuration-and-deployment/odd-platform.md`** (or a new sub-page on "Cluster deployment" if scaled-out deployments warrant it): add a "Cluster deployment + session state" sub-section: "**On multi-instance deployments, ODD Platform's ingestion endpoint `/ingestion/datasources` requires session-state continuity between request hops.** The platform stamps the calling Collector's id into the WebSession on token validation; the controller reads it on the next hop. Under the default `session.provider: IN_MEMORY`, each platform instance has its own session store — without sticky sessions, the second hop lands on a different instance with no session, surfacing as HTTP 500 with body `\"Collector id is null\"` (not 401). **For HA deployments**: (a) enable sticky-session affinity on the load balancer / Service (e.g. Kubernetes Service.spec.sessionAffinity=ClientIP), OR (b) switch `session.provider` to `REDIS` (requires `redis.host/port/password` configuration) or `INTERNAL_POSTGRESQL` (uses the platform's existing Postgres connection). The `IN_MEMORY` default is appropriate for single-instance deployments only. **Diagnosis**: HTTP 500 with body `\"Collector id is null\"` on a previously-working collector login indicates session-state loss (not platform crash); check load-balancer affinity or switch the session provider." Mirror cross-link on `developer-guides/build-and-run/custom-collectors.md` (in the troubleshooting section).
    2. **Doc-side companion — `developer-guides/build-and-run/custom-collectors.md`**: add a "Cluster compatibility" caveat to the lifecycle description: "When deploying ODD Platform with multiple replicas, the `POST /ingestion/datasources` registration flow requires session-state continuity (cross-link the cluster-deployment sub-section above). Collectors that intermittently see 5xx errors after a successful initial registration are likely hitting different platform instances — verify session affinity or use a shared session store."
    3. **Code-side preferred long-term** (file `/log-issue odd-platform`): two ordered options. (a) **Minimum**: convert `IllegalStateException("Collector id is null")` to a typed exception that the global error handler maps to HTTP 401 with a clear body (e.g. `"Session lost; re-establish connection"`) — converts the cluster-deployment failure mode from "platform crash" to "session expired" (more diagnosable, more honest). (b) **Architectural**: replace the WebSession-attribute mechanism with a Spring Security `Authentication` object wrapping the matched Collector, pushed into `ReactiveSecurityContextHolder` by the filter and consumed via `Mono<Principal>` in the controller — eliminates the cluster-deployment session-state dependency entirely. Document the trade-off: the architectural fix breaks backward-compatibility for any external code depending on the session attribute (none observed in the substrate, but the audit is worth running before changing).
