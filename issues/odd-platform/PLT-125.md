## What

The `OWNER_CREATE` permission gate is **path-anchored** on `POST /api/owners` only, so the `OWNER` table is writable from three service-tier `getOrCreate` side-doors that never touch `/api/owners`. `OwnerServiceImpl.getOrCreate` is reached from `OwnerAssociationRequestServiceImpl` (via `POST /api/owner_association_request` — which is **not** in `SECURITY_RULES`, so it is reachable by **any authenticated user**), from `OwnershipServiceImpl` (gated only by `DATA_ENTITY_OWNERSHIP_CREATE`), and from `TermOwnershipServiceImpl` (gated only by `TERM_OWNERSHIP_CREATE`). A caller supplying a never-seen `ownerName` mints a new `OWNER` row **without holding `OWNER_CREATE`**, and it appears in `GET /api/owners` immediately. The `/permissions` doc tells operators `OWNER_CREATE` controls owner creation; three paths bypass it. The mint is also audit-silent (see PLT-062).

This is **distinct from PLT-101 / PLT-059**, which track the TERM and NAMESPACE `getOrCreate` side-doors. This is the OWNER-side side-door, not tracked by any code-side PLT (only as a doc-gap extension, DOC-262 → Owner side). It compounds with F-075 `DIRECT_OWNER_SYNC` self-mint-and-self-bind into a privilege chain.

## Impact

(1) Directory pollution: a caller holding only `DATA_ENTITY_OWNERSHIP_CREATE` — or merely authenticated, via the association-request POST — can spam the Owner directory with arbitrary names, none gated by `OWNER_CREATE`. (2) The `/permissions` doc is authoritatively wrong about what `OWNER_CREATE` controls. (3) Combined with audit-silence (PLT-062) and name-reuse, the side-door is a self-mint primitive in a privilege chain (compounds with F-075 `DIRECT_OWNER_SYNC` per SHB-087).

## Suggested fix

Per the reflection's `proposed_fix_anchor`: gate `OwnerServiceImpl.getOrCreate` at the service method (programmatic permission check), **or** document the side-door as intentional on `/permissions`. File as the Owner-side sibling of PLT-101 with the F-075 privilege-chain cross-link. Distinct from PLT-101 (TERM/NAMESPACE side-doors).
