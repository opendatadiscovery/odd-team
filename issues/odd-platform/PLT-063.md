## What

`PolicyServiceImpl.getCurrentUserPolicies` (`service/PolicyServiceImpl.java:103-107`) is invoked from `ManagementPermissionExtractor.java:33` + `AbstractContextualPermissionExtractor.java:28` on EVERY authorized HTTP request. Cost per call: 2 reactive DB roundtrips - `getCurrentUserRoles` -> `getUserRolesByOwner` (a **5-table** JOIN: ROLE, ROLE_TO_POLICY, POLICY, OWNER_TO_ROLE, USER_OWNER_MAPPING) at `ReactiveUserOwnerMappingRepositoryImpl:99-113`, then `getRolesPolicies` (a **2-table** JOIN: POLICY, ROLE_TO_POLICY) at `ReactivePolicyRepositoryImpl:28-39`. No request-scoped cache, no user-scoped cache (verified 2026-06-10: the only `@Cacheable`/Caffeine usage in `odd-platform-api/src/main` is `SlackMessageProviderClient`, unrelated to the auth path).

For a platform receiving N authenticated requests/sec, the authorization hot-path generates **~2N Postgres queries/sec** - over and above the application-logic queries.

## User-facing impact

Not directly user-visible - this is an operator/capacity-planning concern, and the **structure** is code-settled: every authorized request resolves permissions through `getCurrentUserPolicies`, which issues two uncached DB queries (a 5-table JOIN then a 2-table JOIN), verified by reading the call sites and both repository methods 2026-06-10. The cited per-second magnitudes ("~2N Postgres queries/sec", "500 req/s -> ~1000 extra queries/sec") are **arithmetic extrapolations**, not measured values - they assume one extractor invocation per request, but a request that triggers both a non-contextual and a contextual permission check would call `getCurrentUserPolicies` more than once (each context extractor calls it again), so the real multiplier can be **higher** than 2x on some endpoints. No load test or probe has measured the actual query rate or its contribution to pool contention. The defect (no cache on a per-request hot path) is real and code-settled; the runtime cost figure is a model, not an observation.

## Why it matters

Operators sizing the Postgres connection pool, JVM heap, or database CPU budget based on application-logic-only req/s underprovision the deployment. On a busy platform (500 req/s) this is ~1000 extra Postgres queries/sec from the auth hot-path alone; multiply for replicas. The structural per-request cost is invisible from request-path tracing - it shows up as Postgres contention or pool exhaustion that operators struggle to attribute.

## Suggested fix

**Option A - Spring `@Cacheable` with Caffeine (recommended).**

Add a Caffeine cache keyed on `(ownerId, requestId)` (or `(ownerId, sessionId)` if the request boundary is too aggressive). TTL ~30s for session-scoped; eviction on Policy/Role CRUD via `@CacheEvict`. The platform already uses Spring; minimal new dependency.

```java
@Cacheable(cacheNames = "currentUserPolicies", key = "#ownerId")
public Mono<List<Policy>> getCurrentUserPolicies(Long ownerId) { ... }

// Eviction:
@CacheEvict(cacheNames = "currentUserPolicies", allEntries = true)
public Mono<Void> create(PolicyFormData formData) { ... }
// repeat for update, delete, role-binding changes
```

**Option B - Request-scoped cache via Spring WebFlux context attribute.**

Store the resolved `List<Policy>` in the request context on first resolution; subsequent extractor calls in the same request read from the context. Tighter scope than Caffeine (no cross-request cache); no eviction needed. Slightly more invasive to plumb.

Recommended Option A for the simpler operator story + the wins from cross-request caching at session timescales.
