## What

The shared `ConfirmationDialog` (used by ~20 call sites across the UI — every "Are you sure?" destructive action) silently eats any rejection from its `onConfirm` promise. When the backend rejects the confirmed action (e.g. deleting a DataSource that is still actively ingested returns HTTP 400 from the cascade-block), the dialog's confirm handler resets the loading state and closes the modal **only in the `.then(...)` success branch**; the `.catch(() => {})` does nothing. The result is a modal that stays open with the confirm button stuck in its spinning/loading state, no inline error, and no way forward except reloading the page. Because the defect is in the shared component, every consumer inherits it — confirmed live on the three Management cascade-delete arms (Owner, Namespace, DataSource), which all render the same dialog.

## Where

`odd-platform-ui/src/components/shared/elements/ConfirmationDialog/ConfirmationDialog.tsx:24-35` — the confirm handler:

```tsx
const [isLoading, setIsLoading] = React.useState(false);
const onClose = (handleClose: () => void, action?: () => Promise<unknown>) => () => {
  if (action) {
    setIsLoading(true);
    action()
      .then(() => {
        setIsLoading(false);   // <- only path that clears the spinner
        handleClose();         // <- only path that closes the modal
      })
      .catch(() => {});        // :33 — rejection swallowed; isLoading stays true, modal stays open
  }
};
```

On a rejected `action()` neither `setIsLoading(false)` nor `handleClose()` runs, so the modal is left open with the confirm button locked in its loading state.

Shared-component consumers that inherit the defect include the three cascade-delete arms named in the source reflections:

```
odd-platform-ui/src/components/Management/DataSourcesList/DataSourceItem/DataSourceItem.tsx        (DataSource delete arm)
odd-platform-ui/src/components/Management/NamespaceList/EditableNamespaceItem/EditableNamespaceItem.tsx  (Namespace delete arm)
odd-platform-ui/src/components/Management/OwnersList/EditableOwnerItem/EditableOwnerItem.tsx        (Owner delete arm)
```

(plus Role, Policy, Tag, Collector, ownership-delete, attachment, lookup-table and query-example call sites — all import the same `ConfirmationDialog`.)

## Why it matters

This is a **loud-then-frozen** failure on the most destructive affordances in the product. The operator clicks Delete on a real cascade-protected resource, the backend correctly refuses (400), and instead of a comprehensible "cannot delete — still in use" message the operator gets a spinning button on a modal that will not close and will not retry. The only escape is a full page reload. Because the bug lives in the shared dialog rather than any one feature, it is not a single-screen polish issue — it degrades the failure UX of every confirm-and-mutate flow at once, and it does so precisely where the platform's guardrails (cascade-block, RBAC denial, optimistic-lock conflict) are working as designed. Severity high: it is the worst feedback on the highest-consequence actions, it affects many surfaces, and the recovery path (reload) risks the operator re-attempting a destructive action they believe failed.

## Suggested fix

Fix the shared component so a rejected `onConfirm` is recoverable: in the `.catch`, call `setIsLoading(false)` (so the spinner clears and the dialog is interactive again) and surface the error rather than discarding it — keep the modal open and render an inline error region, or rethrow so the caller's error-handling toast fires while the dialog stays usable. Do **not** leave `.catch(() => {})`. Open to alternatives on where the error string is rendered (inline in the dialog vs. the existing toast channel), but the spinner-reset on rejection is mandatory.
