## What

Four UX defects on the Catalog search surface that compound into "users with large catalogs lose facet options" + "routine browsing inflates the Popular ranking" + "keyboard-only users cannot reach result rows" + "double-navigate hazard on inner clickable children."

**Defect 1 - Filters.tsx silently truncates datasource + namespace facet options at 100 (F-017e).** `Search/Filters/Filters.tsx:31-34` hardcodes `dispatch(fetchDataSourcesList({ page: 1, size: 100 })); dispatch(fetchNamespaceList({ page: 1, size: 100 }));` in a mount-once `useEffect` (the dispatch calls are lines 32-33). Deployments with >100 datasources or namespaces silently lose options past index 100, with no "+N more" affordance, no pagination, no search-within-dropdown. (The two list endpoints already accept a `query` param - `DataSourceController.getDataSourceList(page, size, query)` and `NamespaceController.getNamespaceList(page, size, query)` - so the FE simply does not use the substring-search the backend offers.)

**Defect 2 - Result-row click is an entry point into the PLT-104 view_count loop; it is NOT a separate search-side write.** `ResultItem.tsx:42` computes `detailsLink = dataEntityDetailsPath(searchResult.id)` and `:72-76` mounts the entire row as `onClick={() => navigate(detailsLink)}`. `dataEntityDetailsPath(id)` defaults its path arg to `'overview'` (`routes/dataEntitiesRoutes.ts:66-73`), so the click navigates to `/dataentities/{id}/overview`. The `+2 view_count` is then written by the **destination** detail page, not by anything in the search code: the search row dispatches no view_count write at all (the FE never increments view_count anywhere - the counter is a backend side-effect of the `GET /api/dataentities/{id}` read, and the FE only renders `viewCount`). The doubling is `DataEntityDetails.tsx:56-64`'s `useEffect` firing twice (`details.status?.status` in the dependency array, line 63) - this is exactly the mechanism **PLT-104** owns and **probe P-004** pins (`final_view_count == 2` after one open). So this is the **same defect as PLT-104**, reached via a search-result click rather than any other navigation; search is one of many entry points (the home Popular strip, a lineage node, a bookmark all do the same). Fixing PLT-104's double-fetch closes this with no search-specific code change. Kept here only to record that the search surface is a high-traffic entry into that loop - not as an independent bug locus.

**Defect 3 - Result row has no a11y semantics; keyboard-only users cannot reach result rows (F-147b).** `ResultItem.tsx:72-76` renders the row as `<S.Container data-testid='search-result-item' container onClick={() => navigate(detailsLink)}>` - no `<a>` / `<button>`, no `tabindex`, no `role`, no `aria-label`, no `onKeyDown` for Enter/Space. Screen readers do not announce the row as actionable; keyboard navigation skips every result row. This is the genuine, search-local, code-settled defect of this cluster.

**Defect 4 - Clicking a tooltip-trigger icon inside the row navigates away (overstated as "double-navigate" in the original draft).** `ResultItem.tsx:87-90, :102-104, :106` mount `<MetadataStale>`, `<AppTooltip><QuestionIcon/></AppTooltip>`, and `<DataEntityDetailsPreview>` inside the row. Verified against the child components: `MetadataStale` (`StaleIcon` wrapped in `AppTooltip`) and `DataEntityDetailsPreview` (`InformationIcon` wrapped in `AppTooltip`) are **hover tooltips with no own click handler and no `stopPropagation`**. Consequence (corrected): a click on one of these icons has no competing handler, so it bubbles to the row `onClick` and navigates exactly **once** - there is no double-navigate and no doubled view_count write. The real (minor) defect is that clicking a tooltip-trigger icon - which a user may do expecting to pin/inspect the tooltip - unexpectedly navigates off the search page. Low-polish UX, not the duplicate-navigation hazard the original draft asserted.

## User-facing impact

Verified by tracing both ends (FE components + routing + the BE endpoints the fix relies on):

- **Defect 1 (Filters truncation) - HOLDS, code-settled.** `Filters.tsx:32-33` requests at most 100 datasources and 100 namespaces and renders `SingleFilterItem` straight off those arrays (`:47-61`); there is no pagination, no "+N more", no query input. An operator with >100 datasources (the standard collector matrix ships 40+ adapters; large estates exceed 100) or >100 namespaces silently cannot facet on anything past the first 100. The backend already supports the fix (`getDataSourceList`/`getNamespaceList` both take `query`). This is the strongest defect in the cluster.
- **Defect 3 (a11y) - HOLDS, code-settled.** The result row is a `<div>` (`S.Container`) with a bare `onClick` and no `<a>`/`<button>`/`role`/`tabindex`/`onKeyDown`; a keyboard-only or screen-reader user can run a search, see results, and have no way to open a row. WCAG 2.1.1. Search-local and real.
- **Defect 2 (view_count +2) - RUNTIME-CONFIRMED but NOT a search-side defect; it is PLT-104.** The search row only `navigate()`s to `/dataentities/{id}/overview`; the +2 is written by the destination detail page's double-fetch, which PLT-104 owns and probe P-004 (`lineage/odd-platform/probe-runs/2026-05-19-P-004.yaml`) measured (`final_view_count == 2` per open). No search-side write exists. Coordinate the fix with PLT-104; do not count it twice.
- **Defect 4 (tooltip-icon click) - PARTIALLY FALSIFIED.** The inner children are hover tooltips with no competing onClick, so a click bubbles to the row and navigates exactly once (one +2 via the PLT-104 path, not doubled). The corrected, milder defect: clicking a tooltip-trigger icon navigates off the page unexpectedly. Not driven at runtime; static trace of the child components.

Auth note: the search and detail surfaces are reachable under the shipped `auth.type=DISABLED` default (anonymous), so all four observations apply to the default deployment.

## Why it matters

- **Defect 1** turns the Filters sidebar from a precision tool into a 100-row sample for any operator running ODD in an enterprise (40+ data sources from the standard collector matrix; 50+ namespaces is common in multi-team deployments).
- **Defect 2** is one entry point into the F-001 / LSN-017 Popular-ranking inflation loop (PLT-104), not a distinct search-side write. Routine browsing from search reaches the detail page, which over-counts +2 per open. The Popular ranking becomes an artifact of how often pages are opened, not what operators value - but the fix lives in PLT-104 (the detail-page double-fetch), not here.
- **Defect 3** locks out keyboard-only operators from the search surface entirely - they can type a query, see the results render, and have no way to open a result without a mouse. WCAG 2.1.1 (Keyboard). This is the cluster's load-bearing search-local code fix.
- **Defect 4** (corrected) is a low-polish UX wart: clicking a tooltip-trigger icon navigates off the page. It does NOT double the view_count (no competing handler; a click bubbles to the row and navigates once).

Severity MEDIUM held (downgraded scope, not number): Defects 1 + 3 are real, search-local, code-settled defects and Defect 1 (facet truncation in any enterprise estate) plus Defect 3 (keyboard lock-out) justify medium on their own. Defect 2 is descoped to "entry point into PLT-104" and Defect 4 is descoped to a minor navigation wart - so the cluster's *independent* weight rests on 1 + 3.

## Suggested fix

### (a) Defect 1 - Paginate / search-within-dropdown the Filters sidebar

```tsx
// Filters.tsx - fetch on dropdown open with a debounced query input
const [dsQuery, setDsQuery] = useState('');
const dsQueryDebounced = useDebounce(dsQuery, 250);
useEffect(() => {
  dispatch(fetchDataSourcesList({ page: 1, size: 50, query: dsQueryDebounced }));
}, [dsQueryDebounced, dispatch]);
// (same for namespace)
```

Backend endpoints `/api/datasources` and `/api/namespaces` already accept `query` for substring matching; this is a one-component change.

### (b) Defect 2 - no search-side fix; close it in PLT-104

There is nothing to fix in the search code for Defect 2: the row click is navigation-only and writes no view_count. The +2 is the detail-page double-fetch (`DataEntityDetails.tsx:63` status-in-deps), which **PLT-104** already owns with the correct fix (remove `details.status?.status` from the dependency array / mount-once sentinel + server-side dedup). When PLT-104 lands, every navigation entry point - search included - writes at most +1. This sub-section is retained only to cross-link; do not duplicate the fix here.

### (c) Defect 3 - Semantic markup + keyboard handler

```tsx
// ResultItem.tsx:72-76
<S.Container
  container
  component="a"
  href={detailsLink}
  role="link"
  aria-label={`Open ${searchResult.dataEntity.externalName ?? searchResult.dataEntity.internalName}`}
  tabIndex={0}
  onClick={(e) => { e.preventDefault(); navigate(detailsLink); }}
  onKeyDown={(e) => { if (e.key === 'Enter' || e.key === ' ') { e.preventDefault(); navigate(detailsLink); } }}
>
```

Renders as a real `<a>` so middle-click / right-click / browser-bookmark behaviour works as expected. Same fix shape as the existing F-001 PopularStrip a11y backlog.

### (d) Defect 4 - Stop tooltip-icon clicks from navigating

The fix that falls out of (c): once the row is a real `<a>`/`role="link"` with an explicit handler, gate navigation on the event target - e.g. `if (e.target === e.currentTarget || rowBodyClicked(e)) navigate(detailsLink)` - or have the tooltip-trigger icons call `e.stopPropagation()` so a click that was meant to inspect a tooltip does not navigate. Note this is a minor UX wart, not a duplicate-navigation / double-count bug (the corrected analysis: the icons have no own onClick, so a click already navigates only once).
