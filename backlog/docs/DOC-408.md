## Description

The permission **read** surface that the UI uses to decide which buttons to show has two operator-relevant properties that the docs do not yet capture. DOC-243 (done) already documented the two-endpoint *orchestration* on `permissions.md` (a contextual call + a non-contextual call); this item adds the two consequences that orchestration leaves implicit.

1. **No unified "all my permissions" call — the client fans out per resource (N+1).** The `PermissionService` interface exposes exactly two read methods — `getResourcePermissionsForCurrentUser(resourceType, resourceId)` and `getNonContextualPermissionsForCurrentUser(resourceType)` (`PermissionService.java:8-11`). `PermissionController.getResourcePermissions(...)` returns the permissions for **one** `(resourceType, resourceId)` pair (`PermissionController.java:20-25`). There is no batch / "give me everything I can do across the catalog" endpoint, so a screen that renders N resources and wants the per-resource action set issues N calls. For an operator scripting against the API, or for anyone reasoning about UI latency on a busy listing page, this N+1 shape is non-obvious and worth stating — plus it is the natural anchor for a future batch-permissions REFACTOR candidate.

2. **Under `LOGIN_FORM` the answer these endpoints return is meaningless — every user is statically ADMIN.** `LoginFormSecurityConfiguration` builds every credential with `grantedAuthorityExtractor.getAuthorities(true)` i.e. `isAdmin=true` (`LoginFormSecurityConfiguration.java:81`; `GrantedAuthorityExtractor.java:12-17`), and the `LOGIN_FORM` chain is `.pathMatchers("/**").authenticated()` with no `SecurityConstants.SECURITY_RULES` wiring. So Policies/Roles an operator authors are stored but never gate the live chain — revoking a policy changes nothing a user can do under `LOGIN_FORM`. This consequence is already written up on `login-form.md` (the static-ADMIN / "do Policy testing on your production auth mode" caveat); DOC-408 only needs to **cross-link** it from `permissions.md` so a reader who lands on the permission model learns that the model is inert under `LOGIN_FORM`.

How it misleads: an operator reading `permissions.md` today could (a) assume a single "my permissions" call exists and design around it, and (b) test a revoked policy under a `LOGIN_FORM` dev instance, see the user still blocked-or-allowed as the static ADMIN, and draw the wrong conclusion about production `OAUTH2`/`LDAP` behaviour.
