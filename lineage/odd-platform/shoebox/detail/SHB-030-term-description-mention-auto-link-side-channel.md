# SHB-030 — `[[ns:term]]` description-mention syntax silently creates term-link rows, bypassing `DATA_ENTITY_ADD_TERM` permission

**Category**: merged
**Severity**: HIGH

## Hypothesis

Operators see two named permissions in the Business Glossary docs that gate term linkage: `DATA_ENTITY_ADD_TERM` (data-entity → term) and `DATASET_FIELD_ADD_TERM` (dataset-field → term). They reasonably assume those are the only paths that create `data_entity_to_term` / `dataset_field_to_term` rows. They are not. Any user with `DATA_ENTITY_DESCRIPTION_UPDATE` (the permission gating the description-edit endpoint) can plant `[[finance:Customer]]` syntax in a data-entity description; on save, the service-tier `TermServiceImpl.handleDataEntityDescriptionTerms` (lines 201-207) parses the description with the regex `\[\[([^:]*?):([^\]]*?)\]\]` (line 67), looks up matching terms via `termRepository.getByNameAndNamespace(List)`, and **INSERTs `data_entity_to_term` rows with `is_description_link = TRUE`** for every matched mention — bypassing `DATA_ENTITY_ADD_TERM` entirely. Worse, the cross-time variant: when a user CREATES term "Customer", `TermServiceImpl.createTerm` (lines 99-117) drains the `data_entity_description_unhandled_term` staging table via `resolveUnhandledDescriptionMentions` (lines 421-442) — instantly auto-linking the new term to data-entities whose descriptions were written days or weeks ago by users who never had `DATA_ENTITY_ADD_TERM` permission. The auto-linked rows surface in the data-entity's Terms section identically to manually-linked terms; operators viewing the catalog cannot tell the two apart without inspecting `is_description_link`. The Business Glossary docs (live `https://docs.opendatadiscovery.org/features/data-glossary/business-glossary`, verified 2026-05-19) describe term-mentions but do NOT describe the permission-bypass property.

## Notes

- **The cross-time aspect is the most surprising property**: a user creates term X today; the system silently materialises term-link rows from descriptions written months ago by OTHER users who never had `DATA_ENTITY_ADD_TERM`. The terms graph becomes "spontaneously dense" in ways the operator who created the term didn't intend or audit.
- **`is_description_link` flag is invisible in the UI** (per TermServiceImpl sidecar concepts.entities[7] + TermDetails sidecar bugs[4]): the read-side `removeDuplicateNonDescriptionTerms` (TermServiceImpl.java:444-448) actually PREFERS the description-link variant when both exist — so a manually-created term-link row is HIDDEN by an auto-created description-link row pointing at the same (entity, term) pair. Operators viewing the data-entity's Terms section see a single chip; they cannot tell if it's manual or auto.
- **Cross-namespace pollution amplifies**: `[[other-team-ns:Customer]]` in team-A's data-entity description silently links team-B's term into team-A's entity — without team-A having any permission on team-B's namespace. The Business Glossary docs claim "Searches and term-to-entity link operations resolve within the namespace by default" — but the auto-link path crosses namespace boundaries unrestricted (per TermController sidecar doc-drift[2]).
- **REFACTOR-227 / namespace side-channel cluster**: this thread sits alongside the `namespaceService.getOrCreate` side-door (TermServiceImpl.createTerm/updateTerm silently creates new namespaces via TERM_CREATE/TERM_UPDATE — per TermController sidecar bugs[6]) and the `tagService.getOrCreateTagsByName` side-door (TERM_TAGS_UPDATE silently creates tags — bugs[7]). Three side-channels in one service, same architectural class: "permission to author X side-doors permission to author Y."
- **F-002 enrichment, not new feature**: F-002 (Term-to-Entity Linkage) is the substrate anchor; this thread captures the auto-link permission-bypass axis F-002's current drift discussion mentions tangentially. Set `Category: open` because the cross-time / cross-namespace aspects are not yet anchored anywhere and warrant their own promotion candidate before merging.
- **F-004 intersection on payload**: per TermServiceImpl sidecar operations[3], the regex consumes the raw Markdown body — a `<script>` payload inside `[[ns:term]]` markers parses through the regex unchanged. The staging-table row's `term_name` / `term_namespace_name` columns hold the verbatim user input. This is the F-004 XSS family touching a different storage layer (the unhandled-mention staging table, not the data_entity.internal_description text column).
- guess: a probe creating a `[[ns:term]]` mention as a user holding ONLY `DATA_ENTITY_DESCRIPTION_UPDATE` (and NOT `DATA_ENTITY_ADD_TERM`), saving the description, then reading the data-entity's Terms section would surface the auto-linked term — proving the bypass.
