## Description

Live `/user-owner-association` lines 20-22 (verbatim): "In the [Management → Associations](../../../management.md) tab admin user will see your association request. Admin should approve request for finishing association process or deny it if there are any issues with current request."

Code reality (verified this session, `NewAssociationRequest.tsx:33-104` + `SecurityConstants.java:151-154`): the admin's workflow is a 3-tab UI (Pending / Active / History) with the Pending tab listing every PENDING `OwnerAssociationRequest`; per-row Accept / Reject buttons; both behind ConfirmationDialog. Backend write is `PUT /api/owner_association_request/{id}` with status APPROVED or DECLINED (gated by `OWNER_ASSOCIATION_MANAGE`). Per-row context: username / ownerName / role / provider only — no requester history, no requester-stated reason, no submission timestamp surfaced inline.

Operator-visible consequence: an admin reading the doc cannot orient to the Pending list, the per-row affordances, the ConfirmationDialog wording, or the limited context surfaced per row. They navigate by trial-and-error.
