## Description

The live Notifications page (WebFetched 2026-05-27) DOES disclose two of the substrate's nine drift facets — (a) WAL-driven outbound via PostgreSQL logical replication slot and (b) "SMTP timeouts are unset — an unreachable SMTP server will hang notification delivery." The other **seven** facets remain undocumented. Each is a load-bearing operator-visible footgun:

1. **Poison-message WAL replay loop (F-009a.1).** `NotificationSubscriber.java:77-91` has no try/catch around `messageProcessor.process()`. A persistent-bad ALERT row pins the LSN and blocks all subsequent delivery indefinitely. Operator sees notifications silently stop; no error surface; only diagnosis is reading Postgres logical replication state.
2. **Cross-channel abort when EmailNotificationSender wraps as RuntimeException (F-009a.2).** `EmailNotificationSender.java:58-60` wraps SMTP errors as RuntimeException, bypassing the dispatcher's `NotificationSenderException` catch. If email is first in iteration order and SMTP is failing, fan-out aborts for subsequent senders (Slack / webhook) — Slack channel silent, webhook silent, only email is "attempted".
3. **Empty-senders silent DB cost (F-009a.3).** The translator runs the recursive-CTE downstream-lineage walk on every WAL event even when zero notification channels are configured. Operators evaluating the platform on a small cluster see disproportionate DB load with no configured outbound channels.
4. **No idempotency / no DLQ / no audit on delivery (F-009a.4).** `PostgresWALMessageProcessor` SPI has void-return — the dispatcher cannot signal partial-failure / requires-replay. Failed deliveries are lost without trace; operators cannot diagnose which alerts were delivered to which channel without inspecting downstream channel state.
5. **PII passthrough to every channel (F-009a.5).** `dataEntity.owners[]` and `downstream` lineage entities flow verbatim to Slack/webhook/email — no redaction. Cross-team owner identities reach every configured notification channel.
6. **Slack mrkdwn injection via `AlertChunkPojo.description` (F-009a.6).** `SlackMessageGenerator.java:77, 95-101` renders operator-supplied / ingestion-supplied descriptions verbatim into Slack mrkdwn payload. `@channel`, `<https://attacker.example|click here>`, `<!here>` render in the Slack workspace as **broadcast notify + fake-link injection**. Combined with the F-007 AlertManager forge-and-display compound, a forged AlertManager webhook payload reaches every Slack channel with `@channel` broadcast. This is the load-bearing immediate-action item.
7. **Webhook signing absence (F-009a.7).** `WebhookNotificationSender.java:18-23` POSTs notifications with no `Authorization`, no `X-ODD-Signature`, no HMAC. Operator's receiver cannot verify the message came from their ODD Platform.
