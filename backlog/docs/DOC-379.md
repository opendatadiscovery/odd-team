## Description

The entity Overview → **Metadata** panel renders **two audiences of metadata in one undifferentiated list**: collector-ingested *predefined* (origin `EXTERNAL`) fields and operator-curated *custom* (origin `INTERNAL`) fields. The only thing that visually separates them at render time is that custom (INTERNAL) rows carry edit / copy / delete action buttons and predefined (EXTERNAL) rows do not — i.e. **only the custom side is edit-gated**. There is **no origin label, badge, or marker** rendered on either kind of row.

This produces two problems:

1. **Audience conflation / missing origin cue (the harvest finding).** An operator reading the panel cannot tell, at a glance, which facts came from the source system (collector-owned, refreshed every ingestion pass, will silently revert if hand-edited via the API) and which they authored themselves. The provenance only becomes inferable by noticing which rows have edit buttons — a cue that disappears entirely for a read-only user who has no edit permission on either kind.

2. **A doc-vs-code drift that this item must correct.** `data-discovery/custom-metadata.md` currently asserts an Origin badge exists: line 13 — "rendered side by side, **distinguished by the field's Origin badge**"; line 45 — "The UI distinguishes them with an **inline origin marker**." The shipping component renders no such badge or marker. `MetadataItem.tsx:75` reads `metadataItem.field.origin === 'INTERNAL'` **only** to decide whether to show the action buttons (`isCustom`); it does not render the origin anywhere in the row. So the doc tells an operator to look for an origin badge that is not on screen.

This item corrects `custom-metadata.md` to describe what is actually rendered (no origin label; provenance inferable only from the presence of edit affordances) and adds the operator-facing caveat that the two origins are conflated in one list — i.e. either documents the absence of an origin cue, or, if a UI origin cue is later added upstream, the doc is updated to match. DOC-189/190 cover custom metadata generally but not this audience-conflation / origin-cue facet, and neither flagged the inaccurate badge claim.
