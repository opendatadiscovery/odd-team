## What

`AuthIdentityProviderImpl` builds the per-request identity as a `(username, provider)` tuple, but the `provider` field is the OAuth2 client-registration id **only** for OAUTH2 - for LOGIN_FORM, LDAP, and S2S the else-branch hard-codes `provider=null` (`AuthIdentityProviderImpl.java:29-33`). Because every owner lookup keys on `OIDC_USERNAME=? AND PROVIDER IS NULL` for all non-OAUTH2 modes (`getConditions`, `ReactiveUserOwnerMappingRepositoryImpl.java:116-127`), two **genuinely different people** who share a username string across two non-OAUTH2 modes (a LOGIN_FORM `alice` and an LDAP `alice`) resolve to the **same** `OwnerPojo` - and therefore the same My Objects, My Alerts, owner-scoped mutations, and role bindings. On a LOGIN_FORM -> LDAP migration the LDAP `alice` lookup matches the pre-existing `(alice, null)` mapping and inherits its owner. (Note: this is the *resolver* collapsing the provider, not the DB index blocking a distinct mapping - the partial unique index is on `(oidc_username, provider)` and Postgres treats `provider = NULL` rows as distinct, so multiple active `(alice, null)` rows are actually allowed; in a concurrent multi-mode deployment where each `alice` has her own mapping, `getAssociatedOwner`'s single-row read then resolves to an arbitrary one.) The takeover is silent: no warning, no fail-fast, no log.

This is the **resolver root-cause** and is **distinct from PLT-065**, which fixes the *read-side* activity-feed JOIN sites (adding `AND PROVIDER=?` to 4 LEFT JOINs). The one-line resolver change at `AuthIdentityProviderImpl.java:32` closes the bleed at the source for all 15 `fetchAssociatedOwner` consumers; PLT-065's JOIN fix is complementary but does not address the resolver. The cross-mode DOC caveat is DOC-GAP-103 / DOC-272.

## Evidence

From the F-011 reflection (`lineage/odd-platform/feature-reflections/detail/F-011.yaml`), hypothesis H-001:

```
AuthIdentityProviderImpl.java:29-33
  // line 29: if (authentication instanceof OAuth2AuthenticationToken oauthToken)
  // line 30:   -> new UserDto(username, oauthToken.getAuthorizedClientRegistrationId())
  // line 32: else -> new UserDto(username, null)   for LOGIN_FORM / LDAP / S2S / DISABLED alike
  //   -> the resolver IS the fix-site

ReactiveUserOwnerMappingRepositoryImpl.java:116-127
  // getConditions: WHERE OIDC_USERNAME=? AND DELETED_AT IS NULL
  //   + (StringUtils.isNotEmpty(provider) ? PROVIDER=? : PROVIDER IS NULL)   // if/else, NOT an OR
  //   -> both non-OAUTH2 alices have provider=null, so both resolve via PROVIDER IS NULL

V0_0_89__update_user_owner.sql:13-15
  // CREATE UNIQUE INDEX user_owner_mapping_oidc_username_provider_deleted_key
  //   ON user_owner_mapping (oidc_username, provider) WHERE deleted_at IS NULL
  // Does NOT bound (alice, null) rows -- Postgres unique indexes treat NULLs as DISTINCT,
  //   so multiple active (alice, provider=null) rows are allowed. The takeover is the resolver
  //   matching the existing (alice, null) row, not the index forcing a shared mapping.
```

The whoami response (`IdentityServiceImpl.getAssociatedOwner`, `:36-51`) surfaces the resolved owner with no provenance signal, so a collision (an inherited owner) is indistinguishable from a correct resolution; the `.defaultIfEmpty(new OwnerPojo())` at `:38-39` separately masks the *no-mapping* case (it turns an empty lookup into a 200 with a null-id owner - see PLT-122), it is not what masks the collision.

## User-facing impact

WHO: a real person who authenticates under a non-OAUTH2 mode (LOGIN_FORM, LDAP, or S2S) whose username string collides with another non-OAUTH2 user. WHAT THEY GET: they resolve to the **same** `OwnerPojo` and therefore the same My Objects, My Alerts, owner-scoped mutations, role-granted permissions, and discussions as the colliding user.

- **The resolver collapse is verified by BE/schema trace 2026-06-10.** Non-OAUTH2 auth produces `provider=null` (`AuthIdentityProviderImpl.java:32`); `getConditions` keys the owner lookup on `PROVIDER IS NULL` for a null provider (`ReactiveUserOwnerMappingRepositoryImpl.java:121-125`); the unique index does not separate `(username, null)` rows (`V0_0_89:13-15`, Postgres NULL-distinct). So the lookup keyspace for every non-OAUTH2 user is `(username, NULL)`.
- **The observable takeover is static-trace consistent; not driven.** Confirming a real person lands on another's populated account requires a multi-mode deployment (a LOGIN_FORM -> LDAP migration, or concurrent LOGIN_FORM + LDAP with an overlapping username) - an RBAC/identity condition not observable under the default `auth.type=DISABLED`, so `user_facing_verified` stays false. The remaining check: stand up LDAP over an existing LOGIN_FORM mapping for the same username and confirm `whoami` / My Objects return the first user's owner.
- The `whoami` endpoint gives the operator no signal to detect this: it returns the resolved owner with no provenance, so an inherited owner looks identical to a correct resolution (`IdentityServiceImpl.java:36-51`).

This is a confidentiality / least-privilege boundary failure, not a cosmetic bug.

## Suggested fix

Per the reflection's `proposed_fix_anchor`: at `AuthIdentityProviderImpl.java:31-32`, emit distinct provider literals (`"LOGIN_FORM"` / `"LDAP"` / `"S2S"` / `"DISABLED"`) instead of `null` in the else-branch. Existing `(username, null)` rows stay and the DB partial unique index naturally segregates new mappings. Pair with PLT-065's read-side JOIN fix. Confirmatory probe P-227 is emitted to pin the end-to-end bleed.

**Corrected 2026-06-10 (user-facing verification sweep).** The resolver collapse (provider=null for non-OAUTH2; `getConditions` resolves on `PROVIDER IS NULL`) is verified and the finding survives, but two evidence claims were wrong: (1) `getConditions` was described as `AND (PROVIDER=? OR PROVIDER IS NULL)`; it is actually an if/else (`PROVIDER=?` when a provider is present, else `PROVIDER IS NULL`) - both non-OAUTH2 alices hit the `PROVIDER IS NULL` branch. (2) The partial unique index was claimed to "enforce at-most-one active (username=alice, provider=null) row" so "the LDAP alice cannot get a distinct mapping"; in fact the index is on `(oidc_username, provider)` and Postgres treats `NULL` providers as distinct, so multiple `(alice, null)` rows ARE allowed - the takeover is the resolver matching the existing `(alice, null)` row (migration case) or `getAssociatedOwner` arbitrarily picking one of several (concurrent case), not the index forcing a shared mapping. The `IdentityServiceImpl:38-39 defaultIfEmpty` was also re-scoped: it masks the no-mapping case (PLT-122), not the collision.

Related existing items (deliberately NOT duplicated): **PLT-065** (read-side activity-feed JOIN fix - complementary, distinct fix-site), **DOC-GAP-103 / DOC-272** (cross-mode DOC caveat).
