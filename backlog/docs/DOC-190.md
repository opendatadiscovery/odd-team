## Description

The live `tagging.md` page (WebFetched 2026-05-27, 200 OK) covers TAG_CREATE/UPDATE/DELETE + the `TAG_ASSIGNMENT_UPDATED` activity event. The page is **silent on three load-bearing operator-visible behaviours**:

**Caveat 1 — `listMostPopular` returns OLDEST-by-id, not most-popular (F-018a; LSN-019 canonical).** `ReactiveTagRepositoryImpl.java:147-148` calls `paginate(homogeneousQuery, List.of(new OrderByField(TAG.ID, SortOrder.ASC)), (page - 1) * size, size)` — the inner pagination orders by `TAG.ID ASC` BEFORE the COUNT aggregation. The outer `cteSelect.orderBy(field(COUNT_FIELD).desc())` at line 158 only re-ranks within the already-truncated window. The maintainer's empirical test (LSN-019:23-32, 2026-05-20): 35 tags all equally popular, size=30 → response = 30 OLDEST by `tag.id` ASC; 5 youngest absent despite equal usage. The OpenAPI spec at `openapi.yaml:344-346` describes `getPopularTagList` as "sorted by popularity". The "Top Tags" Catalog Overview tile and the Tag-facet search seed are both consumers — both render OLDEST tags. The method name + spec promise are the operator-facing contract; the implementation cannot satisfy it without an SQL restructure (PLT-026).

**Caveat 2 — Five side-channel mints into the global Tag directory (F-018b; REFACTOR-223 + DOC-GAP-168).** `TAG_CREATE` is the documented write path but is **one of five**:
  1. `POST /api/tags` (TAG_CREATE) — the documented path.
  2. `setDataEntityTags` (DATA_ENTITY_TAGS_UPDATE) — `DataEntityController` chain.
  3. `createTermTagsRelations` (TERM_TAGS_UPDATE) — `TermController` chain; `SecurityConstants.java:185-186`.
  4. `updateDatasetFieldTags` (DATASET_FIELD_TAGS_UPDATE) — `DatasetFieldController` chain; `SecurityConstants.java:288-290`.
  5. `ExternalTagIngestionRequestProcessor` (collector-ingested) — no auth at this layer.

Each side-channel calls `TagServiceImpl.getOrCreateTagsByName:80-86, 144-159` which silently creates new tag rows for novel names. An operator restricting `TAG_CREATE` to "vocabulary stewards" discovers that any user with per-entity tag-update on a single entity mints arbitrary new tag names visible to every user via `GET /api/tags`. The Top-Tags UI surface inflates with un-stewarded entries; the Tag-facet search becomes polluted.

**Caveat 3 — Three-way activity-audit asymmetry across the three tag-assign endpoints (F-018c).** Three nominally-symmetric tag-assign surfaces have THREE different audit-log behaviours:
  - `DataEntityServiceImpl.upsertTags:358` — `@ActivityLog` with `dataEntityId` only (no diff payload).
  - `DatasetFieldServiceImpl.updateDatasetFieldTags:117-132` — `@ActivityLog DATASET_FIELD_TAGS_UPDATED` with full before/after.
  - `TermServiceImpl.upsertTags:254-264` — no `@ActivityLog`.

An auditor querying activity for a term's tag changes finds nothing; for an entity, finds an event with no payload diff; for a dataset-field, finds full diff. The audit-log surface for tag operations is non-uniform; building "who changed which tags when" reports requires three different decoders.
