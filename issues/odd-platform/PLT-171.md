## What

The notification sender that delivers alerts to a configured **webhook** (and Slack) accepts **only HTTP 200** as success. Any other 2xx status — `201 Created`, `202 Accepted`, `204 No Content` — is treated as a failed delivery and the sender throws. `202 Accepted` in particular is the conventional response from an **async-accept** receiver (a queue/relay that acknowledges receipt and processes the payload later); against such a receiver every ODD alert is recorded as a delivery failure even though the receiver accepted it. The alert is then dropped on the floor.

## Where

`odd-platform-api/src/main/java/.../notification/sender/AbstractNotificationSender.java:26`

```java
if (response.statusCode() != HttpStatus.OK.value()) {
    throw new NotificationSenderException(
        "Notification sender response didn't complete with 200 status code", receiverId());
}
```

`HttpStatus.OK.value()` is exactly `200`. The check is an exact-equality test, so `201`/`202`/`204` all fall into the `!=` branch and raise `NotificationSenderException`. This `sendAndValidate(...)` method is the shared delivery primitive for the concrete webhook/Slack senders that extend `AbstractNotificationSender`.

## Why it matters

Alert delivery is the load-bearing operator surface for on-call paging and incident response. The failure is **silent to the operator**: a receiver that legitimately returns `202 Accepted` (an async relay, an API gateway, a serverless function that enqueues and returns immediately) makes every alert look failed on the ODD side, and the alert never reaches the operator's downstream channel. There is no status-code negotiation and no way for an operator to opt their receiver's `2xx` contract in. An operator who validated their webhook against a simple `200`-returning endpoint will not discover the gap until a real incident, when the alert that should have paged them is dropped because their production receiver answers `202`. Severity is medium: it is a reliability defect on the alerting path (not a security or data-loss issue on its own), but it can silently disable an entire alert channel for a class of standards-compliant receivers.

## Suggested fix

Accept the full `2xx` range as success rather than exact `200`:

```java
if (!HttpStatus.valueOf(response.statusCode()).is2xxSuccessful()) {
    throw new NotificationSenderException(
        "Notification sender response didn't complete with a 2xx status code", receiverId());
}
```

This treats `200`/`201`/`202`/`204` uniformly as accepted while still failing on `3xx`/`4xx`/`5xx`. (Open to alternatives — e.g. an explicit per-receiver list of acceptable codes — but the `is2xxSuccessful()` widening is the minimal correct change and matches HTTP semantics for an accept-and-forward receiver.)

**How to verify:** a receiver returning `202` (or `201`/`204`) is treated as a successful delivery — a unit test on the sender asserting no `NotificationSenderException` for a 202 response.

## How discovered

Surfaced during a product-owner review of the WAL-driven notification-delivery flow ("are non-200 2xx responses honoured?"); confirmed by reading `AbstractNotificationSender`. Scope note: this is only the delivery success-status-code check — broader notification hardening (signing, idempotency, dead-lettering) is a separate concern.
