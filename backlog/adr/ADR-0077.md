# ADR-0077: Retire flat index/mirror files — graph + retriever is navigation

## Status
ACCEPTED + IMPLEMENTED (2026-06-04). All reducer contracts cleaned, the dedup playbook +
registry-search retired, and the 4 dead index mirrors deleted (see table). Formalises a
decision already partly in force since rev-7.1 / 2026-05-26 (next-batch SKILL had stopped
index maintenance; the reducer contracts had not been cleaned up to match — this ADR finished that).

## Context
Reducer subagents each maintain a flat `index.yaml` mirror of their per-node detail files
(`feature-reflections/index.yaml`, `test-map/index.yaml`, the `registry-shard` outputs).
**These mirrors grow unboundedly and duplicate what the derived ontology graph already holds**
with embedded descriptions. They are the bloat-prone navigation layer the maintainer called out.

`adrs/drafts/agentic-graph-retriever.md` already established that the **graph-retriever**
(`/retrieve` → `graph-search`/`graph-node`/`graph-neighbours`/`graph-traverse`) supersedes the
grep-over-sharded-registry approach. The derived graph is deterministically rebuilt from the
canonical per-node detail files via `lineage-extractor graph-build {repo}` (git-ignored, never
committed). Navigation is: detail file → embedded in graph → found by the retriever.

## Decision
No reducer maintains a flat index/mirror file. The **per-node detail files are the sole durable
artefacts**; the **graph + retriever is the access path**; the **graph rebuild** (`graph-build`)
is the post-batch "make-navigable" step (NOT index regeneration).

## Consequences
- Smaller, non-bloating substrate; the graph is the single queryable index.
- The "refresh navigation after a batch" step becomes `graph-build`, not index regeneration.
- `registry-search` (dedup helper) is replaced by spawning the graph-retriever with a
  dedup-shaped query (already noted in the /retrieve skill).
- Any tooling that READ an index (e.g. methodology-reviewer overview) switches to graph queries.
