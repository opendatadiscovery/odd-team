- **REFACTOR-390** (NEW 2026-05-19O): GitHub Enterprise Server (GHES) is structurally incompatible — `GithubUserHandler.java:39` hard-codes `WebClient.create("https://api.github.com")`; no `@Value` injection, no operator-property knob, no GHES API base URL config field on `ODDOAuth2Properties.OAuth2Provider`. A GHES deployment with API at `https://github.example.com/api/v3` is silently locked out
  - **Category**: hard-coded-path
  - **Surfaced by**:
    - `GithubUserHandler.md:bugs_limitations_corner_cases.[1]` (MEDIUM)
    - `GithubUserHandler.md:docs_link_semantic.doc_drift_findings.[1]` (MEDIUM doc-vs-code)
  - **Statement**: The platform's GitHub OAuth2 user-enrichment handler is bound EXCLUSIVELY to `api.github.com` via a field-initialised singleton WebClient at `GithubUserHandler.java:39`. The `GithubCondition` only checks `provider=github` (the literal string), so a GHES operator who sets `auth.oauth2.client.github.provider: github` + `issuer-uri: https://github.example.com/api/v3` will (i) successfully boot, (ii) successfully authenticate against GHES for the `/oauth2/authorize` + `/oauth2/access_token` flow (Spring's `ClientRegistration` uses the issuer-uri), then (iii) FAIL at user-enrichment because this handler's `WebClient` is hard-coded to api.github.com. The user sees a login error with DNS or TLS-certificate-mismatch underlying cause. The live OAuth2/OIDC docs (WebFetched 2026-05-19 status 200) describe GitHub provider configuration without flagging the GHES incompatibility.
  - **Evidence**: `GithubUserHandler.java:39` (`private final WebClient webClient = WebClient.create("https://api.github.com");` — field initializer, no constructor injection) + `ODDOAuth2Properties.java:31-53` (no `apiBaseUrl` / `apiUri` field on OAuth2Provider POJO) + WebFetch `/configuration-and-deployment/enable-security/authentication/oauth2-oidc` 2026-05-19 status 200 (silent on GHES)
  - **Existing-ADR-or-implied-prescription**: ADR-CANDIDATE-135 NEW (GitHub OAuth2-non-OIDC + two-pass HTTP) — the two-pass HTTP architecture commits the platform to api.github.com only; ADR-CANDIDATE-035 NEW does not defend this gap. The gap is a configuration-surface omission: the maintainer DID NOT add an operator-configurable endpoint when the hardcoded URL was first written. There is no comment defending the choice; no commit message naming GHES as out-of-scope.
  - **Proposed remedy**: Add `apiBaseUrl: String` to `ODDOAuth2Properties.OAuth2Provider` (default `https://api.github.com`). Wire via constructor injection: `this.webClient = WebClient.create(StringUtils.defaultIfEmpty(provider.getApiBaseUrl(), "https://api.github.com"));`. Update live docs to document the field for GHES operators. The fix is one Properties field + one constructor change + one doc update — strictly within existing structure (refactoring, NOT structural change).
  - **Severity rationale**: HIGH — an entire class of GitHub operator (GHES users) is silently locked out. The symptom is operator-debug-hostile (DNS / certificate errors at api.github.com when the operator is at github.example.com). GHES is the dominant GitHub deployment shape for enterprise environments — the gap excludes a major user segment.
  - **Suggested backlog grouping**: `OAuth2 hardening sprint` (paired with REFACTOR-391/392/393/394 GitHub-handler-family gaps + DOC-NNN to flag GHES support in live docs)
