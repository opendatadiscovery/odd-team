## What

odd-platform exposes a Prometheus scrape endpoint (`/actuator/prometheus` is enabled by default), but it publishes **no metrics for the R2DBC connection pool** - there is no gauge for connections acquired (in use), allocated (total in the pool), or pending (callers waiting to acquire). The R2DBC pool is hand-built in `R2DBCConfiguration` and that configuration never registers a Micrometer `MeterBinder` for the pool, so operators cannot see pool utilisation, cannot tell how close the platform is to the pool ceiling, and cannot alert on connection-acquire backpressure. On a reactive platform whose entire DB access goes through this pool, the single most important saturation signal is therefore invisible on the dashboards the platform otherwise feeds.

## Where

`config/R2DBCConfiguration.java` - the class builds and returns `io.r2dbc.pool.ConnectionPool` beans (`connectionFactory`, `R2DBCConfiguration.java:27-52`; the secondary `customConnectionPool`, `:54-87`) and the matching `DatabaseClient`/`ReactiveTransactionManager` beans, but registers **no** `MeterBinder` and never binds the pool's metrics to a `MeterRegistry`. The pool is constructed straight from `ConnectionPoolConfiguration.builder(...)` with no metrics hook:

```java
@Bean(destroyMethod = "dispose")
@Primary
public ConnectionPool connectionFactory(final DataSourceProperties dataSourceProperties,
                                        final R2dbcProperties properties) {
    ...
    return new ConnectionPool(builder.build());   // no MeterBinder, no metricsRecorder
}
```

(The `ConnectionPoolConfiguration.Builder` is configured for sizing/timeouts only - `maxSize`, `maxIdleTime`, etc. at `R2DBCConfiguration.java:41-50` - never for metrics.)

`application.yml:226-257` confirms the scrape endpoint is live but pool-less:

```yaml
management:
  endpoints:
    enabled-by-default: false
    web:
      exposure:
        include: health, prometheus, env, info
  endpoint:
    ...
    prometheus:
      enabled: true
```

So `/actuator/prometheus` is exposed and scrapeable, yet no `r2dbc_pool_*` series appears because nothing binds the pool to the registry.

## Why it matters

This is a **silent observability gap** on the platform's primary saturation point. R2DBC pool exhaustion manifests as request latency and acquire-timeout errors, but without an acquired/allocated/pending gauge an operator cannot see it coming, cannot size the pool from evidence, and cannot build an alert on "pending acquisitions rising" - they only learn of saturation after requests start failing. This compounds a known sizing hazard: the framework default pool ceiling is small and one `R2dbcProperties.Pool` feeds two pools, so per-replica connection use can be higher than operators expect (tracked separately as the F-120 R2DBC pool-sizing caveat / DOC-249 extension). Affected: every production deployment scraping Prometheus, i.e. the standard observability setup. Severity is medium - no data loss or security exposure - but for a reactive, DB-bound service the missing pool gauge is a meaningful operability hole that turns a diagnosable capacity problem into an after-the-fact incident.

## Suggested fix

Bind the R2DBC pool's metrics to Micrometer so `/actuator/prometheus` exposes acquired/allocated/pending gauges:

1. Register a `MeterBinder` for each `ConnectionPool` (the primary and the `customConnectionPool`) against the application `MeterRegistry`, exposing the pool's `PoolMetrics` (acquired / allocated / idle / pending / max-allocated) as gauges. `io.r2dbc.pool.ConnectionPool#getMetrics()` returns the `PoolMetrics` to publish.
2. Name the series predictably (e.g. `r2dbc.pool.*` with a pool-name tag) so the primary and custom pools are distinguishable on the dashboard.
3. Verify the new series appear on a live `/actuator/prometheus` scrape after the change. Open to alternatives on the binding approach (a dedicated `@Bean MeterBinder` vs binding inline where the pool is created).
