## What

`PermissionServiceImpl.java:47-48` throws `IllegalArgumentException("No extractor for resource type %s".formatted(resourceType))` when a new `PolicyTypeDto` value with `hasContext=true` is added without a corresponding `ContextualPermissionExtractor` bean. `ControllerAdvice.java:23-66` has NO `@ExceptionHandler` for `IllegalArgumentException`. The exception falls through to the catch-all and surfaces as HTTP 500 with body `"Internal Server Error"`.

Same shape as batch-2 F-007b / Policy JSON validator finding (IllegalArgumentException → 500 instead of 400). This is a CLASS issue — `IllegalArgumentException` is a common-enough JVM idiom that not handling it is a regression vector for every new feature that uses it as a guard.

## Where

| File | Lines | Role |
|------|-------|------|
| `odd-platform-api/src/main/java/.../service/permission/PermissionServiceImpl.java` | 47-48 | The IllegalArgumentException source |
| `odd-platform-api/src/main/java/.../controller/exception/ControllerAdvice.java` | 23-66 | Catch-all coverage — no IllegalArgumentException handler |

## Why it matters

Maintainer adding a new resource type AND forgetting the extractor sees HTTP 500 not the descriptive HTTP 400 — confusing diagnostic; misleads on-call who reads "Internal Server Error" as a platform crash instead of a config gap. Class-wide fix benefits F-006 + F-090 + future cases (anywhere in the codebase that uses IllegalArgumentException as a validation guard).

## Suggested fix

Add a class-wide @ExceptionHandler:

```java
// ControllerAdvice.java
@ExceptionHandler(IllegalArgumentException.class)
public Mono<ResponseEntity<ProblemDetails>> handleIllegalArgument(IllegalArgumentException ex) {
    log.warn("IllegalArgumentException at request boundary: {}", ex.getMessage());
    ProblemDetails problem = new ProblemDetails()
        .code("USR400")
        .message(ex.getMessage());
    return Mono.just(ResponseEntity.status(HttpStatus.BAD_REQUEST).body(problem));
}
```

Verify the contract with existing IllegalArgumentException-throwing paths — particularly the Policy JSON validator (batch-2 F-007b) — that the mapping to HTTP 400 is the operator-correct semantic.

Alternative: be more selective — wrap each known IllegalArgumentException-throwing branch with a `BadUserRequestException` so the existing handler in ControllerAdvice fires. Less Spring-idiomatic but more explicit.

Recommended: the class-wide handler — minimum-code-change + future-proofs against new IllegalArgumentException paths.
