## Description

The Data Quality dashboard renders two labelled "Clear" buttons — one for the tables block, one for the tests block — and the operator expects each to clear only its own side (F-104 / H-009, verdict `confirmed`). The two writer atoms in `DataQualityStore.ts` encode that independence:

- `clearTableFiltersAtom` (`DataQualityStore.ts:44-54`) spreads `currentFilters` and resets ONLY the five table-side keys: `deNamespaceIds`, `deDatasourceIds`, `deOwnerIds`, `deTitleIds`, `deTagIds` — leaving the five test-side keys untouched.
- `clearTestFiltersAtom` (`DataQualityStore.ts:56-66`) spreads `currentFilters` and resets ONLY the five test-side keys: `namespaceIds`, `datasourceIds`, `ownerIds`, `titleIds`, `tagIds`.

The independence is asserted nowhere. A future refactor that accidentally reset both sides (e.g. dropping the `...currentFilters` spread, or wiring one button to the wrong atom) would silently wipe the operator's selections on the other block — operator-visible, and currently unguarded (`DataQualityStore.md` lists it under uncovered behaviours).

**Typed gate: validates-feature** (LSN-029). The hypothesis was `confirmed` against the source, so this is a happy-path regression test that asserts the CORRECT current behaviour (the two-Clear independence promise), not a known-bug pin. It is GREEN today and stays GREEN; it goes RED only if a regression breaks the side-isolation. This item also carries the small misc RTL/jotai store-test guards opened against F-127 (fold any cheap store-level assertions for the same DataQuality filter atoms here rather than minting a separate item).
